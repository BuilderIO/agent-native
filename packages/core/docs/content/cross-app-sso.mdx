# Cross-App SSO

The browser-facing "Sign in with Agent-Native" option and automatic browser
handoff are removed. Normal per-app sign-in is the default for web users. This
page describes the remaining explicit Desktop and server-side federation
contracts.

<!-- i18n-copy-ignore: Agent-Native is a proper name. -->

<Callout tone="info">

If all apps share one origin, a shared cookie domain already provides shared
login. No federation is needed.

</Callout>

## What remains

### Packaged Desktop workspace

Workspace sign-in is an explicit action in Desktop Settings. When enabled,
Desktop can provision eligible registered apps through its dedicated broker.
Each target app still owns its local user store, session, and access checks.
Desktop does not intercept anonymous browser navigation to an app sign-in page.

An app is eligible only when all of these are true:

- Desktop enables workspace SSO for the app.
- The production URL is exact HTTPS.
- Dispatch has an exact server-side registration for the app.
- The <code>desktop.workspace-sso</code> rollout flag is enabled.

The per-device <code>desktopSsoEnabled</code> preference is enabled by default.
An explicit false remains an opt-out. If the flag, preference, registration, or
eligibility check is unavailable, ordinary per-app sign-in remains available.

### Server-side federation

The remaining broker and server-side callers use a short-lived,
server-verified protocol. It is not exposed as a browser login control.

1. The caller requests an exact registered app binding.
2. Dispatch authenticates the workspace identity and returns a short-lived,
   one-time authorization code.
3. The target app server redeems the code with its PKCE verifier.
4. The target app verifies the signed assertion, exact app binding, callback,
   scope, nonce, and expiry.
5. The target app links or creates a local user by verified email and mints its
   normal local session.

The assertion is returned only through the server-to-server exchange. It never
appears in a browser URL and it is not a reusable bearer token.

## Organization federation

The <code>organization.cross-app-federation</code> flag is off by default. When
enabled, the source app registers its local organization with Dispatch and
stores the exact <code>(identity_authority, identity_id)</code> mapping. A
target app accepts the canonical organization ID, name, and verified membership
role only from the server-verified assertion.

Organization names, email domains, and browser cookies are not join keys. An
existing local organization without a mapping remains unchanged until an
explicit migration links it. Linked memberships continue to use the target
app's normal access checks.

Organization federation uses a separate credential for each registered source
app:

- Set <code>AGENT_NATIVE_IDENTITY_FEDERATION_SECRET</code> on the source app.
- Set the matching <code>AGENT*NATIVE_IDENTITY_FEDERATION_SECRET*&lt;NORMALIZED_APP_ID&gt;</code>
  on Dispatch.
- Do not reuse <code>A2A_SECRET</code> for this authority boundary.

The app ID suffix replaces every run of non-alphanumeric characters with an
underscore and uppercases the result. For example, the app ID

<code>workspace-reports</code> uses
<code>AGENT_NATIVE_IDENTITY_FEDERATION_SECRET_WORKSPACE_REPORTS</code>.

Identity and organization writes are additive. Existing same-email users are
reused without modification. A new verified email creates a local user.
Disabling federation does not delete users, organizations, memberships, or
credentials.

## Configuration

<code>AGENT_NATIVE_IDENTITY_HUB_URL</code> is used only by the remaining
server-side and Desktop path when a self-hosted app needs an explicit Dispatch
deployment. It does not add a browser login option or automatic browser handoff.

For a self-hosted Dispatch deployment, register every custom app with its
exact app ID, client ID, HTTPS origin, callback path, and

<code>identity-sso</code> capability through
<code>IDENTITY_SSO_APP_REGISTRY_JSON</code>. An example registration is:

```bash
IDENTITY_SSO_APP_REGISTRY_JSON='[{"appId":"workspace-reports","clientId":"workspace-reports","origin":"https://reports.example.com","callbackPath":"/_agent-native/identity/callback","capabilities":["identity-sso"]}]'
```

Production registrations must use HTTPS and an exact callback path. Localhost
is allowed only for local development. Unknown subdomains, mismatched app IDs,
arbitrary paths, and cross-origin callbacks are rejected.

## Security contract

- One-time codes and PKCE prevent a code from being replayed by another
  client.
- The signed assertion is server-only, short-lived, and scoped to identity.
- Exact app, origin, client, and callback checks prevent token exfiltration.
- Verified email is the only local user join key.
- Exact organization ID is the only organization join key.
- Per-app federation credentials prevent one app from minting another app's
  organization identity.
- Identity and organization writes never rename, repoint, or delete existing
  data.

## Verification and rollback

After deployment:

1. Verify that normal email, password, magic-link, and configured provider
   sign-in continue to work in a browser.
2. Verify that the browser auth surface has no Agent-Native sign-in option.
3. If Desktop workspace SSO is enabled, verify one exact registered app from
   the explicit Desktop Settings action.
4. If organization federation is enabled, verify the exact organization ID
   and membership role in the target app.

To roll back the remaining server-side or Desktop path, disable the relevant
feature flag and remove <code>AGENT_NATIVE_IDENTITY_HUB_URL</code> from a
self-hosted deployment, then redeploy. The additive identity and organization
records remain available for ordinary local auth.
