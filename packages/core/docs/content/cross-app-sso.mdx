# Cross-App SSO

Each hosted app at `*.agent-native.com` runs its own deployment with its **own separate user store**. `mail.agent-native.com` and `calendar.agent-native.com` do not share a database, a session table, or a cookie domain. So "sign in once, use every app" cannot be a shared cookie — it has to be **identity federation**, with [Dispatch](/docs/dispatch) acting as the identity authority for the workspace.

The browser flow uses a short-lived authorization code with PKCE. Dispatch
returns the `A2A_SECRET`-signed identity assertion only through a server-to-server
exchange, so a reusable JWT never appears in a browser URL.

<Callout tone="info">

**Unified deploy vs. per-domain deploy.** If you host all apps at one origin (`your-agents.com/mail`, `your-agents.com/calendar`), you already get shared login via a single cookie domain — no federation needed. Cross-App SSO is only necessary when apps run on separate domains. See [Multi-App Workspaces — Unified deploy](/docs/multi-app-workspace#deployment).

</Callout>

## What the user sees {#user-flow}

Cross-App SSO should feel like moving between products in one workspace, not
creating a second account. For example:

1. Sign in to [Dispatch](https://dispatch.agent-native.com), or to any app
   that already uses the workspace identity.
2. Open [Mail](https://mail.agent-native.com), [Calendar](https://calendar.agent-native.com),
   or another enabled app in a new tab.
3. The app sends the browser to Dispatch only if it does not already have a
   Dispatch session. If the session exists, the redirect is effectively
   invisible.
4. Return to the app already signed in, with the same email, records, and org
   context as before.

The important distinction is that this is **one sign-in, not one shared
cookie**. Each separately hosted app still creates and owns its own local
session. Dispatch proves the user's identity at the app's front door, and the
app then continues with its normal local auth and access checks.

The packaged Desktop Canary is deliberately more explicit: it never intercepts
anonymous app sign-in navigation. The user chooses workspace sign-in once in
Desktop Settings; Desktop then provisions every currently eligible registered
app and lazily provisions a later eligible webview. Ordinary app sign-in remains
the default path when that action is not chosen or the flag is unavailable.

For a product walkthrough, record this exact sequence: sign in once in
Dispatch, open two other hosted apps, show that neither asks for credentials,
then sign out of one app and show that the other app's session is independent.
That last step makes the security boundary visible: SSO removes repeated
logins without turning every app into one shared session store.

## What & why {#what-why}

Per-app user stores mean there is no single place a browser cookie could live that every app trusts. The federation model instead names one app — **Dispatch** — as the identity authority. Any other app can delegate "who is this person?" to Dispatch, get back a short-lived signed assertion of the user's verified email, and then **link that to its own local account by email**.

The linking rule is deliberately narrow and additive:

- **Existing same-email user → linked.** The local account is matched by verified email and reused as-is. It is **never modified, renamed, or deleted** — the federation layer only ever reads it and mints a session for it.
- **New email → created.** A fresh local account is created for that verified email, then a normal local session is minted.

This makes the rollout safe even though it logs people out. **Logout is expected.** When an app turns this on, existing sessions end and users re-authenticate through Dispatch. But they always log back into the **same email-matched account, with all their data intact**, because identity rows are only ever _added to_ — never destroyed, renamed, or repointed.

2. **Dispatch authenticates the human.** If the user already has a Dispatch session, this is transparent. If not, Dispatch shows its own normal login (email/password, Google, etc. — see [Authentication](/docs/authentication)). Dispatch is just a regular agent-native app here; it is not running a special auth mode.

3. **Dispatch → App (code, then server exchange).** Dispatch validates the
   exact app registration and 302-redirects back with a short-lived,
   one-time **authorization code**. The app server immediately posts that code,
   the original state, and its PKCE verifier to
   `/_agent-native/identity/token`. Dispatch atomically consumes the code and
   returns the short-lived `A2A_SECRET`-signed identity assertion in that
   server-to-server response. The browser never receives the assertion. Its
   claims are intentionally minimal:

   | Claim        | Meaning                                                  |
   | ------------ | -------------------------------------------------------- |
   | `sub`        | Stable user id at the identity authority                 |
   | `email`      | The user's **verified** email — the only join key        |
   | `name`       | Display name (non-authoritative, for UI only)            |
   | `org_domain` | Workspace/org domain, when present                       |
   | `scope`      | Always `"identity"` — this token authorizes sign-in only |
   | `exp`        | **≤ 2 minutes** from issue                               |

4. **App verifies and JIT-links by email.** The app's callback verifies the
   server-to-server assertion with its own `A2A_SECRET`, checks the exact
   authority, client, callback, `scope: "identity"`, `jti`, and `exp`, then
   performs **just-in-time linking strictly by verified email**:
   - If a local user with that email exists → reuse it unchanged.
   - If not → create a local user for that email.

5. **App mints a normal local session.** From here on the user has an ordinary local session in that app's own store — every existing access check, org scoping, and action guard works exactly as before. The federation only happened at the front door.

### Opting in {#opt-in}

An app's ordinary web sign-in participates **only** when this environment variable is set on its deployment:

```bash
AGENT_NATIVE_IDENTITY_HUB_URL=https://dispatch.agent-native.com
```

- **Set** → the app shows a **"Sign in with Agent-Native"** option that runs the flow above. Direct local login (email/password, Google) still works alongside it.
- **Unset (default)** → **zero behavior change.** The app authenticates exactly as it did before; the federation code path is dormant. There is no schema change and nothing to migrate, so flipping the variable on or off is fully reversible at any time.

## Security {#security}

The whole model rests on a few deliberately small guarantees:

- **One-time code + PKCE.** The browser carries only a short-lived,
  single-use authorization code. The callback-scoped HttpOnly verifier cookie,
  exact app binding, and atomic code consumption prevent a stolen redirect from
  being redeemed by another client.
- **Server-only signed assertion.** The identity assertion is an
  `A2A_SECRET`-signed JWT with a **≤ 2-minute** expiry and `scope: "identity"`.
  It is returned only from the server-to-server token exchange and is never
  placed in a browser URL.
- **Strict app-bound `redirect_uri` allowlist.** Every canonical app ID maps to one exact production origin and callback path; localhost remains available for development. Unknown subdomains, mismatched app IDs, arbitrary paths, scheme-relative (`//host`), and cross-origin targets are rejected, so the authority can't become a token-exfiltration oracle.
- **Email-only join from a verified assertion.** The _only_ identity attribute
  that crosses the trust boundary is the verified email. The app does not
  accept a user id, role, org membership, or any privileged state from the
  wire — it derives everything locally from the matched account.
- **Additive-only identity writes.** Linking either reuses an existing same-email account untouched or inserts a new one. No update, rename, repoint, or delete of identity rows ever happens on this path.
- **Off by default.** With `AGENT_NATIVE_IDENTITY_HUB_URL` unset, ordinary browser federation is inert. The separately gated packaged Desktop path is described below.

**Safe to enable, safe to revert.** Identity writes are **additive only** — an existing same-email account is reused untouched, and a new email just inserts a fresh row. There is no schema change and nothing to migrate, so flipping `AGENT_NATIVE_IDENTITY_HUB_URL` on or off is fully reversible at any time, per app.

</Callout>

## Packaged Desktop workspace {#desktop-workspace}

The signed Agent Native Desktop SSO Canary uses this same federation flow as the
ordinary sign-in front door for canonical first-party apps. A dedicated
Electron partition holds the Dispatch authority session; each target app still
mints its own local session, and Desktop transfers only that app's allowlisted
session cookie into its isolated `persist:app-<id>` partition. One explicit
Settings action provisions every currently eligible app; a later eligible
webview is provisioned lazily when it loads. Arbitrary third-party sites remain
isolated. A custom workspace app is eligible only when Desktop config sets
`workspaceSso: true`, the production URL is exact HTTPS, and Dispatch has an
exact server-side registration.

Dispatch registers the default-off `desktop.workspace-sso` rollout flag. The
flag controls whether Desktop may begin the ceremony; it does not authorize a
user or weaken nonce, signature, origin, callback, app-binding, cookie,
revocation, or credential-custody checks. With the flag Off or unavailable,
Desktop leaves ordinary per-app sign-in, sign-out, and Settings unchanged.
Canonical hosted apps recognize the packaged Desktop request without requiring
`AGENT_NATIVE_IDENTITY_HUB_URL` on every deployment; ordinary web browsers and
self-hosted apps still require that explicit configuration.
Stable Desktop builds do not initialize the broker until a later release is
separately approved.
The Canary user-agent marker is an availability hint, not remote attestation;
the server cannot infer code signature from HTTP. No authentication or
authorization decision trusts it. Supervised acceptance therefore binds the
tested client through the signed artifact's exact commit, manifest, hashes, and
notarization evidence.

## Self-hosting {#self-hosting}

Any Dispatch deployment can serve as the identity hub — you are not limited to `dispatch.agent-native.com`. Set `AGENT_NATIVE_IDENTITY_HUB_URL` on each client app to point at your Dispatch instance:

```bash
AGENT_NATIVE_IDENTITY_HUB_URL=https://dispatch.yourcompany.com
```

**Redirect allowlist.** The hub (Dispatch) validates `redirect_uri` on the authorize endpoint before issuing a code. The allowlist is configured in `templates/dispatch/server/lib/identity-sso.ts`:

- **Default:** exact registered Agent Native app ID, client ID, origin, and callback pairs (`CANONICAL_IDENTITY_SSO_APP_ORIGINS`).
- **Custom workspace apps:** set `IDENTITY_SSO_APP_REGISTRY_JSON` on Dispatch with exact registrations. Every entry must include the app ID, client ID, exact HTTPS origin, fixed callback path, and `identity-sso` capability:

  ```bash
  IDENTITY_SSO_APP_REGISTRY_JSON='[{"appId":"workspace-reports","clientId":"workspace-reports","origin":"https://reports.yourcompany.com","callbackPath":"/_agent-native/identity/callback","capabilities":["identity-sso"]}]'
  ```

- **Localhost** is allowed only for local development, with the exact callback path and app/client binding. Remote HTTP hubs and custom origins are rejected; production must use HTTPS.

Without an exact custom registry entry, a self-hosted Dispatch can only issue codes to the canonical registered app origins.

## Canary rollout runbook {#canary-rollout}

Cutover and rollback are **a single environment variable per app deployment**. Roll out one app at a time, verify, then expand. Do not set the variable on every app at once.

**1. Deploy the code — no behavior change.**
Ship the release to every app with `AGENT_NATIVE_IDENTITY_HUB_URL` **unset everywhere**. Confirm normal logins still work on a couple of apps.

**2. Enable the canary on ONE app at a time.**
Set, on one deployment only:

```bash
AGENT_NATIVE_IDENTITY_HUB_URL=https://dispatch.agent-native.com
```

Leave every other app's environment unset. Redeploy/restart so it picks up the variable.

**3. Verify the canary (checklist).**

- Log **out** of the app.
- The login screen now shows **"Sign in with Agent-Native"**. Click it.
- You are taken to **Dispatch** and complete its login (or pass straight through if already signed in there).
- You are redirected **back to the app, logged in** — and it is the **same pre-existing account** (same email) you had before, not a new one.
- **App data is intact** — your existing records, settings, and org scoping are exactly as they were.
- **Existing direct logins still work** — email/password and Google sign-in continue to function alongside SSO.

If any check fails, go straight to step 4 (rollback) — it is instant and data-safe.

**4. Expand app-by-app.**
Once one app is verified, repeat steps 2–3 for the next app — setting `AGENT_NATIVE_IDENTITY_HUB_URL` on one deployment at a time. Never batch-enable.

**5. Rollback = unset the env var on that app's deploy.**
To revert any app, **remove `AGENT_NATIVE_IDENTITY_HUB_URL` from that app's environment and redeploy/restart it.** The app immediately returns to its prior auth behavior. There is **no data change to undo** — identity rows were only ever added, and unsetting the variable simply makes the federation path dormant again. Each app's cutover and rollback are independent and reversible.

<Callout tone="info">

Rollout logs users out as each app is enabled (they re-auth via Dispatch), but they always log back into the **same email-matched account with data intact**, because identity rows are never destroyed or renamed — only added.

</Callout>
