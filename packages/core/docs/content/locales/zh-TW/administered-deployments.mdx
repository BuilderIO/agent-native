# 管理式部署

若單一組織營運內部應用程式，請使用工作區。組織是成員與資料界線。工作區彙整一或多個應用程式的部署設定。

## 關閉註冊與組織建立

```dotenv
AUTH_SIGNUP=invited
ORG_CREATION=closed
AUTO_CREATE_DEFAULT_ORG=0
AUTH_BOOTSTRAP_ADMINS=admin@example.com
AUTH_REQUIRE_EMAIL_VERIFICATION=1
```

設定 `AUTH_SIGNUP=invited` 後，新帳戶必須有待處理邀請、已驗證且允許的電子郵件網域，或列於 `AUTH_BOOTSTRAP_ADMINS` 的地址。密碼、魔法連結和社交註冊都會檢查。依網域加入不是邀請，也不會指派應用程式角色。

第一位登入的引導管理員會建立標準組織並成為擁有者。如果已有一個組織，管理員會加入並成為擁有者。如果有多個組織，系統不會自行選擇。接著在 Team settings 設定允許的網域並邀請團隊。

當 `ORG_CREATION=closed` 時，組織建立會被拒絕，直到 `AUTH_BOOTSTRAP_ADMINS` 中列出至少一位已驗證的管理員，該管理員會在首次登入時建立標準組織。

## 公司金鑰與角色

組織擁有者或管理員可以儲存組織範圍的 LLM 金鑰。個人金鑰會優先，直到成員選擇使用組織金鑰。應用程式角色只適用於單一應用程式，成員可擁有多個角色。管理員可將程式碼宣告的權限對應至角色，且不必重新部署即可調整。

## 變更電子郵件與身分

使用者驗證新地址後，可在帳戶設定中變更登入電子郵件。管理員遷移時，每個應用程式都執行一次 `agent-native identity rekey --from old@example.com --to new@example.com`。使用 `--yes` 前請先檢查資料表與列數。既有稽核紀錄不會更改。不可變主體 ID 遷移規劃於 1.0 之後進行。

## 組織 SSO 與目錄佈建

組織 SSO 和 SCIM 是選用功能。設定 `AUTH_SSO=1` 和 `AUTH_SCIM=1` 後，Team settings 會顯示管理控制項。請在建置環境和執行環境中同時設定這些變數；部署後變更需要重新建置。先設定組織的電子郵件網域。OIDC 需要 issuer、client ID 和 client secret。SAML 需要 IdP entry point、entity ID，並貼上 metadata XML。設定頁會顯示 redirect URI 和 SP metadata。使用頁面顯示的值建立 `_better-auth-token-<provider-id>.<organization-domain>` DNS TXT 記錄，等待 DNS 傳播後驗證網域。驗證後，管理員可要求成員使用 Google 或已驗證的 SSO 提供者登入。建立 SCIM 連線後，將僅顯示一次的 token 和 endpoint 設定至身分提供者。在 Okta 或 Microsoft Entra ID 中建立 OIDC 或 SAML 企業應用程式並設定 SCIM client。先以小型群組測試建立、更新和停用使用者，再擴大範圍。這與應用程式間身分聯合不同。

伺服器操作應使用 `accessFilter()` 和 `assertAccess()`。Agent SQL 使用暫存篩選檢視。`pnpm guards` 包含無範圍查詢檢查。RLS 目前不是實際執行層，規劃作為 1.0 之後的強化措施。多個內部應用程式適合使用工作區；獨立工具或原型則適合使用獨立應用程式。請參閱[獨立應用程式還是工作區](/docs/multi-app-workspace#standalone-or-workspace)與[版本與穩定性](/docs/versioning-and-stability)。
