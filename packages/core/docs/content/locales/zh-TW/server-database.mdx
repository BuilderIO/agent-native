# 資料庫

每個 Agent-Native 應用都將其狀態儲存在 PostgreSQL 中。UI 與 agent 都透過同一組 actions，使用同一個 [Drizzle ORM](https://orm.drizzle.team) 用戶端，讀寫相同的資料表。即時同步使用 SSE，並以輪詢作為備援，因此不需手動重新整理，變更就會顯示在另一端。

## 託管選項 {#hosting}

應用程式使用 PostgreSQL。當 `DATABASE_URL` 未設定時，會使用本機 PGlite，讓您無需設定即可開始開發。

### 預設：PGlite 檔案 {#default-pglite}

當 `DATABASE_URL` 未設定時，應用會在 `data/pglite` 建立一個 PGlite 資料庫。無需任何設定。啟動開發伺服器後，該檔案會在第一次執行時建立。

這僅適用於本機開發。容器、無伺服器函式與預覽環境可能會在重啟之間重設其檔案系統，因此本機 PGlite 檔案可能會消失。部署前請將 `DATABASE_URL` 設定為持久化的託管 PostgreSQL 資料庫。

### 本機 Postgres：PGlite {#local-pglite}

若要在不使用 Docker 或託管資料庫的情況下於本機開發 PostgreSQL，請安裝選用的 PGlite 套件並設定 `DATABASE_URL`：

```bash
pnpm add @electric-sql/pglite@^0.5.8
```

```bash
DATABASE_URL=pglite:./data/pglite
```

[PGlite](https://pglite.dev/) 在行程內執行一個 WASM 版本的 Postgres 資料庫。它讓您能在部署前就抓到僅限 Postgres 的架構問題,同時維持與 PGlite 預設值一樣簡單的設定方式。和 PGlite 一樣，它僅是本機儲存,請勿用於正式環境或共用環境。

### 正式環境資料庫 {#production}

在 `.env` 檔案或部署提供者的環境變數中設定 `DATABASE_URL`，以連線託管 PostgreSQL 資料庫：

```bash
# Neon Postgres 資料庫
DATABASE_URL=postgres://user:pass@ep-cool-name-123456.us-east-2.aws.neon.tech/mydb?sslmode=require

# Supabase Postgres 資料庫
DATABASE_URL=postgres://postgres.xxxx:pass@aws-0-us-east-1.pooler.supabase.com:6543/postgres

# 普通 Postgres 資料庫
DATABASE_URL=postgres://user:pass@localhost:5432/mydb

DATABASE_URL=pglite:./data/pglite
```

框架會根據 `DATABASE_URL` 將 Drizzle 設定為使用 PostgreSQL。

### Builder.io 託管資料庫 {#builder-managed}

*計畫中（尚不可用）：*連線到 Builder.io 後，您的應用將能使用自動佈建的託管 PostgreSQL 資料庫，無需任何 PostgreSQL 連線字串。

## 設定資料庫 {#setup}

使用資料庫的應用需要三個檔案：

- `server/db/schema.ts`：資料表定義
- `server/db/index.ts`：具型別的資料庫用戶端單例
- `server/plugins/db.ts`：本機啟動時執行的應用程式自有遷移

### 1. 定義您的架構 {#schema}

從 `@agent-native/core/db/schema` 匯入架構幫手。框架幫手會產生適用於 PostgreSQL 和 PGlite 的定義。

```ts filename="server/db/schema.ts"
import { integer, now, table, text } from "@agent-native/core/db/schema";

export const tasks = table("tasks", {
  id: text("id").primaryKey(),
  title: text("title").notNull(),
  priority: integer("priority").notNull().default(0),
  done: integer("done", { mode: "boolean" }).notNull().default(false),
  ownerEmail: text("owner_email").notNull(),
  createdAt: text("created_at").notNull().default(now()),
});
```

| 幫手      | 目的                                                                   |
| --------- | ---------------------------------------------------------------------- |
| `table`   | 定義一個資料表，使用 PostgreSQL 幫手                                   |
| `text`    | 文字欄，支援 `{ enum: [...] }`                                         |
| `integer` | 整數欄，`{ mode: "boolean" }` 對應到 Postgres 的布林值                 |
| `real`    | 浮點欄。在 PGlite 上對應 `real`，在 Postgres 上對應 `double precision` |
| `now`     | 為 `.default(now())` 設定目前時間戳                                    |

### 2. 建立資料庫用戶端 {#db-client}

每個應用透過呼叫 `createGetDb(schema)` 來建立一個惰性的單例 Drizzle 用戶端。規範位置是 `server/db/index.ts`：

```ts filename="server/db/index.ts"
import { createGetDb } from "@agent-native/core/db";
import * as schema from "./schema.js";

export const getDb = createGetDb(schema);
```

`createGetDb` 回傳一個 `getDb()` 函式，會在第一次呼叫時開啟 PostgreSQL 連線，並在後續呼叫時回傳同一個具型別的 Drizzle 實例。它會讀取 `DATABASE_URL`，連線至託管 PostgreSQL 或本機 PGlite。

在 actions 與路由中，從這個範本本機路徑匯入 `getDb`。不要直接從 `@agent-native/core` 匯入。核心匯出是無型別的；本機匯出則帶有您的架構型別。

`runMigrations` 會依序執行每個待處理項目一次，將其記錄為已套用，之後的
執行會跳過它。請為新的項目提供穩定的 `name`；具名遷移會獨立於版本號追蹤。

  Chat 範本提供 `pnpm migrate:production`，用於在發佈步驟執行遷移。
</Callout>

### 使用 Drizzle Kit 產生新的應用程式遷移 {#drizzle-migrations}

對於新的應用程式架構變更，請使用 `pnpm db:generate` 產生可供審查的 SQL。
這會建立 `server/db/migrations/<id_name>.sql`，並由
`runDrizzleMigrations` 在 Node.js 與以 Node 為基礎的 serverless runtime 中將
這些檔案載入共用的 Agent-Native runner。正式環境的變更仍由發佈步驟負責。
PostgreSQL 專用 SQL、Postgres 行為、資料回填與延遲的 JavaScript 步驟，請繼續使用
`runMigrations()`。

以檔案系統為基礎的 loader 不適用於 Cloudflare Workers/Pages 或其他沒有可部署
檔案系統的 edge runtime。在這些環境中，請使用嵌入 worker bundle 的 PostgreSQL migration 項目
呼叫 `runMigrations()`。請針對 PostgreSQL 產生遷移，不要在同一資料夾中切換本機 PGlite
與託管 PostgreSQL。

<Callout tone="risk">
  切勿針對正式環境資料庫執行 `drizzle-kit
  push`。範本架構僅定義特定於應用程式的資料表；它們不包含中央框架資料表（`user`、`session`、`application_state`
  等）。若針對正式環境執行 `drizzle-kit
  push`，會將這些資料表偵測為「不在架構中」並嘗試刪除它們，造成立即的資料遺失。
</Callout>

每個應用根目錄下的 `drizzle.config.ts` 會為本機開發時的 PostgreSQL 架構檢視設定 drizzle-kit。請明確設定 PostgreSQL 資料庫，例如 `createDrizzleConfig({ dialect: "postgresql" })`：

```ts filename="drizzle.config.ts"
import { createDrizzleConfig } from "@agent-native/core/db/drizzle-config";
export default createDrizzleConfig();
```

使用 `pnpm db:generate` 檢視您的架構，並僅針對本機資料庫使用 `pnpm db:push`。

### 4. 在 actions 中查詢 {#querying}

從您的 actions 中呼叫 `getDb()` 以取得具型別的 Drizzle 用戶端。使用 Drizzle 的查詢建構器與 `drizzle-orm` 中的可移植運算子：

```ts
import { and, desc, eq } from "drizzle-orm";
import { getDb } from "../server/db/index.js";
import * as schema from "../server/db/schema.js";

const db = getDb();

const openTasks = await db
  .select()
  .from(schema.tasks)
  .where(
    and(eq(schema.tasks.ownerEmail, userEmail), eq(schema.tasks.done, false)),
  )
  .orderBy(desc(schema.tasks.createdAt));

await db
  .update(schema.tasks)
  .set({ done: true })
  .where(eq(schema.tasks.id, taskId));
```

## 將資料範圍限定給使用者 {#scoping}

所有針對面向使用者資料表的讀寫，都必須限定在經驗證的使用者範圍內。框架依資料是私有還是可共用，提供兩種模式。

**私有資料：**屬於單一使用者的資料表。在架構中加入 `ownerEmail: text("owner_email").notNull()`，並在每個查詢中包含 `eq(table.ownerEmail, userEmail)`：

```ts
.where(eq(schema.tasks.ownerEmail, userEmail))
```

**共用資源：**可與其他使用者或組織共用的資料表。請在架構中展開 `...ownableColumns()`，而不是單純的 `owner_email`。這會在一次呼叫中新增 `owner_email`、`org_id` 和 `visibility`，並用 `createSharesTable` 建立一個對應的分享資料表：

```ts filename="server/db/schema.ts"
import {
  table,
  text,
  ownableColumns,
  createSharesTable,
} from "@agent-native/core/db/schema";

export const decks = table("decks", {
  id: text("id").primaryKey(),
  title: text("title").notNull(),
  ...ownableColumns(),
});
export const deckShares = createSharesTable("deck_shares");
```

接著在列表查詢中使用 `@agent-native/core/sharing` 中的 `accessFilter`，取代手動的 `eq` 檢查：

```ts
import { accessFilter } from "@agent-native/core/sharing";

const rows = await db
  .select()
  .from(schema.decks)
  .where(accessFilter(schema.decks, schema.deckShares));
```

`accessFilter` 建構的查詢會納入呼叫者擁有的行、與其組織共用的行,以及明確與其分享的行。它不會暴露其他使用者的行。

完整模型請參閱 [Security — 資料範圍限定](/docs/security#data-scoping) 與 [Sharing](/docs/sharing#building)。

## 由 SQL 支援的同步 {#sync}

Agent-Native 不仰賴檔案系統監看器或黏著式的記憶體內狀態。當某個 action 寫入資料庫時，一個同步版本號會遞增。用戶端的 `useDbSync()` hook 會輪詢 `/_agent-native/poll`，當偵測到更高的版本號時，使 React Query 快取失效。

由於資料庫是協調點，這在無伺服器與多實例部署間都能運作。若您在 actions 之外撰寫自訂的變更操作，請使用框架幫手，或發出對應的同步失效通知，讓開啟中的 UI 得以重新整理。

## 原始 PostgreSQL {#raw-sql}

對於 Drizzle 查詢建構器無法表達的進階查詢、健康檢查或一次性維護作業，請使用 `@agent-native/core/db` 中的 `getDbExec`：

```ts
import { getDbExec } from "@agent-native/core/db";

const { rows } = await getDbExec().execute({
  sql: `SELECT id, title FROM tasks WHERE owner_email = ? LIMIT ?`,
  args: [userEmail, 50],
});
```

`getDbExec` 會自動將 `?` 參數轉換成 Postgres 的 `$1`、`$2` 等格式。一般讀寫請優先選用 Drizzle 查詢建構器；原始 SQL 會繞過型別安全，也更難維護。
