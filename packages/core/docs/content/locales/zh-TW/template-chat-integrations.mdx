# 多應用工作區中的聊天

聊天是 [Dispatch](/docs/template-dispatch) 工作區中眾多應用程式之一。本頁涵蓋
這在實務上究竟意味著什麼：連接如何運作，以及聊天的代理如何觸及周圍的其他應用
程式。總覽請參閱 [聊天](/docs/template-chat)。

## 聊天如何連接到 Dispatch

這是否自動運作，取決於聊天和 Dispatch 當初是如何一起設定的，而不是取決於其中
任何一個是託管執行還是在本機執行。

### 相同工作區：自動運作

如果聊天和 Dispatch 是一起產生或加入到同一個 Agent-Native 工作區中（透過
`create` 或 `add-app`），並部署為一個整體單元，它們就已經共用同一個
`.env`、同一個 `A2A_SECRET`，以及同一個工作區登錄。無論這個工作區是在您的
機器上執行，還是在生產環境中執行，發現機制和已驗證的 A2A 呼叫都能直接運作，
不需要任何額外設定。

### 各自部署：一個手動步驟

如果聊天和 Dispatch 是兩個各自獨立建立的 Agent-Native 專案，它們就不會共用
密鑰，也還無法互相呼叫。連接它們需要在雙方各執行一個手動步驟：透過 Settings
→ Agent → 子代理（Connect agent），或 Dispatch → Agents → Add external
agent，加入一個帶有共用密鑰的 `remote-agents/<id>.json` 資源。完整操作步驟請
參閱 [A2A 協議](/docs/a2a-protocol)。

若要確認您目前是哪種情況，可以詢問任一應用程式的代理「what apps can you
see?」如果 Dispatch 的回答中沒有出現聊天，就代表您屬於第二種情況。

## 整合策略

**請其他應用程式協助。** 聊天的代理可以查詢工作區中有哪些應用程式，以及每一個
能做什麼。接著它可以請其中一個執行特定的 action，並在對話中使用得到的答案。
例如，在有行事曆的工作區中，您可以問聊天「what's on my calendar tomorrow?」，
代理會把這個問題交給行事曆，而不是自己猜測。聊天不需要持有行事曆與 Google 的
連線，行事曆已經有了。

**聊天作為入口。** 因為每個應用程式的代理都能以相同的方式觸及，聊天中的對話是
一個很自然的地方，可以開始那些位於其他應用程式中的工作。您在一個地方描述想要
什麼，代理會決定由哪個應用程式來處理。聊天在這方面表現良好，因為它沒有自己的
領域來造成阻礙。

**保持解耦。** 聊天從不需要其他應用程式的憑證，其他應用程式也不需要聊天的。
每個應用程式都保有自己的連線和自己的資料。聊天只負責傳遞請求並接收答案。
