# 組織、團隊與權限

組織定義團隊成員和租戶界線。工作區彙整應用程式與部署設定，但不會取代組織。權限必須由伺服器檢查。在介面隱藏按鈕並不等於存取控制。

## 三種角色範圍

- 組織角色 `owner`、`admin` 和 `member` 控制團隊管理。擁有者和管理員管理電子郵件網域自動加入；應用程式之間共用的 A2A 密鑰只有擁有者可以管理。
- 應用程式角色控制單一應用程式內的操作。一位成員可以有多個應用程式角色。
- 資源角色 `viewer`、`editor` 和 `admin` 控制單筆資料的存取。

應用程式程式碼宣告角色和權限鍵。管理員可在團隊頁面取代成員的整組角色，並將已宣告的權限對應到角色。沒有覆寫時採用應用程式預設值。邀請可以預先包含應用程式角色。應用程式管理員不會因此取得組織管理權限。

邀請和設定請參閱[管理式部署指南](/docs/administered-deployments)。資料存取請參閱[資料範圍控制](/docs/security#data-scoping)。

## 可選權限政策

預設情況下，權限檢查要求已指派的應用程式角色。透過 `defineAppRoles` 的可選第二個參數，可以變更伺服器端政策。Forms 使用：

```ts
const formsAccess = defineAppRoles(
  {
    appId: "forms",
    roles: ["editor", "reviewer"] as const,
    permissions: {
      "forms.edit": ["editor"],
      "forms.review": ["editor", "reviewer"],
    },
  },
  { unassignedRole: "editor", allowOrgAdmins: true },
);
```

- `unassignedRole` 將已宣告角色的權限套用至沒有應用程式角色指派的有效成員。權限覆寫仍然生效。它不會建立角色指派，也不適用於已移除的成員或僅包含已廢棄角色的指派。清除全部指派後，會恢復此預設行為。
- `allowOrgAdmins: true` 允許組織的有效擁有者和管理員通過任何已宣告的應用程式權限檢查，不受其應用程式角色或權限覆寫影響。它不會向應用程式管理員授予組織管理權限。

這些選項僅影響 `requirePermission` 和 `assertPermission`。`resolve`、`requireAny` 和 `assertAny` 仍使用明確指派；`defaultRole` 仍僅用於顯示。省略選項時保留嚴格政策。兩者都不取代資源授權：請保留 `accessFilter` 和 `assertAccess` 檢查。

Forms 保留現有未指派角色成員的編輯權限。明確指派的 Reviewer 可以審查提交內容，但不能編輯表單；Editor 可以執行兩種操作。資源分享仍決定他們能存取哪些表單和提交內容。

## 使用者群組 {#user-groups}

組織可以建立由目前成員組成的可重複使用使用者群組。擁有者和管理員負責管理群組成員，同一個人可以加入多個群組。應用程式可以使用群組來分享支援群組分享的資源，或限制可使用工作區連線的人員。

群組是存取名單，不是下層團隊。它沒有獨立的組織或應用程式角色、資料邊界，也沒有團隊專屬的設定、指示、脈絡、技能、記憶或工作檢視。將資源分享給群組後，該資源的分享角色會授予群組內所有目前成員。存取者仍須屬於資源所在的組織。

詳情請參閱[分享與隱私 → 群組分享](/docs/sharing#group-grants)和[工作區連線](/docs/workspace-connections)。
