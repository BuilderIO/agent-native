# Azure Static Web Apps

<Badge label="Beta" color="orange" icon="rocket" />

Azure Static Web Apps 會為你代管應用程式，因此不需要架設或維護伺服器。它會直接提供
應用程式的靜態檔案，並把應用程式的伺服器當作受管理的 Azure Functions 執行，還會為
應用程式提供一個支援 HTTPS 的公開網址。

本指南會從頭開始示範如何部署一個獨立應用程式。你將建立應用程式，為它設定正式環境
資料庫和驗證密鑰，準備好資料庫，為 Azure 建置應用程式，建立一個靜態 Web 應用程式，
然後使用 Static Web Apps CLI 上傳完成的建置成果。

<Callout tone="info">

需要 Node.js `22.22+`。

</Callout>

你還需要一個 Azure 帳號。請在你自己的電腦上執行本指南中的指令。你會使用 Node.js
建置應用程式，Static Web Apps CLI 會把完成的建置成果上傳到 Azure。

## 步驟 1：建立應用程式 {#step-1-create-the-app}

建立新的獨立應用程式。下面的範例以 Chat 範本建立應用程式，但你可以從任何範本開始。
進入應用程式的資料夾並安裝相依套件。`corepack enable` 會啟用應用程式所需的 `pnpm`
版本，因此你不需要自行安裝 `pnpm`。

```bash
npx --yes @agent-native/core@latest create my-app --standalone --template chat

cd my-app

corepack enable

pnpm install
```

如果你想要，可以把 `my-app` 換成你自己的應用程式名稱。本指南的其餘部分假設你位於
應用程式的資料夾中。

<Callout tone="info">

如果這些指令因對等相依性錯誤而失敗，原因可能是 npx 快取中有過時的套件副本。執行 `npx clear-npx-cache` 清除快取，然後重新執行這些指令。

</Callout>

## 步驟 2：設定環境密鑰 {#step-2-configure-environment-secrets}

應用程式會從環境變數讀取其正式環境設定：

| 變數                 | 必要 | 用途                                       |
| -------------------- | ---- | ------------------------------------------ |
| `DATABASE_URL`       | 是   | 將應用程式連線到它的 PostgreSQL 資料庫     |
| `BETTER_AUTH_SECRET` | 是   | 為使用者工作階段簽章                       |
| `BETTER_AUTH_URL`    | 否   | 設定使用者連到你的應用程式時使用的公開網址 |

下面的 export 指令讓後續指令能在目前的 shell 中正常運作。部署之前，請把這些變數
同樣儲存到主機的專案或服務環境設定中。步驟 5 會說明如何在 Azure 中儲存它們。

### 資料庫 URL {#database-url}

在本機開發期間，如果未設定 `DATABASE_URL`，應用程式會把資料儲存在本機資料庫中。
已部署的應用程式需要一個真正的 PostgreSQL 資料庫，在每次部署之間保留資料。Azure
Functions 不會在每次請求之間保留檔案，因此資料庫必須位於靜態 Web 應用程式之外。
從你的提供者複製連線字串並匯出它：

```bash
export DATABASE_URL='your-postgres-url-string'
```

[資料庫提供者指南](/docs/neon)說明了在各個提供者處找到連線字串的位置，其中包括
[Azure Database for PostgreSQL](/docs/azure-postgresql)。

<Callout tone="warning">

請選擇持久性的 PostgreSQL 提供者，例如 Neon、Supabase、Amazon RDS 等。

</Callout>

### 驗證密鑰 {#auth-secret}

只需要產生一次，並在每次部署之間保持不變。

應用程式使用 `BETTER_AUTH_SECRET` 為使用者工作階段簽章。如果它變更了，所有已登入的
使用者都會被登出。下面的指令會產生一個隨機值：

```bash
export BETTER_AUTH_SECRET="$(openssl rand -hex 32)"
```

請把產生的值儲存在安全的地方，例如密碼管理工具。每次部署時都使用相同的值。

### 公開 URL {#public-url}

選用。在使用自訂網域、反向代理，或需要固定公開來源的驗證/OAuth 流程時設定它。

`BETTER_AUTH_URL` 是使用者連到你的應用程式時使用的公開網址。如果沒有設定，應用程式
會根據每個傳入的請求推斷自己的網址。在 Azure 提供給你的網址上，這通常沒有問題，
但當你連接自訂網域時，請設定它，讓登入連結和 OAuth 重新導向使用該網域。

```bash
export BETTER_AUTH_URL='https://your-domain.example'
```

## 步驟 3：遷移 {#step-3-migrate}

遷移會在你的資料庫中建立和更新應用程式所需的資料表。請在第一次部署之前執行此指令：

```bash
pnpm migrate:production
```

這個指令會在你的電腦上執行，並使用你在步驟 2 中匯出的 `DATABASE_URL` 連線到正式
環境資料庫。升級應用程式之後、部署新版本之前，請再執行一次。

## 步驟 4：建置 {#step-4-build}

### 建置應用程式 {#build-the-app}

為 Azure Static Web Apps 建置應用程式：

```bash
NITRO_PRESET=azure-swa pnpm build
```

`NITRO_PRESET=azure-swa` 會依照 Azure Static Web Apps 要求的格式建置應用程式。建置會把
靜態檔案寫入 `.output/public`，並把伺服器函式寫入 `.output/server`。它還會把一個
`staticwebapp.config.json` 檔案寫入應用程式的資料夾，這個檔案會告訴 Azure 如何路由
請求，以及使用哪個 Node.js 版本執行伺服器。

### 設定 API 執行環境 {#set-the-api-runtime}

Azure 會使用 `staticwebapp.config.json` 中指定的 Node.js 版本執行應用程式的伺服器。
建置會從 `package.json` 的 `engines` 欄位選取該版本，但只有在該欄位剛好是 `20` 或
`22` 時才會這樣做。新的應用程式要求 `>=22.22.0`，因此建置會改為寫入 Node.js 18，
而這個版本對應用程式來說太舊，Azure 也已不再支援。

每次建置之後，將版本設定為 Node.js 22：

```bash
node -e "const fs = require('node:fs'); const file = 'staticwebapp.config.json'; const config = JSON.parse(fs.readFileSync(file, 'utf8')); config.platform = { ...config.platform, apiRuntime: 'node:22' }; fs.writeFileSync(file, JSON.stringify(config, null, 2));"
```

這個指令只會變更 `apiRuntime` 設定，並保留建置寫入的檔案中的其餘內容。建置每次都會
重寫這個檔案，因此請在每次建置之後、部署之前執行這個指令。

## 步驟 5：建立靜態 Web 應用程式並儲存密鑰 {#step-5-create-the-static-web-app-and-save-the-secrets}

在 Azure 入口網站中，建立一個新的 **Static Web App**。選擇訂用帳戶、資源群組、名稱和
方案。在 **Deployment details** 下選擇 **Other**，因為你要自行上傳建置成果，而不是
連接 GitHub 儲存庫。

在應用程式的 **Overview** 頁面中，從 **Manage deployment token** 下複製部署權杖，
並匯出它：

```bash
export SWA_CLI_DEPLOYMENT_TOKEN='your-deployment-token'
```

Static Web Apps CLI 會在步驟 6 中讀取這個變數。請妥善保管這個權杖，不要外流，因為
任何擁有它的人都可以部署到你的應用程式。

接著儲存兩個必要變數。在 Azure 入口網站中開啟該靜態 Web 應用程式，前往 **Settings** >
**Environment variables**，選擇 **Production** 環境，然後加入 `DATABASE_URL` 和
`BETTER_AUTH_SECRET`，值為你在步驟 2 中匯出的值。如果你有設定 `BETTER_AUTH_URL`，
請用同樣的方式加入它。Azure 會把這些值當作環境變數傳給應用程式的伺服器函式。

## 步驟 6：部署 {#step-6-deploy}

<Steps>

### 上傳建置成果

在應用程式的資料夾中，把靜態檔案和伺服器函式上傳到正式環境：

```bash
npx @azure/static-web-apps-cli deploy .output/public --api-location .output/server --swa-config-location . --env production
```

`.output/public` 存放靜態檔案，`--api-location .output/server` 指向伺服器函式。
`--swa-config-location .` 指向應用程式的資料夾，建置會把 `staticwebapp.config.json`
寫到那裡。如果沒有加上這個參數，Azure 就看不到步驟 4 中設定的 API 執行環境。
`--env production` 會發布到你的正式環境網址，而不是預覽環境。

### 開啟應用程式

指令完成後，會輸出應用程式的網址，該網址以 `azurestaticapps.net` 結尾。開啟它並建立
第一個帳號。

</Steps>

## 部署更新 {#deploy-updates}

若要發布新版本，請執行遷移，再次建置，然後上傳：

```bash
pnpm migrate:production

NITRO_PRESET=azure-swa pnpm build

node -e "const fs = require('node:fs'); const file = 'staticwebapp.config.json'; const config = JSON.parse(fs.readFileSync(file, 'utf8')); config.platform = { ...config.platform, apiRuntime: 'node:22' }; fs.writeFileSync(file, JSON.stringify(config, null, 2));"

npx @azure/static-web-apps-cli deploy .output/public --api-location .output/server --swa-config-location . --env production
```

在新的 shell 中，請再次匯出 `SWA_CLI_DEPLOYMENT_TOKEN`。已儲存的環境變數會保留在
靜態 Web 應用程式上，因此你不需要重複步驟 5。

## 請求限制 {#request-limits}

Azure Static Web Apps 會在 45 秒後結束對應用程式伺服器的任何請求，而且不支援
WebSockets。Agent-Native 已經會在大約 40 秒後結束一次對話回合，並從瀏覽器繼續執行，
因此較長的代理程式回合仍然能夠完成，只是會分成多個步驟執行，而不是一次完成。如果你的
應用程式需要長時間的請求，請使用沒有這項限制的主機，例如 [Node.js](/docs/node-js) 或
[Docker](/docs/docker)。
