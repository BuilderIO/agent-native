# 其他介面

UI 掛鉤介面已在[資料與同步](/docs/client-data)中涵蓋：`useActionQuery()`、`useActionMutation()` 與 `callAction()`。本頁涵蓋其餘所有可以呼叫、或被一個 action 所驅動的方式。

## 渲染原生聊天 UI {#native-chat-ui}

Action 可以回傳結構化的 widget 資料，讓應用程式內的聊天以原生方式渲染。這是可重複使用的表格、圖表、設定摘要與洞察卡片的第一方聊天路徑。當代理需要在應用程式內聊天中產生任意的互動式控制項時，請使用[生成式 UI](/docs/generative-ui)；若要在外部 MCP 主機中呈現內嵌 UI，請使用 [MCP Apps](/docs/mcp-apps)。

```ts
import { defineAction } from "@agent-native/core/action";
import { ACTION_CHAT_UI_DATA_CHART_RENDERER } from "@agent-native/core/action-ui";
import {
  createDataChartWidgetResult,
  dataChartWidgetResultSchema,
} from "@agent-native/core/data-widgets";

export default defineAction({
  description: "Summarize response trends.",
  readOnly: true,
  outputSchema: dataChartWidgetResultSchema,
  chatUI: { renderer: ACTION_CHAT_UI_DATA_CHART_RENDERER },
  run: async () =>
    createDataChartWidgetResult({
      title: "Response trends",
      chartSeries: {
        type: "line",
        xKey: "day",
        series: [{ key: "responses", label: "Responses" }],
        data: [
          { day: "Mon", responses: 12 },
          { day: "Tue", responses: 18 },
        ],
      },
    }),
});
```

內建的判別值有 `"data-table"`、`"data-chart"` 與
`"data-insights"`，並在 `@agent-native/core/data-widgets` 中提供伺服器安全的
建構函式與架構。純圖表答案請用 `data-chart`，SQL／列表結果請用
`data-table`，只有在需要一張結合摘要／圖表／表格的卡片時才用
`data-insights`。完整的結果契約請參閱
[原生聊天 UI](/docs/native-chat-ui)，若您要接上自訂的代理執行環境而非
內建的聊天迴圈，請參閱
[BYO 代理執行環境](/docs/native-chat-ui#byo-agent-runtimes)。同一個 action
如何保持對自動化友善、在聊天中渲染，或成長為完整畫面，請參閱
[Agent 介面](/docs/agent-surfaces)。

## 從 CLI 呼叫它 {#cli}

每個 action 都可以透過 `pnpm action` 執行：

```bash
pnpm action reply-to-email '{"emailId":"thread-123","body":"Thanks!"}'
```

對代理與複雜物件而言，JSON 輸入是偏好的格式。旗標對於簡單的手動
執行與既有腳本來說，運作方式相同：

```bash
pnpm action reply-to-email --emailId thread-123 --body "Thanks!"
```

對於 `defineAction()` 呼叫，CLI 會使用已準備、解析並套用結構描述預設值的引數，以及呼叫者 `cli` 來評估 `needsApproval`。若 stdin 和 stdout 都是 TTY，它會顯示 action 名稱與引數，並提示 `y/N`。只有 `y` 或 `yes` 才會執行 action。

若缺少任一 TTY，CLI 會要求代理向本人請求核准。本人核准這次特定呼叫後，使用完全相同的原始 `pnpm action` 引數重新執行，並在結尾加上 `--approved`：

```bash
pnpm action reply-to-email --emailId thread-123 --body "Thanks!" --approved
```

`--approved` 是保留的 CLI 中繼資料，會在解析輸入前移除。用於不需核准的 action 時不會造成影響。CLI 無法確認是誰加上它：代理未經詢問就加上它，便會略過確認。這個旗標讓核准顯示在本人核准的命令中，也顯示在稽核記錄裡，稽核記錄會將其標為未驗證。在沒有 POSIX `SHELL` 的 Windows 上，拒絕訊息會提供 PowerShell 用的命令；引號規則不同時，也會提供 cmd.exe 用的命令。在 Windows 上，無論從哪個 shell 執行，pnpm 都會經由 cmd.exe 傳遞 action 參數，而 cmd.exe 即使在引號內也會展開 `%NAME%`。參數中含有這類變數時，拒絕訊息不會提供帶 `--approved` 的重新執行命令：由本人在終端機中執行命令，並在確認提示中核對參數值。

本機開發橋接會在 JSON 請求主體中將核准中繼資料放在 `input` 之外：

```ts
{ name, input, approved: true, approvalSource: "flag" }
```

對於尚未核准的受限呼叫，橋接會傳回 HTTP `409`：

```ts
{
  ok: false,
  errorCode: "approval_required",
  error: 'Action "<name>" requires human approval. Ask the person, then rerun with --approved.',
  arguments: preparedArgs,
  argumentsHash: prepared.argumentsHash,
}
```

在 TTY 中確認後，CLI 會使用核准請求回應中的 `argumentsHash` 重試：

```ts
{
  name,
  input,
  approved: true,
  approvalSource: "prompt",
  approvalArgumentsHash: challenge.argumentsHash,
}
```

橋接只會執行一次本人審閱過的那次呼叫，因此每次呼叫都會變動的預設值（例如時間戳記）會保留本人看到的值。沒有可執行的保留呼叫的確認（已執行過、已過 10 分鐘或開發伺服器已重新啟動）會收到 HTTP `409` 和 `errorCode: "approval_expired"`。請重新執行命令進行審閱。

`arguments` 包含準備好的引數。本機開發橋接的此約定不會改變[公開 HTTP action API 的核准規則](/docs/actions-access-control#needs-approval)。已核准的受限 CLI 呼叫會在該 action 自己的稽核記錄列中寫入 `approval: "cli-prompt"` 或 `approval: "cli-flag"`，呼叫者為 `cli`。由於只有 CLI 能看到確認提示，稽核記錄會將兩者都顯示為未驗證。

## 從另一個代理呼叫它（A2A）{#a2a}

若您的應用程式是一個 [A2A](/docs/a2a-protocol) 對等節點，其他 agent-native 應用程式會自動探索您的 action，並能依名稱呼叫它們。同源部署會跳過 JWT 簽署；跨來源部署則改用共用的 `A2A_SECRET`。

## 透過 MCP 曝露它 {#mcp}

啟用 MCP 後，您的 action 會出現在框架位於 `/mcp` 的 MCP 伺服器中。每位呼叫者預設都會取得一份精簡目錄（面向應用程式的內建項目，加上範本宣告的應用程式 action），且 `tool-search` 一律存在，讓任何其他工具都能依需求被找到。完整的 action 介面只有在明確選擇加入時才會提供（`--full-catalog` 權杖或 `AGENT_NATIVE_MCP_FULL_CATALOG=1`），而 [`publicAgent.expose`](/docs/actions-access-control#public-agent) 則可以讓一個安全的讀取／匯入工具加入公開介面。目錄層級、驗證與 `mcpApp` 資源的細節，請參閱 [MCP 協定](/docs/mcp-protocol)。

對於具備 UI 能力的 MCP 主機，一個 action 可以透過 `mcpApp` 欄位（加上對應的 `link`）宣告一個選用的 MCP Apps 資源，讓有能力的主機能夠內嵌渲染結果。當 `link` 與 `mcpApp` 應該指向同一個路由時，`embedRoute()` 可以用同一個純路徑建構函式同時建構兩者：

```ts
import { embedRoute } from "@agent-native/core";

export default defineAction({
  description: "Create an email draft for review.",
  schema: z.object({ body: z.string() }),
  run: async ({ body }) => ({ body }),
  ...embedRoute({
    title: "Review draft",
    openLabel: "Open in Mail",
    path: ({ result }) => ({
      label: "Open draft in Mail",
      url: "/_agent-native/open?app=mail&view=inbox",
    }),
  }),
});
```

請將 `link` 保留作為 CLI 與非 UI MCP 主機的備援方案，它同時也是內嵌的啟動目標。內嵌橋接（已簽署的內嵌啟動工作階段、transplant 與 controlled-frame 渲染方式的取捨、`ui/*` 主機橋接、CSP，以及高度限制）的所有權屬於[外部代理](/docs/external-agents#mcp-app-bridge)。

目前沒有自動檢查來確認某個範本是否具備 `view-screen`、`navigate`，或針對其主要資源的 create/read/update/list 完整集合；鷹架會內建 `view-screen` 與 `navigate`，而 `pnpm guard:external-result-contract` 會攔截對外公開的 action 的 `description` 或 `nextRequiredAction` 中「等待使用者」之類的措辭，並要求新增的、對外公開的 `create-*` action 攜帶深層連結。是否存在這些 action 是一項需要人工審查的事項。

## 標準 actions {#standard-actions}

每個範本都應該包含這兩個 action，以支援[情境感知](/docs/context-awareness)。

### view-screen {#view-screen}

讀取目前的導覽狀態、取得情境相關資料，並回傳使用者目前所見畫面的快照。當代理需要重新查看畫面時，會呼叫此 action。

```ts
// actions/view-screen.ts
import { defineAction } from "@agent-native/core/action";
import { readAppState } from "@agent-native/core/application-state";
import { z } from "zod";

export default defineAction({
  description: "Read the current screen state for context.",
  schema: z.object({}),
  http: { method: "GET" },
  run: async () => {
    const navigation = await readAppState("navigation");
    const screen: Record<string, unknown> = { navigation };

    if (navigation?.view === "inbox") {
      screen.emailList = await listEmailsForLabel(navigation.label);
    }

    return screen;
  },
});
```

### navigate {#navigate}

將一次性的導覽指令寫入應用程式狀態。UI 會讀取它、進行導覽，然後刪除該筆項目。

```ts
// actions/navigate.ts
import { defineAction } from "@agent-native/core/action";
import { writeAppState } from "@agent-native/core/application-state";
import { z } from "zod";

export default defineAction({
  description: "Navigate the user to a view.",
  schema: z.object({
    view: z.string(),
    threadId: z.string().optional(),
  }),
  run: async (args) => {
    await writeAppState("navigate", args);
    return { ok: true };
  },
});
```
