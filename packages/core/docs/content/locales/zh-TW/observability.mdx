# 代理可觀察性

每個 Agent-Native 應用程式都具有開箱即用的可觀察性。跟蹤、自動評估、使用者意見回饋和 A/B 實驗可在零設定下執行 - 所有資料都儲存在應用自己的 SQL 資料庫中。

此頁面涵蓋*代理品質*指標：儲存在資料庫中的跟蹤、成本、評估和意見回饋。對於*product*分析（您的應用程式的事件流向PostHog/Mixpanel/Amplitude），請參閱[Tracking](/docs/tracking)。

## 三樣東西叫做“評估”/“可觀察性”——我想要哪一個？ {#which}

這三個頁面很容易混淆。根據您要問的問題進行選取：

| 頁面                                                   | 它回答的問題                           | 當它執行時                       | 關注      |
| ------------------------------------------------------ | -------------------------------------- | -------------------------------- | --------- |
| **可觀測性評估**（此頁面，_Evals_ 分頁）               | “我的實際正式環境情況如何？”           | 被動，每次執行後（LLM-判斷取樣） | 品質      |
| **[CI Eval Gate](/docs/evals)** (`*.eval.ts`)          | “代理在此固定輸入上執行正確的操作嗎？” | 主動、確定性、CI/部署門          | 品質      |
| **[Observational Memory](/docs/observational-memory)** | “這條長線是否便宜且位於窗戶內？”       | 長對話串上的背景壓縮             | 成本/環境 |

可觀察性和 CI 評估門都對品質進行評分，但兩端不同——對實際流量進行被動事後評分，與對固定輸入進行主動透過/失敗檢查。觀察記憶與品質無關；這與代幣成本和脈絡視窗壓力有關。 將已完成的生產 trace 提升為 `*.eval.ts` 案例（儀表板 **Promote to eval**、`promote-trace-eval` 或 `agent-native eval promote <runId> --write evals/from-trace.eval.ts`）。見 [從生產 Trace 提升](/docs/evals#from-trace)。

## 自動捕獲的內容 {#captured}

當使用者傳送訊息時，框架會自動紀錄：

- **權杖使用** — 輸入、輸出、快取讀取、快取寫入
- **成本** — 根據代幣數量和模型定價計算
- **延遲** — 每次工具呼叫的總持續時間和時間
- **工具呼叫** — 呼叫了哪些 actions、成功/錯誤狀態、持續時間
- **自動評估** - 每次執行後計算 5 個品質分數

無需更改程式碼。儀器透明地掛接到 `production-agent.ts`。

## 儀表板 {#dashboard}

將儀表板新增到具有單一路由的任何範本：

```tsx
// app/routes/observability.tsx
import { ObservabilityDashboard } from "@agent-native/toolkit/app/observability";
export default function ObservabilityPage() {
  return (
    <div className="min-h-screen bg-background p-6">
      <ObservabilityDashboard />
    </div>
  );
}
```

所有資料的範圍僅限於登入使用者；今天沒有跨使用者管理檢視。

儀表板有 6 個分頁：

| 分頁         | 它顯示了什麼                                                 |
| ------------ | ------------------------------------------------------------ |
| **概述**     | 關鍵指標 - 執行、成本、延遲、工具成功率、滿意度、評估分數    |
| **對話**     | 跟蹤清單，可深入到各個範圍（agent_run、llm_call、tool_call） |
| **評估**     | 按標準自動評估分數、隨時間變化的趨勢                         |
| **實驗**     | 帶有狀態徽章的 A/B 測試清單、帶有置信區間的變數結果          |
| **意見回饋** | 讚成/反對、類別細分、挫敗感分數                              |
| **人工審查** | 檢視請求與回答、記錄意見回饋並草擬指示更新                   |

### 對話詳細資料 {#conversations}

「對話」分頁會顯示已記錄的執行。選取一個執行即可檢視其範圍，展開任一範圍即可查看已擷取的工具輸入、輸出、錯誤和中繼資料。選取**開啟完整對話**可前往相關的聊天對話串。

預設不會擷取工具引數、結果和完整的錯誤內文。若要儲存這些內容，請在 `observability` 設定中啟用 `captureToolArgs`（儲存引數）和 `captureToolResults`（儲存結果和完整錯誤內文）。敏感欄位會在儲存前遮蔽。失敗的工具一律會保留其錯誤的第一行（長度有限），其中的憑證、電子郵件地址和較長的不透明 ID 會被遮蔽，因此即使關閉 `captureToolResults`，失敗仍可診斷。

提示詞擷取預設為關閉。在 `observability` 設定中設為 `capturePrompts: true`，或設定 `AGENT_NATIVE_OBSERVABILITY_CAPTURE_PROMPTS=true`，即可在此詳細檢視中儲存每個 `llm_call` 範圍的輸入與輸出。系統提示詞不會包含在內，結構化敏感欄位會遮蔽，且輸入與輸出各限制為 128 KiB。既有範圍不會追溯補齊。

### 人工審查 {#review}

「人工審查」分頁會顯示每次執行的請求與回答，並可記錄意見回饋及草擬指示更新，交由人員審查。儲存草稿不會自動變更指示。

## 使用者意見回饋 {#feedback}

### 明確意見回饋

“豎起大拇指”/“豎起大拇指”按鈕在聊天 UI 中的每條代理訊息上呈現行內。拇指朝下會開啟一個類別快顯視窗（不準確、沒有幫助、工具錯誤、太慢）。這會自動連線到 `AssistantChat.tsx`。

### 隱性意見回饋（挫敗指數）

框架根據對話信號計算挫敗指數（0-100）：

| 信號     | 重量 | 它偵測到什麼             |
| -------- | ---- | ------------------------ |
| 改寫     | 30%  | 使用者重複類似的訊息     |
| 重試模式 | 20%  | “再試一次”，“不，錯了”   |
| 放棄     | 20%  | 工作階段在回應後不久結束 |
| 情緒     | 15%  | 負面語言模式             |
| 長度趨勢 | 15%  | 訊息長度減少             |

分數解釋：0-20 = 健康，20-40 = 摩擦，40-60 = 不滿意，60+ = 中斷的訓練。

### PostHog 中的意見回饋 {#posthog-feedback}

按讚/倒讚、分類與自由文字都會送出 `$ai_feedback`。但 PostHog LLM 分析的意見回饋檢視讀取的是 `survey sent` 事件，因此請將 `POSTHOG_AI_FEEDBACK_SURVEY_ID` 設為 PostHog 從追蹤的 **Feedback** 分頁建立的問卷。這一個 id 就是全部設定；未設定時不會送出任何問卷事件。

按讚/倒讚以 PostHog 的選項序號回答問卷的第一個問題（`1` 為讚，`2` 為倒讚），倒讚之後的自由文字則回答追問，因此文字絕不會落在評分的位置。兩者對同一則被評分的訊息使用同一個提交 id，PostHog 便是據此把它們合併為一則回應；在追問送達之前，倒讚會維持標記為未完成。

## 自動評估 {#evals}

每次代理執行後都會執行五個確定性記分器：

| 標準                | 它測量什麼                              | 分數範圍 |
| ------------------- | --------------------------------------- | -------- |
| `tool_success_rate` | 沒有錯誤的工具呼叫百分比                | 0-1      |
| `step_efficiency`   | 對使用工具的執行進行過多的 LLM 迭代懲罰 | 0-1      |
| `latency_score`     | 根據 10 秒/工具基線進行歸一化           | 0-1      |
| `cost_efficiency`   | 根據成本基線標準化                      | 0-1      |
| `error_recovery`    | 代理是否從工具錯誤中恢復？              | 0 或 1   |

### LLM 作為法官（可選）

透過設定 `evalSampleRate` 啟用基於取樣 LLM 的評估：

```ts
// server/plugins/config.ts
import { defineAppConfig } from "@agent-native/core/server";

export default defineAppConfig({
  observability: {
    enabled: true,
    evalSampleRate: 0.05, // 5%
  },
});
```

自訂標準使用自然語言規則：

```ts
const criteria = {
  name: "helpfulness",
  description: "Was the response helpful and complete?",
  rubric: "0.0 = unhelpful, 0.5 = partially helpful, 1.0 = fully resolved",
};
```

## 設定 {#config}

透過 `defineAppConfig()` 在伺服器外掛程式中設定。每個欄位還有一個部署環境變數別名——請參閱宣告式設定參考。

```ts
// server/plugins/config.ts
import { defineAppConfig } from "@agent-native/core/server";

export default defineAppConfig({
  observability: {
    enabled: true, // Master switch
    capturePrompts: false, // Store prompt content in traces
    captureToolArgs: false, // Store action input arguments
    captureToolResults: false, // Store action results
    evalSampleRate: 0, // 0-1, fraction of runs to LLM-judge
  },
});
```

<Callout id="doc-block-1xvsimn" tone="info">

內容**預設會遮蔽**：儲存的是 token 數量、成本和耗時，對於失敗的工具，還會儲存其錯誤的第一行（長度有限），其中的憑證、電子郵件地址和較長的不透明 ID 會被遮蔽。除非啟用 `capturePrompts`、`captureToolArgs` 和 `captureToolResults`，否則提示詞、工具輸入、工具結果和完整錯誤內文都不會被儲存。僅在偵錯需要提示詞或引數內容時才啟用它們。

</Callout>

## API 端點 {#api}

全部自動安裝在`/_agent-native/observability/`：

| 方法 | 路徑                       | 目的                       |
| ---- | -------------------------- | -------------------------- |

| POST | `/feedback`                | 提交意見回饋               |
| GET  | `/feedback`                | 列出意見回饋               |
| GET  | `/feedback/stats`          | 意見回饋聚合               |
| GET  | `/satisfaction`            | 滿意度分數                 |
| GET  | `/evals/stats`             | 評估統計                   |
| POST | `/experiments`             | 建立實驗                   |
| GET  | `/experiments`             | 列出實驗                   |
| GET  | `/experiments/:id`         | 取得實驗詳細資訊           |

## 匯出到外部平台 {#export}

透過在您自己的應用程式中註冊 OpenTelemetry 提供者，將跟蹤傳送到 Langfuse、Datadog、Grafana 或任何 OTel 相容後端——請參閱下面的 [OpenTelemetry 範圍](#otel)。

核心有意不提供任何匯出器，也不保存匯出端點或權杖，因此後端憑證存在於您的提供者接線（以及保險庫）中，而絕不在框架設定中。

## OpenTelemetry 跨度 {#otel}

代理迴圈為每次執行、模型呼叫和工具呼叫發出**即時 OpenTelemetry 範圍**，因此已經執行 OTel 收集器的主機可以看到代理活動以及其分散式跟蹤的其餘部分。

該層是**可選且預設情況下無操作**：

- `@opentelemetry/api` 是**可選依賴項**。如果未安裝，幫助程式將降級為靜默無操作 - 這裡不會將任何內容放入代理迴圈中。
- 即使 api 包存在，它也會提供預設的無操作跟蹤器。只有當**主機註冊了 `TracerProvider`**（透過 `@opentelemetry/sdk-node` 或類似的）時，跨度才變得真實。此框架故意**不**依賴於繁重的 SDK/exporter 包或本身註冊提供者 - 偵測是由嵌入應用程式選取加入的。

因此，當您未連線 OTel 時，成本是每次呼叫都會讀取幾次快取的屬性。要開啟它，請安裝 api 包和 SDK，並在伺服器啟動時註冊提供者，就像任何其他 Node 服務一樣。

代理迴圈發出三種跨度型別：

| 跨度                  | 何時             | 屬性                                                                                                      |
| --------------------- | ---------------- | --------------------------------------------------------------------------------------------------------- |
| `invoke_agent`        | 每個代理執行一次 | `gen_ai.provider.name`, `agent.run_id`, `gen_ai.conversation.id`, `agent.user_id`, `gen_ai.request.model` |
| `execute_tool {tool}` | 每次操作呼叫一次 | `gen_ai.tool.name`，加上成功/錯誤狀態                                                                     |
| `chat {model}`        | 每個模型呼叫     | `gen_ai.provider.name`, 計時+正常/錯誤狀態                                                                |

跨度以 OK/ERROR 狀態完成，並在失敗時紀錄由代碼產生的固定訊息。零/哨兵屬性值被修剪，因此跨度不會因噪音而混亂。該 OTel 層純粹是對內部 `agent_trace_spans` / `agent_trace_summaries` 表的補充，這些表為上面的儀表板提供支援 - 兩者都是由相同的執行事件產生的。

### 指標 {#otel-metrics}

宿主透過 `@agent-native/core/server` 中的 `registerObservabilityProvider()` 註冊指標提供者（meter provider）後，Core 也會記錄指標。指標會針對每個請求與每次執行記錄，不進行取樣：

| 指標工具                                    | 屬性                                                                                         |
| ------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `http.server.request.duration`              | `http.request.method`, `http.response.status_code`, `http.route`, `error.type`               |
| `agent_native.http.server.handoff.duration` | `http.request.method`, `http.response.status_code`, `http.route`, `error.type`               |
| `gen_ai.client.operation.duration`          | `gen_ai.operation.name`, `gen_ai.provider.name`, `gen_ai.request.model`, `error.type`        |
| `gen_ai.client.token.usage`                 | `gen_ai.operation.name`, `gen_ai.provider.name`, `gen_ai.request.model`, `gen_ai.token.type` |
| `agent_native.agent.runs`                   | `status`, `terminal_reason`, `gen_ai.provider.name`, `gen_ai.request.model`                  |
| `agent_native.tool.calls`                   | `gen_ai.tool.name`, `error.type`                                                             |
| `agent_native.telemetry.flush_failures`     | `error.type`, `agent_native.telemetry.signal`                                                |

`agent_native.http.server.handoff.duration` 與 `http.server.request.duration` 具有相同的屬性與分桶，但它不是在回應掛鉤開始時結束，而是在掛鉤把回應交還給執行環境時結束。當它的百分位數與 `http.server.request.duration` 的百分位數拉開差距時，表示已完成的回應正被卡住，例如被內嵌遙測排清卡住。兩個百分位數可能來自不同的請求，因此這個差值只是一個訊號，而不是某個請求的等待時間。沒有 `waitUntil` 時，core 會在該次排清之後記錄樣本，因此樣本會隨下一次排清抵達後端。

在指標中，`gen_ai.tool.name` 是框架動作的名稱或 `other`；只有當引擎將某個模型 ID 列為支援時，`gen_ai.request.model` 才會是該模型 ID，否則為 `_OTHER`。因此，應用程式自訂的工具與呼叫端傳入的模型 ID 不會產生無限增長的序列；span 中會保留確切的值。

每個請求都會設定 `http.route`，其值來自一個封閉集合：框架端點的路由範本（`/_agent-native/auth/session`、`/_agent-native/agent-chat/runs/:runId/events`）、動作宣告的範本、應用程式自身的 Nitro 檔案路由（`/api/clips/:id`），或一個分桶。分桶包括：這些命名空間中未列出的路徑對應的 `/_agent-native/*`、`/mcp/*` 與 `/.well-known/*`，其他 API 路徑對應的 `/api/*`，檔案請求對應的 `static`，其他 `GET` 或 `HEAD` 請求對應的 `page`，以及 `other`。原始請求路徑永遠不會被記錄。`http.server` span 會帶有相同的值。

## 連接 OpenTelemetry 後端 {#otel-provider}

Core 不附帶任何 OpenTelemetry SDK 或匯出器。應用程式自行建立 SDK 提供者，並透過 `@agent-native/core/server` 中的 `registerObservabilityProvider()` 交給 Core。Core 接著透過它們發出上文的[跨度](#otel)與[指標](#otel-metrics)，再由應用程式的匯出器傳送到任意 OTLP 後端。

### `registerObservabilityProvider()` {#register-observability-provider}

`registerObservabilityProvider()` 接受一個物件，包含兩個選用欄位：

- **tracerProvider**：具有 `getTracer(name, version?)` 的物件。Core 從這裡取得追蹤器。未提供時，跨度會使用全域的 `@opentelemetry/api` 追蹤器。
- **meterProvider**：具有 `getMeter(name, version?)` 的物件。只有註冊了指標提供者，指標才會被記錄。指標沒有全域備援，因此未註冊時每個指標都是空操作。

兩種提供者都可以另外實作 `forceFlush()`，Core 會在每次回應後呼叫它（請參閱[在無伺服器環境中排清](#otel-flush)）。SDK 的 `BasicTracerProvider` 與 `MeterProvider` 已經符合這些形狀。

```ts
function registerObservabilityProvider(
  provider: ObservabilityProvider,
): () => void;

interface ObservabilityProvider {
  tracerProvider?: ObservabilityTracerProvider;
  meterProvider?: ObservabilityMeterProvider;
}

interface ObservabilityTracerProvider {
  getTracer(name: string, version?: string): unknown;
  forceFlush?(): Promise<void>;
}

interface ObservabilityMeterProvider {
  getMeter(name: string, version?: string): unknown;
  forceFlush?(): Promise<void>;
}
```

之後的呼叫會取代先前的提供者。回傳的函式會在該提供者仍為已註冊者時取消註冊。跨度還需要在應用程式中安裝 `@opentelemetry/api`。未安裝時，Core 會關閉追蹤並記錄一次警告。

### 在無伺服器環境中排清 {#otel-flush}

無伺服器函式在兩次呼叫之間會被凍結，因此 SDK 的匯出計時器可能永遠不會觸發。當已註冊的提供者實作了 `forceFlush()` 時，Core 會在每個請求之後從回應掛鉤中呼叫它並等待完成。每次排清都與同一個共用的 2 秒逾時競速，因此遙測占用回應的時間絕不會超過這個上限。當平台提供 `waitUntil`（Cloudflare，或 Netlify 的呼叫內容）時，Core 會把清空交給它，先送出回應而不是等待。

Core 每個行程最多每 10 秒呼叫一次指標提供者的 `forceFlush()`，其間的請求會略過它。每次指標匯出都會重新傳送行程持有的所有序列，因此這樣可以避免上傳量隨請求速率成長。被略過的資料點不會遺失：下一次匯出會攜帶它們，除非該執行個體不再處理任何請求。追蹤提供者在每個請求時都會排清。

排清失敗或逾時後，Core 會停止等待它，並將 `agent_native.telemetry.flush_failures` 加 1，下一次排清會匯出這個計數。逾時的匯出會繼續執行，只要執行環境沒有先凍結程序，它仍可能送達。該失敗的 `error.type` 為 `timeout`，執行環境在排清途中凍結程序時為 `suspended`，否則為錯誤名稱。由於持續逾時的收集器永遠收不到該計數，Core 也會在每個程序中依訊號與錯誤類型，向函式記錄寫入一行 `agent-native.telemetry_flush_failed`。

在長時間執行的伺服器上，每次回應後都排清意味著每個請求匯出一次。在這類環境中，請註冊不帶 `forceFlush()` 的提供者，讓 SDK 自己的計時器負責匯出。`@agent-native/core/server` 中的 `isServerlessRuntime()` 可以區分這兩種情況。它在 Netlify、Vercel、AWS Lambda 與 Cloudflare 上為 true。

### 範例：透過 HTTP 傳送 OTLP {#otel-example}

這個伺服器外掛程式把 OpenTelemetry JS SDK 接到 Core。請先安裝 SDK 套件：

```bash
pnpm add @opentelemetry/api @opentelemetry/context-async-hooks @opentelemetry/exporter-metrics-otlp-proto @opentelemetry/exporter-trace-otlp-proto @opentelemetry/resources @opentelemetry/sdk-metrics @opentelemetry/sdk-trace-base
```

```ts filename="server/plugins/otel.ts"
import { randomUUID } from "node:crypto";

import {
  defineNitroPlugin,
  isServerlessRuntime,
  registerObservabilityProvider,
} from "@agent-native/core/server";
import { context } from "@opentelemetry/api";
import { AsyncLocalStorageContextManager } from "@opentelemetry/context-async-hooks";
import { OTLPMetricExporter } from "@opentelemetry/exporter-metrics-otlp-proto";
import { OTLPTraceExporter } from "@opentelemetry/exporter-trace-otlp-proto";
import {
  defaultResource,
  detectResources,
  envDetector,
  resourceFromAttributes,
} from "@opentelemetry/resources";
import {
  MeterProvider,
  PeriodicExportingMetricReader,
} from "@opentelemetry/sdk-metrics";
import {
  BasicTracerProvider,
  BatchSpanProcessor,
} from "@opentelemetry/sdk-trace-base";

export default defineNitroPlugin(() => {
  if (!process.env.OTEL_EXPORTER_OTLP_ENDPOINT) return;

  // Metric counters are cumulative and restart with each process, so each
  // process needs its own series.
  const resource = defaultResource()
    .merge(resourceFromAttributes({ "service.instance.id": randomUUID() }))
    .merge(detectResources({ detectors: [envDetector] }));

  const meterProvider = new MeterProvider({
    resource,
    readers: [
      new PeriodicExportingMetricReader({
        exporter: new OTLPMetricExporter(),
        exportIntervalMillis: 60_000,
      }),
    ],
  });

  context.setGlobalContextManager(
    new AsyncLocalStorageContextManager().enable(),
  );
  const tracerProvider = new BasicTracerProvider({
    resource,
    spanProcessors: [new BatchSpanProcessor(new OTLPTraceExporter())],
  });

  if (isServerlessRuntime()) {
    registerObservabilityProvider({ meterProvider, tracerProvider });
    return;
  }
  // Without forceFlush(), core leaves exporting to the SDK's own timers.
  registerObservabilityProvider({
    meterProvider: {
      getMeter: (name, version) => meterProvider.getMeter(name, version),
    },
    tracerProvider: {
      getTracer: (name, version) => tracerProvider.getTracer(name, version),
    },
  });
});
```

在設定 `OTEL_EXPORTER_OTLP_ENDPOINT` 之前，這個外掛程式不會做任何事。其餘設定由 SDK 從標準 OpenTelemetry 環境變數讀取：

| 變數                                              | 作用                                                                |
| ------------------------------------------------- | ------------------------------------------------------------------- |
| `OTEL_EXPORTER_OTLP_ENDPOINT`                     | OTLP 接收端的基礎 URL。匯出器會附加 `/v1/traces` 與 `/v1/metrics`。 |
| `OTEL_EXPORTER_OTLP_HEADERS`                      | 每次匯出時傳送的標頭，例如 `Authorization=Bearer%20<token>`         |
| `OTEL_SERVICE_NAME`                               | 每個跨度與指標上的 `service.name`                                   |
| `OTEL_RESOURCE_ATTRIBUTES`                        | 額外的資源屬性，例如 `deployment.environment.name=production`       |
| `OTEL_TRACES_SAMPLER` / `OTEL_TRACES_SAMPLER_ARG` | 追蹤取樣，例如 `parentbased_traceidratio` 與 `0.1`。指標從不取樣。  |

`-proto` 匯出器透過 HTTP 以 protobuf 傳送 OTLP，因此請將端點指向接收端的 HTTP 連接埠（預設 4318），而不是 gRPC 連接埠。跨度不包含提示詞或回覆文字。[設定](#config)中的 `capture*` 設定作用於 SQL 追蹤與 PostHog，而不是 OTLP。

儲存庫中的 [`packages/otel`](https://github.com/BuilderIO/agent-native/tree/main/packages/otel) 提供這個外掛程式更完整的版本，支援依訊號設定端點並驗證匯出器。它沒有發布到 npm，因此請從上面的外掛程式開始，而不是安裝它。

## 錯誤報告（Sentry） {#sentry}

設定 DSN 時，轉義 Nitro 路由處理常式的伺服器端錯誤將報告給 Sentry。如果沒有它，SDK 會默默地無操作，因此可以安全地在開發中保留環境變數未設定。瀏覽器和伺服器事件可以去同一個Sentry專案；僅當您希望所有權、數量、配額或警報路由的操作分離時，才將它們拆分為單獨的專案。

| 表面               | SDK               | 環境變數                                                      | 註解                                                    |
| ------------------ | ----------------- | ------------------------------------------------------------- | ------------------------------------------------------- |
| 瀏覽器/SPA         | `@sentry/browser` | `VITE_SENTRY_CLIENT_DSN`、`SENTRY_CLIENT_DSN` 或 `SENTRY_DSN` | 捕獲用戶端中未處理的錯誤和路由更改面包屑。              |
| Nitro伺服器        | `@sentry/node`    | `SENTRY_SERVER_DSN`或`SENTRY_DSN`                             | 捕獲 5xx 回應和 Nitro 生命週期錯誤。每個請求的使用者。  |
| `agent-native` CLI | `@sentry/node`    | _硬編碼_                                                      | 來自已發布的 CLI 二進制檔案的當機報告；使用者不可設定。 |

### 伺服器端設定 {#sentry-config}

在部署環境（Netlify 儀表板、Cloudflare 機密等）中設定 `SENTRY_SERVER_DSN` 或共用 `SENTRY_DSN`。此框架自動安裝 Nitro 外掛：

1. 啟動時呼叫 `Sentry.init` 一次（冪等 - 可以安全地從多個外掛呼叫）。
2. 透過 `getSession(event)` 對每個 API/框架請求解析使用者，並將 `id` / `email` / `username` 加上 `orgId` 標籤附加到 Sentry 的每個請求隔離範圍。跳過靜態資產路徑以避免額外的資料庫命中。
3. 使用可搜尋的 `route`、`method` 和 `userAgent` 標籤捕獲每個框架路由 5xx。

可選旋鈕：

- `SENTRY_SERVER_TRACES_SAMPLE_RATE`（浮點 `0`–`1`）— 選取加入性能跟蹤。預設為 `0`（僅限錯誤）。無效值限制為 `0`。
- `AGENT_NATIVE_RELEASE` — 覆蓋 `release` 標籤。預設為 `agent-native-server@<core-version>`。

### 範本

每個範本都會自動繼承它——無需匯入任何內容。對於 SSR 應用程式，當 `SENTRY_CLIENT_DSN`、`VITE_SENTRY_CLIENT_DSN` 或共用 `SENTRY_DSN` 在執行時可用時，伺服器會注入一個小型瀏覽器設定指令碼，因此瀏覽器捕獲不限於 Vite 建置時環境。想要自訂行為的範本（額外標籤、每個範本不同的 DSN、硬停用 Sentry）可以透過從 `server/plugins/sentry.ts` 匯出自己的外掛來覆蓋：

```ts
// server/plugins/sentry.ts
import { createSentryPlugin } from "@agent-native/core/server";
export default createSentryPlugin();
```

CLI 的硬編碼 DSN 是有意為之的 - 發布的二進制檔案需要通知家庭當機，無論執行它的環境如何。伺服器模組從不硬編碼 DSN，因為它在客戶環境中執行，操作者決定錯誤是否應該到達 Sentry。

### 隱私和 PII {#privacy}

伺服器和 CLI 都使用 `sendDefaultPii: false` 和剝離的 `beforeSend` 鉤子進行初始化：

- `request.headers.authorization`, `cookie`, `set-cookie`, `proxy-authorization`
- `request.cookies`
- `user.ip_address`（未經同意自動收集）
- `contexts.runtime_env`（行程環境快照）
- 頂級異常型別為 `ValidationError` 的任何事件（被視為預期的使用者輸入拒絕，而不是錯誤）。

透過 `setUser({ id, email, username })` 顯式設定的身分欄位將被保留。

即使啟用了內容擷取，執行失敗訊息也不會傳送至 Analytics 或 Monitoring。`$ai_error` 包含終止代碼、具名原因、是否可重試，以及根據代碼產生的固定訊息。追蹤事件省略 `error_message`、`agent_run_terminal.error_detail` 和失敗工具結果的文字；終止事件保留 `error_code` 和 `error_cause`。`agent_runs.error_detail` 與 `agent_trace_spans.error_message` 仍保存在應用程式自身的資料庫中，供擁有者權限範圍內的除錯使用。

執行與 Builder 閘道例外保留類型、代碼及堆疊框架，但使用固定訊息 `Internal Server Error`，不包含原始訊息或巢狀原因的文字。Monitoring 依應用程式、類型、堆疊框架、錯誤代碼與失敗類別分組，而非依訊息中的姓名分組。`$ai_trace_id` 仍用於連結到執行追蹤。由宿主管理的選用 OpenTelemetry 執行匯出也會省略失敗文字，並保留 `agent.error_code` 和 `agent.error_cause`。其他例外擷取維持原有行為。
