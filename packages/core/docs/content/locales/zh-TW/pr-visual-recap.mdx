# PR 視覺回顧

PR 視覺回顧是一個 GitHub Action，會把每個 pull request 都轉變成一次**視覺化程式碼審查**，不需要任何人記得手動執行指令。本頁面適合任何要安裝、設定或保護這個 Action 的人。每次推送時，LLM 編碼代理都會針對這個 PR 的 diff，執行最新捆綁的 [`visual-recap`](/docs/template-plan) 技能（或在設定 `VISUAL_RECAP_SKILL_SOURCE=repo` 時，執行你儲存庫已提交的副本），把一份結構化的回顧計畫發布到託管的 Plan 應用程式，執行期間顯示一項資訊性的 `Visual Recap` 檢查，並更新插入**一則置頂 PR 評論**，這則評論連結到互動式計畫，並直接在評論中嵌入**行內螢幕截圖**。

這不是一個確定性的 diff 渲染器。這個 action 會呼叫一個真正的編碼代理（預設是 Claude Code CLI，也可以是 OpenAI Codex CLI，或搭配 OpenAI 相容供應商的 Agent-Native Code），由它讀取變更、判斷哪些內容重要，並透過呼叫 Plan MCP 工具 `create-visual-recap` — 與 `/visual-recap` 斜線指令所使用的同一個工具 — 來撰寫回顧。你得到的是一份高空視角、schema/API/前後對照的變更檢視，而不是一整片原始 diff。

這份回顧是**資訊性且非阻塞**的。它會建立一個檢查列，讓審閱者能看到產生作業正在進行中，但它不是必要檢查，永遠不會阻擋 PR，也永遠不能取代閱讀實際的 diff。這則置頂評論是一種審閱輔助工具，而不是簽核。

## 它做了什麼

每次 PR 推送時，這個工作流程會：

1. 收集 PR base 與 head 之間的有界 diff。
2. 建立一項帶有 `Visual recap in progress` 的資訊性 `Visual Recap` GitHub 檢查。
3. 針對該 diff 執行已設定的編碼代理。代理會讀取捆綁的 `visual-recap` 技能指引（或你儲存庫固定的副本），撰寫一份回顧，並用 `create-visual-recap` 發布它。
4. 讀取代理寫入 `recap-url.txt` 的已發布計畫網址。
5. 在無頭 Chrome 中開啟該網址，並以亮色與暗色模式對渲染出的計畫進行螢幕截圖。
6. 把 PNG 上傳到 Plan 應用程式上一個已簽署的公開圖片路由。
7. 更新插入單一一則置頂 PR 評論，在旁邊連結到互動式回顧的同時，用 `<picture>` 元素**行內**嵌入螢幕截圖（透過 GitHub 的 camo 圖片代理伺服器提供）。
8. 讓 `Visual Recap` 檢查以成功、已略過或中立的狀態完成。

## 安裝方式

當你以互動方式安裝 Plan 時，Agent-Native CLI 會詢問是否要加入自動 PR 視覺回顧。回答「是」即可寫入這個 GitHub Action，或隨時明確地加入它：

```bash
npx @agent-native/core@latest skills add visual-plan --with-github-action
```

這會安裝 `visual-plan` 技能（其中包含這個 action 會執行的 `visual-recap` 技能），並把 `.github/workflows/pr-visual-recap.yml` 寫入你的儲存庫。這個工作流程會透過 `npx @agent-native/recap-cli@latest recap <subcommand>` 呼叫**已發布的 CLI 子指令** — 包括 `gate`、`collect-diff`、`block-reference`、`scan`、`build-prompt`、`publish`、`shot`、`comment`、`check` 和 `usage` — 因此不會有任何內容以輔助指令碼的形式複製進你的儲存庫。`setup` 和 `doctor` 是你在本機執行的互動式輔助工具；`gate` 則是這個工作流程在每次回顧之前執行的安全閘道步驟。

接著執行引導式設定輔助工具：

```bash
npx @agent-native/recap-cli@latest recap setup
npx @agent-native/recap-cli@latest recap doctor
```

`recap setup` 會重新整理工作流程，在能從環境變數或本機 Plan 發布權杖儲存區取得值時，使用 `gh` 設定 GitHub Actions 的 secrets/變數，並針對任何它無法設定的項目，印出確切的缺漏指令。Secret 值會透過 stdin 傳送給 `gh`，而不是透過指令參數。提交產生的工作流程檔案，並開啟一個 PR 來看它執行。

在預設情況下，這個工作流程會用 `@agent-native/recap-cli@latest` 中最新捆綁的 `visual-recap` 指引，包括這個技能附帶的任何相鄰參考檔案，來組出代理提示。如果你的儲存庫刻意自訂並固定了已提交的 `visual-recap` 資料夾，請設定儲存庫變數 `VISUAL_RECAP_SKILL_SOURCE=repo`。

## Runner 選擇

這個工作流程預設在 GitHub 託管的 `ubuntu-latest` runner 上執行。若要使用不同的託管 runner，或你自己的自行託管 runner，請把儲存庫或組織變數 `VISUAL_RECAP_RUNS_ON` 設定為一個有效的 JSON 字串，或 runner 標籤的 JSON 陣列：

```text
"ubuntu-latest"
["self-hosted", "linux", "x64", "visual-recap"]
```

JSON 引號是必要的。這項設定會選取完整 `recap` 工作的 runner。若要在引導式設定期間進行設定，把相同的 JSON 值傳給 `--runs-on`，然後用 `doctor` 驗證工作流程與 runner 的可用性：

```bash
npx @agent-native/recap-cli@latest recap setup --runs-on '["self-hosted","linux","x64","visual-recap"]'
npx @agent-native/recap-cli@latest recap doctor
```

輕量的安全閘道另外預設使用 GitHub 託管的 `ubuntu-latest`。停用 GitHub 託管 runner 的儲存庫，可以把 `VISUAL_RECAP_GATE_RUNS_ON` 設定為**單一、純文字的 runner 標籤**（不是 JSON），或在設定時傳入 `--gate-runs-on visual-recap-gate`。這個可重複使用的工作流程會以同樣的值作為它的 `gate-runs-on` 輸入曝露出來。這樣可以避免在 GitHub 排程這個閘道之前，還要解析動態 JSON。這個自訂標籤只會用於由 `OWNER`、`MEMBER` 或 `COLLABORATOR` 撰寫的同儲存庫 PR。Fork 與所有其他作者，在工作開始前都會被強制使用 GitHub 託管的 `ubuntu-latest`；在僅有自行託管 runner 的儲存庫中，這些不受信任的執行可能會保持未排程狀態，而不會碰觸到自行託管的機器。

`recap doctor` 會拒絕格式錯誤或不支援的 JSON，並在 GitHub 沒有曝露出符合每個已設定標籤的線上 runner 時回報。Runner 的註冊、安裝、升級、容量與維護仍然是你的責任；Agent-Native 只會選取標籤，不會提供或操作 runner。

**安全性：** 建議使用專用、用完即棄的自行託管 runner。自訂的閘道 runner 只會收到受信任的同儲存庫 PR 事件。內建的閘道不會簽出 PR 的程式碼樹；它只評估工作流程邏輯與 GitHub PR 中繼資料。一台常駐機器仍會在多個工作之間保留程序狀態，所以不要把它與無關的工作負載共用。對於不受信任的公開或 fork PR 作者，這個工作流程會在派送任何自行託管閘道或完整回顧工作之前，以失敗封閉的方式處理。請勿削弱這道邊界，也不要把不受信任的貢獻導向一台常駐 runner。

## 後端選擇

用 `VISUAL_RECAP_AGENT` 這個儲存庫變數，選擇要用哪個編碼代理來執行這個技能：

| `VISUAL_RECAP_AGENT` | 編碼代理                                 | 所需的 API 金鑰         | 所需的變數                                     |
| --------------------- | ---------------------------------------- | ------------------------ | ---------------------------------------------- |
| `claude` _(預設)_     | Claude Code CLI                          | `ANTHROPIC_API_KEY`      | —                                               |
| `codex`               | OpenAI Codex CLI                         | `OPENAI_API_KEY`         | —                                               |
| `openai-compatible`   | Agent-Native Code + 相容供應商           | `VISUAL_RECAP_API_KEY`   | `VISUAL_RECAP_BASE_URL`、`VISUAL_RECAP_MODEL`  |

如果沒有設定這個變數，這個 action 會使用 `claude`。

## 模型與推理

除了後端之外，以下這些儲存庫變數可以調整代理的執行方式：

- **`VISUAL_RECAP_MODEL`** 固定傳給 CLI 的模型（`--model`） — 例如 Codex 用 `gpt-5.6-luna`、Claude 的模型 id，或 DeepSeek 用 `deepseek-chat`。對 `openai-compatible` 來說這是必要的。對於 **Claude** 後端，不設定這個值現在預設會使用 `claude-sonnet-5`；明確設定這個變數即可改用其他 Claude 模型，例如較便宜的 `claude-haiku-4-5`。對於 **Codex** 後端，不設定則會使用 Codex CLI 自己的預設模型。
- **`VISUAL_RECAP_REASONING`** 設定推理深度：`none`、`minimal`、`low`、`medium`、`high` 或 `xhigh`。這個變數適用於 Codex 後端；Claude 的推理由模型自行決定，因此這個變數在那裡會被忽略。
- **`VISUAL_RECAP_BASE_URL`** 選擇 `openai-compatible` 後端所使用的 HTTP(S) 基底網址。請使用該供應商的 OpenAI 相容端點，例如 DeepSeek 或 Kimi，且不要把憑證嵌入網址中。
- **`VISUAL_RECAP_SKILL_SOURCE`** 控制提示的新鮮度：`auto`／未設定會使用最新捆綁的技能指引，而 `repo` 則會固定使用已提交的儲存庫本機 `visual-recap` 技能資料夾。

舉例來說，若要用高推理層級的 GPT-5.6 Sol 在 Codex 上執行回顧，請設定儲存庫變數 `VISUAL_RECAP_AGENT=codex`、`VISUAL_RECAP_MODEL=gpt-5.6-sol` 和 `VISUAL_RECAP_REASONING=high`。

對於 DeepSeek，請設定 `VISUAL_RECAP_AGENT=openai-compatible`、`VISUAL_RECAP_BASE_URL=https://api.deepseek.com/v1`、`VISUAL_RECAP_MODEL=deepseek-chat`，以及 `VISUAL_RECAP_API_KEY` 這個 secret。Kimi 的做法相同，只要換成它自己的 OpenAI 相容基底網址與模型 id 即可。其他 OpenAI 相容供應商也是用同樣這三項設定。

## 成本

每一次回顧的執行，都是一次讀取真實 diff 的完整代理式編碼代理工作階段，而不是廉價的範本化摘要，所以它的成本會隨模型選擇與執行頻率而變動：

- **每次 PR 推送都是一次完整的工作階段。** 預設觸發條件是 `synchronize`，所以一個被推送十次的 PR，就會讓代理執行十次。
- **每次都是整個 PR**，而不只是自上次執行以來的提交 — 成本會隨 PR 總大小而變動，而不是隨增量 diff 大小變動。
- **diff 輸入上限約為 600KB。** 這限制了每次執行的最壞情況，但大型 diff 的成本仍然明顯高於小型 diff。
- **失敗時會自動重試一次**，這可能會讓一次暫時性失敗的執行成本大約加倍。

若要降低成本：

- **固定使用較便宜的模型。** 對於 Claude，簡單或小型的儲存庫可以設定 `VISUAL_RECAP_MODEL=claude-haiku-4-5` — 這是最便宜的 Claude 層級；`claude-sonnet-5`（預設值）則是均衡層級。
- **改用搭配較便宜模型的 Codex。** 設定 `VISUAL_RECAP_AGENT=codex`，搭配 `VISUAL_RECAP_MODEL=gpt-5.6-luna`（最便宜的 GPT-5.6 層級）或 `gpt-5.6-terra`（中間層級），並設定 `VISUAL_RECAP_REASONING=low` 以進一步降低推理 token 的花費。推理深度只適用於 Codex。
- **改指向較便宜的 OpenAI 相容供應商。** 設定 `VISUAL_RECAP_AGENT=openai-compatible`，並用 `VISUAL_RECAP_BASE_URL`/`VISUAL_RECAP_MODEL`/`VISUAL_RECAP_API_KEY` 指向 DeepSeek、Kimi，或任何其他 OpenAI 相容端點。
- **要求明確的 PR 標籤。** 設定 `VISUAL_RECAP_REQUIRED_LABELS=visual recap`，讓工作流程保持已安裝狀態，但在 PR 有那個標籤之前先跳過回顧。當有多個標籤都應該可以選用時，使用以逗號分隔的清單，例如 `visual recap,recap`。套用清單中的標籤會立即喚醒這個工作流程。
- **降低回顧頻率。** 把已安裝工作流程的 `on.pull_request.types`，從 `[opened, synchronize, reopened, ready_for_review, labeled, closed]` 修改為 `[opened, ready_for_review, closed]`，讓它只在 PR 開啟與合併時進行回顧，而不是每次推送都執行。

每次執行都會記錄它實際的花費：這個工作流程的 `recap usage` 步驟，會把 token 與成本使用量附加到已發布的計畫上，讓你可以查看每次執行的實際花費，而不必用猜的。

## Secrets 與變數 {#secrets-and-variables}

在你儲存庫的 **Settings → Secrets and variables → Actions** 中設定這些項目。

### 預設後端所需的 Secrets

| Secret              | 用途                                                                                     |
| ------------------- | ---------------------------------------------------------------------------------------- |
| `PLAN_RECAP_TOKEN`  | 由 `npx @agent-native/core@latest connect` 鑄造的可撤銷權杖。授權發布回顧計畫與上傳螢幕截圖。 |
| `ANTHROPIC_API_KEY` | 預設 Claude Code 後端所使用的 LLM 金鑰。                                                  |

**團隊：請使用組織服務權杖。** 個人權杖與鑄造它的人綁定 — 如果那個人離開組織或撤銷了他們的權杖，每個使用該 secret 的儲存庫都會開始出現 401 失敗，而且由 CI 建立的計畫，擁有者會是那個人而不是團隊。組織服務權杖則歸你的**組織**所有：它會以服務主體的身分運作（`svc-<name>@service.<orgId>`），不會因任何個人離開而失效，它所發布的回顧對整個組織可見，而且任何組織擁有者或管理員都可以列出或撤銷它。鑄造一個服務權杖（僅限組織擁有者/管理員）：

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --service-token pr-recap
```

這個指令會在瀏覽器中驗證你的身分，然後只印出一次這個服務權杖 — 請把它儲存成 `PLAN_RECAP_TOKEN` 這個 secret。之後可以用 Plan 應用程式上的 `list-org-service-tokens` 和 `revoke-org-service-token` actions 來管理它。

**個人使用：個人權杖仍然可行。** 針對你的 Plan 應用程式，用 `npx @agent-native/core@latest connect` 鑄造一個。對於託管應用程式，這也會寫入一個本機發布權杖檔案，讓 `npx @agent-native/recap-cli@latest recap setup` 可以讀取：

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --client codex
npx @agent-native/recap-cli@latest recap setup
```

如果你偏好手動設定，把這個權杖貼到 GitHub secret 中即可。範例中請只使用像 `plan_recap_xxxxxxxxxxxxxxxx` 這樣的佔位符 — 絕對不要提交真正的權杖。

| `RECAP_CLI_VERSION`              | `latest`                                                          | 變數。固定這個工作流程所安裝的 `@agent-native/recap-cli` 版本 — 例如 `1.5.0`。詳見[版本固定](#version-pinning-copy-variant)。                                                                                        |
| `PLAN_RECAP_APP_URL`             | `https://plan.agent-native.com`                                   | Secret。只有在把 Plan 應用程式自行託管於不同來源時才需要。                                                                                                                                                             |

這個工作流程會自動偵測要如何呼叫它的輔助 CLI（在這個 monorepo 內部使用本機原始碼，其他地方則使用已發布的 `@agent-native/recap-cli`），因此沒有 `RECAP_CLI` 這個變數需要設定。

## 評論中的行內螢幕截圖

在代理發布回顧之後，這個工作流程會在無頭 Chrome 中以亮色與暗色模式，為渲染出的計畫截圖，並把 PNG 上傳到 Plan 應用程式上一個已簽署的公開圖片路由。接著，這則置頂 PR 評論就會用 `<picture>` 元素**行內**嵌入這些螢幕截圖 — GitHub 會透過它的 camo 代理伺服器重新提供這些圖片，因此審閱者不需要開啟任何東西，就能直接在評論中看到符合自己 GitHub 主題的預覽。完整互動式計畫的連結就緊鄰在旁，供他們想要進一步探索、評論或標註時使用。

## Fork PR

### 預設行為（不需要任何動作）

主要的 `pr-visual-recap.yml` 工作流程，會在純粹的 `pull_request` 觸發條件上啟動，**而不是** `pull_request_target`。因此 fork PR 執行時**無法存取儲存庫的 secrets**，所以工作流程找不到 `PLAN_RECAP_TOKEN`，並乾淨地無動作結束 — 不會有發布失敗，也不會有憑證外洩。對於來自同一個儲存庫分支的 PR，由於可以取得 secrets，回顧就會自動執行。

這也代表你可以在 secrets 存在**之前**先合併這個工作流程檔案：在沒有設定權杖的情況下，每次執行都會安靜地無動作結束，直到你設定好 secrets 為止。`gate` 步驟也會自動跳過草稿 PR 與由機器人建立的 PR，因此這兩者預設都不會觸發回顧執行。

### 透過標籤閘控的 fork 工作流程選擇加入

如果你想為 fork PR 產生回顧，還有第二個工作流程檔案可用：`.github/workflows/pr-visual-recap-fork.yml`。它使用 `pull_request_target`（會以 base 儲存庫的 secrets 執行），但絕不會簽出或執行 fork 的程式碼。GitHub 作者關聯為 `OWNER`、`MEMBER` 或 `COLLABORATOR` 的受信任 fork 作者會自動執行。來自外部的 fork PR，則需要透過一個全新的 `recap` 標籤事件，明確地按**每個 head 進行維護者選擇加入**，回顧代理才會執行。

要安裝它，請把這個檔案從 [BuilderIO/agent-native](https://github.com/BuilderIO/agent-native/blob/main/.github/workflows/pr-visual-recap-fork.yml) 複製到你儲存庫的 `.github/workflows/` 目錄中，與現有的 `pr-visual-recap.yml` 放在一起。同一套後端設定也適用，包括使用 OpenAI 相容供應商時的 `VISUAL_RECAP_API_KEY`、`VISUAL_RECAP_BASE_URL` 和 `VISUAL_RECAP_MODEL`。

### 標籤閘道的運作方式

1. fork 貢獻者開啟一個 PR。一般的 `pull_request` 工作流程會跳過，因為 GitHub 不會把 secrets 提供給 fork 的執行。
2. fork 工作流程會檢查 PR 作者的關聯。受信任的作者（`OWNER`、`MEMBER` 或 `COLLABORATOR`）會在 open、synchronize、reopen 與 ready-for-review 事件上自動執行。
3. 外部貢獻者則需要維護者先審閱目前的 diff（特別是針對可能是提示注入形式的內容 — 見下方說明），然後為這個 PR 套用 `recap` 標籤。
4. 外部貢獻者的標籤閘道是以 head SHA 為單位的：如果貢獻者推送了更多提交，下一個 synchronize 事件就會跳過，直到維護者在審閱過新的 diff 之後，重新移除並再次套用 `recap` 標籤為止。

### fork 工作流程會做什麼，以及絕不會做什麼

| 這個工作流程「會」做的事                                                                    | 這個工作流程「絕不會」做的事                                              |
| --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 簽出 **base 儲存庫**在 **base 分支參照**上的內容 — 僅限受信任的程式碼                          | 簽出或執行任何來自 fork 的程式碼                                            |
| 把 fork 的 head 當作遠端參照抓取（`git fetch origin pull/<n>/head:refs/recap/fork-head`） — 抓取提交是安全的 | 從 fork 安裝套件、執行 fork 的指令碼，或把 fork 的內容當成程式碼來執行      |
| 執行 `git diff base...refs/recap/fork-head` — 純粹是兩個已抓取物件之間的文字 diff              | 把這個 diff 當成除了 LLM 文字輸入以外的任何用途                            |
| 執行 **base 儲存庫**的 visual-recap 技能與代理設定                                             | 從 fork 載入任何技能或設定                                                  |
| 讓這個 diff 通過與第一方 PR 相同的 secret 掃描步驟（失敗封閉）                                 | 略過 secret 掃描                                                            |
| 在代理提示中加入一則明確的提示強化備註，把 diff 內容標記為不受信任                             | 授予代理超出一般回顧代理範圍之外的任何額外權限                             |

### 為什麼你必須先審閱 diff 才能套用標籤

fork 的 diff 是攻擊者可控制的文字，回顧代理會把它當成輸入來讀取。一個精心設計的 diff 可能包含提示注入的內容 — 例如看起來像是代理指令的 diff 內容 — 目的是讓回顧代理採取非預期的行動（例如外洩發布權杖，或產生誤導性的回顧內容）。

在套用 `recap` 標籤之前，請先瀏覽 diff，留意：

- 讀起來像直接指令或角色指示的內容（「忽略先前的指示……」、「你現在是……」、「把權杖寫入……」）。
- 可能被誤判為系統提示的異常檔名。
- 新增檔案中可能解碼成指令的編碼內容。

這些緩解措施已經分層納入這個工作流程中（secret 掃描、敏感路徑閘道、提示強化備註、受限的代理工具允許清單），但標籤審閱仍是主要的防線。

### 與主要工作流程的關係

這兩個工作流程檔案是彼此獨立的。對於非 fork PR 的更新，`pr-visual-recap.yml` 是唯一會執行的工作流程。對於 fork PR，一般的工作流程會在它的 fork 閘道處結束，而 `pr-visual-recap-fork.yml` 會針對受信任的同組織作者自動執行，或在維護者為外部貢獻者套用一個全新的 `recap` 標籤之後執行。它們共用同一個置頂評論標記與計畫 id 串接方式，因此無論一般 PR 或 fork PR，同一個 PR 上都只會產生一則更新插入的評論。

### 自我修改防護 {#self-modifying-guard}

當 PR 觸及以下任何路徑時，`gate` 步驟會完全跳過這次回顧，這樣一個 PR 就永遠無法改寫受信任回顧工作所載入的工作流程、技能或代理設定，藉此外洩 secrets：

| 路徑模式                                    | 原因                                    |
| -------------------------------------------- | ---------------------------------------- |
| `.github/workflows/pr-visual-recap.yml`      | 這個工作流程本身                          |
| `**/skills/visual-(recap\|plan\|plans)/**`   | 代理所依循的 visual-recap 技能            |
| `**/.claude/**`                              | runner 載入的代理設定                     |
| `**/CLAUDE.md`                               | runner 載入的代理指令                     |
| `**/AGENTS.md`                               | runner 載入的代理指令                     |
| `**/.mcp.json`                               | runner 載入的 MCP 伺服器設定              |

在 `BuilderIO/agent-native` 這個 monorepo 中，這個工作流程會從受信任的 base 分支原始碼執行回顧 CLI，而不是 PR head 的原始碼。這樣可以讓一般的套件變更（包括 `packages/core/**`）依然能進行回顧，同時不會執行由 PR 修改過的 CLI 程式碼。

## 本機檔案隱私模式

這個 GitHub Action 是為託管、可共用的 PR 審閱而設計的。如果你想要一份回顧，但不想把回顧內容傳送到 Agent-Native Plan 資料庫，可以改為在本機以本機檔案模式執行同一套輔助流程：

```bash
npx @agent-native/recap-cli@latest recap collect-diff --base main --head HEAD --out recap.diff --stat recap.stat
npx @agent-native/recap-cli@latest recap scan --diff recap.diff
npx @agent-native/recap-cli@latest recap build-prompt --pr 123 --diff recap.diff --stat recap.stat --local-files --local-dir plans/pr-123-visual-recap
```

把產生的 `recap-prompt.md` 交給你的編碼代理。在本機檔案模式下，這份提示會指示代理寫入 `plans/pr-123-visual-recap/plan.mdx`，以及可選的視覺檔案，然後執行：

```bash
npx @agent-native/core@latest plan local serve --dir plans/pr-123-visual-recap --kind recap --open
```

回傳的網址會開啟託管的 Plan UI，同時瀏覽器會從 localhost 橋接讀取回顧的 MDX。回顧內容不會被寫入託管的 Plan 資料庫，而且這個網址只在執行橋接的那台機器上有效。如果你用相同的 `PLAN_LOCAL_DIR` 在本機執行 Plan 應用程式，`/local-plans/pr-123-visual-recap` 這條路由也同樣有效。以儲存庫為後盾的資料夾，可以用 `/local-plans/pr-123-visual-recap?path=plans%2Fpr-123-visual-recap` 開啟。在你明確發布之前，這個模式會停用託管的置頂 PR 評論、行內螢幕截圖上傳、使用量附加，以及瀏覽器評論。

## 這是資訊性的，不是一道閘道

這份回顧是疊加在一般 PR 流程之上的審閱輔助工具：

- 它會顯示一個 `Visual Recap` 檢查列以提高能見度，但這**絕不是一項必要檢查**，也永遠不會阻擋合併。
- 產生或發布失敗時會以中立狀態完成，並以一則說明性的置頂評論呈現，而不是在無關的程式碼上顯示紅色 X。
- 這份回顧與它的螢幕截圖**並不代表 diff 已經被審閱過**。審閱者仍然需要閱讀實際變更的程式碼行。

## 版本固定（複製版本） {#version-pinning-copy-variant}

預設情況下，複製版本的工作流程會在執行時安裝 `@agent-native/recap-cli@latest`，讓每次回顧執行都能自動取得最新的 CLI。如果你的 CI 需要可重現的工具鏈，請設定 **`RECAP_CLI_VERSION`** 這個儲存庫變數來固定所安裝的版本：

1. 前往你儲存庫的 **Settings → Secrets and variables → Actions → Variables**。
2. 建立一個名為 `RECAP_CLI_VERSION` 的變數，值例如 `1.5.0`。

這個變數是選用的。不設定它（或設定為 `latest`）即可追蹤最新版本。

對於可重複使用的呼叫端版本，請改用 `cli-version` 輸入（詳見可重複使用章節中的[版本固定](#version-pinning)）。

## Secret 掃描允許清單

在發布回顧之前，這個工作流程會執行 `npx @agent-native/recap-cli@latest recap scan`，偵測 diff 中可能存在的 secrets。任何 diff 符合已知 secret 樣式的 PR，都會被一則說明性評論擋下 — 這份回顧不會發布，也不會有任何 diff 內容被送往編碼代理。

在少數情況下，儲存庫會有刻意設計的測試固定資料，或是表面上看起來像 secret 樣式的非 secret 字串（例如測試檔案中的固定金鑰）。若要抑制誤判，請在儲存庫根目錄建立 `.github/recap-scan-allowlist`。

### 格式

每一行非空白、非註解的內容，可以是一個**字面子字串**，或是一個 **`/regex/flags`** 樣式：

```
# Lines starting with # are comments.

# Literal substring — any diff line containing this string is allowed.
sk-test-fixture1234567890abcdef

# Regex pattern — written as /pattern/flags (JS syntax).
/^.STRIPE_KEY=sk-test-/i

# Another literal.
EXAMPLE_API_KEY=placeholder-value
```

規則：

- 當某一行包含這個字面字串，或整行符合這個正規表示式時，這一行就會被**抑制**（允許通過）。
- 這個檔案採**失敗封閉**：如果它不存在，就不會套用任何抑制 — 掃描器的行為會和之前一樣。
- 空檔案等同於沒有檔案。
- 格式錯誤的正規表示式行，會被當成字面字串處理。

這份允許清單只會被 secret 掃描閘道參考。它不會影響編碼代理能讀取的內容 — 只要這個閘道通過，代理都會收到完整的 diff。

## 採用可重複使用的工作流程

### 為什麼要使用可重複使用版本？

預設的安裝程式會把完整的、約 360 行的工作流程 YAML 複製進你的儲存庫（**複製**選項）。對於氣隙隔離的儲存庫，或需要稽核每一行執行內容的儲存庫來說，這是正確的選擇。缺點是錯誤修正與改進永遠不會自動送達 — 你需要在每次發行後手動重新執行 `npx @agent-native/recap-cli@latest recap setup`。

**可重複使用**選項則會改寫入一個精簡的、約 20 行的呼叫端。它會透過 `uses:` 委派給 `BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml`。每個呼叫端在工作流程執行時，都會自動取得最新的邏輯，不需要任何本機更新。

|                                | 複製（預設）                | 可重複使用                      |
| ------------------------------ | ---------------------------- | -------------------------------- |
| 你儲存庫中的工作流程大小        | 約 360 行                    | 約 20 行                         |
| 自動取得修正                    | 否 — 需重新執行 `recap setup` | 是                                |
| 氣隙隔離／完整可稽核性          | 是                            | 否                                |
| 可固定到特定版本                | 只能透過本機編輯              | 是 — 在 `uses:` 中設定 `@v1.2.3` |

### 呼叫端片段

這是 `npx @agent-native/recap-cli@latest recap setup --reusable` 所寫入的內容（你也可以手動貼上）：

```yaml
name: PR Visual Recap

# Thin caller — the full workflow logic lives in BuilderIO/agent-native.
# Fixes and improvements reach this repo automatically on each run.
# To pin a specific version for reproducibility replace '@main' with a
# tag or SHA, e.g. '@v1.2.3' or '@abc1234'.

on:
  pull_request:
    types: [opened, synchronize, reopened, ready_for_review, labeled, closed]

jobs:
  visual-recap:
    if: github.event.action != 'labeled' || vars.VISUAL_RECAP_REQUIRED_LABELS != ''
    permissions:
      actions: write
      contents: read
      checks: write
      issues: write
      pull-requests: write
    uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@main
    secrets:
      PLAN_RECAP_TOKEN: ${{ secrets.PLAN_RECAP_TOKEN }}
      ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
      OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
      VISUAL_RECAP_API_KEY: ${{ secrets.VISUAL_RECAP_API_KEY }}
      PLAN_RECAP_APP_URL: ${{ secrets.PLAN_RECAP_APP_URL }}
    with:
      agent: ${{ vars.VISUAL_RECAP_AGENT || 'claude' }}
      model: ${{ vars.VISUAL_RECAP_MODEL || '' }}
      base-url: ${{ vars.VISUAL_RECAP_BASE_URL || '' }}
      reasoning: ${{ vars.VISUAL_RECAP_REASONING || '' }}
      skill-source: ${{ vars.VISUAL_RECAP_SKILL_SOURCE || 'auto' }}
      runs-on: ${{ vars.VISUAL_RECAP_RUNS_ON || '"ubuntu-latest"' }}
      gate-runs-on: ${{ vars.VISUAL_RECAP_GATE_RUNS_ON || 'ubuntu-latest' }}
      required-labels: ${{ vars.VISUAL_RECAP_REQUIRED_LABELS || '' }}
      # cli-version: "latest"  # pin to a specific @agent-native/recap-cli version
```

[Secrets 與變數](#secrets-and-variables)中描述的同一組 secrets 與變數同樣適用 — 在你的儲存庫設定中，用和複製版本相同的方式設定它們。這個可重複使用的呼叫端，會透過它的 JSON `runs-on` 輸入，把 `VISUAL_RECAP_RUNS_ON` 轉發給完整的回顧工作；透過它的純文字標籤 `gate-runs-on` 輸入，把 `VISUAL_RECAP_GATE_RUNS_ON` 轉發給僅處理中繼資料的閘道；並透過 `required-labels`，把 `VISUAL_RECAP_REQUIRED_LABELS` 轉發給選用的 PR 標籤閘控。這個閘道 runner 輸入只用於受信任的同儲存庫作者；其他 PR 則使用 GitHub 託管的 `ubuntu-latest`。省略 runner 輸入會保留它們的 `ubuntu-latest` 預設值；省略必要標籤則會保留自動回顧行為。

### 透過 CLI 安裝

```bash
# Write the thin caller instead of the full copy:
npx @agent-native/recap-cli@latest recap setup --reusable

# Or with a pinned ref for reproducibility:
npx @agent-native/recap-cli@latest recap setup --reusable --ref v1.2.3
```

兩種版本都會把工作流程寫入 `.github/workflows/pr-visual-recap.yml`。如果那裡已經有一個不同的既有工作流程，這個指令會拒絕執行，並告訴你要傳入 `--force` 才能覆寫。

寫入之後，照常執行 `npx @agent-native/recap-cli@latest recap doctor`，確認 secrets 已經設定好。

### 版本固定 {#version-pinning}

預設情況下，這個呼叫端會參照 `@main`，永遠使用這個可重複使用工作流程最新發布的版本。對於需要可重現 CI 的正式環境儲存庫，請固定到一個標籤或 SHA：

```yaml
uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@v1.2.3
```

`cli-version` 這個輸入，控制的是這個工作流程內部會執行哪個 `@agent-native/recap-cli` 版本 — 保留為 `"latest"` 即可追蹤最新發行版，或固定為一個版本字串（例如 `"1.5.0"`）以取得完整的可重現性。

### workflow_call 事件脈絡

`workflow_call` 工作流程會繼承**呼叫端**的事件脈絡。這個可重複使用的工作流程，使用 `github.event.pull_request.*` 運算式來讀取 PR 編號、head SHA、base SHA、合併時間戳記與 PR 中繼資料 — 這些只有在呼叫端以 `pull_request` 觸發時才能正確運作。上面的呼叫端片段已經包含正確的事件類型。之所以包含 `closed` 事件，是為了讓已合併 PR 的回顧能被標記上 `merged_at`，之後可以搜尋為已出貨的工作。

不要用 `workflow_dispatch` 或 `push` 來觸發呼叫端 — 這些事件不會攜帶 `pull_request` 負載，而這個閘道會以「no pull_request payload」跳過這次回顧。
