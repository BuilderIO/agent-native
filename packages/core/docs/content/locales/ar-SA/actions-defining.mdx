# تعريف Actions

يبدأ كل action باستدعاء `defineAction()`. فهو يجمع وصفًا للوكيل، ومخططًا يتحقق من صحة المدخلات، ودالة `run` تقوم بالعمل الفعلي، بحيث تستدعي واجهة المستخدم والوكيل الكود نفسه تمامًا.

## خيارات المخطط {#schemas}

يقبل `schema` أي مكتبة متوافقة مع [Standard Schema](https://standardschema.dev):

- **Zod** (v4): الخيار الأكثر شيوعًا، مع أفضل استنتاج للأنواع وتحويل تلقائي إلى JSON Schema.
- **Valibot**: خيار جيد عندما يهم حجم الحزمة.
- **ArkType**: خيار جيد إذا كنت تفضّل صيغته.

يقوم المخطط بمهمتين. يحوّل إلى JSON Schema لتعريف أداة Claude API، ويتحقق من صحة المدخلات في وقت التشغيل قبل إطلاق `run()`. لا تصل المدخلات غير الصالحة أبدًا إلى المعالج الخاص بك.

## التحقق من صحة القيمة المرجعة {#output-schema}

يتحقق `schema` من صحة _المدخلات_. للتحقق أيضًا مما **تُرجعه** action، مرّر `outputSchema` (أي مخطط متوافق مع Standard Schema: Zod، أو Valibot، أو ArkType، السطح نفسه المستخدم في `schema`). يتحقق إطار العمل من صحة المدخل قبل `run()` ومن صحة النتيجة بعد أن يُحلّ `run()`.

```ts
export default defineAction({
  description: "Summarize a thread.",
  schema: z.object({ threadId: z.string() }),
  outputSchema: z.object({
    summary: z.string(),
    messageCount: z.number(),
  }),
  outputErrorStrategy: "warn", // default
  run: async ({ threadId }) => {
    /* ...returns { summary, messageCount } ... */
  },
});
```

`outputErrorStrategy` controls what happens on a mismatch:

| الاستراتيجية | السلوك عند عدم التطابق                                                                         |
| ------------ | ---------------------------------------------------------------------------------------------- |
| `"warn"`     | **الافتراضي.** ينفّذ `console.warn` للمشكلات ويُرجع النتيجة **الأصلية** دون تغيير. غير معطِّل. |
| `"strict"`   | يطرح خطأ واضحًا، بحيث يسهل ملاحظة أي خلل في الـ action.                                        |
| `"fallback"` | يُرجع قيمة `outputFallback` المقدَّمة بدلاً من النتيجة غير الصالحة.                            |

عندما تنجح `run()`، يُرجع إطار العمل القيمة التي تم التحقق من صحتها، بحيث تسري أي قيم افتراضية أو تحويلات على `outputSchema`، بالطريقة نفسها التي تسري بها على المدخل. عندما لا تمرّر `outputSchema`، تبقى القيمة المرجعة دون تغيير.

## إعداد HTTP {#http}

بشكل افتراضي، يُعرَض كل action كـ `POST /_agent-native/actions/<name>`. تجاوز ذلك عبر خيار `http`:

```ts
export default defineAction({
  description: "Get details for a lead.",
  schema: z.object({ leadId: z.string() }),
  http: { method: "GET" },
  run: async ({ leadId }) => {
    return await db.select().from(leads).where(eq(leads.id, leadId));
  },
});
```

بالنسبة إلى action من نوع `GET`، يُمرَّر `leadId` كمعلمة استعلام: `/_agent-native/actions/get-lead?leadId=abc`.

POST هو الافتراضي، ويجعله `http: { method: "GET" }` GET. تستدعي خطافات React و`callAction()` دائمًا هذا المسار بالاسم، بغض النظر عن أي تجاوز لـ `http.path`. يمكن للأنظمة الخارجية استدعاء المسار نفسه برمز حامل طويل الأمد. راجع [HTTP API](/docs/http-api).

</Endpoint>

- **`http: { method: "GET" | "POST" | "PUT" | "DELETE" }`**: الافتراضي `POST`. تُعلَّم actions من نوع `GET` تلقائيًا بـ `readOnly`، لذا لا يؤدي الاستدعاء الناجح إلى تحفيز إعادة تحديث الاستقصاء في واجهة المستخدم.
- **`http: { path: "..." }`**: يتجاوز عنوان URL المثبَّت تحت `/_agent-native/actions/`. الافتراضي هو اسم الملف. لا يغيّر هذا التجاوز العنوان إلا للمستدعين المباشرين عبر HTTP. تستدعي `useActionQuery()` و`useActionMutation()` و`callAction()` دائمًا `/_agent-native/actions/<name>`، بغض النظر عن هذا التجاوز، لذا فإن تجاوز المسار يجعل هذه الخطافات تُرجع 404. استخدم تجاوز المسار فقط للمستدعين الخارجيين عبر HTTP. لاحظ أيضًا أن أجزاء المسار `:param` في مسار التجاوز لا تُحلَّل إلى وسائط `run()`. فقط معلمات سلسلة الاستعلام وحقول جسم JSON تُحلَّل.
- **`http: false`**: يعطّل نقطة نهاية HTTP بالكامل. فقط الوكيل وCLI يمكنهما استدعاء الـ action.
- **`readOnly: true`**: يتخطى إعادة تحديث الاستقصاء صراحة، حتى لأجل actions من نوع POST لا تغيّر أي شيء. هذا ليس تحكمًا في الوصول. فهو لا يقيّد من يمكنه استدعاء الـ action، ولا يؤثر على `useActionQuery()` أو `useActionMutation()` أو أي خطاف عميل. تأثيراه الوحيدان هما كبت حدث إعادة التحديث بعد الاستدعاء، واستبعاد الـ action من تدقيق الكتابة. لإخفاء action عن النموذج، استخدم `agentTool: false`. للتحكم في من يمكنه استدعاءه، استخدم خيارات المصادقة والوصول في [الوصول والتخويل](/docs/actions-access-control).
- **`parallelSafe: true`**: يسمح لـ action يغيّر البيانات بالعمل في الوقت نفسه مع استدعاءات أدوات أخرى في الدور نفسه. لا تضبط هذا إلا عندما يكون تشغيل الـ action بالتزامن آمنًا ولا يعتمد على الترتيب. تُسلسَل actions التي تغيّر البيانات بشكل افتراضي.

## إفشال إجراء {#failing}

يبلّغ الإجراء عن الفشل عبر الطرح. أما إعادة `{ error: "..." }` فتبدو نجاحًا لكل جزء من إطار العمل، لذا لا تحسبها قواطع إعادة المحاولة لدى الوكيل أبدًا، ويُسجَّل الاستدعاء كأثر جانبي مكتمل.

ما تطرحه هو ما يحدد مقدار ما يبقى من الرسالة. يطرح `fail()` خطأ `ActionContractError`، وهذا النوع تحديدًا هو السبب الوحيد لوصول النص إلى المستدعي. أما `throw new Error("No such email")` المجرد فلا يمكن تمييزه عن عطل في Postgres أو في خدمة أعلى السلسلة، لذا يستبدله مسار الإجراء بخطأ 500 عام `"Internal server error"`، ويُبقي الرسالة الحقيقية في سجل الخادم، ويبلّغ عنها إلى تتبّع الأخطاء. احتفظ بالطرح المجرد للأعطال الداخلية الحقيقية. فهذا ما وُجد الخطأ 500 من أجله.

يقبل `fail()` رسالة وكائن خيارات:

- **message**: النص الذي يقرأه المستدعي. اكتبه لشخص، لا لسجلّ.
- **options.errorCode**: رمز ثابت مقروء آليًا. القيمة الافتراضية `"action_failed"`.
- **options.statusCode**: حالة HTTP لمسار الإجراء. القيمة الافتراضية `400`.
- **options.details**: سياق منظَّم وآمن للمستدعي. لا تضع هنا أسرارًا أو مخرجات خام من مشغّل قاعدة البيانات.

أبسط استدعاء لا يحتاج سوى رسالة:

```ts
import { defineAction, fail } from "@agent-native/core/action";
import { eq } from "drizzle-orm";
import { z } from "zod";

import { getDb, schema } from "../server/db/index.js";

export default defineAction({
  description: "Reply to an email thread in the user's voice.",
  schema: z.object({
    emailId: z.string().describe("The id of the email to reply to."),
    body: z.string().describe("The reply body, in markdown."),
  }),
  run: async ({ emailId, body }) => {
    const db = getDb();
    const [email] = await db
      .select()
      .from(schema.emails)
      .where(eq(schema.emails.id, emailId));
    if (!email) fail("That email is no longer in the mailbox.");
    await db.insert(schema.replies).values({ emailId, body });
    return { ok: true, emailId };
  },
});
```

تسمية السبب هي ما يتيح لواجهة المستخدم التفرّع على الفشل بدلًا من طباعته فقط. ويبقى كل من الرمز والحالة عبر طبقة النقل:

```ts
if (!email) {
  fail("That email is no longer in the mailbox.", {
    errorCode: "email_not_found",
    statusCode: 404,
  });
}
```

يستقبل المتصفح `{ error, errorCode, details }`. وتُظهرها `useActionQuery()` و`useActionMutation()` و`callAction()` جميعًا ككائن `Error` يحمل `status` و`errorCode` و`details` و`actionMessage`.

يحتفظ `error.message` بالبادئة `Action <name> failed:`، وهي بادئة تناسب سجل الطرفية وتبدو في غير موضعها داخل إشعار منبثق. تعيد `actionErrorMessage()` النص الذي كتبه الإجراء فقط، أو `undefined` إن لم يكتبه أحد:

```tsx
import {
  actionErrorMessage,
  useActionMutation,
} from "@agent-native/core/client/hooks";

const reply = useActionMutation("reply-to-email", {
  onError: (error) =>
    toast.error(actionErrorMessage(error) ?? t("email.replyFailed")),
});
```

انقطاع الشبكة، وصفحة الخطأ بصيغة HTML من وسيط، وسطر الحالة المجرد لا يكتب أي منها رسالة. لذا تعيد `undefined` بدلًا من نص قد تعرضه الواجهة عن طريق الخطأ. اقرنها دائمًا بنصوصك أنت.

### ما ينتجه كل طرح {#failure-shapes}

| مطروح من `run()`                                | حالة HTTP                   | جسم الاستجابة                                | مُبلَّغ إلى تتبّع الأخطاء |
| ----------------------------------------------- | --------------------------- | -------------------------------------------- | ------------------------- |
| `fail(msg)`                                     | 400                         | `{ error: msg, errorCode: "action_failed" }` | لا                        |
| `fail(msg, { errorCode, statusCode, details })` | الـ `statusCode` الذي تحدده | `{ error, errorCode, details }`              | لا                        |
| `new ActionContractError(msg, { errorCode })`   | 409                         | `{ error, errorCode, details }`              | لا                        |
| `new AgentActionStopError(msg)`                 | 500                         | `{ error: msg }`                             | لا                        |
| `new Error(msg)`                                | 500                         | `{ error: "Internal server error" }`         | نعم                       |
| مدخل يفشل في `schema`                           | 400                         | `{ error: "Invalid action parameters..." }`  | لا                        |

اطرح `AgentActionStopError` عندما ينبغي للوكيل إنهاء دوره بدل قراءة الفشل والمحاولة مجددًا. أما `ActionContractError` فهو ما يطرحه `fail()` نيابة عنك، فلا تستخدمه مباشرة إلا حين تكون 409 هي الحالة المطلوبة.

### اختر حالة يمكن لسياسة إعادة المحاولة أن تتصرف بناءً عليها {#failure-status}

تعيد `useActionQuery()` المحاولة مع `429` و`502` و`503` و`504` فقط، حتى ثلاث مرات، بتراجع مقداره 500 مللي ثانية ثم ثانية واحدة ثم ثانيتان. أما كل حالة أخرى فتُعامَل كحالة حتمية وتظهر مع أول استجابة. وإعادة إرسال طلب رُفض لأنه خاطئ لا تشتري سوى الرفض نفسه مرة أخرى. ولا تعيد `useActionMutation()` المحاولة إطلاقًا.

لذا فالحالة ليست زينة. الرفض المُرسَل بوصفه `404` يكلّف رحلة ذهاب وإياب واحدة. والرفض نفسه مُرسَلًا بوصفه `500`، أو مطروحًا مجردًا، يكلّف أربع رحلات وأربعة تقارير أخطاء مكررة.

لا يرى المستدعون من جهة الوكيل رمز الحالة. فالوكيل ينفّذ `run()` داخل العملية نفسها، ومن ثم يتلقى الرسالة مباشرة أيًا كان نوعها، بالصيغة `Error running <action>: <message>`. ويُلحق أي `errorCode` غير القيمة الافتراضية `action_failed` بالصيغة `(errorCode: not_found)`، ليتفرّع النموذج بناءً عليه دون تحليل النص. ويحصل الوكلاء الخارجيون عبر MCP على النص نفسه. أما الأسرار الواردة في الرسالة فتُحجب أولًا، وقواطع الوكيل الخاصة بالأخطاء المتكررة هي ما يحدّ من عدد محاولاته.

## أبقِ سطح actions صغيرًا {#small-surface}

يشغل كل action يمكن للوكيل رؤيته فتحة في قائمة أدوات النموذج، وتجعل القائمة الطويلة والمتداخلة اختيار النموذج للأداة الصحيحة أصعب. صمّم سطح actions مثل API تصونه، وليس action واحدًا لكل زر في واجهة المستخدم:

- فضّل **action واحد بأسلوب CRUD باسم `update`** يأخذ تصحيحًا (patch) من الحقول الاختيارية، بدلاً من actions عديدة لكل حقل مثل `update-name` و`update-order` و`update-color`. لا يرسل المستدعي إلا الحقول التي تغيّرت.
- قبل إضافة action قراءة جديد لكل استعلام أو عامل تصفية، ضع في اعتبارك خيارًا أكثر عمومية أولاً: [ثلاثي provider API](/docs/template-dispatch-vault-integrations#provider-api) (`provider-api-catalog` و`provider-api-docs` و`provider-api-request`) لبيانات الموفر، أو أداة `db-query` للتطوير لبيانات التطبيق.
- علّم actions الخاصة بواجهة المستخدم فقط أو البرمجية بـ [`agentTool: false`](/docs/actions-access-control#agent-tool). تبقى قابلة للاستدعاء من الواجهة الأمامية أو عبر HTTP، دون أن تشغل فتحة في قائمة أدوات النموذج.
- ضع `deferLoading: false` على الحفنة القليلة من actions التي يلجأ إليها الوكيل باستمرار. هذه هي المخططات التي تُرسَل في أول طلب إلى النموذج؛ وكل ما عداها يُحمَّل عند الحاجة عبر `tool-search`. وبمجرد أن تخرج action واحدة بهذه الطريقة، تُؤجَّل كل action غير معلَّمة، لذا علّم مجموعة البداية كاملة دفعة واحدة لا action تلو الأخرى. المسألة هنا كلفة الدور الأول، لا الصلاحية: تبقى الـ action المؤجَّلة قابلة للاستدعاء فور أن يعيدها `tool-search`. وهذا هو الشكل الخاص بكل action من مصفوفة `initialToolNames` في الملحق، ويمكن للتطبيق استخدام أيٍّ من الشكلين.
- احذف أو أخفِ actions التي لم تعد واجهة المستخدم تستخدمها، بدلاً من تركها مكشوفة للنموذج.

يتضمن المستودع مساعدًا استشاريًا، `node scripts/audit-template-actions.mjs [template ...]` (بالاسم المستعار `pnpm actions:audit`). يفحص مجلد `actions/` الخاص بالقالب ويشير إلى actions قد لا تستخدمها واجهة المستخدم بعد الآن، إلى جانب مجموعات actions لكل حقل يمكن دمجها في واحد. يخرج دائمًا برمز 0 ولا يُفشل CI أبدًا، وقواعده الاستدلالية متحفظة، لذا تعامل مع مخرجاته على أنها اقتراح، لا خطأ.
