# نشر مساحة العمل

إذا كان مشروعك [مساحة عمل](/docs/multi-app-workspace) بأكثر من تطبيق واحد، يمكنك نشر كل تطبيق إلى مصدر واحد بدلاً من إدارة عمليات نشر منفصلة لكل تطبيق. تغطي هذه الصفحة المسار المُدار بأمر واحد وبديل Docker Compose المستضاف ذاتيًا. راجع [النشر](/docs/deployment) لاختيار قاعدة بيانات، وإعداد مسبق، ومنصة أولاً.

## مصدر واحد، تطبيقات متعددة {#workspace-deploy}

انشر كل تطبيق في مساحة عمل إلى مصدر واحد بأمر واحد:

```bash
npx @agent-native/core@latest deploy
# https://your-agents.com/mail/*       → apps/mail
# https://your-agents.com/calendar/*   → apps/calendar
# https://your-agents.com/forms/*      → apps/forms
```

**نفس المصدر** تعني أن كل تطبيق يبدو للمتصفح جزءًا من نفس الموقع. هذا يمنحك فوزين كبيرين مجانًا:

- **جلسة تسجيل دخول مشتركة**. سجّل الدخول إلى أي تطبيق، وكل تطبيق يصبح مسجَّل الدخول.
- **A2A بين التطبيقات بلا تكوين**. الإشارة إلى `@calendar` من mail هي جلب من نفس المصدر. لا يوجد CORS ولا توقيع JWT بين الأشقاء.

<Callout tone="info">

تحت الغطاء، يُبنى كل تطبيق بـ **مسار قاعدة** خاص به، وهو بادئة عنوان URL مثل `/mail` مضبوطة عبر `APP_BASE_PATH`/`VITE_APP_BASE_PATH`، ثم يُحزَم لأجل إعداد Nitro المسبق المستهدف. يوجّه Cloudflare Pages من خلال **عامل مُرسِل** مُولَّد، وهو نص برمجي صغير في `dist/_worker.js` يقرأ المسار الوارد ويُحيل الطلب إلى التطبيق المطابق. يستخدم Netlify دالة واحدة لكل تطبيق بالإضافة إلى عمليات إعادة توجيه مُولَّدة. يكتب Vercel `.vercel/output` على مستوى مساحة العمل باستخدام Build Output API.

</Callout>

<Callout tone="warning">

تتطلب عمليات بناء مساحة العمل المستضافة `A2A_SECRET` في بيئة مزود النشر. بدونه، لا يعمل Slack، وwebhooks الواردة، واستئناف A2A بين التطبيقات، بما أن كل تلك تمر عبر معالجات خلفية موقَّعة. لا تزال فحوصات الأصول `--build-only` المحلية تعمل بدونه.

</Callout>

<Callout tone="info">

هل تُكوِّن أمر بناء مزود بدلاً من النشر يدويًا؟ أضف `--build-only` إلى نفس الأمر، على سبيل المثال `npx @agent-native/core@latest deploy --preset vercel --build-only`. يكتب المخرجات مباشرةً، لذا لا يُطلَب `vercel.json` لتوجيه مساحة العمل.

هل تفضّل نطاقًا منفصلًا لكل تطبيق بدلاً من مصدر مشترك واحد؟ لا يزال كل تطبيق في مساحة العمل قابلاً للنشر بشكل مستقل. شغّل `cd apps/<name> && npx @agent-native/core@latest build` مثل سقالة مستقلة.

</Callout>

## مساحة عمل مستضافة ذاتيًا باستخدام Docker Compose {#workspace-docker-compose}

**الوكيل العكسي** هو نقطة الدخول الواحدة تلك في الصورة أعلاه: يستقبل كل طلب ويُحيله إلى الحاوية الصحيحة بناءً على مسار عنوان URL، نفس المهمة التي يقوم بها عامل مُرسِل Cloudflare لنشر مُدار. على VPS، هذا يعني حاوية واحدة لكل تطبيق في مساحة العمل، تشير جميعها إلى نفس قاعدة بيانات Postgres والأسرار الإنتاجية المشتركة، مع الوكيل في المقدمة.

<Steps>

### ابنِ كل تطبيق بمسار قاعدة مطابق

مسار القاعدة هو مُدخَل وقت بناء لحزمة العميل ومُدخَل وقت تشغيل للخادم. ابنِ كل تطبيق بنفس المسار الذي سيوجّهه إليه الوكيل:

```bash maxLines=8
APP_BASE_PATH=/mail VITE_APP_BASE_PATH=/mail npx @agent-native/core@latest build
node .output/server/index.mjs
```

### اكتب Dockerfile قابل لإعادة الاستخدام

خذ اسم التطبيق وبادئة المسار كوسائط بناء، بحيث يخدم Dockerfile واحد كل تطبيق في مساحة العمل:

```dockerfile filename="Dockerfile.workspace-app" maxLines=12
FROM node:24-slim AS build
WORKDIR /workspace
RUN corepack enable
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY packages ./packages
COPY apps ./apps
ARG APP_NAME
ARG APP_BASE_PATH
ENV APP_BASE_PATH=$APP_BASE_PATH
ENV VITE_APP_BASE_PATH=$APP_BASE_PATH
RUN pnpm install --frozen-lockfile
RUN pnpm --dir apps/$APP_NAME build

FROM node:24-slim
WORKDIR /app
ARG APP_NAME
ARG APP_BASE_PATH
ENV NODE_ENV=production
ENV PORT=3000
ENV APP_BASE_PATH=$APP_BASE_PATH
COPY --from=build /workspace/apps/$APP_NAME/.output .output
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

### ركّب Postgres، والتطبيقات، والوكيل

يستخدم هذا المثال Caddy لأنه يمكنه إنهاء HTTP محليًا أو الجلوس خلف وكيل SSL الخاص بـ Cloudflare، لكن الجزء المهم هو التوجيه بحسب بادئة المسار:

```yaml filename="docker-compose.yml" maxLines=30
services:
  postgres:
    image: postgres:17
    restart: unless-stopped
    environment:
      POSTGRES_DB: agent_native
      POSTGRES_USER: agent_native
      POSTGRES_PASSWORD: change-me
    volumes:
      - postgres-data:/var/lib/postgresql/data

  mail:
    build:
      context: .
      dockerfile: Dockerfile.workspace-app
      args:
        APP_NAME: mail
        APP_BASE_PATH: /mail
    restart: unless-stopped
    environment:
      DATABASE_URL: postgres://agent_native:change-me@postgres:5432/agent_native
      BETTER_AUTH_URL: https://agents.example.com/mail
      BETTER_AUTH_SECRET: ${BETTER_AUTH_SECRET}
      A2A_SECRET: ${A2A_SECRET}
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
    depends_on:
      - postgres

  calendar:
    build:
      context: .
      dockerfile: Dockerfile.workspace-app
      args:
        APP_NAME: calendar
        APP_BASE_PATH: /calendar
    restart: unless-stopped
    environment:
      DATABASE_URL: postgres://agent_native:change-me@postgres:5432/agent_native
      BETTER_AUTH_URL: https://agents.example.com/calendar
      BETTER_AUTH_SECRET: ${BETTER_AUTH_SECRET}
      A2A_SECRET: ${A2A_SECRET}
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
    depends_on:
      - postgres

  proxy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
    depends_on:
      - mail
      - calendar

volumes:
  postgres-data:
```

### كوِّن الوكيل

```caddyfile filename="Caddyfile"
agents.example.com {
  reverse_proxy /mail* mail:3000
  reverse_proxy /calendar* calendar:3000
}
```

</Steps>

<Callout tone="info">

- أبقِ `DATABASE_URL`، و`BETTER_AUTH_SECRET`، و`A2A_SECRET`، والأسرار
  الإنتاجية الأخرى متطابقة عبر حاويات التطبيق عندما تريد مصادقة مشتركة،
  وبيانات اعتماد مشتركة، وA2A بين التطبيقات.
- اضبط `BETTER_AUTH_URL` على عنوان URL العام لمسار ذلك التطبيق. يجب أن
  تستخدم عناوين URL لرد اتصال OAuth نفس عنوان URL العام.
- لا تعتمد على نظام ملفات الحاوية لبيانات الإنتاج. استخدم Postgres (أو
  خلفية SQL دائمة أخرى) لأجل `DATABASE_URL`.
- إذا كان Cloudflare يُنهي TLS أمام VPS، كوِّن Cloudflare لإرسال ترويسات
  `X-Forwarded-Proto` / `X-Forwarded-Host` العادية وتوجيه المضيف العام
  إلى حاوية الوكيل.

</Callout>
