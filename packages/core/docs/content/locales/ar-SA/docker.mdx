# Docker

يحزم Docker تطبيق Agent-Native وكل ما يحتاجه للتشغيل في صورة حاوية واحدة. تشغّل
الصورة خادم Node.js نفسه الموضح في [دليل Node.js](/docs/node-js)، لذلك يعمل
بالطريقة نفسها على حاسوبك المحمول، أو على جهاز افتراضي، أو على أي مضيف يشغّل
الحاويات.

يشرح هذا الدليل نشر تطبيق مستقل واحد من البداية. ستنشئ التطبيق، وتضيف ملف
`Dockerfile`، وتمنح التطبيق قاعدة بيانات إنتاجية وسر مصادقة، وتجهّز قاعدة
البيانات، ثم تبني الحاوية وتشغّلها.

<Callout tone="info">

يلزم Node.js `22.22+`.

</Callout>

تحتاج أيضًا إلى تثبيت Docker على الجهاز الذي يبني الصورة ويشغّلها. شغّل الأوامر
في هذا الدليل على الخادم الذي سيشغّل الحاوية. في حالة الجهاز الافتراضي، يعني ذلك
عادةً الاتصال به عبر SSH أولًا.

<a id="self-host-quickstart"></a>

## الخطوة 1: إنشاء التطبيق {#step-1-create-the-app}

أنشئ تطبيقك المستقل الجديد. ينشئ المثال أدناه تطبيقًا من قالب Chat، لكن يمكنك
البدء من أي قالب. انتقل إلى مجلد التطبيق وثبّت تبعياته. يفعّل الأمر
`corepack enable` إصدار `pnpm` الذي يتوقعه التطبيق، لذلك لا تحتاج إلى تثبيت
`pnpm` بنفسك.

```bash
npx --yes @agent-native/core@latest create my-app --standalone --template chat

cd my-app

corepack enable

pnpm install
```

استبدل `my-app` باسم تطبيقك إذا أردت. يفترض باقي هذا الدليل أنك داخل مجلد
التطبيق.

<Callout tone="info">

إذا فشلت هذه الأوامر بأخطاء في التبعيات النظيرة، فقد يكون السبب نسخة قديمة من حزمة في ذاكرة npx المؤقتة. شغّل `npx clear-npx-cache` لمسح الذاكرة المؤقتة، ثم شغّل الأوامر مرة أخرى.

</Callout>

## الخطوة 2: إنشاء Dockerfile {#step-2-create-dockerfile}

لا يتضمن التطبيق الجديد ملف `Dockerfile`، لذلك تضيفه بنفسك. تضيف أيضًا ملف
`.dockerignore` الذي يُبقي الملفات المحلية خارج الصورة. أنشئ الملفين في المجلد
الجذر للتطبيق، بجوار `package.json`.

### Dockerfile {#dockerfile}

أنشئ ملفًا باسم `Dockerfile`، بدون امتداد، وانسخ فيه ما يلي:

```dockerfile filename="Dockerfile"
FROM node:24-slim AS build
WORKDIR /app

RUN apt-get update \
  && apt-get install -y --no-install-recommends python3 make g++ \
  && rm -rf /var/lib/apt/lists/*

ENV PYTHON=/usr/bin/python3

COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile

COPY . .
RUN pnpm build

FROM node:24-slim
WORKDIR /app

ENV NODE_ENV=production
ENV PORT=3000

COPY --from=build /app/.output .output

EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

يبني ملف `Dockerfile` الصورة على مرحلتين:

- **مرحلة البناء.** تثبّت الأدوات التي تحتاجها بعض التبعيات للتصريف أثناء
  التثبيت (`python3` و`make` و`g++`)، وتثبّت تبعيات التطبيق، وتبني التطبيق.
- **المرحلة النهائية.** تبدأ من صورة Node.js نظيفة وتنسخ إليها الخادم النهائي
  فقط من المجلد `.output`. يُبقي ذلك الصورة صغيرة ويترك أدوات البناء والشيفرة
  المصدرية خلفه.

تعمل الصورة النهائية في وضع الإنتاج وتستمع إلى المنفذ `3000`.

### ملف تجاهل Docker {#docker-ignore-file}

أنشئ ملفًا باسم `.dockerignore` وانسخ فيه ما يلي:

```text filename=".dockerignore"
node_modules
.output
.git
.env
.env.*
data
*.log
```

تُبقي هذه الإدخالات خارج الصورة كلًا من التبعيات المحلية، وناتج البناء القديم،
وسجل Git، والأسرار المحلية في ملفات `.env`، وقاعدة بيانات التطوير المحلية في
`data`، وملفات السجل. تثبّت مرحلة البناء تبعيات جديدة وتبني التطبيق من البداية،
لذلك لا حاجة إلى أي منها. كما أن استبعاد ملفات `.env` يمنع تضمين أسرارك داخل
الصورة.

## الخطوة 3: ضبط أسرار البيئة {#step-3-configure-environment-secrets}

يقرأ التطبيق إعدادات الإنتاج من متغيرات البيئة:

| المتغير              | مطلوب | الغرض                                                   |
| -------------------- | ----- | ------------------------------------------------------- |
| `DATABASE_URL`       | نعم   | يربط التطبيق بقاعدة بيانات PostgreSQL الخاصة به         |
| `BETTER_AUTH_SECRET` | نعم   | يوقّع جلسات المستخدمين                                  |
| `BETTER_AUTH_URL`    | لا    | يحدد العنوان العام الذي يستخدمه الناس للوصول إلى تطبيقك |

تجعل أوامر التصدير أدناه الأوامر التالية تعمل في هذه الصدفة. قبل النشر، احفظ
المتغيرات نفسها في إعدادات بيئة المشروع أو الخدمة لدى موفر الاستضافة، حتى تظل
متاحة للحاوية بعد إعادة التشغيل أو بعد عملية نشر جديدة.

### عنوان URL لقاعدة البيانات {#database-url}

أثناء التطوير المحلي، يخزّن التطبيق البيانات في قاعدة بيانات محلية عندما يكون
`DATABASE_URL` غير مضبوط. يحتاج التطبيق المنشور إلى قاعدة بيانات PostgreSQL
حقيقية تحتفظ ببياناتها بين عمليات إعادة التشغيل. تفقد الحاوية أي ملفات تكتبها
عند استبدالها، لذلك يجب أن توجد قاعدة البيانات خارج الحاوية. انسخ سلسلة الاتصال
من موفر قاعدة البيانات وصدّرها:

```bash
export DATABASE_URL='your-postgres-url-string'
```

توضح [أدلة موفري قواعد البيانات](/docs/neon) مكان العثور على سلسلة الاتصال لدى
كل موفر.

<Callout tone="warning">

اختر موفر PostgreSQL دائمًا: Neon أو Supabase أو Amazon RDS أو غيرها.

</Callout>

### سر المصادقة {#auth-secret}

أنشئ هذه القيمة مرة واحدة وأبقها ثابتة عبر عمليات النشر.

يستخدم التطبيق `BETTER_AUTH_SECRET` لتوقيع جلسات المستخدمين. إذا تغيّرت القيمة،
يُسجَّل خروج كل مستخدم مسجّل الدخول. ينشئ الأمر أدناه قيمة عشوائية:

```bash
export BETTER_AUTH_SECRET="$(openssl rand -hex 32)"
```

احفظ القيمة المُنشأة في مكان آمن، مثل إعدادات الأسرار لدى موفر الاستضافة أو مدير
كلمات المرور. استخدم القيمة نفسها في كل مرة تنشر فيها.

### عنوان URL العام {#public-url}

اختياري. اضبطه عند استخدام نطاق مخصص، أو وكيل عكسي، أو تدفق مصادقة أو OAuth يحتاج
إلى أصل عام ثابت.

`BETTER_AUTH_URL` هو العنوان العام الذي يستخدمه الناس للوصول إلى تطبيقك. بدونه،
يستنتج التطبيق عنوانه من كل طلب وارد. يكون ذلك مناسبًا عادةً، لكن روابط تسجيل
الدخول وعمليات إعادة توجيه OAuth قد تشير إلى مكان خاطئ عندما يكون التطبيق خلف
وكيل أو نطاق مخصص.

```bash
export BETTER_AUTH_URL='https://your-domain.example'
```

## الخطوة 4: الترحيل {#step-4-migrate}

تنشئ عمليات الترحيل الجداول التي يحتاجها التطبيق في قاعدة البيانات وتحدّثها.

شغّل هذا الأمر على الخادم المضيف، مقابل `DATABASE_URL` الإنتاجي، قبل أول زيارة.

```bash
pnpm migrate:production
```

شغّل الأمر من مجلد التطبيق، وليس داخل الحاوية. تحتوي الصورة على الخادم النهائي
فقط، لذلك لا يمكنها تشغيل عمليات الترحيل بنفسها. يقرأ الأمر `DATABASE_URL` من
البيئة التي صدّرتها في الخطوة السابقة. شغّله مرة أخرى بعد ترقية التطبيق، وقبل
تشغيل الإصدار الجديد.

## الخطوة 5: النشر {#step-5-deploy}

ابنِ الصورة من مجلد التطبيق:

```bash
docker build -t my-agent-native-app .
```

يمنح الخيار `-t` الصورة الاسم `my-agent-native-app`. استخدم أي اسم تريده،
واستخدم الاسم نفسه في الأمر التالي.

شغّل الحاوية:

```bash
docker run --rm \
  -p 3000:3000 \
  -e DATABASE_URL \
  -e BETTER_AUTH_SECRET \
  my-agent-native-app
```

يجعل `-p 3000:3000` المنفذ `3000` الخاص بالحاوية قابلًا للوصول عبر المنفذ `3000`
على الخادم. يمرّر كل خيار `-e` المتغير الذي يحمل الاسم نفسه من الصدفة إلى
الحاوية. إذا ضبطت `BETTER_AUTH_URL`، فأضف `-e BETTER_AUTH_URL` إلى الأمر أيضًا.
يزيل `--rm` الحاوية عند توقفها.

للوصول إلى التطبيق من الإنترنت، افتح المنفذ `3000` في جدار حماية الخادم، أو ضع
وكيلًا عكسيًا مثل Nginx أو Caddy أمامه لتقديم نطاقك عبر HTTPS. ثم افتح العنوان
العام للتطبيق وأنشئ الحساب الأول.

## إبقاء الحاوية قيد التشغيل {#keep-the-container-running}

يعمل الأمر `docker run` أعلاه في الطرفية ويتوقف عندما تغلقها. لإبقاء التطبيق
قيد التشغيل، شغّل الحاوية في الخلفية مع سياسة إعادة تشغيل، حتى يعيد Docker
تشغيلها بعد تعطلها أو بعد إعادة تشغيل الخادم. للقيام بذلك، استبدل `--rm` بـ
`-d --restart unless-stopped`. كما يتولى كثير من المضيفين الذين يشغّلون الحاويات
إعادة التشغيل نيابةً عنك.
