# قاعدة البيانات

## خيارات الاستضافة {#hosting}

يستخدم التطبيق PostgreSQL. وعند عدم ضبط `DATABASE_URL`، يستخدم PGlite المحلي لتتمكن من البدء دون إعداد.

### الافتراضي: ملف PGlite {#default-pglite}

عند عدم ضبط `DATABASE_URL`، ينشئ التطبيق قاعدة بيانات PGlite في `data/pglite`. لا يتطلب أي تكوين. شغّل خادم التطوير وسيُنشأ الملف عند أول تشغيل.

هذا مخصص للتطوير المحلي فقط. قد تعيد الحاويات، والوظائف بدون خادم، وبيئات المعاينة ضبط نظام الملفات الخاص بها بين عمليات إعادة التشغيل، مما يعني أن ملف PGlite المحلي يمكن أن يختفي. اضبط `DATABASE_URL` على قاعدة PostgreSQL مستضافة ومستمرة قبل النشر.

### Postgres محلي: PGlite {#local-pglite}

للتطوير محليًا باستخدام PostgreSQL دون Docker أو قاعدة بيانات مستضافة، ثبّت حزمة PGlite الاختيارية واضبط `DATABASE_URL`:

```bash
pnpm add @electric-sql/pglite@^0.5.3
```

```bash
DATABASE_URL=pglite:./data/pglite
```

يُشغّل [PGlite](https://pglite.dev/) قاعدة بيانات Postgres مبنية بتقنية WASM داخل العملية نفسها. يتيح لك اكتشاف مشكلات المخطط الخاصة بـ Postgres فقط قبل النشر، مع إبقاء الإعداد بسيطًا مثل الإعداد الافتراضي لـ PGlite. وهو، مثل PGlite، تخزين محلي فقط. لا تستخدمه في الإنتاج أو البيئات المشتركة.

### قاعدة بيانات الإنتاج {#production}

اضبط `DATABASE_URL` في ملف `.env` الخاص بك أو في بيئة موفر النشر للاتصال بقاعدة بيانات مستضافة:

```bash
# Neon Postgres
DATABASE_URL=postgres://user:pass@ep-cool-name-123456.us-east-2.aws.neon.tech/mydb?sslmode=require

# Supabase Postgres
DATABASE_URL=postgres://postgres.xxxx:pass@aws-0-us-east-1.pooler.supabase.com:6543/postgres

# Plain Postgres
DATABASE_URL=postgres://user:pass@localhost:5432/mydb

DATABASE_URL=pglite:./data/pglite
```

يكتشف إطار العمل اللهجة تلقائيًا من بادئة الرابط ويهيئ Drizzle وفقًا لذلك.

### قاعدة بيانات مُدارة من Builder.io {#builder-managed}

_مخطط له (غير متاح بعد):_ عند الاتصال بـ Builder.io، سيتمكن تطبيقك من استخدام قاعدة بيانات مُدارة يتم توفيرها تلقائيًا، دون الحاجة إلى سلاسل اتصال.

## إعداد قاعدة البيانات {#setup}

يحتاج التطبيق الذي يستخدم قاعدة البيانات إلى ثلاثة ملفات:

- `server/db/schema.ts`: تعريفات الجداول
- `server/db/index.ts`: مثيل عميل قاعدة البيانات الوحيد المكتوب (typed singleton)
- `server/plugins/db.ts`: ترحيلات التطبيق الخاصة ببدء التشغيل المحلي

### 1. عرّف مخططك {#schema}

استورد مساعدات المخطط من `@agent-native/core/db/schema`. تنتج مساعدات الإطار تعريفات خاصة بـ PostgreSQL وPGlite.

```ts filename="server/db/schema.ts"
import { integer, now, table, text } from "@agent-native/core/db/schema";

export const tasks = table("tasks", {
  id: text("id").primaryKey(),
  title: text("title").notNull(),
  priority: integer("priority").notNull().default(0),
  done: integer("done", { mode: "boolean" }).notNull().default(false),
  ownerEmail: text("owner_email").notNull(),
  createdAt: text("created_at").notNull().default(now()),
});
```

| المساعد   | الغرض                                                                    |
| --------- | ------------------------------------------------------------------------ |
| `table`   | تحديد جدول؛ يستخدم مساعد PostgreSQL                            |
| `text`    | عمود نصي، يدعم `{ enum: [...] }`                                         |
| `integer` | عمود صحيح، `{ mode: "boolean" }` يُعيَّن إلى قيمة منطقية في Postgres     |
| `real`    | عمود عائم. يُعيَّن إلى `real` في PGlite، و`double precision` في Postgres |
| `now`     | يضع الطابع الزمني الحالي لاستخدامه مع `.default(now())`                 |

### 2. أنشئ عميل قاعدة البيانات {#db-client}

ينشئ كل تطبيق عميل Drizzle كسولًا ومفردًا (singleton) عن طريق استدعاء `createGetDb(schema)`. الموقع الأساسي هو `server/db/index.ts`:

```ts filename="server/db/index.ts"
import { createGetDb } from "@agent-native/core/db";
import * as schema from "./schema.js";

export const getDb = createGetDb(schema);
```

يُرجع `createGetDb` دالة `getDb()` تفتح اتصال PostgreSQL عند أول استدعاء، وتُرجع نفس مثيل Drizzle المكتوب في الاستدعاءات اللاحقة. وهي تقرأ `DATABASE_URL` للاتصال بـ PostgreSQL المستضاف أو PGlite المحلي.

استورد `getDb` من هذا المسار المحلي للقالب في actions والمسارات. لا تستورد مباشرةً من `@agent-native/core`. التصدير الأساسي (core) غير مكتوب النوع؛ بينما يحمل التصدير المحلي أنواع مخططك.

### 3. اكتب الترحيلات {#migrations}

أثناء التطوير المحلي، يمكن تطبيق تغييرات المخطط عبر إضافة Nitro في
`server/plugins/db.ts`. في الإنتاج أو البيئات الخالية من الخادم، شغّل الترحيلات
في خطوة إصدار أو نشر بدلاً من الطلب الأول. استخدم `runMigrations` من
`@agent-native/core/db`:

### إنشاء ترحيلات التطبيق الجديدة باستخدام Drizzle Kit {#drizzle-migrations}

بالنسبة إلى تغييرات مخطط التطبيق الجديدة، استخدم `pnpm db:generate` لإنشاء SQL
قابل للمراجعة. ينشئ ذلك `server/db/migrations/<id_name>.sql`، ويحمّل
`runDrizzleMigrations` هذه الملفات إلى مشغّل Agent-Native المشترك في بيئات Node.js
وبيئات serverless المستندة إلى Node. تبقى خطوة الإصدار هي المسؤولة عن تغييرات
الإنتاج. احتفظ بـ `runMigrations()` لجداول PostgreSQL، وعمليات ملء
البيانات، وخطوات JavaScript المؤجلة.

لا يتوفر محمّل نظام الملفات في Cloudflare Workers/Pages أو بيئات edge الأخرى
التي لا توفر نظام ملفات. استخدم `runMigrations()` هناك مع إدخالات SQL الخاصة بـ PostgreSQL المضمّنة
في حزمة العامل. أنشئ الترحيلات لـ PostgreSQL ولا تبدّل مجلدًا واحدًا بين
PGlite وPostgreSQL.
<Callout tone="risk">
  لا تقم أبدًا بتشغيل `drizzle-kit push` مقابل قاعدة بيانات إنتاج. تُعرّف مخططات
  القالب جداول التطبيق الخاصة فقط؛ ولا تتضمن جداول إطار العمل المركزية (`user`،
  و`session`، و`application_state`، وغيرها). سيؤدي تشغيل `drizzle-kit push`
  مقابل الإنتاج إلى اكتشاف تلك الجداول كجداول غير معروفة ومحاولة حذفها، مما
  يتسبب في فقدان فوري للبيانات.
</Callout>

يهيئ `drizzle.config.ts` الموجود في جذر كل تطبيق drizzle-kit لفحص مخطط PostgreSQL أثناء التطوير المحلي. اضبط قاعدة PostgreSQL صراحةً، مثل `createDrizzleConfig({ dialect: "postgresql" })`:

```ts filename="drizzle.config.ts"
import { createDrizzleConfig } from "@agent-native/core/db/drizzle-config";
export default createDrizzleConfig();
```

استخدم `pnpm db:generate` لفحص مخططك، و`pnpm db:push` مقابل قاعدة بيانات محلية فقط.

### 4. استعلم داخل actions {#querying}

استدعِ `getDb()` من actions الخاصة بك للحصول على عميل Drizzle المكتوب. استخدم منشئ الاستعلامات في Drizzle والمشغلات المحمولة من `drizzle-orm`:

```ts
import { and, desc, eq } from "drizzle-orm";
import { getDb } from "../server/db/index.js";
import * as schema from "../server/db/schema.js";

const db = getDb();

const openTasks = await db
  .select()
  .from(schema.tasks)
  .where(
    and(eq(schema.tasks.ownerEmail, userEmail), eq(schema.tasks.done, false)),
  )
  .orderBy(desc(schema.tasks.createdAt));

await db
  .update(schema.tasks)
  .set({ done: true })
  .where(eq(schema.tasks.id, taskId));
```

## تحديد نطاق البيانات للمستخدمين {#scoping}

يجب تحديد نطاق جميع عمليات القراءة والكتابة على الجداول التي تواجه المستخدم بحيث تقتصر على المستخدم المصادق عليه. يوفر إطار العمل نمطين حسب ما إذا كانت البيانات خاصة أو قابلة للمشاركة.

**البيانات الخاصة:** الجداول التي تخص مستخدمًا واحدًا. أضف `ownerEmail: text("owner_email").notNull()` إلى المخطط وأدرج `eq(table.ownerEmail, userEmail)` في كل استعلام:

```ts
.where(eq(schema.tasks.ownerEmail, userEmail))
```

**الموارد القابلة للمشاركة:** الجداول التي يمكن مشاركتها مع مستخدمين أو مؤسسات أخرى. انشر `...ownableColumns()` في المخطط بدلاً من `owner_email` مجردة. يضيف هذا `owner_email`، و`org_id`، و`visibility` في استدعاء واحد، وينشئ جدول مشاركات مرافقًا باستخدام `createSharesTable`:

```ts filename="server/db/schema.ts"
import {
  table,
  text,
  ownableColumns,
  createSharesTable,
} from "@agent-native/core/db/schema";

export const decks = table("decks", {
  id: text("id").primaryKey(),
  title: text("title").notNull(),
  ...ownableColumns(),
});
export const deckShares = createSharesTable("deck_shares");
```

ثم استخدم `accessFilter` من `@agent-native/core/sharing` في استعلامات القوائم بدلاً من فحص `eq` يدوي:

```ts
import { accessFilter } from "@agent-native/core/sharing";

const rows = await db
  .select()
  .from(schema.decks)
  .where(accessFilter(schema.decks, schema.deckShares));
```

يبني `accessFilter` استعلامًا يسمح بالصفوف التي يملكها المستدعي، والصفوف المشتركة مع مؤسسته، والصفوف المشتركة معه صراحةً. ولا يكشف عن صفوف تخص مستخدمين آخرين.

راجع [الأمان — تحديد نطاق البيانات](/docs/security#data-scoping) و[المشاركة](/docs/sharing#building) للاطلاع على النموذج الكامل.

## المزامنة المدعومة بـ PostgreSQL {#sync}

لا يعتمد Agent-Native على مراقبي نظام الملفات أو الحالة اللاصقة في الذاكرة. فعندما يكتب action إلى قاعدة البيانات، يزداد إصدار المزامنة. يستطلع خطاف العميل `useDbSync()` نقطة النهاية `/_agent-native/poll` ويُبطل ذاكرات React Query المؤقتة عندما يرى إصدارًا أعلى.

يعمل هذا عبر عمليات النشر بدون خادم ومتعددة المثيلات لأن قاعدة البيانات هي نقطة التنسيق. إذا كتبت عمليات تغيير مخصصة خارج actions، استخدم مساعدات إطار العمل أو أصدر إبطال المزامنة المناسب حتى تتحدث واجهات المستخدم المفتوحة.

## PostgreSQL الخام {#raw-sql}

بالنسبة للاستعلامات المتقدمة، أو فحوصات السلامة، أو الصيانة لمرة واحدة التي لا يمكن لمنشئ استعلامات Drizzle التعبير عنها، استخدم `getDbExec` من `@agent-native/core/db`:

```ts
import { getDbExec } from "@agent-native/core/db";

const { rows } = await getDbExec().execute({
  sql: `SELECT id, title FROM tasks WHERE owner_email = ? LIMIT ?`,
  args: [userEmail, 50],
});
```

يحوّل `getDbExec` تلقائيًا معلمات `?` إلى `$1`، و`$2`، وهكذا بالنسبة إلى Postgres. يُفضّل استخدام منشئ استعلامات Drizzle لعمليات القراءة والكتابة العادية. يتجاوز SQL الخام أمان الأنواع (type safety) ويصعب صيانته.
