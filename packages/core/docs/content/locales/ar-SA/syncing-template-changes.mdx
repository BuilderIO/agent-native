# مزامنة تغييرات القالب

ينسخ `agent-native create` قالبًا من الطرف الأول إلى تطبيقك ثم يجعله ملكًا لك - يستبدل اسم التطبيق، ويعيد تسمية `_gitignore`، ويعيد كتابة `package.json`، ويثبّت تبعيات `workspace:*` و`catalog:` على إصدارات محددة، و(في مساحة عمل) يستبدل ملحقات المصادقة والدردشة الموروثة. ومنذ تلك اللحظة يصبح التطبيق تطبيقًا مستقلاً تم إنشاؤه من القالب. الإصلاحات والتحسينات التي تصل إلى القالب في المنبع لا تصل إليه.

لا يقوم `agent-native upgrade` بسد تلك الفجوة. فهو ينقل إصدارات الحزم، ويشغّل تحويلات الاستيراد البرمجية (codemods)، ويحدّث أدلة skills - لكنه لا يمس أبدًا ملفًا تم نسخه من قالب.

`agent-native template` هو النصف المفقود. فهو يعيد جلب القالب بإصدار أحدث، ويعيد تطبيق التحويلات نفسها التي طبّقها `create` بالضبط، ثم يدمج النتيجة في تطبيقك ملفًا تلو الآخر.

قوالب المجتمع خارج مسار المزامنة هذا عمدًا. تسجّل بيانات `agent-native.communityTemplate` مصدر التثبيت فقط، ولا يجلب `agent-native template sync` التغييرات من ذلك المستودع. ثبّت مراجعة محددة لنقطة بداية مستقرة، ثم راجع التغييرات اللاحقة وانقلها يدويًا.

## البدء السريع {#quick-start}

```bash
agent-native upgrade
agent-native template sync
```

يستخدم `sync` افتراضيًا إصدار القالب المطابق لإصدار `@agent-native/core` المثبَّت لديك، لذا فإن تشغيله بعد `upgrade` يُبقي الكود والحزم على الإصدار نفسه.

ألقِ نظرة قبل أن تدمج:

```bash
agent-native template status
agent-native template diff
```

## كيف يعمل الدمج {#how-the-merge-works}

يحتاج الدمج المفيد إلى ثلاث أشجار، لا شجرتين:

- **الأساس (base)** — القالب النقي كما كان عند إنشاء تطبيقك.
- **نسخة الطرف الآخر (theirs)** — القالب نفسه بالإصدار الذي تُزامن إليه، بعد مروره بخط أنابيب التحويل نفسه.
- **نسختنا (ours)** — تطبيقك كما هو الآن.

بهذه الأشجار الثلاث، يقع كل ملف ضمن حالة واضحة. لم يمسّه المنبع، فيُترك كما هو. أنت لم تلمسه أبدًا، فيُحدَّث تلقائيًا (fast-forward). كلاكما غيّره، فيحصل على علامات تعارض. لا يُستبدل أي شيء لمجرد أنه مختلف.

بدون أساس، لا يمكن أن تعني "المزامنة" سوى الاستبدال الكامل، الذي يتجاهل عملك بصمت أو يتراجع عن تغييرات المنبع.

## خط الأساس {#the-baseline}

تُخزَّن شجرة الأساس كـ git ref في المستودع (repo) الخاص بك:

```txt
refs/agent-native/template-baseline/apps/slides
```

يُكتب هذا باستخدام أدوات git منخفضة المستوى (plumbing) مقابل ملف فهرسة (index) مؤقت يُستغنى عنه. لا يُمس `HEAD` أبدًا، ولا فرعك، ولا فهرستك، ولا شجرة العمل الخاصة بك - تشغيل `template baseline` أثناء التحرير آمن، وتقرأ `git status` بنفس الطريقة قبل وبعد.

عند أول كتابة، تُضاف مواصفات الجلب والدفع (refspecs) لـ `refs/agent-native/*` إلى المستودع البعيد الخاص بك حتى يبقى خط الأساس بعد الاستنساخ (clone). إذا لم يكن التطبيق داخل مستودع git، فإن خط الأساس يعود إلى tarball ضمن `.agent-native/`.

التطبيقات التي أُنشئت قبل وجود بيانات المنشأ (provenance) ليس لها خط أساس. أنشئ واحدًا، ثم زامِن:

```bash
agent-native template baseline
agent-native template sync
```

## بيانات المنشأ {#provenance}

يسجّل `create` ما يحتاجه دمج لاحق داخل `package.json` الخاص بالتطبيق:

```json
{
  "agent-native": {
    "scaffold": {
      "template": "slides",
      "frameworkSkills": "default",
      "templateRef": "@agent-native/core@0.120.3",
      "templateSource": "github",
      "coreVersion": "0.120.3",
      "shape": "workspace"
    }
  }
}
```

`templateRef` هو الوسم الثابت (immutable tag) الذي جُلب منه القالب فعليًا، وهو ما يجعل الأساس قابلًا لإعادة الإنتاج. يحدد `shape` ما إذا كانت تحويلات مساحة العمل تُعاد أثناء التجسيد (materialization).

## الأوامر {#commands}

### status {#status}

```bash
agent-native template status [app]
```

يُبلغ عن المرجع (ref) المسجَّل، وأحدث مرجع متاح، وما إذا كان هناك خط أساس، وعدد الملفات التي غيّرها المنبع، وعدد الملفات التي عدّلتها محليًا.

### diff {#diff}

```bash
agent-native template diff [app] [--to <ref>]
```

فرق موحّد (diff) للقراءة فقط لما تغيّر في المنبع بين خط الأساس لديك والهدف. لا يكتب شيئًا.

### sync {#sync}

```bash
agent-native template sync [app] [--to <ref>] [--dry-run] [--force]
```

يُنفّذ الدمج. تكون القيمة الافتراضية لـ `--to` هي المرجع المطابق للنواة (core) المثبَّتة. يطبع `--dry-run` الخطة دون الكتابة.

يرفض `sync` التشغيل عندما يحتوي دليل التطبيق على تغييرات غير ملتزم بها (uncommitted)، لذا يمكن دائمًا التعافي من دمج سيّئ باستخدام `git checkout`. يتجاوز `--force` هذا الأمر؛ يُفضَّل الالتزام (commit) أولًا.

عندما يكون الدمج نظيفًا، يتقدّم خط الأساس تلقائيًا. أما عند وجود تعارضات فإنه لا يتقدّم عمدًا - راجع `accept`.

### accept {#accept}

```bash
agent-native template accept [app]
```

يُقدِّم خط الأساس بعد أن تحل علامات التعارض. يرفض ذلك ما دامت أي علامة `<<<<<<<` باقية، بحيث لا يتجاوز خط الأساس أبدًا دمجًا لم يُحل بعد، ولا يُدمج علامات التعارض بهدوء في أساسك التالي.

### baseline {#baseline}

```bash
agent-native template baseline [app] [--ref <ref>] [--template <name>]
```

يسجّل خط أساس لتطبيق يسبق وجود بيانات منشأ الإنشاء (scaffold provenance). مرِّر `--ref` عندما تعرف الإصدار الذي أتى منه التطبيق فعليًا؛ فكلما اقترب من الحقيقة، قلّت التعارضات الوهمية التي تنتجها أول مزامنة.

## ما لا يُدمج أبدًا {#what-is-never-merged}

بعض الملفات ملكك بحكم التعريف، وبعضها لا يمكن دمجه بمعنى مفيد:

- الأسرار والتكوين المحلي: `.env`, `.env.local`
- ملفات القفل: `pnpm-lock.yaml`
- المخرجات المُولّدة: `node_modules`, `.output`, `.react-router`, `dist`, `build`
- محتوى مملوك للتطبيق: `learnings.md`، والإدخالات المعلَّقة ضمن `changelog/`

لا تُدمج الملفات الثنائية أبدًا بعلامات. إذا غيّر الطرفان أحدها، تُحفظ نسختك ويُبلَّغ عن الملف للمعالجة اليدوية. تُبلَّغ الروابط الرمزية (symlinks) بدلًا من استبدالها.

## المساهمة بالتغييرات إلى الخلف {#contributing-changes-back}

المزامنة أحادية الاتجاه بالتصميم: المنبع هو المصدر الوحيد للحقيقة لمحتوى القالب، والتحويلات التي يطبّقها `create` ليست قابلة للعكس بشكل تام. استرجاع `{{APP_NAME}}` من اسم تطبيق فعلي هو تخمين، والملفات التي أعاد `create` كتابتها بالكامل - `package.json`، و`netlify.toml`، و`app/root.tsx`، و`server/plugins/auth.ts` - ليس لها عكس دقيق على الإطلاق.

إذا كنت تعمل داخل إطار العمل monorepo وتريد دفع تحسين من جانب التطبيق إلى الخلف نحو قالب، فإن سكربت `contribute:template` يقوم بالتمرير العكسي مع توضيح هذه الحدود بشكل صريح:

```bash
pnpm contribute:template --app <path-to-app> --dry-run
```

يقارن التطبيق الخاص بك بخط أساسه بحيث تكون تغييراتك أنت فقط هي المرشحة، ثم يعكس استبدال العناصر النائبة (placeholder) على هذه الملفات فقط، ويدمجها بدمج ثلاثي الاتجاهات في `templates/<name>/` كتعديلات غير ملتزم بها (unstaged) على الفرع الحالي، ويطبع كل ما رفض لمسه حتى تنقل القصد يدويًا.

## العلاقة بالأوامر الأخرى {#relationship-to-other-commands}

| الأمر                        | ما يُحرِّكه                                               |
| ---------------------------- | --------------------------------------------------------- |
| `agent-native upgrade`       | إصدارات حزم `@agent-native/*`، والاستيرادات، وأدلة skills |
| `agent-native template sync` | الملفات المنسوخة من قالب وقت الإنشاء                      |
| `agent-native eject`         | مكوّن إطار عمل إلى مصدر مملوك للتطبيق، مع بيانات المنشأ   |

`upgrade` و`template sync` متكاملان وآمنان للتشغيل معًا. `eject` هي الحركة المعاكسة - فهي تأخذ ملكية ملف عمدًا، وتُتتبَّع الملفات المُخرَجة (ejected) بشكل منفصل في `agent-native.ejections.json`.
