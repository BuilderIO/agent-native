# نظرة عامة

Actions هي المصدر الوحيد للحقيقة بالنسبة إلى أي شيء يقوم به تطبيقك. عرّف action باستخدام `defineAction()` وضعه في `actions/`. يلتقطه كل سطح أدناه تلقائيًا. تكتب المنطق مرة واحدة فقط. لا يحصل أي سطح على نسخته الخاصة، ولا يمكن لأي منها أن ينحرف عن الآخرين.

<Cards columns={2}>

### :robot: [أداة الوكيل](/docs/agent-surfaces)

يقرأ الوكيل الوصف والمخطط كأداة قابلة للاستدعاء. اطلبها في المحادثة، مثل "رد على هذه التذكرة" أو "لخّص هذا الموضوع".

### :components: [خطافات واجهة المستخدم](/docs/client-data)

تستدعي `useActionQuery()` و`useActionMutation()` و`callAction()` نفس الـ action من React. تُشغّل نقرة ورسالة محادثة العملية نفسها تمامًا.

### :server: [نقل إطار العمل](/docs/http-api)

يتم تركيبه تلقائيًا عند `/_agent-native/actions/<name>` عند بدء التشغيل. تستدعي خطافات واجهة المستخدم هذا المسار في الخلفية، ويمكن لعميل HTTP خارجي استدعاءه مباشرة أيضًا.

### :plug: [أداة MCP](/docs/actions-other-surfaces#mcp)

تظهر كأداة لأي مضيف MCP: Claude، وClaude Desktop، وCursor، وCodex. استخدمها عندما يحتاج عميل ذكاء اصطناعي مختلف إلى تشغيل تطبيقك.

### :network: [أداة A2A](/docs/actions-other-surfaces#a2a)

تكتشفها تطبيقات agent-native أخرى وتستدعيها عبر A2A. استخدمها عندما يحتاج تطبيق ثانٍ في مساحة عملك إلى أن يتصرف هذا التطبيق نيابة عنه.

### :terminal: [أمر CLI](/docs/actions-other-surfaces#cli)

يشغّله `pnpm action <name>` من الطرفية. استخدمه للنصوص البرمجية، ومهام cron، والاختبارات اليدوية السريعة.

</Cards>

تبني معظم التطبيقات طبقة API منفصلة بين الواجهة الأمامية وقاعدة البيانات، طبقة لا يمكن للمتصفح وحده استدعاؤها. يحتاج الوكيل الذي يريد القدرة نفسها إلى تكامل منفصل خاص به، يُكتب ويُصان من جديد. تتجاوز تطبيقات agent-native هذا الانقسام. تستدعي واجهة المستخدم والوكيل الـ action نفسه تمامًا، لذا لا يوجد سوى تطبيق واحد يُكتب، ومكان واحد فقط يمكن أن يختبئ فيه خطأ.

إذا احتاجت واجهة المستخدم والوكيل كلاهما إلى فعل شيء ما، فاستخدم action بدلاً من مسار مخصص. للحالة النادرة التي يكون فيها بروتوكول على هيئة مسار هو الخيار الصحيح، راجع [تفضيل Actions لعمليات التطبيق](/docs/server-overview#actions-first).

## أين تتناسب Actions {#role}

يتحول كل من `app/` (راجع [نظرة عامة على العميل](/docs/client-overview#role)) والوكيل إلى نفس actions ونفس قاعدة بيانات SQL. لا توجد "خلفية تطبيق" منفصلة تتحدث معها هذه الطبقة ولا يستطيع الوكيل الوصول إليها أيضًا. بناء ميزة يعني تعريف عملية هنا والحصول على واجهة مستخدم، وأداة وكيل، وكل سطح آخر لها في الوقت نفسه.

`actions/` نفسه مجلد مسطّح. كل ملف هو action واحد: استدعاء `defineAction()` يُصدَّر كتصدير افتراضي للملف. يفحص إطار العمل هذا المجلد عند بدء التشغيل ويركّب كل ملف يجده. لا توجد خطوة تسجيل ولا ملف فهرس يجب إبقاؤه محدّثًا.

جسم `run()` الخاص بـ action هو كود خادم عادي، لذا فهو يصل عادةً إلى عدد قليل من الدلائل الأخرى:

## ابدأ بـ action واحد {#hello-action}

يمكن أن تكون أول عملية في تطبيق يعتمد على المحادثة أولاً صغيرة جدًا. في قالب Chat،
استبدل `actions/hello.ts` أو أضف ملفًا جديدًا بجانبه:

```ts
// actions/hello.ts
import { defineAction } from "@agent-native/core/action";
import { z } from "zod";

export default defineAction({
  description: "Say hello from the local agent.",
  schema: z.object({
    name: z.string().default("world"),
  }),
  http: { method: "GET" },
  readOnly: true,
  run: async ({ name }) => {
    return { message: `Hello, ${name}!` };
  },
});
```

شغّله من الدليل نفسه:

```bash
pnpm action hello '{"name":"Steve"}'
```

يقبل CLI كائن JSON كمدخل لـ action، وهو ما يطابق استدعاءات الأداة المنظَّمة
التي يقوم بها الوكلاء بالفعل. لا تزال الأعلام البسيطة تعمل للتشغيلات اليدوية السريعة:

```bash
pnpm action hello --name Steve
```

بعد ذلك، شغّل حلقة التطبيق-الوكيل على المجلد:

```bash
npx agent-native agent "Call hello for Steve and explain the result"
```

هذه هي حلقة التطبيق-الوكيل نفسها التي ستستخدمها مهامك المجدولة، وواجهة
محادثتك، وأدوات MCP الخارجية، والشاشات المستقبلية. قوالب Chat والقوالب
الخاصة بالمجال مخصصة لإضافة واجهة مستخدم حول actions، وليست شرطًا مسبقًا
مطلوبًا لـ action نفسه.
