# Render

<Badge label="Beta" color="orange" icon="rocket" />

يستضيف Render تطبيقك كخدمة ويب، لذلك لا يوجد خادم تحتاج إلى إعداده أو إبقائه
قيد التشغيل. يشغّل Render خادم Node.js نفسه الموضح في
[دليل Node.js](/docs/node-js)، ويبنيه من مستودع Git الخاص بك، ويمنح التطبيق
عنوانًا عامًا مع HTTPS.

يشرح هذا الدليل نشر تطبيق مستقل واحد من البداية. ستنشئ التطبيق وترفعه إلى مستودع
Git، وتمنحه قاعدة بيانات إنتاجية وسر مصادقة، وتجهّز قاعدة البيانات، ثم تنشئ خدمة
ويب على Render تبنيه وتشغّله.

<Callout tone="info">

يلزم Node.js `22.22+`.

</Callout>

تحتاج أيضًا إلى حساب Render ومستودع على GitHub أو GitLab أو Bitbucket. شغّل
الأوامر في هذا الدليل على حاسوبك الخاص. يبني Render التطبيق ويشغّله من مستودعك.

## الخطوة 1: إنشاء التطبيق {#step-1-create-the-app}

أنشئ تطبيقك المستقل الجديد. ينشئ المثال أدناه تطبيقًا من قالب Chat، لكن يمكنك
البدء من أي قالب. انتقل إلى مجلد التطبيق وثبّت تبعياته. يفعّل الأمر
`corepack enable` إصدار `pnpm` الذي يتوقعه التطبيق، لذلك لا تحتاج إلى تثبيت
`pnpm` بنفسك.

```bash
npx --yes @agent-native/core@latest create my-app --standalone --template chat

cd my-app

corepack enable

pnpm install
```

استبدل `my-app` باسم تطبيقك إذا أردت. يفترض باقي هذا الدليل أنك داخل مجلد
التطبيق.

يبني Render التطبيق من مستودع Git، لذلك ارفع مجلد التطبيق إلى مستودع جديد على
GitHub أو GitLab أو Bitbucket قبل أن تتابع. أضف الملف `pnpm-lock.yaml` إلى
الإيداع أيضًا، لأن البناء يثبّت الإصدارات الدقيقة المدرجة فيه.

<Callout tone="info">

إذا فشلت هذه الأوامر بأخطاء في التبعيات النظيرة، فقد يكون السبب نسخة قديمة من حزمة في ذاكرة npx المؤقتة. شغّل `npx clear-npx-cache` لمسح الذاكرة المؤقتة، ثم شغّل الأوامر مرة أخرى.

</Callout>

## الخطوة 2: ضبط أسرار البيئة {#step-2-configure-environment-secrets}

يقرأ التطبيق إعدادات الإنتاج من متغيرات البيئة:

| المتغير              | مطلوب | الغرض                                                   |
| -------------------- | ----- | ------------------------------------------------------- |
| `DATABASE_URL`       | نعم   | يربط التطبيق بقاعدة بيانات PostgreSQL الخاصة به         |
| `BETTER_AUTH_SECRET` | نعم   | يوقّع جلسات المستخدمين                                  |
| `BETTER_AUTH_URL`    | لا    | يحدد العنوان العام الذي يستخدمه الناس للوصول إلى تطبيقك |

تجعل أوامر التصدير أدناه الأوامر التالية تعمل في هذه الصدفة. قبل النشر، احفظ
المتغيرات نفسها في إعدادات بيئة المشروع أو الخدمة لدى موفر الاستضافة. توضح الخطوة
4 كيفية حفظها في Render.

### عنوان URL لقاعدة البيانات {#database-url}

أثناء التطوير المحلي، يخزّن التطبيق البيانات في قاعدة بيانات محلية عندما يكون
`DATABASE_URL` غير مضبوط. يحتاج التطبيق المنشور إلى قاعدة بيانات PostgreSQL
حقيقية تحتفظ ببياناتها بين عمليات النشر. يستبدل Render ملفات الخدمة في كل عملية
نشر وإعادة تشغيل، لذلك يجب أن توجد قاعدة البيانات خارج خدمة الويب. انسخ سلسلة
الاتصال من موفر قاعدة البيانات وصدّرها:

```bash
export DATABASE_URL='your-postgres-url-string'
```

توضح [أدلة موفري قواعد البيانات](/docs/neon) مكان العثور على سلسلة الاتصال لدى
كل موفر. يعمل Render Postgres أيضًا. استخدم سلسلة الاتصال الخارجية الخاصة به هنا،
وسلسلة الاتصال الداخلية في إعدادات خدمة الويب.

<Callout tone="warning">

اختر موفر PostgreSQL دائمًا: Neon أو Supabase أو Amazon RDS أو غيرها.

</Callout>

### سر المصادقة {#auth-secret}

أنشئ هذه القيمة مرة واحدة وأبقها ثابتة عبر عمليات النشر.

يستخدم التطبيق `BETTER_AUTH_SECRET` لتوقيع جلسات المستخدمين. إذا تغيّرت القيمة،
يُسجَّل خروج كل مستخدم مسجّل الدخول. ينشئ الأمر أدناه قيمة عشوائية:

```bash
export BETTER_AUTH_SECRET="$(openssl rand -hex 32)"
```

احفظ القيمة المُنشأة في مكان آمن، مثل مدير كلمات المرور. استخدم القيمة نفسها في
كل مرة تنشر فيها.

### عنوان URL العام {#public-url}

اختياري. اضبطه عند استخدام نطاق مخصص، أو وكيل عكسي، أو تدفق مصادقة أو OAuth يحتاج
إلى أصل عام ثابت.

`BETTER_AUTH_URL` هو العنوان العام الذي يستخدمه الناس للوصول إلى تطبيقك. بدونه،
يستنتج التطبيق عنوانه من كل طلب وارد. يكون ذلك مناسبًا عادةً على العنوان الذي
يمنحك إياه Render، لكن اضبطه عندما تربط نطاقًا مخصصًا حتى تستخدم روابط تسجيل
الدخول وعمليات إعادة توجيه OAuth ذلك النطاق.

```bash
export BETTER_AUTH_URL='https://your-domain.example'
```

## الخطوة 3: الترحيل {#step-3-migrate}

تنشئ عمليات الترحيل الجداول التي يحتاجها التطبيق في قاعدة البيانات وتحدّثها.
شغّل هذا الأمر قبل أول عملية نشر:

```bash
pnpm migrate:production
```

يعمل الأمر على حاسوبك ويتصل بقاعدة بيانات الإنتاج باستخدام `DATABASE_URL` الذي
صدّرته في الخطوة 2. شغّله مرة أخرى بعد ترقية التطبيق، وقبل نشر الإصدار الجديد.

على مثيل Render مدفوع، يمكنك بدلًا من ذلك ضبط **Pre-Deploy Command** الخاص
بالخدمة على `pnpm migrate:production`. يشغّل Render عندها عمليات الترحيل قبل أن
تصبح كل عملية نشر متاحة. لا يتوفر Pre-Deploy Command على نوع المثيل Free.

## الخطوة 4: إنشاء خدمة الويب {#step-4-create-the-web-service}

في لوحة تحكم Render، أنشئ **Web Service** جديدة واربطها بالمستودع من الخطوة 1.
استخدم هذه الإعدادات:

| الإعداد       | القيمة                                                                                    |
| ------------- | ----------------------------------------------------------------------------------------- |
| Language      | `Node`                                                                                    |
| Branch        | الفرع الذي تنشر منه، مثل `main`                                                           |
| Build Command | `corepack enable && pnpm install --frozen-lockfile && NITRO_PRESET=render_com pnpm build` |
| Start Command | `node .output/server/index.mjs`                                                           |

يفعّل Build Command إصدار `pnpm` الخاص بالتطبيق، ويثبّت التبعيات المدرجة في
`pnpm-lock.yaml`، ويبني التطبيق. يبني `NITRO_PRESET=render_com` خادم Node.js
نفسه الموجود في دليل Node.js، مُعدًّا لتقديم ملفاته الثابتة بنفسه. يشغّل Start
Command ذلك الخادم. يخبر Render الخادم بالمنفذ الذي يستخدمه عبر متغير البيئة
`PORT`، ويقرأه الخادم تلقائيًا.

ضمن **Environment Variables**، أضف `DATABASE_URL` و`BETTER_AUTH_SECRET` بالقيم
التي صدّرتها في الخطوة 2. إذا ضبطت `BETTER_AUTH_URL`، فأضفه بالطريقة نفسها.

يختار Render إصدار Node.js من متغير البيئة `NODE_VERSION`، أو من ملف
`.node-version` أو `.nvmrc`، أو من الحقل `engines` في `package.json`، بهذا
الترتيب. تستخدم الخدمات الجديدة افتراضيًا إصدارًا يستوفي المتطلب المذكور أعلاه.
لتثبيت إصدار معيّن، أضف `NODE_VERSION`، على سبيل المثال بالقيمة `24`.

## الخطوة 5: النشر {#step-5-deploy}

<Steps>

### اختيار نوع المثيل

اختر نوع المثيل لخدمة الويب. يكفي نوع المثيل Free لتجربة التطبيق. اختر نوع مثيل
مدفوعًا إذا كان التطبيق يحتاج إلى الاستجابة فورًا أو أردت استخدام Pre-Deploy
Command من الخطوة 3.

### إنشاء خدمة الويب

أنشئ خدمة الويب. يبني Render التطبيق من مستودعك ويشغّله. يستغرق البناء الأول بضع
دقائق، ويمكنك متابعته في سجلات الخدمة.

### فتح التطبيق

عندما تنتهي عملية النشر، تعرض لوحة التحكم عنوان التطبيق، الذي ينتهي بـ
`onrender.com`. افتحه وأنشئ الحساب الأول.

</Steps>

على نوع المثيل Free، يوقف Render الخدمة مؤقتًا بعد 15 دقيقة بدون حركة مرور. ثم
تنتظر الزيارة التالية نحو دقيقة بينما تبدأ الخدمة من جديد.

## نشر التحديثات {#deploy-updates}

ينشر Render من جديد في كل مرة ترفع فيها إلى الفرع الذي اخترته في الخطوة 4.
لإصدار نسخة جديدة، شغّل عمليات الترحيل أولًا، ثم ارفع التغييرات:

```bash
pnpm migrate:production

git push
```

تبقى إعدادات الخدمة والمتغيرات المحفوظة كما هي، لذلك لا تحتاج إلى تكرار الخطوة 4.
