# Azure Static Web Apps

<Badge label="Beta" color="orange" icon="rocket" />

يستضيف Azure Static Web Apps تطبيقك نيابةً عنك، لذلك لا يوجد خادم تحتاج إلى
إعداده أو إبقائه قيد التشغيل. يقدّم الملفات الثابتة للتطبيق مباشرةً ويشغّل خادم
التطبيق بصفته Azure Functions مُدارة، ويمنح التطبيق عنوانًا عامًا مع HTTPS.

يشرح هذا الدليل نشر تطبيق مستقل واحد من البداية. ستنشئ التطبيق، وتمنحه قاعدة
بيانات إنتاجية وسر مصادقة، وتجهّز قاعدة البيانات، وتبنيه لـ Azure، وتنشئ تطبيق
ويب ثابتًا، ثم ترفع البناء النهائي باستخدام Static Web Apps CLI.

<Callout tone="info">

يلزم Node.js `22.22+`.

</Callout>

تحتاج أيضًا إلى حساب Azure. شغّل الأوامر في هذا الدليل على حاسوبك الخاص. تبني
التطبيق باستخدام Node.js، ويرفع Static Web Apps CLI البناء النهائي إلى Azure.

## الخطوة 1: إنشاء التطبيق {#step-1-create-the-app}

أنشئ تطبيقك المستقل الجديد. ينشئ المثال أدناه تطبيقًا من قالب Chat، لكن يمكنك
البدء من أي قالب. انتقل إلى مجلد التطبيق وثبّت تبعياته. يفعّل الأمر
`corepack enable` إصدار `pnpm` الذي يتوقعه التطبيق، لذلك لا تحتاج إلى تثبيت
`pnpm` بنفسك.

```bash
npx --yes @agent-native/core@latest create my-app --standalone --template chat

cd my-app

corepack enable

pnpm install
```

استبدل `my-app` باسم تطبيقك إذا أردت. يفترض باقي هذا الدليل أنك داخل مجلد
التطبيق.

## الخطوة 2: ضبط أسرار البيئة {#step-2-configure-environment-secrets}

يقرأ التطبيق إعدادات الإنتاج من متغيرات البيئة:

| المتغير              | مطلوب | الغرض                                                   |
| -------------------- | ----- | ------------------------------------------------------- |
| `DATABASE_URL`       | نعم   | يربط التطبيق بقاعدة بيانات PostgreSQL الخاصة به         |
| `BETTER_AUTH_SECRET` | نعم   | يوقّع جلسات المستخدمين                                  |
| `BETTER_AUTH_URL`    | لا    | يحدد العنوان العام الذي يستخدمه الناس للوصول إلى تطبيقك |

تجعل أوامر التصدير أدناه الأوامر التالية تعمل في هذه الصدفة. قبل النشر، احفظ
المتغيرات نفسها في إعدادات بيئة المشروع أو الخدمة لدى موفر الاستضافة. توضح الخطوة
5 كيفية حفظها في Azure.

### عنوان URL لقاعدة البيانات {#database-url}

أثناء التطوير المحلي، يخزّن التطبيق البيانات في قاعدة بيانات محلية عندما يكون
`DATABASE_URL` غير مضبوط. يحتاج التطبيق المنشور إلى قاعدة بيانات PostgreSQL
حقيقية تحتفظ ببياناتها بين عمليات النشر. لا تحتفظ Azure Functions بالملفات بين
الطلبات، لذلك يجب أن توجد قاعدة البيانات خارج تطبيق الويب الثابت. انسخ سلسلة
الاتصال من موفر قاعدة البيانات وصدّرها:

```bash
export DATABASE_URL='your-postgres-url-string'
```

توضح [أدلة موفري قواعد البيانات](/docs/neon) مكان العثور على سلسلة الاتصال لدى
كل موفر، بما في ذلك
[Azure Database for PostgreSQL](/docs/azure-postgresql).

<Callout tone="warning">

اختر موفر PostgreSQL دائمًا: Neon أو Supabase أو Amazon RDS أو غيرها.

</Callout>

### سر المصادقة {#auth-secret}

أنشئ هذه القيمة مرة واحدة وأبقها ثابتة عبر عمليات النشر.

يستخدم التطبيق `BETTER_AUTH_SECRET` لتوقيع جلسات المستخدمين. إذا تغيّرت القيمة،
يُسجَّل خروج كل مستخدم مسجّل الدخول. ينشئ الأمر أدناه قيمة عشوائية:

```bash
export BETTER_AUTH_SECRET="$(openssl rand -hex 32)"
```

احفظ القيمة المُنشأة في مكان آمن، مثل مدير كلمات المرور. استخدم القيمة نفسها في
كل مرة تنشر فيها.

### عنوان URL العام {#public-url}

اختياري. اضبطه عند استخدام نطاق مخصص، أو وكيل عكسي، أو تدفق مصادقة أو OAuth يحتاج
إلى أصل عام ثابت.

`BETTER_AUTH_URL` هو العنوان العام الذي يستخدمه الناس للوصول إلى تطبيقك. بدونه،
يستنتج التطبيق عنوانه من كل طلب وارد. يكون ذلك مناسبًا عادةً على العنوان الذي
يمنحك إياه Azure، لكن اضبطه عندما تربط نطاقًا مخصصًا حتى تستخدم روابط تسجيل
الدخول وعمليات إعادة توجيه OAuth ذلك النطاق.

```bash
export BETTER_AUTH_URL='https://your-domain.example'
```

## الخطوة 3: الترحيل {#step-3-migrate}

تنشئ عمليات الترحيل الجداول التي يحتاجها التطبيق في قاعدة البيانات وتحدّثها.
شغّل هذا الأمر قبل أول عملية نشر:

```bash
pnpm migrate:production
```

يعمل الأمر على حاسوبك ويتصل بقاعدة بيانات الإنتاج باستخدام `DATABASE_URL` الذي
صدّرته في الخطوة 2. شغّله مرة أخرى بعد ترقية التطبيق، وقبل نشر الإصدار الجديد.

## الخطوة 4: البناء {#step-4-build}

### ضبط بيئة تشغيل الواجهة البرمجية {#set-the-api-runtime}

يشغّل Azure خادم التطبيق على إصدار Node.js المذكور في الملف
`staticwebapp.config.json` الخاص بالبناء. يختار البناء هذا الإصدار من الحقل
`engines` في `package.json`، لكن فقط عندما تكون قيمة الحقل `20` أو `22` تمامًا.
يتطلب التطبيق الجديد `>=22.22.0`، لذلك يعود البناء إلى Node.js 18، وهو إصدار قديم
جدًا بالنسبة إلى التطبيق ولم يعد Azure يدعمه.

اضبط الإصدار بنفسك في `vite.config.ts`. أضف الخيار `nitro` إلى استدعاء الإضافة
`agentNative` الموجود، واترك باقي الملف دون تغيير:

```ts filename="vite.config.ts"
...agentNativePlugins({
  ssrStubs: ["shiki"],
  nitro: {
    azure: { config: { platform: { apiRuntime: "node:22" } } },
  },
}),
```

يستخدم هذا المثال ملف `vite.config.ts` من قالب Chat. في القوالب الأخرى، أضف
الخيار `nitro` نفسه إلى استدعاء `agentNative` هناك.

### بناء التطبيق {#build-the-app}

ابنِ التطبيق لـ Azure Static Web Apps:

```bash
NITRO_PRESET=azure-swa pnpm build
```

يبني `NITRO_PRESET=azure-swa` التطبيق بالتنسيق الذي يتوقعه Azure Static Web Apps.
يكتب البناء الملفات الثابتة في `.output/public` ودوال الخادم في `.output/server`.
ويكتب أيضًا الملف `staticwebapp.config.json`، مع بيئة تشغيل الواجهة البرمجية من
القسم السابق، في مجلد التطبيق.

## الخطوة 5: إنشاء تطبيق الويب الثابت وحفظ الأسرار {#step-5-create-the-static-web-app-and-save-the-secrets}

في بوابة Azure، أنشئ **Static Web App** جديدًا. اختر اشتراكًا ومجموعة موارد
واسمًا وخطة. ضمن **Deployment details**، اختر **Other**، لأنك ترفع البناء بنفسك
بدلًا من ربط مستودع GitHub.

انسخ رمز النشر من صفحة **Overview** الخاصة بالتطبيق ضمن **Manage deployment
token**، وصدّره:

```bash
export SWA_CLI_DEPLOYMENT_TOKEN='your-deployment-token'
```

يقرأ Static Web Apps CLI هذا المتغير في الخطوة 6. أبقِ الرمز سريًا، لأن أي شخص
يملكه يستطيع النشر إلى تطبيقك.

ثم احفظ المتغيرين المطلوبين. في بوابة Azure، افتح تطبيق الويب الثابت، وانتقل إلى
**Settings** > **Environment variables**، واختر البيئة **Production**، وأضف
`DATABASE_URL` و`BETTER_AUTH_SECRET` بالقيم التي صدّرتها في الخطوة 2. إذا ضبطت
`BETTER_AUTH_URL`، فأضفه بالطريقة نفسها. يمرّر Azure هذه القيم إلى دوال خادم
التطبيق بصفتها متغيرات بيئة.

## الخطوة 6: النشر {#step-6-deploy}

<Steps>

### رفع البناء

من مجلد التطبيق، ارفع الملفات الثابتة ودوال الخادم إلى الإنتاج:

```bash
npx @azure/static-web-apps-cli deploy .output/public --api-location .output/server --swa-config-location . --env production
```

يحتوي `.output/public` على الملفات الثابتة، ويشير `--api-location .output/server`
إلى دوال الخادم. ويشير `--swa-config-location .` إلى مجلد التطبيق، حيث كتب البناء
الملف `staticwebapp.config.json`. بدونه، لا يرى Azure بيئة تشغيل الواجهة البرمجية
من الخطوة 4. وينشر `--env production` إلى عنوان الإنتاج الخاص بك بدلًا من بيئة
معاينة.

### فتح التطبيق

عندما ينتهي الأمر، يطبع عنوان التطبيق، الذي ينتهي بـ `azurestaticapps.net`.
افتحه وأنشئ الحساب الأول.

</Steps>

## نشر التحديثات {#deploy-updates}

لإصدار نسخة جديدة، شغّل عمليات الترحيل، وابنِ التطبيق مرة أخرى، ثم ارفعه:

```bash
pnpm migrate:production

NITRO_PRESET=azure-swa pnpm build

npx @azure/static-web-apps-cli deploy .output/public --api-location .output/server --swa-config-location . --env production
```

صدّر `SWA_CLI_DEPLOYMENT_TOKEN` مرة أخرى في صدفة جديدة. تبقى متغيرات البيئة
المحفوظة على تطبيق الويب الثابت، لذلك لا تحتاج إلى تكرار الخطوة 5.

## حدود الطلبات {#request-limits}

ينهي Azure Static Web Apps أي طلب إلى خادم التطبيق بعد 45 ثانية، ولا يدعم
WebSockets. ينهي Agent-Native بالفعل دورة المحادثة بعد نحو 40 ثانية ويواصلها من
المتصفح، لذلك تكتمل دورات الوكيل الطويلة، لكنها تعمل على عدة خطوات بدلًا من خطوة
واحدة. إذا كان تطبيقك يحتاج إلى طلبات طويلة، فاستخدم مضيفًا بلا هذا الحد، مثل
[Node.js](/docs/node-js) أو [Docker](/docs/docker).
