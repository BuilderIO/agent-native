# 반복 작업

**반복 작업**은 크론 일정에 따라 실행되는 프롬프트입니다. 에이전트가 자체적으로 작업을 수행하는 방식입니다. "매일 아침 7시에 밤샘 이메일 요약", "매주 월요일 지난 주의 가입 번호를 Slack에 게시", "매시간 오래된 초안을 검색하여 삭제합니다."

<Callout tone="info">

**Recurring Jobs**는 **Scheduled** 자동화의 기존 이름입니다. **Automations**는 **Scheduled**와 **Event**를 포괄합니다. `jobs/`와 `manage-jobs`는 기존 schedule-only 통합을 위해 유지됩니다. 모델과 MCP 허용 목록을 포함한 새로운 개인 또는 조직 작업에는 `manage-automations`와 `/agent#jobs`의 **Automations**를 사용하세요.

</Callout>

반복 작업은 정해진 시간에 실행됩니다. _이벤트_(예약 생성, 이메일 수신)에 반응하려면 — 동일한 `jobs/` 파일 형식과 조건 — [Automations](/docs/automations)를 참조하세요.

작업은 `jobs/<name>.md`의 [에이전트 리소스](/docs/agent-resources)에 있습니다. YAML 머리말이 있는 Markdown 파일입니다. 등록도 없고 배선도 없습니다. 파일을 드롭하면 프레임워크가 이를 선택합니다.

## 머리말 {#frontmatter}

| 필드         | 유형                          | 기본값      | 설명                                                                                                             |
| ------------ | ----------------------------- | ----------- | ---------------------------------------------------------------------------------------------------------------- |
| `schedule`   | 크론 표현                     | _(필수)_    | 표준 5필드 크론. `"0 7 * * *"` = 매일 07:00; `"0 */4 * * *"` = 4시간마다.                                        |
| `enabled`    | 부울                          | `true`      | 작업을 삭제하지 않고 일시 중지하려면 `false`로 전환하세요.                                                       |
| `runAs`      | `"creator"` \| `"shared"`     | `"creator"` | `"creator"`는 작업 소유자의 ID와 `ANTHROPIC_API_KEY`를 사용하여 실행됩니다. `"shared"`는 조직의 키를 사용합니다. |
| `createdBy`  | 이메일                        | _(자동)_    | 에이전트 리소스 UI를 통해 또는 에이전트에 의해 작업이 생성될 때 채워집니다.                                      |
| `orgId`      | 문자열                        | _(자동)_    | 조직 범위; 작성자의 활성 조직에서 상속됩니다.                                                                    |
| `lastRun`    | ISO 타임스탬프                | _(관리)_    | 각 실행 후 스케줄러에 의해 작성됩니다.                                                                           |
| `lastStatus` | `"success"` \| `"error"` \| … | _(관리)_    | 최신 결과.                                                                                                       |
| `lastError`  | 문자열                        | _(관리)_    | 마지막 실행이 실패한 경우 오류 메시지.                                                                           |
| `nextRun`    | ISO 타임스탬프                | _(관리)_    | `schedule`에서 계산됩니다. 스케줄러가 다음에 실행할 시기를 결정하는 데 사용됩니다.                               |
| `mcpTools`   | MCP 도구 이름 배열            | _(없음)_    | `mcp__server__tool`과 같은 선택적 명시적 허용 목록입니다. 자격 증명은 연결된 MCP grant에 유지됩니다.             |

`last*` 및 `nextRun` 필드는 스케줄러에 의해 작성됩니다. 이를 읽어 기록을 볼 수 있지만 직접 편집하지 마십시오. 다음 실행 시 덮어쓰게 됩니다.

## 작업에 MCP 도구 연결 {#connected-mcps}

반복 작업에서는 이미 앱에 연결된 원격 또는 로컬 MCP 도구를 사용할 수 있습니다. 먼저 에이전트에게 `tool-search`로 정확한 이름을 찾도록 요청한 다음, `mcpTools`를 사용해 해당 작업에 필요한 도구만 바인딩하세요.

```md
---
schedule: "0 * * * *"
enabled: true
mcpTools:
  ["mcp__meeting-notes__list_recordings", "mcp__meeting-notes__get_transcript"]
---

마지막으로 성공한 실행 이후의 새 녹화를 찾습니다. 실행 가능한 후속 조치만 추출한 뒤, 안정적인 소스 및 외부 ID, 짧은 인용, 녹화 URL과 함께 앱의 범위가 제한된 가져오기 action을 한 번만 호출하세요. 전체 트랜스크립트는 가져오지 마세요.
```

작업은 MCP URL, 액세스 토큰 또는 OAuth 새로 고침 토큰이 아니라 도구 이름을 저장합니다. 실행 시 프레임워크는 작업 생성자 또는 조직의 요청 컨텍스트에서 연결된 grant를 확인하고 허용 목록의 도구만 노출합니다. 목록은 좁게 유지하고, 겹치는 실행으로 중복 항목이 생기지 않도록 최종 가져오기에는 멱등성 app action을 사용하세요. 연결 및 OAuth 설정은 [MCP Clients](/docs/mcp-clients)를 참조하세요.

## 크론 구문 {#cron}

표준 5필드 크론(분, 시간, 일, 월, 요일):

| 크론           | 의미              |
| -------------- | ----------------- |
| `*/5 * * * *`  | 5분마다           |
| `0 * * * *`    | 매시 정각         |
| `0 */4 * * *`  | 4시간마다         |
| `0 7 * * *`    | 매일 07:00        |
| `0 9 * * 1`    | 매주 월요일 09:00 |
| `0 17 * * 1-5` | 평일 17:00        |
| `0 0 1 * *`    | 매월 1일          |

프레임워크에는 리소스 및 스케줄러 계층에서 내부적으로 사용되는 cron 문자열을 검증하고 렌더링하기 위한 cron 유틸리티(`isValidCron()` 및 `describeCron()`)가 포함되어 있습니다.

## 작업 생성 {#creating}

### 작업공간 탭에서

`+` → 에이전트 리소스 패널의 **예약된 작업**. 프롬프트와 일정을 입력하세요. `jobs/<slug>.md`로 저장하고 다음 일치하는 틱에서 실행을 시작합니다.

### 에이전트에게 요청

> "매일 아침 7시에 읽지 않은 이메일을 요약하는 예약된 작업을 만듭니다."

에이전트가 파일을 작성합니다.

### 손으로

프레임워크의 리소스 APIs를 통해 `jobs/`에 Markdown 파일을 삭제합니다.

```ts
import { resourcePut } from "@agent-native/core/resources";

await resourcePut(
  ownerEmail,
  "jobs/morning-digest.md",
  `---
schedule: "0 7 * * *"
enabled: true
---
Summarize overnight emails.`,
);
```

## 스케줄러 실행 방법 {#how-scheduler-runs}

각 틱마다 스케줄러(내부 `processRecurringJobs()` 루틴)는 실행할 때가 된 작업을 찾아 실행합니다. 틱을 발생시키는 주체는 앱이 실행되는 위치에 따라 다릅니다:

| 호스트                                                           | 틱을 발생시키는 것                                      | 요구 사항 및 제한                                                                                                    |
| ---------------------------------------------------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 장기 실행 서버(Node.js, Docker, Fly, Render, VPS)                | 부팅 10초 후부터 60초마다 실행되는 프로세스 내 타이머   | 프로세스가 실행 중인 동안 동작합니다.                                                                                |
| [Netlify](/docs/netlify)                                         | 빌드가 생성하는 예약 함수, 1분마다                      | 게시된 배포에서만 동작하며 Deploy Preview나 브랜치 배포에서는 동작하지 않습니다. 빌드에 `A2A_SECRET`이 필요합니다.   |
| [Vercel](/docs/vercel#vercel-scheduled-work)                     | 빌드가 추가하는 Vercel cron 작업, 기본값은 1분마다      | 프로덕션 배포에서만 동작합니다. `CRON_SECRET`이 필요합니다. Hobby 프로젝트는 하루에 최대 한 번만 실행할 수 있습니다. |
| [Cloudflare Workers](/docs/cloudflare#cloudflare-scheduled-work) | 빌드가 `wrangler.json`에 추가하는 Cron Trigger, 1분마다 | Worker 시크릿으로 `A2A_SECRET`이 필요합니다.                                                                         |
| AWS Lambda                                                       | 없음                                                    | 예약 자동화가 실행되지 않습니다.                                                                                     |
| 로컬 개발                                                        | 옵트인하지 않으면 없음                                  | 아래 안내를 참조하세요.                                                                                              |

Netlify, Vercel, Cloudflare에서는 같은 틱이 이벤트 트리거 자동화 대기열을 비우고,
함수가 중간에 끊긴 실행을 정리하며, Mail의 다시 알림과 예약 발송 같은 앱 스윕도
실행합니다. 트리거가 없는 서버리스 배포에서는 이 중 어느 것도 일어나지 않습니다.
이벤트 트리거 자동화는 대기열에서 기다리고, 중단된 실행은 멈춘 상태로 남습니다.
웹훅 트리거 자동화와 **Run now**는 자체적으로 디스패치되므로 계속 동작합니다.
배포에서 일정을 실행할 수 없으면 **Automations** 페이지가 그 사실과 이유를 알려 줍니다.

<Callout id="doc-block-j6yn07" tone="risk">

**웜 인스턴스는 일정을 실행하지 않습니다.** 서버리스 호스트는 프로세스 내 타이머를 시작하지 않으므로 keep-alive 핑을 보내도 작업이 실행되지 않습니다. 작업을 실행하는 것은 위 표의 플랫폼 트리거뿐입니다. AWS Lambda에서는 아직 아무것도 작업을 실행하지 않으므로, 예약 자동화는 장기 실행 호스트(Fly, Render, VPS)에서 실행하세요.

</Callout>

<Callout id="doc-block-rj2" tone="warning">

**로컬 개발에서는 기본적으로 비활성화됩니다.** 스케줄러의 `setInterval` 루프는 `NODE_ENV`가 `development` 또는 `test`이거나, 앱 URL이 `localhost` / `127.0.0.1` / `*.localhost`를 가리킬 때 시작되지 않습니다. 대부분의 로컬 개발 환경이 여기에 해당합니다. 그래도 로컬에서 스케줄러를 실행하려면 `AGENT_NATIVE_ENABLE_LOCAL_RECURRING_JOBS=1`을 설정하세요. 어떤 호스트에서든 예약된 작업을 끄려면 바로 아래에서 설명하는 `AGENT_NATIVE_DISABLE_RECURRING_JOBS=1`을 사용하세요.

</Callout>

<Callout id="doc-block-rj3" tone="warning">

**`AGENT_NATIVE_DISABLE_RECURRING_JOBS`는 두 범위에서 읽힙니다.** Netlify, Vercel, Cloudflare에서는 **빌드** 환경이 결정합니다. 플랫폼 트리거는 이벤트 자동화 대기열을 비우고 실행을 정리하기 위해 계속 실행되지만, 스위치를 켠 빌드는 배포된 환경의 설정과 관계없이 예약된 작업을 건너뜁니다. 장기 실행 서버에서는 **런타임** 환경이 프로세스 내 타이머를 제어합니다. 호스트가 이 값을 읽는 곳에 설정하세요. 빌드가 결정을 기록하므로, **Automations** 페이지는 아무도 지키지 않을 다음 실행 날짜를 보여 주는 대신 일정이 절대 실행되지 않는다고 알려 줄 수 있습니다.

</Callout>

## 작업 디버깅 {#debugging}

- 에이전트 리소스에서 `jobs/<name>.md`를 엽니다. 머리말에는 `lastRun`, `lastStatus`, `lastError`, `nextRun`가 표시됩니다.
- **기다리지 않고 테스트하세요.** **Automations**에서 자동화를 열고 **Run now**를 선택하세요. 자동화가 실제 부수 효과와 함께 즉시 실행되며 스케줄러 틱을 기다리지 않으므로, 로컬과 트리거가 없는 호스트에서도 동작합니다.
- **일시 중지:** `enabled: false`를 뒤집습니다. 파일은 그대로 유지되고 실행이 중지됩니다.

## 에이전트 도구 {#agent-tool}

단일 `manage-jobs` 도구가 모든 템플릿에 등록됩니다. `action` 매개변수는 작업을 선택합니다:

| 액션     | 매개변수                                                                 | 목적                                                       |
| -------- | ------------------------------------------------------------------------ | ---------------------------------------------------------- |
| `create` | `name`, `schedule`, `instructions`(필수); `scope`, `runAs`, `mcpTools`   | 새 반복 작업 만들기                                        |
| `list`   | `scope`(`personal`, `shared` 또는 모두)                                  | 상태(일정, 활성화, 마지막/다음 실행)와 함께 모든 작업 나열 |
| `update` | `name`(필수); `schedule`, `instructions`, `enabled`, `runAs`, `mcpTools` | 기존 작업 편집                                             |
| `delete` | `name` (필수)                                                            | 작업 삭제 — 항상 먼저 사용자에게 확인                      |

**개인 범위와 공유 범위.** 각 자동화는 개인 또는 조직 범위에 있으며 생성자로 실행됩니다. 관리자는 공유 정의를 관리할 수 있지만 생성자 ID는 변경할 수 없습니다. 조직 실행 전마다 프레임워크는 생성자가 존재하고 여전히 구성원인지 확인합니다.

## 스케줄링 패키지와 다름 {#vs-scheduling-package}

반복 작업을 `@agent-native/scheduling`와 혼동하지 마십시오:

- **반복 작업(이 페이지)** — cron-scheduled _prompts_ 에이전트가 백그라운드에서 실행됩니다. 프레임워크 수준. 에이전트 리소스에 거주합니다. 스케줄러가 있는 모든 호스트에서 실행됩니다([스케줄러 실행 방법](#how-scheduler-runs) 참조).
- **`@agent-native/scheduling`** — 달력/예약 기능(이벤트 유형, 이용 가능 기간, 예약) 구축을 위한 재사용 가능한 도메인 패키지입니다. `calendar` 템플릿과 맞춤형 일정 관리 화면을 강화합니다.

반복 작업은 "에이전트가 스스로 작동하도록 하려면 어떻게 해야 합니까?"입니다. 일정 패키지는 "캘린더 앱을 어떻게 구축하나요?"입니다. 다양한 우려 사항.
