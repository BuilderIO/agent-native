# 데이터베이스

모든 에이전트 기반 앱은 상태를 PostgreSQL에 저장합니다. UI와 에이전트는 동일한 [Drizzle ORM](https://orm.drizzle.team) 클라이언트를 사용해 동일한 액션을 통해 동일한 테이블을 읽고 씁니다. 실시간 동기화는 SSE를 사용하고 폴링을 fallback으로 사용하므로, 수동으로 새로 고치지 않아도 변경 사항이 다른 화면에 표시됩니다.

## 호스팅 옵션 {#hosting}

앱은 PostgreSQL을 사용합니다. `DATABASE_URL`이 설정되지 않으면 로컬 PGlite을 사용하므로 구성 없이 시작할 수 있습니다.

### 기본값: PGlite 파일 {#default-pglite}

`DATABASE_URL`이 설정되어 있지 않으면 앱은 `data/pglite`에 PGlite 데이터베이스를 생성합니다. 별도의 구성이 필요 없습니다. 개발 서버를 시작하면 첫 실행 시 파일이 생성됩니다.

이는 로컬 개발용으로만 사용됩니다. 컨테이너, 서버리스 함수, 미리보기 환경은 재시작 사이에 파일 시스템을 초기화할 수 있으므로 로컬 PGlite 파일이 사라질 수 있습니다. 배포하기 전에 `DATABASE_URL`을 영구적인 호스팅 PostgreSQL 데이터베이스로 설정하세요.

### 로컬 Postgres: PGlite {#local-pglite}

Docker나 호스팅 데이터베이스 없이 로컬에서 PostgreSQL을 개발하려면 선택적 PGlite 패키지를 설치하고 `DATABASE_URL`을 설정하세요:

```bash
pnpm add @electric-sql/pglite@^0.5.8
```

```bash
DATABASE_URL=pglite:./data/pglite
```

[PGlite](https://pglite.dev/)는 프로세스 내에서 실행되는 WASM 기반 Postgres 데이터베이스입니다. PGlite 기본값만큼 설정을 간단하게 유지하면서도 Postgres 전용 스키마 문제를 배포 전에 잡아낼 수 있게 해줍니다. PGlite와 마찬가지로 로컬 전용 저장소입니다. 프로덕션이나 공유 환경에는 사용하지 마세요.

### 프로덕션 데이터베이스 {#production}

`.env` 파일이나 배포 제공자 환경에서 `DATABASE_URL`을 설정해 호스팅된 데이터베이스를 연결하세요.

```bash
# Neon Postgres
DATABASE_URL=postgres://user:pass@ep-cool-name-123456.us-east-2.aws.neon.tech/mydb?sslmode=require

# Supabase Postgres
DATABASE_URL=postgres://postgres.xxxx:pass@aws-0-us-east-1.pooler.supabase.com:6543/postgres

# 일반 Postgres
DATABASE_URL=postgres://user:pass@localhost:5432/mydb

DATABASE_URL=pglite:./data/pglite
```

프레임워크는 `DATABASE_URL`을 기준으로 Drizzle을 PostgreSQL용으로 구성합니다.

### Builder.io 관리형 데이터베이스 {#builder-managed}

_계획됨(아직 사용할 수 없음):_ Builder.io에 연결되면 앱은 PostgreSQL 연결 문자열 없이도 자동으로 프로비저닝되는 관리형 PostgreSQL 데이터베이스를 사용할 수 있게 됩니다.

## 데이터베이스 설정하기 {#setup}

데이터베이스를 사용하는 앱에는 세 개의 파일이 필요합니다.

- `server/db/schema.ts`: 테이블 정의
- `server/db/index.ts`: 타입이 지정된 DB 클라이언트 싱글톤
- `server/plugins/db.ts`: 로컬 시작을 위한 앱 소유 마이그레이션

### 1. 스키마 정의하기 {#schema}

`@agent-native/core/db/schema`에서 스키마 도우미를 가져오세요. 프레임워크 도우미는 PostgreSQL 및 PGlite 전용 정의를 생성합니다.

```ts filename="server/db/schema.ts"
import { sql } from "drizzle-orm";
import { boolean, integer, pgTable, text } from "drizzle-orm/pg-core";

export const tasks = pgTable("tasks", {
  id: text("id").primaryKey(),
  title: text("title").notNull(),
  priority: integer("priority").notNull().default(0),
  done: boolean("done").notNull().default(false),
  ownerEmail: text("owner_email").notNull(),
  createdAt: text("created_at")
    .notNull()
    .default(sql`now()`),
});
```

| 도우미            | 목적                              |
| ----------------- | --------------------------------- |
| `pgTable`         | PostgreSQL 테이블을 정의합니다    |
| `text`            | 텍스트 열, `{ enum: [...] }` 지원 |
| `integer`         | 정수 열                           |
| `boolean`         | 불리언 열                         |
| `doublePrecision` | 배정밀도 부동소수점 열            |
| `sql`             | `now()`와 같은 SQL 표현식         |

### 2. DB 클라이언트 생성하기 {#db-client}

각 앱은 `createGetDb(schema)`를 호출해 게으른(lazy) 싱글톤 Drizzle 클라이언트를 생성합니다. 정식 위치는 `server/db/index.ts`입니다.

```ts filename="server/db/index.ts"
import { createGetDb } from "@agent-native/core/db";
import * as schema from "./schema.js";

export const getDb = createGetDb(schema);
```

`createGetDb`는 처음 호출할 때 PostgreSQL 연결을 열고 이후 호출에서 동일한 타입 지정 Drizzle 인스턴스를 반환하는 `getDb()` 함수를 반환합니다. `DATABASE_URL`을 읽어 호스팅 PostgreSQL 또는 로컬 PGlite에 연결합니다.

액션과 라우트에서는 이 템플릿 로컬 경로에서 `getDb`를 가져오세요. `@agent-native/core`에서 직접 가져오지 마세요. 코어의 내보내기는 타입이 지정되어 있지 않으며, 로컬 내보내기가 여러분의 스키마 타입을 담고 있습니다.

### 3. 마이그레이션 작성하기 {#migrations}

로컬 개발에서는 `server/plugins/db.ts`의 Nitro 플러그인을 통해 스키마 변경을
적용할 수 있습니다. 프로덕션 또는 서버리스 배포에서는 첫 요청이 아니라
릴리스 또는 배포 단계에서 마이그레이션을 실행하세요.
`@agent-native/core/db`의 `runMigrations`를 사용하세요.

### Drizzle Kit으로 새 앱 마이그레이션 생성하기 {#drizzle-migrations}

새 앱 스키마 변경에는 `pnpm db:generate`를 사용해 검토 가능한 SQL을
생성하세요. 이 명령은 `server/db/migrations/<id_name>.sql`을 만들고,
`runDrizzleMigrations`가 Node.js 및 Node 기반 serverless 런타임에서 이 파일들을
공유 Agent-Native 러너에 로드합니다. 운영 변경의 책임은 계속 릴리스 단계에
있습니다. PostgreSQL 전용 SQL, Postgres 동작, backfill 및 지연된 JavaScript 단계에는
`runMigrations()`를 계속 사용하세요.

파일 시스템 기반 loader는 Cloudflare Workers/Pages 또는 배포 가능한 파일 시스템이
없는 다른 edge runtime에서 사용할 수 없습니다. 해당 환경에서는 worker bundle에 포함한
PostgreSQL migration 항목과 함께 `runMigrations()`를 사용하세요. 마이그레이션은 PostgreSQL용으로
생성하고 같은 폴더를 로컬 PGlite와 호스팅 PostgreSQL 사이에서 전환하지 마세요.

<Callout tone="risk">
  프로덕션 데이터베이스에 대해 `drizzle-kit push`를 절대 실행하지 마세요. 템플릿
  스키마는 앱별 테이블만 정의하며, 중앙 프레임워크 테이블(`user`, `session`,
  `application_state` 등)은 포함하지 않습니다. 프로덕션에 대해 `drizzle-kit
  push`를 실행하면 이러한 테이블을 알 수 없는 것으로 감지해 삭제를 시도하며,
  즉각적인 데이터 손실로 이어집니다.
</Callout>

각 앱 루트의 `drizzle.config.ts`는 로컬 개발용 PostgreSQL 스키마 검사를 위해 drizzle-kit을 구성합니다. PostgreSQL 데이터베이스를 명시적으로 구성하세요. 예: `createDrizzleConfig({ dialect: "postgresql" })`:

```ts filename="drizzle.config.ts"
import { createDrizzleConfig } from "@agent-native/core/db/drizzle-config";
export default createDrizzleConfig();
```

스키마를 검사하려면 `pnpm db:generate`를, 로컬 데이터베이스에 대해서만 `pnpm db:push`를 사용하세요.

### 4. 액션에서 쿼리하기 {#querying}

액션에서 `getDb()`를 호출해 타입이 지정된 Drizzle 클라이언트를 얻으세요. Drizzle의 쿼리 빌더와 `drizzle-orm`의 이식 가능한 연산자를 사용하세요.

```ts
import { and, desc, eq } from "drizzle-orm";
import { getDb } from "../server/db/index.js";
import * as schema from "../server/db/schema.js";

const db = getDb();

const openTasks = await db
  .select()
  .from(schema.tasks)
  .where(
    and(eq(schema.tasks.ownerEmail, userEmail), eq(schema.tasks.done, false)),
  )
  .orderBy(desc(schema.tasks.createdAt));

await db
  .update(schema.tasks)
  .set({ done: true })
  .where(eq(schema.tasks.id, taskId));
```

## 사용자에게 데이터 범위 지정하기 {#scoping}

사용자 대상 테이블에 대한 모든 읽기와 쓰기는 인증된 사용자로 범위가 지정되어야 합니다. 프레임워크는 데이터가 비공개인지 공유 가능한지에 따라 두 가지 패턴을 제공합니다.

**비공개 데이터:** 한 사용자에게 속한 테이블입니다. 스키마에 `ownerEmail: text("owner_email").notNull()`을 추가하고, 모든 쿼리에 `eq(table.ownerEmail, userEmail)`을 포함하세요.

```ts
.where(eq(schema.tasks.ownerEmail, userEmail))
```

**공유 리소스:** 다른 사용자나 조직과 공유할 수 있는 테이블입니다. 스키마에서 단순한 `owner_email` 대신 `...ownableColumns()`를 확산하세요. 이는 한 번의 호출로 `owner_email`, `org_id`, `visibility`를 추가하고, `createSharesTable`로 짝이 되는 공유 테이블을 생성합니다.

```ts filename="server/db/schema.ts"
import {
  table,
  text,
  ownableColumns,
  createSharesTable,
} from "@agent-native/core/db/schema";

export const decks = table("decks", {
  id: text("id").primaryKey(),
  title: text("title").notNull(),
  ...ownableColumns(),
});
export const deckShares = createSharesTable("deck_shares");
```

그런 다음 목록 조회 쿼리에서는 수동 `eq` 검사 대신 `@agent-native/core/sharing`의 `accessFilter`를 사용하세요.

```ts
import { accessFilter } from "@agent-native/core/sharing";

const rows = await db
  .select()
  .from(schema.decks)
  .where(accessFilter(schema.decks, schema.deckShares));
```

`accessFilter`는 호출자가 소유한 행, 호출자의 조직과 공유된 행, 호출자에게 명시적으로 공유된 행만 허용하는 쿼리를 구성합니다. 다른 사용자의 행은 노출하지 않습니다.

전체 모델은 [Security — Data Scoping](/docs/security#data-scoping)과 [Sharing](/docs/sharing#building)을 참조하세요.

## PostgreSQL 기반 동기화 {#sync}

에이전트 네이티브는 파일 시스템 워처나 고정된 인메모리 상태에 의존하지 않습니다. 액션이 데이터베이스에 쓸 때마다 동기화 버전이 증가합니다. 클라이언트의 `useDbSync()` 후크는 `/_agent-native/poll`을 폴링하다가 더 높은 버전을 감지하면 React Query 캐시를 무효화합니다.

이 방식은 데이터베이스가 조율 지점이 되기 때문에 서버리스 및 다중 인스턴스 배포 환경에서도 동작합니다. 액션 바깥에서 커스텀 뮤테이션을 작성하는 경우, 프레임워크 도우미를 사용하거나 열려 있는 UI가 새로고침되도록 적절한 동기화 무효화를 발생시키세요.

## 원시 PostgreSQL {#raw-sql}

Drizzle 쿼리 빌더로 표현할 수 없는 고급 쿼리, 상태 확인, 일회성 유지 관리 작업에는 `@agent-native/core/db`의 `getDbExec`를 사용하세요.

```ts
import { getDbExec } from "@agent-native/core/db";

const { rows } = await getDbExec().execute({
  sql: `SELECT id, title FROM tasks WHERE owner_email = ? LIMIT ?`,
  args: [userEmail, 50],
});
```

`getDbExec`는 Postgres를 위해 `?` 매개변수를 `$1`, `$2` 등으로 자동 변환합니다. 일반적인 읽기와 쓰기에는 Drizzle 쿼리 빌더를 우선 사용하세요. 원시 SQL은 타입 안전성을 우회하며 유지 보수가 더 어렵습니다.
