# 다른 표면들

UI 후크 표면은 [데이터 및 동기화](/docs/client-data)에서 다룹니다: `useActionQuery()`, `useActionMutation()`, `callAction()`. 이 페이지는 action을 호출하거나 action에 의해 구동될 수 있는 그 밖의 모든 것을 다룹니다.

## 네이티브 채팅 UI 렌더링하기 {#native-chat-ui}

Action은 앱 내 채팅이 네이티브하게 렌더링하는 구조화된 위젯 데이터를
반환할 수 있습니다. 이는 재사용 가능한 표, 차트, 설정 요약, 인사이트
카드를 위한 퍼스트파티 채팅 경로입니다. 에이전트가 앱 내 채팅 안에서
임의의 인터랙티브 컨트롤을 생성해야 할 때는 [Generative UI](/docs/generative-ui)를,
외부 MCP 호스트에서의 인라인 UI에는 [MCP Apps](/docs/mcp-apps)를 사용하세요.

```ts
import { defineAction } from "@agent-native/core/action";
import { ACTION_CHAT_UI_DATA_CHART_RENDERER } from "@agent-native/core/action-ui";
import {
  createDataChartWidgetResult,
  dataChartWidgetResultSchema,
} from "@agent-native/core/data-widgets";

export default defineAction({
  description: "Summarize response trends.",
  readOnly: true,
  outputSchema: dataChartWidgetResultSchema,
  chatUI: { renderer: ACTION_CHAT_UI_DATA_CHART_RENDERER },
  run: async () =>
    createDataChartWidgetResult({
      title: "Response trends",
      chartSeries: {
        type: "line",
        xKey: "day",
        series: [{ key: "responses", label: "Responses" }],
        data: [
          { day: "Mon", responses: 12 },
          { day: "Tue", responses: 18 },
        ],
      },
    }),
});
```

내장된 판별자는 `"data-table"`, `"data-chart"`, `"data-insights"`이며,
서버에서 안전하게 쓸 수 있는 빌더와 schema는 `@agent-native/core/data-widgets`에
있습니다. 차트만 있는 답변에는 `data-chart`를, SQL/목록 결과에는
`data-table`을, 요약/차트/표가 결합된 카드가 적합할 때만 `data-insights`를
사용하세요. 전체 결과 계약은 [Native Chat UI](/docs/native-chat-ui)를,
내장 채팅 루프 대신 커스텀 에이전트 런타임을 연결하는 경우라면
[BYO agent runtimes](/docs/native-chat-ui#byo-agent-runtimes)를 참고하세요.
같은 action이 자동화 친화적인 상태를 유지하면서, 채팅에서 렌더링되거나
전체 화면으로 성장하는 방법은 [에이전트 표면](/docs/agent-surfaces)을
참고하세요.

## CLI에서 호출하기 {#cli}

모든 action은 `pnpm action`으로 실행할 수 있습니다.

```bash
pnpm action reply-to-email '{"emailId":"thread-123","body":"Thanks!"}'
```

JSON 입력이 에이전트와 복잡한 객체를 위한 선호되는 형태입니다. 단순한
수동 실행이나 기존 스크립트에는 플래그도 동일하게 동작합니다.

```bash
pnpm action reply-to-email --emailId thread-123 --body "Thanks!"
```

`defineAction()` 호출에서 CLI는 준비 및 파싱 후 스키마 기본값이 적용된 인수와 caller `cli`로 `needsApproval`을 평가합니다. stdin과 stdout이 모두 TTY이면 action 이름과 인수를 표시하고 `y/N`을 묻습니다. `y` 또는 `yes`만 action을 실행합니다.

두 TTY가 모두 갖춰지지 않으면 CLI는 에이전트에게 당사자의 승인을 요청하도록 안내합니다. 당사자가 해당 호출을 승인한 후 원래 `pnpm action` 인수를 그대로 유지하고 끝에 `--approved`를 붙여 다시 실행하세요.

```bash
pnpm action reply-to-email --emailId thread-123 --body "Thanks!" --approved
```

`--approved`는 CLI 예약 메타데이터이며 입력 파싱 전에 제거됩니다. 승인이 필요 없는 action에 붙여도 문제없습니다. CLI는 누가 이 플래그를 붙였는지 확인할 수 없으므로, 묻지 않고 붙인 에이전트는 확인 절차를 건너뜁니다. 이 플래그는 당사자가 승인하는 명령과 감사 로그에 승인을 드러내며, 감사 로그는 이를 확인되지 않음으로 표시합니다. POSIX `SHELL`이 없는 Windows에서는 거부 메시지가 PowerShell용 명령과, 따옴표 처리가 다를 때 cmd.exe용 명령도 보여 줍니다.

로컬 개발 브리지는 JSON 본문의 `input` 밖에 승인 메타데이터를 전송합니다.

```ts
{ name, input, approved: true, approvalSource: "flag" }
```

승인이 필요한 호출에 승인이 없으면 브리지는 HTTP `409`를 반환합니다.

```ts
{
  ok: false,
  errorCode: "approval_required",
  error: 'Action "<name>" requires human approval. Ask the person, then rerun with --approved.',
  arguments: preparedArgs,
  argumentsHash: prepared.argumentsHash,
}
```

TTY에서 확인한 후 CLI는 승인 요청 응답의 `argumentsHash`로 재시도합니다.

```ts
{
  name,
  input,
  approved: true,
  approvalSource: "prompt",
  approvalArgumentsHash: challenge.argumentsHash,
}
```

브리지는 당사자가 검토한 호출을 한 번만 그대로 실행하므로, 타임스탬프처럼 호출마다 달라지는 기본값도 표시된 값을 유지합니다. 실행할 보관된 호출이 없는 확인(이미 실행됐거나, 10분이 지났거나, 개발 서버가 재시작된 경우)은 HTTP `409`와 `errorCode: "approval_expired"`를 받습니다. 명령을 다시 실행해 검토하세요.

`arguments`에는 준비된 인수가 담깁니다. 이 로컬 개발 브리지 계약은 [공개 HTTP action API의 승인 규칙](/docs/actions-access-control#needs-approval)을 변경하지 않습니다. 승인된 승인 대상 CLI 호출은 action 자체의 감사 행에 caller `cli`와 함께 `approval: "cli-prompt"` 또는 `approval: "cli-flag"`를 기록합니다. 확인 프롬프트는 CLI만 보므로, 감사 로그는 둘 다 확인되지 않음으로 표시합니다.

## 다른 에이전트에서 호출하기 (A2A) {#a2a}

여러분의 앱이 [A2A](/docs/a2a-protocol) 피어라면, 다른 에이전트 네이티브
앱은 여러분의 action을 자동으로 발견하고 이름으로 호출할 수 있습니다.
동일 오리진 배포는 JWT 서명을 건너뜁니다. 교차 오리진 배포는 대신
공유된 `A2A_SECRET`을 사용합니다.

## MCP로 노출하기 {#mcp}

MCP가 활성화되어 있으면, 여러분의 action은 `/mcp`에 있는 프레임워크의
MCP 서버에 나타납니다. 모든 호출자는 기본적으로 (앱 전면의 내장 도구와
템플릿이 선언한 앱 action으로 이루어진) 압축된 카탈로그를 받으며,
`tool-search`는 항상 존재하여 다른 어떤 도구든 필요할 때 도달할 수
있게 합니다. 전체 action 표면은 명시적 옵트인(`--full-catalog` 토큰 또는
`AGENT_NATIVE_MCP_FULL_CATALOG=1`)일 때만 제공되며, [`publicAgent.expose`](/docs/actions-access-control#public-agent)는
안전한 읽기/수집 도구를 공개 표면에 옵트인시킵니다. 카탈로그 등급,
인증, `mcpApp` 리소스 세부 사항은 [MCP 프로토콜](/docs/mcp-protocol)을
참고하세요.

UI를 지원하는 MCP 호스트를 위해, action은 `mcpApp` 필드(그리고 짝을
이루는 `link`)를 통해 선택적인 MCP Apps 리소스를 선언하여, 이를 지원하는
호스트가 결과를 인라인으로 렌더링하게 할 수 있습니다. `link`와 `mcpApp`이
같은 라우트를 가리켜야 할 때는, `embedRoute()`가 하나의 순수한 경로
빌더로부터 둘 다를 만들어 줍니다.

```ts
import { embedRoute } from "@agent-native/core";

export default defineAction({
  description: "Create an email draft for review.",
  schema: z.object({ body: z.string() }),
  run: async ({ body }) => ({ body }),
  ...embedRoute({
    title: "Review draft",
    openLabel: "Open in Mail",
    path: ({ result }) => ({
      label: "Open draft in Mail",
      url: "/_agent-native/open?app=mail&view=inbox",
    }),
  }),
});
```

`link`는 CLI와 UI가 없는 MCP 호스트를 위한 폴백으로 유지하세요. 이는
또한 임베드의 실행 대상이기도 합니다. 임베드 브리지(서명된 임베드 시작
세션, transplant 대 controlled-frame 렌더링, `ui/*` 호스트 브리지, CSP,
높이 클램핑)는 [외부 에이전트](/docs/external-agents#mcp-app-bridge)가
소유합니다.

템플릿에 주요 리소스에 대한 `view-screen`, `navigate`, 또는 create/read/update/list 세트가 있는지 자동으로 확인하는 장치는 없습니다. 스캐폴드는 `view-screen`과 `navigate`를 기본 제공하며, `pnpm guard:external-result-contract`는 외부에 노출된 action의 `description` 또는 `nextRequiredAction`에 있는 "사용자를 기다리라"는 표현을 실패 처리하고, 외부에 노출된 새 `create-*` action에는 딥 링크를 요구합니다. 존재 여부는 리뷰 항목입니다.

## 표준 actions {#standard-actions}

[컨텍스트 인식](/docs/context-awareness)을 위해 모든 템플릿은 이 두
가지를 포함해야 합니다.

### view-screen {#view-screen}

현재 내비게이션 상태를 읽고, 문맥에 맞는 데이터를 가져와 사용자가
보고 있는 화면의 스냅샷을 반환합니다. 에이전트는 화면을 새로 확인해야
할 때 이를 호출합니다.

```ts
// actions/view-screen.ts
import { defineAction } from "@agent-native/core/action";
import { readAppState } from "@agent-native/core/application-state";
import { z } from "zod";

export default defineAction({
  description: "Read the current screen state for context.",
  schema: z.object({}),
  http: { method: "GET" },
  run: async () => {
    const navigation = await readAppState("navigation");
    const screen: Record<string, unknown> = { navigation };

    if (navigation?.view === "inbox") {
      screen.emailList = await listEmailsForLabel(navigation.label);
    }

    return screen;
  },
});
```

### navigate {#navigate}

애플리케이션 상태에 일회성 내비게이션 명령을 씁니다. UI는 이를 읽고,
이동한 뒤 항목을 삭제합니다.

```ts
// actions/navigate.ts
import { defineAction } from "@agent-native/core/action";
import { writeAppState } from "@agent-native/core/application-state";
import { z } from "zod";

export default defineAction({
  description: "Navigate the user to a view.",
  schema: z.object({
    view: z.string(),
    threadId: z.string().optional(),
  }),
  run: async (args) => {
    await writeAppState("navigate", args);
    return { ok: true };
  },
});
```
