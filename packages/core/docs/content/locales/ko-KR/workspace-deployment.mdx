# 작업 공간 배포

프로젝트가 앱이 두 개 이상인 [작업 공간](/docs/multi-app-workspace)이라면, 앱마다 별도의 배포를 관리하는 대신 모든 앱을 하나의 오리진에 배포할 수 있습니다. 이 페이지는 관리형 원커맨드 경로와 자체 호스팅 Docker Compose 대안을 다룹니다. 먼저 데이터베이스, 프리셋, 플랫폼을 선택하려면 [Deployment](/docs/deployment)를 참조하세요.

## 하나의 오리진, 여러 앱 {#workspace-deploy}

명령 하나로 작업 공간의 모든 앱을 하나의 오리진에 배포하세요:

```bash
npx @agent-native/core@latest deploy
# https://your-agents.com/mail/*       → apps/mail
# https://your-agents.com/calendar/*   → apps/calendar
# https://your-agents.com/forms/*      → apps/forms
```

**동일 출처(Same-origin)**란 브라우저 입장에서 모든 앱이 같은 웹사이트의 일부로 보인다는 뜻입니다. 이는 두 가지 큰 이점을 무료로 제공합니다:

- **공유 로그인 세션**. 어떤 앱에든 로그인하면 모든 앱에 로그인됩니다.
- **제로 설정 앱 간 A2A**. mail에서 `@calendar`를 태그하는 것은 동일 출처 fetch입니다. 형제 앱 사이에는 CORS도, JWT 서명도 필요 없습니다.

<Callout tone="info">

내부적으로 각 앱은 `APP_BASE_PATH`/`VITE_APP_BASE_PATH`로 설정되는 `/mail` 같은 URL 접두사인 자체 **base path**로 빌드된 다음, 대상 Nitro 프리셋에 맞게 패키징됩니다. Cloudflare Pages는 생성된 **디스패처 워커(dispatcher worker)**, 즉 들어오는 경로를 읽어 해당하는 앱으로 요청을 전달하는 `dist/_worker.js`의 작은 스크립트를 통해 라우팅합니다. Netlify는 앱마다 하나의 함수와 생성된 리디렉션을 사용합니다. Vercel은 Build Output API를 사용해 작업 공간 수준의 `.vercel/output`을 작성합니다.

</Callout>

<Callout tone="warning">

호스팅된 작업 공간 빌드는 배포 제공업체 환경에 `A2A_SECRET`이 필요합니다. 이것이 없으면 Slack, 인바운드 웹훅, 앱 간 A2A resume이 동작하지 않습니다. 이들은 모두 서명된 백그라운드 프로세서를 거치기 때문입니다. 로컬 `--build-only` 아티팩트 확인은 이것 없이도 계속 실행됩니다.

</Callout>

<Callout tone="info">

직접 배포하는 대신 제공업체의 빌드 명령을 연결하시나요? 동일한 명령에 `--build-only`를 추가하세요. 예를 들면 `npx @agent-native/core@latest deploy --preset vercel --build-only`입니다. 출력물을 직접 작성하므로 작업 공간 라우팅을 위한 `vercel.json`이 필요하지 않습니다.

하나의 공유 오리진 대신 앱마다 별도 도메인을 선호하시나요? 작업 공간의 모든 앱은 여전히 독립적으로 배포할 수 있습니다. 독립형 스캐폴드처럼 `cd apps/<name> && npx @agent-native/core@latest build`를 실행하세요.

</Callout>

## Docker Compose로 작업 공간 자체 호스팅하기 {#workspace-docker-compose}

현재 작업 공간은 하나의 Nitro 서버 프로세스가 아닙니다. 각 앱은 여전히 자체 `.output/` 디렉터리로 빌드되고 자체 Node/Nitro 서버로 실행되므로, 작업 공간을 자체 호스팅한다는 것은 하나의 진입점 뒤에서 여러 서버를 실행한다는 뜻입니다.

**리버스 프록시**는 위 그림에서 그 단일 진입점입니다. 모든 요청을 받아 URL 경로에 따라 올바른 컨테이너로 전달하며, 이는 관리형 배포에서 Cloudflare의 디스패처 워커가 하는 역할과 동일합니다. VPS에서는 작업 공간 앱마다 하나의 컨테이너를 두고, 모두 동일한 Postgres 데이터베이스와 공유 프로덕션 시크릿을 가리키며, 앞에는 프록시를 둔다는 뜻입니다.

<Steps>

### 일치하는 base path로 각 앱 빌드하기

base path는 클라이언트 번들에는 빌드 타임 입력값이고 서버에는 런타임 입력값입니다. 프록시가 라우팅할 경로와 동일한 경로로 각 앱을 빌드하세요:

```bash maxLines=8
APP_BASE_PATH=/mail VITE_APP_BASE_PATH=/mail npx @agent-native/core@latest build
node .output/server/index.mjs
```

### 재사용 가능한 Dockerfile 작성하기

앱 이름과 경로 접두사를 빌드 인자로 받아, 하나의 Dockerfile이 작업 공간의 모든 앱을 처리하도록 합니다:

```dockerfile filename="Dockerfile.workspace-app" maxLines=12
FROM node:24-slim AS build
WORKDIR /workspace
RUN corepack enable
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY packages ./packages
COPY apps ./apps
ARG APP_NAME
ARG APP_BASE_PATH
ENV APP_BASE_PATH=$APP_BASE_PATH
ENV VITE_APP_BASE_PATH=$APP_BASE_PATH
RUN pnpm install --frozen-lockfile
RUN pnpm --dir apps/$APP_NAME build

FROM node:24-slim
WORKDIR /app
ARG APP_NAME
ARG APP_BASE_PATH
ENV NODE_ENV=production
ENV PORT=3000
ENV APP_BASE_PATH=$APP_BASE_PATH
COPY --from=build /workspace/apps/$APP_NAME/.output .output
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

### Postgres, 앱, 프록시 구성하기

이 예제는 로컬에서 HTTP를 종료하거나 Cloudflare의 SSL 프록시 뒤에 위치할 수 있다는 이유로 Caddy를 사용하지만, 중요한 부분은 경로 접두사 라우팅입니다:

```yaml filename="docker-compose.yml" maxLines=30
services:
  postgres:
    image: postgres:17
    restart: unless-stopped
    environment:
      POSTGRES_DB: agent_native
      POSTGRES_USER: agent_native
      POSTGRES_PASSWORD: change-me
    volumes:
      - postgres-data:/var/lib/postgresql/data

  mail:
    build:
      context: .
      dockerfile: Dockerfile.workspace-app
      args:
        APP_NAME: mail
        APP_BASE_PATH: /mail
    restart: unless-stopped
    environment:
      DATABASE_URL: postgres://agent_native:change-me@postgres:5432/agent_native
      BETTER_AUTH_URL: https://agents.example.com/mail
      BETTER_AUTH_SECRET: ${BETTER_AUTH_SECRET}
      A2A_SECRET: ${A2A_SECRET}
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
    depends_on:
      - postgres

  calendar:
    build:
      context: .
      dockerfile: Dockerfile.workspace-app
      args:
        APP_NAME: calendar
        APP_BASE_PATH: /calendar
    restart: unless-stopped
    environment:
      DATABASE_URL: postgres://agent_native:change-me@postgres:5432/agent_native
      BETTER_AUTH_URL: https://agents.example.com/calendar
      BETTER_AUTH_SECRET: ${BETTER_AUTH_SECRET}
      A2A_SECRET: ${A2A_SECRET}
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
    depends_on:
      - postgres

  proxy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
    depends_on:
      - mail
      - calendar

volumes:
  postgres-data:
```

### 프록시 설정하기

```caddyfile filename="Caddyfile"
agents.example.com {
  reverse_proxy /mail* mail:3000
  reverse_proxy /calendar* calendar:3000
}
```

</Steps>

<Callout tone="info">

- 공유 인증, 공유 자격 증명, 앱 간 A2A를 원한다면 `DATABASE_URL`,
  `BETTER_AUTH_SECRET`, `A2A_SECRET` 등 프로덕션 시크릿을 모든 앱 컨테이너에서
  동일하게 유지하세요.
- `BETTER_AUTH_URL`을 해당 앱 경로의 공개 URL로 설정하세요. OAuth 콜백 URL도
  동일한 공개 URL을 사용해야 합니다.
- 프로덕션 데이터를 컨테이너 파일 시스템에 의존하지 마세요. `DATABASE_URL`에는
  Postgres(또는 다른 영구 SQL 백엔드)를 사용하세요.
- Cloudflare가 VPS 앞에서 TLS를 종료하는 경우, Cloudflare가 일반적인
  `X-Forwarded-Proto` / `X-Forwarded-Host` 헤더를 보내도록 설정하고 공개
  호스트를 프록시 컨테이너로 라우팅하세요.

</Callout>
