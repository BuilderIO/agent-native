# Vercel

Vercel이 앱을 대신 호스팅하므로 서버를 설정하거나 계속 실행해 둘 필요가 없습니다. 빌드하면 앱이 Vercel이 직접 제공하는 파일과 Vercel이 필요할 때 실행하는 함수로 변환되며, Vercel은 앱에 HTTPS가 적용된 공개 주소를 제공합니다.

이 가이드는 독립 실행형 앱 하나를 처음부터 배포하는 과정을 안내합니다. 앱을 만들고, 프로덕션 데이터베이스와 인증 시크릿을 지정하고, Vercel 프로젝트에 연결하고, 데이터베이스를 준비한 다음, 빌드하고 배포합니다.

<Callout tone="info">

Node.js `22.22+`가 필요합니다.

</Callout>

Vercel 계정도 필요합니다. 이 가이드의 명령은 자신의 컴퓨터에서 실행하세요. 완성된 빌드는 Vercel CLI가 Vercel에 업로드합니다.

## 1단계: 앱 만들기 {#step-1-create-the-app}

새 독립 실행형 앱을 만듭니다. 아래 예시는 Chat 템플릿으로 앱을 만들지만, 어떤 템플릿으로든 시작할 수 있습니다. 앱 폴더로 이동한 뒤 의존성을 설치하세요. `corepack enable`은 앱이 기대하는 `pnpm` 버전을 활성화하므로 `pnpm`을 직접 설치할 필요가 없습니다.

```bash
npx --yes @agent-native/core@latest create my-app --standalone --template chat

cd my-app

corepack enable

pnpm install
```

원한다면 `my-app`을 원하는 앱 이름으로 바꾸세요. 이 가이드의 나머지 부분은 앱 폴더 안에 있다고 가정합니다.

<Callout tone="info">

이 명령이 피어 종속성 오류로 실패한다면 npx 캐시에 있는 오래된 패키지가 원인일 수 있습니다. `npx clear-npx-cache`를 실행해 캐시를 지운 다음 명령을 다시 실행하세요.

</Callout>

## 2단계: 환경 시크릿 구성하기 {#step-2-configure-environment-secrets}

앱은 프로덕션 설정을 환경 변수에서 읽습니다.

| 변수                 | 필수   | 용도                                          |
| -------------------- | ------ | --------------------------------------------- |
| `DATABASE_URL`       | 예     | 앱을 PostgreSQL 데이터베이스에 연결합니다     |
| `BETTER_AUTH_SECRET` | 예     | 사용자 세션에 서명합니다                      |
| `BETTER_AUTH_URL`    | 아니요 | 사용자가 앱에 접속하는 공개 주소를 설정합니다 |

아래의 export 명령을 실행하면 이 셸에서 이후 명령이 동작합니다. 배포하기 전에 같은 변수를 호스트의 프로젝트 또는 서비스 환경 설정에도 저장하세요. Vercel에 저장하는 방법은 다음 단계에서 설명합니다.

### 데이터베이스 URL {#database-url}

로컬 개발 중에는 `DATABASE_URL`이 설정되지 않으면 앱이 로컬 데이터베이스에 데이터를 저장합니다. 배포된 앱에는 배포 후에도 데이터를 유지하는 실제 PostgreSQL 데이터베이스가 필요합니다. Vercel은 요청 사이에 파일을 유지하지 않으므로 데이터베이스는 Vercel 함수 밖에 있어야 합니다. 프로바이더에서 연결 문자열을 복사해 export하세요.

```bash
export DATABASE_URL='your-postgres-url-string'
```

[데이터베이스 프로바이더 가이드](/docs/neon)에서 프로바이더별로 연결 문자열을 찾는 위치를 확인할 수 있습니다.

<Callout tone="warning">

Neon, Supabase, Amazon RDS 등 영구적인 PostgreSQL 프로바이더를 선택하세요.

</Callout>

### 인증 시크릿 {#auth-secret}

이 값은 한 번만 생성하고 배포할 때마다 바꾸지 마세요.

앱은 `BETTER_AUTH_SECRET`을 사용해 사용자 세션에 서명합니다. 이 값이 바뀌면 로그인한 모든 사용자가 로그아웃됩니다. 아래 명령은 임의의 값을 생성합니다.

```bash
export BETTER_AUTH_SECRET="$(openssl rand -hex 32)"
```

생성한 값은 비밀번호 관리자처럼 안전한 곳에 저장하세요. 배포할 때마다 같은 값을 사용합니다.

### 공개 URL {#public-url}

선택 사항입니다. 사용자 지정 도메인, 리버스 프록시, 또는 고정된 공개 origin이 필요한 인증이나 OAuth 흐름을 사용할 때 설정하세요.

`BETTER_AUTH_URL`은 사용자가 앱에 접속하는 공개 주소입니다. 이 값이 없으면 앱은 들어오는 요청마다 자신의 주소를 판단합니다. Vercel이 제공하는 주소에서는 대개 문제가 없지만, 사용자 지정 도메인을 연결할 때는 로그인 링크와 OAuth 리디렉션이 그 도메인을 사용하도록 이 값을 설정하세요.

```bash
export BETTER_AUTH_URL='https://your-domain.example'
```

## 3단계: 프로젝트 연결 및 시크릿 저장하기 {#step-3-link-the-project-and-save-the-secrets}

명령줄에서 Vercel에 로그인합니다.

```bash
npx vercel login
```

앱 폴더를 Vercel 프로젝트에 연결합니다. 새 프로젝트를 만들되, 설정을 따로 바꿀 필요는 없습니다.

```bash
npx vercel link
```

CLI는 폴더 이름을 바탕으로 프로젝트 이름을 제안합니다. 제안된 설정을 그대로 받아들여도 됩니다. 5단계에서 앱을 직접 빌드하므로 Vercel 자체의 빌드 설정은 필요하지 않기 때문입니다.

필수 변수 두 개를 프로젝트의 프로덕션 환경에 저장합니다.

```bash
printf '%s' "$DATABASE_URL" | npx vercel env add DATABASE_URL production

printf '%s' "$BETTER_AUTH_SECRET" | npx vercel env add BETTER_AUTH_SECRET production
```

각 명령은 2단계에서 export한 값을 읽어 Vercel에 저장하므로 시크릿을 직접 붙여 넣을 필요가 없습니다. `BETTER_AUTH_URL`을 설정했다면 같은 방법으로 저장하세요. 이 값들은 나중에 Vercel 대시보드의 프로젝트 설정에서 확인하고 변경할 수도 있습니다.

## 4단계: 마이그레이션 {#step-4-migrate}

마이그레이션은 앱에 필요한 테이블을 데이터베이스에 만들고 업데이트합니다. 첫 배포 전에 이 명령을 실행하세요.

```bash
pnpm migrate:production
```

이 명령은 자신의 컴퓨터에서 실행되며, 2단계에서 export한 `DATABASE_URL`로 프로덕션 데이터베이스에 연결합니다. 앱을 업그레이드한 뒤에는 새 버전을 배포하기 전에 다시 실행하세요.

## 5단계: 배포 {#step-5-deploy}

Vercel용으로 앱을 빌드합니다.

```bash
NITRO_PRESET=vercel pnpm build
```

`NITRO_PRESET=vercel`은 Vercel이 기대하는 형식으로 앱을 빌드해 `.vercel/output` 폴더에 씁니다.

빌드를 업로드하고 게시합니다.

```bash
npx vercel deploy --prebuilt --prod
```

`--prebuilt`는 Vercel에서 앱을 다시 빌드하지 않고 방금 만든 빌드를 업로드합니다. `--prod`는 빌드를 프로덕션 주소에 게시하며, 이 주소에서는 프로덕션 환경에 저장한 변수가 사용됩니다.

명령이 끝나면 앱의 프로덕션 주소가 출력됩니다. 그 주소를 열고 첫 계정을 만듭니다.

## 업데이트 배포하기 {#deploy-updates}

새 버전을 배포하려면 앱 폴더에서 마이그레이션, 빌드, 배포 명령을 다시 실행하세요.

```bash
pnpm migrate:production

NITRO_PRESET=vercel pnpm build

npx vercel deploy --prebuilt --prod
```

프로젝트 연결과 저장한 변수는 그대로 유지되므로 3단계를 반복할 필요가 없습니다.

## 예약 작업 {#vercel-scheduled-work}

예약 자동화, 대기 중인 이벤트 자동화, 중단된 실행 정리는 모두 1분에 한 번
실행되는 스윕에서 처리됩니다. 빌드는 `/_agent-native/jobs/_process-sweep`에서
스윕을 호출하는 [Vercel cron 작업](https://vercel.com/docs/cron-jobs)을 추가합니다.
작업 공간 빌드는 앱마다 하나씩 `/<app-id>/_agent-native/jobs/_process-sweep`에
cron 작업을 추가합니다.

배포하기 전에 프로젝트 환경 변수에 `CRON_SECRET`을 설정하세요. Vercel은 각 cron
요청에 이 값을 bearer 토큰으로 보내며, 스윕은 이 값이 없는 모든 요청을 거부합니다.
값은 `openssl rand -hex 32`로 생성하세요.

- **프로덕션 전용.** Vercel은 cron 작업을 프로덕션 배포에서만 실행하고 프리뷰에서는
  실행하지 않으므로, 프리뷰에서는 일정이 실행되지 않습니다. **Automations**
  페이지에도 그렇게 표시됩니다.
- **Hobby는 하루에 한 번 실행됩니다.** Vercel은 cron 작업이 하루에 두 번 이상
  실행되는 Hobby 배포를 거부합니다. 빌드 환경에서
  `AGENT_NATIVE_VERCEL_CRON_SCHEDULE`을 `0 9 * * *` 같은 일일 표현식으로
  설정하세요. Hobby에서는 그 시간대 안의 아무 때나 실행될 수도 있습니다. 스윕이
  하루에 한 번이면 예약 자동화와 이벤트 트리거 자동화가 최대 하루까지 대기하므로,
  타이밍이 중요하다면 Pro나 다른 호스트를 사용하세요.
- **함수 실행 시간.** 스윕은 cron 작업의 함수 호출 안에서 실행할 때가 된 작업을
  실행하므로, 작업은 함수의 최대 실행 시간(기본값 300초)에 도달하면 중단됩니다.
- **재시도 없음.** Vercel은 실패한 cron 호출을 재시도하지 않습니다. 스윕은 다음
  예정 시간에 다시 실행됩니다.

다른 호스트는 [스케줄러 실행 방법](/docs/recurring-jobs#how-scheduler-runs)을
참조하세요.
