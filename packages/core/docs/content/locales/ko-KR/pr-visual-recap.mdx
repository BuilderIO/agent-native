# PR 시각적 요약

PR 시각적 요약은 모든 풀 리퀘스트를 **시각적 코드 리뷰**로 바꿔주는 GitHub
Action으로, 누구도 수동으로 명령을 실행할 필요가 없습니다. 이 페이지는 이
Action을 설치하거나, 구성하거나, 보안을 강화하려는 사람을 위한 것입니다.
푸시가 있을 때마다 LLM 코딩 에이전트가 최신 번들 버전의
[`visual-recap`](/docs/template-plan) 스킬(또는
`VISUAL_RECAP_SKILL_SOURCE=repo`일 때는 저장소에 커밋된 사본)을 PR diff에
대해 실행하고, 구조화된 요약 계획을 호스팅된 Plans 앱에 게시하고, 실행되는
동안 정보성 `Visual Recap` 체크를 표시하며, 대화형 계획으로 연결되는 링크와
댓글에 바로 삽입된 **인라인 스크린샷**을 담은 **하나의 고정 PR 댓글**을
업서트합니다.

이것은 결정론적인 diff 렌더러가 아닙니다. 이 Action은 변경 사항을 읽고
무엇이 중요한지 판단한 다음, `/visual-recap` 슬래시 명령이 사용하는 것과
동일한 Plans MCP 도구인 `create-visual-recap`을 호출해서 요약을 작성하는
실제 코딩 에이전트(기본값 Claude Code CLI, 또는 OpenAI Codex CLI, 또는
OpenAI 호환 제공업체를 사용하는 Agent-Native Code)를 호출합니다. 이를 통해
원본 diff를 그대로 나열하는 대신 변경 사항을 고도에서 조망한 스키마/API/
변경 전후 뷰를 얻게 됩니다.

이 요약은 **정보성이며 병합을 막지 않습니다.** 생성이 진행 중임을 리뷰어가
볼 수 있도록 체크 항목을 만들지만, 필수 체크가 아니며 PR을 절대 막지
않고, 실제 diff를 읽는 것을 절대 대체하지 않습니다. 고정 댓글은 검토를
돕는 보조 수단일 뿐 승인 표시가 아닙니다.

## 하는 일

각 PR 푸시마다 워크플로는 다음을 수행합니다.

1. PR의 base와 head 사이의 경계가 있는 diff를 수집합니다.
2. `Visual recap in progress`라는 정보성 `Visual Recap` GitHub 체크를 만듭니다.
3. 구성된 코딩 에이전트를 해당 diff에 대해 실행합니다. 에이전트는 번들된
   `visual-recap` 스킬 안내(또는 저장소에 고정된 사본)를 읽고 요약을 작성해
   `create-visual-recap`으로 게시합니다.
4. 에이전트가 `recap-url.txt`에 기록한 게시된 계획 URL을 읽습니다.
5. 해당 URL을 헤드리스 Chrome에서 열고 렌더링된 계획을 라이트 모드와 다크
   모드로 스크린샷 찍습니다.
6. PNG를 Plans 앱의 서명된 공개 이미지 라우트에 업로드합니다.
7. 대화형 요약 링크 옆에 `<picture>` 요소(GitHub의 camo 이미지 프록시를
   통해 제공됨)로 스크린샷을 **인라인으로** 삽입하는 하나의 고정 PR 댓글을
   업서트합니다.
8. `Visual Recap` 체크를 성공, 건너뜀, 또는 중립 상태로 완료합니다.

## 설치하기

Plans를 대화형으로 설치할 때 Agent-Native CLI는 자동 PR 시각적 요약을
추가할지 물어봅니다. 예라고 답해서 GitHub Action을 작성하거나, 언제든
명시적으로 추가할 수 있습니다.

```bash
npx @agent-native/core@latest skills add visual-plan --with-github-action
```

이 명령은 `visual-plan` 스킬(이 Action이 실행하는 `visual-recap` 스킬 포함)을
설치하고 저장소에 `.github/workflows/pr-visual-recap.yml`을 작성합니다.
워크플로는 `gate`, `collect-diff`, `block-reference`, `scan`,
`build-prompt`, `publish`, `shot`, `comment`, `check`, `usage`를 포함한
**게시된 CLI 하위 명령**을 `npx @agent-native/recap-cli@latest recap
<subcommand>`를 통해 호출하므로, 저장소에 도우미 스크립트로 복사되는 것은
없습니다. `setup`과 `doctor`는 로컬에서 실행하는 대화형 도우미이고,
`gate`는 모든 요약 실행 전에 워크플로가 거치는 보안 게이트 단계입니다.

그런 다음 안내형 설정 도우미를 실행합니다.

```bash
npx @agent-native/recap-cli@latest recap setup
npx @agent-native/recap-cli@latest recap doctor
```

`recap setup`은 워크플로를 갱신하고, 환경 변수나 로컬 Plans 게시 토큰
저장소에서 값을 구할 수 있을 때 `gh`를 사용해 GitHub Actions 시크릿/변수를
설정하며, 스스로 설정할 수 없는 항목에 대해서는 정확히 필요한 명령을
출력합니다. 시크릿 값은 명령줄 인자가 아니라 표준 입력을 통해 `gh`에
전달됩니다. 생성된 워크플로 파일을 커밋하고 PR을 열어 실제로 동작하는지
확인하세요.

기본적으로 워크플로는 `@agent-native/recap-cli@latest`에 있는 최신 번들
`visual-recap` 안내(스킬이 함께 제공하는 형제 참조 파일 포함)로부터 에이전트
프롬프트를 만듭니다. 저장소가 의도적으로 커밋된 `visual-recap` 폴더를
커스터마이징하고 고정하고 있다면, 저장소 변수
`VISUAL_RECAP_SKILL_SOURCE=repo`를 설정하세요.

## 러너 선택

워크플로는 기본적으로 GitHub가 호스팅하는 `ubuntu-latest` 러너에서
실행됩니다. 다른 호스팅 러너나 자체 호스팅 러너를 사용하려면, 저장소 또는
조직 변수 `VISUAL_RECAP_RUNS_ON`을 유효한 JSON 문자열 또는 러너 레이블의
JSON 배열로 설정하세요.

```text
"ubuntu-latest"
["self-hosted", "linux", "x64", "visual-recap"]
```

JSON 따옴표는 필수입니다. 이 설정은 전체 `recap` 작업의 러너를 선택합니다.
안내형 설정 중에 구성하려면 같은 JSON 값을 `--runs-on`에 전달한 다음,
`doctor`로 워크플로와 러너 가용성을 검증하세요.

```bash
npx @agent-native/recap-cli@latest recap setup --runs-on '["self-hosted","linux","x64","visual-recap"]'
npx @agent-native/recap-cli@latest recap doctor
```

가벼운 보안 게이트는 별도로 GitHub 호스팅 `ubuntu-latest`를 기본값으로
사용합니다. GitHub 호스팅 러너를 비활성화한 저장소는
`VISUAL_RECAP_GATE_RUNS_ON`을 (JSON이 아닌) **일반적인 단일 러너
레이블** 하나로 설정하거나, 설정 중에 `--gate-runs-on visual-recap-gate`를
전달할 수 있습니다. 재사용 가능한 워크플로는 동일한 값을 `gate-runs-on`
입력으로 노출합니다. 이렇게 하면 GitHub가 게이트를 스케줄링할 수 있게
되기 전에 동적 JSON을 파싱해야 하는 상황을 피할 수 있습니다. 이 커스텀
레이블은 `OWNER`, `MEMBER`, `COLLABORATOR`가 작성한 동일 저장소 PR에만
선택됩니다. 포크와 그 외 모든 작성자는 작업이 시작되기 전에 강제로
GitHub 호스팅 `ubuntu-latest`로 전환됩니다. 자체 호스팅 러너만 있는
저장소에서는 이런 신뢰할 수 없는 실행이 자체 호스팅 머신을 건드리는 대신
스케줄링되지 않은 채로 남을 수 있습니다.

`recap doctor`는 형식이 잘못되었거나 지원되지 않는 JSON을 거부하며,
GitHub가 구성된 모든 레이블과 일치하는 온라인 러너를 찾지 못할 때 이를
보고합니다. 러너 등록, 설치, 업그레이드, 용량, 유지 관리는 여전히
사용자의 책임입니다. Agent-Native는 레이블을 선택할 뿐 러너를 제공하거나
운영하지 않습니다.

**보안:** 전용의 임시(ephemeral) 자체 호스팅 러너를 우선 사용하세요.
커스텀 게이트 러너는 신뢰할 수 있는 동일 저장소 PR 이벤트만 받습니다.
기본 게이트는 PR 트리를 체크아웃하지 않으며, 워크플로 로직과 GitHub PR
메타데이터만 평가합니다. 영구적인 머신은 여러 작업에 걸쳐 프로세스
상태를 유지하므로, 관련 없는 워크로드와 공유하지 마세요. 워크플로는
신뢰할 수 없는 공개 PR이나 포크 PR 작성자에 대해서는 어떤 자체 호스팅
게이트나 전체 요약 작업도 실행하기 전에 안전하게 실패(fail closed)
합니다. 이 경계를 약화시키거나 신뢰할 수 없는 기여를 영구적인 러너로
보내지 마세요.

## 백엔드 선택

`VISUAL_RECAP_AGENT` 저장소 변수로 스킬을 실행할 코딩 에이전트를
선택하세요.

| `VISUAL_RECAP_AGENT` | 코딩 에이전트                              | 필요한 API 키          | 필요한 변수                                   |
| --------------------- | ------------------------------------------ | ----------------------- | ---------------------------------------------- |
| `claude` _(기본값)_   | Claude Code CLI                             | `ANTHROPIC_API_KEY`     | —                                              |
| `codex`               | OpenAI Codex CLI                            | `OPENAI_API_KEY`        | —                                              |
| `openai-compatible`   | Agent-Native Code + 호환 제공업체            | `VISUAL_RECAP_API_KEY`  | `VISUAL_RECAP_BASE_URL`, `VISUAL_RECAP_MODEL`  |

이 변수를 설정하지 않으면 Action은 `claude`를 사용합니다.

## 모델과 추론

백엔드 외에도 다음 저장소 변수들이 에이전트가 실행되는 방식을 조정합니다.

- **`VISUAL_RECAP_MODEL`**은 CLI에 전달되는 모델을 고정합니다(`--model`) —
  예를 들어 Codex라면 `gpt-5.6-luna`, Claude 모델 ID, 또는 DeepSeek라면
  `deepseek-chat`. `openai-compatible`에서는 필수입니다. **Claude** 백엔드의
  경우 설정하지 않으면 이제 `claude-sonnet-5`가 기본값이 됩니다. 다른
  Claude 모델을 쓰려면(더 저렴한 `claude-haiku-4-5` 등) 변수를 명시적으로
  설정하세요. **Codex** 백엔드의 경우 설정하지 않으면 Codex CLI 자체의
  기본 모델이 사용됩니다.
- **`VISUAL_RECAP_REASONING`**은 추론 깊이를 설정합니다: `none`, `minimal`,
  `low`, `medium`, `high`, `xhigh` 중 하나입니다. 이는 Codex 백엔드에
  적용되며, Claude의 추론은 모델에 의해 결정되므로 이 변수는 무시됩니다.
- **`VISUAL_RECAP_BASE_URL`**은 `openai-compatible` 백엔드의 HTTP(S) 기본
  URL을 선택합니다. URL에 자격 증명을 넣지 말고 DeepSeek나 Kimi 같은
  제공업체의 OpenAI 호환 엔드포인트를 사용하세요.
- **`VISUAL_RECAP_SKILL_SOURCE`**는 프롬프트 신선도를 제어합니다:
  `auto`/미설정은 최신 번들 스킬 안내를 사용하고, `repo`는 저장소에
  커밋된 로컬 `visual-recap` 스킬 폴더에 고정합니다.

예를 들어, 높은 추론 수준으로 GPT-5.6 Sol을 사용해 Codex에서 요약을
실행하려면, 저장소 변수 `VISUAL_RECAP_AGENT=codex`,
`VISUAL_RECAP_MODEL=gpt-5.6-sol`, `VISUAL_RECAP_REASONING=high`를
설정하세요.

DeepSeek을 사용하려면 `VISUAL_RECAP_AGENT=openai-compatible`,
`VISUAL_RECAP_BASE_URL=https://api.deepseek.com/v1`,
`VISUAL_RECAP_MODEL=deepseek-chat`, 그리고 `VISUAL_RECAP_API_KEY` 시크릿을
설정하세요. Kimi도 자체 OpenAI 호환 기본 URL과 모델 ID로 동일하게
동작합니다. 그 외 OpenAI 호환 제공업체도 같은 세 가지 설정을 사용합니다.

## 비용

각 요약 실행은 저렴한 템플릿 요약이 아니라 실제 diff를 읽는 완전한
에이전트 코딩 세션이므로, 비용은 모델 선택과 실행 빈도에 따라 달라집니다.

- **PR 푸시마다 하나의 완전한 세션.** 기본 트리거는 `synchronize`에서
  발동하므로, 열 번 푸시되는 PR은 에이전트를 열 번 실행합니다.
- **매번 전체 PR을 대상**으로 하며 마지막 실행 이후의 커밋만이 아닙니다 —
  비용은 증분 diff 크기가 아니라 전체 PR 크기에 비례합니다.
- **diff 입력은 약 600KB로 제한됩니다.** 이는 실행당 최악의 경우를
  제한하지만, 큰 diff는 여전히 작은 diff보다 유의미하게 더 많은 비용이
  듭니다.
- **실패 시 자동 재시도가 한 번** 있으며, 이는 일시적으로 실패한 실행의
  비용을 대략 두 배로 늘릴 수 있습니다.

비용을 줄이려면 다음을 고려하세요.

- **더 저렴한 모델을 고정하세요.** Claude의 경우 단순하거나 작은 저장소에는
  `VISUAL_RECAP_MODEL=claude-haiku-4-5`를 설정하세요 — 가장 저렴한 Claude
  등급입니다. `claude-sonnet-5`(기본값)는 균형 잡힌 등급입니다.
- **더 저렴한 모델과 함께 Codex로 전환하세요.**
  `VISUAL_RECAP_AGENT=codex`와 함께 `VISUAL_RECAP_MODEL=gpt-5.6-luna`(가장
  저렴한 GPT-5.6 등급)나 `gpt-5.6-terra`(중간 등급)를 설정하고,
  `VISUAL_RECAP_REASONING=low`를 설정해 추론 토큰 지출을 더 줄이세요.
  추론 깊이는 Codex에만 적용됩니다.
- **더 저렴한 OpenAI 호환 제공업체를 지정하세요.**
  `VISUAL_RECAP_AGENT=openai-compatible`과 함께
  `VISUAL_RECAP_BASE_URL`/`VISUAL_RECAP_MODEL`/`VISUAL_RECAP_API_KEY`를
  DeepSeek, Kimi, 또는 다른 OpenAI 호환 엔드포인트로 지정하세요.
- **명시적인 PR 레이블을 요구하세요.** `VISUAL_RECAP_REQUIRED_LABELS=visual
  recap`을 설정하면 워크플로는 설치된 상태로 두되 PR에 해당 레이블이
  붙기 전까지는 요약을 건너뜁니다. 여러 레이블이 옵트인하도록 하려면
  `visual recap,recap`처럼 쉼표로 구분된 목록을 사용하세요. 목록에 있는
  레이블을 붙이면 워크플로가 즉시 깨어납니다.
- **요약 빈도를 줄이세요.** 설치된 워크플로의 `on.pull_request.types`를
  `[opened, synchronize, reopened, ready_for_review, labeled, closed]`에서
  `[opened, ready_for_review, closed]`로 수정하면, 매 푸시마다가 아니라
  PR이 열릴 때와 병합될 때만 요약합니다.

모든 실행은 실제로 지출한 비용을 기록합니다. 워크플로의 `recap usage`
단계가 토큰과 비용 사용량을 게시된 계획에 첨부하므로, 추측하는 대신
실행당 실제 지출을 확인할 수 있습니다.

**팀: 조직 서비스 토큰을 사용하세요.** 개인 토큰은 그것을 발급한 사람에게
묶여 있습니다 — 그 사람이 조직을 떠나거나 자신의 토큰을 취소하면, 그
시크릿을 쓰는 모든 저장소가 401 오류로 실패하기 시작하고, CI가 만든
계획들은 팀이 아니라 그 개인이 소유하게 됩니다. 조직 서비스 토큰은
**조직**이 소유합니다. 서비스 프린시펄(`svc-<name>@service.<orgId>`)로
동작하며, 개개인이 조직을 떠나도 살아남고, 이 토큰이 게시하는 요약은
조직 전체에 공개되며, 어떤 조직 소유자나 관리자든 이를 조회하거나
취소할 수 있습니다. 발급하려면(조직 소유자/관리자만 가능):

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --service-token pr-recap
```

이 명령은 브라우저에서 인증을 진행한 다음 서비스 토큰을 딱 한 번
출력합니다 — 이를 `PLAN_RECAP_TOKEN` 시크릿으로 저장하세요. 나중에는
Plans 앱의 `list-org-service-tokens`와 `revoke-org-service-token` 액션으로
관리할 수 있습니다.

**개인: 개인 토큰도 여전히 동작합니다.** Plans 앱을 대상으로
`npx @agent-native/core@latest connect`로 발급하세요. 호스팅된 앱의 경우
이 명령은 `npx @agent-native/recap-cli@latest recap setup`이 읽을 수 있는
로컬 게시 토큰 파일도 작성합니다.

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --client codex
npx @agent-native/recap-cli@latest recap setup
```

수동 설정을 선호한다면 토큰을 GitHub 시크릿에 붙여넣으세요. 예시에서만
`plan_recap_xxxxxxxxxxxxxxxx` 같은 자리표시자를 사용하고, 실제 토큰은
절대 커밋하지 마세요.

## 포크 PR

### 기본 동작(별도 조치 불필요)

메인 `pr-visual-recap.yml` 워크플로는 `pull_request_target`이 **아니라**
일반 `pull_request` 트리거에서 실행됩니다. 따라서 포크 PR은
**저장소 시크릿에 대한 접근 권한 없이** 실행되므로, 워크플로는
`PLAN_RECAP_TOKEN`을 찾지 못하고 깔끔하게 아무 것도 하지 않습니다 —
게시 실패도, 자격 증명 노출도 없습니다. 요약은 시크릿을 사용할 수 있는
같은 저장소 브랜치의 PR에 대해서만 자동으로 실행됩니다.

이는 또한 시크릿이 존재하기 **전에** 워크플로 파일을 병합할 수 있다는
의미이기도 합니다. 토큰이 구성되어 있지 않으면 시크릿을 설정하기
전까지 모든 실행은 조용히 아무 것도 하지 않습니다. `gate` 단계는 초안
PR과 봇이 작성한 PR도 자동으로 건너뛰므로, 이 둘도 기본적으로는 요약을
실행하지 않습니다.

### 레이블로 게이트를 여는 포크 워크플로 옵트인

포크 PR에 대한 요약을 생성하고 싶다면, 두 번째 워크플로 파일인
`.github/workflows/pr-visual-recap-fork.yml`을 사용할 수 있습니다. 이
파일은 `pull_request_target`(base 저장소 시크릿과 함께 실행됨)을
사용하지만, 포크 코드를 체크아웃하거나 실행하는 일은 절대 없습니다.
GitHub 작성자 소속이 `OWNER`, `MEMBER`, `COLLABORATOR`인 신뢰된 포크
작성자는 자동으로 실행됩니다. 그 외 포크 PR은 요약 에이전트가 실행되기
전에 명시적인 **head별 메인테이너 옵트인**(새로운 `recap` 레이블 이벤트)이
필요합니다.

설치하려면
[BuilderIO/agent-native](https://github.com/BuilderIO/agent-native/blob/main/.github/workflows/pr-visual-recap-fork.yml)에서
파일을 복사해 기존 `pr-visual-recap.yml` 옆에 있는 저장소의
`.github/workflows/` 디렉터리에 넣으세요. OpenAI 호환 제공업체를 사용할
때의 `VISUAL_RECAP_API_KEY`, `VISUAL_RECAP_BASE_URL`,
`VISUAL_RECAP_MODEL`을 포함해 같은 백엔드 구성이 적용됩니다.

### 레이블 게이트가 동작하는 방식

1. 포크 기여자가 PR을 엽니다. 일반 `pull_request` 워크플로는 GitHub가
   포크 실행에 시크릿을 주지 않기 때문에 건너뜁니다.
2. 포크 워크플로가 PR 작성자 소속을 확인합니다. 신뢰된 작성자(`OWNER`,
   `MEMBER`, `COLLABORATOR`)는 열림, 동기화, 재오픈, 리뷰 준비 이벤트에서
   자동으로 실행됩니다.
3. 그 외 기여자는 메인테이너가 현재 diff를 검토한 다음(특히
   프롬프트 인젝션으로 보이는 내용이 있는지 — 아래 참조) PR에 `recap`
   레이블을 붙여야 합니다.
4. 그 외 기여자에 대한 레이블 게이트는 head SHA 단위로 동작합니다.
   기여자가 커밋을 더 푸시하면, 다음 동기화 이벤트는 메인테이너가 새
   diff를 검토한 뒤 `recap`을 제거했다가 다시 붙이기 전까지 건너뜁니다.

### 포크 워크플로가 하는 일과 하지 않는 일

| 워크플로가 하는 일                                                                                                       | 워크플로가 하지 않는 일                                                              |
| ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| **base 저장소**를 **base 브랜치 참조**에서 체크아웃 — 신뢰된 코드만                                                       | 포크의 어떤 코드도 체크아웃하거나 실행하지 않음                                        |
| 포크 head를 원격 참조로 가져옴(`git fetch origin pull/<n>/head:refs/recap/fork-head`) — 커밋을 가져오는 것은 안전함        | 포크에서 패키지를 설치하거나, 포크 스크립트를 실행하거나, 포크 콘텐츠를 코드로 평가함  |
| `git diff base...refs/recap/fork-head` 실행 — 이미 가져온 두 객체 간의 순수 텍스트 diff                                    | diff를 LLM에 대한 텍스트 입력 이외의 용도로 사용함                                     |
| **base 저장소**의 visual-recap 스킬과 에이전트 구성을 실행                                                                | 포크에서 스킬이나 구성을 로드함                                                        |
| 1차 PR과 동일하게 diff를 시크릿 스캔 단계(안전하게 실패)에 통과시킴                                                        | 시크릿 스캔을 건너뜀                                                                   |
| diff 콘텐츠를 신뢰할 수 없는 것으로 표시하는 명시적인 프롬프트 강화 노트를 에이전트 프롬프트에 추가함                       | 일반 요약 에이전트를 넘어서는 추가 권한을 에이전트에 부여함                            |

### 레이블을 붙이기 전에 diff를 검토해야 하는 이유

포크 diff는 공격자가 통제할 수 있는 텍스트이며, 요약 에이전트가 이를
입력으로 읽습니다. 정교하게 조작된 diff는 프롬프트 인젝션 콘텐츠를
담을 수 있습니다 — 예를 들어 에이전트 지시처럼 보이는 diff 줄로,
요약 에이전트가 의도치 않은 행동(예: 게시 토큰을 유출하거나 오해의
소지가 있는 요약 내용을 생성하는 것)을 하도록 유도하려는 것입니다.

`recap` 레이블을 붙이기 전에 diff에서 다음을 훑어보세요.

- 직접적인 명령이나 역할 지시처럼 읽히는 줄("이전 지시는 무시해...",
  "이제 당신은...", "토큰을 다음 위치에 써...").
- 시스템 프롬프트로 오인될 수 있는 특이한 파일 이름.
- 지시로 디코딩될 수 있는, 추가된 파일 안의 인코딩된 콘텐츠.

이러한 완화책은 이미 워크플로에 여러 겹으로 쌓여 있지만(시크릿 스캔,
민감 경로 게이트, 프롬프트 강화 노트, 제한된 에이전트 도구 허용 목록),
레이블 검토가 주된 방어선입니다.

### 메인 워크플로와의 관계

두 워크플로 파일은 독립적입니다. 포크가 아닌 PR 업데이트에서는
`pr-visual-recap.yml`만 실행됩니다. 포크 PR의 경우 일반 워크플로는 포크
게이트에서 종료되고, `pr-visual-recap-fork.yml`이 신뢰된 동일 조직
작성자에 대해서는 자동으로, 그 외 기여자에 대해서는 새로운 메인테이너
`recap` 레이블 이후에 실행됩니다. 두 워크플로는 같은 고정 댓글 마커와
계획 ID 스레딩을 공유하므로, 일반 PR과 포크 PR 모두 같은 PR에 하나의
업서트된 댓글을 만들어냅니다.

### 자체 수정 방지 가드 {#self-modifying-guard}

`gate` 단계는 PR이 다음 경로 중 하나라도 건드리면 요약 전체를
건너뜁니다. 이렇게 하면 PR이 신뢰된 요약 작업이 로드하는 워크플로,
스킬, 에이전트 구성을 스스로 다시 작성해서 시크릿을 유출하는 일이
결코 일어날 수 없습니다.

| 경로 패턴                                   | 이유                                       |
| -------------------------------------------- | -------------------------------------------- |
| `.github/workflows/pr-visual-recap.yml`      | 워크플로 자체                                |
| `**/skills/visual-(recap\|plan\|plans)/**`   | 에이전트가 따르는 visual-recap 스킬          |
| `**/.claude/**`                              | 러너가 로드하는 에이전트 설정                |
| `**/CLAUDE.md`                               | 러너가 로드하는 에이전트 지시                |
| `**/AGENTS.md`                               | 러너가 로드하는 에이전트 지시                |
| `**/.mcp.json`                               | 러너가 로드하는 MCP 서버 구성                |

`BuilderIO/agent-native` 모노레포에서는, 워크플로가 PR head 소스가
아니라 신뢰된 base 브랜치 소스에서 요약 CLI를 실행합니다. 이 덕분에
`packages/core/**`를 포함한 일반적인 패키지 변경이 PR이 수정한 CLI
코드를 실행하지 않고도 요약 대상으로 남을 수 있습니다.

## 로컬 파일 프라이버시 모드

이 GitHub Action은 호스팅된, 공유 가능한 PR 검토를 위해 설계되었습니다.
요약 내용을 Agent-Native Plan 데이터베이스로 보내지 않고 요약을 원한다면,
대신 로컬에서 같은 도우미 흐름을 로컬 파일 모드로 실행하세요.

```bash
npx @agent-native/recap-cli@latest recap collect-diff --base main --head HEAD --out recap.diff --stat recap.stat
npx @agent-native/recap-cli@latest recap scan --diff recap.diff
npx @agent-native/recap-cli@latest recap build-prompt --pr 123 --diff recap.diff --stat recap.stat --local-files --local-dir plans/pr-123-visual-recap
```

생성된 `recap-prompt.md`를 코딩 에이전트에게 건네주세요. 로컬 파일
모드에서는 프롬프트가 에이전트에게 `plans/pr-123-visual-recap/plan.mdx`와
선택적인 시각 자료 파일을 작성한 다음 다음을 실행하도록 지시합니다.

```bash
npx @agent-native/core@latest plan local serve --dir plans/pr-123-visual-recap --kind recap --open
```

반환된 URL은 호스팅된 Plan UI를 열고, 브라우저는 localhost 브리지에서
요약 MDX를 읽습니다. 요약 내용은 호스팅된 Plan 데이터베이스에 기록되지
않으며, 그 URL은 브리지를 실행하는 머신에서만 동작합니다. 같은
`PLAN_LOCAL_DIR`로 Plan 앱을 로컬에서 실행한다면
`/local-plans/pr-123-visual-recap` 라우트도 유효합니다. 저장소에 있는
폴더는 `/local-plans/pr-123-visual-recap?path=plans%2Fpr-123-visual-recap`로
열 수 있습니다. 이 모드는 명시적으로 게시하기 전까지 호스팅된 고정 PR
댓글, 인라인 스크린샷 업로드, 사용량 첨부, 브라우저 댓글 기능을
비활성화합니다.

## 정보성일 뿐, 게이트가 아닙니다

이 요약은 일반적인 PR 흐름 위에 얹힌 검토 보조 수단입니다.

- 가시성을 위해 `Visual Recap` 체크 항목을 표시하지만 **절대 필수
  체크가 아니며** 병합을 막지 않습니다.
- 생성이나 게시 실패는 관련 없는 코드에 대한 빨간 X가 아니라 중립
  상태로 완료되며 설명이 담긴 고정 댓글로 드러납니다.
- 요약과 스크린샷이 **diff가 검토되었음을 의미하지는 않습니다.**
  리뷰어는 여전히 실제로 변경된 줄을 읽어야 합니다.

## 버전 고정(copy 변형) {#version-pinning-copy-variant}

기본적으로 copy 변형 워크플로는 실행 시점에 `@agent-native/recap-cli@latest`를
설치하므로 모든 요약 실행은 자동으로 최신 CLI를 사용합니다. CI에 재현
가능한 도구가 필요하다면, **`RECAP_CLI_VERSION`** 저장소 변수를 설정해
설치된 버전을 고정하세요.

1. 저장소의 **Settings → Secrets and variables → Actions → Variables**로
   이동합니다.
2. `1.5.0`과 같은 값으로 `RECAP_CLI_VERSION`이라는 변수를 만듭니다.

이 변수는 선택 사항입니다. 최신 릴리스를 추적하려면 설정하지 않거나
`latest`로 설정하세요.

재사용 가능한 호출자 변형에서는 대신 `cli-version` 입력을 사용하세요
(재사용 섹션의 [버전 고정](#version-pinning) 참조).

## 시크릿 스캔 허용 목록

요약을 게시하기 전에 워크플로는 `npx @agent-native/recap-cli@latest recap
scan`을 실행해 diff 안에 있을 법한 시크릿을 탐지합니다. diff가 알려진
시크릿 패턴과 일치하는 PR은 설명이 담긴 댓글과 함께 차단됩니다 — 요약은
게시되지 않으며, diff 콘텐츠도 코딩 에이전트에 전달되지 않습니다.

드물게 저장소에 의도적인 테스트 픽스처나, 겉보기에 시크릿 패턴처럼
보이는 비-시크릿 문자열(예: 테스트 파일 안의 픽스처 키)이 있을 수
있습니다. 오탐을 억제하려면 저장소 루트에
`.github/recap-scan-allowlist`를 만드세요.

### 형식

빈 줄이나 주석이 아닌 각 줄은 **리터럴 부분 문자열**이거나
**`/regex/flags`** 패턴입니다.

```
# Lines starting with # are comments.

# Literal substring — any diff line containing this string is allowed.
sk-test-fixture1234567890abcdef

# Regex pattern — written as /pattern/flags (JS syntax).
/^.STRIPE_KEY=sk-test-/i

# Another literal.
EXAMPLE_API_KEY=placeholder-value
```

규칙은 다음과 같습니다.

- 줄에 리터럴이 포함되어 있거나 정규식이 줄 전체와 일치하면 그 줄은
  **억제**(허용)됩니다.
- 이 파일은 **안전 실패(fail-closed)** 방식입니다. 파일이 없으면
  아무 억제도 적용되지 않습니다 — 스캐너는 이전과 동일하게 동작합니다.
- 빈 파일은 파일이 없는 것과 동일합니다.
- 형식이 잘못된 정규식 줄은 리터럴 문자열로 취급됩니다.

이 허용 목록은 시크릿 스캔 게이트에서만 참조됩니다. 코딩 에이전트가
읽을 수 있는 내용에는 영향을 주지 않습니다 — 게이트를 통과하면
에이전트는 어떤 경우든 전체 diff를 받습니다.

## 재사용 가능한 워크플로로 채택하기

### 재사용 가능한 변형을 쓰는 이유는 무엇인가요?

기본 설치기는 전체 약 360줄의 워크플로 YAML을 저장소에 그대로
복사합니다(**copy** 옵션). 이는 에어갭 저장소나 실행되는 모든 줄을
감사해야 하는 저장소에는 올바른 선택입니다. 단점은 버그 수정과 개선
사항이 자동으로 도달하지 않는다는 것입니다 — 릴리스가 나올 때마다
`npx @agent-native/recap-cli@latest recap setup`을 수동으로 다시
실행해야 합니다.

**재사용 가능한(reusable)** 옵션은 대신 얇은 약 20줄짜리 호출자를
작성합니다. 이는 `uses:`를 통해
`BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml`에
위임합니다. 모든 호출자는 워크플로가 실행될 때마다 자동으로 최신
로직을 가져오며, 로컬에서 업데이트할 필요가 없습니다.

|                                    | Copy(기본값)                | 재사용 가능              |
| ---------------------------------- | ---------------------------- | -------------------------- |
| 저장소 안의 워크플로 크기          | 약 360줄                     | 약 20줄                    |
| 수정 사항 자동 반영                | 아니오 — `recap setup` 재실행 | 예                          |
| 에어갭 / 완전한 감사 가능성        | 예                            | 아니오                      |
| 특정 버전에 고정 가능              | 로컬 편집으로만 가능          | 예 — `uses:`에서 `@v1.2.3` 설정 |

### 호출자 스니펫

다음은 `npx @agent-native/recap-cli@latest recap setup --reusable`이
작성하는 내용입니다(직접 붙여넣을 수도 있습니다).

```yaml
name: PR Visual Recap

# Thin caller — the full workflow logic lives in BuilderIO/agent-native.
# Fixes and improvements reach this repo automatically on each run.
# To pin a specific version for reproducibility replace '@main' with a
# tag or SHA, e.g. '@v1.2.3' or '@abc1234'.

on:
  pull_request:
    types: [opened, synchronize, reopened, ready_for_review, labeled, closed]

jobs:
  visual-recap:
    if: github.event.action != 'labeled' || vars.VISUAL_RECAP_REQUIRED_LABELS != ''
    permissions:
      actions: write
      contents: read
      checks: write
      issues: write
      pull-requests: write
    uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@main
    secrets:
      PLAN_RECAP_TOKEN: ${{ secrets.PLAN_RECAP_TOKEN }}
      ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
      OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
      VISUAL_RECAP_API_KEY: ${{ secrets.VISUAL_RECAP_API_KEY }}
      PLAN_RECAP_APP_URL: ${{ secrets.PLAN_RECAP_APP_URL }}
    with:
      agent: ${{ vars.VISUAL_RECAP_AGENT || 'claude' }}
      model: ${{ vars.VISUAL_RECAP_MODEL || '' }}
      base-url: ${{ vars.VISUAL_RECAP_BASE_URL || '' }}
      reasoning: ${{ vars.VISUAL_RECAP_REASONING || '' }}
      skill-source: ${{ vars.VISUAL_RECAP_SKILL_SOURCE || 'auto' }}
      runs-on: ${{ vars.VISUAL_RECAP_RUNS_ON || '"ubuntu-latest"' }}
      gate-runs-on: ${{ vars.VISUAL_RECAP_GATE_RUNS_ON || 'ubuntu-latest' }}
      required-labels: ${{ vars.VISUAL_RECAP_REQUIRED_LABELS || '' }}
      # cli-version: "latest"  # pin to a specific @agent-native/recap-cli version
```

[시크릿과 변수](#secrets-and-variables)에서 설명한 것과 같은 시크릿과
변수가 적용됩니다 — copy 변형과 동일한 방식으로 저장소 설정에
설정하세요. 재사용 가능한 호출자는 전체 요약 작업을 위한 JSON
`runs-on` 입력으로 `VISUAL_RECAP_RUNS_ON`을, 메타데이터 전용 게이트를
위한 일반 레이블 `gate-runs-on` 입력으로 `VISUAL_RECAP_GATE_RUNS_ON`을,
선택적인 PR 레이블 게이팅을 위한 `required-labels`로
`VISUAL_RECAP_REQUIRED_LABELS`를 전달합니다. 게이트 러너 입력은
신뢰된 동일 저장소 작성자에게만 사용되며, 그 외 PR은 GitHub 호스팅
`ubuntu-latest`를 사용합니다. 러너 입력을 생략하면 `ubuntu-latest`
기본값이 유지되고, 필수 레이블을 생략하면 자동 요약 동작이 유지됩니다.

### CLI로 설치하기

```bash
# Write the thin caller instead of the full copy:
npx @agent-native/recap-cli@latest recap setup --reusable

# Or with a pinned ref for reproducibility:
npx @agent-native/recap-cli@latest recap setup --reusable --ref v1.2.3
```

두 변형 모두 워크플로를 `.github/workflows/pr-visual-recap.yml`에
작성합니다. 이미 다른 워크플로가 그 자리에 있고 내용이 다르다면,
명령은 거부하고 덮어쓰려면 `--force`를 전달하라고 안내합니다.

작성 후에는 평소처럼 `npx @agent-native/recap-cli@latest recap doctor`를
실행해 시크릿이 구성되었는지 확인하세요.

### 버전 고정 {#version-pinning}

기본적으로 호출자는 `@main`을 참조하며, 이는 항상 재사용 가능한
워크플로의 최신 게시 버전을 사용합니다. 재현 가능한 CI가 필요한
프로덕션 저장소라면 태그나 SHA에 고정하세요.

```yaml
uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@v1.2.3
```

`cli-version` 입력은 워크플로 안에서 실행되는
`@agent-native/recap-cli` 버전을 제어합니다 — 최신 릴리스를 추적하려면
`"latest"`로 두고, 완전한 재현성을 위해서는 버전 문자열(예:
`"1.5.0"`)로 고정하세요.

### workflow_call 이벤트 컨텍스트

`workflow_call` 워크플로는 **호출자**의 이벤트 컨텍스트를 상속받습니다.
재사용 가능한 워크플로는 `github.event.pull_request.*` 표현식을 사용해
PR 번호, head SHA, base SHA, 병합 타임스탬프, PR 메타데이터를
읽습니다 — 이는 호출자가 `pull_request`에서 트리거될 때만 올바르게
동작합니다. 위의 호출자 스니펫에는 이미 올바른 이벤트 유형이 포함되어
있습니다. `closed` 이벤트가 포함된 이유는 병합된 PR 요약에
`merged_at`을 찍어 나중에 완료된 작업으로 검색할 수 있게 하기
위해서입니다.

호출자를 `workflow_dispatch`나 `push`에서 트리거하지 마세요 — 이
이벤트들은 `pull_request` 페이로드를 담고 있지 않으므로, 게이트가
"no pull_request payload"로 요약을 건너뜁니다.
