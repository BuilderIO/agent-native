# SSR 캐싱

모든 SSR HTML 응답과 모든 React Router `.data` 응답은 하나의 개인화되지 않은 공개 셸입니다. `createH3SSRHandler`는 렌더링 전에 쿠키를 제거하므로, 동일한 바이트가 모든 방문자에게 올바르며 모든 개인화는 로드 후 클라이언트에서 이루어집니다. 이 덕분에 기본적으로 이러한 응답에 하나의 하드 캐시 정책을 적용해도 안전합니다:

```txt
cache-control: public, max-age=600, stale-while-revalidate=604800, stale-if-error=3600
```

동일한 값이 `cdn-cache-control`에도 미러링됩니다. `netlify-cdn-cache-control`은 대신 더 오래 유지되는 자체 기본값인 `public, durable, s-maxage=31536000, stale-while-revalidate=604800, stale-if-error=3600`을 갖습니다. Netlify의 CDN이 이 헤더를 표준 헤더와 별도로 읽기 때문입니다. 그러면 요청마다 렌더링하는 대신 하나의 공유 CDN 항목이 전체 사이트를 제공합니다. 이는 첫 응답 지연 시간에 가장 큰 영향을 미치는 단일 요소입니다. 아래 사례 중 하나가 배포에 해당하지 않는 한 이를 그대로 켜 두세요.

## `AGENT_NATIVE_SSR_CACHE`로 재정의하기 {#ssr-cache-env}

배포 전체의 정책을 변경하려면 배포 환경에서 `AGENT_NATIVE_SSR_CACHE`를 설정하세요:

| 값                                                  | 결과                                                                                                                                                                                                                                                                      |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 설정 안 함, `on`, `default`, `true`, `1`            | 위의 기본 정책 그대로 유지됩니다. 최상의 성능을 위해 권장됩니다.                                                                                                                                                                                                          |
| `off`, `false`, `0`, `none`, `no-store`, `disabled` | `cache-control`, `cdn-cache-control`, `netlify-cdn-cache-control`에 `no-store`가 적용됩니다.                                                                                                                                                                              |
| 기간: `30`, `30s`, `5m`, `2h`                       | `cache-control`과 `cdn-cache-control`에 `public, max-age=<n>, stale-while-revalidate=<n>, stale-if-error=3600`이 적용됩니다. `netlify-cdn-cache-control`은 동일한 기간으로 `public, durable, s-maxage=<n>, stale-while-revalidate=<n>, stale-if-error=3600`을 사용합니다. |

숫자만 있으면 초 단위입니다. 사용자 지정 기간에 대해 `stale-while-revalidate`는 의도적으로 `max-age`를 그대로 따릅니다. 짧은 신선도 기간에 기본값인 7일짜리 stale 기간을 결합하면 오히려 사용자가 원치 않았던 정확히 그 오래된 데이터를 돌려주게 되기 때문입니다. 인식할 수 없는 값은 경고를 기록하고 기본값으로 대체되므로, 오타가 CDN을 조용히 비활성화하는 일은 결코 없습니다.

다음 중 하나라도 해당한다면 낮추거나 끄세요:

1. **호스트가 배포 시 CDN을 퍼지하지 않는 경우.** Netlify와 Vercel은 퍼지합니다. 일부 자체 관리 환경은 그렇지 않습니다. 퍼지가 없으면 배포된 빌드가 `max-age`와 `stale-while-revalidate`를 합한 기간 동안 이전 셸을 계속 제공할 수 있습니다.
2. **로더가 변경 가능한 공개 데이터를 반환하는 경우.** 성공적인 mutation 이후 `useRevalidator()`나 액션 후 리디렉션 재요청이 새로운 로더 출력 대신 브라우저의 캐시된 `.data` 사본을 읽을 수 있습니다.

이 설정은 모든 공개 셸 표면에 적용됩니다. React Router SSR HTML과 `.data`, 로그인 HTML 셸, `/_agent-native/speculation-rules.json` 라우트, docs 사이트, forms 템플릿의 공개 폼 SSR입니다. 생성된 Cloudflare Worker는 빌드 시점에 이를 확인하므로, 빌드가 실행되기 전에 배포 환경에서 설정하세요.

유의해야 할 세 가지가 있습니다:

- **캐싱을 끈다고 SSR이 개인화되지는 않습니다.** 쿠키는 여전히 렌더링 전에 제거되며 SSR 로더는 여전히 익명 분기를 봅니다. 사용자별 데이터는 여전히 클라이언트 측에서 해결해야 합니다. 이 변수는 캐시 *기간*만 제어합니다.
- **의도적으로 라우트별이 아니라 배포 전체에 적용됩니다.** 라우트별 또는 요청별 캐시 재정의는 한 방문자의 페이로드가 다른 방문자의 공유 CDN 항목에 들어가게 되는 원인이 되므로, 프레임워크는 이를 제공하지 않습니다. `guard:ssr-cache-shell`이 이를 강제합니다.
- **mutation 직후의 신선한 데이터가 필요하다면 캐시를 비활성화하기보다 actions를 선호하세요.** 앱 데이터는 [actions](/docs/actions-overview)에 속하며, 클라이언트에서 `useActionQuery` / `useActionMutation`으로 읽고 `useDbSync()` 폴링으로 최신 상태를 유지합니다. 이들 중 어느 것도 SSR 셸 캐시를 거치지 않습니다. SSR 로더는 공개 셸을 렌더링하는 용도로 유지하고, 로더 데이터를 정말로 더 신선하게 만들고 싶을 때만 이 변수를 사용하세요.
