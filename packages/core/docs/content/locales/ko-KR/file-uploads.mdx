# 파일 업로드

프레임워크는 구성 가능한 공급자를 통해 업로드를 라우팅하는 파일 업로드 추상화를 제공합니다. 템플릿은 `uploadFile()`을 호출하고 URL을 반환받습니다. 스토리지 백엔드는 애플리케이션 코드를 변경하지 않고도 교체할 수 있습니다.

## 작동 방식 {#how-it-works}

업로드 요청은 `POST /_agent-native/file-upload`로 전달되며, 이 엔드포인트가 활성 공급자로 요청을 전달합니다. 어떤 공급자가 구성되어 있는지는 `GET /_agent-native/file-upload/status`에서 확인할 수 있습니다.

공급자 해결 순서는 다음과 같습니다.

1. **사용자 등록 공급자**: `registerFileUploadProvider()`를 통해 등록된 사용자 지정 공급자입니다.
2. **Builder.io 공급자**: 내장되어 있으며, Builder.io가 연결되면 자동으로 활성화됩니다.
3. **공급자 없음**: 업로드가 거부되고 채팅에 스토리지 설정 CTA가 표시됩니다. 바이너리 데이터는 SQL에 저장되지 않습니다.

사용자 등록 공급자 중에서는 스스로 구성되었다고 보고하는 첫 번째 공급자가 우선합니다. `registerFileUploadProvider()`는 `id`별로 멱등적입니다. 이미 사용 중인 id로 등록하면 기존 공급자를 대체합니다.

UI는 업로드가 시도되기 전에 동기적인 `isConfigured()` 검사만으로 스토리지 설정 프롬프트를 표시할지 결정합니다. 실제 업로드는 `isConfigured()`와 `isConfiguredForRequest()`를 모두 확인합니다. `isConfiguredForRequest()`를 통해서만 스스로 구성되었다고 보고하는 공급자는 이를 통한 업로드가 성공하더라도 설정 프롬프트에는 표시되지 않습니다.

## 영구 업로드를 위한 스토리지 필요 {#storage-required}

구성된 공급자가 없으면 `uploadFile()`은 `null`을 반환하고 멀티파트 라우트는 `503`을 반환합니다. 채팅 첨부 파일은 현재 요청에서만 사용할 수 있고, 에이전트는 스토리지 설정 힌트를 받으며, 트랜스크립트에는 바이너리 페이로드 대신 설정 마커가 저장됩니다. 이러한 안전 실패 동작은 SQL을 작게 유지하고 누락된 구성을 명확하게 드러냅니다.

## Builder.io 호스팅 {#builder-hosting}

앱이 Builder.io에 연결되면 파일 업로드가 자동으로 Builder의 자산 호스팅으로 라우팅됩니다. Builder.io의 무료 요금제에는 이 관리형 스토리지가 포함되어 있습니다. 파일은 별도 구성 없이 CDN에서 제공되며, 영구 URL이 채팅 스레드에 저장되어 이후 턴에서 재사용할 수 있습니다. 이는 권장되는 프로덕션 설정입니다.

## 사용자 지정 공급자 {#custom-providers}

프레임워크에는 S3 호환 스토리지(AWS S3, Cloudflare R2, MinIO 등)용 내장 공급자가 이미 포함되어 있습니다. 환경 변수를 사용하거나 사이드바 온보딩 체크리스트를 통해 연결할 수 있습니다. 코드를 작성할 필요는 없습니다. [온보딩](/docs/onboarding)을 참고하세요.

사용자 지정 공급자는 다른 종류의 백엔드를 사용할 때만 등록하세요. 다음 예시는 `fetch()`를 사용하여 일반 HTTP API를 통해 업로드합니다.

```ts filename="server/plugins/file-upload.ts"
import { registerFileUploadProvider } from "@agent-native/core/file-upload";
import { defineNitroPlugin } from "@agent-native/core/server";

export default defineNitroPlugin(() => {
  registerFileUploadProvider({
    id: "my-storage",
    name: "My Storage",
    isConfigured: () => !!process.env.UPLOAD_ENDPOINT,
    upload: async ({ data, filename, mimeType }) => {
      const endpoint = process.env.UPLOAD_ENDPOINT!;
      const body = new FormData();
      body.append("file", new Blob([data], { type: mimeType }), filename);

      // This example assumes an upload API that accepts a multipart file
      // and returns { url }. Adjust the request and response handling to
      // match your own provider's actual contract.
      const response = await fetch(endpoint, { method: "POST", body });
      if (!response.ok) {
        throw new Error(`Upload failed with status ${response.status}`);
      }

      const { url } = await response.json();
      return { url, provider: "my-storage" };
    },
  });
});
```

공급자가 API 키 같은 실제 자격 증명을 필요로 하는 경우에는 환경 변수 대신
`@agent-native/core/server`의 `resolveSecret()`을 사용하세요.
[보안 — 비밀 관리](/docs/security#secrets)를 참고하세요.

## 업로드 API {#upload-api}

`FileUploadProvider` 인터페이스:

```ts
interface FileUploadProvider {
  id: string; // Unique id, e.g. "s3"
  name: string; // Human-readable name
  isConfigured: () => boolean; // True when ready from sync runtime state
  isConfiguredForRequest?: () => Promise<boolean>; // True from scoped DB secrets
  upload: (input: FileUploadInput) => Promise<FileUploadResult>;
}

interface FileUploadInput {
  data: Uint8Array | Buffer; // File contents
  filename?: string; // Original filename
  mimeType?: string; // MIME type, e.g. "image/png"
  ownerEmail?: string; // For request-scoped provider credentials
  stableUrl?: boolean; // Builder.io hint: one stable URL while compression finishes
  recordAsset?: boolean; // Builder.io hint: set false to skip the asset library
}

interface FileUploadResult {
  url: string; // Public URL for the uploaded file
  id?: string; // Provider-specific id
  provider: string; // Which provider handled it
}
```

actions나 서버 코드에서 `@agent-native/core/file-upload`의 `uploadFile()`을 사용하세요.

```ts
import { uploadFile } from "@agent-native/core/file-upload";

const result = await uploadFile({
  data: fileBuffer,
  filename: "photo.jpg",
  mimeType: "image/jpeg",
});

if (result) {
  // Provider handled it. result.url is the public URL.
} else {
  // No provider configured. Show the storage setup CTA, or skip.
}
```

## 재개 가능 / 스트리밍 업로드 {#resumable}

공급자는 전체 파일을 먼저 버퍼링하는 대신 데이터가 도착하는 대로 스토리지로 스트리밍해야 하는 업로드를 위해 `FileUploadProvider`에 `resumable` 블록을 선택적으로 구현할 수 있습니다. Clips 템플릿은 이를 사용하여 녹화가 끝난 후 전체 블롭을 조립하는 대신, 녹화가 진행되는 동안 청크 단위로 녹화 데이터를 스토리지에 전달합니다.

```ts
interface FileUploadProvider {
  // ...id, name, isConfigured, upload...

  resumable?: {
    startSession(
      filename: string,
      mimeType: string,
      maxBytes: number,
    ): Promise<ResumableUploadSession>;
    relayChunk(
      session: ResumableUploadSession,
      contentRange: string,
      bytes: Uint8Array,
      options?: { mimeType?: string },
    ): Promise<ResumableChunkResult>;
    completeSession(
      session: ResumableUploadSession,
      filename: string,
      options?: { stableUrl?: boolean; recordAsset?: boolean },
    ): Promise<string>;
    // Best-effort provider cleanup for a session the caller will not resume.
    abortSession?(session: ResumableUploadSession): Promise<void>;
  };
}

interface ResumableUploadSession {
  sessionId: string; // Provider-specific: GCS Location URI, S3 UploadId, etc.
  meta: Record<string, unknown>; // Provider state carried between calls
}

interface ResumableChunkResult {
  ok: boolean;
  status: number;
  updatedMeta?: Record<string, unknown>; // Merged back into the stored session
}
```

`resumable`이 존재하면 (레코더처럼) 데이터를 스트리밍으로 전달하는 호출자는 `startSession`을 한 번 호출하고, 바이트가 도착할 때마다 `relayChunk`를 반복 호출하며, 스트림이 끝나면 `completeSession`을 호출합니다. 이는 단일 버퍼링 `upload()` 호출을 대체합니다. `resumable` 블록이 없는 공급자는 항상 버퍼링 경로만 사용됩니다. 스토리지 백엔드에 노출할 가치가 있는 네이티브 청크/재개 가능 업로드 API(S3 멀티파트, GCS 재개 가능 업로드 등)가 있는 경우에만 이를 구현하세요.
