# 다중 앱 작업 공간 속 캘린더

캘린더는 [Dispatch](/docs/template-dispatch) 작업 공간에 속한 여러 앱 중 하나입니다.
이 페이지는 그것이 실제로 무엇을 의미하는지, 즉 연결이 어떻게 동작하는지, 그리고
다른 앱이 여러분의 캘린더에 실제로 어떻게 작용하거나 캘린더에서 일어나는 일에
반응할 수 있는지를 구체적으로 다룹니다. 전체 개요는 [캘린더](/docs/template-calendar)
문서를 참고하세요.

## 캘린더가 Dispatch와 연결되는 방식

이것이 자동으로 이루어지는지는 캘린더와 Dispatch를 어떻게 함께 설정했는지에 따라
달라지며, 둘 중 하나가 호스팅되어 있는지 로컬에서 실행 중인지와는 관련이 없습니다.

### 같은 작업 공간: 자동

캘린더와 Dispatch가 하나의 Agent-Native 작업 공간에 (`create` 또는 `add-app`을
통해) 함께 생성되거나 추가되어 하나의 단위로 배포되었다면, 이미 하나의 `.env`,
하나의 `A2A_SECRET`, 하나의 작업 공간 레지스트리를 공유합니다. 검색과 인증된 A2A
호출 모두 그 작업 공간이 여러분의 컴퓨터에서 실행되든 프로덕션에서 실행되든 별도로
설정할 것 없이 그대로 동작합니다. 캘린더를 기반으로 한 실제 다중 앱 제품이라면 이
설정이 기본적으로 예상됩니다.

### 별도 배포: 수동 단계 하나

캘린더와 Dispatch가 독립적으로 생성된 두 개의 Agent-Native 프로젝트라면, 시크릿을
공유하지 않으므로 아직 서로를 호출할 수 없습니다. 이들을 연결하려면 양쪽 각각에서
수동 단계 하나가 필요합니다. 설정 → 연결된 에이전트, Agent 페이지의 연결 탭, 또는
Dispatch → 에이전트 → 외부 에이전트 추가에서 공유 시크릿과 함께
`remote-agents/<id>.json` 리소스를 추가하세요. 전체 과정은
[A2A 프로토콜](/docs/a2a-protocol) 문서를 참고하세요.

어느 쪽 상황인지 확인하려면 두 앱 중 어느 쪽 에이전트에게든 "어떤 앱들을 볼 수
있어?"라고 물어보세요. Dispatch의 답변에 캘린더가 빠져 있다면 두 번째 경우에
해당합니다.

## 통합 전략

**캘린더 이벤트를 기반으로 자동화하기.** 이벤트를 만드는 것과 예약을 만드는 것
모두 공유 프레임워크 이벤트 버스에서 실제 이벤트(`calendar.event.created`,
`calendar.booking.created`)를 발생시킵니다. 어떤 앱이 정의했는지와 무관하게 어떤
앱의 [자동화](/docs/automations)든 이 둘 중 하나를 구독할 수 있습니다. 캘린더에
예약이 들어오면 메일에서 환영 이메일 초안을 작성하거나, 회의가 시작되기 전에
슬라이드에서 회의 안건을 만드는 식으로 이어질 수 있습니다. 캘린더는 이런 자동화를
기본으로 제공하지 않지만, 이벤트는 실제로 존재하며 원할 때 언제든 연결해 만들 수
있습니다.

**Dispatch를 통한 자연어 위임.** 다른 형제 앱이 캘린더와 함께 동작하는 데 특별한
통합이 필요하지는 않습니다. 여러분이 채팅에서 하는 것과 같은 방식으로, "다음 주에
Sam과 30분 시간 찾아줘" 같은 자연어 요청을 캘린더의 에이전트에게 그대로 건네면,
캘린더가 직접 답하거나 처리합니다. 메일이나 Slack으로 들어온 일정 요청이 예약된
이벤트로 바뀌는 것 같은 일의 실제 메커니즘이 바로 이것입니다. Dispatch(또는
메시지를 받은 앱)가 요청을 캘린더의 에이전트에게 위임하면, 캘린더는 다른
프롬프트와 똑같이 그 요청을 처리합니다.

**분리된 상태 유지하기.** 이 모든 과정에서 캘린더가 메일이나 Slack의 자격 증명을
알아야 할 필요는 전혀 없으며, 반대 방향도 마찬가지입니다. 이벤트 버스와 그것을
구독하는 자동화가 앱들 사이에 자리 잡고 있으므로, 캘린더는 실제 이벤트를
발생시키거나 실제 요청에 답하기만 하면 됩니다. 누가 듣고 있는지, 어떻게 듣고
있는지는 알 필요가 없습니다.
