# 다중 앱 작업 공간 속 슬라이드

슬라이드는 [Dispatch](/docs/template-dispatch) 작업 공간에 속한 여러 앱 중 하나입니다.
이 페이지는 그것이 실제로 무엇을 의미하는지, 즉 연결이 어떻게 동작하는지, 그리고
다른 앱이 여러분의 데크에 실제로 어떻게 작용하거나 그 안의 내용을 재사용할 수
있는지를 구체적으로 다룹니다. 전체 개요는 [슬라이드](/docs/template-slides) 문서를
참고하세요.

## 슬라이드가 Dispatch와 연결되는 방식

이것이 자동으로 이루어지는지는 슬라이드와 Dispatch를 어떻게 함께 설정했는지에
따라 달라지며, 둘 중 하나가 호스팅되어 있는지 로컬에서 실행 중인지와는 관련이
없습니다.

### 같은 작업 공간: 자동

슬라이드와 Dispatch가 하나의 Agent-Native 작업 공간에 (`create` 또는 `add-app`을
통해) 함께 생성되거나 추가되어 하나의 단위로 배포되었다면, 이미 하나의 `.env`,
하나의 `A2A_SECRET`, 하나의 작업 공간 레지스트리를 공유합니다. 검색과 인증된
A2A 호출 모두 그 작업 공간이 여러분의 컴퓨터에서 실행되든 프로덕션에서 실행되든
별도로 설정할 것 없이 그대로 동작합니다. 슬라이드를 기반으로 한 실제 다중 앱
제품이라면 이 설정이 기본적으로 예상됩니다.

### 별도 배포: 수동 단계 하나

슬라이드와 Dispatch가 독립적으로 생성된 두 개의 Agent-Native 프로젝트라면,
시크릿을 공유하지 않으므로 아직 서로를 호출할 수 없습니다. 이들을 연결하려면
양쪽 각각에서 수동 단계 하나가 필요합니다. Settings → Agent → Sub-agents(Connect agent), 또는 Dispatch → 에이전트 → 외부 에이전트 추가에서 공유 시크릿과 함께
`remote-agents/<id>.json` 리소스를 추가하세요. 전체 과정은 [A2A
프로토콜](/docs/a2a-protocol) 문서를 참고하세요.

어느 쪽 상황인지 확인하려면 두 앱 중 어느 쪽 에이전트에게든 "어떤 앱들을 볼 수
있어?"라고 물어보세요. Dispatch의 답변에 슬라이드가 빠져 있다면 두 번째 경우에
해당합니다.

## 통합 전략

**Creative Context Library를 통해 데크 공유하기.** 데크를 제출하면 정확히 그
시점의 버전 하나가 공유 Creative Context Library에 고정되며, 슬라이드뿐 아니라
작업 공간의 어떤 앱이든 나중에 그 슬라이드를 검색해서 재사용할 수 있습니다.
회의록 앱이라면 프롬프트로 설명하는 대신 승인된 지표 슬라이드를 자신의 결과물에
그대로 가져올 수 있습니다.

**Dispatch를 통한 자연어 위임.** 다른 형제 앱이 슬라이드와 함께 동작하는 데
특별한 통합이 필요하지는 않습니다. 여러분이 채팅에서 하는 것과 같은 방식으로,
"이번 분기 수치를 5장짜리로 정리해줘" 같은 평범한 문장의 요청을 슬라이드의
에이전트에게 그대로 건네면, 슬라이드가 직접 답하거나 처리합니다. 메일로 들어온
보고서 요청이 완성된 데크로 바뀌는 것 같은 일의 실제 메커니즘이 바로 이것입니다.
Dispatch(또는 메시지를 받은 앱)가 요청을 슬라이드의 에이전트에게 위임하면,
슬라이드는 다른 프롬프트와 똑같이 그 요청을 처리합니다.

**분리된 상태 유지하기.** 이 모든 과정에서 슬라이드가 형제 앱의 자격 증명을
알아야 할 필요는 전혀 없으며, 반대 방향도 마찬가지입니다. A2A 프로토콜과 공유
Creative Context Library가 앱들 사이에 자리 잡고 있으므로, 슬라이드는 실제
요청에 답하거나 실제 공유 리소스를 노출하기만 하면 됩니다. 누가 호출하고
있는지, 어떻게 호출하고 있는지는 알 필요가 없습니다.
