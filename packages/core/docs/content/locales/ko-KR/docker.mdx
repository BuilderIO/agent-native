# Docker

Docker는 Agent-Native 앱과 실행에 필요한 모든 것을 하나의 컨테이너 이미지로 패키징합니다. 이 이미지는 [Node.js 가이드](/docs/node-js)에서 설명하는 것과 같은 Node.js 서버를 실행하므로, 노트북, 가상 머신, 컨테이너를 실행하는 모든 호스트에서 똑같이 동작합니다.

이 가이드는 독립 실행형 앱 하나를 처음부터 배포하는 과정을 안내합니다. 앱을 만들고, `Dockerfile`을 추가하고, 프로덕션 데이터베이스와 인증 시크릿을 지정하고, 데이터베이스를 준비한 다음, 컨테이너를 빌드하고 실행합니다.

<Callout tone="info">

Node.js `22.22+`가 필요합니다.

</Callout>

이미지를 빌드하고 실행하는 머신에는 Docker도 설치되어 있어야 합니다. 이 가이드의 명령은 컨테이너를 실행할 서버에서 실행하세요. 가상 머신이라면 보통 먼저 SSH로 접속해야 합니다.

<a id="self-host-quickstart"></a>

## 1단계: 앱 만들기 {#step-1-create-the-app}

새 독립 실행형 앱을 만듭니다. 아래 예시는 Chat 템플릿으로 앱을 만들지만, 어떤 템플릿으로든 시작할 수 있습니다. 앱 폴더로 이동한 뒤 의존성을 설치하세요. `corepack enable`은 앱이 기대하는 `pnpm` 버전을 활성화하므로 `pnpm`을 직접 설치할 필요가 없습니다.

```bash
npx --yes @agent-native/core@latest create my-app --standalone --template chat

cd my-app

corepack enable

pnpm install
```

원한다면 `my-app`을 원하는 앱 이름으로 바꾸세요. 이 가이드의 나머지 부분은 앱 폴더 안에 있다고 가정합니다.

## 2단계: Dockerfile 만들기 {#step-2-create-dockerfile}

새 앱에는 `Dockerfile`이 포함되어 있지 않으므로 직접 추가해야 합니다. 로컬 파일이 이미지에 들어가지 않도록 하는 `.dockerignore` 파일도 함께 추가합니다. 두 파일 모두 앱의 루트 폴더, 즉 `package.json`과 같은 위치에 만드세요.

### Dockerfile {#dockerfile}

파일 확장자 없이 `Dockerfile`이라는 이름의 파일을 만들고 다음 내용을 복사하세요.

```dockerfile filename="Dockerfile"
FROM node:24-slim AS build
WORKDIR /app

RUN apt-get update \
  && apt-get install -y --no-install-recommends python3 make g++ \
  && rm -rf /var/lib/apt/lists/*

ENV PYTHON=/usr/bin/python3

COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile

COPY . .
RUN pnpm build

FROM node:24-slim
WORKDIR /app

ENV NODE_ENV=production
ENV PORT=3000

COPY --from=build /app/.output .output

EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

이 `Dockerfile`은 이미지를 두 단계로 빌드합니다.

- **빌드 단계.** 일부 의존성이 설치 중 컴파일에 필요로 하는 도구(`python3`, `make`, `g++`)를 설치하고, 앱의 의존성을 설치한 뒤 앱을 빌드합니다.
- **최종 단계.** 깨끗한 Node.js 이미지에서 시작해 `.output` 폴더에 있는 완성된 서버만 복사합니다. 이렇게 하면 이미지가 작게 유지되고 빌드 도구와 소스 코드는 포함되지 않습니다.

최종 이미지는 프로덕션 모드로 실행되며 포트 `3000`에서 수신합니다.

### Docker 제외 파일 {#docker-ignore-file}

`.dockerignore`라는 이름의 파일을 만들고 다음 내용을 복사하세요.

```text filename=".dockerignore"
node_modules
.output
.git
.env
.env.*
data
*.log
```

이 항목들은 로컬 의존성, 이전 빌드 출력, Git 기록, `.env` 파일에 있는 로컬 시크릿, `data`에 있는 로컬 개발 데이터베이스, 로그 파일이 이미지에 들어가지 않도록 합니다. 빌드 단계에서 의존성을 새로 설치하고 앱을 처음부터 빌드하므로 이 중 어떤 것도 필요하지 않습니다. `.env` 파일을 제외하면 시크릿이 이미지에 포함되는 것도 막을 수 있습니다.

## 3단계: 환경 시크릿 구성하기 {#step-3-configure-environment-secrets}

앱은 프로덕션 설정을 환경 변수에서 읽습니다.

| 변수                 | 필수   | 용도                                           |
| -------------------- | ------ | ---------------------------------------------- |
| `DATABASE_URL`       | 예     | 앱을 PostgreSQL 데이터베이스에 연결합니다      |
| `BETTER_AUTH_SECRET` | 예     | 사용자 세션에 서명합니다                       |
| `BETTER_AUTH_URL`    | 아니요 | 사용자가 앱에 접속하는 공개 주소를 설정합니다 |

아래의 export 명령을 실행하면 이 셸에서 이후 명령이 동작합니다. 배포하기 전에 같은 변수를 호스트의 프로젝트 또는 서비스 환경 설정에도 저장하세요. 그래야 재시작하거나 새로 배포한 뒤에도 컨테이너가 이 값을 유지합니다.

### 데이터베이스 URL {#database-url}

로컬 개발 중에는 `DATABASE_URL`이 설정되지 않으면 앱이 로컬 데이터베이스에 데이터를 저장합니다. 배포된 앱에는 재시작 후에도 데이터를 유지하는 실제 PostgreSQL 데이터베이스가 필요합니다. 컨테이너는 교체되면 그동안 쓴 파일을 모두 잃으므로 데이터베이스는 컨테이너 밖에 있어야 합니다. 프로바이더에서 연결 문자열을 복사해 export하세요.

```bash
export DATABASE_URL='your-postgres-url-string'
```

[데이터베이스 프로바이더 가이드](/docs/neon)에서 프로바이더별로 연결 문자열을 찾는 위치를 확인할 수 있습니다.

<Callout tone="warning">

Neon, Supabase, Amazon RDS 등 영구적인 PostgreSQL 프로바이더를 선택하세요.

</Callout>

### 인증 시크릿 {#auth-secret}

이 값은 한 번만 생성하고 배포할 때마다 바꾸지 마세요.

앱은 `BETTER_AUTH_SECRET`을 사용해 사용자 세션에 서명합니다. 이 값이 바뀌면 로그인한 모든 사용자가 로그아웃됩니다. 아래 명령은 임의의 값을 생성합니다.

```bash
export BETTER_AUTH_SECRET="$(openssl rand -hex 32)"
```

생성한 값은 호스트의 시크릿 설정이나 비밀번호 관리자처럼 안전한 곳에 저장하세요. 배포할 때마다 같은 값을 사용합니다.

### 공개 URL {#public-url}

선택 사항입니다. 사용자 지정 도메인, 리버스 프록시, 또는 고정된 공개 origin이 필요한 인증이나 OAuth 흐름을 사용할 때 설정하세요.

`BETTER_AUTH_URL`은 사용자가 앱에 접속하는 공개 주소입니다. 이 값이 없으면 앱은 들어오는 요청마다 자신의 주소를 판단합니다. 대개는 문제가 없지만, 앱이 프록시나 사용자 지정 도메인 뒤에 있으면 로그인 링크와 OAuth 리디렉션이 잘못된 곳을 가리킬 수 있습니다.

```bash
export BETTER_AUTH_URL='https://your-domain.example'
```

## 4단계: 마이그레이션 {#step-4-migrate}

마이그레이션은 앱에 필요한 테이블을 데이터베이스에 만들고 업데이트합니다.

첫 방문 전에 호스트에서 프로덕션 `DATABASE_URL`을 대상으로 이 명령을 실행하세요.

```bash
pnpm migrate:production
```

이 명령은 컨테이너 안이 아니라 앱 폴더에서 실행하세요. 이미지에는 완성된 서버만 들어 있으므로 이미지 자체로는 마이그레이션을 실행할 수 없습니다. 이 명령은 이전 단계에서 export한 환경에서 `DATABASE_URL`을 읽습니다. 앱을 업그레이드한 뒤에는 새 버전을 시작하기 전에 다시 실행하세요.

## 5단계: 배포 {#step-5-deploy}

앱 폴더에서 이미지를 빌드합니다.

```bash
docker build -t my-agent-native-app .
```

`-t` 플래그는 이미지 이름을 `my-agent-native-app`으로 지정합니다. 원하는 이름을 사용해도 되지만, 다음 명령에서도 같은 이름을 사용하세요.

컨테이너를 실행합니다.

```bash
docker run --rm \
  -p 3000:3000 \
  -e DATABASE_URL \
  -e BETTER_AUTH_SECRET \
  my-agent-native-app
```

`-p 3000:3000`은 컨테이너의 포트 `3000`에 서버의 포트 `3000`으로 접속할 수 있게 합니다. 각 `-e` 플래그는 셸에 있는 같은 이름의 변수를 컨테이너에 전달합니다. `BETTER_AUTH_URL`을 설정했다면 명령에 `-e BETTER_AUTH_URL`도 추가하세요. `--rm`은 컨테이너가 중지되면 컨테이너를 삭제합니다.

인터넷에서 앱에 접속하려면 서버 방화벽에서 포트 `3000`을 열거나, Nginx나 Caddy 같은 리버스 프록시를 앞에 두고 도메인을 HTTPS로 제공하세요. 그런 다음 앱의 공개 주소를 열고 첫 계정을 만듭니다.

## 컨테이너 계속 실행하기 {#keep-the-container-running}

위의 `docker run` 명령은 터미널에서 실행되며 터미널을 닫으면 중지됩니다. 앱을 계속 실행하려면 재시작 정책을 지정해 컨테이너를 백그라운드에서 시작하세요. 그러면 충돌이 발생하거나 서버가 재시작된 뒤에 Docker가 컨테이너를 다시 시작합니다. 이렇게 하려면 `--rm`을 `-d --restart unless-stopped`로 바꾸세요. 컨테이너를 실행하는 많은 호스트는 재시작도 대신 처리해 줍니다.
