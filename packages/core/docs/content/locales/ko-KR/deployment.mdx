# 배포

에이전트 네이티브 앱은 내부적으로 [Nitro](https://nitro.build)를 사용합니다. 즉, 구성 변경 없이 모든 플랫폼에 배포할 수 있습니다. 사전 설정만 하면 됩니다.

## 빠른 시작: Chat 앱을 로컬에서 셀프 호스팅하기 {#self-host-quickstart}

시작하는 방법은 두 가지입니다.

- **앱을 만들고 있나요?** [Getting Started](/docs/getting-started)에서 시작하고 앱을 영구적인 곳에 배포할 때 여기로 돌아오세요.
- **앱을 운영하고 있나요?** 먼저 로컬 Docker 경로를 사용하세요. 작은 서버에서 사용할 Node.js, Postgres, 인증 및 환경 변수 구성을 같은 형태로 확인할 수 있습니다.

로컬 스택은 의도적으로 예시 인증 시크릿과 로컬 Postgres 볼륨을 사용합니다. `localhost`용이며 인터넷에 공개하기 위한 것이 아닙니다. 전체 Compose 파일과 복사 가능한 단계는 [영문 빠른 시작](/docs/deployment#self-host-quickstart)을 참조하세요.

### 1. 앱 만들기

```bash
npx @agent-native/core@latest create my-app --template chat
cd my-app
pnpm install
```

### 2. 로컬 스택 시작하기

```bash
docker compose up --build
```

[http://localhost:3000](http://localhost:3000)을 여세요. 포함된 에이전트를 사용하려면 로컬 `.env` 파일에 `ANTHROPIC_API_KEY`를 추가하세요.

## 배포 전: 영구 데이터베이스 선택 {#persistent-database}

배포된 모든 앱에는 영구 SQL 데이터베이스가 필요합니다. 로컬 개발에서 에이전트 네이티브는 `data/app.db`의 SQLite 파일로 대체됩니다. 이는 컴퓨터에서는 편리하지만 파일 시스템을 재설정할 수 있는 컨테이너, 미리 보기 또는 서버리스 환경에서는 내구성이 없습니다.

앱을 프로덕션으로 승격하기 전에 배포 공급자에서 `DATABASE_URL`를 설정하세요. 에이전트 네이티브는 스키마 및 쿼리에 Drizzle를 사용하므로 데이터 계층은 Drizzle 호환 SQL 백엔드 간에 이식 가능하며 프레임워크는 URL에서 방언을 자동 감지합니다. 어댑터 목록 및 방언 세부정보는 [Database](/docs/database#production)를 참조하세요.

Turso/libSQL와 같이 데이터베이스 공급자가 별도의 토큰을 요구하는 경우에만 `DATABASE_AUTH_TOKEN`를 사용하세요. 작업 영역의 경우 모든 앱은 기본적으로 루트 `DATABASE_URL`를 상속합니다. 하나의 앱이 다른 데이터베이스를 사용해야 하는 경우 `<APP_NAME>_DATABASE_URL`를 설정하세요.

## 작업 공간 배포: 하나의 오리진, 다양한 앱 {#workspace-deploy}

프로젝트가 [workspace](/docs/multi-app-workspace)인 경우 다음 명령 하나로 모든 앱을 단일 오리진으로 출시할 수 있습니다.

```bash
npx @agent-native/core@latest deploy
# https://your-agents.com/mail/*       → apps/mail
# https://your-agents.com/calendar/*   → apps/calendar
# https://your-agents.com/forms/*      → apps/forms
```

각 앱은 `APP_BASE_PATH=/<name>` 및 `VITE_APP_BASE_PATH=/<name>`로 빌드된 다음 대상 Nitro 사전 설정용으로 패키징됩니다. Cloudflare Pages는 기본 사전 설정이며 `dist/_worker.js`에서 생성된 디스패처 작업자를 사용합니다. Netlify는 `.netlify/functions-internal/<app>-server`의 앱당 하나의 기능과 생성된 리디렉션을 사용합니다. Vercel은 빌드 출력 API를 사용하여 작업공간 수준 `.vercel/output`를 작성합니다.

동일 출처 배포를 통해 두 가지 큰 이점을 무료로 얻을 수 있습니다.

- **공유 로그인 세션** — 모든 앱에 로그인하면 모든 앱이 로그인됩니다.
- **Zero-config 교차 앱 A2A** — 메일에서 `@calendar`를 태그하는 것은 동일 출처 가져오기입니다. CORS 없음, 형제 간 JWT 서명 없음.

다음을 사용하여 출력 게시:

```bash
wrangler pages deploy dist
```

Netlify 통합 배포의 경우 Netlify 사전 설정을 사용합니다.

```bash
npx @agent-native/core@latest deploy --preset netlify
```

Vercel 통합 배포의 경우 Vercel 사전 설정을 사용하세요.

```bash
npx @agent-native/core@latest deploy --preset vercel
```

공급자 빌드 명령을 구성할 때 `--build-only`와 동일한 명령을 사용하십시오. Vercel은 `npx @agent-native/core@latest deploy --preset vercel --build-only`를 실행해야 합니다. 이 명령은 `.vercel/output`를 직접 작성하므로 작업공간 라우팅에는 `vercel.json`가 필요하지 않습니다.

호스팅 작업공간 빌드에는 배포 공급자 환경에 `A2A_SECRET`가 필요합니다.
이렇게 하면 Slack, 인바운드 webhooks 및 교차 앱 A2A 재개가 서명을 통해 작동됩니다.
백그라운드 프로세서. 로컬 `--build-only` 아티팩트 검사는 그것 없이도 계속 실행됩니다.

앱별 독립 배포는 계속 지원됩니다. 독립 실행형 스캐폴드처럼 `cd apps/<name> && npx @agent-native/core@latest build`만 지원됩니다.

## 프리셋 설정 {#setting-the-preset}

기본적으로 Nitro는 Node.js용으로 빌드됩니다. 다른 플랫폼을 대상으로 하려면 `vite.config.ts`에서 사전 설정을 설정하세요:

```ts
import { agentNative } from "@agent-native/core/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [agentNative({ nitro: { preset: "vercel" } })],
});
```

또는 빌드 시 `NITRO_PRESET` 환경 변수를 사용하세요.

```bash
NITRO_PRESET=netlify npx @agent-native/core@latest build
```

## Node.js(기본값) {#nodejs}

기본 사전 설정입니다. 빌드 및 실행:

```bash
npx @agent-native/core@latest build
node .output/server/index.mjs
```

`PORT`를 설정하여 청취 포트를 구성합니다(기본값: `3000`).

프로덕션 배포에는 현재 Node.js LTS 라인을 사용합니다. 2026년 5월 현재
는 Node.js 24입니다. Node.js 20은 2026년 4월 30일에 수명이 종료되었으며 더 이상
업스트림 보안 업데이트를 받습니다.

### 도커 {#docker}

```dockerfile
FROM node:24-slim AS build
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile
COPY . .
RUN pnpm build

FROM node:24-slim
WORKDIR /app
COPY --from=build /app/.output .output
# data/는 런타임에 생성된 SQLite 디렉터리입니다. dev DB를 prod에 복사하지 마세요.
# 프로덕션의 경우 DATABASE_URL를 호스팅된 Postgres 또는 Turso 인스턴스로 설정합니다.
RUN mkdir -p /app/data
ENV NODE_ENV=production
ENV PORT=3000
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

## 베르셀 {#vercel}

```ts
// vite.config.ts
export default defineConfig({
  plugins: [agentNative({ nitro: { preset: "vercel" } })],
});
```

Vercel CLI 또는 git push를 통해 배포합니다.

```bash
vercel deploy
```

작업공간의 경우 모든 앱을 하나의 Vercel 빌드 출력 API 번들로 빌드합니다.

```bash
npx @agent-native/core@latest deploy --preset vercel
```

Vercel Git 배포의 경우 빌드 명령을 다음과 같이 설정합니다.

```bash
npx @agent-native/core@latest deploy --preset vercel --build-only
```

작업공간 빌드는 각 앱의 Nitro `vercel` 출력을 루트 `.vercel/output`에 복사하고 각 기능에 고유한 마운트 경로 환경을 제공하며 `/<app-id>`에서 앱을 제공하는 경로 구성을 작성합니다.

## 넷티파이 {#netlify}

Nitro `netlify` 사전 설정은 잘 작동하며 실제로 외부 Postgres(Neon)와 통신하는 템플릿의 경우 Cloudflare Pages(~200ms TTFB 대 ~9s)보다 훨씬 빠른 콜드 스타트를 제공합니다. `vite.config.ts`에서 사전 설정을 설정하세요:

```ts
// vite.config.ts
export default defineConfig({
  plugins: [agentNative({ nitro: { preset: "netlify" } })],
});
```

...또는 빌드 시 `NITRO_PRESET=netlify`를 설정하세요.

작업 공간의 경우 다음을 실행하여 하나의 Netlify 사이트에서 모든 앱을 배포하세요.

```bash
npx @agent-native/core@latest deploy --preset netlify
```

작업공간 빌드는 `dist/_workspace_static/` 아래에 정적 자산을 작성하고 강제 자산 리디렉션 없이 각 앱을 자체 Netlify 기능으로 라우팅하므로 서버 기능이 앱 경로를 처리하기 전에 `/mail/assets/...`와 같은 파일이 정적으로 제공됩니다.

### Keep-warm 및 제로 스케일 데이터베이스 {#netlify-keep-warm}

활성화된 경우 Netlify 빌드는 **매분** `/_agent-native/health` 를 요청하는 예약 함수를 생성합니다. 이를 통해 서버 함수와 데이터베이스가 웜 상태로 유지되어, 유휴 기간 후 다음 방문자가 콜드 스타트(Neon에서 1~5초)를 부담하지 않습니다.

Keep-warm은 사용량 과금 제로 스케일 데이터베이스에서 자동 일시 중단을 막기 때문에 **기본적으로 비활성화**됩니다. 다음 방문자의 지연 시간 감소가 데이터베이스 활성 시간의 가치가 있을 때 `AGENT_NATIVE_ENABLE_KEEP_WARM=1` 을 설정하세요.

| 변수                                        | 효과                                                                                                 |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `AGENT_NATIVE_ENABLE_KEEP_WARM`             | 서버와 데이터베이스의 예약 워밍을 활성화합니다. 기본적으로 설정되지 않습니다.                        |
| `AGENT_NATIVE_DISABLE_KEEP_WARM`            | 호환성을 위한 비활성화 스위치이며, 설정되면 옵트인 플래그보다 우선합니다.                            |
| `AGENT_NATIVE_KEEP_WARM_SCHEDULE`           | 활성화된 경우 주기를 재정의합니다. 기본값은 `* * * * *`이며 파싱할 수 없는 값은 빌드를 실패시킵니다. |
| `AGENT_NATIVE_DISABLE_KEEP_WARM_BACKGROUND` | Keep-warm이 활성화된 경우 백그라운드 함수 워밍만 중단하고 서버는 웜 상태로 유지합니다.               |

무료 또는 할당량이 제한된 데이터베이스 등급을 사용한다면 `AGENT_NATIVE_ENABLE_KEEP_WARM` 을 설정하지 마세요. 활성화한다면 더 느린 주기를 선택하거나 `AGENT_NATIVE_DISABLE_KEEP_WARM_BACKGROUND=1` 을 설정하세요.

### 온디맨드 스키마 DDL {#skip-ensure-tables}

각 스토어는 첫 데이터베이스 접촉 시 `ensureTable()` 을 호출해 `information_schema` / `pg_indexes` 를 프로브하고, 실제로 없는 것에 대해서만 `CREATE TABLE` / `ADD COLUMN` / `CREATE INDEX` 를 실행합니다. 오래 사는 Node 서버에서는 이 비용을 부팅당 한 번만 지불하므로 보이지 않습니다. 서버리스에서는 '첫 접촉'이 **모든 콜드 스타트**마다 발생하며 약 57개 스토어에 걸칩니다. 즉 콜드 요청은 실제 작업을 시작하기 전에 수백 번의 직렬 왕복을 지불할 수 있습니다.

이를 줄이는 두 가지가 있습니다:

- 프로브는 테이블·컬럼·인덱스마다 한 번씩 질의하는 대신 **데이터베이스당 한 번의 일괄 인트로스펙션**(두 개의 쿼리)으로 응답됩니다. 자동이며 설정이 필요 없습니다.
- `AGENT_NATIVE_SKIP_ENSURE_TABLES=1` 은 프로브와 DDL 절차를 아예 건너뜁니다. 사용할 수 있는 콜드 스타트 지연 개선 중 가장 큽니다.

데이터베이스 스키마가 이미 마이그레이션되어 있고 애플리케이션 부팅이 테이블을 만들거나 변경하지 않기를 원한다면 `AGENT_NATIVE_SKIP_ENSURE_TABLES=1` 을 설정하세요. 실제 마이그레이션 단계를 갖춘 프로덕션 배포에서는 일반적인 경우입니다.

<Callout tone="risk">

**이 플래그는 안전하게 실패하지 않으며, 그럴 수도 없습니다.** 스키마가 실제로 없다면 첫 실제 쿼리가 즉석에서 복구되는 대신 크게 실패합니다. 그것이 목적이지만, 마이그레이션은 당신의 책임이라는 뜻입니다. 테이블 프로비저닝을 애플리케이션 부팅에 의존하는 배포에는 설정하지 마세요.

</Callout>

## SSR 캐싱 {#ssr-caching}

모든 SSR HTML 응답과 모든 React Router `.data` 응답은 하나의 비개인화된 공개 셸입니다. `createH3SSRHandler`가 렌더링 전에 쿠키를 제거하므로 동일한 바이트가 모든 방문자에게 올바르게 제공되며, 모든 개인화는 로드 후 클라이언트에서 이루어집니다. 이 때문에 이러한 응답에 기본적으로 단일 하드 캐시 정책을 적용해도 안전합니다.

```txt
cache-control: public, max-age=600, stale-while-revalidate=604800, stale-if-error=3600
```

동일한 값이 `cdn-cache-control`과 `netlify-cdn-cache-control`에도 미러링됩니다. 그러면 요청마다 렌더링하는 대신 하나의 공유 CDN 항목이 사이트 전체를 제공하게 되며, 이는 최초 응답 지연 시간을 좌우하는 가장 큰 요인입니다 — 아래 사례 중 하나가 배포에 해당하지 않는 한 켜 둔 상태로 두세요.

### `AGENT_NATIVE_SSR_CACHE`로 재정의하기 {#ssr-cache-env}

배포 환경에서 `AGENT_NATIVE_SSR_CACHE`를 설정하면 배포 전체의 정책을 변경할 수 있습니다.

| 값                                                  | 결과                                                                                         |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| unset, `on`, `default`, `true`, `1`                 | 위의 기본 정책 그대로 유지됩니다. 권장 — 최고의 성능.                                        |
| `off`, `false`, `0`, `none`, `no-store`, `disabled` | `cache-control`, `cdn-cache-control`, `netlify-cdn-cache-control`에 `no-store`를 적용합니다. |
| 기간: `30`, `30s`, `5m`, `2h`                       | `public, max-age=<n>, stale-while-revalidate=<n>, stale-if-error=3600`.                      |

숫자만 있으면 초 단위로 처리됩니다. `stale-while-revalidate`는 커스텀 기간에 대해 의도적으로 `max-age`를 그대로 반영합니다. 짧은 신선도 창에 기본 7일 stale 창을 그대로 두면, 정확히 여러분이 없애려던 그 오래됨이 그대로 돌아오기 때문입니다. 인식할 수 없는 값은 경고를 기록하고 기본값으로 대체되므로, 오타로 인해 CDN이 조용히 비활성화되는 일은 없습니다.

다음 중 하나에 해당하면 캐시를 낮추거나 꺼야 합니다.

1. **호스트가 배포 시 CDN을 퍼지하지 않는 경우.** Netlify와 Vercel은 퍼지하지만, 일부 자체 관리 환경은 그렇지 않습니다. 퍼지가 없으면 배포된 빌드가 `max-age`에 `stale-while-revalidate`를 더한 기간 동안 이전 셸을 계속 제공할 수 있습니다.
2. **로더가 변경 가능한 공개 데이터를 반환하는 경우.** 뮤테이션이 성공한 후 `useRevalidator()` 또는 액션 후 리디렉션에 의한 재요청이 최신 로더 출력 대신 브라우저에 캐시된 `.data` 사본을 읽을 수 있습니다.

이 설정은 모든 공개 셸 서페이스에 적용됩니다: React Router SSR HTML 및 `.data`, 로그인 HTML 셸, `/_agent-native/speculation-rules.json` 경로, 문서 사이트, forms 템플릿의 공개 폼 SSR. 생성된 Cloudflare Worker는 이를 빌드 시점에 해석하므로, 빌드를 실행하기 전에 배포 환경에서 설정하세요.

기억해야 할 세 가지가 있습니다.

- **캐싱을 끈다고 해서 SSR이 개인화되는 것은 아닙니다.** 쿠키는 여전히 렌더링 전에 제거되며 SSR 로더는 여전히 익명 분기를 봅니다. 사용자별 데이터는 여전히 클라이언트 측에서 해결해야 합니다. 이 변수는 캐시 *기간*만 제어합니다.
- **이는 설계상 라우트별이 아니라 배포 전체 설정입니다.** 라우트별 또는 요청별 캐시 재정의는 한 방문자의 페이로드가 다른 방문자의 공유 CDN 항목에 섞여 들어가는 원인이 되므로, 프레임워크는 이를 제공하지 않습니다 — `guard:ssr-cache-shell`이 이를 강제합니다.
- **뮤테이션 직후의 최신 데이터가 필요하면 캐시를 비활성화하는 대신 Actions를 사용하세요.** 앱 데이터는 [Actions](/docs/actions-overview)에 속하며, 클라이언트에서는 `useActionQuery` / `useActionMutation`으로 읽고 `useDbSync()` 폴링으로 최신 상태를 유지합니다. 이 중 어느 것도 SSR 셸 캐시를 거치지 않습니다. SSR 로더는 계속 공개 셸을 렌더링하게 두고, 이 변수는 정말로 로더 데이터를 더 신선하게 만들고 싶을 때만 사용하세요.

### 프로덕션에 민감한 구성 {#env-required-prod}

이 설정은 프로덕션에 민감한 동작을 다룹니다. 프레임워크 인증을 사용하는 독립 앱에는 안정적인 `BETTER_AUTH_SECRET`과 영구 데이터베이스가 필요하며, 공개 auth URL을 설정하지 않으면 요청, 템플릿 또는 호스팅 컨텍스트에서 자동으로 추론합니다. Workspace 및 A2A 설정은 사용하는 기능에 따라 필요합니다. 값이 없으면 안전하게 실패하거나 큰 경고와 함께 더 약한 동작으로 돌아갑니다.

| 변수                                        | 설명                                                                                                                                                                                                                                                    |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BETTER_AUTH_SECRET`                        | 32자 이상의 임의 문자열. 세션 쿠키에 서명하고 `OAUTH_STATE_SECRET` 및 앱 로컬 암호화 값의 fallback입니다. 기존 공유 vault ciphertext의 legacy 읽기 후보이기도 합니다. 프로덕션에서 필수입니다.                                                          |
| `BETTER_AUTH_URL`                           | 이 앱의 공개 출처에 대한 선택적 override(예: `https://mail.example.com`). 설정하지 않으면 요청, 템플릿 및 호스팅 컨텍스트에서 추론합니다.                                                                                                               |
| `ANTHROPIC_API_KEY`                         | 임베디드 프로덕션 에이전트용 API 키입니다. **다중 테넌트 배포**에서 프레임워크는 사용자에게 사용자별 키가 없으면 이 방식으로 대체하는 것을 거부합니다. 즉, 자체 키 가져오기가 필요합니다. 단일 테넌트 자체 호스팅 설치에서는 이를 전역 키로 사용합니다. |
| `OAUTH_STATE_SECRET`                        | OAuth 상태 봉투(Google, Atlassian, Zoom)용 전용 HMAC 키입니다. 설정되지 않은 경우 `BETTER_AUTH_SECRET`로 대체되지만 하나를 회전해도 다른 값이 무효화되지 않도록 전용 값을 사용하는 것이 좋습니다. `openssl rand -hex 32`를 통해 생성합니다.             |
| `A2A_SECRET`                                | 앱 간 A2A JSON-RPC의 공유 HMAC. 전용 워크스페이스 키가 없으면 공유 vault가 이 값에서 용도별로 파생한 키를 사용하므로 이 값의 회전은 vault 키도 회전시킵니다.                                                                                            |
| `WORKSPACE_SECRETS_ENCRYPTION_KEY`          | 공유 워크스페이스 vault에 권장되는 안정적인 AES-256-GCM 키. 읽는 모든 앱에 같은 값을 설정하고 앱별 OAuth 암호화와 분리하세요.                                                                                                                           |
| `WORKSPACE_SECRETS_ENCRYPTION_KEY_PREVIOUS` | 회전 기간에 사용하는 선택적 이전 워크스페이스 키. 새 키와 함께 배포하고 읽기 마이그레이션 후 제거하세요.                                                                                                                                                |
| `SECRETS_ENCRYPTION_KEY`                    | 앱별 암호화와 vault를 위한 기존 결합 키. 계속 지원되지만 새 멀티앱 배포에서는 전용 워크스페이스 키를 사용하세요.                                                                                                                                        |

### 인바운드 Webhooks {#env-webhooks}

각 메시징 통합에는 프로덕션에서 자체 서명 비밀이 필요합니다(비밀이 누락된 경우 위조된 요청에 대해 핸들러가 실패 처리됩니다). 통합별 변수는 [Messaging](/docs/messaging) 및 [Security](/docs/security)에 나열되어 있습니다. 로컬 개발의 경우에만 `AGENT_NATIVE_ALLOW_UNVERIFIED_WEBHOOKS=1`는 "경고 및 승인"을 다시 선택합니다. 프로덕션에서는 절대로 설정하지 마세요.

### 보안 구성(선택) {#security-config}

기본값은 엄격합니다. 몇 가지 옵트인 플래그는 동작을 완화합니다(디버그 스택 추적, 확인되지 않은 webhooks, 작업 공간 범위 키 대체, MCP 허브 다중 조직 스위치, 런타임 env-var 쓰기). [Security](/docs/security)에 보안 절충 사항이 문서화되어 있습니다. 특별히 편안한 경로를 원하지 않는 한 설정하지 마세요.

### 작업공간 .env 상속 {#env-inheritance}

작업 공간 내에서 루트 `.env`는 모든 앱에 자동으로 로드되므로 `ANTHROPIC_API_KEY`, `A2A_SECRET`, `BETTER_AUTH_SECRET` 및 `OAUTH_STATE_SECRET`와 같은 공유 키는 한 번만 설정하면 됩니다. 충돌 시 앱별 `apps/<name>/.env`가 승리합니다.

### 강력한 비밀 생성 {#env-generate-secrets}

"32자 이상의 무작위"로 표시된 비밀(`BETTER_AUTH_SECRET`, `OAUTH_STATE_SECRET`, `A2A_SECRET`, `WORKSPACE_SECRETS_ENCRYPTION_KEY`, `SECRETS_ENCRYPTION_KEY`, `AGENT_NATIVE_BUILDER_RELAY_SECRET`)의 경우 다음을 사용하여 새로운 값을 생성하세요.

```bash
openssl rand -hex 32
```

모든 인스턴스에서 env var를 교체하고 재배포하여 순환합니다. 이전 키로 서명된 세션/OAuth 상태 봉투가 유효하지 않게 되므로 사용자가 다시 로그인해야 할 수도 있습니다.

## 제작 에이전트 도구 {#production-agent-tools}

프로덕션 에이전트는 다음에서 앱에 등록된 actions와 프레임워크 도구를 얻습니다.
상담원 채팅 플러그인. SQL 검사는 기본적으로 활성화되며, 데이터베이스 쓰기는
앱이 raw write tools를 명시적으로 켜지 않는 한 typed app actions를 통해 수행됩니다.

```ts
// server/plugins/agent-chat.ts
export default createAgentChatPlugin({
  frameworkTools: {
    database: "read", // "write" | "read" | "off" — default "read"
    extensions: true, // default false
  },
});
```

```ts
// server/plugins/core-routes.ts
export default createCoreRoutesPlugin({
  extensionTools: true,
});
```

- `database: "read"` — 기본값. `db-schema`와 `db-query`만 등록합니다.
  에이전트는 SQL로 데이터를 검사하지만 쓰기에는 typed app actions를 사용해야 합니다.
- `database: "write"` 또는 `true` — 의도적인 raw SQL 유지보수를 위해
  `db-exec`와 `db-patch`도 등록합니다. 쓰기는 현재 사용자/조직으로 scoped되고
  스키마 변경은 차단됩니다.
- `database: "off"` 또는 `false` — 원시 데이터베이스 도구를 제거합니다.
  에이전트 표면이므로 앱의 actions가 유일한 데이터 액세스 경로입니다.
- `extensions: true` — 앱에서 프레임워크 확장 관리 actions와 안내
  (`create-extension`, `update-extension` 등)를 활성화합니다. 인증된
  REST 생성도 허용하려면 두 plugins 모두에 설정하세요. 확장 프로그램은
  기본적으로 비활성화됩니다.

나머지 그룹은 불리언이며 기본적으로 모두 켜져 있습니다: `sharing`, `review`, `history`, `featureFlags`, `localization`, `audit`, `contextXray`, `userProfile`, `automation`, `docs`, `resources`, `web`, `workspaceApps`, `chat`, `email`.
음성 우선 앱이나 단일 목적 앱에서는 `frameworkTools: "minimal"`로 모든 그룹을
한 번에 끌 수 있고, `frameworkTools: { preset: "minimal", resources: true }`처럼
하나만 남길 수도 있습니다. 명시적인 그룹 키는 항상 프리셋을 이깁니다.

그룹을 끄면 대화형 채팅, MCP, A2A, 백그라운드 실행 같은 **에이전트** 표면에서만
제거됩니다. 해당 HTTP action 라우트는 계속 마운트됩니다. UI가 클라이언트 hooks로
그것들을 호출하기 때문입니다 — `sharing`을 끈다고 해서 화면에 떠 있는 공유
다이얼로그가 404가 되어서는 안 됩니다. 이 패리티 비용을 먼저 따져 보세요.
UI가 할 수 있는 일은 에이전트도 할 수 있다는 것이 프레임워크의 계약이므로,
공유 버튼이 보이는 상태의 `sharing: false`는 의도적인 위반이며 앱에 그 표면이
아예 없을 때만 타당합니다.

이 옵션과 무관하게, 프레임워크 도구는 더 이상 기본으로 첫 모델 요청에
포함되지 않습니다. 검색 가능한 레지스트리에는 남아 있어 `tool-search`로
불러오며, 앱이 `initialToolNames`에 명시하면 즉시 로드됩니다.

<Callout tone="warning">
  최상위 `databaseTools`와 `extensionTools` 옵션은 `frameworkTools.database`와
  `frameworkTools.extensions`로 대체되어 더 이상 권장되지 않습니다. 여전히
  동작하지만, 최상위 플래그와 `frameworkTools`의 동등한 값이 서로 충돌하면
  아무도 선택하지 않은 도구 표면으로 부팅하는 대신 plugin 시작 시 오류가
  발생합니다.
</Callout>

## 생산 코드 실행 {#production-code-execution}

기본적으로 프로덕션 에이전트는 코드 실행 도구 없이 실행됩니다. 앱 actions, 데이터베이스 도구, MCP 도구, 브라우저/세션 도구 및 기타 등록된 프레임워크 도구를 호출할 수 있지만 셸 또는 파일 시스템 액세스 권한은 얻지 못합니다.

노드 호환 배포는 에이전트 채팅 플러그인 또는 환경 재정의를 통해 프로덕션 코드 실행을 선택할 수 있습니다.

```ts
// server/plugins/agent-chat.ts
export default createAgentChatPlugin({
  codeExecution: { production: "sandboxed" },
});
```

사용 가능한 모드는 다음과 같습니다:

- `off` — 기본값입니다. 프로덕션에는 코드 실행 도구가 등록되어 있지 않습니다.
- `sandboxed` — 스크러빙된 환경, 새로운 임시 디렉토리, 출력/시간 제한, `provider-api-request`, `provider-api-docs`, `provider-api-catalog`, `web-request` 및 사용된 리소스 지원 작업 공간 파일 브리지와 같은 허용 목록에 등록된 도구에 대한 로컬 호스트 브리지를 갖춘 격리된 Node.js JavaScript 실행자인 `run-code`를 등록합니다. 작성자: `workspaceRead` / `workspaceWrite`.
- `trusted` — `run-code`와 전체 코딩 도구 레지스트리(`bash`, `read`, `edit`, `write`)를 등록합니다. 호스트에 대한 전체 셸 액세스가 의도적으로 이루어진 단일 테넌트 또는 운영자 제어 배포에만 이 옵션을 사용하세요.

`AGENT_PROD_CODE_EXECUTION=sandboxed` 또는 `AGENT_PROD_CODE_EXECUTION=trusted`를 설정하여 코드 변경 없이 특정 배포에 대한 플러그인 옵션을 재정의합니다. `AGENT_PROD_CODE_EXECUTION=off`는 플러그인 옵션이 활성화된 경우에도 코드 실행을 강제로 중지합니다.

`run-code` 샌드박스는 OS 컨테이너가 아닌 프로세스 수준 격리입니다. 하위 프로세스 환경에서 앱 비밀을 제거하고 가능한 경우 노드 권한 모델을 사용하지만 아웃바운드 네트워크는 노드 자체에 의해 차단되지 않습니다. 인증된 호출은 도구가 노출하는 브리지 도우미를 거쳐야 합니다.

## 프로덕션에서 UI 업데이트 {#updating-ui-in-production}

일반적인 배포 앱 에이전트는 소스에 자동으로 접근하지 않고 actions, 데이터베이스, MCP, 구성된 통합 같은 앱 도구로 작업합니다. 소스 변경은 저장소 개발 워크플로에 속합니다. 임베디드, 로컬 또는 Builder frame은 workspace 및 쓰기 도구를 의도적으로 부여받았을 때 저장소를 편집할 수 있습니다.

[production code execution](#production-code-execution)가 중단된 표준 프로덕션 배포에서 에이전트는 앱 도구(actions, 데이터베이스, MCP)에 액세스할 수 있지만 파일 시스템에는 액세스할 수 없습니다. 즉, 에이전트는 데이터를 읽고 쓰고, actions를 실행하고, 외부 서비스와 상호 작용할 수 있지만 React 구성 요소를 편집하거나 배포된 인스턴스에 새 경로를 추가할 수는 없습니다.

### Builder.io: 프로덕션에서의 시각적 편집 {#builderio}

[Builder.io](https://www.builder.io?utm_source=agent-native&utm_medium=docs&utm_campaign=framework&utm_content=deployment)는 별도의 관리형 코드 지원 워크플로이며 에이전트가 프로덕션 앱 UI를 변경할 수 있습니다. 저장소를 Builder.io(무료 요금제 제공)에 연결하고 UI 변경을 직접 요청할 수 있으며 재배포가 필요하지 않습니다.

**작동 방식:**

1. 에이전트 기본 저장소를 Builder.io(무료 요금제 제공)에 연결
2. Builder.io는 에이전트, 시각적 편집 및 실시간 협업 기능을 갖춘 클라우드 프레임을 제공합니다
3. 에이전트에게 UI 변경을 요청합니다. 구성 요소, 경로 및 스타일을 실시간으로 편집합니다.
4. 변경 사항이 저장소에 다시 커밋됩니다.

내장된 에이전트 패널과 클라우드 프레임 옵션에 대한 자세한 내용은 [Frames](/docs/frames)를 참조하세요.

## 다중 인스턴스 배포 {#multi-instance}

에이전트 네이티브 앱은 Drizzle를 통해 SQL에 모든 상태를 저장하고 [polling](/docs/key-concepts#polling-sync)를 통해 UI를 데이터베이스와 동기화합니다. 파일 시스템 상태, 고정 세션, 메모리 내 캐시가 없습니다. 이는 다중 인스턴스 및 서버리스 배포가 즉시 작동한다는 것을 의미합니다. 모든 인스턴스가 동일한 `DATABASE_URL`를 가리키면 자동으로 수렴됩니다. [Key Concepts — Data in SQL](/docs/key-concepts#data-in-sql) 및 [Portability](/docs/key-concepts#hosting-agnostic)를 참조하세요.
