# 배포

Agent-native 앱은 내부적으로 [Nitro](https://nitro.build)를 사용합니다. 즉, 설정 변경 없이 어떤 플랫폼에도 배포할 수 있습니다. 프리셋만 설정하면 됩니다.

## 배포 전에: 영구 데이터베이스 선택하기 {#persistent-database}

**영구(persistent)** 데이터베이스란 재시작, 재배포, 그리고 둘 이상의 서버 인스턴스에서 동시에 실행되는 상황에서도 데이터가 유지되는 데이터베이스입니다. 배포되는 모든 앱에 필요한 것이 바로 이것입니다.

<Comparison>

### 이전

로컬 개발 환경은 `data/app.db` 경로의 SQLite 파일로 대체됩니다. 이는 로컬 머신에서는 편리하지만, 이 파일은 로컬 파일 시스템에 있으므로 컨테이너, 프리뷰, 서버리스 플랫폼은 언제든 이를 초기화할 수 있습니다.

### 이후

프로덕션에는 재시작, 재배포, 그리고 둘 이상의 인스턴스에서 동시에 실행되는 상황에서도 유지되는 Postgres나 Turso/libSQL 같은 영구 데이터베이스가 필요합니다.

</Comparison>

연결하는 데는 세 단계가 필요합니다:

<Steps>

### 제공업체 선택하기

Postgres 호환 호스트(Neon, Supabase, Railway, RDS 등)나 libSQL/Turso 데이터베이스라면 무엇이든 사용할 수 있습니다. Agent-native는 스키마를 직접 작성한 SQL 대신 타입 안전한 쿼리로 바꿔주는 TypeScript 라이브러리인 [Drizzle](https://orm.drizzle.team)을 통해 읽고 씁니다. 따라서 동일한 앱 코드가 이들 중 어떤 것에 대해서도 그대로 동작합니다.

### 연결 문자열 받기

제공업체는 데이터베이스를 식별하고 접근 방법을 알려주는 URL을 제공합니다. 예를 들면 `postgres://user:pass@host:5432/dbname`과 같습니다.

### `DATABASE_URL` 설정하기

첫 프로덕션 배포 전에 배포 제공업체의 환경 변수에 이를 설정하세요. Agent-native는 이 URL을 읽어 어떤 **dialect**(어떤 기반 데이터베이스 엔진, 즉 Postgres인지 SQLite/libSQL인지)와 통신할지 자동으로 감지합니다. 전체 어댑터 목록은 [Database](/docs/server-database#production)를 참조하세요.

</Steps>

<Callout tone="info">

별도의 토큰으로 인증하는 Turso나 다른 libSQL 제공업체를 사용하시나요? `DATABASE_URL`과 함께 `DATABASE_AUTH_TOKEN`을 설정하세요. 앱이 두 개 이상인 [작업 공간](/docs/multi-app-workspace)을 구축 중이신가요? 모든 앱은 기본적으로 루트 `DATABASE_URL`을 상속합니다. 다른 데이터베이스가 필요한 앱 하나에 대해서만 `<APP_NAME>_DATABASE_URL`을 설정하세요.

</Callout>

### 자동 스키마 설정 {#skip-ensure-tables}

시작하는 데 별도의 마이그레이션 단계는 필요하지 않습니다. 앱의 어떤 부분이든 데이터베이스에 처음 접근할 때, agent-native는 필요한 테이블, 열, 인덱스가 이미 존재하는지 확인하고 없는 것을 생성합니다. 이는 서버가 부팅될 때마다 한 번씩 일어나며, 평소 사용에서는 눈에 띄지 않습니다.

구체적으로, 각 데이터 저장소는 처음 사용될 때 내부 `ensureTable()` 함수를 호출합니다. 이 함수는 데이터베이스 자체의 카탈로그(예를 들어 Postgres의 `information_schema`)를 확인하고, 실제로 없는 것에 대해서만 `CREATE TABLE`, `ADD COLUMN`, `CREATE INDEX`를 실행합니다. 이들은 **DDL** 문으로, Data Definition Language의 줄임말이며 테이블 내부의 행을 읽거나 쓰는 것이 아니라 테이블 자체의 구조를 만드는 SQL 부분입니다.

### 서버리스에서 콜드 스타트 지연 줄이기 {#reducing-cold-start}

장기 실행 서버에서는 이 확인이 부팅당 한 번만 실행되므로 거의 눈치채지 못할 것입니다. 서버리스 플랫폼은 다르게 동작합니다. **콜드 스타트**란 플랫폼이 요청을 처리하기 위해 서버의 완전히 새로운 인스턴스를 띄우는 것을 말하며, 서버리스에서는 "처음 접근"이 대략 57개의 서로 다른 저장소에 걸쳐 매 콜드 스타트마다 발생할 수 있음을 의미합니다. 이는 요청이 실제 작업을 수행하기 전에 수백 번의 왕복으로 누적됩니다.

이를 억제하는 세 가지 장치가 있습니다:

- **일괄 인트로스펙션(Batched introspection).** 테이블, 열, 인덱스마다 하나씩 쿼리를 날리는 대신, 위의 확인 작업은 데이터베이스당 한 번의 인트로스펙션으로 실행되며 총 두 개의 쿼리만 사용합니다. 이는 자동으로 이루어지며 별도 설정이 필요 없습니다.
- **관리형 서버리스에서 자동 건너뛰기.** Netlify Functions, AWS Lambda, Vercel Functions는 모두 프로덕션에서 이 확인을 완전히 건너뛰며, 별도 설정이 필요 없습니다.
- **`AGENT_NATIVE_SKIP_ENSURE_TABLES=1`.** 스키마가 이미 마이그레이션되어 있고 애플리케이션 부팅 시 테이블을 생성하거나 변경하지 않기를 원한다면, 장기 실행 Node 서버, Docker, 또는 다른 자체 호스팅 환경처럼 자동 건너뛰기가 적용되지 않는 배포에 이를 설정하세요.

<Callout tone="risk">

이 플래그도, 자동 서버리스 건너뛰기도 안전한 실패(fail closed) 방식으로 동작하지 않습니다. 테이블이 실제로 없다면, 이를 필요로 하는 첫 실제 쿼리는 조용히 복구되는 대신 눈에 띄게 실패합니다. 이는 의도된 동작입니다(조용한 복구는 실제 마이그레이션 버그를 숨기게 됩니다). 다만 이제부터는 마이그레이션을 직접 책임져야 한다는 뜻입니다. 애플리케이션 부팅이 자체 테이블을 생성하는 데 의존하는 배포에서는 이 플래그를 설정하지 말고 자동 건너뛰기에 의존하지도 마세요.

</Callout>

여러 앱을 하나의 오리진에 배포하거나 Docker Compose로 작업 공간을 자체 호스팅하는
방법은 별도 페이지에서 다룹니다.
[Workspace Deployment](/docs/workspace-deployment)를 참조하세요.

## 프리셋 설정하기 {#setting-the-preset}

기본적으로 Nitro는 Node.js용으로 빌드합니다. 다른 플랫폼을 대상으로 하려면 `vite.config.ts`에서 프리셋을 설정하세요:

```ts
import { agentNative } from "@agent-native/core/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [agentNative({ nitro: { preset: "vercel" } })],
});
```

또는 빌드 시점에 `NITRO_PRESET` 환경 변수를 사용하세요:

```bash
NITRO_PRESET=netlify npx @agent-native/core@latest build
```

플랫폼별 빌드 및 배포 세부 정보는 해당 페이지를 참조하세요:

- [**Node.js & Docker**](/docs/node-docker) — 기본 프리셋과 독립형 Dockerfile
- [**Vercel**](/docs/vercel)
- [**Netlify**](/docs/netlify) — scale-to-zero 데이터베이스를 위한 keep-warm 포함
- [**Cloudflare**](/docs/cloudflare) — Pages 및 Workers
- [**Other Platforms**](/docs/other-platforms) — AWS Lambda 및 Deno Deploy

기본 SSR 셸 캐시 정책과 `AGENT_NATIVE_SSR_CACHE`로 이를 재정의하는 방법은
별도 페이지에서 다룹니다. [SSR Caching](/docs/ssr-caching)을 참조하세요.

전체 프로덕션 환경 변수 참조(빌드/런타임, 필수 시크릿, 인증, 웹훅, 보안
옵트인, 작업 공간 `.env` 상속, 강력한 시크릿 생성 방법)는 별도 페이지에서
다룹니다. [Deployment: Environment Variables](/docs/deployment-environment-variables)를 참조하세요.

배포된 프로덕션 에이전트가 `frameworkTools`와 `codeExecution`을 통해 어떤
프레임워크 도구와 코드 실행 기능을 갖는지는 별도 페이지에서 다룹니다.
[Production Agent Access](/docs/actions-agent-tools)를 참조하세요.

배포된 앱의 UI가 출시 후 어떻게 업데이트되는지, 그리고 프로덕션에서의 시각적
편집을 위한 Builder.io의 별도 관리형 워크플로를 포함해 이는 별도 페이지에서
다룹니다. [Updating UI in Production](/docs/updating-ui-in-production)을 참조하세요.

## 다중 인스턴스 배포 {#multi-instance}

Agent-native 앱은 Drizzle을 통해 모든 상태를 SQL에 저장하고, 데이터베이스에 대한 [폴링](/docs/key-concepts#polling-sync)을 통해 UI를 동기화합니다. 파일 시스템 상태도, 스티키 세션도, 인메모리 캐시도 없습니다. 즉, 다중 인스턴스와 서버리스 배포는 별도 설정 없이 바로 동작합니다. 모든 인스턴스를 동일한 `DATABASE_URL`로 지정하면 자동으로 수렴됩니다. [Key Concepts — Data in SQL](/docs/key-concepts#data-in-sql)과 [Portability](/docs/key-concepts#hosting-agnostic)를 참조하세요.
