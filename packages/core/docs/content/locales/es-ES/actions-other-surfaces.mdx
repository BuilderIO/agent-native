# Otras superficies

La superficie de hooks de UI se cubre en [Datos y sincronización](/docs/client-data): `useActionQuery()`, `useActionMutation()` y `callAction()`. Esta página cubre todo lo demás que puede llamar a una acción, o ser impulsado por ella.

## Renderizar UI de chat nativa {#native-chat-ui}

Las acciones pueden devolver datos de widget estructurados que el chat dentro de la
app renderiza de forma nativa. Esta es la ruta de chat de primera parte para tablas
reutilizables, gráficos, resúmenes de configuración y tarjetas de insights. Usa
[UI generativa](/docs/generative-ui) cuando el agente necesite generar controles
interactivos arbitrarios dentro del chat de la app, y usa [Aplicaciones MCP](/docs/mcp-apps)
para UI en línea en hosts MCP externos.

```ts
import { defineAction } from "@agent-native/core/action";
import { ACTION_CHAT_UI_DATA_CHART_RENDERER } from "@agent-native/core/action-ui";
import {
  createDataChartWidgetResult,
  dataChartWidgetResultSchema,
} from "@agent-native/core/data-widgets";

export default defineAction({
  description: "Summarize response trends.",
  readOnly: true,
  outputSchema: dataChartWidgetResultSchema,
  chatUI: { renderer: ACTION_CHAT_UI_DATA_CHART_RENDERER },
  run: async () =>
    createDataChartWidgetResult({
      title: "Response trends",
      chartSeries: {
        type: "line",
        xKey: "day",
        series: [{ key: "responses", label: "Responses" }],
        data: [
          { day: "Mon", responses: 12 },
          { day: "Tue", responses: 18 },
        ],
      },
    }),
});
```

Los discriminantes integrados son `"data-table"`, `"data-chart"` y
`"data-insights"`, con constructores y esquemas seguros para el servidor en
`@agent-native/core/data-widgets`. Usa `data-chart` para respuestas que son solo
un gráfico, `data-table` para resultados de SQL/listas, y `data-insights` solo
cuando la salida correcta es una tarjeta combinada de resumen/gráfico/tabla. Consulta
[Chat nativo UI](/docs/native-chat-ui) para el contrato completo de resultado, o
[Runtimes de agente propios](/docs/native-chat-ui#byo-agent-runtimes) si estás
conectando un runtime de agente personalizado en lugar del bucle de chat
integrado. Consulta [Superficies del agente](/docs/agent-surfaces) para ver cómo
la misma acción puede seguir siendo compatible con automatizaciones, renderizarse
en el chat, o crecer hasta convertirse en una pantalla completa.

## Llamarla desde la CLI {#cli}

Toda acción se puede ejecutar mediante `pnpm action`:

```bash
pnpm action reply-to-email '{"emailId":"thread-123","body":"Thanks!"}'
```

La entrada JSON es la forma preferida para agentes y objetos complejos. Los flags
funcionan igual para ejecuciones manuales simples y scripts existentes:

```bash
pnpm action reply-to-email --emailId thread-123 --body "Thanks!"
```

Para las llamadas a `defineAction()`, la CLI evalúa `needsApproval` sobre los argumentos preparados y analizados, con los valores predeterminados del esquema y caller `cli`. Si stdin y stdout son TTY, muestra el nombre de la acción y los argumentos y pregunta `y/N`. Solo `y` o `yes` ejecuta la acción.

Sin ambos TTY, la CLI indica al agente que pida aprobación a la persona. Cuando esta apruebe esa llamada concreta, repite exactamente los argumentos originales de `pnpm action` añadiendo `--approved`:

```bash
pnpm action reply-to-email --emailId thread-123 --body "Thanks!" --approved
```

`--approved` son metadatos reservados de la CLI y se elimina antes de analizar la entrada. No tiene efecto adverso en acciones sin aprobación obligatoria. La CLI no puede comprobar quién lo añadió: un agente que lo añade sin preguntar se salta la confirmación. El indicador deja la aprobación a la vista en el comando que la persona aprueba y en el registro de auditoría, que la señala como no verificada. En Windows sin una `SHELL` POSIX, el rechazo muestra el comando para PowerShell y, si las comillas difieren, también para cmd.exe. En Windows, pnpm pasa los argumentos de la acción por cmd.exe desde cualquier shell, y cmd.exe expande `%NAME%` incluso entre comillas. Si un argumento contiene una variable así, el rechazo no ofrece repetir el comando con `--approved`: la persona ejecuta el comando en una terminal y comprueba los valores en la confirmación.

El puente local de desarrollo envía los metadatos de aprobación fuera de `input` en el cuerpo JSON:

```ts
{ name, input, approved: true, approvalSource: "flag" }
```

Para una llamada protegida sin aprobación, el puente devuelve HTTP `409`:

```ts
{
  ok: false,
  errorCode: "approval_required",
  error: 'Action "<name>" requires human approval. Ask the person, then rerun with --approved.',
  arguments: preparedArgs,
  argumentsHash: prepared.argumentsHash,
}
```

Tras la confirmación en TTY, la CLI reintenta con el `argumentsHash` de la respuesta que solicita aprobación:

```ts
{
  name,
  input,
  approved: true,
  approvalSource: "prompt",
  approvalArgumentsHash: challenge.argumentsHash,
}
```

El puente ejecuta una sola vez la llamada que la persona revisó, así que un valor predeterminado que cambia en cada llamada, como una marca de tiempo, conserva el valor que vio. Una confirmación sin llamada retenida que ejecutar (ya se ejecutó, pasaron 10 minutos o el servidor de desarrollo se reinició) recibe HTTP `409` con `errorCode: "approval_expired"`. Vuelve a ejecutar el comando para revisarla.

`arguments` contiene los argumentos preparados. Este contrato del puente local de desarrollo no cambia las [reglas de aprobación de la API HTTP pública de acciones](/docs/actions-access-control#needs-approval). Una llamada CLI protegida y aprobada registra `approval: "cli-prompt"` o `approval: "cli-flag"` en la propia fila de auditoría de la acción, con caller `cli`. El registro de auditoría muestra ambos como no verificados, porque solo la CLI ve la confirmación.

## Llamarla desde otro agente (A2A) {#a2a}

Si tu app es un par [A2A](/docs/a2a-protocol), otras apps nativas del agente descubren tus acciones automáticamente y pueden llamarlas por nombre. Los despliegues del mismo origen se saltan la firma JWT. Los despliegues de origen cruzado usan en su lugar un `A2A_SECRET` compartido.

## Exponerla mediante MCP {#mcp}

Con MCP activado, tus acciones aparecen en el servidor MCP del framework en `/mcp`. Cada invocador recibe por defecto un catálogo compacto (integraciones orientadas a la app más las acciones de app declaradas por la plantilla), y `tool-search` siempre está presente para que cualquier otra herramienta se pueda alcanzar bajo demanda. La superficie completa de acciones solo se sirve con inclusión explícita (token `--full-catalog` o `AGENT_NATIVE_MCP_FULL_CATALOG=1`), y [`publicAgent.expose`](/docs/actions-access-control#public-agent) incluye una herramienta segura de lectura/ingesta en la superficie pública. Consulta [Protocolo MCP](/docs/mcp-protocol) para los niveles de catálogo, la autenticación y los detalles del recurso `mcpApp`.

Para hosts MCP capaces de mostrar UI, una acción puede declarar un recurso opcional de Aplicaciones MCP mediante el campo `mcpApp` (más un `link` a juego) para que los hosts compatibles rendericen el resultado en línea. Cuando `link` y `mcpApp` deben apuntar a la misma ruta, `embedRoute()` construye ambos a partir de un único constructor de ruta puro:

```ts
import { embedRoute } from "@agent-native/core";

export default defineAction({
  description: "Create an email draft for review.",
  schema: z.object({ body: z.string() }),
  run: async ({ body }) => ({ body }),
  ...embedRoute({
    title: "Review draft",
    openLabel: "Open in Mail",
    path: ({ result }) => ({
      label: "Open draft in Mail",
      url: "/_agent-native/open?app=mail&view=inbox",
    }),
  }),
});
```

Mantén `link` como el respaldo para la CLI y para hosts MCP sin UI. También es el destino de lanzamiento de la incrustación. El puente de incrustación (la sesión firmada de embed-start, el renderizado transplant frente a controlled-frame, el puente de host `ui/*`, la CSP y el ajuste de altura) pertenece a [Agentes externos](/docs/external-agents#mcp-app-bridge).

No existe una comprobación automática de que una plantilla tenga `view-screen`, `navigate`, o un conjunto de create/read/update/list para su recurso principal; el scaffold incluye `view-screen` y `navigate`, y `pnpm guard:external-result-contract` rechaza el lenguaje de "esperar a que el usuario" en el `description` o `nextRequiredAction` de una acción expuesta externamente, y exige un enlace profundo en una nueva acción `create-*` expuesta externamente. Su presencia es un punto de revisión.

## Acciones estándar {#standard-actions}

Toda plantilla debería incluir estas dos para la [conciencia del contexto](/docs/context-awareness).

### view-screen {#view-screen}

Lee el estado de navegación actual, obtiene datos contextuales y devuelve una instantánea de lo que ve el usuario. El agente la llama cuando necesita una vista actualizada de la pantalla.

```ts
// actions/view-screen.ts
import { defineAction } from "@agent-native/core/action";
import { readAppState } from "@agent-native/core/application-state";
import { z } from "zod";

export default defineAction({
  description: "Read the current screen state for context.",
  schema: z.object({}),
  http: { method: "GET" },
  run: async () => {
    const navigation = await readAppState("navigation");
    const screen: Record<string, unknown> = { navigation };

    if (navigation?.view === "inbox") {
      screen.emailList = await listEmailsForLabel(navigation.label);
    }

    return screen;
  },
});
```

### navigate {#navigate}

Escribe un comando de navegación de un solo uso en el estado de la aplicación. La UI lo lee, navega y elimina la entrada.

```ts
// actions/navigate.ts
import { defineAction } from "@agent-native/core/action";
import { writeAppState } from "@agent-native/core/application-state";
import { z } from "zod";

export default defineAction({
  description: "Navigate the user to a view.",
  schema: z.object({
    view: z.string(),
    threadId: z.string().optional(),
  }),
  run: async (args) => {
    await writeAppState("navigate", args);
    return { ok: true };
  },
});
```
