# Guía para desarrolladores

Esta página es para cualquiera que personalice la plantilla de Design o
construya directamente sobre ella: el inicio rápido, todas las acciones, el
modelo de datos, un recorrido por una acción, la superficie de rutas y cómo
añadir a ella. Consulta [Design](/docs/template-design) para saber qué hace
la app.

## Inicio rápido

<Steps>

### Crea la app

```bash
npx @agent-native/core@latest create my-design --standalone --template design
cd my-design
pnpm install
```

Esto necesita [Node.js](https://nodejs.org) 22.22 o posterior y
[pnpm](https://pnpm.io) instalados primero. Consulta [Primeros
pasos](/docs/getting-started) si todavía no tienes ninguno de los dos
instalado, o no tienes configurada una conexión LLM (Builder.io, una clave
de Anthropic/OpenAI, o Ollama local). Para un espacio de trabajo con Design
junto a otras apps, ejecuta `npx @agent-native/core@latest create
my-platform` y elige Design durante la configuración en su lugar.

### Inicia el servidor de desarrollo

```bash
pnpm dev
```

La app se abre en `http://localhost:8099`, el puerto de desarrollo
predeterminado de Design. Design funciona por completo sin conexiones
externas. Solo te encontrarás con un aviso de conexión si intentas una
importación de Figma o Full App Building antes de configurarlos.

</Steps>

## Modelo de datos

Todos los datos residen en SQL a través de Drizzle ORM. Esquema: `templates/design/server/db/schema.ts`. Los diseños y los sistemas de diseño llevan el `ownableColumns` estándar y una tabla de recursos compartidos del framework correspondiente, por lo que encajan en el modelo de uso compartido por usuario/por organización.

La siguiente tabla cubre los recursos propios principales: diseños, archivos, plantillas, versiones y sistemas de diseño.

| Tabla                                    | Qué contiene                                                                                                                                         |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `designs`                                | Un proyecto de diseño — `title`, `description`, `project_type` (`prototype` / `other`), el blob JSON `data`, y un enlace `design_system_id` opcional |
| `design_files`                           | Archivos individuales que pertenecen a un diseño (`filename`, `content`, `file_type` con valor por defecto `html`)                                   |
| `design_templates`                       | Metadatos de plantilla reutilizables, dimensiones, valores predeterminados, referencia al diseño de origen y recuento de capas bloqueadas            |
| `design_template_files`                  | Archivos de plantilla en forma de instantánea, copiados a un diseño normal y editable cuando un usuario empieza desde una plantilla                  |
| `design_template_shares`                 | Tabla de recursos compartidos del framework para el descubrimiento de plantillas privadas, de organización, compartidas explícitamente y públicas    |
| `design_versions`                        | `snapshot`s puntuales de un diseño con un `label` opcional, para historial y reversión                                                               |
| `design_systems`                         | Tokens de marca reutilizables — `data` (colores/tipografía/espaciado), `assets`, `custom_instructions`, y una bandera `is_default`                   |
| `design_shares` / `design_system_shares` | Tablas de recursos compartidos del framework que asignan principales (usuarios u organizaciones) a roles (lector, editor, administrador)             |

Un proyecto de diseño es un shell hasta que tiene contenido: `create-design` crea una fila vacía (`data: "{}"`), luego `generate-design` escribe los archivos HTML/JSX independientes reales. El artefacto generado, la fuente editable y cada exportación provienen todos del mismo HTML, así que no existe un formato de "maqueta de IA" aparte que traducir. Un sistema de diseño vinculado proporciona tokens y `custom_instructions` que el agente respeta en cada paso de generación.

Otras siete tablas respaldan funciones cubiertas en otras partes de esta página en lugar del modelo de recursos principal: `design_localhost_connections` y `design_localhost_write_grants` respaldan la [importación de app local](/docs/template-design-features#import), `component_index` respalda la [sección Componente de la pestaña Design](/docs/template-design-features#design-tab), `motion_timeline` respalda la línea de tiempo de movimiento editable de cada elemento (el panel de movimiento en el editor), `design_state` guarda estados alternativos con nombre, fixtures estáticos y capturas de apps en vivo para un diseño, `design_fusion_edits` respalda la cola de ediciones de fusion descrita en [Full App Building](#full-app-building) más arriba, y `design_review_snapshot` almacena en caché los hallazgos de accesibilidad y la diferencia visual detrás de `get-design-review`, descrita en [Calidad](#quality) más arriba.

Los comentarios y hilos de revisión persistidos (`get-review-feedback`, `resolve-review-thread`, y el resto) no son en absoluto una tabla específica de Design: son el sistema de revisión compartido del framework de `@agent-native/core/review` (`agent_review_comments` / `agent_review_statuses`), delimitado a un diseño de la misma forma en que puede adjuntarlo cualquier app. Consulta la [pestaña Comentarios](/docs/template-design-features#comments-tab) para ver el comportamiento de cara al usuario.

## Un recorrido por una acción

`save-design-as-template` muestra patrones que vale la pena reutilizar en cualquier acción: rechazar una forma de entrada no compatible antes de hacer cualquier trabajo, protegerse contra guardar nada, remapear ids una sola vez en lugar de en cada lector, y escribir en dos tablas dentro de una transacción para que una plantilla nunca pueda terminar con metadatos pero sin archivos.

## Modelo del editor

Design prioriza la vista general para el trabajo con varias pantallas.
Después de la generación o de actualizaciones amplias, el editor abre la
vista general de pantallas: un lienzo infinito donde cada pantalla es un
marco estático que puedes seleccionar, mover, redimensionar, soltar o
duplicar. Usa el botón de vista completa de un marco cuando una pantalla
necesite desplazamiento enfocado o interacción de prototipo.

El modo de una sola pantalla sirve para desplazarse, interactuar con el
comportamiento del prototipo y editar las capas de DOM/código dentro de un
archivo renderizado. El panel de capas refleja esa división: las pantallas
son marcos de nivel superior, con capas de DOM/código anidadas para la
pantalla activa.

Cada pantalla es un único documento renderizado a diferentes anchos, no
copias separadas por punto de quiebre: un marco base (el más ancho) se
propaga hacia abajo, y las ediciones hechas en un punto de quiebre activo
más estrecho persisten como anulaciones acotadas a ese ancho, por encima de
él.

## Extensiones del editor

El editor incluye una pestaña de inspector **Extensiones** después de
**Tweaks**. Funciona como un carril de plugins específico de Design: los
usuarios pueden hacer clic en **+ Extensión** para pedirle al agente que
construya una extensión, o instalar una extensión que declare el espacio
`design.editor.inspector`, usando las acciones del framework
`create-extension`, `add-extension-slot-target` e `install-extension`, no
una acción específica de Design.

Las extensiones de Design se renderizan en línea junto al artboard mediante
el sandbox estándar de extensiones. El host pasa actualizaciones de
`window.slotContext` y `window.onSlotContext(...)` con el `designId` actual,
el archivo activo, la lista de pantallas, los ids de pantalla seleccionados,
los metadatos del elemento seleccionado, el modo de vista, el zoom, la
herramienta activa y los valores de tweaks. Eso permite que una extensión
muestre información sobre la selección actual, ofrezca controles de estilo o
construya flujos de trabajo compactos alrededor del diseño abierto.

Para trabajo determinista, las extensiones pueden llamar a acciones de la
app a través del puente de extensiones. Para cambios impulsados por IA, haz
que la extensión llame a `agentNative.chat.send(...)` con el selector/id de
origen del elemento seleccionado y el cambio solicitado. El agente debe
llamar primero a `view-screen`, y luego usar `apply-visual-edit` para
cambios de estilo, clase, texto o movimiento de un elemento, o
`update-design` / `generate-design` con `canvasFrames` para cambios de
colocación en el artboard. Consulta [Extensiones](/docs/extensions#capabilities)
para el sandbox, el estado persistente y las APIs del puente.

## Personalizándola

Design es una plantilla completa y clonable. Algunas ideas prácticas de
extensión:

- "Añade un sistema de diseño de ecommerce reutilizable con nuestros tokens y componentes de muestra."
- "Añade un paso de exportación que suba el ZIP a nuestro sistema de revisión interno."
- "Déjame pegar el HTML existente de una página de destino y pedirle al agente tres versiones más sólidas."
- "Añade una biblioteca de peticiones guardadas para briefs de página de producto, panel y pantalla de incorporación."
- "Añade un preajuste de exportación PDF personalizado para la revisión de las partes interesadas."

El agente edita rutas, componentes, acciones y modelos respaldados por SQL
según sea necesario. Consulta [Plantillas](/docs/cloneable-saas) para ver el
flujo completo de clonar, personalizar y desplegar, y [Primeros
pasos](/docs/getting-started) si esta es tu primera plantilla nativa del
agente.
