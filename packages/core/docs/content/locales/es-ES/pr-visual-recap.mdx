# Resumen visual de PR

Resumen visual de PR es una GitHub Action que convierte cada pull request en una
**revisión de código visual**, sin que nadie tenga que acordarse de ejecutar un comando a
mano. Esta página es para quien instale, configure o proteja esa Action. En cada push, un
agente de codificación LLM ejecuta la skill [`visual-recap`](/docs/template-plan) incluida
más reciente (o la copia confirmada de tu repositorio cuando `VISUAL_RECAP_SKILL_SOURCE=repo`)
contra el diff del PR, publica un plan de resumen estructurado en la app Plans alojada,
muestra una verificación informativa `Visual Recap` mientras se ejecuta, y hace upsert de
**un único comentario fijo en el PR** que enlaza al plan interactivo con una **captura de
pantalla en línea** incrustada directamente en el comentario.

Esto no es un renderizador de diff determinista. La action invoca un agente de codificación
real (Claude Code CLI de forma predeterminada, OpenAI Codex CLI, o Agent-Native Code con un
proveedor compatible con OpenAI) que lee el cambio, decide qué importa y redacta el resumen
llamando a la herramienta de Plans MCP `create-visual-recap` — la misma herramienta que usa
el comando de barra diagonal `/visual-recap`. Obtienes una vista de alto nivel, de
esquema/API/antes-después del cambio, en lugar de un muro de diff sin formato.

El resumen es **informativo y no bloqueante**. Crea una fila de verificación para que los revisores puedan ver que la generación está en curso, pero no es una verificación obligatoria, nunca bloquea el PR y nunca sustituye la lectura del diff real. El comentario fijo es una ayuda para la revisión, no una aprobación.

## Qué hace

En cada push al PR, el flujo de trabajo:

1. Recopila un diff acotado entre la base y el head del PR.
2. Crea una verificación informativa `Visual Recap` de GitHub con `Visual recap in progress`.
3. Ejecuta el agente de codificación configurado contra ese diff. El agente lee las indicaciones de la skill `visual-recap` incluida (o tu copia fijada en el repositorio) y redacta un resumen, publicándolo con `create-visual-recap`.
4. Lee la URL del plan publicado que el agente escribió en `recap-url.txt`.
5. Abre esa URL en Chrome sin interfaz y captura el plan renderizado en modo claro y oscuro.
6. Sube los PNG a una ruta de imágenes públicas firmada en la app Plans.
7. Hace upsert de un único comentario fijo en el PR que incrusta las capturas de pantalla **en línea** con un elemento `<picture>` (servido a través del proxy de imágenes camo de GitHub) junto al enlace al resumen interactivo.
8. Completa la verificación `Visual Recap` como success, skipped o neutral.

## Instalarla

Cuando instalas Plans de forma interactiva, la CLI de Agent-Native pregunta si quieres añadir
Resúmenes visuales de PR automáticos. Responde que sí para escribir la GitHub Action, o
añádela explícitamente en cualquier momento:

```bash
npx @agent-native/core@latest skills add visual-plan --with-github-action
```

Esto instala la skill `visual-plan` (que incluye la skill `visual-recap` que ejecuta la action) y escribe `.github/workflows/pr-visual-recap.yml` en tu repositorio. El flujo de trabajo llama a **subcomandos de CLI publicados** mediante `npx @agent-native/recap-cli@latest recap <subcommand>` — incluidos `gate`, `collect-diff`, `block-reference`, `scan`, `build-prompt`, `publish`, `shot`, `comment`, `check` y `usage` — de modo que no se copia nada en tu repositorio como scripts auxiliares. `setup` y `doctor` son los ayudantes interactivos que ejecutas localmente; `gate` es el paso de barrera de seguridad que ejecuta el flujo de trabajo antes de cada resumen.

Luego ejecuta el ayudante de configuración guiada:

```bash
npx @agent-native/recap-cli@latest recap setup
npx @agent-native/recap-cli@latest recap doctor
```

`recap setup` actualiza el flujo de trabajo, usa `gh` para establecer los secrets/variables
de GitHub Actions cuando los valores están disponibles desde el entorno o desde el almacén
local de tokens de publicación de Plans, e imprime los comandos exactos que faltan para todo
lo que no puede establecer. Los valores de los secrets se envían a `gh` mediante stdin, no
como argumentos de comando. Confirma el archivo de flujo de trabajo generado y abre un PR
para verlo en ejecución.

De forma predeterminada, el flujo de trabajo construye su prompt de agente a partir de las
indicaciones incluidas más recientes de `visual-recap` en `@agent-native/recap-cli@latest`,
incluidos los archivos de referencia hermanos con los que se distribuye la skill. Si tu
repositorio personaliza y fija intencionadamente su carpeta `visual-recap` confirmada,
establece la variable de repositorio `VISUAL_RECAP_SKILL_SOURCE=repo`.

## Selección de ejecutor

El flujo de trabajo se ejecuta en ejecutores `ubuntu-latest` alojados por GitHub de forma
predeterminada. Para usar un ejecutor alojado diferente o tu propio ejecutor autoalojado,
establece la variable de repositorio u organización `VISUAL_RECAP_RUNS_ON` con una cadena
JSON válida o un array JSON de etiquetas de ejecutor:

```text
"ubuntu-latest"
["self-hosted", "linux", "x64", "visual-recap"]
```

Las comillas JSON son obligatorias. Este ajuste selecciona el ejecutor del job `recap`
completo. Para configurarlo durante la configuración guiada, pasa el mismo valor JSON a
`--runs-on`, y después valida el flujo de trabajo y la disponibilidad del ejecutor con
`doctor`:

```bash
npx @agent-native/recap-cli@latest recap setup --runs-on '["self-hosted","linux","x64","visual-recap"]'
npx @agent-native/recap-cli@latest recap doctor
```

La barrera de seguridad ligera usa por separado, de forma predeterminada, `ubuntu-latest`
alojado por GitHub. Los repositorios que desactivan los ejecutores alojados por GitHub pueden
establecer `VISUAL_RECAP_GATE_RUNS_ON` con **una única etiqueta de ejecutor sencilla** (no
JSON), o pasar `--gate-runs-on visual-recap-gate` durante la configuración. El flujo de
trabajo reutilizable expone el mismo valor como su input `gate-runs-on`. Esto evita tener que
analizar JSON dinámico antes de que GitHub pueda programar la barrera. La etiqueta
personalizada solo se selecciona para PR del mismo repositorio creados por un `OWNER`,
`MEMBER` o `COLLABORATOR`. Los forks y el resto de autores se fuerzan a `ubuntu-latest`
alojado por GitHub antes de que el job empiece; en un repositorio exclusivamente autoalojado,
esas ejecuciones no confiables pueden quedar sin programar en lugar de tocar una máquina
autoalojada.

`recap doctor` rechaza JSON con formato incorrecto o no compatible, e informa cuando GitHub
no expone ningún ejecutor en línea que coincida con todas las etiquetas configuradas. El
registro, la instalación, las actualizaciones, la capacidad y el mantenimiento del ejecutor
siguen siendo tu responsabilidad; Agent-Native selecciona las etiquetas, pero no proporciona
ni opera el ejecutor.

**Seguridad:** prefiere ejecutores autoalojados dedicados y efímeros. Un ejecutor de barrera
personalizado solo recibe eventos de PR de confianza del mismo repositorio. La barrera
estándar no descarga el árbol del PR; evalúa la lógica del flujo de trabajo y los metadatos
del PR de GitHub. Una máquina persistente sigue conservando el estado de los procesos entre
jobs, así que no la compartas con cargas de trabajo no relacionadas. El flujo de trabajo
falla de forma cerrada antes de despachar cualquier barrera autoalojada o job de resumen
completo para autores de PR públicos o de fork no confiables. No debilites ese límite ni
dirijas contribuciones no confiables a un ejecutor persistente.

## Selección de backend

Elige qué agente de codificación ejecuta la skill con la variable de repositorio `VISUAL_RECAP_AGENT`:

| `VISUAL_RECAP_AGENT` | Agente de codificación                   | Clave de API necesaria | Variables necesarias                          |
| --------------------- | ---------------------------------------- | ----------------------- | ---------------------------------------------- |
| `claude` _(predeterminado)_ | Claude Code CLI                    | `ANTHROPIC_API_KEY`     | —                                              |
| `codex`               | OpenAI Codex CLI                         | `OPENAI_API_KEY`        | —                                              |
| `openai-compatible`   | Agent-Native Code + proveedor compatible | `VISUAL_RECAP_API_KEY`  | `VISUAL_RECAP_BASE_URL`, `VISUAL_RECAP_MODEL` |

Si la variable no está definida, la action usa `claude`.

## Modelo y razonamiento

Más allá del backend, estas variables de repositorio ajustan cómo se ejecuta el agente:

- **`VISUAL_RECAP_MODEL`** fija el modelo que se pasa a la CLI (`--model`) — por ejemplo, `gpt-5.6-luna` para Codex, un id de modelo de Claude, o `deepseek-chat` para DeepSeek. Es obligatoria para `openai-compatible`. Para el backend **Claude**, dejarla sin definir ahora usa por defecto `claude-sonnet-5`; establece la variable explícitamente para usar un modelo de Claude diferente, como el más económico `claude-haiku-4-5`. Para el backend **Codex**, dejarla sin definir usa el propio modelo predeterminado de la CLI de Codex.
- **`VISUAL_RECAP_REASONING`** establece la profundidad de razonamiento: `none`, `minimal`, `low`, `medium`, `high` o `xhigh`. Se aplica al backend Codex; el razonamiento de Claude depende del modelo, así que esta variable se ignora allí.
- **`VISUAL_RECAP_BASE_URL`** selecciona la URL base HTTP(S) para el backend `openai-compatible`. Usa el endpoint compatible con OpenAI del proveedor, como DeepSeek o Kimi, sin incrustar credenciales en la URL.
- **`VISUAL_RECAP_SKILL_SOURCE`** controla la actualidad del prompt: `auto`/sin definir usa las indicaciones de la skill incluida más recientes, mientras que `repo` fija la carpeta local del repositorio con la skill `visual-recap` confirmada.

Por ejemplo, para ejecutar el resumen en Codex con GPT-5.6 Sol con razonamiento alto, establece las variables de repositorio `VISUAL_RECAP_AGENT=codex`, `VISUAL_RECAP_MODEL=gpt-5.6-sol` y `VISUAL_RECAP_REASONING=high`.

Para DeepSeek, establece `VISUAL_RECAP_AGENT=openai-compatible`, `VISUAL_RECAP_BASE_URL=https://api.deepseek.com/v1`, `VISUAL_RECAP_MODEL=deepseek-chat`, y el secret `VISUAL_RECAP_API_KEY`. Kimi funciona de la misma manera con su URL base y su id de modelo compatibles con OpenAI. Otros proveedores compatibles con OpenAI usan los mismos tres ajustes.

## Coste

Cada ejecución de resumen es una sesión agéntica completa de un agente de codificación leyendo un diff real, no un resumen barato basado en una plantilla, así que su coste depende del modelo elegido y de la frecuencia con la que se ejecuta:

- **Una sesión completa por cada push al PR.** El disparador predeterminado se activa en `synchronize`, así que un PR al que se le hacen diez pushes ejecuta el agente diez veces.
- **El PR completo cada vez**, no solo los commits desde la última ejecución: el coste escala con el tamaño total del PR, no con el tamaño incremental del diff.
- **Entrada de diff limitada a ~600 KB.** Esto acota el peor caso por ejecución, pero los diffs grandes siguen costando notablemente más que los pequeños.
- **Un reintento automático en caso de fallo**, que puede aproximadamente duplicar el coste de una ejecución que falla de forma transitoria.

Para reducir el coste:

- **Fija un modelo más económico.** Para Claude, establece `VISUAL_RECAP_MODEL=claude-haiku-4-5` en repositorios simples o pequeños: es el nivel más económico de Claude; `claude-sonnet-5` (el predeterminado) es el nivel equilibrado.
- **Cambia a Codex con un modelo más económico.** Establece `VISUAL_RECAP_AGENT=codex` con `VISUAL_RECAP_MODEL=gpt-5.6-luna` (el nivel más económico de GPT-5.6) o `gpt-5.6-terra` (nivel intermedio), y establece `VISUAL_RECAP_REASONING=low` para reducir aún más el gasto en tokens de razonamiento. La profundidad de razonamiento solo se aplica a Codex.
- **Apunta a un proveedor compatible con OpenAI más económico.** Establece `VISUAL_RECAP_AGENT=openai-compatible` con `VISUAL_RECAP_BASE_URL`/`VISUAL_RECAP_MODEL`/`VISUAL_RECAP_API_KEY` apuntando a DeepSeek, Kimi o cualquier otro endpoint compatible con OpenAI.
- **Exige una etiqueta explícita en el PR.** Establece `VISUAL_RECAP_REQUIRED_LABELS=visual recap` para mantener el flujo de trabajo instalado pero omitir los resúmenes hasta que un PR tenga esa etiqueta. Usa una lista separada por comas, como `visual recap,recap`, cuando varias etiquetas deban habilitarlo. Aplicar una etiqueta de la lista despierta el flujo de trabajo de inmediato.
- **Genera resúmenes con menos frecuencia.** Edita `on.pull_request.types` del flujo de trabajo instalado de `[opened, synchronize, reopened, ready_for_review, labeled, closed]` a `[opened, ready_for_review, closed]` para que solo genere un resumen cuando se abre un PR y cuando se fusiona, en lugar de en cada push.

Cada ejecución registra lo que realmente gastó: el paso `recap usage` del flujo de trabajo adjunta el uso de tokens y coste al plan publicado, para que puedas ver el gasto real por ejecución en lugar de adivinar.

## Secrets y variables {#secrets-and-variables}

Configura estos valores en **Settings → Secrets and variables → Actions** de tu repositorio.

### Secrets para el backend predeterminado

| Secret              | Propósito                                                                                                                          |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `PLAN_RECAP_TOKEN`  | Token revocable generado por `npx @agent-native/core@latest connect`. Autoriza publicar el plan de resumen y subir la captura de pantalla. |
| `ANTHROPIC_API_KEY` | La clave del LLM para el backend predeterminado de Claude Code.                                                                    |

**Equipos: usa un token de servicio de la organización.** Un token personal está vinculado a
la persona que lo generó: si abandona la organización o revoca sus tokens, todos los
repositorios que usan ese secret empiezan a fallar con 401, y los planes creados por CI
quedan en propiedad de esa persona en lugar de la del equipo. Un token de servicio de la
organización pertenece a tu **organización**: actúa como un principal de servicio
(`svc-<name>@service.<orgId>`), sobrevive a que cualquier persona se vaya, los resúmenes que
publica son visibles para toda la organización, y cualquier propietario o administrador de la
organización puede listarlo o revocarlo. Genera uno (solo propietarios/administradores de la
organización):

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --service-token pr-recap
```

El comando te autentica en el navegador y luego imprime el token de servicio exactamente una
vez: guárdalo como el secret `PLAN_RECAP_TOKEN`. Gestiónalo más adelante con las actions
`list-org-service-tokens` y `revoke-org-service-token` de la app Plans.

**En solitario: un token personal también funciona.** Genéralo con `npx @agent-native/core@latest connect`
contra tu app Plans. Para la app alojada, esto también escribe un archivo local de token de
publicación que `npx @agent-native/recap-cli@latest recap setup` puede leer:

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --client codex
npx @agent-native/recap-cli@latest recap setup
```

Si prefieres una configuración manual, pega el token en el secret de GitHub. Usa un marcador
de posición como `plan_recap_xxxxxxxxxxxxxxxx` solo para ejemplos; nunca confirmes un token
real.

## Captura de pantalla en línea en el comentario

Después de que el agente publique el resumen, el flujo de trabajo captura el plan renderizado
en Chrome sin interfaz, tanto en modo claro como oscuro, y sube los PNG a una ruta de
imágenes públicas firmada en la app Plans. El comentario fijo en el PR incrusta entonces esas
capturas **en línea** con un elemento `<picture>`: GitHub las vuelve a servir a través de su
proxy camo, de modo que los revisores ven una vista previa que coincide con su tema de GitHub
directamente en el comentario, sin abrir nada. El enlace al plan interactivo completo se sitúa
justo al lado para cuando quieran explorar, comentar o anotar.

## PRs de fork

### Comportamiento predeterminado (no requiere ninguna acción)

El flujo de trabajo principal `pr-visual-recap.yml` se activa con el disparador simple
`pull_request`, **no** `pull_request_target`. Por eso los PR de fork se ejecutan **sin acceso
a los secrets del repositorio**, así que el flujo de trabajo no encuentra ningún
`PLAN_RECAP_TOKEN` y no hace nada de forma limpia: no hay publicación fallida, ni credenciales
expuestas. Los resúmenes se ejecutan automáticamente para los PR de ramas del mismo
repositorio, donde los secrets sí están disponibles.

Esto también significa que puedes fusionar el archivo de flujo de trabajo **antes** de que
existan los secrets: sin ningún token configurado, cada ejecución es un no-op silencioso
hasta que establezcas los secrets. El paso `gate` también omite automáticamente los PR en
borrador y los PR creados por bots, así que ninguno de los dos activa la generación de
resúmenes de forma predeterminada.

### Habilitación explícita con el flujo de trabajo de fork controlado por etiqueta

Si quieres generar resúmenes para PR de fork, hay disponible un segundo archivo de flujo de
trabajo: `.github/workflows/pr-visual-recap-fork.yml`. Usa `pull_request_target` (que se
ejecuta con los secrets del repositorio base) pero nunca descarga ni ejecuta código del fork.
Los autores de fork de confianza con asociación de autor de GitHub `OWNER`, `MEMBER` o
`COLLABORATOR` se ejecutan automáticamente. Los PR de fork externos requieren una
**habilitación explícita del mantenedor por cada head** mediante un evento nuevo de la
etiqueta `recap` antes de que se ejecute el agente de resumen.

Para instalarlo, copia el archivo desde [BuilderIO/agent-native](https://github.com/BuilderIO/agent-native/blob/main/.github/workflows/pr-visual-recap-fork.yml) al directorio `.github/workflows/` de tu repositorio, junto al `pr-visual-recap.yml` ya existente. Se aplica la misma configuración de backend, incluidas `VISUAL_RECAP_API_KEY`, `VISUAL_RECAP_BASE_URL` y `VISUAL_RECAP_MODEL` cuando se usa un proveedor compatible con OpenAI.

### Cómo funciona la barrera de etiqueta

1. Un colaborador de un fork abre un PR. El flujo de trabajo normal de `pull_request` se omite porque GitHub retiene los secrets en las ejecuciones de fork.
2. El flujo de trabajo de fork comprueba la asociación de autor del PR. Los autores de confianza (`OWNER`, `MEMBER` o `COLLABORATOR`) se ejecutan automáticamente en los eventos de apertura, sincronización, reapertura y listo para revisión.
3. Los colaboradores externos necesitan que un mantenedor revise el diff actual (especialmente en busca de contenido con forma de inyección de prompts; consulta más abajo) y luego aplique la etiqueta `recap` al PR.
4. La barrera de etiqueta para colaboradores externos es por SHA de head: si el colaborador hace push de más commits, el siguiente evento de sincronización se omite hasta que un mantenedor quite y vuelva a aplicar `recap` tras revisar el nuevo diff.

### Qué hace y qué NO hace el flujo de trabajo de fork

| El flujo de trabajo SÍ hace                                                                                             | El flujo de trabajo NO hace                                                          |
| ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| Descarga el **repositorio base** en la ref de la **rama base** — solo código de confianza                                | Descargar o ejecutar ningún código del fork                                            |
| Obtiene el head del fork como ref remota (`git fetch origin pull/<n>/head:refs/recap/fork-head`) — obtener commits es seguro | Instalar paquetes del fork, ejecutar scripts del fork o evaluar contenido del fork como código |
| Ejecuta `git diff base...refs/recap/fork-head` — un diff de texto puro entre dos objetos ya obtenidos                    | Usar el diff como algo distinto de una entrada de texto para el LLM                     |
| Ejecuta la skill `visual-recap` y la configuración de agente **del repositorio base**                                   | Cargar ninguna skill ni configuración del fork                                          |
| Pasa el diff por el mismo paso de escaneo de secrets (fail-closed) que los PR propios                                    | Omitir el escaneo de secrets                                                            |
| Añade una nota explícita de refuerzo del prompt que marca el contenido del diff como no confiable                       | Conceder al agente ningún permiso adicional más allá del agente de resumen normal       |

### Por qué debes revisar el diff antes de etiquetar

El diff del fork es texto controlado por un posible atacante que el agente de resumen lee
como entrada. Un diff cuidadosamente elaborado podría contener contenido de inyección de
prompts — por ejemplo, líneas de diff que parecen instrucciones para el agente — con la
intención de hacer que el agente de resumen realice acciones no deseadas (por ejemplo,
exfiltrar el token de publicación o producir contenido de resumen engañoso).

Antes de aplicar la etiqueta `recap`, revisa por encima el diff en busca de:

- Líneas que se leen como comandos directos o instrucciones de rol ("Ignore previous instructions...", "You are now...", "Write the token to...").
- Nombres de archivo inusuales que podrían confundirse con prompts de sistema.
- Contenido codificado en archivos añadidos que podría decodificarse como instrucciones.

Estas mitigaciones ya están integradas en capas en el flujo de trabajo (escaneo de secrets,
barrera de rutas sensibles, nota de refuerzo del prompt, lista de permitidas de herramientas
del agente restringida), pero la revisión antes de etiquetar es la principal línea de
defensa.

### Relación con el flujo de trabajo principal

Los dos archivos de flujo de trabajo son independientes. Para las actualizaciones de PR que
no son de fork, `pr-visual-recap.yml` es el único flujo de trabajo que se ejecuta. Para los
PR de fork, el flujo de trabajo normal termina en su barrera de fork, y
`pr-visual-recap-fork.yml` se ejecuta automáticamente para autores de confianza de la misma
organización, o tras una etiqueta `recap` nueva del mantenedor para colaboradores externos.
Comparten el mismo marcador de comentario fijo y el mismo hilo de id de plan, así que tanto
los PR normales como los de fork producen un único comentario mediante upsert en el mismo PR.

### Protección contra automodificación {#self-modifying-guard}

El paso `gate` omite el resumen por completo cuando un PR toca cualquiera de las siguientes
rutas, de modo que un PR nunca puede reescribir el flujo de trabajo, la skill o la
configuración de agente que carga el job de resumen de confianza, ni exfiltrar secrets:

| Patrón de ruta                             | Motivo                                    |
| ------------------------------------------ | ------------------------------------------ |
| `.github/workflows/pr-visual-recap.yml`    | El propio flujo de trabajo                 |
| `**/skills/visual-(recap\|plan\|plans)/**` | La skill `visual-recap` que sigue el agente |
| `**/.claude/**`                            | Configuración del agente que carga el ejecutor |
| `**/CLAUDE.md`                             | Instrucciones del agente que carga el ejecutor |
| `**/AGENTS.md`                             | Instrucciones del agente que carga el ejecutor |
| `**/.mcp.json`                             | Configuración del servidor MCP que carga el ejecutor |

En el monorepo `BuilderIO/agent-native`, el flujo de trabajo ejecuta la CLI de resumen desde
la fuente de confianza de la rama base, en lugar de la fuente del head del PR. Eso mantiene
los cambios normales de paquetes, incluido `packages/core/**`, elegibles para resúmenes sin
ejecutar código de la CLI modificado por el PR.

## Modo de privacidad de archivos locales

La GitHub Action está diseñada para la revisión de PR alojada y compartible. Si quieres un
resumen sin enviar su contenido a la base de datos de Agent-Native Plan, ejecuta en su lugar
localmente el mismo flujo auxiliar en modo de archivos locales:

```bash
npx @agent-native/recap-cli@latest recap collect-diff --base main --head HEAD --out recap.diff --stat recap.stat
npx @agent-native/recap-cli@latest recap scan --diff recap.diff
npx @agent-native/recap-cli@latest recap build-prompt --pr 123 --diff recap.diff --stat recap.stat --local-files --local-dir plans/pr-123-visual-recap
```

Dale el `recap-prompt.md` generado a tu agente de codificación. En modo de archivos locales,
el prompt indica al agente que escriba `plans/pr-123-visual-recap/plan.mdx` más archivos
visuales opcionales, y que luego ejecute:

```bash
npx @agent-native/core@latest plan local serve --dir plans/pr-123-visual-recap --kind recap --open
```

La URL devuelta abre la interfaz de Plan alojada mientras el navegador lee el MDX del resumen
desde un puente localhost. El contenido del resumen no se escribe en la base de datos alojada
de Plan, y la URL solo funciona en la máquina que ejecuta el puente. Si ejecutas la app Plan
localmente con el mismo `PLAN_LOCAL_DIR`, la ruta `/local-plans/pr-123-visual-recap` también
es válida. Las carpetas respaldadas por el repositorio pueden abrirse como
`/local-plans/pr-123-visual-recap?path=plans%2Fpr-123-visual-recap`. Este modo desactiva el
comentario fijo alojado en el PR, la subida de capturas en línea, el adjunto de uso y los
comentarios del navegador hasta que publiques explícitamente.

## Es informativo, no una barrera

El resumen es una ayuda para la revisión que se superpone al flujo normal del PR:

- Muestra una fila de verificación `Visual Recap` para dar visibilidad, pero **nunca es una verificación obligatoria** y nunca bloquea la fusión.
- Un fallo de generación o de publicación se completa de forma neutral y se muestra como un comentario fijo explicativo, no como una X roja sobre código no relacionado.
- El resumen y su captura de pantalla **no implican que el diff se haya revisado**. Los revisores todavía tienen que leer las líneas realmente cambiadas.

## Fijar la versión (variante de copia) {#version-pinning-copy-variant}

De forma predeterminada, el flujo de trabajo de la variante de copia instala
`@agent-native/recap-cli@latest` en tiempo de ejecución, de modo que cada ejecución del
resumen recoge automáticamente la CLI más reciente. Si tu CI necesita herramientas
reproducibles, establece la variable de repositorio **`RECAP_CLI_VERSION`** para fijar la
versión instalada:

1. Ve a **Settings → Secrets and variables → Actions → Variables** de tu repositorio.
2. Crea una variable llamada `RECAP_CLI_VERSION` con un valor como `1.5.0`.

La variable es opcional. Déjala sin definir (o establécela en `latest`) para seguir la
versión más reciente.

Para la variante de llamador reutilizable, usa en su lugar el input `cli-version` (consulta [Fijar la versión](#version-pinning) en la sección reutilizable).

## Lista de permitidas del escaneo de secrets

Antes de publicar un resumen, el flujo de trabajo ejecuta `npx @agent-native/recap-cli@latest recap scan` para detectar posibles secrets en el diff. Cualquier PR cuyo diff coincida con un patrón de secret conocido se bloquea con un comentario explicativo: el resumen no se publica, y no se envía ningún contenido del diff al agente de codificación.

En casos poco frecuentes, un repositorio tiene fixtures de prueba intencionados o cadenas que no son secrets pero que superficialmente se parecen a patrones de secret (por ejemplo, una clave de fixture en un archivo de prueba). Para suprimir un falso positivo, crea `.github/recap-scan-allowlist` en la raíz de tu repositorio.

### Formato

Cada línea que no está en blanco ni es un comentario es una **subcadena literal** o un patrón **`/regex/flags`**:

```
# Lines starting with # are comments.

# Literal substring — any diff line containing this string is allowed.
sk-test-fixture1234567890abcdef

# Regex pattern — written as /pattern/flags (JS syntax).
/^.STRIPE_KEY=sk-test-/i

# Another literal.
EXAMPLE_API_KEY=placeholder-value
```

Reglas:

- Una línea queda **suprimida** (permitida) cuando contiene el literal, o cuando la línea completa coincide con el regex.
- El archivo es **fail-closed**: si está ausente, no se aplica ninguna supresión; el escáner se comporta como antes.
- Un archivo vacío equivale a no tener archivo.
- Las líneas de regex con formato incorrecto se tratan como cadenas literales.

La lista de permitidas solo la consulta la barrera de escaneo de secrets. No afecta a lo que puede leer el agente de codificación: si la barrera pasa, el agente recibe el diff completo de todos modos.

## Adóptalo como flujo de trabajo reutilizable

### ¿Por qué usar la variante reutilizable?

El instalador predeterminado copia el YAML completo del flujo de trabajo (~360 líneas) en tu repositorio (la opción **copia**). Es la opción correcta para repositorios air-gapped o que necesitan auditar cada línea de lo que se ejecuta. La desventaja es que las correcciones de errores y las mejoras nunca te llegan: tienes que volver a ejecutar `npx @agent-native/recap-cli@latest recap setup` manualmente después de cada versión.

La opción **reutilizable** escribe en su lugar un llamador ligero de ~20 líneas. Delega en `BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml` mediante `uses:`. Cada llamador recoge automáticamente la lógica más reciente cuando se ejecuta el flujo de trabajo, sin necesidad de ninguna actualización local.

|                                          | Copia (predeterminada)      | Reutilizable                   |
| ---------------------------------------- | ---------------------------- | ------------------------------- |
| Tamaño del flujo de trabajo en tu repositorio | ~360 líneas              | ~20 líneas                      |
| Recoge correcciones automáticamente      | No — hay que volver a ejecutar `recap setup` | Sí               |
| Air-gap / auditabilidad completa         | Sí                            | No                               |
| Se puede fijar a una versión concreta    | Solo editando localmente     | Sí — establece `@v1.2.3` en `uses:` |

### Fragmento del llamador

Esto es lo que escribe `npx @agent-native/recap-cli@latest recap setup --reusable` (o puedes pegarlo manualmente):

```yaml
name: PR Visual Recap

# Thin caller — the full workflow logic lives in BuilderIO/agent-native.
# Fixes and improvements reach this repo automatically on each run.
# To pin a specific version for reproducibility replace '@main' with a
# tag or SHA, e.g. '@v1.2.3' or '@abc1234'.

on:
  pull_request:
    types: [opened, synchronize, reopened, ready_for_review, labeled, closed]

jobs:
  visual-recap:
    if: github.event.action != 'labeled' || vars.VISUAL_RECAP_REQUIRED_LABELS != ''
    permissions:
      actions: write
      contents: read
      checks: write
      issues: write
      pull-requests: write
    uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@main
    secrets:
      PLAN_RECAP_TOKEN: ${{ secrets.PLAN_RECAP_TOKEN }}
      ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
      OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
      VISUAL_RECAP_API_KEY: ${{ secrets.VISUAL_RECAP_API_KEY }}
      PLAN_RECAP_APP_URL: ${{ secrets.PLAN_RECAP_APP_URL }}
    with:
      agent: ${{ vars.VISUAL_RECAP_AGENT || 'claude' }}
      model: ${{ vars.VISUAL_RECAP_MODEL || '' }}
      base-url: ${{ vars.VISUAL_RECAP_BASE_URL || '' }}
      reasoning: ${{ vars.VISUAL_RECAP_REASONING || '' }}
      skill-source: ${{ vars.VISUAL_RECAP_SKILL_SOURCE || 'auto' }}
      runs-on: ${{ vars.VISUAL_RECAP_RUNS_ON || '"ubuntu-latest"' }}
      gate-runs-on: ${{ vars.VISUAL_RECAP_GATE_RUNS_ON || 'ubuntu-latest' }}
      required-labels: ${{ vars.VISUAL_RECAP_REQUIRED_LABELS || '' }}
      # cli-version: "latest"  # pin to a specific @agent-native/recap-cli version
```

Se aplican los mismos secrets y variables descritos en [Secrets y variables](#secrets-and-variables); configúralos en los ajustes de tu repositorio de la misma manera que en la variante de copia. El llamador reutilizable reenvía `VISUAL_RECAP_RUNS_ON` a través de su input JSON `runs-on` para el job de resumen completo, `VISUAL_RECAP_GATE_RUNS_ON` a través de su input de etiqueta simple `gate-runs-on` para la barrera de solo metadatos, y `VISUAL_RECAP_REQUIRED_LABELS` a través de `required-labels` para el filtrado opcional por etiqueta de PR. El input del ejecutor de la barrera solo se usa para autores de confianza del mismo repositorio; el resto de PR usan `ubuntu-latest` alojado por GitHub. Omitir los inputs de ejecutor conserva sus valores predeterminados `ubuntu-latest`; omitir las etiquetas obligatorias conserva el comportamiento automático de generación de resúmenes.

### Instalación mediante la CLI

```bash
# Write the thin caller instead of the full copy:
npx @agent-native/recap-cli@latest recap setup --reusable

# Or with a pinned ref for reproducibility:
npx @agent-native/recap-cli@latest recap setup --reusable --ref v1.2.3
```

Ambas variantes escriben el flujo de trabajo en `.github/workflows/pr-visual-recap.yml`. Si ya existe un flujo de trabajo distinto en esa ruta, el comando se niega y te indica que pases `--force` para sobrescribirlo.

Después de escribirlo, ejecuta `npx @agent-native/recap-cli@latest recap doctor` como de costumbre para confirmar que los secrets están configurados.

### Fijar la versión {#version-pinning}

De forma predeterminada, el llamador hace referencia a `@main`, que siempre usa la última versión publicada del flujo de trabajo reutilizable. Para repositorios de producción que necesiten un CI reproducible, fíjalo a un tag o un SHA:

```yaml
uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@v1.2.3
```

El input `cli-version` controla qué versión de `@agent-native/recap-cli` se ejecuta dentro del flujo de trabajo: déjalo en `"latest"` para seguir la versión más reciente, o fíjalo a una cadena de versión (por ejemplo, `"1.5.0"`) para una reproducibilidad completa.

### Contexto de evento de workflow_call

Los flujos de trabajo `workflow_call` heredan el contexto de evento del llamador. El flujo de trabajo reutilizable usa expresiones `github.event.pull_request.*` para leer el número de PR, el SHA del head, el SHA de la base, la marca de tiempo de fusión y los metadatos del PR: estas solo funcionan correctamente cuando el llamador se activa con `pull_request`. El fragmento del llamador de arriba ya incluye los tipos de evento correctos. El evento `closed` se incluye para que los resúmenes de PR fusionados puedan marcarse con `merged_at` y buscarse más adelante como trabajo entregado.

No actives el llamador con `workflow_dispatch` ni `push` — esos eventos no llevan un payload de `pull_request`, y la barrera omitirá el resumen con "no pull_request payload".
