# Docker

Docker empaqueta una aplicación de Agent-Native y todo lo que necesita para ejecutarse en una
única imagen de contenedor. La imagen ejecuta el mismo servidor Node.js descrito en la
[guía de Node.js](/docs/node-js), así que se comporta igual en tu portátil, en una
máquina virtual o en cualquier host que ejecute contenedores.

Esta guía explica cómo implementar una aplicación independiente desde cero. Vas a
crear la aplicación, añadir un `Dockerfile`, darle a la aplicación una base de datos de producción y un
secreto de autenticación, preparar la base de datos y, después, compilar y ejecutar el contenedor.

<Callout tone="info">

Se requiere Node.js `22.22+`.

</Callout>

También necesitas tener Docker instalado en la máquina que compila y ejecuta la imagen.
Ejecuta los comandos de esta guía en el servidor que ejecutará el contenedor. En una
máquina virtual, eso normalmente significa conectarte primero a ella por SSH.

<a id="self-host-quickstart"></a>

## Paso 1: Crea la aplicación {#step-1-create-the-app}

Crea tu nueva aplicación independiente. El siguiente ejemplo crea una aplicación a partir de la plantilla Chat,
pero puedes empezar desde cualquier plantilla. Entra en la carpeta de la aplicación e
instala sus dependencias. `corepack enable` activa la versión de `pnpm` que la aplicación
espera, así que no necesitas instalar `pnpm` por tu cuenta.

```bash
npx --yes @agent-native/core@latest create my-app --standalone --template chat

cd my-app

corepack enable

pnpm install
```

Si quieres, reemplaza `my-app` por el nombre de tu aplicación. El resto de esta guía
supone que estás dentro de la carpeta de la aplicación.

<Callout tone="info">

Si estos comandos fallan con errores de dependencias peer, la causa puede ser una copia desactualizada de un paquete en tu caché de npx. Ejecuta `npx clear-npx-cache` para vaciar la caché y vuelve a ejecutar los comandos.

</Callout>

## Paso 2: Crea el Dockerfile {#step-2-create-dockerfile}

Una aplicación nueva no incluye un `Dockerfile`, así que tienes que añadirlo tú. También añades
un archivo `.dockerignore` que mantiene los archivos locales fuera de la imagen. Crea ambos
archivos en la carpeta raíz de la aplicación, junto a `package.json`.

### Dockerfile {#dockerfile}

Crea un archivo llamado `Dockerfile`, sin extensión, y copia en él lo
siguiente:

```dockerfile filename="Dockerfile"
FROM node:24-slim AS build
WORKDIR /app

RUN apt-get update \
  && apt-get install -y --no-install-recommends python3 make g++ \
  && rm -rf /var/lib/apt/lists/*

ENV PYTHON=/usr/bin/python3

COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile

COPY . .
RUN pnpm build

FROM node:24-slim
WORKDIR /app

ENV NODE_ENV=production
ENV PORT=3000

COPY --from=build /app/.output .output

EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

El `Dockerfile` compila la imagen en dos etapas:

- **Etapa de compilación.** Instala las herramientas que algunas dependencias necesitan para compilarse durante
  la instalación (`python3`, `make` y `g++`), instala las dependencias de la aplicación y
  compila la aplicación.
- **Etapa final.** Parte de una imagen limpia de Node.js y copia solo el
  servidor terminado de la carpeta `.output`. Así la imagen es pequeña y
  deja atrás las herramientas de compilación y el código fuente.

La imagen final se ejecuta en modo de producción y escucha en el puerto `3000`.

### Archivo de exclusiones de Docker {#docker-ignore-file}

Crea un archivo llamado `.dockerignore` y copia en él lo siguiente:

```text filename=".dockerignore"
node_modules
.output
.git
.env
.env.*
data
*.log
```

Estas entradas mantienen fuera de la imagen las dependencias locales, los resultados de compilaciones anteriores, el historial de Git, los
secretos locales de los archivos `.env`, la base de datos de desarrollo local en `data` y los archivos
de registro. La etapa de compilación instala dependencias nuevas y compila
la aplicación desde cero, así que no se necesita nada de esto. Excluir los archivos `.env` también
evita que tus secretos queden incluidos en la imagen.

## Paso 3: Configura los secretos del entorno {#step-3-configure-environment-secrets}

La aplicación lee su configuración de producción desde variables de entorno:

| Variable             | Obligatoria | Propósito                                                                      |
| -------------------- | ----------- | ------------------------------------------------------------------------------ |
| `DATABASE_URL`       | Sí          | Conecta la aplicación con su base de datos PostgreSQL                          |
| `BETTER_AUTH_SECRET` | Sí          | Firma las sesiones de los usuarios                                             |
| `BETTER_AUTH_URL`    | No          | Define la dirección pública que usan las personas para acceder a tu aplicación |

Las exportaciones siguientes hacen que los comandos posteriores funcionen en esta terminal. Antes de
implementar, guarda estas mismas variables en la configuración del entorno del proyecto o servicio de tu host,
para que el contenedor las siga teniendo después de un reinicio o de una nueva
implementación.

### URL de la base de datos {#database-url}

Durante el desarrollo local, la aplicación guarda los datos en una base de datos local cuando
`DATABASE_URL` no está definida. Una aplicación implementada necesita una base de datos PostgreSQL real que
conserve sus datos entre reinicios. Un contenedor pierde todos los archivos que escribe cuando se
reemplaza, así que la base de datos debe estar fuera del contenedor. Copia la
cadena de conexión de tu proveedor y expórtala:

```bash
export DATABASE_URL='your-postgres-url-string'
```

Las [guías de proveedores de bases de datos](/docs/neon) muestran dónde encontrar la cadena de conexión
de cada proveedor.

<Callout tone="warning">

Elige un proveedor de PostgreSQL persistente, como Neon, Supabase o Amazon RDS.

</Callout>

### Secreto de autenticación {#auth-secret}

Genéralo una sola vez y mantenlo igual en todas las implementaciones.

La aplicación usa `BETTER_AUTH_SECRET` para firmar las sesiones de los usuarios. Si cambia, se cierra la sesión de
todos los usuarios que la tenían iniciada. El siguiente comando genera un valor aleatorio:

```bash
export BETTER_AUTH_SECRET="$(openssl rand -hex 32)"
```

Guarda el valor generado en un lugar seguro, como la configuración de secretos de tu host o
un gestor de contraseñas. Usa el mismo valor cada vez que implementes.

### URL pública {#public-url}

Es opcional. Defínela cuando uses un dominio personalizado, un proxy inverso o un flujo de autenticación u OAuth
que necesite un origen público fijo.

`BETTER_AUTH_URL` es la dirección pública que usan las personas para acceder a tu aplicación. Sin
ella, la aplicación deduce su dirección a partir de cada solicitud entrante. Eso suele
funcionar bien, pero los enlaces de inicio de sesión y las redirecciones de OAuth pueden apuntar al lugar equivocado cuando
la aplicación está detrás de un proxy o de un dominio personalizado.

```bash
export BETTER_AUTH_URL='https://your-domain.example'
```

## Paso 4: Ejecuta las migraciones {#step-4-migrate}

Las migraciones crean y actualizan las tablas que la aplicación necesita en tu base de datos.

Ejecuta esto en el host, contra la `DATABASE_URL` de producción, antes de la primera
visita.

```bash
pnpm migrate:production
```

Ejecuta el comando desde la carpeta de la aplicación, no dentro del contenedor. La imagen solo
contiene el servidor terminado, así que no puede ejecutar las migraciones por sí misma. El comando lee
`DATABASE_URL` del entorno que exportaste en el paso anterior. Vuelve a ejecutarlo
después de actualizar la aplicación y antes de iniciar la nueva versión.

## Paso 5: Implementa {#step-5-deploy}

Compila la imagen desde la carpeta de la aplicación:

```bash
docker build -t my-agent-native-app .
```

La opción `-t` le da a la imagen el nombre `my-agent-native-app`. Puedes usar el nombre que quieras, pero
usa el mismo nombre en el siguiente comando.

Ejecuta el contenedor:

```bash
docker run --rm \
  -p 3000:3000 \
  -e DATABASE_URL \
  -e BETTER_AUTH_SECRET \
  my-agent-native-app
```

`-p 3000:3000` hace que el puerto `3000` del contenedor sea accesible en el puerto
`3000` del servidor. Cada opción `-e` pasa al contenedor la variable del mismo nombre de tu terminal.
Si defines `BETTER_AUTH_URL`, añade también `-e BETTER_AUTH_URL` al
comando. `--rm` elimina el contenedor cuando se detiene.

Para acceder a la aplicación desde internet, abre el puerto `3000` en el firewall del servidor
o coloca delante un proxy inverso como Nginx o Caddy para servir tu
dominio a través de HTTPS. Después, abre la dirección pública de la aplicación y crea la primera
cuenta.

## Mantén el contenedor en ejecución {#keep-the-container-running}

El comando `docker run` anterior se ejecuta en tu terminal y se detiene cuando la cierras.
Para mantener la aplicación en ejecución, inicia el contenedor en segundo plano con una
política de reinicio, para que Docker lo vuelva a iniciar después de un fallo o de un reinicio del servidor.
Para ello, reemplaza `--rm` por `-d --restart unless-stopped`. Muchos hosts que
ejecutan contenedores también se encargan de los reinicios por ti.
