# Base de datos

Toda aplicación nativa del agente almacena su estado en PostgreSQL. La UI y el agente leen y escriben las mismas tablas a través de las mismas actions, usando el mismo cliente [Drizzle ORM](https://orm.drizzle.team). La sincronización en vivo usa SSE con polling como alternativa, por lo que los cambios aparecen en la otra superficie sin actualizar manualmente.

## Opciones de Alojamiento {#hosting}

La aplicación usa PostgreSQL. Si `DATABASE_URL` no está configurado, utiliza PGlite local para que pueda empezar sin configuración.

### Predeterminado: archivo PGlite {#default-pglite}

Cuando `DATABASE_URL` no está configurado, la aplicación crea una base de datos PGlite en `data/pglite`. No se requiere configuración. Inicie el servidor de desarrollo y el archivo se crea en la primera ejecución.

Esto es solo para desarrollo local. Los contenedores, las funciones sin servidor y los entornos de vista previa pueden restablecer su sistema de archivos entre reinicios, por lo que un archivo PGlite local puede desaparecer. Configure `DATABASE_URL` en una base de datos PostgreSQL alojada y persistente antes de desplegar.

### Postgres local: PGlite {#local-pglite}

Para desarrollar localmente con PostgreSQL sin Docker ni una base de datos alojada, instale el paquete opcional PGlite y configure `DATABASE_URL`:

```bash
pnpm add @electric-sql/pglite@^0.5.8
```

```bash
DATABASE_URL=pglite:./data/pglite
```

[PGlite](https://pglite.dev/) ejecuta una base de datos Postgres WASM dentro del mismo proceso. Le permite detectar problemas de esquema exclusivos de Postgres antes de desplegar, manteniendo una configuración tan sencilla como la del valor predeterminado PGlite. Al igual que PGlite, es almacenamiento solo local. No lo use para producción ni para entornos compartidos.

### Base de datos de producción {#production}

Configure `DATABASE_URL` en su archivo `.env` o en el entorno del proveedor de despliegue para conectar una base de datos PostgreSQL alojada:

```bash
# Neon Postgres
DATABASE_URL=postgres://user:pass@ep-cool-name-123456.us-east-2.aws.neon.tech/mydb?sslmode=require

# Supabase Postgres
DATABASE_URL=postgres://postgres.xxxx:pass@aws-0-us-east-1.pooler.supabase.com:6543/postgres

# Postgres simple
DATABASE_URL=postgres://user:pass@localhost:5432/mydb

DATABASE_URL=pglite:./data/pglite
```

El marco configura Drizzle para PostgreSQL a partir de `DATABASE_URL`.

### Base de datos administrada por Builder.io {#builder-managed}

_Planificado (aún no disponible):_ cuando esté conectada a Builder.io, su aplicación podrá usar una base de datos PostgreSQL administrada y aprovisionada automáticamente, sin necesidad de una cadena de conexión de PostgreSQL.

## Configurar la Base de Datos {#setup}

Una aplicación que usa la base de datos necesita tres archivos:

- `server/db/schema.ts`: definiciones de tablas
- `server/db/index.ts`: el singleton del cliente de base de datos tipado
- `server/plugins/db.ts`: migraciones propias de la aplicación para el inicio local

### 1. Defina su esquema {#schema}

Importe los ayudantes de esquema desde `@agent-native/core/db/schema`. Los ayudantes del marco producen definiciones específicas para PostgreSQL y PGlite.

```ts filename="server/db/schema.ts"
import { sql } from "drizzle-orm";
import { boolean, integer, pgTable, text } from "drizzle-orm/pg-core";

export const tasks = pgTable("tasks", {
  id: text("id").primaryKey(),
  title: text("title").notNull(),
  priority: integer("priority").notNull().default(0),
  done: boolean("done").notNull().default(false),
  ownerEmail: text("owner_email").notNull(),
  createdAt: text("created_at").notNull().default(sql`now()`),
});
```

| Ayudante  | Propósito                                                                         |
| --------- | --------------------------------------------------------------------------------- |
| `pgTable` | Define una tabla con PostgreSQL                                                     |
| `text`    | Columna de texto, admite `{ enum: [...] }`                                        |
| `integer` | Columna entera                                                                    |
| `boolean` | Columna booleana                                                                  |
| `doublePrecision` | Columna de punto flotante de doble precisión                              |
| `sql` | Expresión SQL como `now()`                                                         |

Las tablas que almacenan datos por usuario deben incluir una columna `owner_email` para que el marco pueda filtrar filas para el usuario autenticado. Las tablas que también admiten compartirse con otros usuarios u organizaciones deberían difundir `...ownableColumns()` en su lugar, lo que agrega `owner_email`, `org_id` y `visibility` en una sola llamada. Consulte [Delimitar datos a usuarios](#scoping) más abajo.

### 2. Cree el cliente de base de datos {#db-client}

Cada aplicación crea un cliente Drizzle único y diferido llamando a `createGetDb(schema)`. La ubicación canónica es `server/db/index.ts`:

```ts filename="server/db/index.ts"
import { createGetDb } from "@agent-native/core/db";
import * as schema from "./schema.js";

export const getDb = createGetDb(schema);
```

`createGetDb` devuelve una función `getDb()` que abre la conexión PostgreSQL en la primera llamada y devuelve la misma instancia tipada de Drizzle en las llamadas siguientes. Lee `DATABASE_URL` para conectarse a PostgreSQL alojado o PGlite local.

Importe `getDb` desde esta ruta local de la plantilla en actions y rutas. No importe directamente desde `@agent-native/core`. La exportación del core no está tipada; la exportación local lleva los tipos de su esquema.

### 3. Escriba las migraciones {#migrations}

plugin de Nitro en `server/plugins/db.ts`. En producción o despliegues serverless,
ejecuta las migraciones en un paso de release o despliegue, no en la primera
solicitud. Usa `runMigrations` desde `@agent-native/core/db`:

`runMigrations` ejecuta cada entrada pendiente en orden una vez, la registra como
aplicada y la omite en las ejecuciones posteriores. Da a las entradas nuevas un
`name` estable; las migraciones con nombre se registran independientemente de su
número de versión.

<Callout tone="warning">
  La plantilla Chat incluye `pnpm migrate:production` para ejecutar migraciones
  como parte del paso de release.
</Callout>

### Generar nuevas migraciones de la aplicación con Drizzle Kit {#drizzle-migrations}

Para los nuevos cambios del esquema de la aplicación, use `pnpm db:generate` para
crear SQL revisable. Esto crea `server/db/migrations/<id_name>.sql` y
`runDrizzleMigrations` carga esos archivos en el ejecutor compartido de
Agent-Native en runtimes Node.js y serverless basados en Node. El paso de release sigue
siendo el responsable de los cambios en producción. Mantenga `runMigrations()`
para SQL específico de PostgreSQL, Postgres, backfills y pasos de JavaScript diferidos.

El cargador basado en el sistema de archivos no está disponible en Cloudflare
Workers/Pages ni en otros runtimes edge sin sistema de archivos. Allí, use
`runMigrations()` con entradas de SQL de PostgreSQL integradas en el bundle del worker.
Genere las migraciones para PostgreSQL y no cambie la misma carpeta entre PGlite
local y PostgreSQL alojado.

<Callout tone="risk">
  Nunca ejecute `drizzle-kit push` contra una base de datos de producción. Los
  esquemas de las plantillas solo definen tablas específicas de la aplicación;
  no incluyen las tablas centrales del marco (`user`, `session`,
  `application_state` y otras). Ejecutar `drizzle-kit push` contra producción
  detectará esas tablas como desconocidas e intentará eliminarlas, provocando
  una pérdida de datos inmediata.
</Callout>

`drizzle.config.ts`, en la raíz de cada aplicación, configura drizzle-kit para la inspección del esquema PostgreSQL en desarrollo local. Configure explícitamente la base de datos PostgreSQL, por ejemplo `createDrizzleConfig({ dialect: "postgresql" })`:

```ts filename="drizzle.config.ts"
import { createDrizzleConfig } from "@agent-native/core/db/drizzle-config";
export default createDrizzleConfig();
```

Use `pnpm db:generate` para inspeccionar su esquema y `pnpm db:push` solo contra una base de datos local.

### 4. Consulte en las actions {#querying}

Llame a `getDb()` desde sus actions para obtener el cliente Drizzle tipado. Use el generador de consultas de Drizzle y los operadores portátiles de `drizzle-orm`:

```ts
import { and, desc, eq } from "drizzle-orm";
import { getDb } from "../server/db/index.js";
import * as schema from "../server/db/schema.js";

const db = getDb();

const openTasks = await db
  .select()
  .from(schema.tasks)
  .where(
    and(eq(schema.tasks.ownerEmail, userEmail), eq(schema.tasks.done, false)),
  )
  .orderBy(desc(schema.tasks.createdAt));

await db
  .update(schema.tasks)
  .set({ done: true })
  .where(eq(schema.tasks.id, taskId));
```

## Delimitar Datos a Usuarios {#scoping}

Todas las lecturas y escrituras contra tablas de cara al usuario deben estar delimitadas al usuario autenticado. El marco ofrece dos patrones según si los datos son privados o compartibles.

**Datos privados:** tablas que pertenecen a un solo usuario. Agregue `ownerEmail: text("owner_email").notNull()` al esquema e incluya `eq(table.ownerEmail, userEmail)` en cada consulta:

```ts
.where(eq(schema.tasks.ownerEmail, userEmail))
```

**Recursos compartidos:** tablas que pueden compartirse con otros usuarios u organizaciones. Difunda `...ownableColumns()` en el esquema en lugar de un simple `owner_email`. Esto agrega `owner_email`, `org_id` y `visibility` en una sola llamada, y crea una tabla de shares complementaria con `createSharesTable`:

```ts filename="server/db/schema.ts"
import {
  table,
  text,
  ownableColumns,
  createSharesTable,
} from "@agent-native/core/db/schema";

export const decks = table("decks", {
  id: text("id").primaryKey(),
  title: text("title").notNull(),
  ...ownableColumns(),
});
export const deckShares = createSharesTable("deck_shares");
```

Luego use `accessFilter` desde `@agent-native/core/sharing` en las consultas de listado en lugar de una comprobación `eq` manual:

```ts
import { accessFilter } from "@agent-native/core/sharing";

const rows = await db
  .select()
  .from(schema.decks)
  .where(accessFilter(schema.decks, schema.deckShares));
```

`accessFilter` construye una consulta que admite las filas que el llamante posee, las filas compartidas con su organización y las filas compartidas explícitamente con él. No expone filas de otros usuarios.

Consulte [Seguridad — Delimitación de datos](/docs/security#data-scoping) y [Compartir](/docs/sharing#building) para el modelo completo.

## Sincronización Respaldada por PostgreSQL {#sync}

Agent-Native no depende de watchers del sistema de archivos ni de estado persistente en memoria. Cuando una action escribe en la base de datos, se incrementa una versión de sincronización. El hook de cliente `useDbSync()` sondea `/_agent-native/poll` e invalida las cachés de React Query cuando detecta una versión superior.

Esto funciona en despliegues sin servidor y de múltiples instancias porque la base de datos es el punto de coordinación. Si escribe mutaciones personalizadas fuera de las actions, use los ayudantes del marco o emita la invalidación de sincronización adecuada para que las UI abiertas se actualicen.

## PostgreSQL Sin Procesar {#raw-sql}

Para consultas avanzadas, comprobaciones de estado o mantenimiento puntual que el generador de consultas de Drizzle no puede expresar, use `getDbExec` desde `@agent-native/core/db`:

```ts
import { getDbExec } from "@agent-native/core/db";

const { rows } = await getDbExec().execute({
  sql: `SELECT id, title FROM tasks WHERE owner_email = ? LIMIT ?`,
  args: [userEmail, 50],
});
```

`getDbExec` convierte automáticamente los parámetros `?` a `$1`, `$2`, etc. para Postgres. Prefiera el generador de consultas de Drizzle para las lecturas y escrituras normales. El SQL sin procesar omite la seguridad de tipos y es más difícil de mantener.
