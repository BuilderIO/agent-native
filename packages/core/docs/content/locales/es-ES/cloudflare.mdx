# Cloudflare

<a id="cloudflare-workers"></a>

Cloudflare Workers ejecuta tu aplicación en la red de Cloudflare, así que no hay ningún servidor
que configurar ni mantener en ejecución. La compilación convierte la aplicación en un Worker, que gestiona
las páginas y la API de la aplicación, además de archivos estáticos que Cloudflare sirve directamente.
Cloudflare le da a la aplicación una dirección pública con HTTPS.

Esta guía explica cómo implementar una aplicación independiente desde cero. Vas a
crear la aplicación, darle una base de datos de producción y un secreto de autenticación, preparar la
base de datos, compilar el Worker, guardar los secretos en Cloudflare y, después, implementarlo.

<Callout tone="info">

Se requiere Node.js `22.22+`.

</Callout>

También necesitas una cuenta de Cloudflare. Ejecuta los comandos de esta guía en tu propio
equipo. Wrangler, la herramienta de línea de comandos de Cloudflare, sube el Worker terminado
a Cloudflare por ti.

## Paso 1: Crea la aplicación {#step-1-create-the-app}

Crea tu nueva aplicación independiente. El siguiente ejemplo crea una aplicación a partir de la plantilla Chat,
pero puedes empezar desde cualquier plantilla. Entra en la carpeta de la aplicación e
instala sus dependencias. `corepack enable` activa la versión de `pnpm` que la aplicación
espera, así que no necesitas instalar `pnpm` por tu cuenta.

```bash
npx --yes @agent-native/core@latest create my-app --standalone --template chat

cd my-app

corepack enable

pnpm install
```

Si quieres, reemplaza `my-app` por el nombre de tu aplicación. El resto de esta guía
supone que estás dentro de la carpeta de la aplicación.

## Paso 2: Configura los secretos del entorno {#step-2-configure-environment-secrets}

La aplicación lee su configuración de producción desde variables de entorno:

| Variable             | Obligatoria | Propósito                                                                      |
| -------------------- | ----------- | ------------------------------------------------------------------------------ |
| `DATABASE_URL`       | Sí          | Conecta la aplicación con su base de datos PostgreSQL                          |
| `BETTER_AUTH_SECRET` | Sí          | Firma las sesiones de los usuarios                                             |
| `BETTER_AUTH_URL`    | No          | Define la dirección pública que usan las personas para acceder a tu aplicación |

Las exportaciones siguientes hacen que los comandos posteriores funcionen en esta terminal. Antes de
implementar, guarda estas mismas variables en la configuración del entorno del proyecto o servicio de tu host.
El paso 5 muestra cómo guardarlas en Cloudflare.

### URL de la base de datos {#database-url}

Durante el desarrollo local, la aplicación guarda los datos en una base de datos local cuando
`DATABASE_URL` no está definida. Una aplicación implementada necesita una base de datos PostgreSQL real que
conserve sus datos entre implementaciones. Un Worker no puede conservar archivos entre solicitudes, así que
la base de datos debe estar fuera de Cloudflare Workers. Copia la cadena de conexión
de tu proveedor y expórtala:

```bash
export DATABASE_URL='your-postgres-url-string'
```

Las [guías de proveedores de bases de datos](/docs/neon) muestran dónde encontrar la cadena de conexión
de cada proveedor.

<Callout tone="warning">

Elige un proveedor de PostgreSQL persistente, como Neon, Supabase o Amazon RDS.

</Callout>

### Secreto de autenticación {#auth-secret}

Genéralo una sola vez y mantenlo igual en todas las implementaciones.

La aplicación usa `BETTER_AUTH_SECRET` para firmar las sesiones de los usuarios. Si cambia, se cierra la sesión de
todos los usuarios que la tenían iniciada. El siguiente comando genera un valor aleatorio:

```bash
export BETTER_AUTH_SECRET="$(openssl rand -hex 32)"
```

Guarda el valor generado en un lugar seguro, como un gestor de contraseñas. Usa el
mismo valor cada vez que implementes.

### URL pública {#public-url}

Es opcional. Defínela cuando uses un dominio personalizado, un proxy inverso o un flujo de autenticación u OAuth
que necesite un origen público fijo.

`BETTER_AUTH_URL` es la dirección pública que usan las personas para acceder a tu aplicación. Sin
ella, la aplicación deduce su dirección a partir de cada solicitud entrante. Eso suele
funcionar bien con la dirección que te da Cloudflare, pero defínela cuando conectes un dominio
personalizado para que los enlaces de inicio de sesión y las redirecciones de OAuth usen ese dominio.

```bash
export BETTER_AUTH_URL='https://your-domain.example'
```

## Paso 3: Ejecuta las migraciones {#step-3-migrate}

Las migraciones crean y actualizan las tablas que la aplicación necesita en tu base de datos. Ejecuta
esto antes de la primera implementación:

```bash
pnpm migrate:production
```

El comando se ejecuta en tu equipo y se conecta a la base de datos de producción con
la `DATABASE_URL` que exportaste en el paso 2. Vuelve a ejecutarlo después de actualizar la
aplicación y antes de implementar la nueva versión.

## Paso 4: Compila {#step-4-build}

Compila la aplicación como un Worker de Cloudflare:

```bash
NITRO_PRESET=cloudflare_module pnpm build
```

`NITRO_PRESET=cloudflare_module` compila la aplicación en el formato que Cloudflare Workers
espera. La compilación escribe el Worker en la carpeta `.output/server` y los
archivos estáticos en la carpeta `.output/public`.

La compilación también escribe un archivo de configuración de Wrangler en
`.output/server/wrangler.json`. Este archivo le indica a Wrangler qué debe implementar y
le da su nombre al Worker. El nombre sale del `package.json` de la aplicación, así que una
aplicación creada como `my-app` se convierte en un Worker llamado `my-app`. Si la carpeta es un repositorio
de Git con un remoto, el nombre sale del repositorio. La compilación
muestra el nombre que eligió.

## Paso 5: Inicia sesión y guarda los secretos {#step-5-log-in-and-save-the-secrets}

Inicia sesión en Cloudflare desde la línea de comandos:

```bash
npx wrangler login
```

Guarda las dos variables obligatorias como secretos en el Worker:

```bash
printf '%s' "$DATABASE_URL" | npx wrangler secret put DATABASE_URL --config .output/server/wrangler.json
```

```bash
printf '%s' "$BETTER_AUTH_SECRET" | npx wrangler secret put BETTER_AUTH_SECRET --config .output/server/wrangler.json
```

Cada comando lee el valor que exportaste en el paso 2 y lo guarda en Cloudflare, así que
no tienes que pegar los secretos a mano. `--config` le indica a Wrangler el archivo de
configuración del paso 4, para que los secretos vayan al Worker con el nombre que eligió la
compilación. La primera vez, el Worker todavía no existe. Como el valor se pasa por una tubería, Wrangler crea el Worker automáticamente sin preguntar.

Si defines `BETTER_AUTH_URL`, guárdala de la misma forma. También puedes ver y cambiar
estos valores más adelante en la configuración del Worker en el panel de Cloudflare.

## Paso 6: Implementa {#step-6-deploy}

Sube el Worker y publícalo:

```bash
npx wrangler deploy --config .output/server/wrangler.json
```

`--config` le indica a Wrangler el archivo de configuración del paso 4, que le dice
dónde encontrar el Worker y los archivos estáticos.

Cuando el comando termina, muestra la dirección de la aplicación, que termina en
`workers.dev`. Ábrela y crea la primera cuenta.

## Implementa actualizaciones {#deploy-updates}

Para publicar una nueva versión, vuelve a ejecutar los comandos de migración, compilación e implementación desde
la carpeta de la aplicación:

```bash
pnpm migrate:production

NITRO_PRESET=cloudflare_module pnpm build

npx wrangler deploy --config .output/server/wrangler.json
```

Los secretos se mantienen guardados en el Worker entre implementaciones, así que no necesitas
repetir el paso 5.
