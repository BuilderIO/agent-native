# Carga de archivos

El marco proporciona una abstracción de carga de archivos que enruta las cargas a través de un proveedor configurable. Las plantillas llaman a `uploadFile()` y obtienen un URL. El backend de almacenamiento se puede intercambiar sin cambiar el código de la aplicación.

## Cómo funciona {#how-it-works}

Las solicitudes de carga van a `POST /_agent-native/file-upload`, que las envía al proveedor activo. Puedes comprobar qué proveedor está configurado en `GET /_agent-native/file-upload/status`.

El orden de resolución del proveedor es:

1. **Proveedores registrados por el usuario**: proveedores personalizados registrados a través de `registerFileUploadProvider()`.
2. **Proveedor Builder.io**: integrado, se activa automáticamente cuando Builder.io está conectado.
3. **Sin proveedor**: la carga se rechaza y el chat muestra un aviso para configurar el almacenamiento. Los datos binarios nunca se persisten en SQL.

Entre los proveedores registrados por el usuario, gana el primero que se registró y que informa estar configurado. `registerFileUploadProvider()` es idempotente por `id`. Registrar con un id que ya está en uso reemplaza al proveedor existente.

La interfaz decide si mostrar un aviso de configuración de almacenamiento usando solo la comprobación síncrona `isConfigured()`, antes de intentar una carga. La carga real comprueba tanto `isConfigured()` como `isConfiguredForRequest()`. Un proveedor que solo informa estar configurado a través de `isConfiguredForRequest()` permanece invisible para el aviso de configuración, aunque las cargas a través de él tendrían éxito.

## Se requiere almacenamiento para cargas duraderas {#storage-required}

Cuando no hay ningún proveedor configurado, `uploadFile()` devuelve `null` y la ruta multipart devuelve `503`. Los archivos adjuntos del chat solo permanecen disponibles durante la solicitud actual, el agente recibe una indicación para configurar el almacenamiento y la transcripción guarda un marcador de configuración en lugar de la carga binaria. Este comportamiento de fallo seguro mantiene SQL pequeño y hace visible la configuración faltante.

## Alojamiento en Builder.io {#builder-hosting}

Cuando tu aplicación está conectada a Builder.io, las cargas de archivos se enrutan automáticamente al alojamiento de activos de Builder. El nivel gratuito de Builder.io incluye este almacenamiento gestionado. Los archivos se sirven desde un CDN sin necesidad de configuración, y el URL duradero se guarda en el hilo del chat para que turnos posteriores puedan reutilizarlo. Esta es la configuración de producción recomendada.

## Proveedores personalizados {#custom-providers}

El marco ya incluye un proveedor integrado para almacenamiento compatible con
S3 (AWS S3, Cloudflare R2, MinIO y similares). Conéctalo con variables de
entorno o desde la lista de verificación de incorporación de la barra
lateral. No se necesita código. Consulta [Onboarding](/docs/onboarding).

Registra un proveedor personalizado solo para un tipo distinto de backend.
Este ejemplo carga a través de una API HTTP genérica usando `fetch()`:

```ts filename="server/plugins/file-upload.ts"
import { registerFileUploadProvider } from "@agent-native/core/file-upload";
import { defineNitroPlugin } from "@agent-native/core/server";

export default defineNitroPlugin(() => {
  registerFileUploadProvider({
    id: "my-storage",
    name: "My Storage",
    isConfigured: () => !!process.env.UPLOAD_ENDPOINT,
    upload: async ({ data, filename, mimeType }) => {
      const endpoint = process.env.UPLOAD_ENDPOINT!;
      const body = new FormData();
      body.append("file", new Blob([data], { type: mimeType }), filename);

      // This example assumes an upload API that accepts a multipart file
      // and returns { url }. Adjust the request and response handling to
      // match your own provider's actual contract.
      const response = await fetch(endpoint, { method: "POST", body });
      if (!response.ok) {
        throw new Error(`Upload failed with status ${response.status}`);
      }

      const { url } = await response.json();
      return { url, provider: "my-storage" };
    },
  });
});
```

Usa `resolveSecret()` de `@agent-native/core/server` en lugar de una
variable de entorno cuando el proveedor necesite una credencial real, como
una clave API. Consulta [Seguridad — Gestión de secretos](/docs/security#secrets).

## API de carga {#upload-api}

La interfaz `FileUploadProvider`:

```ts
interface FileUploadProvider {
  id: string; // Unique id, e.g. "s3"
  name: string; // Human-readable name
  isConfigured: () => boolean; // True when ready from sync runtime state
  isConfiguredForRequest?: () => Promise<boolean>; // True from scoped DB secrets
  upload: (input: FileUploadInput) => Promise<FileUploadResult>;
}

interface FileUploadInput {
  data: Uint8Array | Buffer; // File contents
  filename?: string; // Original filename
  mimeType?: string; // MIME type, e.g. "image/png"
  ownerEmail?: string; // For request-scoped provider credentials
  stableUrl?: boolean; // Builder.io hint: one stable URL while compression finishes
  recordAsset?: boolean; // Builder.io hint: set false to skip the asset library
}

interface FileUploadResult {
  url: string; // Public URL for the uploaded file
  id?: string; // Provider-specific id
  provider: string; // Which provider handled it
}
```

Usa `uploadFile()` de `@agent-native/core/file-upload` en actions o código de servidor:

```ts
import { uploadFile } from "@agent-native/core/file-upload";

const result = await uploadFile({
  data: fileBuffer,
  filename: "photo.jpg",
  mimeType: "image/jpeg",
});

if (result) {
  // Provider handled it. result.url is the public URL.
} else {
  // No provider configured. Show the storage setup CTA, or skip.
}
```

## Cargas reanudables / en streaming {#resumable}

Un proveedor puede implementar opcionalmente un bloque `resumable` en `FileUploadProvider` para cargas que necesitan transmitirse al almacenamiento a medida que llegan los datos, en lugar de almacenar primero el archivo completo en un búfer. La plantilla Clips usa esto para retransmitir una grabación al almacenamiento fragmento a fragmento mientras aún se está grabando, en lugar de ensamblar el blob completo después de que se detiene el grabador.

```ts
interface FileUploadProvider {
  // ...id, name, isConfigured, upload...

  resumable?: {
    startSession(
      filename: string,
      mimeType: string,
      maxBytes: number,
    ): Promise<ResumableUploadSession>;
    relayChunk(
      session: ResumableUploadSession,
      contentRange: string,
      bytes: Uint8Array,
      options?: { mimeType?: string },
    ): Promise<ResumableChunkResult>;
    completeSession(
      session: ResumableUploadSession,
      filename: string,
      options?: { stableUrl?: boolean; recordAsset?: boolean },
    ): Promise<string>;
    // Best-effort provider cleanup for a session the caller will not resume.
    abortSession?(session: ResumableUploadSession): Promise<void>;
  };
}

interface ResumableUploadSession {
  sessionId: string; // Provider-specific: GCS Location URI, S3 UploadId, etc.
  meta: Record<string, unknown>; // Provider state carried between calls
}

interface ResumableChunkResult {
  ok: boolean;
  status: number;
  updatedMeta?: Record<string, unknown>; // Merged back into the stored session
}
```

Cuando `resumable` está presente, los llamadores que transmiten datos a medida que llegan (como un grabador) llaman una vez a `startSession`, llaman repetidamente a `relayChunk` a medida que llegan los bytes y llaman a `completeSession` cuando termina la transmisión. Esto reemplaza la llamada única a `upload()` con búfer. Un proveedor sin bloque `resumable` solo ve la ruta con búfer. Impleméntalo solo cuando tu backend de almacenamiento tenga una API nativa de carga fragmentada/reanudable (multiparte de S3, cargas reanudables de GCS, etc.) que valga la pena exponer.
