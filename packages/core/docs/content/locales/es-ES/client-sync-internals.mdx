# Sincronización interna

[Sincronización en vivo](/docs/key-concepts#polling-sync) cubre el modelo mental: una escritura del agente se convierte en un evento de cambio, `useDbSync()` lo recoge, y las consultas afectadas se recuperan. Esta página cubre el mecanismo subyacente que la mayoría de las apps nunca tocan directamente: los contadores de versión de cambio que incrementa `useDbSync()`, y cómo incorporarlos en una llamada `useQuery()` sin procesar que no pasa por `useActionQuery()`.

`useActionQuery()` ya se recupera automáticamente cuando se completa una acción mutante (consulta [Datos y sincronización](/docs/client-data#fetching-mutating)). Recurre a `useChangeVersion()`/`useChangeVersions()` solo cuando estés sincronizando una llamada `useQuery()` sin procesar fuera de esa ruta, como un helper de cliente de bajo nivel que lee el estado de una integración.

## Cómo funcionan las versiones de cambio {#how-it-works}

Cuando ocurre una mutación de base de datos del lado del servidor, el servidor registra un evento de cambio etiquetado con una clave `source`. `useDbSync()` recibe ese evento e incrementa un contador local para esa fuente. Incorporar el contador en una clave de consulta de React Query hace que la consulta se recupere automáticamente cada vez que el backend reporta nueva actividad para esa fuente.

En el ejemplo siguiente, una llamada `useQuery()` sin procesar lee un dashboard directamente, incorporando el contador de versión de la fuente `"dashboards"` en su clave de consulta para que se recupere cada vez que cambie esa fuente:

```tsx
import { useQuery } from "@tanstack/react-query";
import { useChangeVersion } from "@agent-native/core/client/hooks";

function DashboardView({ id }) {
  const version = useChangeVersion("dashboards");

  const { data } = useQuery({
    queryKey: ["dashboard", id, version],
    queryFn: () => fetchDashboard(id),
    placeholderData: (prev) => prev,
  });

  return <div>{data?.title}</div>;
}
```

`placeholderData: (prev) => prev` mantiene los datos anteriores en pantalla durante la recuperación, así que la vista no parpadea a un estado de carga.

## Dos rutas hacia una recuperación {#latency-models}

Una mutación llega a la UI de una de dos formas, y tienen latencia distinta.

Una mutación local, una que acaba de hacer tu propia llamada a `useActionMutation()`, emite un evento `source: "action"` en cuanto tiene éxito. Cada consulta que depende de esa acción se recupera de inmediato. No hay retraso de ida y vuelta, ya que la pestaña que hizo la escritura ya sabe de ella.

Una mutación remota, del agente, un webhook, otra pestaña, u otro usuario, tiene que llegar primero a esta pestaña. `useDbSync()` la recoge por SSE casi de inmediato, o por el respaldo de sondeo dentro de unos dos segundos si SSE no está disponible. Solo una vez que llega ese evento, el contador de versión correspondiente se incrementa y la consulta se recupera en segundo plano.
