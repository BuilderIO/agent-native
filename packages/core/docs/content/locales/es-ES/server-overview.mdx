# Servidor

El directorio `server/` es la capa de infraestructura de una aplicación nativa del agente. Se encarga de las tareas de arranque, la autenticación y las superficies HTTP que las actions no cubren. La mayor parte del comportamiento del producto pertenece a [Actions](/docs/actions). El servidor es lo que hace que esas actions estén disponibles.

## Dónde encaja el servidor {#role}

En una aplicación web tradicional, el servidor es donde vive la mayor parte de la lógica. Las reglas de negocio, el acceso a datos y la presentación ocurren todos dentro de los manejadores de ruta. Las aplicaciones nativas del agente funcionan de otra forma. La lógica vive en las actions, que el agente y la UI comparten como socios en igualdad de condiciones. El trabajo del servidor es la coordinación: ejecutar migraciones de la base de datos, configurar la autenticación, montar el bucle del agente y gestionar el conjunto reducido de asuntos HTTP que las actions no pueden expresar por sí solas.

Las solicitudes del navegador, el bucle del agente y los clientes de API externos se enrutan todos a través del mismo servidor Nitro y leen de la misma base de datos SQL. No existe un backend independiente para el agente ni para la UI. La capa de servidor es lo que expone las actions al mundo exterior.

## Qué hay en el directorio server/ {#server-directory}

Estos son los directorios y archivos dentro de `server/` que incluye toda aplicación nativa del agente. Cada uno corresponde a una pieza concreta de la capa de servidor: qué hace, cuándo recurrir a él y cómo se conecta con el resto del marco.

| Página                                     | Qué cubre                                                                                                          |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| **[Base de datos](/docs/server-database)** | Definición de esquemas con los ayudantes `table()`, `getDb` y los patrones de tablas ownable                       |
| **[Middleware](/docs/server-middleware)**  | Guardias de autenticación en `server/middleware/` y por qué se ejecutan ahí en lugar de en un plugin               |
| **[Plugins](/docs/server-plugins)**        | Los tres plugins de inicio que incluye toda aplicación: migraciones de base de datos, autenticación y agent-chat   |
| **[Rutas](/docs/server-routes)**           | Rutas basadas en archivos, el catch-all de SSR y el alcance de las rutas personalizadas al usuario de la solicitud |

## Nitro {#nitro}

[Nitro](https://nitro.build) es el conjunto de herramientas de servidor que impulsa la capa HTTP nativa del agente. La mayor parte de lo que configurará en `server/` es Nitro: rutas basadas en archivos, plugins de inicio y middleware.

- **Enrutamiento basado en archivos**: el nombre del archivo se asigna directamente a un método HTTP y una ruta URL, sin necesidad de registro. `server/routes/api/health.get.ts` se convierte automáticamente en `GET /api/health`. Visite [Rutas](/docs/server-routes) para más detalles.
- **Plugins**: código que se ejecuta una sola vez al iniciar el servidor, antes de que se sirva ninguna solicitud. Las migraciones de la base de datos, la configuración de autenticación y el montaje del agent-chat ocurren todos en `server/plugins/`. Visite [Plugins](/docs/server-plugins) para más detalles.
- **Middleware**: código que se ejecuta en cada solicitud entrante antes de que llegue a una ruta. El guardia de autenticación vive en `server/middleware/`. Visite [Middleware](/docs/server-middleware) para más detalles.

Nitro también es independiente del despliegue. La misma aplicación se despliega en Node.js, Cloudflare Workers, Netlify, Vercel y otros entornos de ejecución sin cambios de código. Basta con configurar un preset. Consulte [Implementación](/docs/deployment).

La API subyacente de solicitud/respuesta es [H3](https://h3.unjs.io). Cuando vea `defineEventHandler`, `createError` o `getQuery` en rutas personalizadas, eso es H3. Los [documentos de Nitro](https://nitro.build/guide) y los [documentos de H3](https://h3.unjs.io) son la referencia para cualquier cosa que el marco no cubra directamente.

## Recurrir primero a las Actions {#actions-first}

La arquitectura de Agent Native es distinta. Cada vez que piense en una nueva función para su aplicación, considere primero si puede ser una action. Por ejemplo, si tanto la UI como el agente necesitan hacer algo, defina una action en lugar de una ruta de API personalizada. Las actions se convierten automáticamente en:

- Herramientas del agente.
- Hooks de frontend tipados.
- Endpoints HTTP bajo `/_agent-native/actions/:name`.
- Herramientas invocables por MCP y A2A.
- Comandos de CLI para el desarrollo.

Use rutas `/api/*` personalizadas solo cuando necesite un protocolo con forma de ruta o un comportamiento binario/de streaming. Para más detalles, visite [Actions](/docs/actions).

## ¿Qué sigue? {#whats-next}

- [**Actions**](/docs/actions): la superficie de operaciones predeterminada. Recurra a una ruta personalizada solo cuando no encaje.
- [**Base de datos**](/docs/server-database): el patrón `getDb()`/esquema que importan tanto las rutas personalizadas como las actions
- [**Middleware**](/docs/server-middleware): guardias de autenticación y el directorio `server/middleware/`
- [**Plugins**](/docs/server-plugins): plugins de inicio para migraciones, autenticación y el agente
- [**Rutas**](/docs/server-routes): rutas basadas en archivos, contexto de solicitud y el catch-all de SSR
