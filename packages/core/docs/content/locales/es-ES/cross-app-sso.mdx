# SSO de organización y federación entre aplicaciones

El SSO de organización usa el proveedor OIDC o SAML de una empresa para iniciar sesión en un despliegue de Agent-Native. La federación entre aplicaciones comparte identidad verificada o contexto de organización entre despliegues separados. Su configuración y límites de confianza son distintos.

Las páginas de inicio de sesión de las aplicaciones Agent-Native registradas de
forma exacta ofrecen la acción "Continue with Agent-Native". Esta inicia el
flujo existente de Dispatch con correo verificado. Esta página describe la
federación en el navegador, Desktop y el servidor.

## Federación entre aplicaciones

### Espacio de trabajo en Desktop

El inicio de sesión del espacio de trabajo es una acción explícita en
Configuración de Desktop. Cuando está habilitado, Desktop puede aprovisionar
aplicaciones registradas elegibles mediante su intermediario dedicado. Cada
aplicación conserva su propio almacén de usuarios, sesión y controles de acceso.
Desktop no intercepta la navegación anónima del navegador a una página de inicio
de sesión.

Una aplicación es elegible solo si:

- Desktop habilita el SSO del espacio de trabajo para la aplicación.
- La URL de producción es HTTPS exacto.
- Dispatch tiene un registro exacto del servidor para la aplicación.
- La bandera de lanzamiento <code>desktop.workspace-sso</code> está habilitada.

La preferencia por dispositivo <code>desktopSsoEnabled</code> está habilitada de
forma predeterminada. Un valor explícito de false mantiene la exclusión. Si
falta la bandera, la preferencia, el registro o una comprobación de elegibilidad,
el inicio de sesión normal por aplicación sigue disponible.

### Federación del servidor

Los intermediarios y clientes del servidor usan un protocolo breve y verificado
por el servidor. Las aplicaciones oficiales con registro exacto inician ese
mismo protocolo cuando la persona elige "Continue with Agent-Native":

1. El cliente solicita un vínculo exacto con una aplicación registrada.
2. Dispatch autentica la identidad del espacio de trabajo y devuelve un código
   de autorización breve y de un solo uso.
3. El servidor de la aplicación canjea el código con su verificador PKCE.
4. La aplicación verifica la aserción firmada, la aplicación exacta, el callback,
   el alcance, el nonce y la expiración.
5. La aplicación vincula o crea un usuario local por correo verificado y emite su
   sesión local normal.

La aserción solo se devuelve mediante el intercambio entre servidores. Nunca
aparece en una URL del navegador ni es un token portador reutilizable.

## Federación de organizaciones

La bandera <code>organization.cross-app-federation</code> está desactivada por
defecto. Al habilitarla, la aplicación de origen registra su organización local
en Dispatch y guarda la correspondencia exacta

<code>(identity_authority, identity_id)</code>. La aplicación destino acepta el
ID canónico, el nombre y el rol verificado solo desde la aserción verificada por
el servidor.

Los nombres de organizaciones, dominios de correo y cookies del navegador no
son claves de unión. Una organización local sin correspondencia no cambia hasta
una migración explícita. Las membresías vinculadas siguen usando los controles
de acceso normales de la aplicación destino.

La federación usa una credencial separada para cada aplicación de origen:

- Configura <code>AGENT_NATIVE_IDENTITY_FEDERATION_SECRET</code> en la aplicación
  de origen.
- Configura la credencial coincidente
  <code>AGENT_NATIVE_IDENTITY_FEDERATION_SECRET_&lt;NORMALIZED_APP_ID&gt;</code>
  en Dispatch.
- No reutilices <code>A2A_SECRET</code> para este límite de autoridad.

El sufijo del ID de aplicación reemplaza cada secuencia de caracteres no
alfanuméricos por un guion bajo y convierte el resultado a mayúsculas. Por
ejemplo, el ID <code>workspace-reports</code> usa

<code>AGENT_NATIVE_IDENTITY_FEDERATION_SECRET_WORKSPACE_REPORTS</code>.

Las escrituras de identidad y organización son aditivas. Los usuarios existentes
con el mismo correo se reutilizan sin modificarlos. Un correo verificado nuevo
crea un usuario local. Desactivar la federación no elimina datos.

## Configuración

<code>AGENT_NATIVE_IDENTITY_HUB_URL</code> identifica Dispatch para las rutas
del servidor y del navegador cuando una aplicación autoalojada necesita una
configuración explícita. Las aplicaciones oficiales con registro exacto ofrecen
la acción "Continue with Agent-Native" en su página de inicio de sesión. La
bandera <code>browser.identity-sso</code> sigue controlando el inicio silencioso
con <code>prompt=none</code> y la inicialización tras el inicio de sesión local.
El inicio de sesión local sigue disponible como alternativa.

Para una implementación autoalojada de Dispatch, registra cada aplicación
personalizada con su ID, client ID, origen HTTPS, ruta de callback y capacidad

<code>identity-sso</code> exactos mediante
<code>IDENTITY_SSO_APP_REGISTRY_JSON</code>.

Las inscripciones de producción deben usar HTTPS y una ruta de callback exacta.
Localhost solo se permite durante el desarrollo local. Se rechazan subdominios
desconocidos, IDs de aplicación que no coinciden, rutas arbitrarias y callbacks
entre orígenes.

## Verificación y reversión

Después del despliegue:

1. Comprueba que el correo, la contraseña, el enlace mágico y los proveedores
   configurados siguen funcionando en un navegador.
2. Comprueba que aparece la acción "Continue with Agent-Native" y que el inicio
   de sesión local sigue disponible. Con <code>browser.identity-sso</code>
   desactivado, comprueba que ambos siguen funcionando. Con la bandera activada,
   comprueba el inicio silencioso con <code>prompt=none</code> y el formulario
   local como alternativa.
3. Si Desktop SSO está habilitado, verifica una aplicación registrada exacta
   desde la acción explícita de Configuración de Desktop.
4. Si la federación de organizaciones está habilitada, verifica el ID exacto de
   la organización y el rol de membresía en la aplicación destino.

Para revertir el inicio silencioso en el navegador o la ruta de Desktop,
deshabilita su bandera. Para quitar la acción explícita del navegador en una
aplicación autoalojada, elimina <code>AGENT_NATIVE_IDENTITY_HUB_URL</code> o su
registro exacto y vuelve a desplegar. El inicio de sesión local sigue disponible
y los registros aditivos de identidad y organización se conservan.

## Guía de lanzamiento de SSO de identidad en el navegador

Habilita `browser.identity-sso` primero para un correo de prueba. Inicia sesión en Dispatch, cierra sesión en la app objetivo y comprueba la prueba silenciosa al cargarla. Repite sin sesión del hub y confirma que `login_required` vuelve al formulario local antes de ampliar el grupo. La primera activación puede requerir revocar las sesiones existentes una vez.
