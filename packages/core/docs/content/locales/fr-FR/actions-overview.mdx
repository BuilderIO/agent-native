# Vue d’ensemble

Les actions sont la source unique de vérité pour tout ce que fait votre application. Définissez-en une avec `defineAction()` et placez-la dans `actions/`. Chaque surface ci-dessous la récupère automatiquement. Vous écrivez la logique une seule fois. Aucune surface n’a sa propre copie, et aucune ne peut dériver et se désynchroniser des autres.

<Cards columns={2}>

### :robot: [Outil agent](/docs/agent-surfaces)

L’agent lit la description et le schéma comme un outil qu’il peut appeler. Demandez-le dans le chat, par exemple « répondre à ce ticket » ou « résumer ce fil ».

### :components: [Hooks d’UI](/docs/client-data)

`useActionQuery()`, `useActionMutation()` et `callAction()` appellent la même action depuis React. Un clic et un message de chat exécutent exactement la même opération.

### :server: [Transport du framework](/docs/http-api)

Monté automatiquement sur `/_agent-native/actions/<name>` au démarrage. Les hooks d’UI appellent cette route en coulisses, et un client HTTP externe peut aussi l’appeler directement.

### :plug: [Outil MCP](/docs/actions-other-surfaces#mcp)

Apparaît comme un outil pour tout hôte MCP : Claude, Claude Desktop, Cursor, Codex. Utilisez-le lorsqu’un autre client IA doit piloter votre application.

### :network: [Outil A2A](/docs/actions-other-surfaces#a2a)

D’autres applications natives d’agent la découvrent et l’appellent via A2A. Utilisez-la lorsqu’une seconde application de votre espace de travail a besoin que celle-ci agisse en son nom.

### :terminal: [Commande CLI](/docs/actions-other-surfaces#cli)

`pnpm action <name>` l’exécute depuis un terminal. Utilisez-la pour les scripts, les tâches cron, et les tests manuels rapides.

</Cards>

La plupart des applications construisent une couche API séparée entre le frontend et la base de données, une couche que seul le navigateur peut appeler. Un agent qui veut la même capacité a besoin de sa propre intégration séparée, écrite et maintenue à nouveau. Les applications natives d’agent évitent cette séparation. L’UI et l’agent appellent exactement la même action, il n’y a donc qu’une seule implémentation à écrire, et un seul endroit où un bug peut se cacher.

Si l’UI et l’agent doivent tous les deux faire quelque chose, utilisez une action plutôt qu’une route personnalisée. Pour le cas rare où un protocole en forme de route est le bon choix, consultez [Préférer les actions pour les opérations d’application](/docs/server-overview#actions-first).

## Où s’intègrent les actions {#role}

`app/` (consultez [Vue d’ensemble du client](/docs/client-overview#role)) et l’agent aboutissent tous deux aux mêmes actions et à la même base de données SQL. Il n’existe pas de « backend d’application » séparé auquel cette couche parle et que l’agent ne pourrait pas aussi atteindre. Construire une fonctionnalité signifie définir une opération ici et obtenir en même temps une UI, un outil agent, et toute autre surface pour elle.

`actions/` lui-même est un dossier plat. Chaque fichier est une action : un appel à `defineAction()` exporté comme export par défaut du fichier. Le framework scanne ce dossier au démarrage et monte chaque fichier qu’il trouve. Il n’y a aucune étape d’enregistrement ni de fichier d’index à tenir à jour.

Le corps de `run()` d’une action est du code serveur ordinaire, il touche donc généralement à quelques autres répertoires :

Rien en dehors de `actions/` ne doit importer directement la fonction `run` d’une action. Appelez-la plutôt via l’une des surfaces ci-dessus : l’outil agent, un hook d’UI, HTTP, MCP, A2A, ou la CLI. Chacun de ces chemins exécute la même validation de schéma, les mêmes contrôles d’accès, et la même piste d’audit.

## Commencer avec une seule action {#hello-action}

La première opération d’une application chat-first peut être minuscule. Dans le template Chat,
remplacez `actions/hello.ts` ou ajoutez un nouveau fichier à côté :

```ts
// actions/hello.ts
import { defineAction } from "@agent-native/core/action";
import { z } from "zod";

export default defineAction({
  description: "Say hello from the local agent.",
  schema: z.object({
    name: z.string().default("world"),
  }),
  http: { method: "GET" },
  readOnly: true,
  run: async ({ name }) => {
    return { message: `Hello, ${name}!` };
  },
});
```

Exécutez-la depuis le même répertoire :

```bash
pnpm action hello '{"name":"Steve"}'
```

La CLI accepte un objet JSON comme entrée de l’action, ce qui correspond aux
appels d’outils structurés que les agents effectuent déjà. Des flags simples
fonctionnent toujours pour des exécutions manuelles rapides :

```bash
pnpm action hello --name Steve
```

Exécutez ensuite la boucle app-agent sur le répertoire :

```bash
npx agent-native agent "Call hello for Steve and explain the result"
```

C’est la même boucle app-agent que vos tâches planifiées, votre UI de chat,
vos outils MCP externes, et vos futurs écrans utiliseront. Les templates Chat
et de domaine servent à ajouter une UI autour des actions, ce n’est pas un
prérequis pour l’action elle-même.
