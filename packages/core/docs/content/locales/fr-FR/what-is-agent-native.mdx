# Qu'est-ce qu'Agent-Native ?

Agent-native est une façon de construire des logiciels où l'agent IA et la surface produit qui l'entoure sont des **partenaires à égalité**. Le chemin habituel commence par le chat, ajoute des actions typées, affiche des résultats structurés en ligne, et évolue vers des pages d'application durables autour du même état SQL. L'essentiel est que les agents et les humains partagent les mêmes actions, la même base de données et le même état.

Si vous ne retenez qu'une seule chose de cette page, retenez ceci : la plupart des applications IA s'arrêtent aujourd'hui à une étape de l'utilité, et ce manque est la plus grande erreur dans cet espace en ce moment.

## À quoi cela ressemble pour un utilisateur {#what-it-looks-like}

Imaginez un worker en arrière-plan, une boîte de réception, un calendrier, un constructeur de formulaires ou un tableau de bord analytique. Souvent le premier écran est un chat : vous demandez ce que vous voulez, l'agent guide la configuration, affiche un tableau ou un graphique, et ouvre la bonne vue de l'application. Parfois le chat est ancré sur le côté droit d'une application complète. Parfois il n'y a pas encore d'écran personnalisé parce que le flux de travail est une tâche planifiée, une file d'attente, un script ou une intégration d'agent externe. À travers ces différentes formes, vous pouvez :

- **Commencer par la vraie opération.** Une seule action durable peut s'exécuter depuis le CLI, HTTP, MCP, A2A, la boucle app-agent, et ultérieurement une interface utilisateur.
- **Cliquer sur tout ce que vous cliqueriez normalement quand il y a une interface utilisateur.** Tous les boutons, listes, tableaux de bord, raccourcis clavier — ils appellent tous les mêmes opérations que l'agent peut appeler.
- **Ou simplement demander.** Tapez « répondre à l'e-mail de Sara en disant que je serai là à 15h » dans l'agent. Il ouvre le bon fil, rédige la réponse et vous la montre pour approbation — exactement comme si vous l'aviez fait à la main.
- **Voir ce qu'il voit.** Ouvrez un e-mail, et l'agent sait lequel. Sélectionnez un graphique, et l'agent sait quel graphique. Surlignez un paragraphe et appuyez sur Cmd+I, et l'agent agit sur ce seul paragraphe.
- **Regarder-le travailler.** Pendant que l'agent fait des choses — ouvre des vues, modifie des brouillons, exécute des rapports — l'interface se met à jour en temps réel. Vous pouvez l'arrêter, le réorienter ou reprendre la main avec la souris à tout moment.
- **Le guider comme un coéquipier.** Donnez des retours, mettez en file d'attente une autre tâche, modifiez ses instructions et auditez ce qu'il a fait hier.

C'est l'expérience pour laquelle agent-native est conçu. Voici maintenant pourquoi la plupart des produits n'y arrivent pas.

## Pourquoi la plupart des « applications IA » sont insuffisantes (Le Principe de l'Échelle) {#the-ladder}

Il y a une progression que la plupart des équipes gravissent, un peu comme une échelle, et la plupart s'arrêtent un barreau trop tôt.

### Barreau 1 — un seul appel LLM (l'anti-pattern) {#rung-one}

Une zone de texte envoie une invite, l'IA retourne une chaîne de caractères, et vous l'affichez. Peut-être avec un spinner. Il n'y a aucun moyen pour l'utilisateur de corriger le tir, aucun moyen pour l'IA d'agir, aucun moyen de voir ce qui s'est passé ou pourquoi.

On voit cela partout : des « fonctionnalités IA » qui sont essentiellement un bouton « Résumer » vissé sur un produit SaaS. Elles semblent impressionnantes dans les démos et s'effondrent dès que la réalité devient complexe. Ce n'est pas un produit ; c'est un jouet.

### Barreau 2 — un chat avec des outils {#rung-two}

Maintenant l'IA peut _faire des choses_. Elle dispose d'outils — « rédiger un e-mail », « rechercher des contacts », « exécuter une requête » — et d'une interface de chat où elle travaille devant vous, montrant les appels d'outils et les résultats au fur et à mesure. C'est à cela que ressemblent Claude, ChatGPT et Cursor sous le capot.

C'est une vraie amélioration. Mais en soi, c'est encore une fenêtre de chat. Pas d'interface utilisateur correcte. Pas de tableaux de bord, pas de listes, pas de formulaires, pas de raccourcis clavier, pas de collaboration d'équipe. Si l'IA se perd, vous êtes bloqué à retaper plutôt que de simplement cliquer sur le bon bouton. Les non-développeurs ont du mal à accomplir un vrai travail dans ce format.

### Barreau 3 — agent + interface utilisateur comme partenaires à égalité {#rung-three}

C'est agent-native. Vous ajoutez une vraie application complète autour de l'agent — et de manière cruciale, chaque action que l'agent peut effectuer est aussi un bouton dans l'interface, et chaque bouton que l'utilisateur clique exécute la même logique que l'agent utilise. Une seule implémentation, deux façons d'y accéder.

Trois choses changent quand vous atteignez le barreau 3 :

- **Vous avez arrêté d'ajouter des boutons à un chatbot. Vous avez ajouté un agent à une application.** C'est un produit de bien meilleure qualité des deux côtés.
- **L'agent dispose d'un vrai contexte.** Il voit ce que vous regardez, ce que vous avez sélectionné, ce que vous venez de faire. Il écrit dans la même base de données que l'interface lit, donc son travail apparaît immédiatement.
- **Les agents externes peuvent l'utiliser aussi.** D'autres applications agent-native peuvent appeler les actions de celle-ci via le [protocole A2A](/docs/a2a-protocol). Claude Code, Codex, les applications MCP personnalisées de ChatGPT, Cursor, et d'autres hôtes MCP peuvent le piloter comme un [serveur MCP](/docs/mcp-protocol). Une seule application, de nombreux points d'entrée.

C'est le barreau 3. C'est agent-native.

## Pourquoi chaque agent a besoin d'une interface utilisateur {#why-every-agent-needs-a-ui}

Même quand l'agent fait tout le travail difficile, les humains ont encore besoin de :

- **Voir ce qu'il fait** — progression, résultats intermédiaires, ce qu'il a touché
- **Le guider** — donner des retours, interrompre, mettre en file d'attente la prochaine tâche
- **Le gérer** — modifier ses instructions, compétences, mémoire, tâches planifiées, comptes connectés
- **Inspecter son travail** — examiner les brouillons, auditer l'historique, annuler les erreurs
- **Partager ses résultats** — tableaux de bord, rapports, formulaires, liens à envoyer aux coéquipiers

Au minimum, « une interface pour l'agent » est un tableau de bord d'observabilité et de gestion. Au maximum, c'est une application SaaS complète avec l'agent intégré comme co-pilote. Les deux extrémités comptent comme agent-native, et la surface peut évoluer de l'un à l'autre sans réécriture.

Vous n'avez pas à choisir toutes les surfaces dès le départ. L'agent peut commencer dans un chat riche, afficher une interface native en ligne, vivre à l'intérieur d'une application complète, ou s'exécuter depuis des canaux d'automatisation et d'agents externes autour de la même surface d'action — voir [Agent Surfaces](/docs/agent-surfaces) pour les formes concrètes et les API.

## Pourquoi chaque application bénéficie d'un agent {#why-every-app-benefits-from-an-agent}

L'autre côté est tout aussi important. Les produits SaaS existants continuent de heurter le même mur : 80 % de ce dont vous avez besoin fonctionne très bien, et 20 % vous ne pouvez tout simplement pas le changer. Ajouter une barre latérale de chat résout rarement ce problème — le chat ne peut généralement pas vraiment _faire_ les choses que l'interface peut faire.

Agent-native renverse cela. Parce que chaque action dans l'application est définie une fois et exposée à la fois comme un bouton et comme un outil agent, l'agent peut faire tout ce que les boutons peuvent faire — et plus encore — sans un « monde IA » séparé à maintenir. Le langage naturel devient une entrée de première classe aux côtés des clics.

L'argument n'est pas « les agents remplacent l'interface utilisateur ». C'est « **les agents appartiennent à l'intérieur des applications, avec une interface par-dessus, comme partenaires à égalité** ». Même une application automation-first a encore besoin d'une surface pour que les humains supervisent, configurent et la pilotent — généralement un chat, un historique de tâches ou une petite page de statut. Voir [Agent Surfaces — Application automation-first](/docs/agent-surfaces#headless).

## Parité agent + interface utilisateur {#agent-ui-parity}

C'est le principe fondateur.

- **Depuis l'interface utilisateur** — cliquer sur des boutons, remplir des formulaires, naviguer dans les vues. L'interface écrit dans la base de données ; l'agent voit les résultats.
- **Depuis l'agent** — langage naturel, autres agents via A2A, Slack, Telegram. L'agent écrit dans la base de données ; l'interface se met à jour automatiquement.

Un bon modèle mental est une machine d'état partagée. La surface utilisateur et la surface agent
soumettent toutes deux des actions typées ; ces actions se comportent comme des événements de réducteur avec
un schéma et une limite de permission autour d'eux : valider l'entrée, autoriser l'acteur,
appliquer la mise à jour d'état, puis diffuser/afficher le résultat. L'interface est principalement
une projection de cet état résultant. L'agent ne devine pas à partir du DOM ni
ne mute directement l'état privé des composants ; il interagit via la même couche d'action typée
que l'interface utilise.

## Personnalisation habituellement réservée aux outils avancés {#workspace-customization}

La raison pour laquelle des outils comme Claude Code semblent si puissants n'est pas le modèle — c'est la **couche de personnalisation** : instructions par projet, compétences, mémoire, sous-agents, services connectés. Vous pouvez façonner l'agent selon votre codebase, vos préférences, votre équipe.

Agent-native donne à chaque utilisateur cette même couche de personnalisation — sans jamais quitter l'application. Chaque application est livrée avec des **ressources agent** personnelles que vous (ou n'importe qui dans votre équipe) pouvez utiliser pour :

- Modifier les règles d'équipe que l'agent de chacun lit
- Laisser l'agent mémoriser automatiquement les préférences au fur et à mesure que vous le corrigez
- Écrire des guides pratiques réutilisables comme commandes `/slash`
- Conserver des sous-agents personnalisés pour des tâches spécifiques (invoqués avec `@mentions`)
- Planifier des tâches à exécuter selon un cron (ex. : « chaque lundi matin, résumer la semaine passée »)
- Connecter des services externes (Gmail, Stripe, Slack, API internes) via des serveurs MCP par utilisateur

Le twist : tout est stocké dans la base de données, pas dans le système de fichiers. Il n'y a pas d'environnement de développement à démarrer, pas de conteneur par utilisateur. Chaque utilisateur obtient son propre ensemble complet de ressources agent — mémoire personnelle, connexions personnelles, compétences personnelles — pour pratiquement rien, parce que tout n'est que des lignes dans une table. C'est ce qui rend la flexibilité de niveau Claude Code viable dans un vrai produit SaaS multi-locataire.

Voir [Ressources Agent](/docs/agent-resources) pour le concept complet.

## Ce qui le différencie {#what-makes-it-different}

| Approche                                         | Description                                                                                                                                                         |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Applications traditionnelles avec IA greffée** | L'IA est une réflexion après coup. Limitée à la complétion automatique, aux résumés, ou à une barre latérale de chat qui ne peut rien faire dans l'application.     |
| **Interfaces purement chat / agent**             | Puissantes mais inaccessibles. Pas de tableaux de bord, pas de flux de travail, pas de persistance. Les non-développeurs ne peuvent pas les utiliser efficacement.  |
| **Claude Code / Codex pour SaaS**                | Idéal pour les développeurs sur leurs propres machines. Ne se traduit pas en SaaS multi-locataire — un codebase par utilisateur sur une dev-box n'est pas scalable. |
| **Applications agent-native**                    | L'agent est un citoyen de première classe. Il partage la même base de données, le même état, et peut faire tout ce que l'interface peut faire — et vice versa.      |

## Développement pour toute l'équipe {#whole-team-development}

Agent-native n'est pas seulement pour les développeurs. L'agent intégré donne à toute l'équipe un moyen partagé d'exploiter l'application, tandis que les modifications du code source restent dans le flux de développement normal de l'application et peuvent être déléguées à un frame intentionnellement doté d'un accès workspace et d'outils d'écriture :

- **Les designers** mettent à jour les données et les flux de travail de l'application directement via l'agent
- **Les chefs de produit** configurent les flux de travail et décrivent les changements pour l'équipe de développement
- **L'assurance qualité** teste l'application et signale ce qui est cassé via l'agent
- **Toute personne dans l'équipe** contribue via le langage naturel

La vision : moins de transferts, une personne faisant le travail d'une petite équipe.

## Commencer à partir d'un template et personnaliser {#fork-and-customize}

Les applications agent-native suivent un modèle de démarrage à partir d'une application fonctionnelle. Vous commencez à partir d'un **template** — Calendar, Content, Slides, Analytics, Mail, Clips, Design, Forms, Dispatch — et vous en faites le vôtre. Chacun est un produit SaaS complet et fonctionnel, pas un squelette vide :

1. Choisissez un template sur [agent-native.com/templates](/templates)
2. De nombreux templates de première partie sont disponibles comme applications hébergées (ex. : mail.agent-native.com)
3. Créez votre propre application à partir du template quand vous souhaitez personnaliser — « connecter notre compte Stripe », « ajouter un graphique de cohorte »
4. Personnalisez le code source dans votre propre dépôt et flux de développement
5. Déployez votre application sur votre propre domaine — ou restez sur agent-native.com

Parce que c'est _votre_ application, pas une infrastructure partagée, vous êtes propriétaire de son code source et pouvez la faire évoluer sans modifier le framework partagé. L'agent intégré exploite l'application déployée via ses actions et sa surface de données par défaut, et peut modifier le code source quand son frame est explicitement activé pour le code. Voir [Templates](/docs/cloneable-saas) pour l'histoire complète.

Pas encore prêt à commencer à partir d'un template complet ? Vous pouvez aussi essayer agent-native en ajoutant une **compétence** à un agent de codage que vous utilisez déjà — installez la compétence Plans avec `npx @agent-native/core@latest skills add visual-plan`. Voir le [Guide des Compétences](/docs/skills-guide#app-backed-skills).

## Agents composables {#composable-agents}

Les applications agent-native peuvent se parler entre elles. Depuis l'intérieur de l'application mail, vous pouvez mentionner l'agent analytique pour interroger des données et inclure le résultat dans un brouillon d'e-mail. Les agents découvrent quels autres agents sont disponibles, se transmettent le travail et affichent les résultats dans l'interface dans laquelle vous vous trouvez déjà.

Cela est propulsé par [A2A](/docs/a2a-protocol) et [MCP](/docs/mcp-protocol) sous le capot — même définition, plusieurs surfaces — mais en tant qu'utilisateur, tout ce que vous devez savoir est « je peux demander à n'importe laquelle de mes applications de l'aide pour tout ce que chacune d'elles peut faire ».

## À quoi cela ressemble-t-il en code ? {#what-does-it-look-like-in-code}

Si vous construisez ou étendez une application agent-native, voici le schéma central : chaque opération dans l'application est une **action** — définie une fois, disponible à la fois pour l'agent et l'interface.

Une action, plusieurs surfaces : l'agent l'appelle comme un outil, l'interface l'appelle comme une mutation fortement typée, le [chat natif](/docs/native-chat-ui) peut afficher des résultats de widgets explicites, les agents externes l'atteignent via [A2A](/docs/a2a-protocol), et les hôtes MCP l'appellent via le [serveur MCP](/docs/mcp-protocol) de l'application, optionnellement avec les ressources UI MCP Apps et l'OAuth MCP distant standard géré par le framework. Voir [Actions](/docs/actions-overview) pour la référence complète.
