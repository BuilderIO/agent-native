# Vue d’ensemble

`app/` est l'endroit où vous construisez l'affichage réel d'une application native d'agent : pages, mise en page, composants, styles. `public/` contient les ressources statiques servies à côté — icônes, manifeste, marques. Il s'agit d'une application React Router v8 typique, pas d'une surface réservée à l'agent, et c'est là que va la majeure partie du temps de développement.

L'unique différence architecturale par rapport à un frontend typique : cette couche n'a pas de backend-for-frontend propre. Elle lit et écrit des données via les mêmes actions que celles appelées par l'agent, donc tout ce qui est câblé ici est automatiquement quelque chose que l'agent peut aussi faire.

## Où s'intègre le Client {#role}

Les requêtes du navigateur, la boucle de l'agent et les clients API externes aboutissent tous aux mêmes actions et à la même base de données SQL — il n'existe pas de « backend d'application » séparé auquel cette couche parle et que l'agent ne pourrait pas aussi atteindre. Construire une fonctionnalité ici signifie construire une UI au-dessus d'une opération que l'agent possède déjà, ou définir une nouvelle action et obtenir une UI pour elle en même temps. Voir [Actions](/docs/actions) pour le côté opération de ce contrat.

Cette page couvre les répertoires dans lesquels vous construisez et les éléments du runtime navigateur que rien d'autre ne documente (`root.tsx`, `public/`). Les hooks React qui connectent vos composants aux actions et à l'agent vivent sur leurs propres pages dédiées :

| Page                                                       | Ce qu'elle couvre                                                                                                               |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **[Données et synchronisation](/docs/client-data)**        | `useActionQuery`, `useActionMutation`, `callAction`, et `useDbSync`                                                             |
| **[Chat de l’Agent](/docs/client-agent-chat)**             | `sendToAgentChat`, `askUserQuestion`, `openAgentSettings`, suggestions dynamiques, et état de contexte de chat agent en attente |
| **[Avancé](/docs/client-advanced)**                        | Accès direct à `application_state`, envois de chat en arrière-plan, puces de suggestion personnalisées, et le pont hôte MCP App |
| **[Synchronisation interne](/docs/client-sync-internals)** | `useChangeVersion`/`useChangeVersions` pour synchroniser un `useQuery` brut                                                     |
| **[Points d'entrée](/docs/client-entry-points)**           | `app/entry.client.tsx`/`app/entry.server.tsx` et la personnalisation SSR                                                        |

## Le shell du navigateur : root.tsx et AppProviders {#app-shell}

`app/root.tsx` est le sommet de l'arborescence React : le shell du document HTML (`<html>`, `<head>`, `<Meta>`, `<Links>`, `<Scripts>`) plus la pile de providers dans laquelle chaque route s'affiche.

```tsx filename="app/root.tsx"
import {
  AppProviders,
  createAgentNativeQueryClient,
} from "@agent-native/core/client/hooks";
import { useState } from "react";
import { Outlet } from "react-router";
import { i18nCatalog } from "./i18n";

export default function Root() {
  const [queryClient] = useState(() => createAgentNativeQueryClient());

  return (
    <AppProviders queryClient={queryClient} i18n={{ catalog: i18nCatalog }}>
      <Outlet />
    </AppProviders>
  );
}
```

`AppProviders` est le wrapper unique qui met en place :

- Le client React Query utilisé par `useActionQuery`/`useActionMutation` (voir [Données et synchronisation](/docs/client-data#fetching-mutating)).
- Le catalogue i18n transmis en tant que `i18n.catalog` (voir [Internationalisation](/docs/internationalization)).
- Les contrôles de session côté client : sur un chemin privé, un visiteur anonyme est redirigé vers la connexion avant qu'aucune UI privée ne se monte. Transmettez `isPublicPath` pour les routes publiques/SEO, ou `sessionBypass` pour une surface qui s'authentifie d'une autre manière, comme un jeton d'intégration MCP. Voir [Authentication](/docs/authentication).

La plupart des applications montent aussi `<AgentSidebar>` ou `<AgentPanel>` ici afin que chaque route bénéficie gratuitement du panneau d'agent. Voir [Agent sans rendez-vous](/docs/drop-in-agent#sidebar).

## Ressources statiques : public/ {#public-directory}

Tout ce qui se trouve dans `public/` est servi tel quel à la racine du site, non traité par le build. Chaque modèle inclut :

```text
public/
  favicon.svg           -> browser tab icon
  icon-180.svg           -> apple-touch-icon
  icon-192.svg, icon-512.svg -> PWA icons referenced from manifest.json
  manifest.json          -> web app manifest (name, theme color, icons)
  *-logo-*.svg, *-icon-*.svg -> brand marks used in the default UI
```

`manifest.json` contrôle ce qui s'affiche si un visiteur installe l'application sur un écran d'accueil ou un dock — nom, nom court, couleur de thème/arrière-plan, et l'ensemble d'icônes :

```json filename="public/manifest.json"
{
  "name": "My App",
  "short_name": "My App",
  "theme_color": "#18181B",
  "icons": [
    { "src": "icon-192.svg", "sizes": "192x192", "type": "image/svg+xml" }
  ]
}
```

Rebrandez une application en remplaçant ces fichiers et en mettant à jour `manifest.json` ainsi que les balises `<link rel="icon">`/`<link rel="apple-touch-icon">` dans `root.tsx` qui les référencent — il n'y a pas d'étape d'enregistrement séparée. Pour récupérer un système de marque complet (couleurs, polices, favicon) à partir d'un site existant au lieu de modifier ces fichiers à la main, voir [Brand Systems and Figma](/docs/template-design-brand-and-figma).

## Utilitaires : cn {#utilities}

```ts
import { cn } from "@agent-native/toolkit/utils";

<div className={cn(
  "px-4 py-2 rounded",
  isActive && "bg-primary text-primary-foreground",
  className
)} />
```

`cn` fusionne les noms de classe (clsx + tailwind-merge) et constitue la méthode standard pour composer des classes Tailwind conditionnelles dans `app/components/`.
