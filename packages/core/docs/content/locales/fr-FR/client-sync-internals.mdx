# Synchronisation interne

[Synchronisation en direct](/docs/key-concepts#polling-sync) couvre le modèle mental : une écriture de l'agent devient un événement de changement, `useDbSync()` le capte, et les requêtes affectées se relancent. Cette page couvre le mécanisme sous-jacent que la plupart des applications ne touchent jamais directement : les compteurs de version de changement que `useDbSync()` incrémente, et comment les intégrer dans un appel `useQuery()` brut qui ne passe pas par `useActionQuery()`.

`useActionQuery()` se relance déjà automatiquement lorsqu'une action de mutation se termine (voir [Données et synchronisation](/docs/client-data#fetching-mutating)). Recourez à `useChangeVersion()`/`useChangeVersions()` uniquement lorsque vous synchronisez un appel `useQuery()` brut hors de ce chemin, comme un assistant client de bas niveau lisant un statut d'intégration.

## Comment fonctionnent les versions de changement {#how-it-works}

Lorsqu'une mutation de base de données côté serveur se produit, le serveur enregistre un événement de changement marqué avec une clé `source`. `useDbSync()` reçoit cet événement et incrémente un compteur local pour cette source. Intégrer le compteur dans une clé de requête React Query fait que la requête se relance automatiquement chaque fois que le backend signale une nouvelle activité pour cette source.

Dans l'exemple ci-dessous, un appel `useQuery()` brut lit directement un tableau de bord, en intégrant le compteur de version de la source `"dashboards"` dans sa clé de requête afin qu'il se relance chaque fois que cette source change :

```tsx
import { useQuery } from "@tanstack/react-query";
import { useChangeVersion } from "@agent-native/core/client/hooks";

function DashboardView({ id }) {
  const version = useChangeVersion("dashboards");

  const { data } = useQuery({
    queryKey: ["dashboard", id, version],
    queryFn: () => fetchDashboard(id),
    placeholderData: (prev) => prev,
  });

  return <div>{data?.title}</div>;
}
```

`placeholderData: (prev) => prev` garde les données précédentes affichées pendant la relance, afin que la vue ne clignote pas vers un état de chargement.

## Deux chemins vers une relance {#latency-models}

Une mutation atteint l'UI d'une des deux façons, et elles ont des latences différentes.

Une mutation locale, celle qu'un appel `useActionMutation()` propre vient de faire, déclenche un événement `source: "action"` dès qu'elle réussit. Chaque requête dépendant de cette action se relance immédiatement. Il n'y a pas de délai d'aller-retour, puisque l'onglet qui a fait l'écriture la connaît déjà.

Une mutation distante, provenant de l'agent, d'un webhook, d'un autre onglet, ou d'un autre utilisateur, doit atteindre cet onglet d'abord. `useDbSync()` la capte via SSE presque immédiatement, ou via le secours par interrogation en environ deux secondes si SSE n'est pas disponible. Ce n'est qu'une fois cet événement arrivé que le compteur de version pertinent s'incrémente et que la requête se relance en arrière-plan.
