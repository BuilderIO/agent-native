# Guide développeur

Cette page est destinée à toute personne qui personnalise le modèle Design ou construit directement dessus : le démarrage rapide, chaque action, le modèle de données, une action passée en revue, la surface de routes, et comment y ajouter des éléments. Consultez [Design](/docs/template-design) pour ce que fait l'application.

## Démarrage rapide

<Steps>

### Créer l'application

```bash
npx @agent-native/core@latest create my-design --standalone --template design
cd my-design
pnpm install
```

Cela nécessite [Node.js](https://nodejs.org) 22.22 ou une version plus
récente, et [pnpm](https://pnpm.io) installé au préalable. Consultez [Bien
démarrer](/docs/getting-started) si vous n'avez installé ni l'un ni l'autre
encore, ou si vous n'avez pas de connexion LLM (Builder.io, une clé
Anthropic/OpenAI, ou Ollama en local) configurée. Pour un espace de travail
avec Design aux côtés d'autres applications, exécutez plutôt `npx
@agent-native/core@latest create my-platform` et choisissez Design pendant
la configuration.

### Démarrer le serveur de développement

```bash
pnpm dev
```

L'application s'ouvre à `http://localhost:8099`, le port de développement
par défaut de Design. Design fonctionne entièrement sans connexions
externes. Vous ne rencontrerez une invite de connexion que si vous essayez
un import Figma ou la Construction d'application complète avant de les avoir
configurés.

</Steps>

## Inventaire des actions

Chaque opération spécifique à Design est un fichier TypeScript dans
`templates/design/actions/`, monté automatiquement sur `POST
/_agent-native/actions/:name` et exécutable depuis le CLI en tant que `pnpm
action <name>`.

## Modèle de données

Toutes les données vivent dans SQL via Drizzle ORM. Schéma :
`templates/design/server/db/schema.ts`. Les designs et les systèmes de
conception portent le standard `ownableColumns` et une table de partages de
framework correspondante, si bien qu'ils s'intègrent dans le modèle de
partage par utilisateur / par organisation.

Le tableau ci-dessous couvre les ressources possédables principales :
designs, fichiers, modèles, versions, et systèmes de conception.

| Table                                    | Ce qu'elle contient                                                                                                                                |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `designs`                                | Un projet de design — `title`, `description`, `project_type` (`prototype` / `other`), le blob JSON `data`, et un lien `design_system_id` optionnel |
| `design_files`                           | Fichiers individuels appartenant à un design (`filename`, `content`, `file_type` par défaut à `html`)                                              |
| `design_templates`                       | Métadonnées de modèle réutilisable, dimensions, valeurs par défaut, référence au design source, et nombre de couches verrouillées                  |
| `design_template_files`                  | Fichiers de modèle instantanés copiés dans un design normal modifiable quand un utilisateur démarre à partir d'un modèle                           |
| `design_template_shares`                 | Table de partages du framework pour la découverte de modèles privés, d'organisation, explicitement partagés, et publics                            |
| `design_versions`                        | `snapshot`s ponctuels d'un design avec un `label` optionnel, pour l'historique et la restauration                                                  |
| `design_systems`                         | Jetons de marque réutilisables — `data` (couleurs/typographie/espacement), `assets`, `custom_instructions`, et un drapeau `is_default`             |
| `design_shares` / `design_system_shares` | Tables de partages du framework mappant les principaux (utilisateurs ou organisations) aux rôles (spectateur, éditeur, administrateur)             |

Un projet de design est une coquille jusqu'à ce qu'il ait du contenu :
`create-design` crée une ligne vide (`data: "{}"`), puis `generate-design`
écrit les véritables fichiers HTML/JSX autonomes. L'artefact généré, la
source modifiable, et chaque export proviennent tous du même HTML, il n'y a
donc pas de format « maquette IA » séparé à traduire. Un système de
conception lié fournit des jetons et des `custom_instructions` que l'agent
honore à chaque passage de génération.

Sept autres tables prennent en charge des fonctionnalités couvertes ailleurs
dans cette page plutôt que le modèle de ressources principal :
`design_localhost_connections` et `design_localhost_write_grants` prennent
en charge l'[import d'application locale](/docs/template-design-features#import),
`component_index` prend en charge la [section Composant de l'onglet
Design](/docs/template-design-features#design-tab), `motion_timeline` prend
en charge la chronologie de mouvement modifiable de chaque élément (le
panneau Motion dans l'éditeur), `design_state` conserve les états
alternatifs nommés, les fixtures statiques, et les captures d'application en
direct pour un design, `design_fusion_edits` prend en charge la file
d'attente de modifications fusion décrite sous [Construction d'application
complète](#full-app-building) ci-dessus, et `design_review_snapshot` met en
cache les constats d'accessibilité et le diff visuel derrière
`get-design-review`, décrit sous [Qualité](#quality) ci-dessus.

Les commentaires et fils de révision persistés (`get-review-feedback`,
`resolve-review-thread`, et le reste) ne sont pas du tout une table
spécifique à Design : ce sont le système de révision partagé du framework
`@agent-native/core/review` (`agent_review_comments` /
`agent_review_statuses`), rattaché à un design de la même façon que toute
application peut l'attacher. Consultez [l'onglet
Commentaires](/docs/template-design-features#comments-tab) pour le
comportement côté utilisateur.

## Une action passée en revue

`save-design-as-template` montre des modèles qui valent la peine d'être
réutilisés dans n'importe quelle action : rejeter une forme d'entrée non
prise en charge avant de faire quoi que ce soit, se prémunir contre
l'enregistrement de rien, remapper les ids une seule fois plutôt que dans
chaque lecteur, et écrire dans deux tables en une seule transaction pour
qu'un modèle ne puisse jamais se retrouver avec des métadonnées mais sans
fichiers.

## Modèle de l'éditeur

Design privilégie la vue d'ensemble pour le travail multi-écran. Après une
génération ou des mises à jour larges, l'éditeur ouvre la vue d'ensemble des
écrans : un canevas infini où chaque écran est un cadre statique que vous
pouvez sélectionner, déplacer, redimensionner, déposer, ou dupliquer.
Utilisez le bouton de vue complète d'un cadre lorsqu'un écran nécessite un
défilement ciblé ou une interaction de prototype.

Le mode écran unique sert à faire défiler, interagir avec le comportement du
prototype, et modifier les couches DOM/code à l'intérieur d'un fichier
rendu. Le panneau des couches reflète cette séparation : les écrans sont des
cadres de premier niveau, avec des couches DOM/code imbriquées pour l'écran
actif.

Chaque écran est un seul document rendu à différentes largeurs, pas des
copies séparées par point de rupture : un cadre de base (le plus large) se
répercute vers le bas, et les modifications faites à un point de rupture
actif plus étroit persistent comme des surcharges limitées à cette largeur
par-dessus.

## Extensions de l'éditeur

L'éditeur inclut un onglet d'inspecteur **Extensions** après **Tweaks**. Il
fonctionne comme une piste de plugins propre à Design : les utilisateurs
peuvent cliquer sur **+ Extension** pour demander à l'agent de créer une
extension, ou installer une extension qui déclare l'emplacement
`design.editor.inspector`, en utilisant les actions du framework
`create-extension`, `add-extension-slot-target`, et `install-extension`, pas
une action propre à Design.

Les extensions Design s'affichent en ligne à côté du plan de travail via le
bac à sable standard des extensions. L'hôte transmet les mises à jour
`window.slotContext` et `window.onSlotContext(...)` avec le `designId`
actuel, le fichier actif, la liste des écrans, les ids d'écrans
sélectionnés, les métadonnées de l'élément sélectionné, le mode
d'affichage, le zoom, l'outil actif, et les valeurs de réglage. Cela permet
à une extension d'afficher des informations sur la sélection actuelle,
d'offrir des contrôles de style, ou de construire des workflows compacts
autour du design ouvert.

Pour un travail déterministe, les extensions peuvent appeler les actions de
l'application via le pont d'extension. Pour les changements pilotés par
l'IA, faites appeler à l'extension `agentNative.chat.send(...)` avec le
sélecteur/id source de l'élément sélectionné et le changement demandé.
L'agent doit d'abord appeler `view-screen`, puis utiliser
`apply-visual-edit` pour les changements de style, classe, texte, ou
déplacement d'élément, ou `update-design` / `generate-design` avec
`canvasFrames` pour les changements de placement du plan de travail.
Consultez [Extensions](/docs/extensions#capabilities) pour le bac à sable,
l'état persistant, et les API du pont.

## Le personnaliser

Design est un modèle complet et clonable. Quelques idées d'extension
pratiques :

- "Ajoute un système de conception e-commerce réutilisable avec nos jetons et exemples de composants."
- "Ajoute une étape d'export qui télécharge le ZIP vers notre système de révision interne."
- "Laisse-moi coller le HTML existant d'une page d'atterrissage et demander à l'agent trois versions plus fortes."
- "Ajoute une bibliothèque d'invites enregistrées pour les briefs de page produit, de tableau de bord, et d'écran d'intégration."
- "Ajoute un préréglage d'export PDF personnalisé pour la révision par les parties prenantes."

L'agent modifie les routes, composants, actions, et modèles adossés à SQL
selon les besoins. Consultez [Modèles](/docs/cloneable-saas) pour le flux
complet de clonage, personnalisation, déploiement, et [Bien
démarrer](/docs/getting-started) si c'est votre premier modèle natif
d'agent.
