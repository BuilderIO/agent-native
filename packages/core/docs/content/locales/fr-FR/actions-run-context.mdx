# Contexte d’exécution

`run` reçoit un second argument optionnel, `ctx`, qui porte l’identité résolue de la requête et la surface qui a invoqué l’action. Lisez-le au lieu d’appeler `getRequestUserEmail()` / `getRequestOrgId()` à la main, et transmettez le `ctx` entier au suivi :

```ts
export default defineAction({
  description: "Log an audit entry for the current request.",
  schema: z.object({ event: z.string() }),
  run: async (args, ctx) => {
    // ctx is undefined-safe: a 1-arg `run(args)` is still valid.
    const actor = ctx?.userEmail ?? "system";
    if (ctx?.caller === "frontend") {
      // tighter rules for browser-initiated calls, looser for "tool"/"cli"
    }
    await db.insert(audit).values({
      actor,
      orgId: ctx?.orgId ?? null,
      source: ctx?.caller ?? "unknown",
      event: args.event,
    });
    return { ok: true };
  },
});
```

La plupart des actions ne lisent que `ctx?.userEmail` et `ctx?.orgId`, le [découpage de contrôle d’accès](/docs/actions-access-control#access-control) utilisé dans presque chaque action réelle. Le reste de cette page couvre des préoccupations transverses comme le suivi et l’attribution des automatisations, dont moins d’actions ont besoin.

## L’argument `ctx` {#ctx}

`ctx` porte deux types d’information : l’identité résolue de la requête (`userEmail`, `orgId`) présente sur presque chaque appel, et des métadonnées sur la surface qui a invoqué l’action (`caller`, plus des champs spécifiques à la surface comme `threadId` ou `automation` qui ne sont peuplés que pour certains appelants). `run()` reste rétrocompatible : les gestionnaires existants à un argument et les gestionnaires qui ne déstructurent que `{ send }` continuent de fonctionner sans changement.

### L’union `caller` {#caller}

`caller` est l’union `"tool" | "http" | "frontend" | "cli" | "mcp" | "a2a" | "automation"` :

| `caller`       | Défini quand…                                                                                                                                                                                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `"tool"`       | La boucle d’agent intégrée à l’application, un sous-agent ou une équipe d’agents, ou la délégation A2A inter-applications en langage naturel, qui pilote la même boucle d’agent, donc ses appels d’outil sont `"tool"`.  |
| `"frontend"`   | Un appel navigateur via `useActionMutation()`, `useActionQuery()`, ou `callAction()` (marqué avec l’en-tête `X-Agent-Native-Frontend: 1`).                                                                               |
| `"http"`       | Un `POST` ou `GET` programmatique brut vers `/_agent-native/actions/<name>` sans le marqueur frontend.                                                                                                                   |
| `"cli"`        | `pnpm action <name>` (l’exécuteur CLI).                                                                                                                                                                                  |
| `"mcp"`        | Un agent externe via le point de terminaison MCP `tools/call`.                                                                                                                                                           |
| `"a2a"`        | Un appel HTTP direct vers `/_agent-native/actions/<name>` portant un jeton de délégation A2A signé. C’est un dispatch inter-applications explicitement exposé, distinct du chemin `"tool"` en langage naturel ci-dessus. |
| `"automation"` | Une automatisation déclenchée par événement, dispatchée depuis un déclencheur d’espace de travail stocké. `ctx.automation` porte la lignée du déclencheur. Voir [Automatisations](/docs/automations).                    |
