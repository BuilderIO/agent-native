# Mettre à niveau les applications existantes vers Core 0.198.0

Suivez ce guide pour mettre à niveau une application existante vers Core
0.198.0. Exécutez les commandes depuis la racine de l’application ou du
workspace et conservez un diff révisable avant de commencer. Vérifiez
séparément les réglages des environnements de déploiement : la CLI peut lire les
fichiers d’environnement locaux, mais elle ne peut pas inspecter les
environnements distants ni les réglages de fonctionnalités stockés en base.

## 1. Prévisualiser la mise à niveau et les codemods d’import

Utilisez la CLI de Core 0.198.0 pour charger le manifeste de migration de cette
version :

    npx @agent-native/core@0.198.0 upgrade --codemods --dry-run

Une fois Core 0.198.0 installé dans l’application, le même aperçu est disponible via le binaire CLI local :

    npx agent-native upgrade --codemods --dry-run

La commande `--codemods` utilise `ts-morph`. Si le paquet ne peut pas déjà être résolu depuis l’application, installez-le d’abord comme dépendance de développement : `pnpm add -D ts-morph`.

`--codemods` applique par défaut les modifications d’import prises en charge. Ajoutez
`--dry-run` pour prévisualiser les changements de dépendances prévus, le diff des fichiers et
les avertissements avant de continuer. `--yes` n’est plus nécessaire.

Le codemod utilise les manifestes de migration actifs de Core et Toolkit. Il
ne parcourt que les fichiers .ts et .tsx (hors fichiers de déclaration, fichiers
générés et répertoires de dépendances), puis réécrit les spécificateurs
d’import et de ré-export pris en charge. Si des exports nommés migrent vers
différents modules, il peut séparer une déclaration par symbole tout en
conservant les alias et les imports de type. Il réécrit aussi les chemins CSS
@import simples et ajoute une dépendance manquante lorsqu’une réécriture
résolue traverse la frontière d’un package.

Le diagnostic détecte également les formes CommonJS `require()` et les formes `import()` dynamiques. Le codemod réécrit les appels `import()` littéraux lorsque l’ancien module n’a qu’une seule nouvelle destination. Il laisse `require()` et les imports dynamiques nécessitant une séparation par symbole inchangés et signale un avertissement ; remplacez-les en utilisant la nouvelle destination indiquée dans le rapport, puis relancez Vite ou `agent-native doctor`. Les chemins CSS `@import url(...)` sont réécrits qu’ils soient entre guillemets ou non.

Il ne modifie pas les sites d’appel et ne déplace pas vos fichiers. Les
migrations non résolues ou planifiées restent inchangées et génèrent un
avertissement. Il ne peut pas séparer les imports ou exports default,
namespace, side-effect ou star ; il ne peut pas séparer les imports CSS par symbole. Examinez ces cas manuellement.
Les exports supprimés peuvent nécessiter une modification du code ; suivez le
guide indiqué dans l’avertissement CLI.

La prévisualisation montre aussi le plan complet : overrides ou patches du
framework bloquants, mises à niveau de versions @agent-native/\* en attente,
dépendances de fonctionnalités déduites de la configuration locale,
installation du gestionnaire de paquets, actualisation des skills de scaffold
et typecheck si le package racine a ce script. La commande passe les versions
des packages à latest dans le registre, puis épingle les versions réellement
résolues par l’installation. Exécutez-la lorsque 0.198.0 est la version actuelle
voulue ; si vous exigez ensuite une version précise, vérifiez les versions
épinglées.

## 2. Confirmer Toolkit et les packages facultatifs

Les imports déplacés vers `@agent-native/toolkit/*` nécessitent `@agent-native/toolkit`. Le codemod ajoute Toolkit lorsqu’un import ou export pris en charge et résolu y est déplacé. Si l’application utilise un export Toolkit sans que la dépendance ait été ajoutée, installez la version Toolkit correspondante à Core 0.198.0 :

    pnpm add @agent-native/toolkit@0.198.0
    # npm install @agent-native/toolkit@0.198.0
    # yarn add @agent-native/toolkit@0.198.0

### Dépendances sélectionnées par la CLI de mise à niveau

Elle ne peut pas inspecter les environnements distants ni les paramètres de fonctionnalité stockés en base de données : vérifiez séparément la production et la prévisualisation.

## 3. Appliquer la mise à niveau

Après examen de la simulation et confirmation des packages de fonctionnalités,
appliquez le plan avec la CLI versionnée. C’est important si l’application
utilise encore Core 0.196 ou une CLI plus ancienne, qui contient un ancien
manifeste de migration :

    npx @agent-native/core@0.198.0 upgrade --codemods

Une fois Core 0.198.0 installé dans l’application, la même commande est
disponible depuis la CLI locale :

    npx agent-native upgrade --codemods

Les deux commandes mettent à jour les spécifications de dépendance
@agent-native/\* admissibles, alignent les dépendances des fonctionnalités
détectées, lancent le gestionnaire de paquets, épinglent les versions
Agent-Native résolues, appliquent les codemods pris en charge, actualisent les
skills de scaffold et exécutent le script typecheck racine s’il existe. Ne
lancez pas une seconde commande upgrade uniquement pour appliquer les codemods.
Corrigez les avertissements et erreurs au niveau du code de l’application ;
n’ajoutez pas d’overrides ou de patches du framework.

## 4. Vérifier le résultat

Examinez le diff complet, notamment les avertissements de codemod ignorés et
les versions de dépendances, puis exécutez :

    npx @agent-native/core@0.198.0 upgrade check
    npx agent-native doctor
    pnpm typecheck

Doctor exécute par défaut les contrôles `migration-manifest` et
`feature-dependencies`. Ils signalent les anciens imports et les peers
facultatifs manquants pour les fonctionnalités détectées depuis la configuration
locale. Doctor ne peut pas consulter les paramètres de déploiement distants ni
les paramètres de fonctionnalité stockés en base de données. Vérifiez-les
séparément.

Utilisez la commande typecheck équivalente pour npm ou Yarn. Exécutez les scripts
de test et de compilation de l’application lorsqu’ils existent, généralement
`pnpm test` et `pnpm build`. Vérifiez que les réglages locaux et déployés figurent
dans le tableau des peers facultatifs. Recherchez les anciens imports du tableau
ci-dessous ; les résultats restants doivent être intentionnels, non pris en
charge par le manifeste ou expliqués par un avertissement.
