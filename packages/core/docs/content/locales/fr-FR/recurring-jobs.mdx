# Tâches récurrentes

Une **tâche récurrente** est une invite qui s'exécute selon une planification cron. C'est ainsi que l'agent fait les choses tout seul : "chaque matin à 7 heures, résumez mes e-mails de la nuit", "chaque lundi, publiez les numéros d'inscription de la semaine dernière sur Slack", "chaque heure recherchez les brouillons périmés et supprimez-les."

<Callout tone="info">

**Recurring Jobs** est l'ancien nom des automatisations **Scheduled**. **Automations** couvre **Scheduled** et **Event**. Les fichiers `jobs/` et `manage-jobs` restent disponibles pour les anciennes intégrations uniquement planifiées. Utilisez `manage-automations` et **Automations** sur `/agent#jobs` pour les nouveaux travaux personnels ou d'organisation, y compris le modèle et les listes MCP.

</Callout>

Les tâches récurrentes se déclenchent selon une horloge. Pour réagir aux _événements_ (une réservation créée, un e-mail reçu) — même format de fichier `jobs/` plus conditions — voir [Automations](/docs/automations).

Les tâches sont en direct dans le [Ressources de l'agent](/docs/agent-resources) sur `jobs/<name>.md` — juste un fichier Markdown avec le frontmatter YAML. Pas d'enregistrement, pas de câblage. Déposez le fichier et le framework le récupère.

C'est tout. Le corps est une invite que l'agent exécute à chaque déclenchement planifié. L'agent a accès aux mêmes outils et au même contexte de l'agent que dans un chat interactif : actions, skills, mémoire, serveurs MCP connectés, sous-agents.

## Première question {#frontmatter}

| Champ        | Tapez                         | Par défaut      | Description                                                                                                                               |
| ------------ | ----------------------------- | --------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `schedule`   | expression cron               | _(obligatoire)_ | Cron standard à 5 champs. `"0 7 * * *"` = tous les jours à 07h00 ; `"0 */4 * * *"` = toutes les 4 heures.                                 |
| `enabled`    | booléen                       | `true`          | Basculez vers `false` pour mettre en pause sans supprimer la tâche.                                                                       |
| `runAs`      | `"creator"` \| `"shared"`     | `"creator"`     | `"creator"` s'exécute avec l'identité du propriétaire de la tâche et `ANTHROPIC_API_KEY`. `"shared"` utilise la clé de l'organisation.    |
| `createdBy`  | e-mail                        | _(auto)_        | Rempli lorsque le travail est créé via l'ressources de l'agent UI ou par l'agent.                                                         |
| `orgId`      | chaîne                        | _(auto)_        | Portée de l'organisation ; hérité de l'organisation active du créateur.                                                                   |
| `lastRun`    | Horodatage ISO                | _(géré)_        | Écrit par le planificateur après chaque exécution.                                                                                        |
| `lastStatus` | `"success"` \| `"error"` \| … | _(géré)_        | Dernier résultat.                                                                                                                         |
| `lastError`  | chaîne                        | _(géré)_        | Message d'erreur si la dernière exécution a échoué.                                                                                       |
| `nextRun`    | Horodatage ISO                | _(géré)_        | Calculé à partir de `schedule` ; utilisé par le planificateur pour décider quand déclencher ensuite.                                      |
| `mcpTools`   | tableau de noms d'outils MCP  | _(aucun)_       | Liste d'autorisation explicite facultative, par exemple `mcp__server__tool` ; les identifiants restent dans l'autorisation MCP connectée. |

Les champs `last*` et `nextRun` sont écrits par le planificateur. Vous pouvez les lire pour voir l'historique, mais ne les modifiez pas manuellement : la prochaine exécution les écrasera.

## Connecter des outils MCP à une tâche {#connected-mcps}

Les tâches récurrentes peuvent utiliser des outils MCP distants ou locaux déjà connectés à l'application. Demandez à l'agent de découvrir les noms exacts avec `tool-search`, puis liez uniquement les outils dont la tâche a besoin avec `mcpTools` :

```md
---
schedule: "0 * * * *"
enabled: true
mcpTools:
  ["mcp__meeting-notes__list_recordings", "mcp__meeting-notes__get_transcript"]
---

Recherchez les nouveaux enregistrements depuis la dernière exécution réussie. Extrayez uniquement les suivis exploitables, puis appelez une seule fois l'action d'importation bornée de l'application avec une source et des identifiants externes stables, une courte citation et l'URL de l'enregistrement. N'importez pas la transcription complète.
```

La tâche stocke des noms d'outils, pas des URL MCP, des jetons d'accès ou des jetons d'actualisation OAuth. À l'exécution, le framework résout l'autorisation connectée dans le contexte de requête du créateur ou de l'organisation de la tâche et n'expose que les outils de la liste d'autorisation. Gardez cette liste restreinte et utilisez une action d'application idempotente pour l'import final afin que des exécutions qui se chevauchent ne créent pas de doublons. Consultez [Clients MCP](/docs/mcp-clients) pour la configuration de la connexion et d'OAuth.

## Syntaxe Cron {#cron}

Cron standard à 5 champs (minute, heure, jour du mois, mois, jour de la semaine) :

| Cron           | Signification               |
| -------------- | --------------------------- |
| `*/5 * * * *`  | Toutes les 5 minutes        |
| `0 * * * *`    | Toutes les heures           |
| `0 */4 * * *`  | Toutes les 4 heures         |
| `0 7 * * *`    | Tous les jours à 07h00      |
| `0 9 * * 1`    | Tous les lundis à 09h00     |
| `0 17 * * 1-5` | En semaine à 17h00          |
| `0 0 1 * *`    | Premier jour de chaque mois |

Le framework comprend des utilitaires cron (`isValidCron()` et `describeCron()`) pour valider et restituer les chaînes cron, utilisées en interne par les couches de ressources et de planificateur.

## Créer une tâche {#creating}

### Depuis l'onglet Espace de travail

`+` → **Tâche planifiée** dans le panneau de l'ressources de l'agent. Remplissez l'invite et le calendrier. Enregistre sous `jobs/<slug>.md` et commence à s'exécuter au prochain tick correspondant.

### En demandant à l'agent

> "Créez une tâche planifiée qui résume mes e-mails non lus chaque matin à 7 heures."

L'agent écrit le fichier pour vous.

### À la main

Déposez un fichier Markdown dans `jobs/` via la ressource APIs du framework :

```ts
import { resourcePut } from "@agent-native/core/resources";

await resourcePut(
  ownerEmail,
  "jobs/morning-digest.md",
  `---
schedule: "0 7 * * *"
enabled: true
---
Summarize overnight emails.`,
);
```

## Fonctionnement du planificateur {#how-scheduler-runs}

À chaque tick, le planificateur (la routine interne `processRecurringJobs()`) trouve les tâches dues et les exécute. Ce qui déclenche le tick dépend de l'endroit où l'application s'exécute :

| Environnement                                                       | Ce qui déclenche le tick                                                                             | Exigences et limites                                                                                                           |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Serveur à exécution continue (Node.js, Docker, Fly, Render, un VPS) | Un minuteur en cours de processus toutes les 60 secondes, qui démarre 10 secondes après le lancement | S'exécute tant que le processus est actif.                                                                                     |
| [Netlify](/docs/netlify)                                            | Une fonction planifiée émise par le build, toutes les minutes                                        | Déploiements publiés uniquement, jamais les Deploy Previews ni les déploiements de branche. Le build a besoin de `A2A_SECRET`. |
| [Vercel](/docs/vercel#vercel-scheduled-work)                        | Une tâche cron Vercel ajoutée par le build, toutes les minutes par défaut                            | Déploiement de production uniquement. Nécessite `CRON_SECRET`. Les projets Hobby peuvent l'exécuter au plus une fois par jour. |
| [Cloudflare Workers](/docs/cloudflare#cloudflare-scheduled-work)    | Un Cron Trigger ajouté par le build à `wrangler.json`, toutes les minutes                            | Nécessite `A2A_SECRET` comme secret du Worker.                                                                                 |
| AWS Lambda                                                          | Rien                                                                                                 | Les automatisations planifiées ne se déclenchent pas.                                                                          |
| Développement local                                                 | Rien, sauf si vous l'activez                                                                         | Voir l'encadré ci-dessous.                                                                                                     |

Sur Netlify, Vercel et Cloudflare, le même tick vide aussi la file des
automatisations déclenchées par événement, nettoie les exécutions dont la
fonction a été interrompue et exécute les balayages des applications, comme la
mise en attente et l'envoi programmé de Mail. Un déploiement serverless sans
déclencheur n'a rien de tout cela : les automatisations déclenchées par
événement attendent dans la file et les exécutions interrompues restent
bloquées. Les automatisations déclenchées par webhook et **Run now** se lancent
d'elles-mêmes, elles fonctionnent donc toujours. Lorsqu'un déploiement ne peut
pas déclencher les planifications, la page **Automations** l'indique et en donne
la raison.

<Callout id="doc-block-j6yn07" tone="risk">

**Une instance chaude n'exécute pas les planifications.** Les hôtes serverless ne démarrent jamais le minuteur en cours de processus, donc les pings keep-alive ne déclenchent pas les tâches. Seul le déclencheur de la plateforme du tableau ci-dessus le fait. Sur AWS Lambda, rien ne les déclenche encore : exécutez donc les automatisations planifiées sur un hôte à exécution continue (Fly, Render, un VPS).

</Callout>

<Callout id="doc-block-rj2" tone="warning">

**Désactivé par défaut en développement local.** La boucle `setInterval` du planificateur ne démarre jamais lorsque `NODE_ENV` vaut `development` ou `test`, ou lorsque l'URL de l'application pointe vers `localhost` / `127.0.0.1` / `*.localhost`, ce qui couvre la plupart des configurations de développement local. Définissez `AGENT_NATIVE_ENABLE_LOCAL_RECURRING_JOBS=1` pour exécuter quand même le planificateur en local. Pour désactiver les tâches planifiées sur n'importe quel hôte, utilisez `AGENT_NATIVE_DISABLE_RECURRING_JOBS=1`, décrit ci-après.

</Callout>

<Callout id="doc-block-rj3" tone="warning">

**`AGENT_NATIVE_DISABLE_RECURRING_JOBS` est lu dans deux contextes.** Sur Netlify, Vercel et Cloudflare, c'est l'environnement de **build** qui décide : le déclencheur de la plateforme continue de se déclencher pour vider les automatisations par événement et nettoyer les exécutions, mais un build avec l'interrupteur activé ignore les tâches planifiées, quoi qu'en dise l'environnement déployé. Sur un serveur à exécution continue, c'est l'environnement d'**exécution** qui contrôle le minuteur en cours de processus. Définissez-le là où votre hôte le lit. Le build enregistre sa décision, afin que la page **Automations** puisse indiquer que les planifications ne s'exécuteront jamais au lieu d'afficher une date de prochaine exécution que rien ne respectera.

</Callout>

## Débogage d'une tâche {#debugging}

- Ouvrez `jobs/<name>.md` dans l'ressources de l'agent : le premier plan affiche `lastRun`, `lastStatus`, `lastError`, `nextRun`.
- **Testez-le sans attendre :** ouvrez l'automatisation dans **Automations** et
  choisissez **Run now**. L'automatisation s'exécute immédiatement, avec ses
  effets de bord réels, sans attendre un tick du planificateur ; cela fonctionne
  donc aussi en local et sur les hôtes sans déclencheur.
- **Mettez-le en pause :** retournez `enabled: false`. Le fichier reste en place, arrête simplement de s'exécuter.

## Outil d'agent {#agent-tool}

Un seul outil `manage-jobs` est enregistré dans chaque modèle. Le paramètre `action` sélectionne l'opération :

| Actions  | Paramètres                                                                        | Objectif                                                                                     |
| -------- | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `create` | `name`, `schedule`, `instructions` (obligatoire) ; `scope`, `runAs`, `mcpTools`   | Créer une nouvelle tâche récurrente                                                          |
| `list`   | `scope` (`personal`, `shared` ou tous)                                            | Liste de toutes les tâches avec statut (planification, activé, dernière/prochaine exécution) |
| `update` | `name` (obligatoire) ; `schedule`, `instructions`, `enabled`, `runAs`, `mcpTools` | Modifier une tâche existante                                                                 |
| `delete` | `name` (obligatoire)                                                              | Supprimer une tâche – toujours confirmer d'abord avec l'utilisateur                          |

**Portée personnelle ou partagée.** Chaque automatisation est personnelle ou d'organisation et s'exécute en tant que son créateur. Les administrateurs peuvent gérer les définitions partagées, mais pas changer l'identité du créateur. Avant chaque exécution d'organisation, le framework vérifie que le créateur existe et reste membre.

## Différent du package de planification {#vs-scheduling-package}

Ne confondez pas les tâches récurrentes avec `@agent-native/scheduling` :

- **Tâches récurrentes (cette page)** — _invites_ planifiées par cron que l'agent exécute en arrière-plan. Au niveau du framework. Vit dans l'ressources de l'agent. Se déclenche sur tout hôte doté d'un planificateur (voir [Fonctionnement du planificateur](#how-scheduler-runs)).
- **`@agent-native/scheduling`** — un package de domaine réutilisable pour créer des fonctionnalités de calendrier/réservation (types d'événements, fenêtres de disponibilité, réservations). Alimente le modèle `calendar` et les surfaces de planification personnalisées.

Les tâches récurrentes sont : "Comment faire en sorte que l'agent agisse seul ?" Le package de planification est « Comment puis-je créer une application de calendrier ? » Différentes préoccupations.
