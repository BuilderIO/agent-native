# Récapitulatif visuel de PR

Récapitulatif visuel de PR est une Action GitHub qui transforme chaque pull
request en une **revue de code visuelle**, sans que personne n'ait à se
souvenir de lancer une commande à la main. Cette page s'adresse à
quiconque installe, configure ou sécurise cette Action. À chaque push, un
agent de codage LLM exécute la dernière compétence
[`visual-recap`](/docs/template-plan) groupée (ou la copie committée de
votre dépôt quand `VISUAL_RECAP_SKILL_SOURCE=repo`) sur le diff de la PR,
publie un plan récapitulatif structuré dans l'application Plans hébergée,
affiche une vérification informative `Visual Recap` pendant son exécution,
et crée ou met à jour **un unique commentaire de PR persistant** qui
pointe vers le plan interactif avec une **capture d'écran en ligne**
intégrée directement dans le commentaire.

Ce n'est pas un moteur de rendu de diff déterministe. L'action invoque un
véritable agent de codage (CLI Claude Code par défaut, CLI OpenAI Codex,
ou Agent-Native Code avec un fournisseur compatible OpenAI) qui lit le
changement, décide de ce qui compte, et rédige le récapitulatif en
appelant l'outil MCP Plans `create-visual-recap` — le même outil
qu'utilise la commande slash `/visual-recap`. Vous obtenez une vue
d'ensemble, avec schéma/API/avant-après, du changement, plutôt qu'un mur
de diff brut.

Le récapitulatif est **informatif et non bloquant**. Il crée une ligne de
vérification pour que les relecteurs voient que la génération est en
cours, mais ce n'est pas une vérification requise, elle ne bloque jamais
la PR, et elle ne remplace jamais la lecture du diff réel. Le commentaire
persistant est une aide à la revue, pas un feu vert.

## Ce que ça fait

À chaque push de PR, le workflow :

1. Récupère un diff borné entre la base et la tête de la PR.
2. Crée une vérification GitHub informative `Visual Recap` avec
   `Visual recap in progress`.
3. Exécute l'agent de codage configuré sur ce diff. L'agent lit les
   consignes de la compétence `visual-recap` groupée (ou votre copie
   épinglée dans le dépôt) et rédige un récapitulatif, en le publiant avec
   `create-visual-recap`.
4. Lit l'URL du plan publié que l'agent a écrite dans `recap-url.txt`.
5. Ouvre cette URL dans Chrome sans tête et capture le plan rendu en
   modes clair et sombre.
6. Téléverse les PNG vers une route d'image publique signée de
   l'application Plans.
7. Crée ou met à jour un unique commentaire de PR persistant qui intègre
   les captures d'écran **en ligne** avec un élément `<picture>` (servi
   via le proxy d'images camo de GitHub) juste à côté du lien vers le
   récapitulatif interactif.
8. Termine la vérification `Visual Recap` en succès, ignorée, ou neutre.

## Installation

Quand vous installez Plans en mode interactif, la CLI Agent-Native
demande si elle doit ajouter des récapitulatifs visuels de PR
automatiques. Répondez oui pour écrire l'Action GitHub, ou ajoutez-la
explicitement à tout moment :

```bash
npx @agent-native/core@latest skills add visual-plan --with-github-action
```

Cela installe la compétence `visual-plan` (qui inclut la compétence
`visual-recap` que l'action exécute) et écrit
`.github/workflows/pr-visual-recap.yml` dans votre dépôt. Le workflow
appelle des **sous-commandes CLI publiées** via
`npx @agent-native/recap-cli@latest recap <subcommand>` — dont `gate`,
`collect-diff`, `block-reference`, `scan`, `build-prompt`, `publish`,
`shot`, `comment`, `check`, et `usage` — si bien que rien n'est copié dans
votre dépôt comme script auxiliaire. `setup` et `doctor` sont les aides
interactives que vous exécutez localement ; `gate` est l'étape de
sécurité que le workflow exécute avant chaque récapitulatif.

Exécutez ensuite l'aide de configuration guidée :

```bash
npx @agent-native/recap-cli@latest recap setup
npx @agent-native/recap-cli@latest recap doctor
```

`recap setup` actualise le workflow, utilise `gh` pour définir les
secrets et variables des Actions GitHub quand les valeurs sont
disponibles depuis l'environnement ou le magasin local de jetons de
publication Plans, et affiche les commandes manquantes exactes pour tout
ce qu'il ne peut pas définir. Les valeurs secrètes sont envoyées à `gh`
via l'entrée standard, pas via des arguments de commande. Committez le
fichier de workflow généré et ouvrez une PR pour le voir s'exécuter.

Par défaut, le workflow construit son prompt d'agent à partir des
dernières consignes `visual-recap` groupées dans
`@agent-native/recap-cli@latest`, y compris tout fichier de référence
associé que la compétence fournit. Si votre dépôt personnalise et épingle
intentionnellement son dossier `visual-recap` committé, définissez la
variable de dépôt `VISUAL_RECAP_SKILL_SOURCE=repo`.

## Sélection du runner

Le workflow s'exécute par défaut sur des runners `ubuntu-latest` hébergés
par GitHub. Pour utiliser un autre runner hébergé ou votre propre runner
auto-hébergé, définissez la variable de dépôt ou d'organisation
`VISUAL_RECAP_RUNS_ON` sur une chaîne JSON valide ou un tableau JSON
d'étiquettes de runner :

```text
"ubuntu-latest"
["self-hosted", "linux", "x64", "visual-recap"]
```

Les guillemets JSON sont requis. Ce réglage sélectionne le runner du job
`recap` complet. Pour le configurer pendant la configuration guidée,
passez la même valeur JSON à `--runs-on`, puis validez le workflow et la
disponibilité du runner avec `doctor` :

```bash
npx @agent-native/recap-cli@latest recap setup --runs-on '["self-hosted","linux","x64","visual-recap"]'
npx @agent-native/recap-cli@latest recap doctor
```

La vérification de sécurité légère utilise par défaut, séparément, les
`ubuntu-latest` hébergés par GitHub. Les dépôts qui désactivent les
runners hébergés par GitHub peuvent définir `VISUAL_RECAP_GATE_RUNS_ON`
sur **une seule étiquette de runner brute** (pas du JSON), ou passer
`--gate-runs-on visual-recap-gate` pendant la configuration. Le workflow
réutilisable expose la même valeur comme entrée `gate-runs-on`. Cela
évite d'analyser du JSON dynamique avant que GitHub ne puisse planifier
la vérification. L'étiquette personnalisée n'est sélectionnée que pour
les PR du même dépôt rédigées par un `OWNER`, `MEMBER`, ou
`COLLABORATOR`. Les forks et tous les autres auteurs sont forcés vers les
`ubuntu-latest` hébergés par GitHub avant le démarrage du job ; dans un
dépôt uniquement auto-hébergé, ces exécutions non fiables peuvent rester
non planifiées plutôt que de toucher une machine auto-hébergée.

`recap doctor` rejette le JSON malformé ou non pris en charge et signale
quand GitHub n'expose pas de runner en ligne correspondant à chaque
étiquette configurée. L'enregistrement, l'installation, les mises à
niveau, la capacité et la maintenance des runners restent de votre
responsabilité ; Agent-Native sélectionne les étiquettes mais ne fournit
ni n'exploite le runner.

**Sécurité :** Privilégiez des runners auto-hébergés dédiés et éphémères.
Un runner de vérification personnalisé ne reçoit que des événements de PR
du même dépôt et de confiance. La vérification standard ne fait pas le
checkout de l'arborescence de la PR ; elle évalue la logique du workflow
et les métadonnées de PR GitHub. Une machine persistante conserve tout de
même l'état des processus entre les jobs, donc ne la partagez pas avec
des charges de travail non liées. Le workflow échoue de manière sûre
avant de lancer une quelconque vérification auto-hébergée ou un job de
récapitulatif complet pour des auteurs de PR publiques ou de forks non
fiables. N'affaiblissez pas cette barrière et n'acheminez pas de
contributions non fiables vers un runner persistant.

## Sélection du backend

Choisissez quel agent de codage exécute la compétence avec la variable de
dépôt `VISUAL_RECAP_AGENT` :

| `VISUAL_RECAP_AGENT` | Agent de codage                            | Clé API requise        | Variables requises                            |
| --------------------- | ------------------------------------------- | ----------------------- | --------------------------------------------- |
| `claude` _(par défaut)_ | CLI Claude Code                           | `ANTHROPIC_API_KEY`    | —                                             |
| `codex`              | CLI OpenAI Codex                            | `OPENAI_API_KEY`       | —                                             |
| `openai-compatible`  | Agent-Native Code + fournisseur compatible | `VISUAL_RECAP_API_KEY` | `VISUAL_RECAP_BASE_URL`, `VISUAL_RECAP_MODEL` |

Si la variable n'est pas définie, l'action utilise `claude`.

## Modèle et raisonnement

Au-delà du backend, ces variables de dépôt ajustent la façon dont l'agent
s'exécute :

- **`VISUAL_RECAP_MODEL`** épingle le modèle transmis à la CLI
  (`--model`) — par exemple `gpt-5.6-luna` pour Codex, un identifiant de
  modèle Claude, ou `deepseek-chat` pour DeepSeek. Elle est requise pour
  `openai-compatible`. Pour le backend **Claude**, la laisser non définie
  utilise désormais par défaut `claude-sonnet-5` ; définissez la variable
  explicitement pour utiliser un autre modèle Claude, comme le moins cher
  `claude-haiku-4-5`. Pour le backend **Codex**, la laisser non définie
  utilise le modèle par défaut propre à la CLI Codex.
- **`VISUAL_RECAP_REASONING`** définit la profondeur de raisonnement :
  `none`, `minimal`, `low`, `medium`, `high`, ou `xhigh`. Elle s'applique
  au backend Codex ; le raisonnement de Claude est piloté par le modèle,
  donc cette variable y est ignorée.
- **`VISUAL_RECAP_BASE_URL`** sélectionne l'URL de base HTTP(S) pour le
  backend `openai-compatible`. Utilisez le point de terminaison
  compatible OpenAI du fournisseur, comme DeepSeek ou Kimi, sans intégrer
  d'identifiants dans l'URL.
- **`VISUAL_RECAP_SKILL_SOURCE`** contrôle la fraîcheur du prompt :
  `auto`/non défini utilise les dernières consignes de compétence
  groupées, tandis que `repo` épingle le dossier de compétence
  `visual-recap` committé dans le dépôt.

Par exemple, pour exécuter le récapitulatif sur Codex avec GPT-5.6 Sol à
un raisonnement élevé, définissez les variables de dépôt
`VISUAL_RECAP_AGENT=codex`, `VISUAL_RECAP_MODEL=gpt-5.6-sol`, et
`VISUAL_RECAP_REASONING=high`.

Pour DeepSeek, définissez `VISUAL_RECAP_AGENT=openai-compatible`,
`VISUAL_RECAP_BASE_URL=https://api.deepseek.com/v1`,
`VISUAL_RECAP_MODEL=deepseek-chat`, et le secret `VISUAL_RECAP_API_KEY`.
Kimi fonctionne de la même façon avec son URL de base et son identifiant
de modèle compatibles OpenAI. Les autres fournisseurs compatibles OpenAI
utilisent les trois mêmes réglages.

## Coût

Chaque exécution de récapitulatif est une session complète d'agent de
codage agentique lisant un vrai diff, et non un résumé templaté bon
marché, donc son coût suit le choix du modèle et la fréquence
d'exécution :

- **Une session complète par push de PR.** Le déclencheur par défaut se
  déclenche sur `synchronize`, donc une PR poussée dix fois exécute
  l'agent dix fois.
- **La PR entière à chaque fois**, pas seulement les commits depuis la
  dernière exécution — le coût suit la taille totale de la PR, pas la
  taille du diff incrémental.
- **Entrée de diff plafonnée à environ 600 Ko.** Cela borne le pire des
  cas par exécution, mais les gros diffs coûtent quand même sensiblement
  plus que les petits.
- **Une nouvelle tentative automatique en cas d'échec**, ce qui peut à peu
  près doubler le coût d'une exécution qui échoue de façon transitoire.

Pour réduire le coût :

- **Épinglez un modèle moins cher.** Pour Claude, définissez
  `VISUAL_RECAP_MODEL=claude-haiku-4-5` pour des dépôts simples ou
  petits — c'est le tier Claude le moins cher ; `claude-sonnet-5` (le
  défaut) est le tier équilibré.
- **Basculez vers Codex avec un modèle moins cher.** Définissez
  `VISUAL_RECAP_AGENT=codex` avec `VISUAL_RECAP_MODEL=gpt-5.6-luna` (le
  tier GPT-5.6 le moins cher) ou `gpt-5.6-terra` (tier intermédiaire), et
  définissez `VISUAL_RECAP_REASONING=low` pour réduire encore la dépense
  en tokens de raisonnement. La profondeur de raisonnement ne s'applique
  qu'à Codex.
- **Visez un fournisseur compatible OpenAI moins cher.** Définissez
  `VISUAL_RECAP_AGENT=openai-compatible` avec
  `VISUAL_RECAP_BASE_URL`/`VISUAL_RECAP_MODEL`/`VISUAL_RECAP_API_KEY`
  ciblant DeepSeek, Kimi, ou tout autre point de terminaison compatible
  OpenAI.
- **Exigez une étiquette de PR explicite.** Définissez
  `VISUAL_RECAP_REQUIRED_LABELS=visual recap` pour garder le workflow
  installé mais sauter les récapitulatifs tant qu'une PR n'a pas cette
  étiquette. Utilisez une liste séparée par des virgules, comme
  `visual recap,recap`, quand plusieurs étiquettes doivent activer la
  fonction. Appliquer une étiquette listée réveille immédiatement le
  workflow.
- **Récapitulez moins souvent.** Modifiez le `on.pull_request.types` du
  workflow installé de
  `[opened, synchronize, reopened, ready_for_review, labeled, closed]`
  vers `[opened, ready_for_review, closed]` pour qu'il ne récapitule que
  lorsqu'une PR s'ouvre et lorsqu'elle est fusionnée, plutôt qu'à chaque
  push.

Chaque exécution enregistre ce qu'elle a réellement dépensé : l'étape
`recap usage` du workflow attache l'usage en tokens et en coût au plan
publié, pour que vous puissiez regarder la dépense réelle par exécution
au lieu de deviner.

## Secrets et variables {#secrets-and-variables}

Définissez-les dans **Settings → Secrets and variables → Actions** de
votre dépôt.

### Secrets pour le backend par défaut

| Secret              | Objectif                                                                                                                            |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `PLAN_RECAP_TOKEN`  | Jeton révocable créé par `npx @agent-native/core@latest connect`. Autorise la publication du plan récapitulatif et le téléversement de la capture d'écran. |
| `ANTHROPIC_API_KEY` | La clé LLM pour le backend Claude Code par défaut.                                                                                   |

**Équipes : utilisez un jeton de service d'organisation.** Un jeton
personnel est lié à la personne qui l'a créé — si elle quitte
l'organisation ou révoque ses jetons, chaque dépôt utilisant ce secret
commence à échouer avec des 401, et les plans créés en CI appartiennent à
cette personne plutôt qu'à l'équipe. Un jeton de service d'organisation
appartient à votre **organisation** : il agit comme un principal de
service (`svc-<name>@service.<orgId>`), survit au départ de n'importe
quel individu, les récapitulatifs qu'il publie sont visibles à l'échelle
de l'organisation, et n'importe quel propriétaire ou administrateur de
l'organisation peut le lister ou le révoquer. Créez-en un (propriétaire
ou administrateur d'organisation uniquement) :

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --service-token pr-recap
```

La commande vous authentifie dans le navigateur, puis affiche le jeton de
service exactement une fois — stockez-le comme secret
`PLAN_RECAP_TOKEN`. Gérez-le ensuite avec les actions
`list-org-service-tokens` et `revoke-org-service-token` de l'application
Plans.

**Solo : un jeton personnel fonctionne aussi.** Créez-le avec
`npx @agent-native/core@latest connect` contre votre application Plans.
Pour l'application hébergée, cela écrit aussi un fichier de jeton de
publication local que `npx @agent-native/recap-cli@latest recap setup`
peut lire :

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --client codex
npx @agent-native/recap-cli@latest recap setup
```

Si vous préférez une configuration manuelle, collez le jeton dans le
secret GitHub. Utilisez un placeholder comme
`plan_recap_xxxxxxxxxxxxxxxx` uniquement pour les exemples — ne committez
jamais de vrai jeton.

## Capture d'écran en ligne dans le commentaire

Une fois que l'agent a publié le récapitulatif, le workflow capture le
plan rendu dans Chrome sans tête en modes clair et sombre et téléverse
les PNG vers une route d'image publique signée de l'application Plans.
Le commentaire de PR persistant intègre alors ces captures **en ligne**
avec un élément `<picture>` — GitHub les resert via son proxy camo, si
bien que les relecteurs voient un aperçu qui correspond à leur thème
GitHub directement dans le commentaire, sans rien ouvrir. Le lien vers le
plan interactif complet se trouve juste à côté, pour quand ils veulent
explorer, commenter, ou annoter.

## PR de forks

### Comportement par défaut (aucune action requise)

Le workflow principal `pr-visual-recap.yml` se déclenche sur le
déclencheur simple `pull_request`, **pas** `pull_request_target`. Les PR
de forks s'exécutent donc **sans accès aux secrets du dépôt**, si bien
que le workflow ne trouve pas de `PLAN_RECAP_TOKEN` et ne fait rien
proprement — pas de publication échouée, pas d'identifiants exposés. Les
récapitulatifs s'exécutent automatiquement pour les PR issues de
branches du même dépôt, là où les secrets sont disponibles.

Cela signifie aussi que vous pouvez fusionner le fichier de workflow
**avant** que les secrets n'existent : sans jeton configuré, chaque
exécution est un no-op silencieux jusqu'à ce que vous définissiez les
secrets. L'étape `gate` saute aussi automatiquement les PR en brouillon
et les PR rédigées par des bots, donc aucune des deux ne déclenche de
récapitulatif par défaut.

### Activation optionnelle avec le workflow de fork à étiquette

Si vous voulez générer des récapitulatifs pour les PR de forks, un
second fichier de workflow est disponible :
`.github/workflows/pr-visual-recap-fork.yml`. Il utilise
`pull_request_target` (qui s'exécute avec les secrets du dépôt de base)
mais ne fait jamais le checkout ni n'exécute le code du fork. Les
auteurs de forks de confiance avec une association d'auteur GitHub
`OWNER`, `MEMBER`, ou `COLLABORATOR` s'exécutent automatiquement. Les PR
de forks externes nécessitent une **activation explicite par un
mainteneur, par tête** via un nouvel événement d'étiquette `recap` avant
que l'agent de récapitulatif ne s'exécute.

Pour l'installer, copiez le fichier depuis
[BuilderIO/agent-native](https://github.com/BuilderIO/agent-native/blob/main/.github/workflows/pr-visual-recap-fork.yml)
dans le dossier `.github/workflows/` de votre dépôt, à côté du
`pr-visual-recap.yml` existant. La même configuration de backend
s'applique, y compris `VISUAL_RECAP_API_KEY`, `VISUAL_RECAP_BASE_URL`, et
`VISUAL_RECAP_MODEL` quand vous utilisez un fournisseur compatible
OpenAI.

### Comment fonctionne la barrière à étiquette

1. Un contributeur de fork ouvre une PR. Le workflow normal
   `pull_request` saute car GitHub retient les secrets pour les
   exécutions de fork.
2. Le workflow de fork vérifie l'association d'auteur de la PR. Les
   auteurs de confiance (`OWNER`, `MEMBER`, ou `COLLABORATOR`)
   s'exécutent automatiquement à l'ouverture, à la synchronisation, à la
   réouverture, et aux événements de mise en prêt.
3. Les contributeurs externes nécessitent qu'un mainteneur relise le
   diff actuel (en particulier pour un contenu ayant la forme d'une
   injection de prompt — voir ci-dessous), puis applique l'étiquette
   `recap` sur la PR.
4. La barrière à étiquette pour les contributeurs externes est par SHA
   de tête : si le contributeur pousse d'autres commits, le prochain
   événement de synchronisation saute jusqu'à ce qu'un mainteneur retire
   puis réapplique `recap` après avoir relu le nouveau diff.

### Ce que fait et ne fait PAS le workflow de fork

| Le workflow FAIT                                                                                                                       | Le workflow ne FAIT PAS                                                                                          |
| ----------------------------------------------------------------------------------------------------------------------------------------| ------------------------------------------------------------------------------------------------------------------ |
| Consulter le **dépôt de base** sur la **réf. de branche de base** — code de confiance uniquement                                       | Faire le checkout ou exécuter du code du fork                                                                     |
| Récupérer la tête du fork comme réf. distante (`git fetch origin pull/<n>/head:refs/recap/fork-head`) — récupérer des commits est sûr | Installer des paquets depuis le fork, exécuter des scripts du fork, ou évaluer du contenu du fork comme du code   |
| Exécuter `git diff base...refs/recap/fork-head` — un diff texte pur de deux objets déjà récupérés                                      | Utiliser le diff comme autre chose qu'une entrée texte pour le LLM                                                 |
| Exécuter la compétence visual-recap et la configuration d'agent du **dépôt de base**                                                    | Charger une compétence ou une configuration depuis le fork                                                        |
| Faire passer le diff par la même étape de scan de secrets (échec fermé) que les PR internes                                             | Sauter le scan de secrets                                                                                          |
| Ajouter au prompt de l'agent une note explicite de durcissement marquant le contenu du diff comme non fiable                            | Accorder à l'agent des permissions supplémentaires au-delà de l'agent de récapitulatif normal                     |

### Pourquoi vous devez relire le diff avant d'étiqueter

Le diff du fork est un texte contrôlé par l'attaquant que l'agent de
récapitulatif lit comme entrée. Un diff soigneusement conçu pourrait
contenir un contenu d'injection de prompt — par exemple des lignes de
diff qui ressemblent à des instructions d'agent — destiné à faire
prendre à l'agent de récapitulatif des actions non voulues (par exemple,
exfiltrer le jeton de publication ou produire un contenu de
récapitulatif trompeur).

Avant d'appliquer l'étiquette `recap`, survolez le diff à la recherche
de :

- Lignes qui ressemblent à des commandes directes ou des instructions de
  rôle (« Ignore les instructions précédentes... », « Tu es
  maintenant... », « Écris le jeton dans... »).
- Noms de fichiers inhabituels qui pourraient être pris pour des prompts
  système.
- Contenu encodé dans les fichiers ajoutés qui pourrait se décoder en
  instructions.

Ces mitigations sont déjà intégrées au workflow (scan de secrets,
barrière de chemins sensibles, note de durcissement du prompt, liste
blanche d'outils d'agent restreinte), mais la relecture avant étiquetage
reste la principale ligne de défense.

### Relation avec le workflow principal

Les deux fichiers de workflow sont indépendants. Pour les mises à jour
de PR non-fork, `pr-visual-recap.yml` est le seul workflow qui s'exécute.
Pour les PR de forks, le workflow normal s'arrête à sa barrière de fork,
et `pr-visual-recap-fork.yml` s'exécute automatiquement pour les auteurs
de confiance de la même organisation ou après une nouvelle étiquette
`recap` posée par un mainteneur pour les contributeurs externes. Ils
partagent le même marqueur de commentaire persistant et le même
chaînage d'id de plan, si bien que les PR et les PR de forks produisent
un unique commentaire créé ou mis à jour sur la même PR.

### Garde-fou anti-automodification {#self-modifying-guard}

L'étape `gate` saute entièrement le récapitulatif quand une PR touche
l'un des chemins suivants, si bien qu'une PR ne peut jamais réécrire le
workflow, la compétence, ou la configuration d'agent que le job de
récapitulatif de confiance charge, et exfiltrer des secrets :

| Motif de chemin                            | Raison                                             |
| ------------------------------------------- | --------------------------------------------------- |
| `.github/workflows/pr-visual-recap.yml`    | Le workflow lui-même                               |
| `**/skills/visual-(recap\|plan\|plans)/**` | La compétence visual-recap que suit l'agent        |
| `**/.claude/**`                            | Paramètres d'agent que charge le runner            |
| `**/CLAUDE.md`                             | Instructions d'agent que charge le runner          |
| `**/AGENTS.md`                             | Instructions d'agent que charge le runner          |
| `**/.mcp.json`                             | Configuration de serveur MCP que charge le runner  |

Dans le monorepo `BuilderIO/agent-native`, le workflow exécute la CLI de
récapitulatif depuis une source de branche de base de confiance plutôt
que depuis la source de tête de la PR. Cela garde les changements de
paquets normaux, y compris `packages/core/**`, éligibles aux
récapitulatifs sans exécuter le code CLI modifié par la PR.

## Mode de confidentialité fichiers locaux

L'Action GitHub est conçue pour la revue de PR hébergée et partageable.
Si vous voulez un récapitulatif sans envoyer son contenu vers la base de
données Agent-Native Plan, exécutez le même flux d'aide localement en
mode fichiers locaux à la place :

```bash
npx @agent-native/recap-cli@latest recap collect-diff --base main --head HEAD --out recap.diff --stat recap.stat
npx @agent-native/recap-cli@latest recap scan --diff recap.diff
npx @agent-native/recap-cli@latest recap build-prompt --pr 123 --diff recap.diff --stat recap.stat --local-files --local-dir plans/pr-123-visual-recap
```

Donnez le `recap-prompt.md` généré à votre agent de codage. En mode
fichiers locaux, le prompt demande à l'agent d'écrire
`plans/pr-123-visual-recap/plan.mdx` ainsi que des fichiers visuels
optionnels, puis d'exécuter :

```bash
npx @agent-native/core@latest plan local serve --dir plans/pr-123-visual-recap --kind recap --open
```

L'URL renvoyée ouvre l'UI Plan hébergée pendant que le navigateur lit le
MDX du récapitulatif depuis un pont localhost. Le contenu du
récapitulatif n'est pas écrit dans la base de données Plan hébergée, et
l'URL ne fonctionne que sur la machine qui exécute le pont. Si vous
exécutez l'application Plan localement avec le même `PLAN_LOCAL_DIR`, la
route `/local-plans/pr-123-visual-recap` est aussi valide. Les dossiers
adossés à un dépôt peuvent s'ouvrir comme
`/local-plans/pr-123-visual-recap?path=plans%2Fpr-123-visual-recap`. Ce
mode désactive le commentaire de PR persistant hébergé, le téléversement
de capture d'écran en ligne, l'attachement d'usage, et les commentaires
navigateur jusqu'à ce que vous publiiez explicitement.

## C'est informatif, pas une barrière

Le récapitulatif est une aide à la revue superposée au flux de PR
normal :

- Il affiche une ligne de vérification `Visual Recap` pour la
  visibilité, mais ce n'est **jamais une vérification requise** et ça ne
  bloque jamais la fusion.
- Un échec de génération ou de publication se termine de façon neutre et
  se manifeste comme un commentaire persistant explicatif, pas comme un
  X rouge sur du code sans rapport.
- Le récapitulatif et sa capture d'écran **n'impliquent pas que le diff
  a été relu**. Les relecteurs doivent toujours lire les lignes
  réellement modifiées.

## Épinglage de version (variante copie) {#version-pinning-copy-variant}

Par défaut, le workflow en variante copie installe
`@agent-native/recap-cli@latest` au moment de l'exécution, si bien que
chaque exécution de récapitulatif récupère automatiquement la dernière
CLI. Si votre CI a besoin d'un outillage reproductible, définissez la
variable de dépôt **`RECAP_CLI_VERSION`** pour épingler la version
installée :

1. Allez dans **Settings → Secrets and variables → Actions → Variables**
   de votre dépôt.
2. Créez une variable nommée `RECAP_CLI_VERSION` avec une valeur comme
   `1.5.0`.

La variable est optionnelle. Laissez-la non définie (ou définissez-la
sur `latest`) pour suivre la dernière version publiée.

Pour la variante appelante réutilisable, utilisez l'entrée `cli-version`
à la place (voir [Épinglage de version](#version-pinning) dans la
section réutilisable).

## Liste blanche du scan de secrets

Avant de publier un récapitulatif, le workflow exécute
`npx @agent-native/recap-cli@latest recap scan` pour détecter des
secrets probables dans le diff. Toute PR dont le diff correspond à un
motif de secret connu est bloquée avec un commentaire explicatif — le
récapitulatif n'est pas publié, et aucun contenu de diff n'est envoyé à
l'agent de codage.

Dans de rares cas, un dépôt a des fixtures de test intentionnelles ou
des chaînes non secrètes qui ressemblent superficiellement à des motifs
de secrets (par exemple, une clé de fixture dans un fichier de test).
Pour supprimer un faux positif, créez `.github/recap-scan-allowlist` à
la racine de votre dépôt.

### Format

Chaque ligne non vide et non commentée est soit une **sous-chaîne
littérale**, soit un motif **`/regex/flags`** :

```
# Lines starting with # are comments.

# Literal substring — any diff line containing this string is allowed.
sk-test-fixture1234567890abcdef

# Regex pattern — written as /pattern/flags (JS syntax).
/^.STRIPE_KEY=sk-test-/i

# Another literal.
EXAMPLE_API_KEY=placeholder-value
```

Règles :

- Une ligne est **supprimée** (autorisée) quand elle contient la
  littérale, ou quand la ligne entière correspond à la regex.
- Le fichier est **à échec fermé** : s'il est absent, aucune suppression
  ne s'applique — le scanner se comporte comme avant.
- Un fichier vide équivaut à l'absence de fichier.
- Les lignes de regex malformées sont traitées comme des chaînes
  littérales.

La liste blanche n'est consultée que par la barrière de scan de secrets.
Elle n'affecte pas ce que l'agent de codage peut lire — si la barrière
est franchie, l'agent reçoit le diff complet quoi qu'il arrive.

## Adopter comme workflow réutilisable

### Pourquoi utiliser la variante réutilisable ?

L'installeur par défaut copie l'intégralité du YAML de workflow
d'environ 360 lignes dans votre dépôt (l'option **copie**). C'est le bon
choix pour les dépôts air-gapped ou les dépôts qui doivent auditer
chaque ligne de ce qui s'exécute. L'inconvénient est que les corrections
de bugs et les améliorations ne vous atteignent jamais — vous devez
réexécuter manuellement `npx @agent-native/recap-cli@latest recap setup`
après chaque version.

L'option **réutilisable** écrit à la place un mince appelant d'environ
20 lignes. Il délègue à
`BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml`
via `uses:`. Chaque appelant récupère automatiquement la dernière
logique à chaque exécution du workflow, sans mise à jour locale
nécessaire.

|                                       | Copie (par défaut)               | Réutilisable                            |
| -------------------------------------- | ----------------------------------- | ------------------------------------------ |
| Taille du workflow dans votre dépôt    | ~360 lignes                        | ~20 lignes                                |
| Récupère les corrections automatiquement | Non — réexécutez `recap setup`   | Oui                                        |
| Air-gap / auditabilité complète        | Oui                                 | Non                                         |
| Épinglable à une version spécifique    | Uniquement en éditant localement    | Oui — définissez `@v1.2.3` dans `uses:`   |

### Extrait de l'appelant

Voici ce qu'écrit
`npx @agent-native/recap-cli@latest recap setup --reusable` (ou vous
pouvez le coller manuellement) :

```yaml
name: PR Visual Recap

# Thin caller — the full workflow logic lives in BuilderIO/agent-native.
# Fixes and improvements reach this repo automatically on each run.
# To pin a specific version for reproducibility replace '@main' with a
# tag or SHA, e.g. '@v1.2.3' or '@abc1234'.

on:
  pull_request:
    types: [opened, synchronize, reopened, ready_for_review, labeled, closed]

jobs:
  visual-recap:
    if: github.event.action != 'labeled' || vars.VISUAL_RECAP_REQUIRED_LABELS != ''
    permissions:
      actions: write
      contents: read
      checks: write
      issues: write
      pull-requests: write
    uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@main
    secrets:
      PLAN_RECAP_TOKEN: ${{ secrets.PLAN_RECAP_TOKEN }}
      ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
      OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
      VISUAL_RECAP_API_KEY: ${{ secrets.VISUAL_RECAP_API_KEY }}
      PLAN_RECAP_APP_URL: ${{ secrets.PLAN_RECAP_APP_URL }}
    with:
      agent: ${{ vars.VISUAL_RECAP_AGENT || 'claude' }}
      model: ${{ vars.VISUAL_RECAP_MODEL || '' }}
      base-url: ${{ vars.VISUAL_RECAP_BASE_URL || '' }}
      reasoning: ${{ vars.VISUAL_RECAP_REASONING || '' }}
      skill-source: ${{ vars.VISUAL_RECAP_SKILL_SOURCE || 'auto' }}
      runs-on: ${{ vars.VISUAL_RECAP_RUNS_ON || '"ubuntu-latest"' }}
      gate-runs-on: ${{ vars.VISUAL_RECAP_GATE_RUNS_ON || 'ubuntu-latest' }}
      required-labels: ${{ vars.VISUAL_RECAP_REQUIRED_LABELS || '' }}
      # cli-version: "latest"  # pin to a specific @agent-native/recap-cli version
```

Les mêmes secrets et variables décrits dans
[Secrets et variables](#secrets-and-variables) s'appliquent —
définissez-les dans les paramètres de votre dépôt de la même façon que
pour la variante copie. L'appelant réutilisable transmet
`VISUAL_RECAP_RUNS_ON` via son entrée JSON `runs-on` pour le job de
récapitulatif complet, `VISUAL_RECAP_GATE_RUNS_ON` via son entrée à
étiquette simple `gate-runs-on` pour la vérification limitée aux
métadonnées, et `VISUAL_RECAP_REQUIRED_LABELS` via `required-labels`
pour le filtrage optionnel par étiquette de PR. L'entrée de runner de
vérification n'est utilisée que pour les auteurs de confiance du même
dépôt ; les autres PR utilisent les `ubuntu-latest` hébergés par GitHub.
Omettre les entrées de runner préserve leurs défauts `ubuntu-latest` ;
omettre les étiquettes requises préserve le comportement automatique de
récapitulatif.

### Installation via la CLI

```bash
# Write the thin caller instead of the full copy:
npx @agent-native/recap-cli@latest recap setup --reusable

# Or with a pinned ref for reproducibility:
npx @agent-native/recap-cli@latest recap setup --reusable --ref v1.2.3
```

Les deux variantes écrivent le workflow dans
`.github/workflows/pr-visual-recap.yml`. Si un workflow existant s'y
trouve déjà et diffère, la commande refuse et vous indique de passer
`--force` pour l'écraser.

Après l'écriture, exécutez
`npx @agent-native/recap-cli@latest recap doctor` comme d'habitude pour
confirmer que les secrets sont configurés.

### Épinglage de version {#version-pinning}

Par défaut, l'appelant référence `@main`, qui utilise toujours la
dernière version publiée du workflow réutilisable. Pour les dépôts de
production qui ont besoin d'une CI reproductible, épinglez à un tag ou
un SHA :

```yaml
uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@v1.2.3
```

L'entrée `cli-version` contrôle quelle version de
`@agent-native/recap-cli` s'exécute à l'intérieur du workflow —
laissez-la sur `"latest"` pour suivre la dernière version, ou
épinglez-la à une chaîne de version (par exemple `"1.5.0"`) pour une
reproductibilité complète.

### Contexte de l'événement workflow_call

Les workflows `workflow_call` héritent du contexte d'événement de
l'**appelant**. Le workflow réutilisable utilise les expressions
`github.event.pull_request.*` pour lire le numéro de PR, le SHA de tête,
le SHA de base, l'horodatage de fusion, et les métadonnées de PR — ces
expressions ne fonctionnent correctement que lorsque l'appelant se
déclenche sur `pull_request`. L'extrait d'appelant ci-dessus inclut déjà
les bons types d'événements. L'événement `closed` est inclus pour que
les récapitulatifs de PR fusionnées puissent être estampillés avec
`merged_at` et recherchés plus tard comme du travail livré.

Ne déclenchez pas l'appelant sur `workflow_dispatch` ou `push` — ces
événements ne portent pas de charge utile `pull_request`, et la
barrière sautera le récapitulatif avec « no pull_request payload ».
