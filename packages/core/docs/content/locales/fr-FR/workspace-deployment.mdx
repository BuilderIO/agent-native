# Déploiement de workspace

Si votre projet est un [workspace](/docs/multi-app-workspace) avec plusieurs applications, vous pouvez déployer chaque application vers une seule origine au lieu de gérer des déploiements séparés par application. Cette page couvre le chemin géré en une commande et une alternative auto-hébergée avec Docker Compose. Voir [Déploiement](/docs/deployment) pour choisir d'abord une base de données, un préréglage, et une plateforme.

## Une origine, plusieurs applications {#workspace-deploy}

Déployez chaque application d'un workspace vers une seule origine avec une seule commande :

```bash
npx @agent-native/core@latest deploy
# https://your-agents.com/mail/*       → apps/mail
# https://your-agents.com/calendar/*   → apps/calendar
# https://your-agents.com/forms/*      → apps/forms
```

**Même origine** signifie que chaque application ressemble à une partie du même site web pour le navigateur. Cela vous donne deux grands avantages gratuitement :

- **Session de connexion partagée**. Connectez-vous à une application, et toutes les applications sont connectées.
- **A2A inter-applications sans configuration**. Mentionner `@calendar` depuis mail est une requête de même origine. Il n'y a ni CORS ni signature JWT entre applications sœurs.

<Callout tone="info">

En interne, chaque application est construite avec son propre **chemin de base**, un préfixe d'URL comme `/mail` défini via `APP_BASE_PATH`/`VITE_APP_BASE_PATH`, puis empaqueté pour le préréglage Nitro cible. Cloudflare Pages achemine via un **worker répartiteur** généré, un petit script à `dist/_worker.js` qui lit le chemin entrant et transfère la requête vers l'application correspondante. Netlify utilise une fonction par application plus des redirections générées. Vercel écrit une sortie `.vercel/output` au niveau du workspace en utilisant la Build Output API.

</Callout>

<Callout tone="warning">

Les builds de workspace hébergés nécessitent `A2A_SECRET` dans l'environnement du fournisseur de déploiement. Sans lui, Slack, les webhooks entrants, et la reprise A2A inter-applications ne fonctionnent pas, car tous passent par des processeurs d'arrière-plan signés. Les vérifications d'artefacts locales avec `--build-only` fonctionnent toujours sans lui.

</Callout>

<Callout tone="info">

Vous configurez une commande de build de fournisseur au lieu de déployer manuellement ? Ajoutez `--build-only` à la même commande, par exemple `npx @agent-native/core@latest deploy --preset vercel --build-only`. Cela écrit directement la sortie, donc aucun `vercel.json` n'est requis pour le routage du workspace.

Vous préférez un domaine séparé par application plutôt qu'une origine partagée ? Chaque application du workspace reste déployable indépendamment. Exécutez `cd apps/<name> && npx @agent-native/core@latest build` comme un scaffold autonome.

</Callout>

## Workspace auto-hébergé avec Docker Compose {#workspace-docker-compose}

Un workspace n'est pas aujourd'hui un seul processus serveur Nitro. Chaque application construit toujours dans son propre répertoire `.output/` et exécute son propre serveur Node/Nitro, donc auto-héberger un workspace signifie exécuter plusieurs serveurs derrière un seul point d'entrée.

Un **reverse proxy** est ce point d'entrée unique dans le schéma ci-dessus : il reçoit chaque requête et la transfère au bon conteneur selon le chemin de l'URL, le même rôle que joue le worker répartiteur de Cloudflare pour un déploiement géré. Sur un VPS, cela signifie un conteneur par application du workspace, tous pointant vers la même base de données Postgres et les mêmes secrets de production partagés, avec le proxy devant.

<Steps>

### Construisez chaque application avec un chemin de base correspondant

Le chemin de base est une entrée au moment du build pour le bundle client et une entrée d'exécution pour le serveur. Construisez chaque application avec le même chemin vers lequel le proxy l'acheminera :

```bash maxLines=8
APP_BASE_PATH=/mail VITE_APP_BASE_PATH=/mail npx @agent-native/core@latest build
node .output/server/index.mjs
```

### Écrivez un Dockerfile réutilisable

Prenez le nom de l'application et le préfixe de chemin comme arguments de build, de sorte qu'un seul Dockerfile serve chaque application du workspace :

```dockerfile filename="Dockerfile.workspace-app" maxLines=12
FROM node:24-slim AS build
WORKDIR /workspace
RUN corepack enable
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY packages ./packages
COPY apps ./apps
ARG APP_NAME
ARG APP_BASE_PATH
ENV APP_BASE_PATH=$APP_BASE_PATH
ENV VITE_APP_BASE_PATH=$APP_BASE_PATH
RUN pnpm install --frozen-lockfile
RUN pnpm --dir apps/$APP_NAME build

FROM node:24-slim
WORKDIR /app
ARG APP_NAME
ARG APP_BASE_PATH
ENV NODE_ENV=production
ENV PORT=3000
ENV APP_BASE_PATH=$APP_BASE_PATH
COPY --from=build /workspace/apps/$APP_NAME/.output .output
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

### Composez Postgres, les applications, et le proxy

Cet exemple utilise Caddy car il peut terminer HTTP localement ou se placer derrière le proxy SSL de Cloudflare, mais la partie importante est le routage par préfixe de chemin :

```yaml filename="docker-compose.yml" maxLines=30
services:
  postgres:
    image: postgres:17
    restart: unless-stopped
    environment:
      POSTGRES_DB: agent_native
      POSTGRES_USER: agent_native
      POSTGRES_PASSWORD: change-me
    volumes:
      - postgres-data:/var/lib/postgresql/data

  mail:
    build:
      context: .
      dockerfile: Dockerfile.workspace-app
      args:
        APP_NAME: mail
        APP_BASE_PATH: /mail
    restart: unless-stopped
    environment:
      DATABASE_URL: postgres://agent_native:change-me@postgres:5432/agent_native
      BETTER_AUTH_URL: https://agents.example.com/mail
      BETTER_AUTH_SECRET: ${BETTER_AUTH_SECRET}
      A2A_SECRET: ${A2A_SECRET}
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
    depends_on:
      - postgres

  calendar:
    build:
      context: .
      dockerfile: Dockerfile.workspace-app
      args:
        APP_NAME: calendar
        APP_BASE_PATH: /calendar
    restart: unless-stopped
    environment:
      DATABASE_URL: postgres://agent_native:change-me@postgres:5432/agent_native
      BETTER_AUTH_URL: https://agents.example.com/calendar
      BETTER_AUTH_SECRET: ${BETTER_AUTH_SECRET}
      A2A_SECRET: ${A2A_SECRET}
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
    depends_on:
      - postgres

  proxy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
    depends_on:
      - mail
      - calendar

volumes:
  postgres-data:
```

### Configurez le proxy

```caddyfile filename="Caddyfile"
agents.example.com {
  reverse_proxy /mail* mail:3000
  reverse_proxy /calendar* calendar:3000
}
```

</Steps>

<Callout tone="info">

- Gardez `DATABASE_URL`, `BETTER_AUTH_SECRET`, `A2A_SECRET`, et les autres
  secrets de production identiques entre les conteneurs d'applications quand vous
  voulez une authentification, des identifiants, et une A2A inter-applications partagés.
- Définissez `BETTER_AUTH_URL` sur l'URL publique pour ce chemin d'application. Les URL de
  rappel OAuth doivent utiliser la même URL publique.
- Ne comptez pas sur le système de fichiers du conteneur pour les données de production. Utilisez
  Postgres (ou un autre backend SQL persistant) pour `DATABASE_URL`.
- Si Cloudflare termine TLS devant le VPS, configurez Cloudflare pour envoyer
  des en-têtes `X-Forwarded-Proto` / `X-Forwarded-Host` normaux et acheminer l'hôte
  public vers le conteneur proxy.

</Callout>
