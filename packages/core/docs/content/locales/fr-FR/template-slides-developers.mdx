# Guide développeur

Cette page est destinée à toute personne qui personnalise le modèle Diapositives ou l'étend : le modèle de données SQL, comment les écritures concurrentes restent sûres, chaque action appelable par l'agent, la carte des routes, et où effectuer les changements courants.

## Démarrage rapide

```bash
npx @agent-native/core@latest create my-slides --standalone --template slides
```

Consultez [Bien démarrer](/docs/getting-started) pour le reste de la configuration (`cd`, `pnpm install`, `pnpm dev`) et les principes fondamentaux du framework.

## Modèle de persistance

Chaque deck est un unique blob JSON dans `decks.data`. Chaque écriture passe par une action côté serveur de lecture-modification-écriture qui détient un verrou par deck, si bien que des écrivains concurrents, un humain et l'agent, ou deux humains, touchant différentes diapositives du même deck, n'écrasent jamais le travail l'un de l'autre.

- **Les actions de l'agent** (`add-slide`, `update-slide`) utilisent leurs propres actions granulaires dédiées et partagent ce même verrou.
- **L'éditeur du navigateur** met en file d'attente des opérations granulaires (`patch-slide`, `delete-slide`, `reorder-slides`, `add-slide`, `patch-deck-fields`) via `patch-deck` plutôt qu'un PUT complet du deck.

<Callout id="doc-block-slides10" tone="warning">

Si vous étendez le chemin de sauvegarde de l'éditeur, mettez en file d'attente une nouvelle opération via `patch-deck`. N'ajoutez pas de nouveau PUT complet du deck. Cela réintroduirait la course « dernière écriture gagne » que le verrou existe pour empêcher.

</Callout>

Les tables de partages du framework (`deck_shares`, `design_system_shares`) associent des principaux, utilisateurs ou organisations, à des rôles spectateur / éditeur / administrateur par ressource, et sont créées via l'utilitaire partagé `createSharesTable` plutôt qu'écrites à la main.

#### Structure des diapositives

Chaque diapositive à l'intérieur de `decks.data` est :

```json
{
  "id": "slide-1",
  "layout": "title",
  "content": "<div class=\"fmd-slide\" style=\"...\">...</div>"
}
```

`content` est du HTML brut. Le moteur de rendu fournit le rapport hauteur/largeur fixe et l'arrière-plan, et le HTML fournit tout le reste. L'intégration riche est également prise en charge : des diagrammes dessinés à la main et des graphiques en direct peuvent vivre dans une diapositive aux côtés du HTML classique.

## Inventaire des actions

### Cycle de vie du deck

- `create-deck` — nouveau deck, éventuellement pré-rempli avec des diapositives, ou remplacement groupé atomique des diapositives d'un deck existant. Omettez `slides` ou passez `[]` pour un deck vide. L'action ouvre le nouveau deck via l'état de l'application.
- `get-deck` — JSON complet du deck, ou une vue compacte récapitulative des diapositives
- `list-decks` — tous les decks visibles par l'appelant, avec des projections légère/compacte/diapositives complètes pour un polling peu coûteux
- `duplicate-deck` — copier un deck avec de nouveaux identifiants de diapositive
- `update-deck-aspect-ratio` — 16:9, 1:1, 9:16, ou 4:5

`add-deck`, `save-deck`, et `delete-deck` soutiennent les flux de création optimiste, d'annulation/rétablissement et de suppression de l'éditeur du navigateur. L'agent utilise plutôt `create-deck`, `add-slide`/`update-slide`/`patch-deck`, et les actions de partage propres au framework.

### Demandes d'accès

- `request-deck-access`, `approve-deck-access-request`, `get-deck-access-status` — le flux de demande d'accès pour un deck privé : un visiteur sans accès en fait la demande, le propriétaire approuve ou refuse depuis l'application ou la route `/access-request/approve`, et chaque partie peut interroger le statut actuel

### Modifications de diapositives

- `add-slide` — ajouter (ou insérer à une position) une diapositive. Appelez-la de manière séquentielle après un `create-deck` vide pour que l'éditeur puisse afficher la progression.
- `update-slide` — modification chirurgicale par recherche/remplacement ou remplacement complet du contenu de la diapositive
- `patch-deck` — la file d'opérations granulaires que l'éditeur du navigateur utilise au lieu d'un PUT complet du deck
- `get-layout-overflows` — lire les résultats d'ajustement de diapositive mesurés par le navigateur, si bien qu'une modification qui ne rentre plus dans sa mise en page peut être détectée et révisée

### Historique

- `list-deck-versions`, `get-deck-version`, `restore-deck-version` — chaque écriture prend d'abord un instantané, si bien que n'importe quel point dans le temps peut être répertorié et restauré

### Commentaires

- `list-slide-comments`, `add-slide-comment`, `update-slide-comment`, `delete-slide-comment`

### Importation

- `import-pptx`, `import-docx`, `import-google-doc` — importateurs dédiés à un seul format
- `import-google-slides-reference` — importer un deck Google Slides comme deck de référence réutilisable, plutôt que d'intégrer son contenu dans le deck de travail
- `import-file` — un point d'entrée unique pour PPTX, DOCX, ou PDF, ou un fichier Figma `.fig` (qui est acheminé vers l'indexation du système de conception Builder plutôt qu'un import de diapositives)
- `extract-pdf` — extraction brute de texte d'un PDF, réservée au CLI, surtout pour le débogage local

### Exportation

- `export-pptx` — PowerPoint natif et modifiable
- `export-google-slides` — génère le même PPTX plus un lien d'import Google Slides prêt à l'emploi
- `export-html` — un fichier HTML autonome avec navigation au clavier intégrée

### Systèmes de conception

- `create-design-system`, `update-design-system`, `delete-design-system`, `get-design-system`, `list-design-systems`, `set-default-design-system`, `apply-design-system` (lier un système à un deck)
- `get-workspace-defaults`, `set-workspace-defaults` — le deck et le système de conception par défaut à l'échelle de l'espace de travail. Les définir est réservé aux administrateurs
- `analyze-brand-assets`, `import-document`, `import-from-url`, `import-code` — rassembler des signaux de marque bruts (CSS/polices du site web, contenu de documents ou fichiers de code téléversés) pour un système de conception **local**, rédigé par l'agent
- `index-design-system-with-builder`, `sync-design-system-with-builder`, `import-design-project` — le chemin indexé par Builder pour les fichiers Figma, les dépôts de code/GitHub connectés, et `design.md`. `import-design-project` part d'un système de conception existant plutôt que d'une source brute

### Contexte créatif

- `clone-context-slide` — insérer une diapositive épinglée de la bibliothèque dans un deck sans changement, sans régénérer son HTML/CSS
- `clone-creative-context-deck` — recréer une version exacte et gouvernée d'un deck
- `get-deck-reference-context` — extraire le langage visuel d'un deck existant comme bibliothèque de motifs réutilisable
- La récupération et la soumission à la bibliothèque (recherche, récupération d'un élément de contexte, gestion de l'appartenance à la bibliothèque) sont des actions partagées du framework que l'agent appelle de la même façon dans chaque application prenant en charge le contexte créatif. Consultez le skill `creative-context` pour la procédure de récupération et l'échelle de réutilisation.

### Escalade et données mises en scène

- `provider-api-catalog`, `provider-api-docs`, `provider-api-request` — accès brut à l'API Google Drive quand une action d'import/export prédéfinie est trop étroite. Diapositives résout l'authentification à partir du compte Google Docs connecté de l'utilisateur
- `list-staged-datasets`, `query-staged-dataset`, `delete-staged-dataset` — agréger un grand résultat de fournisseur mis en scène sans le récupérer à nouveau

### Navigation et contexte

- `view-screen` — ce que l'utilisateur regarde actuellement : le deck ouvert, la diapositive actuelle, et toute sélection visuelle active
- `navigate` — déplacer l'interface vers un deck, une diapositive, ou une vue

## Le personnaliser

Le modèle Diapositives est entièrement personnalisable. Principaux endroits à consulter pour l'étendre :

#### Actions — `templates/slides/actions/`

Chaque opération appelable par l'agent réside ici sous la forme d'un fichier TypeScript, montée automatiquement sur `POST /_agent-native/actions/:name` et appelable depuis le CLI en tant que `pnpm action <name>`. Ajoutez un nouveau fichier ici pour donner à l'agent une nouvelle capacité.

  code={
    'import { defineAction, fail } from "@agent-native/core/action";\nimport { assertAccess } from "@agent-native/core/sharing";\nimport { eq } from "drizzle-orm";\nimport { z } from "zod";\n\nimport { getDb, schema } from "../server/db/index.js";\nimport { notifyClients } from "../server/handlers/decks.js";\nimport { withDeckLock } from "./patch-deck.js";\n\nexport default defineAction({\n  description:\n    "Surgically edit a slide\'s content using search-replace or full replacement. " +\n    "Syncs live to open editors. Prefer this over full deck rewrites.",\n  schema: z.object({\n    deckId: z.string(),\n    slideId: z.string(),\n    find: z.string().optional(),\n    replace: z.string().optional(),\n    fullContent: z.string().optional(),\n  }),\n  run: async ({ deckId, slideId, find, replace, fullContent }) => {\n    await assertAccess("deck", deckId, "editor");\n    return withDeckLock(deckId, async () => {\n      const db = getDb();\n      const [row] = await db\n        .select()\n        .from(schema.decks)\n        .where(eq(schema.decks.id, deckId));\n      if (!row) {\n        fail(`Deck ${deckId} not found`, { errorCode: "deck_not_found", statusCode: 404 });\n      }\n\n      const deck = JSON.parse(row.data);\n      const slide = deck.slides.find((s: { id: string }) => s.id === slideId);\n      if (!slide) {\n        fail(`Slide ${slideId} not found`, { errorCode: "slide_not_found", statusCode: 404 });\n      }\n\n      if (fullContent) {\n        slide.content = fullContent;\n      } else if (find) {\n        const idx = slide.content.indexOf(find);\n        if (idx === -1) {\n          fail("Text not found", { errorCode: "slide_find_no_match" });\n        }\n        slide.content =\n          slide.content.slice(0, idx) +\n          (replace ?? "") +\n          slide.content.slice(idx + find.length);\n      }\n\n      deck.updatedAt = new Date().toISOString();\n      await db\n        .update(schema.decks)\n        .set({ data: JSON.stringify(deck), updatedAt: deck.updatedAt })\n        .where(eq(schema.decks.id, deckId));\n\n      notifyClients(deckId, { slideId, actor: "agent" });\n      return { ok: true, deckId, slideId };\n    });\n  },\n});'

La plupart des personnalisations de l'interface de l'éditeur se font sous `app/components/editor/` : le canevas de diapositive, la barre d'outils, la barre latérale, le menu à bulles, le menu barre oblique, et le panneau d'historique.

#### Skills — `templates/slides/.agents/skills/`

Skills de l'agent qui expliquent les modèles quand l'agent doit modifier du code :

- `create-deck` — comment créer un nouveau deck, avec des modèles HTML de diapositive exacts pour chaque mise en page
- `slide-editing` — comment modifier des diapositives individuelles
- `deck-management` — comment les decks sont stockés et accessibles
- `design-systems` — la forme des données du système de conception et comment les jetons s'appliquent aux diapositives générées
- `creative-context` — l'échelle de réutilisation, la procédure de récupération, et la soumission à la bibliothèque

#### AGENTS.md

`templates/slides/AGENTS.md` est le court routeur que l'agent lit à chaque conversation. Il pointe vers les skills sous `.agents/skills/` et expose les règles de base, le modèle de persistance, et le contrat d'état de l'application. Mettez à jour le skill concerné chaque fois que vous ajoutez ou modifiez une mise en page de diapositive ou une source de système de conception.
