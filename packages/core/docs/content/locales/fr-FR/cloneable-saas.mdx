# Apps

Vous souhaitez proposer votre propre outil d'analyse basé sur l'IA ? Client de messagerie ? Générateur de formulaires ? Choisissez une app d'exemple et vous obtenez un SaaS fonctionnel en quelques minutes : agent, base de données, authentification et pipeline de déploiement déjà connectés.

La plupart des modèles de démarrage vous donnent un échafaudage vierge et une longue liste TODO. L'agent natif inverse cela. Chaque app d'exemple est un **produit complet de qualité SaaS** — déjà exécutable dès le premier jour, déjà livrable et entièrement à vous pour personnaliser, marquer et déployer. Considérez-les comme des SaaS clonables, et non comme des kits de démarrage : vous créez un produit fini, et non un passe-partout.

Utilisez [Chat](/docs/template-chat) lorsque vous souhaitez une application de base avec laquelle les utilisateurs peuvent parler immédiatement et que vous pouvez étendre avec des actions, des résultats natifs et des écrans. Utilisez [Automation-First Apps](/docs/pure-agent-apps) seulement lorsque le workflow n'a pas encore besoin d'UI navigateur.

Consultez le catalogue complet sous [Apps](/apps) ou passez directement à l'un d'entre eux. Par exemple, [Dispatch](/docs/template-dispatch) est un excellent point de départ si vous souhaitez une application de style espace de travail.

## Modèles communautaires {#community-templates}

Les modèles nommés dans le sélecteur CLI sont **officiels** : Agent Native les
maintient, les teste, les documente et les publie avec le framework. Un
**modèle communautaire** est maintenu et versionné par le propriétaire de son
dépôt. Il peut utiliser la même surface du framework, mais sa présence dans la
liste communautaire ne constitue ni une recommandation ni une promesse de
support de la part d'Agent Native.

Exécutez `create`, choisissez **Modèle communautaire**, puis collez l'URL simple
d'un dépôt GitHub public :

```bash
https://github.com/owner/repo
```

Si la racine du dépôt contient une seule app Agent Native, la CLI l'installe
directement sans autre sélecteur. Si le dépôt est un espace de travail Agent
Native, la CLI découvre les enfants directs valides de `apps/*`, exclut
`dispatch` et demande quelle app installer.

Un marqueur `agent-native.workspaceCore` non vide fait du dépôt un espace de
travail même si le package racine dépend aussi de `@agent-native/core` ; un
marqueur mal formé est rejeté.

Transmettez la même URL simple à `--template` pour les scripts, ou utilisez la
forme courte `community:`. Épinglez une branche, un tag ou un commit après `#`
pour obtenir un point de départ reproductible. Sans référence, la CLI essaie
`main`, puis `master` :

```bash
npx @agent-native/core@latest create my-app --template community:owner/repo#v1.2.0
npx @agent-native/core@latest create my-app --template https://github.com/owner/repo#v1.2.0
```

Pour choisir l'app source d'un dépôt d'espace de travail sans interaction,
utilisez `?app=<app-name>`. Le sélecteur précède le `#ref` facultatif. Conservez
la valeur entière entre guillemets, car les shells comme zsh interprètent `?`
comme un glob :

```bash
npx @agent-native/core@latest create my-app --template 'community:owner/repo?app=analytics#v1.2.0'
npx @agent-native/core@latest create my-app --template 'https://github.com/owner/repo?app=analytics#v1.2.0'
```

En dehors d'un espace de travail, `create` transforme l'app source sélectionnée
en app autonome. Pour l'ajouter à un espace de travail existant, transmettez
explicitement le dépôt communautaire, car le sélecteur `add-app` ne présente que
les modèles officiels. Omettez `?app` pour choisir interactivement dans l'espace
de travail source, ou incluez-le pour une installation scriptable :

```bash
npx @agent-native/core@latest add-app my-app --template community:owner/repo#v1.2.0
npx @agent-native/core@latest add-app my-app --template 'community:owner/repo?app=analytics#v1.2.0'
```

Seuls les dépôts GitHub publics sont acceptés. Les dépôts privés, les
hébergeurs autres que GitHub, les URL d'arborescence ou de sous-répertoire
GitHub et les chemins d'app imbriqués ne sont pas pris en charge. Une app à la
racine doit avoir un `package.json` lisible qui répertorie
`@agent-native/core` dans `dependencies`, `devDependencies` ou
`peerDependencies`. Dans un dépôt d'espace de travail, chaque app source
sélectionnable doit respecter la même exigence directement sous
`apps/<app-name>/` ; `dispatch` n'est jamais sélectionnable.

Les apps d'un espace de travail communautaire doivent être des unités
portables, et non des tranches arbitraires d'un monorepo :

- les références de dépendance `catalog:` par défaut sont résolues depuis le
  `pnpm-workspace.yaml` à la racine du dépôt source ; les références de
  catalogue nommées ne sont pas prises en charge ;
- les références `workspace:*` à `@agent-native/core`,
  `@agent-native/dispatch` et `@agent-native/toolkit` sont réécrites vers des
  versions publiées. Les autres packages frères de l'espace de travail ne sont
  pas copiés ; publiez-les et utilisez une version concrète ;
- la dépendance au package `workspaceCore` source est supprimée. Les plugins
  canoniques hérités d'authentification et d'agent chat de l'espace de travail
  sont détachés pour une installation autonome ou reliés à l'espace de travail
  de destination. Toute autre importation du package `workspaceCore` source
  échoue avec un message clair ; déplacez ce code dans l'app ou publiez-le comme
  dépendance concrète.

Conservez le reste de chaque app complète avec son `package.json` :
`agent-native.json` lorsqu'il est utilisé, sources, actions, instructions
d'agent et configuration de la base de données. Un dépôt prêt pour le catalogue
doit également inclure :

- une licence et un lien vers le mainteneur ou le support ;
- un README avec les étapes de configuration, les variables d'environnement
  requises et la commande CLI exacte ;
- un `.env.example` contenant uniquement des valeurs fictives, sans secrets,
  données client, bases de données d'exécution ni sorties de build générées ;
- une installation et une commande de développement fonctionnelles, un
  typecheck et des tests adaptés au modèle.

Le programme d'installation enregistre les valeurs `source` et `ref` résolues
dans `agent-native.communityTemplate` au sein du `package.json` de l'app
installée. Les apps sélectionnées dans un dépôt d'espace de travail enregistrent
aussi l'app source dans `agent-native.communityTemplate.app`. `agent-native
template sync` reste réservé aux modèles officiels ; pour mettre à jour un
modèle communautaire, examinez une référence upstream plus récente et fusionnez
vous-même ses modifications.

Consultez [Creating Templates](/docs/creating-templates) pour la liste complète
des exigences relatives à l'app, aux actions, à l'état, à la sécurité et à la
publication.

> **Examinez le code communautaire avant d'installer ses dépendances ou de
> l'exécuter.** Les modèles communautaires sont téléchargés depuis des dépôts
> tiers ; Agent Native ne les isole, ne les audite et ne les maintient pas.
> La CLI télécharge uniquement les sources ; elle n'installe aucune dépendance
> et n'exécute aucun script du modèle. Vérifiez les sources, la licence, les
> dépendances et les scripts d'installation des packages, et préférez une
> référence fiable épinglée.

Une démo hébergée est facultative. Si vous en fournissez une, utilisez un lien
public permettant de l'essayer et documentez les éventuelles exigences de
connexion, de données d'exemple ou de fournisseur. Le dépôt reste la source de
vérité pour l'installation, et son propriétaire reste responsable du modèle et
de la démo.

Vous souhaitez figurer dans la liste ? [Proposez un modèle communautaire](https://github.com/BuilderIO/agent-native/issues/new?template=community-template.yml)
avec l'URL du dépôt, une description en une phrase, les coordonnées du
mainteneur et la licence, la commande CLI testée et, si disponible, l'URL d'une
démo hébergée.

## Ce que vous obtenez hors de la boîte {#what-you-get}

Chaque app d'exemple est livrée avec les éléments dont la création prend normalement des mois :

- **Un agent fonctionnel** — déjà connecté à l'application, déjà capable d'utiliser actions sur vos données, déjà conscient du contexte de ce que vous regardez. Voir [Messaging the agent](/docs/messaging) pour savoir comment cela fonctionne.
- **Auth** : connexion, sessions, organisations, isolation multi-locataires. Déjà fait.
- **Une base de données** : chaque app d'exemple a son schéma, ses requêtes et ses migrations prêts à l'emploi. Apportez votre propre base de données SQL (Postgres, SQLite, Turso, D1) — le framework s'adapte.
- **Un UI** en temps réel : l'écran reste synchronisé avec ce que fait l'agent. Cliquez sur « rédiger un e-mail » dans le chat et regardez le brouillon apparaître immédiatement dans votre boîte de réception.
- **Prêt pour le déploiement** : envoyez-le vers Netlify, Vercel, Cloudflare, AWS ou n'importe quel autre endroit exécutant Node. Pas de dépendance envers un fournisseur.
- **Crochets de branding** : le nom, les couleurs, le logo et la copie sont tous faciles à modifier.

Ce n'est pas une affirmation théorique. L'auteur du framework exécute sa boîte de réception réelle dans l'app Mail, son calendrier réel dans l'app Calendar et ses analyses réelles dans l'app Analytics. Ces apps sont des logiciels du quotidien.

1. **Choisissez une app d'exemple.** Utilisez le sélecteur CLI ou parcourez la documentation et choisissez-en une pour commencer.
2. **Marquez-la.** Modifiez le nom, les couleurs, le logo et la copie. La plupart des apps d'exemple exposent cela dans un seul fichier de configuration.
3. **Personnalisez-le.** Modifiez le code source dans votre dépôt et votre workflow de développement. Un agent peut aider lorsque son frame reçoit intentionnellement des outils de workspace et d’écriture ; sinon, l’agent intégré exploite l’app via ses actions, ses données et ses intégrations configurées.
4. **Expédiez-le.** Exécutez la commande de déploiement. Vous disposez désormais de votre propre SaaS de production sur votre propre domaine.

Les étapes 2 à 4 prennent généralement des jours et non des mois. L’étape 3 reste ouverte parce que l’app vous appartient et peut évoluer, tandis que l’agent intégré continue d’exploiter le produit déployé et peut aider aux changements de source lorsque l’accès au code est explicitement activé.

## Pourquoi c'est pratique {#why}

Un modèle traditionnel de fork-the-codebase s'effondre à grande échelle : chaque utilisateur gérant sa propre boîte de réception ressemble à un cauchemar de maintenance. Deux décisions-cadres permettent que cela fonctionne :

1. **L’app respecte le contrat du framework.** Votre source possède le comportement métier, tandis que Core maintient la cohérence des actions, de SQL, de l’état et de la synchronisation à mesure que l’app évolue.
2. **Personnalisation par utilisateur sans code par utilisateur.** Skills, la mémoire, les instructions, les serveurs MCP connectés et les sous-agents résident tous dans SQL. Chaque utilisateur dispose de sa propre couche de personnalisation ; la base de code partagée les héberge tous en même temps.

Le résultat : une flexibilité au niveau du code Claude pour chaque utilisateur, avec des coûts de déploiement SaaS normaux.

## Vous ne voulez pas personnaliser ? {#hosted}

Vous n'êtes pas obligé. Chaque app d'exemple est également disponible sous forme d'application hébergée sur `agent-native.com` — `mail.agent-native.com`, `calendar.agent-native.com`, etc. Utilisez la version hébergée gratuitement ou payante ; créez votre propre app à partir d'un modèle lorsque vous souhaitez modifier quelque chose que la version hébergée n'expose pas.

### Pour les développeurs {#dev-details}

Si vous créez un échafaudage maintenant, la commande CLI est :

```bash
npx @agent-native/core@latest create my-platform
```

La CLI demande d’abord **Comment souhaitez-vous commencer ?** Choisissez **Chat** pour un espace de travail minimal avec Chat et Dispatch, ou **First-party template(s)** pour ouvrir le sélecteur multiple. Community et Headless sont les accès pour une app autonome. Les apps de l’espace de travail partagent l’authentification, la marque, la configuration de l’agent et la base de données ; chaque app est intégrée dans `apps/<name>/` avec tous les fichiers nécessaires. Pour une automation sans UI navigateur au lieu d’une UI d’app, utilisez `npx @agent-native/core@latest create my-agent --headless`.

Remplissez `.env` (principalement `ANTHROPIC_API_KEY` et `DATABASE_URL`), `pnpm install`, `pnpm dev`, et cela fonctionne. Pas de "TODO : implémenter la connexion", pas de routes d'espace réservé.

Cibles de déploiement : tout hôte compatible Nitro (Node, Cloudflare, Netlify, Vercel, Deno, Lambda, Bun) et toute base de données SQL compatible Drizzle (SQLite, Postgres, Turso, D1, Supabase, Neon). Pour les espaces de travail, `npx @agent-native/core@latest deploy` crée chaque application en même temps et les livre derrière une seule origine. Voir [Deployment](/docs/deployment).

Pour créer et publier votre propre modèle d'app, consultez [Creating Templates](/docs/creating-templates).
