# Autres surfaces

La surface des hooks d’UI est couverte dans [Données et synchronisation](/docs/client-data) : `useActionQuery()`, `useActionMutation()`, et `callAction()`. Cette page couvre tout le reste qui peut appeler, ou être piloté par, une action.

## Afficher une UI de chat native {#native-chat-ui}

Les actions peuvent renvoyer des données de widget structurées que le chat intégré à l’application affiche
nativement. C’est le chemin de chat de premier ordre pour les tableaux, graphiques,
résumés de configuration, et cartes d’insight réutilisables. Utilisez [UI générative](/docs/generative-ui) quand
l’agent doit générer des contrôles interactifs arbitraires à l’intérieur du chat intégré, et utilisez
[Applications MCP](/docs/mcp-apps) pour une UI en ligne dans les hôtes MCP externes.

```ts
import { defineAction } from "@agent-native/core/action";
import { ACTION_CHAT_UI_DATA_CHART_RENDERER } from "@agent-native/core/action-ui";
import {
  createDataChartWidgetResult,
  dataChartWidgetResultSchema,
} from "@agent-native/core/data-widgets";

export default defineAction({
  description: "Summarize response trends.",
  readOnly: true,
  outputSchema: dataChartWidgetResultSchema,
  chatUI: { renderer: ACTION_CHAT_UI_DATA_CHART_RENDERER },
  run: async () =>
    createDataChartWidgetResult({
      title: "Response trends",
      chartSeries: {
        type: "line",
        xKey: "day",
        series: [{ key: "responses", label: "Responses" }],
        data: [
          { day: "Mon", responses: 12 },
          { day: "Tue", responses: 18 },
        ],
      },
    }),
});
```

Les discriminants intégrés sont `"data-table"`, `"data-chart"`, et
`"data-insights"`, avec des constructeurs et schémas sûrs côté serveur dans
`@agent-native/core/data-widgets`. Utilisez `data-chart` pour des réponses uniquement graphiques,
`data-table` pour des résultats SQL/liste, et `data-insights` seulement quand une carte
combinée résumé/graphique/tableau est la bonne sortie. Voir
[Chat natif UI](/docs/native-chat-ui) pour le contrat complet de résultat, ou
[Runtimes d’agent maison](/docs/native-chat-ui#byo-agent-runtimes) si vous
câblez un runtime d’agent personnalisé au lieu de la boucle de chat intégrée. Voir
[Surfaces de l’agent](/docs/agent-surfaces) pour comment la même action peut rester
adaptée aux automatisations, s’afficher dans le chat, ou évoluer vers un écran complet.

## L’appeler depuis la CLI {#cli}

Chaque action est exécutable via `pnpm action` :

```bash
pnpm action reply-to-email '{"emailId":"thread-123","body":"Thanks!"}'
```

L’entrée JSON est la forme préférée pour les agents et les objets complexes. Les flags fonctionnent
de la même manière pour des exécutions manuelles simples et des scripts existants :

```bash
pnpm action reply-to-email --emailId thread-123 --body "Thanks!"
```

Pour les appels `defineAction()`, la CLI évalue `needsApproval` sur les arguments préparés et analysés, avec les valeurs par défaut du schéma et l’appelant `cli`. Si stdin et stdout sont des TTY, elle affiche le nom de l’action et les arguments, puis demande `y/N`. Seuls `y` ou `yes` exécutent l’action.

Sans ces deux TTY, la CLI demande à l’agent de solliciter l’accord de la personne. Après son accord pour cet appel précis, relancez les arguments exacts de la commande `pnpm action` d’origine en ajoutant `--approved` :

```bash
pnpm action reply-to-email --emailId thread-123 --body "Thanks!" --approved
```

`--approved` est une métadonnée réservée à la CLI, retirée avant l’analyse de l’entrée. Il ne prend pas de valeur : si autre chose qu’un drapeau ou un objet JSON le suit, l’appel est refusé, et une entrée nommée `approved` s’écrit `--approved=<value>`. Ce drapeau est sans effet indésirable sur les actions sans approbation obligatoire. La CLI ne peut pas vérifier qui l’a ajouté : un agent qui l’ajoute sans demander contourne la confirmation. Le drapeau rend l’approbation visible dans la commande que la personne approuve et dans le journal d’audit, qui la signale comme non vérifiée. Sous Windows sans `SHELL` POSIX, le refus indique la commande pour PowerShell et, si les guillemets diffèrent, pour cmd.exe. Sous Windows, pnpm transmet les arguments de l’action à cmd.exe depuis n’importe quel shell, et cmd.exe développe `%NAME%` même entre guillemets. Si un argument contient une telle variable, le refus ne propose pas de relancer avec `--approved` : la personne exécute la commande dans un terminal et vérifie les valeurs à la confirmation. Si les arguments contiennent un guillemet et l’un de `&`, `|`, `<`, `>` ou `^`, pnpm ne peut pas les transmettre intacts à cmd.exe : le refus n’affiche alors aucune commande, et la personne approuve l’appel dans l’app. Windows PowerShell 5.1 supprime chaque `"` à l’intérieur d’un argument : sous Windows sans `SHELL` POSIX, un argument contenant un guillemet double passe donc lui aussi par la confirmation plutôt que par une relance avec `--approved`.

Le pont de développement local envoie les métadonnées d’approbation hors de `input` dans le corps JSON :

```ts
{ name, input, approved: true, approvalSource: "flag" }
```

Pour un appel protégé sans approbation, le pont renvoie HTTP `409` :

```ts
{
  ok: false,
  errorCode: "approval_required",
  error: 'Action "<name>" requires human approval. Ask the person, then rerun with --approved.',
  arguments: preparedArgs,
  argumentsHash: prepared.argumentsHash,
}
```

Après la confirmation en TTY, la CLI réessaie avec le `argumentsHash` de la réponse demandant l’approbation :

```ts
{
  name,
  input,
  approved: true,
  approvalSource: "prompt",
  approvalArgumentsHash: challenge.argumentsHash,
}
```

Le pont exécute une seule fois l’appel que la personne a examiné : une valeur par défaut qui change à chaque appel, comme un horodatage, garde la valeur affichée. Une confirmation sans appel conservé à exécuter (il a déjà été exécuté, 10 minutes sont passées ou le serveur de développement a redémarré) reçoit HTTP `409` avec `errorCode: "approval_expired"`. Relancez la commande pour l’examiner.

`arguments` contient les arguments préparés. Ce contrat du pont de développement local ne modifie pas les [règles d’approbation de l’API HTTP publique des actions](/docs/actions-access-control#needs-approval). Un appel CLI protégé et approuvé inscrit `approval: "cli-prompt"` ou `approval: "cli-flag"` sur la ligne d’audit propre à l’action, avec l’appelant `cli`. Le journal d’audit affiche les deux comme non vérifiés, car seule la CLI voit l’invite.

## L’appeler depuis un autre agent (A2A) {#a2a}

Si votre application est un pair [A2A](/docs/a2a-protocol), les autres applications natives d’agent découvrent vos actions automatiquement et peuvent les appeler par leur nom. Les déploiements de même origine se passent de la signature JWT. Les déploiements d’origines différentes utilisent à la place un `A2A_SECRET` partagé.

## L’exposer via MCP {#mcp}

Avec MCP activé, vos actions apparaissent dans le serveur MCP du framework, sur `/mcp`. Chaque appelant obtient par défaut un catalogue compact (les intégrés orientés application plus les actions d’application déclarées par le template), et `tool-search` est toujours présent pour que tout autre outil reste atteignable à la demande. La surface d’actions complète n’est servie que sur opt-in explicite (jeton `--full-catalog` ou `AGENT_NATIVE_MCP_FULL_CATALOG=1`), et [`publicAgent.expose`](/docs/actions-access-control#public-agent) fait entrer un outil sûr de lecture/ingestion dans la surface publique. Voir [Protocole MCP](/docs/mcp-protocol) pour les niveaux de catalogue, l’authentification, et les détails de la ressource `mcpApp`.

Pour les hôtes MCP capables d’UI, une action peut déclarer une ressource optionnelle Applications MCP via le champ `mcpApp` (plus un `link` correspondant) afin que les hôtes capables affichent le résultat en ligne. Quand `link` et `mcpApp` doivent pointer vers la même route, `embedRoute()` construit les deux à partir d’un seul constructeur de chemin pur :

```ts
import { embedRoute } from "@agent-native/core";

export default defineAction({
  description: "Create an email draft for review.",
  schema: z.object({ body: z.string() }),
  run: async ({ body }) => ({ body }),
  ...embedRoute({
    title: "Review draft",
    openLabel: "Open in Mail",
    path: ({ result }) => ({
      label: "Open draft in Mail",
      url: "/_agent-native/open?app=mail&view=inbox",
    }),
  }),
});
```

Gardez `link` comme repli pour la CLI et les hôtes MCP sans UI. C’est aussi la cible de lancement de l’intégration. Le pont d’intégration (la session de démarrage d’intégration signée, la transplantation vs. le rendu en frame contrôlée, le pont hôte `ui/*`, le CSP, et l’ajustement de hauteur) est possédé par [Agents externes](/docs/external-agents#mcp-app-bridge).

Il n'existe aucune vérification automatique qu'un modèle possède `view-screen`, `navigate`, ou un ensemble create/read/update/list pour sa ressource principale ; le scaffold fournit `view-screen` et `navigate`, et `pnpm guard:external-result-contract` rejette tout langage « attendre l'utilisateur » dans le `description` ou le `nextRequiredAction` d'une action exposée en externe, et exige un lien profond sur toute nouvelle action `create-*` exposée en externe. Sa présence relève de la revue.

## Actions standard {#standard-actions}

Chaque template devrait inclure ces deux-là pour la [conscience du contexte](/docs/context-awareness).

### view-screen {#view-screen}

Lit l’état de navigation actuel, récupère les données contextuelles, et renvoie un instantané de ce que l’utilisateur voit. L’agent appelle ceci quand il a besoin d’un regard neuf sur l’écran.

```ts
// actions/view-screen.ts
import { defineAction } from "@agent-native/core/action";
import { readAppState } from "@agent-native/core/application-state";
import { z } from "zod";

export default defineAction({
  description: "Read the current screen state for context.",
  schema: z.object({}),
  http: { method: "GET" },
  run: async () => {
    const navigation = await readAppState("navigation");
    const screen: Record<string, unknown> = { navigation };

    if (navigation?.view === "inbox") {
      screen.emailList = await listEmailsForLabel(navigation.label);
    }

    return screen;
  },
});
```

### navigate {#navigate}

Écrit une commande de navigation ponctuelle dans l’état de l’application. L’UI la lit, navigue, et supprime l’entrée.

```ts
// actions/navigate.ts
import { defineAction } from "@agent-native/core/action";
import { writeAppState } from "@agent-native/core/application-state";
import { z } from "zod";

export default defineAction({
  description: "Navigate the user to a view.",
  schema: z.object({
    view: z.string(),
    threadId: z.string().optional(),
  }),
  run: async (args) => {
    await writeAppState("navigate", args);
    return { ok: true };
  },
});
```
