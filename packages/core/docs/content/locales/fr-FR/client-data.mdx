# Données et synchronisation

Le principal moyen de lire et d'écrire des données d'application depuis le client est d'utiliser les hooks d'[action](/docs/actions-overview). En intégrant les requêtes dans des actions, votre client et votre agent peuvent tous deux interagir avec votre application de la même manière.

Dans l'exemple ci-dessous, un ticket est assigné à l'utilisateur actuel manuellement via une liste déroulante, puis via l'agent de chat. L'UI et l'agent accèdent tous deux à la même action.

### Hooks d'action {#action-hooks}

Il y a deux hooks d'action que vous êtes le plus susceptible d'utiliser : `useActionQuery()` et `useActionMutation()`. Ces deux hooks donnent accès aux actions de votre application.

#### useActionQuery {#use-action-query}

Ce hook est destiné à être utilisé pour les actions en lecture seule. C'est un wrapper léger autour de la fonction [useQuery()](https://tanstack.com/query/latest/docs/framework/react/reference/useQuery).

Dans l'exemple ci-dessous, l'action `list-tickets` est appelée. C'est similaire à effectuer une requête GET pour tous les tickets.

```ts
import { useActionQuery } from "@agent-native/core/client/hooks";

const { data, isLoading } = useActionQuery("list-tickets", {});
```

L'exemple suivant montre une requête pour récupérer un seul ticket, via l'action `get-ticket`. Un `ticketId` est fourni pour restreindre la requête à un ticket spécifique. L'option supplémentaire `enabled` est fournie pour garantir que la requête ne s'exécute pas automatiquement, et ne s'exécute que lorsqu'un `ticketId` est présent.

```ts
import { useActionQuery } from "@agent-native/core/client/hooks";

const { data, isLoading } = useActionQuery(
  "get-ticket",
  { ticketId: ticketId ?? "" },
  { enabled: Boolean(ticketId) },
);
```

Ce hook est destiné à être utilisé pour les actions qui modifient des données, comme la création, la mise à jour ou l'envoi de quelque chose. C'est un wrapper léger autour de la fonction [useMutation()](https://tanstack.com/query/latest/docs/framework/react/reference/useMutation).

Contrairement à `useActionQuery()`, l'entrée de l'action n'est pas transmise au hook lui-même. Elle est transmise à `mutate()` ou `mutateAsync()` lorsque vous êtes prêt à exécuter la mutation.

Dans l'exemple ci-dessous, l'action `send-ticket-reply` est appelée pour publier une réponse à un ticket. Appelez `mutate()` depuis un gestionnaire d'événement, comme l'`onClick` d'un bouton.

```ts
import { useActionMutation } from "@agent-native/core/client/hooks";

const { mutate, isPending } = useActionMutation("send-ticket-reply");

mutate({ ticketId, body: draft });
```

L'exemple suivant montre la même mutation avec une option `onSuccess`. L'invalidation du cache se produit automatiquement après chaque mutation, donc `onSuccess` n'est nécessaire que pour des effets de bord locaux, comme vider le composeur de réponse une fois la réponse envoyée.

```ts
import { useActionMutation } from "@agent-native/core/client/hooks";

const { mutate, isPending } = useActionMutation("send-ticket-reply", {
  onSuccess: () => setDraft(""),
});

mutate({ ticketId, body: draft });
```

### Invalidation par ressource {#resource-scoped-invalidation}

Les deux hooks acceptent un tableau facultatif `resources`. Une requête indique les ressources qu’elle lit et une mutation celles qu’elle modifie. Utilisez `type` pour tout un type de ressource ou `type:id` pour un ID précis. Lors de la comparaison des mutations locales, le premier deux-points d’une étiquette `type:id` sépare le type de l’ID. Le type ne doit pas contenir de deux-points, mais l’ID peut en contenir. Les événements de synchronisation transmettent le type et l’ID séparément.

```ts
import {
  useActionMutation,
  useActionQuery,
} from "@agent-native/core/client/hooks";

const tickets = useActionQuery("list-tickets", {}, { resources: ["ticket"] });
const ticket = useActionQuery(
  "get-ticket",
  { ticketId },
  { resources: [`ticket:${ticketId}`] },
);
const reply = useActionMutation("send-ticket-reply", {
  resources: [`ticket:${ticketId}`],
});
```

Pour les types sans deux-points et les étiquettes dont l’ID d’enregistrement n’est pas vide, la correspondance est symétrique entre les mutations locales et les événements de synchronisation. Pour une modification locale de tout un type, utilisez `type`, pas `type:`. Lors de la comparaison des mutations locales, `design:layer` désigne le type `design` et l’ID `layer`. Un événement de synchronisation dont le `resourceType` est `design:layer` a un type distinct de `design` et ne correspond pas à l’étiquette de requête `design`. Une étiquette `ticket` correspond à `ticket` et à toute étiquette `ticket:id`. Une étiquette `ticket:123` correspond à `ticket` et à `ticket:123`, mais pas à `ticket:456`. Les requêtes sans étiquette sont invalidées par précaution. Une mutation sans étiquette invalide toutes les requêtes d’action.

Pour un événement de synchronisation d’action, `resourceType` et `resourceId` identifient séparément la ressource modifiée. Si `resourceId` est absent ou vide, toutes les requêtes correspondant à ce type sont invalidées. Si un événement d’action non supprimé n’a pas de `resourceType`, le filtrage par ressource est désactivé pour le lot et toutes les requêtes d’action sont concernées. Le prédicat facultatif peut toujours filtrer l’invalidation.

Pour un lot contenant des événements d’action et uniquement des événements d’action ou app-state, le filtre de ressources correspond à toute ressource modifiée dans les événements d’action non supprimés. Avec `actionInvalidatePredicate`, une requête doit satisfaire à la fois le filtre et le prédicat. Le prédicat reçoit tout le lot pertinent hors événements awareness, y compris les événements d’action supprimés. Si le lot contient aussi une autre source qui modifie les données, le filtrage par ressource est désactivé, mais le prédicat reste appliqué. Dans un lot avec un autre événement qui modifie les données mais sans événement d’action non supprimé, le prédicat filtre aussi l’invalidation générale des actions.

`changeResource` d’une action désigne une ressource pour la livraison de l’événement et le contrôle d’accès. Ce n’est pas nécessairement la liste exhaustive des écritures de l’action. Les étiquettes de requête propres à un enregistrement ne sont sûres que si le marqueur livré de chaque action pertinente représente tous les enregistrements dont dépend la requête. Pour les écritures groupées ou les dépendances entre enregistrements du type du marqueur, une étiquette de requête couvrant ce type peut correspondre à l’événement livré. Pour les dépendances entre types, incluez le type de chaque événement livré dans les étiquettes de la requête ou utilisez une requête sans étiquette. Plusieurs événements livrés indépendamment peuvent couvrir les enregistrements concernés, à condition que chaque personne concernée reçoive un événement auquel elle est autorisée à accéder. Élargir les étiquettes côté client ne modifie la correspondance qu’après la livraison. Cela ne rend pas l’événement visible à une personne sans accès à sa ressource de livraison. Assurez-vous que les personnes concernées reçoivent un événement auquel elles ont accès.

Cette fonction est destinée aux appels d'action impératifs ponctuels hors d'un flux de rendu React, comme un simple gestionnaire d'événement, un script, ou tout autre chemin de code non React. Elle renvoie directement une promesse plutôt qu'un résultat de hook.

Dans l'exemple ci-dessous, l'action `update-ticket` est appelée depuis un gestionnaire de raccourci clavier hors du flux de rendu de React, pour assigner le ticket à un représentant.

```ts
import { callAction } from "@agent-native/core/client/hooks";

await callAction("update-ticket", {
  ticketId,
  assignedToEmail: "jordan@example.com",
});
```

L'exemple suivant montre le même appel avec une option `timeoutMs`, utile pour les actions qui prennent légitimement plus de temps que le délai d'expiration par défaut de 60 secondes.

```ts
import { callAction } from "@agent-native/core/client/hooks";

await callAction(
  "update-ticket",
  { ticketId, assignedToEmail: "jordan@example.com" },
  { timeoutMs: 120_000 },
);
```

Chaque requête `useActionQuery()`, `useActionMutation()`, et `callAction()` est limitée par un délai d'expiration de 60 secondes, et les délais d'expiration apparaissent comme des erreurs plutôt que de relancer silencieusement. `useActionQuery()` annule aussi automatiquement les requêtes remplacées, en utilisant le signal d'abandon de React Query.

### Échecs d'écriture {#write-failures}

Lorsqu'une sauvegarde lancée par l'utilisateur échoue, l'application affiche une notification partagée (toast) au lieu de rien. `useActionMutation()` le fait automatiquement. Un `mutate()` en échec affiche la notification, sauf si un `onError` gère l'échec, que ce soit dans les options du hook ou dans l'appel à `mutate()`. Un `mutateAsync()` en échec ne l'affiche que si le rejet reste non géré, par exemple un `await` sans `try/catch` au-dessus. Un `catch` qui lève une nouvelle `Error` à la place de l'erreur d'origine n'est pas signalé.

L'option `errorNotification` modifie ce comportement par défaut :

| Valeur                | Comportement                                                                                                                                                                  |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `"auto"` (par défaut) | Affiche la notification uniquement si rien d'autre ne gère l'échec.                                                                                                           |
| `"shared"`            | Affiche la notification à chaque échec, même à côté de votre propre `onError`. À utiliser lorsque le gestionnaire se contente d'annuler ou de journaliser.                    |
| `"caller"`            | N'affiche jamais la notification. À utiliser pour les sauvegardes en arrière-plan, un échec que vous ignorez volontairement, ou un emplacement qui affiche lui-même l'erreur. |

`errorLabel` remplace le titre de la notification par votre propre texte, déjà traduit. Dans l'exemple ci-dessous, une assignation échouée affiche ce titre au lieu du titre générique.

```tsx
import { useActionMutation } from "@agent-native/core/client/hooks";

const assign = useActionMutation("update-ticket", {
  errorLabel: t("tickets.assignFailed"),
});

assign.mutate({ ticketId, assignedToEmail: "jordan@example.com" });
```

Une sauvegarde automatique qui se relance au changement suivant ne doit pas interrompre l'utilisateur ; elle est donc désactivée.

```tsx
import { useActionMutation } from "@agent-native/core/client/hooks";

const saveDraft = useActionMutation("save-ticket-draft", {
  errorNotification: "caller",
});
```

Une écriture qui n'est pas un `useActionMutation()`, comme un `fetch` pour un envoi de fichier ou un `catch` qui avale une erreur, signale son échec avec `reportWriteFailure()`. L'erreur d'un `fetch` brut ne contient pas de statut ; la notification affiche donc votre libellé ou le titre générique. Un `useMutation()` brut active la notification en passant `meta: surfaceMutationError(label)`, qui accepte le même libellé facultatif.

```ts
import { reportWriteFailure } from "@agent-native/core/client/write-failure";

try {
  const response = await fetch(uploadUrl, { method: "PUT", body: file });
  if (!response.ok) throw new Error(`Upload failed with ${response.status}`);
} catch (error) {
  reportWriteFailure(error, { label: t("tickets.uploadFailed") });
}
```

Le texte de la notification dépend de l'échec. Une requête annulée n'affiche rien. Hors ligne, un délai d'expiration, un `401` et un `403` affichent chacun un court message traduit sous le titre. Un `5xx` n'affiche que le titre, car le serveur masque son propre texte d'erreur. Lorsqu'une action refuse avec une erreur `4xx` typée levée par `fail()`, la notification affiche le message écrit par l'action ; voir [Faire échouer une action](/docs/actions-defining#failing). Un `401` ou un `403` n'affiche jamais le texte du serveur.

`AppProviders` monte toujours le composant qui écoute ces échecs, `WriteFailureToaster`. Celui-ci affiche sa notification via le `Toaster` de l'application, donc une application qui passe `toaster={null}` doit rendre le sien. Une application qui n'utilise pas `AppProviders` rend `<WriteFailureToaster />` depuis `@agent-native/toolkit/app/shared` à l'intérieur de son `QueryClientProvider` et à côté de son `Toaster`. Sans lui, aucune notification n'est affichée.

`useDbSync()` traite les fins d'outils du flux de chat local et actualise les données à la fin de l'exécution. Les modifications d'un agent seul restent ainsi à jour sans requête en arrière-plan. La synchronisation des changements venant d'autres onglets, personnes, webhooks ou tâches reste désactivée, sauf si cette page l'active avec une courte raison. Chaque onglet partage un transport, le met en pause lorsqu'il est masqué et espace les interrogations à vide à 1, 2 puis 5 minutes.

```ts
import { useDbSync } from "@agent-native/core/client/hooks";
import { useQueryClient } from "@tanstack/react-query";

function App() {
  const queryClient = useQueryClient();

  useDbSync({
    queryClient,
    realtime: { reason: "teammates can edit this shared record" },
    pollUrl: "/_agent-native/poll",
    onEvent: (data) => console.log("Data changed:", data),
  });

  return <div>...</div>;
}
```

N'activez le temps réel que si les données peuvent changer sans action de l'utilisateur actuel et si celui-ci doit voir le changement avant d'actualiser.
