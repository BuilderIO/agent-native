# Téléchargements de fichiers

Le framework fournit une abstraction de téléchargement de fichiers qui achemine les téléchargements via un fournisseur configurable. Les modèles appellent `uploadFile()` et récupèrent un URL. Le backend de stockage est interchangeable sans modifier le code de l'application.

## Comment ça marche {#how-it-works}

Les requêtes de téléchargement sont envoyées à `POST /_agent-native/file-upload`, qui les transmet au fournisseur actif. Vous pouvez vérifier quel fournisseur est configuré à l'adresse `GET /_agent-native/file-upload/status`.

L'ordre de résolution du fournisseur est le suivant :

1. **Fournisseurs enregistrés par l'utilisateur** : fournisseurs personnalisés enregistrés via `registerFileUploadProvider()`.
2. **Fournisseur Builder.io** : intégré, il s'active automatiquement lorsque Builder.io est connecté.
3. **Aucun fournisseur** : le téléchargement est refusé et le chat affiche un appel à l'action pour configurer le stockage. Les données binaires ne sont jamais persistées dans SQL.

Parmi les fournisseurs enregistrés par l'utilisateur, le premier à s'être enregistré et à se signaler comme configuré l'emporte. `registerFileUploadProvider()` est idempotent par `id`. Enregistrer un fournisseur sous un id déjà utilisé remplace le fournisseur existant.

L'interface décide d'afficher ou non une invite de configuration du stockage en utilisant uniquement la vérification synchrone `isConfigured()`, avant qu'un téléchargement ne soit tenté. Le téléchargement lui-même vérifie à la fois `isConfigured()` et `isConfiguredForRequest()`. Un fournisseur qui ne se signale comme configuré que via `isConfiguredForRequest()` reste invisible pour l'invite de configuration, même si les téléchargements effectués via ce fournisseur réussiraient.

## Stockage requis pour des téléchargements durables {#storage-required}

Lorsqu'aucun fournisseur n'est configuré, `uploadFile()` renvoie `null` et la route multipart renvoie `503`. Les pièces jointes du chat restent disponibles uniquement pour la requête en cours, l'agent reçoit une indication pour configurer le stockage, et la transcription enregistre un marqueur de configuration au lieu de la charge utile binaire. Ce comportement d'échec contrôlé permet de garder SQL léger et de rendre visible la configuration manquante.

## Hébergement Builder.io {#builder-hosting}

Lorsque votre application est connectée à Builder.io, les téléchargements de fichiers sont automatiquement acheminés vers l'hébergement d'actifs de Builder. L'offre gratuite de Builder.io inclut ce stockage géré. Les fichiers sont servis à partir d'un CDN sans aucune configuration nécessaire, et l'URL durable est stockée dans le fil de discussion afin que les tours suivants puissent la réutiliser. Il s'agit de la configuration de production recommandée.

## Fournisseurs personnalisés {#custom-providers}

Le framework fournit déjà un fournisseur intégré pour le stockage compatible
S3 (AWS S3, Cloudflare R2, MinIO, et similaires). Connectez-le avec des
variables d'environnement ou via la liste de configuration initiale de la
barre latérale. Aucun code n'est nécessaire. Voir [Onboarding](/docs/onboarding).

N'enregistrez un fournisseur personnalisé que pour un type de backend
différent. Cet exemple effectue un téléchargement via une API HTTP générique
en utilisant `fetch()` :

```ts filename="server/plugins/file-upload.ts"
import { registerFileUploadProvider } from "@agent-native/core/file-upload";
import { defineNitroPlugin } from "@agent-native/core/server";

export default defineNitroPlugin(() => {
  registerFileUploadProvider({
    id: "my-storage",
    name: "My Storage",
    isConfigured: () => !!process.env.UPLOAD_ENDPOINT,
    upload: async ({ data, filename, mimeType }) => {
      const endpoint = process.env.UPLOAD_ENDPOINT!;
      const body = new FormData();
      body.append("file", new Blob([data], { type: mimeType }), filename);

      // This example assumes an upload API that accepts a multipart file
      // and returns { url }. Adjust the request and response handling to
      // match your own provider's actual contract.
      const response = await fetch(endpoint, { method: "POST", body });
      if (!response.ok) {
        throw new Error(`Upload failed with status ${response.status}`);
      }

      const { url } = await response.json();
      return { url, provider: "my-storage" };
    },
  });
});
```

Utilisez `resolveSecret()` depuis `@agent-native/core/server` plutôt qu'une
variable d'environnement lorsque le fournisseur nécessite une véritable
information d'identification, comme une clé API. Voir [Sécurité — Gestion des secrets](/docs/security#secrets).

## API de téléchargement {#upload-api}

L'interface `FileUploadProvider` :

```ts
interface FileUploadProvider {
  id: string; // Unique id, e.g. "s3"
  name: string; // Human-readable name
  isConfigured: () => boolean; // True when ready from sync runtime state
  isConfiguredForRequest?: () => Promise<boolean>; // True from scoped DB secrets
  upload: (input: FileUploadInput) => Promise<FileUploadResult>;
}

interface FileUploadInput {
  data: Uint8Array | Buffer; // File contents
  filename?: string; // Original filename
  mimeType?: string; // MIME type, e.g. "image/png"
  ownerEmail?: string; // For request-scoped provider credentials
  stableUrl?: boolean; // Builder.io hint: one stable URL while compression finishes
  recordAsset?: boolean; // Builder.io hint: set false to skip the asset library
}

interface FileUploadResult {
  url: string; // Public URL for the uploaded file
  id?: string; // Provider-specific id
  provider: string; // Which provider handled it
}
```

Utilisez `uploadFile()` depuis `@agent-native/core/file-upload` dans les actions ou le code serveur :

```ts
import { uploadFile } from "@agent-native/core/file-upload";

const result = await uploadFile({
  data: fileBuffer,
  filename: "photo.jpg",
  mimeType: "image/jpeg",
});

if (result) {
  // Provider handled it. result.url is the public URL.
} else {
  // No provider configured. Show the storage setup CTA, or skip.
}
```

## Téléchargements reprenables / en streaming {#resumable}

Un fournisseur peut implémenter de façon optionnelle un bloc `resumable` sur `FileUploadProvider` pour les téléchargements qui doivent transmettre les données au stockage au fur et à mesure de leur arrivée, plutôt que de mettre en mémoire tampon le fichier entier au préalable. Le modèle Clips utilise cette fonctionnalité pour relayer un enregistrement vers le stockage morceau par morceau pendant qu'il est encore en cours d'enregistrement, plutôt que d'assembler le blob complet une fois l'enregistreur arrêté.

```ts
interface FileUploadProvider {
  // ...id, name, isConfigured, upload...

  resumable?: {
    startSession(
      filename: string,
      mimeType: string,
      maxBytes: number,
    ): Promise<ResumableUploadSession>;
    relayChunk(
      session: ResumableUploadSession,
      contentRange: string,
      bytes: Uint8Array,
      options?: { mimeType?: string },
    ): Promise<ResumableChunkResult>;
    completeSession(
      session: ResumableUploadSession,
      filename: string,
      options?: { stableUrl?: boolean; recordAsset?: boolean },
    ): Promise<string>;
    // Best-effort provider cleanup for a session the caller will not resume.
    abortSession?(session: ResumableUploadSession): Promise<void>;
  };
}

interface ResumableUploadSession {
  sessionId: string; // Provider-specific: GCS Location URI, S3 UploadId, etc.
  meta: Record<string, unknown>; // Provider state carried between calls
}

interface ResumableChunkResult {
  ok: boolean;
  status: number;
  updatedMeta?: Record<string, unknown>; // Merged back into the stored session
}
```

Lorsque `resumable` est présent, les appelants qui transmettent des données en continu (comme un enregistreur) appellent `startSession` une fois, `relayChunk` de façon répétée à mesure que les octets arrivent, et `completeSession` lorsque le flux se termine. Cela remplace l'appel unique et mis en mémoire tampon à `upload()`. Un fournisseur sans bloc `resumable` ne voit jamais que le chemin mis en mémoire tampon. Implémentez-le uniquement lorsque votre backend de stockage dispose d'une API de téléchargement fragmenté ou reprenable native (S3 multipart, téléchargements reprenables GCS, etc.) qui mérite d'être exposée.
