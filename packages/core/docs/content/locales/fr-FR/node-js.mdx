# Node.js

Node.js est le moyen le plus simple d'exécuter une application Agent-Native en
production. Le build produit un seul serveur Node.js qui sert à la fois les pages
de l'application et son API. Vous pouvez exécuter ce serveur partout où Node.js
fonctionne, par exemple sur une machine virtuelle, chez un hébergeur Node.js géré
ou sur votre propre matériel.

Ce guide présente le déploiement d'une application autonome depuis le début.
Vous allez créer l'application, lui fournir une base de données de production et
un secret d'authentification, préparer la base de données, puis construire et
démarrer le serveur.

<Callout tone="info">

Node.js `22.22+` est requis.

</Callout>

Exécutez chaque commande de ce guide sur le serveur qui hébergera l'application.
Pour une machine virtuelle, cela signifie généralement vous y connecter d'abord
en SSH. Le dossier de l'application, ses variables d'environnement et le serveur
en cours d'exécution se trouvent tous sur cette machine.

## Étape 1 : Créer l'application {#step-1-create-the-app}

Créez votre nouvelle application autonome. L'exemple ci-dessous crée une
application à partir du template Chat, mais vous pouvez partir de n'importe quel
template. Placez-vous dans le dossier de l'application et installez ses
dépendances. `corepack enable` active la version de `pnpm` attendue par
l'application. Vous n'avez donc pas besoin d'installer `pnpm` vous-même.

```bash
npx --yes @agent-native/core@latest create my-app --standalone --template chat

cd my-app

corepack enable

pnpm install
```

Remplacez `my-app` par le nom de votre application si vous le souhaitez. La
suite de ce guide suppose que vous vous trouvez dans le dossier de
l'application.

## Étape 2 : Configurer les secrets d'environnement {#step-2-configure-environment-secrets}

L'application lit ses paramètres de production depuis des variables
d'environnement :

| Variable             | Requise | Rôle                                                                   |
| -------------------- | ------- | ---------------------------------------------------------------------- |
| `DATABASE_URL`       | Oui     | Connecte l'application à sa base de données PostgreSQL                 |
| `BETTER_AUTH_SECRET` | Oui     | Signe les sessions utilisateur                                         |
| `BETTER_AUTH_URL`    | Non     | Définit l'adresse publique utilisée pour accéder à votre application   |

Les exports ci-dessous permettent aux commandes suivantes de fonctionner dans ce
shell. Avant de déployer, enregistrez ces mêmes variables dans les paramètres
d'environnement du projet ou du service chez votre hébergeur. Le serveur les
conservera ainsi après un redémarrage ou un nouveau déploiement.

### URL de la base de données {#database-url}

En développement local, l'application stocke ses données dans une base de
données locale lorsque `DATABASE_URL` n'est pas défini. Une application déployée
a besoin d'une vraie base de données PostgreSQL qui conserve ses données entre
les redémarrages. Copiez la chaîne de connexion fournie par votre fournisseur et
exportez-la :

```bash
export DATABASE_URL='your-postgres-url-string'
```

Les [guides des fournisseurs de bases de données](/docs/neon) indiquent où
trouver la chaîne de connexion pour chaque fournisseur.

<Callout tone="warning">

Choisissez un fournisseur PostgreSQL persistant, par exemple Neon, Supabase ou Amazon RDS.

</Callout>

### Secret d'authentification {#auth-secret}

Générez-le une seule fois et gardez-le identique d'un déploiement à l'autre.

L'application utilise `BETTER_AUTH_SECRET` pour signer les sessions utilisateur.
S'il change, tous les utilisateurs connectés sont déconnectés. La commande
ci-dessous génère une valeur aléatoire :

```bash
export BETTER_AUTH_SECRET="$(openssl rand -hex 32)"
```

Conservez la valeur générée en lieu sûr, par exemple dans les paramètres de
secrets de votre hébergeur ou dans un gestionnaire de mots de passe. Utilisez la
même valeur à chaque déploiement.

### URL publique {#public-url}

Facultatif. Définissez-la si vous utilisez un domaine personnalisé, un reverse
proxy ou un flux d'authentification ou OAuth qui exige une origine publique
fixe.

`BETTER_AUTH_URL` est l'adresse publique utilisée pour accéder à votre
application. Sans elle, l'application déduit son adresse de chaque requête
entrante. Cela convient généralement, mais les liens de connexion et les
redirections OAuth peuvent pointer au mauvais endroit lorsque l'application se
trouve derrière un proxy ou un domaine personnalisé.

```bash
export BETTER_AUTH_URL='https://your-domain.example'
```

## Étape 3 : Migrer {#step-3-migrate}

Les migrations créent et mettent à jour les tables dont l'application a besoin
dans votre base de données.

Exécutez cette commande sur l'hôte, avec la `DATABASE_URL` de production, avant
la première visite.

```bash
pnpm migrate:production
```

La commande lit `DATABASE_URL` depuis l'environnement que vous avez exporté à
l'étape précédente. Exécutez-la de nouveau après une mise à niveau de
l'application, avant de démarrer la nouvelle version.

## Étape 4 : Construire et démarrer {#step-4-build-and-start}

Construisez explicitement pour la cible Node.js :

```bash
NITRO_PRESET=node pnpm build
```

Le build écrit le serveur final dans le dossier `.output`. `NITRO_PRESET=node`
garantit que la sortie est un simple serveur Node.js, même sur une machine où
une autre cible d'hébergement est détectée.

Démarrez le serveur généré avec les variables d'environnement exportées :

```bash
NODE_ENV=production \
DATABASE_URL="$DATABASE_URL" \
BETTER_AUTH_SECRET="$BETTER_AUTH_SECRET" \
pnpm start
```

`NODE_ENV=production` exécute le serveur en mode production. Comme vous avez
exporté les variables plus tôt, le serveur reçoit aussi `BETTER_AUTH_URL` si
vous l'avez définie.

Le serveur écoute sur le port `3000`. Si votre hébergeur attribue un autre port,
définissez la variable d'environnement `PORT` avant de démarrer le serveur.

Pour rendre l'application accessible depuis Internet, ouvrez le port `3000` dans
le pare-feu du serveur, ou placez devant lui un reverse proxy comme Nginx ou
Caddy pour servir votre domaine en HTTPS. Ouvrez ensuite l'adresse publique de
l'application et créez le premier compte.

## Garder le serveur en marche {#keep-the-server-running}

La commande `pnpm start` s'arrête lorsque vous fermez votre terminal ou que le
serveur redémarre. Pour que l'application reste en marche, lancez la même
commande depuis un gestionnaire de processus ou un service, comme `systemd`, et
fournissez à ce service les mêmes variables d'environnement.
