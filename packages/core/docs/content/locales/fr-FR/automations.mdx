# Automatisations

Une **automatisation** est une tâche exécutée par l'agent selon un calendrier, lorsqu'un événement survient ou lorsqu'un webhook est appelé : _quand X se produit, faites Y_. **Scheduled**, **Event** et **Webhook** sont des types de déclencheurs, pas des produits distincts.

Le framework présentait à l'origine les automatisations planifiées comme des **Recurring Jobs**. Ce nom, le chemin `jobs/<name>.md` et l'outil `manage-jobs` restent disponibles pour compatibilité. La nouvelle documentation utilise **Automations** comme terme générique ; consultez [Recurring Jobs](/docs/recurring-jobs) pour maintenir une ancienne tâche planifiée ou utiliser la portée organisation et les champs avancés.

## Types de déclencheurs {#trigger-types}

| Tapez      | Se déclenche quand                                                              | Champ clé                    |
| ---------- | ------------------------------------------------------------------------------- | ---------------------------- |
| `schedule` | Une expression cron correspond (comme pour les tâches récurrentes)              | `schedule` (cron)            |
| `event`    | Un événement correspondant est émis sur le bus d'événements du framework        | `event` (nom)                |
| `webhook`  | Une requête HTTP `POST` arrive sur l'URL de webhook secrète de l'automatisation | L'URL renvoyée à la création |

Les déclencheurs d'événement et de webhook peuvent inclure un `condition` : une chaîne en langage naturel qu'un modèle vérifie par rapport à la charge utile avant l'envoi. Si la condition ne correspond pas, l'automatisation est ignorée et enregistre le statut `skipped`. Si la condition ne peut pas être évaluée, l'automatisation ne s'exécute pas. Voir [Conditions](#conditions).

### Déclencheurs webhook {#webhook-triggers}

Créer une automatisation webhook renvoie un chemin d'URL de la forme `/_agent-native/automations/webhook/<token>`. Le jeton est le secret : ne donnez donc l'URL qu'au service qui l'appelle. Chaque `POST` envoyé à cette URL devient la charge utile de l'automatisation, jusqu'à 64 Ko. Un corps envoyé avec un type de contenu JSON est analysé, et tout autre corps est transmis comme texte. Le point de terminaison répond `202` et exécute l'automatisation en arrière-plan.

Envoyez un identifiant d'événement stable dans un en-tête `X-Webhook-Event-Id`, `X-Event-Id` ou `X-GitHub-Delivery`, ou sous la forme d'un `id` de type chaîne de premier niveau dans un corps JSON. Une livraison répétée avec le même identifiant n'est pas remise en file d'attente et reçoit une réponse `200` marquée comme doublon. L'identifiant n'empêche que les livraisons en double. Une exécution échouée peut faire l'objet d'une nouvelle tentative, et cette nouvelle tentative peut répéter des effets de bord que l'exécution échouée a déjà causés. Une fois qu'une livraison a définitivement échoué, son identifiant est libéré, et une livraison ultérieure avec cet identifiant est mise en file d'attente comme une nouvelle livraison.

## Créer des automatisations {#creating}

### En demandant à l'agent

> "Lorsque quelqu'un réserve une réunion avec un e-mail @builder.io, envoyez-moi un message en Slack."

L'agent découvre les événements disponibles, confirme le plan et rédige l'automatisation pour vous.

### Depuis l'interface Automations

Ouvrez **Settings › Automations**. C'est l'endroit principal pour voir les automatisations planifiées, déclenchées par événement et par webhook, consulter leur statut, en exécuter une immédiatement, les mettre en pause ou les reprendre, et les supprimer. Les anciens liens `/agent#jobs` y redirigent.

**Run now** est le moyen le plus rapide de tester une automatisation. Il exécute immédiatement les instructions de l'automatisation, avec leurs effets de bord réels. Il ignore le déclencheur et la condition, et il ne modifie pas la prochaine exécution planifiée, à une exception près : si le framework a mis l'automatisation en pause, une exécution réussie la réactive, et la prochaine exécution d'une automatisation planifiée est à nouveau calculée. L'agent peut faire la même chose avec `manage-automations` et `action=run-now`.

<Callout tone="warning">

`manage-automations` prend en charge les automatisations personnelles et d'organisation pour les déclencheurs Scheduled et Event. Les automatisations d'événement d'une organisation sont visibles par ses membres, mais s'exécutent toujours en tant que leur créateur ; les administrateurs peuvent les gérer sans changer cette identité.

</Callout>

Le troisième chemin (écriture manuelle du fichier `jobs/<name>.md` via `resourcePut`) fonctionne exactement comme pour [recurring jobs](/docs/recurring-jobs#creating). Pour une automatisation basée sur les événements, vous ajoutez le thème déclencheur d'événement ci-dessous à ce même fichier. Une tâche déclenchée par un événement définit `schedule: ""` et fournit `triggerType: event`, un nom `event` et un `condition` facultatif :

## Questions avant l'automatisation {#frontmatter}

Les automatisations partagent tous les champs du [recurring-jobs frontmatter table](/docs/recurring-jobs#frontmatter). Ces champs supplémentaires contrôlent les déclencheurs d'événements, les conditions et le mode d'exécution :

| Champ         | Tapez                                    | Par défaut     | Description                                                                                                                                                                                     |
| ------------- | ---------------------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `triggerType` | `"schedule"` \| `"event"` \| `"webhook"` | `"schedule"`   | Comment se déclenche l'automatisation                                                                                                                                                           |
| `event`       | chaîne                                   | _(facultatif)_ | Nom de l'événement auquel s'abonner (déclencheurs d'événement uniquement)                                                                                                                       |
| `condition`   | chaîne                                   | _(facultatif)_ | Condition en langage naturel évaluée avant l'envoi (déclencheurs d'événement et de webhook)                                                                                                     |
| `mode`        | `"agentic"`                              | `"agentic"`    | Boucle d'agent complète (le seul mode pris en charge). `"deterministic"` a été supprimé — il n'a jamais été implémenté, et les automatisations qui le définissaient ne se déclenchaient jamais. |
| `domain`      | chaîne                                   | _(facultatif)_ | Balise de regroupement (mail, calendrier, clips, etc.)                                                                                                                                          |

Pour un déclencheur d'événement ou de webhook, `schedule` est `""` (vide) ; pour un déclencheur de planification, il porte l'expression cron. Le répartiteur écrit également les mêmes champs gérés `lastRun` / `lastStatus` / `lastError` que le planificateur, plus un statut `"skipped"` lorsqu'une condition est évaluée comme fausse. Lorsqu'une condition ne peut pas être évaluée, consultez [Conditions](#conditions) pour savoir ce qui est enregistré.

## Le bus événementiel {#event-bus}

Les intégrations enregistrent les événements au moment du chargement du module. Le bus valide les charges utiles par rapport aux définitions [Standard Schema](https://standardschema.dev) et les envoie aux abonnés.

### Événements intégrés {#built-in-events}

| Événement              | Source                                         |
| ---------------------- | ---------------------------------------------- |
| `test.event.fired`     | Manuel / Action `manage-automations`=fire-test |
| `agent.turn.completed` | Chat avec les agents                           |
| `calendar.*`           | Intégration du calendrier                      |
| `clip.*`               | Intégration de clips                           |
| `mail.*`               | Intégration de messagerie                      |

Appelez `manage-automations` avec `action=list-events` depuis l'agent pour voir tous les événements enregistrés avec des descriptions et des schémas de charge utile pour le modèle actuel.

### Émettre des événements personnalisés {#emitting-events}

Enregistrez un type d'événement dans un plugin de serveur, puis émettez-le à partir de actions ou des gestionnaires de webhook :

```ts
import { registerEvent, emit } from "@agent-native/core/event-bus";
import { z } from "zod";

// Register the event type (once, at module load)
registerEvent({
  name: "order.completed",
  description: "A customer completed an order",
  payloadSchema: z.object({
    orderId: z.string(),
    customerEmail: z.string(),
    total: z.number(),
  }),
  example: {
    orderId: "ord_123",
    customerEmail: "jane@example.com",
    total: 49.99,
  },
});

// Emit the event (from an action, webhook handler, etc.)
emit(
  "order.completed",
  {
    orderId: "ord_123",
    customerEmail: "jane@example.com",
    total: 49.99,
  },
  { owner: "user@example.com" },
);
```

Le `owner` des métadonnées d'émission détermine quelles automatisations se déclenchent. Les automatisations d'événement personnelles et d'organisation exigent une correspondance exacte avec `createdBy`.

## Conditions {#conditions}

Les conditions sont des chaînes en langage naturel qu'un modèle vérifie par rapport à la charge utile de l'événement ou du webhook. Il s'agit d'une classification oui/non, pas d'une tâche de génération.

- **Condition vide ou manquante** = inconditionnel (se déclenche toujours).
- Les résultats sont mis en cache pendant 5 minutes, avec pour clé un hachage SHA-256 de la condition et de la charge utile, et au plus 500 entrées.
- La charge utile est tronquée à 4 000 caractères avant d'être envoyée au modèle.

<Callout tone="info">

Une condition qui ne peut pas être évaluée ne compte ni comme une correspondance ni comme une non-correspondance, et l'automatisation ne s'exécute pas. Une erreur du fournisseur enregistre `lastStatus: error` avec la raison dans `lastError`, et l'événement fait l'objet d'une nouvelle tentative. Si aucune clé API n'est disponible pour évaluer la condition, une automatisation d'événement enregistre une erreur pour chaque événement correspondant et se met en pause d'elle-même après trois erreurs consécutives. Dès qu'une clé est disponible, un planificateur en cours d'exécution la réactive de lui-même en 15 minutes environ. Dans un environnement où aucun planificateur ne s'exécute, réactivez-la dans **Settings › Automations**. Une automatisation webhook dans le même état ne se met pas en pause. Sa livraison échoue et fait l'objet d'une nouvelle tentative.

</Callout>

Exemples de conditions :

- `"attendee email ends with @builder.io"`
- `"the order total is greater than $100"`
- `"the message contains the word 'urgent'"`

## L'outil de requête Web {#web-request}

Les automatisations utilisent l'outil `web-request` pour les HTTP sortants. Il prend en charge les espaces réservés `${keys.NAME}` dans le URL, les en-têtes et le corps :

```
POST to ${keys.SLACK_WEBHOOK}

Headers: {"Authorization": "Bearer ${keys.API_TOKEN}"}

Body: {"text": "New booking from ${attendeeEmail}"}
```

Les espaces réservés sont résolus **côté serveur** après que l'agent a émis l'appel à l'outil : la valeur secrète brute n'entre jamais dans le contexte de l'agent.

### Paramètres {#web-request-params}

| Paramètre    | Tapez  | Par défaut | Description                                               |
| ------------ | ------ | ---------- | --------------------------------------------------------- |
| `url`        | chaîne | —          | URL complet. Peut contenir des références `${keys.NAME}`. |
| `method`     | chaîne | `GET`      | Méthode HTTP (GET, POST, PUT, PATCH, DELETE, HEAD).       |
| `headers`    | chaîne | `{}`       | Objet JSON des en-têtes. Peut contenir `${keys.NAME}`.    |
| `body`       | chaîne | —          | Corps de la requête. Peut contenir `${keys.NAME}`.        |
| `timeout_ms` | numéro | 15000      | Délai d'expiration en millisecondes (max 30 000).         |

## Clés {#keys}

Les clés sont des secrets ad hoc créés par les utilisateurs ou l'agent à des fins d'automatisation (par exemple, `SLACK_WEBHOOK`, `HUBSPOT_API_KEY`). Ils diffèrent des secrets enregistrés (`registerRequiredSecret`) en ce sens qu'ils n'ont pas de métadonnées définies par un modèle ni d'étape d'intégration.

- Créé via les paramètres UI ou `/_agent-native/secrets/adhoc` API.
- Une clé créée via l'API peut inclure un `urlAllowlist` qui restreint les origines auxquelles la clé peut être envoyée (correspondance au niveau de l'origine). Les clés ajoutées dans les paramètres n'ont pas de liste d'autorisation.
- La valeur brute n'est jamais exposée à l'IA : seuls les espaces réservés `${keys.NAME}` apparaissent dans le contexte de l'agent.
- La résolution passe de la portée utilisateur à la portée de l'espace de travail, afin que les utilisateurs puissent remplacer les clés partagées.

## Outils d'agent {#agent-tools}

Les automatisations personnelles et d'organisation utilisent `manage-automations` avec un paramètre `action` :

| Actions       | Objectif                                                                                                         |
| ------------- | ---------------------------------------------------------------------------------------------------------------- |
| `list-events` | Découvrez tous les événements enregistrés avec des descriptions et des schémas de charge utile                   |
| `list-hosts`  | Lister les hôtes d'exécution associés avant d'en attribuer un à une automatisation                               |
| `list`        | Liste de toutes les automatisations avec statut ; filtrer par domaine ou activé                                  |
| `define`      | Créer une nouvelle automatisation (nom, type de déclencheur, événement, condition, corps)                        |
| `update`      | Mettre à jour une automatisation existante (activée, condition, corps)                                           |
| `delete`      | Supprimer une automatisation (toujours confirmer d'abord avec l'utilisateur)                                     |
| `run-now`     | Exécuter une automatisation immédiatement, avec des effets de bord réels. Ignore le déclencheur et la condition. |
| `fire-test`   | Émettre un événement `test.event.fired`. Seules les automatisations abonnées à cet événement réagissent.         |

Outil supplémentaire : `web-request` — HTTP sortant avec substitution `${keys.NAME}`.

`manage-automations` prend en charge la portée organisation, les remplacements de modèle et les listes d'autorisation MCP strictement appliquées. `manage-jobs` reste disponible pour les anciennes intégrations uniquement planifiées et les métadonnées de livraison.

## Exemple {#example}

**Utilisateur :** "Lorsque quelqu'un réserve avec un e-mail @builder.io, envoyez-moi un message en Slack."

**Flux d'agent :**

1. Appelle `manage-automations` avec `action=list-events` — trouve `calendar.booking.created`.
2. Confirme le plan avec l'utilisateur.
3. Appelle `manage-automations` avec `action=define` :
   - `name`: `slack-on-builder-booking`
   - `trigger_type`: `event`
   - `event`: `calendar.booking.created`
   - `condition`: `attendee email ends with @builder.io`
   - `mode`: `agentic`
   - `domain`: `calendar`
   - `body`: `Send a Slack message to #sales with the booking details. Use the web-request tool to POST to ${keys.SLACK_WEBHOOK}.`
4. L'automatisation est enregistrée sous le nom `jobs/slack-on-builder-booking.md` et commence à écouter immédiatement.

## Plus d'exemples {#more-examples}

### Notifier via webhook lorsqu'un plan est commenté

Demandez à l'agent du plan : _"Lorsque quelqu'un ajoute un commentaire humain sur un plan, POST a
notification à mon webhook."_

```yaml
---
schedule: ""
triggerType: event
event: plan.commented
condition: "resolutionTarget is human or resolutionTarget is null"
mode: agentic
domain: plan
enabled: true
---

POST to ${keys.NOTIFY_WEBHOOK} with a JSON body:
{"title": "<plan title>", "excerpt": "<comment excerpt>", "author": "<author email or null>", "url": "<app base url + path>"}
```

Définissez `NOTIFY_WEBHOOK` sur n'importe quel point de terminaison HTTP : un webhook entrant Slack, un générique
service de notification ou récepteur personnalisé. L'outil `web-request` résout
`${keys.NOTIFY_WEBHOOK}` côté serveur ; le URL brut n'apparaît jamais dans le dossier de l'agent
contexte. Voir [Visual Plans — Events and notifications](/docs/template-plan#events)
pour la référence complète de la charge utile `plan.commented` et les quatre événements du plan.
