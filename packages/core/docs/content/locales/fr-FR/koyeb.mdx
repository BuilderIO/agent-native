# Koyeb

<Badge label="Beta" color="orange" icon="rocket" />

Koyeb héberge votre application en tant que service web. Vous n'avez donc aucun
serveur à configurer ni à maintenir en marche. Koyeb exécute le même serveur
Node.js que celui décrit dans le [guide Node.js](/docs/node-js), le construit à
partir de votre dépôt GitHub et fournit à l'application une adresse publique en
HTTPS.

Ce guide présente le déploiement d'une application autonome depuis le début.
Vous allez créer l'application et la pousser vers GitHub, lui fournir une base
de données de production et un secret d'authentification, préparer la base de
données, puis créer un service web Koyeb qui la construit et l'exécute.

<Callout tone="info">

Node.js `22.22+` est requis.

</Callout>

Vous avez aussi besoin d'un compte Koyeb et d'un dépôt GitHub. Exécutez les
commandes de ce guide sur votre propre ordinateur. Koyeb construit et exécute
l'application à partir de votre dépôt.

## Étape 1 : Créer l'application {#step-1-create-the-app}

Créez votre nouvelle application autonome. L'exemple ci-dessous crée une
application à partir du template Chat, mais vous pouvez partir de n'importe quel
template. Placez-vous dans le dossier de l'application et installez ses
dépendances. `corepack enable` active la version de `pnpm` attendue par
l'application. Vous n'avez donc pas besoin d'installer `pnpm` vous-même.

```bash
npx --yes @agent-native/core@latest create my-app --standalone --template chat

cd my-app

corepack enable

pnpm install
```

Remplacez `my-app` par le nom de votre application si vous le souhaitez. La
suite de ce guide suppose que vous vous trouvez dans le dossier de
l'application.

Koyeb construit l'application à partir de GitHub. Poussez donc le dossier de
l'application vers un nouveau dépôt GitHub avant de continuer. Committez aussi
le fichier `pnpm-lock.yaml`. Koyeb l'utilise, avec le champ `packageManager` de
`package.json`, pour installer l'application avec `pnpm`. Koyeb lit aussi la
version de Node.js dans le champ `engines` de `package.json`. Une nouvelle
application définit déjà ces deux champs.

## Étape 2 : Configurer les secrets d'environnement {#step-2-configure-environment-secrets}

L'application lit ses paramètres de production depuis des variables
d'environnement :

| Variable             | Requise | Rôle                                                                 |
| -------------------- | ------- | -------------------------------------------------------------------- |
| `DATABASE_URL`       | Oui     | Connecte l'application à sa base de données PostgreSQL               |
| `BETTER_AUTH_SECRET` | Oui     | Signe les sessions utilisateur                                       |
| `BETTER_AUTH_URL`    | Non     | Définit l'adresse publique utilisée pour accéder à votre application |

Les exports ci-dessous permettent aux commandes suivantes de fonctionner dans ce
shell. Avant de déployer, enregistrez ces mêmes variables dans les paramètres
d'environnement du projet ou du service chez votre hébergeur. L'étape 4 montre
comment les enregistrer dans Koyeb.

### URL de la base de données {#database-url}

En développement local, l'application stocke ses données dans une base de
données locale lorsque `DATABASE_URL` n'est pas défini. Une application déployée
a besoin d'une vraie base de données PostgreSQL qui conserve ses données d'un
déploiement à l'autre. Koyeb remplace les fichiers du service à chaque
déploiement et à chaque redémarrage. La base de données doit donc se trouver en
dehors du service web. Copiez la chaîne de connexion fournie par votre
fournisseur et exportez-la :

```bash
export DATABASE_URL='your-postgres-url-string'
```

Les [guides des fournisseurs de bases de données](/docs/neon) indiquent où
trouver la chaîne de connexion pour chaque fournisseur.

<Callout tone="warning">

Choisissez un fournisseur PostgreSQL persistant, par exemple Neon, Supabase ou Amazon RDS.

</Callout>

### Secret d'authentification {#auth-secret}

Générez-le une seule fois et gardez-le identique d'un déploiement à l'autre.

L'application utilise `BETTER_AUTH_SECRET` pour signer les sessions utilisateur.
S'il change, tous les utilisateurs connectés sont déconnectés. La commande
ci-dessous génère une valeur aléatoire :

```bash
export BETTER_AUTH_SECRET="$(openssl rand -hex 32)"
```

Conservez la valeur générée en lieu sûr, par exemple dans un gestionnaire de
mots de passe. Utilisez la même valeur à chaque déploiement.

### URL publique {#public-url}

Facultatif. Définissez-la si vous utilisez un domaine personnalisé, un reverse
proxy ou un flux d'authentification ou OAuth qui exige une origine publique
fixe.

`BETTER_AUTH_URL` est l'adresse publique utilisée pour accéder à votre
application. Sans elle, l'application déduit son adresse de chaque requête
entrante. Cela convient généralement avec l'adresse que Koyeb vous fournit,
mais définissez-la lorsque vous connectez un domaine personnalisé, afin que les
liens de connexion et les redirections OAuth utilisent ce domaine.

```bash
export BETTER_AUTH_URL='https://your-domain.example'
```

## Étape 3 : Migrer {#step-3-migrate}

Les migrations créent et mettent à jour les tables dont l'application a besoin
dans votre base de données. Exécutez cette commande avant le premier
déploiement :

```bash
pnpm migrate:production
```

La commande s'exécute sur votre ordinateur et se connecte à la base de données
de production avec la `DATABASE_URL` que vous avez exportée à l'étape 2.
Exécutez-la de nouveau après une mise à niveau de l'application, avant de
déployer la nouvelle version.

## Étape 4 : Créer le service web {#step-4-create-the-web-service}

Dans le panneau de contrôle Koyeb, créez un nouveau **Web Service**, choisissez
**GitHub** comme méthode de déploiement, puis sélectionnez le dépôt et la
branche de l'étape 1. Conservez le builder **Buildpack**, puis remplacez les
commandes de build et d'exécution par ces valeurs :

| Paramètre     | Valeur                          |
| ------------- | ------------------------------- |
| Build command | `NITRO_PRESET=koyeb pnpm build` |
| Run command   | `node .output/server/index.mjs` |

`NITRO_PRESET=koyeb` construit le même serveur Node.js que dans le guide
Node.js, configuré pour servir ses propres fichiers statiques. La commande
d'exécution démarre ce serveur. Koyeb expose le port `8000` par défaut et
définit la variable d'environnement `PORT` en conséquence. Le serveur lit `PORT`
automatiquement, vous n'avez donc pas besoin de modifier les paramètres de port.

Sous **Environment variables**, ajoutez `DATABASE_URL` et `BETTER_AUTH_SECRET`.
Pour ce type de valeurs, Koyeb recommande d'enregistrer chacune comme
**Secret** et d'y faire référence depuis la variable. Par exemple, enregistrez
la chaîne de connexion comme Secret nommé `DATABASE_URL`, puis définissez la
valeur de la variable sur `{{ secret.DATABASE_URL }}`. Si vous avez défini
`BETTER_AUTH_URL`, ajoutez-la de la même façon.

## Étape 5 : Déployer {#step-5-deploy}

<Steps>

### Choisir un type d'instance

Choisissez le type d'instance du service web. Le type d'instance Free suffit
pour essayer l'application. Choisissez un type d'instance payant si
l'application doit répondre immédiatement.

### Créer le service web

Nommez le service et l'application, puis déployez. Koyeb construit
l'application à partir de votre dépôt et la démarre. Le premier build prend
quelques minutes, et vous pouvez le suivre dans les logs de build et
d'exécution du service.

### Ouvrir l'application

Lorsque le déploiement se termine, le panneau de contrôle affiche l'adresse de
l'application, qui se termine par `koyeb.app`. Ouvrez-la et créez le premier
compte.

</Steps>

Avec le type d'instance Free, Koyeb réduit le service à zéro après une heure
sans trafic. La visite suivante attend alors le temps que le service redémarre.
Chaque organisation peut exécuter une instance Free.

## Déployer les mises à jour {#deploy-updates}

Koyeb redéploie chaque fois que vous poussez vers la branche choisie à
l'étape 4. Pour publier une nouvelle version, exécutez d'abord les migrations,
puis poussez :

```bash
pnpm migrate:production

git push
```

Les paramètres du service et les variables enregistrées restent en place. Vous
n'avez donc pas besoin de répéter l'étape 4.
