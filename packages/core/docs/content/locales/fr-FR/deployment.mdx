# Déploiement

Les applications Agent-Native s'exécutent sur [Nitro](https://nitro.build). La
même application peut donc être déployée sur Node.js, sur des fonctions
serverless, sur des workers edge ou chez un hébergeur géré. Choisissez le
parcours qui correspond à ce que vous livrez :

<Cards columns={2}>

### :server: [Déployer une application](/docs/deploy-an-app)

Construisez et lancez une application autonome sur Node.js, Docker, Vercel,
Netlify ou Cloudflare Workers.

### :network: [Déployer un workspace](/docs/workspace-deployment)

Construisez plusieurs applications derrière une même origine, avec une
connexion partagée et une communication d'application à application sur la
même origine.

</Cards>

## Avant le déploiement : choisir une base de données persistante {#persistent-database}

Chaque application déployée a besoin d'une base de données PostgreSQL
persistante. Le développement local peut utiliser la base de données PGlite
située dans `data/pglite`, mais les systèmes de fichiers des conteneurs, des
previews et des environnements serverless peuvent être réinitialisés à tout
moment.

<Steps>

### Choisir un fournisseur

Utilisez un fournisseur PostgreSQL hébergé comme [Neon](/docs/neon),
[Supabase](/docs/supabase), Railway, Render, [Amazon RDS for PostgreSQL](/docs/aws-rds),
[Cloud SQL for PostgreSQL](/docs/cloud-sql) ou [Azure Database for PostgreSQL](/docs/azure-postgresql).
Utilisez le guide [Plain Postgres](/docs/postgres) pour les autres services
gérés et les serveurs PostgreSQL auto-hébergés. Le framework configure
PostgreSQL à partir de l'URL de connexion.

### Définir la chaîne de connexion

Définissez `DATABASE_URL` dans les paramètres de variables d'environnement ou de
secrets de votre hébergeur avant le premier déploiement de production. Un
fichier `.env` local ne configure que votre machine et n'est pas envoyé par la
commande de déploiement.

### Ajouter les secrets de production

Générez un secret de signature stable avec `openssl rand -hex 32`, puis
définissez-le comme `BETTER_AUTH_SECRET` pour une application autonome. Un
workspace a aussi besoin de `A2A_SECRET` lorsqu'il utilise des requêtes signées
entre applications ou des transferts en arrière-plan. La [référence des
variables d'environnement de déploiement](/docs/deployment-environment-variables)
couvre le reste de la configuration de production.

### Exécuter les migrations

Exécutez `pnpm migrate:production` sur la base de données de production avant
la première visite. Cette commande crée les tables dont l'application a besoin.
Exécutez-la de nouveau après chaque mise à niveau, avant la mise en ligne de la
nouvelle version. Chaque guide d'hébergement montre où se place cette étape.

</Steps>

<Callout tone="info">

Dans un workspace, chaque application hérite par défaut de la `DATABASE_URL` de
la racine. Définissez `<APP_NAME>_DATABASE_URL` uniquement lorsqu'une
application a besoin d'une autre base de données.

</Callout>

## L'envoi d'e-mails est facultatif, mais recommandé {#email-provider}

Un fournisseur d'e-mails n'est pas nécessaire pour l'authentification par
e-mail et mot de passe. Sans fournisseur, une application déployée utilise
l'inscription et la connexion par e-mail et mot de passe, ignore la
vérification de l'e-mail à l'inscription et ne propose pas l'authentification
par lien magique.

Agent-Native ne fournit pas de compte d'envoi d'e-mails. Connectez Resend ou
SendGrid avant le déploiement si vous voulez des liens magiques, la
vérification des e-mails, la réinitialisation des mots de passe, les invitations
ou les notifications de partage. Définissez `RESEND_API_KEY` ou
`SENDGRID_API_KEY` dans l'environnement de déploiement. SendGrid nécessite aussi
`EMAIL_FROM`. Consultez [Authentification](/docs/authentication) pour les modes
d'authentification disponibles.

### Personnaliser les e-mails du framework {#email-templates}

Chaque e-mail envoyé par le framework a un modèle par défaut. Pour utiliser
votre propre design, enregistrez un override depuis un plugin serveur. Le
framework choisit toujours le destinataire et l'expéditeur, et remet le message.
Votre override décide de ce que dit le message et de son apparence.

```ts
// server/plugins/email-templates.ts
import {
  escapeEmailHtml,
  overrideTransactionalEmail,
} from "@agent-native/core/server";

export default function registerEmailTemplates(): void {
  overrideTransactionalEmail("core.resource-shared", (props) => ({
    subject: `${props.sender.name} shared "${props.resource.title}"`,
    html: `<p>${escapeEmailHtml(props.sender.name)} invited you to
      <a href="${escapeEmailHtml(props.resource.url)}">${escapeEmailHtml(props.resource.title)}</a>
      in ${escapeEmailHtml(props.app.name)}.</p>`,
  }));
}
```

| ID de l'e-mail                   | Props                                                                              |
| -------------------------------- | ---------------------------------------------------------------------------------- |
| `core.verify-signup`             | `email`, `verifyUrl`                                                               |
| `core.reset-password`            | `email`, `resetUrl`                                                                |
| `core.magic-link`                | `email`, `magicLinkUrl`                                                            |
| `core.change-email-confirmation` | `email`, `newEmail`, `confirmationUrl`                                             |
| `core.change-email-verification` | `email`, `verifyUrl`                                                               |
| `core.organization-invite`       | `invitee`, `orgName`, `inviter`, `acceptUrl`                                       |
| `core.builder-credit-limit`      | `subject`, `heading`, `body`, `upgradeLabel`, `upgradeUrl`                         |
| `core.resource-shared`           | `recipientEmail`, `sender`, `resource` (`type`, `title`, `url`), `role`, `message` |

Chaque override reçoit aussi `app` (`name`, `logoUrl`). Un second argument
contient le rendu par défaut, ce qui vous permet de réutiliser son objet ou son
texte.

- Les props sont des valeurs brutes. Échappez-les avec `escapeEmailHtml` avant
  de les insérer dans une chaîne HTML.
- Renvoyez `react` avec un élément React au lieu de `html` pour rendre un
  composant. React échappe les props pour vous.
- Omettez `subject` pour conserver l'objet par défaut. Omettez `text` pour
  dériver le texte brut de votre HTML.
- Si un override lève une erreur, l'envoi échoue. Le framework ne revient pas
  au design par défaut. L'aperçu des e-mails transactionnels affiche votre
  override. Vérifiez-le donc à cet endroit.
