# Bereitstellung

Agentennative Apps verwenden unter der Haube [Nitro](https://nitro.build). Das bedeutet, Sie können ohne Konfigurationsänderungen auf jeder Plattform bereitstellen. Legen Sie einfach eine Voreinstellung fest.

## Vor der Bereitstellung: Eine persistente Datenbank wählen {#persistent-database}

Eine **persistente** Datenbank ist eine, deren Daten Neustarts, erneute Bereitstellungen und den gleichzeitigen Betrieb auf mehr als einer Serverinstanz überstehen. Das braucht jede bereitgestellte App.

<Comparison>

### Vorher

Die lokale Entwicklung greift auf eine SQLite-Datei unter `data/app.db` zurück. Das ist auf Ihrem Rechner praktisch, aber die Datei liegt auf dem lokalen Dateisystem, das Container, Vorschauumgebungen und serverlose Plattformen jederzeit zurücksetzen können.

### Nachher

Produktion braucht eine persistente Datenbank, etwa Postgres oder Turso/libSQL, die Neustarts, erneute Bereitstellungen und den gleichzeitigen Betrieb auf mehr als einer Instanz übersteht.

</Comparison>

Eine Datenbank zu verbinden dauert drei Schritte:

<Steps>

### Einen Anbieter wählen

Jeder Postgres-kompatible Host (Neon, Supabase, Railway, RDS und ähnliche) oder eine libSQL/Turso-Datenbank funktioniert. Agent-native liest und schreibt über [Drizzle](https://orm.drizzle.team), eine TypeScript-Bibliothek, die Ihr Schema statt handgeschriebenem SQL in typsichere Abfragen verwandelt, sodass derselbe App-Code gegen jede von ihnen läuft.

### Eine Verbindungszeichenfolge erhalten

Ihr Anbieter gibt Ihnen eine URL, die die Datenbank identifiziert und zeigt, wie sie zu erreichen ist, zum Beispiel `postgres://user:pass@host:5432/dbname`.

### `DATABASE_URL` festlegen

Legen Sie sie vor Ihrer ersten Produktionsbereitstellung in den Umgebungsvariablen Ihres Deploy-Anbieters fest. Agent-native liest die URL und erkennt automatisch, mit welchem **Dialekt** (welcher zugrunde liegenden Datenbank-Engine, Postgres oder SQLite/libSQL) gesprochen werden soll. Die vollständige Adapterliste finden Sie unter [Datenbank](/docs/server-database#production).

</Steps>

<Callout tone="info">

Verwenden Sie Turso oder einen anderen libSQL-Anbieter, der sich mit einem separaten Token authentifiziert? Legen Sie `DATABASE_AUTH_TOKEN` zusätzlich zu `DATABASE_URL` fest. Bauen Sie einen [Arbeitsbereich](/docs/multi-app-workspace) mit mehr als einer App? Jede App erbt standardmäßig die Root-`DATABASE_URL`. Legen Sie `<APP_NAME>_DATABASE_URL` nur für die eine App fest, die eine andere Datenbank benötigt.

</Callout>

### Automatische Schema-Einrichtung {#skip-ensure-tables}

Sie brauchen keinen separaten Migrationsschritt, um loszulegen. Beim ersten Datenbankzugriff eines beliebigen Teils Ihrer App prüft agent-native, ob die benötigten Tabellen, Spalten und Indizes bereits existieren, und legt an, was fehlt. Das passiert einmal pro Server-Boot und bleibt im normalen Betrieb unsichtbar.

Konkret ruft jeder Datenspeicher beim ersten Gebrauch eine interne Funktion `ensureTable()` auf. Diese Funktion prüft den eigenen Katalog der Datenbank (zum Beispiel Postgres' `information_schema`) und gibt nur dann `CREATE TABLE`, `ADD COLUMN` oder `CREATE INDEX` aus, wenn wirklich etwas fehlt. Das sind **DDL**-Anweisungen, kurz für Data Definition Language, der Teil von SQL, der Tabellen formt, statt die darin enthaltenen Zeilen zu lesen oder zu schreiben.

### Kaltstart-Latenz bei Serverless reduzieren {#reducing-cold-start}

Auf einem langlebigen Server läuft diese Prüfung einmal pro Boot, und Sie bemerken sie wahrscheinlich nie. Serverlose Plattformen funktionieren anders. Ein **Kaltstart** ist der Moment, in dem die Plattform eine brandneue Instanz Ihres Servers hochfährt, um eine Anfrage zu bedienen. Bei Serverless kann „erster Zugriff“ jeden Kaltstart bedeuten, über etwa 57 verschiedene Stores hinweg. Das summiert sich auf einige Hundert Roundtrips, bevor eine Anfrage überhaupt echte Arbeit leistet.

Drei Dinge halten das im Zaum:

- **Gebündelte Introspektion.** Statt einer Abfrage pro Tabelle, Spalte und Index laufen die obigen Prüfungen als ein einziger Introspektionsdurchgang pro Datenbank, insgesamt nur zwei Abfragen. Das geschieht automatisch und braucht keine Konfiguration.
- **Automatisches Überspringen bei verwaltetem Serverless.** Netlify Functions, AWS Lambda und Vercel Functions überspringen diese Prüfung in Produktion vollständig, ohne dass eine Einrichtung nötig ist.
- **`AGENT_NATIVE_SKIP_ENSURE_TABLES=1`.** Legen Sie das für Bereitstellungen fest, die das automatische Überspringen nicht abdeckt, etwa ein langlebiger Node-Server, Docker oder ein anderes selbstgehostetes Setup, sobald Ihr Schema bereits migriert ist und Sie nicht möchten, dass der App-Boot Tabellen erstellt oder ändert.

<Callout tone="risk">

Weder das Flag noch das automatische serverlose Überspringen können fail-closed ausfallen. Fehlt eine Tabelle wirklich, schlägt die erste echte Abfrage, die sie braucht, laut fehl, statt still repariert zu werden. Das ist beabsichtigt (eine stille Reparatur würde einen echten Migrationsfehler verbergen), bedeutet aber, dass Sie ab hier für die Migration verantwortlich sind. Setzen Sie dieses Flag nicht und verlassen Sie sich nicht auf das automatische Überspringen bei einer Bereitstellung, die darauf angewiesen ist, dass der App-Boot ihre eigenen Tabellen erstellt.

</Callout>

Mehr als eine App auf einen einzigen Ursprung bereitzustellen oder einen
Arbeitsbereich mit Docker Compose selbst zu hosten, ist eine eigene Seite:
siehe [Workspace-Bereitstellung](/docs/workspace-deployment).

## Voreinstellung festlegen {#setting-the-preset}

Standardmäßig baut Nitro für Node.js. Um eine andere Plattform anzusprechen, legen Sie die Voreinstellung in Ihrer `vite.config.ts` fest:

```ts
import { agentNative } from "@agent-native/core/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [agentNative({ nitro: { preset: "vercel" } })],
});
```

Oder verwenden Sie zur Build-Zeit die Umgebungsvariable `NITRO_PRESET`:

```bash
NITRO_PRESET=netlify npx @agent-native/core@latest build
```

Build- und Deploy-Details für Ihre Plattform finden Sie auf der jeweiligen Seite:

- [**Node.js & Docker**](/docs/node-docker): die Standard-Voreinstellung, plus ein eigenständiges Dockerfile
- [**Vercel**](/docs/vercel)
- [**Netlify**](/docs/netlify): enthält Keep-Warm für Scale-to-Zero-Datenbanken
- [**Cloudflare**](/docs/cloudflare): Pages und Workers
- [**Andere Plattformen**](/docs/other-platforms): AWS Lambda und Deno Deploy

Die Standard-Cache-Richtlinie für die SSR-Shell und wie Sie sie mit
`AGENT_NATIVE_SSR_CACHE` überschreiben, ist eine eigene Seite: siehe [SSR-Caching](/docs/ssr-caching).

Die vollständige Referenz der Produktions-Umgebungsvariablen (Build/Laufzeit,

Wie die UI einer bereitgestellten App nach dem Launch aktualisiert wird,

## Multi-Instanz-Bereitstellungen {#multi-instance}

Agentennative Apps speichern den gesamten Zustand in SQL über Drizzle und synchronisieren die UI über [Polling](/docs/key-concepts#polling-sync) gegen die Datenbank. Es gibt keinen Dateisystemzustand, keine Sticky Sessions und keine In-Memory-Caches. Das bedeutet, Multi-Instanz- und serverlose Bereitstellungen funktionieren sofort: Zeigen Sie jede Instanz auf dieselbe `DATABASE_URL`, und sie konvergieren automatisch. Siehe [Kernkonzepte: Daten in SQL](/docs/key-concepts#data-in-sql) und [Kernkonzepte: Portabilität](/docs/key-concepts#hosting-agnostic).
