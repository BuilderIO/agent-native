# Deployment

Agent-Native-Apps laufen auf [Nitro](https://nitro.build). Dieselbe App lässt
sich daher auf Node.js, Serverless-Funktionen, Edge-Workern oder einem
verwalteten Hoster bereitstellen. Wählen Sie den Weg, der zu dem passt, was Sie
ausliefern:

<Cards columns={2}>

### :server: [Eine App bereitstellen](/docs/deploy-an-app)

Bauen und starten Sie eine einzelne eigenständige App auf Node.js, Docker,
Vercel, Netlify oder Cloudflare Workers.

### :network: [Einen Workspace bereitstellen](/docs/workspace-deployment)

Bauen Sie mehrere Apps hinter einem Origin, mit gemeinsamem Login und
Kommunikation von App zu App über denselben Origin.

</Cards>

## Vor dem Deployment: eine persistente Datenbank wählen {#persistent-database}

Jede bereitgestellte App braucht eine persistente PostgreSQL-Datenbank. Die
lokale Entwicklung kann die PGlite-Datenbank unter `data/pglite` verwenden, aber
die Dateisysteme von Containern, Previews und Serverless-Umgebungen können
jederzeit zurückgesetzt werden.

<Steps>

### Einen Anbieter wählen

Verwenden Sie einen gehosteten PostgreSQL-Anbieter wie [Neon](/docs/neon),
[Supabase](/docs/supabase), Railway, Render, [Amazon RDS for PostgreSQL](/docs/aws-rds),
[Cloud SQL for PostgreSQL](/docs/cloud-sql) oder [Azure Database for PostgreSQL](/docs/azure-postgresql).
Für andere verwaltete Dienste und selbst gehostete PostgreSQL-Server gibt es die
Anleitung [Plain Postgres](/docs/postgres). Das Framework konfiguriert
PostgreSQL anhand der Verbindungs-URL.

### Den Verbindungsstring setzen

Setzen Sie `DATABASE_URL` vor dem ersten Produktions-Deployment in den
Einstellungen für Umgebungsvariablen oder Secrets Ihres Hosters. Eine lokale
`.env` konfiguriert nur Ihren eigenen Computer und wird vom Deploy-Befehl nicht
hochgeladen.

### Produktions-Secrets hinzufügen

Erzeugen Sie mit `openssl rand -hex 32` ein stabiles Signatur-Secret und setzen
Sie es bei einer eigenständigen App als `BETTER_AUTH_SECRET`. Ein Workspace
braucht zusätzlich `A2A_SECRET`, wenn er signierte App-übergreifende Anfragen
oder Hintergrundübergaben verwendet. Die [Referenz der Umgebungsvariablen für
das Deployment](/docs/deployment-environment-variables) deckt die übrige
Produktionskonfiguration ab.

### Migrationen ausführen

Führen Sie `pnpm migrate:production` vor dem ersten Aufruf gegen die
Produktionsdatenbank aus. Der Befehl erstellt die Tabellen, die die App braucht.
Führen Sie ihn nach jedem Upgrade erneut aus, bevor die neue Version live geht.
Jede Hosting-Anleitung zeigt, wo dieser Schritt hingehört.

</Steps>

<Callout tone="info">

In einem Workspace übernimmt jede App standardmäßig die `DATABASE_URL` aus dem
Root. Setzen Sie `<APP_NAME>_DATABASE_URL` nur, wenn eine App eine andere
Datenbank braucht.

</Callout>

## E-Mail-Zustellung ist optional, aber empfohlen {#email-provider}

Für die Authentifizierung mit E-Mail und Passwort ist kein E-Mail-Anbieter
erforderlich. Ohne Anbieter verwendet eine bereitgestellte App E-Mail und
Passwort für Registrierung und Anmeldung, überspringt die E-Mail-Verifizierung
bei der Registrierung und bietet keine Magic-Link-Authentifizierung an.

Agent-Native enthält kein Konto für die E-Mail-Zustellung. Verbinden Sie vor dem
Deployment Resend oder SendGrid, wenn Sie Magic Links, E-Mail-Verifizierung,
Passwortzurücksetzungen, Einladungen oder Freigabebenachrichtigungen möchten.
Setzen Sie `RESEND_API_KEY` oder `SENDGRID_API_KEY` in der
Deployment-Umgebung. SendGrid braucht zusätzlich `EMAIL_FROM`. Unter
[Authentifizierung](/docs/authentication) finden Sie die verfügbaren
Authentifizierungsmodi.

### Framework-E-Mails anpassen {#email-templates}

Jede E-Mail, die das Framework sendet, hat eine Standardvorlage. Um Ihr eigenes
Design zu verwenden, registrieren Sie in einem Server-Plugin einen Override. Das
Framework wählt weiterhin Empfänger und Absender und stellt die Nachricht zu.
Ihr Override bestimmt, was die Nachricht sagt und wie sie aussieht.

```ts
// server/plugins/email-templates.ts
import {
  escapeEmailHtml,
  overrideTransactionalEmail,
} from "@agent-native/core/server";

export default function registerEmailTemplates(): void {
  overrideTransactionalEmail("core.resource-shared", (props) => ({
    subject: `${props.sender.name} shared "${props.resource.title}"`,
    html: `<p>${escapeEmailHtml(props.sender.name)} invited you to
      <a href="${escapeEmailHtml(props.resource.url)}">${escapeEmailHtml(props.resource.title)}</a>
      in ${escapeEmailHtml(props.app.name)}.</p>`,
  }));
}
```

| E-Mail-ID                        | Props                                                                              |
| -------------------------------- | ---------------------------------------------------------------------------------- |
| `core.verify-signup`             | `email`, `verifyUrl`                                                               |
| `core.reset-password`            | `email`, `resetUrl`                                                                |
| `core.magic-link`                | `email`, `magicLinkUrl`                                                            |
| `core.change-email-confirmation` | `email`, `newEmail`, `confirmationUrl`                                             |
| `core.change-email-verification` | `email`, `verifyUrl`                                                               |
| `core.organization-invite`       | `invitee`, `orgName`, `inviter`, `acceptUrl`                                       |
| `core.builder-credit-limit`      | `subject`, `heading`, `body`, `upgradeLabel`, `upgradeUrl`                         |
| `core.resource-shared`           | `recipientEmail`, `sender`, `resource` (`type`, `title`, `url`), `role`, `message` |

Jeder Override erhält zusätzlich `app` (`name`, `logoUrl`). Ein zweites Argument
enthält das Standard-Rendering, damit Sie dessen Betreff oder Text
wiederverwenden können.

- Props sind Rohwerte. Maskieren Sie sie mit `escapeEmailHtml`, bevor Sie sie
  in einen HTML-String einsetzen.
- Geben Sie `react` mit einem React-Element statt `html` zurück, um eine
  Komponente zu rendern. React maskiert Props für Sie.
- Lassen Sie `subject` weg, um den Standardbetreff zu behalten. Lassen Sie
  `text` weg, um den Klartext aus Ihrem HTML abzuleiten.
- Wenn ein Override einen Fehler wirft, schlägt der Versand fehl. Das Framework
  fällt nicht auf das Standarddesign zurück. Die Vorschau für
  Transaktions-E-Mails rendert Ihren Override. Prüfen Sie ihn also dort.

## Erweitertes Deployment {#advanced-deployment}

Beginnen Sie mit dem Weg oben. Nutzen Sie diese Seiten, wenn Sie
anbieterspezifische Einstellungen oder Steuerungsmöglichkeiten für die
Produktion brauchen:

- [**Node.js**](/docs/node-js) - das Standard-Server-Preset von Nitro ausführen
- [**Docker**](/docs/docker) - den Node.js-Server in einen Container packen
- [**Vercel**](/docs/vercel), [**Netlify**](/docs/netlify) und [**Cloudflare Workers**](/docs/cloudflare#cloudflare-workers) - gehostete Ziele konfigurieren
- [**SSR-Caching**](/docs/ssr-caching) - den Cache für die öffentliche Shell konfigurieren
- [**Umgebungsvariablen für das Deployment**](/docs/deployment-environment-variables) - Produktions-Secrets, Laufzeit-Flags und Vererbung im Workspace
- [**Zugriff für Produktionsagenten**](/docs/actions-agent-tools) - Framework-Tools und Codeausführung steuern
- [**UI in der Produktion aktualisieren**](/docs/updating-ui-in-production) - den verwalteten Workflow für visuelles Bearbeiten verstehen
