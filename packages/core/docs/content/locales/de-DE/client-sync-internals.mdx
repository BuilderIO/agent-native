# Sync-Interna

[Live Sync](/docs/key-concepts#polling-sync) behandelt das mentale Modell: Ein Agenten-Schreibvorgang wird zu einem Änderungsereignis, `useDbSync()` nimmt es auf, und betroffene Abfragen rufen erneut ab. Diese Seite behandelt den Mechanismus darunter, den die meisten Apps nie direkt anfassen: die Änderungsversionszähler, die `useDbSync()` erhöht, und wie man sie in einen rohen `useQuery()`-Aufruf einbaut, der nicht über `useActionQuery()` läuft.

`useActionQuery()` ruft bereits automatisch erneut ab, wenn eine mutierende Action abschließt (siehe [Daten & Sync](/docs/client-data#fetching-mutating)). Greifen Sie nur zu `useChangeVersion()`/`useChangeVersions()`, wenn Sie einen rohen `useQuery()`-Aufruf außerhalb dieses Pfads synchronisieren, etwa einen niedrigen Client-Helfer, der den Integrationsstatus liest.

## Wie Änderungsversionen funktionieren {#how-it-works}

Wenn eine serverseitige Datenbankmutation auftritt, zeichnet der Server ein Änderungsereignis mit einem `source`-Schlüssel auf. `useDbSync()` empfängt dieses Ereignis und erhöht einen lokalen Zähler für diese Quelle. Das Einbauen des Zählers in einen React-Query-Schlüssel lässt die Abfrage automatisch erneut abrufen, sobald das Backend neue Aktivität für diese Quelle meldet.

Im folgenden Beispiel liest ein roher `useQuery()`-Aufruf direkt ein Dashboard und baut den Versionszähler der Quelle `"dashboards"` in seinen Abfrageschlüssel ein, sodass er erneut abruft, sobald sich diese Quelle ändert:

```tsx
import { useQuery } from "@tanstack/react-query";
import { useChangeVersion } from "@agent-native/core/client/hooks";

function DashboardView({ id }) {
  const version = useChangeVersion("dashboards");

  const { data } = useQuery({
    queryKey: ["dashboard", id, version],
    queryFn: () => fetchDashboard(id),
    placeholderData: (prev) => prev,
  });

  return <div>{data?.title}</div>;
}
```

`placeholderData: (prev) => prev` behält die vorherigen Daten während des erneuten Abrufens auf dem Bildschirm, sodass die Ansicht nicht zu einem Ladezustand flackert.

## Zwei Wege zu einem erneuten Abruf {#latency-models}

Eine Mutation erreicht die UI auf einem von zwei Wegen, und diese haben unterschiedliche Latenz.

Eine lokale Mutation, eine, die Ihr eigener `useActionMutation()`-Aufruf gerade ausgeführt hat, löst bei Erfolg sofort ein `source: "action"`-Ereignis aus. Jede Abfrage, die von dieser Action abhängt, ruft sofort erneut ab. Es gibt keine Roundtrip-Verzögerung, da der Tab, der den Schreibvorgang ausgeführt hat, bereits davon weiß.

Eine entfernte Mutation, vom Agenten, einem Webhook, einem anderen Tab oder einem anderen Benutzer, muss diesen Tab erst erreichen. `useDbSync()` nimmt sie fast sofort über SSE auf, oder über den Polling-Fallback innerhalb von etwa zwei Sekunden, wenn SSE nicht verfügbar ist. Erst wenn dieses Ereignis eintrifft, erhöht sich der entsprechende Versionszähler und die Abfrage ruft im Hintergrund erneut ab.
