# PR Visual Recap

PR Visual Recap ist eine GitHub Action, die jeden Pull Request in ein
**visuelles Code-Review** verwandelt, ohne dass sich jemand merken muss,
einen Befehl von Hand auszuführen. Diese Seite richtet sich an alle, die
diese Action installieren, konfigurieren oder absichern. Bei jedem Push
führt ein LLM-Coding-Agent den aktuellen gebündelten
[`visual-recap`](/docs/template-plan)-Skill aus (oder die committete Kopie
Ihres Repos, wenn `VISUAL_RECAP_SKILL_SOURCE=repo` gesetzt ist) gegen den
PR-Diff, veröffentlicht einen strukturierten Recap-Plan in der gehosteten
Plans-App, zeigt während der Ausführung einen informativen
`Visual Recap`-Check und aktualisiert oder erstellt **einen sticky
PR-Kommentar**, der zum interaktiven Plan verlinkt, mit einem
**eingebetteten Screenshot** direkt im Kommentar.

Dies ist kein deterministischer Diff-Renderer. Die Action ruft einen
echten Coding-Agenten auf (standardmäßig die Claude Code CLI, die OpenAI
Codex CLI oder Agent-Native Code mit einem OpenAI-kompatiblen Anbieter),
der die Änderung liest, entscheidet, was wichtig ist, und den Recap durch
Aufruf des Plans-MCP-Tools `create-visual-recap` verfasst — desselben
Tools, das der `/visual-recap`-Slash-Befehl verwendet. Sie erhalten eine
Schema-/API-/Vorher-Nachher-Ansicht der Änderung aus der
Vogelperspektive statt einer Wand aus rohem Diff.

Der Recap ist **informativ und nicht blockierend**. Er erstellt eine
Check-Zeile, damit Reviewer sehen können, dass die Generierung läuft,
aber er ist kein erforderlicher Check, er blockiert den PR nie und
ersetzt nie das Lesen des tatsächlichen Diffs. Der sticky Kommentar ist
eine Review-Hilfe, kein Freigabe-Nachweis.

## Was es tut

Bei jedem PR-Push macht der Workflow Folgendes:

1. Sammelt einen begrenzten Diff zwischen PR-Base und -Head.
2. Erstellt einen informativen `Visual Recap`-GitHub-Check mit
   `Visual recap in progress`.
3. Führt den konfigurierten Coding-Agenten gegen diesen Diff aus. Der
   Agent liest die gebündelte `visual-recap`-Skill-Anleitung (oder Ihre
   im Repo fixierte Kopie) und verfasst einen Recap, den er mit
   `create-visual-recap` veröffentlicht.
4. Liest die veröffentlichte Plan-URL, die der Agent in `recap-url.txt`
   geschrieben hat.
5. Öffnet diese URL in headless Chrome und macht Screenshots des
   gerenderten Plans im hellen und dunklen Modus.
6. Lädt die PNGs auf eine signierte öffentliche Bild-Route der Plans-App
   hoch.
7. Aktualisiert oder erstellt einen einzigen sticky PR-Kommentar, der
   die Screenshots **inline** mit einem `<picture>`-Element einbettet
   (über GitHubs Camo-Bildproxy ausgeliefert) neben dem Link zum
   interaktiven Recap.
8. Schließt den `Visual Recap`-Check als Erfolg, übersprungen oder
   neutral ab.

## Installation

Wenn Sie Plans interaktiv installieren, fragt die Agent-Native-CLI, ob
automatische PR Visual Recaps hinzugefügt werden sollen. Sagen Sie Ja,
um die GitHub Action zu schreiben, oder fügen Sie sie jederzeit explizit
hinzu:

```bash
npx @agent-native/core@latest skills add visual-plan --with-github-action
```

Dies installiert den `visual-plan`-Skill (der den `visual-recap`-Skill
enthält, den die Action ausführt) und schreibt
`.github/workflows/pr-visual-recap.yml` in Ihr Repo. Der Workflow ruft
**veröffentlichte CLI-Unterbefehle** über
`npx @agent-native/recap-cli@latest recap <subcommand>` auf —
einschließlich `gate`, `collect-diff`, `block-reference`, `scan`,
`build-prompt`, `publish`, `shot`, `comment`, `check` und `usage` —
sodass nichts als Hilfsskript in Ihr Repo kopiert wird. `setup` und
`doctor` sind die interaktiven Hilfsprogramme, die Sie lokal ausführen;
`gate` ist der Sicherheits-Gate-Schritt, den der Workflow vor jedem
Recap ausführt.

Führen Sie dann den geführten Einrichtungshelfer aus:

```bash
npx @agent-native/recap-cli@latest recap setup
npx @agent-native/recap-cli@latest recap doctor
```

`recap setup` aktualisiert den Workflow, verwendet `gh`, um
GitHub-Actions-Secrets/-Variablen zu setzen, wenn Werte aus der
Umgebung oder dem lokalen Plans-Publish-Token-Speicher verfügbar sind,
und gibt exakte fehlende Befehle für alles aus, was es nicht setzen
kann. Secret-Werte werden über stdin an `gh` gesendet, nicht als
Befehlsargumente. Committen Sie die generierte Workflow-Datei und
öffnen Sie einen PR, um sie laufen zu sehen.

Standardmäßig baut der Workflow seinen Agenten-Prompt aus der aktuellen
gebündelten `visual-recap`-Anleitung in `@agent-native/recap-cli@latest`,
einschließlich aller begleitenden Referenzdateien, die der Skill
mitliefert. Wenn Ihr Repo absichtlich seinen committeten
`visual-recap`-Ordner anpasst und fixiert, setzen Sie die
Repository-Variable `VISUAL_RECAP_SKILL_SOURCE=repo`.

## Runner-Auswahl

Der Workflow läuft standardmäßig auf GitHub-gehosteten
`ubuntu-latest`-Runnern. Um einen anderen gehosteten Runner oder Ihren
eigenen selbst gehosteten Runner zu verwenden, setzen Sie die
Repository- oder Organisationsvariable `VISUAL_RECAP_RUNS_ON` auf einen
gültigen JSON-String oder ein JSON-Array von Runner-Labels:

```text
"ubuntu-latest"
["self-hosted", "linux", "x64", "visual-recap"]
```

Die JSON-Anführungszeichen sind erforderlich. Diese Einstellung wählt
den vollständigen `recap`-Job-Runner aus. Um dies während der geführten
Einrichtung zu konfigurieren, übergeben Sie denselben JSON-Wert an
`--runs-on`, und validieren Sie dann den Workflow und die
Runner-Verfügbarkeit mit `doctor`:

```bash
npx @agent-native/recap-cli@latest recap setup --runs-on '["self-hosted","linux","x64","visual-recap"]'
npx @agent-native/recap-cli@latest recap doctor
```

Das leichtgewichtige Sicherheits-Gate verwendet separat standardmäßig
GitHub-gehostete `ubuntu-latest`-Runner. Repositories, die
GitHub-gehostete Runner deaktivieren, können `VISUAL_RECAP_GATE_RUNS_ON`
auf **ein einzelnes, einfaches Runner-Label** setzen (kein JSON), oder
während der Einrichtung `--gate-runs-on visual-recap-gate` übergeben.
Der wiederverwendbare Workflow stellt denselben Wert als
`gate-runs-on`-Eingabe bereit. Dies vermeidet das Parsen von dynamischem
JSON, bevor GitHub das Gate planen kann. Das benutzerdefinierte Label
wird nur für PRs desselben Repositorys ausgewählt, die von einem
`OWNER`, `MEMBER` oder `COLLABORATOR` verfasst wurden. Forks und alle
anderen Autoren werden vor Jobstart auf GitHub-gehostete
`ubuntu-latest`-Runner gezwungen; in einem rein selbst gehosteten Repo
bleiben diese nicht vertrauenswürdigen Läufe möglicherweise
ungeplant, statt eine selbst gehostete Maschine zu berühren.

`recap doctor` weist fehlerhaftes oder nicht unterstütztes JSON zurück
und meldet, wenn GitHub keinen Online-Runner bereitstellt, der jedem
konfigurierten Label entspricht. Runner-Registrierung, -Installation,
-Upgrades, -Kapazität und -Wartung bleiben Ihre Verantwortung;
Agent-Native wählt die Labels aus, stellt den Runner aber weder bereit
noch betreibt es ihn.

**Sicherheit:** Bevorzugen Sie dedizierte, ephemere selbst gehostete
Runner. Ein benutzerdefinierter Gate-Runner erhält nur vertrauenswürdige
PR-Events desselben Repositorys. Das Standard-Gate checkt den PR-Baum
nicht aus; es wertet die Workflow-Logik und die GitHub-PR-Metadaten
aus. Eine dauerhafte Maschine behält den Prozesszustand dennoch über
Jobs hinweg bei, teilen Sie sie also nicht mit unabhängigen
Workloads. Der Workflow schlägt fehl, bevor er einen selbst gehosteten
Gate- oder vollständigen Recap-Job für nicht vertrauenswürdige
öffentliche oder Fork-PR-Autoren auslöst. Schwächen Sie diese Grenze
nicht ab und leiten Sie nicht vertrauenswürdige Beiträge nicht auf
einen dauerhaften Runner um.

## Backend-Auswahl

Wählen Sie mit der Repository-Variable `VISUAL_RECAP_AGENT`, welcher
Coding-Agent den Skill ausführt:

| `VISUAL_RECAP_AGENT` | Coding-Agent                            | Erforderlicher API-Schlüssel | Erforderliche Variablen                       |
| --------------------- | --------------------------------------- | ----------------------- | --------------------------------------------- |
| `claude` _(Standard)_ | Claude Code CLI                         | `ANTHROPIC_API_KEY`     | —                                              |
| `codex`               | OpenAI Codex CLI                        | `OPENAI_API_KEY`        | —                                              |
| `openai-compatible`   | Agent-Native Code + kompatibler Anbieter | `VISUAL_RECAP_API_KEY`  | `VISUAL_RECAP_BASE_URL`, `VISUAL_RECAP_MODEL` |

Wenn die Variable nicht gesetzt ist, verwendet die Action `claude`.

## Modell und Reasoning

Über das Backend hinaus stimmen diese Repository-Variablen ab, wie der
Agent läuft:

- **`VISUAL_RECAP_MODEL`** fixiert das an die CLI übergebene Modell
  (`--model`) — zum Beispiel `gpt-5.6-luna` für Codex, eine
  Claude-Modell-ID oder `deepseek-chat` für DeepSeek. Es ist für
  `openai-compatible` erforderlich. Für das **Claude**-Backend
  verwendet das Nichtsetzen jetzt standardmäßig `claude-sonnet-5`;
  setzen Sie die Variable explizit, um ein anderes Claude-Modell zu
  verwenden, etwa das günstigere `claude-haiku-4-5`. Für das
  **Codex**-Backend verwendet das Nichtsetzen das eigene
  Standardmodell der Codex-CLI.
- **`VISUAL_RECAP_REASONING`** setzt die Reasoning-Tiefe: `none`,
  `minimal`, `low`, `medium`, `high` oder `xhigh`. Sie gilt für das
  Codex-Backend; Claudes Reasoning ist modellgesteuert, sodass diese
  Variable dort ignoriert wird.
- **`VISUAL_RECAP_BASE_URL`** wählt die HTTP(S)-Basis-URL für das
  `openai-compatible`-Backend aus. Verwenden Sie den
  OpenAI-kompatiblen Endpunkt des Anbieters, etwa DeepSeek oder Kimi,
  ohne Zugangsdaten in die URL einzubetten.
- **`VISUAL_RECAP_SKILL_SOURCE`** steuert die Aktualität des Prompts:
  `auto`/nicht gesetzt verwendet die aktuelle gebündelte
  Skill-Anleitung, während `repo` den committeten repo-lokalen
  `visual-recap`-Skill-Ordner fixiert.

Um zum Beispiel den Recap auf Codex mit GPT-5.6 Sol bei hohem Reasoning
auszuführen, setzen Sie die Repository-Variablen
`VISUAL_RECAP_AGENT=codex`, `VISUAL_RECAP_MODEL=gpt-5.6-sol` und
`VISUAL_RECAP_REASONING=high`.

Für DeepSeek setzen Sie `VISUAL_RECAP_AGENT=openai-compatible`,
`VISUAL_RECAP_BASE_URL=https://api.deepseek.com/v1`,
`VISUAL_RECAP_MODEL=deepseek-chat` und das Secret
`VISUAL_RECAP_API_KEY`. Kimi funktioniert genauso mit seiner
OpenAI-kompatiblen Basis-URL und Modell-ID. Andere OpenAI-kompatible
Anbieter verwenden dieselben drei Einstellungen.

## Kosten

Jeder Recap-Lauf ist eine vollständige agentische
Coding-Agent-Sitzung, die einen echten Diff liest, keine billige
schablonenhafte Zusammenfassung, sodass ihre Kosten der Modellwahl und
der Häufigkeit der Ausführung folgen:

- **Eine vollständige Sitzung pro PR-Push.** Der Standard-Trigger löst
  bei `synchronize` aus, sodass ein PR, der zehnmal gepusht wird, den
  Agenten zehnmal ausführt.
- **Der gesamte PR jedes Mal**, nicht nur die Commits seit dem letzten
  Lauf — die Kosten skalieren mit der Gesamt-PR-Größe, nicht mit der
  inkrementellen Diff-Größe.
- **Diff-Eingabe auf ~600 KB begrenzt.** Dies begrenzt den
  schlimmsten Fall pro Lauf, aber große Diffs kosten dennoch spürbar
  mehr als kleine.
- **Ein automatischer Wiederholungsversuch bei Fehlschlag**, der die
  Kosten eines Laufs, der vorübergehend fehlschlägt, ungefähr
  verdoppeln kann.

So senken Sie die Kosten:

- **Fixieren Sie ein günstigeres Modell.** Setzen Sie für Claude
  `VISUAL_RECAP_MODEL=claude-haiku-4-5` für einfache oder kleine Repos
  — es ist die günstigste Claude-Stufe; `claude-sonnet-5` (der
  Standard) ist die ausgewogene Stufe.
- **Wechseln Sie zu Codex mit einem günstigeren Modell.** Setzen Sie
  `VISUAL_RECAP_AGENT=codex` mit `VISUAL_RECAP_MODEL=gpt-5.6-luna` (die
  günstigste GPT-5.6-Stufe) oder `gpt-5.6-terra` (mittlere Stufe), und
  setzen Sie `VISUAL_RECAP_REASONING=low`, um die Ausgaben für
  Reasoning-Token weiter zu senken. Die Reasoning-Tiefe gilt nur für
  Codex.
- **Zielen Sie auf einen günstigeren OpenAI-kompatiblen Anbieter.**
  Setzen Sie `VISUAL_RECAP_AGENT=openai-compatible` mit
  `VISUAL_RECAP_BASE_URL`/`VISUAL_RECAP_MODEL`/`VISUAL_RECAP_API_KEY`,
  gerichtet auf DeepSeek, Kimi oder einen anderen
  OpenAI-kompatiblen Endpunkt.
- **Verlangen Sie ein explizites PR-Label.** Setzen Sie
  `VISUAL_RECAP_REQUIRED_LABELS=visual recap`, um den Workflow
  installiert zu halten, aber Recaps zu überspringen, bis ein PR
  dieses Label hat. Verwenden Sie eine kommagetrennte Liste, etwa
  `visual recap,recap`, wenn mehrere Labels opt-in ermöglichen sollen.
  Das Anwenden eines gelisteten Labels weckt den Workflow sofort.
- **Recap seltener ausführen.** Bearbeiten Sie
  `on.pull_request.types` des installierten Workflows von
  `[opened, synchronize, reopened, ready_for_review, labeled, closed]`
  zu `[opened, ready_for_review, closed]`, damit er nur recappt, wenn
  ein PR eröffnet wird und wenn er gemergt wird, statt bei jedem
  Push.

Jeder Lauf zeichnet auf, was er tatsächlich ausgegeben hat: Der Schritt
`recap usage` des Workflows hängt Token- und Kostenverbrauch an den
veröffentlichten Plan an, sodass Sie die tatsächlichen Ausgaben pro
Lauf ansehen können, statt zu raten.

## Secrets und Variablen {#secrets-and-variables}

Setzen Sie diese unter **Settings → Secrets and variables → Actions**
Ihres Repositorys.

### Secrets für das Standard-Backend

| Secret              | Zweck                                                                                                                              |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `PLAN_RECAP_TOKEN`  | Widerrufbares Token, geprägt von `npx @agent-native/core@latest connect`. Autorisiert das Veröffentlichen des Recap-Plans und den Screenshot-Upload. |
| `ANTHROPIC_API_KEY` | Der LLM-Schlüssel für das Standard-Backend Claude Code.                                                                              |

**Teams: verwenden Sie ein Org-Service-Token.** Ein persönliches Token
ist an die Person gebunden, die es geprägt hat — wenn sie die Org
verlässt oder ihre Token widerruft, beginnen alle Repos, die dieses
Secret verwenden, mit 401ern zu scheitern, und von CI erstellte Pläne
gehören dieser Einzelperson statt dem Team. Ein Org-Service-Token
gehört Ihrer **Organisation**: Es agiert als Service-Principal
(`svc-<name>@service.<orgId>`), überlebt jeden individuellen Austritt,
die von ihm veröffentlichten Recaps sind org-weit sichtbar, und jeder
Org-Owner oder -Admin kann es auflisten oder widerrufen. Prägen Sie
eines (nur Org-Owner/-Admin):

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --service-token pr-recap
```

Der Befehl authentifiziert Sie im Browser und gibt dann das
Service-Token genau einmal aus — speichern Sie es als Secret
`PLAN_RECAP_TOKEN`. Verwalten Sie es später mit den Actions
`list-org-service-tokens` und `revoke-org-service-token` der
Plans-App.

**Solo: Ein persönliches Token funktioniert weiterhin.** Prägen Sie es
mit `npx @agent-native/core@latest connect` gegen Ihre Plans-App. Für
die gehostete App schreibt dies auch eine lokale
Publish-Token-Datei, die
`npx @agent-native/recap-cli@latest recap setup` lesen kann:

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --client codex
npx @agent-native/recap-cli@latest recap setup
```

Wenn Sie die manuelle Einrichtung bevorzugen, fügen Sie das Token in
das GitHub-Secret ein. Verwenden Sie einen Platzhalter wie
`plan_recap_xxxxxxxxxxxxxxxx` nur für Beispiele — committen Sie nie ein
echtes Token.

## Eingebetteter Screenshot im Kommentar

Nachdem der Agent den Recap veröffentlicht hat, macht der Workflow
Screenshots des gerenderten Plans in headless Chrome sowohl im hellen
als auch im dunklen Modus und lädt die PNGs auf eine signierte
öffentliche Bild-Route der Plans-App hoch. Der sticky PR-Kommentar
bettet diese Screenshots dann **inline** mit einem `<picture>`-Element
ein — GitHub liefert sie über seinen Camo-Proxy erneut aus, sodass
Reviewer direkt im Kommentar eine Vorschau sehen, die zu ihrem
GitHub-Theme passt, ohne irgendetwas zu öffnen. Der Link zum
vollständigen interaktiven Plan sitzt direkt daneben für den Fall, dass
sie erkunden, kommentieren oder annotieren möchten.

## Fork-PRs

### Standardverhalten (keine Aktion erforderlich)

Der Haupt-Workflow `pr-visual-recap.yml` löst beim einfachen
`pull_request`-Trigger aus, **nicht** bei `pull_request_target`.
Fork-PRs laufen daher **ohne Zugriff auf Repository-Secrets**, sodass
der Workflow kein `PLAN_RECAP_TOKEN` findet und sauber zu einem No-op
wird — kein fehlgeschlagenes Veröffentlichen, keine offengelegten
Zugangsdaten. Recaps laufen automatisch für PRs aus Branches im
selben Repository, wo die Secrets verfügbar sind.

Das bedeutet auch, dass Sie die Workflow-Datei mergen können, **bevor**
die Secrets existieren: Ohne konfiguriertes Token ist jeder Lauf ein
stiller No-op, bis Sie die Secrets setzen. Der `gate`-Schritt
überspringt auch automatisch Draft-PRs und von Bots verfasste PRs,
sodass keines von beiden standardmäßig Recap-Läufe auslöst.

### Opt-in mit dem label-gesteuerten Fork-Workflow

Wenn Sie Recaps für Fork-PRs generieren möchten, ist eine zweite
Workflow-Datei verfügbar: `.github/workflows/pr-visual-recap-fork.yml`.
Sie verwendet `pull_request_target` (das mit Base-Repo-Secrets läuft),
checkt aber nie Fork-Code aus und führt ihn nie aus. Vertrauenswürdige
Fork-Autoren mit der GitHub-Autorenzugehörigkeit `OWNER`, `MEMBER` oder
`COLLABORATOR` laufen automatisch. Externe Fork-PRs benötigen ein
explizites **Opt-in pro Head durch einen Maintainer** über ein
frisches `recap`-Label-Event, bevor der Recap-Agent läuft.

Um sie zu installieren, kopieren Sie die Datei von
[BuilderIO/agent-native](https://github.com/BuilderIO/agent-native/blob/main/.github/workflows/pr-visual-recap-fork.yml)
in das Verzeichnis `.github/workflows/` Ihres Repos, neben dem
bestehenden `pr-visual-recap.yml`. Dieselbe Backend-Konfiguration gilt,
einschließlich `VISUAL_RECAP_API_KEY`, `VISUAL_RECAP_BASE_URL` und
`VISUAL_RECAP_MODEL`, wenn ein OpenAI-kompatibler Anbieter verwendet
wird.

### Wie das Label-Gate funktioniert

1. Ein Fork-Mitwirkender öffnet einen PR. Der normale
   `pull_request`-Workflow überspringt, weil GitHub Fork-Läufen
   Secrets vorenthält.
2. Der Fork-Workflow prüft die Autorenzugehörigkeit des PRs.
   Vertrauenswürdige Autoren (`OWNER`, `MEMBER` oder `COLLABORATOR`)
   laufen automatisch bei Open-, Synchronize-, Reopen- und
   Ready-for-Review-Events.
3. Externe Mitwirkende benötigen einen Maintainer, der den aktuellen
   Diff überprüft (besonders bei Inhalten, die wie Prompt-Injection
   aussehen — siehe unten), und dann das Label `recap` auf den PR
   anwendet.
4. Das Label-Gate für externe Mitwirkende gilt pro Head-SHA: Wenn der
   Mitwirkende weitere Commits pusht, überspringt das nächste
   Synchronize-Event, bis ein Maintainer `recap` entfernt und nach
   Überprüfung des neuen Diffs erneut anwendet.

### Was der Fork-Workflow tut und was NICHT

| Der Workflow TUT                                                                                                      | Der Workflow tut NICHT                                                              |
| ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Das **Base-Repository** am **Base-Branch-Ref** auschecken — nur vertrauenswürdiger Code                                | Irgendwelchen Code aus dem Fork auschecken oder ausführen                             |
| Den Fork-Head als Remote-Ref abrufen (`git fetch origin pull/<n>/head:refs/recap/fork-head`) — Commits abzurufen ist sicher | Pakete aus dem Fork installieren, Fork-Skripte ausführen oder Fork-Inhalte als Code auswerten |
| `git diff base...refs/recap/fork-head` ausführen — reiner Text-Diff zweier bereits abgerufener Objekte                 | Den Diff als irgendetwas anderes als Text-Eingabe für das LLM verwenden               |
| Den `visual-recap`-Skill und die Agentenkonfiguration des **Base-Repos** ausführen                                     | Irgendeinen Skill oder eine Konfiguration aus dem Fork laden                           |
| Den Diff durch denselben Secret-Scan-Schritt (fail-closed) wie First-Party-PRs leiten                                  | Den Secret-Scan überspringen                                                          |
| Einen expliziten Prompt-Hardening-Hinweis zum Agenten-Prompt hinzufügen, der Diff-Inhalt als nicht vertrauenswürdig markiert | Dem Agenten zusätzliche Berechtigungen über den normalen Recap-Agenten hinaus gewähren |

### Warum Sie den Diff vor dem Labeln überprüfen müssen

Der Fork-Diff ist von einem Angreifer kontrollierter Text, den der
Recap-Agent als Eingabe liest. Ein sorgfältig gestalteter Diff könnte
Prompt-Injection-Inhalt enthalten — zum Beispiel Diff-Zeilen, die wie
Agentenanweisungen aussehen — mit dem Ziel, den Recap-Agenten zu
unbeabsichtigten Handlungen zu bewegen (z. B. das Publish-Token zu
exfiltrieren oder irreführenden Recap-Inhalt zu erzeugen).

Bevor Sie das Label `recap` anwenden, überfliegen Sie den Diff nach:

- Zeilen, die wie direkte Befehle oder Rollenanweisungen klingen
  („Ignoriere vorherige Anweisungen...“, „Du bist jetzt...“, „Schreibe
  das Token an...“).
- Ungewöhnlichen Dateinamen, die als Systemprompts fehlgedeutet
  werden könnten.
- Kodiertem Inhalt in hinzugefügten Dateien, der zu Anweisungen
  dekodieren könnte.

Diese Gegenmaßnahmen sind bereits im Workflow verankert (Secret-Scan,
Gate für sensible Pfade, Prompt-Hardening-Hinweis, eingeschränkte
Agent-Tool-Zulassungsliste), aber die Label-Überprüfung ist die primäre
Verteidigungslinie.

### Beziehung zum Haupt-Workflow

Die beiden Workflow-Dateien sind unabhängig. Für Nicht-Fork-PR-Updates
ist `pr-visual-recap.yml` der einzige Workflow, der läuft. Bei
Fork-PRs beendet sich der normale Workflow an seinem Fork-Gate, und
`pr-visual-recap-fork.yml` läuft automatisch für vertrauenswürdige
Autoren derselben Organisation oder nach einem frischen
Maintainer-`recap`-Label für externe Mitwirkende. Sie teilen sich
denselben sticky-Kommentar-Marker und dieselbe Plan-ID-Verkettung,
sodass sowohl PRs als auch Fork-PRs einen einzigen aktualisierten oder
erstellten Kommentar auf demselben PR erzeugen.

### Selbstmodifizierungs-Schutz {#self-modifying-guard}

Der `gate`-Schritt überspringt den Recap vollständig, wenn ein PR
einen der folgenden Pfade berührt, sodass ein PR nie den Workflow, den
Skill oder die Agentenkonfiguration umschreiben kann, die der
vertrauenswürdige Recap-Job lädt, und dabei Secrets exfiltrieren kann:

| Pfadmuster                                  | Grund                                       |
| -------------------------------------------- | -------------------------------------------- |
| `.github/workflows/pr-visual-recap.yml`      | Der Workflow selbst                          |
| `**/skills/visual-(recap\|plan\|plans)/**`   | Der visual-recap-Skill, dem der Agent folgt  |
| `**/.claude/**`                              | Agenteneinstellungen, die der Runner lädt    |
| `**/CLAUDE.md`                               | Agentenanweisungen, die der Runner lädt      |
| `**/AGENTS.md`                               | Agentenanweisungen, die der Runner lädt      |
| `**/.mcp.json`                               | MCP-Server-Konfiguration, die der Runner lädt |

Im Monorepo `BuilderIO/agent-native` führt der Workflow die
Recap-CLI aus vertrauenswürdiger Base-Branch-Quelle statt aus
PR-Head-Quelle aus. Das hält normale Paketänderungen, einschließlich
`packages/core/**`, für Recaps berechtigt, ohne von PR modifizierten
CLI-Code auszuführen.

## Local-Files-Datenschutzmodus

Die GitHub Action ist für gehostetes, teilbares PR-Review konzipiert.
Wenn Sie einen Recap möchten, ohne Recap-Inhalt an die
Agent-Native-Plan-Datenbank zu senden, führen Sie stattdessen denselben
Helfer-Flow lokal im Local-Files-Modus aus:

```bash
npx @agent-native/recap-cli@latest recap collect-diff --base main --head HEAD --out recap.diff --stat recap.stat
npx @agent-native/recap-cli@latest recap scan --diff recap.diff
npx @agent-native/recap-cli@latest recap build-prompt --pr 123 --diff recap.diff --stat recap.stat --local-files --local-dir plans/pr-123-visual-recap
```

Geben Sie das generierte `recap-prompt.md` an Ihren Coding-Agenten. Im
Local-Files-Modus weist der Prompt den Agenten an,
`plans/pr-123-visual-recap/plan.mdx` plus optionale visuelle Dateien zu
schreiben und dann auszuführen:

```bash
npx @agent-native/core@latest plan local serve --dir plans/pr-123-visual-recap --kind recap --open
```

Die zurückgegebene URL öffnet die gehostete Plan-UI, während der
Browser das Recap-MDX aus einer lokalen Bridge liest. Recap-Inhalte
werden nicht in die gehostete Plan-Datenbank geschrieben, und die URL
funktioniert nur auf der Maschine, auf der die Bridge läuft. Wenn Sie
die Plan-App lokal mit demselben `PLAN_LOCAL_DIR` betreiben, ist die
Route `/local-plans/pr-123-visual-recap` ebenfalls gültig.
Repo-gestützte Ordner können als
`/local-plans/pr-123-visual-recap?path=plans%2Fpr-123-visual-recap`
geöffnet werden. Dieser Modus deaktiviert den gehosteten sticky
PR-Kommentar, den eingebetteten Screenshot-Upload, das Anhängen der
Nutzung und Browser-Kommentare, bis Sie explizit veröffentlichen.

## Es ist informativ, kein Gate

Der Recap ist eine Review-Hilfe, die über den normalen PR-Flow gelegt
wird:

- Er zeigt eine `Visual Recap`-Check-Zeile zur Sichtbarkeit, ist aber
  **nie ein erforderlicher Check** und blockiert nie das Mergen.
- Ein Fehler bei Generierung oder Veröffentlichung schließt neutral ab
  und erscheint als erklärender sticky Kommentar, nicht als rotes X
  auf nicht zusammenhängendem Code.
- Der Recap und sein Screenshot **implizieren nicht, dass der Diff
  überprüft wurde**. Reviewer müssen weiterhin die tatsächlich
  geänderten Zeilen lesen.

## Versionsfixierung (Copy-Variante) {#version-pinning-copy-variant}

Standardmäßig installiert der Copy-Varianten-Workflow
`@agent-native/recap-cli@latest` zur Laufzeit, sodass jeder Recap-Lauf
automatisch die neueste CLI übernimmt. Wenn Ihre CI reproduzierbares
Tooling benötigt, setzen Sie die Repository-Variable
**`RECAP_CLI_VERSION`**, um die installierte Version zu fixieren:

1. Gehen Sie zu **Settings → Secrets and variables → Actions →
   Variables** Ihres Repos.
2. Erstellen Sie eine Variable namens `RECAP_CLI_VERSION` mit einem
   Wert wie `1.5.0`.

Die Variable ist optional. Lassen Sie sie nicht gesetzt (oder setzen
Sie sie auf `latest`), um dem neuesten Release zu folgen.

Für die wiederverwendbare Caller-Variante verwenden Sie stattdessen die
Eingabe `cli-version` (siehe [Versionsfixierung](#version-pinning) im
Abschnitt zur wiederverwendbaren Variante).

## Secret-Scan-Zulassungsliste

Vor dem Veröffentlichen eines Recaps führt der Workflow
`npx @agent-native/recap-cli@latest recap scan` aus, um
wahrscheinliche Secrets im Diff zu erkennen. Jeder PR, dessen Diff
einem bekannten Secret-Muster entspricht, wird mit einem erklärenden
Kommentar blockiert — der Recap wird nicht veröffentlicht, und kein
Diff-Inhalt wird an den Coding-Agenten gesendet.

In seltenen Fällen hat ein Repo absichtliche Test-Fixtures oder
Nicht-Secret-Strings, die Secret-Mustern oberflächlich ähneln (z. B.
ein Fixture-Schlüssel in einer Testdatei). Um einen falsch-positiven
Treffer zu unterdrücken, erstellen Sie
`.github/recap-scan-allowlist` im Wurzelverzeichnis Ihres Repositorys.

### Format

Jede nicht-leere, nicht-kommentierte Zeile ist entweder ein
**literaler Teilstring** oder ein **`/regex/flags`**-Muster:

```
# Lines starting with # are comments.

# Literal substring — any diff line containing this string is allowed.
sk-test-fixture1234567890abcdef

# Regex pattern — written as /pattern/flags (JS syntax).
/^.STRIPE_KEY=sk-test-/i

# Another literal.
EXAMPLE_API_KEY=placeholder-value
```

Regeln:

- Eine Zeile wird **unterdrückt** (erlaubt), wenn sie das Literal
  enthält, oder wenn die gesamte Zeile dem Regex entspricht.
- Die Datei ist **fail-closed**: Wenn sie fehlt, gelten keine
  Unterdrückungen — der Scanner verhält sich wie zuvor.
- Eine leere Datei entspricht keiner Datei.
- Fehlerhafte Regex-Zeilen werden als literale Strings behandelt.

Die Zulassungsliste wird nur vom Secret-Scan-Gate konsultiert. Sie
beeinflusst nicht, was der Coding-Agent lesen kann — wenn das Gate
passiert, erhält der Agent den vollständigen Diff unabhängig davon.

## Als wiederverwendbaren Workflow übernehmen

### Warum die wiederverwendbare Variante verwenden?

Der Standard-Installer kopiert die vollständige ~360-zeilige
Workflow-YAML in Ihr Repo (die **Copy**-Option). Dies ist die richtige
Wahl für abgeschottete Repos oder Repos, die jede Zeile dessen prüfen
müssen, was läuft. Der Nachteil ist, dass Fehlerbehebungen und
Verbesserungen Sie nie erreichen — Sie müssen
`npx @agent-native/recap-cli@latest recap setup` nach jedem Release
manuell erneut ausführen.

Die **wiederverwendbare** Option schreibt stattdessen einen dünnen
~20-zeiligen Caller. Er delegiert über `uses:` an
`BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml`.
Jeder Caller übernimmt automatisch die neueste Logik, wenn der Workflow
läuft, ohne lokale Aktualisierung.

|                                     | Copy (Standard)              | Wiederverwendbar                |
| ------------------------------------ | ----------------------------- | --------------------------------- |
| Workflow-Größe in Ihrem Repo         | ~360 Zeilen                   | ~20 Zeilen                        |
| Übernimmt Fixes automatisch          | Nein — `recap setup` erneut ausführen | Ja                          |
| Air-Gap / vollständige Prüfbarkeit   | Ja                             | Nein                               |
| Auf bestimmte Version fixierbar      | Nur durch lokales Bearbeiten  | Ja — `@v1.2.3` in `uses:` setzen |

### Caller-Snippet

Dies ist, was
`npx @agent-native/recap-cli@latest recap setup --reusable` schreibt
(oder Sie können es manuell einfügen):

```yaml
name: PR Visual Recap

# Thin caller — the full workflow logic lives in BuilderIO/agent-native.
# Fixes and improvements reach this repo automatically on each run.
# To pin a specific version for reproducibility replace '@main' with a
# tag or SHA, e.g. '@v1.2.3' or '@abc1234'.

on:
  pull_request:
    types: [opened, synchronize, reopened, ready_for_review, labeled, closed]

jobs:
  visual-recap:
    if: github.event.action != 'labeled' || vars.VISUAL_RECAP_REQUIRED_LABELS != ''
    permissions:
      actions: write
      contents: read
      checks: write
      issues: write
      pull-requests: write
    uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@main
    secrets:
      PLAN_RECAP_TOKEN: ${{ secrets.PLAN_RECAP_TOKEN }}
      ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
      OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
      VISUAL_RECAP_API_KEY: ${{ secrets.VISUAL_RECAP_API_KEY }}
      PLAN_RECAP_APP_URL: ${{ secrets.PLAN_RECAP_APP_URL }}
    with:
      agent: ${{ vars.VISUAL_RECAP_AGENT || 'claude' }}
      model: ${{ vars.VISUAL_RECAP_MODEL || '' }}
      base-url: ${{ vars.VISUAL_RECAP_BASE_URL || '' }}
      reasoning: ${{ vars.VISUAL_RECAP_REASONING || '' }}
      skill-source: ${{ vars.VISUAL_RECAP_SKILL_SOURCE || 'auto' }}
      runs-on: ${{ vars.VISUAL_RECAP_RUNS_ON || '"ubuntu-latest"' }}
      gate-runs-on: ${{ vars.VISUAL_RECAP_GATE_RUNS_ON || 'ubuntu-latest' }}
      required-labels: ${{ vars.VISUAL_RECAP_REQUIRED_LABELS || '' }}
      # cli-version: "latest"  # pin to a specific @agent-native/recap-cli version
```

Dieselben Secrets und Variablen, die unter
[Secrets und Variablen](#secrets-and-variables) beschrieben sind,
gelten auch hier — setzen Sie sie in Ihren Repo-Einstellungen genauso
wie für die Copy-Variante. Der wiederverwendbare Caller leitet
`VISUAL_RECAP_RUNS_ON` über seine JSON-Eingabe `runs-on` für den
vollständigen Recap-Job weiter, `VISUAL_RECAP_GATE_RUNS_ON` über seine
Eingabe `gate-runs-on` mit einfachem Label für das nur
metadatenbasierte Gate, und `VISUAL_RECAP_REQUIRED_LABELS` über
`required-labels` für optionales PR-Label-Gating. Die
Gate-Runner-Eingabe wird nur für vertrauenswürdige Autoren desselben
Repositorys verwendet; andere PRs verwenden GitHub-gehostete
`ubuntu-latest`-Runner. Das Weglassen der Runner-Eingaben bewahrt ihre
`ubuntu-latest`-Standardwerte; das Weglassen erforderlicher Labels
bewahrt das automatische Recap-Verhalten.

### Installation über die CLI

```bash
# Write the thin caller instead of the full copy:
npx @agent-native/recap-cli@latest recap setup --reusable

# Or with a pinned ref for reproducibility:
npx @agent-native/recap-cli@latest recap setup --reusable --ref v1.2.3
```

Beide Varianten schreiben den Workflow nach
`.github/workflows/pr-visual-recap.yml`. Wenn dort bereits ein
Workflow existiert und sich unterscheidet, verweigert der Befehl und
weist Sie an, `--force` zum Überschreiben zu übergeben.

Führen Sie nach dem Schreiben wie üblich
`npx @agent-native/recap-cli@latest recap doctor` aus, um zu
bestätigen, dass die Secrets konfiguriert sind.

### Versionsfixierung {#version-pinning}

Standardmäßig referenziert der Caller `@main`, das immer die neueste
veröffentlichte Version des wiederverwendbaren Workflows verwendet.
Für Produktions-Repos, die reproduzierbare CI benötigen, fixieren Sie
auf ein Tag oder eine SHA:

```yaml
uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@v1.2.3
```

Die Eingabe `cli-version` steuert, welche Version von
`@agent-native/recap-cli` innerhalb des Workflows läuft — lassen Sie
sie bei `"latest"`, um dem neuesten Release zu folgen, oder fixieren
Sie sie auf einen Versionsstring (z. B. `"1.5.0"`) für vollständige
Reproduzierbarkeit.

### workflow_call-Ereigniskontext

`workflow_call`-Workflows erben den Ereigniskontext des **Callers**.
Der wiederverwendbare Workflow verwendet
`github.event.pull_request.*`-Ausdrücke, um die PR-Nummer, Head-SHA,
Base-SHA, Merge-Zeitstempel und PR-Metadaten zu lesen — diese
funktionieren nur korrekt, wenn der Caller bei `pull_request` auslöst.
Das obige Caller-Snippet enthält bereits die korrekten Event-Typen. Das
`closed`-Event ist enthalten, damit gemergte PR-Recaps mit `merged_at`
gestempelt und später als versendete Arbeit durchsucht werden können.

Lösen Sie den Caller nicht bei `workflow_dispatch` oder `push` aus —
diese Events tragen keine `pull_request`-Payload, und das Gate
überspringt den Recap mit „no pull_request payload“.
