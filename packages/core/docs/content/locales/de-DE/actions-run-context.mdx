# Ausführungskontext

`run` erhält ein optionales zweites Argument, `ctx`, das die aufgelöste Anfrageidentität und die Oberfläche trägt, die die Action aufgerufen hat. Lesen Sie es, statt `getRequestUserEmail()` / `getRequestOrgId()` von Hand aufzurufen, und übergeben Sie das gesamte `ctx` an das Tracking:

```ts
export default defineAction({
  description: "Log an audit entry for the current request.",
  schema: z.object({ event: z.string() }),
  run: async (args, ctx) => {
    // ctx is undefined-safe: a 1-arg `run(args)` is still valid.
    const actor = ctx?.userEmail ?? "system";
    if (ctx?.caller === "frontend") {
      // tighter rules for browser-initiated calls, looser for "tool"/"cli"
    }
    await db.insert(audit).values({
      actor,
      orgId: ctx?.orgId ?? null,
      source: ctx?.caller ?? "unknown",
      event: args.event,
    });
    return { ok: true };
  },
});
```

Die meisten Actions lesen nur `ctx?.userEmail` und `ctx?.orgId`, das [Zugriffskontroll-Scoping](/docs/actions-access-control#access-control), das in nahezu jeder echten Action verwendet wird. Der Rest dieser Seite behandelt Querschnittsbelange wie Tracking und Automatisierungs-Attribution, die weniger Actions brauchen.

## Das Argument `ctx` {#ctx}

`ctx` trägt zwei Arten von Informationen: die aufgelöste Anfrageidentität (`userEmail`, `orgId`), die bei nahezu jedem Aufruf vorhanden ist, und Metadaten über die Oberfläche, die die Action aufgerufen hat (`caller`, plus oberflächenspezifische Felder wie `threadId` oder `automation`, die nur für bestimmte Aufrufer befüllt werden). `run()` bleibt abwärtskompatibel: bestehende 1-Argument-Handler und Handler, die nur `{ send }` destrukturieren, funktionieren weiterhin unverändert.

### Die Union `caller` {#caller}

`caller` ist die Union `"tool" | "http" | "frontend" | "cli" | "mcp" | "a2a" | "automation"`:

| `caller`       | Gesetzt, wenn…                                                                                                                                                                                                                |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `"tool"`       | Die In-App-Agentenschleife, ein Sub-Agent oder ein Agent-Team, oder die A2A-Delegation über natürliche Sprache app-übergreifend, die dieselbe Agentenschleife antreibt, sodass ihre Tool-Aufrufe `"tool"` sind.               |
| `"frontend"`   | Ein Browser-Aufruf über `useActionMutation()`, `useActionQuery()` oder `callAction()` (markiert mit dem Header `X-Agent-Native-Frontend: 1`).                                                                                 |
| `"http"`       | Ein reiner programmatischer `POST` oder `GET` an `/_agent-native/actions/<name>` ohne die Frontend-Markierung.                                                                                                                |
| `"cli"`        | `pnpm action <name>` (der CLI-Runner).                                                                                                                                                                                        |
| `"mcp"`        | Ein externer Agent über den MCP-Endpunkt `tools/call`.                                                                                                                                                                        |
| `"a2a"`        | Ein direkter HTTP-Aufruf an `/_agent-native/actions/<name>` mit einem signierten A2A-Delegationstoken. Dies ist ein explizit exponierter, app-übergreifender Dispatch, getrennt vom natürlichsprachlichen `"tool"`-Pfad oben. |
| `"automation"` | Eine ereignisausgelöste Automatisierung, ausgelöst von einem gespeicherten Workspace-Trigger. `ctx.automation` trägt die Trigger-Abstammung. Siehe [Automatisierungen](/docs/automations).                                    |
