# Arbeitsbereichsbereitstellung

Wenn Ihr Projekt ein [Arbeitsbereich](/docs/multi-app-workspace) mit mehr als einer App ist, können Sie jede App auf einem einzigen Ursprung bereitstellen, statt separate Bereitstellungen pro App zu verwalten. Diese Seite behandelt den verwalteten Ein-Befehl-Pfad und eine selbstgehostete Docker-Compose-Alternative. Wählen Sie zuerst unter [Bereitstellung](/docs/deployment) eine Datenbank, eine Voreinstellung und eine Plattform.

## Ein Ursprung, viele Apps {#workspace-deploy}

Stellen Sie jede App in einem Arbeitsbereich mit einem einzigen Befehl auf einem Ursprung bereit:

```bash
npx @agent-native/core@latest deploy
# https://your-agents.com/mail/*       → apps/mail
# https://your-agents.com/calendar/*   → apps/calendar
# https://your-agents.com/forms/*      → apps/forms
```

**Same-Origin** bedeutet, dass jede App für den Browser wie Teil derselben Website aussieht. Das bringt Ihnen zwei große Vorteile kostenlos:

- **Gemeinsame Anmeldesitzung**. Melden Sie sich bei einer App an, und jede App ist angemeldet.
- **Zero-Config App-übergreifendes A2A**. Das Markieren von `@calendar` aus Mail heraus ist ein Same-Origin-Fetch. Es gibt kein CORS und kein JWT-Signieren zwischen Geschwister-Apps.

<Callout tone="info">

Unter der Haube wird jede App mit einem eigenen **Basispfad** erstellt, einem URL-Präfix wie `/mail`, festgelegt über `APP_BASE_PATH`/`VITE_APP_BASE_PATH`, und dann für die Ziel-Nitro-Voreinstellung verpackt. Cloudflare Pages leitet über einen generierten **Dispatcher-Worker**, ein kleines Skript unter `dist/_worker.js`, das den eingehenden Pfad liest und die Anfrage an die passende App weiterleitet. Netlify verwendet eine Funktion pro App plus generierte Weiterleitungen. Vercel schreibt ein Arbeitsbereichs-`.vercel/output` mit der Build Output API.

</Callout>

<Callout tone="warning">

Gehostete Workspace-Builds erfordern `A2A_SECRET` in der Umgebung des Deploy-Anbieters. Ohne es funktionieren Slack, eingehende Webhooks und die Fortsetzung von App-übergreifendem A2A nicht, da diese alle über signierte Hintergrundprozessoren laufen. Lokale `--build-only`-Artefaktprüfungen laufen auch ohne es.

</Callout>

<Callout tone="info">

Verdrahten Sie stattdessen einen Anbieter-Build-Befehl, statt von Hand bereitzustellen? Fügen Sie `--build-only` demselben Befehl hinzu, zum Beispiel `npx @agent-native/core@latest deploy --preset vercel --build-only`. Es schreibt die Ausgabe direkt, sodass für das Workspace-Routing keine `vercel.json` erforderlich ist.

Bevorzugen Sie eine separate Domain pro App statt eines gemeinsamen Ursprungs? Jede App im Arbeitsbereich bleibt weiterhin unabhängig bereitstellbar. Führen Sie `cd apps/<name> && npx @agent-native/core@latest build` wie bei einem eigenständigen Scaffold aus.

</Callout>

## Selbstgehosteter Arbeitsbereich mit Docker Compose {#workspace-docker-compose}

Ein Arbeitsbereich ist heute kein einzelner Nitro-Serverprozess. Jede App baut weiterhin in ihr eigenes `.output/`-Verzeichnis und läuft mit ihrem eigenen Node/Nitro-Server, sodass das Selbsthosten eines Arbeitsbereichs bedeutet, mehrere Server hinter einem einzigen Einstiegspunkt laufen zu lassen.

Ein **Reverse Proxy** ist dieser einzelne Einstiegspunkt im Bild oben. Er empfängt jede Anfrage und leitet sie anhand des URL-Pfads an den richtigen Container weiter, dieselbe Aufgabe, die Cloudflares Dispatcher-Worker bei einer verwalteten Bereitstellung übernimmt. Auf einem VPS bedeutet das einen Container pro Workspace-App, alle zeigen auf dieselbe Postgres-Datenbank und gemeinsame Produktions-Secrets, mit dem Proxy davor.

<Steps>

### Jede App mit passendem Basispfad bauen

Der Basispfad ist eine Build-Zeit-Eingabe für das Client-Bundle und eine Laufzeit-Eingabe für den Server. Bauen Sie jede App mit demselben Pfad, zu dem der Proxy sie weiterleiten wird:

```bash maxLines=8
APP_BASE_PATH=/mail VITE_APP_BASE_PATH=/mail npx @agent-native/core@latest build
node .output/server/index.mjs
```

### Ein wiederverwendbares Dockerfile schreiben

Nehmen Sie den App-Namen und das Pfadpräfix als Build-Argumente, sodass ein Dockerfile jede App im Arbeitsbereich bedient:

```dockerfile filename="Dockerfile.workspace-app" maxLines=12
FROM node:24-slim AS build
WORKDIR /workspace
RUN corepack enable
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY packages ./packages
COPY apps ./apps
ARG APP_NAME
ARG APP_BASE_PATH
ENV APP_BASE_PATH=$APP_BASE_PATH
ENV VITE_APP_BASE_PATH=$APP_BASE_PATH
RUN pnpm install --frozen-lockfile
RUN pnpm --dir apps/$APP_NAME build

FROM node:24-slim
WORKDIR /app
ARG APP_NAME
ARG APP_BASE_PATH
ENV NODE_ENV=production
ENV PORT=3000
ENV APP_BASE_PATH=$APP_BASE_PATH
COPY --from=build /workspace/apps/$APP_NAME/.output .output
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

### Postgres, die Apps und den Proxy zusammenstellen

Dieses Beispiel verwendet Caddy, weil es HTTP lokal terminieren oder hinter Cloudflares SSL-Proxy sitzen kann, aber der wichtige Teil ist das Pfadpräfix-Routing:

```yaml filename="docker-compose.yml" maxLines=30
services:
  postgres:
    image: postgres:17
    restart: unless-stopped
    environment:
      POSTGRES_DB: agent_native
      POSTGRES_USER: agent_native
      POSTGRES_PASSWORD: change-me
    volumes:
      - postgres-data:/var/lib/postgresql/data

  mail:
    build:
      context: .
      dockerfile: Dockerfile.workspace-app
      args:
        APP_NAME: mail
        APP_BASE_PATH: /mail
    restart: unless-stopped
    environment:
      DATABASE_URL: postgres://agent_native:change-me@postgres:5432/agent_native
      BETTER_AUTH_URL: https://agents.example.com/mail
      BETTER_AUTH_SECRET: ${BETTER_AUTH_SECRET}
      A2A_SECRET: ${A2A_SECRET}
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
    depends_on:
      - postgres

  calendar:
    build:
      context: .
      dockerfile: Dockerfile.workspace-app
      args:
        APP_NAME: calendar
        APP_BASE_PATH: /calendar
    restart: unless-stopped
    environment:
      DATABASE_URL: postgres://agent_native:change-me@postgres:5432/agent_native
      BETTER_AUTH_URL: https://agents.example.com/calendar
      BETTER_AUTH_SECRET: ${BETTER_AUTH_SECRET}
      A2A_SECRET: ${A2A_SECRET}
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
    depends_on:
      - postgres

  proxy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
    depends_on:
      - mail
      - calendar

volumes:
  postgres-data:
```

### Den Proxy konfigurieren

```caddyfile filename="Caddyfile"
agents.example.com {
  reverse_proxy /mail* mail:3000
  reverse_proxy /calendar* calendar:3000
}
```

</Steps>

<Callout tone="info">

- Halten Sie `DATABASE_URL`, `BETTER_AUTH_SECRET`, `A2A_SECRET` und andere
  Produktions-Secrets über alle App-Container hinweg identisch, wenn Sie
  gemeinsame Authentifizierung, gemeinsame Anmeldedaten und App-übergreifendes
  A2A möchten.
- Legen Sie `BETTER_AUTH_URL` auf die öffentliche URL für diesen App-Pfad fest.
  OAuth-Callback-URLs sollten dieselbe öffentliche URL verwenden.
- Verlassen Sie sich für Produktionsdaten nicht auf das Container-Dateisystem.
  Verwenden Sie Postgres (oder ein anderes persistentes SQL-Backend) für
  `DATABASE_URL`.
- Wenn Cloudflare TLS vor dem VPS terminiert, konfigurieren Sie Cloudflare so,
  dass normale `X-Forwarded-Proto`- / `X-Forwarded-Host`-Header gesendet werden
  und der öffentliche Host zum Proxy-Container geroutet wird.

</Callout>
