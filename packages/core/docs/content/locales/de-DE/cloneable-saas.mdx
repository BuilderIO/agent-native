# Apps

Agent-Native-Apps gibt es in zwei Formen: Vorlagen mit vollständiger Browser-UI und Automation-First-Apps ohne Browser-UI – zum Beispiel ein Slack-Bot, ein nächtlicher Report oder ein Webhook-Responder. Dieses Dokument behandelt Vorlagen; die andere Form finden Sie unter [Automation-First Apps](/docs/pure-agent-apps).

Eine Vorlage ist ein vollständiges SaaS-Produkt: UI, Datenbank, Authentifizierung und Agent sind bereits fertig gebaut und miteinander verbunden. Wählen Sie eine aus, branden Sie sie und stellen Sie sie als Ihr eigenes Produkt bereit, statt mit einem leeren Gerüst zu beginnen. Dieses Modell nennt man klonbare SaaS: Sie starten von einem fertigen Produkt, nicht von einem Gerüst.

## Community-Templates {#community-templates}

Die benannten Templates in der CLI-Auswahl sind **offiziell**: Agent Native
wartet, testet, dokumentiert und veröffentlicht sie zusammen mit dem Framework.
Ein **Community-Template** wird vom Eigentümer seines Repositorys gewartet und
versioniert. Es kann dieselbe Framework-Oberfläche verwenden, aber ein Eintrag
in der Community-Liste ist weder eine Empfehlung noch ein Supportversprechen
von Agent Native.

Führen Sie `create` aus, wählen Sie **Community-Template**, und fügen Sie eine
einfache öffentliche GitHub-Repository-URL ein:

```bash
https://github.com/owner/repo
```

Wenn das Repository-Stammverzeichnis eine einzelne Agent-Native-App enthält,
installiert die CLI sie direkt ohne weitere Auswahl. Handelt es sich um einen
Agent-Native-Workspace, erkennt die CLI gültige direkte Unterverzeichnisse von
`apps/*`, schließt `dispatch` aus und fragt, welche App installiert werden soll.

Eine nicht leere `agent-native.workspaceCore`-Markierung macht das Repository
auch dann zu einem Workspace, wenn das Root-Paket von `@agent-native/core`
abhängt; eine fehlerhafte Markierung wird abgelehnt.

Übergeben Sie dieselbe einfache URL für Skripte an `--template`, oder verwenden
Sie die kürzere `community:`-Form. Fixieren Sie Branch, Tag oder Commit nach `#`
für einen reproduzierbaren Ausgangspunkt. Ohne Referenz versucht die CLI zuerst
`main`, dann `master`:

```bash
npx @agent-native/core@latest create my-app --template community:owner/repo#v1.2.0
npx @agent-native/core@latest create my-app --template https://github.com/owner/repo#v1.2.0
```

Treffen Sie die Quell-App-Auswahl für ein Workspace-Repository mit
`?app=<app-name>` ohne Interaktion. Der Selektor steht vor der optionalen
`#ref`. Setzen Sie den gesamten Wert in Anführungszeichen, da Shells wie zsh
`?` als Glob behandeln:

```bash
npx @agent-native/core@latest create my-app --template 'community:owner/repo?app=analytics#v1.2.0'
npx @agent-native/core@latest create my-app --template 'https://github.com/owner/repo?app=analytics#v1.2.0'
```

Außerhalb eines Workspace erstellt `create` aus der ausgewählten Quell-App eine
eigenständige App. Für einen vorhandenen Workspace müssen Sie das
Community-Repository explizit übergeben, weil die `add-app`-Auswahl nur
offizielle Templates auflistet. Lassen Sie `?app` für die interaktive Auswahl
aus dem Quell-Workspace weg, oder geben Sie es für eine skriptfähige
Installation an:

```bash
npx @agent-native/core@latest add-app my-app --template community:owner/repo#v1.2.0
npx @agent-native/core@latest add-app my-app --template 'community:owner/repo?app=analytics#v1.2.0'
```

Nur öffentliche GitHub-Repositorys werden akzeptiert. Private Repositorys,
andere Hosts als GitHub, GitHub-Tree- oder Unterverzeichnis-URLs und
verschachtelte App-Pfade werden nicht unterstützt. Eine Root-App benötigt eine
lesbare `package.json`, die `@agent-native/core` unter `dependencies`,
`devDependencies` oder `peerDependencies` auflistet. In einem
Workspace-Repository muss jede auswählbare Quell-App dieselbe Anforderung
direkt unter `apps/<app-name>/` erfüllen; `dispatch` ist nie auswählbar.

Community-Workspace-Apps müssen portable Blätter sein, keine beliebigen
Monorepo-Ausschnitte:

- Standard-`catalog:`-Abhängigkeitsreferenzen werden aus der
  `pnpm-workspace.yaml` im Stammverzeichnis des Quell-Repositorys aufgelöst;
  benannte Katalogreferenzen werden nicht unterstützt;
- `workspace:*`-Referenzen auf `@agent-native/core`,
  `@agent-native/dispatch` und `@agent-native/toolkit` werden auf
  veröffentlichte Versionen umgeschrieben. Andere benachbarte
  Workspace-Pakete werden nicht kopiert; veröffentlichen Sie sie und verwenden
  Sie stattdessen eine konkrete Version;
- die Abhängigkeit vom Quellpaket `workspaceCore` wird entfernt. Die kanonisch
  geerbten Workspace-Plugins für Auth und Agent Chat werden bei einer
  eigenständigen Installation getrennt oder an den Ziel-Workspace gebunden.
  Jeder andere Import des Quellpakets `workspaceCore` schlägt mit einer klaren
  Meldung fehl; verschieben Sie den Code in die App oder veröffentlichen Sie ihn
  als konkrete Abhängigkeit.

Auch der Rest jeder vollständigen App gehört zu ihrer `package.json`:
`agent-native.json`, falls verwendet, Quellcode, Actions, Agentenanweisungen und
Datenbankeinrichtung. Ein katalogfähiges Repository sollte außerdem Folgendes
enthalten:

- eine Lizenz und einen Link zum Maintainer oder Support;
- eine README mit Einrichtungsschritten, erforderlichen Umgebungsvariablen und
  dem genauen CLI-Befehl;
- eine `.env.example` ausschließlich mit Platzhaltern, ohne Secrets,
  Kundendaten, Laufzeitdatenbanken oder generierte Build-Ausgaben;
- eine funktionierende Installation und einen Entwicklungsbefehl sowie einen
  angemessenen Typecheck und passende Tests.

Das Installationsprogramm zeichnet die aufgelösten Werte `source` und `ref`
unter `agent-native.communityTemplate` in der `package.json` der installierten
App auf. Apps aus einem Workspace-Repository zeichnen außerdem die Quell-App
als `agent-native.communityTemplate.app` auf. `agent-native template sync`
bleibt auf offizielle Templates beschränkt; prüfen Sie zum Aktualisieren eines
Community-Templates eine neuere Upstream-Referenz und führen Sie deren
Änderungen selbst zusammen.

Unter [Creating Templates](/docs/creating-templates) finden Sie die vollständige
Checkliste zu App, Actions, Zustand, Sicherheit und Veröffentlichung.

> **Prüfen Sie Community-Code, bevor Sie Abhängigkeiten installieren oder ihn
> ausführen.** Community-Templates werden aus Repositorys von Drittanbietern
> heruntergeladen; Agent Native isoliert, auditiert oder wartet sie nicht.
> Die CLI lädt nur den Quellcode herunter; sie installiert keine Abhängigkeiten
> und führt keine Template-Skripte aus. Prüfen Sie Quellcode, Lizenz,
> Abhängigkeiten und Package-Installationsskripte und bevorzugen Sie eine
> fixierte, vertrauenswürdige Referenz.

Eine gehostete Demo ist optional. Falls Sie eine anbieten, verwenden Sie einen
öffentlichen Link zum Ausprobieren und dokumentieren Sie Anforderungen an
Anmeldung, Beispieldaten oder Anbieter. Das Repository bleibt die maßgebliche
Installationsquelle, und sein Eigentümer bleibt für Template und Demo
verantwortlich.

Möchten Sie aufgenommen werden? [Reichen Sie ein Community-Template ein](https://github.com/BuilderIO/agent-native/issues/new?template=community-template.yml)
und nennen Sie Repository-URL, eine Beschreibung in einem Satz, Maintainer- und
Lizenzdetails, den getesteten CLI-Befehl und optional die URL einer gehosteten
Demo.

## Was Sie im Lieferumfang enthalten {#what-you-get}

Jede Beispiel-App enthält:

- **Ein funktionierender Agent** – mit der App verbunden, kann actions auf Ihren Daten ausführen und weiß, was Sie sich gerade ansehen. Siehe [Messaging the agent](/docs/messaging).
- **Auth** – Anmeldung, Sitzungen, Organisationen und mandantenfähige Isolation.
- **Eine Datenbank** – Schema, Abfragen und Migrationen, einsatzbereit. Bringen Sie Ihre eigene SQL-Datenbank mit (Postgres, SQLite, Turso, D1); das Framework passt sich an.
- **Ein Echtzeit-UI** – der Bildschirm bleibt mit dem Agenten synchronisiert. Wenn Sie im Chat zum Beispiel eine E-Mail entwerfen, aktualisiert sich der Posteingang sofort.
- **Bereitstellungsbereit** – Bereitstellung auf Netlify, Vercel, Cloudflare, AWS oder jedem anderen Host, auf dem Node läuft.
- **Branding-Hooks** – Name, Farben, Logo und Text ändern.

Der Maintainer des Frameworks nutzt für seine eigene E-Mail, seinen Kalender und seine Analysen die Mail-, Calendar- und Analytics-App.

1. **Wählen Sie eine App.** Verwenden Sie die CLI-Auswahl oder durchsuchen Sie die Dokumente.
2. **Marken Sie es.** Ändern Sie den Namen, die Farben, das Logo und den Text. Die meisten Beispiel-Apps stellen dies in einer einzigen Konfigurationsdatei bereit.
3. **Passen Sie es an.** Nehmen Sie Quelländerungen in Ihrem Repository und Entwicklungsworkflow vor. Ein Agent kann helfen, wenn seinem Frame bewusst Workspace- und Schreibwerkzeuge gewährt wurden; andernfalls bedient der eingebettete Agent die App über Actions, Daten und konfigurierte Integrationen.
4. **Versenden Sie es.** Führen Sie den Bereitstellungsbefehl aus. Sie haben jetzt eine Produktions-App in Ihrer eigenen Domain.

Die Schritte 2–4 dauern normalerweise ein paar Tage. Schritt 3 hat keinen festen Endpunkt – die App gehört Ihnen und lässt sich weiterentwickeln, während der eingebettete Agent weiterhin verfügbar bleibt, um das bereitgestellte Produkt zu bedienen, und bei Quelländerungen helfen kann, wenn Codezugriff ausdrücklich aktiviert ist.

## Warum das praktisch ist {#why}

Eine separate Codebase pro Benutzer skaliert nicht – einen Fork der App für jeden Benutzer zu pflegen wird irgendwann unhaltbar. Zwei Framework-Entscheidungen vermeiden das:

1. **Die App hält den Framework-Vertrag ein.** Ihre Quelle besitzt das Domänenverhalten, während Core Actions, SQL, Zustand und Synchronisierung konsistent hält, wenn sich die App entwickelt.
2. **Anpassung pro Benutzer ohne Code pro Benutzer.** Skills, Speicher, Anweisungen, verbundene MCP-Server und Subagenten befinden sich alle in SQL. Jeder Benutzer erhält seine eigene Anpassungsebene; Die gemeinsame Codebasis hostet sie alle gleichzeitig.

Das Ergebnis: Anpassung pro Benutzer ohne Bereitstellung pro Benutzer.

## Möchten Sie nicht anpassen? {#hosted}

Jede Beispiel-App ist auch als gehostetes Produkt auf `agent-native.com` verfügbar – `mail.agent-native.com`, `calendar.agent-native.com` usw. Nutzen Sie die gehostete Version kostenlos oder kostenpflichtig; erstellen Sie eine eigene App aus einer Vorlage, wenn Sie etwas ändern möchten, das die gehostete Version nicht offenlegt.

### Für Entwickler {#dev-details}

Um eine neue App aufzusetzen:

```bash
npx @agent-native/core@latest create my-platform
```

Die CLI fragt zuerst **Wie möchten Sie beginnen?** Wählen Sie **Chat** für einen minimalen Workspace mit Chat und Dispatch oder **First-party template(s)** für die Mehrfachauswahl. Community und Headless sind die eigenständigen Einstiege. Workspace-Apps teilen Authentifizierung, Marke, Agentenkonfiguration und Datenbank; jede App wird mit allen benötigten Dateien in `apps/<name>/` eingebunden. Für eine Automation ohne Browser-UI anstelle einer App-UI verwenden Sie `npx @agent-native/core@latest create my-agent --headless`.

Füllen Sie `.env` aus (`ANTHROPIC_API_KEY` und `DATABASE_URL`), und führen Sie dann `pnpm install` und `pnpm dev` aus. Es gibt kein Login zu implementieren und keine Platzhalterrouten.

Ziele bereitstellen: jeder Nitro-kompatible Host (Node, Cloudflare, Netlify, Vercel, Deno, Lambda, Bun) und jede Drizzle-kompatible SQL-Datenbank (SQLite, Postgres, Turso, D1, Supabase, Neon). Für Arbeitsbereiche erstellt `npx @agent-native/core@latest deploy` jede App auf einmal und versendet sie hinter einem einzigen Ursprung. Siehe [Deployment](/docs/deployment).

Informationen zum Erstellen und Veröffentlichen Ihrer eigenen App-Vorlage finden Sie unter [Creating Templates](/docs/creating-templates).
