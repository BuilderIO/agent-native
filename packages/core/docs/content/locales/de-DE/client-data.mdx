# Daten & Sync

Der primäre Weg, App-Daten aus dem Client zu lesen und zu schreiben, führt über [Action](/docs/actions-overview)-Hooks. Indem Anfragen in Actions eingebettet werden, können sowohl Ihr Client als auch der Agent auf dieselbe Weise mit Ihrer Anwendung interagieren.

Im folgenden Beispiel wird ein Ticket manuell über ein Dropdown und dann über den Chat-Agenten dem aktuellen Benutzer zugewiesen. Sowohl die UI als auch der Agent greifen auf dieselbe Action zu.

### Action-Hooks {#action-hooks}

Es gibt zwei Action-Hooks, die Sie am wahrscheinlichsten verwenden werden: `useActionQuery()` und `useActionMutation()`. Diese beiden Hooks bieten Zugriff auf die Actions Ihrer App.

#### useActionQuery {#use-action-query}

Dieser Hook ist für schreibgeschützte Actions gedacht. Es ist ein dünner Wrapper um die Funktion [useQuery()](https://tanstack.com/query/latest/docs/framework/react/reference/useQuery).

Im folgenden Beispiel wird die Action `list-tickets` aufgerufen. Dies ähnelt einer GET-Anfrage für alle Tickets.

```ts
import { useActionQuery } from "@agent-native/core/client/hooks";

const { data, isLoading } = useActionQuery("list-tickets", {});
```

Das folgende Beispiel zeigt eine Anfrage, um ein einzelnes Ticket über die Action `get-ticket` abzurufen. Eine `ticketId` wird übergeben, um die Abfrage auf ein bestimmtes Ticket zu beschränken. Die zusätzliche Option `enabled` sorgt dafür, dass die Abfrage nicht automatisch läuft, sondern nur, wenn eine `ticketId` vorhanden ist.

```ts
import { useActionQuery } from "@agent-native/core/client/hooks";

const { data, isLoading } = useActionQuery(
  "get-ticket",
  { ticketId: ticketId ?? "" },
  { enabled: Boolean(ticketId) },
);
```

Dieser Hook ist für Actions gedacht, die Daten ändern, wie Erstellen, Aktualisieren oder Senden. Es ist ein dünner Wrapper um die Funktion [useMutation()](https://tanstack.com/query/latest/docs/framework/react/reference/useMutation).

Im Gegensatz zu `useActionQuery()` wird die Eingabe der Action nicht dem Hook selbst übergeben. Sie wird `mutate()` oder `mutateAsync()` übergeben, wenn Sie bereit sind, die Mutation auszuführen.

Im folgenden Beispiel wird die Action `send-ticket-reply` aufgerufen, um eine Antwort auf ein Ticket zu posten. Rufen Sie `mutate()` aus einem Event-Handler auf, etwa dem `onClick` einer Schaltfläche.

```ts
import { useActionMutation } from "@agent-native/core/client/hooks";

const { mutate, isPending } = useActionMutation("send-ticket-reply");

mutate({ ticketId, body: draft });
```

Das folgende Beispiel zeigt dieselbe Mutation mit einer `onSuccess`-Option. Die Cache-Invalidierung erfolgt nach jeder Mutation automatisch, daher wird `onSuccess` nur für lokale Nebeneffekte benötigt, etwa das Leeren des Antwort-Composers, nachdem die Antwort gesendet wurde.

```ts
import { useActionMutation } from "@agent-native/core/client/hooks";

const { mutate, isPending } = useActionMutation("send-ticket-reply", {
  onSuccess: () => setDraft(""),
});

mutate({ ticketId, body: draft });
```

### Ressourcenbezogene Invalidierung {#resource-scoped-invalidation}

Beide Hooks akzeptieren ein optionales `resources`-Array. Eine Abfrage nennt die gelesenen Ressourcen, eine Mutation die geänderten Ressourcen. Verwenden Sie `type` für einen ganzen Ressourcentyp oder `type:id` für eine bestimmte ID. Beim Abgleich lokaler Mutationen trennt der erste Doppelpunkt in einem `type:id`-Tag den Typ von der ID. Der Typ darf keinen Doppelpunkt enthalten, die ID darf Doppelpunkte enthalten. Sync-Ereignisse übertragen Typ und ID getrennt.

```ts
import {
  useActionMutation,
  useActionQuery,
} from "@agent-native/core/client/hooks";

const tickets = useActionQuery("list-tickets", {}, { resources: ["ticket"] });
const ticket = useActionQuery(
  "get-ticket",
  { ticketId },
  { resources: [`ticket:${ticketId}`] },
);
const reply = useActionMutation("send-ticket-reply", {
  resources: [`ticket:${ticketId}`],
});
```

Für Typen ohne Doppelpunkt und Tags mit nicht leeren Datensatz-IDs ist der Abgleich zwischen lokalen Mutationen und Sync-Ereignissen symmetrisch. Verwenden Sie für eine typweite lokale Änderung `type`, nicht `type:`. Beim Abgleich lokaler Mutationen steht `design:layer` für den Typ `design` und die ID `layer`. Ein Sync-Ereignis mit `resourceType` `design:layer` hat einen von `design` verschiedenen Typ und passt nicht zum Abfrage-Tag `design`. Ein Tag `ticket` passt zu `ticket` und jedem Tag `ticket:id`. Ein Tag `ticket:123` passt zu `ticket` und `ticket:123`, aber nicht zu `ticket:456`. Abfragen ohne Tags werden vorsorglich invalidiert. Eine Mutation ohne Tags invalidiert alle Action-Abfragen.

Bei einem Action-Sync-Ereignis identifizieren `resourceType` und `resourceId` die geänderte Ressource getrennt. Fehlt `resourceId` oder ist es leer, werden alle Abfragen für diesen Typ invalidiert. Fehlt bei einem nicht unterdrückten Action-Ereignis `resourceType`, entfällt die Ressourceneingrenzung für den Stapel und alle Action-Abfragen kommen infrage. Das optionale Prädikat kann die Invalidierung weiterhin filtern.

Enthält ein Stapel Action-Ereignisse und ausschließlich Action- oder App-State-Ereignisse, passt der Ressourcenfilter auf jede geänderte Ressource der nicht unterdrückten Action-Ereignisse. Mit `actionInvalidatePredicate` muss eine Abfrage sowohl den Filter als auch das Prädikat erfüllen. Das Prädikat erhält den gesamten relevanten Stapel ohne Awareness-Ereignisse, einschließlich unterdrückter Action-Ereignisse. Enthält der Stapel auch eine andere datenändernde Quelle, entfällt die Ressourceneingrenzung, das Prädikat gilt aber weiterhin. Bei einem Stapel mit einem anderen datenändernden Ereignis, aber ohne nicht unterdrücktes Action-Ereignis filtert das Prädikat auch die breite Action-Invalidierung.

`changeResource` einer Action bezeichnet eine Ressource für die Ereigniszustellung und Zugriffsprüfung. Sie ist nicht unbedingt eine vollständige Liste der Schreibzugriffe der Action. Datensatzspezifische Abfrage-Tags sind nur sicher, wenn der zugestellte Marker jeder relevanten Action alle Datensätze repräsentiert, von denen die Abfrage abhängt. Bei Sammelschreibvorgängen oder datensatzübergreifenden Abhängigkeiten innerhalb des Markertyps kann ein typweites Abfrage-Tag zum zugestellten Ereignis passen. Nehmen Sie bei Abhängigkeiten über Typgrenzen hinweg den Typ jedes zugestellten Ereignisses in die Abfrage-Tags auf oder verwenden Sie eine Abfrage ohne Tags. Mehrere unabhängig zugestellte Ereignisse können betroffene Datensätze abdecken, sofern jede betroffene Person ein für sie autorisiertes Ereignis erhält. Breitere Client-Tags beeinflussen den Abgleich erst nach der Zustellung. Sie machen ein Ereignis nicht für Personen sichtbar, die keinen Zugriff auf seine Zustellressource haben. Stellen Sie sicher, dass die betroffenen Personen ein für sie zugängliches Ereignis erhalten.

Diese Funktion ist für imperative Einzelaufrufe von Actions außerhalb eines React-Render-Flows gedacht, etwa einen einfachen Event-Handler, ein Skript oder einen anderen Nicht-React-Codepfad. Sie gibt direkt ein Promise zurück statt eines Hook-Ergebnisses.

Im folgenden Beispiel wird die Action `update-ticket` aus einem Tastenkürzel-Handler außerhalb des Render-Flows von React aufgerufen, um das Ticket einem Mitarbeiter zuzuweisen.

```ts
import { callAction } from "@agent-native/core/client/hooks";

await callAction("update-ticket", {
  ticketId,
  assignedToEmail: "jordan@example.com",
});
```

Das folgende Beispiel zeigt denselben Aufruf mit einer `timeoutMs`-Option, nützlich für Actions, die berechtigterweise länger als das Standard-Timeout von 60 Sekunden dauern.

```ts
import { callAction } from "@agent-native/core/client/hooks";

await callAction(
  "update-ticket",
  { ticketId, assignedToEmail: "jordan@example.com" },
  { timeoutMs: 120_000 },
);
```

Jede Anfrage von `useActionQuery()`, `useActionMutation()` und `callAction()` ist durch ein 60-Sekunden-Timeout begrenzt, und Timeouts erscheinen als Fehler statt stillschweigend erneut zu versuchen. `useActionQuery()` bricht außerdem automatisch überholte Anfragen ab, mithilfe des Abort-Signals von React Query.

### Fehlgeschlagene Schreibvorgänge {#write-failures}

Wenn ein vom Benutzer gestartetes Speichern fehlschlägt, zeigt die App einen gemeinsamen Toast statt gar keiner Meldung. `useActionMutation()` macht das automatisch. Ein fehlgeschlagenes `mutate()` zeigt den Toast, außer ein `onError` behandelt den Fehler, entweder in den Hook-Optionen oder im Aufruf von `mutate()`. Ein fehlgeschlagenes `mutateAsync()` zeigt ihn nur, wenn die Ablehnung unbehandelt bleibt, etwa bei einem `await` ohne `try/catch` darüber. Ein `catch`, das anstelle des ursprünglichen Fehlers einen neuen `Error` wirft, wird nicht gemeldet.

Die Option `errorNotification` ändert diesen Standard:

| Wert                | Verhalten                                                                                                                                                       |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `"auto"` (Standard) | Zeigt den Toast nur, wenn nichts anderes den Fehler behandelt.                                                                                                  |
| `"shared"`          | Zeigt den Toast bei jedem Fehler, auch neben Ihrem eigenen `onError`. Verwenden Sie das, wenn der Handler nur zurücksetzt oder protokolliert.                   |
| `"caller"`          | Zeigt nie den Toast. Verwenden Sie das für Hintergrundspeicherungen, einen Fehler, den Sie bewusst ignorieren, oder eine Stelle, die den Fehler selbst anzeigt. |

`errorLabel` ersetzt den Titel des Toasts durch Ihren eigenen, bereits übersetzten Text. Im folgenden Beispiel zeigt ein fehlgeschlagenes Zuweisen diesen Titel statt des allgemeinen.

```tsx
import { useActionMutation } from "@agent-native/core/client/hooks";

const assign = useActionMutation("update-ticket", {
  errorLabel: t("tickets.assignFailed"),
});

assign.mutate({ ticketId, assignedToEmail: "jordan@example.com" });
```

Ein Autosave, der bei der nächsten Änderung erneut versucht, sollte den Benutzer nicht unterbrechen, daher schaltet er die Meldung ab.

```tsx
import { useActionMutation } from "@agent-native/core/client/hooks";

const saveDraft = useActionMutation("save-ticket-draft", {
  errorNotification: "caller",
});
```

Ein Schreibvorgang, der kein `useActionMutation()` ist, etwa ein `fetch` für einen Upload oder ein `catch`, das einen Fehler schluckt, meldet seinen Fehler mit `reportWriteFailure()`. Der Fehler eines rohen `fetch` enthält keinen Status, deshalb zeigt der Toast Ihre Bezeichnung oder den allgemeinen Titel. Ein rohes `useMutation()` nimmt daran teil, indem es `meta: surfaceMutationError(label)` übergibt; die Funktion nimmt dasselbe optionale Label entgegen.

```ts
import { reportWriteFailure } from "@agent-native/core/client/write-failure";

try {
  const response = await fetch(uploadUrl, { method: "PUT", body: file });
  if (!response.ok) throw new Error(`Upload failed with ${response.status}`);
} catch (error) {
  reportWriteFailure(error, { label: t("tickets.uploadFailed") });
}
```

Der Text des Toasts hängt vom Fehler ab. Eine abgebrochene Anfrage zeigt nichts. Offline sein, ein Timeout, ein `401` und ein `403` zeigen jeweils eine kurze übersetzte Meldung unter dem Titel. Ein `5xx` zeigt nur den Titel, weil der Server seinen eigenen Fehlertext verbirgt. Wenn eine Action mit einem typisierten `4xx`-Fehler aus `fail()` ablehnt, zeigt der Toast die Meldung, die die Action geschrieben hat; siehe [Eine Action fehlschlagen lassen](/docs/actions-defining#failing). Ein `401` oder `403` zeigt nie Text des Servers.

`AppProviders` rendert immer die Komponente, die auf diese Fehler hört, `WriteFailureToaster`. Sie zeigt ihren Toast über den `Toaster` der App, daher muss eine App, die `toaster={null}` übergibt, einen eigenen rendern. Eine App, die `AppProviders` nicht verwendet, rendert `<WriteFailureToaster />` aus `@agent-native/toolkit/app/shared` innerhalb ihres `QueryClientProvider` und neben ihrem `Toaster`. Ohne sie wird kein Toast angezeigt.

`useDbSync()` verarbeitet lokale Tool-Abschlüsse während eines Chat-Laufs und aktualisiert die Daten am Laufende. Änderungen eines einzelnen Agenten bleiben so ohne Hintergrundanfrage aktuell. Die Hintergrundsynchronisierung für Änderungen aus anderen Tabs, von anderen Personen, Webhooks oder Jobs bleibt aus, sofern diese Seite sie nicht mit einem kurzen Grund aktiviert. Ein Tab teilt einen Transport, pausiert ihn im Hintergrund und verlängert leere Polling-Intervalle auf 1, 2 und 5 Minuten.

```ts
import { useDbSync } from "@agent-native/core/client/hooks";
import { useQueryClient } from "@tanstack/react-query";

function App() {
  const queryClient = useQueryClient();

  useDbSync({
    queryClient,
    realtime: { reason: "teammates can edit this shared record" },
    pollUrl: "/_agent-native/poll",
    onEvent: (data) => console.log("Data changed:", data),
  });

  return <div>...</div>;
}
```

Aktivieren Sie Live-Sync nur, wenn sich Daten ohne Aktion des aktuellen Nutzers ändern können und dieser die Änderung vor dem Neuladen sehen muss. Gemeinsames Bearbeiten in Slides und der Mail-Posteingang eignen sich. Öffentliche Seiten, Docs, Einstellungen, Formulare, selten geänderte Listen und Änderungen eines einzelnen Agenten bleiben deaktiviert; aktualisieren Sie bei Fokus oder Navigation. Jeder aktivierte offene Tab pollt einmal pro Leerlaufintervall.
