# Plugins

Plugins sind Startup-Hooks. Jede Datei in `server/plugins/` exportiert eine Funktion, die Nitro einmal aufruft, wenn der Server initialisiert wird, bevor irgendeine Route bedient wird. Sie sind der richtige Ort für einmalige Einrichtung: Auth konfigurieren, die Agentenschleife einhängen, Datenbankmigrationen ausführen oder jeglichen anderen Initialisierungscode registrieren, der abgeschlossen sein muss, bevor Anfragen eintreffen.

Nitro entdeckt Plugins automatisch über das Dateisystem. Weder Registrierung noch Imports sind erforderlich. Dateien laufen in alphabetischer Reihenfolge, sodass die Ausführungsreihenfolge über das Dateinamenspräfix gesteuert wird.

Jede agentennative App bringt standardmäßig zwei Plugins mit:

```text
server/plugins/
  auth.ts        -> configure auth provider and public paths
  agent-chat.ts  -> mount the agent loop with your actions and system prompt
```

Apps, die benutzerdefinierte Datenbanktabellen benötigen, fügen ein drittes hinzu:

```text
server/plugins/
  db.ts          -> run migrations on startup
```

## Auth-Plugin {#auth-plugin}

`server/plugins/auth.ts` konfiguriert, wie sich Benutzer anmelden. `createAuthPlugin` aus `@agent-native/core/server` verdrahtet den Auth-Provider und legt das Branding der Anmeldeseite fest:

```ts filename="server/plugins/auth.ts"
import { createAuthPlugin } from "@agent-native/core/server";

export default createAuthPlugin({
  marketing: {
    appName: "My App",
    tagline: "A short description shown on the sign-in page.",
    features: [
      "Feature one",
      "Feature two",
      "Feature three",
    ],
  },
});
```

Um bestimmte Routen für unauthentifizierte Benutzer zu öffnen, übergeben Sie `publicPaths`:

```ts
export default createAuthPlugin({
  publicPaths: ["/public", "/api/webhook"],
  marketing: { appName: "My App", tagline: "..." },
});
```

Das Auth-Plugin konfiguriert den Guard. Die Middleware in `server/middleware/auth.ts` erzwingt ihn bei jeder Anfrage. Siehe [Middleware](/docs/server-middleware).

## Agent-Chat-Plugin {#agent-chat-plugin}

`server/plugins/agent-chat.ts` hängt die Agentenschleife mit den Actions, dem System-Prompt und dem initialen Tool-Set Ihrer App ein. Dieses Plugin macht Ihre App zu einer agentennativen App.

```ts filename="server/plugins/agent-chat.ts"
import { getOrgContext } from "@agent-native/core/org";
import {
  createAgentChatPlugin,
  loadActionsFromStaticRegistry,
} from "@agent-native/core/server";

import actionsRegistry from "../../.generated/actions-registry.js";

export default createAgentChatPlugin({
  appId: "my-app",
  actions: loadActionsFromStaticRegistry(actionsRegistry),
  initialToolNames: ["view-screen", "navigate"],
  resolveOrgId: async (event) => (await getOrgContext(event)).orgId,
  systemPrompt: `You are the My App agent.

Use actions as the source of truth. Start by inspecting the current
screen when context matters.`,
});
```

`loadActionsFromStaticRegistry` erfasst jede Action, die aus `actions/` über die generierte Registry exportiert wird. `initialToolNames` steuert, auf welche Actions der Agent zu Beginn einer Unterhaltung Zugriff hat. Er kann bei Bedarf weiterhin andere aufrufen.

## Datenbank-Plugin {#database-plugin}

Wenn Ihre App benutzerdefinierte Datenbanktabellen definiert, fügen Sie `server/plugins/db.ts` hinzu, um Schemamigrationen beim Start auszuführen. Es verwendet `runMigrations` aus `@agent-native/core/db`:

```ts filename="server/plugins/db.ts"
import { runMigrations } from "@agent-native/core/db";

export default runMigrations(
  [
    {
      version: 1,
      sql: `CREATE TABLE IF NOT EXISTS projects (
        id TEXT PRIMARY KEY,
        title TEXT NOT NULL,
        owner_email TEXT NOT NULL,
        org_id TEXT,
        created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
      )`,
    },
  ],
  { table: "my_app_migrations" },
);
```

Jeder Eintrag benötigt eine `version`-Nummer und einen `sql`-String. Die Option `table` benennt die Tabelle zur Migrations-Nachverfolgung. Verwenden Sie einen für Ihre App eindeutigen Namen, damit es nicht zu Kollisionen mit Framework-Migrationen kommt. Die vollständige Anleitung zur Schemaerstellung finden Sie unter [Datenbank](/docs/server-database).

<Callout tone="warning">
  Migrationen müssen additiv sein. Setzen Sie niemals destruktives SQL
  (`DROP TABLE`, `ALTER TABLE ... DROP COLUMN`, `DELETE FROM`) in
  Startup-Plugins ein.
</Callout>

## Eigene Plugins schreiben {#custom-plugins}

Die Framework-Helfer (`createAuthPlugin`, `createAgentChatPlugin`, `runMigrations`) geben jeweils eine Nitro-Plugin-Funktion zurück. Für alles außerhalb dieser Helfer schreiben Sie ein Plugin mit `defineNitroPlugin`:

```ts filename="server/plugins/my-plugin.ts"
import { defineNitroPlugin } from "nitropack/runtime";

export default defineNitroPlugin((nitro) => {
  nitro.hooks.hook("request", (event) => {
    // runs on every request
  });

  nitro.hooks.hookOnce("close", async () => {
    // runs when the server shuts down
  });
});
```

Plugins können jeden der Lifecycle-Hooks von Nitro verwenden: `request`, `beforeResponse`, `close` und weitere. Die [Nitro-Plugin-Dokumentation](https://nitro.build/guide/plugins) behandelt die vollständige Hook-API und den Plugin-Vertrag im Detail.

## Startreihenfolge {#startup-order}

Nitro führt Plugins in alphabetischer Dateinamenreihenfolge aus. Innerhalb einer einzelnen Plugin-Datei wird der Default-Export abgewartet, bevor das nächste Plugin startet. Eine typische Reihenfolge:

1. `db.ts` — Migrationen sind abgeschlossen, bevor irgendeine Route oder ein Plugin die Datenbank liest
2. `auth.ts` — die Auth-Konfiguration steht, bevor Anfragen eintreffen
3. `agent-chat.ts` — Agent-Routen werden eingehängt, nachdem Auth konfiguriert ist

Wenn Sie eigene Plugins hinzufügen, versehen Sie deren Dateinamen mit einem Präfix, um zu steuern, wo sie in der Abfolge einsortiert werden.
