# Actions definieren

Jede Action beginnt mit einem Aufruf von `defineAction()`. Sie bündelt eine Beschreibung für den Agenten, ein Schema, das die Eingabe validiert, und eine `run`-Funktion, die die eigentliche Arbeit erledigt, sodass die UI und der Agent exakt denselben Code aufrufen.

## Schema-Optionen {#schemas}

`schema` akzeptiert jede mit [Standard Schema](https://standardschema.dev) kompatible Bibliothek:

- **Zod** (v4): die gängigste Wahl, mit der besten Typinferenz und automatischer Umwandlung in JSON Schema.
- **Valibot**: eine gute Wahl, wenn die Bundle-Größe wichtig ist.
- **ArkType**: eine gute Wahl, wenn Sie dessen Syntax bevorzugen.

Das Schema erfüllt zwei Aufgaben. Es wandelt sich für die Tool-Definition der Claude API in JSON Schema um, und es validiert die Eingabe zur Laufzeit, bevor `run()` ausgelöst wird. Ungültige Eingaben erreichen Ihren Handler nie.

## Rückgabewert validieren {#output-schema}

`schema` validiert _Eingaben_. Um auch zu validieren, was eine Action **zurückgibt**, übergeben Sie ein `outputSchema` (ein beliebiges mit Standard Schema kompatibles Schema: Zod, Valibot, ArkType, dieselbe Oberfläche wie `schema`). Das Framework validiert die Eingabe vor `run()` und validiert das Ergebnis, nachdem `run()` aufgelöst wurde.

```ts
export default defineAction({
  description: "Summarize a thread.",
  schema: z.object({ threadId: z.string() }),
  outputSchema: z.object({
    summary: z.string(),
    messageCount: z.number(),
  }),
  outputErrorStrategy: "warn", // default
  run: async ({ threadId }) => {
    /* ...returns { summary, messageCount } ... */
  },
});
```

`outputErrorStrategy` steuert, was bei einer Abweichung passiert:

| Strategie    | Verhalten bei Abweichung                                                                                                       |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| `"warn"`     | **Standard.** `console.warn` gibt die Probleme aus und gibt das **ursprüngliche** Ergebnis unverändert zurück. Nicht breaking. |
| `"strict"`   | Wirft einen klaren Fehler, sodass ein Bug in der Action leicht auffällt.                                                       |
| `"fallback"` | Gibt den bereitgestellten `outputFallback`-Wert anstelle des ungültigen Ergebnisses zurück.                                    |

Wenn `run()` erfolgreich ist, gibt das Framework den validierten Wert zurück, sodass alle Defaults oder Coercions auf `outputSchema` greifen, genau wie bei der Eingabe. Wenn Sie kein `outputSchema` übergeben, bleibt der Rückgabewert unverändert.

## HTTP-Konfiguration {#http}

Standardmäßig wird jede Action als `POST /_agent-native/actions/<name>` exponiert. Überschreiben Sie dies mit der Option `http`:

```ts
export default defineAction({
  description: "Get details for a lead.",
  schema: z.object({ leadId: z.string() }),
  http: { method: "GET" },
  run: async ({ leadId }) => {
    return await db.select().from(leads).where(eq(leads.id, leadId));
  },
});
```

Für eine `GET`-Action wird `leadId` als Query-Parameter übergeben: `/_agent-native/actions/get-lead?leadId=abc`.

POST ist der Standard, und `http: { method: "GET" }` macht daraus ein GET. Die React-Hooks und `callAction()` rufen diesen Pfad immer namentlich auf, unabhängig von einer `http.path`-Überschreibung. Externe Systeme können dieselbe Route mit einem langlebigen Bearer-Token aufrufen. Siehe [HTTP API](/docs/http-api).

</Endpoint>

- **`http: { method: "GET" | "POST" | "PUT" | "DELETE" }`**: Standard ist `POST`. `GET`-Actions werden automatisch als `readOnly` markiert, sodass ein erfolgreicher Aufruf keine UI-Poll-Aktualisierung auslöst.
- **`http: { path: "..." }`**: überschreibt die eingebundene URL unter `/_agent-native/actions/`. Standardmäßig ist es der Dateiname. Diese Überschreibung ändert nur die URL für direkte HTTP-Aufrufer. `useActionQuery()`, `useActionMutation()` und `callAction()` rufen immer `/_agent-native/actions/<name>` auf, unabhängig von dieser Überschreibung, sodass ein Pfad-Override diese Hooks zu einem 404 führt. Verwenden Sie einen Pfad-Override nur für externe HTTP-Aufrufer. Beachten Sie außerdem, dass `:param`-Routensegmente im überschriebenen Pfad nicht in `run()`-Argumente geparst werden. Nur Query-String-Parameter und JSON-Body-Felder werden es.
- **`http: false`**: deaktiviert den HTTP-Endpunkt vollständig. Nur der Agent und die CLI können die Action aufrufen.
- **`readOnly: true`**: überspringt explizit die Poll-Aktualisierung, auch für POST-Actions, die nichts mutieren. Dies ist keine Zugriffskontrolle. Es beschränkt nicht, wer die Action aufrufen darf, und beeinflusst nicht `useActionQuery()`, `useActionMutation()` oder einen anderen Client-Hook. Die einzigen Effekte sind, das Refresh-Ereignis nach dem Aufruf zu unterdrücken und die Action vom Write-Auditing abzumelden. Um eine Action vor dem Modell zu verbergen, verwenden Sie `agentTool: false`. Um zu steuern, wer sie aufrufen darf, verwenden Sie die Auth- und Zugriffsoptionen unter [Zugriff & Autorisierung](/docs/actions-access-control).
- **`parallelSafe: true`**: erlaubt einer mutierenden Action, gleichzeitig mit anderen Tool-Aufrufen derselben Runde zu laufen. Setzen Sie dies nur, wenn die Action sicher gleichzeitig laufen kann und nicht von der Reihenfolge abhängt. Mutierende Actions werden standardmäßig serialisiert.

## Eine Action fehlschlagen lassen {#failing}

Eine Action meldet ein Scheitern, indem sie wirft. `{ error: "..." }` zurückzugeben sieht für jeden Teil des Frameworks wie Erfolg aus, also zählen die Retry-Schutzschalter des Agenten es nie und der Aufruf wird als abgeschlossener Seiteneffekt protokolliert.

Was du wirfst, entscheidet, wie viel von der Nachricht überlebt. `fail()` wirft einen `ActionContractError`, und genau dieser Typ ist der einzige Grund, warum der Text den Aufrufer erreicht. Ein blankes `throw new Error("No such email")` ist von einem Postgres- oder Upstream-Ausfall nicht zu unterscheiden, also ersetzt die Action-Route es durch ein generisches 500 `"Internal server error"`, behält die echte Nachricht im Server-Log und meldet sie an das Error-Tracking. Hebe den blanken Throw für echte interne Fehler auf. Dafür ist die 500 da.

`fail()` nimmt eine Nachricht und ein Options-Objekt:

- **message**: der Text, den der Aufrufer liest. Schreibe ihn für einen Menschen, nicht für ein Log.
- **options.errorCode**: ein stabiler, maschinenlesbarer Code. Standard: `"action_failed"`.
- **options.statusCode**: der HTTP-Status für die Action-Route. Standard: `400`.
- **options.details**: sicherer strukturierter Kontext für den Aufrufer. Niemals Secrets oder rohe Treiberausgabe hier ablegen.

Der einfachste Aufruf braucht nur eine Nachricht:

```ts
import { defineAction, fail } from "@agent-native/core/action";
import { eq } from "drizzle-orm";
import { z } from "zod";

import { getDb, schema } from "../server/db/index.js";

export default defineAction({
  description: "Reply to an email thread in the user's voice.",
  schema: z.object({
    emailId: z.string().describe("The id of the email to reply to."),
    body: z.string().describe("The reply body, in markdown."),
  }),
  run: async ({ emailId, body }) => {
    const db = getDb();
    const [email] = await db
      .select()
      .from(schema.emails)
      .where(eq(schema.emails.id, emailId));
    if (!email) fail("That email is no longer in the mailbox.");
    await db.insert(schema.replies).values({ emailId, body });
    return { ok: true, emailId };
  },
});
```

Die Ursache zu benennen ist das, was die UI auf einen Fehler reagieren lässt, statt ihn nur auszugeben. Code und Status überstehen beide den Transport:

```ts
if (!email) {
  fail("That email is no longer in the mailbox.", {
    errorCode: "email_not_found",
    statusCode: 404,
  });
}
```

Der Browser erhält `{ error, errorCode, details }`. `useActionQuery()`, `useActionMutation()` und `callAction()` reichen es als `Error` mit `status`, `errorCode` und `details` weiter.

### Was jeder Throw erzeugt {#failure-shapes}

| Geworfen aus `run()` | HTTP-Status | Response-Body | An Error-Tracking gemeldet |
| --- | --- | --- | --- |
| `fail(msg)` | 400 | `{ error: msg, errorCode: "action_failed" }` | Nein |
| `fail(msg, { errorCode, statusCode, details })` | dein `statusCode` | `{ error, errorCode, details }` | Nein |
| `new ActionContractError(msg, { errorCode })` | 409 | `{ error, errorCode, details }` | Nein |
| `new AgentActionStopError(msg)` | 500 | `{ error: msg }` | Nein |
| `new Error(msg)` | 500 | `{ error: "Internal server error" }` | Ja |
| Eingabe, die am `schema` scheitert | 400 | `{ error: "Invalid action parameters..." }` | Nein |

`AgentActionStopError` wirfst du, wenn der Agent seinen Zug beenden soll, statt den Fehler zu lesen und es erneut zu versuchen. `ActionContractError` ist das, was `fail()` für dich wirft, greife also nur direkt darauf zurück, wenn 409 der gewünschte Status ist.

### Wähle einen Status, auf den die Retry-Policy reagieren kann {#failure-status}

`useActionQuery()` wiederholt `429`, `502`, `503` und `504`, bis zu dreimal, mit 500 ms, dann 1 s, dann 2 s Wartezeit. Jeder andere Status gilt als deterministisch und erscheint bei der ersten Antwort. Eine Anfrage erneut zu senden, die als falsch abgelehnt wurde, kauft nur dieselbe Ablehnung noch einmal. `useActionMutation()` wiederholt überhaupt nicht.

Der Status ist also nicht kosmetisch. Eine als `404` gesendete Ablehnung kostet einen Roundtrip. Dieselbe Ablehnung als `500` gesendet oder blank geworfen kostet vier Roundtrips und vier doppelte Fehlerberichte.

Agent-Aufrufer sehen davon nichts. Der Agent führt `run()` im Prozess aus, bekommt die geworfene Nachricht also direkt, unabhängig vom Typ, und seine eigenen Schutzschalter für wiederholte Fehler begrenzen, wie oft er es erneut versucht.

## Die Action-Oberfläche klein halten {#small-surface}

Jede Action, die der Agent sehen kann, belegt einen Platz in der Tool-Liste des Modells, und eine lange, sich überschneidende Liste erschwert es dem Modell, das richtige Tool auszuwählen. Gestalten Sie die Action-Oberfläche wie eine API, die Sie pflegen, nicht wie eine Action pro Schaltfläche in der UI:

- Bevorzugen Sie **eine CRUD-artige `update`-Action**, die ein Patch aus optionalen Feldern annimmt, gegenüber vielen Pro-Feld-Actions wie `update-name`, `update-order` und `update-color`. Der Aufrufer sendet nur die Felder, die sich geändert haben.
- Bevor Sie für jede Abfrage oder jeden Filter eine neue Lese-Action hinzufügen, ziehen Sie zuerst eine allgemeinere Option in Betracht: das [Provider-API-Trio](/docs/template-dispatch-vault-integrations#provider-api) (`provider-api-catalog`, `provider-api-docs` und `provider-api-request`) für Provider-Daten, oder das Dev-Tool `db-query` für App-Daten.
- Markieren Sie reine UI- oder programmatische Actions als [`agentTool: false`](/docs/actions-access-control#agent-tool). Sie bleiben vom Frontend oder über HTTP aufrufbar, ohne einen Platz in der Tool-Liste des Modells zu belegen.
- Markieren Sie die wenigen Actions, zu denen der Agent ständig greift, mit `deferLoading: false`. Genau deren Schemas werden mit der ersten Modellanfrage gesendet; alles andere lädt bei Bedarf über `tool-search` nach. Sobald sich eine einzige Action so abmeldet, wird jede nicht markierte Action zurückgestellt, markieren Sie also den ganzen Startsatz auf einmal statt eine Action nach der anderen. Es geht darum, was der erste Zug kostet, nicht um Zugriff: Eine zurückgestellte Action ist aufrufbar, sobald `tool-search` sie zurückgibt. Das ist die Action-eigene Form des Plugin-Arrays `initialToolNames`, und eine App kann beides nutzen.
- Löschen oder verbergen Sie Actions, die die UI nicht mehr verwendet, statt sie dem Modell weiterhin auszusetzen.

Das Repo enthält einen beratenden Helfer, `node scripts/audit-template-actions.mjs [template ...]` (Alias `pnpm actions:audit`). Er durchsucht den `actions/`-Ordner eines Templates und markiert Actions, die die UI möglicherweise nicht mehr verwendet, zusammen mit Gruppen von Pro-Feld-Actions, die zu einer zusammengefasst werden könnten. Er endet immer mit Code 0 und lässt CI nie fehlschlagen, und seine Heuristiken sind konservativ, behandeln Sie seine Ausgabe also als Vorschlag, nicht als Fehler.
