# Server

Das Verzeichnis `server/` ist die Infrastrukturschicht einer agentennativen App. Es übernimmt Startaufgaben, Authentifizierung und die HTTP-Oberflächen, die Actions nicht abdecken. Das meiste Produktverhalten gehört in [Actions](/docs/actions). Der Server macht diese Actions verfügbar.

## Wo der Server einzuordnen ist {#role}

In einer traditionellen Web-App lebt der Großteil der Logik im Server. Geschäftsregeln, Datenzugriff und Darstellung passieren allesamt innerhalb von Route-Handlern. Agentennative Apps funktionieren anders. Die Logik lebt in Actions, die sich Agent und UI als gleichberechtigte Partner teilen. Die Aufgabe des Servers ist Koordination: Datenbankmigrationen ausführen, Authentifizierung konfigurieren, die Agentenschleife einhängen und die schmale Menge an HTTP-Belangen abdecken, die Actions allein nicht ausdrücken können.

Browseranfragen, die Agentenschleife und externe API-Clients laufen alle über denselben Nitro-Server und lesen aus derselben SQL-Datenbank. Es gibt kein separates Agenten-Backend oder UI-Backend. Die Serverschicht ist das, was Actions der Außenwelt zugänglich macht.

## Nitro {#nitro}

[Nitro](https://nitro.build) ist das Server-Toolkit, das die agentennative HTTP-Schicht antreibt. Das meiste, was Sie in `server/` konfigurieren, ist Nitro: dateibasierte Routen, Startup-Plugins und Middleware.

- **Dateibasiertes Routing**: Der Dateiname wird ohne Registrierung direkt auf eine HTTP-Methode und einen URL-Pfad abgebildet. `server/routes/api/health.get.ts` wird automatisch zu `GET /api/health`. Weitere Details finden Sie unter [Routen](/docs/server-routes).
- **Plugins**: Code, der einmal beim Serverstart läuft, bevor irgendeine Anfrage bedient wird. Datenbankmigrationen, Auth-Konfiguration und das Einhängen des Agent-Chats geschehen alle in `server/plugins/`. Weitere Details finden Sie unter [Plugins](/docs/server-plugins).
- **Middleware**: Code, der bei jeder eingehenden Anfrage läuft, bevor sie eine Route erreicht. Der Auth-Guard lebt in `server/middleware/`. Weitere Details finden Sie unter [Middleware](/docs/server-middleware).

Nitro ist außerdem bereitstellungsunabhängig. Dieselbe App wird ohne Codeänderungen auf Node.js, Cloudflare Workers, Netlify, Vercel und weiteren Laufzeitumgebungen bereitgestellt. Legen Sie einfach ein Preset fest. Siehe [Deployment](/docs/deployment).

Die zugrunde liegende Request/Response-API ist [H3](https://h3.unjs.io). Wenn Sie in benutzerdefinierten Routen `defineEventHandler`, `createError` oder `getQuery` sehen, ist das H3. Die [Nitro-Dokumentation](https://nitro.build/guide) und die [H3-Dokumentation](https://h3.unjs.io) sind die Referenz für alles, was das Framework nicht direkt abdeckt.

## Standardmäßig zuerst Actions {#actions-first}

Die Agent-Native-Architektur ist anders. Wann immer Sie an ein neues Feature für Ihre App denken, prüfen Sie zuerst, ob es eine Action sein kann. Wenn zum Beispiel sowohl UI als auch Agent etwas tun müssen, definieren Sie eine Action statt einer benutzerdefinierten API-Route. Actions werden automatisch zu:

- Agenten-Tools.
- Typisierten Frontend-Hooks.
- HTTP-Endpunkten unter `/_agent-native/actions/:name`.
- MCP- und A2A-aufrufbaren Tools.
- CLI-Befehlen für die Entwicklung.

Verwenden Sie benutzerdefinierte `/api/*`-Routen nur, wenn Sie ein routenförmiges Protokoll oder binäres/streamendes Verhalten benötigen. Weitere Details finden Sie unter [Actions](/docs/actions).
