# Entwicklerhandbuch

Diese Seite ist für alle, die die Design-Vorlage anpassen oder direkt darauf
aufbauen: der Schnellstart, jede Aktion, das Datenmodell, eine durchgesehene
Aktion, die Routenoberfläche und wie Sie sie erweitern. Was die App tut,
erfahren Sie unter [Design](/docs/template-design).

## Schnellstart

<Steps>

### Die App erstellen

```bash
npx @agent-native/core@latest create my-design --standalone --template design
cd my-design
pnpm install
```

Dafür brauchen Sie zuerst [Node.js](https://nodejs.org) 22.22 oder neuer und
[pnpm](https://pnpm.io) installiert. Siehe [Erste
Schritte](/docs/getting-started), falls Sie noch keins von beidem
installiert haben oder noch keine LLM-Verbindung (Builder.io, ein
Anthropic-/OpenAI-Schlüssel oder lokales Ollama) eingerichtet haben. Für
einen Arbeitsbereich mit Design neben anderen Apps führen Sie stattdessen
`npx @agent-native/core@latest create my-platform` aus und wählen Design
während der Einrichtung.

### Den Dev-Server starten

```bash
pnpm dev
```

Die App öffnet sich unter `http://localhost:8099`, dem Standard-Dev-Port
von Design. Design funktioniert vollständig ohne externe Verbindungen. Sie
stoßen nur dann auf eine Verbindungsaufforderung, wenn Sie einen
Figma-Import oder Vollständige App-Erstellung ausprobieren, bevor Sie diese
eingerichtet haben.

</Steps>

## Aktionsinventar

Jeder design-spezifische Vorgang ist eine TypeScript-Datei in
`templates/design/actions/`, automatisch gemountet unter `POST
/_agent-native/actions/:name` und ausführbar über die CLI als `pnpm action

<name>`.

## Datenmodell

Alle Daten befinden sich in SQL über Drizzle ORM. Schema:
`templates/design/server/db/schema.ts`. Designs und Designsysteme verfügen
über den Standard `ownableColumns` und eine passende Framework-Freigabetabelle,
sodass sie in das Freigabemodell pro Benutzer/pro Organisation passen.

Die folgende Tabelle behandelt die zentralen eigenen Ressourcen: Designs,
Dateien, Vorlagen, Versionen und Designsysteme.

| Tabelle                                  | Was sie enthält                                                                                                                                     |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `designs`                                | Ein Designprojekt — `title`, `description`, `project_type` (`prototype` / `other`), der `data`-JSON-Blob und ein optionaler `design_system_id`-Link |
| `design_files`                           | Einzelne Dateien, die zu einem Design gehören (`filename`, `content`, `file_type`, standardmäßig `html`)                                            |
| `design_templates`                       | Metadaten wiederverwendbarer Vorlagen, Abmessungen, Standardwerte, Quelldesign-Referenz und Anzahl gesperrter Ebenen                                |
| `design_template_files`                  | Momentaufnahme-Vorlagendateien, die in ein normales, bearbeitbares Design kopiert werden, wenn ein Benutzer mit einer Vorlage beginnt               |
| `design_template_shares`                 | Framework-Freigabetabelle für private, organisationsweite, explizit geteilte und öffentliche Vorlagen-Auffindbarkeit                                |
| `design_versions`                        | Zeitpunkt-`snapshot`s eines Designs mit einem optionalen `label`, für Verlauf und Rollback                                                          |
| `design_systems`                         | Wiederverwendbare Markentokens — `data` (Farben/Typografie/Abstände), `assets`, `custom_instructions` und eine `is_default`-Flagge                  |
| `design_shares` / `design_system_shares` | Framework-Freigabetabellen, die Prinzipale (Benutzer oder Organisationen) Rollen (Betrachter, Bearbeiter, Admin) zuordnen                           |

Ein Designprojekt ist eine Hülle, bis es Inhalt hat: `create-design` erstellt
eine leere Zeile (`data: "{}"`), dann schreibt `generate-design` die
eigentlichen eigenständigen HTML/JSX-Dateien. Das generierte Artefakt, die
bearbeitbare Quelle und jeder Export stammen alle aus demselben HTML, sodass
kein separates „AI-Mockup“-Format übersetzt werden muss. Ein verknüpftes
Designsystem liefert Tokens und `custom_instructions`, die der Agent bei
jedem Generierungsdurchgang berücksichtigt.

Sieben weitere Tabellen unterstützen Funktionen, die an anderer Stelle auf
dieser Seite behandelt werden, statt zum zentralen Ressourcenmodell zu
gehören: `design_localhost_connections` und `design_localhost_write_grants`
unterstützen den [Import lokaler Apps](/docs/template-design-features#import),
`component_index` unterstützt den [Abschnitt Komponente im Tab
Design](/docs/template-design-features#design-tab), `motion_timeline`
unterstützt die bearbeitbare Bewegungs-Timeline jedes Elements (das
Motion-Dock im Editor), `design_state` speichert benannte alternative
Zustände, statische Fixtures und Aufnahmen laufender Apps für ein Design,
`design_fusion_edits` unterstützt die Fusion-Bearbeitungswarteschlange, die
unter [Vollständige App-Erstellung](#full-app-building) oben beschrieben
wird, und `design_review_snapshot` speichert die
Barrierefreiheits-Befunde und den Sichtvergleich hinter
`get-design-review`, beschrieben unter [Qualität](#quality) oben.

Gespeicherte Review-Kommentare und -Threads (`get-review-feedback`,
`resolve-review-thread` und der Rest) sind überhaupt keine
design-spezifische Tabelle: Es ist das gemeinsame Framework-Review-System
aus `@agent-native/core/review` (`agent_review_comments` /
`agent_review_statuses`), an ein Design angehängt auf dieselbe Weise, wie es
jede App tun kann. Siehe [Tab Kommentare](/docs/template-design-features#comments-tab)
für das benutzerseitige Verhalten.

## Eine durchgesehene Aktion

`save-design-as-template` zeigt Muster, die es wert sind, in jeder Aktion
wiederverwendet zu werden: eine nicht unterstützte Eingabeform ablehnen,
bevor irgendeine Arbeit beginnt, sich davor schützen, nichts zu speichern,
IDs einmal statt in jedem Leser neu zuordnen, und in zwei Tabellen innerhalb
einer Transaktion schreiben, sodass eine Vorlage niemals mit Metadaten, aber
ohne Dateien enden kann.

## Editor-Modell

Design ist bei der Arbeit mit mehreren Bildschirmen übersichtsorientiert.
Nach der Generierung oder größeren Aktualisierungen öffnet der Editor die
Bildschirmübersicht: eine unendliche Arbeitsfläche, auf der jeder Bildschirm
ein statischer Rahmen ist, den Sie auswählen, verschieben, in der Größe
ändern, ablegen oder duplizieren können. Verwenden Sie die
Vollansicht-Schaltfläche eines Rahmens, wenn ein Bildschirm fokussiertes
Scrollen oder Prototyp-Interaktion braucht.

Der Einzelbildschirmmodus ist für Scrollen, Interaktion mit
Prototypverhalten und die Bearbeitung der DOM-/Code-Ebenen innerhalb einer
gerenderten Datei gedacht. Das Ebenenfenster spiegelt diese Trennung wider:
Bildschirme sind Rahmen der obersten Ebene, mit verschachtelten
DOM-/Code-Ebenen für den aktiven Bildschirm darunter.

Jeder Bildschirm ist ein Dokument, das bei unterschiedlichen Breiten
gerendert wird, keine separaten Kopien pro Breakpoint: Ein Basis-Rahmen (der
breiteste) kaskadiert nach unten, und Bearbeitungen, die bei einem
schmaleren aktiven Breakpoint vorgenommen werden, bleiben als
breitenbezogene Überschreibungen darüber erhalten.

## Erweiterungen im Editor

Der Editor enthält nach **Tweaks** einen Inspektor-Tab **Extensions**. Er
funktioniert wie eine design-spezifische Plugin-Spur: Benutzer können auf
**+ Extension** klicken, um den Agenten zu bitten, eine Erweiterung zu
bauen, oder eine Erweiterung installieren, die den Slot
`design.editor.inspector` deklariert, unter Verwendung der
Framework-Aktionen `create-extension`, `add-extension-slot-target` und
`install-extension`, nicht einer design-spezifischen Aktion.

Design-Erweiterungen werden über die Standard-Erweiterungssandbox inline
neben der Arbeitsfläche gerendert. Der Host übergibt `window.slotContext`
und `window.onSlotContext(...)`-Updates mit der aktuellen `designId`, der
aktiven Datei, der Bildschirmliste, ausgewählten Bildschirm-IDs, Metadaten
des ausgewählten Elements, Ansichtsmodus, Zoom, aktivem Werkzeug und
Tweak-Werten. So kann eine Erweiterung Informationen zur aktuellen Auswahl
anzeigen, Stilsteuerungen anbieten oder kompakte Workflows rund um das
geöffnete Design erstellen.

Für deterministische Arbeit können Erweiterungen App-Aktionen über die
Erweiterungsbrücke aufrufen. Für KI-gesteuerte Änderungen sollte die
Erweiterung `agentNative.chat.send(...)` mit dem Selektor/Quell-ID des
ausgewählten Elements und der gewünschten Änderung aufrufen. Der Agent
sollte zuerst `view-screen` aufrufen und dann `apply-visual-edit` für
Stil-, Klassen-, Text- oder Verschiebungsänderungen an Elementen verwenden,
oder `update-design` / `generate-design` mit `canvasFrames` für Änderungen
an der Platzierung der Arbeitsfläche. Siehe
[Extensions](/docs/extensions#capabilities) für Sandbox, dauerhafte Daten
und Bridge-APIs.

## Anpassen

Design ist eine vollständige, klonbare Vorlage. Einige praktische
Erweiterungsideen:

- „Füge ein wiederverwendbares E-Commerce-Designsystem mit unseren Tokens und Beispielkomponenten hinzu.“
- „Füge einen Exportschritt hinzu, der das ZIP in unser internes Überprüfungssystem hochlädt.“
- „Lass mich vorhandenes Landingpage-HTML einfügen und den Agenten um drei stärkere Versionen bitten.“
- „Füge eine gespeicherte Bibliothek mit Eingabeaufforderungen für Produktseiten-, Dashboard- und Onboarding-Bildschirm-Briefings hinzu.“
- „Füge eine benutzerdefinierte PDF-Export-Voreinstellung für die Überprüfung durch Stakeholder hinzu.“

Der Agent bearbeitet Routen, Komponenten, Aktionen und SQL-gestützte Modelle
nach Bedarf. Siehe [Vorlagen](/docs/cloneable-saas) für den vollständigen
Klon-, Anpassungs- und Bereitstellungsablauf, und [Erste
Schritte](/docs/getting-started), wenn dies Ihre erste agentennative Vorlage
ist.
