# Datenbank

Jede agentennative App speichert ihren Zustand in SQL. UI und Agent lesen und schreiben dieselben Tabellen über dieselben Actions, mit demselben [Drizzle ORM](https://orm.drizzle.team)-Client. Wenn eine Seite Daten ändert, sieht die andere das über die Polling-Schicht.

## Hosting-Optionen {#hosting}

Die App erkennt anhand von `DATABASE_URL`, welches Backend verwendet werden soll. Ist die Variable nicht gesetzt, greift sie auf eine lokale SQLite-Datei zurück, sodass Sie ohne jede Einrichtung starten können.

### Standard: SQLite-Datei {#default-sqlite}

Wenn `DATABASE_URL` nicht gesetzt ist, erstellt die App eine SQLite-Datenbank unter `data/app.db`. Keine Konfiguration erforderlich. Starten Sie den Dev-Server, und die Datei wird beim ersten Lauf angelegt.

Dies ist nur für die lokale Entwicklung gedacht. Container, serverlose Funktionen und Vorschauumgebungen setzen ihr Dateisystem zwischen Neustarts möglicherweise zurück, sodass eine lokale SQLite-Datei verschwinden kann. Legen Sie `DATABASE_URL` vor dem Deployment auf eine dauerhaft gehostete Datenbank fest.

### Lokales Postgres: PGlite {#local-pglite}

Um lokal gegen den Postgres-Dialekt zu entwickeln, ohne Docker oder eine gehostete Datenbank zu benötigen, installieren Sie das optionale PGlite-Paket und setzen Sie `DATABASE_URL`:

```bash
pnpm add @electric-sql/pglite@^0.5.3
```

```bash
DATABASE_URL=pglite:./data/pglite
```

[PGlite](https://pglite.dev/) betreibt eine In-Process-WASM-Postgres-Datenbank. Damit können Sie Postgres-spezifische Schemaprobleme erkennen, bevor Sie deployen, während die Einrichtung so einfach bleibt wie beim SQLite-Standard. Wie SQLite ist es reiner lokaler Speicher. Verwenden Sie es nicht für Produktion oder gemeinsam genutzte Umgebungen.

### Produktionsdatenbank {#production}

Legen Sie `DATABASE_URL` in Ihrer `.env`-Datei oder der Umgebung Ihres Deploy-Providers fest, um eine gehostete Datenbank zu verbinden:

```bash
# Neon Postgres
DATABASE_URL=postgres://user:pass@ep-cool-name-123456.us-east-2.aws.neon.tech/mydb?sslmode=require

# Supabase Postgres
DATABASE_URL=postgres://postgres.xxxx:pass@aws-0-us-east-1.pooler.supabase.com:6543/postgres

# Einfaches Postgres
DATABASE_URL=postgres://user:pass@localhost:5432/mydb

# Turso (libSQL). Erfordert außerdem DATABASE_AUTH_TOKEN.
DATABASE_URL=libsql://my-db-org.turso.io
```

Das Framework erkennt den Dialekt automatisch anhand des URL-Präfixes und konfiguriert Drizzle entsprechend.

### Von Builder.io verwaltete Datenbank {#builder-managed}

_Geplant (noch nicht verfügbar):_ Wenn Ihre App mit Builder.io verbunden ist, kann sie eine verwaltete Datenbank nutzen, die automatisch bereitgestellt wird – ganz ohne Connection Strings.

## Einrichten der Datenbank {#setup}

Eine App, die die Datenbank verwendet, benötigt drei Dateien:

- `server/db/schema.ts`: Tabellendefinitionen
- `server/db/index.ts`: das typisierte DB-Client-Singleton
- `server/plugins/db.ts`: Migrationen, die beim Start ausgeführt werden

### 1. Schema definieren {#schema}

Importieren Sie Schema-Helfer aus `@agent-native/core/db/schema`. Importieren Sie niemals direkt aus `drizzle-orm/sqlite-core` oder `drizzle-orm/pg-core`. Die Framework-Helfer erzeugen dialektunabhängige Definitionen, die über alle unterstützten Backends hinweg funktionieren.

```ts filename="server/db/schema.ts"
import { integer, now, table, text } from "@agent-native/core/db/schema";

export const tasks = table("tasks", {
  id: text("id").primaryKey(),
  title: text("title").notNull(),
  priority: integer("priority").notNull().default(0),
  done: integer("done", { mode: "boolean" }).notNull().default(false),
  ownerEmail: text("owner_email").notNull(),
  createdAt: text("created_at").notNull().default(now()),
});
```

| Helfer    | Zweck                                                                                 |
| --------- | ------------------------------------------------------------------------------------- |
| `table`   | Definiert eine Tabelle; delegiert an `pgTable` oder `sqliteTable`                     |
| `text`    | Textspalte, unterstützt `{ enum: [...] }`                                             |
| `integer` | Integer-Spalte, `{ mode: "boolean" }` wird dem booleschen Wert in Postgres zugeordnet |
| `real`    | Float-Spalte. Wird auf SQLite zu `real`, auf Postgres zu `double precision`           |
| `now`     | Dialektunabhängiger aktueller Zeitstempel für `.default(now())`                       |

Siehe [Daten auf Benutzer beschränken](#scoping) weiter unten.

### 2. DB-Client erstellen {#db-client}

Jede App erstellt einen verzögerten (lazy) Singleton-Drizzle-Client, indem sie `createGetDb(schema)` aufruft. Der kanonische Speicherort ist `server/db/index.ts`:

```ts filename="server/db/index.ts"
import { createGetDb } from "@agent-native/core/db";
import * as schema from "./schema.js";

export const getDb = createGetDb(schema);
```

`createGetDb` gibt eine `getDb()`-Funktion zurück, die beim ersten Aufruf die Datenbankverbindung öffnet und bei nachfolgenden Aufrufen dieselbe typisierte Drizzle-Instanz zurückgibt. Sie liest `DATABASE_URL` zur Laufzeit, um zu bestimmen, welches Backend und welcher Dialekt verwendet werden.

Importieren Sie `getDb` in Actions und Routen von diesem vorlagenlokalen Pfad. Importieren Sie nicht direkt aus `@agent-native/core`. Der Core-Export ist untypisiert; der lokale Export trägt Ihre Schematypen.

`runMigrations` führt jeden Eintrag einmal der Reihe nach aus und protokolliert dann die Version, sodass sie bei zukünftigen Neustarts übersprungen wird. Einträge sind idempotent. Das Plugin kann bei jedem Start gefahrlos aufgerufen werden.

<Callout tone="risk">
  Führen Sie `drizzle-kit push` niemals gegen eine Produktionsdatenbank aus.
  Vorlagenschemata definieren nur app-spezifische Tabellen; sie enthalten keine
  zentralen Framework-Tabellen (`user`, `session`, `application_state` und
  andere). Wird `drizzle-kit push` gegen die Produktion ausgeführt, erkennt es
  diese Tabellen als unbekannt und versucht, sie zu löschen, was zu sofortigem
  Datenverlust führt.
</Callout>

`drizzle.config.ts` im Root jeder App konfiguriert drizzle-kit für die lokale Schema-Inspektion in der Entwicklung:

```ts filename="drizzle.config.ts"
import { createDrizzleConfig } from "@agent-native/core/db/drizzle-config";
export default createDrizzleConfig();
```

Verwenden Sie `pnpm db:generate`, um Ihr Schema zu inspizieren, und `pnpm db:push` ausschließlich gegen eine lokale Datenbank.

### 4. Abfragen in Actions {#querying}

Rufen Sie `getDb()` aus Ihren Actions auf, um den typisierten Drizzle-Client zu erhalten. Verwenden Sie den Query-Builder von Drizzle und die portablen Operatoren aus `drizzle-orm`:

```ts
import { and, desc, eq } from "drizzle-orm";
import { getDb } from "../server/db/index.js";
import * as schema from "../server/db/schema.js";

const db = getDb();

const openTasks = await db
  .select()
  .from(schema.tasks)
  .where(
    and(eq(schema.tasks.ownerEmail, userEmail), eq(schema.tasks.done, false)),
  )
  .orderBy(desc(schema.tasks.createdAt));

await db
  .update(schema.tasks)
  .set({ done: true })
  .where(eq(schema.tasks.id, taskId));
```

## Daten auf Benutzer beschränken {#scoping}

Alle Lese- und Schreibvorgänge gegen benutzerorientierte Tabellen müssen auf den authentifizierten Benutzer eingegrenzt werden. Das Framework bietet zwei Muster, je nachdem, ob die Daten privat oder teilbar sind.

**Private Daten:** Tabellen, die einem einzigen Benutzer gehören. Fügen Sie dem Schema `ownerEmail: text("owner_email").notNull()` hinzu und nehmen Sie `eq(table.ownerEmail, userEmail)` in jede Abfrage auf:

```ts
.where(eq(schema.tasks.ownerEmail, userEmail))
```

**Gemeinsam genutzte Ressourcen:** Tabellen, die mit anderen Benutzern oder Organisationen geteilt werden können. Verbreiten Sie im Schema `...ownableColumns()` statt eines bloßen `owner_email`. Dies fügt in einem Aufruf `owner_email`, `org_id` und `visibility` hinzu und erstellt mit `createSharesTable` eine begleitende Shares-Tabelle:

```ts filename="server/db/schema.ts"
import {
  table,
  text,
  ownableColumns,
  createSharesTable,
} from "@agent-native/core/db/schema";

export const decks = table("decks", {
  id: text("id").primaryKey(),
  title: text("title").notNull(),
  ...ownableColumns(),
});
export const deckShares = createSharesTable("deck_shares");
```

Verwenden Sie dann `accessFilter` aus `@agent-native/core/sharing` in Listenabfragen statt einer manuellen `eq`-Prüfung:

```ts
import { accessFilter } from "@agent-native/core/sharing";

const rows = await db
  .select()
  .from(schema.decks)
  .where(accessFilter(schema.decks, schema.deckShares));
```

`accessFilter` erstellt eine Abfrage, die Zeilen zulässt, die dem Aufrufer gehören, die mit seiner Organisation geteilt wurden, und die explizit mit ihm geteilt wurden. Sie legt keine Zeilen anderer Benutzer offen.

Das vollständige Modell finden Sie unter [Security — Data Scoping](/docs/security#data-scoping) und [Sharing](/docs/sharing#building).

## SQL-gestützte Synchronisierung {#sync}

Agent-native verlässt sich nicht auf Dateisystem-Watcher oder klebrigen In-Memory-Zustand. Wenn eine Action in die Datenbank schreibt, erhöht sich eine Sync-Version. Der Client-Hook `useDbSync()` pollt `/_agent-native/poll` und invalidiert React-Query-Caches, sobald er eine höhere Version sieht.

Das funktioniert über serverlose und Multi-Instanz-Deployments hinweg, weil die Datenbank der Koordinationspunkt ist. Wenn Sie benutzerdefinierte Mutationen außerhalb von Actions schreiben, verwenden Sie Framework-Helfer oder lösen Sie die passende Sync-Invalidierung aus, damit offene UIs sich aktualisieren.

## Rohes SQL {#raw-sql}

Verwenden Sie für erweiterte Abfragen, Health-Checks oder einmalige Wartungsarbeiten, die der Drizzle-Query-Builder nicht ausdrücken kann, `getDbExec` aus `@agent-native/core/db`:

```ts
import { getDbExec, isPostgres, intType } from "@agent-native/core/db";

const { rows } = await getDbExec().execute({
  sql: `SELECT id, title FROM tasks WHERE owner_email = ? LIMIT ?`,
  args: [userEmail, 50],
});
```

`getDbExec` konvertiert `?`-Parameter für Postgres automatisch in `$1`, `$2` usw. Verwenden Sie `isPostgres()`, um nach Dialekt zu verzweigen, und `intType()`, um den richtigen Integer-Typ für das aktuelle Backend zurückzugeben. Bevorzugen Sie für normale Lese- und Schreibvorgänge den Drizzle-Query-Builder. Rohes SQL umgeht die Typsicherheit und ist schwerer zu warten.
