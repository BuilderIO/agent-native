# Verwaltete Bereitstellungen

Verwenden Sie einen Workspace für interne Apps einer Organisation. Die Organisation bildet die Mitgliedschafts- und Datengrenze. Der Workspace bündelt Bereitstellung und Konfiguration für eine oder mehrere Apps.

## Registrierung und Org-Erstellung schließen

```dotenv
AUTH_SIGNUP=invited
ORG_CREATION=closed
AUTO_CREATE_DEFAULT_ORG=0
AUTH_BOOTSTRAP_ADMINS=admin@example.com
AUTH_REQUIRE_EMAIL_VERIFICATION=1
```

Bei `AUTH_SIGNUP=invited` benötigt ein neues Konto eine offene Einladung, eine verifizierte erlaubte E-Mail-Domain oder eine Adresse aus `AUTH_BOOTSTRAP_ADMINS`. Die Prüfung gilt für Passwort-, Magic-Link- und Social-Registrierung. Domain-Beitritt ist keine Einladung und weist keine App-Rolle zu.

Der erste angemeldete Bootstrap-Admin erstellt die kanonische Organisation und wird Eigentümer. Gibt es bereits genau eine Organisation, wird der Admin dort Eigentümer. Bei mehreren Organisationen nimmt der Bootstrap keine Auswahl vor. Konfigurieren Sie anschließend die erlaubte Domain und laden Sie das Team unter **Team settings** ein.

## Unternehmensschlüssel und Rollen

Ein Owner oder Admin kann einen LLM-Schlüssel für die Organisation speichern. Ein persönlicher Schlüssel hat Vorrang, bis das Mitglied den Organisationsschlüssel auswählt. App-Rollen gelten innerhalb einer App. Mitglieder können mehrere Rollen haben. Admins können code-definierte Berechtigungen Rollen zuordnen und diese Zuordnung ohne Deployment ändern.

## E-Mail-Änderung

Benutzer ändern ihre Anmelde-E-Mail über die Kontoeinstellungen mit E-Mail-Bestätigung. Für eine administrative Migration führen Sie `agent-native identity rekey --from old@example.com --to new@example.com` in jeder App einzeln aus. Prüfen Sie die Tabellen- und Zeilenzahlen vor `--yes`. Audit-Einträge bleiben unverändert. Die Umstellung auf unveränderliche Principal-IDs ist nach 1.0 geplant.

## Organisations-SSO und Verzeichnisbereitstellung

Organisations-SSO und SCIM sind optionale Funktionen. Aktivieren Sie `AUTH_SSO=1` und `AUTH_SCIM=1`, um die Einstellungen unter Team-Einstellungen einzublenden. Setzen Sie die Flags sowohl in der Build- als auch in der Laufzeitumgebung; Änderungen nach der Bereitstellung erfordern einen erneuten Build. Konfigurieren Sie zuerst die Organisationsdomain. Fügen Sie einen OIDC- oder SAML-Anbieter mit Aussteller, Client-ID und Geheimnis oder SAML-Einstiegspunkt, Entitäts-ID und eingefügten IdP-Metadaten hinzu. Die Einstellungen zeigen Weiterleitungs-URI und SP-Metadaten. Erstellen Sie den DNS-TXT-Eintrag `_better-auth-token-<provider-id>.<organization-domain>` mit dem angezeigten Wert. Warten Sie die DNS-Propagation ab und verifizieren Sie die Domain. Danach kann ein Admin Google oder einen verifizierten SSO-Anbieter voraussetzen. Erstellen Sie eine SCIM-Verbindung und kopieren Sie das einmal angezeigte Token zusammen mit dem Endpunkt in den Identitätsanbieter. Richten Sie in Okta oder Microsoft Entra ID eine OIDC- oder SAML-Unternehmensanwendung ein. Für Provisionierung konfigurieren Sie den SCIM-Client und testen Benutzererstellung, Aktualisierung und Deaktivierung zunächst mit einer kleinen Gruppe. Dies ist unabhängig von der App-übergreifenden Identitätsföderation.

Serverzugriffe verwenden `accessFilter()` und `assertAccess()`. Agent-SQL verwendet temporäre gefilterte Views. `pnpm guards` enthält die Prüfung auf nicht eingeschränkte Abfragen. RLS ist nicht aktiv und als Härtung nach 1.0 geplant. Für mehrere interne Apps wählen Sie einen Workspace. Eine unabhängige App oder ein Prototyp kann standalone laufen. Siehe [Standalone oder Workspace](/docs/multi-app-workspace#standalone-or-workspace) und [Versionierung und Stabilität](/docs/versioning-and-stability).
