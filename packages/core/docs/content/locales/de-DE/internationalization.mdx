# Internationalisierung

Agent Native-Apps können die Benutzeroberfläche von Framework und Vorlage über die
gemeinsame `@agent-native/core/client/i18n`-Laufzeit lokalisieren. Das Framework
speichert die Sprachauswahl des Benutzers in den SQL-Einstellungen, macht sie als
Actions verfügbar und greift auf Englisch zurück, wenn eine App eine
Zeichenfolge noch nicht übersetzt hat.

## Laufzeit

Verwenden Sie den Provider über `AppProviders`:

```tsx
import { AppProviders } from "@agent-native/core/client/hooks";
import { getLocaleInitScript } from "@agent-native/core/client/i18n";
import { i18nCatalog } from "./i18n";

const LOCALE_INIT_SCRIPT = getLocaleInitScript();

<script
  data-agent-native-locale-init
  dangerouslySetInnerHTML={{ __html: LOCALE_INIT_SCRIPT }}
/>;

<AppProviders queryClient={queryClient} i18n={{ catalog: i18nCatalog }}>
  <Outlet />
</AppProviders>;
```

`getLocaleInitScript()` legt vor der Hydration durch React die anfänglichen
Werte für `lang`, `dir` und `window.__AGENT_NATIVE_LOCALE__` fest. Öffentliche
SSR-Routen können `resolveLocaleFromRequest()` aus `@agent-native/core/server`
aufrufen und das aufgelöste Gebietsschema beziehungsweise den Katalog an dieses
Skript übergeben, um Abweichungen bei der Hydration zu vermeiden.

## Kataloge

Jede lokalisierte Vorlage bewahrt ihre Kataloge unter `app/i18n/` auf:

```ts filename="app/i18n/index.ts"
import { createAgentNativeI18nCatalog } from "@agent-native/core/client/i18n";
import enUS from "./en-US";

export const i18nCatalog = createAgentNativeI18nCatalog({
  messages: enUS,
  localeLoaders: {
    "zh-CN": () => import("./zh-CN"),
    "zh-TW": () => import("./zh-TW"),
    "es-ES": () => import("./es-ES"),
    "fr-FR": () => import("./fr-FR"),
    "de-DE": () => import("./de-DE"),
    "ja-JP": () => import("./ja-JP"),
    "ko-KR": () => import("./ko-KR"),
    "pt-BR": () => import("./pt-BR"),
    "hi-IN": () => import("./hi-IN"),
    "ar-SA": () => import("./ar-SA"),
  },
});
```

`messages` bündelt `en-US` direkt, sodass es immer verfügbar ist, bevor ein
Gebietsschema geladen wird. `localeLoaders` lädt jeden anderen Katalog per
dynamischem Import, sodass Benutzer nur das aktive Gebietsschema
herunterladen. Die unterstützten Gebietsschemacodes sind `en-US`, `zh-CN`,
`zh-TW`, `es-ES`, `fr-FR`, `de-DE`, `ja-JP`, `ko-KR`, `pt-BR`, `hi-IN` und
`ar-SA`.

Diese Liste ist durch das Framework fest vorgegeben. Sie ist nicht nur das,
was dieses Beispiel zufällig bündelt. `LocaleCode` ist eine TypeScript-Union
genau dieser Codes, und `set-localization-preference` lehnt zur Laufzeit
alles andere ab. Jedes Gebietsschema benötigt außerdem vom Framework
kuratierte Metadaten, etwa die Textrichtung für Sprachen, die von rechts nach
links geschrieben werden. Ein neues Gebietsschema hinzuzufügen bedeutet, das
Framework selbst zu erweitern, nicht nur eine Katalogdatei zur App
hinzuzufügen.

`createAgentNativeI18nCatalog` akzeptiert außerdem ein optionales
`sourceLocale`, das standardmäßig `en-US` ist, sowie ein optionales
`supportedLocales`-Array. Setzen Sie `supportedLocales`, wenn eine App
Übersetzungen nur für einen Teil der Gebietsschemata des Frameworks statt für
alle zehn ausliefert. Der Standardwert umfasst jedes vom Framework
unterstützte Gebietsschema. `LanguagePicker` listet nur Gebietsschemata aus
dieser Menge auf, und jedes erkannte oder angeforderte Gebietsschema
außerhalb dieser Menge fällt auf `sourceLocale` zurück.

## UI

Verwenden Sie `useT()`, um Schnittstellenzeichenfolgen zu übersetzen:

```tsx
import { useT } from "@agent-native/core/client/i18n";

function Greeting({ name }: { name: string }) {
  const t = useT();
  return <p>{t("greeting.hello", { name })}</p>;
}
```

Verwenden Sie `useFormatters()` für Datumsangaben, Zahlen, relative Zeit und
Listen. Fügen Sie keine gebietsschemaabhängige Datums- oder Zahlenformatierung
in Übersetzungszeichenfolgen ein.

Platzieren Sie `<LanguagePicker />` überall dort, wo die App einem Benutzer
erlaubt, seine Sprache zu ändern. Das Standardmuster für die
Einstellungsseite, einschließlich der Frage, wo `openAgentSettings()`
hineinpasst, finden Sie unter
[Toolkit: Settings](/docs/toolkit-settings).

## Actions und Persistenz

Jede App erbt:

- `get-localization-preference` — liest die `{ locale, timezone }` des aktuellen Benutzers
- `set-localization-preference` — legt `locale` und/oder `timezone` fest, jeweils optional

`locale` ist `"system"` oder ein unterstütztes BCP-47-Gebietsschema.
`timezone` ist `"system"` oder eine IANA-Zone wie `America/New_York`. Sie
existiert, damit geplante Aufgaben und Automatisierungen in der Zeitzone des
Benutzers statt in der des Hosts ausgeführt werden. Wenn nur ein Feld gesetzt
wird, bleibt das andere unverändert, da `set-localization-preference` den
gespeicherten Wert zusammenführt, statt ihn zu überschreiben.

Der dauerhafte Wert befindet sich in benutzerbezogenen SQL-Einstellungen
unter `localization`. `localStorage` wird nur für die Vorhydration und den
anonymen Fallback verwendet. Das aktive Gebietsschema wird als
Umgebungskontext in den Anwendungsstatus gespiegelt, sodass Agenten die
aktuelle Sprache der Benutzeroberfläche sehen können.

## Guard

Ausführen:

```bash
pnpm guard:i18n-catalogs
```

Für App- und Vorlagenkataloge prüft der Guard:

- Gebietsschema-Dateinamen, Schlüsselparität, Platzhalterparität und veraltete Schlüssel
- Doppelte Schlüssel und übrig gebliebene, nur für die Entwicklung gedachte Marker
- Kontamination durch die falsche Schrift, zum Beispiel chinesischer Text innerhalb eines arabischen Katalogs
- CLDR-Pluralkategorien über `Intl.PluralRules`
- `t()`-Aufrufe im App-Quellcode, deren Schlüssel im englischen Katalog fehlt

Der Guard prüft die Struktur, nicht die Übersetzungsqualität. Gut sichtbare
Zeichenfolgen brauchen weiterhin eine menschliche Überprüfung.

Übersetzen Sie keine stabilen Bezeichner wie Aktionsnamen, Routen,
Enum-Werte, App-Statusschlüssel, Datenbankwerte, Protokollfelder,
Umgebungsvariablennamen oder Anbieternamen.
