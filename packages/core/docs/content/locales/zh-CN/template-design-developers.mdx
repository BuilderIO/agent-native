# 开发者指南

本页适用于任何想要定制或直接基于 Design 模板进行构建的人：快速入门、每一个 action、数据模型、一次 action 的逐步解析、路由结构，以及如何在此基础上进行扩展。有关该应用的功能，请参阅 [Design](/docs/template-design)。

## 快速入门

<Steps>

### 创建应用

```bash
npx @agent-native/core@latest create my-design --standalone --template design
cd my-design
pnpm install
```

这需要先安装 [Node.js](https://nodejs.org) 22.22 或更高版本，以及
[pnpm](https://pnpm.io)。如果您还没有安装它们，或者还没有配置好 LLM
连接（Builder.io、Anthropic/OpenAI 密钥，或本地 Ollama），请参阅
[快速入门](/docs/getting-started)。如果想要一个把 Design 和其他应用放在
一起的工作区，请运行 `npx @agent-native/core@latest create my-platform`，
并在设置过程中选择 Design。

### 启动开发服务器

```bash
pnpm dev
```

应用会在 `http://localhost:8099` 打开，这是 Design 的默认开发端口。Design 在
不连接任何外部服务的情况下也能完全正常运行。只有当您在完成相应设置之
前尝试使用 Figma 导入或完整应用构建时，才会遇到连接提示。

</Steps>

## Action 清单

每一个 Design 专属的操作都是 `templates/design/actions/` 目录下的一个
TypeScript 文件，自动挂载在 `POST /_agent-native/actions/:name` 上，
并可作为 `pnpm action <name>` 从 CLI 运行。

### 设计

| Action                    | 作用                                       |
| ------------------------- | ------------------------------------------ |
| `create-design`           | 创建空的设计外壳                           |
| `generate-design`         | 写入生成的 HTML/JSX 文件内容               |
| `edit-design`             | 对现有文件进行精确的查找/替换编辑          |

## 数据模型

所有数据通过 Drizzle ORM 存储在 SQL 中。架构：
`templates/design/server/db/schema.ts`。设计和设计系统都带有标准的
`ownableColumns` 以及一个匹配的框架共享表，因此它们可以纳入按用户/按
组织的共享模型。

下表涵盖可拥有的核心资源：设计、文件、模板、版本和设计系统。

| 表                                       | 它包含什么                                                                                                                              |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `designs`                                | 一个设计项目——`title`、`description`、`project_type`（`prototype` / `other`）、`data` JSON blob，以及一个可选的 `design_system_id` 关联 |
| `design_files`                           | 属于某个设计的各个文件（`filename`、`content`、默认为 `html` 的 `file_type`）                                                           |
| `design_templates`                       | 可复用的模板元数据、尺寸、默认值、源设计引用，以及锁定图层数量                                                                          |
| `design_template_files`                  | 用户从模板开始时，快照并复制到一个正常可编辑设计中的模板文件                                                                            |
| `design_template_shares`                 | 框架共享表，用于私有、组织内、明确共享和公开发现的模板                                                                                  |
| `design_versions`                        | 一个设计带有可选 `label` 的时间点 `snapshot`，用于历史记录和回滚                                                                        |
| `design_systems`                         | 可复用的品牌令牌——`data`（颜色/排版/间距）、`assets`、`custom_instructions`，以及一个 `is_default` 标志                                 |
| `design_shares` / `design_system_shares` | 框架共享表，将主体（用户或组织）映射到角色（查看者、编辑者、管理员）                                                                    |

一个设计项目在拥有内容之前只是一个外壳：`create-design` 创建一个空
行（`data: "{}"`），然后 `generate-design` 写入实际的独立 HTML/JSX
文件。生成的工件、可编辑的源，以及每一次导出，都来自同一个 HTML，因
此不存在一种需要单独转换的"AI 模型稿"格式。一个已关联的设计系统会提
供令牌和 `custom_instructions`，代理在每一次生成时都会遵循它们。

另外七个表支撑着本页其他部分介绍的功能，而不是核心资源模型：
`design_localhost_connections` 和 `design_localhost_write_grants` 支
撑[本地应用导入](/docs/template-design-features#import)，
`component_index` 支撑[Design 标签页的组件区块](/docs/template-design-features#design-tab)，
`motion_timeline` 支撑每个元素可编辑的动效时间轴（编辑器中的动效面
板），`design_state` 保存一个设计的具名备用状态、静态固件和真实应用
的捕获内容，`design_fusion_edits` 支撑上文[完整应用构建](#full-app-building)
中介绍的 fusion 编辑队列，`design_review_snapshot` 缓存
`get-design-review` 背后的无障碍性发现和视觉差异，即上文
[质量](#quality)中介绍的内容。

持久化的审阅评论和讨论串（`get-review-feedback`、
`resolve-review-thread` 及其他）根本不是一个设计专属的表：它们是来自
`@agent-native/core/review`（`agent_review_comments` /
`agent_review_statuses`）的共享框架审阅系统，以任何应用都可以接入的
同一种方式，关联到一个设计上。用户可见的行为请参阅
[评论标签页](/docs/template-design-features#comments-tab)。

## 一次 action 逐步解析

`save-design-as-template` 展示了值得在任何 action 中复用的一些模
式：在做任何工作之前拒绝一种不受支持的输入形态、防止保存空内容、只
统一重映射一次 id 而不是在每个读取处重复处理，以及在一次事务中写入
两个表，这样一个模板就永远不会出现有元数据却没有文件的情况。

## 编辑器模型

Design 对多屏工作采用概览优先的方式。生成或进行大范围更新之后，编辑器会
打开屏幕概览：一个无限画布，其中每个屏幕都是一个可以选择、移动、调整
大小、拖放或复制的静态框架。当某个屏幕需要聚焦滚动或原型交互时，使用
框架的完整视图按钮。

单屏模式用于滚动、与原型行为交互，以及编辑一个已渲染文件内部的
DOM/代码层。图层面板也反映这种划分：屏幕是顶层框架，活动屏幕的
DOM/代码层嵌套在其下方。

每个屏幕都是同一份文档在不同宽度下的渲染，而不是每个断点各有一份独
立的副本：一个基准（最宽）框架向下级联，在某个更窄的激活断点上所做的
编辑，会作为宽度限定的覆盖保存在它之上。

## 编辑器扩展

编辑器在**调整**之后包含一个**扩展**检查器标签页。它的运作方式像是
Design 专属的插件通道：用户可以点击**+ 扩展**让代理构建一个扩展，也可以
安装一个声明了 `design.editor.inspector` 插槽的扩展，使用的是框架的
`create-extension`、`add-extension-slot-target` 和 `install-extension`
actions，而不是一个设计专属的 action。

Design 扩展通过标准的扩展沙盒，内嵌渲染在画板旁边。宿主会通过
`window.slotContext` 和 `window.onSlotContext(...)` 更新，传入当前的
`designId`、活动文件、屏幕列表、已选屏幕 id、已选元素元数据、视图模
式、缩放级别、激活工具，以及调整值。这让一个扩展可以显示当前选择的
信息、提供样式控件，或围绕打开的设计构建紧凑的工作流。

对于确定性的工作，扩展可以通过扩展桥调用应用 actions。对于 AI 驱动
的更改，让扩展调用 `agentNative.chat.send(...)`，并附带所选元素的
selector/source id 和请求的更改。代理应先调用 `view-screen`，然后使
用 `apply-visual-edit` 处理元素样式、class、文本或移动方面的更改，
或者使用带 `canvasFrames` 的 `update-design` / `generate-design` 处
理画板放置方面的更改。有关沙盒、持久状态和桥接 API，请参阅
[扩展](/docs/extensions#capabilities)。
