# 多应用工作区中的表单

表单只是 [Dispatch](/docs/template-dispatch) 工作区中众多应用之一。本页介绍这在实践中究竟意味着什么：连接是如何运作的，以及其他应用可以对表单采取哪些具体操作，或向表单发送哪些具体数据。有关概览，请参阅 [表单](/docs/template-forms)。

## 表单如何与 Dispatch 连接

这是否是自动完成的，取决于表单和 Dispatch 是如何被一起搭建起来的，而不取决于两者中任何一个是托管运行还是本地运行。

### 同一工作区：自动完成

如果表单和 Dispatch 是通过 `create` 或 `add-app` 一起生成或添加到同一个 Agent-Native 工作区中，并作为一个整体部署的，那么它们已经共享同一个 `.env`、同一个 `A2A_SECRET` 和同一个工作区注册表。无论该工作区运行在您的本机还是生产环境中，发现和经过身份验证的 A2A 调用都会自动生效，无需任何额外设置。这是基于表单构建真正的多应用产品时应有的搭建方式。

### 独立部署：需要一步手动操作

如果表单和 Dispatch 是两个独立创建的 Agent-Native 项目，它们不会共享密钥，因此还无法互相调用。连接它们需要在双方各执行一步手动操作：添加一个带有共享密钥的 `remote-agents/<id>.json` 资源，可以从设置 → 已连接的代理、Agent 页面的连接标签页，或 Dispatch → 代理 → 添加外部代理来完成。完整的操作步骤请参阅 [A2A 协议](/docs/a2a-protocol)。

要检查您属于哪种情况，可以问任意一个应用的代理“你能看到哪些应用？”。如果表单没有出现在 Dispatch 的回答中，那么您就属于第二种情况。

## 集成策略

**通过 Dispatch 进行自然语言委托。** 一个同级应用不需要任何特殊集成就能与表单协同工作。它可以像您在聊天中那样，向表单的代理提交一条用简单易懂的语言表达的请求，例如“Beta 注册表单有多少条回复”，表单会直接回答或据此执行操作。这正是诸如在 Slack 或 Mail 中收到的一个问题，最终变成表单给出的一个真实答案背后的真实机制：Dispatch（或接收到该消息的应用）把请求委托给表单的代理，表单就像处理任何其他提示一样处理它。

**其他应用直接向表单提交数据。** 对于另一个应用向它发送数据这件事，表单根本不需要 A2A 或 Dispatch。任何应用都可以向表单的公开提交地址发送一个普通的网络请求，就像一位匿名受访者填写公开页面时所做的那样。框架自带的反馈按钮正是以这种方式运作的：它从另一个应用的侧边栏内部，向一个已部署的表单应用发送一条提交，并附带反馈来自哪个页面、哪个应用，表单会把它记录为一条正常的回复。这意味着您工作区中的任何应用都可以在完全不需要 A2A 连接的情况下，仅通过一个普通的网络请求，就把结构化数据发送到表单中。

**保持解耦。** 无论表单是在回答一个委托来的问题，还是在接收一次直接提交，它都不需要知道调用方应用的凭证，调用方应用也不需要知道表单是如何存储数据的。委托请求会像处理任何其他提示一样经过代理，而直接提交则会走人类受访者使用的那个同一个公开地址。
