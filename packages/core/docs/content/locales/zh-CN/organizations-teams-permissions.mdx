# 组织、团队与权限

组织定义团队成员关系和租户边界。工作区汇集应用和部署配置，但不能替代组织。权限必须由服务端检查。在界面隐藏按钮并不等于访问控制。

## 三种角色范围

- 组织角色 `owner`、`admin` 和 `member` 控制团队管理。所有者和管理员管理邮箱域名自动加入；应用之间共享的 A2A 密钥只有所有者可以管理。
- 应用角色控制单个应用内的操作。一个成员可以有多个应用角色。
- 资源角色 `viewer`、`editor` 和 `admin` 控制单条数据的访问。

应用代码声明角色和权限键。管理员可以在团队页面替换成员的整个角色集合，并将已声明的权限映射到角色。没有覆盖设置时，使用应用默认值。邀请可预先包含应用角色。应用管理员不会因此获得组织管理权限。

邀请和配置请参阅[管理式部署指南](/docs/administered-deployments)。数据访问请参阅[数据范围控制](/docs/security#data-scoping)。

## 可选权限策略

默认情况下，权限检查要求已分配的应用角色。通过 `defineAppRoles` 的可选第二个参数，可以更改服务器端策略。Forms 使用：

```ts
const formsAccess = defineAppRoles(
  {
    appId: "forms",
    roles: ["editor", "reviewer"] as const,
    defaultRole: "editor",
    permissions: {
      "forms.edit": ["editor"],
      "forms.review": ["editor", "reviewer"],
    },
  },
  { unassignedRole: "editor", allowOrgAdmins: true },
);
```

- `unassignedRole` 将已声明角色的权限应用于没有应用角色分配的有效成员。权限覆盖仍然生效。它不会创建角色分配，也不适用于已移除的成员或仅包含已废弃角色的分配。清除全部分配后，会恢复此默认行为。
- `allowOrgAdmins: true` 允许组织的有效所有者和管理员通过任何已声明的应用权限检查，不受其应用角色或权限覆盖影响。它不会向应用管理员授予组织管理权限。

这些选项仅影响 `requirePermission` 和 `assertPermission`。`resolve`、`requireAny` 和 `assertAny` 仍使用显式分配；`defaultRole` 仍仅用于显示。省略选项时保留严格策略。两者都不替代资源授权：请保留 `accessFilter` 和 `assertAccess` 检查。

Forms 保留现有未分配角色成员的编辑权限。显式分配的 Reviewer 可以审核提交，但不能编辑表单；Editor 可以执行两种操作。资源共享仍决定他们能访问哪些表单和提交。

编辑组织所属的表单或审核其提交，要求调用者是该表单所在组织的有效成员，除非共享系统将调用者识别为表单所有者。仅有直接共享权限并不足以通过此应用权限检查。

## 用户组 {#user-groups}

组织可以创建由当前成员组成的可复用用户组。所有者和管理员负责管理组成员，一个人可以加入多个组。应用可以使用用户组共享支持组共享的资源，也可以限制哪些人可以使用工作区连接。

用户组是访问名单，不是下级团队。它没有独立的组织或应用角色、数据边界，也没有团队专属的设置、说明、上下文、技能、记忆或工作视图。将资源共享给用户组后，该资源的共享角色会授予组内所有当前成员。访问者仍须属于资源所在的组织。

详情请参阅[共享与隐私 → 组共享](/docs/sharing#group-grants)和[工作区连接](/docs/workspace-connections)。
