# 多应用工作区中的聊天

聊天只是 [Dispatch](/docs/template-dispatch) 工作区中众多应用之一。本页
介绍这在实践中究竟意味着什么：连接是如何运作的，以及聊天的代理如何触达
周围的其他应用。有关概览，请参阅 [聊天](/docs/template-chat)。

## 聊天如何与 Dispatch 连接

这是否是自动完成的，取决于聊天和 Dispatch 是如何被一起搭建起来的，而不取
决于两者中任何一个是托管运行还是本地运行。

### 同一工作区：自动完成

如果聊天和 Dispatch 是通过 `create` 或 `add-app` 一起生成或添加到同一个
Agent Native 工作区中，并作为一个整体部署的，那么它们已经共享同一个
`.env`、同一个 `A2A_SECRET` 和同一个工作区注册表。无论该工作区运行在您的
本机还是生产环境中，发现和经过身份验证的 A2A 调用都会自动生效，无需任何
设置。

### 独立部署：需要一步手动操作

如果聊天和 Dispatch 是两个独立创建的 Agent-Native 项目，它们不会共享密
钥，因此还无法互相调用。连接它们需要在双方各执行一步手动操作：添加一个
带有共享密钥的 `remote-agents/<id>.json` 资源，可以从设置 → 智能体 → 子智能体（连接代理），或 Dispatch → 代理 → 添加外部代理来完成。完
整的操作步骤请参阅 [A2A 协议](/docs/a2a-protocol)。

要检查您属于哪种情况，可以问任意一个应用的代理“你能看到哪些应用？”。如
果聊天没有出现在 Dispatch 的回答中，那么您就属于第二种情况。

## 集成策略

**请其他应用帮忙。** 聊天的代理可以查看工作区中有哪些应用，以及每个应用能做什么。
然后它可以请其中一个应用运行某个具体的 action，并在对话中使用得到的答案。例如，在
包含日历的工作区中，您可以问聊天“我明天的日历上有什么？”，代理会把这个问题交给日历，
而不是自己猜测。聊天不需要持有日历与 Google 的连接，日历已经有了。

**聊天作为入口。** 由于每个应用的代理都以相同的方式可被访问，聊天中的一场对话就成了
开始处理其他应用中工作的自然场所。您在一个地方描述想要的内容，由代理决定应该由哪个
应用来处理。聊天在这方面表现出色，因为它没有自己的领域来造成干扰。

**保持解耦。** 聊天从不需要其他应用的凭证，其他应用也不需要聊天的凭证。每个应用保留
自己的连接和自己的数据。聊天只负责传递请求并接收回答。
