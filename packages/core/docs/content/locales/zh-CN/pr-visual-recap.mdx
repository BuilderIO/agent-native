# PR Visual Recap

PR Visual Recap 是一个 GitHub Action，它能把每个 pull request 都
变成一次**可视化代码审查**，不需要任何人记得手动去运行某个命令。
本页面适合任何要安装、配置或加固这个 Action 的人。每次推送时，
一个 LLM 编码代理都会针对 PR diff 运行最新打包的
[`visual-recap`](/docs/template-plan) skill（或者当
`VISUAL_RECAP_SKILL_SOURCE=repo` 时，运行你仓库中提交的那份副本），
把一份结构化的回顾计划发布到托管的 Plans 应用，运行期间显示一个
信息性的 `Visual Recap` 检查项，并更新插入**一条置顶的 PR 评论**，
这条评论会链接到交互式计划，并在评论中直接嵌入一张**内嵌截图**。

这不是一个确定性的 diff 渲染器。该 action 会调用一个真正的编码
代理（默认是 Claude Code CLI，也可以是 OpenAI Codex CLI，或者搭配
某个 OpenAI 兼容服务商的 Agent-Native Code），由它读取改动、判断
哪些内容重要，并通过调用 Plans MCP 工具 `create-visual-recap`——
也就是 `/visual-recap` slash 命令所使用的同一个工具——来撰写这份
回顾。你得到的是一份高空视角的、按 schema/API/前后对比组织的改动
视图，而不是一整墙原始 diff。

这份回顾是**仅供参考、不会阻塞流程的**。它会创建一个检查行，让
审阅者能看到生成正在进行中，但它不是必需检查项，永远不会阻塞 PR，
也永远不能替代阅读真正的 diff。这条置顶评论是一个审阅辅助工具，
不是签核。

## 它做了什么

每次 PR 推送时，该工作流会：

1. 收集 PR 的 base 与 head 之间一份有边界限制的 diff。
2. 创建一个信息性的 `Visual Recap` GitHub 检查项，状态为 `Visual recap in progress`。
3. 针对该 diff 运行已配置的编码代理。代理会读取打包的 `visual-recap` skill 指引（或你仓库固定的副本）并撰写一份回顾，然后通过 `create-visual-recap` 发布它。
4. 读取代理写入 `recap-url.txt` 的已发布计划 URL。
5. 在无头 Chrome 中打开该 URL，并对渲染出的计划分别截取浅色和深色模式的屏幕截图。
6. 把这些 PNG 上传到 Plans 应用上一个已签名的公开图片路由。
7. 更新插入一条置顶的 PR 评论，把截图通过 `<picture>` 元素**内嵌**在评论中（通过 GitHub 的 camo 图片代理提供），紧挨着通向交互式回顾的链接。
8. 把 `Visual Recap` 检查项标记为成功、跳过或中立。

## 安装它

当你交互式地安装 Plans 时，Agent-Native CLI 会询问是否要添加自动的
PR Visual Recap。选择“是”即可写入 GitHub Action，或者随时显式地
添加它：

```bash
npx @agent-native/core@latest skills add visual-plan --with-github-action
```

这会安装 `visual-plan` skill（其中包含该 action 运行所需的
`visual-recap` skill），并把 `.github/workflows/pr-visual-recap.yml`
写入你的仓库。该工作流通过
`npx @agent-native/recap-cli@latest recap <subcommand>` 调用
**已发布的 CLI 子命令**——包括 `gate`、`collect-diff`、
`block-reference`、`scan`、`build-prompt`、`publish`、`shot`、
`comment`、`check` 和 `usage`——因此不会有任何内容作为辅助脚本被
复制进你的仓库。`setup` 和 `doctor` 是你在本地运行的交互式辅助
命令；`gate` 是工作流在每次回顾之前运行的安全门禁步骤。

然后运行引导式的安装辅助命令：

```bash
npx @agent-native/recap-cli@latest recap setup
npx @agent-native/recap-cli@latest recap doctor
```

`recap setup` 会刷新工作流，当能从环境变量或本地 Plans 发布令牌
存储中取到值时，就用 `gh` 设置 GitHub Actions 的 secrets/变量，
并针对任何它无法自动设置的项，打印出确切需要手动执行的命令。
secret 的值是通过标准输入发送给 `gh` 的，而不是作为命令参数。
提交生成的工作流文件并打开一个 PR，即可看到它运行。

默认情况下，该工作流会依据 `@agent-native/recap-cli@latest` 中
最新打包的 `visual-recap` 指引来构建代理提示词，包括该 skill
附带的所有同级参考文件。如果你的仓库有意对其提交的 `visual-recap`
文件夹进行了定制并想固定使用它，请设置仓库变量
`VISUAL_RECAP_SKILL_SOURCE=repo`。

## 运行器选择

该工作流默认运行在 GitHub 托管的 `ubuntu-latest` 运行器上。要使用
其他托管运行器，或者你自己的自托管运行器，请把仓库或组织变量
`VISUAL_RECAP_RUNS_ON` 设置为一个有效的 JSON 字符串，或者运行器
标签组成的 JSON 数组：

```text
"ubuntu-latest"
["self-hosted", "linux", "x64", "visual-recap"]
```

这里的 JSON 引号是必需的。这个设置决定了完整 `recap` 任务所使用的
运行器。要在引导式安装过程中配置它，把同样的 JSON 值传给
`--runs-on`，然后用 `doctor` 验证工作流和运行器的可用性：

```bash
npx @agent-native/recap-cli@latest recap setup --runs-on '["self-hosted","linux","x64","visual-recap"]'
npx @agent-native/recap-cli@latest recap doctor
```

轻量级的安全门禁单独默认使用 GitHub 托管的 `ubuntu-latest`。禁用了
GitHub 托管运行器的仓库，可以把 `VISUAL_RECAP_GATE_RUNS_ON` 设置为
**一个纯文本、单一的运行器标签**（不是 JSON），或者在安装时传入
`--gate-runs-on visual-recap-gate`。可复用工作流会通过它的
`gate-runs-on` 输入项暴露同样的值。这样可以避免在 GitHub 能调度
门禁之前就去解析动态 JSON。这个自定义标签只会用于由 `OWNER`、
`MEMBER` 或 `COLLABORATOR` 在同一仓库内发起的 PR。分支仓库（fork）
以及其他所有作者，在任务开始前都会被强制使用 GitHub 托管的
`ubuntu-latest`；在一个只有自托管运行器的仓库中，这些不受信任的
运行可能会保持未调度状态，而不会触及自托管机器。

`recap doctor` 会拒绝格式错误或不受支持的 JSON，并在 GitHub 没有
暴露出与每个已配置标签都匹配的在线运行器时进行报告。运行器的
注册、安装、升级、容量和维护仍然是你自己的责任；Agent-Native 只
负责选择标签，并不提供或运营运行器。

**安全性：** 优先使用专用的、一次性的自托管运行器。自定义的门禁
运行器只会接收来自同一仓库、受信任的 PR 事件。标准门禁不会检出
PR 的代码树；它只评估工作流逻辑和 GitHub 的 PR 元数据。一台持久化
的机器仍会在多个任务之间保留进程状态，因此不要把它和不相关的
工作负载共用。对于不受信任的公开或分支 PR 作者，该工作流会在
派发任何自托管门禁或完整回顾任务之前失败关闭（fail closed）。
不要削弱这道边界，也不要把不受信任的贡献路由到持久化运行器上。

## 后端选择

通过 `VISUAL_RECAP_AGENT` 仓库变量选择由哪个编码代理来运行该
skill：

| `VISUAL_RECAP_AGENT` | 编码代理                                 | 所需的 API 密钥        | 所需的变量                                     |
| --------------------- | ---------------------------------------- | ----------------------- | ----------------------------------------------- |
| `claude` _（默认）_  | Claude Code CLI                          | `ANTHROPIC_API_KEY`     | —                                                |
| `codex`               | OpenAI Codex CLI                         | `OPENAI_API_KEY`        | —                                                |
| `openai-compatible`   | Agent-Native Code + 兼容的服务商         | `VISUAL_RECAP_API_KEY`  | `VISUAL_RECAP_BASE_URL`、`VISUAL_RECAP_MODEL`   |

如果没有设置该变量，该 action 会使用 `claude`。

## 模型与推理

除了后端选择之外，以下这些仓库变量还可以调整代理的运行方式：

- **`VISUAL_RECAP_MODEL`** 固定传给 CLI 的模型（`--model`）——例如 Codex 用 `gpt-5.6-luna`，一个 Claude 模型 id，或者 DeepSeek 用 `deepseek-chat`。对 `openai-compatible` 而言这是必需的。对于**Claude**后端，不设置它现在会默认使用 `claude-sonnet-5`；如果想使用其他 Claude 模型（比如更便宜的 `claude-haiku-4-5`），需要显式设置该变量。对于**Codex**后端，不设置它会使用 Codex CLI 自身的默认模型。
- **`VISUAL_RECAP_REASONING`** 设置推理深度：`none`、`minimal`、`low`、`medium`、`high` 或 `xhigh`。它适用于 Codex 后端；Claude 的推理由模型自身驱动，因此这个变量在 Claude 上会被忽略。
- **`VISUAL_RECAP_BASE_URL`** 为 `openai-compatible` 后端选择 HTTP(S) 基础 URL。请使用服务商的 OpenAI 兼容端点，比如 DeepSeek 或 Kimi，并且不要把凭据嵌入到 URL 中。
- **`VISUAL_RECAP_SKILL_SOURCE`** 控制提示词的新鲜度：`auto`/不设置时使用最新打包的 skill 指引，而 `repo` 会固定使用仓库内已提交的本地 `visual-recap` skill 文件夹。

例如，要用 Codex 搭配 GPT-5.6 Sol、以 high 推理深度运行回顾，设置
仓库变量 `VISUAL_RECAP_AGENT=codex`、`VISUAL_RECAP_MODEL=gpt-5.6-sol`
和 `VISUAL_RECAP_REASONING=high`。

对于 DeepSeek，设置 `VISUAL_RECAP_AGENT=openai-compatible`、
`VISUAL_RECAP_BASE_URL=https://api.deepseek.com/v1`、
`VISUAL_RECAP_MODEL=deepseek-chat`，以及 `VISUAL_RECAP_API_KEY`
这个 secret。Kimi 的用法相同，只是换成它自己的 OpenAI 兼容基础
URL 和模型 id。其他 OpenAI 兼容服务商也使用同样这三项设置。

## 成本

每一次回顾运行都是一次完整的、由编码代理读取真实 diff 的代理式
会话，不是一次廉价的模板化摘要，因此它的成本会随模型选择和运行
频率变化：

- **每次 PR 推送都是一次完整会话。** 默认触发器在 `synchronize` 事件上触发，所以一个被推送十次的 PR 就会让代理运行十次。
- **每次都是整个 PR**，而不只是上次运行之后新增的那些提交——成本会随 PR 的总规模而变化，而不是随增量 diff 的大小变化。
- **diff 输入上限约为 600KB。** 这限制了每次运行的最坏情况，但大 diff 的成本仍然会明显高于小 diff。
- **失败时会自动重试一次**，这可能会让一次瞬时失败的运行成本大致翻倍。

要降低成本：

- **固定使用更便宜的模型。** 对于简单或较小的仓库，为 Claude 设置 `VISUAL_RECAP_MODEL=claude-haiku-4-5`——这是最便宜的 Claude 档位；`claude-sonnet-5`（默认值）是均衡档位。
- **切换到 Codex，并使用更便宜的模型。** 设置 `VISUAL_RECAP_AGENT=codex`，配合 `VISUAL_RECAP_MODEL=gpt-5.6-luna`（最便宜的 GPT-5.6 档位）或 `gpt-5.6-terra`（中间档位），并设置 `VISUAL_RECAP_REASONING=low` 进一步削减推理 token 的花费。推理深度只适用于 Codex。
- **指向更便宜的 OpenAI 兼容服务商。** 设置 `VISUAL_RECAP_AGENT=openai-compatible`，并把 `VISUAL_RECAP_BASE_URL`/`VISUAL_RECAP_MODEL`/`VISUAL_RECAP_API_KEY` 指向 DeepSeek、Kimi 或任何其他 OpenAI 兼容端点。
- **要求显式的 PR 标签。** 设置 `VISUAL_RECAP_REQUIRED_LABELS=visual recap`，这样工作流仍会安装，但会跳过回顾，直到 PR 带上该标签。当希望多个标签都可以触发时，使用逗号分隔的列表，例如 `visual recap,recap`。打上列表中的任意一个标签，都会立即唤醒该工作流。
- **减少回顾的频率。** 把已安装工作流的 `on.pull_request.types` 从 `[opened, synchronize, reopened, ready_for_review, labeled, closed]` 改为 `[opened, ready_for_review, closed]`，这样只会在 PR 打开和合并时才生成回顾，而不是每次推送都生成。

每次运行都会记录实际花费：工作流的 `recap usage` 步骤会把 token
和成本使用情况附加到已发布的计划上，这样你就能查看每次运行的
真实花费，而不是靠猜测。

## Secrets 与变量 {#secrets-and-variables}

在你仓库的 **Settings → Secrets and variables → Actions** 中设置
这些内容。

### 默认后端所需的 secrets

| Secret              | 用途                                                                                        |
| ------------------- | ------------------------------------------------------------------------------------------- |
| `PLAN_RECAP_TOKEN`  | 由 `npx @agent-native/core@latest connect` 铸造的可撤销令牌。用于授权发布回顾计划和上传截图。 |
| `ANTHROPIC_API_KEY` | 默认 Claude Code 后端所使用的 LLM 密钥。                                                     |

**团队场景：使用组织服务令牌。** 个人令牌绑定在铸造它的那个人身上——
如果他们离开组织或撤销了自己的令牌，所有使用该 secret 的仓库就会
开始出现 401 失败，而且由 CI 创建的计划会归属于那个人，而不是团队。
组织服务令牌则归属于你的**组织**：它以服务主体
（`svc-<name>@service.<orgId>`）的身份存在，不会因任何个人离开而
失效，它发布的回顾对整个组织可见，任何组织所有者或管理员都可以
列出或撤销它。铸造一个（仅限组织所有者/管理员）：

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --service-token pr-recap
```

该命令会在浏览器中对你进行身份验证，然后只打印一次这个服务
令牌——把它存为 `PLAN_RECAP_TOKEN` 这个 secret。之后可以用 Plans
应用上的 `list-org-service-tokens` 和 `revoke-org-service-token`
actions 来管理它。

**个人场景：个人令牌依然可用。** 针对你的 Plans 应用运行
`npx @agent-native/core@latest connect` 来铸造它。对于托管应用来说，
这同时也会写入一份本地发布令牌文件，
`npx @agent-native/recap-cli@latest recap setup` 可以读取它：

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --client codex
npx @agent-native/recap-cli@latest recap setup
```

如果你更喜欢手动设置，把令牌粘贴到 GitHub secret 中即可。像
`plan_recap_xxxxxxxxxxxxxxxx` 这样的占位符只应该用在示例里——绝不
要提交真实的令牌。

## 评论中的内嵌截图

代理发布回顾之后，该工作流会在无头 Chrome 中分别用浅色和深色模式
对渲染出的计划截图，并把这些 PNG 上传到 Plans 应用上一个已签名的
公开图片路由。随后，置顶的 PR 评论会用一个 `<picture>` 元素把这些
截图**内嵌**进去——GitHub 会通过它的 camo 代理重新提供这些图片，
因此审阅者可以直接在评论中看到与自己 GitHub 主题相匹配的预览，
不需要打开任何东西。当他们想要进一步探索、评论或标注时，通向
完整交互式计划的链接就紧挨在旁边。

## 分支（fork）PR

### 默认行为（不需要任何操作）

主工作流 `pr-visual-recap.yml` 是在普通的 `pull_request` 触发器上
触发的，**不是** `pull_request_target`。因此，来自分支（fork）的
PR 运行时**无法访问仓库 secrets**，工作流找不到 `PLAN_RECAP_TOKEN`，
于是干净地什么都不做——不会有发布失败，也不会暴露任何凭据。对于
来自同一仓库内分支的 PR，由于 secrets 可用，回顾会自动运行。

这也意味着你可以在 secrets 存在**之前**就合并这个工作流文件：
只要没有配置令牌，每次运行都只是安静地什么都不做，直到你设置好
这些 secrets 为止。`gate` 步骤还会自动跳过草稿 PR 和由机器人创建
的 PR，因此默认情况下这两者都不会触发回顾运行。

### 通过标签门禁的分支工作流进行选择性启用

如果你想为分支 PR 生成回顾，还有第二个可用的工作流文件：
`.github/workflows/pr-visual-recap-fork.yml`。它使用
`pull_request_target`（会带着 base 仓库的 secrets 运行），但绝不会
检出或执行分支中的代码。GitHub 作者关联为 `OWNER`、`MEMBER` 或
`COLLABORATOR` 的受信任分支作者会自动运行。而来自外部的分支 PR，
在回顾代理运行之前，都需要通过一个全新的 `recap` 标签事件来完成
一次显式的**按 head 逐次维护者启用**。

要安装它，把这个文件从
[BuilderIO/agent-native](https://github.com/BuilderIO/agent-native/blob/main/.github/workflows/pr-visual-recap-fork.yml)
复制到你仓库的 `.github/workflows/` 目录中，与已有的
`pr-visual-recap.yml` 放在一起。同样的后端配置在这里也适用，包括
在使用 OpenAI 兼容服务商时的 `VISUAL_RECAP_API_KEY`、
`VISUAL_RECAP_BASE_URL` 和 `VISUAL_RECAP_MODEL`。

### 标签门禁如何工作

1. 一个分支贡献者打开了一个 PR。由于 GitHub 不会向分支运行提供 secrets，普通的 `pull_request` 工作流会跳过。
2. 分支工作流会检查 PR 的作者关联。受信任的作者（`OWNER`、`MEMBER` 或 `COLLABORATOR`）会在打开、同步、重新打开和标记为可审阅时自动运行。
3. 外部贡献者需要先让一位维护者审阅当前的 diff（尤其要留意提示注入形态的内容——见下文），然后再给该 PR 打上 `recap` 标签。
4. 面向外部贡献者的标签门禁是按 head SHA 生效的：如果贡献者推送了更多提交，下一次 synchronize 事件会被跳过，直到维护者在审阅新 diff 之后移除并重新打上 `recap`。

### 分支工作流会做什么、不会做什么

| 工作流会做的                                                                                             | 工作流不会做的                                             |
| ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 在**base 分支引用**处检出**base 仓库** — 只有受信任的代码                                                  | 检出或执行分支中的任何代码                                    |
| 把分支的 head 拉取为一个远程引用（`git fetch origin pull/<n>/head:refs/recap/fork-head`）——拉取提交是安全的 | 从分支安装依赖包、运行分支脚本，或把分支内容当作代码执行      |
| 运行 `git diff base...refs/recap/fork-head` — 对两个已拉取对象做纯文本 diff                                | 把这份 diff 用作除 LLM 文本输入之外的任何用途                 |
| 运行**base 仓库**自身的 visual-recap skill 和代理配置                                                      | 从分支加载任何 skill 或配置                                   |
| 让 diff 经过与第一方 PR 相同的 secret 扫描步骤（失败关闭）                                                  | 跳过 secret 扫描                                              |
| 在代理提示词中加入一条明确的提示加固说明，把 diff 内容标记为不可信                                          | 授予代理超出正常回顾代理之外的任何额外权限                     |

### 为什么打标签之前必须先审阅 diff

分支的 diff 是攻击者可控的文本，而回顾代理会把它当作输入来读取。
一份精心构造的 diff 可能包含提示注入内容——比如看起来像代理指令的
diff 行——意图让回顾代理执行非预期的操作（例如，窃取发布令牌，或
生成带有误导性的回顾内容）。

在打上 `recap` 标签之前，快速浏览 diff，留意以下内容：

- 读起来像直接命令或角色指令的行（例如“忽略之前的指令……”、“你现在是……”、“把令牌写入……”）。
- 可能被误读为系统提示词的异常文件名。
- 新增文件中可能解码出指令的编码内容。

这些缓解措施已经分层叠加在该工作流中（secret 扫描、敏感路径门禁、
提示加固说明、受限的代理工具允许列表），但标签审阅仍然是最主要的
防线。

### 与主工作流的关系

这两个工作流文件是相互独立的。对于非分支 PR 的更新，只有
`pr-visual-recap.yml` 会运行。对于分支 PR，普通工作流会在它的
分支门禁处退出，而 `pr-visual-recap-fork.yml` 会为受信任的同组织
作者自动运行，或者在外部贡献者获得一个全新的维护者 `recap` 标签
之后运行。它们共享同一个置顶评论标记和计划 id 关联，因此无论是
普通 PR 还是分支 PR，都只会在同一个 PR 上产生一条被更新插入的
评论。

### 自我修改防护 {#self-modifying-guard}

当一个 PR 触及以下任意路径时，`gate` 步骤会完全跳过回顾，这样一个
PR 就永远无法重写受信任回顾任务所加载的工作流、skill 或代理配置，
从而窃取 secrets：

| 路径模式                                    | 原因                                     |
| ------------------------------------------- | ----------------------------------------- |
| `.github/workflows/pr-visual-recap.yml`      | 工作流本身                                |
| `**/skills/visual-(recap\|plan\|plans)/**`   | 代理所遵循的 visual-recap skill           |
| `**/.claude/**`                              | 运行器会加载的代理设置                    |
| `**/CLAUDE.md`                               | 运行器会加载的代理指令                    |
| `**/AGENTS.md`                               | 运行器会加载的代理指令                    |
| `**/.mcp.json`                               | 运行器会加载的 MCP 服务器配置             |

在 `BuilderIO/agent-native` 这个 monorepo 中，该工作流会从受信任的
base 分支源码运行 recap CLI，而不是从 PR head 的源码运行。这样
一来，普通的包变更（包括 `packages/core/**`）仍然可以生成回顾，
同时不会执行被 PR 修改过的 CLI 代码。

## 本地文件隐私模式

这个 GitHub Action 是为托管、可共享的 PR 审阅设计的。如果你想要
一份回顾，但不希望回顾内容被发送到 Agent-Native Plan 数据库，
可以改为在本地以本地文件模式运行同一套辅助流程：

```bash
npx @agent-native/recap-cli@latest recap collect-diff --base main --head HEAD --out recap.diff --stat recap.stat
npx @agent-native/recap-cli@latest recap scan --diff recap.diff
npx @agent-native/recap-cli@latest recap build-prompt --pr 123 --diff recap.diff --stat recap.stat --local-files --local-dir plans/pr-123-visual-recap
```

把生成的 `recap-prompt.md` 交给你的编码代理。在本地文件模式下，
这份提示词会指示代理写入 `plans/pr-123-visual-recap/plan.mdx`，
以及可选的视觉文件，然后运行：

```bash
npx @agent-native/core@latest plan local serve --dir plans/pr-123-visual-recap --kind recap --open
```

返回的 URL 会打开托管的 Plan UI，同时浏览器会通过一个本地主机桥
来读取回顾的 MDX。回顾内容不会被写入托管的 Plan 数据库，而且这个
URL 只在运行该网桥的那台机器上有效。如果你用同样的 `PLAN_LOCAL_DIR`
本地运行 Plan 应用，`/local-plans/pr-123-visual-recap` 这条路由
同样有效。以仓库为支撑的文件夹可以按
`/local-plans/pr-123-visual-recap?path=plans%2Fpr-123-visual-recap`
的形式打开。在你明确发布之前，这个模式会禁用托管的置顶 PR 评论、
内嵌截图上传、用量附加信息，以及浏览器评论。

## 它是信息性的，不是一道门禁

这份回顾是叠加在正常 PR 流程之上的一个审阅辅助工具：

- 它会显示一个 `Visual Recap` 检查行以提高可见性，但它**永远不是必需检查项**，也永远不会阻止合并。
- 生成或发布失败会以中立状态完成，并表现为一条带解释性说明的置顶评论，而不是不相关代码上的一个红色 X。
- 这份回顾及其截图**并不意味着这份 diff 已经被审阅过**。审阅者仍然需要去阅读真正改动的那些代码行。

## 版本固定（复制版本） {#version-pinning-copy-variant}

默认情况下，复制版本的工作流会在运行时安装
`@agent-native/recap-cli@latest`，因此每次回顾运行都会自动获取
最新的 CLI。如果你的 CI 需要可复现的工具链，可以设置
**`RECAP_CLI_VERSION`** 这个仓库变量来固定所安装的版本：

1. 进入你仓库的 **Settings → Secrets and variables → Actions → Variables**。
2. 创建一个名为 `RECAP_CLI_VERSION` 的变量，值类似 `1.5.0`。

这个变量是可选的。保持不设置（或者设置为 `latest`）即可跟随最新
发布版本。

对于可复用调用方版本，请改用 `cli-version` 输入项（参见可复用
章节中的 [Version pinning](#version-pinning)）。

## Secret 扫描允许列表

在发布回顾之前，该工作流会运行
`npx @agent-native/recap-cli@latest recap scan`，检测 diff 中
可能存在的 secret。任何 diff 匹配到已知 secret 模式的 PR，都会被
一条带解释说明的评论阻止——回顾不会被发布，diff 内容也不会被
发送给编码代理。

在少数情况下，某个仓库会故意含有测试夹具，或者一些表面上看起来
像 secret 模式、实际上并不是 secret 的字符串（例如测试文件中的
一个夹具密钥）。要抑制这种误报，在你仓库的根目录创建
`.github/recap-scan-allowlist`。

### 格式

每一个非空白、非注释的行，要么是一个**字面子字符串**，要么是一个
**`/regex/flags`** 模式：

```
# Lines starting with # are comments.

# Literal substring — any diff line containing this string is allowed.
sk-test-fixture1234567890abcdef

# Regex pattern — written as /pattern/flags (JS syntax).
/^.STRIPE_KEY=sk-test-/i

# Another literal.
EXAMPLE_API_KEY=placeholder-value
```

规则：

- 当一行包含该字面字符串，或者整行匹配该正则表达式时，这一行就会被**抑制**（即被允许）。
- 这个文件是**失败关闭**的：如果它不存在，就不会应用任何抑制——扫描器的行为和之前一样。
- 一个空文件等同于没有这个文件。
- 格式错误的正则表达式行会被当作字面字符串处理。

这份允许列表只会被 secret 扫描门禁参考。它不会影响编码代理能读到
什么内容——只要门禁通过，代理都会收到完整的 diff。

## 采用可复用工作流

### 为什么要用可复用版本？

默认的安装程序会把完整的约 360 行工作流 YAML 复制到你的仓库中
（**copy** 选项）。对于隔离网络的仓库，或者需要审计每一行实际
运行内容的仓库来说，这是正确的选择。缺点是错误修复和改进永远
不会自动送达你——你需要在每次发布之后手动重新运行
`npx @agent-native/recap-cli@latest recap setup`。

**reusable** 选项则会写入一个精简的约 20 行调用方。它通过 `uses:`
委托给
`BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml`。
每个调用方在工作流运行时都会自动获取最新的逻辑，不需要任何本地
更新。

|                              | 复制版本（默认）              | 可复用版本                          |
| ---------------------------- | ------------------------------ | -------------------------------------- |
| 仓库中工作流的大小            | 约 360 行                      | 约 20 行                                |
| 是否自动获取修复              | 否 — 需要重新运行 `recap setup` | 是                                      |
| 隔离网络 / 完全可审计         | 是                              | 否                                      |
| 是否可固定到特定版本          | 只能通过本地编辑                | 是 — 在 `uses:` 中设置 `@v1.2.3`        |

### 调用方片段

这就是 `npx @agent-native/recap-cli@latest recap setup --reusable`
所写入的内容（你也可以手动粘贴它）：

```yaml
name: PR Visual Recap

# Thin caller — the full workflow logic lives in BuilderIO/agent-native.
# Fixes and improvements reach this repo automatically on each run.
# To pin a specific version for reproducibility replace '@main' with a
# tag or SHA, e.g. '@v1.2.3' or '@abc1234'.

on:
  pull_request:
    types: [opened, synchronize, reopened, ready_for_review, labeled, closed]

jobs:
  visual-recap:
    if: github.event.action != 'labeled' || vars.VISUAL_RECAP_REQUIRED_LABELS != ''
    permissions:
      actions: write
      contents: read
      checks: write
      issues: write
      pull-requests: write
    uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@main
    secrets:
      PLAN_RECAP_TOKEN: ${{ secrets.PLAN_RECAP_TOKEN }}
      ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
      OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
      VISUAL_RECAP_API_KEY: ${{ secrets.VISUAL_RECAP_API_KEY }}
      PLAN_RECAP_APP_URL: ${{ secrets.PLAN_RECAP_APP_URL }}
    with:
      agent: ${{ vars.VISUAL_RECAP_AGENT || 'claude' }}
      model: ${{ vars.VISUAL_RECAP_MODEL || '' }}
      base-url: ${{ vars.VISUAL_RECAP_BASE_URL || '' }}
      reasoning: ${{ vars.VISUAL_RECAP_REASONING || '' }}
      skill-source: ${{ vars.VISUAL_RECAP_SKILL_SOURCE || 'auto' }}
      runs-on: ${{ vars.VISUAL_RECAP_RUNS_ON || '"ubuntu-latest"' }}
      gate-runs-on: ${{ vars.VISUAL_RECAP_GATE_RUNS_ON || 'ubuntu-latest' }}
      required-labels: ${{ vars.VISUAL_RECAP_REQUIRED_LABELS || '' }}
      # cli-version: "latest"  # pin to a specific @agent-native/recap-cli version
```

[Secrets and variables](#secrets-and-variables) 中描述的那些
secrets 和变量在这里同样适用——把它们设置在你的仓库设置中，方式
和复制版本一样。这个可复用调用方会把 `VISUAL_RECAP_RUNS_ON`
通过它的 JSON 输入项 `runs-on` 转发给完整的回顾任务，把
`VISUAL_RECAP_GATE_RUNS_ON` 通过它的纯文本标签输入项
`gate-runs-on` 转发给仅处理元数据的门禁，并把
`VISUAL_RECAP_REQUIRED_LABELS` 通过 `required-labels` 用于可选的
PR 标签门禁。门禁运行器输入项只会用于受信任的同仓库作者；其他
PR 会使用 GitHub 托管的 `ubuntu-latest`。省略运行器输入项会保留
它们默认的 `ubuntu-latest`；省略必需标签会保留自动回顾的行为。

### 通过 CLI 安装

```bash
# Write the thin caller instead of the full copy:
npx @agent-native/recap-cli@latest recap setup --reusable

# Or with a pinned ref for reproducibility:
npx @agent-native/recap-cli@latest recap setup --reusable --ref v1.2.3
```

这两种版本都会把工作流写入 `.github/workflows/pr-visual-recap.yml`。
如果那里已经存在一个不同的工作流，该命令会拒绝执行，并提示你
传入 `--force` 来覆盖它。

写入之后，照常运行 `npx @agent-native/recap-cli@latest recap doctor`
来确认 secrets 已经配置好。

### 版本固定 {#version-pinning}

默认情况下，调用方引用的是 `@main`，它始终使用可复用工作流最新
发布的版本。对于需要可复现 CI 的生产仓库，请固定到某个 tag 或
SHA：

```yaml
uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@v1.2.3
```

`cli-version` 这个输入项控制工作流内部运行的是哪个
`@agent-native/recap-cli` 版本——保留为 `"latest"` 即可跟随最新
发布版本，或者固定为一个版本字符串（例如 `"1.5.0"`）以获得完全的
可复现性。

### workflow_call 事件上下文

`workflow_call` 工作流会继承**调用方**的事件上下文。这个可复用
工作流使用 `github.event.pull_request.*` 表达式来读取 PR 编号、
head SHA、base SHA、合并时间戳和 PR 元数据——只有当调用方在
`pull_request` 上触发时，这些才能正常工作。上面的调用方片段已经
包含了正确的事件类型。之所以包含 `closed` 事件，是为了让已合并
PR 的回顾能被打上 `merged_at` 的时间戳，之后可以作为已完成的工作
被检索到。

不要在 `workflow_dispatch` 或 `push` 上触发这个调用方——这些事件
不携带 `pull_request` 负载，门禁会以“no pull_request payload”为由
跳过回顾。
