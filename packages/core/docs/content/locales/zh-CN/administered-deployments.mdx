# 管理式部署

一个组织运营内部应用时，请使用工作区。组织是成员和数据边界。工作区汇集一个或多个应用的部署配置。

## 关闭注册和组织创建

```dotenv
AUTH_SIGNUP=invited
ORG_CREATION=closed
AUTO_CREATE_DEFAULT_ORG=0
AUTH_BOOTSTRAP_ADMINS=admin@example.com
AUTH_REQUIRE_EMAIL_VERIFICATION=1
```

设置 `AUTH_SIGNUP=invited` 后，新账户必须有待处理邀请、已验证且获准的邮箱域名，或位于 `AUTH_BOOTSTRAP_ADMINS` 中的邮箱。密码、魔法链接和社交注册都会检查。按域名加入不等同于邀请，也不会分配应用角色。

首位登录的引导管理员会创建规范组织并成为所有者。如果已有一个组织，管理员会加入并成为所有者。如果存在多个组织，系统不会自行选择。随后在 Team settings 中配置允许的域名并邀请团队。

## 公司密钥和角色

组织所有者或管理员可以保存组织级 LLM 密钥。个人密钥优先，直到成员选择使用组织密钥。应用角色仅在单个应用内有效，成员可拥有多个角色。管理员可以把代码声明的权限映射到角色，无需重新部署即可调整。

## 更改邮箱和身份

用户验证新邮箱后，可以在账户设置中更改登录邮箱。管理员迁移时，每个应用都运行一次 `agent-native identity rekey --from old@example.com --to new@example.com`。使用 `--yes` 前先检查表名和行数。既有审计记录保持不变。不可变主体 ID 迁移计划在 1.0 之后进行。

## 组织 SSO 与目录配置

组织 SSO 和 SCIM 是可选功能。设置 `AUTH_SSO=1` 和 `AUTH_SCIM=1` 后，Team settings 会显示相应管理控件。请在构建环境和运行时环境中同时设置这些变量；部署后更改需要重新构建。先配置组织的邮箱域名。OIDC 需要 issuer、client ID 和 client secret。SAML 需要 IdP entry point、entity ID，并粘贴 metadata XML。设置页面会显示 redirect URI 和 SP metadata。按页面显示的值创建 `_better-auth-token-<provider-id>.<organization-domain>` DNS TXT 记录，等待 DNS 传播后验证域名。验证后，管理员可以要求成员使用 Google 或已验证的 SSO 提供方登录。创建 SCIM 连接后，将仅显示一次的 token 和 endpoint 配置到身份提供方。在 Okta 或 Microsoft Entra ID 中创建 OIDC 或 SAML 企业应用，并配置 SCIM client。先用小范围用户组测试创建、更新和停用，再扩大范围。这与应用间身份联邦是不同功能。

服务端操作应使用 `accessFilter()` 和 `assertAccess()`。Agent SQL 使用临时过滤视图。`pnpm guards` 包含无范围查询检查。RLS 当前不是生效层，计划作为 1.0 之后的强化措施。多个内部应用适合使用工作区，独立工具或原型适合使用独立应用。请参阅[独立应用还是工作区](/docs/multi-app-workspace#standalone-or-workspace)和[版本与稳定性](/docs/versioning-and-stability)。
