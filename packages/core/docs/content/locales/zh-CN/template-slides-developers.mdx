# 开发者指南

本页适用于任何想要定制或扩展幻灯片模板的人：SQL 数据模型、如何确保并发写入者的安全、每一个可供代理调用的 action、路由结构，以及应该在哪些常见位置进行修改。

## 快速入门

```bash
npx @agent-native/core@latest create my-slides --standalone --template slides
```

剩余的搭建步骤（`cd`、`pnpm install`、`pnpm dev`）以及框架基础知识，请参阅[快速入门](/docs/getting-started)。

## 持久化模型

每一份演示文稿都是 `decks.data` 中的一个 JSON 数据块。每一次写入都会经过一个持有按演示文稿加锁的服务器端读取-修改-写入 action，因此并发写入者——一个人和代理，或者两个人——即使同时操作同一份演示文稿的不同幻灯片，也永远不会覆盖对方的工作成果。

- **代理 actions**（`add-slide`、`update-slide`）使用各自专属的细粒度 action，并共享同一个锁。
- **浏览器编辑器**通过 `patch-deck` 将细粒度操作（`patch-slide`、`delete-slide`、`reorder-slides`、`add-slide`、`patch-deck-fields`）加入队列，而不是发起一次全量演示文稿的 PUT 请求。

<Callout id="doc-block-slides10" tone="warning">

如果您要扩展编辑器的保存路径，请通过 `patch-deck` 将新的操作加入队列。不要新增一个全量演示文稿的 PUT 请求，那样会重新引入这个锁本来就是为了防止的“后写入者获胜”竞争问题。

</Callout>

#### 幻灯片结构

`decks.data` 内部的每一张幻灯片为：

```json
{
  "id": "slide-1",
  "layout": "title",
  "content": "<div class=\"fmd-slide\" style=\"...\">...</div>"
}
```

`content` 是原始的 HTML。渲染器负责提供固定的宽高比和背景，HTML 则负责提供其内部的所有内容。富媒体嵌入同样受支持：手绘图表和实时渲染的图表都可以和普通 HTML 一起存在于一张幻灯片内部。

## Action 清单

### 演示文稿生命周期

- `create-deck` — 新建一份演示文稿，可以选择预先填充幻灯片，也可以对现有演示文稿的幻灯片进行一次原子化的批量替换。省略 `slides` 或传入 `[]` 即可创建一份空的演示文稿。该 action 会通过应用状态打开新建的演示文稿。
- `get-deck` — 完整的演示文稿 JSON，或一个精简的幻灯片摘要视图
- `list-decks` — 调用者可见的每一份演示文稿，提供轻量/精简/全幻灯片三种投影，便于低成本轮询
- `duplicate-deck` — 复制一份演示文稿，并为其中的幻灯片生成全新的 id
- `update-deck-aspect-ratio` — 16:9、1:1、9:16 或 4:5

`add-deck`、`save-deck` 和 `delete-deck` 分别支撑浏览器编辑器的乐观创建、撤销/重做和删除流程。代理则改用 `create-deck`、`add-slide`/`update-slide`/`patch-deck`，以及框架自带的共享 actions。

### 访问请求

- `request-deck-access`、`approve-deck-access-request`、`get-deck-access-status` — 私密演示文稿的访问请求流程：没有访问权限的访问者提出请求，所有者从应用内或 `/access-request/approve` 路由批准或拒绝该请求，双方都可以轮询当前状态

### 幻灯片编辑

- `add-slide` — 追加一张幻灯片（或插入到指定位置）。在一次空的 `create-deck` 之后依次调用它，编辑器就能展示生成进度。
- `update-slide` — 对幻灯片进行精确的查找/替换编辑，或整体替换其内容
- `patch-deck` — 浏览器编辑器使用的细粒度操作队列，用来替代全量演示文稿的 PUT 请求
- `get-layout-overflows` — 读取浏览器测量得到的幻灯片排版结果，以便捕获并修正那些不再适配其布局的编辑

### 历史记录

- `list-deck-versions`、`get-deck-version`、`restore-deck-version` — 每一次写入都会先创建快照，因此任意一个时间点都可以被列出并恢复

### 评论

- `list-slide-comments`、`add-slide-comment`、`update-slide-comment`、`delete-slide-comment`

### 导入

- `import-pptx`、`import-docx`、`import-google-doc` — 各自专用的单格式导入器
- `import-google-slides-reference` — 将一份 Google Slides 演示文稿导入为可复用的参考演示文稿，而不是把其内容拉入当前正在编辑的演示文稿中
- `import-file` — PPTX、DOCX、PDF 或 Figma `.fig` 文件的统一入口（`.fig` 文件会被导向 Builder 设计系统索引，而不是幻灯片导入）
- `extract-pdf` — 仅限 CLI 使用的 PDF 原始文本导出，主要用于本地调试

### 导出

- `export-pptx` — 原生、可编辑的 PowerPoint
- `export-google-slides` — 生成同一份 PPTX，并附带一个可直接使用的 Google Slides 导入链接
- `export-html` — 一个内置键盘导航的独立、自包含 HTML 文件

### 设计系统

- `create-design-system`、`update-design-system`、`delete-design-system`、`get-design-system`、`list-design-systems`、`set-default-design-system`、`apply-design-system`（将某个设计系统关联到一份演示文稿）
- `get-workspace-defaults`、`set-workspace-defaults` — 工作区范围内的默认演示文稿和默认设计系统。设置它们仅限管理员操作
- `analyze-brand-assets`、`import-document`、`import-from-url`、`import-code` — 收集原始品牌信号（网站的 CSS/字体、上传的文档或代码文件内容），用于生成一个**本地**的、由代理起草的设计系统
- `index-design-system-with-builder`、`sync-design-system-with-builder`、`import-design-project` — 针对 Figma 文件、已连接的代码/GitHub 仓库以及 `design.md` 的 Builder 索引路径。`import-design-project` 从一个已有的设计系统开始，而不是从一个原始素材来源开始

### Creative Context

- `clone-context-slide` — 将 Library 中固定的一张幻灯片原样插入到一份演示文稿中，不重新生成其 HTML/CSS
- `clone-creative-context-deck` — 重新创建一个精确的、受管控的演示文稿版本
- `get-deck-reference-context` — 从一份现有的演示文稿中提取其视觉语言，形成一个可复用的模式库
- 检索和 Library 提交（搜索、获取一个上下文条目、管理 Library 成员资格）都是共享的框架 actions，代理在每一个支持 Creative Context 的应用中都以相同的方式调用它们。检索流程和复用阶梯请参阅 `creative-context` skill。

### 升级调用与暂存数据

- `provider-api-catalog`、`provider-api-docs`、`provider-api-request` — 当一个预设的导入/导出 action 覆盖范围过窄时，直接访问原始的 Google Drive API。幻灯片会从用户已连接的 Google Docs 账户中解析身份验证信息
- `list-staged-datasets`、`query-staged-dataset`、`delete-staged-dataset` — 在不重新获取的情况下，对一个已暂存的大规模 provider 结果进行聚合处理

### 导航和上下文

- `view-screen` — 用户当前正在查看的内容：打开的演示文稿、当前幻灯片，以及任何激活中的可视化选择
- `navigate` — 将界面切换到某份演示文稿、某张幻灯片或某个视图

## 自定义

幻灯片模板是完全可定制的。扩展时需要关注的关键位置：

#### Actions — `templates/slides/actions/`

每一个可供代理调用的操作都以 TypeScript 文件的形式存放在这里，自动挂载在 `POST /_agent-native/actions/:name` 上，并且可以从 CLI 以 `pnpm action <name>` 的方式调用。在此处新增一个文件，即可赋予代理一项新的能力。

  code={
    'import { defineAction, fail } from "@agent-native/core/action";\nimport { assertAccess } from "@agent-native/core/sharing";\nimport { eq } from "drizzle-orm";\nimport { z } from "zod";\n\nimport { getDb, schema } from "../server/db/index.js";\nimport { notifyClients } from "../server/handlers/decks.js";\nimport { withDeckLock } from "./patch-deck.js";\n\nexport default defineAction({\n  description:\n    "Surgically edit a slide\'s content using search-replace or full replacement. " +\n    "Syncs live to open editors. Prefer this over full deck rewrites.",\n  schema: z.object({\n    deckId: z.string(),\n    slideId: z.string(),\n    find: z.string().optional(),\n    replace: z.string().optional(),\n    fullContent: z.string().optional(),\n  }),\n  run: async ({ deckId, slideId, find, replace, fullContent }) => {\n    await assertAccess("deck", deckId, "editor");\n    return withDeckLock(deckId, async () => {\n      const db = getDb();\n      const [row] = await db\n        .select()\n        .from(schema.decks)\n        .where(eq(schema.decks.id, deckId));\n      if (!row) {\n        fail(`Deck ${deckId} not found`, { errorCode: "deck_not_found", statusCode: 404 });\n      }\n\n      const deck = JSON.parse(row.data);\n      const slide = deck.slides.find((s: { id: string }) => s.id === slideId);\n      if (!slide) {\n        fail(`Slide ${slideId} not found`, { errorCode: "slide_not_found", statusCode: 404 });\n      }\n\n      if (fullContent) {\n        slide.content = fullContent;\n      } else if (find) {\n        const idx = slide.content.indexOf(find);\n        if (idx === -1) {\n          fail("Text not found", { errorCode: "slide_find_no_match" });\n        }\n        slide.content =\n          slide.content.slice(0, idx) +\n          (replace ?? "") +\n          slide.content.slice(idx + find.length);\n      }\n\n      deck.updatedAt = new Date().toISOString();\n      await db\n        .update(schema.decks)\n        .set({ data: JSON.stringify(deck), updatedAt: deck.updatedAt })\n        .where(eq(schema.decks.id, deckId));\n\n      notifyClients(deckId, { slideId, actor: "agent" });\n      return { ok: true, deckId, slideId };\n    });\n  },\n});'

大部分编辑器界面的定制都发生在 `app/components/editor/` 下：幻灯片画布、工具栏、侧边栏、气泡菜单、斜线菜单，以及历史记录面板。

#### Skills — `templates/slides/.agents/skills/`

当代理需要修改代码时，用于解释相应模式的代理 skills：

- `create-deck` — 如何创建一份新的演示文稿，包含每种布局的精确幻灯片 HTML 模板
- `slide-editing` — 如何编辑单张幻灯片
- `deck-management` — 演示文稿如何被存储和访问
- `design-systems` — 设计系统的数据结构，以及令牌如何应用到生成的幻灯片上
- `creative-context` — 复用阶梯、检索流程，以及 Library 提交

#### AGENTS.md

`templates/slides/AGENTS.md` 是代理在每次对话中都会读取的简短路由器。它指向 `.agents/skills/` 下的各个 skills，并列出了核心规则、持久化模型和应用状态约定。每当您新增或更改一种幻灯片布局或设计系统素材来源时，请更新相应的 skill。
