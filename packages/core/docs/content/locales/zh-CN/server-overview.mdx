# 服务器

`server/` 目录是代理本机应用的基础设施层。它负责启动任务、身份验证，以及 Actions 无法覆盖的 HTTP 表面。大多数产品行为都应该放在 [Actions](/docs/actions) 中。服务器的作用是让这些 Actions 变得可用。

## 服务器的定位 {#role}

在传统的 Web 应用中，服务器是大多数逻辑所在之处：业务规则、数据访问和展示都发生在路由处理函数内部。代理本机应用的做法不同。逻辑放在 Actions 中，由代理和 UI 作为平等的一方共享。服务器的职责是协调：运行数据库迁移、配置身份验证、挂载 Agent 循环,以及处理 Actions 本身无法表达的少数 HTTP 相关事项。

浏览器请求、Agent 循环和外部 API 客户端都经由同一个 Nitro 服务器路由，并读取同一个 SQL 数据库。不存在为代理和 UI 分别搭建的后端。服务器层的作用就是把 Actions 暴露给外部世界。

## Nitro {#nitro}

[Nitro](https://nitro.build) 是驱动代理本机 HTTP 层的服务器工具集。你在 `server/` 中配置的大部分内容都属于 Nitro：基于文件的路由、启动插件和中间件。

- **基于文件的路由**：文件名直接映射到 HTTP 方法和 URL 路径，无需注册。`server/routes/api/health.get.ts` 会自动变成 `GET /api/health`。更多细节参见[路由](/docs/server-routes)。
- **插件**：在服务器启动时注册并加载一次的代码。框架辅助函数会初始化身份验证和 agent-chat；可选的应用自有数据库迁移在第一个请求到达时可能仍在运行。更多细节参见[插件](/docs/server-plugins)。
- **中间件**：在每个到来的请求到达路由之前都会运行的代码。身份验证守卫就位于 `server/middleware/` 中。更多细节参见[中间件](/docs/server-middleware)。

Nitro 同时与部署环境无关。同一个应用可以零代码改动地部署到 Node.js、Cloudflare Workers、Netlify、Vercel 及其他运行时，只需设置一个预设（preset）。参见[部署](/docs/deployment)。

底层的请求/响应 API 是 [H3](https://h3.unjs.io)。当你在自定义路由中看到 `defineEventHandler`、`createError` 或 `getQuery` 时，那就是 H3。[Nitro 文档](https://nitro.build/guide)和 [H3 文档](https://h3.unjs.io)是框架未直接涵盖内容的参考资料。

## 优先默认使用 Actions {#actions-first}

Agent-Native 的架构思路有所不同。每当你为应用构思一个新功能时，先考虑它能否做成一个 Action。举例来说，如果 UI 和代理都需要执行某项操作,应该定义一个 Action，而不是自定义 API 路由。Actions 会自动成为：

- 代理工具。
- 类型化的前端 Hook。
- `/_agent-native/actions/:name` 下的 HTTP 端点。
- 可通过 MCP 和 A2A 调用的工具。
- 用于开发的 CLI 命令。

只有在你需要路由形态的协议或二进制/流式行为时，才使用自定义的 `/api/*` 路由。更多细节参见 [Actions](/docs/actions)。
