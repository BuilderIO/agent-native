# 应用

想要发布您自己的人工智能分析工具吗？邮件客户端？表格生成器？选择一个示例应用，您只需几分钟即可获得一个可运行的 SaaS — 代理、数据库、身份验证和部署管道已连接完毕。

大多数入门模板都会为您提供一个空白的脚手架和一个很长的 TODO 列表。代理本机翻转了这一点。每个示例应用都是**完整的 SaaS 级产品** - 在第一天就已经可以运行，已经可以发货，并且完全由您来定制、品牌化和部署。将它们视为可克隆的 SaaS，而不是入门工具包：您正在分叉成品，而不是盯着样板文件。

## 社区模板 {#community-templates}

CLI 选择器中按名称提供的模板是**第一方模板**：Agent Native 会随框架一起
维护、测试、记录和发布它们。**社区模板**由其仓库所有者负责维护和版本管理。
它可以使用相同的框架能力，但进入社区列表并不表示 Agent Native 对其背书或
承诺提供支持。

运行 `create`，选择**社区模板**，然后粘贴公开 GitHub 仓库的简单 URL：

```bash
https://github.com/owner/repo
```

如果仓库根目录是单个 Agent Native 应用，CLI 会直接安装，不再显示其他
选择器。如果仓库是 Agent Native 工作区，CLI 会发现 `apps/*` 的有效直接
子项，排除 `dispatch`，并询问要安装哪个应用。

非空的 `agent-native.workspaceCore` 标记会使仓库被视为工作区，即使根
package 也依赖 `@agent-native/core`；格式错误的标记会被拒绝。

在脚本中，将相同的简单 URL 传给 `--template`，或使用更短的 `community:`
形式。如果需要可复现的起点，请在 `#` 后固定 branch、tag 或 commit。如果
未提供 ref，CLI 会先尝试 `main`，再尝试 `master`：

```bash
npx @agent-native/core@latest create my-app --template community:owner/repo#v1.2.0
npx @agent-native/core@latest create my-app --template https://github.com/owner/repo#v1.2.0
```

要以非交互方式选择工作区仓库中的源应用，请使用 `?app=<app-name>`。
选择器位于可选的 `#ref` 之前。请为整个值加引号，因为 zsh 等 shell 会将
`?` 视为 glob：

```bash
npx @agent-native/core@latest create my-app --template 'community:owner/repo?app=analytics#v1.2.0'
npx @agent-native/core@latest create my-app --template 'https://github.com/owner/repo?app=analytics#v1.2.0'
```

在工作区外，`create` 会将所选源应用创建为独立应用。要将其添加到现有
工作区，请显式传入社区仓库，因为 `add-app` 选择器只列出第一方模板。
省略 `?app` 可从源工作区进行交互式选择；包含它则可用于脚本化安装：

```bash
npx @agent-native/core@latest add-app my-app --template community:owner/repo#v1.2.0
npx @agent-native/core@latest add-app my-app --template 'community:owner/repo?app=analytics#v1.2.0'
```

只接受公开 GitHub 仓库。不支持私有仓库、非 GitHub 主机、GitHub tree 或
子目录 URL，以及嵌套应用路径。根应用必须包含可读取的 `package.json`，
其中在 `dependencies`、`devDependencies` 或 `peerDependencies` 中列出
`@agent-native/core`。在工作区仓库中，每个可选择的源应用都必须直接位于
`apps/<app-name>/` 并满足相同要求；`dispatch` 永远不可选择。

社区工作区应用必须是可移植的独立单元，而不是 monorepo 的任意切片：

- 默认 `catalog:` 依赖引用从源仓库根目录的 `pnpm-workspace.yaml` 解析；
  不支持命名 catalog 引用；
- 对 `@agent-native/core`、`@agent-native/dispatch` 和
  `@agent-native/toolkit` 的 `workspace:*` 引用会改写为已发布版本。其他
  同级工作区 package 不会被复制；请发布它们并使用具体版本；
- 源 `workspaceCore` 依赖项会被移除。继承的标准工作区 auth 和 agent-chat
  plugin 会在独立安装时解除绑定，或重新绑定到目标工作区。对源
  `workspaceCore` package 的任何其他 import 都会明确失败；请将该代码移入
  应用，或将其发布为具体依赖项。

每个完整应用的其余内容都应与其 `package.json` 放在一起，包括使用时的
`agent-native.json`、源代码、actions、代理指令和数据库设置。准备列入目录
的仓库还应包括：

- 许可证以及维护者或支持链接；
- 包含设置步骤、必需环境变量和准确 CLI 命令的 README；
- 只包含占位符的 `.env.example`，不得包含 secrets、客户数据、运行时
  数据库或生成的构建产物；
- 可正常工作的安装和开发命令、typecheck，以及适合该模板的测试。

安装程序会将解析后的 `source` 和 `ref` 记录在已安装应用的 `package.json`
中的 `agent-native.communityTemplate` 下。从工作区仓库选择的应用还会将
源应用记录为 `agent-native.communityTemplate.app`。`agent-native template
sync` 仍然只适用于第一方模板；更新社区模板时，请检查较新的 upstream ref
并自行合并其更改。

有关应用、action、state、安全和发布的完整检查清单，请参阅
[Creating Templates](/docs/creating-templates)。

> **安装依赖项或运行社区代码之前，请先进行审查。** 社区模板从第三方仓库
> 下载；Agent Native 不会对其进行 sandbox、审计或维护。CLI 只下载源代码，
> 不会安装依赖项或运行模板脚本。请检查源代码、许可证、依赖项和 package
> install scripts，并优先使用已固定且可信的 ref。

托管 demo 是可选的。如果提供，请使用公开的试用链接，并说明登录、示例数据
或 provider 要求。仓库仍然是安装内容的事实来源，仓库所有者仍然对模板和
demo 负责。

希望加入列表？请提交[社区模板](https://github.com/BuilderIO/agent-native/issues/new?template=community-template.yml)，
并附上仓库 URL、一句话描述、维护者和许可证信息、已测试的 CLI 命令，以及
可选的托管 demo URL。

## 开箱即用的东西 {#what-you-get}

每个示例应用都附带通常需要数月才能构建的部件：

- **工作代理** — 已经连接到应用程序，已经能够在您的数据上获取 actions，已经能够了解您正在查看的内容。请参阅 [Messaging the agent](/docs/messaging) 了解其工作原理。
- **Auth** — 登录、会话、组织、多租户隔离。已经完成了。
- **数据库** — 每个示例应用都有其架构、查询和迁移准备就绪。带上您自己的 SQL 数据库（Postgres、SQLite、Turso、D1）——框架会进行调整。
- **实时 UI** — 屏幕与代理的操作保持同步。在聊天中点击“草稿电子邮件”，草稿立即出现在您的收件箱中。
- **部署就绪** — 推送到 Netlify、Vercel、Cloudflare、AWS 或运行 Node.js 的任何其他地方。没有供应商锁定。
- **品牌挂钩** - 名称、颜色、徽标、文案都很容易更改。

这不是理论上的主张。该框架的作者在 Mail 应用上运行他的实际收件箱，在 Calendar 应用上运行他的实际日历，在 Analytics 应用上运行他的实际分析。这些都是日常使用的应用。

1. **选择一个示例应用。**使用 CLI 选择器，或浏览文档并选择一个开始。
2. **打造品牌。**更改名称、颜色、徽标和文案。大多数示例应用都将其公开在单个配置文件中。
3. **自定义它。** 在自己的仓库和开发工作流中更改源代码。如果代理 frame 被有意授予工作区和写入工具，它可以提供帮助；否则嵌入式代理通过 actions、数据和已配置的集成来操作应用。
4. **发货。**运行部署命令。您现在在自己的域中拥有自己的生产 SaaS。

步骤 2-4 通常需要几天而不是几个月。第 3 步是开放式的，因为应用归您所有并可持续演进；嵌入式代理仍可操作已部署的产品，并在明确启用代码访问时协助更改源代码。

## 为什么这是实用的 {#why}

传统的代码库分叉模型会大规模崩溃：每个用户维护自己的收件箱听起来像是一场维护噩梦。两个框架决策使其发挥作用：

1. **应用保持框架契约。** 源代码拥有领域行为，而 Core 会随着应用演进保持 actions、SQL、状态和同步的一致性。
2. **每用户自定义，无需每用户代码。** Skills、内存、指令、连接的 MCP 服务器和子代理都位于 SQL 中。每个用户都有自己的定制层；共享代码库同时托管所有这些内容。

结果：Claude - 每个用户的代码级灵活性，以及正常的 SaaS 部署经济性。

## 不想定制？ {#hosted}

你不必这样做。每个示例应用还可以作为 `agent-native.com` 上的托管应用程序使用 - `mail.agent-native.com`、`calendar.agent-native.com` 等。免费或付费使用托管版本；仅当您想要更改托管版本未公开的内容时才进行分叉。

### 对于开发者 {#dev-details}

如果您现在正在搭建脚手架，则 CLI 命令为：

```bash
npx @agent-native/core@latest create my-platform
```

CLI 会先询问 **如何开始？**。选择 **Chat** 可创建包含 Chat 和 Dispatch 的最小工作区，选择 **First-party template(s)** 可打开多选选择器。Community 和 Headless 是独立应用的入口。工作区应用共享身份验证、品牌、代理配置和数据库；每个应用都会连同所需的全部文件构建到 `apps/<name>/` 中。对于没有浏览器 UI 的自动化应用，而不是应用 UI，请使用 `npx @agent-native/core@latest create my-agent --headless`。

填写`.env`（主要是`ANTHROPIC_API_KEY`和`DATABASE_URL`）、`pnpm install`、`pnpm dev`，就可以了。没有“TODO：实现登录”，没有占位符路由。

部署目标：任何 Nitro 兼容主机（Node、Cloudflare、Netlify、Vercel、Deno、Lambda、Bun）和任何 Drizzle 兼容 SQL 数据库（SQLite、Postgres、Turso、D1、Supabase、Neon）。对于工作区，`npx @agent-native/core@latest deploy` 一次构建每个应用程序并将它们发送到单个源。参见[Deployment](/docs/deployment)。

要创作和发布您自己的应用模板，请参阅 [Creating Templates](/docs/creating-templates)。
