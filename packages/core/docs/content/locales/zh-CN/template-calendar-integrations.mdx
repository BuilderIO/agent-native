# 多应用工作区中的日历

日历只是 [Dispatch](/docs/template-dispatch) 工作区中众多应用之一。本页
介绍这在实践中究竟意味着什么：连接是如何运作的，以及其他应用可以对您的
日历采取哪些具体操作，或对日历上发生的事情做出哪些具体反应。有关概览，请
参阅 [日历](/docs/template-calendar)。

## 日历如何与 Dispatch 连接

这是否是自动完成的，取决于日历和 Dispatch 是如何被一起搭建起来的，而不取
决于两者中任何一个是托管运行还是本地运行。

### 同一工作区：自动完成

如果日历和 Dispatch 是通过 `create` 或 `add-app` 一起生成或添加到同一个
Agent-Native 工作区中，并作为一个整体部署的，那么它们已经共享同一个
`.env`、同一个 `A2A_SECRET` 和同一个工作区注册表。无论该工作区运行在您的
本机还是生产环境中，发现和经过身份验证的 A2A 调用都会自动生效，无需任何
额外设置。这是基于日历构建真正的多应用产品时应有的搭建方式。

### 独立部署：需要一步手动操作

如果日历和 Dispatch 是两个独立创建的 Agent-Native 项目，它们不会共享密
钥，因此还无法互相调用。连接它们需要在双方各执行一步手动操作：添加一个
带有共享密钥的 `remote-agents/<id>.json` 资源，可以从设置 → 已连接的代
理、Agent 页面的连接标签页，或 Dispatch → 代理 → 添加外部代理来完成。完
整的操作步骤请参阅 [A2A 协议](/docs/a2a-protocol)。

要检查您属于哪种情况，可以问任意一个应用的代理“你能看到哪些应用？”。如
果日历没有出现在 Dispatch 的回答中，那么您就属于第二种情况。

## 集成策略

**基于日历事件构建自动化。** 创建活动和创建预订都会在共享的框架事件总线
上触发一个真实的事件（`calendar.event.created`、`calendar.booking.created`）。
任何应用的[自动化](/docs/automations)都可以订阅其中任意一个事件，无论该
自动化是由哪个应用定义的。一条落到您日历上的预订，可以触发邮件中生成一封
欢迎邮件草稿，或在幻灯片中生成一份会议议程，在会议开始之前就准备好。日历
并没有内置提供这类自动化，但这个事件是真实的，随时可以在您想构建这类自动
化时接入。

**通过 Dispatch 进行自然语言委托。** 一个同级应用不需要任何特殊集成就能
与日历协同工作。它可以像您在聊天中那样，向日历的代理提交一条用简单易懂的
语言表达的请求，例如“下周找 Sam 空出 30 分钟”，日历会直接回答或据此执行
操作。这正是诸如邮件或 Slack 中收到的一条日程安排请求最终变成一个已预订
活动背后的真实机制：Dispatch（或接收到该消息的应用）把请求委托给日历的代
理，日历就像处理任何其他提示一样处理它。

**保持解耦。** 对于以上所有这一切，日历都不需要知道邮件或 Slack 的凭证，
反过来也一样。事件总线以及订阅它的自动化位于各应用之间，因此日历只需要发
出一个真实的事件，或回答一个真实的请求即可，它不需要知道是谁在监听，也不
需要知道监听的方式。
