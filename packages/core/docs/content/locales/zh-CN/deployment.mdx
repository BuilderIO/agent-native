# 部署

代理本机应用程序在底层使用 [Nitro](https://nitro.build)，这意味着您可以部署到任何平台，无需进行零配置更改 - 只需设置预设即可。

## 部署之前：选择持久数据库 {#persistent-database}

每个部署的应用程序都需要一个持久的 SQL 数据库。在本地开发中，agent-native 回退到 `data/app.db` 处的 SQLite 文件；这在您的计算机上很方便，但在可以重置文件系统的容器、预览或无服务器环境中并不持久。

在将应用推广到生产环境之前，在部署提供程序中设置 `DATABASE_URL`。 Agent-native 使用 Drizzle 进行架构和查询，因此数据层可跨 Drizzle 兼容的 SQL 后端移植，并且框架会自动检测 URL 的方言。有关适配器列表和方言详细信息，请参阅 [Database](/docs/database#production)。

仅当您的数据库提供程序需要单独的令牌（例如 Turso/libSQL）时才使用 `DATABASE_AUTH_TOKEN`。对于工作区，所有应用默认继承根`DATABASE_URL`；当一个应用程序应使用不同的数据库时设置 `<APP_NAME>_DATABASE_URL`。

## 工作区部署：一个源，多个应用 {#workspace-deploy}

如果您的项目是 [workspace](/docs/multi-app-workspace)，您可以使用一个命令将其中的每个应用程序发送到单个源：

```bash
npx @agent-native/core@latest deploy
# https://your-agents.com/mail/*       → apps/mail
# https://your-agents.com/calendar/*   → apps/calendar
# https://your-agents.com/forms/*      → apps/forms
```

每个应用程序均使用 `APP_BASE_PATH=/<name>` 和 `VITE_APP_BASE_PATH=/<name>` 构建，然后打包为目标 Nitro 预设。 Cloudflare Pages 是默认预设，并使用 `dist/_worker.js` 生成的调度程序工作人员； Netlify 在 `.netlify/functions-internal/<app>-server` 中为每个应用程序使用一个函数以及生成的重定向； Vercel 使用构建输出 API 编写工作区级 `.vercel/output`。

同源部署免费为您带来两大胜利：

- **共享登录会话** — 登录任何应用程序，每个应用程序都会登录。

发布输出：

```bash
wrangler pages deploy dist
```

对于 Netlify 统一部署，请使用 Netlify 预设：

```bash
npx @agent-native/core@latest deploy --preset netlify
```

对于 Vercel 统一部署，请使用 Vercel 预设：

```bash
npx @agent-native/core@latest deploy --preset vercel
```

配置提供程序构建命令时，请使用与 `--build-only` 相同的命令。 Vercel 应运行 `npx @agent-native/core@latest deploy --preset vercel --build-only`；该命令直接写入 `.vercel/output`，因此工作区路由不需要 `vercel.json`。

后台处理器。本地 `--build-only` 工件检查在没有它的情况下仍然可以运行。

仍然支持每个应用程序独立部署 - 只是 `cd apps/<name> && npx @agent-native/core@latest build` 就像独立的脚手架。

## 设置预设 {#setting-the-preset}

默认情况下，Nitro 为 Node.js 构建。要针对不同的平台，请在 `vite.config.ts` 中设置预设：

```ts
import { agentNative } from "@agent-native/core/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [agentNative({ nitro: { preset: "vercel" } })],
});
```

或者在构建时使用 `NITRO_PRESET` 环境变量：

```bash
NITRO_PRESET=netlify npx @agent-native/core@latest build
```

## Node.js（默认） {#nodejs}

默认预设。构建并运行：

```bash
npx @agent-native/core@latest build
node .output/server/index.mjs
```

设置`PORT`配置监听端口（默认：`3000`）。

使用当前的 Node.js LTS 系列进行生产部署。截至 2026 年 5 月，
是Node.js 24； Node.js 20 已于 2026 年 4 月 30 日达到使用寿命，不再适用
接收上游安全更新。

### Docker {#docker}

```dockerfile
FROM node:24-slim AS build
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile
COPY . .
RUN pnpm build

FROM node:24-slim
WORKDIR /app
COPY --from=build /app/.output .output
# data/ 是运行时创建的 SQLite 目录 - 不要将开发数据库复制到产品中。
# 对于生产，将 DATABASE_URL 设置为托管的 Postgres 或 Turso 实例。
RUN mkdir -p /app/data
ENV PORT=3000
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

## Netlify {#netlify}

Nitro `netlify` 预设运行良好，在实践中，对于与外部 Postgres (Neon) 通信的模板，它比 Cloudflare Pages 更快地冷启动（TTFB 与 ~9 秒相比约为 200 毫秒）。在 `vite.config.ts` 中设置预设：

```ts
// vite.config.ts
export default defineConfig({
  plugins: [agentNative({ nitro: { preset: "netlify" } })],
});
```

...或在构建时设置 `NITRO_PRESET=netlify`。

对于工作区，通过运行以下命令从一个 Netlify 站点部署每个应用：

```bash
npx @agent-native/core@latest deploy --preset netlify
```

工作区构建在 `dist/_workspace_static/` 下写入静态资产，并将每个应用程序路由到自己的 Netlify 函数，而无需强制资产重定向，因此像 `/mail/assets/...` 这样的文件会在服务器函数处理应用程序路由之前静态提供服务。

### Keep-warm 与缩容到零的数据库 {#netlify-keep-warm}

启用后，Netlify 构建会生成一个计划函数，**每分钟**请求一次 `/_agent-native/health`。这会让服务器函数及其数据库保持温热，使空闲一段时间后的下一位访问者不必承担冷启动（在 Neon 上为 1–5 秒）。

Keep-warm **默认关闭**，因为每分钟唤醒会阻止按量计费、可缩容到零的数据库自动挂起。只有当下一位访问者的低延迟值得数据库持续运行时，才设置 `AGENT_NATIVE_ENABLE_KEEP_WARM=1`。

| 变量                                        | 效果                                                             |
| ------------------------------------------- | ---------------------------------------------------------------- |
| `AGENT_NATIVE_ENABLE_KEEP_WARM`             | 启用服务器和数据库的计划预热。默认未设置。                       |
| `AGENT_NATIVE_DISABLE_KEEP_WARM`            | 兼容性禁用开关；设置后优先于启用标志。                           |
| `AGENT_NATIVE_KEEP_WARM_SCHEDULE`           | 启用后覆盖节奏；默认值为 `* * * * *`，无法解析的值会使构建失败。 |
| `AGENT_NATIVE_DISABLE_KEEP_WARM_BACKGROUND` | 启用 keep-warm 后仅取消后台函数预热，仍保持服务器温热。          |

如果你使用免费或受配额限制的数据库套餐，请不要设置 `AGENT_NATIVE_ENABLE_KEEP_WARM`。如果启用它，请选择更慢的节奏或设置 `AGENT_NATIVE_DISABLE_KEEP_WARM_BACKGROUND=1`。

### 按需 schema DDL {#skip-ensure-tables}

每个 store 在首次接触数据库时调用 `ensureTable()`，它会探测 `information_schema` / `pg_indexes`，并只对确实缺失的对象执行 `CREATE TABLE` / `ADD COLUMN` / `CREATE INDEX`。在长期运行的 Node 服务器上，这个开销每次启动只付一次，几乎不可见。在 serverless 上，「首次接触」发生在**每一次冷启动**，涉及约 57 个 store —— 因此一个冷请求可能在做任何实际工作之前先付出数百次串行往返。

有两点可以减少它：

- 这些探测由**每个数据库一次批量 introspection**（两条查询）来回答，而不是每张表、每个列、每个索引各一条查询。这是自动的，无需配置。
- `AGENT_NATIVE_SKIP_ENSURE_TABLES=1` 会完全跳过探测与 DDL 流程，这是可获得的最大冷启动延迟收益。

当你的数据库 schema 已经迁移完毕、并且不希望应用启动去创建或修改表时，设置 `AGENT_NATIVE_SKIP_ENSURE_TABLES=1` —— 这是具备真实迁移步骤的生产部署的常规情况。

<Callout tone="risk">

**这个开关不会、也无法「失败即关闭」。** 如果 schema 确实缺失，第一条真实查询会大声失败，而不是被就地修复 —— 这正是目的，但也意味着迁移由你负责。不要在依赖应用启动来创建表的部署上设置它。

</Callout>

## SSR 缓存 {#ssr-caching}

每个 SSR HTML 响应和每个 React Router `.data` 响应都是同一个非个性化的公共外壳：`createH3SSRHandler` 会在渲染前剥离 cookie，因此同样的字节对每个访问者都是正确的，所有个性化都在加载完成后于客户端进行。这正是为什么默认在这些响应上盖上单一硬缓存策略是安全的：

```txt
cache-control: public, max-age=600, stale-while-revalidate=604800, stale-if-error=3600
```

同样的值会镜像到 `cdn-cache-control` 和 `netlify-cdn-cache-control` 上。这样一个共享的 CDN 条目就能服务整个站点，而不是逐请求渲染，这是首次响应延迟上最大的单一杠杆——除非您的部署符合下面的某种情况，否则请保持开启。

### 使用 `AGENT_NATIVE_SSR_CACHE` 覆盖设置 {#ssr-cache-env}

在部署环境中设置 `AGENT_NATIVE_SSR_CACHE`，即可更改整个部署的策略：

| 值                                                  | 结果                                                                                  |
| --------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 未设置、`on`、`default`、`true`、`1`                | 上面的默认策略，不变。推荐——性能最佳。                                                |
| `off`、`false`、`0`、`none`、`no-store`、`disabled` | `cache-control`、`cdn-cache-control` 和 `netlify-cdn-cache-control` 上的 `no-store`。 |
| 一个时长：`30`、`30s`、`5m`、`2h`                   | `public, max-age=<n>, stale-while-revalidate=<n>, stale-if-error=3600`。              |

裸数字表示秒。`stale-while-revalidate` 有意为自定义时长镜像 `max-age`：将一个短的新鲜度窗口与默认的七天陈旧窗口搭配，会恰好返回您本想选择退出的那种陈旧数据。无法识别的值会记录一条警告并回退到默认值，因此拼写错误永远不会悄悄禁用 CDN。

在以下任一情况成立时，请将其调低或关闭：

1. **您的主机不会在部署时清除其 CDN。** Netlify 和 Vercel 会；一些自托管的部署不会。如果没有清除，已发布的构建可能会在 `max-age` 加上 `stale-while-revalidate` 的时长内继续提供之前的外壳。
2. **您的加载器返回可变的公共数据。** 在一次成功的变更之后，`useRevalidator()` 或操作后重定向触发的重新获取，可能会读取浏览器缓存的 `.data` 副本，而不是最新的加载器输出。

该设置适用于每一个公共外壳界面：React Router 的 SSR HTML 与 `.data`、登录 HTML 外壳、`/_agent-native/speculation-rules.json` 路由、文档站点，以及 forms 模板中的公共表单 SSR。生成的 Cloudflare Worker 会在构建时解析该值，因此请在构建运行之前于部署环境中设置它。

有三点需要记住：

- **关闭缓存并不会让 SSR 变得个性化。** Cookie 在渲染前仍会被剥离，SSR 加载器仍然只会看到匿名分支。用户专属数据依然必须在客户端解析。此变量只控制缓存*时长*。
- **它是部署范围的设置，而非按路由，这是有意为之的设计。** 按路由或按请求的缓存覆盖，会导致一个访问者的负载最终出现在另一个访问者共享的 CDN 条目中，因此框架不提供这种选项——`guard:ssr-cache-shell` 会强制执行这一点。
- **对于需要变更后立即新鲜的数据，优先使用 actions 而不是禁用缓存。** 应用数据属于 [actions](/docs/actions)，通过 `useActionQuery` / `useActionMutation` 从客户端读取，并通过 `useDbSync()` 轮询保持实时；这些都不会经过 SSR 外壳缓存。让 SSR 加载器继续渲染公共外壳，只有在您确实需要更新鲜的加载器数据时，才使用此变量。

| `AGENT_NATIVE_KEEP_WARM_SCHEDULE`           | 启用后覆盖 keep-warm 节奏（默认 `* * * * *`）。无法解析的值会使构建失败。参见 [Keep-warm](#netlify-keep-warm)。                                                                                                                                                                       |
| `AGENT_NATIVE_DISABLE_KEEP_WARM_BACKGROUND` | 启用 keep-warm 后仅取消后台函数预热。参见 [Keep-warm](#netlify-keep-warm)。                                                                                                                                                                                                           |
| `AGENT_NATIVE_DISABLE_INPROCESS_SWEEPS`     | 关闭进程内的兜底清扫定时器（自动化重派发、agent-teams 对账、沙箱执行恢复）。在 serverless 上它们按每个温实例运行，因此查询速率随实例数增长。**仅**在已有持久调度器驱动同样的恢复时才设置，否则排队的工作不会被重试。                                                                  |
| `AGENT_NATIVE_SKIP_ENSURE_TABLES`           | 完全跳过按需 schema DDL。移除每次冷启动在做任何工作前都要支付的 schema 探测往返。要求 schema 已经迁移完毕 —— 参见 [按需 schema DDL](#skip-ensure-tables)。                                                                                                                            |
| `AGENT_NATIVE_BUILDER_RELAY_SECRET`         | 用于预览安全的 Builder 授权中继的专用 32+ 字符共享 HMAC 密钥。只有当授权结果必须写入隔离的预览数据库时，才在获批的企业回调部署和预览部署上设置相同的值。                                                                                                                              |
| `AGENT_NATIVE_BUILDER_RELAY_TARGET_ORIGINS` | 仅用于企业回调的、以逗号分隔的精确可信预览来源允许列表（例如 `https://0123456789abcdef01234567--content.netlify.app`）。仅在企业回调部署中设置。Netlify 来源必须使用包含 24 位十六进制 ID、不可变且特定于部署的永久链接；可变的 `deploy-preview-*` 别名、通配符和域名后缀均会被拒绝。 |

数据库连接变量（`DATABASE_URL`、`DATABASE_AUTH_TOKEN`、每个应用程序 `<APP_NAME>_DATABASE_URL`）位于 [Database](/docs/database#production) 中。

### 生产敏感配置 {#env-required-prod}

这些设置涵盖生产敏感行为。使用框架身份验证的独立应用需要稳定的 `BETTER_AUTH_SECRET` 和持久数据库；未设置公开 auth URL 时，框架会根据请求、模板或托管平台上下文推断。Workspace 和 A2A 设置取决于使用的功能。缺失值要么安全失败，要么在发出明确警告后回退到较弱行为。

| 变量                                        | 描述                                                                                                                                                                                      |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BETTER_AUTH_SECRET`                        | 32+ 字符的随机字符串。签署会话 cookie，并作为 `OAUTH_STATE_SECRET` 和应用本地加密值的后备。它也是读取现有共享保管库密文的旧版候选项。生产环境中必需。                                     |
| `BETTER_AUTH_URL`                           | 此应用程序公共来源的可选覆盖值（例如 `https://mail.example.com`）。未设置时，框架会根据请求、模板和托管平台上下文推断。                                                                   |
| `ANTHROPIC_API_KEY`                         | API 嵌入式生产代理密钥。 **在多租户部署中**，当用户没有每用户密钥时，框架拒绝回退到此 - 需要自带密钥。单租户自托管安装将其用作全局密钥。                                                  |
| `OAUTH_STATE_SECRET`                        | 用于 OAuth 状态信封（Google、Atlassian、Zoom）的专用 HMAC 密钥。未设置时回落到 `BETTER_AUTH_SECRET`，但建议使用专用值，以便旋转一个值不会使另一个值无效。通过`openssl rand -hex 32`生成。 |
| `A2A_SECRET`                                | 应用间 A2A JSON-RPC 的共享 HMAC。未设置专用工作区密钥时，共享保管库使用由此值按用途派生的密钥，因此轮换它也会轮换保管库密钥。                                                             |
| `WORKSPACE_SECRETS_ENCRYPTION_KEY`          | 共享工作区保管库首选的稳定 AES-256-GCM 密钥。每个读取保管库的应用都应设置相同值；它与应用本地 OAuth 加密分开。                                                                            |
| `WORKSPACE_SECRETS_ENCRYPTION_KEY_PREVIOUS` | 轮换期间可选的旧工作区密钥。与新密钥一起部署，等待读取迁移数据行，然后删除旧密钥。                                                                                                        |
| `SECRETS_ENCRYPTION_KEY`                    | 用于应用本地加密和保管库的旧版组合密钥。仍受支持，但新的多应用部署应使用专用工作区密钥。                                                                                                  |

### 身份验证和身份 {#env-auth}

OAuth 提供商凭证（Google、GitHub）、静态 MCP 承载后备（`ACCESS_TOKEN` / `ACCESS_TOKENS`）和电子邮件验证切换记录在 [Authentication](/docs/authentication) 中。根据您选择的身份验证模式将它们设置在那里。

### 入站Webhooks {#env-webhooks}

每个消息集成在生产中都需要自己的签名密钥（当密钥丢失时，处理程序会因伪造请求而失败关闭）。每个积分变量列在 [Messaging](/docs/messaging) 和 [Security](/docs/security) 中。仅对于本地开发，`AGENT_NATIVE_ALLOW_UNVERIFIED_WEBHOOKS=1` 选择返回“警告并接受”——永远不要在产品中设置它。

### 安全配置（选择加入） {#security-config}

默认值是严格的。一些选择加入标志放松了行为（调试堆栈跟踪、未经验证的 webhooks、工作区范围的密钥回退、MCP 集线器多组织切换、运行时 env-var 写入）。它们的安全权衡记录在 [Security](/docs/security) 中。除非您特别想要宽松的路径，否则不要设置它们。

### 工作区.env继承 {#env-inheritance}

在工作空间内，根 `.env` 会自动加载到每个应用程序中，因此 `ANTHROPIC_API_KEY`、`A2A_SECRET`、`BETTER_AUTH_SECRET` 和 `OAUTH_STATE_SECRET` 等共享密钥只需设置一次。每个应用 `apps/<name>/.env` 在冲突中获胜。

### 生成强大的秘密 {#env-generate-secrets}

对于任何标记为“32+ char random”的密钥（`BETTER_AUTH_SECRET`、`OAUTH_STATE_SECRET`、`A2A_SECRET`、`SECRETS_ENCRYPTION_KEY`、`AGENT_NATIVE_BUILDER_RELAY_SECRET`），请使用以下命令生成新值：

```bash
openssl rand -hex 32
```

通过替换每个实例上的环境变量并重新部署来轮换它们 — 使用旧密钥签名的会话/OAuth 状态信封将变得无效，因此用户可能需要再次登录。

## 生产代理工具 {#production-agent-tools}

生产代理从
代理聊天插件。默认启用 SQL 检查；数据库写入通过类型化应用程序 actions 进行，
除非应用程序明确启用原始写入工具：

```ts
// server/plugins/agent-chat.ts
export default createAgentChatPlugin({
  frameworkTools: {
    database: "read", // "write" | "read" | "off" — default "read"
    extensions: true, // default false
  },
});
```

```ts
// server/plugins/core-routes.ts
export default createCoreRoutesPlugin({
  extensionTools: true,
});
```

- `database: "read"` — 默认。仅注册 `db-schema` 和 `db-query`；
  代理使用 SQL 检查数据，但必须使用类型化应用程序 actions 进行写入。
- `database: "write"` 或 `true` — 还会注册 `db-exec` 和 `db-patch`
  用于有意的原始 SQL 维护。写入范围限定为当前用户/组织，并阻止架构更改。
- `database: "off"` 或 `false` — 从
  代理表面，因此应用程序的 actions 是唯一的数据访问路径。
- `extensions: true` — 为应用启用框架扩展管理 actions 和提示指导
  （`create-extension`、`update-extension` 等）。在两个 plugins 上都设置
  此选项，也可允许经过身份验证的 REST 创建。扩展默认关闭。

其余分组都是布尔值，默认全部开启：`sharing`, `review`, `history`, `featureFlags`, `localization`, `audit`, `contextXray`, `userProfile`, `automation`, `docs`, `resources`, `web`, `workspaceApps`, `chat`, `email`。
在语音优先或单一用途的应用中，可用 `frameworkTools: "minimal"` 一次关闭全部；
若只想保留一个，可写成 `frameworkTools: { preset: "minimal", resources: true }`——
显式的分组键始终优先于预设。

关闭某个分组只会将它从**智能体**侧的表面移除：交互式聊天、MCP、A2A 和后台运行。
对应的 HTTP action 路由仍然挂载，因为 UI 是通过客户端 hooks 调用它们的——关闭
`sharing` 不应让仍显示在界面上的分享对话框返回 404。请先权衡这项对等性代价：
框架的约定是 UI 能做的事智能体也能做，所以在分享按钮可见的情况下设置
`sharing: false` 是一次有意的破坏，只有当应用根本没有该表面时才合理。

与该选项无关，框架工具默认不再加载进第一次模型请求。它们仍留在可搜索的注册表中，
通过 `tool-search` 加载；若应用在 `initialToolNames` 中指定，则会立即加载。

<Callout tone="warning">
  顶层的 `databaseTools` 与 `extensionTools` 选项已废弃，请改用
  `frameworkTools.database` 和 `frameworkTools.extensions`。它们仍会被识别，但当
  顶层标志与 `frameworkTools` 中的对应值冲突时，plugin
  会在启动时抛出错误，而不是 以无人选择的工具表面启动。
</Callout>

## 生产代码执行 {#production-code-execution}

默认情况下，生产代理在没有代码执行工具的情况下运行。他们可以调用应用程序 actions、数据库工具、MCP 工具、浏览器/会话工具和其他已注册的框架工具，但他们无法获得 shell 或文件系统访问权限。

节点兼容的部署可以通过代理聊天插件或环境覆盖选择生产代码执行：

```ts
// server/plugins/agent-chat.ts
export default createAgentChatPlugin({
  codeExecution: { production: "sandboxed" },
});
```

可用模式有：

- `off` — 默认值。生产环境中未注册任何代码执行工具。
- `sandboxed` — 注册 `run-code`，一个隔离的 Node.js JavaScript 运行器，具有清理环境、新的临时目录、输出/时间限制以及本地主机桥，以连接到允许列入名单的注册工具，例如 `provider-api-request`、`provider-api-docs`、`provider-api-catalog`、`web-request` 以及使用的资源支持的工作区文件桥作者：`workspaceRead` / `workspaceWrite`。
- `trusted` — 注册 `run-code` 以及完整的编码工具注册表（`bash`、`read`、`edit`、`write`）。仅将其用于单租户或操作员控制的部署，其中有意对主机进行完全 shell 访问。

设置 `AGENT_PROD_CODE_EXECUTION=sandboxed` 或 `AGENT_PROD_CODE_EXECUTION=trusted` 以覆盖特定部署的插件选项，而无需更改代码。即使插件选项启用了它，`AGENT_PROD_CODE_EXECUTION=off` 也会强制代码执行。

`run-code` 沙箱是进程级隔离，而不是操作系统容器。它从子进程环境中剥离应用程序机密，并在可用时使用 Node 权限模型，但出站网络不会被 Node 本身阻止；经过身份验证的调用应通过该工具公开的桥接助手。

## 在生产中更新 UI {#updating-ui-in-production}

普通的已部署应用代理通过应用工具 - actions、数据库、MCP 和已配置的集成 - 工作，而不会自动获得源代码访问权限。源代码更改属于仓库开发工作流。嵌入式、本地或 Builder frame 只有在被有意授予工作区和写入工具时才能编辑仓库。

在 [production code execution](#production-code-execution) 关闭的标准生产部署中，代理可以访问应用程序工具（actions、数据库、MCP），但不能访问文件系统。这意味着代理可以读取和写入数据、运行 actions 以及与外部服务交互 - 但它无法编辑 React 组件或在已部署的实例上添加新路由。

### Builder.io：制作中的可视化编辑 {#builderio}

[Builder.io](https://www.builder.io?utm_source=agent-native&utm_medium=docs&utm_campaign=framework&utm_content=deployment) 是一个独立的托管代码工作流，代理可在其中修改生产应用的 UI。将仓库连接到 Builder.io（提供免费套餐）后即可直接请求 UI 更改，无需重新部署。

**Connect Builder** in Settings uses Builder OAuth (`builder:ai:invoke`) with a same-origin HTTPS callback under `/_agent-native/builder/callback`, so hosted origins such as Railway work without a domain allowlist. Legacy `BUILDER_*` private keys remain a runtime fallback for existing connections.

**工作原理：**

1. 将您的代理本机存储库连接到 Builder.io（提供免费套餐）
2. Builder.io提供具有代理、可视化编辑和实时协作的云框架
3. 提示代理进行 UI 更改 - 它会实时编辑您的组件、路线和样式
4. 更改将提交回您的存储库

有关嵌入式代理面板与云框架选项的更多信息，请参阅 [Frames](/docs/frames)。

## 多实例部署 {#multi-instance}

代理本机应用程序通过 Drizzle 将所有状态存储在 SQL 中，并通过 [polling](/docs/key-concepts#polling-sync) 与数据库同步 UI — 无文件系统状态、无粘性会话、无内存缓存。这意味着多实例和无服务器部署开箱即用：将每个实例指向同一个 `DATABASE_URL`，它们会自动聚合。请参阅 [Key Concepts — Data in SQL](/docs/key-concepts#data-in-sql) 和 [Portability](/docs/key-concepts#hosting-agnostic)。
