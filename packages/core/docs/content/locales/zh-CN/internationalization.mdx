# 国际化

Agent Native 应用可以通过共享的 `@agent-native/core/client/i18n` 运行时来本地化框架和模板 UI。框架会将用户的语言选择存储在 SQL 设置中，并将其公开为 actions。当应用尚未翻译某个字符串时，框架会回退到英语。

## 运行时

通过 `AppProviders` 使用该提供者：

```tsx
import { AppProviders } from "@agent-native/core/client/hooks";
import { getLocaleInitScript } from "@agent-native/core/client/i18n";
import { i18nCatalog } from "./i18n";

const LOCALE_INIT_SCRIPT = getLocaleInitScript();

<script
  data-agent-native-locale-init
  dangerouslySetInnerHTML={{ __html: LOCALE_INIT_SCRIPT }}
/>;

<AppProviders queryClient={queryClient} i18n={{ catalog: i18nCatalog }}>
  <Outlet />
</AppProviders>;
```

`getLocaleInitScript()` 会在 React 水合之前设置初始的 `lang`、`dir` 和
`window.__AGENT_NATIVE_LOCALE__`。公共 SSR 路由可以从
`@agent-native/core/server` 调用 `resolveLocaleFromRequest()`，并将解析出的
区域设置或目录传入该脚本，以避免水合不匹配。

## 目录

每个已本地化的模板都会将目录保存在 `app/i18n/` 下：

```ts filename="app/i18n/index.ts"
import { createAgentNativeI18nCatalog } from "@agent-native/core/client/i18n";
import enUS from "./en-US";

export const i18nCatalog = createAgentNativeI18nCatalog({
  messages: enUS,
  localeLoaders: {
    "zh-CN": () => import("./zh-CN"),
    "zh-TW": () => import("./zh-TW"),
    "es-ES": () => import("./es-ES"),
    "fr-FR": () => import("./fr-FR"),
    "de-DE": () => import("./de-DE"),
    "ja-JP": () => import("./ja-JP"),
    "ko-KR": () => import("./ko-KR"),
    "pt-BR": () => import("./pt-BR"),
    "hi-IN": () => import("./hi-IN"),
    "ar-SA": () => import("./ar-SA"),
  },
});
```

`messages` 会直接打包 `en-US`，因此在任何区域设置加载之前它始终可用。
`localeLoaders` 会动态导入其余的每个目录，这样用户只需下载当前使用的
区域设置。支持的区域设置代码为 `en-US`、`zh-CN`、`zh-TW`、`es-ES`、
`fr-FR`、`de-DE`、`ja-JP`、`ko-KR`、`pt-BR`、`hi-IN` 和 `ar-SA`。

这份列表是由框架固定下来的，并不只是这个示例恰好打包的内容。
`LocaleCode` 是一个恰好包含这些代码的 TypeScript 联合类型，
`set-localization-preference` 会在运行时拒绝其他任何值。每个区域设置
还需要由框架维护的元数据，例如从右到左语言的文字方向。添加新的
区域设置意味着扩展框架本身，而不是在应用中添加一个目录文件。

`createAgentNativeI18nCatalog` 还接受一个可选的 `sourceLocale`（默认值
为 `en-US`）和一个可选的 `supportedLocales` 数组。当应用只为框架支持
的部分区域设置（而不是全部十种）提供翻译时，需要设置
`supportedLocales`。它默认包含框架支持的所有区域设置。`LanguagePicker`
只会列出这个集合中的区域设置，任何检测到或请求的区域设置如果不在
其中，都会回退到 `sourceLocale`。

## UI

使用 `useT()` 来翻译界面字符串：

```tsx
import { useT } from "@agent-native/core/client/i18n";

function Greeting({ name }: { name: string }) {
  const t = useT();
  return <p>{t("greeting.hello", { name })}</p>;
}
```

使用 `useFormatters()` 来处理日期、数字、相对时间和列表。不要把与
区域设置相关的日期或数字格式放进翻译字符串里。

在应用中任何允许用户更改语言的地方放置 `<LanguagePicker />`。有关
标准设置页面模式，包括 `openAgentSettings()` 适合放在哪里，请参阅
[工具包：设置](/docs/toolkit-settings)。

## Actions 与持久化

每个应用都会继承：

- `get-localization-preference` — 读取当前用户的 `{ locale, timezone }`
- `set-localization-preference` — 设置 `locale` 和/或 `timezone`，两者均为可选

`locale` 可以是 `"system"`，也可以是受支持的 BCP-47 区域设置。
`timezone` 可以是 `"system"`，也可以是像 `America/New_York` 这样的
IANA 时区。它的存在是为了让计划任务和自动化工作按照用户所在时区
运行，而不是按照宿主所在时区运行。只设置其中一个字段时，另一个
字段会保持不变，因为 `set-localization-preference` 会合并到已存储
的值上，而不是直接覆盖它。

持久化的值存储在用户范围的 SQL 设置中的 `localization` 下。
`localStorage` 仅用于预水合阶段和匿名回退。当前使用的区域设置会
作为环境上下文镜像到应用状态中，以便代理能够看到当前的界面语言。

## 守卫

运行：

```bash
pnpm guard:i18n-catalogs
```

对于应用和模板目录，该守卫会检查：

- 区域设置文件名、键的一致性、占位符的一致性以及过时的键
- 重复的键和遗留的仅限开发环境的标记
- 错误文字系统混入的问题，例如阿拉伯语目录中出现中文文本
- 通过 `Intl.PluralRules` 检查 CLDR 复数类别
- 应用源码中 `t()` 调用所使用的键在英文目录中缺失的情况

该守卫检查的是结构，而不是翻译质量。高可见度的字符串仍然需要
人工审查。

不要翻译稳定的标识符，例如 action 名称、路由、枚举值、应用状态键、
数据库值、协议字段、环境变量名称或提供程序名称。
