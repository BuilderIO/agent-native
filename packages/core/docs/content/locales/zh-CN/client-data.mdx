# 数据与同步

从客户端应用读取和写入应用数据的主要方式是通过 [action](/docs/actions-overview) 钩子。通过将请求封装进 actions，您的客户端和代理都能以相同的方式与应用交互。

在下面的示例中，一个工单先通过下拉菜单手动分配给当前用户，然后再通过聊天代理分配。UI 和代理访问的是同一个 action。

### Action 钩子 {#action-hooks}

您最可能用到的两个 action 钩子是：`useActionQuery()` 和 `useActionMutation()`。这两个钩子提供对您应用中 actions 的访问。

该钩子用于只读 actions，是围绕 [useQuery()](https://tanstack.com/query/latest/docs/framework/react/reference/useQuery) 函数的一层轻量封装。

在下面的示例中，调用了 `list-tickets` action，这类似于对所有工单发起一次 GET 请求。

```ts
import { useActionQuery } from "@agent-native/core/client/hooks";

const { data, isLoading } = useActionQuery("list-tickets", {});
```

下面的示例展示了通过 `get-ticket` action 获取单个工单的请求。提供 `ticketId` 用于将查询限定为只返回特定工单。额外提供的 `enabled` 选项确保该查询不会自动运行，而是只在存在 `ticketId` 时才运行。

```ts
import { useActionQuery } from "@agent-native/core/client/hooks";

const { data, isLoading } = useActionQuery(
  "get-ticket",
  { ticketId: ticketId ?? "" },
  { enabled: Boolean(ticketId) },
);
```

该钩子用于会改变数据的 actions，例如创建、更新或发送某些内容，是围绕 [useMutation()](https://tanstack.com/query/latest/docs/framework/react/reference/useMutation) 函数的一层轻量封装。

与 `useActionQuery()` 不同，action 的输入不会传给钩子本身，而是在您准备运行该变更时传给 `mutate()` 或 `mutateAsync()`。

在下面的示例中，调用 `send-ticket-reply` action 来为工单发布一条回复。从事件处理函数（例如按钮的 `onClick`）中调用 `mutate()`。

```ts
import { useActionMutation } from "@agent-native/core/client/hooks";

const { mutate, isPending } = useActionMutation("send-ticket-reply");

mutate({ ticketId, body: draft });
```

下面的示例展示了带有 `onSuccess` 选项的同一个变更。每次变更后缓存失效都会自动发生，所以 `onSuccess` 只在需要处理本地副作用时才用到，例如回复发送后清空回复输入框。

```ts
import { useActionMutation } from "@agent-native/core/client/hooks";

const { mutate, isPending } = useActionMutation("send-ticket-reply", {
  onSuccess: () => setDraft(""),
});

mutate({ ticketId, body: draft });
```

### 按资源限定失效范围 {#resource-scoped-invalidation}

两个钩子都接受可选的 `resources` 数组。查询指定它读取的资源，变更指定它修改的资源。使用 `type` 表示整个资源类型，使用 `type:id` 表示特定 ID。匹配本地变更时，`type:id` 标签中的第一个冒号用于分隔类型和 ID。类型不能包含冒号，但 ID 可以包含冒号。同步事件分别携带类型和 ID。

```ts
import {
  useActionMutation,
  useActionQuery,
} from "@agent-native/core/client/hooks";

const tickets = useActionQuery("list-tickets", {}, { resources: ["ticket"] });
const ticket = useActionQuery(
  "get-ticket",
  { ticketId },
  { resources: [`ticket:${ticketId}`] },
);
const reply = useActionMutation("send-ticket-reply", {
  resources: [`ticket:${ticketId}`],
});
```

对于不含冒号的类型和记录 ID 非空的标签，本地变更和同步事件使用对称匹配。对于整个类型的本地变更，使用 `type`，而不是 `type:`。匹配本地变更时，`design:layer` 表示类型 `design` 和 ID `layer`。`resourceType` 为 `design:layer` 的同步事件使用的类型不同于 `design`，不会匹配查询标签 `design`。`ticket` 标签匹配 `ticket` 和任意 `ticket:id` 标签。`ticket:123` 标签匹配 `ticket` 和 `ticket:123`，但不匹配 `ticket:456`。没有标签的查询会保守地失效。没有标签的变更会使所有 action 查询失效。

对于 action 同步事件，`resourceType` 和 `resourceId` 分别标识已更改的资源。如果 `resourceId` 缺失或为空，则所有匹配该类型的查询都会失效。如果任何未被抑制的 action 事件缺少 `resourceType`，该批次将禁用资源范围过滤，所有 action 查询都有可能失效。可选的谓词仍可过滤失效操作。

对于包含 action 事件且仅包含 action 或 app-state 事件的批次，资源过滤器匹配未被抑制的 action 事件中任一已更改资源。提供 `actionInvalidatePredicate` 时，查询必须同时通过资源过滤器和谓词。谓词接收完整的相关非 awareness 事件批次，包括被抑制的 action 事件。如果批次还包含其他会更改数据的来源，则禁用资源范围过滤，但仍应用谓词。对于包含其他数据变更事件但没有未被抑制的 action 事件的批次，谓词也会过滤广泛的 action 失效操作。

action 的 `changeResource` 指定一个用于事件投递和访问检查的资源。它不一定是 action 写入内容的完整列表。只有当每个相关 action 投递的标记能够代表查询依赖的所有记录时，使用特定记录的查询标签才是安全的。对于标记类型内的批量写入或跨记录依赖，可以使用整个类型的查询标签匹配已投递的事件。对于跨类型依赖，请在查询标签中包含每个已投递事件的类型，或使用不带标签的查询。多个独立投递的事件可以覆盖受影响的记录，但每位相关查看者都必须收到自己有权访问的事件。扩大客户端标签只会改变事件投递后的匹配，不能让无权访问投递资源的查看者看到该事件。必须确保相关查看者能收到自己有权访问的事件。

该函数用于 React 渲染流程之外的一次性命令式 action 调用，例如普通的事件处理函数、脚本，或任何其他非 React 代码路径。它直接返回一个 promise，而不是一个钩子结果。

在下面的示例中，`update-ticket` action 在 React 渲染流程之外，从一个键盘快捷键处理函数中被调用，将工单分配给一名客服。

```ts
import { callAction } from "@agent-native/core/client/hooks";

await callAction("update-ticket", {
  ticketId,
  assignedToEmail: "jordan@example.com",
});
```

下面的示例展示了带有 `timeoutMs` 选项的同一个调用，适用于那些确实需要比默认 60 秒超时更长时间的 actions。

```ts
import { callAction } from "@agent-native/core/client/hooks";

await callAction(
  "update-ticket",
  { ticketId, assignedToEmail: "jordan@example.com" },
  { timeoutMs: 120_000 },
);
```

每个 `useActionQuery()`、`useActionMutation()` 和 `callAction()` 请求都受 60 秒超时限制，超时会以错误的形式呈现，而不会静默重试。`useActionQuery()` 还会使用 React Query 的 abort signal 自动取消被替代的请求。

### 失败的写入 {#write-failures}

当用户发起的保存失败时，应用会显示一个共享的 toast 提示，而不是毫无反应。`useActionMutation()` 会自动完成这一步。失败的 `mutate()` 会显示 toast，除非 `onError` 处理了该失败（无论是在 hook 选项中还是在 `mutate()` 调用中）。失败的 `mutateAsync()` 只有在拒绝未被处理时才会显示 toast，例如上层没有 `try/catch` 的 `await`。如果 `catch` 抛出了新的 `Error` 来替代原始错误，则不会被报告。

`errorNotification` 选项会改变这一默认行为：

| 值               | 行为                                                                               |
| ---------------- | ---------------------------------------------------------------------------------- |
| `"auto"`（默认） | 仅当没有其他代码处理该失败时才显示 toast。                                         |
| `"shared"`       | 即使您自己有 `onError`，每次失败都会显示 toast。当处理函数只回滚或记录日志时使用。 |
| `"caller"`       | 从不显示 toast。用于后台保存、您有意忽略的失败，或由页面自行渲染错误的位置。       |

`errorLabel` 会用您已翻译好的文本替换 toast 的标题。在下面的示例中，分配失败时会显示该标题，而不是通用标题。

```tsx
import { useActionMutation } from "@agent-native/core/client/hooks";

const assign = useActionMutation("update-ticket", {
  errorLabel: t("tickets.assignFailed"),
});

assign.mutate({ ticketId, assignedToEmail: "jordan@example.com" });
```

在下次修改时自动重试的自动保存不应打断用户，因此将其关闭。

```tsx
import { useActionMutation } from "@agent-native/core/client/hooks";

const saveDraft = useActionMutation("save-ticket-draft", {
  errorNotification: "caller",
});
```

不是 `useActionMutation()` 的写入操作，例如用于上传的 `fetch`，或吞掉错误的 `catch`，应使用 `reportWriteFailure()` 报告失败。原始 `fetch` 的错误不包含状态码，因此 toast 会显示您设置的标签或通用标题。原始的 `useMutation()` 可以通过传入 `meta: surfaceMutationError(label)` 参与其中，该函数接受同样可选的标签。

```ts
import { reportWriteFailure } from "@agent-native/core/client/write-failure";

try {
  const response = await fetch(uploadUrl, { method: "PUT", body: file });
  if (!response.ok) throw new Error(`Upload failed with ${response.status}`);
} catch (error) {
  reportWriteFailure(error, { label: t("tickets.uploadFailed") });
}
```

toast 的文本取决于失败类型。被取消的请求不会显示任何内容。离线、超时、`401` 和 `403` 各自会在标题下方显示一条简短的翻译消息。`5xx` 只显示标题，因为服务器会隐藏其自身的错误文本。当 action 通过 `fail()` 返回类型化的 `4xx` 错误时，toast 会显示 action 编写的消息；参见 [Action 失败](/docs/actions-defining#failing)。`401` 或 `403` 永远不会显示服务器文本。

`AppProviders` 总会挂载监听这些失败的组件 `WriteFailureToaster`。它通过应用的 `Toaster` 显示 toast，因此传入 `toaster={null}` 的应用需要自己渲染 `Toaster`。不使用 `AppProviders` 的应用，需要在 `QueryClientProvider` 内、自己的 `Toaster` 旁边渲染来自 `@agent-native/toolkit/app/shared` 的 `<WriteFailureToaster />`。否则不会显示任何 toast。

`useDbSync()` 始终处理本地聊天运行中的工具完成事件，并在运行结束时刷新。这样，单用户代理编辑无需后台请求也能保持最新。来自其他标签页、用户、webhook 或任务的变化默认不进行后台同步，除非此页面提供简短原因并显式启用。每个标签页共享一个连接，隐藏时暂停，空闲轮询间隔依次延长至 1、2、5 分钟。

```ts
import { useDbSync } from "@agent-native/core/client/hooks";
import { useQueryClient } from "@tanstack/react-query";

function App() {
  const queryClient = useQueryClient();

  useDbSync({
    queryClient,
    realtime: { reason: "teammates can edit this shared record" },
    pollUrl: "/_agent-native/poll",
    onEvent: (data) => console.log("Data changed:", data),
  });

  return <div>...</div>;
}
```

只有当数据可能在当前用户未操作时发生变化，且用户需要在刷新前看到变化时才启用实时同步。Slides 协作编辑和 Mail 收件箱是合适例子。公共页面、Docs、设置、表单、变化较少的列表以及单用户代理编辑都应保持关闭；可在页面重新获得焦点或导航时刷新。每个已订阅的打开标签页在每个空闲间隔增加一次轮询。
