# マルチアプリ ワークスペースでのフォームのクロスアプリ利用

フォームは、[Dispatch](/docs/template-dispatch) ワークスペース内にある数多くのアプリの中の 1 つです。このページでは、それが実際に何を意味するのかを具体的に説明します。連携がどのように機能するか、そして他のアプリがフォームを操作したりフォームへデータを送ったりする具体的な方法についてです。概要は [フォーム](/docs/template-forms) を参照してください。

## フォームが Dispatch と連携する仕組み

これが自動的に行われるかどうかは、フォームと Dispatch がどちらもホストされているか、ローカルで動いているかではなく、両者がどのように一緒に設定されたかに依存します。

### 同じワークスペース: 自動

フォームと Dispatch が(`create` または `add-app` を通じて)1 つの Agent-Native ワークスペースに一緒に生成または追加され、1 つの単位としてデプロイされている場合、両者はすでに 1 つの `.env`、1 つの `A2A_SECRET`、1 つのワークスペースレジストリを共有しています。発見と認証済み A2A 呼び出しは、そのワークスペースがあなたのマシンで動いているか本番環境で動いているかにかかわらず、何も設定せずにそのまま機能します。これは、フォームを土台にした実際のマルチアプリ プロダクトで想定されるセットアップです。

### 別々のデプロイ: 手動の手順が 1 つ

フォームと Dispatch が独立して作成された 2 つの Agent-Native プロジェクトである場合、両者はシークレットを共有しておらず、まだお互いを呼び出せません。接続するには、それぞれの側で手動の手順が 1 つ必要です。設定 → 接続されたエージェント、Agent ページの接続タブ、または Dispatch → エージェント → 外部エージェントを追加のいずれかから、共有シークレットを持つ `remote-agents/<id>.json` リソースを追加します。全体の手順については [A2A プロトコル](/docs/a2a-protocol) を参照してください。

どちらの状況にあるかを確認するには、いずれかのアプリのエージェントに「どのアプリが見える?」と尋ねてください。Dispatch の回答にフォームが含まれていなければ、2 番目のケースに当たります。

## 連携戦略

**Dispatch を介した自然言語での委任。** 姉妹アプリがフォームと連携するために特別な統合は必要ありません。チャットで頼むのと同じように、「ベータ登録フォームの回答は何件ありますか」のような平易な言葉のリクエストをフォームのエージェントに渡すことができ、フォームはそれに直接答えたり、実行したりします。これが、Slack や Mail に届いた質問が実際にフォームからの本物の回答に変わる、といったことの実際の仕組みです。Dispatch(またはメッセージを受け取ったアプリ)がそのリクエストをフォームのエージェントに委任し、フォームは他のどんなプロンプトとも同じようにそれを処理します。

**他のアプリがフォームへ直接送信する。** フォームが別のアプリからデータを受け取るために、A2A や Dispatch はまったく必要ありません。どのアプリでも、匿名の回答者が公開ページに入力するのと同じ方法で、フォームの公開の送信アドレスへ普通のウェブリクエストを送ることができます。フレームワーク自体のフィードバックボタンもまさにこの方法で動作しています。デプロイされたフォームアプリへ、どのページとどのアプリから届いたフィードバックかという情報とともに送信を送り、フォームはそれを通常の回答として記録します。つまり、ワークスペース内のどのアプリも、A2A 接続なしに、ただの普通のウェブリクエストだけで構造化されたデータをフォームへ送信できます。

**分離されたままでいる。** フォームが委任された質問に答えているときも、直接の送信を受け取っているときも、フォームは呼び出し元アプリの認証情報を知る必要はありませんし、呼び出し元アプリもフォームがどのようにデータを保存しているかを知る必要はありません。委任は他のどのプロンプトとも同じようにエージェントを経由し、直接の送信は人間の回答者が使うのと同じ公開アドレスを経由します。
