# Docker

Docker は、Agent-Native アプリとその実行に必要なものすべてを、単一のコンテナ イメージにパッケージ化します。このイメージは [Node.js ガイド](/docs/node-js)で説明しているものと同じ Node.js サーバーを実行するため、ノート PC、仮想マシン、コンテナを実行できる任意のホストのどこでも同じように動作します。

このガイドでは、スタンドアロン アプリを 1 つ、ゼロからデプロイする手順を説明します。アプリを作成し、`Dockerfile` を追加し、本番用のデータベースと認証シークレットを用意し、データベースを準備してから、コンテナをビルドして実行します。

<Callout tone="info">

Node.js `22.22+` が必要です。

</Callout>

イメージをビルドして実行するマシンには、Docker もインストールされている必要があります。このガイドのコマンドは、コンテナを実行するサーバー上で実行してください。仮想マシンの場合、通常はまず SSH で接続します。

<a id="self-host-quickstart"></a>

## ステップ 1: アプリを作成する {#step-1-create-the-app}

新しいスタンドアロン アプリを作成します。以下の例では Chat テンプレートからアプリを作成していますが、どのテンプレートから始めてもかまいません。アプリのフォルダーに移動し、依存関係をインストールします。`corepack enable` はアプリが想定する `pnpm` のバージョンを有効にするため、`pnpm` を自分でインストールする必要はありません。

```bash
npx --yes @agent-native/core@latest create my-app --standalone --template chat

cd my-app

corepack enable

pnpm install
```

必要に応じて、`my-app` を自分のアプリ名に置き換えてください。このガイドの以降の手順は、アプリのフォルダー内にいることを前提としています。

<Callout tone="info">

これらのコマンドがピア依存関係のエラーで失敗する場合は、npx キャッシュ内の古いパッケージが原因の可能性があります。`npx clear-npx-cache` を実行してキャッシュを消去してから、もう一度コマンドを実行してください。

</Callout>

## ステップ 2: Dockerfile を作成する {#step-2-create-dockerfile}

新しいアプリには `Dockerfile` が含まれていないため、自分で追加します。あわせて、ローカルのファイルをイメージに含めないための `.dockerignore` ファイルも追加します。どちらのファイルも、アプリのルート フォルダーの `package.json` と同じ場所に作成してください。

### Dockerfile {#dockerfile}

拡張子なしの `Dockerfile` という名前のファイルを作成し、以下の内容をコピーします。

```dockerfile filename="Dockerfile"
FROM node:24-slim AS build
WORKDIR /app

RUN apt-get update \
  && apt-get install -y --no-install-recommends python3 make g++ \
  && rm -rf /var/lib/apt/lists/*

ENV PYTHON=/usr/bin/python3

COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile

COPY . .
RUN pnpm build

FROM node:24-slim
WORKDIR /app

ENV NODE_ENV=production
ENV PORT=3000

COPY --from=build /app/.output .output

EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

この `Dockerfile` は、イメージを 2 つのステージでビルドします。

- **ビルド ステージ。** 一部の依存関係がインストール時のコンパイルに必要とするツール (`python3`、`make`、`g++`) をインストールし、アプリの依存関係をインストールして、アプリをビルドします。
- **最終ステージ。** クリーンな Node.js イメージから開始し、`.output` フォルダーにある完成したサーバーだけをコピーします。これによりイメージが小さく保たれ、ビルド ツールやソース コードは含まれません。

最終イメージは本番モードで実行され、ポート `3000` で待ち受けます。

### Docker の除外ファイル {#docker-ignore-file}

`.dockerignore` という名前のファイルを作成し、以下の内容をコピーします。

```text filename=".dockerignore"
node_modules
.output
.git
.env
.env.*
data
*.log
```

これらのエントリにより、ローカルの依存関係、古いビルド出力、Git の履歴、`.env` ファイル内のローカルのシークレット、`data` 内のローカル開発用データベース、ログ ファイルがイメージに含まれなくなります。ビルド ステージでは依存関係を新たにインストールし、アプリをゼロからビルドするため、これらはどれも必要ありません。`.env` ファイルを除外することで、シークレットがイメージに焼き込まれることも防げます。

## ステップ 3: 環境シークレットを設定する {#step-3-configure-environment-secrets}

アプリは本番用の設定を環境変数から読み取ります。

| 変数                 | 必須   | 用途                                                 |
| -------------------- | ------ | ---------------------------------------------------- |
| `DATABASE_URL`       | はい   | アプリを PostgreSQL データベースに接続する           |
| `BETTER_AUTH_SECRET` | はい   | ユーザー セッションに署名する                        |
| `BETTER_AUTH_URL`    | いいえ | ユーザーがアプリにアクセスする公開アドレスを設定する |

以下の export により、このシェルで後続のコマンドが動作するようになります。デプロイする前に、同じ変数をホストのプロジェクトまたはサービスの環境設定にも保存してください。そうすれば、再起動や新しいデプロイの後もコンテナがそれらの値を保持できます。

### データベース URL {#database-url}

ローカル開発中、`DATABASE_URL` が設定されていない場合、アプリはデータをローカル データベースに保存します。デプロイしたアプリには、再起動後もデータを保持する本物の PostgreSQL データベースが必要です。コンテナは置き換えられると、書き込んだファイルをすべて失うため、データベースはコンテナの外に置く必要があります。プロバイダーから接続文字列をコピーし、export します。

```bash
export DATABASE_URL='your-postgres-url-string'
```

各プロバイダーで接続文字列を確認する場所は、[データベース プロバイダー ガイド](/docs/neon)で説明しています。

<Callout tone="warning">

Neon、Supabase、Amazon RDS などの永続的な PostgreSQL プロバイダーを選択してください。

</Callout>

### 認証シークレット {#auth-secret}

この値は一度だけ生成し、デプロイ間で変更しないでください。

アプリは `BETTER_AUTH_SECRET` を使ってユーザー セッションに署名します。この値が変わると、サインイン中のすべてのユーザーがサインアウトされます。以下のコマンドでランダムな値を生成します。

```bash
export BETTER_AUTH_SECRET="$(openssl rand -hex 32)"
```

生成した値は、ホストのシークレット設定やパスワード マネージャーなど、安全な場所に保存してください。デプロイのたびに同じ値を使用します。

### 公開 URL {#public-url}

省略可能です。カスタム ドメイン、リバース プロキシ、または固定の公開オリジンを必要とする認証や OAuth のフローを使う場合に設定します。

`BETTER_AUTH_URL` は、ユーザーがアプリにアクセスする公開アドレスです。設定しない場合、アプリは受信したリクエストごとに自身のアドレスを判断します。通常はそれで問題ありませんが、アプリがプロキシやカスタム ドメインの背後にある場合、サインイン リンクや OAuth のリダイレクトが誤った場所を指すことがあります。

```bash
export BETTER_AUTH_URL='https://your-domain.example'
```

## ステップ 4: マイグレーション {#step-4-migrate}

マイグレーションは、アプリに必要なテーブルをデータベースに作成し、更新します。

最初のアクセスの前に、ホスト上で本番用の `DATABASE_URL` に対してこれを実行してください。

```bash
pnpm migrate:production
```

このコマンドは、コンテナ内ではなくアプリのフォルダーから実行してください。イメージには完成したサーバーしか含まれていないため、イメージ自体ではマイグレーションを実行できません。このコマンドは、前のステップで export した環境から `DATABASE_URL` を読み取ります。アプリをアップグレードした後は、新しいバージョンを起動する前にもう一度実行してください。

## ステップ 5: デプロイ {#step-5-deploy}

アプリのフォルダーからイメージをビルドします。

```bash
docker build -t my-agent-native-app .
```

`-t` フラグは、イメージに `my-agent-native-app` という名前を付けます。名前は自由に決めてかまいませんが、次のコマンドでも同じ名前を使ってください。

コンテナを実行します。

```bash
docker run --rm \
  -p 3000:3000 \
  -e DATABASE_URL \
  -e BETTER_AUTH_SECRET \
  my-agent-native-app
```

`-p 3000:3000` は、コンテナのポート `3000` にサーバーのポート `3000` からアクセスできるようにします。各 `-e` フラグは、シェルにある同じ名前の変数をコンテナに渡します。`BETTER_AUTH_URL` を設定した場合は、コマンドに `-e BETTER_AUTH_URL` も追加してください。`--rm` は、コンテナが停止したときにコンテナを削除します。

インターネットからアプリにアクセスできるようにするには、サーバーのファイアウォールでポート `3000` を開放するか、Nginx や Caddy などのリバース プロキシを前段に置いて、自分のドメインを HTTPS で提供します。その後、アプリの公開アドレスを開き、最初のアカウントを作成します。

## コンテナを動かし続ける {#keep-the-container-running}

上記の `docker run` コマンドはターミナル上で実行され、ターミナルを閉じると停止します。アプリを動かし続けるには、再起動ポリシーを指定してコンテナをバックグラウンドで起動します。そうすれば、クラッシュやサーバーの再起動の後に Docker がコンテナを再び起動します。そのためには、`--rm` を `-d --restart unless-stopped` に置き換えてください。コンテナを実行する多くのホストは、再起動も自動で処理します。
