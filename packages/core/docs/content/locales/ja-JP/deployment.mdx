# デプロイ

agent-native アプリは内部で [Nitro](https://nitro.build) を使用しています。つまり、設定変更なしで任意のプラットフォームにデプロイできます。プリセットを設定するだけです。

## デプロイ前に: 永続的なデータベースを選ぶ {#persistent-database}

**永続的な** データベースとは、再起動、再デプロイ、そして複数のサーバーインスタンスでの同時稼働を経てもデータが失われないデータベースのことです。デプロイされるすべてのアプリに必要なものです。

<Comparison>

### 変更前

ローカル開発では `data/app.db` の SQLite ファイルにフォールバックします。これは手元のマシンでは便利ですが、そのファイルはローカルのファイルシステム上にあり、コンテナ、プレビュー、サーバーレスプラットフォームはこれをいつでもリセットしうる場所です。

### 変更後

本番環境には、再起動、再デプロイ、複数インスタンスでの同時稼働を経てもデータが失われない、Postgres や Turso/libSQL のような永続的なデータベースが必要です。

</Comparison>

接続には 3 つのステップがあります。

<Steps>

### プロバイダーを選ぶ

Postgres 互換の任意のホスト（Neon、Supabase、Railway、RDS など）や、libSQL/Turso データベースが使えます。Agent-native は、スキーマを手書きの SQL の代わりに型安全なクエリへと変換する TypeScript ライブラリである [Drizzle](https://orm.drizzle.team) を介して読み書きするため、同じアプリコードがそのどれに対しても動作します。

### 接続文字列を取得する

プロバイダーは、データベースとその接続方法を示す URL を提供します。例えば `postgres://user:pass@host:5432/dbname` のような形式です。

### `DATABASE_URL` を設定する

初回の本番デプロイの前に、デプロイプロバイダーの環境変数でこれを設定してください。Agent-native はその URL を読み取り、どの**方言**（どの基盤データベースエンジン、Postgres なのか SQLite/libSQL なのか）で通信するかを自動的に検出します。アダプターの完全な一覧は [データベース](/docs/server-database#production) を参照してください。

</Steps>

<Callout tone="info">

Turso や、別トークンで認証する他の libSQL プロバイダーを使っていますか？ `DATABASE_URL` と併せて `DATABASE_AUTH_TOKEN` を設定してください。複数のアプリを持つ [ワークスペース](/docs/multi-app-workspace) を構築していますか？ すべてのアプリはデフォルトでルートの `DATABASE_URL` を継承します。異なるデータベースが必要な、そのアプリだけに `<APP_NAME>_DATABASE_URL` を設定してください。

</Callout>

### 自動スキーマセットアップ {#skip-ensure-tables}

開始するのに、別途マイグレーションのステップは必要ありません。アプリのどこかがデータベースに初めて触れる際、agent-native は必要なテーブル、カラム、インデックスがすでに存在するかを確認し、欠けているものを作成します。これはサーバーの起動ごとに 1 回だけ発生し、通常の使用では目に見えません。

具体的には、各データストアは、最初に使用される際に内部の `ensureTable()` 関数を呼び出します。この関数はデータベース自身のカタログ（例えば Postgres の `information_schema`）を確認し、本当に欠けているものに対してのみ `CREATE TABLE`、`ADD COLUMN`、`CREATE INDEX` を発行します。これらは **DDL** 文、すなわち Data Definition Language の略で、行の読み書きではなくテーブルの形を定める SQL の部分です。

### サーバーレスでのコールドスタート遅延を減らす {#reducing-cold-start}

長時間稼働するサーバーでは、この確認は起動ごとに 1 回だけ実行され、まず気づくことはないでしょう。サーバーレスプラットフォームは事情が異なります。**コールドスタート** とは、リクエストを処理するためにプラットフォームがサーバーの真新しいインスタンスを立ち上げることです。サーバーレスでは、「最初のアクセス」が約 57 個の異なるストアにまたがるすべてのコールドスタートを意味しかねません。これは、リクエストが実際の処理を始める前に、数百回のラウンドトリップが積み重なることになります。

これを抑える仕組みが 3 つあります。

- **バッチ化されたイントロスペクション。** テーブル、カラム、インデックスごとに 1 クエリを発行する代わりに、上記の確認はデータベースごとに 1 回のイントロスペクションパス、合計わずか 2 クエリとして実行されます。これは自動で行われ、設定は不要です。
- **マネージドサーバーレスでの自動スキップ。** Netlify Functions、AWS Lambda、Vercel Functions は、いずれも本番環境でこの確認を完全にスキップします。セットアップは不要です。
- **`AGENT_NATIVE_SKIP_ENSURE_TABLES=1`。** スキーマがすでにマイグレーション済みで、アプリケーションの起動時にテーブルの作成や変更を行いたくない場合、長時間稼働する Node サーバーや Docker、その他のセルフホスト構成など、自動スキップの対象外となるデプロイでこれを設定してください。

<Callout tone="risk">

このフラグも、自動的なサーバーレススキップも、フェイルクローズすることはできません。もし本当にテーブルが欠けていた場合、それを必要とする最初の実クエリは、静かに修復されるのではなく、大きく失敗します。これは意図的なものです（静かな修復は本物のマイグレーションのバグを隠してしまいます）が、その代わりマイグレーションの管理はここから先すべてあなたの責任になります。アプリケーションの起動によるテーブル作成に依存しているデプロイでは、このフラグを設定せず、自動スキップにも頼らないでください。

</Callout>

複数のアプリを 1 つのオリジンにデプロイすること、あるいは Docker Compose でワークスペースを
セルフホストすることは、それ自体が独立したページです。[ワークスペースのデプロイ](/docs/workspace-deployment) を参照してください。

## プリセットの設定 {#setting-the-preset}

デフォルトでは、Nitro は Node.js 向けにビルドします。別のプラットフォームを対象にするには、`vite.config.ts` でプリセットを設定します。

```ts
import { agentNative } from "@agent-native/core/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [agentNative({ nitro: { preset: "vercel" } })],
});
```

あるいは、ビルド時に `NITRO_PRESET` 環境変数を使用します。

```bash
NITRO_PRESET=netlify npx @agent-native/core@latest build
```

ビルドとデプロイの詳細は、お使いのプラットフォームのページを参照してください。

- [**Node.js & Docker**](/docs/node-docker) — デフォルトのプリセットと、スタンドアロンの Dockerfile
- [**Vercel**](/docs/vercel)
- [**Netlify**](/docs/netlify) — スケールツーゼロデータベース向けの keep-warm を含む
- [**Cloudflare**](/docs/cloudflare) — Pages と Workers
- [**その他のプラットフォーム**](/docs/other-platforms) — AWS Lambda と Deno Deploy

デフォルトの SSR シェルキャッシュポリシーと、`AGENT_NATIVE_SSR_CACHE` によるその上書き方法は、それ自体が独立したページです。[SSR キャッシュ](/docs/ssr-caching) を参照してください。

本番環境変数の完全なリファレンス（ビルド/ランタイム、必須のシークレット、認証、Webhook、セキュリティのオプトイン、ワークスペースの `.env` 継承、強力なシークレットの生成）は、それ自体が独立したページです。[デプロイ: 環境変数](/docs/deployment-environment-variables) を参照してください。

デプロイされた本番エージェントが `frameworkTools` と `codeExecution` を通じてどのフレームワークツールとコード実行機能を持つかは、それ自体が独立したページです。[本番エージェントアクセス](/docs/actions-agent-tools) を参照してください。

デプロイされたアプリの UI がリリース後にどのように更新されるか、本番環境でのビジュアル編集のための Builder.io の別個のマネージドワークフローも含めて、それ自体が独立したページです。[本番環境での UI 更新](/docs/updating-ui-in-production) を参照してください。

## マルチインスタンスデプロイ {#multi-instance}

agent-native アプリは、すべての状態を Drizzle 経由で SQL に保存し、データベースに対する [ポーリング](/docs/key-concepts#polling-sync) を介して UI を同期します。ファイルシステムの状態も、スティッキーセッションも、インメモリキャッシュもありません。つまり、マルチインスタンスとサーバーレスのデプロイはそのまま動作します。すべてのインスタンスを同じ `DATABASE_URL` に向ければ、自動的に収束します。[主要な概念: SQL 内のデータ](/docs/key-concepts#data-in-sql) と [移植性](/docs/key-concepts#hosting-agnostic) を参照してください。
