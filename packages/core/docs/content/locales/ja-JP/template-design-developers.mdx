# 開発者ガイド

このページは、Design テンプレートをカスタマイズしたり、その上に直接構築
したりする人のためのものです。クイックスタート、すべての action、データ
モデル、1 つの action の詳しい解説、ルートのサーフェス、そして追加の仕方を
扱います。アプリが何をするかについては [Design](/docs/template-design) を
参照してください。

## クイックスタート

<Steps>

### アプリを作成する

```bash
npx @agent-native/core@latest create my-design --standalone --template design
cd my-design
pnpm install
```

これには [Node.js](https://nodejs.org) 22.22 以降と [pnpm](https://pnpm.io)
が事前にインストールされている必要があります。どちらもまだインストールして
いない場合や、LLM 接続 (Builder.io、Anthropic/OpenAI のキー、またはローカルの
Ollama) を設定していない場合は、[はじめに](/docs/getting-started) を参照して
ください。Design を他のアプリと一緒に使うワークスペースにする場合は、代わりに
`npx @agent-native/core@latest create my-platform` を実行し、セットアップ中に
Design を選んでください。

### 開発サーバーを起動する

```bash
pnpm dev
```

アプリは `http://localhost:8099`、Design の既定の開発用ポートで開きます。
Design は外部接続なしでも完全に動作します。接続プロンプトに出会うのは、
それらを設定する前に Figma のインポートや Full App Building を試したときだけ
です。

</Steps>

## Action 一覧

デザイン固有の操作はすべて `templates/design/actions/` にある TypeScript
ファイルで、`POST /_agent-native/actions/:name` に自動的にマウントされ、CLI
から `pnpm action <name>` として実行できます。

### デザイン

| Action                    | 何をするか                                                                    |
| ------------------------- | ----------------------------------------------------------------------------- |
| `create-design`           | 空のデザイン シェルを作成する                                                 |
| `generate-design`         | 生成された HTML/JSX ファイルの内容を書き込む                                  |
| `edit-design`             | 既存のファイルに対して、的を絞った検索/置換の編集を行う                       |
| `update-design`           | デザインのメタデータ (タイトルやリンクされたデザイン システムなど) を更新する |
| `get-design`              | id で 1 件のデザインを読み取る                                                |
| `list-designs`            | アクセス可能なデザインを一覧表示する                                          |
| `duplicate-design`        | デザインとそのファイルをコピーする                                            |
| `delete-design`           | デザインを削除する                                                            |
| `apply-tweaks`            | ライブの調整ノブの値を永続化する                                              |
| `present-design-variants` | いくつかの方向性を画面として保存し、横並びのピッカーを表示する                |
| `show-design-questions`   | あいまいなプロンプトに対して、確認の質問オーバーレイを表示する                |
| `generate-screens`        | 複数の画面を一括で生成する                                                    |

| `delete-review-comment`       | コメントを削除する                                         |
| `set-review-status`           | デザイン全体のレビュー ステータスを設定する                |

## データモデル

すべてのデータは Drizzle ORM を介して SQL に存在します。スキーマ:
`templates/design/server/db/schema.ts`。デザインとデザイン システムは、標準の
`ownableColumns` と対応するフレームワーク共有テーブルを備えているため、
ユーザーごと/組織ごとの共有モデルに組み込まれます。

以下の表は、デザイン、ファイル、テンプレート、バージョン、デザイン システム
という中核の所有可能リソースを扱います。

| テーブル                                 | 内容                                                                                                                                             |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `designs`                                | デザイン プロジェクト — `title`、`description`、`project_type` (`prototype` / `other`)、`data` JSON blob、そして任意の `design_system_id` リンク |
| `design_files`                           | デザインに属する個々のファイル (`filename`、`content`、既定で `html` になる `file_type`)                                                         |
| `design_templates`                       | 再利用可能なテンプレートのメタデータ、寸法、既定値、元になったデザインへの参照、ロックされたレイヤー数                                           |
| `design_template_files`                  | ユーザーがテンプレートから開始したときに、通常の編集可能なデザインへコピーされる、スナップショットされたテンプレート ファイル                    |
| `design_template_shares`                 | 非公開、組織、明示的な共有、公開のテンプレート発見のためのフレームワーク共有テーブル                                                             |
| `design_versions`                        | 履歴とロールバックのための、任意の `label` を伴うデザインのポイントインタイム `snapshot`                                                         |
| `design_systems`                         | 再利用可能なブランド トークン — `data` (色/タイポグラフィ/間隔)、`assets`、`custom_instructions`、そして `is_default` フラグ                     |
| `design_shares` / `design_system_shares` | プリンシパル (ユーザーまたは組織) をロール (閲覧者、編集者、管理者) にマッピングするフレームワーク共有テーブル                                   |

デザイン プロジェクトは、コンテンツを持つまではシェルです。`create-design`
は空の行 (`data: "{}"`) を作り、その後 `generate-design` が実際のスタンドアロン
HTML/JSX ファイルを書き込みます。生成された成果物、編集可能なソース、そして
すべてのエクスポートは同じ HTML から来ているので、翻訳すべき独立した「AI
モックアップ」形式は存在しません。リンクされたデザイン システムは、エージェント
がすべての生成パスで尊重するトークンと `custom_instructions` を提供します。

他に 7 つのテーブルが、中核のリソース モデルではなく、このページの他の場所で
扱っている機能を支えています。`design_localhost_connections` と
`design_localhost_write_grants` は [ローカル アプリのインポート](/docs/template-design-features#import)
を支え、`component_index` は [Design タブのコンポーネント セクション](/docs/template-design-features#design-tab)
を支え、`motion_timeline` は各要素の編集可能なモーション タイムライン
(エディター内の Motion ドック) を支え、`design_state` はデザインの名前付き
代替状態、静的フィクスチャ、ライブアプリのキャプチャを保持し、
`design_fusion_edits` は上記の [Full App Building](#full-app-building) で
説明した fusion 編集キューを支え、`design_review_snapshot` は上記の
[品質](#quality) で説明した `get-design-review` の裏にあるアクセシビリティの
検出結果とビジュアル差分をキャッシュします。

永続化されたレビュー コメントとスレッド (`get-review-feedback`、
`resolve-review-thread`、その他) は、Design 専用のテーブルではまったく
ありません。どのアプリでも取り付けられるのと同じ方法でデザインにスコープ
された、`@agent-native/core/review` の共有フレームワーク レビュー システム
(`agent_review_comments` / `agent_review_statuses`) です。ユーザー向けの動作
については [コメント タブ](/docs/template-design-features#comments-tab) を
参照してください。

## 1 つの action を詳しく見る

`save-design-as-template` は、どの action でも再利用する価値のあるパターンを
示しています。何か作業をする前にサポートされていない入力形式を拒否すること、
何も保存しない事態を防ぐこと、id を各読み取り側でではなく一度だけ再マッピング
すること、そして 1 つのトランザクションで 2 つのテーブルに書き込むことで、
テンプレートがメタデータだけでファイルがない状態に絶対にならないようにする
ことです。

## エディター モデル

Design は、複数画面の作業では概要表示を最初に使います。生成や大きな更新の
後、エディターは画面概要を開きます。これは無限キャンバスで、各画面は選択、
移動、リサイズ、ドロップ、複製できる静的なフレームです。1 つの画面に集中した
スクロールやプロトタイプの操作が必要なときは、フレームのフルビュー ボタンを
使います。

単一画面モードは、スクロール、プロトタイプの動作とのインタラクション、そして
1 つのレンダリング済みファイル内の DOM/コード レイヤーの編集のためのもの
です。レイヤー パネルもこの分割を反映しており、画面が最上位のフレームで、
アクティブな画面の DOM/コード レイヤーがその下にネストされます。

すべての画面は、ブレークポイントごとの別々のコピーではなく、異なる幅で
レンダリングされる 1 つのドキュメントです。ベース (最も幅広い) フレームが
下にカスケードし、より狭いアクティブなブレークポイントで行った編集は、その
上に幅スコープのオーバーライドとして保持されます。

## エディター拡張機能

エディターには **調整** の後に **拡張機能** インスペクター タブがあります。
これは Design 専用のプラグイン レーンのように動作します。ユーザーは
**+ 拡張機能** をクリックしてエージェントに拡張機能の作成を依頼するか、
Design 専用の action ではなく、フレームワークの `create-extension`、
`add-extension-slot-target`、`install-extension` の各 action を使って
`design.editor.inspector` スロットを宣言する拡張機能をインストールできます。

Design の拡張機能は、標準の拡張機能サンドボックスを通じて、アートボードの
横にインラインで表示されます。ホストは `window.slotContext` と
`window.onSlotContext(...)` の更新として、現在の `designId`、アクティブな
ファイル、画面一覧、選択中の画面 id、選択中の要素のメタデータ、表示モード、
ズーム、アクティブなツール、調整の値を渡します。これにより、拡張機能は
現在の選択に関する情報を表示したり、スタイルのコントロールを提供したり、
開いているデザインの周辺にコンパクトなワークフローを構築したりできます。

決定的な処理では、拡張機能は拡張機能ブリッジを通じてアプリの actions を
呼び出せます。AI 主導の変更では、選択中の要素のセレクター/ソース id と
要求された変更を添えて、拡張機能に `agentNative.chat.send(...)` を呼び出させて
ください。エージェントはまず `view-screen` を呼び出し、要素のスタイル、
クラス、テキスト、移動の変更には `apply-visual-edit` を、アートボードの配置
変更には `canvasFrames` を伴う `update-design` / `generate-design` を使うべき
です。サンドボックス、永続状態、ブリッジ API については
[拡張機能](/docs/extensions#capabilities) を参照してください。

## カスタマイズする

Design は完全な、複製可能なテンプレートです。実践的な拡張のアイデアを
いくつか挙げます。

- 「自分たちのトークンとサンプル コンポーネントを使った、再利用可能な e コマース デザイン システムを追加して。」
- 「ZIP を社内のレビュー システムにアップロードするエクスポート手順を追加して。」
- 「既存のランディング ページの HTML を貼り付けて、より強力な 3 つのバージョンをエージェントに頼めるようにして。」
- 「製品ページ、ダッシュボード、オンボーディング画面のブリーフ用に、保存されたプロンプト ライブラリを追加して。」
- 「関係者レビュー用のカスタム PDF エクスポート プリセットを追加して。」

エージェントは必要に応じてルート、コンポーネント、actions、SQL に基づく
モデルを編集します。クローン、カスタマイズ、デプロイの全体的な流れについては
[テンプレート](/docs/cloneable-saas) を、これがはじめてのエージェントネイティブ
テンプレートであれば [はじめに](/docs/getting-started) を参照してください。
