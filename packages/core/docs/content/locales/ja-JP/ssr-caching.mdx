# SSR キャッシュ

すべての SSR HTML レスポンスと、すべての React Router `.data` レスポンスは、個人を特定しない 1 つの公開シェルです。`createH3SSRHandler` はレンダリング前に Cookie を取り除くため、同じバイト列がすべての訪問者にとって正しく、パーソナライズはすべてロード後にクライアント側で行われます。だからこそ、これらのレスポンスにデフォルトで単一のハードキャッシュポリシーを刻印しても安全なのです。

```txt
cache-control: public, max-age=600, stale-while-revalidate=604800, stale-if-error=3600
```

同じ値が `cdn-cache-control` にもミラーされます。`netlify-cdn-cache-control` は代わりにそれ自体のより長期なデフォルト値、`public, durable, s-maxage=31536000, stale-while-revalidate=604800, stale-if-error=3600` を持ちます。Netlify の CDN はこのヘッダーを標準のものとは別に読み取るためです。これにより、1 つの共有 CDN エントリがリクエストごとのレンダリングの代わりにサイト全体を配信します。これは初回レスポンスのレイテンシに対する単一最大のレバーです。以下のケースのいずれかがあなたのデプロイに当てはまらない限り、有効なままにしてください。

## `AGENT_NATIVE_SSR_CACHE` による上書き {#ssr-cache-env}

デプロイ環境全体のポリシーを変更するには、デプロイ環境で `AGENT_NATIVE_SSR_CACHE` を設定します。

| 値                                                    | 結果                                                                                     |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 未設定、`on`、`default`、`true`、`1`                  | 上記のデフォルトポリシーのまま変更なし。最高のパフォーマンスのために推奨されます。         |
| `off`、`false`、`0`、`none`、`no-store`、`disabled`   | `cache-control`、`cdn-cache-control`、`netlify-cdn-cache-control` に `no-store` を設定。   |
| 期間: `30`、`30s`、`5m`、`2h`                          | `cache-control` と `cdn-cache-control` に `public, max-age=<n>, stale-while-revalidate=<n>, stale-if-error=3600` を設定。`netlify-cdn-cache-control` は同じ期間で `public, durable, s-maxage=<n>, stale-while-revalidate=<n>, stale-if-error=3600` を使用。 |

裸の数値は秒として扱われます。カスタム期間の場合、`stale-while-revalidate` は意図的に `max-age` を反映します。短い鮮度ウィンドウに、デフォルトの 7 日間の stale ウィンドウを組み合わせてしまうと、まさにオプトアウトしたはずの古さがそのまま返ってきてしまうからです。認識できない値は警告をログに出してデフォルトにフォールバックするため、タイプミスが CDN を黙って無効化することはありません。

次のいずれかが当てはまる場合は、下げるか無効にしてください。

1. **ホストがデプロイ時に CDN をパージしない。** Netlify と Vercel はパージします。一部のセルフマネージド構成はパージしません。パージがないと、リリース済みのビルドが `max-age` に `stale-while-revalidate` を加えた期間、以前のシェルを配信し続けることがあります。
2. **ローダーが変化しうる公開データを返す。** ミューテーションが成功した後、`useRevalidator()` やアクション後のリダイレクトによる再フェッチが、最新のローダー出力ではなくブラウザにキャッシュされた `.data` のコピーを読んでしまうことがあります。

この設定は、React Router の SSR HTML と `.data`、ログイン HTML シェル、`/_agent-native/speculation-rules.json` ルート、ドキュメントサイト、forms テンプレートの公開フォーム SSR など、すべての公開シェルのサーフェスに適用されます。生成された Cloudflare Worker はこれをビルド時に解決するため、ビルドを実行する前にデプロイ環境で設定してください。

留意すべき点が 3 つあります。

- **キャッシュを無効にしても SSR がパーソナライズされるわけではありません。** Cookie は依然としてレンダリング前に取り除かれ、SSR ローダーは引き続き匿名ブランチを見ます。ユーザーごとのデータは、これまで通りクライアント側で解決する必要があります。この変数が制御するのはキャッシュの _期間_ だけです。
- **これは設計上、ルートごとではなくデプロイ全体に適用されます。** ルートごとやリクエストごとのキャッシュ上書きは、ある訪問者のペイロードが別の訪問者と共有される CDN エントリに紛れ込む原因になるため、フレームワークはそれを提供しません。`guard:ssr-cache-shell` がこれを強制します。
- **ミューテーション後の新鮮なデータには、キャッシュを無効にするよりアクションを優先してください。** アプリのデータは [アクション](/docs/actions-overview) に属し、クライアントからは `useActionQuery` / `useActionMutation` で読み取り、`useDbSync()` のポーリングでライブに保たれます。これらはいずれも SSR シェルキャッシュを経由しません。SSR ローダーは公開シェルのレンダリングに専念させ、この変数は本当にローダーのデータをより新しくしたい場合にのみ使ってください。
