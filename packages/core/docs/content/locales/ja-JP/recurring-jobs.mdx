# 定期的なジョブ

**定期的なジョブ** は、cron スケジュールで実行されるプロンプトです。これは、エージェントが独自に物事を行う方法です。「毎朝 7 時に夜間のメールを要約する」「毎週月曜日に先週の登録番号を Slack に投稿する」「1 時間ごとに古い下書きを徹底的に調べて削除する」

<Callout tone="info">

**Recurring Jobs** は **Scheduled** 自動化の旧称です。**Automations** は **Scheduled** と **Event** の包括的な名称です。`jobs/` と `manage-jobs` は既存のスケジュール専用連携向けに残ります。モデルと MCP 許可リストを含む新しい個人または組織の作業には、`manage-automations` と **Settings › Automations** を使用してください。

</Callout>

定期的なジョブは時計に合わせて起動されます。 _events_ (予約の作成、電子メールの受信) に反応するには、同じ `jobs/` ファイル形式と条件を使用します。[Automations](/docs/automations) を参照してください。

ジョブは `jobs/<name>.md` の [エージェント リソース](/docs/agent-resources) に存在します。これは、YAML フロントマターを持つ Markdown ファイルだけです。登録も配線も必要ありません。ファイルをドロップすると、フレームワークがそれを取得します。

## フロントマター {#frontmatter}

| フィールド   | タイプ                        | デフォルト   | 説明                                                                                                                    |
| ------------ | ----------------------------- | ------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `schedule`   | cron 式                       | _(必須)_     | 標準の 5 フィールド cron。 `"0 7 * * *"` = 毎日 07:00; `"0 */4 * * *"` = 4 時間ごと。                                   |
| `enabled`    | ブール値                      | `true`       | `false` に切り替えて、ジョブを削除せずに一時停止します。                                                                |
| `runAs`      | `"creator"` \| `"shared"`     | `"creator"`  | `"creator"` は、ジョブ所有者の ID と `ANTHROPIC_API_KEY` を使用して実行されます。 `"shared"` は組織のキーを使用します。 |
| `createdBy`  | メール                        | _(自動)_     | ジョブがエージェント リソース UI を通じて、またはエージェントによって作成されたときに設定されます。                     |
| `orgId`      | 文字列                        | _(自動)_     | 組織の範囲。作成者のアクティブな組織から継承されます。                                                                  |
| `lastRun`    | ISO タイムスタンプ            | _(管理対象)_ | 各実行後にスケジューラによって書き込まれます。                                                                          |
| `lastStatus` | `"success"` \| `"error"` \| … | _(管理対象)_ | 最新の結果。                                                                                                            |
| `lastError`  | 文字列                        | _(管理対象)_ | 最後の実行が失敗した場合のエラー メッセージ。                                                                           |
| `nextRun`    | ISO タイムスタンプ            | _(管理対象)_ | `schedule` から計算されます。スケジューラが次にいつ起動するかを決定するために使用されます。                             |
| `mcpTools`   | MCP ツール名の配列            | _(なし)_     | `mcp__server__tool` などの明示的な許可リスト（allowlist）。資格情報は接続済みの MCP grant に残ります。                  |

`last*` フィールドと `nextRun` フィールドは、スケジューラによって書き込まれます。これらを読んで履歴を確認することはできますが、手動で編集しないでください。次回の実行で上書きされます。

## MCP ツールをジョブに接続する {#connected-mcps}

定期ジョブでは、アプリにすでに接続されているリモートまたはローカルの MCP ツールを使用できます。まずエージェントに `tool-search` で正確な名前を調べてもらい、`mcpTools` にはそのジョブで必要なツールだけを指定します。

```md
---
schedule: "0 * * * *"
enabled: true
mcpTools:
  ["mcp__meeting-notes__list_recordings", "mcp__meeting-notes__get_transcript"]
---

前回の成功した実行以降の新しい録画を見つけます。実行可能なフォローアップのみを抽出し、安定したソース ID と外部 ID、短い引用、録画 URL を使って、アプリの境界付きインポート action を一度だけ呼び出します。完全なトランスクリプトはインポートしないでください。
```

ジョブが保存するのはツール名であり、MCP URL、アクセストークン、OAuth リフレッシュトークンではありません。実行時にフレームワークが、ジョブ作成者または組織のリクエストコンテキストで接続済み grant を解決し、許可リストにあるツールだけを公開します。リストは狭く保ち、重複実行で重複が生じないよう、最終インポートには冪等な app action を使用してください。接続と OAuth の設定については、[MCP Clients](/docs/mcp-clients) を参照してください。

## Cron 構文 {#cron}

標準の 5 フィールド cron (分、時、日、月、曜日):

| クロン         | 意味             |
| -------------- | ---------------- |
| `*/5 * * * *`  | 5 分ごと         |
| `0 * * * *`    | 毎正時           |
| `0 */4 * * *`  | 4 時間ごと       |
| `0 7 * * *`    | 毎日 07:00       |
| `0 9 * * 1`    | 毎週月曜日 09:00 |
| `0 17 * * 1-5` | 平日 17:00       |
| `0 0 1 * *`    | 毎月 1 日        |

フレームワークには、リソース層とスケジューラ層によって内部的に使用される cron 文字列を検証およびレンダリングするための cron ユーティリティ (`isValidCron()` および `describeCron()`) が含まれています。

## ジョブの作成 {#creating}

### Automations UI から

**Settings › Automations** を開き、**Scheduled** の自動化を作成します。古い `/agent#jobs` リンクはそこにリダイレクトされます。

### 「エージェント リソース」タブから

`+` → エージェント リソース パネルの **スケジュールされたタスク**。プロンプトとスケジュールを入力します。 `jobs/<slug>.md` として保存し、次の一致するティックで実行を開始します。

### エージェントに問い合わせる

> 「毎朝 7 時に未読メールを要約するスケジュールされたタスクを作成します。」

エージェントがファイルを書き込みます。

### 手動

フレームワークのリソース APIs を介して、Markdown ファイルを `jobs/` にドロップします。

```ts
import { resourcePut } from "@agent-native/core/resources";

await resourcePut(
  ownerEmail,
  "jobs/morning-digest.md",
  `---
schedule: "0 7 * * *"
enabled: true
---
Summarize overnight emails.`,
);
```

## スケジューラの実行方法 {#how-scheduler-runs}

スケジューラ (内部の `processRecurringJobs()` ルーチン) は、ティックごとに実行時刻を迎えたジョブを見つけて実行します。ティックを起動するものは、アプリの実行場所によって異なります。

| ホスト                                                           | ティックを起動するもの                                  | 要件と制限                                                                                                         |
| ---------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 長時間稼働するサーバー (Node.js、Docker、Fly、Render、VPS)       | 起動の 10 秒後から 60 秒ごとに動くプロセス内タイマー    | プロセスが稼働している間は実行されます。                                                                           |
| [Netlify](/docs/netlify)                                         | ビルドが出力するスケジュール function (毎分)            | 公開済みのデプロイのみ。Deploy Previews やブランチデプロイでは実行されません。ビルドには `A2A_SECRET` が必要です。 |
| [Vercel](/docs/vercel#vercel-scheduled-work)                     | ビルドが追加する Vercel cron job (デフォルトでは毎分)   | 本番デプロイのみ。`CRON_SECRET` が必要です。Hobby プロジェクトでは最大で 1 日 1 回しか実行できません。             |
| [Cloudflare Workers](/docs/cloudflare#cloudflare-scheduled-work) | ビルドが `wrangler.json` に追加する Cron Trigger (毎分) | Worker シークレットとして `A2A_SECRET` が必要です。                                                                |
| AWS Lambda                                                       | なし                                                    | スケジュールされた自動化は起動しません。                                                                           |
| ローカル開発                                                     | オプトインしない限りなし                                | 下のコールアウトを参照してください。                                                                               |

Netlify、Vercel、Cloudflare では、同じティックでイベントトリガーの自動化のキューも処理し、function が途中で打ち切られた実行をクリーンアップし、Mail のスヌーズや送信予約などのアプリのスイープも実行します。トリガーのないサーバーレスデプロイでは、これらはいずれも行われません。イベントトリガーの自動化はキューで待ち続け、中断された実行は止まったままになります。Webhook トリガーの自動化と **Run now** は個別にディスパッチされるため、引き続き動作します。デプロイでスケジュールを起動できない場合は、**Automations** ページにその旨と理由が表示されます。

<Callout id="doc-block-j6yn07" tone="risk">

**ウォームなインスタンスはスケジュールを実行しません。** サーバーレスホストはプロセス内タイマーを開始しないため、keep-alive ping を送ってもジョブは起動しません。ジョブを起動するのは上の表にあるプラットフォームのトリガーだけです。AWS Lambda ではまだ何もジョブを起動しないため、スケジュールされた自動化は長時間稼働するホスト (Fly、Render、VPS) で実行してください。

</Callout>

<Callout id="doc-block-rj2" tone="warning">

**ローカル開発ではデフォルトで無効です。** `NODE_ENV` が `development` または `test` の場合、あるいはアプリの URL が `localhost` / `127.0.0.1` / `*.localhost` を指している場合 (ほとんどのローカル開発環境が該当します)、スケジューラの `setInterval` ループは開始されません。それでもローカルでスケジューラを実行するには、`AGENT_NATIVE_ENABLE_LOCAL_RECURRING_JOBS=1` を設定してください。どのホストでもスケジュールされたジョブを無効にするには、次に説明する `AGENT_NATIVE_DISABLE_RECURRING_JOBS=1` を使用します。

</Callout>

<Callout id="doc-block-rj3" tone="warning">

**`AGENT_NATIVE_DISABLE_RECURRING_JOBS` は 2 つのスコープで読み取られます。** Netlify、Vercel、Cloudflare では **ビルド** 環境で決まります。プラットフォームのトリガーはイベント自動化のキュー処理と実行のクリーンアップのために起動し続けますが、スイッチを有効にしたビルドでは、デプロイ先の環境の設定に関係なく、スケジュールされたジョブがスキップされます。長時間稼働するサーバーでは、**ランタイム** 環境がプロセス内タイマーを制御します。ホストが読み取る側の環境に設定してください。ビルドはその判断を記録するため、**Automations** ページでは、実際には守られない次回実行日時を表示する代わりに、スケジュールが実行されないことを示せます。

</Callout>

## ジョブのデバッグ {#debugging}

- **Settings › Automations** でオートメーションの詳細を開くか、エージェント リソースで `jobs/<name>.md` を確認します。フロントマターには `lastRun`、`lastStatus`、`lastError`、`nextRun` が表示されます。
- **待たずにテストしてください:** **Settings › Automations** で **Run now** をクリックするか、エージェントに実行を依頼します (`manage-automations` の `action=run-now`)。ジョブのプロンプトが実際の副作用を伴ってすぐに実行され、`nextRun` は変わりません。例外は、フレームワークが一時停止したジョブです。実行が成功するとジョブが再び有効になり、`nextRun` が再計算されます。Run now はスケジューラのティックを待たないため、`AGENT_NATIVE_ENABLE_LOCAL_RECURRING_JOBS` なしの localhost や、スケジューラのトリガーのないホストでも動作します。
- **一時停止します:** `enabled: false` を反転します。ファイルはそのまま残り、実行が停止するだけです。

## エージェント ツール {#agent-tool}

すべてのテンプレートに 1 つの `manage-jobs` ツールが登録されます。 `action` パラメータは操作を選択します:

| アクション | パラメータ                                                                | 目的                                                                                  |
| ---------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `create`   | `name`、`schedule`、`instructions` (必須); `scope`、`runAs`、`mcpTools`   | 新しい定期的なジョブを作成する                                                        |
| `list`     | `scope` (`personal`、`shared`、またはすべて)                              | すべてのジョブをステータス (スケジュール、有効、最後/次回の実行) とともにリストします |
| `update`   | `name` (必須); `schedule`、`instructions`、`enabled`、`runAs`、`mcpTools` | 既存のジョブを編集する                                                                |
| `delete`   | `name` (必須)                                                             | ジョブを削除します - 最初に常にユーザーに確認してください                             |

**個人スコープと共有スコープ。** 各自動化は個人または組織スコープにあり、作成者として実行されます。管理者は共有定義を管理できますが、作成者のIDは変更できません。組織で実行する前に、フレームワークは作成者が存在し、引き続きメンバーであることを検証します。

## スケジュール パッケージとは異なります {#vs-scheduling-package}

定期的なジョブと `@agent-native/scheduling` を混同しないでください:

- **定期的なジョブ (このページ)** — cron でスケジュールされた _プロンプト_ エージェントがバックグラウンドで実行されます。フレームワークレベル。エージェント リソースに住んでいます。スケジューラのあるすべてのホストで起動します ([スケジューラの実行方法](#how-scheduler-runs) を参照)。
- **`@agent-native/scheduling`** — カレンダー/予約機能 (イベント タイプ、空き状況ウィンドウ、予約) を構築するための再利用可能なドメイン パッケージ。 `calendar` テンプレートとカスタム スケジュール サーフェスを強化します。

定期的なジョブとは、「エージェントを独自に動作させるにはどうすればよいか?」というものです。スケジュール パッケージは、「カレンダー アプリをどうやって構築するか?」です。さまざまな懸念。
