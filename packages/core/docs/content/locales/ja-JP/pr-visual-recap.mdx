# PR Visual Recap

PR Visual Recap は、誰も手動でコマンドを実行しようと覚えておく必要なく、すべてのプルリクエスト
を**ビジュアルコードレビュー**に変える GitHub Action です。このページは、この Action を
インストール、設定、またはセキュリティ面で扱う人向けです。プッシュのたびに、LLM コーディング
エージェントが、同梱された最新の [`visual-recap`](/docs/template-plan) スキル
(`VISUAL_RECAP_SKILL_SOURCE=repo` の場合はリポジトリにコミットされたコピー) を PR の diff に
対して実行し、構造化されたリキャップ Plan をホスト型の Plans アプリに公開し、実行中は情報提供
用の `Visual Recap` チェックを表示し、インタラクティブな Plan へのリンクと、コメント内に直接
埋め込まれた**インラインスクリーンショット**を持つ**固定 PR コメント 1 件**を upsert します。

これは決定論的な diff レンダラーではありません。この Action は、実際のコーディングエージェント
(デフォルトでは Claude Code CLI、ほかに OpenAI Codex CLI、または OpenAI 互換プロバイダーを使う
Agent-Native Code) を呼び出し、変更内容を読み取らせ、何が重要かを判断させ、Plans の MCP ツール
`create-visual-recap` を呼び出してリキャップを作成させます — これは `/visual-recap` スラッシュ
コマンドが使うのと同じツールです。生の diff の壁の代わりに、変更内容を俯瞰したスキーマ/API/
ビフォーアフターのビューが得られます。

リキャップは**情報提供のみで、マージをブロックしません**。生成が進行中であることをレビュアーが
確認できるようチェック行を作成しますが、必須チェックではなく、PR をブロックすることも、実際の
diff を読むことの代わりになることもありません。固定コメントはレビューの助けであり、承認では
ありません。

## これが行うこと

PR がプッシュされるたびに、このワークフローは:

1. PR のベースとヘッドの間で、上限のある diff を収集します。
2. `Visual recap in progress` を伴う、情報提供用の `Visual Recap` GitHub チェックを作成します。
3. その diff に対して、設定済みのコーディングエージェントを実行します。エージェントは、同梱された `visual-recap` スキルのガイダンス (またはリポジトリに固定されたコピー) を読み、リキャップを作成し、`create-visual-recap` で公開します。
4. エージェントが `recap-url.txt` に書き出した、公開済み Plan の URL を読み取ります。
5. ヘッドレス Chrome でその URL を開き、レンダリングされた Plan をライトモードとダークモードでスクリーンショットします。
6. PNG 画像を、Plans アプリの署名付き公開画像ルートにアップロードします。
7. インタラクティブなリキャップへのリンクの隣に、`<picture>` 要素 (GitHub の camo 画像プロキシ経由で配信) でスクリーンショットを**インライン**に埋め込んだ、固定 PR コメント 1 件を upsert します。
8. `Visual Recap` チェックを success、skipped、neutral のいずれかで完了させます。

## インストールする

Plans を対話的にインストールすると、Agent-Native CLI は自動 PR Visual Recap を追加するかどうかを
尋ねます。「はい」と答えると GitHub Action が書き出されます。または、いつでも明示的に追加でき
ます。

```bash
npx @agent-native/core@latest skills add visual-plan --with-github-action
```

これにより `visual-plan` スキル (Action が実行する `visual-recap` スキルを含む) がインストール
され、`.github/workflows/pr-visual-recap.yml` がリポジトリに書き出されます。このワークフローは、
`npx @agent-native/recap-cli@latest recap <subcommand>` を通じて**公開済みの CLI サブコマンド**
— `gate`、`collect-diff`、`block-reference`、`scan`、`build-prompt`、`publish`、`shot`、
`comment`、`check`、`usage` を含む — を呼び出すため、ヘルパースクリプトとしてリポジトリに
コピーされるものは何もありません。`setup` と `doctor` はローカルで実行する対話的なヘルパーで、
`gate` はワークフローが各リキャップの前に実行するセキュリティゲートのステップです。

続いて、案内付きのセットアップヘルパーを実行します。

```bash
npx @agent-native/recap-cli@latest recap setup
npx @agent-native/recap-cli@latest recap doctor
```

`recap setup` はワークフローを更新し、環境変数やローカルの Plans 公開トークンストアから値が
得られる場合は `gh` を使って GitHub Actions のシークレット/変数を設定し、設定できないものに
ついては正確な不足コマンドを表示します。シークレットの値は、コマンド引数ではなく標準入力経由で
`gh` に渡されます。生成されたワークフローファイルをコミットし、PR を開いて実行を確認してくだ
さい。

デフォルトでは、ワークフローは `@agent-native/recap-cli@latest` に同梱された最新の
`visual-recap` ガイダンス (スキルに付属する関連リファレンスファイルを含む) からエージェント
プロンプトを組み立てます。リポジトリが意図的に `visual-recap` フォルダーをカスタマイズして
固定している場合は、リポジトリ変数 `VISUAL_RECAP_SKILL_SOURCE=repo` を設定してください。

## ランナーの選択

このワークフローはデフォルトで、GitHub がホストする `ubuntu-latest` ランナー上で実行されます。
別のホスト型ランナーや、自前のセルフホストランナーを使うには、リポジトリまたは組織の変数
`VISUAL_RECAP_RUNS_ON` に、有効な JSON 文字列またはランナーラベルの JSON 配列を設定します。

```text
"ubuntu-latest"
["self-hosted", "linux", "x64", "visual-recap"]
```

JSON の引用符は必須です。この設定は、完全な `recap` ジョブのランナーを選択します。案内付き
セットアップ中に設定するには、同じ JSON の値を `--runs-on` に渡し、その後 `doctor` でワーク
フローとランナーの可用性を検証してください。

```bash
npx @agent-native/recap-cli@latest recap setup --runs-on '["self-hosted","linux","x64","visual-recap"]'
npx @agent-native/recap-cli@latest recap doctor
```

軽量なセキュリティゲートは、これとは別にデフォルトで GitHub ホストの `ubuntu-latest` を使い
ます。GitHub ホストランナーを無効にしているリポジトリでは、`VISUAL_RECAP_GATE_RUNS_ON` に
(JSON ではなく) **単一のプレーンなランナーラベル**を 1 つ設定するか、セットアップ時に
`--gate-runs-on visual-recap-gate` を渡せます。再利用可能なワークフローも、同じ値を
`gate-runs-on` 入力として公開しています。これにより、GitHub がゲートをスケジュールできる前に
動的な JSON を解析する必要がなくなります。このカスタムラベルが選ばれるのは、`OWNER`、
`MEMBER`、`COLLABORATOR` のいずれかが作成した、同一リポジトリ内の PR に限られます。フォークや
それ以外の作成者は、ジョブが始まる前に強制的に GitHub ホストの `ubuntu-latest` を使わされます。
セルフホストのみのリポジトリでは、そうした信頼されていない実行は、セルフホストマシンに触れる
のではなく、スケジュールされないままになることがあります。

`recap doctor` は不正な形式や非対応の JSON を拒否し、設定されたすべてのラベルに一致する
オンラインのランナーを GitHub が公開していない場合に報告します。ランナーの登録、インストール、
アップグレード、キャパシティ、メンテナンスは引き続きあなたの責任です。Agent-Native はラベルを
選択するだけで、ランナー自体を提供したり運用したりはしません。

**セキュリティ:** 専用の使い捨てセルフホストランナーを優先してください。カスタムのゲート
ランナーが受け取るのは、信頼された同一リポジトリの PR イベントだけです。標準のゲートは PR の
ツリーをチェックアウトせず、ワークフローのロジックと GitHub の PR メタデータだけを評価します。
永続的なマシンはジョブをまたいでプロセスの状態を保持し続けるため、無関係なワークロードと共有
しないでください。信頼されていない公開/フォーク PR の作成者に対しては、セルフホストのゲートや
完全なリキャップジョブをディスパッチする前に、ワークフローはフェイルクローズします。この境界を
弱めたり、信頼されていない貢献を永続的なランナーに回したりしないでください。

## バックエンドの選択

リポジトリ変数 `VISUAL_RECAP_AGENT` で、どのコーディングエージェントにスキルを実行させるかを
選びます。

| `VISUAL_RECAP_AGENT`  | コーディングエージェント                 | 必要な API キー        | 必要な変数                                     |
| --------------------- | ---------------------------------------- | ----------------------- | ---------------------------------------------- |
| `claude` _(デフォルト)_ | Claude Code CLI                         | `ANTHROPIC_API_KEY`    | —                                              |
| `codex`               | OpenAI Codex CLI                         | `OPENAI_API_KEY`       | —                                              |
| `openai-compatible`   | Agent-Native Code + 互換プロバイダー      | `VISUAL_RECAP_API_KEY` | `VISUAL_RECAP_BASE_URL`、`VISUAL_RECAP_MODEL` |

変数が未設定の場合、この Action は `claude` を使います。

## モデルと推論

バックエンドに加えて、次のリポジトリ変数でエージェントの実行方法を調整できます。

- **`VISUAL_RECAP_MODEL`** は、CLI に渡すモデル (`--model`) を固定します — 例えば Codex 向けの `gpt-5.6-luna`、Claude のモデル ID、DeepSeek 向けの `deepseek-chat` などです。`openai-compatible` では必須です。**Claude** バックエンドでは、未設定のままにすると現在はデフォルトで `claude-sonnet-5` が使われます。より安価な `claude-haiku-4-5` など、別の Claude モデルを使うには、この変数を明示的に設定してください。**Codex** バックエンドでは、未設定のままだと Codex CLI 自身のデフォルトモデルが使われます。
- **`VISUAL_RECAP_REASONING`** は、推論の深さを設定します: `none`、`minimal`、`low`、`medium`、`high`、`xhigh` のいずれかです。これは Codex バックエンドに適用されます。Claude の推論はモデル側で決まるため、この変数は Claude では無視されます。
- **`VISUAL_RECAP_BASE_URL`** は、`openai-compatible` バックエンド向けの HTTP(S) ベース URL を選択します。DeepSeek や Kimi など、プロバイダーの OpenAI 互換エンドポイントを、URL に認証情報を埋め込まずに使ってください。
- **`VISUAL_RECAP_SKILL_SOURCE`** は、プロンプトの鮮度を制御します: `auto` または未設定では同梱された最新のスキルガイダンスが使われ、`repo` ではリポジトリにコミットされたローカルの `visual-recap` スキルフォルダーに固定されます。

例えば、GPT-5.6 Sol を使って高い推論レベルで Codex 上でリキャップを実行するには、リポジトリ
変数 `VISUAL_RECAP_AGENT=codex`、`VISUAL_RECAP_MODEL=gpt-5.6-sol`、
`VISUAL_RECAP_REASONING=high` を設定します。

DeepSeek を使うには、`VISUAL_RECAP_AGENT=openai-compatible`、
`VISUAL_RECAP_BASE_URL=https://api.deepseek.com/v1`、`VISUAL_RECAP_MODEL=deepseek-chat`、
そしてシークレット `VISUAL_RECAP_API_KEY` を設定します。Kimi も、その OpenAI 互換のベース URL
とモデル ID を使えば同じように動作します。他の OpenAI 互換プロバイダーも、同じ 3 つの設定を
使います。

## コスト

リキャップの実行は、安価なテンプレート要約ではなく、実際の diff を読み取るフルエージェンティック
なコーディングエージェントセッションです。そのため、コストはモデルの選択と実行頻度に応じて
変わります。

- **PR のプッシュごとにフルセッションが実行されます。** デフォルトのトリガーは `synchronize` で発火するため、10 回プッシュされた PR ではエージェントが 10 回実行されます。
- 前回の実行以降のコミットだけでなく、**毎回 PR 全体**が対象になります — コストは増分の diff サイズではなく、PR 全体のサイズに応じて増えます。
- **diff の入力は約 600KB を上限とします。** これにより 1 回の実行あたりの最悪ケースには上限が設けられますが、大きな diff は小さな diff よりも依然として大きなコストがかかります。
- **失敗時に 1 回自動リトライします。** 一時的な失敗が起きた実行では、コストがおよそ倍になることがあります。

コストを抑えるには:

- **より安価なモデルに固定します。** Claude の場合、シンプルまたは小規模なリポジトリでは `VISUAL_RECAP_MODEL=claude-haiku-4-5` を設定してください — これは最も安価な Claude のティアです。`claude-sonnet-5` (デフォルト) はバランス型のティアです。
- **より安価なモデルの Codex に切り替えます。** `VISUAL_RECAP_AGENT=codex` を、`VISUAL_RECAP_MODEL=gpt-5.6-luna` (最も安価な GPT-5.6 ティア) または `gpt-5.6-terra` (中間ティア) と組み合わせて設定し、さらに推論トークンの消費を抑えるには `VISUAL_RECAP_REASONING=low` を設定してください。推論の深さは Codex にのみ適用されます。
- **より安価な OpenAI 互換プロバイダーを指定します。** `VISUAL_RECAP_AGENT=openai-compatible` を、DeepSeek、Kimi、その他任意の OpenAI 互換エンドポイントを指す `VISUAL_RECAP_BASE_URL`/`VISUAL_RECAP_MODEL`/`VISUAL_RECAP_API_KEY` と組み合わせて設定します。
- **明示的な PR ラベルを必須にします。** `VISUAL_RECAP_REQUIRED_LABELS=visual recap` を設定すると、ワークフローはインストールされたままですが、PR にそのラベルが付くまでリキャップをスキップします。複数のラベルをオプトインさせたい場合は、`visual recap,recap` のようにカンマ区切りのリストを使います。掲載されているラベルを付けると、ワークフローはすぐに動き出します。
- **リキャップの頻度を下げます。** インストールされたワークフローの `on.pull_request.types` を `[opened, synchronize, reopened, ready_for_review, labeled, closed]` から `[opened, ready_for_review, closed]` に編集すると、毎回のプッシュではなく、PR が開いたときとマージされたときだけリキャップするようになります。

どの実行でも、実際に使った量が記録されます。ワークフローの `recap usage` ステップが、トークンと
コストの使用量を公開済みの Plan に添付するため、推測ではなく実行ごとの実際の支出を確認できます。

## シークレットと変数 {#secrets-and-variables}

これらは、リポジトリの **Settings → Secrets and variables → Actions** で設定してください。

### デフォルトバックエンド用のシークレット

| シークレット        | 用途                                                                                                                                |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `PLAN_RECAP_TOKEN`  | `npx @agent-native/core@latest connect` で発行される、取り消し可能なトークンです。リキャップ Plan の公開とスクリーンショットのアップロードを許可します。 |
| `ANTHROPIC_API_KEY` | デフォルトの Claude Code バックエンド向けの LLM キーです。                                                                          |

**チームの場合: 組織のサービストークンを使ってください。** 個人トークンは、それを発行した本人に
紐づいています — その人が組織を離れたりトークンを取り消したりすると、そのシークレットを使う
すべてのリポジトリで 401 エラーが発生し始め、CI が作成した Plan もチームではなくその個人の
所有物になってしまいます。組織のサービストークンは、あなたの**組織**が所有します。サービス
プリンシパル (`svc-<name>@service.<orgId>`) として動作し、個人が離れても存続し、公開される
リキャップは組織内で閲覧可能になり、組織のオーナーまたは管理者であれば誰でも一覧表示や取り消し
ができます。発行するには (組織のオーナー/管理者のみ):

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --service-token pr-recap
```

このコマンドはブラウザであなたを認証し、その後サービストークンを一度だけ表示します —
これを `PLAN_RECAP_TOKEN` シークレットとして保存してください。後から管理するには、Plans アプリ
の `list-org-service-tokens` と `revoke-org-service-token` の actions を使います。

**個人利用の場合: 個人トークンでも問題なく動作します。** あなたの Plans アプリに対して
`npx @agent-native/core@latest connect` で発行してください。ホスト型アプリの場合、これは
`npx @agent-native/recap-cli@latest recap setup` が読み取れるローカルの公開トークンファイルも
書き出します。

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --client codex
npx @agent-native/recap-cli@latest recap setup
```

手動でのセットアップを好む場合は、トークンを GitHub のシークレットに貼り付けてください。
`plan_recap_xxxxxxxxxxxxxxxx` のようなプレースホルダーは例としてのみ使い、実際のトークンを
コミットしないでください。

| `VISUAL_RECAP_BASE_URL`        | 互換バックエンドでは必須                                         | 変数。OpenAI 互換バックエンド向けの HTTP(S) ベース URL です。認証情報を含めると拒否されます。                                                                                                             |
| `VISUAL_RECAP_MODEL`           | Claude では `claude-sonnet-5`。互換バックエンドでは必須          | 変数。OpenAI 互換バックエンドではプロバイダーのモデル ID です (そこでは必須)。Claude では、未設定の場合は現在 `claude-sonnet-5` がデフォルトになります — 上書きするには設定してください。例えば最も安価なティアには `claude-haiku-4-5` を使います。Codex では、未設定だと Codex CLI 自身のデフォルトが使われます。 |
| `VISUAL_RECAP_REASONING`       | 各モデルのデフォルト                                             | 変数。推論の深さ: `none`、`minimal`、`low`、`medium`、`high`、`xhigh` のいずれかです。Codex バックエンドに適用されます。                                                                                   |
| `VISUAL_RECAP_REQUIRED_LABELS` | —                                                                | 変数。カンマ区切りの PR ラベルです。設定すると、PR に掲載されたラベルのうち少なくとも 1 つが付くまで、ゲートはスキップされます。例: `visual recap`。                                                       |
| `RECAP_CLI_VERSION`            | `latest`                                                         | 変数。ワークフローがインストールする `@agent-native/recap-cli` のバージョンを固定します — 例: `1.5.0`。[バージョンの固定](#version-pinning-copy-variant) を参照してください。                             |
| `PLAN_RECAP_APP_URL`           | `https://plan.agent-native.com`                                  | シークレット。Plans アプリを別のオリジンでセルフホストしている場合のみ必要です。                                                                                                                           |

このワークフローは、ヘルパー CLI をどう呼び出すかを自動検出するため (このモノレポ内では
ローカルソース、それ以外では公開されている `@agent-native/recap-cli`)、設定すべき `RECAP_CLI`
という変数はありません。

## コメント内のインラインスクリーンショット

エージェントがリキャップを公開すると、ワークフローはヘッドレス Chrome でレンダリングされた
Plan をライトモードとダークモードの両方でスクリーンショットし、その PNG 画像を Plans アプリの
署名付き公開画像ルートにアップロードします。続いて固定 PR コメントは、それらのスクリーン
ショットを `<picture>` 要素で**インライン**に埋め込みます — GitHub は camo プロキシ経由で
それらを再配信するため、レビュアーは何も開くことなく、コメント内で自分の GitHub テーマに合った
プレビューをそのまま確認できます。探索したり、コメントしたり、注釈を付けたりしたいときのために、
完全なインタラクティブ Plan へのリンクがすぐ隣にあります。

## フォーク PR

### デフォルトの動作 (対応不要)

メインの `pr-visual-recap.yml` ワークフローは、`pull_request_target` では**なく**、プレーンな
`pull_request` トリガーで起動します。そのため、フォーク PR は**リポジトリのシークレットに
アクセスできない**状態で実行され、ワークフローは `PLAN_RECAP_TOKEN` を見つけられず、きれいに
何もしません — 公開の失敗も、認証情報の漏えいも起きません。リキャップは、シークレットが利用
できる同一リポジトリ内のブランチからの PR に対してのみ、自動的に実行されます。

つまり、シークレットが存在する**前に**ワークフローファイルをマージしても構いません。トークン
が設定されていなければ、シークレットを設定するまで、すべての実行は静かに何もしません。`gate`
ステップは、ドラフト PR と bot 作成の PR も自動的にスキップするため、デフォルトではどちらも
リキャップの実行をトリガーしません。

### ラベルゲートの仕組み

1. フォークの貢献者が PR を開きます。GitHub がフォークの実行にシークレットを渡さないため、通常の `pull_request` ワークフローはスキップされます。
2. フォークワークフローは、PR の作成者関連付けを確認します。信頼された作成者 (`OWNER`、`MEMBER`、`COLLABORATOR`) は、open、synchronize、reopen、ready-for-review の各イベントで自動的に実行されます。
3. それ以外の貢献者の場合は、メンテナーが現在の diff をレビューし (特にプロンプトインジェクションのような内容がないか — 下記参照)、その後 PR に `recap` ラベルを付ける必要があります。
4. それ以外の貢献者向けのラベルゲートはヘッド SHA ごとに機能します。貢献者がさらにコミットをプッシュすると、次の synchronize イベントは、メンテナーが新しい diff をレビューした上で `recap` を外して再度付けるまでスキップされます。

### フォークワークフローが行うこと・行わないこと

| ワークフローが行うこと                                                                                                  | ワークフローが行わないこと                                                          |
| ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| **ベースブランチの ref** で**ベースリポジトリ**をチェックアウトする — 信頼されたコードのみ                              | フォークからのコードをチェックアウトまたは実行すること                                |
| フォークのヘッドをリモート ref として fetch する (`git fetch origin pull/<n>/head:refs/recap/fork-head`) — コミットの fetch は安全 | フォークからパッケージをインストールする、フォークのスクリプトを実行する、フォークの内容をコードとして評価すること |
| `git diff base...refs/recap/fork-head` を実行する — すでに fetch 済みの 2 つのオブジェクトの純粋なテキスト diff        | diff を LLM へのテキスト入力以外の何かとして使うこと                                  |
| **ベースリポジトリの** visual-recap スキルとエージェント設定を実行する                                                  | フォークからスキルや設定を読み込むこと                                                |
| ファーストパーティの PR と同じシークレットスキャンのステップ (フェイルクローズ) に diff を通す                          | シークレットスキャンをスキップすること                                                |
| diff の内容を信頼できないものとして明示する、プロンプトハードニングの注記をエージェントプロンプトに追加する            | 通常のリキャップエージェントを超える追加の権限をエージェントに付与すること            |

### ラベルを付ける前に diff をレビューしなければならない理由

フォークの diff は、リキャップエージェントが入力として読み取る、攻撃者が制御できるテキストです。
巧妙に作られた diff には、プロンプトインジェクションの内容 — 例えばエージェントへの指示のように
見える diff の行 — が含まれ、リキャップエージェントに意図しない動作 (公開トークンの窃取や、
誤解を招くリキャップ内容の生成など) を取らせようとする可能性があります。

`recap` ラベルを付ける前に、diff の中に次のようなものがないかざっと確認してください。

- 直接的なコマンドやロールの指示のように読める行 (「Ignore previous instructions...」、「You are now...」、「Write the token to...」など)。
- システムプロンプトと誤読されかねない、不自然なファイル名。
- デコードすると指示になりうる、追加されたファイル内のエンコードされた内容。

これらの緩和策 (シークレットスキャン、機密パスのゲート、プロンプトハードニングの注記、制限
された agent tool allowlist) はすでにワークフローに組み込まれていますが、ラベルのレビューが
主たる防衛線です。

### メインワークフローとの関係

この 2 つのワークフローファイルは独立しています。フォークでない PR の更新では、
`pr-visual-recap.yml` だけが実行されます。フォーク PR では、通常のワークフローはそのフォーク
ゲートで終了し、`pr-visual-recap-fork.yml` が、信頼された同一組織の作成者に対しては自動的に、
それ以外の貢献者に対してはメンテナーによる新しい `recap` ラベルの後に実行されます。この 2 つ
は同じ固定コメントのマーカーと Plan ID のスレッド化を共有するため、PR でもフォーク PR でも、
同じ PR に対して 1 件の upsert されたコメントが作られます。

### 自己書き換えガード {#self-modifying-guard}

`gate` ステップは、PR が次のいずれかのパスに触れている場合、リキャップを完全にスキップします。
これにより、PR が信頼されたリキャップジョブの読み込むワークフロー、スキル、エージェント設定を
書き換えてシークレットを窃取することは決してできません。

| パスパターン                                | 理由                                       |
| -------------------------------------------- | ------------------------------------------ |
| `.github/workflows/pr-visual-recap.yml`      | ワークフロー自体                            |
| `**/skills/visual-(recap\|plan\|plans)/**`   | エージェントが従う visual-recap スキル      |
| `**/.claude/**`                              | ランナーが読み込むエージェント設定          |
| `**/CLAUDE.md`                               | ランナーが読み込むエージェントの指示        |
| `**/AGENTS.md`                               | ランナーが読み込むエージェントの指示        |
| `**/.mcp.json`                               | ランナーが読み込む MCP サーバー設定         |

`BuilderIO/agent-native` のモノレポでは、ワークフローは PR ヘッドのソースではなく、信頼された
ベースブランチのソースからリキャップ CLI を実行します。これにより、`packages/core/**` を含む
通常のパッケージの変更は、PR によって変更された CLI コードを実行することなく、リキャップの
対象であり続けます。

## ローカルファイルプライバシーモード

GitHub Action は、ホスト型で共有可能な PR レビュー向けに設計されています。リキャップの内容を
Agent-Native の Plan データベースに送らずにリキャップが欲しい場合は、代わりに同じヘルパー
フローをローカルファイルモードで実行してください。

```bash
npx @agent-native/recap-cli@latest recap collect-diff --base main --head HEAD --out recap.diff --stat recap.stat
npx @agent-native/recap-cli@latest recap scan --diff recap.diff
npx @agent-native/recap-cli@latest recap build-prompt --pr 123 --diff recap.diff --stat recap.stat --local-files --local-dir plans/pr-123-visual-recap
```

生成された `recap-prompt.md` をコーディングエージェントに渡します。ローカルファイルモードでは、
このプロンプトはエージェントに `plans/pr-123-visual-recap/plan.mdx` と任意のビジュアル
ファイルを書き出し、続けて次を実行するよう指示します。

```bash
npx @agent-native/core@latest plan local serve --dir plans/pr-123-visual-recap --kind recap --open
```

返される URL はホスト型の Plan UI を開きますが、ブラウザは localhost ブリッジからリキャップの
MDX を読み取ります。リキャップの内容はホスト型の Plan データベースには書き込まれず、この URL
はブリッジを実行しているマシン上でのみ動作します。同じ `PLAN_LOCAL_DIR` で Plan アプリを
ローカルで実行している場合は、`/local-plans/pr-123-visual-recap` ルートも有効です。リポジトリ
に紐づくフォルダーは、`/local-plans/pr-123-visual-recap?path=plans%2Fpr-123-visual-recap` として
開けます。このモードでは、明示的に公開するまで、ホスト型の固定 PR コメント、インライン
スクリーンショットのアップロード、使用量の添付、ブラウザコメントは無効になります。

## これは情報提供であり、ゲートではありません

リキャップは、通常の PR フローの上に重ねられたレビューの助けです。

- 可視性のために `Visual Recap` のチェック行を表示しますが、これは**決して必須チェックにはならず**、マージをブロックすることもありません。
- 生成や公開の失敗は neutral として完了し、無関係なコードへの赤い X ではなく、説明付きの固定コメントとして表面化します。
- リキャップとそのスクリーンショットは、**diff がレビュー済みであることを意味しません**。レビュアーは、実際に変更された行を読む必要が引き続きあります。

## バージョンの固定 (コピー版) {#version-pinning-copy-variant}

デフォルトでは、コピー版のワークフローは実行時に `@agent-native/recap-cli@latest` をインストール
するため、リキャップを実行するたびに自動的に最新の CLI が使われます。CI で再現可能なツール
チェーンが必要な場合は、リポジトリ変数 **`RECAP_CLI_VERSION`** を設定して、インストールされる
バージョンを固定してください。

1. リポジトリの **Settings → Secrets and variables → Actions → Variables** に移動します。
2. 値を `1.5.0` のようにした `RECAP_CLI_VERSION` という変数を作成します。

この変数は任意です。未設定のままにする (または `latest` を設定する) と、最新リリースを追い
続けます。

再利用可能な呼び出し元のバリアントでは、代わりに `cli-version` 入力を使ってください
(再利用可能セクションの [バージョンの固定](#version-pinning) を参照)。

## シークレットスキャンの許可リスト

リキャップを公開する前に、ワークフローは `npx @agent-native/recap-cli@latest recap scan` を
実行し、diff の中にシークレットらしきものがないか検出します。diff が既知のシークレット
パターンに一致する PR は、説明付きのコメントとともにブロックされます — リキャップは公開されず、
diff の内容はコーディングエージェントに送られません。

まれに、リポジトリに意図的なテスト用フィクスチャや、シークレットのパターンに表面的には似ている
が実際にはシークレットではない文字列がある場合があります (テストファイル内のフィクスチャキー
など)。誤検知を抑制するには、リポジトリのルートに `.github/recap-scan-allowlist` を作成して
ください。

### 形式

空行でもコメント行でもない各行は、**リテラルの部分文字列**か、**`/regex/flags`** パターンの
いずれかです。

```
# Lines starting with # are comments.

# Literal substring — any diff line containing this string is allowed.
sk-test-fixture1234567890abcdef

# Regex pattern — written as /pattern/flags (JS syntax).
/^.STRIPE_KEY=sk-test-/i

# Another literal.
EXAMPLE_API_KEY=placeholder-value
```

ルール:

- ある行がリテラルを含んでいるか、行全体が正規表現に一致する場合、その行は**抑制**されます (許可されます)。
- このファイルは**フェイルクローズ**です。ファイルが存在しない場合、抑制は一切適用されず、スキャナーは以前と同じように動作します。
- 空のファイルは、ファイルが存在しないのと同じです。
- 不正な形式の正規表現の行は、リテラル文字列として扱われます。

この許可リストは、シークレットスキャンのゲートでのみ参照されます。コーディングエージェントが
何を読み取れるかには影響しません — ゲートを通過すれば、エージェントはいずれにせよ diff 全体を
受け取ります。

## 再利用可能なワークフローとして導入する

### 再利用可能なバリアントを使う理由

デフォルトのインストーラーは、約 360 行あるワークフロー YAML の全文をリポジトリにコピーします
(**copy** オプション)。これは、エアギャップ環境のリポジトリや、実行されるすべての行を監査する
必要があるリポジトリにとって正しい選択です。欠点は、バグ修正や改善が自動的には届かないこと
です — 各リリースの後、手動で `npx @agent-native/recap-cli@latest recap setup` を再実行する
必要があります。

**reusable** オプションは、代わりに約 20 行の薄い呼び出し元を書き出します。これは `uses:`
経由で `BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml` に処理を委譲
します。どの呼び出し元も、ワークフローが実行されるたびに自動的に最新のロジックを取り込むため、
ローカルでの更新は不要です。

|                                    | Copy (デフォルト)               | Reusable                       |
| ---------------------------------- | -------------------------------- | ------------------------------- |
| リポジトリ内のワークフローのサイズ | 約 360 行                        | 約 20 行                        |
| 修正を自動的に取り込む             | いいえ — `recap setup` を再実行  | はい                             |
| エアギャップ/完全な監査可能性      | はい                              | いいえ                           |
| 特定バージョンへの固定             | ローカルでの編集でのみ可能        | はい — `uses:` に `@v1.2.3` を設定 |

### 呼び出し元のスニペット

これは `npx @agent-native/recap-cli@latest recap setup --reusable` が書き出す内容です
(手動で貼り付けることもできます)。

```yaml
name: PR Visual Recap

# Thin caller — the full workflow logic lives in BuilderIO/agent-native.
# Fixes and improvements reach this repo automatically on each run.
# To pin a specific version for reproducibility replace '@main' with a
# tag or SHA, e.g. '@v1.2.3' or '@abc1234'.

on:
  pull_request:
    types: [opened, synchronize, reopened, ready_for_review, labeled, closed]

jobs:
  visual-recap:
    if: github.event.action != 'labeled' || vars.VISUAL_RECAP_REQUIRED_LABELS != ''
    permissions:
      actions: write
      contents: read
      checks: write
      issues: write
      pull-requests: write
    uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@main
    secrets:
      PLAN_RECAP_TOKEN: ${{ secrets.PLAN_RECAP_TOKEN }}
      ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
      OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
      VISUAL_RECAP_API_KEY: ${{ secrets.VISUAL_RECAP_API_KEY }}
      PLAN_RECAP_APP_URL: ${{ secrets.PLAN_RECAP_APP_URL }}
    with:
      agent: ${{ vars.VISUAL_RECAP_AGENT || 'claude' }}
      model: ${{ vars.VISUAL_RECAP_MODEL || '' }}
      base-url: ${{ vars.VISUAL_RECAP_BASE_URL || '' }}
      reasoning: ${{ vars.VISUAL_RECAP_REASONING || '' }}
      skill-source: ${{ vars.VISUAL_RECAP_SKILL_SOURCE || 'auto' }}
      runs-on: ${{ vars.VISUAL_RECAP_RUNS_ON || '"ubuntu-latest"' }}
      gate-runs-on: ${{ vars.VISUAL_RECAP_GATE_RUNS_ON || 'ubuntu-latest' }}
      required-labels: ${{ vars.VISUAL_RECAP_REQUIRED_LABELS || '' }}
      # cli-version: "latest"  # pin to a specific @agent-native/recap-cli version
```

[シークレットと変数](#secrets-and-variables) で説明した同じシークレットと変数が適用されます —
copy バリアントと同じ方法でリポジトリの設定に設定してください。reusable の呼び出し元は、
完全なリキャップジョブ向けに `VISUAL_RECAP_RUNS_ON` を JSON の `runs-on` 入力として、
メタデータのみのゲート向けに `VISUAL_RECAP_GATE_RUNS_ON` をプレーンラベルの `gate-runs-on`
入力として、任意の PR ラベルによるゲーティング向けに `VISUAL_RECAP_REQUIRED_LABELS` を
`required-labels` として、それぞれ転送します。ゲートのランナー入力が使われるのは、信頼された
同一リポジトリの作成者に限られます。それ以外の PR は GitHub ホストの `ubuntu-latest` を使い
ます。ランナー入力を省略すると、`ubuntu-latest` のデフォルトが維持されます。必須ラベルを
省略すると、自動的なリキャップの動作が維持されます。

### CLI 経由でインストールする

```bash
# Write the thin caller instead of the full copy:
npx @agent-native/recap-cli@latest recap setup --reusable

# Or with a pinned ref for reproducibility:
npx @agent-native/recap-cli@latest recap setup --reusable --ref v1.2.3
```

どちらのバリアントも、ワークフローを `.github/workflows/pr-visual-recap.yml` に書き出します。
既存のワークフローがすでにそこにあり、内容が異なる場合、このコマンドは拒否し、上書きするには
`--force` を渡すように伝えます。

書き出した後は、いつものように `npx @agent-native/recap-cli@latest recap doctor` を実行して、
シークレットが設定されていることを確認してください。

### バージョンの固定 {#version-pinning}

デフォルトでは、呼び出し元は `@main` を参照しており、これは常に再利用可能なワークフローの
最新の公開バージョンを使います。再現可能な CI が必要な本番リポジトリでは、タグまたは SHA に
固定してください。

```yaml
uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@v1.2.3
```

`cli-version` 入力は、ワークフロー内でどの `@agent-native/recap-cli` バージョンが実行される
かを制御します — 最新リリースを追い続けるには `"latest"` のままにし、完全な再現性のために
バージョン文字列 (例: `"1.5.0"`) に固定することもできます。

### workflow_call イベントコンテキスト

`workflow_call` ワークフローは、**呼び出し元**のイベントコンテキストを引き継ぎます。再利用可能
なワークフローは、PR 番号、ヘッド SHA、ベース SHA、マージ時刻、PR のメタデータを読み取るために
`github.event.pull_request.*` の式を使います — これらは、呼び出し元が `pull_request` で
トリガーされている場合にのみ正しく動作します。上記の呼び出し元のスニペットには、すでに正しい
イベントタイプが含まれています。マージ済みの PR のリキャップに `merged_at` を刻印し、後で
出荷済みの作業として検索できるようにするため、`closed` イベントが含まれています。

呼び出し元を `workflow_dispatch` や `push` でトリガーしないでください — これらのイベントには
`pull_request` ペイロードが含まれておらず、ゲートは「no pull_request payload」としてリキャップ
をスキップします。
