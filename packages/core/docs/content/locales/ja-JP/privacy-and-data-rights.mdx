# プライバシーとデータに関する権利

Agent-Native には、既定のアカウント設定にプライバシーリクエストの画面が含まれています。サインインしたユーザーは、自分の個人データのコピーまたは削除を依頼できます。

これは実装の基準であり、法的助言やコンプライアンス認証ではありません。アプリを運用する組織は自らの法的な立場を判断し、利用環境に合った通知と手続きを公開する必要があります。

## ユーザーができること

**設定 > アカウント > セキュリティ**を開くと、**あなたのデータ**グループで次の操作ができます。

- アクセスまたはデータポータビリティの確認のため個人データのコピーを依頼する。
- 消去の確認のため個人データの削除を依頼する。
- 既存のプロフィールとメール設定からアカウント情報を訂正する。

リクエストは永続的に保存され、重複せず、監査されます。アクションが保存するのは種類、状態、時刻だけです。データのダンプを返したり、他人のメールアドレスやユーザー ID を受け取ったり、直ちにデータを削除したりすることはありません。

## エージェントができないこと

プライバシーリクエストはアカウント設定の UI から送信します。`request-privacy-right` は認証され、エージェントツールと MCP/A2A の検出から隠され、ツールブリッジから拒否され、フロントエンドからの呼び出しだけが許可されます。

コアの `offboard-member` にも同じ UI-only の境界があります。メンバーのオフボードは所有行を移してアクセスを取り消す組織操作であり、アカウント消去ではありません。組織の削除も既存の所有者向け UI 確認の背後にあります。

人による承認ダイアログはセキュリティ境界ではありません。データ消去、ID の無効化、メンバーシップや認証を変更するカスタムアクションには明示的な UI-only 境界を使い、検証済みのリクエストコンテキストから ID を取得してください。

## 運用者による対応

フレームワークはリクエストを記録します。運用者は次を行う必要があります。

1. 申請者の本人確認を行い、組織と法的な範囲を決める。
2. 管理対象のデータを集め、非公開でアクセス制御された経路で渡す。
3. アプリの行と非公開ファイルを削除または匿名化し、必要に応じてセッションと認証情報を失効させ、接続されたプロバイダーや処理者と調整する。
4. バックアップ、セキュリティ・監査ログ、不正防止、その他の文書化された例外に保存期間を適用する。
5. 完了、部分対応、保留理由を記録し、申請者に結果を伝える。

組織の行を一つ、または設定を一つ削除しただけで完了と判断しないでください。ホストされたプロバイダー、アップロード、接続サービス、キャッシュ、バックアップ、不変の監査記録には別々の保持・削除経路があります。

## 既定のプライバシー姿勢

新しく共有できるリソースは既定で非公開です。ブラウザー分析では DOM とネットワークの自動取得を無効にし、設定した場合もセッションリプレイはオプトインかつサインイン済みユーザーだけです。これらはプライバシー通知、法的根拠、保持方針、同意・オプトアウトの仕組みに代わるものではありません。

デプロイが個人情報を販売または共有する場合、該当する CCPA のオプトアウトと Global Privacy Control を扱う必要があります。フレームワークは販売・共有の仕組みを作りません。

## デプロイチェックリスト

- データの種類、目的、提供先、保持期間、権利、連絡先を記載したプライバシー通知を公開する。
- 法的根拠、同意、機微データ、年齢要件を決めて文書化する。
- アクセス、訂正、削除、移植、異議、オプトアウトの受付担当と手順を決める。
- テーブル、非公開ファイル、分析、接続サービス、メール、キャッシュ、ログ、バックアップ、再委託先を一覧化する。
- 本人確認、期限、保持例外、削除の証跡、異議申立てを定義する。
- 影響の大きいアクションを UI-only にし、エージェント、MCP、A2A、CLI、HTTP、ツール iframe から呼べないことをテストする。
