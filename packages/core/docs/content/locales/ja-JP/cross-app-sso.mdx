# 組織 SSO とアプリ間フェデレーション

組織 SSO は会社の OIDC または SAML プロバイダーで 1 つの Agent-Native デプロイメントにログインします。アプリ間フェデレーションは別々のデプロイメント間で検証済み ID や組織コンテキストを共有します。設定と信頼境界は異なります。

正確に登録された Agent-Native アプリのログインページには、
「Continue with Agent-Native」という明示的な操作があります。これは
Dispatch の既存の検証済みメールアドレスのフローを開始します。このページ
ではブラウザ、Desktop、サーバー側のフェデレーションを説明します。

## アプリ間フェデレーション

### Desktop ワークスペース

ワークスペースへのログインは Desktop 設定で明示的に実行します。有効に
すると、Desktop は専用ブローカーを通じて条件を満たす登録済みアプリを
プロビジョニングできます。各対象アプリは独自のユーザーストア、セッション、
アクセスチェックを保持します。Desktop はアプリのログインページへの
匿名ブラウザナビゲーションを横取りしません。

アプリが対象になるには、次の条件をすべて満たす必要があります。

- Desktop がそのアプリのワークスペース SSO を有効にしている。
- 本番 URL が正確な HTTPS である。
- Dispatch にそのアプリの正確なサーバー登録がある。
- <code>desktop.workspace-sso</code> ロールアウトフラグが有効である。

デバイス単位の <code>desktopSsoEnabled</code> は既定で有効です。明示的な
false はオプトアウトとして残ります。フラグ、設定、登録、または適格性
チェックが利用できない場合は、通常のアプリ別ログインを利用できます。

### サーバー側フェデレーション

ブローカーとサーバー側の呼び出し元は、短時間だけ有効なサーバー検証
プロトコルを使います。正確に登録されたファーストパーティアプリでは、
ユーザーが「Continue with Agent-Native」を選ぶと同じプロトコルが始まります。

1. 呼び出し元が登録済みアプリへの正確なバインディングを要求します。
2. Dispatch がワークスペース ID を認証し、短時間だけ有効な一回限りの
   認可コードを返します。
3. 対象アプリのサーバーが PKCE 検証子でコードを交換します。
4. 対象アプリが署名済みアサーション、アプリ、コールバック、スコープ、
   nonce、有効期限を検証します。
5. 検証済みメールアドレスでローカルユーザーをリンクまたは作成し、通常の
   ローカルセッションを発行します。

アサーションはサーバー間交換でのみ返されます。ブラウザ URL には現れず、
再利用可能な bearer token でもありません。

## 組織フェデレーション

<code>organization.cross-app-federation</code> フラグは既定で無効です。有効に
すると、ソースアプリは Dispatch にローカル組織を登録し、正確な
<code>(identity_authority, identity_id)</code> マッピングを保存します。
ターゲットアプリは、サーバー検証済みアサーションからの正規組織 ID、名前、
検証済みメンバー役割だけを受け入れます。

組織名、メールドメイン、ブラウザ Cookie は結合キーではありません。マッピング
のないローカル組織は明示的な移行まで変更されません。リンク済みメンバーシップ
にはターゲットアプリの通常のアクセスチェックが適用されます。

組織フェデレーションでは登録済みソースアプリごとに別の認証情報を使います。

- ソースアプリに <code>AGENT_NATIVE_IDENTITY_FEDERATION_SECRET</code> を設定します。
- Dispatch に対応する
  <code>AGENT_NATIVE_IDENTITY_FEDERATION_SECRET_&lt;NORMALIZED_APP_ID&gt;</code>
  を設定します。
- この権限境界で <code>A2A_SECRET</code> を再利用しないでください。

アプリ ID のサフィックスは、英数字以外の各連続部分をアンダースコアに
置き換え、結果を大文字にします。たとえばアプリ ID

<code>workspace-reports</code> には
<code>AGENT_NATIVE_IDENTITY_FEDERATION_SECRET_WORKSPACE_REPORTS</code>
を使います。

ID と組織の書き込みは追加のみです。同じメールアドレスの既存ユーザーは変更
せずに再利用されます。新しい検証済みメールアドレスではローカルユーザーを
作成します。フェデレーションを無効にしてもデータは削除されません。

## 設定

<code>AGENT_NATIVE_IDENTITY_HUB_URL</code> は、自ホストアプリで明示的な
設定が必要な場合に、サーバー側とブラウザの経路で Dispatch を指定します。
正確に登録されたファーストパーティアプリのログインページには 「Continue with
Agent-Native」が表示されます。<code>browser.identity-sso</code>
ロールアウトフラグは、サイレントな <code>prompt=none</code> ログインと
ローカルログイン後のブートストラップを引き続き制御します。ローカルログイン
はフォールバックとして利用できます。

自ホストの Dispatch では、<code>IDENTITY_SSO_APP_REGISTRY_JSON</code> を使って
各カスタムアプリに正確なアプリ ID、クライアント ID、HTTPS オリジン、
コールバックパス、<code>identity-sso</code> 機能を登録します。

本番登録では HTTPS と正確なコールバックパスを使う必要があります。Localhost
はローカル開発だけで許可されます。不明なサブドメイン、不一致のアプリ ID、
任意のパス、クロスオリジンのコールバックは拒否されます。

## 検証とロールバック

デプロイ後:

1. ブラウザでメール、パスワード、マジックリンク、設定済みプロバイダーの
   ログインが引き続き機能することを確認します。
2. 「Continue with Agent-Native」が表示され、ローカルログインも利用できる
   ことを確認します。<code>browser.identity-sso</code> が無効でも両方が
   利用できることを確認します。有効な場合は、サイレントな
   <code>prompt=none</code>
   ログインとローカルフォームのフォールバックを確認します。
3. Desktop SSO を有効にした場合は、Desktop 設定の明示的な操作から正確に
   登録されたアプリを 1 つ確認します。
4. 組織フェデレーションを有効にした場合は、対象アプリで正確な組織 ID と
   メンバー役割を確認します。

サイレントなブラウザログインまたは Desktop の経路を戻すには、対応する機能
フラグを無効にします。自ホストアプリから明示的なブラウザ操作を削除するには、

<code>AGENT_NATIVE_IDENTITY_HUB_URL</code> または正確なアプリ登録を削除して
再デプロイします。ローカルログインは引き続き利用でき、追加された ID と組織の
レコードも保持されます。

## ブラウザー ID SSO の展開手順

まず `browser.identity-sso` を 1 つのテストメールだけで有効にします。Dispatch にログインし、対象アプリからログアウトして再読み込みし、サイレントプローブを確認します。Hub セッションなしで `login_required` がローカルフォームに戻ることを確認してから対象を広げます。初回有効化では既存セッションを一度取り消す必要がある場合があります。
