# マルチアプリ ワークスペースでのカレンダーのクロスアプリ利用

カレンダーは、[Dispatch](/docs/template-dispatch) ワークスペース内にある数多くの
アプリの中の 1 つです。このページでは、それが実際に何を意味するのかを具体的に
説明します。連携がどのように機能するか、そして他のアプリがあなたのカレンダーに
働きかけたり、そこで起きたことに反応したりする具体的な方法についてです。概要は
[カレンダー](/docs/template-calendar) を参照してください。

## カレンダーが Dispatch と連携する仕組み

これが自動的に行われるかどうかは、カレンダーと Dispatch がどちらもホストされて
いるか、ローカルで動いているかではなく、両者がどのように一緒に設定されたかに
依存します。

### 同じワークスペース: 自動

カレンダーと Dispatch が (`create` または `add-app` を通じて) 1 つの Agent
Native ワークスペースに一緒に生成または追加され、1 つの単位としてデプロイされて
いる場合、両者はすでに 1 つの `.env`、1 つの `A2A_SECRET`、1 つのワークスペース
レジストリを共有しています。発見と認証済み A2A 呼び出しは、そのワークスペースが
あなたのマシンで動いているか本番環境で動いているかにかかわらず、何も設定せずに
そのまま機能します。これは、カレンダーを土台にした実際のマルチアプリ プロダクト
で想定されるセットアップです。

### 別々のデプロイ: 手動の手順が 1 つ

カレンダーと Dispatch が独立して作成された 2 つの Agent Native プロジェクトで
ある場合、両者はシークレットを共有しておらず、まだお互いを呼び出せません。接続
するには、それぞれの側で手動の手順が 1 つ必要です。設定 → 接続されたエージェント、
Agent ページの接続タブ、または Dispatch → エージェント → 外部エージェントを追加
のいずれかから、共有シークレットを持つ `remote-agents/<id>.json` リソースを
追加します。全体の手順については [A2A プロトコル](/docs/a2a-protocol) を参照して
ください。

どちらの状況にあるかを確認するには、いずれかのアプリのエージェントに「どのアプリが
見える?」と尋ねてください。Dispatch の回答にカレンダーが含まれていなければ、
2 番目のケースに当たります。

## 連携戦略

**カレンダーのイベントを起点に自動化する。** イベントの作成と予約の作成は、
どちらも共有フレームワークのイベント バス上で本物のイベント
(`calendar.event.created`、`calendar.booking.created`) を発火させます。どの
アプリの[自動化](/docs/automations)も、どちらのアプリがそれを定義しているかに
かかわらず、いずれかを購読できます。カレンダーに予約が入ると、Mail でウェルカム
メールの下書きが作られたり、Slides でミーティングが始まる前に議題が作られたりする、
といったことが起こり得ます。カレンダーはこうした自動化を標準搭載していませんが、
イベント自体は本物であり、いつでも構築したいときに組み込む準備が整っています。

**Dispatch を介した自然言語での委任。** 姉妹アプリがカレンダーと連携するために
特別な統合は必要ありません。チャットで頼むのと同じように、「来週 Sam との 30 分を
見つけて」のような平易な言葉のリクエストをカレンダーのエージェントに渡すことが
でき、カレンダーはそれに直接答えたり、実行したりします。これが、Mail や Slack に
届いたスケジューリングのリクエストが予約済みのイベントに変わる、といったことの
実際の仕組みです。Dispatch (またはメッセージを受け取ったアプリ) がそのリクエスト
をカレンダーのエージェントに委任し、カレンダーは他のどんなプロンプトとも同じように
それを処理します。

**分離されたままでいる。** これらのどれについても、カレンダーが Mail や Slack の
認証情報を知る必要はなく、その逆も同様です。イベント バスと、それを購読する
自動化がアプリ同士の間に立つので、カレンダーは本物のイベントを発行するか、本物の
リクエストに答えるだけで済みます。誰が、どのように聞いているかを知る必要はありません。
