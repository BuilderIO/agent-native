# マルチアプリ ワークスペースでのスライドのクロスアプリ利用

スライドは、[Dispatch](/docs/template-dispatch) ワークスペース内にある数多くのアプリの中の 1 つです。このページでは、それが実際に何を意味するのかを具体的に説明します。連携がどのように機能するか、そして他のアプリがあなたのデッキに働きかけたり、その中にあるものを再利用したりする具体的な方法についてです。概要は [スライド](/docs/template-slides) を参照してください。

## スライドが Dispatch と連携する仕組み

これが自動的に行われるかどうかは、スライドと Dispatch がどちらもホストされているか、ローカルで動いているかではなく、両者がどのように一緒に設定されたかに依存します。

### 同じワークスペース: 自動

スライドと Dispatch が (`create` または `add-app` を通じて) 1 つの Agent-Native ワークスペースに一緒に生成または追加され、1 つの単位としてデプロイされている場合、両者はすでに 1 つの `.env`、1 つの `A2A_SECRET`、1 つのワークスペース レジストリを共有しています。発見と認証済み A2A 呼び出しは、そのワークスペースがあなたのマシンで動いているか本番環境で動いているかにかかわらず、何も設定せずにそのまま機能します。これは、スライドを土台にした実際のマルチアプリ プロダクトで想定されるセットアップです。

### 別々のデプロイ: 手動の手順が 1 つ

スライドと Dispatch が独立して作成された 2 つの Agent-Native プロジェクトである場合、両者はシークレットを共有しておらず、まだお互いを呼び出せません。接続するには、それぞれの側で手動の手順が 1 つ必要です。Settings → Agent → Sub-agents (Connect agent)、または Dispatch → エージェント → 外部エージェントを追加のいずれかから、共有シークレットを持つ `remote-agents/<id>.json` リソースを追加します。全体の手順については [A2A プロトコル](/docs/a2a-protocol) を参照してください。

どちらの状況にあるかを確認するには、いずれかのアプリのエージェントに「どのアプリが見える?」と尋ねてください。Dispatch の回答にスライドが含まれていなければ、2 番目のケースに当たります。

## 連携戦略

**Creative Context ライブラリを通じてデッキを共有する。** デッキを提出すると、正確な 1 つのバージョンが共有の Creative Context ライブラリに固定され、ワークスペース内のどのアプリも、スライドだけでなく、後からそれらのスライドを検索して再利用できます。議事録アプリが、プロンプトで説明する代わりに、承認済みの指標スライドを自分の出力に取り込む、といったことができます。

**Dispatch を介した自然言語での委任。** 姉妹アプリがスライドと連携するために特別な統合は必要ありません。チャットで頼むのと同じように、「今四半期の数字を 5 枚のスライドでまとめて」のような平易な英語のリクエストをスライドのエージェントに渡すことができ、スライドはそれに直接答えたり、実行したりします。これが、Mail に届いたレポート依頼が完成したデッキに変わる、といったことの実際の仕組みです。Dispatch (またはメッセージを受け取ったアプリ) がそのリクエストをスライドのエージェントに委任し、スライドは他のどんなプロンプトとも同じようにそれを処理します。

**分離されたままでいる。** これらのどれについても、スライドが姉妹アプリの認証情報を知る必要はなく、その逆も同様です。A2A プロトコルと共有の Creative Context ライブラリがアプリ同士の間に立つので、スライドは本物のリクエストに答えるか、本物の共有リソースを公開するだけで済みます。誰が、どのように呼び出しているかを知る必要はありません。
