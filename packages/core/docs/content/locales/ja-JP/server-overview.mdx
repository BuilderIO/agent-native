# サーバー

`server/` ディレクトリは、エージェント ネイティブ アプリのインフラストラクチャ層です。起動時のタスク、認証、そして actions ではカバーできない HTTP サーフェスを扱います。プロダクトの動作のほとんどは [Actions](/docs/actions-overview) に属します。サーバーは、それらの actions を外部から利用可能にする存在です。

## サーバーの役割 {#role}

従来の Web アプリでは、サーバーがロジックの大半を担っています。ビジネスルール、データアクセス、プレゼンテーションのすべてがルートハンドラーの内部で行われます。エージェント ネイティブ アプリはこれとは異なります。ロジックは actions に置かれ、エージェントと UI がそれを対等なパートナーとして共有します。サーバーの仕事は調整です。データベースのマイグレーションを実行し、認証を構成し、エージェント ループをマウントし、actions だけでは表現できない狭い範囲の HTTP 関心事を扱います。

ブラウザからのリクエスト、エージェント ループ、外部 API クライアントはすべて同じ Nitro サーバーを経由し、同じ SQL データベースから読み取ります。エージェント専用のバックエンドや UI 専用のバックエンドは存在しません。サーバー層こそが、actions を外部の世界に公開する仕組みです。

## server/ ディレクトリの中身 {#server-directory}

以下は、すべてのエージェント ネイティブ アプリが備える `server/` 内のディレクトリとファイルです。それぞれがサーバー層の特定の部分に対応しています — 何をするものか、いつ使うべきか、フレームワークの他の部分とどうつながっているかを示します。

| ページ                                      | 内容                                                                                              |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **[データベース](/docs/server-database)**   | `table()` ヘルパーによるスキーマ定義、`getDb`、および ownable テーブルのパターン                  |
| **[ミドルウェア](/docs/server-middleware)** | `server/middleware/` にある認証ガードと、それがプラグインではなくそこで動く理由                   |
| **[プラグイン](/docs/server-plugins)**      | 認証と agent-chat の起動プラグイン、および任意のアプリ固有データベースマイグレーション            |
| **[ルート](/docs/server-routes)**           | ファイルベースのルート、SSR キャッチオール、カスタム ルートをリクエストユーザーにスコープする方法 |

## Nitro {#nitro}

[Nitro](https://nitro.build) は、エージェント ネイティブの HTTP 層を支えるサーバー ツールキットです。`server/` で構成するものの大半は Nitro に関するものです。ファイルベースのルート、起動プラグイン、ミドルウェアです。

- **ファイルベースのルーティング**: ファイル名がそのまま HTTP メソッドと URL パスにマッピングされ、登録は一切不要です。`server/routes/api/health.get.ts` は自動的に `GET /api/health` になります。詳細は [ルート](/docs/server-routes) を参照してください。
- **プラグイン**: サーバー起動時に登録され、一度だけ読み込まれるコードです。フレームワークのヘルパーが認証と agent-chat を初期化します。任意のアプリ固有マイグレーションは、最初のリクエスト時にも実行中の可能性があります。詳細は [プラグイン](/docs/server-plugins) を参照してください。
- **ミドルウェア**: ルートに到達する前に、受信するすべてのリクエストに対して実行されるコードです。認証ガードは `server/middleware/` にあります。詳細は [ミドルウェア](/docs/server-middleware) を参照してください。

Nitro はデプロイ先にも依存しません。同じアプリを Node.js、Cloudflare Workers、Netlify、Vercel、その他のランタイムにコードの変更なしでデプロイできます。プリセットを設定するだけです。[デプロイ](/docs/deployment) を参照してください。

基盤となるリクエスト/レスポンス API は [H3](https://h3.unjs.io) です。カスタム ルートで `defineEventHandler`、`createError`、`getQuery` を見かけたら、それは H3 です。フレームワークが直接カバーしていない事柄については、[Nitro のドキュメント](https://nitro.build/guide) と [H3 のドキュメント](https://h3.unjs.io) がリファレンスになります。

## まず Actions をデフォルトにする {#actions-first}

Agent Native のアーキテクチャは従来とは異なります。アプリの新機能を考えるときは、まずそれが action にできないかを検討してください。たとえば、UI とエージェントの両方が何かを行う必要がある場合は、カスタム API ルートではなく action を定義します。actions は自動的に以下になります。

- エージェント ツール。
- 型付きのフロントエンド フック。
- `/_agent-native/actions/:name` 配下の HTTP エンドポイント。
- MCP および A2A から呼び出し可能なツール。
- 開発用の CLI コマンド。

ルート形式のプロトコルやバイナリ/ストリーミングの挙動が必要な場合にのみ、カスタム `/api/*` ルートを使用してください。詳細は [Actions](/docs/actions-overview) を参照してください。

## 次は何ですか {#whats-next}

- [**Actions**](/docs/actions-overview): デフォルトの操作サーフェス。適合しない場合にのみカスタム ルートに頼ってください。
- [**データベース**](/docs/server-database): カスタム ルートと actions の両方がインポートする `getDb()`/スキーマ パターン
- [**ミドルウェア**](/docs/server-middleware): 認証ガードと `server/middleware/` ディレクトリ
- [**プラグイン**](/docs/server-plugins): マイグレーション、認証、エージェントのための起動プラグイン
- [**ルート**](/docs/server-routes): ファイルベースのルート、リクエスト コンテキスト、SSR キャッチオール
