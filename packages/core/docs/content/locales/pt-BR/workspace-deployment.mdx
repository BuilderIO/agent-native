# Implantação de Espaço de Trabalho

Se o seu projeto for um [espaço de trabalho](/docs/multi-app-workspace) com mais de um app, você pode implantar todos os apps em uma única origem em vez de gerenciar implantações separadas por app. Esta página cobre o caminho gerenciado de um único comando e uma alternativa auto-hospedada com Docker Compose. Veja [Implantação](/docs/deployment) para escolher um banco de dados, um preset e uma plataforma primeiro.

## Uma Origem, Muitos Apps {#workspace-deploy}

Envie todos os apps de um espaço de trabalho para uma única origem com um comando:

```bash
npx @agent-native/core@latest deploy
# https://your-agents.com/mail/*       → apps/mail
# https://your-agents.com/calendar/*   → apps/calendar
# https://your-agents.com/forms/*      → apps/forms
```

**Mesma origem** significa que cada app parece fazer parte do mesmo site aos olhos do navegador. Isso te dá dois grandes benefícios de graça:

- **Sessão de login compartilhada**. Faça login em qualquer app, e todos os apps ficam logados.
- **A2A entre apps sem configuração**. Marcar `@calendar` a partir do mail é um fetch de mesma origem. Não há CORS nem assinatura JWT entre apps irmãos.

<Callout tone="info">

Por baixo dos panos, cada app é construído com seu próprio **caminho base**, um prefixo de URL como `/mail` definido via `APP_BASE_PATH`/`VITE_APP_BASE_PATH`, e então empacotado para o preset do Nitro alvo. O Cloudflare Pages roteia através de um **worker de despacho** gerado, um pequeno script em `dist/_worker.js` que lê o caminho recebido e encaminha a requisição para o app correspondente. O Netlify usa uma função por app mais redirecionamentos gerados. O Vercel grava um `.vercel/output` de nível de espaço de trabalho usando a Build Output API.

</Callout>

<Callout tone="warning">

Builds de espaço de trabalho hospedado exigem `A2A_SECRET` no ambiente do provedor de implantação. Sem ele, Slack, webhooks de entrada e a retomada de A2A entre apps não funcionam, já que todos passam por processadores em segundo plano assinados. As verificações locais de artefato com `--build-only` continuam rodando sem ele.

</Callout>

<Callout tone="info">

Está configurando um comando de build de provedor em vez de implantar manualmente? Adicione `--build-only` ao mesmo comando, por exemplo `npx @agent-native/core@latest deploy --preset vercel --build-only`. Isso grava a saída diretamente, então nenhum `vercel.json` é necessário para o roteamento do espaço de trabalho.

Prefere um domínio separado por app em vez de uma origem compartilhada? Todo app no espaço de trabalho ainda pode ser implantado de forma independente. Execute `cd apps/<name> && npx @agent-native/core@latest build` como um scaffold independente.

</Callout>

## Espaço de Trabalho Auto-hospedado com Docker Compose {#workspace-docker-compose}

Hoje, um espaço de trabalho não é um único processo de servidor Nitro. Cada app ainda compila para seu próprio diretório `.output/` e roda seu próprio servidor Node/Nitro, então auto-hospedar um espaço de trabalho significa rodar vários servidores atrás de um único ponto de entrada.

Um **proxy reverso** é esse ponto de entrada único na imagem acima: ele recebe cada requisição e a encaminha para o container certo com base no caminho da URL, o mesmo trabalho que o worker de despacho do Cloudflare faz em uma implantação gerenciada. Em uma VPS, isso significa um container por app do espaço de trabalho, todos apontando para o mesmo banco de dados Postgres e os mesmos segredos de produção compartilhados, com o proxy na frente.

<Steps>

### Compile cada app com um caminho base correspondente

O caminho base é uma entrada em tempo de build para o bundle do cliente e uma entrada em tempo de execução para o servidor. Compile cada app com o mesmo caminho para o qual o proxy vai rotear:

```bash maxLines=8
APP_BASE_PATH=/mail VITE_APP_BASE_PATH=/mail npx @agent-native/core@latest build
node .output/server/index.mjs
```

### Escreva um Dockerfile reutilizável

Receba o nome do app e o prefixo de caminho como argumentos de build, para que um único Dockerfile sirva todos os apps do espaço de trabalho:

```dockerfile filename="Dockerfile.workspace-app" maxLines=12
FROM node:24-slim AS build
WORKDIR /workspace
RUN corepack enable
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY packages ./packages
COPY apps ./apps
ARG APP_NAME
ARG APP_BASE_PATH
ENV APP_BASE_PATH=$APP_BASE_PATH
ENV VITE_APP_BASE_PATH=$APP_BASE_PATH
RUN pnpm install --frozen-lockfile
RUN pnpm --dir apps/$APP_NAME build

FROM node:24-slim
WORKDIR /app
ARG APP_NAME
ARG APP_BASE_PATH
ENV NODE_ENV=production
ENV PORT=3000
ENV APP_BASE_PATH=$APP_BASE_PATH
COPY --from=build /workspace/apps/$APP_NAME/.output .output
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

### Componha o Postgres, os apps e o proxy

Este exemplo usa o Caddy porque ele pode terminar HTTP localmente ou ficar atrás do proxy SSL do Cloudflare, mas a parte importante é o roteamento por prefixo de caminho:

```yaml filename="docker-compose.yml" maxLines=30
services:
  postgres:
    image: postgres:17
    restart: unless-stopped
    environment:
      POSTGRES_DB: agent_native
      POSTGRES_USER: agent_native
      POSTGRES_PASSWORD: change-me
    volumes:
      - postgres-data:/var/lib/postgresql/data

  mail:
    build:
      context: .
      dockerfile: Dockerfile.workspace-app
      args:
        APP_NAME: mail
        APP_BASE_PATH: /mail
    restart: unless-stopped
    environment:
      DATABASE_URL: postgres://agent_native:change-me@postgres:5432/agent_native
      BETTER_AUTH_URL: https://agents.example.com/mail
      BETTER_AUTH_SECRET: ${BETTER_AUTH_SECRET}
      A2A_SECRET: ${A2A_SECRET}
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
    depends_on:
      - postgres

  calendar:
    build:
      context: .
      dockerfile: Dockerfile.workspace-app
      args:
        APP_NAME: calendar
        APP_BASE_PATH: /calendar
    restart: unless-stopped
    environment:
      DATABASE_URL: postgres://agent_native:change-me@postgres:5432/agent_native
      BETTER_AUTH_URL: https://agents.example.com/calendar
      BETTER_AUTH_SECRET: ${BETTER_AUTH_SECRET}
      A2A_SECRET: ${A2A_SECRET}
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
    depends_on:
      - postgres

  proxy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
    depends_on:
      - mail
      - calendar

volumes:
  postgres-data:
```

### Configure o proxy

```caddyfile filename="Caddyfile"
agents.example.com {
  reverse_proxy /mail* mail:3000
  reverse_proxy /calendar* calendar:3000
}
```

</Steps>

<Callout tone="info">

- Mantenha `DATABASE_URL`, `BETTER_AUTH_SECRET`, `A2A_SECRET` e outros
  segredos de produção idênticos entre os containers dos apps quando você
  quiser autenticação compartilhada, credenciais compartilhadas e A2A entre
  apps.
- Defina `BETTER_AUTH_URL` como a URL pública para aquele caminho de app. As
  URLs de callback do OAuth devem usar a mesma URL pública.
- Não confie no sistema de arquivos do container para dados de produção. Use
  Postgres (ou outro back-end SQL persistente) para `DATABASE_URL`.
- Se o Cloudflare terminar o TLS na frente da VPS, configure o Cloudflare para
  enviar os headers normais `X-Forwarded-Proto` / `X-Forwarded-Host` e rotear
  o host público para o container do proxy.

</Callout>
