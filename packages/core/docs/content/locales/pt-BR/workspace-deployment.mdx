# Implantação de Espaço de Trabalho

Se o seu projeto for um [espaço de trabalho](/docs/multi-app-workspace) com mais de um app, você pode implantar todos os apps em uma única origem em vez de gerenciar implantações separadas por app. Esta página cobre o caminho gerenciado de um único comando e uma alternativa auto-hospedada com Docker Compose. Veja [Implantação](/docs/deployment) para escolher um banco de dados, um preset e uma plataforma primeiro.

## Uma Origem, Muitos Apps {#workspace-deploy}

Envie todos os apps de um espaço de trabalho para uma única origem com um comando:

```bash
npx @agent-native/core@latest deploy
# https://your-agents.com/mail/*       → apps/mail
# https://your-agents.com/calendar/*   → apps/calendar
# https://your-agents.com/forms/*      → apps/forms
```

**Mesma origem** significa que cada app parece fazer parte do mesmo site aos olhos do navegador. Isso te dá dois grandes benefícios de graça:

- **Sessão de login compartilhada**. Faça login em qualquer app, e todos os apps ficam logados.
- **A2A entre apps sem configuração**. Marcar `@calendar` a partir do mail é um fetch de mesma origem. Não há CORS nem assinatura JWT entre apps irmãos.

<Callout tone="info">

Por baixo dos panos, cada app é construído com seu próprio **caminho base**, um prefixo de URL como `/mail` definido via `APP_BASE_PATH`/`VITE_APP_BASE_PATH`, e então empacotado para o preset do Nitro alvo. **Netlify** é o padrão: uma função por app mais redirecionamentos gerados. **Vercel** grava um `.vercel/output` de nível de espaço de trabalho usando a Build Output API.

</Callout>

Publique o build para sua plataforma:

<Callout tone="warning">

Builds de espaço de trabalho hospedado exigem `A2A_SECRET` no ambiente do provedor de implantação. Sem ele, Slack, webhooks de entrada e a retomada de A2A entre apps não funcionam, já que todos passam por processadores em segundo plano assinados. As verificações locais de artefato com `--build-only` continuam rodando sem ele.

</Callout>

<Callout tone="info">

Está configurando um comando de build de provedor em vez de implantar manualmente? Adicione `--build-only` ao mesmo comando, por exemplo `npx @agent-native/core@latest deploy --preset vercel --build-only`. Isso grava a saída diretamente, então nenhum `vercel.json` é necessário para o roteamento do espaço de trabalho.

Prefere um domínio separado por app em vez de uma origem compartilhada? Todo app no espaço de trabalho ainda pode ser implantado de forma independente. Execute `cd apps/<name> && pnpm build` como um scaffold independente.

</Callout>

## Cache de Build {#workspace-build-cache}

Uma implantação de espaço de trabalho faz o build de todos os apps, e isso é a maior parte do seu tempo. O cache de build ignora um app cujas entradas não mudaram e, em vez disso, restaura a saída de build anterior dele, incluindo o bundle da função. Ele vem ativado por padrão e mantém as entradas em `node_modules/.cache/agent-native/deploy-build`.

A chave de cache de um app é um SHA-256 calculado sobre:

- os arquivos-fonte do app, conforme listados por `git ls-files` (rastreados e não rastreados, não ignorados), mais seus arquivos `.env*`; os diretórios que um build gera no app (`.agent-native`, `.deploy-tmp`, `.react-router`) ficam de fora
- o conteúdo compilado de cada pacote do espaço de trabalho de que ele depende, de modo que um `@agent-native/core` reconstruído invalida todos os apps (apenas os arquivos que o pacote publica por meio do campo `files`, e um pacote com `dist` é calculado pelo seu `dist`, não pelo seu `src`)
- os arquivos da raiz do espaço de trabalho, incluindo `pnpm-lock.yaml`
- a versão principal do Node, o preset e a versão do Core
- o nome e o valor de cada variável de ambiente passada ao build, com hash e nunca impressos

Cada app registra um acerto ou uma falha. Uma falha informa o motivo e, quando existe uma entrada anterior, quais entradas mudaram. Uma implantação concluída imprime os totais e o tempo economizado.

```bash
[workspace-deploy] cache HIT analytics (restored in 5.9s, saved ~43.8s)
[workspace-deploy] cache MISS forms (no-entry: inputs changed: source); building
[workspace-deploy] Build cache: 1 hit, 1 miss; build phase 32.3s, ~43.4s saved
```

Um problema de cache nunca é um acerto. Um manifesto ilegível (`entry-unreadable`), uma restauração cujos arquivos não correspondem à entrada (`restore-failed`) ou uma entrada que não pode ser calculada por hash (`hash-failed`, por exemplo um espaço de trabalho que não é um repositório git) registra o motivo e refaz o build do app. Uma entrada ruim é excluída.

| Configuração               | Variável de ambiente                   | Padrão                                          |
| -------------------------- | -------------------------------------- | ----------------------------------------------- |
| `deployCache.enabled`      | `AGENT_NATIVE_DEPLOY_CACHE`            | `true`                                          |
| `deployCache.dir`          | `AGENT_NATIVE_DEPLOY_CACHE_DIR`        | `node_modules/.cache/agent-native/deploy-build` |
| `deployCache.verifySample` | `AGENT_NATIVE_DEPLOY_CACHE_VERIFY`     | `0`                                             |
| `deployCache.envIgnore`    | `AGENT_NATIVE_DEPLOY_CACHE_ENV_IGNORE` | nenhum                                          |

Defina `AGENT_NATIVE_DEPLOY_CACHE_VERIFY=2` para refazer o build de dois apps em cache por implantação e comparar a saída reconstruída com a saída em cache arquivo por arquivo, mascarando valores específicos de cada build, como o carimbo de data e hora do build e os tokens de função recém-gerados. Uma diferença faz a implantação falhar e lista os arquivos, o que significa que o build não é reproduzível ou que falta uma entrada na chave. Execute isso no CI de forma agendada, em vez de a cada implantação.

As variáveis que mudam a cada execução sem chegar ao build, como `PATH`, `PWD`, `npm_*` e `PNPM_*`, já ficam fora da chave. Se um ambiente de implantação adicionar as suas (um id de execução, por exemplo), liste-a em `AGENT_NATIVE_DEPLOY_CACHE_ENV_IGNORE`; um `*` no final corresponde a um prefixo. Todo o resto conta, então um `VITE_*` ou `DATABASE_URL` alterado refaz o build de todos os apps.

Builders hospedados que começam com um disco limpo a cada vez não ganham nada com o cache. Defina `AGENT_NATIVE_DEPLOY_CACHE=false` neles para pular a cópia que o cache faz após cada build.

## Espaço de Trabalho Auto-hospedado com Docker Compose {#workspace-docker-compose}

Hoje, um espaço de trabalho não é um único processo de servidor Nitro. Cada app ainda compila para seu próprio diretório `.output/` e roda seu próprio servidor Node/Nitro, então auto-hospedar um espaço de trabalho significa rodar vários servidores atrás de um único ponto de entrada.

Um **proxy reverso** é esse ponto de entrada único na imagem acima: ele recebe cada requisição e a encaminha para o container certo com base no caminho da URL, o mesmo trabalho que o worker de despacho do Cloudflare faz em uma implantação gerenciada. Em uma VPS, isso significa um container por app do espaço de trabalho, todos apontando para o mesmo banco de dados Postgres e os mesmos segredos de produção compartilhados, com o proxy na frente.

<Steps>

### Compile cada app com um caminho base correspondente

O caminho base é uma entrada em tempo de build para o bundle do cliente e uma entrada em tempo de execução para o servidor. Compile cada app com o mesmo caminho para o qual o proxy vai rotear:

```bash maxLines=8
APP_BASE_PATH=/mail VITE_APP_BASE_PATH=/mail pnpm build
node .output/server/index.mjs
```

### Escreva um Dockerfile reutilizável

Receba o nome do app e o prefixo de caminho como argumentos de build, para que um único Dockerfile sirva todos os apps do espaço de trabalho:

```dockerfile filename="Dockerfile.workspace-app" maxLines=12
FROM node:24-slim AS build
WORKDIR /workspace
RUN corepack enable
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY packages ./packages
COPY apps ./apps
ARG APP_NAME
ARG APP_BASE_PATH
ENV APP_BASE_PATH=$APP_BASE_PATH
ENV VITE_APP_BASE_PATH=$APP_BASE_PATH
RUN pnpm install --frozen-lockfile
RUN pnpm --dir apps/$APP_NAME build

FROM node:24-slim
WORKDIR /app
ARG APP_NAME
ARG APP_BASE_PATH
ENV NODE_ENV=production
ENV PORT=3000
ENV APP_BASE_PATH=$APP_BASE_PATH
COPY --from=build /workspace/apps/$APP_NAME/.output .output
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

### Componha o Postgres, os apps e o proxy

Este exemplo usa o Caddy porque ele pode terminar HTTP localmente ou ficar atrás do proxy SSL do Cloudflare, mas a parte importante é o roteamento por prefixo de caminho:

```yaml filename="docker-compose.yml" maxLines=30
services:
  postgres:
    image: postgres:17
    restart: unless-stopped
    environment:
      POSTGRES_DB: agent_native
      POSTGRES_USER: agent_native
      POSTGRES_PASSWORD: change-me
    volumes:
      - postgres-data:/var/lib/postgresql/data

  mail:
    build:
      context: .
      dockerfile: Dockerfile.workspace-app
      args:
        APP_NAME: mail
        APP_BASE_PATH: /mail
    restart: unless-stopped
    environment:
      DATABASE_URL: postgres://agent_native:change-me@postgres:5432/agent_native
      BETTER_AUTH_URL: https://agents.example.com/mail
      BETTER_AUTH_SECRET: ${BETTER_AUTH_SECRET}
      A2A_SECRET: ${A2A_SECRET}
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
    depends_on:
      - postgres

  calendar:
    build:
      context: .
      dockerfile: Dockerfile.workspace-app
      args:
        APP_NAME: calendar
        APP_BASE_PATH: /calendar
    restart: unless-stopped
    environment:
      DATABASE_URL: postgres://agent_native:change-me@postgres:5432/agent_native
      BETTER_AUTH_URL: https://agents.example.com/calendar
      BETTER_AUTH_SECRET: ${BETTER_AUTH_SECRET}
      A2A_SECRET: ${A2A_SECRET}
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
    depends_on:
      - postgres

  proxy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
    depends_on:
      - mail
      - calendar

volumes:
  postgres-data:
```

### Configure o proxy

```caddyfile filename="Caddyfile"
agents.example.com {
  reverse_proxy /mail* mail:3000
  reverse_proxy /calendar* calendar:3000
}
```

</Steps>

<Callout tone="info">

- Mantenha `DATABASE_URL`, `BETTER_AUTH_SECRET`, `A2A_SECRET` e outros
  segredos de produção idênticos entre os containers dos apps quando você
  quiser autenticação compartilhada, credenciais compartilhadas e A2A entre
  apps.
- Defina `BETTER_AUTH_URL` como a URL pública para aquele caminho de app. As
  URLs de callback do OAuth devem usar a mesma URL pública.
- Não confie no sistema de arquivos do container para dados de produção. Use
  PostgreSQL para `DATABASE_URL`.
- Se o Cloudflare terminar o TLS na frente da VPS, configure o Cloudflare para
  enviar os headers normais `X-Forwarded-Proto` / `X-Forwarded-Host` e rotear
  o host público para o container do proxy.

</Callout>

## Configurar o Dispatch para um espaço de trabalho auto-hospedado {#dispatch-workspace-apps}

As imagens de produção do Dispatch geralmente contêm apenas `.output/`, então o servidor não consegue descobrir os diretórios dos apps durante a execução. Configure este manifesto no serviço do Dispatch. Use o mesmo JSON nas duas variáveis: a variável Vite é lida ao compilar o Dispatch e a outra durante a execução do servidor. Liste apenas os apps deste espaço de trabalho. Cada `path` deve corresponder a `APP_BASE_PATH` e à rota do proxy. Defina também APP_URL como a origem pública servida pelo proxy reverso.

```env
AGENT_NATIVE_WORKSPACE_APPS_JSON=[{"id":"dispatch","name":"Dispatch","path":"/dispatch"},{"id":"reports","name":"Reports","path":"/reports"}]
VITE_AGENT_NATIVE_WORKSPACE_APPS_JSON=[{"id":"dispatch","name":"Dispatch","path":"/dispatch"},{"id":"reports","name":"Reports","path":"/reports"}]
APP_URL=https://workspace.example.com
```

## Ativar convites em um novo espaço de trabalho {#workspace-invites}

Se o cadastro exigir convite, configure estas variáveis de acesso em cada contêiner de app que compartilha o banco de dados e a autenticação:

```env
AUTH_SIGNUP=invited
ORG_CREATION=closed
AUTO_CREATE_DEFAULT_ORG=0
AUTH_BOOTSTRAP_ADMINS=admin@example.com
AUTH_REQUIRE_EMAIL_VERIFICATION=1
```

Substitua o endereço de exemplo pelo e-mail verificado da primeira pessoa administradora de cada espaço de trabalho. Em um banco vazio, ela entra primeiro, torna-se proprietária da organização inicial e pode convidar a equipe em Settings → Organization → Members. Consulte [Implantações administradas](/docs/administered-deployments) para ver o processo completo de inicialização.
