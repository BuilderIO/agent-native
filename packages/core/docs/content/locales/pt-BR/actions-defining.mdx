# Definindo Actions

Toda action começa com uma chamada a `defineAction()`. Ela reúne uma description para o agente, um schema que valida a entrada, e uma função `run` que faz o trabalho, para que a UI e o agente chamem exatamente o mesmo código.

## Opções de schema {#schemas}

`schema` aceita qualquer biblioteca compatível com [Standard Schema](https://standardschema.dev):

- **Zod** (v4): a escolha mais comum, com a melhor inferência de tipos e conversão automática para JSON Schema.
- **Valibot**: uma boa escolha quando o tamanho do bundle importa.
- **ArkType**: uma boa escolha se você preferir sua sintaxe.

O schema faz dois trabalhos. Ele se converte em JSON Schema para a definição de ferramenta da Claude API, e valida a entrada em tempo de execução antes de `run()` disparar. Entradas inválidas nunca chegam ao seu handler.

## Validando o valor de retorno {#output-schema}

`schema` valida _entradas_. Para também validar o que uma action **retorna**, passe um `outputSchema` (qualquer schema compatível com Standard Schema: Zod, Valibot, ArkType, a mesma superfície de `schema`). O framework valida a entrada antes de `run()` e valida o resultado depois que `run()` resolve.

```ts
export default defineAction({
  description: "Summarize a thread.",
  schema: z.object({ threadId: z.string() }),
  outputSchema: z.object({
    summary: z.string(),
    messageCount: z.number(),
  }),
  outputErrorStrategy: "warn", // default
  run: async ({ threadId }) => {
    /* ...returns { summary, messageCount } ... */
  },
});
```

`outputErrorStrategy` controla o que acontece em uma incompatibilidade:

| Estratégia   | Comportamento na incompatibilidade                                                                                       |
| ------------ | ------------------------------------------------------------------------------------------------------------------------ |
| `"warn"`     | **Padrão.** Executa `console.warn` com os problemas e retorna o resultado **original** sem alterações. Não é disruptivo. |
| `"strict"`   | Lança um erro claro, para que um bug na action seja fácil de perceber.                                                   |
| `"fallback"` | Retorna o valor `outputFallback` fornecido no lugar do resultado inválido.                                               |

Quando `run()` tem sucesso, o framework retorna o valor validado, então quaisquer defaults ou coerções em `outputSchema` entram em vigor, da mesma forma que acontece para a entrada. Quando você não passa um `outputSchema`, o valor de retorno permanece inalterado.

## Configuração de HTTP {#http}

Por padrão, toda action é exposta como `POST /_agent-native/actions/<name>`. Sobrescreva com a opção `http`:

```ts
export default defineAction({
  description: "Get details for a lead.",
  schema: z.object({ leadId: z.string() }),
  http: { method: "GET" },
  run: async ({ leadId }) => {
    return await db.select().from(leads).where(eq(leads.id, leadId));
  },
});
```

Para uma action `GET`, `leadId` é passado como um query param: `/_agent-native/actions/get-lead?leadId=abc`.

- **`http: { method: "GET" | "POST" | "PUT" | "DELETE" }`**: o padrão é `POST`. Actions `GET` são automaticamente marcadas como `readOnly`, então uma chamada bem-sucedida não dispara uma atualização por polling da UI.
- **`http: { path: "..." }`**: sobrescreve a URL montada sob `/_agent-native/actions/`. O padrão é o nome do arquivo. Esse override só muda a URL para chamadores HTTP diretos. `useActionQuery()`, `useActionMutation()` e `callAction()` sempre chamam `/_agent-native/actions/<name>`, independentemente desse override, então sobrescrever o path faz esses ganchos retornarem 404. Use um override de path apenas para chamadores HTTP externos. Note também que segmentos de rota `:param` no path sobrescrito não são parseados para os args de `run()`. Apenas query-string params e campos do corpo JSON são.
- **`http: false`**: desativa completamente o endpoint HTTP. Apenas o agente e a CLI podem chamar a action.
- **`readOnly: true`**: pula explicitamente a atualização por polling, mesmo para actions `POST` que não mutam nada. Isso não é controle de acesso. Não restringe quem pode chamar a action, e não afeta `useActionQuery()`, `useActionMutation()` ou qualquer gancho de cliente. Seus únicos efeitos são suprimir o evento de atualização pós-chamada e tirar a action da auditoria de escrita. Para ocultar uma action do modelo, use `agentTool: false`. Para restringir quem pode chamá-la, use as opções de auth e acesso em [Acesso e Autorização](/docs/actions-access-control).
- **`parallelSafe: true`**: permite que uma action de mutação rode ao mesmo tempo que outras chamadas de ferramenta no mesmo turno. Só defina isso quando a action for segura para rodar de forma concorrente e não depender de ordem. Actions de mutação são serializadas por padrão.

## Falhar uma action {#failing}

Uma action sinaliza falha lançando. Retornar `{ error: "..." }` parece sucesso para todas as partes do framework, então os disjuntores de retentativa do agente nunca contam isso e a chamada é registrada como um efeito colateral concluído.

O que você lança decide quanto da mensagem sobrevive. `fail()` lança um `ActionContractError`, e esse tipo é a única razão pela qual o texto chega a quem chamou. Um simples `throw new Error("No such email")` é indistinguível de uma falha do Postgres ou de um serviço externo, então a rota de action o substitui por um 500 genérico `"Internal server error"`, mantém a mensagem real no log do servidor e a reporta ao rastreamento de erros. Guarde o throw puro para falhas internas de verdade. É para isso que o 500 serve.

`fail()` aceita uma mensagem e um objeto de opções:

- **message**: o texto que quem chamou lê. Escreva para uma pessoa, não para um log.
- **options.errorCode**: um código estável e legível por máquina. Padrão: `"action_failed"`.
- **options.statusCode**: o status HTTP da rota de action. Padrão: `400`.
- **options.details**: contexto estruturado e seguro para quem chamou. Nunca coloque segredos ou saída bruta de driver aqui.

A chamada mais simples precisa apenas de uma mensagem:

```ts
import { defineAction, fail } from "@agent-native/core/action";
import { eq } from "drizzle-orm";
import { z } from "zod";

import { getDb, schema } from "../server/db/index.js";

export default defineAction({
  description: "Reply to an email thread in the user's voice.",
  schema: z.object({
    emailId: z.string().describe("The id of the email to reply to."),
    body: z.string().describe("The reply body, in markdown."),
  }),
  run: async ({ emailId, body }) => {
    const db = getDb();
    const [email] = await db
      .select()
      .from(schema.emails)
      .where(eq(schema.emails.id, emailId));
    if (!email) fail("That email is no longer in the mailbox.");
    await db.insert(schema.replies).values({ emailId, body });
    return { ok: true, emailId };
  },
});
```

Nomear a causa é o que permite à UI reagir a uma falha em vez de apenas exibi-la. O código e o status sobrevivem ao transporte:

```ts
if (!email) {
  fail("That email is no longer in the mailbox.", {
    errorCode: "email_not_found",
    statusCode: 404,
  });
}
```

O navegador recebe `{ error, errorCode, details }`. `useActionQuery()`, `useActionMutation()` e `callAction()` expõem isso como um `Error` carregando `status`, `errorCode` e `details`.

### O que cada lançamento produz {#failure-shapes}

| Lançado de `run()` | Status HTTP | Corpo da resposta | Reportado ao rastreamento de erros |
| --- | --- | --- | --- |
| `fail(msg)` | 400 | `{ error: msg, errorCode: "action_failed" }` | Não |
| `fail(msg, { errorCode, statusCode, details })` | seu `statusCode` | `{ error, errorCode, details }` | Não |
| `new ActionContractError(msg, { errorCode })` | 409 | `{ error, errorCode, details }` | Não |
| `new AgentActionStopError(msg)` | 500 | `{ error: msg }` | Não |
| `new Error(msg)` | 500 | `{ error: "Internal server error" }` | Sim |
| Entrada que falha no `schema` | 400 | `{ error: "Invalid action parameters..." }` | Não |

`AgentActionStopError` é a que se lança quando o agente deve encerrar o turno em vez de ler a falha e tentar de novo. `ActionContractError` é o que `fail()` lança por você, então use-a diretamente apenas quando 409 for o status desejado.

### Escolha um status sobre o qual a política de retentativa possa agir {#failure-status}

`useActionQuery()` repete `429`, `502`, `503` e `504`, até três vezes, esperando 500 ms, depois 1 s, depois 2 s. Qualquer outro status é tratado como determinístico e aparece na primeira resposta. Reenviar uma requisição recusada por estar errada só compra a mesma recusa de novo. `useActionMutation()` não repete de forma alguma.

Então o status não é cosmético. Uma recusa enviada como `404` custa uma ida e volta. A mesma recusa enviada como `500`, ou lançada pura, custa quatro idas e voltas e quatro relatórios de erro duplicados.

Chamadores do agente não veem nada disso. O agente executa `run()` em processo, então recebe a mensagem lançada diretamente, seja qual for o tipo, e seus próprios disjuntores de erro repetido limitam quantas vezes ele tenta de novo.

## Mantenha a superfície de actions pequena {#small-surface}

Toda action que o agente pode ver ocupa um slot na lista de ferramentas do modelo, e uma lista longa e sobreposta dificulta para o modelo escolher a ferramenta certa. Projete a superfície de actions como uma API que você mantém, não uma action por botão na UI:

- Prefira **uma única action `update` no estilo CRUD** que receba um patch de campos opcionais, em vez de muitas actions por campo como `update-name`, `update-order` e `update-color`. O chamador só envia os campos que mudaram.
- Antes de adicionar uma nova action de leitura para cada consulta ou filtro, considere primeiro uma opção mais geral: o [trio de API de provedor](/docs/template-dispatch-vault-integrations#provider-api) (`provider-api-catalog`, `provider-api-docs` e `provider-api-request`) para dados de provedor, ou a ferramenta dev `db-query` para dados do app.
- Marque actions apenas de UI ou programáticas como [`agentTool: false`](/docs/actions-access-control#agent-tool). Elas continuam chamáveis a partir do frontend ou por HTTP, sem ocupar um slot na lista de ferramentas do modelo.
- Marque com `deferLoading: false` o punhado de actions que o agente usa o tempo todo. São esses os schemas enviados na primeira requisição ao modelo; todo o resto carrega sob demanda pelo `tool-search` quando o agente precisa. Assim que uma action se exclui desse jeito, todas as não marcadas passam a ser adiadas, então marque o conjunto inicial inteiro de uma vez em vez de uma action por vez. Isso é sobre quanto custa o primeiro turno, não sobre acesso: uma action adiada é chamável assim que o `tool-search` a retorna. É a forma por action do array `initialToolNames` do plugin, e um app pode usar qualquer uma das duas.
- Exclua ou oculte actions que a UI não usa mais, em vez de deixá-las expostas ao modelo.

O repositório inclui um helper consultivo, `node scripts/audit-template-actions.mjs [template ...]` (alias `pnpm actions:audit`). Ele varre a pasta `actions/` de um template e sinaliza actions que a UI pode não estar mais usando, além de grupos de actions por campo que poderiam ser combinadas em uma só. Ele sempre sai com código 0 e nunca falha o CI, e suas heurísticas são conservadoras, então trate a saída dele como uma sugestão, não um erro.
