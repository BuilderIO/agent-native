# Visão geral

Actions são a única fonte de verdade para tudo que seu app faz. Defina uma com `defineAction()` e coloque-a em `actions/`. Toda superfície abaixo a capta automaticamente. Você escreve a lógica uma vez. Nenhuma superfície ganha sua própria cópia, e nenhuma pode ficar dessincronizada das outras.

<Cards columns={2}>

### :robot: [Ferramenta do Agente](/docs/agent-surfaces)

O agente lê a description e o schema como uma ferramenta chamável. Peça por ela no chat, como "responda a este ticket" ou "resuma esta thread".

### :components: [Ganchos de UI](/docs/client-data)

`useActionQuery()`, `useActionMutation()` e `callAction()` chamam a mesma action a partir do React. Um clique e uma mensagem de chat executam exatamente a mesma operação.

### :server: [Transporte do Framework](/docs/http-api)

Auto-montado em `/_agent-native/actions/<name>` na inicialização. Os ganchos de UI chamam essa rota por baixo dos panos, e um cliente HTTP externo também pode chamá-la diretamente.

### :plug: [Ferramenta MCP](/docs/actions-other-surfaces#mcp)

Aparece como uma ferramenta para qualquer host MCP: Claude, Claude Desktop, Cursor, Codex. Use-a quando um cliente de IA diferente precisar conduzir seu app.

### :network: [Ferramenta A2A](/docs/actions-other-surfaces#a2a)

Outros apps nativos do agente descobrem e chamam essa ferramenta via A2A. Use-a quando um segundo app no seu espaço de trabalho precisar que este atue em seu nome.

### :terminal: [Comando CLI](/docs/actions-other-surfaces#cli)

`pnpm action <name>` a executa a partir de um terminal. Use-a para scripts, cron jobs e testes manuais rápidos.

</Cards>

A maioria dos apps constrói uma camada de API separada entre o frontend e o banco de dados, uma que só o navegador pode chamar. Um agente que quer a mesma capacidade precisa de sua própria integração separada, escrita e mantida de novo. Apps nativos do agente pulam essa divisão. A UI e o agente chamam exatamente a mesma action, então há apenas uma implementação para escrever, e apenas um lugar onde um bug pode se esconder.

Se a UI e o agente precisam fazer a mesma coisa, use uma action em vez de uma rota personalizada. Para o caso raro em que um protocolo no formato de rota é a escolha certa, visite [Prefira Actions para Operações do App](/docs/server-overview#actions-first).

## Onde as Actions se encaixam {#role}

`app/` (veja [Visão geral](/docs/client-overview#role)) e o agente resolvem ambos para as mesmas actions e o mesmo banco de dados SQL. Não existe um "backend do app" separado com o qual esta camada conversa e que o agente não possa também alcançar. Construir um recurso significa definir uma operação aqui e ganhar uma UI, uma ferramenta do agente e toda outra superfície para ela ao mesmo tempo.

`actions/` em si é uma pasta plana. Cada arquivo é uma action: uma chamada `defineAction()` exportada como o export padrão do arquivo. O framework varre essa pasta na inicialização e monta cada arquivo que encontra. Não há etapa de registro nem arquivo de índice para manter atualizado.

O corpo `run()` de uma action é código de servidor comum, então costuma acessar mais algumas pastas:

Nada fora de `actions/` deve importar a função `run` de uma action diretamente. Em vez disso, chame-a por uma das superfícies acima: a ferramenta do agente, um gancho de UI, HTTP, MCP, A2A ou a CLI. Todos esses caminhos executam a mesma validação de schema, as mesmas verificações de acesso e a mesma trilha de auditoria.

## Comece com uma action {#hello-action}

A primeira operação em um app chat-first pode ser mínima. No template Chat,
substitua `actions/hello.ts` ou adicione um novo arquivo ao lado dele:

```ts
// actions/hello.ts
import { defineAction } from "@agent-native/core/action";
import { z } from "zod";

export default defineAction({
  description: "Say hello from the local agent.",
  schema: z.object({
    name: z.string().default("world"),
  }),
  http: { method: "GET" },
  readOnly: true,
  run: async ({ name }) => {
    return { message: `Hello, ${name}!` };
  },
});
```

Execute-a a partir da mesma pasta:

```bash
pnpm action hello '{"name":"Steve"}'
```

A CLI aceita um objeto JSON como entrada da action, o que corresponde às
chamadas de ferramenta estruturadas que os agentes já fazem. Flags simples
também continuam funcionando para execuções manuais rápidas:

```bash
pnpm action hello --name Steve
```

Depois, execute o loop app-agente contra a pasta:

```bash
npx agent-native agent "Call hello for Steve and explain the result"
```

Esse é o mesmo loop app-agente que seus jobs agendados, a UI de chat,
ferramentas MCP externas e telas futuras vão usar. Templates de chat e de
domínio servem para adicionar UI ao redor das actions, não são um
pré-requisito obrigatório para a action em si.
