# Implantação

Apps nativos do agente usam [Nitro](https://nitro.build) por baixo dos panos. Isso significa que você pode implantar em qualquer plataforma sem nenhuma alteração de configuração. Basta definir um preset.

## Antes de Implantar: Escolha um Banco de Dados Persistente {#persistent-database}

Um banco de dados **persistente** é aquele cujos dados sobrevivem a reinicializações, reimplantações e à execução em mais de uma instância de servidor ao mesmo tempo. É isso que todo app implantado precisa.

<Comparison>

### Antes

O desenvolvimento local recorre a um arquivo SQLite em `data/app.db`. Isso é conveniente na sua máquina, mas o arquivo vive no sistema de arquivos local, que contêineres, previews e plataformas serverless podem redefinir a qualquer momento.

### Depois

A produção precisa de um banco de dados persistente, como Postgres ou Turso/libSQL, que sobreviva a reinicializações, reimplantações e à execução em mais de uma instância ao mesmo tempo.

</Comparison>

Conectar um leva três passos:

<Steps>

### Escolha um provedor

Qualquer host compatível com Postgres (Neon, Supabase, Railway, RDS e similares) ou um banco de dados libSQL/Turso funciona. O agent-native lê e grava através do [Drizzle](https://orm.drizzle.team), uma biblioteca TypeScript que transforma seu schema em consultas type-safe em vez de SQL escrito à mão, de modo que o mesmo código do app roda em qualquer um deles.

### Obtenha uma string de conexão

Seu provedor fornece uma URL que identifica o banco de dados e como alcançá-lo, por exemplo `postgres://user:pass@host:5432/dbname`.

### Defina `DATABASE_URL`

Defina-a nas variáveis de ambiente do seu provedor de implantação antes da sua primeira implantação em produção. O agent-native lê a URL e detecta automaticamente qual **dialeto** (qual motor de banco de dados subjacente, Postgres versus SQLite/libSQL) usar. Veja [Banco de dados](/docs/server-database#production) para a lista completa de adaptadores.

</Steps>

<Callout tone="info">

Está usando Turso ou outro provedor libSQL que autentica com um token separado? Defina `DATABASE_AUTH_TOKEN` junto com `DATABASE_URL`. Está construindo um [espaço de trabalho](/docs/multi-app-workspace) com mais de um app? Todo app herda o `DATABASE_URL` raiz por padrão. Defina `<APP_NAME>_DATABASE_URL` somente para o único app que precisa de um banco de dados diferente.

</Callout>

### Configuração automática de schema {#skip-ensure-tables}

Você não precisa de uma etapa de migração separada para começar. Na primeira vez que qualquer parte do seu app toca o banco de dados, o agent-native verifica se as tabelas, colunas e índices de que precisa já existem, e cria o que estiver faltando. Isso acontece uma vez por inicialização do servidor e é invisível no uso normal.

Concretamente, cada armazenamento de dados chama uma função interna `ensureTable()` na primeira vez que é usado. Essa função verifica o catálogo próprio do banco de dados (o `information_schema` do Postgres, por exemplo) e só emite `CREATE TABLE`, `ADD COLUMN` ou `CREATE INDEX` para o que estiver genuinamente faltando. Essas são instruções **DDL**, abreviação de Data Definition Language, a parte do SQL que molda as tabelas em vez de ler ou gravar as linhas dentro delas.

### Reduzindo a latência de cold start em serverless {#reducing-cold-start}

Em um servidor de longa duração, essa verificação roda uma vez por inicialização e você provavelmente nunca a percebe. Plataformas serverless funcionam de forma diferente. Um **cold start** é quando a plataforma inicia uma instância totalmente nova do seu servidor para atender a uma requisição, e em serverless, o "primeiro toque" pode acontecer em cada cold start, em aproximadamente 57 armazenamentos de dados diferentes. Isso soma algumas centenas de idas e voltas antes de uma requisição fazer qualquer trabalho real.

Três coisas mantêm isso sob controle:

- **Introspecção em lote.** Em vez de uma consulta por tabela, coluna e índice, as verificações acima rodam como uma única passagem de introspecção por banco de dados, apenas duas consultas no total. Isso é automático e não precisa de configuração.
- **Pulo automático em serverless gerenciado.** Netlify Functions, AWS Lambda e Vercel Functions pulam essa verificação completamente em produção, sem nenhuma configuração necessária.
- **`AGENT_NATIVE_SKIP_ENSURE_TABLES=1`.** Defina isso em implantações que o pulo automático não cobre, como um servidor Node de longa duração, Docker ou outra configuração auto-hospedada, uma vez que seu schema já esteja migrado e você não queira que a inicialização do app crie ou altere tabelas.

<Callout tone="risk">

Nem a flag nem o pulo automático em serverless conseguem falhar de forma fechada. Se uma tabela realmente estiver faltando, a primeira consulta real que precisa dela falha de forma explícita, em vez de ser reparada silenciosamente. Isso é proposital (um reparo silencioso esconderia um bug real de migração), mas significa que a partir daqui a responsabilidade pela migração é sua. Não defina essa flag, e não conte com o pulo automático, em uma implantação que dependa da inicialização do app para criar suas próprias tabelas.

</Callout>

## Definindo o Preset {#setting-the-preset}

Por padrão, o Nitro compila para Node.js. Para mirar em uma plataforma diferente, defina o preset no seu `vite.config.ts`:

```ts
import { agentNative } from "@agent-native/core/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [agentNative({ nitro: { preset: "vercel" } })],
});
```

Ou use a variável de ambiente `NITRO_PRESET` no momento do build:

```bash
NITRO_PRESET=netlify npx @agent-native/core@latest build
```

Veja a página da sua plataforma para detalhes de build e deploy:

- [**Node.js & Docker**](/docs/node-docker): o preset padrão, além de um Dockerfile independente
- [**Vercel**](/docs/vercel)
- [**Netlify**](/docs/netlify): inclui keep-warm para bancos de dados com escala a zero
- [**Cloudflare**](/docs/cloudflare): Pages e Workers
- [**Outras Plataformas**](/docs/other-platforms): AWS Lambda e Deno Deploy

A política padrão de cache do shell SSR, e como sobrescrevê-la com
`AGENT_NATIVE_SSR_CACHE`, é uma página própria: veja [Cache SSR](/docs/ssr-caching).

A referência completa de variáveis de ambiente de produção (build/runtime,

`.env` do espaço de trabalho e geração de segredos fortes) é uma página própria:

Quais ferramentas do framework e capacidades de execução de código um agente de

## Implantações Multi-instância {#multi-instance}

Apps nativos do agente armazenam todo o estado em SQL via Drizzle e sincronizam a UI via [polling](/docs/key-concepts#polling-sync) contra o banco de dados. Não há estado no sistema de arquivos, sessões sticky ou caches em memória. Isso significa que implantações multi-instância e serverless funcionam prontas para uso: aponte cada instância para o mesmo `DATABASE_URL` e elas convergem automaticamente. Veja [Conceitos-chave: Dados em SQL](/docs/key-concepts#data-in-sql) e [Portabilidade](/docs/key-concepts#hosting-agnostic).
