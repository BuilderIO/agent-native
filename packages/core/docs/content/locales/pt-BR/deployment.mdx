# Implantação

Os apps Agent-Native rodam sobre o [Nitro](https://nitro.build), então o mesmo app pode
ser implantado em Node.js, funções serverless, workers de edge ou um host gerenciado. Escolha
o caminho que corresponde ao que você vai publicar:

<Cards columns={2}>

### :server: [Fazer deploy de um app](/docs/deploy-an-app)

Faça o build e publique um app independente no Node.js, Docker, Vercel, Netlify ou
Cloudflare Workers.

### :network: [Fazer deploy de um espaço de trabalho](/docs/workspace-deployment)

Faça o build de vários apps em uma única origem, com login compartilhado e comunicação entre
apps na mesma origem.

</Cards>

## Antes de implantar: escolha um banco de dados persistente {#persistent-database}

Todo app implantado precisa de um banco de dados PostgreSQL persistente. O desenvolvimento local pode usar
o banco de dados PGlite em `data/pglite`, mas os sistemas de arquivos de contêineres, prévias e ambientes serverless
podem ser redefinidos a qualquer momento.

<Steps>

### Escolha um provedor

Use um provedor de PostgreSQL hospedado, como [Neon](/docs/neon),
[Supabase](/docs/supabase), Railway, Render, [Amazon RDS for PostgreSQL](/docs/aws-rds),
[Cloud SQL for PostgreSQL](/docs/cloud-sql) ou [Azure Database for PostgreSQL](/docs/azure-postgresql).
Use o guia [Plain Postgres](/docs/postgres) para outros serviços gerenciados e
servidores PostgreSQL auto-hospedados. O framework configura o PostgreSQL a partir da
URL de conexão.

### Defina a string de conexão

Defina `DATABASE_URL` nas configurações de variáveis de ambiente ou de segredos do provedor de hospedagem
antes da primeira implantação de produção. Um `.env` local configura apenas a sua
máquina e não é enviado pelo comando de deploy.

### Adicione os segredos de produção

Gere um segredo de assinatura estável com `openssl rand -hex 32` e defina-o como
`BETTER_AUTH_SECRET` em um app independente. Um espaço de trabalho também precisa de `A2A_SECRET`
quando usa requisições assinadas entre apps ou repasses em segundo plano. A [referência de variáveis de
ambiente de implantação](/docs/deployment-environment-variables) cobre o restante
das configurações de produção.

### Execute as migrações

Execute `pnpm migrate:production` usando o banco de dados de produção antes do primeiro
acesso. Ele cria as tabelas de que o app precisa. Execute-o novamente depois de cada atualização,
antes de a nova versão entrar no ar. Cada guia de hospedagem mostra onde este passo se encaixa.

</Steps>

<Callout tone="info">

Em um espaço de trabalho, todo app herda a `DATABASE_URL` da raiz por padrão. Defina
`<APP_NAME>_DATABASE_URL` apenas quando um app precisar de um banco de dados diferente.

</Callout>

## O envio de e-mail é opcional, mas recomendado {#email-provider}

Um provedor de e-mail não é necessário para a autenticação com e-mail e senha. Sem
ele, um app implantado usa cadastro e login com e-mail e senha, ignora a verificação de e-mail no cadastro
e não oferece autenticação por link mágico.

O Agent-Native não inclui uma conta de entrega de e-mail. Conecte o Resend ou o
SendGrid antes de implantar se quiser links mágicos, verificação de
e-mail, redefinição de senha, convites ou notificações de compartilhamento. Defina
`RESEND_API_KEY` ou `SENDGRID_API_KEY` no ambiente de implantação. O SendGrid
também precisa de `EMAIL_FROM`. Consulte [Autenticação](/docs/authentication) para conhecer os
modos de autenticação disponíveis.

### Personalizar os e-mails do framework {#email-templates}

Todo e-mail que o framework envia tem um modelo padrão. Para usar seu próprio
design, registre um override em um plugin de servidor. O framework continua escolhendo
o destinatário e o remetente e entregando a mensagem. Seu override decide o que
a mensagem diz e como ela aparece.

```ts
// server/plugins/email-templates.ts
import {
  escapeEmailHtml,
  overrideTransactionalEmail,
} from "@agent-native/core/server";

export default function registerEmailTemplates(): void {
  overrideTransactionalEmail("core.resource-shared", (props) => ({
    subject: `${props.sender.name} shared "${props.resource.title}"`,
    html: `<p>${escapeEmailHtml(props.sender.name)} invited you to
      <a href="${escapeEmailHtml(props.resource.url)}">${escapeEmailHtml(props.resource.title)}</a>
      in ${escapeEmailHtml(props.app.name)}.</p>`,
  }));
}
```

| ID do e-mail                     | Props                                                                              |
| -------------------------------- | ---------------------------------------------------------------------------------- |
| `core.verify-signup`             | `email`, `verifyUrl`                                                               |
| `core.reset-password`            | `email`, `resetUrl`                                                                |
| `core.magic-link`                | `email`, `magicLinkUrl`                                                            |
| `core.change-email-confirmation` | `email`, `newEmail`, `confirmationUrl`                                             |
| `core.change-email-verification` | `email`, `verifyUrl`                                                               |
| `core.organization-invite`       | `invitee`, `orgName`, `inviter`, `acceptUrl`                                       |
| `core.builder-credit-limit`      | `subject`, `heading`, `body`, `upgradeLabel`, `upgradeUrl`                         |
| `core.resource-shared`           | `recipientEmail`, `sender`, `resource` (`type`, `title`, `url`), `role`, `message` |

Todo override também recebe `app` (`name`, `logoUrl`). O segundo argumento traz
a renderização padrão, para você reutilizar o assunto ou o texto.

- Props são valores brutos. Escape-as com `escapeEmailHtml` antes de colocá-las
  em uma string HTML.
- Retorne `react` com um elemento React em vez de `html` para renderizar um componente.
  O React escapa as props para você.
- Omita `subject` para manter o assunto padrão. Omita `text` para derivar
  o corpo em texto simples do seu HTML.
- Se um override lançar um erro, o envio falha. O framework não volta
  para o design padrão. A prévia de e-mails transacionais renderiza seu override,
  então confira lá.

## Destinos de implantação compatíveis {#supported-deployment-targets}

Cada destino tem um guia passo a passo. O código do app e o banco de dados continuam os mesmos
qualquer que seja o destino escolhido. Só mudam o preset de build e o comando de
deploy.
