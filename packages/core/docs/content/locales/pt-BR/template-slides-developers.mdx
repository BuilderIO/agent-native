# Guia do desenvolvedor

Esta página é para qualquer pessoa que esteja personalizando o template Apresentações ou estendendo-o: o modelo de dados SQL, como os gravadores concorrentes são mantidos seguros, cada action que o agente pode chamar, o mapa de rotas e onde fazer alterações comuns.

## Início rápido

```bash
npx @agent-native/core@latest create my-slides --standalone --template slides
```

Veja [Primeiros passos](/docs/getting-started) para o restante da configuração (`cd`, `pnpm install`, `pnpm dev`) e os fundamentos do framework.

## Modelo de persistência

Cada deck é um único blob JSON em `decks.data`. Toda escrita passa por uma action de leitura-modificação-escrita do lado do servidor que mantém um lock por deck, então gravadores concorrentes, um humano e o agente, ou dois humanos, tocando slides diferentes do mesmo deck, nunca sobrescrevem o trabalho um do outro.

- **Actions do agente** (`add-slide`, `update-slide`) usam suas próprias actions dedicadas e granulares, e compartilham esse mesmo lock.
- **O editor do navegador** enfileira operações granulares (`patch-slide`, `delete-slide`, `reorder-slides`, `add-slide`, `patch-deck-fields`) através de `patch-deck`, em vez de um PUT do deck inteiro.

<Callout id="doc-block-slides10" tone="warning">

Se você estiver estendendo o caminho de salvamento do editor, enfileire uma nova operação através de `patch-deck`. Não adicione um novo PUT do deck inteiro. Isso reintroduziria a corrida de "a última escrita vence" que o lock existe para evitar.

</Callout>

As tabelas de compartilhamento do framework (`deck_shares`, `design_system_shares`) mapeiam principais, usuários ou organizações, para funções de visualizador / editor / administrador por recurso, e são criadas através do helper compartilhado `createSharesTable`, em vez de escritas à mão.

#### Estrutura do slide

Cada slide dentro de `decks.data` é:

```json
{
  "id": "slide-1",
  "layout": "title",
  "content": "<div class=\"fmd-slide\" style=\"...\">...</div>"
}
```

`content` é HTML bruto. O renderizador fornece a proporção de aspecto fixa e o fundo, e o HTML fornece tudo o que está dentro. Incorporações ricas também são suportadas: diagramas desenhados à mão e gráficos renderizados em tempo real podem existir dentro de um slide junto com HTML simples.

## Inventário de actions

### Ciclo de vida do deck

- `create-deck` — novo deck, opcionalmente pré-populado com slides, ou uma substituição em massa e atômica dos slides de um deck existente. Omita `slides` ou passe `[]` para um deck vazio. A action abre o novo deck através do estado da aplicação.
- `get-deck` — JSON completo do deck, ou uma visualização compacta de resumo dos slides
- `list-decks` — todo deck que o chamador pode ver, com projeções leve/compacta/slide completo para polling barato
- `duplicate-deck` — copia um deck com ids de slide novos
- `update-deck-aspect-ratio` — 16:9, 1:1, 9:16 ou 4:5

`add-deck`, `save-deck` e `delete-deck` sustentam os fluxos de criação otimista, desfazer/refazer e exclusão do editor no navegador. O agente usa `create-deck`, `add-slide`/`update-slide`/`patch-deck`, e as próprias actions de compartilhamento do framework em vez disso.

### Solicitações de acesso

- `request-deck-access`, `approve-deck-access-request`, `get-deck-access-status` — o fluxo de solicitação de acesso para decks privados: um visitante sem acesso solicita, o proprietário aprova ou nega a partir do aplicativo ou da rota `/access-request/approve`, e qualquer um dos lados pode consultar o status atual por polling

### Edições de slide

- `add-slide` — anexa (ou insere em uma posição) um slide. Chame-a sequencialmente após um `create-deck` vazio para que o editor possa mostrar progresso.
- `update-slide` — edição cirúrgica de busca/substituição ou de conteúdo completo do slide
- `patch-deck` — a fila de operações granulares que o editor do navegador usa em vez de um PUT do deck inteiro
- `get-layout-overflows` — lê resultados de ajuste de slide medidos pelo navegador, para que uma edição que não caiba mais em seu layout possa ser detectada e revisada

### Histórico

- `list-deck-versions`, `get-deck-version`, `restore-deck-version` — toda escrita captura um snapshot primeiro, então qualquer ponto no tempo pode ser listado e restaurado

### Comentários

- `list-slide-comments`, `add-slide-comment`, `update-slide-comment`, `delete-slide-comment`

### Importação

- `import-pptx`, `import-docx`, `import-google-doc` — importadores dedicados de formato único
- `import-google-slides-reference` — importa um deck do Google Slides como um deck de referência reutilizável, em vez de trazer seu conteúdo para o deck de trabalho
- `import-file` — um único ponto de entrada para PPTX, DOCX ou PDF, ou um arquivo `.fig` do Figma (que é direcionado para a indexação de sistema de design do Builder em vez de uma importação de slides)
- `extract-pdf` — extração bruta de texto de um PDF, somente via CLI, principalmente para depuração local

### Exportação

- `export-pptx` — PowerPoint nativo e editável
- `export-google-slides` — gera o mesmo PPTX mais um link de importação pronto para o Google Slides
- `export-html` — um arquivo HTML autônomo e autocontido, com navegação por teclado integrada

### Sistemas de design

- `create-design-system`, `update-design-system`, `delete-design-system`, `get-design-system`, `list-design-systems`, `set-default-design-system`, `apply-design-system` (vincula um a um deck)
- `get-workspace-defaults`, `set-workspace-defaults` — o deck e o sistema de design padrão em nível de workspace. Defini-los é restrito a administradores
- `analyze-brand-assets`, `import-document`, `import-from-url`, `import-code` — reúnem sinais brutos de marca (CSS/fontes do site, conteúdo de documentos ou arquivos de código enviados) para um sistema de design **local**, redigido pelo agente
- `index-design-system-with-builder`, `sync-design-system-with-builder`, `import-design-project` — o caminho indexado pelo Builder para arquivos do Figma, código-fonte/repositórios do GitHub conectados e `design.md`. `import-design-project` parte de um sistema de design existente em vez de uma fonte bruta

### Creative Context

- `clone-context-slide` — insere um slide fixado da Library em um deck sem alterações, sem regenerar seu HTML/CSS
- `clone-creative-context-deck` — recria uma versão exata e governada de um deck
- `get-deck-reference-context` — extrai a linguagem visual de um deck existente como uma biblioteca de padrões reutilizável
- Recuperação e envio para a Library (busca, obtenção de um item de contexto, gerenciamento de membros da Library) são actions compartilhadas do framework, que o agente chama da mesma forma em todo aplicativo que suporta Creative Context. Veja a skill `creative-context` para o procedimento de recuperação e a escada de reutilização.

### Escalonamento e dados preparados

- `provider-api-catalog`, `provider-api-docs`, `provider-api-request` — acesso bruto à API do Google Drive para quando uma action pronta de importação/exportação é muito limitada. O Apresentações resolve a autenticação a partir da conta do Google Docs conectada do usuário
- `list-staged-datasets`, `query-staged-dataset`, `delete-staged-dataset` — agregam um resultado grande e preparado do provedor sem buscá-lo novamente

### Navegação e contexto

- `view-screen` — o que o usuário está vendo atualmente: deck aberto, slide atual e qualquer seleção visual ativa
- `navigate` — move a interface para um deck, slide ou visualização

## Personalize

O template Apresentações é totalmente personalizável. Principais lugares para observar ao estendê-lo:

#### Actions — `templates/slides/actions/`

Toda operação que o agente pode chamar vive aqui como um arquivo TypeScript, montada automaticamente em `POST /_agent-native/actions/:name` e chamável a partir da CLI como `pnpm action <name>`. Adicione um novo arquivo aqui para dar ao agente uma nova capacidade.

<AnnotatedCode
  id="doc-block-slides9"
  title="Anatomia de uma action de edição de slide"
  filename="actions/update-slide.ts (simplificado)"
  language="ts"
  code={
    'import { defineAction, fail } from "@agent-native/core/action";\nimport { assertAccess } from "@agent-native/core/sharing";\nimport { eq } from "drizzle-orm";\nimport { z } from "zod";\n\nimport { getDb, schema } from "../server/db/index.js";\nimport { notifyClients } from "../server/handlers/decks.js";\nimport { withDeckLock } from "./patch-deck.js";\n\nexport default defineAction({\n  description:\n    "Surgically edit a slide\'s content using search-replace or full replacement. " +\n    "Syncs live to open editors. Prefer this over full deck rewrites.",\n  schema: z.object({\n    deckId: z.string(),\n    slideId: z.string(),\n    find: z.string().optional(),\n    replace: z.string().optional(),\n    fullContent: z.string().optional(),\n  }),\n  run: async ({ deckId, slideId, find, replace, fullContent }) => {\n    await assertAccess("deck", deckId, "editor");\n    return withDeckLock(deckId, async () => {\n      const db = getDb();\n      const [row] = await db\n        .select()\n        .from(schema.decks)\n        .where(eq(schema.decks.id, deckId));\n      if (!row) {\n        fail(`Deck ${deckId} not found`, { errorCode: "deck_not_found", statusCode: 404 });\n      }\n\n      const deck = JSON.parse(row.data);\n      const slide = deck.slides.find((s: { id: string }) => s.id === slideId);\n      if (!slide) {\n        fail(`Slide ${slideId} not found`, { errorCode: "slide_not_found", statusCode: 404 });\n      }\n\n      if (fullContent) {\n        slide.content = fullContent;\n      } else if (find) {\n        const idx = slide.content.indexOf(find);\n        if (idx === -1) {\n          fail("Text not found", { errorCode: "slide_find_no_match" });\n        }\n        slide.content =\n          slide.content.slice(0, idx) +\n          (replace ?? "") +\n          slide.content.slice(idx + find.length);\n      }\n\n      deck.updatedAt = new Date().toISOString();\n      await db\n        .update(schema.decks)\n        .set({ data: JSON.stringify(deck), updatedAt: deck.updatedAt })\n        .where(eq(schema.decks.id, deckId));\n\n      notifyClients(deckId, { slideId, actor: "agent" });\n      return { ok: true, deckId, slideId };\n    });\n  },\n});'
  }

A action real também valida que exatamente um modo de edição foi fornecido, captura um snapshot de versão antes de escrever, e escreve com uma verificação de concorrência otimista para que uma leitura obsoleta nunca possa sobrescrever silenciosamente uma mais nova, além de registrar a proveniência de reuso do Creative Context e esperar brevemente que o editor reporte uma medição de layout-overflow. Este exemplo reduz tudo isso à forma essencial de acesso, lock, leitura-modificação-escrita e notificação.

A maior parte da personalização da UI do editor acontece em `app/components/editor/`: a tela de slide, a barra de ferramentas, a barra lateral, o menu de bolha, o menu de barra e o painel de histórico.

#### Skills — `templates/slides/.agents/skills/`

Skills do agente que explicam padrões quando o agente precisa modificar código:

- `create-deck` — como criar um novo deck, com templates HTML exatos de slide para cada layout
- `slide-editing` — como editar slides individuais
- `deck-management` — como os decks são armazenados e acessados
- `design-systems` — o formato de dados do sistema de design e como os tokens se aplicam aos slides gerados
- `creative-context` — a escada de reutilização, o procedimento de recuperação e o envio para a Library

#### AGENTS.md

`templates/slides/AGENTS.md` é o roteador curto que o agente lê em cada conversa. Ele aponta para as skills em `.agents/skills/` e estabelece as regras principais, o modelo de persistência e o contrato de estado da aplicação. Atualize a skill relevante sempre que você adicionar ou alterar um layout de slide ou uma origem de sistema de design.
