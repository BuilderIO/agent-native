# Apps

Deseja enviar sua própria ferramenta de análise baseada em IA? Cliente de e-mail? Construtor de formulários? Escolha um app de exemplo e você terá um SaaS funcional em minutos: agente, banco de dados, autenticação e pipeline de implantação já conectados.

A maioria dos modelos iniciais oferece um andaime em branco e uma longa lista TODO. O agente nativo inverte isso. Cada app de exemplo é um **produto completo de nível SaaS** — já executável no primeiro dia, já disponível para entrega e inteiramente seu para personalizar, marcar e implantar. Pense neles como SaaS clonáveis, não como kits iniciais: você está criando um produto acabado, e não olhando para um padrão.

## Templates da comunidade {#community-templates}

Os templates nomeados no seletor da CLI são **oficiais**: a Agent Native os
mantém, testa, documenta e publica junto com o framework. Um **template da
comunidade** é mantido e versionado pelo proprietário do repositório. Ele pode
usar a mesma superfície do framework, mas uma entrada na lista da comunidade
não representa recomendação nem promessa de suporte da Agent Native.

Execute `create`, escolha **Template da comunidade** e cole a URL simples de um
repositório público do GitHub:

```bash
https://github.com/owner/repo
```

Se a raiz do repositório contiver um único app Agent Native, a CLI o instalará
diretamente sem outro seletor. Se o repositório for um workspace Agent Native, a
CLI descobrirá os filhos diretos válidos de `apps/*`, excluirá `dispatch` e
perguntará qual app deve ser instalado.

Um marcador `agent-native.workspaceCore` não vazio faz do repositório um
workspace mesmo quando o pacote raiz também depende de `@agent-native/core`; um
marcador malformado é rejeitado.

Passe a mesma URL simples para `--template` em scripts ou use a forma curta
`community:`. Fixe uma branch, tag ou commit depois de `#` para obter um ponto
de partida reproduzível. Sem uma referência, a CLI tenta `main` e depois
`master`:

```bash
npx @agent-native/core@latest create my-app --template community:owner/repo#v1.2.0
npx @agent-native/core@latest create my-app --template https://github.com/owner/repo#v1.2.0
```

Para escolher o app de origem de um repositório de workspace sem interação, use
`?app=<app-name>`. O seletor vem antes do `#ref` opcional. Mantenha todo o valor
entre aspas, pois shells como zsh tratam `?` como um glob:

```bash
npx @agent-native/core@latest create my-app --template 'community:owner/repo?app=analytics#v1.2.0'
npx @agent-native/core@latest create my-app --template 'https://github.com/owner/repo?app=analytics#v1.2.0'
```

Fora de um workspace, `create` transforma o app de origem selecionado em um app
independente. Para adicioná-lo a um workspace existente, passe explicitamente o
repositório da comunidade, pois o seletor de `add-app` mostra apenas templates
oficiais. Omita `?app` para escolher interativamente no workspace de origem ou
inclua-o para uma instalação automatizável:

```bash
npx @agent-native/core@latest add-app my-app --template community:owner/repo#v1.2.0
npx @agent-native/core@latest add-app my-app --template 'community:owner/repo?app=analytics#v1.2.0'
```

Somente repositórios públicos do GitHub são aceitos. Repositórios privados,
hosts que não sejam GitHub, URLs de árvores ou subdiretórios do GitHub e
caminhos de app aninhados não são compatíveis. Um app na raiz deve ter um
`package.json` legível que liste `@agent-native/core` em `dependencies`,
`devDependencies` ou `peerDependencies`. Em um repositório de workspace, cada
app de origem selecionável deve atender ao mesmo requisito diretamente em
`apps/<app-name>/`; `dispatch` nunca pode ser selecionado.

Apps de um workspace da comunidade devem ser unidades portáteis, não fatias
arbitrárias de um monorepo:

- referências de dependência `catalog:` padrão são resolvidas a partir do
  `pnpm-workspace.yaml` na raiz do repositório de origem; referências de
  catálogo nomeadas não são compatíveis;
- referências `workspace:*` a `@agent-native/core`,
  `@agent-native/dispatch` e `@agent-native/toolkit` são reescritas para versões
  publicadas. Outros pacotes irmãos do workspace não são copiados; publique-os
  e use uma versão concreta;
- a dependência do pacote `workspaceCore` de origem é removida. Os plugins
  canônicos herdados de autenticação e agent chat do workspace são
  desconectados em uma instalação independente ou vinculados ao workspace de
  destino. Qualquer outra importação do pacote `workspaceCore` de origem falha
  com uma mensagem clara; mova esse código para o app ou publique-o como uma
  dependência concreta.

Mantenha o restante de cada app completo junto ao seu `package.json`:
`agent-native.json` quando usado, código-fonte, actions, instruções do agente e
configuração do banco de dados. Um repositório pronto para o catálogo também
deve incluir:

- uma licença e um link para o mantenedor ou suporte;
- um README com as etapas de configuração, variáveis de ambiente obrigatórias
  e o comando exato da CLI;
- um `.env.example` contendo apenas placeholders, sem secrets, dados de
  clientes, bancos de dados de execução ou saídas de build geradas;
- instalação e comando de desenvolvimento funcionais, typecheck e testes
  adequados ao template.

O instalador registra os valores `source` e `ref` resolvidos em
`agent-native.communityTemplate` dentro do `package.json` do app instalado.
Apps selecionados de um repositório de workspace também registram o app de
origem como `agent-native.communityTemplate.app`. `agent-native template sync`
continua exclusivo para templates oficiais; para atualizar um template da
comunidade, revise uma referência upstream mais recente e mescle as alterações
por conta própria.

Consulte [Creating Templates](/docs/creating-templates) para ver o checklist
completo de app, actions, estado, segurança e publicação.

> **Revise o código da comunidade antes de instalar dependências ou executá-lo.**
> Os templates da comunidade são baixados de repositórios de terceiros; a Agent
> Native não os isola, audita ou mantém. A CLI baixa apenas o código-fonte; ela
> não instala dependências nem executa scripts do template. Inspecione o
> código-fonte, a licença, as dependências e os scripts de instalação de pacotes
> e prefira uma referência confiável fixada.

Uma demonstração hospedada é opcional. Se você fornecer uma, use um link
público para experimentar e documente os requisitos de login, dados de exemplo
ou provedores. O repositório continua sendo a fonte da verdade para a
instalação, e seu proprietário continua responsável pelo template e pela
demonstração.

Quer entrar na lista? [Envie um template da comunidade](https://github.com/BuilderIO/agent-native/issues/new?template=community-template.yml)
com a URL do repositório, uma descrição de uma frase, detalhes do mantenedor e
da licença, o comando da CLI testado e uma URL opcional da demonstração
hospedada.

## O que você ganha imediatamente {#what-you-get}

Cada app de exemplo vem com peças que normalmente levam meses para serem construídas:

- **Um agente funcional** — já conectado ao aplicativo, já capaz de capturar actions em seus dados, já ciente do contexto sobre o que você está vendo. Veja [Messaging the agent](/docs/messaging) para saber como funciona.
- **Auth** — login, sessões, organizações, isolamento multilocatário. Já pronto.
- **Um banco de dados** — cada app de exemplo tem seu esquema, consultas e migrações prontos para uso. Traga seu próprio banco de dados SQL (Postgres, SQLite, Turso, D1) — a estrutura se adapta.
- **UI em tempo real** — a tela permanece sincronizada com o que o agente faz. Clique em "rascunhar um e-mail" no bate-papo e veja o rascunho aparecer na sua caixa de entrada imediatamente.
- **Pronto para implantação** — envie para Netlify, Vercel, Cloudflare, AWS ou qualquer outro lugar que execute Node. Sem dependência de fornecedor.
- **Ganchos de branding** — nome, cores, logotipo e cópia são fáceis de alterar.

Esta não é uma afirmação teórica. O autor da estrutura executa sua caixa de entrada real no app Mail, seu calendário real no app Calendar e suas análises reais no app Analytics. Esses apps são softwares de uso diário.

1. **Escolha um app de exemplo.** Use o seletor CLI ou navegue nos documentos e escolha um para começar.
2. **Marque.** Altere o nome, as cores, o logotipo e a cópia. A maioria dos apps de exemplo expõe isso em um único arquivo de configuração.
3. **Personalize.** Faça alterações de código-fonte no seu repositório e fluxo de desenvolvimento. Um agente pode ajudar quando seu frame recebe intencionalmente ferramentas de workspace e escrita; caso contrário, o agente incorporado opera o app por actions, dados e integrações configuradas.
4. **Envie.** Execute o comando de implantação. Agora você tem seu próprio SaaS de produção em seu próprio domínio.

As etapas 2 a 4 normalmente levam dias, não meses. A etapa 3 é aberta porque o app é seu para evoluir, enquanto o agente incorporado continua disponível para operar o produto implantado e pode ajudar em alterações de fonte quando o acesso ao código é explicitamente ativado.

## Por que isso é prático {#why}

Um modelo tradicional de fork-the-codebase se decompõe em grande escala: cada usuário mantendo sua própria caixa de entrada parece um pesadelo de manutenção. Duas decisões-quadro fazem com que tudo funcione:

1. **O app mantém o contrato do framework.** Seu código-fonte possui o comportamento do domínio, enquanto Core mantém actions, SQL, estado e sincronização consistentes conforme o app evolui.
2. **Personalização por usuário sem código por usuário.** Skills, memória, instruções, servidores MCP conectados e subagentes, todos residem em SQL. Cada usuário obtém sua própria camada de personalização; a base de código compartilhada hospeda todos eles de uma vez.

O resultado: flexibilidade em nível de código Claude para cada usuário, com economia normal de implantação de SaaS.

## Não quer desembolsar? {#hosted}

Você não precisa. Cada app de exemplo também está disponível como um aplicativo hospedado em `agent-native.com` — `mail.agent-native.com`, `calendar.agent-native.com` e assim por diante. Use a versão hospedada gratuitamente ou paga; bifurque apenas quando quiser alterar algo que a versão hospedada não expõe.

### Para desenvolvedores {#dev-details}

Se você estiver montando um andaime agora, o comando CLI é:

```bash
npx @agent-native/core@latest create my-platform
```

Você receberá um seletor de seleção múltipla. Escolha um aplicativo (autônomo) ou vários (espaço de trabalho — os aplicativos compartilham autenticação, marca, configuração do agente e banco de dados). Cada app escolhido é estruturado em `apps/<name>/` com todos os arquivos que você precisa. Para uma automação sem UI no navegador em vez de uma UI de app, use `npx @agent-native/core@latest create my-agent --headless`.

Preencha `.env` (principalmente `ANTHROPIC_API_KEY` e `DATABASE_URL`), `pnpm install`, `pnpm dev` e funciona. Sem "TODO: implementar login", sem rotas de espaço reservado.

Destinos de implantação: qualquer host compatível com Nitro (Node, Cloudflare, Netlify, Vercel, Deno, Lambda, Bun) e qualquer banco de dados SQL compatível com Drizzle (SQLite, Postgres, Turso, D1, Supabase, Neon). Para espaços de trabalho, `npx @agent-native/core@latest deploy` cria todos os aplicativos de uma vez e os envia para uma única origem. Consulte [Deployment](/docs/deployment).

Para criar e publicar seu próprio modelo de app, consulte [Creating Templates](/docs/creating-templates).
