# Dados e sincronização

A principal forma de ler e gravar dados do aplicativo a partir do cliente é através dos ganchos de [action](/docs/actions-overview). Ao incorporar solicitações em actions, tanto seu cliente quanto o agente podem interagir com seu aplicativo da mesma maneira.

No exemplo abaixo, um ticket é atribuído ao usuário atual manualmente através de um dropdown, e depois através do agente de chat. Tanto a UI quanto o agente acessam a mesma action.

### Ganchos de action {#action-hooks}

Existem dois ganchos de action que você provavelmente vai usar: `useActionQuery()` e `useActionMutation()`. Esses dois ganchos dão acesso às actions do seu aplicativo.

#### useActionQuery {#use-action-query}

Este gancho é destinado a actions somente leitura. É um wrapper leve em torno da função [useQuery()](https://tanstack.com/query/latest/docs/framework/react/reference/useQuery).

No exemplo abaixo, a action `list-tickets` é chamada. Isso é semelhante a fazer uma solicitação GET para todos os tickets.

```ts
import { useActionQuery } from "@agent-native/core/client/hooks";

const { data, isLoading } = useActionQuery("list-tickets", {});
```

O exemplo a seguir mostra uma solicitação para buscar um único ticket, através da action `get-ticket`. Um `ticketId` é fornecido para restringir a consulta a retornar apenas um ticket específico. A opção adicional `enabled` é fornecida para garantir que a consulta não seja executada automaticamente, e sim apenas quando um `ticketId` estiver presente.

```ts
import { useActionQuery } from "@agent-native/core/client/hooks";

const { data, isLoading } = useActionQuery(
  "get-ticket",
  { ticketId: ticketId ?? "" },
  { enabled: Boolean(ticketId) },
);
```

Este gancho é destinado a actions que alteram dados, como criar, atualizar ou enviar algo. É um wrapper leve em torno da função [useMutation()](https://tanstack.com/query/latest/docs/framework/react/reference/useMutation).

Diferente de `useActionQuery()`, a entrada da action não é passada para o gancho em si. Ela é passada para `mutate()` ou `mutateAsync()` quando você estiver pronto para executar a mutação.

No exemplo abaixo, a action `send-ticket-reply` é chamada para postar uma resposta em um ticket. Chame `mutate()` a partir de um manipulador de evento, como o `onClick` de um botão.

```ts
import { useActionMutation } from "@agent-native/core/client/hooks";

const { mutate, isPending } = useActionMutation("send-ticket-reply");

mutate({ ticketId, body: draft });
```

O exemplo a seguir mostra a mesma mutação com uma opção `onSuccess`. A invalidação de cache acontece automaticamente após cada mutação, então `onSuccess` só é necessário para efeitos colaterais locais, como limpar o composer de resposta depois que a resposta é enviada.

```ts
import { useActionMutation } from "@agent-native/core/client/hooks";

const { mutate, isPending } = useActionMutation("send-ticket-reply", {
  onSuccess: () => setDraft(""),
});

mutate({ ticketId, body: draft });
```

### Invalidação por recurso {#resource-scoped-invalidation}

Ambos os hooks aceitam um array opcional `resources`. Uma consulta informa os recursos que lê e uma mutação informa os recursos que altera. Use `type` para um tipo de recurso inteiro ou `type:id` para um ID específico. Na correspondência de mutações locais, os primeiros dois-pontos em uma tag `type:id` separam o tipo do ID. O tipo não deve conter dois-pontos, mas o ID pode contê-los. Eventos de sincronização transportam o tipo e o ID separadamente.

```ts
import {
  useActionMutation,
  useActionQuery,
} from "@agent-native/core/client/hooks";

const tickets = useActionQuery("list-tickets", {}, { resources: ["ticket"] });
const ticket = useActionQuery(
  "get-ticket",
  { ticketId },
  { resources: [`ticket:${ticketId}`] },
);
const reply = useActionMutation("send-ticket-reply", {
  resources: [`ticket:${ticketId}`],
});
```

Para tipos sem dois-pontos e tags com IDs de registro não vazios, a correspondência é simétrica entre mutações locais e eventos de sincronização. Para uma alteração local de todo um tipo, use `type`, não `type:`. Na correspondência de mutações locais, `design:layer` significa o tipo `design` e o ID `layer`. Um evento de sincronização com `resourceType` `design:layer` tem um tipo distinto de `design` e não corresponde à tag de consulta `design`. Uma tag `ticket` corresponde a `ticket` e a qualquer tag `ticket:id`. Uma tag `ticket:123` corresponde a `ticket` e `ticket:123`, mas não a `ticket:456`. Consultas sem tags são invalidadas por precaução. Uma mutação sem tags invalida todas as consultas de action.

Para um evento de sincronização de action, `resourceType` e `resourceId` identificam o recurso alterado separadamente. Se `resourceId` estiver ausente ou vazio, todas as consultas correspondentes a esse tipo são invalidadas. Se algum evento de action não suprimido não tiver `resourceType`, o filtro por recurso é desativado para o lote e todas as consultas de action são elegíveis. O predicado opcional ainda pode filtrar a invalidação.

Em um lote que contém eventos de action e apenas eventos de action ou app-state, o filtro de recursos corresponde a qualquer recurso alterado dos eventos de action não suprimidos. Com `actionInvalidatePredicate`, uma consulta deve atender ao filtro e ao predicado. O predicado recebe todo o lote relevante sem eventos awareness, incluindo eventos de action suprimidos. Se o lote também contiver outra fonte que altera dados, o filtro por recurso é desativado, mas o predicado continua sendo aplicado. Em um lote com outro evento que altera dados, mas sem eventos de action não suprimidos, o predicado também filtra a invalidação geral de actions.

`changeResource` de uma action identifica um recurso para a entrega do evento e a verificação de acesso. Ele não é necessariamente uma lista completa do que a action escreve. Tags de consulta específicas de registro só são seguras quando o marcador entregue de cada action relevante representa todos os registros dos quais a consulta depende. Para escritas em lote ou dependências entre registros dentro do tipo do marcador, uma tag de consulta para o tipo inteiro pode corresponder ao evento entregue. Para dependências entre tipos, inclua o tipo de cada evento entregue nas tags da consulta ou use uma consulta sem tags. Vários eventos entregues independentemente podem cobrir os registros afetados, desde que cada pessoa afetada receba um evento para o qual tenha autorização. Ampliar as tags do cliente só altera a correspondência depois da entrega. Isso não torna um evento visível para quem não tem acesso ao recurso de entrega. Garanta que as pessoas afetadas recebam um evento ao qual tenham acesso.

Esta função é destinada a chamadas de action imperativas e pontuais fora de um fluxo de renderização React, como um manipulador de evento simples, um script, ou qualquer outro caminho de código que não seja React. Ela retorna uma promise diretamente, em vez de um resultado de gancho.

No exemplo abaixo, a action `update-ticket` é chamada a partir de um manipulador de atalho de teclado fora do fluxo de renderização do React, atribuindo o ticket a um representante.

```ts
import { callAction } from "@agent-native/core/client/hooks";

await callAction("update-ticket", {
  ticketId,
  assignedToEmail: "jordan@example.com",
});
```

O exemplo a seguir mostra a mesma chamada com uma opção `timeoutMs`, útil para actions que legitimamente demoram mais do que o tempo limite padrão de 60 segundos.

```ts
import { callAction } from "@agent-native/core/client/hooks";

await callAction(
  "update-ticket",
  { ticketId, assignedToEmail: "jordan@example.com" },
  { timeoutMs: 120_000 },
);
```

Toda solicitação `useActionQuery()`, `useActionMutation()` e `callAction()` é limitada por um tempo limite de 60 segundos, e os tempos limite surgem como erros em vez de tentar novamente silenciosamente. `useActionQuery()` também cancela solicitações substituídas automaticamente, usando o abort signal do React Query.

### Falhas de gravação {#write-failures}

Quando um salvamento iniciado pelo usuário falha, o app mostra um toast compartilhado em vez de nada. `useActionMutation()` faz isso automaticamente. Um `mutate()` que falha mostra o toast, a menos que um `onError` trate a falha, seja nas opções do hook ou na chamada de `mutate()`. Um `mutateAsync()` que falha mostra o toast somente quando a rejeição fica sem tratamento, por exemplo um `await` sem `try/catch` acima dele. Um `catch` que lança um novo `Error` no lugar do original não é reportado.

A opção `errorNotification` muda esse padrão:

| Valor             | Comportamento                                                                                                                                               |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `"auto"` (padrão) | Mostra o toast somente quando nada mais trata a falha.                                                                                                      |
| `"shared"`        | Mostra o toast em toda falha, mesmo ao lado do seu próprio `onError`. Use quando o handler apenas reverte ou registra logs.                                 |
| `"caller"`        | Nunca mostra o toast. Use em salvamentos em segundo plano, em uma falha que você ignora de propósito ou em um lugar que renderiza o erro por conta própria. |

`errorLabel` substitui o título do toast pelo seu próprio texto, já traduzido. No exemplo abaixo, uma atribuição que falha mostra esse título em vez do genérico.

```tsx
import { useActionMutation } from "@agent-native/core/client/hooks";

const assign = useActionMutation("update-ticket", {
  errorLabel: t("tickets.assignFailed"),
});

assign.mutate({ ticketId, assignedToEmail: "jordan@example.com" });
```

Um salvamento automático que tenta de novo na próxima alteração não deve interromper o usuário, então ele desativa essa opção.

```tsx
import { useActionMutation } from "@agent-native/core/client/hooks";

const saveDraft = useActionMutation("save-ticket-draft", {
  errorNotification: "caller",
});
```

Uma gravação que não é um `useActionMutation()`, como um `fetch` para um upload ou um `catch` que engole um erro, comunica a falha com `reportWriteFailure()`. O erro de um `fetch` puro não traz status, então o toast mostra seu rótulo ou o título genérico. Um `useMutation()` puro entra nesse fluxo ao passar `meta: surfaceMutationError(label)`, que aceita o mesmo rótulo opcional.

```ts
import { reportWriteFailure } from "@agent-native/core/client/write-failure";

try {
  const response = await fetch(uploadUrl, { method: "PUT", body: file });
  if (!response.ok) throw new Error(`Upload failed with ${response.status}`);
} catch (error) {
  reportWriteFailure(error, { label: t("tickets.uploadFailed") });
}
```

O texto do toast depende da falha. Uma requisição cancelada não mostra nada. Estar offline, um timeout, um `401` e um `403` mostram cada um uma mensagem curta e traduzida abaixo do título. Um `5xx` mostra apenas o título, porque o servidor oculta o próprio texto de erro. Quando uma action recusa com um erro `4xx` tipado vindo de `fail()`, o toast mostra a mensagem que a action escreveu; veja [Falhar uma action](/docs/actions-defining#failing). Um `401` ou um `403` nunca mostra texto do servidor.

`AppProviders` sempre monta o componente que escuta essas falhas, `WriteFailureToaster`. Ele mostra seu toast pelo `Toaster` do app, então um app que passa `toaster={null}` precisa renderizar o seu próprio. Um app que não usa `AppProviders` renderiza `<WriteFailureToaster />` de `@agent-native/toolkit/app/shared` dentro do seu `QueryClientProvider` e ao lado do seu `Toaster`. Sem ele, nenhum toast é exibido.

`useDbSync()` sempre processa ferramentas concluídas durante uma execução local do chat e atualiza ao final dela. Assim, alterações de um único agente ficam atualizadas sem uma solicitação em segundo plano. Mudanças de outras abas, pessoas, webhooks ou tarefas não são sincronizadas em segundo plano, a menos que esta página ative esse recurso com um motivo curto. Cada aba compartilha um transporte, pausa quando fica oculta e aumenta os intervalos ociosos para 1, 2 e 5 minutos.

```ts
import { useDbSync } from "@agent-native/core/client/hooks";
import { useQueryClient } from "@tanstack/react-query";

function App() {
  const queryClient = useQueryClient();

  useDbSync({
    queryClient,
    realtime: { reason: "teammates can edit this shared record" },
    pollUrl: "/_agent-native/poll",
    onEvent: (data) => console.log("Data changed:", data),
  });

  return <div>...</div>;
}
```

Ative o tempo real apenas quando os dados puderem mudar sem uma ação do usuário atual e ele precisar ver a mudança antes de atualizar. Edição colaborativa no Slides e a caixa de entrada do Mail são bons exemplos. Mantenha desativados páginas públicas, Docs, configurações, formulários, listas que mudam pouco e alterações de um agente individual; atualize ao voltar o foco ou navegar. Cada aba aberta inscrita acrescenta um poll por intervalo ocioso.
