# Sincronização interna

[Sincronização ao vivo](/docs/key-concepts#polling-sync) cobre o modelo mental: uma gravação do agente se torna um evento de mudança, `useDbSync()` a capta, e as consultas afetadas buscam novamente. Esta página cobre o mecanismo por trás disso que a maioria dos aplicativos nunca toca diretamente: os contadores de versão de mudança que `useDbSync()` incrementa, e como incorporá-los em uma chamada `useQuery()` bruta que não está passando por `useActionQuery()`.

`useActionQuery()` já busca novamente automaticamente quando uma action de mutação é concluída (veja [Dados e sincronização](/docs/client-data#fetching-mutating)). Recorra a `useChangeVersion()`/`useChangeVersions()` apenas quando você estiver sincronizando uma chamada `useQuery()` bruta fora desse caminho, como um auxiliar de cliente de nível mais baixo lendo o status de uma integração.

## Como funcionam as versões de mudança {#how-it-works}

Quando uma mutação de banco de dados do lado do servidor ocorre, o servidor registra um evento de mudança marcado com uma chave `source`. `useDbSync()` recebe esse evento e incrementa um contador local para essa origem. Incorporar o contador em uma chave do React Query faz a consulta buscar novamente automaticamente sempre que o backend reportar nova atividade para essa origem.

No exemplo abaixo, uma chamada `useQuery()` bruta lê um dashboard diretamente, incorporando o contador de versão da origem `"dashboards"` em sua chave de consulta para que ela busque novamente sempre que essa origem mudar:

```tsx
import { useQuery } from "@tanstack/react-query";
import { useChangeVersion } from "@agent-native/core/client/hooks";

function DashboardView({ id }) {
  const version = useChangeVersion("dashboards");

  const { data } = useQuery({
    queryKey: ["dashboard", id, version],
    queryFn: () => fetchDashboard(id),
    placeholderData: (prev) => prev,
  });

  return <div>{data?.title}</div>;
}
```

`placeholderData: (prev) => prev` mantém os dados anteriores na tela durante a nova busca, então a visualização não pisca para um estado de carregamento.

## Dois caminhos para uma nova busca {#latency-models}

Uma mutação chega à UI de uma de duas formas, e elas têm latências diferentes.

Uma mutação local, uma que sua própria chamada `useActionMutation()` acabou de fazer, dispara um evento `source: "action"` no momento em que tem sucesso. Toda consulta que depende dessa action busca novamente imediatamente. Não há atraso de ida e volta, já que a aba que fez a gravação já sabe sobre ela.

Uma mutação remota, do agente, um webhook, outra aba, ou outro usuário, precisa chegar a esta aba primeiro. `useDbSync()` a capta via SSE quase imediatamente, ou via o fallback de pesquisa em cerca de dois segundos se o SSE não estiver disponível. Somente quando esse evento chega é que o contador de versão relevante incrementa e a consulta busca novamente em segundo plano.
