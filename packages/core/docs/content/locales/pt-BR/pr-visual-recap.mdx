# Recapitulação Visual de PR

A Recapitulação Visual de PR é uma GitHub Action que transforma cada pull
request em uma **revisão de código visual**, sem que ninguém precise se
lembrar de rodar um comando manualmente. Esta página é para quem está
instalando, configurando ou protegendo essa Action. A cada push, um agente
de codificação com LLM roda a habilidade
[`visual-recap`](/docs/template-plan) empacotada mais recente (ou a cópia
commitada do seu repositório, quando `VISUAL_RECAP_SKILL_SOURCE=repo`)
sobre o diff do PR, publica um plano de recapitulação estruturado no
aplicativo Plans hospedado, mostra uma verificação informativa
`Visual Recap` enquanto roda, e cria ou atualiza **um único comentário fixo
de PR** que aponta para o plano interativo com uma **captura de tela
embutida** diretamente no comentário.

Isso não é um renderizador de diff determinístico. A action invoca um
agente de codificação real (CLI do Claude Code por padrão, CLI do OpenAI
Codex, ou Agent-Native Code com um provedor compatível com OpenAI) que lê a
mudança, decide o que importa e escreve a recapitulação chamando a
ferramenta MCP do Plans `create-visual-recap` — a mesma ferramenta que o
comando de barra `/visual-recap` usa. Você obtém uma visão de alto nível, em
blocos de schema/API/antes-depois da mudança, em vez de uma parede de diff
bruto.

A recapitulação é **informativa e não bloqueante**. Ela cria uma linha de
verificação para que os revisores vejam que a geração está em andamento,
mas não é uma verificação obrigatória, nunca bloqueia o PR e nunca substitui
a leitura do diff de fato. O comentário fixo é um auxílio de revisão, não
uma aprovação.

## O que ela faz

A cada push no PR, o workflow:

1. Coleta um diff limitado entre a base e o head do PR.
2. Cria uma verificação informativa `Visual Recap` no GitHub com
   `Visual recap in progress`.
3. Roda o agente de codificação configurado sobre esse diff. O agente lê as
   instruções da habilidade `visual-recap` empacotada (ou a cópia fixada no
   seu repositório) e escreve uma recapitulação, publicando-a com
   `create-visual-recap`.
4. Lê a URL do plano publicado que o agente escreveu em `recap-url.txt`.
5. Abre essa URL em um Chrome headless e captura o plano renderizado nos
   modos claro e escuro.
6. Envia os PNGs para uma rota de imagem pública assinada no aplicativo
   Plans.
7. Cria ou atualiza um único comentário fixo de PR que incorpora as
   capturas de tela **embutidas** com um elemento `<picture>` (servido pelo
   proxy de imagens camo do GitHub) ao lado do link para a recapitulação
   interativa.
8. Conclui a verificação `Visual Recap` como sucesso, ignorada ou neutra.

## Instalando

Ao instalar o Plans de forma interativa, o CLI do Agent-Native pergunta se
deseja adicionar Recapitulações Visuais de PR automáticas. Diga sim para
escrever a GitHub Action, ou adicione explicitamente a qualquer momento:

```bash
npx @agent-native/core@latest skills add visual-plan --with-github-action
```

Isso instala a habilidade `visual-plan` (que inclui a habilidade
`visual-recap` que a action executa) e escreve
`.github/workflows/pr-visual-recap.yml` no seu repositório. O workflow
chama **subcomandos publicados do CLI** por meio de
`npx @agent-native/recap-cli@latest recap <subcommand>` — incluindo `gate`,
`collect-diff`, `block-reference`, `scan`, `build-prompt`, `publish`,
`shot`, `comment`, `check` e `usage` — então nada é copiado para o seu
repositório como scripts auxiliares. `setup` e `doctor` são os auxiliares
interativos que você roda localmente; `gate` é a etapa de portão de
segurança que o workflow roda antes de cada recapitulação.

Depois rode o auxiliar de configuração guiada:

```bash
npx @agent-native/recap-cli@latest recap setup
npx @agent-native/recap-cli@latest recap doctor
```

O `recap setup` atualiza o workflow, usa o `gh` para definir
secrets/variáveis da GitHub Action quando os valores estão disponíveis a
partir do ambiente ou do armazenamento local de token de publicação do
Plans, e imprime os comandos exatos que faltam para o que não conseguir
definir. Os valores de secret são enviados ao `gh` pelo stdin, não por
argumentos de comando. Faça o commit do arquivo de workflow gerado e abra
um PR para vê-lo rodar.

Por padrão, o workflow monta o prompt do agente a partir das instruções
mais recentes da habilidade `visual-recap` empacotada em
`@agent-native/recap-cli@latest`, incluindo quaisquer arquivos de
referência complementares que a habilidade traga. Se seu repositório
personaliza e fixa intencionalmente sua pasta commitada `visual-recap`,
defina a variável de repositório `VISUAL_RECAP_SKILL_SOURCE=repo`.

## Seleção de executor

O workflow roda em executores `ubuntu-latest` hospedados pelo GitHub por
padrão. Para usar um executor hospedado diferente ou seu próprio executor
auto-hospedado, defina a variável de repositório ou organização
`VISUAL_RECAP_RUNS_ON` com uma string JSON válida ou um array JSON de
rótulos de executor:

```text
"ubuntu-latest"
["self-hosted", "linux", "x64", "visual-recap"]
```

As aspas do JSON são obrigatórias. Essa configuração seleciona o executor
completo do job `recap`. Para configurá-la durante a configuração guiada,
passe o mesmo valor JSON para `--runs-on`, depois valide o workflow e a
disponibilidade do executor com `doctor`:

```bash
npx @agent-native/recap-cli@latest recap setup --runs-on '["self-hosted","linux","x64","visual-recap"]'
npx @agent-native/recap-cli@latest recap doctor
```

O portão de segurança leve usa por padrão, separadamente, o
`ubuntu-latest` hospedado pelo GitHub. Repositórios que desativam os
executores hospedados pelo GitHub podem definir
`VISUAL_RECAP_GATE_RUNS_ON` com **um único rótulo de executor simples**
(não JSON), ou passar `--gate-runs-on visual-recap-gate` durante a
configuração. O workflow reutilizável expõe o mesmo valor como sua entrada
`gate-runs-on`. Isso evita analisar JSON dinâmico antes de o GitHub
conseguir agendar o portão. O rótulo personalizado só é selecionado para
PRs do mesmo repositório, de autoria de um `OWNER`, `MEMBER` ou
`COLLABORATOR`. Forks e todos os outros autores são forçados ao
`ubuntu-latest` hospedado pelo GitHub antes de o job começar; em um
repositório apenas auto-hospedado, essas execuções não confiáveis podem
ficar sem agendamento em vez de tocar uma máquina auto-hospedada.

O `recap doctor` rejeita JSON malformado ou não suportado e informa quando
o GitHub não expõe um executor online correspondente a cada rótulo
configurado. Registro, instalação, upgrades, capacidade e manutenção do
executor continuam sendo sua responsabilidade; o Agent-Native seleciona os
rótulos, mas não fornece nem opera o executor.

**Segurança:** prefira executores auto-hospedados dedicados e efêmeros. Um
executor de portão personalizado recebe apenas eventos de PR confiáveis do
mesmo repositório. O portão padrão não faz checkout da árvore do PR; ele
avalia a lógica do workflow e os metadados do PR no GitHub. Uma máquina
persistente ainda retém estado de processo entre jobs, então não a
compartilhe com cargas de trabalho não relacionadas. O workflow falha de
forma fechada antes de disparar qualquer portão auto-hospedado ou job
completo de recapitulação para autores não confiáveis de PRs públicos ou de
fork. Não enfraqueça esse limite nem encaminhe contribuições não confiáveis
para um executor persistente.

## Seleção de backend

Escolha qual agente de codificação roda a habilidade com a variável de
repositório `VISUAL_RECAP_AGENT`:

| `VISUAL_RECAP_AGENT` | Agente de codificação                   | Chave de API necessária | Variáveis necessárias                         |
| --------------------- | --------------------------------------- | ----------------------- | ---------------------------------------------- |
| `claude` _(padrão)_   | CLI do Claude Code                      | `ANTHROPIC_API_KEY`     | —                                              |
| `codex`               | CLI do OpenAI Codex                     | `OPENAI_API_KEY`        | —                                              |
| `openai-compatible`   | Agent-Native Code + provedor compatível | `VISUAL_RECAP_API_KEY`  | `VISUAL_RECAP_BASE_URL`, `VISUAL_RECAP_MODEL`  |

Se a variável não estiver definida, a action usa `claude`.

## Modelo e raciocínio

Além do backend, estas variáveis de repositório ajustam como o agente roda:

- **`VISUAL_RECAP_MODEL`** fixa o modelo passado ao CLI (`--model`) — por
  exemplo, `gpt-5.6-luna` para o Codex, um id de modelo Claude, ou
  `deepseek-chat` para o DeepSeek. É obrigatório para `openai-compatible`.
  Para o backend **Claude**, deixá-la indefinida agora usa por padrão
  `claude-sonnet-5`; defina a variável explicitamente para usar um modelo
  Claude diferente, como o mais barato `claude-haiku-4-5`. Para o backend
  **Codex**, deixá-la indefinida usa o próprio modelo padrão do CLI do
  Codex.
- **`VISUAL_RECAP_REASONING`** define a profundidade de raciocínio: `none`,
  `minimal`, `low`, `medium`, `high` ou `xhigh`. Ela se aplica ao backend
  Codex; o raciocínio do Claude é orientado pelo modelo, então essa
  variável é ignorada ali.
- **`VISUAL_RECAP_BASE_URL`** seleciona a URL base HTTP(S) para o backend
  `openai-compatible`. Use o endpoint compatível com OpenAI do provedor,
  como DeepSeek ou Kimi, sem embutir credenciais na URL.
- **`VISUAL_RECAP_SKILL_SOURCE`** controla a atualidade do prompt:
  `auto`/indefinido usa as instruções mais recentes da habilidade
  empacotada, enquanto `repo` fixa na pasta de habilidade `visual-recap`
  commitada no repositório.

Por exemplo, para rodar a recapitulação no Codex com o GPT-5.6 Sol em
raciocínio alto, defina as variáveis de repositório
`VISUAL_RECAP_AGENT=codex`, `VISUAL_RECAP_MODEL=gpt-5.6-sol` e
`VISUAL_RECAP_REASONING=high`.

Para o DeepSeek, defina `VISUAL_RECAP_AGENT=openai-compatible`,
`VISUAL_RECAP_BASE_URL=https://api.deepseek.com/v1`,
`VISUAL_RECAP_MODEL=deepseek-chat`, e o secret `VISUAL_RECAP_API_KEY`. O
Kimi funciona da mesma forma, com sua própria URL base e id de modelo
compatíveis com OpenAI. Outros provedores compatíveis com OpenAI usam as
mesmas três configurações.

## Custo

Cada execução de recapitulação é uma sessão agêntica completa de um agente
de codificação lendo um diff real, não um resumo templado barato, então seu
custo acompanha a escolha do modelo e a frequência de execução:

- **Uma sessão completa por push no PR.** O gatilho padrão dispara em
  `synchronize`, então um PR que recebe dez pushes roda o agente dez vezes.
- **O PR inteiro a cada vez**, não apenas os commits desde a última
  execução — o custo escala com o tamanho total do PR, não com o diff
  incremental.
- **Entrada de diff limitada a ~600KB.** Isso limita o pior caso por
  execução, mas diffs grandes ainda custam significativamente mais que
  pequenos.
- **Uma nova tentativa automática em caso de falha**, o que pode
  praticamente dobrar o custo de uma execução que falha de forma
  transitória.

Para reduzir custo:

- **Fixe um modelo mais barato.** Para o Claude, defina
  `VISUAL_RECAP_MODEL=claude-haiku-4-5` para repositórios simples ou
  pequenos — é o tier mais barato da Claude; `claude-sonnet-5` (o padrão) é
  o tier equilibrado.
- **Mude para o Codex com um modelo mais barato.** Defina
  `VISUAL_RECAP_AGENT=codex` com `VISUAL_RECAP_MODEL=gpt-5.6-luna` (o tier
  mais barato do GPT-5.6) ou `gpt-5.6-terra` (tier intermediário), e defina
  `VISUAL_RECAP_REASONING=low` para cortar ainda mais o gasto com tokens de
  raciocínio. A profundidade de raciocínio só se aplica ao Codex.
- **Aponte para um provedor compatível com OpenAI mais barato.** Defina
  `VISUAL_RECAP_AGENT=openai-compatible` com
  `VISUAL_RECAP_BASE_URL`/`VISUAL_RECAP_MODEL`/`VISUAL_RECAP_API_KEY`
  apontando para DeepSeek, Kimi ou qualquer outro endpoint compatível com
  OpenAI.
- **Exija um rótulo explícito de PR.** Defina
  `VISUAL_RECAP_REQUIRED_LABELS=visual recap` para manter o workflow
  instalado, mas pular recapitulações até que um PR tenha esse rótulo. Use
  uma lista separada por vírgulas, como `visual recap,recap`, quando vários
  rótulos devem habilitar a recapitulação. Aplicar um rótulo listado
  desperta o workflow imediatamente.
- **Recapitule com menos frequência.** Edite o `on.pull_request.types` do
  workflow instalado de
  `[opened, synchronize, reopened, ready_for_review, labeled, closed]` para
  `[opened, ready_for_review, closed]`, para que ele recapitule apenas
  quando um PR abre e quando é mesclado, em vez de a cada push.

Toda execução registra o que realmente gastou: a etapa `recap usage` do
workflow anexa o uso de tokens e custo ao plano publicado, então você pode
olhar o gasto real por execução em vez de adivinhar.

## Secrets e variáveis {#secrets-and-variables}

Defina isto em **Settings → Secrets and variables → Actions** do seu
repositório.

### Secrets para o backend padrão

| Secret              | Finalidade                                                                                                                        |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `PLAN_RECAP_TOKEN`  | Token revogável gerado por `npx @agent-native/core@latest connect`. Autoriza publicar o plano de recapitulação e o envio da captura de tela. |
| `ANTHROPIC_API_KEY` | A chave de LLM para o backend padrão do Claude Code.                                                                              |

**Times: use um token de serviço da organização.** Um token pessoal fica
vinculado à pessoa que o gerou — se ela sair da organização ou revogar seus
tokens, todo repositório que usa esse secret começa a falhar com 401, e os
planos criados pelo CI passam a pertencer a essa pessoa em vez de ao time.
Um token de serviço da organização pertence à sua **organização**: ele age
como um principal de serviço (`svc-<name>@service.<orgId>`), sobrevive à
saída de qualquer indivíduo, as recapitulações que ele publica ficam
visíveis para a organização, e qualquer owner ou admin da organização pode
listá-lo ou revogá-lo. Gere um (apenas owner/admin da organização):

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --service-token pr-recap
```

O comando autentica você no navegador e depois imprime o token de serviço
exatamente uma vez — armazene-o como o secret `PLAN_RECAP_TOKEN`.
Gerencie-o depois com as actions `list-org-service-tokens` e
`revoke-org-service-token` no aplicativo Plans.

**Solo: um token pessoal ainda funciona.** Gere-o com
`npx @agent-native/core@latest connect` no seu aplicativo Plans. Para o
aplicativo hospedado, isso também escreve um arquivo local de token de
publicação que `npx @agent-native/recap-cli@latest recap setup` pode ler:

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --client codex
npx @agent-native/recap-cli@latest recap setup
```

Se preferir configurar manualmente, cole o token no secret do GitHub. Use
um placeholder como `plan_recap_xxxxxxxxxxxxxxxx` apenas para exemplos —
nunca faça commit de um token real.

## Captura de tela embutida no comentário

Depois que o agente publica a recapitulação, o workflow captura o plano
renderizado em Chrome headless nos modos claro e escuro e envia os PNGs
para uma rota de imagem pública assinada no aplicativo Plans. O comentário
fixo de PR então incorpora essas capturas de tela **embutidas** com um
elemento `<picture>` — o GitHub as reexibe pelo seu proxy camo, então os
revisores veem uma prévia que combina com o tema do GitHub deles diretamente
no comentário, sem precisar abrir nada. O link para o plano interativo
completo fica logo ao lado, para quando eles quiserem explorar, comentar ou
anotar.

## PRs de fork

### Comportamento padrão (nenhuma ação necessária)

O workflow principal `pr-visual-recap.yml` dispara no gatilho simples
`pull_request`, **não** em `pull_request_target`. PRs de fork, portanto,
rodam **sem acesso aos secrets do repositório**, então o workflow não
encontra `PLAN_RECAP_TOKEN` e não faz nada de forma limpa — sem publicação
falha, sem credenciais expostas. Recapitulações rodam automaticamente para
PRs de branches no mesmo repositório, onde os secrets estão disponíveis.

Isso também significa que você pode mesclar o arquivo do workflow **antes**
de os secrets existirem: sem um token configurado, toda execução é um
no-op silencioso até você definir os secrets. A etapa `gate` também pula
PRs em rascunho e PRs de autoria de bots automaticamente, então nenhum dos
dois dispara execuções de recapitulação por padrão.

### Habilitando o workflow de fork controlado por rótulo

Se você quiser gerar recapitulações para PRs de fork, um segundo arquivo de
workflow está disponível: `.github/workflows/pr-visual-recap-fork.yml`. Ele
usa `pull_request_target` (que roda com os secrets do repositório base),
mas nunca faz checkout nem executa código do fork. Autores de fork
confiáveis, com associação de autor do GitHub `OWNER`, `MEMBER` ou
`COLLABORATOR`, rodam automaticamente. PRs de fork externos exigem uma
**autorização explícita do mantenedor por head** por meio de um evento novo
do rótulo `recap` antes de o agente de recapitulação rodar.

Para instalá-lo, copie o arquivo de
[BuilderIO/agent-native](https://github.com/BuilderIO/agent-native/blob/main/.github/workflows/pr-visual-recap-fork.yml)
para a pasta `.github/workflows/` do seu repositório, ao lado do
`pr-visual-recap.yml` já existente. A mesma configuração de backend se
aplica, incluindo `VISUAL_RECAP_API_KEY`, `VISUAL_RECAP_BASE_URL` e
`VISUAL_RECAP_MODEL` ao usar um provedor compatível com OpenAI.

### Como funciona o portão de rótulo

1. Um contribuidor de fork abre um PR. O workflow normal `pull_request`
   pula porque o GitHub não fornece secrets para execuções de fork.
2. O workflow de fork verifica a associação de autor do PR. Autores
   confiáveis (`OWNER`, `MEMBER` ou `COLLABORATOR`) rodam automaticamente
   nos eventos de abertura, sincronização, reabertura e pronto-para-revisão.
3. Colaboradores externos exigem que um mantenedor revise o diff atual
   (especialmente por conteúdo com formato de prompt injection — veja
   abaixo) e depois aplique o rótulo `recap` ao PR.
4. O portão de rótulo para colaboradores externos é por head SHA: se o
   colaborador enviar mais commits, o próximo evento de sincronização pula
   até que um mantenedor remova e reaplique `recap` depois de revisar o
   novo diff.

### O que o workflow de fork faz e NÃO faz

| O workflow FAZ                                                                                                          | O workflow NÃO faz                                                                  |
| ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Faz checkout do **repositório base** na **ref da branch base** — apenas código confiável                                  | Fazer checkout ou executar qualquer código do fork                                    |
| Busca o head do fork como uma ref remota (`git fetch origin pull/<n>/head:refs/recap/fork-head`) — buscar commits é seguro | Instalar pacotes do fork, rodar scripts do fork, ou avaliar conteúdo do fork como código |
| Roda `git diff base...refs/recap/fork-head` — diff de texto puro entre dois objetos já buscados                           | Usar o diff como qualquer coisa além de entrada de texto para o LLM                    |
| Roda a habilidade visual-recap e a configuração de agente do **repositório base**                                         | Carregar qualquer habilidade ou configuração do fork                                  |
| Passa o diff pela mesma etapa de varredura de secrets (fail-closed) que PRs de primeira parte                             | Pular a varredura de secrets                                                          |
| Adiciona uma nota explícita de reforço de prompt ao prompt do agente, marcando o conteúdo do diff como não confiável      | Conceder ao agente qualquer permissão além do agente de recapitulação normal          |

### Por que você deve revisar o diff antes de rotular

O diff do fork é texto controlado por um invasor em potencial, que o agente
de recapitulação lê como entrada. Um diff cuidadosamente elaborado poderia
conter conteúdo de prompt injection — por exemplo, linhas de diff que se
parecem com instruções de agente — com a intenção de fazer o agente de
recapitulação realizar ações não pretendidas (por exemplo, exfiltrar o
token de publicação ou produzir conteúdo de recapitulação enganoso).

Antes de aplicar o rótulo `recap`, examine o diff em busca de:

- Linhas que parecem comandos diretos ou instruções de papel ("Ignore
  previous instructions...", "You are now...", "Write the token to...").
- Nomes de arquivo incomuns que poderiam ser lidos por engano como prompts
  de sistema.
- Conteúdo codificado em arquivos adicionados que poderia se decodificar em
  instruções.

Essas mitigações já estão em camadas no workflow (varredura de secrets,
portão de caminhos sensíveis, nota de reforço de prompt, lista de
permissões restrita de ferramentas do agente), mas a revisão do rótulo é a
principal linha de defesa.

### Relação com o workflow principal

Os dois arquivos de workflow são independentes. Para atualizações de PR
que não são de fork, `pr-visual-recap.yml` é o único workflow que roda.
Para PRs de fork, o workflow normal sai no seu portão de fork, e
`pr-visual-recap-fork.yml` roda automaticamente para autores confiáveis da
mesma organização ou depois de um rótulo `recap` novo do mantenedor para
colaboradores externos. Eles compartilham o mesmo marcador de comentário
fixo e o encadeamento por id de plano, então tanto PRs quanto PRs de fork
produzem um único comentário criado ou atualizado no mesmo PR.

### Proteção contra automodificação {#self-modifying-guard}

A etapa `gate` pula a recapitulação inteiramente quando um PR toca qualquer
um dos caminhos a seguir, para que um PR nunca possa reescrever o workflow,
a habilidade ou a configuração de agente que o job confiável de
recapitulação carrega e exfiltrar secrets:

| Padrão de caminho                          | Motivo                                     |
| ------------------------------------------- | ------------------------------------------- |
| `.github/workflows/pr-visual-recap.yml`     | O próprio workflow                          |
| `**/skills/visual-(recap\|plan\|plans)/**`  | A habilidade visual-recap que o agente segue |
| `**/.claude/**`                             | Configurações de agente que o runner carrega |
| `**/CLAUDE.md`                              | Instruções de agente que o runner carrega    |
| `**/AGENTS.md`                              | Instruções de agente que o runner carrega    |
| `**/.mcp.json`                              | Configuração de servidor MCP que o runner carrega |

No monorepo `BuilderIO/agent-native`, o workflow roda o CLI de
recapitulação a partir do código-fonte confiável da branch base, em vez do
código-fonte do head do PR. Isso mantém mudanças normais de pacote,
incluindo `packages/core/**`, elegíveis para recapitulações sem executar
código de CLI modificado pelo PR.

## Modo de privacidade de arquivos locais

A GitHub Action é projetada para revisão de PR hospedada e compartilhável.
Se você quiser uma recapitulação sem enviar o conteúdo dela ao banco de
dados do Agent-Native Plan, rode o mesmo fluxo auxiliar localmente, no modo
de arquivos locais:

```bash
npx @agent-native/recap-cli@latest recap collect-diff --base main --head HEAD --out recap.diff --stat recap.stat
npx @agent-native/recap-cli@latest recap scan --diff recap.diff
npx @agent-native/recap-cli@latest recap build-prompt --pr 123 --diff recap.diff --stat recap.stat --local-files --local-dir plans/pr-123-visual-recap
```

Entregue o `recap-prompt.md` gerado ao seu agente de codificação. No modo
de arquivos locais, o prompt instrui o agente a escrever
`plans/pr-123-visual-recap/plan.mdx` mais arquivos visuais opcionais, e
então rodar:

```bash
npx @agent-native/core@latest plan local serve --dir plans/pr-123-visual-recap --kind recap --open
```

A URL retornada abre a UI hospedada do Plan enquanto o navegador lê o MDX
da recapitulação por uma ponte localhost. O conteúdo da recapitulação não é
escrito no banco de dados hospedado do Plan, e a URL só funciona na máquina
que roda a ponte. Se você rodar o aplicativo Plan localmente com o mesmo
`PLAN_LOCAL_DIR`, a rota `/local-plans/pr-123-visual-recap` também é
válida. Pastas apoiadas em repositório podem abrir como
`/local-plans/pr-123-visual-recap?path=plans%2Fpr-123-visual-recap`. Esse
modo desativa o comentário fixo hospedado do PR, o envio da captura de tela
embutida, o anexo de uso e os comentários do navegador até você publicar
explicitamente.

## É informativo, não um portão

A recapitulação é um auxílio de revisão em camada sobre o fluxo normal de
PR:

- Ela mostra uma linha de verificação `Visual Recap` para visibilidade, mas
  **nunca é uma verificação obrigatória** e nunca bloqueia a mesclagem.
- Uma falha de geração ou publicação é concluída de forma neutra e aparece
  como um comentário fixo explicativo, não como um X vermelho em código
  não relacionado.
- A recapitulação e sua captura de tela **não implicam que o diff foi
  revisado**. Os revisores ainda precisam ler as linhas realmente
  alteradas.

## Fixação de versão (variante de cópia) {#version-pinning-copy-variant}

Por padrão, o workflow na variante de cópia instala
`@agent-native/recap-cli@latest` em tempo de execução, para que toda
execução de recapitulação use automaticamente o CLI mais recente. Se seu CI
precisa de ferramentas reprodutíveis, defina a variável de repositório
**`RECAP_CLI_VERSION`** para fixar a versão instalada:

1. Vá em **Settings → Secrets and variables → Actions → Variables** do seu
   repositório.
2. Crie uma variável chamada `RECAP_CLI_VERSION` com um valor como `1.5.0`.

A variável é opcional. Deixe-a indefinida (ou defina como `latest`) para
acompanhar o lançamento mais recente.

Para a variante de chamador reutilizável, use a entrada `cli-version` em
vez disso (veja [Fixação de versão](#version-pinning) na seção
reutilizável).

## Lista de permissões da varredura de secrets

Antes de publicar uma recapitulação, o workflow roda
`npx @agent-native/recap-cli@latest recap scan` para detectar possíveis
secrets no diff. Qualquer PR cujo diff corresponda a um padrão conhecido de
secret é bloqueado com um comentário explicativo — a recapitulação não é
publicada, e nenhum conteúdo do diff é enviado ao agente de codificação.

Em casos raros, um repositório tem fixtures de teste intencionais ou
strings não secretas que se parecem superficialmente com padrões de
secret (por exemplo, uma chave de fixture em um arquivo de teste). Para
suprimir um falso positivo, crie `.github/recap-scan-allowlist` na raiz do
seu repositório.

### Formato

Cada linha não vazia e que não seja comentário é uma **substring literal**
ou um padrão **`/regex/flags`**:

```
# Lines starting with # are comments.

# Literal substring — any diff line containing this string is allowed.
sk-test-fixture1234567890abcdef

# Regex pattern — written as /pattern/flags (JS syntax).
/^.STRIPE_KEY=sk-test-/i

# Another literal.
EXAMPLE_API_KEY=placeholder-value
```

Regras:

- Uma linha é **suprimida** (permitida) quando contém o literal, ou quando
  a linha inteira corresponde ao regex.
- O arquivo é **fail-closed**: se estiver ausente, nenhuma supressão se
  aplica — o scanner se comporta como antes.
- Um arquivo vazio equivale a nenhum arquivo.
- Linhas de regex malformadas são tratadas como strings literais.

A lista de permissões só é consultada pelo portão de varredura de secrets.
Ela não afeta o que o agente de codificação pode ler — se o portão passar,
o agente recebe o diff completo de qualquer forma.

## Adotando como um workflow reutilizável

### Por que usar a variante reutilizável?

O instalador padrão copia o YAML completo do workflow, com ~360 linhas,
para o seu repositório (a opção **cópia**). Essa é a escolha certa para
repositórios air-gapped ou que precisam auditar cada linha do que roda. A
desvantagem é que correções de bugs e melhorias nunca chegam até você — é
preciso rodar `npx @agent-native/recap-cli@latest recap setup` manualmente
depois de cada lançamento.

A opção **reutilizável** escreve um chamador fino de ~20 linhas em vez
disso. Ele delega para
`BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml` via
`uses:`. Todo chamador recebe automaticamente a lógica mais recente quando
o workflow roda, sem necessidade de atualização local.

|                                        | Cópia (padrão)              | Reutilizável                     |
| --------------------------------------- | ---------------------------- | ---------------------------------- |
| Tamanho do workflow no seu repositório  | ~360 linhas                  | ~20 linhas                         |
| Recebe correções automaticamente        | Não — rode `recap setup` de novo | Sim                             |
| Air-gap / auditabilidade completa       | Sim                          | Não                                 |
| Pode ser fixado em uma versão específica | Somente editando localmente  | Sim — defina `@v1.2.3` em `uses:` |

### Trecho do chamador

Isto é o que `npx @agent-native/recap-cli@latest recap setup --reusable`
escreve (ou você pode colar manualmente):

```yaml
name: PR Visual Recap

# Thin caller — the full workflow logic lives in BuilderIO/agent-native.
# Fixes and improvements reach this repo automatically on each run.
# To pin a specific version for reproducibility replace '@main' with a
# tag or SHA, e.g. '@v1.2.3' or '@abc1234'.

on:
  pull_request:
    types: [opened, synchronize, reopened, ready_for_review, labeled, closed]

jobs:
  visual-recap:
    if: github.event.action != 'labeled' || vars.VISUAL_RECAP_REQUIRED_LABELS != ''
    permissions:
      actions: write
      contents: read
      checks: write
      issues: write
      pull-requests: write
    uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@main
    secrets:
      PLAN_RECAP_TOKEN: ${{ secrets.PLAN_RECAP_TOKEN }}
      ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
      OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
      VISUAL_RECAP_API_KEY: ${{ secrets.VISUAL_RECAP_API_KEY }}
      PLAN_RECAP_APP_URL: ${{ secrets.PLAN_RECAP_APP_URL }}
    with:
      agent: ${{ vars.VISUAL_RECAP_AGENT || 'claude' }}
      model: ${{ vars.VISUAL_RECAP_MODEL || '' }}
      base-url: ${{ vars.VISUAL_RECAP_BASE_URL || '' }}
      reasoning: ${{ vars.VISUAL_RECAP_REASONING || '' }}
      skill-source: ${{ vars.VISUAL_RECAP_SKILL_SOURCE || 'auto' }}
      runs-on: ${{ vars.VISUAL_RECAP_RUNS_ON || '"ubuntu-latest"' }}
      gate-runs-on: ${{ vars.VISUAL_RECAP_GATE_RUNS_ON || 'ubuntu-latest' }}
      required-labels: ${{ vars.VISUAL_RECAP_REQUIRED_LABELS || '' }}
      # cli-version: "latest"  # pin to a specific @agent-native/recap-cli version
```

Os mesmos secrets e variáveis descritos em
[Secrets e variáveis](#secrets-and-variables) se aplicam — defina-os nas
configurações do seu repositório da mesma forma que na variante de cópia.
O chamador reutilizável encaminha `VISUAL_RECAP_RUNS_ON` pela sua entrada
JSON `runs-on` para o job completo de recapitulação, `VISUAL_RECAP_GATE_RUNS_ON`
pela sua entrada de rótulo simples `gate-runs-on` para o portão somente de
metadados, e `VISUAL_RECAP_REQUIRED_LABELS` por `required-labels` para o
controle opcional por rótulo de PR. A entrada de executor do portão só é
usada para autores confiáveis do mesmo repositório; outros PRs usam o
`ubuntu-latest` hospedado pelo GitHub. Omitir as entradas de executor
preserva seus padrões `ubuntu-latest`; omitir rótulos obrigatórios preserva
o comportamento automático de recapitulação.

### Instalando pelo CLI

```bash
# Write the thin caller instead of the full copy:
npx @agent-native/recap-cli@latest recap setup --reusable

# Or with a pinned ref for reproducibility:
npx @agent-native/recap-cli@latest recap setup --reusable --ref v1.2.3
```

As duas variantes escrevem o workflow em
`.github/workflows/pr-visual-recap.yml`. Se já existir um workflow ali e
ele for diferente, o comando recusa e informa que é preciso passar
`--force` para sobrescrever.

Depois de escrever, rode `npx @agent-native/recap-cli@latest recap doctor`
normalmente para confirmar que os secrets estão configurados.

### Fixação de versão {#version-pinning}

Por padrão, o chamador referencia `@main`, que sempre usa a versão
publicada mais recente do workflow reutilizável. Para repositórios de
produção que precisam de CI reprodutível, fixe em uma tag ou SHA:

```yaml
uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@v1.2.3
```

A entrada `cli-version` controla qual versão do `@agent-native/recap-cli`
roda dentro do workflow — deixe-a em `"latest"` para acompanhar o
lançamento mais recente, ou fixe-a em uma string de versão (por exemplo,
`"1.5.0"`) para reprodutibilidade completa.

### Contexto do evento workflow_call

Workflows `workflow_call` herdam o contexto de evento do **chamador**. O
workflow reutilizável usa expressões `github.event.pull_request.*` para ler
o número do PR, o SHA do head, o SHA da base, o timestamp de mesclagem e os
metadados do PR — isso funciona corretamente apenas quando o chamador
dispara em `pull_request`. O trecho de chamador acima já inclui os tipos de
evento corretos. O evento `closed` é incluído para que recapitulações de
PRs mesclados possam ser marcadas com `merged_at` e depois pesquisadas
como trabalho entregue.

Não dispare o chamador em `workflow_dispatch` ou `push` — esses eventos não
carregam um payload `pull_request`, e o portão vai pular a recapitulação
com "no pull_request payload".
