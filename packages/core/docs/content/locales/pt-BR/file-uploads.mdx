# Uploads de arquivos

A estrutura fornece uma abstração de upload de arquivo que roteia os uploads por meio de um provedor configurável. Os modelos chamam `uploadFile()` e recebem um URL de volta. O back-end de armazenamento pode ser trocado sem alterar o código do aplicativo.

## Como funciona {#how-it-works}

As solicitações de upload vão para `POST /_agent-native/file-upload`, que despacha para o provedor ativo. Você pode verificar qual provedor está configurado em `GET /_agent-native/file-upload/status`.

A ordem de resolução do provedor é:

1. **Provedores registrados pelo usuário**: provedores personalizados registrados por meio de `registerFileUploadProvider()`.
2. **Provedor Builder.io**: integrado, e é ativado automaticamente quando o Builder.io está conectado.
3. **Nenhum provedor**: o upload é rejeitado e o chat exibe uma chamada para ação de configuração de armazenamento. Dados binários nunca são persistidos no SQL.

Entre os provedores registrados pelo usuário, vence o primeiro que for registrado e relatar a si mesmo como configurado. `registerFileUploadProvider()` é idempotente por `id`. Registrar com um id já em uso substitui o provedor existente.

A interface decide se deve exibir um aviso de configuração de armazenamento usando apenas a verificação síncrona `isConfigured()`, antes de uma tentativa de upload. O upload em si verifica tanto `isConfigured()` quanto `isConfiguredForRequest()`. Um provedor que só relata a si mesmo como configurado por meio de `isConfiguredForRequest()` permanece invisível para o aviso de configuração, mesmo que uploads por meio dele tenham sucesso.

## Armazenamento necessário para uploads duráveis {#storage-required}

Quando nenhum provedor está configurado, `uploadFile()` retorna `null` e a rota multipart retorna `503`. Os anexos do chat permanecem disponíveis apenas para a solicitação atual, o agente recebe uma dica de configuração de armazenamento, e a transcrição armazena um marcador de configuração em vez do payload binário. Esse comportamento de falha segura mantém o SQL pequeno e torna visível a configuração ausente.

## Hospedagem Builder.io {#builder-hosting}

Quando seu aplicativo está conectado ao Builder.io, os uploads de arquivos são roteados automaticamente para a hospedagem de ativos do Builder. O nível gratuito do Builder.io inclui esse armazenamento gerenciado. Os arquivos são servidos a partir de um CDN sem necessidade de configuração, e o URL durável é armazenado na conversa do chat para que turnos posteriores possam reutilizá-lo. Esta é a configuração de produção recomendada.

## Provedores personalizados {#custom-providers}

A estrutura já vem com um provedor integrado para armazenamento compatível com
S3 (AWS S3, Cloudflare R2, MinIO e similares). Conecte-o com variáveis de
ambiente ou pela lista de integração da barra lateral. Nenhum código é
necessário. Veja [Integração](/docs/onboarding).

Registre um provedor personalizado apenas para um tipo diferente de back-end.
Este exemplo faz upload por meio de uma API HTTP genérica usando `fetch()`:

```ts filename="server/plugins/file-upload.ts"
import { registerFileUploadProvider } from "@agent-native/core/file-upload";
import { defineNitroPlugin } from "@agent-native/core/server";

export default defineNitroPlugin(() => {
  registerFileUploadProvider({
    id: "my-storage",
    name: "My Storage",
    isConfigured: () => !!process.env.UPLOAD_ENDPOINT,
    upload: async ({ data, filename, mimeType }) => {
      const endpoint = process.env.UPLOAD_ENDPOINT!;
      const body = new FormData();
      body.append("file", new Blob([data], { type: mimeType }), filename);

      // This example assumes an upload API that accepts a multipart file
      // and returns { url }. Adjust the request and response handling to
      // match your own provider's actual contract.
      const response = await fetch(endpoint, { method: "POST", body });
      if (!response.ok) {
        throw new Error(`Upload failed with status ${response.status}`);
      }

      const { url } = await response.json();
      return { url, provider: "my-storage" };
    },
  });
});
```

Use `resolveSecret()` de `@agent-native/core/server` em vez de uma variável de
ambiente quando o provedor precisar de uma credencial real, como uma chave de
API. Veja [Segurança — Gerenciamento de segredos](/docs/security#secrets).

## API de upload {#upload-api}

A interface `FileUploadProvider`:

```ts
interface FileUploadProvider {
  id: string; // Unique id, e.g. "s3"
  name: string; // Human-readable name
  isConfigured: () => boolean; // True when ready from sync runtime state
  isConfiguredForRequest?: () => Promise<boolean>; // True from scoped DB secrets
  upload: (input: FileUploadInput) => Promise<FileUploadResult>;
}

interface FileUploadInput {
  data: Uint8Array | Buffer; // File contents
  filename?: string; // Original filename
  mimeType?: string; // MIME type, e.g. "image/png"
  ownerEmail?: string; // For request-scoped provider credentials
  stableUrl?: boolean; // Builder.io hint: one stable URL while compression finishes
  recordAsset?: boolean; // Builder.io hint: set false to skip the asset library
}

interface FileUploadResult {
  url: string; // Public URL for the uploaded file
  id?: string; // Provider-specific id
  provider: string; // Which provider handled it
}
```

Use `uploadFile()` de `@agent-native/core/file-upload` em actions ou código do servidor:

```ts
import { uploadFile } from "@agent-native/core/file-upload";

const result = await uploadFile({
  data: fileBuffer,
  filename: "photo.jpg",
  mimeType: "image/jpeg",
});

if (result) {
  // Provider handled it. result.url is the public URL.
} else {
  // No provider configured. Show the storage setup CTA, or skip.
}
```

## Uploads retomáveis / com streaming {#resumable}

Um provedor pode, opcionalmente, implementar um bloco `resumable` em `FileUploadProvider` para uploads que precisam transmitir dados ao armazenamento à medida que chegam, em vez de armazenar em buffer o arquivo inteiro primeiro. O modelo Clips usa isso para retransmitir uma gravação ao armazenamento em blocos, enquanto ela ainda está sendo gravada, em vez de montar o blob completo depois que o gravador para.

```ts
interface FileUploadProvider {
  // ...id, name, isConfigured, upload...

  resumable?: {
    startSession(
      filename: string,
      mimeType: string,
      maxBytes: number,
    ): Promise<ResumableUploadSession>;
    relayChunk(
      session: ResumableUploadSession,
      contentRange: string,
      bytes: Uint8Array,
      options?: { mimeType?: string },
    ): Promise<ResumableChunkResult>;
    completeSession(
      session: ResumableUploadSession,
      filename: string,
      options?: { stableUrl?: boolean; recordAsset?: boolean },
    ): Promise<string>;
    // Best-effort provider cleanup for a session the caller will not resume.
    abortSession?(session: ResumableUploadSession): Promise<void>;
  };
}

interface ResumableUploadSession {
  sessionId: string; // Provider-specific: GCS Location URI, S3 UploadId, etc.
  meta: Record<string, unknown>; // Provider state carried between calls
}

interface ResumableChunkResult {
  ok: boolean;
  status: number;
  updatedMeta?: Record<string, unknown>; // Merged back into the stored session
}
```

Quando `resumable` está presente, os chamadores que transmitem dados (como um gravador) chamam `startSession` uma vez, `relayChunk` repetidamente à medida que os bytes chegam, e `completeSession` quando o stream termina. Isso substitui a única chamada em buffer `upload()`. Um provedor sem um bloco `resumable` só vê o caminho em buffer. Implemente isso apenas quando seu back-end de armazenamento tiver uma API nativa de upload em blocos/retomável (S3 multipart, uploads retomáveis do GCS etc.) que valha a pena expor.
