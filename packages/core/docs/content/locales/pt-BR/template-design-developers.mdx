# Guia do desenvolvedor

Esta página é para qualquer pessoa que esteja personalizando o template Design ou construindo diretamente sobre ele: o início rápido, todas as actions, o modelo de dados, uma action explicada passo a passo, a superfície de rotas e como adicionar a ela. Veja [Design](/docs/template-design) para o que o aplicativo faz.

## Início rápido

<Steps>

### Crie o aplicativo

```bash
npx @agent-native/core@latest create my-design --standalone --template design
cd my-design
pnpm install
```

Isso requer [Node.js](https://nodejs.org) 22.22 ou posterior e
[pnpm](https://pnpm.io) instalados primeiro. Veja [Primeiros
passos](/docs/getting-started) se você ainda não instalou nenhum dos dois,
ou não tem uma conexão LLM (Builder.io, uma chave Anthropic/OpenAI, ou
Ollama local) configurada. Para um workspace com o Design junto com outros
aplicativos, execute `npx @agent-native/core@latest create my-platform` e
escolha Design durante a configuração.

### Inicie o servidor de desenvolvimento

```bash
pnpm dev
```

O aplicativo abre em `http://localhost:8099`, a porta de desenvolvimento
padrão do Design. O Design funciona completamente sem conexões externas.
Você só vai encontrar um prompt de conexão se tentar uma importação do
Figma ou o Full App Building antes de configurá-los.

</Steps>

## Modelo de dados

Todos os dados residem em SQL via Drizzle ORM. Esquema: `templates/design/server/db/schema.ts`. Designs e sistemas de design carregam o `ownableColumns` padrão e uma tabela de compartilhamentos correspondente do framework, então eles se encaixam no modelo de compartilhamento por usuário/por organização.

A tabela abaixo cobre os principais recursos com proprietário: designs, arquivos, templates, versões e sistemas de design.

| Tabela                                   | O que contém                                                                                                                                     |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `designs`                                | Um projeto de design — `title`, `description`, `project_type` (`prototype` / `other`), o blob JSON `data`, e um link opcional `design_system_id` |
| `design_files`                           | Arquivos individuais pertencentes a um design (`filename`, `content`, `file_type` com padrão `html`)                                             |
| `design_templates`                       | Metadados reutilizáveis de template, dimensões, padrões, referência ao design de origem e contagem de camadas travadas                           |
| `design_template_files`                  | Arquivos de template em snapshot, copiados para um design normal editável quando um usuário começa a partir de um template                       |
| `design_template_shares`                 | Tabela de compartilhamentos do framework para descoberta de templates privados, da organização, explicitamente compartilhados e públicos         |
| `design_versions`                        | `snapshot`s pontuais de um design com um `label` opcional, para histórico e reversão                                                             |
| `design_systems`                         | Tokens de marca reutilizáveis — `data` (cores/tipografia/espaçamento), `assets`, `custom_instructions`, e uma flag `is_default`                  |
| `design_shares` / `design_system_shares` | Tabelas de compartilhamentos do framework mapeando principais (usuários ou organizações) para funções (visualizador, editor, administrador)      |

Um projeto de design é um shell até ter conteúdo: `create-design` cria uma linha vazia (`data: "{}"`), e então `generate-design` grava os arquivos HTML/JSX independentes reais. O artefato gerado, a fonte editável e cada exportação vêm todos do mesmo HTML, então não existe um formato separado de "mockup de IA" para traduzir. Um sistema de design vinculado fornece tokens e `custom_instructions` que o agente respeita em cada passagem de geração.

Mais sete tabelas dão suporte a funcionalidades cobertas em outras partes desta página, em vez do modelo de recursos principal: `design_localhost_connections` e `design_localhost_write_grants` dão suporte à [importação de app local](/docs/template-design-features#import), `component_index` dá suporte à [seção de Componente da aba Design](/docs/template-design-features#design-tab), `motion_timeline` dá suporte à linha do tempo de movimento editável de cada elemento (o dock de Motion no editor), `design_state` armazena estados alternativos nomeados, fixtures estáticas e capturas de app ao vivo para um design, `design_fusion_edits` dá suporte à fila de edições de fusion descrita em [Full App Building](#full-app-building) acima, e `design_review_snapshot` armazena em cache os achados de acessibilidade e o diff visual por trás de `get-design-review`, descrito em [Qualidade](#quality) acima.

Os comentários e threads de revisão persistidos (`get-review-feedback`, `resolve-review-thread`, e o restante) não são uma tabela específica do Design: são o sistema de revisão compartilhado do framework, de `@agent-native/core/review` (`agent_review_comments` / `agent_review_statuses`), com escopo para um design da mesma forma que qualquer aplicativo pode anexá-lo. Veja [Aba Comentários](/docs/template-design-features#comments-tab) para o comportamento voltado ao usuário.

## Uma action explicada passo a passo

`save-design-as-template` mostra padrões que vale a pena reutilizar em qualquer action: rejeitar um formato de entrada não suportado antes de fazer qualquer trabalho, proteger contra salvar nada, remapear ids uma única vez em vez de em cada leitor, e gravar em duas tabelas em uma transação para que um template nunca fique com metadados mas sem arquivos.

## Modelo do editor

O Design prioriza a visão geral para trabalhos com várias telas. Depois da
geração ou de atualizações amplas, o editor abre a visão geral de telas:
uma tela infinita onde cada tela é um frame estático que você pode
selecionar, mover, redimensionar, soltar ou duplicar. Use o botão de
visualização completa de um frame quando uma tela precisar de rolagem
focada ou interação de protótipo.

O modo de tela única serve para rolar, interagir com o comportamento do
protótipo e editar as camadas DOM/código dentro de um arquivo renderizado.
O painel de camadas reflete essa divisão: telas são frames de nível
superior, com camadas DOM/código aninhadas para a tela ativa.

Cada tela é um único documento renderizado em larguras diferentes, não
cópias separadas por breakpoint: um frame base (o mais largo) é herdado em
cascata, e as edições feitas em um breakpoint ativo mais estreito
persistem como substituições com escopo de largura sobre ele.

## Extensões do editor

O editor inclui uma aba de inspetor **Extensions** depois de **Tweaks**.
Ela funciona como uma faixa de plugins específica do Design: os usuários
podem clicar em **+ Extension** para pedir ao agente que construa uma
extensão, ou instalar uma extensão que declare o slot
`design.editor.inspector`, usando as actions do framework
`create-extension`, `add-extension-slot-target` e `install-extension`, não
uma action específica do Design.

As extensões do Design são renderizadas inline ao lado do artboard pelo
sandbox padrão de extensões. O host passa `window.slotContext` e
atualizações de `window.onSlotContext(...)` com o `designId` atual,
arquivo ativo, lista de telas, ids de telas selecionadas, metadados do
elemento selecionado, modo de visualização, zoom, ferramenta ativa e
valores de tweaks. Isso permite que uma extensão mostre informações sobre
a seleção atual, ofereça controles de estilo ou construa fluxos de
trabalho compactos ao redor do design aberto.

Para trabalho determinístico, as extensões podem chamar actions do
aplicativo pelo bridge de extensões. Para mudanças guiadas por IA, faça a
extensão chamar `agentNative.chat.send(...)` com o seletor/id de origem do
elemento selecionado e a mudança solicitada. O agente deve chamar
`view-screen` primeiro, e depois usar `apply-visual-edit` para mudanças de
estilo, classe, texto ou movimento de elementos, ou `update-design` /
`generate-design` com `canvasFrames` para mudanças de posicionamento do
artboard. Veja [Extensions](/docs/extensions#capabilities) para o sandbox,
o estado persistente e as APIs do bridge.

## Personalizando

O Design é um template completo e clonável. Algumas ideias práticas de
extensão:

- "Adicione um sistema de design de e-commerce reutilizável com nossos tokens e componentes de amostra."
- "Adicione uma etapa de exportação que envie o ZIP para nosso sistema interno de revisão."
- "Deixe-me colar o HTML de uma landing page existente e pedir ao agente três versões mais fortes."
- "Adicione uma biblioteca de prompts salvos para briefings de página de produto, dashboard e telas de onboarding."
- "Adicione um preset personalizado de exportação em PDF para revisão das partes interessadas."

O agente edita rotas, componentes, actions e modelos apoiados por SQL conforme necessário. Veja [Apps](/docs/cloneable-saas) para o fluxo completo de clonar, personalizar e implantar, e [Primeiros passos](/docs/getting-started) se este for seu primeiro template nativo do agente.
