# Render

<Badge label="Beta" color="orange" icon="rocket" />

O Render hospeda o seu app como um serviço web, então não há nenhum servidor para configurar ou manter em execução.
O Render executa o mesmo servidor Node.js descrito no
[guia de Node.js](/docs/node-js), faz o build a partir do seu repositório Git e dá
ao app um endereço público com HTTPS.

Este guia mostra como implantar um app independente do zero. Você vai
criar o app e enviá-lo para um repositório Git, dar a ele um banco de dados de produção
e um segredo de autenticação, preparar o banco de dados e, depois, criar um serviço web do Render
que faz o build e executa o app.

<Callout tone="info">

É necessário o Node.js `22.22+`.

</Callout>

Você também precisa de uma conta do Render e de um repositório no GitHub, GitLab ou Bitbucket.
Execute os comandos deste guia no seu próprio computador. O Render faz o build e executa o
app a partir do seu repositório.

## Passo 1: Crie o app {#step-1-create-the-app}

Crie o seu novo app independente. O exemplo abaixo cria um app a partir do template Chat,
mas você pode começar de qualquer template. Entre na pasta do app e
instale as dependências. `corepack enable` ativa a versão do `pnpm` que o app
espera, então você não precisa instalar o `pnpm` por conta própria.

```bash
npx --yes @agent-native/core@latest create my-app --standalone --template chat

cd my-app

corepack enable

pnpm install
```

Se quiser, substitua `my-app` pelo nome do seu app. O restante deste guia
considera que você está dentro da pasta do app.

O Render faz o build do app a partir de um repositório Git, então envie a pasta do app para um novo
repositório no GitHub, GitLab ou Bitbucket antes de continuar. Inclua também o arquivo
`pnpm-lock.yaml` no commit, porque o build instala as versões exatas que
ele lista.

## Passo 2: Configure os segredos do ambiente {#step-2-configure-environment-secrets}

O app lê as configurações de produção a partir de variáveis de ambiente:

| Variável             | Obrigatória | Finalidade                                                           |
| -------------------- | ----------- | -------------------------------------------------------------------- |
| `DATABASE_URL`       | Sim         | Conecta o app ao seu banco de dados PostgreSQL                       |
| `BETTER_AUTH_SECRET` | Sim         | Assina as sessões dos usuários                                       |
| `BETTER_AUTH_URL`    | Não         | Define o endereço público que as pessoas usam para acessar o seu app |

Os exports abaixo fazem os comandos seguintes funcionarem neste shell. Antes de
implantar, salve essas mesmas variáveis nas configurações de ambiente do projeto ou serviço do seu host.
O Passo 4 mostra como salvá-las no Render.

### URL do banco de dados {#database-url}

Durante o desenvolvimento local, o app armazena os dados em um banco de dados local quando
`DATABASE_URL` não está definida. Um app implantado precisa de um banco de dados PostgreSQL real que
mantenha os dados entre implantações. O Render substitui os arquivos do serviço a cada
implantação e reinicialização, então o banco de dados precisa ficar fora do serviço web. Copie a
string de conexão do seu provedor e exporte-a:

```bash
export DATABASE_URL='your-postgres-url-string'
```

Os [guias de provedores de banco de dados](/docs/neon) mostram onde encontrar a string de conexão
de cada provedor. O Render Postgres também funciona. Use aqui a string de conexão
externa dele e, nas configurações do serviço web, a string de conexão interna.

<Callout tone="warning">

Escolha um provedor de PostgreSQL persistente, como Neon, Supabase ou Amazon RDS.

</Callout>

### Segredo de autenticação {#auth-secret}

Gere este valor uma única vez e mantenha-o igual em todas as implantações.

O app usa `BETTER_AUTH_SECRET` para assinar as sessões dos usuários. Se ele mudar, todos os
usuários conectados são desconectados. O comando abaixo gera um valor aleatório:

```bash
export BETTER_AUTH_SECRET="$(openssl rand -hex 32)"
```

Salve o valor gerado em um lugar seguro, como um gerenciador de senhas. Use o
mesmo valor sempre que implantar.

### URL pública {#public-url}

É opcional. Defina-a ao usar um domínio personalizado, um proxy reverso ou um fluxo de autenticação ou OAuth
que precise de uma origem pública fixa.

`BETTER_AUTH_URL` é o endereço público que as pessoas usam para acessar o seu app. Sem
ela, o app descobre o próprio endereço a partir de cada requisição recebida. Isso normalmente
funciona bem no endereço que o Render fornece, mas defina-a quando conectar um domínio
personalizado, para que os links de login e os redirecionamentos de OAuth usem esse domínio.

```bash
export BETTER_AUTH_URL='https://your-domain.example'
```

## Passo 3: Execute as migrações {#step-3-migrate}

As migrações criam e atualizam as tabelas de que o app precisa no seu banco de dados. Execute
isto antes da primeira implantação:

```bash
pnpm migrate:production
```

O comando é executado no seu computador e se conecta ao banco de dados de produção com
a `DATABASE_URL` que você exportou no Passo 2. Execute-o novamente depois de atualizar o
app e antes de implantar a nova versão.

Em uma instância paga do Render, você pode definir o **Pre-Deploy Command** do serviço como
`pnpm migrate:production`. Assim, o Render executa as migrações antes que cada
implantação entre no ar. O Pre-Deploy Command não está disponível no tipo de instância
Free.

## Passo 4: Crie o serviço web {#step-4-create-the-web-service}

No painel do Render, crie um novo **Web Service** e conecte o
repositório do Passo 1. Use estas configurações:

| Configuração  | Valor                                                                                     |
| ------------- | ----------------------------------------------------------------------------------------- |
| Language      | `Node`                                                                                    |
| Branch        | A branch a partir da qual você implanta, como `main`                                      |
| Build Command | `corepack enable && pnpm install --frozen-lockfile && NITRO_PRESET=render_com pnpm build` |
| Start Command | `node .output/server/index.mjs`                                                           |

O Build Command ativa a versão do `pnpm` do app, instala as dependências
listadas em `pnpm-lock.yaml` e faz o build do app. `NITRO_PRESET=render_com` faz o build
do mesmo servidor Node.js do guia de Node.js, configurado para servir os próprios arquivos
estáticos. O Start Command executa esse servidor. O Render informa ao servidor qual porta
usar por meio da variável de ambiente `PORT`, e o servidor a lê
automaticamente.

Em **Environment Variables**, adicione `DATABASE_URL` e `BETTER_AUTH_SECRET`
com os valores que você exportou no Passo 2. Se você definir `BETTER_AUTH_URL`, adicione-a
da mesma forma.

O Render escolhe a versão do Node.js a partir da variável de ambiente `NODE_VERSION`, de um arquivo
`.node-version` ou `.nvmrc` ou do campo `engines` do `package.json`, nessa
ordem. Serviços novos usam por padrão uma versão que atende ao requisito acima.
Para fixar uma versão, adicione `NODE_VERSION`, por exemplo com o valor `24`.

## Passo 5: Implante {#step-5-deploy}

<Steps>

### Escolha um tipo de instância

Escolha o tipo de instância do serviço web. O tipo de instância Free serve para
experimentar o app. Escolha um tipo de instância pago se o app precisar responder
imediatamente ou se você quiser usar o Pre-Deploy Command do Passo 3.

### Crie o serviço web

Crie o serviço web. O Render faz o build do app a partir do seu repositório e o
inicia. O primeiro build leva alguns minutos, e você pode acompanhá-lo nos
logs do serviço.

### Abra o app

Quando a implantação termina, o painel mostra o endereço do app, que termina em
`onrender.com`. Abra-o e crie a primeira conta.

</Steps>

No tipo de instância Free, o Render pausa o serviço depois de 15 minutos sem
tráfego. A próxima visita então espera cerca de um minuto enquanto o serviço é
iniciado novamente.

## Implante atualizações {#deploy-updates}

O Render implanta novamente sempre que você faz push para a branch que escolheu no Passo 4. Para
publicar uma nova versão, execute primeiro as migrações e depois faça o push:

```bash
pnpm migrate:production

git push
```

As configurações do serviço e as variáveis salvas continuam no lugar, então você não precisa
repetir o Passo 4.
