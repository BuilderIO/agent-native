# Internacionalização

Os aplicativos Agent Native podem localizar a UI da estrutura e dos modelos por
meio do tempo de execução `@agent-native/core/client/i18n` compartilhado. A
estrutura armazena a escolha de idioma do usuário nas configurações do SQL, a
expõe como actions e recorre ao inglês quando um aplicativo ainda não traduziu
uma string.

## Tempo de execução

Use o provedor por meio de `AppProviders`:

```tsx
import { AppProviders } from "@agent-native/core/client/hooks";
import { getLocaleInitScript } from "@agent-native/core/client/i18n";
import { i18nCatalog } from "./i18n";

const LOCALE_INIT_SCRIPT = getLocaleInitScript();

<script
  data-agent-native-locale-init
  dangerouslySetInnerHTML={{ __html: LOCALE_INIT_SCRIPT }}
/>;

<AppProviders queryClient={queryClient} i18n={{ catalog: i18nCatalog }}>
  <Outlet />
</AppProviders>;
```

`getLocaleInitScript()` define o `lang`, o `dir` e o
`window.__AGENT_NATIVE_LOCALE__` iniciais antes de o React hidratar. As rotas
públicas SSR podem chamar `resolveLocaleFromRequest()` de
`@agent-native/core/server` e passar a localidade/catálogo resolvidos para
esse script, evitando incompatibilidades de hidratação.

## Catálogos

Cada modelo localizado mantém catálogos em `app/i18n/`:

```ts filename="app/i18n/index.ts"
import { createAgentNativeI18nCatalog } from "@agent-native/core/client/i18n";
import enUS from "./en-US";

export const i18nCatalog = createAgentNativeI18nCatalog({
  messages: enUS,
  localeLoaders: {
    "zh-CN": () => import("./zh-CN"),
    "zh-TW": () => import("./zh-TW"),
    "es-ES": () => import("./es-ES"),
    "fr-FR": () => import("./fr-FR"),
    "de-DE": () => import("./de-DE"),
    "ja-JP": () => import("./ja-JP"),
    "ko-KR": () => import("./ko-KR"),
    "pt-BR": () => import("./pt-BR"),
    "hi-IN": () => import("./hi-IN"),
    "ar-SA": () => import("./ar-SA"),
  },
});
```

`messages` empacota `en-US` diretamente, de modo que ele fica sempre
disponível antes de qualquer localidade carregar. `localeLoaders` faz import
dinâmico de todos os outros catálogos, para que os usuários baixem apenas a
localidade ativa. Os códigos de localidade suportados são `en-US`, `zh-CN`,
`zh-TW`, `es-ES`, `fr-FR`, `de-DE`, `ja-JP`, `ko-KR`, `pt-BR`, `hi-IN` e
`ar-SA`.

Essa lista é fixada pela estrutura. Não é apenas o que este exemplo escolheu
empacotar. `LocaleCode` é uma union do TypeScript com exatamente esses
códigos, e `set-localization-preference` rejeita qualquer outro valor em
tempo de execução. Cada localidade também precisa de metadados curados pela
estrutura, como a direção do texto para idiomas da direita para a esquerda.
Adicionar uma nova localidade significa estender a própria estrutura, não
adicionar um arquivo de catálogo ao seu aplicativo.

`createAgentNativeI18nCatalog` também aceita um `sourceLocale` opcional, cujo
padrão é `en-US`, e um array `supportedLocales` opcional. Defina
`supportedLocales` quando um aplicativo enviar traduções para apenas algumas
das localidades da estrutura, em vez de todas as dez. O padrão é usar todas
as localidades que a estrutura suporta. `LanguagePicker` lista apenas as
localidades desse conjunto, e qualquer localidade detectada ou solicitada
fora dele recorre a `sourceLocale`.

## UI

Use `useT()` para traduzir strings de interface:

```tsx
import { useT } from "@agent-native/core/client/i18n";

function Greeting({ name }: { name: string }) {
  const t = useT();
  return <p>{t("greeting.hello", { name })}</p>;
}
```

Use `useFormatters()` para datas, números, tempo relativo e listas. Não
coloque formatação de data/número sensível à localidade dentro de strings de
tradução.

Coloque `<LanguagePicker />` em qualquer lugar do aplicativo em que o usuário
possa alterar o idioma. Consulte [Kit de configurações](/docs/toolkit-settings)
para o padrão de página de configurações, incluindo onde
`openAgentSettings()` se encaixa.

## Actions e persistência

Todo aplicativo herda:

- `get-localization-preference` — lê o `{ locale, timezone }` do usuário atual
- `set-localization-preference` — define `locale` e/ou `timezone`, cada um opcional

`locale` é `"system"` ou uma localidade BCP-47 suportada. `timezone` é
`"system"` ou um fuso IANA, como `America/New_York`. Ele existe para que o
trabalho agendado e de automação seja executado no fuso do usuário, e não no
do host. Definir apenas um campo deixa o outro inalterado, porque
`set-localization-preference` faz merge sobre o valor armazenado existente,
em vez de sobrescrevê-lo.

O valor durável reside nas configurações SQL com escopo de usuário, em
`localization`. O `localStorage` é usado apenas para pré-hidratação e reserva
anônima. A localidade ativa é espelhada no estado do aplicativo como
contexto ambiente, para que os agentes possam ver o idioma atual da
interface.

## Guarda

Execute:

```bash
pnpm guard:i18n-catalogs
```

Para catálogos de aplicativos e modelos, a guarda verifica:

- Nomes de arquivo de localidade, paridade de chaves, paridade de placeholders e chaves obsoletas
- Chaves duplicadas e marcadores remanescentes usados apenas em desenvolvimento
- Contaminação de script incorreto, por exemplo texto em chinês dentro de um catálogo em árabe
- Categorias plurais CLDR por meio de `Intl.PluralRules`
- Chamadas de `t()` no código-fonte do aplicativo cuja chave está ausente no catálogo em inglês

A guarda verifica a estrutura, não a qualidade da tradução. Strings de alta
visibilidade ainda precisam de revisão humana.

Não traduza identificadores estáveis, como nomes de actions, rotas, valores
de enum, chaves de estado do aplicativo, valores de banco de dados, campos de
protocolo, nomes de variáveis de ambiente ou nomes de provedor.
