# Servidor

O diretório `server/` é a camada de infraestrutura de um aplicativo nativo do agente. Ele cuida de tarefas de inicialização, autenticação e das superfícies HTTP que as actions não cobrem. A maior parte do comportamento do produto pertence a [Actions](/docs/actions-overview). O servidor é o que torna essas actions disponíveis.

## Onde o servidor se encaixa {#role}

Em um aplicativo web tradicional, o servidor é onde reside a maior parte da lógica. Regras de negócio, acesso a dados e apresentação acontecem todos dentro dos manipuladores de rota. Aplicativos nativos do agente funcionam de forma diferente. A lógica reside nas actions, que o agente e a UI compartilham como parceiros iguais. O trabalho do servidor é de coordenação: executar migrações de banco de dados, configurar a autenticação, montar o loop do agente e cuidar do conjunto restrito de questões HTTP que as actions não conseguem expressar sozinhas.

Requisições do navegador, o loop do agente e clientes de API externos passam todos pelo mesmo servidor Nitro e leem do mesmo banco de dados SQL. Não existe um backend separado para o agente ou para a UI. A camada de servidor é o que expõe as actions para o mundo externo.

## O que há no diretório server/ {#server-directory}

Estes são os diretórios e arquivos dentro de `server/` que todo aplicativo nativo do agente inclui. Cada um corresponde a uma parte específica da camada de servidor: o que ela faz, quando recorrer a ela e como se conecta ao restante da estrutura.

| Página                                      | O que aborda                                                                                                  |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| **[Banco de dados](/docs/server-database)** | Definição de esquema com os auxiliares `table()`, `getDb` e os padrões de tabelas ownable                     |
| **[Middleware](/docs/server-middleware)**   | Guardas de autenticação em `server/middleware/` e por que rodam ali em vez de num plugin                      |
| **[Plugins](/docs/server-plugins)**         | Plugins de inicialização para auth e agent-chat, além de migrações de BD opcionais do app                     |
| **[Rotas](/docs/server-routes)**            | Rotas baseadas em arquivo, o catch-all de SSR e como restringir rotas personalizadas ao usuário da requisição |

## Nitro {#nitro}

[Nitro](https://nitro.build) é o conjunto de ferramentas de servidor que sustenta a camada HTTP nativa do agente. A maior parte do que você configura em `server/` é Nitro: rotas baseadas em arquivo, plugins de inicialização e middleware.

- **Roteamento baseado em arquivo**: o nome do arquivo mapeia diretamente para um método HTTP e um caminho de URL, sem necessidade de registro. `server/routes/api/health.get.ts` se torna `GET /api/health` automaticamente. Consulte [Rotas](/docs/server-routes) para mais detalhes.
- **Plugins**: código registrado na inicialização do servidor e carregado uma vez. Os helpers do framework inicializam auth e agent-chat; migrações opcionais do app podem ainda estar em execução quando a primeira requisição chegar. Consulte [Plugins](/docs/server-plugins) para mais detalhes.
- **Middleware**: código que roda em toda requisição recebida antes de ela chegar a uma rota. A guarda de autenticação fica em `server/middleware/`. Consulte [Middleware](/docs/server-middleware) para mais detalhes.

O Nitro também é agnóstico quanto à implantação. O mesmo aplicativo é implantado em Node.js, Cloudflare Workers, Netlify, Vercel e outros runtimes sem nenhuma alteração de código. Basta definir um preset. Consulte [Implantação](/docs/deployment).

A API de requisição/resposta subjacente é o [H3](https://h3.unjs.io). Quando você vir `defineEventHandler`, `createError` ou `getQuery` em rotas personalizadas, isso é H3. Os [docs do Nitro](https://nitro.build/guide) e os [docs do H3](https://h3.unjs.io) são a referência para tudo o que a estrutura não cobre diretamente.

## Prefira Actions primeiro {#actions-first}

A arquitetura do Agent Native é diferente. Sempre que pensar em um novo recurso para o seu aplicativo, considere primeiro se ele pode ser uma action. Por exemplo, se a UI e o agente precisam fazer a mesma coisa, defina uma action em vez de uma rota de API personalizada. As actions se tornam automaticamente:

- Ferramentas do agente.
- Ganchos tipados de frontend.
- Endpoints HTTP em `/_agent-native/actions/:name`.
- Ferramentas chamáveis por MCP e A2A.
- Comandos CLI para desenvolvimento.

Use rotas `/api/*` personalizadas apenas quando precisar de um protocolo em forma de rota ou de comportamento binário/streaming. Para mais detalhes, consulte [Actions](/docs/actions-overview).

## O que vem a seguir {#whats-next}

- [**Actions**](/docs/actions-overview): a superfície de operação padrão. Recorra a uma rota personalizada apenas quando ela não se encaixar.
- [**Banco de dados**](/docs/server-database): o padrão `getDb()`/esquema que rotas personalizadas e actions importam
- [**Middleware**](/docs/server-middleware): guardas de autenticação e o diretório `server/middleware/`
- [**Plugins**](/docs/server-plugins): plugins de inicialização para migrações, auth e o agente
- [**Rotas**](/docs/server-routes): rotas baseadas em arquivo, contexto da requisição e o catch-all de SSR
