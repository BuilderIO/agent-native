# Trabalhos recorrentes

Um **trabalho recorrente** é um prompt executado em uma programação cron. É assim que o agente faz as coisas por conta própria: “todas as manhãs às 7h, resume meus e-mails noturnos”, “todas as segundas-feiras posto os números de inscrição da semana passada para Slack”, “a cada hora verifica se há rascunhos obsoletos e os exclui”.

<Callout tone="info">

**Recurring Jobs** é o nome antigo para automações **Scheduled**. **Automations** abrange **Scheduled** e **Event**. `jobs/` e `manage-jobs` permanecem para integrações antigas apenas agendadas. Use `manage-automations` e **Settings › Automations** para novos trabalhos pessoais ou da organização, incluindo modelo e listas MCP.

</Callout>

Os trabalhos recorrentes são acionados em um relógio. Para reagir a _eventos_ (uma reserva criada, um e-mail recebido) — mesmo formato de arquivo `jobs/` mais condições — consulte [Automations](/docs/automations).

Os trabalhos ficam no [Recursos do Agente](/docs/agent-resources) em `jobs/<name>.md` — apenas um arquivo Markdown com frontmatter YAML. Sem registro, sem fiação. Solte o arquivo e a estrutura o pegará.

É isso. O corpo é um prompt que o agente executa em cada disparo agendado. O agente tem acesso a todas as mesmas ferramentas e contexto do agente que possui em um chat interativo: actions, skills, memória, servidores MCP conectados, subagentes.

## Princípio {#frontmatter}

| Campo        | Tipo                               | Padrão          | Descrição                                                                                                                          |
| ------------ | ---------------------------------- | --------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `schedule`   | expressão cron                     | _(obrigatório)_ | Cron padrão de 5 campos. `"0 7 * * *"` = todos os dias às 07h00; `"0 */4 * * *"` = a cada 4 horas.                                 |
| `enabled`    | booleano                           | `true`          | Mude para `false` para pausar sem excluir o trabalho.                                                                              |
| `runAs`      | `"creator"` \| `"shared"`          | `"creator"`     | `"creator"` é executado com a identidade do proprietário do trabalho e `ANTHROPIC_API_KEY`. `"shared"` usa a chave da organização. |
| `createdBy`  | e-mail                             | _(automático)_  | Preenchido quando o trabalho é criado por meio do recursos do agente UI ou pelo agente.                                            |
| `orgId`      | string                             | _(automático)_  | Escopo da organização; herdado da organização ativa do criador.                                                                    |
| `lastRun`    | Carimbo de data e hora ISO         | _(gerenciado)_  | Escrito pelo agendador após cada execução.                                                                                         |
| `lastStatus` | `"success"` \| `"error"` \| …      | _(gerenciado)_  | Resultado mais recente.                                                                                                            |
| `lastError`  | string                             | _(gerenciado)_  | Mensagem de erro se a última execução falhou.                                                                                      |
| `nextRun`    | Carimbo de data e hora ISO         | _(gerenciado)_  | Calculado a partir de `schedule`; usado pelo agendador para decidir quando disparar em seguida.                                    |
| `mcpTools`   | matriz de nomes de ferramentas MCP | _(nenhum)_      | Lista de permissões explícita opcional, como `mcp__server__tool`; as credenciais permanecem na concessão MCP conectada.            |

Os campos `last*` e `nextRun` são gravados pelo agendador. Você pode lê-los para ver o histórico, mas não os edite manualmente: a próxima execução será substituída.

## Conectar ferramentas MCP a um trabalho {#connected-mcps}

Trabalhos recorrentes podem usar ferramentas MCP remotas ou locais que já estejam conectadas ao aplicativo. Peça ao agente para descobrir os nomes exatos com `tool-search` e, em seguida, associe apenas as ferramentas de que o trabalho precisa usando `mcpTools`:

```md
---
schedule: "0 * * * *"
enabled: true
mcpTools:
  ["mcp__meeting-notes__list_recordings", "mcp__meeting-notes__get_transcript"]
---

Encontre novas gravações desde a última execução bem-sucedida. Extraia apenas acompanhamentos acionáveis e, em seguida, chame uma vez a ação de importação limitada do aplicativo com IDs de origem e externos estáveis, uma citação curta e a URL da gravação. Não importe a transcrição completa.
```

O trabalho armazena nomes de ferramentas, não URLs MCP, tokens de acesso ou tokens de atualização OAuth. Em tempo de execução, o framework resolve a concessão conectada no contexto de solicitação do criador ou da organização do trabalho e expõe apenas as ferramentas da lista de permissões. Mantenha a lista restrita e use uma ação idempotente do aplicativo para a importação final, para que execuções sobrepostas não criem duplicatas. Consulte [Clientes MCP](/docs/mcp-clients) para a configuração de conexão e OAuth.

## Sintaxe do Cron {#cron}

Cron padrão de 5 campos (minuto, hora, dia do mês, mês, dia da semana):

| Cron           | Significado                 |
| -------------- | --------------------------- |
| `*/5 * * * *`  | A cada 5 minutos            |
| `0 * * * *`    | De hora em hora             |
| `0 */4 * * *`  | A cada 4 horas              |
| `0 7 * * *`    | Todos os dias às 07:00      |
| `0 9 * * 1`    | Toda segunda-feira às 09:00 |
| `0 17 * * 1-5` | Dias úteis às 17h           |
| `0 0 1 * *`    | Primeiro dia de cada mês    |

A estrutura inclui utilitários cron (`isValidCron()` e `describeCron()`) para validar e renderizar strings cron, usados internamente pelas camadas de recurso e agendador.

## Criando um trabalho {#creating}

### Na interface Automations

Abra **Settings › Automations** e crie uma automação **Scheduled**. Links antigos para `/agent#jobs` redirecionam para lá.

### Na guia Espaço de trabalho

`+` → **Tarefa agendada** no painel da área de trabalho. Preencha o prompt e agende. Salva como `jobs/<slug>.md` e começa a ser executado no próximo tick correspondente.

### Perguntando ao agente

> "Crie uma tarefa agendada que resuma meus e-mails não lidos todas as manhãs às 7."

O agente grava o arquivo para você.

### Manualmente

Solte um arquivo Markdown em `jobs/` por meio do recurso APIs da estrutura:

```ts
import { resourcePut } from "@agent-native/core/resources";

await resourcePut(
  ownerEmail,
  "jobs/morning-digest.md",
  `---
schedule: "0 7 * * *"
enabled: true
---
Summarize overnight emails.`,
);
```

## Como o agendador é executado {#how-scheduler-runs}

A cada tick, o agendador (a rotina interna `processRecurringJobs()`) encontra os trabalhos vencidos e os executa. O que dispara o tick depende de onde o app é executado:

| Host                                                              | O que dispara o tick                                                                       | Requisitos e limites                                                                                                    |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| Servidor de longa duração (Node.js, Docker, Fly, Render, uma VPS) | Um temporizador em processo a cada 60 segundos, começando 10 segundos após a inicialização | Funciona enquanto o processo estiver ativo.                                                                             |
| [Netlify](/docs/netlify)                                          | Uma função agendada emitida pelo build, a cada minuto                                      | Somente implantações publicadas, nunca Deploy Previews ou implantações de branch. O build precisa de `A2A_SECRET`.      |
| [Vercel](/docs/vercel#vercel-scheduled-work)                      | Um cron job da Vercel adicionado pelo build, a cada minuto por padrão                      | Somente a implantação de produção. Precisa de `CRON_SECRET`. Projetos Hobby podem executá-lo no máximo uma vez por dia. |
| [Cloudflare Workers](/docs/cloudflare#cloudflare-scheduled-work)  | Um Cron Trigger que o build adiciona ao `wrangler.json`, a cada minuto                     | Precisa de `A2A_SECRET` como segredo do Worker.                                                                         |
| AWS Lambda                                                        | Nada                                                                                       | Automações agendadas não são disparadas.                                                                                |
| Desenvolvimento local                                             | Nada, a menos que você opte por ativar                                                     | Veja o aviso abaixo.                                                                                                    |

Na Netlify, na Vercel e no Cloudflare, o mesmo tick também esvazia a fila de
automações acionadas por eventos, limpa execuções cuja função foi interrompida e
executa varreduras de apps, como o adiamento e o envio programado do Mail. Uma
implantação serverless sem gatilho não recebe nada disso: automações acionadas
por eventos ficam esperando na fila e execuções interrompidas continuam travadas.
Automações acionadas por webhook e o **Run now** são despachados por conta
própria, então continuam funcionando. Quando uma implantação não consegue
disparar agendamentos, a página **Automations** avisa e informa o motivo.

<Callout id="doc-block-j6yn07" tone="risk">

**Uma instância aquecida não executa agendamentos.** Hosts serverless nunca iniciam o temporizador em processo, então pings de keep-alive não fazem os trabalhos dispararem. Só o gatilho da plataforma na tabela acima faz isso. No AWS Lambda, nada os dispara ainda, então execute automações agendadas em um host de longa duração (Fly, Render, uma VPS).

</Callout>

<Callout id="doc-block-rj2" tone="warning">

**Desativado por padrão no desenvolvimento local.** O loop `setInterval` do agendador nunca inicia quando `NODE_ENV` é `development` ou `test`, ou quando a URL do app aponta para `localhost` / `127.0.0.1` / `*.localhost` — o que cobre a maioria das configurações de desenvolvimento local. Defina `AGENT_NATIVE_ENABLE_LOCAL_RECURRING_JOBS=1` para executar o agendador localmente mesmo assim. Para desligar os trabalhos agendados em qualquer host, use `AGENT_NATIVE_DISABLE_RECURRING_JOBS=1`, descrito a seguir.

</Callout>

<Callout id="doc-block-rj3" tone="warning">

**`AGENT_NATIVE_DISABLE_RECURRING_JOBS` é lido em dois escopos.** Na Netlify, na Vercel e no Cloudflare, quem decide é o ambiente de **build**: o gatilho da plataforma continua disparando para esvaziar a fila de automações por evento e limpar execuções, mas um build com a chave ligada pula os trabalhos agendados, independentemente do que diga o ambiente implantado. Em um servidor de longa duração, o ambiente de **runtime** controla o temporizador em processo. Defina-o onde o seu host o lê. O build registra sua decisão, então a página **Automations** pode dizer que os agendamentos nunca serão executados, em vez de mostrar uma data de próxima execução que nada vai cumprir.

</Callout>

## Depurando um trabalho {#debugging}

- Abra os detalhes da automação em **Settings › Automations**, ou abra `jobs/<name>.md` na área de trabalho — o frontmatter mostra `lastRun`, `lastStatus`, `lastError`, `nextRun`.
- **Teste sem esperar:** clique em **Run now** em **Settings › Automations**, ou peça ao agente para executá-lo (`manage-automations` com `action=run-now`). O prompt do trabalho é executado imediatamente com seus efeitos colaterais reais, e `nextRun` não muda. A exceção é um trabalho que o framework pausou: uma execução bem-sucedida o reativa e recalcula `nextRun`. Run now não espera um tick do agendador, então também funciona em localhost sem `AGENT_NATIVE_ENABLE_LOCAL_RECURRING_JOBS` e em hosts sem gatilho do agendador.
- **Pause:** vire `enabled: false`. O arquivo permanece no mesmo lugar, apenas para de ser executado.

## Ferramenta de agente {#agent-tool}

Uma única ferramenta `manage-jobs` é registrada em cada modelo. O parâmetro `action` seleciona a operação:

| Ação     | Parâmetros                                                                       | Propósito                                                                        |
| -------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `create` | `name`, `schedule`, `instructions` (obrigatório); `scope`, `runAs`, `mcpTools`   | Crie um novo trabalho recorrente                                                 |
| `list`   | `scope` (`personal`, `shared` ou todos)                                          | Liste todos os trabalhos com status (agendado, ativado, última/próxima execução) |
| `update` | `name` (obrigatório); `schedule`, `instructions`, `enabled`, `runAs`, `mcpTools` | Editar um trabalho existente                                                     |
| `delete` | `name` (obrigatório)                                                             | Exclua um trabalho — sempre confirme primeiro com o usuário                      |

**Escopo pessoal versus compartilhado.** Cada automação está no escopo pessoal ou da organização e executa como seu criador. Administradores podem gerenciar definições compartilhadas, mas não alterar a identidade do criador. Antes de cada execução da organização, o framework verifica se o criador existe e continua membro.

## Diferente do pacote de agendamento {#vs-scheduling-package}

Não confunda trabalhos recorrentes com `@agent-native/scheduling`:

- **Trabalhos recorrentes (esta página)** — _prompts_ agendados em cron que o agente executa em segundo plano. Nível de estrutura. Mora no recursos do agente. Dispara em qualquer host com um agendador (veja [Como o agendador é executado](#how-scheduler-runs)).
- **`@agent-native/scheduling`** — um pacote de domínio reutilizável para criar recursos de calendário/reserva (tipos de eventos, janelas de disponibilidade, reservas). Ativa o modelo `calendar` e superfícies de agendamento personalizadas.

Trabalhos recorrentes são "como faço para o agente agir por conta própria?" O pacote de agendamento é "como faço para construir um aplicativo de calendário?" Preocupações diferentes.
