# डेटाबेस

हर एजेंट-नेटिव ऐप अपनी स्थिति SQL में संग्रहीत करता है। UI और एजेंट दोनों एक ही [Drizzle ORM](https://orm.drizzle.team) क्लाइंट का उपयोग करते हुए, एक ही Actions के माध्यम से एक ही तालिकाओं को पढ़ते और लिखते हैं। लाइव सिंक SSE का उपयोग करता है और पोलिंग को fallback के रूप में रखता है, इसलिए बदलाव दूसरे surface में manual refresh के बिना दिखाई देते हैं।

## होस्टिंग विकल्प {#hosting}

ऐप `DATABASE_URL` से पता लगाता है कि किस बैकएंड का उपयोग करना है। जब वेरिएबल सेट नहीं होता, तो यह एक स्थानीय SQLite फ़ाइल पर वापस आ जाता है ताकि आप बिना किसी सेटअप के शुरुआत कर सकें।

### डिफ़ॉल्ट: SQLite फ़ाइल {#default-sqlite}

जब `DATABASE_URL` सेट नहीं है, तो ऐप `data/app.db` पर एक SQLite डेटाबेस बनाता है। किसी कॉन्फ़िगरेशन की आवश्यकता नहीं है। डेव सर्वर शुरू करें और फ़ाइल पहले रन पर बन जाती है।

यह केवल स्थानीय विकास के लिए है। कंटेनर, सर्वर रहित फ़ंक्शन, और पूर्वावलोकन वातावरण पुनरारंभ के बीच अपने फ़ाइल सिस्टम को रीसेट कर सकते हैं, इसलिए स्थानीय SQLite फ़ाइल गायब हो सकती है। तैनाती से पहले `DATABASE_URL` को स्थायी होस्ट किए गए डेटाबेस पर सेट करें।

### स्थानीय Postgres: PGlite {#local-pglite}

Docker या होस्ट किए गए डेटाबेस के बिना Postgres बोली के विरुद्ध स्थानीय रूप से विकास करने के लिए, वैकल्पिक PGlite पैकेज इंस्टॉल करें और `DATABASE_URL` सेट करें:

```bash
pnpm add @electric-sql/pglite@^0.5.3
```

```bash
DATABASE_URL=pglite:./data/pglite
```

[PGlite](https://pglite.dev/) एक इन-प्रोसेस WASM Postgres डेटाबेस चलाता है। यह आपको तैनाती से पहले Postgres-केवल स्कीमा समस्याओं को पकड़ने देता है, जबकि सेटअप को SQLite डिफ़ॉल्ट जितना ही सरल रखता है। SQLite की तरह, यह भी केवल-स्थानीय संग्रहण है। इसे उत्पादन या साझा वातावरण के लिए उपयोग न करें।

### उत्पादन डेटाबेस {#production}

होस्ट किए गए डेटाबेस को कनेक्ट करने के लिए अपनी `.env` फ़ाइल या डिप्लॉय-प्रदाता वातावरण में `DATABASE_URL` सेट करें:

```bash
# Neon Postgres
DATABASE_URL=postgres://user:pass@ep-cool-name-123456.us-east-2.aws.neon.tech/mydb?sslmode=require

# Supabase Postgres
DATABASE_URL=postgres://postgres.xxxx:pass@aws-0-us-east-1.pooler.supabase.com:6543/postgres

# सादा Postgres
DATABASE_URL=postgres://user:pass@localhost:5432/mydb

# Turso (libSQL). इसके लिए DATABASE_AUTH_TOKEN भी आवश्यक है।
DATABASE_URL=libsql://my-db-org.turso.io
```

फ्रेमवर्क URL प्रीफ़िक्स से बोली का स्वतः पता लगाता है और तदनुसार Drizzle को कॉन्फ़िगर करता है।

### Builder.io प्रबंधित डेटाबेस {#builder-managed}

_योजनाबद्ध (अभी तक उपलब्ध नहीं):_ Builder.io से कनेक्ट होने पर, आपका ऐप स्वचालित रूप से प्रावधानित एक प्रबंधित डेटाबेस का उपयोग करने में सक्षम होगा, बिना किसी कनेक्शन स्ट्रिंग की आवश्यकता के।

## डेटाबेस सेट करना {#setup}

डेटाबेस का उपयोग करने वाले ऐप को तीन फ़ाइलों की आवश्यकता होती है:

- `server/db/schema.ts`: तालिका परिभाषाएँ
- `server/db/index.ts`: टाइप किया गया DB क्लाइंट सिंगलटन
- `server/plugins/db.ts`: local startup के लिए app-owned migrations

### 1. अपनी स्कीमा परिभाषित करें {#schema}

`@agent-native/core/db/schema` से स्कीमा हेल्पर्स इम्पोर्ट करें। कभी भी सीधे `drizzle-orm/sqlite-core` या `drizzle-orm/pg-core` से इम्पोर्ट न करें। फ्रेमवर्क हेल्पर्स बोली-अज्ञेयवादी परिभाषाएँ बनाते हैं जो सभी समर्थित बैकएंड पर काम करती हैं।

```ts filename="server/db/schema.ts"
import { integer, now, table, text } from "@agent-native/core/db/schema";

export const tasks = table("tasks", {
  id: text("id").primaryKey(),
  title: text("title").notNull(),
  priority: integer("priority").notNull().default(0),
  done: integer("done", { mode: "boolean" }).notNull().default(false),
  ownerEmail: text("owner_email").notNull(),
  createdAt: text("created_at").notNull().default(now()),
});
```

| हेल्पर    | उद्देश्य                                                                    |
| --------- | --------------------------------------------------------------------------- |
| `table`   | एक तालिका परिभाषित करें; `pgTable` या `sqliteTable` को डिस्पैच करता है      |
| `text`    | टेक्स्ट कॉलम, `{ enum: [...] }` का समर्थन करता है                           |
| `integer` | पूर्णांक कॉलम, `{ mode: "boolean" }` Postgres बूलियन से मैप होता है         |
| `real`    | फ्लोट कॉलम। SQLite पर `real`, Postgres पर `double precision` से मैप होता है |
| `now`     | `.default(now())` के लिए बोली-अज्ञेयवादी वर्तमान टाइमस्टैम्प                |

### 2. DB क्लाइंट बनाएँ {#db-client}

प्रत्येक ऐप `createGetDb(schema)` को कॉल करके एक आलसी (lazy), सिंगलटन Drizzle क्लाइंट बनाता है। विहित स्थान `server/db/index.ts` है:

```ts filename="server/db/index.ts"
import { createGetDb } from "@agent-native/core/db";
import * as schema from "./schema.js";

export const getDb = createGetDb(schema);
```

`createGetDb` एक `getDb()` फ़ंक्शन लौटाता है जो पहली कॉल पर डेटाबेस कनेक्शन खोलता है और बाद की कॉल में वही टाइप किया गया Drizzle इंस्टेंस लौटाता है। यह रनटाइम पर `DATABASE_URL` पढ़ता है यह तय करने के लिए कि कौन सा बैकएंड और बोली उपयोग करनी है।

actions और routes में `getDb` को इस टेम्पलेट-स्थानीय पथ से इम्पोर्ट करें। सीधे `@agent-native/core` से इम्पोर्ट न करें। कोर निर्यात अनटाइप्ड है; स्थानीय निर्यात आपके स्कीमा प्रकार वहन करता है।

### 3. माइग्रेशन लिखें {#migrations}

Local development में schema changes को `server/plugins/db.ts` के Nitro plugin
से लागू किया जा सकता है। Production या serverless deployments में migrations को
पहली request पर नहीं, बल्कि release या deploy step में चलाएं।
`@agent-native/core/db` से `runMigrations` का उपयोग करें:

`runMigrations` हर pending entry को क्रम से एक बार चलाता है, उसे applied के रूप में
record करता है, और बाद की runs में छोड़ देता है। नई entries को स्थिर `name` दें;
named migrations को version number से स्वतंत्र track किया जाता है।

<Callout tone="warning">
  Chat template migrations को release step में चलाने के लिए `pnpm
  migrate:production` देता है।
</Callout>

<Callout tone="risk">
  उत्पादन डेटाबेस के विरुद्ध कभी भी `drizzle-kit push` न चलाएं। टेम्प्लेट स्कीमा
  केवल ऐप-विशिष्ट तालिकाओं को परिभाषित करते हैं; इनमें केंद्रीय फ्रेमवर्क
  तालिकाएँ (`user`, `session`, `application_state`, और अन्य) शामिल नहीं हैं।
  उत्पादन के विरुद्ध `drizzle-kit push` चलाने से उन तालिकाओं को अज्ञात के रूप
  में पहचाना जाएगा और उन्हें गिराने का प्रयास किया जाएगा, जिससे तत्काल डेटा हानि
  होगी।
</Callout>

प्रत्येक ऐप की जड़ में `drizzle.config.ts` स्थानीय विकास स्कीमा निरीक्षण के लिए drizzle-kit को कॉन्फ़िगर करता है:

```ts filename="drizzle.config.ts"
import { createDrizzleConfig } from "@agent-native/core/db/drizzle-config";
export default createDrizzleConfig();
```

अपनी स्कीमा का निरीक्षण करने के लिए `pnpm db:generate` का उपयोग करें और केवल स्थानीय डेटाबेस के विरुद्ध `pnpm db:push` का उपयोग करें।

### 4. actions में क्वेरी करें {#querying}

टाइप किया गया Drizzle क्लाइंट पाने के लिए अपनी actions से `getDb()` को कॉल करें। `drizzle-orm` से Drizzle के क्वेरी बिल्डर और पोर्टेबल ऑपरेटरों का उपयोग करें:

```ts
import { and, desc, eq } from "drizzle-orm";
import { getDb } from "../server/db/index.js";
import * as schema from "../server/db/schema.js";

const db = getDb();

const openTasks = await db
  .select()
  .from(schema.tasks)
  .where(
    and(eq(schema.tasks.ownerEmail, userEmail), eq(schema.tasks.done, false)),
  )
  .orderBy(desc(schema.tasks.createdAt));

await db
  .update(schema.tasks)
  .set({ done: true })
  .where(eq(schema.tasks.id, taskId));
```

## उपयोगकर्ताओं तक डेटा को स्कोप करना {#scoping}

उपयोगकर्ता-सामना वाली तालिकाओं के विरुद्ध सभी पठन और लेखन प्रमाणित उपयोगकर्ता तक स्कोप्ड होने चाहिए। फ्रेमवर्क दो पैटर्न प्रदान करता है, इस पर निर्भर करते हुए कि डेटा निजी है या साझा करने योग्य।

**निजी डेटा:** वे तालिकाएँ जो एक उपयोगकर्ता की हैं। स्कीमा में `ownerEmail: text("owner_email").notNull()` जोड़ें और हर क्वेरी में `eq(table.ownerEmail, userEmail)` शामिल करें:

```ts
.where(eq(schema.tasks.ownerEmail, userEmail))
```

**साझा संसाधन:** वे तालिकाएँ जिन्हें अन्य उपयोगकर्ताओं या संगठनों के साथ साझा किया जा सकता है। स्कीमा में एक साधारण `owner_email` के बजाय `...ownableColumns()` फैलाएं। यह एक ही कॉल में `owner_email`, `org_id`, और `visibility` जोड़ता है, और `createSharesTable` के साथ एक साथी शेयर्स तालिका बनाता है:

```ts filename="server/db/schema.ts"
import {
  table,
  text,
  ownableColumns,
  createSharesTable,
} from "@agent-native/core/db/schema";

export const decks = table("decks", {
  id: text("id").primaryKey(),
  title: text("title").notNull(),
  ...ownableColumns(),
});
export const deckShares = createSharesTable("deck_shares");
```

फिर सूची क्वेरी में मैनुअल `eq` जांच के बजाय `@agent-native/core/sharing` से `accessFilter` का उपयोग करें:

```ts
import { accessFilter } from "@agent-native/core/sharing";

const rows = await db
  .select()
  .from(schema.decks)
  .where(accessFilter(schema.decks, schema.deckShares));
```

`accessFilter` एक क्वेरी बनाता है जो उन पंक्तियों को स्वीकार करती है जिनका कॉलर मालिक है, जो उनके संगठन के साथ साझा की गई हैं, और जो स्पष्ट रूप से उनके साथ साझा की गई हैं। यह अन्य उपयोगकर्ताओं की पंक्तियों को उजागर नहीं करता।

पूरे मॉडल के लिए [Security — Data Scoping](/docs/security#data-scoping) और [Sharing](/docs/sharing#building) देखें।

## कच्चा SQL {#raw-sql}

उन्नत क्वेरीज़, स्वास्थ्य जांच, या एकमुश्त रखरखाव के लिए जिन्हें Drizzle क्वेरी बिल्डर व्यक्त नहीं कर सकता, `@agent-native/core/db` से `getDbExec` का उपयोग करें:

```ts
import { getDbExec, isPostgres, intType } from "@agent-native/core/db";

const { rows } = await getDbExec().execute({
  sql: `SELECT id, title FROM tasks WHERE owner_email = ? LIMIT ?`,
  args: [userEmail, 50],
});
```

`getDbExec` Postgres के लिए `?` पैरामीटर को स्वतः `$1`, `$2`, आदि में बदल देता है। बोली पर शाखा (branch) लगाने के लिए `isPostgres()` का उपयोग करें, और वर्तमान बैकएंड के लिए सही पूर्णांक प्रकार लौटाने के लिए `intType()` का उपयोग करें। सामान्य पठन और लेखन के लिए Drizzle क्वेरी बिल्डर को प्राथमिकता दें। कच्चा SQL टाइप सुरक्षा को बायपास करता है और इसे बनाए रखना कठिन है।
