# टेम्पलेट परिवर्तनों को सिंक करना

`agent-native create` एक प्रथम-पक्ष टेम्पलेट को आपके ऐप में कॉपी करता है और फिर उसे आपका बना देता है - ऐप का नाम बदलकर, `_gitignore` का नाम बदलकर, `package.json` को फिर से लिखकर, `workspace:*` और `catalog:` निर्भरताओं को ठोस संस्करणों पर पिन करके, और (एक कार्यक्षेत्र में) इनहेरिटेड auth और chat प्लगइन को बदलकर। उस पल से ऐप टेम्पलेट से बनाया गया एक स्वतंत्र ऐप है। जो फिक्स और सुधार टेम्पलेट में अपस्ट्रीम लैंड होते हैं, वे उस तक नहीं पहुंचते।

`agent-native upgrade` उस अंतर को नहीं पाटता। यह पैकेज संस्करणों को स्थानांतरित करता है, इम्पोर्ट कोडमॉड चलाता है, और skill डायरेक्टरी को रीफ़्रेश करता है - यह किसी टेम्पलेट से कॉपी की गई फ़ाइल को कभी नहीं छूता।

`agent-native template` वह गायब आधा हिस्सा है। यह टेम्पलेट को नए संस्करण में फिर से फ़ेच करता है, `create` द्वारा लागू किए गए ठीक वही ट्रांसफ़ॉर्म फिर से लागू करता है, और परिणाम को आपके ऐप में फ़ाइल दर फ़ाइल मर्ज करता है।

कम्युनिटी टेम्पलेट जानबूझकर इस सिंक प्रक्रिया से बाहर हैं। उनका `agent-native.communityTemplate` मेटाडेटा केवल इंस्टॉल किए गए स्रोत को दर्ज करता है; `agent-native template sync` उस रिपॉज़िटरी से बदलाव नहीं खींचता। स्थिर शुरुआत के लिए पिन किया हुआ संशोधन इंस्टॉल करें और बाद के बदलावों को समीक्षा के बाद मैन्युअल रूप से पोर्ट करें।

## त्वरित शुरुआत {#quick-start}

```bash
agent-native upgrade
agent-native template sync
```

`sync` डिफ़ॉल्ट रूप से आपके इंस्टॉल किए गए `@agent-native/core` से मेल खाते टेम्पलेट संस्करण का उपयोग करता है, इसलिए `upgrade` के बाद इसे चलाने से कोड और पैकेज एक ही संस्करण पर बने रहते हैं।

मर्ज करने से पहले देख लें:

```bash
agent-native template status
agent-native template diff
```

## मर्ज कैसे काम करता है {#how-the-merge-works}

एक उपयोगी मर्ज के लिए दो नहीं, तीन ट्री चाहिए:

- **base** — शुद्ध टेम्पलेट, जैसा वह आपके ऐप के जेनरेट होने के समय था।
- **theirs** — वही टेम्पलेट, जिस संस्करण में आप सिंक कर रहे हैं, उसी ट्रांसफ़ॉर्म पाइपलाइन से गुज़ारा हुआ।
- **ours** — आपका ऐप, जैसा वह अभी है।

इनके साथ, हर फ़ाइल एक स्पष्ट स्थिति में आ जाती है। अपस्ट्रीम ने उसे नहीं छुआ, तो उसे वैसे ही छोड़ दिया जाता है। आपने उसे कभी नहीं छुआ, तो वह फ़ास्ट-फ़ॉरवर्ड हो जाती है। आप दोनों ने उसे बदला, तो उसे कॉन्फ़्लिक्ट मार्कर मिलते हैं। कुछ भी सिर्फ़ इसलिए ओवरराइट नहीं होता कि वह अलग है।

बिना किसी base के, "sync" का मतलब सिर्फ़ ओवरराइट हो सकता है, जो चुपचाप या तो आपके काम को छोड़ देता है या अपस्ट्रीम के काम को पलट देता है।

## बेसलाइन {#the-baseline}

base ट्री को आपके अपने रेपो में एक git ref के रूप में संग्रहीत किया जाता है:

```txt
refs/agent-native/template-baseline/apps/slides
```

इसे एक डिस्पोज़ेबल इंडेक्स फ़ाइल के विरुद्ध git plumbing से लिखा जाता है। आपका `HEAD`, आपकी ब्रांच, आपका इंडेक्स, और आपका working tree कभी नहीं छुए जाते - एडिट के बीच में `template baseline` चलाना सुरक्षित है, और `git status` पहले और बाद में एक जैसा ही दिखता है।

पहली बार लिखे जाने पर, `refs/agent-native/*` के लिए fetch और push refspecs आपके रिमोट में जोड़ दिए जाते हैं ताकि बेसलाइन क्लोन के बाद भी बनी रहे। अगर ऐप git repo में नहीं है, तो बेसलाइन `.agent-native/` के अंतर्गत एक tarball पर फ़ॉलबैक हो जाती है।

provenance मौजूद होने से पहले जेनरेट किए गए ऐप्स की कोई बेसलाइन नहीं होती। एक बनाएं, फिर सिंक करें:

```bash
agent-native template baseline
agent-native template sync
```

## Provenance {#provenance}

`create`, बाद के मर्ज को जो चाहिए वह ऐप के `package.json` में दर्ज कर देता है:

```json
{
  "agent-native": {
    "scaffold": {
      "template": "slides",
      "frameworkSkills": "default",
      "templateRef": "@agent-native/core@0.120.3",
      "templateSource": "github",
      "coreVersion": "0.120.3",
      "shape": "workspace"
    }
  }
}
```

`templateRef` वह अपरिवर्तनीय (immutable) टैग है जिससे टेम्पलेट वास्तव में फ़ेच किया गया था, और यही base को reproducible बनाता है। `shape` तय करता है कि materialization के दौरान वर्कस्पेस ट्रांसफ़ॉर्म फिर से चलाए जाएं या नहीं।

## कमांड {#commands}

### status {#status}

```bash
agent-native template status [app]
```

दर्ज किए गए ref, नवीनतम उपलब्ध ref, बेसलाइन मौजूद है या नहीं, अपस्ट्रीम में कितनी फ़ाइलें बदलीं, और आपने स्थानीय रूप से कितनी फ़ाइलें बदली हैं - इसकी रिपोर्ट देता है।

### diff {#diff}

```bash
agent-native template diff [app] [--to <ref>]
```

आपकी बेसलाइन और लक्ष्य के बीच अपस्ट्रीम में जो बदला उसका एक रीड-ओनली यूनिफ़ाइड diff। कुछ भी नहीं लिखता।

### sync {#sync}

```bash
agent-native template sync [app] [--to <ref>] [--dry-run] [--force]
```

मर्ज करता है। `--to` डिफ़ॉल्ट रूप से इंस्टॉल किए गए core से मेल खाते ref पर सेट होता है। `--dry-run` बिना लिखे प्लान प्रिंट करता है।

`sync` तब चलने से मना कर देता है जब ऐप डायरेक्टरी में uncommitted परिवर्तन हों, इसलिए एक खराब मर्ज को हमेशा `git checkout` से रिकवर किया जा सकता है। `--force` इसे ओवरराइड करता है; पहले कमिट करना बेहतर है।

जब मर्ज साफ़ हो, तो बेसलाइन अपने आप आगे बढ़ जाती है। जब कॉन्फ़्लिक्ट होते हैं, तो यह जानबूझकर आगे नहीं बढ़ती - `accept` देखें।

### accept {#accept}

```bash
agent-native template accept [app]
```

आपके द्वारा कॉन्फ़्लिक्ट मार्कर हल कर देने के बाद बेसलाइन को आगे बढ़ाता है। जब तक कोई भी `<<<<<<<` बचा रहता है, यह मना कर देता है, ताकि बेसलाइन कभी भी किसी अनसुलझे मर्ज से आगे न बढ़े और चुपचाप कॉन्फ़्लिक्ट मार्करों को आपके अगले base में न पका दे।

### baseline {#baseline}

```bash
agent-native template baseline [app] [--ref <ref>] [--template <name>]
```

ऐसे ऐप के लिए बेसलाइन दर्ज करता है जो scaffold provenance से पहले का है। जब आपको पता हो कि ऐप वास्तव में किस संस्करण से आया था, तो `--ref` पास करें; यह जितना सच्चाई के करीब होगा, पहली sync उतने ही कम भ्रामक (phantom) कॉन्फ़्लिक्ट पैदा करेगी।

## जो कभी मर्ज नहीं होता {#what-is-never-merged}

कुछ फ़ाइलें परिभाषा से आपकी होती हैं, और कुछ को सार्थक रूप से मर्ज नहीं किया जा सकता:

- सीक्रेट और लोकल कॉन्फ़िग: `.env`, `.env.local`
- लॉकफ़ाइलें: `pnpm-lock.yaml`
- जेनरेट किया गया आउटपुट: `node_modules`, `.output`, `.react-router`, `dist`, `build`
- ऐप के स्वामित्व वाली सामग्री: `learnings.md`, `changelog/` के अंतर्गत लंबित प्रविष्टियाँ

बाइनरी फ़ाइलें कभी मार्कर-मर्ज नहीं होतीं। अगर दोनों पक्षों ने किसी को बदला है, तो आपकी कॉपी रखी जाती है और फ़ाइल को मैनुअल हैंडलिंग के लिए रिपोर्ट किया जाता है। सिमलिंक को नष्ट करने के बजाय रिपोर्ट किया जाता है।

## बदलाव वापस योगदान करना {#contributing-changes-back}

सिंकिंग डिज़ाइन से एकदिशीय (one-directional) है: टेम्पलेट सामग्री के लिए अपस्ट्रीम ही सत्य का स्रोत है, और `create` जो ट्रांसफ़ॉर्म लागू करता है वे पूरी तरह उलटने योग्य नहीं हैं। किसी ठोस ऐप नाम से `{{APP_NAME}}` को वापस पाना एक अनुमान है, और जिन फ़ाइलों को `create` ने पूरी तरह फिर से लिखा - `package.json`, `netlify.toml`, `app/root.tsx`, `server/plugins/auth.ts` - उनका कोई सटीक व्युत्क्रम (inverse) है ही नहीं।

अगर आप फ़्रेमवर्क मोनोरेपो के अंदर काम कर रहे हैं और ऐप-साइड के किसी सुधार को वापस किसी टेम्पलेट में पुश करना चाहते हैं, तो `contribute:template` स्क्रिप्ट उन सीमाओं को स्पष्ट रखते हुए उलटा पास करती है:

```bash
pnpm contribute:template --app <path-to-app> --dry-run
```

यह आपके ऐप की उसकी बेसलाइन से diff निकालता है ताकि केवल आपके अपने बदलाव ही उम्मीदवार हों, सिर्फ़ उन्हीं फ़ाइलों पर प्लेसहोल्डर प्रतिस्थापन को उलटता है, उन्हें `templates/<name>/` में वर्तमान ब्रांच पर unstaged एडिट के रूप में थ्री-वे मर्ज करता है, और जो कुछ भी उसने छूने से मना किया वह सब प्रिंट करता है ताकि आप इरादे को हाथ से पोर्ट कर सकें।

## अन्य कमांड से संबंध {#relationship-to-other-commands}

| कमांड                        | क्या स्थानांतरित करता है                                              |
| ---------------------------- | --------------------------------------------------------------------- |
| `agent-native upgrade`       | `@agent-native/*` पैकेज संस्करण, इम्पोर्ट, skill डायरेक्टरी           |
| `agent-native template sync` | स्कैफ़ोल्ड के समय किसी टेम्पलेट से कॉपी की गई फ़ाइलें                 |
| `agent-native eject`         | फ़्रेमवर्क कॉम्पोनेंट को ऐप-स्वामित्व वाले सोर्स में, provenance सहित |

`upgrade` और `template sync` पूरक हैं और साथ चलाने के लिए सुरक्षित हैं। `eject` इसकी उलटी चाल है - यह जानबूझकर किसी फ़ाइल का स्वामित्व लेता है, और eject की गई फ़ाइलें अलग से `agent-native.ejections.json` में ट्रैक की जाती हैं।
