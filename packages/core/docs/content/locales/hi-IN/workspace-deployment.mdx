# कार्यस्थान तैनाती

अगर आपका प्रोजेक्ट एक से ज़्यादा ऐप वाला [कार्यस्थान](/docs/multi-app-workspace) है, तो आप हर ऐप के लिए अलग-अलग तैनाती manage करने के बजाय हर ऐप को एक ही origin पर तैनात कर सकते हैं। यह पेज managed one-command तरीके और एक self-hosted Docker Compose विकल्प को कवर करता है। पहले एक डेटाबेस, एक preset, और एक platform चुनने के लिए [तैनाती](/docs/deployment) देखें।

## एक Origin, कई ऐप्स {#workspace-deploy}

एक ही command से कार्यस्थान के हर ऐप को एक ही origin पर भेजें:

```bash
npx @agent-native/core@latest deploy
# https://your-agents.com/mail/*       → apps/mail
# https://your-agents.com/calendar/*   → apps/calendar
# https://your-agents.com/forms/*      → apps/forms
```

**Same-origin** का मतलब है कि ब्राउज़र को हर ऐप उसी website का हिस्सा लगता है। इससे आपको मुफ़्त में दो बड़ी जीत मिलती हैं:

- **शेयर्ड login session**। किसी भी ऐप में log in करें, और हर ऐप logged in हो जाता है।
- **Zero-config cross-app A2A**। mail से `@calendar` को tag करना एक same-origin fetch है। यहां न कोई CORS है, न siblings के बीच कोई JWT signing।

<Callout tone="info">

हुड के तहत, हर ऐप अपने खुद के **base path** के साथ बनाया जाता है, जो `APP_BASE_PATH`/`VITE_APP_BASE_PATH` से सेट किया गया `/mail` जैसा एक URL prefix है, फिर उसे target Nitro preset के लिए package किया जाता है। Cloudflare Pages एक generated **dispatcher worker** के ज़रिए route करता है, जो `dist/_worker.js` पर एक छोटी script है जो incoming path को पढ़ती है और request को matching ऐप तक forward करती है। Netlify हर ऐप के लिए एक function और generated redirects का उपयोग करता है। Vercel Build Output API का उपयोग करके एक कार्यस्थान-स्तरीय `.vercel/output` लिखता है।

</Callout>

<Callout tone="warning">

Hosted कार्यस्थान builds के लिए deploy provider environment में `A2A_SECRET` चाहिए। इसके बिना, Slack, inbound webhooks, और cross-app A2A resume काम नहीं करते, क्योंकि ये सब signed background processors से होकर गुज़रते हैं। Local `--build-only` artifact checks इसके बिना भी चलती रहती हैं।

</Callout>

<Callout tone="info">

हाथ से deploy करने के बजाय किसी provider का build command wire कर रहे हैं? उसी command में `--build-only` जोड़ें, उदाहरण के लिए `npx @agent-native/core@latest deploy --preset vercel --build-only`। यह आउटपुट सीधे लिखता है, इसलिए कार्यस्थान routing के लिए किसी `vercel.json` की ज़रूरत नहीं।

एक shared origin के बजाय हर ऐप के लिए अलग domain पसंद करते हैं? कार्यस्थान का हर ऐप अब भी स्वतंत्र रूप से तैनात किया जा सकता है। एक standalone scaffold की तरह `cd apps/<name> && npx @agent-native/core@latest build` चलाएं।

</Callout>

## Docker Compose के साथ Self-hosted कार्यस्थान {#workspace-docker-compose}

एक कार्यस्थान आज एक Nitro server process नहीं है। हर ऐप अब भी अपनी खुद की `.output/` directory में build होता है और अपना खुद का Node/Nitro server चलाता है, इसलिए किसी कार्यस्थान को self-host करने का मतलब है एक ही entry point के पीछे कई servers चलाना।

एक **reverse proxy** ऊपर दी गई तस्वीर में वही एक entry point है: यह हर request receive करता है और उसे URL path के आधार पर सही container तक forward करता है, वही काम जो एक managed deploy के लिए Cloudflare का dispatcher worker करता है। एक VPS पर, इसका मतलब है कार्यस्थान के हर ऐप के लिए एक container, सब एक ही Postgres डेटाबेस और shared production secrets की ओर इशारा करते हुए, और आगे proxy।

<Steps>

### हर ऐप को matching base path के साथ build करें

Base path client bundle के लिए एक build-time input है और server के लिए एक runtime input। हर ऐप को उसी path के साथ build करें जिस पर proxy उसे route करेगा:

```bash maxLines=8
APP_BASE_PATH=/mail VITE_APP_BASE_PATH=/mail npx @agent-native/core@latest build
node .output/server/index.mjs
```

### एक reusable Dockerfile लिखें

ऐप का नाम और path prefix को build arguments के रूप में लें, ताकि एक ही Dockerfile कार्यस्थान के हर ऐप को serve कर सके:

```dockerfile filename="Dockerfile.workspace-app" maxLines=12
FROM node:24-slim AS build
WORKDIR /workspace
RUN corepack enable
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY packages ./packages
COPY apps ./apps
ARG APP_NAME
ARG APP_BASE_PATH
ENV APP_BASE_PATH=$APP_BASE_PATH
ENV VITE_APP_BASE_PATH=$APP_BASE_PATH
RUN pnpm install --frozen-lockfile
RUN pnpm --dir apps/$APP_NAME build

FROM node:24-slim
WORKDIR /app
ARG APP_NAME
ARG APP_BASE_PATH
ENV NODE_ENV=production
ENV PORT=3000
ENV APP_BASE_PATH=$APP_BASE_PATH
COPY --from=build /workspace/apps/$APP_NAME/.output .output
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

### Postgres, ऐप्स, और proxy को compose करें

यह उदाहरण Caddy का उपयोग करता है क्योंकि यह locally HTTP terminate कर सकता है या Cloudflare के SSL proxy के पीछे बैठ सकता है, लेकिन ज़रूरी हिस्सा path-prefix routing है:

```yaml filename="docker-compose.yml" maxLines=30
services:
  postgres:
    image: postgres:17
    restart: unless-stopped
    environment:
      POSTGRES_DB: agent_native
      POSTGRES_USER: agent_native
      POSTGRES_PASSWORD: change-me
    volumes:
      - postgres-data:/var/lib/postgresql/data

  mail:
    build:
      context: .
      dockerfile: Dockerfile.workspace-app
      args:
        APP_NAME: mail
        APP_BASE_PATH: /mail
    restart: unless-stopped
    environment:
      DATABASE_URL: postgres://agent_native:change-me@postgres:5432/agent_native
      BETTER_AUTH_URL: https://agents.example.com/mail
      BETTER_AUTH_SECRET: ${BETTER_AUTH_SECRET}
      A2A_SECRET: ${A2A_SECRET}
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
    depends_on:
      - postgres

  calendar:
    build:
      context: .
      dockerfile: Dockerfile.workspace-app
      args:
        APP_NAME: calendar
        APP_BASE_PATH: /calendar
    restart: unless-stopped
    environment:
      DATABASE_URL: postgres://agent_native:change-me@postgres:5432/agent_native
      BETTER_AUTH_URL: https://agents.example.com/calendar
      BETTER_AUTH_SECRET: ${BETTER_AUTH_SECRET}
      A2A_SECRET: ${A2A_SECRET}
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
    depends_on:
      - postgres

  proxy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
    depends_on:
      - mail
      - calendar

volumes:
  postgres-data:
```

### Proxy configure करें

```caddyfile filename="Caddyfile"
agents.example.com {
  reverse_proxy /mail* mail:3000
  reverse_proxy /calendar* calendar:3000
}
```

</Steps>

<Callout tone="info">

- Shared auth, shared credentials, और cross-app A2A चाहिए तो हर ऐप container में
  `DATABASE_URL`, `BETTER_AUTH_SECRET`, `A2A_SECRET`, और बाकी production
  secrets समान रखें।
- `BETTER_AUTH_URL` को उस ऐप path के public URL पर सेट करें। OAuth callback
  URLs को वही public URL उपयोग करना चाहिए।
- Production data के लिए container filesystem पर भरोसा न करें। `DATABASE_URL`
  के लिए Postgres (या कोई अन्य persistent SQL backend) उपयोग करें।
- अगर Cloudflare VPS के आगे TLS terminate करता है, तो Cloudflare को सामान्य
  `X-Forwarded-Proto` / `X-Forwarded-Host` headers भेजने और public host को
  proxy container पर route करने के लिए configure करें।

</Callout>
