# Render

<Badge label="Beta" color="orange" icon="rocket" />

Render आपके ऐप को web service के रूप में host करता है, इसलिए कोई server set up
करने या चालू रखने की ज़रूरत नहीं होती। Render वही Node.js server चलाता है जो
[Node.js guide](/docs/node-js) में बताया गया है, उसे आपकी Git repository से build
करता है, और ऐप को HTTPS के साथ एक public address देता है।

यह guide शुरुआत से एक standalone ऐप deploy करने के चरण बताती है। आप ऐप बनाकर
उसे Git repository में push करेंगे, उसे production database और auth secret
देंगे, database तैयार करेंगे, और फिर एक Render web service बनाएंगे जो उसे build
करके चलाती है।

<Callout tone="info">

Node.js `22.22+` आवश्यक है।

</Callout>

आपको एक Render account और GitHub, GitLab, या Bitbucket पर एक repository भी
चाहिए। इस guide के commands अपने computer पर चलाएं। Render आपकी repository से ऐप
को build करके चलाता है।

## चरण 1: ऐप बनाएं {#step-1-create-the-app}

अपना नया standalone ऐप बनाएं। नीचे दिया गया उदाहरण Chat template से ऐप बनाता है,
लेकिन आप किसी भी template से शुरू कर सकते हैं। ऐप के folder में जाएं और उसकी
dependencies install करें। `corepack enable` वह `pnpm` version चालू करता है
जिसकी ऐप को ज़रूरत है, इसलिए आपको `pnpm` खुद install करने की ज़रूरत नहीं है।

```bash
npx --yes @agent-native/core@latest create my-app --standalone --template chat

cd my-app

corepack enable

pnpm install
```

चाहें तो `my-app` को अपने ऐप के नाम से बदल दें। इस guide का बाकी हिस्सा मानता है
कि आप ऐप के folder के अंदर हैं।

Render ऐप को Git repository से build करता है, इसलिए आगे बढ़ने से पहले ऐप के
folder को GitHub, GitLab, या Bitbucket पर एक नई repository में push करें।
`pnpm-lock.yaml` file को भी commit करें, क्योंकि build उसमें दिए गए exact
versions install करता है।

## चरण 2: Environment secrets configure करें {#step-2-configure-environment-secrets}

ऐप अपनी production settings environment variables से पढ़ता है:

| Variable             | आवश्यक | उद्देश्य                                                       |
| -------------------- | ------ | -------------------------------------------------------------- |
| `DATABASE_URL`       | हां    | ऐप को उसके PostgreSQL database से connect करता है              |
| `BETTER_AUTH_SECRET` | हां    | User sessions sign करता है                                     |
| `BETTER_AUTH_URL`    | नहीं   | वह public address सेट करता है जिससे लोग आपके ऐप तक पहुंचते हैं |

नीचे दिए गए exports से आगे के commands इस shell में काम करते हैं। Deploy करने
से पहले, यही variables अपने host की project या service environment settings में
save करें। चरण 4 बताता है कि उन्हें Render में कैसे save करें।

### Database URL {#database-url}

Local development के दौरान, `DATABASE_URL` unset होने पर ऐप data को local
database में store करता है। Deployed ऐप को एक असली PostgreSQL database चाहिए जो
deploys के बीच अपना data बनाए रखे। Render हर deploy और restart पर service की
files बदल देता है, इसलिए database को web service के बाहर होना चाहिए। अपने
provider से connection string copy करें और उसे export करें:

```bash
export DATABASE_URL='your-postgres-url-string'
```

[Database provider guides](/docs/neon) बताती हैं कि हर provider के लिए connection
string कहां मिलती है। Render Postgres भी काम करता है। यहां उसकी external
connection string इस्तेमाल करें, और web service की settings में उसकी internal
connection string।

<Callout tone="warning">

एक persistent PostgreSQL provider चुनें: Neon, Supabase, Amazon RDS, आदि।

</Callout>

### Auth secret {#auth-secret}

इसे एक बार generate करें और सभी deploys में इसे एक जैसा रखें।

ऐप user sessions sign करने के लिए `BETTER_AUTH_SECRET` का उपयोग करता है। अगर यह
बदलता है, तो हर signed-in user sign out हो जाता है। नीचे दिया गया command एक
random value generate करता है:

```bash
export BETTER_AUTH_SECRET="$(openssl rand -hex 32)"
```

Generate की गई value को किसी सुरक्षित जगह save करें, जैसे password manager में।
हर बार deploy करते समय यही value इस्तेमाल करें।

### Public URL {#public-url}

वैकल्पिक। इसे तब सेट करें जब आप custom domain, reverse proxy, या ऐसा auth/OAuth
flow इस्तेमाल करें जिसे fixed public origin चाहिए।

`BETTER_AUTH_URL` वह public address है जिससे लोग आपके ऐप तक पहुंचते हैं। इसके
बिना, ऐप हर incoming request से अपना address पता करता है। Render के दिए गए address
पर आमतौर पर यह ठीक रहता है, लेकिन custom domain connect करते समय इसे सेट करें,
ताकि sign-in links और OAuth redirects उसी domain का इस्तेमाल करें।

```bash
export BETTER_AUTH_URL='https://your-domain.example'
```

## चरण 3: Migrate करें {#step-3-migrate}

Migrations आपके database में वे tables बनाती और update करती हैं जिनकी ऐप को
ज़रूरत है। पहले deploy से पहले इसे चलाएं:

```bash
pnpm migrate:production
```

यह command आपके computer पर चलता है और चरण 2 में export किए गए `DATABASE_URL` से
production database से connect करता है। ऐप upgrade करने के बाद, नया version
deploy करने से पहले इसे फिर से चलाएं।

Paid Render instance पर, आप इसके बजाय service का **Pre-Deploy Command**
`pnpm migrate:production` पर सेट कर सकते हैं। तब Render हर deploy live होने से
पहले migrations चलाता है। Pre-Deploy Command, Free instance type पर उपलब्ध नहीं
है।

## चरण 4: Web service बनाएं {#step-4-create-the-web-service}

Render dashboard में एक नई **Web Service** बनाएं और चरण 1 की repository connect
करें। ये settings इस्तेमाल करें:

| Setting       | Value                                                                                     |
| ------------- | ----------------------------------------------------------------------------------------- |
| Language      | `Node`                                                                                    |
| Branch        | वह branch जिससे आप deploy करते हैं, जैसे `main`                                           |
| Build Command | `corepack enable && pnpm install --frozen-lockfile && NITRO_PRESET=render_com pnpm build` |
| Start Command | `node .output/server/index.mjs`                                                           |

Build Command ऐप का `pnpm` version चालू करता है, `pnpm-lock.yaml` में दी गई
dependencies install करता है, और ऐप build करता है। `NITRO_PRESET=render_com`
वही Node.js server build करता है जो Node.js guide में है, और उसे अपनी static
files खुद serve करने के लिए set up करता है। Start Command उस server को चलाता है।
Render server को `PORT` environment variable के ज़रिए बताता है कि कौन सा port
इस्तेमाल करना है, और server उसे अपने आप पढ़ लेता है।

**Environment Variables** के अंदर, `DATABASE_URL` और `BETTER_AUTH_SECRET` को
चरण 2 में export की गई values के साथ जोड़ें। अगर आपने `BETTER_AUTH_URL` सेट
किया है, तो उसे भी इसी तरह जोड़ें।

Render Node.js version को `NODE_VERSION` environment variable, `.node-version` या
`.nvmrc` file, या `package.json` के `engines` field से, इसी क्रम में चुनता है। नई
services default रूप से ऐसा version इस्तेमाल करती हैं जो ऊपर दी गई requirement
पूरी करता है। किसी version को pin करने के लिए `NODE_VERSION` जोड़ें, उदाहरण के लिए
value `24` के साथ।

## चरण 5: Deploy करें {#step-5-deploy}

<Steps>

### Instance type चुनें

Web service के लिए instance type चुनें। ऐप को आज़माने के लिए Free instance type
काफ़ी है। अगर ऐप को तुरंत जवाब देना हो या आप चरण 3 का Pre-Deploy Command
इस्तेमाल करना चाहते हों, तो paid instance type चुनें।

### Web service बनाएं

Web service बनाएं। Render आपकी repository से ऐप build करता है और उसे start करता
है। पहले build में कुछ मिनट लगते हैं, और आप service के logs में उसे देख सकते हैं।

### ऐप खोलें

Deploy पूरा होने पर dashboard ऐप का address दिखाता है, जो `onrender.com` पर
खत्म होता है। उसे खोलें और पहला account बनाएं।

</Steps>

Free instance type पर, 15 मिनट तक traffic न आने पर Render service को pause कर
देता है। तब अगली visit को लगभग एक मिनट इंतज़ार करना पड़ता है, जब तक service फिर
से start होती है।

## Updates deploy करें {#deploy-updates}

हर बार जब आप चरण 4 में चुनी गई branch पर push करते हैं, Render फिर से deploy
करता है। नया version ship करने के लिए, पहले migrations चलाएं, फिर push करें:

```bash
pnpm migrate:production

git push
```

Service settings और save किए गए variables अपनी जगह बने रहते हैं, इसलिए आपको
चरण 4 दोहराने की ज़रूरत नहीं है।
