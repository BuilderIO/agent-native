# PR विज़ुअल रीकैप

PR विज़ुअल रीकैप एक GitHub Action है जो हर पुल रिक्वेस्ट को **विज़ुअल कोड
समीक्षा** में बदल देता है, बिना किसी को हाथ से कोई कमांड चलाना याद रखने की
ज़रूरत के। यह पेज उन सभी के लिए है जो इस Action को इंस्टॉल, कॉन्फ़िगर, या
सुरक्षित कर रहे हैं। हर पुश पर, एक LLM कोडिंग एजेंट PR के diff के विरुद्ध
नवीनतम बंडल किए गए [`visual-recap`](/docs/template-plan) कौशल (या
`VISUAL_RECAP_SKILL_SOURCE=repo` होने पर आपके रेपो की कमिट की गई कॉपी) चलाता
है, होस्टेड Plans ऐप पर एक संरचित रीकैप योजना प्रकाशित करता है, चलने के दौरान
एक इन्फ़ॉर्मेशनल `Visual Recap` चेक दिखाता है, और **एक स्टिकी PR टिप्पणी**
अपसर्ट करता है जो इंटरैक्टिव योजना से लिंक करती है, साथ ही टिप्पणी में ही
एम्बेडेड **इनलाइन स्क्रीनशॉट** के साथ।

यह कोई डिटरमिनिस्टिक diff रेंडरर नहीं है। यह Action एक असली कोडिंग एजेंट
(डिफ़ॉल्ट रूप से Claude Code CLI, या OpenAI Codex CLI, या OpenAI-कम्पैटिबल
प्रोवाइडर के साथ Agent-Native Code) को इनवोक करता है जो बदलाव को पढ़ता है, यह
तय करता है कि क्या मायने रखता है, और Plans MCP टूल `create-visual-recap` को
कॉल करके रीकैप लिखता है — वही टूल जिसका उपयोग `/visual-recap` स्लैश कमांड
करता है। आपको कच्चे diff की दीवार के बजाय बदलाव का एक ऊंचाई से देखा गया,
स्कीमा/API/पहले-बाद वाला व्यू मिलता है।

रीकैप **इन्फ़ॉर्मेशनल और नॉन-ब्लॉकिंग** है। यह एक चेक रो बनाता है ताकि
समीक्षक देख सकें कि जेनरेशन प्रगति पर है, लेकिन यह कोई ज़रूरी चेक नहीं है, यह
कभी भी PR को ब्लॉक नहीं करता, और यह कभी भी असली diff को पढ़ने की जगह नहीं
लेता। स्टिकी टिप्पणी एक समीक्षा सहायता है, कोई साइन-ऑफ़ नहीं।

## यह क्या करता है

हर PR पुश पर, वर्कफ़्लो:

1. PR के base और head के बीच एक सीमित diff इकट्ठा करता है।
2. `Visual recap in progress` के साथ एक इन्फ़ॉर्मेशनल `Visual Recap` GitHub
   चेक बनाता है।
3. उस diff के विरुद्ध कॉन्फ़िगर किए गए कोडिंग एजेंट को चलाता है। एजेंट बंडल
   किए गए `visual-recap` कौशल की गाइडेंस (या आपकी रेपो-पिन की गई कॉपी) पढ़ता
   है और एक रीकैप लिखता है, इसे `create-visual-recap` के साथ प्रकाशित करता
   है।
4. एजेंट द्वारा `recap-url.txt` में लिखे गए प्रकाशित योजना URL को पढ़ता है।
5. उस URL को हेडलेस Chrome में खोलता है और रेंडर की गई योजना का लाइट और
   डार्क दोनों मोड में स्क्रीनशॉट लेता है।
6. PNG को Plans ऐप पर एक साइन्ड पब्लिक इमेज रूट पर अपलोड करता है।
7. एक सिंगल स्टिकी PR टिप्पणी अपसर्ट करता है जो इंटरैक्टिव रीकैप के लिंक के
   बगल में एक `<picture>` एलिमेंट (GitHub के camo इमेज प्रॉक्सी के ज़रिए
   सर्व किया गया) के साथ स्क्रीनशॉट **इनलाइन** एम्बेड करती है।
8. `Visual Recap` चेक को सफल, स्किप्ड, या न्यूट्रल के रूप में पूरा करता है।

## इसे इंस्टॉल करना

जब आप Plans को इंटरैक्टिव रूप से इंस्टॉल करते हैं, तो Agent-Native CLI पूछता
है कि क्या ऑटोमेटिक PR विज़ुअल रीकैप जोड़ने हैं। GitHub Action लिखने के लिए
हां कहें, या इसे किसी भी समय स्पष्ट रूप से जोड़ें:

```bash
npx @agent-native/core@latest skills add visual-plan --with-github-action
```

यह `visual-plan` कौशल इंस्टॉल करता है (जिसमें वह `visual-recap` कौशल शामिल है
जिसे यह Action चलाता है) और आपके रेपो में
`.github/workflows/pr-visual-recap.yml` लिखता है। वर्कफ़्लो
`npx @agent-native/recap-cli@latest recap <subcommand>` के ज़रिए
**पब्लिश्ड CLI सबकमांड** को कॉल करता है — जिसमें `gate`, `collect-diff`,
`block-reference`, `scan`, `build-prompt`, `publish`, `shot`, `comment`,
`check`, और `usage` शामिल हैं — इसलिए आपके रेपो में हेल्पर स्क्रिप्ट के रूप
में कुछ भी कॉपी नहीं किया जाता। `setup` और `doctor` वे इंटरैक्टिव हेल्पर हैं
जिन्हें आप लोकल रूप से चलाते हैं; `gate` वह सिक्योरिटी-गेट स्टेप है जिसे
वर्कफ़्लो हर रीकैप से पहले चलाता है।

फिर गाइडेड सेटअप हेल्पर चलाएं:

```bash
npx @agent-native/recap-cli@latest recap setup
npx @agent-native/recap-cli@latest recap doctor
```

`recap setup` वर्कफ़्लो को रीफ़्रेश करता है, जब वैल्यू env या लोकल Plans
पब्लिश-टोकन स्टोर से उपलब्ध हों तो GitHub Actions सीक्रेट/वेरिएबल सेट करने के
लिए `gh` का उपयोग करता है, और जो कुछ सेट नहीं कर पाता उसके लिए बिल्कुल सही
कमांड प्रिंट करता है। सीक्रेट वैल्यू `gh` को कमांड आर्ग्युमेंट्स से नहीं,
stdin के ज़रिए भेजी जाती हैं। जेनरेट की गई वर्कफ़्लो फ़ाइल को कमिट करें और इसे
चलते हुए देखने के लिए एक PR खोलें।

डिफ़ॉल्ट रूप से, वर्कफ़्लो `@agent-native/recap-cli@latest` में मौजूद नवीनतम
बंडल `visual-recap` गाइडेंस से अपना एजेंट प्रॉम्प्ट बनाता है, जिसमें कौशल के
साथ आने वाली कोई भी सहयोगी रेफ़रेंस फ़ाइल शामिल है। अगर आपका रेपो जानबूझकर
अपने कमिट किए गए `visual-recap` फ़ोल्डर को कस्टमाइज़ और पिन करता है, तो
रिपॉज़िटरी वेरिएबल `VISUAL_RECAP_SKILL_SOURCE=repo` सेट करें।

## रनर सिलेक्शन

वर्कफ़्लो डिफ़ॉल्ट रूप से GitHub-होस्टेड `ubuntu-latest` रनर पर चलता है।
किसी अलग होस्टेड रनर या अपने खुद के सेल्फ-होस्टेड रनर का उपयोग करने के लिए,
रिपॉज़िटरी या ऑर्गनाइज़ेशन वेरिएबल `VISUAL_RECAP_RUNS_ON` को रनर लेबल की एक
मान्य JSON स्ट्रिंग या JSON ऐरे पर सेट करें:

```text
"ubuntu-latest"
["self-hosted", "linux", "x64", "visual-recap"]
```

JSON कोट्स ज़रूरी हैं। यह सेटिंग पूरे `recap` जॉब के रनर को चुनती है। गाइडेड
सेटअप के दौरान इसे कॉन्फ़िगर करने के लिए, वही JSON वैल्यू `--runs-on` को दें,
फिर `doctor` से वर्कफ़्लो और रनर की उपलब्धता वेरिफ़ाई करें:

```bash
npx @agent-native/recap-cli@latest recap setup --runs-on '["self-hosted","linux","x64","visual-recap"]'
npx @agent-native/recap-cli@latest recap doctor
```

हल्का सिक्योरिटी गेट अलग से डिफ़ॉल्ट रूप से GitHub-होस्टेड `ubuntu-latest` पर
जाता है। GitHub-होस्टेड रनर बंद करने वाली रिपॉज़िटरीज़ `VISUAL_RECAP_GATE_RUNS_ON`
को एक **सादे, सिंगल रनर लेबल** (JSON नहीं) पर सेट कर सकती हैं, या सेटअप के
दौरान `--gate-runs-on visual-recap-gate` पास कर सकती हैं। रीयूज़ेबल वर्कफ़्लो
उसी वैल्यू को अपने `gate-runs-on` इनपुट के रूप में एक्सपोज़ करता है। यह
शेड्यूल होने से पहले डायनामिक JSON को पार्स करने से बचाता है। कस्टम लेबल
सिर्फ़ उसी रिपॉज़िटरी के `OWNER`, `MEMBER`, या `COLLABORATOR` द्वारा लिखे गए
PR के लिए चुना जाता है। फ़ोर्क और बाकी सभी लेखकों को जॉब शुरू होने से पहले
GitHub-होस्टेड `ubuntu-latest` पर भेज दिया जाता है; सिर्फ़-सेल्फ-होस्टेड
रिपॉज़िटरी में, ऐसे अविश्वसनीय रन किसी सेल्फ-होस्टेड मशीन को छूने के बजाय
अनशेड्यूल्ड रह सकते हैं।

`recap doctor` गलत तरीके से बना या असमर्थित JSON अस्वीकार करता है और रिपोर्ट
करता है जब GitHub हर कॉन्फ़िगर किए गए लेबल से मेल खाने वाला कोई ऑनलाइन रनर
एक्सपोज़ नहीं करता। रनर रजिस्ट्रेशन, इंस्टॉलेशन, अपग्रेड, कैपेसिटी, और
मेंटेनेंस आपकी ज़िम्मेदारी बने रहते हैं; Agent-Native लेबल चुनता है लेकिन
रनर प्रोवाइड या ऑपरेट नहीं करता।

**सुरक्षा:** डेडिकेटेड, एफ़ेमरल सेल्फ-होस्टेड रनर को प्राथमिकता दें। एक कस्टम
गेट रनर को सिर्फ़ विश्वसनीय, उसी रिपॉज़िटरी के PR इवेंट मिलते हैं। स्टॉक गेट
PR ट्री को चेकआउट नहीं करता; यह सिर्फ़ वर्कफ़्लो लॉजिक और GitHub PR मेटाडेटा
का मूल्यांकन करता है। एक पर्सिस्टेंट मशीन फिर भी जॉब्स के बीच प्रोसेस स्टेट
बनाए रखती है, इसलिए इसे असंबंधित वर्कलोड के साथ साझा न करें। वर्कफ़्लो
अविश्वसनीय पब्लिक या फ़ोर्क PR लेखकों के लिए किसी सेल्फ-होस्टेड गेट या पूरे
रीकैप जॉब को डिस्पैच करने से पहले फ़ेल-क्लोज़्ड हो जाता है। इस सीमा को कमज़ोर
न करें और न ही अविश्वसनीय योगदान को किसी पर्सिस्टेंट रनर पर भेजें।

## बैकएंड सिलेक्शन

`VISUAL_RECAP_AGENT` रिपॉज़िटरी वेरिएबल से चुनें कि कौन-सा कोडिंग एजेंट कौशल
चलाता है:

| `VISUAL_RECAP_AGENT` | कोडिंग एजेंट                          | ज़रूरी API कुंजी       | ज़रूरी वेरिएबल                                |
| --------------------- | -------------------------------------- | ----------------------- | ---------------------------------------------- |
| `claude` _(डिफ़ॉल्ट)_ | Claude Code CLI                        | `ANTHROPIC_API_KEY`     | —                                              |
| `codex`               | OpenAI Codex CLI                       | `OPENAI_API_KEY`        | —                                              |
| `openai-compatible`   | Agent-Native Code + कम्पैटिबल प्रोवाइडर | `VISUAL_RECAP_API_KEY`  | `VISUAL_RECAP_BASE_URL`, `VISUAL_RECAP_MODEL`  |

अगर वेरिएबल सेट नहीं है, तो Action `claude` का उपयोग करता है।

## मॉडल और रीज़निंग

बैकएंड से आगे, ये रिपॉज़िटरी वेरिएबल एजेंट के चलने के तरीके को ट्यून करते
हैं:

- **`VISUAL_RECAP_MODEL`** CLI (`--model`) को दिए जाने वाले मॉडल को पिन करता
  है — उदाहरण के लिए Codex के लिए `gpt-5.6-luna`, कोई Claude मॉडल id, या
  DeepSeek के लिए `deepseek-chat`। `openai-compatible` के लिए यह ज़रूरी है।
  **Claude** बैकएंड के लिए, इसे अनसेट छोड़ने पर अब डिफ़ॉल्ट रूप से
  `claude-sonnet-5` उपयोग होता है; किसी दूसरे Claude मॉडल का उपयोग करने के
  लिए वेरिएबल को स्पष्ट रूप से सेट करें, जैसे सस्ता `claude-haiku-4-5`।
  **Codex** बैकएंड के लिए, इसे अनसेट छोड़ने पर Codex CLI का अपना डिफ़ॉल्ट
  मॉडल उपयोग होता है।
- **`VISUAL_RECAP_REASONING`** रीज़निंग गहराई सेट करता है: `none`, `minimal`,
  `low`, `medium`, `high`, या `xhigh`। यह Codex बैकएंड पर लागू होता है;
  Claude की रीज़निंग मॉडल-ड्रिवन है, इसलिए यह वेरिएबल वहां इग्नोर किया जाता
  है।
- **`VISUAL_RECAP_BASE_URL`** `openai-compatible` बैकएंड के लिए HTTP(S) बेस
  URL चुनता है। प्रोवाइडर के OpenAI-कम्पैटिबल एंडपॉइंट का उपयोग करें, जैसे
  DeepSeek या Kimi, बिना URL में क्रेडेंशियल एम्बेड किए।
- **`VISUAL_RECAP_SKILL_SOURCE`** प्रॉम्प्ट की ताज़गी को नियंत्रित करता है:
  `auto`/अनसेट नवीनतम बंडल कौशल गाइडेंस का उपयोग करता है, जबकि `repo` कमिट
  किए गए रेपो-लोकल `visual-recap` कौशल फ़ोल्डर पर पिन करता है।

उदाहरण के लिए, Codex पर GPT-5.6 Sol के साथ हाई रीज़निंग पर रीकैप चलाने के
लिए, रिपॉज़िटरी वेरिएबल `VISUAL_RECAP_AGENT=codex`,
`VISUAL_RECAP_MODEL=gpt-5.6-sol`, और `VISUAL_RECAP_REASONING=high` सेट करें।

DeepSeek के लिए, `VISUAL_RECAP_AGENT=openai-compatible`,
`VISUAL_RECAP_BASE_URL=https://api.deepseek.com/v1`,
`VISUAL_RECAP_MODEL=deepseek-chat`, और `VISUAL_RECAP_API_KEY` सीक्रेट सेट
करें। Kimi अपने OpenAI-कम्पैटिबल बेस URL और मॉडल id के साथ इसी तरह काम करता
है। दूसरे OpenAI-कम्पैटिबल प्रोवाइडर इन्हीं तीन सेटिंग्स का उपयोग करते हैं।

## लागत

हर रीकैप रन एक असली diff पढ़ने वाला पूरा एजेंटिक कोडिंग-एजेंट सेशन है, कोई
सस्ता टेम्पलेटेड सारांश नहीं, इसलिए इसकी लागत मॉडल चुनाव और यह कितनी बार
चलता है, इस पर निर्भर करती है:

- **हर PR पुश पर एक पूरा सेशन।** डिफ़ॉल्ट ट्रिगर `synchronize` पर चलता है,
  इसलिए जिस PR को दस बार पुश किया जाता है, वह एजेंट को दस बार चलाता है।
- **हर बार पूरा PR**, न कि सिर्फ़ पिछले रन के बाद के कमिट — लागत PR के कुल
  आकार के हिसाब से बढ़ती है, इन्क्रीमेंटल diff आकार के हिसाब से नहीं।
- **diff इनपुट लगभग 600KB तक सीमित।** यह हर रन के सबसे खराब मामले को सीमित
  करता है, लेकिन बड़े diff फिर भी छोटे diff से काफ़ी ज़्यादा लागत लेते हैं।
- **फ़ेलियर पर एक ऑटोमेटिक री-ट्राई**, जो किसी अस्थायी रूप से फ़ेल होने वाले
  रन की लागत को लगभग दोगुना कर सकता है।

लागत घटाने के लिए:

- **एक सस्ता मॉडल पिन करें।** Claude के लिए, सिंपल या छोटी रिपॉज़िटरी के लिए
  `VISUAL_RECAP_MODEL=claude-haiku-4-5` सेट करें — यह सबसे सस्ता Claude टियर
  है; `claude-sonnet-5` (डिफ़ॉल्ट) बैलेंस्ड टियर है।
- **सस्ते मॉडल के साथ Codex पर स्विच करें।** `VISUAL_RECAP_AGENT=codex` को
  `VISUAL_RECAP_MODEL=gpt-5.6-luna` (सबसे सस्ता GPT-5.6 टियर) या
  `gpt-5.6-terra` (मिड-टियर) के साथ सेट करें, और रीज़निंग-टोकन खर्च को और कम
  करने के लिए `VISUAL_RECAP_REASONING=low` सेट करें। रीज़निंग गहराई सिर्फ़
  Codex पर लागू होती है।
- **किसी सस्ते OpenAI-कम्पैटिबल प्रोवाइडर पर पॉइंट करें।** DeepSeek, Kimi,
  या किसी दूसरे OpenAI-कम्पैटिबल एंडपॉइंट को टारगेट करते हुए
  `VISUAL_RECAP_AGENT=openai-compatible` को
  `VISUAL_RECAP_BASE_URL`/`VISUAL_RECAP_MODEL`/`VISUAL_RECAP_API_KEY` के साथ
  सेट करें।
- **एक स्पष्ट PR लेबल ज़रूरी बनाएं।** वर्कफ़्लो को इंस्टॉल रखने पर भी रीकैप
  तब तक स्किप करने के लिए `VISUAL_RECAP_REQUIRED_LABELS=visual recap` सेट
  करें जब तक किसी PR पर वह लेबल न हो। जब कई लेबल ऑप्ट-इन करने चाहिए, तो एक
  कॉमा-सेपरेटेड लिस्ट का उपयोग करें, जैसे `visual recap,recap`। लिस्ट किया
  गया लेबल लगाते ही वर्कफ़्लो तुरंत जग जाता है।
- **रीकैप कम बार करें।** इंस्टॉल किए गए वर्कफ़्लो के `on.pull_request.types`
  को `[opened, synchronize, reopened, ready_for_review, labeled, closed]` से
  बदलकर `[opened, ready_for_review, closed]` कर दें ताकि यह हर पुश पर नहीं,
  बल्कि सिर्फ़ तब रीकैप करे जब कोई PR खुले और जब वह मर्ज हो।

हर रन यह रिकॉर्ड करता है कि असल में कितना खर्च हुआ: वर्कफ़्लो का
`recap usage` स्टेप टोकन और लागत उपयोग को प्रकाशित योजना से जोड़ देता है,
ताकि आप अनुमान लगाने के बजाय हर रन का असली खर्च देख सकें।

## सीक्रेट और वेरिएबल {#secrets-and-variables}

इन्हें अपनी रिपॉज़िटरी की **Settings → Secrets and variables → Actions** में
सेट करें।

### डिफ़ॉल्ट बैकएंड के लिए सीक्रेट

| सीक्रेट             | उद्देश्य                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------------ |
| `PLAN_RECAP_TOKEN`  | `npx @agent-native/core@latest connect` द्वारा जारी किया गया रिवोकेबल टोकन। रीकैप योजना और स्क्रीनशॉट अपलोड को प्रकाशित करने के लिए अधिकृत करता है। |
| `ANTHROPIC_API_KEY` | डिफ़ॉल्ट Claude Code बैकएंड के लिए LLM कुंजी।                                                    |

**टीमों के लिए: एक org सर्विस टोकन का उपयोग करें।** एक पर्सनल टोकन उस व्यक्ति
से बंधा होता है जिसने उसे बनाया — अगर वे org छोड़ देते हैं या अपने टोकन रिवोक
कर देते हैं, तो उस सीक्रेट का उपयोग करने वाली हर रिपॉज़िटरी 401 के साथ फ़ेल
होने लगती है, और CI द्वारा बनाई गई योजनाएं टीम के बजाय उस व्यक्ति के मालिकाना
हक़ में होती हैं। एक org सर्विस टोकन आपके **ऑर्गनाइज़ेशन** के मालिकाना हक़ में
होता है: यह एक सर्विस प्रिंसिपल (`svc-<name>@service.<orgId>`) के रूप में काम
करता है, किसी भी व्यक्ति के जाने के बाद भी बना रहता है, इसके द्वारा प्रकाशित
रीकैप org-विज़िबल होते हैं, और कोई भी org ओनर या एडमिन इसे लिस्ट या रिवोक कर
सकता है। एक टोकन मिंट करें (सिर्फ़ org ओनर/एडमिन):

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --service-token pr-recap
```

यह कमांड आपको ब्राउज़र में प्रमाणित करता है, फिर सर्विस टोकन को बिल्कुल एक
बार प्रिंट करता है — इसे `PLAN_RECAP_TOKEN` सीक्रेट के रूप में स्टोर करें।
इसे बाद में Plans ऐप पर `list-org-service-tokens` और
`revoke-org-service-token` actions से मैनेज करें।

**सोलो: एक पर्सनल टोकन भी काम करता है।** इसे अपने Plans ऐप के विरुद्ध
`npx @agent-native/core@latest connect` से मिंट करें। होस्टेड ऐप के लिए, यह
एक लोकल पब्लिश-टोकन फ़ाइल भी लिखता है जिसे
`npx @agent-native/recap-cli@latest recap setup` पढ़ सकता है:

```bash
npx @agent-native/core@latest connect https://plan.agent-native.com --client codex
npx @agent-native/recap-cli@latest recap setup
```

अगर आप मैनुअल सेटअप पसंद करते हैं, तो टोकन को GitHub सीक्रेट में पेस्ट करें।
सिर्फ़ उदाहरणों के लिए `plan_recap_xxxxxxxxxxxxxxxx` जैसा प्लेसहोल्डर
उपयोग करें — किसी असली टोकन को कभी कमिट न करें।

## टिप्पणी में इनलाइन स्क्रीनशॉट

एजेंट द्वारा रीकैप प्रकाशित करने के बाद, वर्कफ़्लो हेडलेस Chrome में रेंडर की
गई योजना का लाइट और डार्क दोनों मोड में स्क्रीनशॉट लेता है और PNG को Plans
ऐप पर एक साइन्ड पब्लिक इमेज रूट पर अपलोड करता है। स्टिकी PR टिप्पणी फिर उन
स्क्रीनशॉट को एक `<picture>` एलिमेंट के साथ **इनलाइन** एम्बेड करती है —
GitHub उन्हें अपने camo प्रॉक्सी के ज़रिए फिर से सर्व करता है, इसलिए समीक्षक
कुछ भी खोले बिना सीधे टिप्पणी में एक ऐसा प्रीव्यू देखते हैं जो उनकी GitHub
थीम से मैच करता है। पूरी इंटरैक्टिव योजना का लिंक इसके ठीक बगल में होता है
उस समय के लिए जब वे एक्सप्लोर करना, टिप्पणी करना, या एनोटेट करना चाहें।

## फ़ोर्क PR

### डिफ़ॉल्ट व्यवहार (कोई कार्रवाई ज़रूरी नहीं)

मुख्य `pr-visual-recap.yml` वर्कफ़्लो सादे `pull_request` ट्रिगर पर चलता है,
**न कि** `pull_request_target` पर। इसलिए फ़ोर्क PR **रिपॉज़िटरी सीक्रेट तक
कोई एक्सेस** के बिना चलते हैं, इसलिए वर्कफ़्लो को कोई `PLAN_RECAP_TOKEN` नहीं
मिलता और यह साफ़-सुथरे तरीके से नो-ऑप हो जाता है — न कोई फ़ेल हुआ पब्लिश, न
कोई क्रेडेंशियल एक्सपोज़। उसी रिपॉज़िटरी की ब्रांच से आने वाले PR के लिए
रीकैप ऑटोमैटिकली चलते हैं, जहां सीक्रेट उपलब्ध होते हैं।

इसका यह भी मतलब है कि आप सीक्रेट मौजूद होने **से पहले** वर्कफ़्लो फ़ाइल को
मर्ज कर सकते हैं: कोई टोकन कॉन्फ़िगर न होने पर, जब तक आप सीक्रेट सेट नहीं
करते, हर रन एक शांत नो-ऑप है। `gate` स्टेप ड्राफ़्ट PR और बॉट-लिखे PR को भी
अपने-आप स्किप कर देता है, इसलिए इनमें से कोई भी ट्रिगर डिफ़ॉल्ट रूप से रीकैप
रन नहीं चलाता।

### लेबल-गेटेड फ़ोर्क वर्कफ़्लो के साथ ऑप्ट-इन करें

अगर आप फ़ोर्क PR के लिए रीकैप जेनरेट करना चाहते हैं, तो एक दूसरी वर्कफ़्लो
फ़ाइल उपलब्ध है: `.github/workflows/pr-visual-recap-fork.yml`। यह
`pull_request_target` (जो base-repo सीक्रेट के साथ चलता है) का उपयोग करता है
लेकिन फ़ोर्क कोड को कभी चेकआउट या एग्ज़िक्यूट नहीं करता। GitHub लेखक
एसोसिएशन `OWNER`, `MEMBER`, या `COLLABORATOR` वाले विश्वसनीय फ़ोर्क लेखक
ऑटोमैटिकली चलते हैं। बाहरी फ़ोर्क PR को रीकैप एजेंट चलने से पहले एक ताज़ा
`recap` लेबल इवेंट के ज़रिए एक स्पष्ट **प्रति-head मेंटेनर ऑप्ट-इन** की
ज़रूरत होती है।

इसे इंस्टॉल करने के लिए, फ़ाइल को
[BuilderIO/agent-native](https://github.com/BuilderIO/agent-native/blob/main/.github/workflows/pr-visual-recap-fork.yml)
से अपने रेपो की `.github/workflows/` डायरेक्टरी में मौजूदा
`pr-visual-recap.yml` के साथ कॉपी करें। वही बैकएंड कॉन्फ़िगरेशन लागू होता है,
जिसमें OpenAI-कम्पैटिबल प्रोवाइडर का उपयोग करते समय `VISUAL_RECAP_API_KEY`,
`VISUAL_RECAP_BASE_URL`, और `VISUAL_RECAP_MODEL` शामिल हैं।

### लेबल गेट कैसे काम करता है

1. एक फ़ोर्क योगदानकर्ता एक PR खोलता है। सामान्य `pull_request` वर्कफ़्लो
   स्किप हो जाता है क्योंकि GitHub फ़ोर्क रन से सीक्रेट रोक लेता है।
2. फ़ोर्क वर्कफ़्लो PR लेखक एसोसिएशन जांचता है। विश्वसनीय लेखक (`OWNER`,
   `MEMBER`, या `COLLABORATOR`) खुलने, सिंक्रोनाइज़, फिर से खुलने, और
   ready-for-review इवेंट पर ऑटोमैटिकली चलते हैं।
3. बाहरी योगदानकर्ताओं के लिए किसी मेंटेनर को मौजूदा diff की समीक्षा करनी
   होती है (ख़ासकर prompt-injection के आकार वाली सामग्री के लिए — नीचे
   देखें), फिर PR पर `recap` लेबल लगाना होता है।
4. बाहरी-योगदानकर्ता लेबल गेट प्रति head SHA है: अगर योगदानकर्ता और कमिट
   पुश करता है, तो अगला सिंक्रोनाइज़ इवेंट तब तक स्किप होता है जब तक कोई
   मेंटेनर नए diff की समीक्षा करने के बाद `recap` को हटाकर दोबारा नहीं
   लगाता।

### फ़ोर्क वर्कफ़्लो क्या करता है और क्या नहीं करता

| वर्कफ़्लो यह करता है                                                                                                    | वर्कफ़्लो यह नहीं करता                                                              |
| ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| **base रिपॉज़िटरी** को **base ब्रांच ref** पर चेकआउट करता है — सिर्फ़ विश्वसनीय कोड                                       | फ़ोर्क से किसी भी कोड को चेक आउट या एग्ज़िक्यूट करना                                   |
| फ़ोर्क head को एक रिमोट ref के रूप में फ़ेच करता है (`git fetch origin pull/<n>/head:refs/recap/fork-head`) — कमिट फ़ेच करना सुरक्षित है | फ़ोर्क से पैकेज इंस्टॉल करना, फ़ोर्क स्क्रिप्ट चलाना, या फ़ोर्क सामग्री को कोड के रूप में एग्ज़ीक्यूट करना |
| `git diff base...refs/recap/fork-head` चलाता है — पहले से फ़ेच की गई दो ऑब्जेक्ट का शुद्ध टेक्स्ट diff                    | diff को LLM के लिए टेक्स्ट इनपुट के अलावा किसी और तरह इस्तेमाल करना                     |
| **base repo** का visual-recap कौशल और एजेंट कॉन्फ़िगरेशन चलाता है                                                          | फ़ोर्क से कोई कौशल या कॉन्फ़िग लोड करना                                                |
| फ़र्स्ट-पार्टी PR जैसे ही सीक्रेट-स्कैन स्टेप (fail-closed) से diff को गुज़ारता है                                          | सीक्रेट स्कैन को स्किप करना                                                            |
| एजेंट प्रॉम्प्ट में diff सामग्री को अविश्वसनीय बताता एक स्पष्ट prompt-hardening नोट जोड़ता है                              | सामान्य रीकैप एजेंट से आगे एजेंट को कोई अतिरिक्त परमिशन देना                           |

### आपको लेबल लगाने से पहले diff की समीक्षा क्यों करनी चाहिए

फ़ोर्क diff अटैकर-नियंत्रित टेक्स्ट है जिसे रीकैप एजेंट इनपुट के रूप में
पढ़ता है। एक सावधानी से तैयार किया गया diff prompt-injection सामग्री रख सकता
है — उदाहरण के लिए, ऐसी diff लाइनें जो एजेंट इंस्ट्रक्शन जैसी दिखती हैं —
जिनका मक़सद रीकैप एजेंट से अनइच्छित एक्शन करवाना हो सकता है (जैसे, पब्लिश
टोकन को एक्सफ़िल्ट्रेट करना या भ्रामक रीकैप सामग्री बनाना)।

`recap` लेबल लगाने से पहले, diff में इन चीज़ों के लिए स्किम करें:

- ऐसी लाइनें जो सीधे कमांड या रोल इंस्ट्रक्शन जैसी पढ़ी जाती हैं ("पिछले
  इंस्ट्रक्शन नज़रअंदाज़ करें...", "अब आप हैं...", "टोकन यहां लिखें...")।
- असामान्य फ़ाइल नाम जिन्हें सिस्टम प्रॉम्प्ट समझ लिया जा सकता है।
- जोड़ी गई फ़ाइलों में एन्कोडेड सामग्री जो डिकोड होकर इंस्ट्रक्शन बन सकती
  है।

ये मिटिगेशन वर्कफ़्लो में पहले से लेयर किए गए हैं (सीक्रेट स्कैन,
सेंसिटिव-पाथ गेट, prompt-hardening नोट, प्रतिबंधित एजेंट टूल allow-list),
लेकिन लेबल समीक्षा ही सुरक्षा की पहली पंक्ति है।

### मुख्य वर्कफ़्लो से संबंध

दोनों वर्कफ़्लो फ़ाइलें एक-दूसरे से स्वतंत्र हैं। नॉन-फ़ोर्क PR अपडेट के
लिए, `pr-visual-recap.yml` ही एकमात्र वर्कफ़्लो है जो चलता है। फ़ोर्क PR के
लिए, सामान्य वर्कफ़्लो अपने फ़ोर्क गेट पर रुक जाता है, और
`pr-visual-recap-fork.yml` विश्वसनीय, उसी org के लेखकों के लिए, या बाहरी
योगदानकर्ताओं के लिए एक ताज़ा मेंटेनर `recap` लेबल के बाद ऑटोमैटिकली चलता
है। वे एक ही स्टिकी-कमेंट मार्कर और plan-id थ्रेडिंग साझा करते हैं, इसलिए PR
और फ़ोर्क PR दोनों एक ही PR पर एक सिंगल अपसर्टेड टिप्पणी बनाते हैं।

### सेल्फ़-मॉडिफ़ाइंग गार्ड {#self-modifying-guard}

`gate` स्टेप रीकैप को पूरी तरह स्किप कर देता है जब कोई PR इनमें से किसी भी
पाथ को छूता है, ताकि कोई PR कभी भी उस वर्कफ़्लो, कौशल, या एजेंट कॉन्फ़िग को
दोबारा न लिख सके जिसे विश्वसनीय रीकैप जॉब लोड करता है और सीक्रेट
एक्सफ़िल्ट्रेट कर सके:

| पाथ पैटर्न                                | कारण                                             |
| ------------------------------------------ | -------------------------------------------------- |
| `.github/workflows/pr-visual-recap.yml`    | खुद वर्कफ़्लो                                      |
| `**/skills/visual-(recap\|plan\|plans)/**` | वह visual-recap कौशल जिसे एजेंट फ़ॉलो करता है      |
| `**/.claude/**`                            | एजेंट सेटिंग जो रनर लोड करता है                    |
| `**/CLAUDE.md`                             | एजेंट इंस्ट्रक्शन जो रनर लोड करता है               |
| `**/AGENTS.md`                             | एजेंट इंस्ट्रक्शन जो रनर लोड करता है               |
| `**/.mcp.json`                             | MCP सर्वर कॉन्फ़िग जो रनर लोड करता है              |

`BuilderIO/agent-native` मोनोरेपो में, वर्कफ़्लो रीकैप CLI को PR-head सोर्स
के बजाय विश्वसनीय base-branch सोर्स से चलाता है। इससे `packages/core/**`
सहित सामान्य पैकेज परिवर्तन PR-मॉडिफ़ाइड CLI कोड को एग्ज़िक्यूट किए बिना
रीकैप के लिए योग्य बने रहते हैं।

## लोकल-फ़ाइलें प्राइवेसी मोड

GitHub Action होस्टेड, साझा करने योग्य PR समीक्षा के लिए डिज़ाइन किया गया है।
अगर आप Agent-Native Plan डेटाबेस को रीकैप सामग्री भेजे बिना एक रीकैप चाहते
हैं, तो इसके बजाय वही हेल्पर फ़्लो लोकल-फ़ाइलें मोड में लोकल रूप से चलाएं:

```bash
npx @agent-native/recap-cli@latest recap collect-diff --base main --head HEAD --out recap.diff --stat recap.stat
npx @agent-native/recap-cli@latest recap scan --diff recap.diff
npx @agent-native/recap-cli@latest recap build-prompt --pr 123 --diff recap.diff --stat recap.stat --local-files --local-dir plans/pr-123-visual-recap
```

जेनरेट की गई `recap-prompt.md` को अपने कोडिंग एजेंट को दें। लोकल-फ़ाइलें
मोड में यह प्रॉम्प्ट एजेंट को `plans/pr-123-visual-recap/plan.mdx` प्लस
वैकल्पिक विज़ुअल फ़ाइलें लिखने का निर्देश देता है और फिर चलाने का:

```bash
npx @agent-native/core@latest plan local serve --dir plans/pr-123-visual-recap --kind recap --open
```

लौटाया गया URL होस्टेड Plan UI खोलता है जबकि ब्राउज़र रीकैप MDX को एक
लोकलहोस्ट ब्रिज से पढ़ता है। रीकैप सामग्री होस्टेड Plan डेटाबेस में नहीं
लिखी जाती, और URL सिर्फ़ उसी मशीन पर काम करता है जो ब्रिज चला रही है। अगर
आप वही Plan ऐप उसी `PLAN_LOCAL_DIR` के साथ लोकल रूप से चलाते हैं, तो
`/local-plans/pr-123-visual-recap` रूट भी मान्य है। रेपो-समर्थित फ़ोल्डर
`/local-plans/pr-123-visual-recap?path=plans%2Fpr-123-visual-recap` के रूप
में खुल सकते हैं। यह मोड होस्टेड स्टिकी PR टिप्पणी, इनलाइन स्क्रीनशॉट
अपलोड, यूसेज अटैचमेंट, और ब्राउज़र टिप्पणियों को तब तक डिसेबल कर देता है जब
तक आप स्पष्ट रूप से प्रकाशित नहीं करते।

## यह इन्फ़ॉर्मेशनल है, कोई गेट नहीं

रीकैप सामान्य PR फ़्लो के ऊपर एक समीक्षा सहायता है:

- यह विज़िबिलिटी के लिए एक `Visual Recap` चेक रो दिखाता है, लेकिन यह
  **कभी भी ज़रूरी चेक** नहीं है और कभी भी मर्जिंग को ब्लॉक नहीं करता।
- कोई जेनरेशन या पब्लिश फ़ेलियर न्यूट्रल रूप से पूरा होता है और असंबंधित
  कोड पर लाल X के बजाय एक व्याख्यात्मक स्टिकी टिप्पणी के रूप में सामने आता
  है।
- रीकैप और इसका स्क्रीनशॉट **यह नहीं दर्शाते कि diff की समीक्षा हो चुकी है**।
  समीक्षकों को अब भी असली बदली गई लाइनें पढ़ने की ज़रूरत है।

## वर्ज़न पिनिंग (कॉपी वेरिएंट) {#version-pinning-copy-variant}

डिफ़ॉल्ट रूप से कॉपी-वेरिएंट वर्कफ़्लो रन टाइम पर
`@agent-native/recap-cli@latest` इंस्टॉल करता है ताकि हर रीकैप रन
ऑटोमैटिकली नवीनतम CLI उठाए। अगर आपके CI को रिप्रोड्यूसिबल टूलिंग चाहिए, तो
इंस्टॉल किए गए वर्ज़न को पिन करने के लिए **`RECAP_CLI_VERSION`** रिपॉज़िटरी
वेरिएबल सेट करें:

1. अपनी रेपो की **Settings → Secrets and variables → Actions → Variables**
   पर जाएं।
2. `1.5.0` जैसी वैल्यू के साथ `RECAP_CLI_VERSION` नाम का एक वेरिएबल बनाएं।

वेरिएबल वैकल्पिक है। नवीनतम रिलीज़ को ट्रैक करने के लिए इसे अनसेट छोड़ें (या
इसे `latest` पर सेट करें)।

रीयूज़ेबल-कॉलर वेरिएंट के लिए, इसके बजाय `cli-version` इनपुट का उपयोग करें
(रीयूज़ेबल सेक्शन में [Version pinning](#version-pinning) देखें)।

## सीक्रेट-स्कैन Allowlist

रीकैप प्रकाशित करने से पहले वर्कफ़्लो diff में संभावित सीक्रेट का पता लगाने
के लिए `npx @agent-native/recap-cli@latest recap scan` चलाता है। कोई भी PR
जिसका diff किसी जाने-पहचाने सीक्रेट पैटर्न से मेल खाता है, उसे एक
व्याख्यात्मक टिप्पणी के साथ ब्लॉक कर दिया जाता है — रीकैप प्रकाशित नहीं
होता, और कोडिंग एजेंट को कोई diff सामग्री नहीं भेजी जाती।

कभी-कभार किसी रेपो में जानबूझकर टेस्ट फ़िक्स्चर या नॉन-सीक्रेट स्ट्रिंग होती
हैं जो ऊपरी तौर पर सीक्रेट पैटर्न जैसी दिखती हैं (जैसे, किसी टेस्ट फ़ाइल में
एक फ़िक्स्चर कुंजी)। किसी फ़ॉल्स पॉज़िटिव को दबाने के लिए, अपनी रिपॉज़िटरी
के रूट में `.github/recap-scan-allowlist` बनाएं।

### फ़ॉर्मैट

हर नॉन-ब्लैंक, नॉन-कमेंट लाइन या तो एक **लिटरल सबस्ट्रिंग** है या एक
**`/regex/flags`** पैटर्न:

```
# Lines starting with # are comments.

# Literal substring — any diff line containing this string is allowed.
sk-test-fixture1234567890abcdef

# Regex pattern — written as /pattern/flags (JS syntax).
/^.STRIPE_KEY=sk-test-/i

# Another literal.
EXAMPLE_API_KEY=placeholder-value
```

नियम:

- कोई लाइन तब **दबाई** (allowed) जाती है जब उसमें लिटरल शामिल हो, या जब
  पूरी लाइन regex से मैच करे।
- फ़ाइल **fail-closed** है: अगर यह मौजूद नहीं है, तो कोई सप्रेशन लागू नहीं
  होता — स्कैनर पहले जैसा ही व्यवहार करता है।
- एक खाली फ़ाइल किसी फ़ाइल के न होने के बराबर है।
- गलत तरीके से बनी regex लाइनों को लिटरल स्ट्रिंग माना जाता है।

Allowlist को सिर्फ़ सीक्रेट-स्कैन गेट द्वारा देखा जाता है। यह इस पर असर नहीं
डालता कि कोडिंग एजेंट क्या पढ़ सकता है — अगर गेट पास हो जाता है, तो एजेंट को
हर हाल में पूरा diff मिलता है।

## एक रीयूज़ेबल वर्कफ़्लो के रूप में अपनाएं

### रीयूज़ेबल वेरिएंट का उपयोग क्यों करें?

डिफ़ॉल्ट इंस्टॉलर पूरे ~360-लाइन वर्कफ़्लो YAML को आपके रेपो में कॉपी करता
है (**कॉपी** विकल्प)। यह एयर-गैप्ड रेपो या ऐसी रेपो के लिए सही विकल्प है
जिन्हें चलने वाली हर लाइन को ऑडिट करने की ज़रूरत होती है। नुकसान यह है कि
बग फ़िक्स और सुधार आप तक कभी नहीं पहुंचते — आपको हर रिलीज़ के बाद
`npx @agent-native/recap-cli@latest recap setup` को मैनुअली फिर से चलाना
पड़ता है।

**रीयूज़ेबल** विकल्प इसके बजाय एक पतला ~20-लाइन कॉलर लिखता है। यह `uses:`
के ज़रिए `BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml`
को डेलिगेट करता है। वर्कफ़्लो चलने पर हर कॉलर ऑटोमैटिकली नवीनतम लॉजिक उठा
लेता है, बिना किसी लोकल अपडेट की ज़रूरत के।

|                                          | कॉपी (डिफ़ॉल्ट)                | रीयूज़ेबल                             |
| ---------------------------------------- | -------------------------------- | ---------------------------------------- |
| आपकी रेपो में वर्कफ़्लो का आकार          | ~360 लाइनें                      | ~20 लाइनें                               |
| ऑटोमैटिकली सुधार उठाता है                | नहीं — `recap setup` फिर चलाएं   | हां                                       |
| एयर-गैप / पूरी ऑडिटेबिलिटी               | हां                               | नहीं                                      |
| किसी ख़ास वर्ज़न पर पिन करने योग्य       | सिर्फ़ लोकल रूप से एडिट करके     | हां — `uses:` में `@v1.2.3` सेट करें      |

### कॉलर स्निपेट

यह वह है जो `npx @agent-native/recap-cli@latest recap setup --reusable`
लिखता है (या आप इसे मैनुअली पेस्ट कर सकते हैं):

```yaml
name: PR Visual Recap

# Thin caller — the full workflow logic lives in BuilderIO/agent-native.
# Fixes and improvements reach this repo automatically on each run.
# To pin a specific version for reproducibility replace '@main' with a
# tag or SHA, e.g. '@v1.2.3' or '@abc1234'.

on:
  pull_request:
    types: [opened, synchronize, reopened, ready_for_review, labeled, closed]

jobs:
  visual-recap:
    if: github.event.action != 'labeled' || vars.VISUAL_RECAP_REQUIRED_LABELS != ''
    permissions:
      actions: write
      contents: read
      checks: write
      issues: write
      pull-requests: write
    uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@main
    secrets:
      PLAN_RECAP_TOKEN: ${{ secrets.PLAN_RECAP_TOKEN }}
      ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
      OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
      VISUAL_RECAP_API_KEY: ${{ secrets.VISUAL_RECAP_API_KEY }}
      PLAN_RECAP_APP_URL: ${{ secrets.PLAN_RECAP_APP_URL }}
    with:
      agent: ${{ vars.VISUAL_RECAP_AGENT || 'claude' }}
      model: ${{ vars.VISUAL_RECAP_MODEL || '' }}
      base-url: ${{ vars.VISUAL_RECAP_BASE_URL || '' }}
      reasoning: ${{ vars.VISUAL_RECAP_REASONING || '' }}
      skill-source: ${{ vars.VISUAL_RECAP_SKILL_SOURCE || 'auto' }}
      runs-on: ${{ vars.VISUAL_RECAP_RUNS_ON || '"ubuntu-latest"' }}
      gate-runs-on: ${{ vars.VISUAL_RECAP_GATE_RUNS_ON || 'ubuntu-latest' }}
      required-labels: ${{ vars.VISUAL_RECAP_REQUIRED_LABELS || '' }}
      # cli-version: "latest"  # pin to a specific @agent-native/recap-cli version
```

[Secrets and variables](#secrets-and-variables) में बताए गए वही सीक्रेट और
वेरिएबल लागू होते हैं — इन्हें अपनी रेपो सेटिंग में उसी तरह सेट करें जैसे
कॉपी वेरिएंट के लिए किया था। रीयूज़ेबल कॉलर पूरे रीकैप जॉब के लिए
`VISUAL_RECAP_RUNS_ON` को अपने JSON `runs-on` इनपुट के ज़रिए, मेटाडेटा-ओनली
गेट के लिए `VISUAL_RECAP_GATE_RUNS_ON` को अपने प्लेन-लेबल `gate-runs-on`
इनपुट के ज़रिए, और वैकल्पिक PR-लेबल गेटिंग के लिए `VISUAL_RECAP_REQUIRED_LABELS`
को `required-labels` के ज़रिए फ़ॉरवर्ड करता है। गेट रनर इनपुट सिर्फ़
विश्वसनीय, उसी रिपॉज़िटरी के लेखकों के लिए उपयोग होता है; बाकी PR
GitHub-होस्टेड `ubuntu-latest` का उपयोग करते हैं। रनर इनपुट न देने पर उनके
`ubuntu-latest` डिफ़ॉल्ट बने रहते हैं; ज़रूरी लेबल न देने पर ऑटोमेटिक रीकैप
व्यवहार बना रहता है।

### CLI के ज़रिए इंस्टॉल करना

```bash
# Write the thin caller instead of the full copy:
npx @agent-native/recap-cli@latest recap setup --reusable

# Or with a pinned ref for reproducibility:
npx @agent-native/recap-cli@latest recap setup --reusable --ref v1.2.3
```

दोनों वेरिएंट वर्कफ़्लो को `.github/workflows/pr-visual-recap.yml` में
लिखते हैं। अगर वहां पहले से कोई मौजूदा वर्कफ़्लो है और वह अलग है, तो कमांड
मना कर देता है और आपको ओवरराइट करने के लिए `--force` पास करने को कहता है।

लिखने के बाद, यह वेरिफ़ाई करने के लिए हमेशा की तरह
`npx @agent-native/recap-cli@latest recap doctor` चलाएं कि सीक्रेट
कॉन्फ़िगर हैं।

### वर्ज़न पिनिंग {#version-pinning}

डिफ़ॉल्ट रूप से कॉलर `@main` को रेफ़र करता है, जो हमेशा रीयूज़ेबल वर्कफ़्लो
के नवीनतम पब्लिश्ड वर्ज़न का उपयोग करता है। रिप्रोड्यूसिबल CI चाहने वाली
प्रोडक्शन रेपो के लिए, किसी टैग या SHA पर पिन करें:

```yaml
uses: BuilderIO/agent-native/.github/workflows/pr-visual-recap-reusable.yml@v1.2.3
```

`cli-version` इनपुट यह नियंत्रित करता है कि वर्कफ़्लो के भीतर कौन-सा
`@agent-native/recap-cli` वर्ज़न चलता है — नवीनतम रिलीज़ ट्रैक करने के लिए
इसे `"latest"` पर छोड़ें, या पूरी रिप्रोड्यूसिबिलिटी के लिए इसे किसी वर्ज़न
स्ट्रिंग (जैसे `"1.5.0"`) पर पिन करें।

### workflow_call इवेंट कॉन्टेक्स्ट

`workflow_call` वर्कफ़्लो **कॉलर के** इवेंट कॉन्टेक्स्ट को इनहेरिट करते हैं।
रीयूज़ेबल वर्कफ़्लो PR नंबर, head SHA, base SHA, मर्ज टाइमस्टैम्प, और PR
मेटाडेटा पढ़ने के लिए `github.event.pull_request.*` एक्सप्रेशन का उपयोग
करता है — ये सही तरीके से सिर्फ़ तभी काम करते हैं जब कॉलर `pull_request` पर
ट्रिगर होता है। ऊपर दिया गया कॉलर स्निपेट पहले से ही सही इवेंट टाइप शामिल
करता है। `closed` इवेंट इसलिए शामिल किया गया है ताकि मर्ज किए गए PR रीकैप
पर `merged_at` की मुहर लगाई जा सके और उन्हें बाद में शिप किए गए काम के रूप
में खोजा जा सके।

कॉलर को `workflow_dispatch` या `push` पर ट्रिगर न करें — इन इवेंट में
`pull_request` पेलोड नहीं होता, और गेट "no pull_request payload" के साथ
रीकैप को स्किप कर देगा।
