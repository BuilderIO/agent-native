# संगठन, टीमें और अनुमतियाँ

संगठन team membership और tenant boundary तय करता है। Workspace apps और deployment config को समूहित करता है, लेकिन संगठन का विकल्प नहीं है। Server को permissions जाँचनी चाहिए। UI में button छिपाना authorization नहीं है।

## भूमिकाओं के तीन दायरे

- संगठन के `owner`, `admin` और `member` roles टीम प्रबंधन नियंत्रित करते हैं। मालिक और एडमिन ईमेल डोमेन से अपने-आप जुड़ना मैनेज करते हैं; ऐप्स के बीच साझा A2A secret सिर्फ़ मालिक मैनेज करता है।
- App roles एक app के भीतर की क्षमताएँ नियंत्रित करते हैं। किसी सदस्य के कई app roles हो सकते हैं।
- Resource roles `viewer`, `editor` और `admin` एक row तक पहुँच नियंत्रित करते हैं।

App code में roles और permission keys घोषित होते हैं। Admin टीम पेज से सदस्य के पूरे role set को बदल सकता है और घोषित permissions को roles से जोड़ सकता है। Override न होने पर app defaults लागू होते हैं। Invitation में app roles पहले से दिए जा सकते हैं। App admin को organization admin अधिकार नहीं मिलते।

आमंत्रण और config के लिए [प्रशासित डिप्लॉयमेंट](/docs/administered-deployments) देखें। डेटा पहुँच के लिए [डेटा स्कोपिंग](/docs/security#data-scoping) देखें।

## उपयोगकर्ता समूह {#user-groups}

किसी संगठन में उसके मौजूदा सदस्यों के पुन: उपयोग योग्य समूह हो सकते हैं। मालिक और एडमिन समूह की सदस्यता संभालते हैं, और एक व्यक्ति कई समूहों में हो सकता है। ऐप किसी समूह का उपयोग ऐसे संसाधन को साझा करने के लिए कर सकते हैं जो समूह साझाकरण का समर्थन करता हो, या वर्कस्पेस कनेक्शन तक पहुँच सीमित करने के लिए कर सकते हैं।

समूह एक एक्सेस सूची है, अलग टीम नहीं। उसके अपने संगठन या ऐप रोल, अलग डेटा सीमा, या टीम-विशिष्ट सेटिंग, निर्देश, संदर्भ, कौशल, मेमोरी या काम देखने की जगह नहीं होती। समूह के साथ साझा किए गए संसाधन का वही रोल उसके सभी मौजूदा सदस्यों पर लागू होता है। पहुँच के लिए व्यक्ति का उस संसाधन के संगठन का सदस्य होना अब भी ज़रूरी है।

विवरण के लिए [Sharing & Privacy → Group grants](/docs/sharing#group-grants) और [Workspace Connections](/docs/workspace-connections) देखें.
