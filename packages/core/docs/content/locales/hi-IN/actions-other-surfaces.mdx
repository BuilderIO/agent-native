# अन्य सतहें

UI-हुक सतह [Data & Sync](/docs/client-data) पर कवर की गई है: `useActionQuery()`, `useActionMutation()`, और `callAction()`। यह पेज बाकी हर उस चीज़ को कवर करता है जो किसी action को कॉल कर सकती है, या उससे संचालित हो सकती है।

## नेटिव चैट UI रेंडर करना {#native-chat-ui}

Actions structured widget डेटा लौटा सकते हैं जिसे in-app चैट नेटिव रूप से
रेंडर करता है। यह reusable टेबल, चार्ट, सेटअप सारांश, और insight कार्ड्स के
लिए first-party चैट पथ है। जब एजेंट को in-app चैट के अंदर मनमाने interactive
controls generate करने हों तो [Generative UI](/docs/generative-ui) का उपयोग
करें, और बाहरी MCP होस्ट्स में inline UI के लिए [MCP Apps](/docs/mcp-apps) का
उपयोग करें।

```ts
import { defineAction } from "@agent-native/core/action";
import { ACTION_CHAT_UI_DATA_CHART_RENDERER } from "@agent-native/core/action-ui";
import {
  createDataChartWidgetResult,
  dataChartWidgetResultSchema,
} from "@agent-native/core/data-widgets";

export default defineAction({
  description: "Summarize response trends.",
  readOnly: true,
  outputSchema: dataChartWidgetResultSchema,
  chatUI: { renderer: ACTION_CHAT_UI_DATA_CHART_RENDERER },
  run: async () =>
    createDataChartWidgetResult({
      title: "Response trends",
      chartSeries: {
        type: "line",
        xKey: "day",
        series: [{ key: "responses", label: "Responses" }],
        data: [
          { day: "Mon", responses: 12 },
          { day: "Tue", responses: 18 },
        ],
      },
    }),
});
```

built-in discriminants हैं `"data-table"`, `"data-chart"`, और
`"data-insights"`, इनके server-safe builders और schemas
`@agent-native/core/data-widgets` में हैं। केवल-chart उत्तरों के लिए
`data-chart` का उपयोग करें, SQL/list results के लिए `data-table`, और
`data-insights` केवल तब जब summary/chart/table का संयुक्त कार्ड सही आउटपुट
हो। पूरे result कॉन्ट्रैक्ट के लिए [Native Chat UI](/docs/native-chat-ui)
देखें, या अगर आप built-in चैट लूप के बजाय एक कस्टम एजेंट runtime वायर कर रहे
हैं तो [BYO agent runtimes](/docs/native-chat-ui#byo-agent-runtimes) देखें।
कैसे एक ही action automation-friendly बना रह सकता है, चैट में रेंडर हो सकता
है, या पूरी स्क्रीन में बढ़ सकता है, इसके लिए [Agent Surfaces](/docs/agent-surfaces)
देखें।

## इसे CLI से कॉल करना {#cli}

हर action `pnpm action` के माध्यम से चलाने योग्य है:

```bash
pnpm action reply-to-email '{"emailId":"thread-123","body":"Thanks!"}'
```

JSON इनपुट एजेंट्स और जटिल ऑब्जेक्ट्स के लिए पसंदीदा shape है। साधारण मैनुअल
रन और मौजूदा स्क्रिप्ट्स के लिए flags उसी तरह काम करते हैं:

```bash
pnpm action reply-to-email --emailId thread-123 --body "Thanks!"
```

`defineAction()` calls के लिए CLI तैयार और parsed arguments पर schema defaults लागू करके caller `cli` के साथ `needsApproval` evaluate करता है। अगर stdin और stdout दोनों TTY हैं, तो यह action का नाम और arguments दिखाकर `y/N` पूछता है। केवल `y` या `yes` से action चलता है।

दोनों TTY न होने पर CLI agent को व्यक्ति से approval माँगने को कहता है। उस विशेष call के लिए व्यक्ति की approval मिलने के बाद, बिल्कुल वही मूल `pnpm action` arguments दोबारा चलाएँ और अंत में `--approved` जोड़ें:

```bash
pnpm action reply-to-email --emailId thread-123 --body "Thanks!" --approved
```

`--approved` reserved CLI metadata है, जिसे input parsing से पहले हटा दिया जाता है। जिन actions को approval नहीं चाहिए, उनमें यह हानिरहित है। CLI यह नहीं जाँच सकता कि इसे किसने जोड़ा: जो agent बिना पूछे इसे जोड़ता है, वह पुष्टि को छोड़ देता है। यह flag approval को उस command में दिखाता है जिसे व्यक्ति approve करता है, और audit log में भी, जहाँ इसे असत्यापित दिखाया जाता है। POSIX `SHELL` के बिना Windows पर, refusal PowerShell के लिए command दिखाता है, और quoting अलग होने पर cmd.exe के लिए भी।

Local dev bridge JSON body में approval metadata को `input` के बाहर भेजता है:

```ts
{ name, input, approved: true, approvalSource: "flag" }
```

Approval के बिना gated call पर bridge HTTP `409` लौटाता है:

```ts
{
  ok: false,
  errorCode: "approval_required",
  error: 'Action "<name>" requires human approval. Ask the person, then rerun with --approved.',
  arguments: preparedArgs,
  argumentsHash: prepared.argumentsHash,
}
```

TTY में पुष्टि के बाद, CLI अनुमोदन माँगने वाली प्रतिक्रिया के `argumentsHash` के साथ फिर से प्रयास करता है:

```ts
{
  name,
  input,
  approved: true,
  approvalSource: "prompt",
  approvalArgumentsHash: challenge.argumentsHash,
}
```

Bridge वही call एक बार चलाता है जिसे व्यक्ति ने review किया था, इसलिए हर call में बदलने वाला default, जैसे timestamp, वही value रखता है जो व्यक्ति ने देखी थी। जिस confirmation के लिए चलाने को कोई held call नहीं है (वह पहले ही चल चुका है, 10 मिनट बीत गए हैं, या dev server restart हुआ है), उसे HTTP `409` के साथ `errorCode: "approval_expired"` मिलता है। Review करने के लिए command फिर से चलाएँ।

`arguments` में तैयार arguments होते हैं। Local dev bridge का यह contract [public HTTP action API के approval rules](/docs/actions-access-control#needs-approval) को नहीं बदलता। Approved gated CLI call, action की अपनी audit row पर caller `cli` के साथ `approval: "cli-prompt"` या `approval: "cli-flag"` दर्ज करती है। Prompt केवल CLI देखता है, इसलिए audit log दोनों को असत्यापित दिखाता है।

## इसे किसी अन्य एजेंट से कॉल करना (A2A) {#a2a}

अगर आपका ऐप एक [A2A](/docs/a2a-protocol) peer है, तो अन्य एजेंट-नेटिव ऐप्स आपके actions को अपने आप खोज लेते हैं और उन्हें नाम से कॉल कर सकते हैं। Same-origin deploys JWT signing को छोड़ देते हैं। Cross-origin deploys इसके बजाय एक साझा `A2A_SECRET` का उपयोग करते हैं।

## इसे MCP पर एक्सपोज़ करना {#mcp}

MCP सक्षम होने पर, आपके actions फ्रेमवर्क के MCP सर्वर में `/mcp` पर दिखाई देते हैं। हर कॉलर को डिफ़ॉल्ट रूप से एक compact catalog मिलता है (app-facing builtins प्लस टेम्पलेट-घोषित app actions), और `tool-search` हमेशा मौजूद रहता है ताकि कोई भी अन्य टूल मांग पर पहुंच योग्य बना रहे। पूरी action सतह केवल स्पष्ट opt-in पर परोसी जाती है (`--full-catalog` टोकन या `AGENT_NATIVE_MCP_FULL_CATALOG=1`), और [`publicAgent.expose`](/docs/actions-access-control#public-agent) किसी सुरक्षित read/ingest टूल को public सतह पर opt करता है। catalog tiers, auth, और `mcpApp` resource विवरण के लिए [MCP Protocol](/docs/mcp-protocol) देखें।

UI-सक्षम MCP होस्ट्स के लिए, कोई action `mcpApp` फ़ील्ड (प्लस एक मेल खाता `link`) के माध्यम से एक वैकल्पिक MCP Apps resource घोषित कर सकता है ताकि सक्षम होस्ट्स result को inline रेंडर करें। जब `link` और `mcpApp` को एक ही route पर पॉइंट करना हो, `embedRoute()` एक शुद्ध path builder से दोनों बनाता है:

```ts
import { embedRoute } from "@agent-native/core";

export default defineAction({
  description: "Create an email draft for review.",
  schema: z.object({ body: z.string() }),
  run: async ({ body }) => ({ body }),
  ...embedRoute({
    title: "Review draft",
    openLabel: "Open in Mail",
    path: ({ result }) => ({
      label: "Open draft in Mail",
      url: "/_agent-native/open?app=mail&view=inbox",
    }),
  }),
});
```

`link` को CLI और non-UI MCP होस्ट्स के लिए fallback के रूप में रखें। यह embed का launch target भी है। embed ब्रिज (signed embed-start session, transplant बनाम controlled-frame rendering, `ui/*` host ब्रिज, CSP, और height clamping) [External Agents](/docs/external-agents#mcp-app-bridge) के स्वामित्व में है।

यह कोई automated जांच मौजूद नहीं है कि किसी template में `view-screen`, `navigate`, या उसके primary resource के लिए create/read/update/list सेट है या नहीं; scaffold `view-screen` और `navigate` को शिप करता है, और `pnpm guard:external-result-contract` किसी externally-exposed action के `description` या `nextRequiredAction` में "user का इंतज़ार करें" जैसी भाषा को fail करता है, और किसी नए externally-exposed `create-*` action पर deep link अनिवार्य करता है। इनकी मौजूदगी एक review आइटम है।

## स्टैंडर्ड actions {#standard-actions}

हर टेम्पलेट को [context awareness](/docs/context-awareness) के लिए ये दोनों शामिल करने चाहिए।

### view-screen {#view-screen}

वर्तमान navigation स्थिति पढ़ता है, contextual डेटा fetch करता है, और उपयोगकर्ता जो देखता है उसका एक snapshot लौटाता है। एजेंट इसे तब कॉल करता है जब उसे स्क्रीन का एक ताज़ा लुक चाहिए।

```ts
// actions/view-screen.ts
import { defineAction } from "@agent-native/core/action";
import { readAppState } from "@agent-native/core/application-state";
import { z } from "zod";

export default defineAction({
  description: "Read the current screen state for context.",
  schema: z.object({}),
  http: { method: "GET" },
  run: async () => {
    const navigation = await readAppState("navigation");
    const screen: Record<string, unknown> = { navigation };

    if (navigation?.view === "inbox") {
      screen.emailList = await listEmailsForLabel(navigation.label);
    }

    return screen;
  },
});
```

### navigate {#navigate}

application state में एक one-shot navigation कमांड लिखता है। UI इसे पढ़ता है, navigate करता है, और entry को delete कर देता है।

```ts
// actions/navigate.ts
import { defineAction } from "@agent-native/core/action";
import { writeAppState } from "@agent-native/core/application-state";
import { z } from "zod";

export default defineAction({
  description: "Navigate the user to a view.",
  schema: z.object({
    view: z.string(),
    threadId: z.string().optional(),
  }),
  run: async (args) => {
    await writeAppState("navigate", args);
    return { ok: true };
  },
});
```
