# डेवलपर गाइड

यह पेज उन सभी के लिए है जो Design टेम्पलेट को कस्टमाइज़ या इस पर सीधे
कुछ बना रहे हैं: क्विक स्टार्ट, हर action, डेटा मॉडल, एक action को
स्टेप-बाय-स्टेप समझना, रूट सरफ़ेस, और इसमें कुछ जोड़ने का तरीका। ऐप क्या
करता है यह जानने के लिए [Design](/docs/template-design) देखें।

## क्विक स्टार्ट

<Steps>

### ऐप बनाएं

```bash
npx @agent-native/core@latest create my-design --standalone --template design
cd my-design
pnpm install
```

इसके लिए पहले [Node.js](https://nodejs.org) 22.22 या उसके बाद का वर्शन
और [pnpm](https://pnpm.io) इंस्टॉल होना चाहिए। अगर आपने अभी तक इनमें से
कोई इंस्टॉल नहीं किया है, या आपके पास कोई LLM कनेक्शन (Builder.io, कोई
Anthropic/OpenAI key, या लोकल Ollama) सेट अप नहीं है, तो [शुरुआत
करें](/docs/getting-started) देखें। Design को दूसरे ऐप्स के साथ एक
वर्कस्पेस में चलाने के लिए, इसके बजाय `npx @agent-native/core@latest
create my-platform` चलाएं और सेटअप के दौरान Design चुनें।

### डेव सर्वर शुरू करें

```bash
pnpm dev
```

ऐप `http://localhost:8099` पर खुलता है, Design का डिफ़ॉल्ट डेव पोर्ट।
Design बिना किसी एक्सटर्नल कनेक्शन के पूरी तरह काम करता है। आपको कनेक्ट
प्रॉम्प्ट सिर्फ़ तभी मिलेगा जब आप इन्हें सेट करने से पहले कोई Figma
इम्पोर्ट या Full App Building ट्राई करें।

</Steps>

## Actions की इन्वेंटरी

हर Design-स्पेसिफ़िक ऑपरेशन `templates/design/actions/` में एक
TypeScript फ़ाइल है, जो अपने आप `POST /_agent-native/actions/:name` पर
माउंट हो जाती है और CLI से `pnpm action <name>` के रूप में चलने योग्य है।

### डिज़ाइन

| Action                    | यह क्या करता है                                                               |
| ------------------------- | ----------------------------------------------------------------------------- |
| `create-design`           | खाली डिज़ाइन शेल बनाएं                                                        |
| `generate-design`         | जनरेट किया गया HTML/JSX फ़ाइल कॉन्टेंट लिखें                                  |
| `edit-design`             | किसी मौजूदा फ़ाइल में एक सटीक सर्च/रिप्लेस एडिट करें                          |
| `update-design`           | किसी डिज़ाइन का मेटाडेटा अपडेट करें, जैसे उसका टाइटल या लिंक्ड डिज़ाइन सिस्टम |
| `get-design`              | id से एक डिज़ाइन पढ़ें                                                        |
| `list-designs`            | एक्सेस किए जा सकने वाले डिज़ाइन लिस्ट करें                                    |
| `duplicate-design`        | एक डिज़ाइन और उसकी फ़ाइलें कॉपी करें                                          |
| `delete-design`           | एक डिज़ाइन डिलीट करें                                                         |
| `apply-tweaks`            | लाइव ट्वीक-नॉब वैल्यू परसिस्ट करें                                            |
| `present-design-variants` | कुछ दिशाओं को स्क्रीन के तौर पर सेव करें और साइड-बाय-साइड पिकर दिखाएं         |
| `show-design-questions`   | किसी अस्पष्ट प्रॉम्प्ट के लिए क्लैरिफ़ाइंग-क्वेश्चंस ओवरले दिखाएं             |
| `generate-screens`        | एक बैच में एक से ज़्यादा स्क्रीन जनरेट करें                                   |

### Full App Building (fusion, feature flag के पीछे) {#full-app-building}

यह `full-app-building` feature flag के पीछे है, और इसके लिए Builder.io
कनेक्टेड होना और एक branch project id कॉन्फ़िगर होना ज़रूरी है। नीचे
[Full App Building](#full-app-building) देखें।

| Action                         | यह क्या करता है                                                                         |
| ------------------------------ | --------------------------------------------------------------------------------------- |
| `create-fusion-app`            | एक Builder Fusion branch प्रोविज़न करें और किसी प्रॉम्प्ट से एक असली ऐप स्कैफ़ोल्ड करें |
| `sync-fusion-app`              | किसी fusion branch के कंटेनर को उसके प्रीव्यू URL के लिए पोल करें                       |
| `add-fusion-screens`           | किसी fusion-बैक्ड डिज़ाइन में स्क्रीन जोड़ें                                            |

## डेटा मॉडल

सभी डेटा Drizzle ORM के ज़रिए SQL में रहता है। स्कीमा:
`templates/design/server/db/schema.ts`। डिज़ाइन और डिज़ाइन सिस्टम में
स्टैंडर्ड `ownableColumns` और एक मेल खाती फ़्रेमवर्क शेयर टेबल होती है,
इसलिए वे पर-यूज़र / पर-ऑर्ग शेयरिंग मॉडल में फ़िट हो जाते हैं।

नीचे दी गई टेबल मुख्य ownable रिसोर्स को कवर करती है: designs, files,
templates, versions, और design systems।

| तालिका                                   | इसमें क्या है                                                                                                                                  |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `designs`                                | एक डिज़ाइन प्रोजेक्ट — `title`, `description`, `project_type` (`prototype` / `other`), `data` JSON ब्लॉब, और एक ऑप्शनल `design_system_id` लिंक |
| `design_files`                           | किसी डिज़ाइन से जुड़ी अलग-अलग फ़ाइलें (`filename`, `content`, `file_type` डिफ़ॉल्ट रूप से `html`)                                              |
| `design_templates`                       | रीयूज़ेबल टेम्पलेट मेटाडेटा, डायमेंशन, डिफ़ॉल्ट, सोर्स डिज़ाइन रेफ़रेंस, और लॉक्ड-लेयर काउंट                                                   |
| `design_template_files`                  | स्नैपशॉट किए गए टेम्पलेट फ़ाइलें, जो किसी यूज़र के टेम्पलेट से शुरू करने पर एक सामान्य एडिटेबल डिज़ाइन में कॉपी होती हैं                       |
| `design_template_shares`                 | प्राइवेट, org, एक्सप्लिसिटली शेयर्ड, और पब्लिक टेम्पलेट डिस्कवरी के लिए फ़्रेमवर्क शेयर टेबल                                                   |
| `design_versions`                        | इतिहास और रोलबैक के लिए एक ऑप्शनल `label` के साथ किसी डिज़ाइन के पॉइंट-इन-टाइम `snapshot`s                                                     |
| `design_systems`                         | रीयूज़ेबल ब्रांड टोकन — `data` (रंग/टाइपोग्राफ़ी/स्पेसिंग), `assets`, `custom_instructions`, और एक `is_default` फ़्लैग                         |
| `design_shares` / `design_system_shares` | प्रिंसिपल (यूज़र या ऑर्ग) को रोल (viewer, editor, admin) से मैप करने वाली फ़्रेमवर्क शेयर टेबल                                                 |

असली स्टैंडअलोन HTML/JSX फ़ाइलें लिखता है। जनरेट किया गया आर्टिफ़ैक्ट,
एडिटेबल सोर्स, और हर एक्सपोर्ट, सब उसी HTML से आते हैं, इसलिए अनुवाद
करने के लिए कोई अलग "AI मॉकअप" फ़ॉर्मेट नहीं है। एक लिंक्ड डिज़ाइन सिस्टम
टोकन और `custom_instructions` सप्लाई करता है जिन्हें एजेंट हर जनरेशन पास
पर सम्मान देता है।

सात और टेबल इस पेज में कहीं और कवर की गई सुविधाओं को सपोर्ट करती हैं, न
कि मुख्य रिसोर्स मॉडल को: `design_localhost_connections` और
`design_localhost_write_grants` [Local app import](/docs/template-design-features#import)
को सपोर्ट करते हैं, `component_index` [Design टैब के Component
सेक्शन](/docs/template-design-features#design-tab) को सपोर्ट करता है,
`motion_timeline` हर एलिमेंट की एडिटेबल मोशन टाइमलाइन (एडिटर में Motion
dock) को सपोर्ट करता है, `design_state` किसी डिज़ाइन के लिए नामित
ऑल्टरनेट स्टेट, स्टैटिक फ़िक्स्चर, और लाइव-ऐप कैप्चर रखता है,
`design_fusion_edits` ऊपर [Full App Building](#full-app-building) के तहत
बताई गई fusion edit queue को सपोर्ट करता है, और `design_review_snapshot`
`get-design-review` के पीछे की एक्सेसिबिलिटी फ़ाइंडिंग और विज़ुअल डिफ़ को
कैश करता है, जो ऊपर [क्वालिटी](#quality) के तहत बताया गया है।

परसिस्टेड रिव्यू कमेंट और थ्रेड (`get-review-feedback`,
`resolve-review-thread`, और बाकी) बिल्कुल भी कोई Design-स्पेसिफ़िक टेबल
नहीं हैं: ये `@agent-native/core/review` (`agent_review_comments` /
`agent_review_statuses`) का शेयर्ड फ़्रेमवर्क रिव्यू सिस्टम हैं, जिसे उसी
तरह किसी डिज़ाइन के दायरे में लाया जाता है जैसे कोई भी ऐप इसे अटैच कर
सकता है। यूज़र-फ़ेसिंग व्यवहार के लिए [Comments टैब](/docs/template-design-features#comments-tab)
देखें।

## एक action को स्टेप-बाय-स्टेप समझना

`save-design-as-template` कुछ ऐसे पैटर्न दिखाता है जो किसी भी action में
दोबारा इस्तेमाल करने लायक हैं: कोई काम शुरू करने से पहले किसी अनसपोर्टेड
इनपुट शेप को रिजेक्ट करना, कुछ भी सेव न होने से बचाव करना, हर reader में
बार-बार करने के बजाय ids को एक बार रीमैप करना, और एक ही transaction में
दो टेबल में लिखना ताकि किसी टेम्पलेट के पास कभी मेटाडेटा हो लेकिन फ़ाइलें
न हों, ऐसा न हो सके।

## एडिटर मॉडल

मल्टी-स्क्रीन काम के लिए Design overview-first है। जनरेशन या बड़े अपडेट
के बाद, एडिटर स्क्रीन ओवरव्यू खोलता है: एक इनफ़िनिट कैनवास जहां हर स्क्रीन
एक स्टैटिक फ़्रेम है जिसे आप सिलेक्ट, मूव, रीसाइज़, ड्रॉप, या डुप्लिकेट कर
सकते हैं। जब किसी स्क्रीन को फ़ोकस्ड स्क्रॉलिंग या प्रोटोटाइप इंटरैक्शन
चाहिए, तो फ़्रेम के full-view बटन का इस्तेमाल करें।

Single-screen मोड स्क्रॉलिंग, प्रोटोटाइप व्यवहार के साथ इंटरैक्ट करने,
और एक रेंडर्ड फ़ाइल के अंदर DOM/code लेयर एडिट करने के लिए है। Layers
पैनल इसी बंटवारे को दिखाता है: स्क्रीन टॉप-लेवल फ़्रेम होती हैं, और
एक्टिव स्क्रीन के लिए नेस्टेड DOM/code लेयर उनके नीचे रहती हैं।

हर स्क्रीन अलग-अलग चौड़ाई पर रेंडर किया गया एक ही डॉक्यूमेंट है, हर
ब्रेकपॉइंट की अलग कॉपी नहीं: एक बेस (सबसे चौड़ा) फ़्रेम नीचे तक cascade
होता है, और किसी संकरे एक्टिव ब्रेकपॉइंट पर किए गए एडिट उसके ऊपर
width-scoped overrides के तौर पर परसिस्ट होते हैं।

## एडिटर एक्सटेंशन

एडिटर में **Tweaks** के बाद एक **Extensions** इंस्पेक्टर टैब शामिल है।
यह एक Design-स्पेसिफ़िक plugin lane की तरह काम करता है: यूज़र
**+ Extension** पर क्लिक करके एजेंट से एक्सटेंशन बनवा सकते हैं, या ऐसा
एक्सटेंशन इंस्टॉल कर सकते हैं जो `design.editor.inspector` स्लॉट घोषित
करता है, फ़्रेमवर्क के `create-extension`, `add-extension-slot-target`,
और `install-extension` actions का इस्तेमाल करते हुए, न कि किसी
Design-स्पेसिफ़िक action से।

Design एक्सटेंशन स्टैंडर्ड extension sandbox के ज़रिए artboard के बगल
में इनलाइन रेंडर होते हैं। host `window.slotContext` और
`window.onSlotContext(...)` अपडेट में मौजूदा `designId`, एक्टिव फ़ाइल,
स्क्रीन लिस्ट, सिलेक्टेड स्क्रीन ids, सिलेक्टेड एलिमेंट मेटाडेटा, व्यू
मोड, ज़ूम, एक्टिव टूल, और ट्वीक वैल्यू भेजता है। इससे कोई एक्सटेंशन
मौजूदा सिलेक्शन की जानकारी दिखा सकता है, स्टाइल कंट्रोल दे सकता है, या
खुले डिज़ाइन के आसपास कॉम्पैक्ट वर्कफ़्लो बना सकता है।

डिटरमिनिस्टिक काम के लिए, एक्सटेंशन extension bridge के ज़रिए ऐप actions
कॉल कर सकते हैं। AI-ड्रिवन बदलावों के लिए, एक्सटेंशन से
`agentNative.chat.send(...)` कॉल करवाएं, साथ में सिलेक्टेड एलिमेंट
selector/source id और मांगा गया बदलाव दें। एजेंट को पहले `view-screen`
कॉल करना चाहिए, फिर एलिमेंट स्टाइल, क्लास, टेक्स्ट, या मूव बदलावों के
लिए `apply-visual-edit`, या आर्टबोर्ड प्लेसमेंट बदलावों के लिए
`canvasFrames` के साथ `update-design` / `generate-design` इस्तेमाल करना
चाहिए। sandbox, persistent state, और bridge APIs के लिए
[Extensions](/docs/extensions#capabilities) देखें।

## इसे कस्टमाइज़ करना

Design एक पूरा, क्लोन करने लायक टेम्पलेट है। कुछ व्यावहारिक एक्सटेंशन
आइडिया:

- "हमारे टोकन और सैंपल कंपोनेंट के साथ एक रीयूज़ेबल ईकॉमर्स डिज़ाइन सिस्टम जोड़ें।"
- "एक एक्सपोर्ट स्टेप जोड़ें जो ZIP को हमारे इंटरनल रिव्यू सिस्टम पर अपलोड करे।"
- "मुझे मौजूदा लैंडिंग-पेज HTML पेस्ट करने दें और एजेंट से तीन ज़्यादा मज़बूत वर्शन मांगने दें।"
- "प्रोडक्ट-पेज, डैशबोर्ड, और ऑनबोर्डिंग-स्क्रीन ब्रीफ़ के लिए एक सेव की गई प्रॉम्प्ट लाइब्रेरी जोड़ें।"
- "स्टेकहोल्डर रिव्यू के लिए एक कस्टम PDF एक्सपोर्ट प्रीसेट जोड़ें।"

एजेंट ज़रूरत के हिसाब से रूट्स, कंपोनेंट, actions, और SQL-बैक्ड मॉडल
एडिट करता है। पूरे clone, customize, deploy फ़्लो के लिए
[टेम्पलेट्स](/docs/cloneable-saas) देखें, और अगर यह आपका पहला
agent-native टेम्पलेट है तो [शुरुआत करें](/docs/getting-started) देखें।
