# आवर्ती नौकरियाँ

एक **आवर्ती कार्य** एक संकेत है जो क्रॉन शेड्यूल पर चलता है। इस तरह से एजेंट अपने आप काम करता है: "हर सुबह 7 बजे मेरे रात भर के ईमेल को सारांशित करें," "हर सोमवार को पिछले सप्ताह के साइनअप नंबर Slack पर पोस्ट करें," "हर घंटे पुराने ड्राफ्ट के लिए स्वीप करें और उन्हें हटा दें।"

<Callout tone="info">

**Recurring Jobs**, **Scheduled** ऑटोमेशन का पुराना नाम है। **Automations**, **Scheduled** और **Event** दोनों का व्यापक नाम है। `jobs/` और `manage-jobs` पुराने केवल-शेड्यूल इंटीग्रेशन के लिए बने रहते हैं। मॉडल और MCP अनुमत-सूचियों सहित नए व्यक्तिगत या संगठन कार्य के लिए `manage-automations` और `/agent#jobs` पर **Automations** का उपयोग करें।

</Callout>

आवर्ती नौकरियां एक घड़ी पर सक्रिय होती हैं। _घटनाओं_ पर प्रतिक्रिया करने के लिए (एक बुकिंग बनाई गई, एक ईमेल प्राप्त हुआ) - समान `jobs/` फ़ाइल प्रारूप और शर्तें - [Automations](/docs/automations) देखें।

जॉब्स `jobs/<name>.md` पर [एजेंट संसाधन](/docs/agent-resources) में रहते हैं - YAML फ्रंटमैटर के साथ सिर्फ एक Markdown फ़ाइल। कोई रजिस्ट्रेशन नहीं, कोई वायरिंग नहीं. फ़ाइल को अंदर छोड़ें और फ़्रेमवर्क उसे उठा लेता है।

बस इतना ही। बॉडी एक प्रॉम्प्ट है जिसे एजेंट प्रत्येक निर्धारित फायरिंग पर चलाता है। एजेंट के पास इंटरैक्टिव चैट में मौजूद सभी समान टूल और एजेंट संदर्भ तक पहुंच होती है - actions, skills, मेमोरी, कनेक्टेड MCP सर्वर, सब-एजेंट।

## फ्रंटमैटर {#frontmatter}

| फ़ील्ड       | प्रकार                        | डिफ़ॉल्ट     | विवरण                                                                                                               |
| ------------ | ----------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------- |
| `schedule`   | क्रोन अभिव्यक्ति              | _(आवश्यक)_   | मानक 5-फ़ील्ड क्रोन। `"0 7 * * *"` = प्रतिदिन प्रातः 07:00 बजे; `"0 */4 * * *"` = हर 4 घंटे।                        |
| `enabled`    | बूलियन                        | `true`       | कार्य को हटाए बिना रुकने के लिए `false` पर पलटें।                                                                   |
| `runAs`      | `"creator"` \| `"shared"`     | `"creator"`  | `"creator"` नौकरी मालिक की पहचान और `ANTHROPIC_API_KEY` के साथ चलता है। `"shared"` संगठन की कुंजी का उपयोग करता है। |
| `createdBy`  | ईमेल                          | _(ऑटो)_      | एजेंट संसाधन UI के माध्यम से या एजेंट द्वारा कार्य सृजित होने पर जनसंख्या।                                          |
| `orgId`      | स्ट्रिंग                      | _(ऑटो)_      | संगठन का दायरा; निर्माता के सक्रिय संगठन से विरासत में मिला है।                                                     |
| `lastRun`    | ISO टाइमस्टैम्प               | _(प्रबंधित)_ | प्रत्येक रन के बाद शेड्यूलर द्वारा लिखा गया।                                                                        |
| `lastStatus` | `"success"` \| `"error"` \| … | _(प्रबंधित)_ | नवीनतम परिणाम।                                                                                                      |
| `lastError`  | स्ट्रिंग                      | _(प्रबंधित)_ | अंतिम रन विफल होने पर त्रुटि संदेश।                                                                                 |
| `nextRun`    | ISO टाइमस्टैम्प               | _(प्रबंधित)_ | `schedule` से गणना; शेड्यूलर द्वारा यह तय करने के लिए उपयोग किया जाता है कि अगली बार कब फायर करना है।               |
| `mcpTools`   | MCP टूल नामों की ऐरे          | _(कोई नहीं)_ | वैकल्पिक स्पष्ट allowlist, जैसे `mcp__server__tool`; क्रेडेंशियल कनेक्टेड MCP grant में ही रहते हैं।                |

`last*` और `nextRun` फ़ील्ड शेड्यूलर द्वारा लिखे गए हैं। आप इतिहास देखने के लिए उन्हें पढ़ सकते हैं, लेकिन उन्हें हाथ से संपादित न करें - अगला रन ओवरराइट हो जाएगा।

## किसी जॉब से MCP टूल कनेक्ट करना {#connected-mcps}

आवर्ती जॉब उन रिमोट या लोकल MCP टूल का उपयोग कर सकते हैं जो पहले से ऐप से कनेक्टेड हैं। एजेंट से पहले `tool-search` के जरिए सटीक नाम खोजने को कहें, फिर `mcpTools` में केवल उस जॉब के आवश्यक टूल बाँधें:

```md
---
schedule: "0 * * * *"
enabled: true
mcpTools:
  ["mcp__meeting-notes__list_recordings", "mcp__meeting-notes__get_transcript"]
---

पिछले सफल रन के बाद की नई रिकॉर्डिंग खोजें। केवल काम करने योग्य फॉलो-अप निकालें, फिर स्थिर source और external IDs, एक छोटा citation और रिकॉर्डिंग URL के साथ ऐप के सीमित import action को एक बार कॉल करें। पूरा ट्रांसक्रिप्ट इंपोर्ट न करें।
```

जॉब MCP URL, access token या OAuth refresh token नहीं, केवल टूल नाम संग्रहीत करता है। रन टाइम पर फ़्रेमवर्क जॉब के creator या organization request context में कनेक्टेड grant का समाधान करता है और केवल allowlist वाले टूल उपलब्ध कराता है। सूची को सीमित रखें और अंतिम इंपोर्ट के लिए idempotent app action का उपयोग करें, ताकि ओवरलैप होने वाले रन डुप्लिकेट न बनाएं। कनेक्शन और OAuth सेटअप के लिए [MCP Clients](/docs/mcp-clients) देखें।

## क्रॉन सिंटैक्स {#cron}

मानक 5-फ़ील्ड क्रोन (मिनट, घंटा, महीने का दिन, महीना, सप्ताह का दिन):

| क्रॉन          | अर्थ                          |
| -------------- | ----------------------------- |
| `*/5 * * * *`  | हर 5 मिनट                     |
| `0 * * * *`    | हर घंटे पर घंटे               |
| `0 */4 * * *`  | हर 4 घंटे                     |
| `0 7 * * *`    | हर दिन 07:00 बजे              |
| `0 9 * * 1`    | प्रत्येक सोमवार प्रातः 09:00  |
| `0 17 * * 1-5` | सप्ताह के दिनों में 17:00 बजे |
| `0 0 1 * *`    | हर महीने का पहला दिन          |

फ्रेमवर्क में क्रॉन स्ट्रिंग्स को सत्यापित और रेंडर करने के लिए क्रॉन यूटिलिटीज (`isValidCron()` और `describeCron()`) शामिल हैं, जिनका उपयोग आंतरिक रूप से संसाधन और शेड्यूलर परतों द्वारा किया जाता है।

## नौकरी बनाना {#creating}

### एजेंट संसाधन टैब से

`+` → कार्यक्षेत्र पैनल में **निर्धारित कार्य**। प्रॉम्प्ट और शेड्यूल भरें. `jobs/<slug>.md` के रूप में सहेजता है और अगले मिलान टिक पर चलना शुरू कर देता है।

### एजेंट से पूछकर

> "एक निर्धारित कार्य बनाएं जिसमें हर सुबह 7 बजे मेरे अपठित ईमेल का सारांश हो।"

एजेंट आपके लिए फ़ाइल लिखता है।

### हाथ से

फ्रेमवर्क के संसाधन APIs के माध्यम से `jobs/` में एक Markdown फ़ाइल ड्रॉप करें:

```ts
import { resourcePut } from "@agent-native/core/resources";

await resourcePut(
  ownerEmail,
  "jobs/morning-digest.md",
  `---
schedule: "0 7 * * *"
enabled: true
---
Summarize overnight emails.`,
);
```

## शेड्यूलर कैसे चलता है {#how-scheduler-runs}

हर टिक पर शेड्यूलर (आंतरिक `processRecurringJobs()` रूटीन) उन जॉब को ढूंढता है जिनका समय हो गया है और उन्हें चलाता है। टिक किससे फायर होता है, यह इस पर निर्भर करता है कि ऐप कहाँ चल रहा है:

| होस्ट                                                               | टिक किससे फायर होता है                                              | आवश्यकताएँ और सीमाएँ                                                                                       |
| ------------------------------------------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| लंबे समय तक चलने वाला सर्वर (Node.js, Docker, Fly, Render, कोई VPS) | हर 60 सेकंड में एक इन-प्रोसेस टाइमर, बूट के 10 सेकंड बाद से शुरू    | प्रोसेस चालू रहने तक चलता है।                                                                              |
| [Netlify](/docs/netlify)                                            | Build द्वारा emit किया गया एक scheduled function, हर मिनट           | केवल published deploys पर, Deploy Previews या branch deploys पर कभी नहीं। Build को `A2A_SECRET` चाहिए।     |
| [Vercel](/docs/vercel#vercel-scheduled-work)                        | Build द्वारा जोड़ा गया एक Vercel cron job, डिफ़ॉल्ट रूप से हर मिनट  | केवल production deployment पर। `CRON_SECRET` चाहिए। Hobby projects इसे दिन में अधिकतम एक बार चला सकते हैं। |
| [Cloudflare Workers](/docs/cloudflare#cloudflare-scheduled-work)    | Build द्वारा `wrangler.json` में जोड़ा गया एक Cron Trigger, हर मिनट | Worker secret के रूप में `A2A_SECRET` चाहिए।                                                               |
| AWS Lambda                                                          | कुछ नहीं                                                            | Scheduled automations फायर नहीं होते।                                                                      |
| लोकल डेवलपमेंट                                                      | कुछ नहीं, जब तक आप opt in न करें                                    | नीचे दिया गया callout देखें।                                                                               |

Netlify, Vercel और Cloudflare पर वही टिक event-triggered automations की queue भी खाली करता है, उन runs को साफ़ करता है जिनका function बीच में कट गया था, और Mail के snooze और send-later जैसे ऐप sweeps भी चलाता है। बिना trigger वाले serverless deploy को इनमें से कुछ नहीं मिलता: event-triggered automations queue में इंतज़ार करते रहते हैं और बाधित runs अटके रहते हैं। Webhook-triggered automations और **Run now** अपने-आप dispatch होते हैं, इसलिए वे फिर भी काम करते हैं। जब कोई deploy schedules फायर नहीं कर सकता, तो **Automations** पेज यह बताता है और इसका कारण भी बताता है।

<Callout id="doc-block-j6yn07" tone="risk">

**गर्म instance schedules नहीं चलाता।** Serverless hosts कभी भी in-process timer शुरू नहीं करते, इसलिए keep-alive pings से जॉब फायर नहीं होते। केवल ऊपर की तालिका में दिया गया platform trigger ही उन्हें फायर करता है। AWS Lambda पर अभी कुछ भी उन्हें फायर नहीं करता, इसलिए scheduled automations को इसके बजाय किसी लंबे समय तक चलने वाले host (Fly, Render, कोई VPS) पर चलाएँ।

</Callout>

<Callout id="doc-block-rj2" tone="warning">

**लोकल dev में डिफ़ॉल्ट रूप से बंद।** जब `NODE_ENV` `development` या `test` हो, या ऐप URL `localhost` / `127.0.0.1` / `*.localhost` की ओर इशारा करता हो, तब शेड्यूलर का `setInterval` loop कभी शुरू नहीं होता — इसमें अधिकांश लोकल dev सेटअप आ जाते हैं। फिर भी लोकल रूप से शेड्यूलर चलाने के लिए `AGENT_NATIVE_ENABLE_LOCAL_RECURRING_JOBS=1` सेट करें। किसी भी host पर scheduled jobs बंद करने के लिए `AGENT_NATIVE_DISABLE_RECURRING_JOBS=1` का उपयोग करें, जिसका वर्णन आगे है।

</Callout>

<Callout id="doc-block-rj3" tone="warning">

**`AGENT_NATIVE_DISABLE_RECURRING_JOBS` दो scopes में पढ़ा जाता है।** Netlify, Vercel और Cloudflare पर **build** environment तय करता है: platform trigger event automations की queue खाली करने और runs साफ़ करने के लिए फायर होता रहता है, लेकिन switch चालू वाला build scheduled jobs को छोड़ देता है, चाहे deployed environment कुछ भी कहे। लंबे समय तक चलने वाले सर्वर पर **runtime** environment in-process timer को नियंत्रित करता है। इसे वहीं सेट करें जहाँ आपका host इसे पढ़ता है। Build अपना निर्णय रिकॉर्ड करता है, ताकि **Automations** पेज ऐसी next-run तारीख दिखाने के बजाय, जिसका कोई पालन नहीं होगा, यह बता सके कि schedules कभी नहीं चलेंगे।

</Callout>

## किसी कार्य को डिबग करना {#debugging}

- एजेंट संसाधन में `jobs/<name>.md` खोलें - फ्रंटमैटर `lastRun`, `lastStatus`, `lastError`, `nextRun` दिखाता है।
- **बिना प्रतीक्षा किए इसका परीक्षण करें:** **Automations** में ऑटोमेशन खोलें और **Run now** चुनें। यह ऑटोमेशन को उसके वास्तविक side effects के साथ तुरंत चलाता है और शेड्यूलर टिक का इंतज़ार नहीं करता, इसलिए यह लोकल रूप से और बिना trigger वाले hosts पर भी काम करता है।
- **इसे रोकें:** `enabled: false` को पलटें। फ़ाइल वहीं रुक जाती है, बस चलना बंद हो जाती है।

## एजेंट टूल {#agent-tool}

प्रत्येक टेम्पलेट में एक एकल `manage-jobs` टूल पंजीकृत है। `action` पैरामीटर ऑपरेशन का चयन करता है:

| कार्रवाई | पैरामीटर                                                                    | उद्देश्य                                                                    |
| -------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `create` | `name`, `schedule`, `instructions` (आवश्यक); `scope`, `runAs`, `mcpTools`   | नया आवर्ती कार्य बनाएँ                                                      |
| `list`   | `scope` (`personal`, `shared`, या सभी)                                      | सभी नौकरियों को स्थिति के साथ सूचीबद्ध करें (शेड्यूल, सक्षम, अंतिम/अगला रन) |
| `update` | `name` (आवश्यक); `schedule`, `instructions`, `enabled`, `runAs`, `mcpTools` | मौजूदा कार्य संपादित करें                                                   |
| `delete` | `name` (आवश्यक)                                                             | कोई कार्य हटाएं — हमेशा पहले उपयोगकर्ता से पुष्टि करें                      |

**व्यक्तिगत बनाम साझा दायरा।** प्रत्येक ऑटोमेशन व्यक्तिगत या संगठन दायरे में होता है और अपने निर्माता के रूप में चलता है। व्यवस्थापक साझा परिभाषाओं का प्रबंधन कर सकते हैं, लेकिन निर्माता की पहचान नहीं बदल सकते। हर संगठन रन से पहले फ्रेमवर्क जांचता है कि निर्माता मौजूद है और अभी भी सदस्य है।

## शेड्यूलिंग पैकेज से भिन्न {#vs-scheduling-package}

आवर्ती नौकरियों को `@agent-native/scheduling` के साथ भ्रमित न करें:

- **आवर्ती नौकरियां (यह पृष्ठ)** - क्रॉन-शेड्यूल _प्रॉम्प्ट_ एजेंट पृष्ठभूमि में चलता है। ढाँचा-स्तर। कार्यक्षेत्र में रहता है. शेड्यूलर वाले किसी भी host पर फायर होता है (देखें [शेड्यूलर कैसे चलता है](#how-scheduler-runs))।
- **`@agent-native/scheduling`** - कैलेंडर/बुकिंग सुविधाओं (इवेंट प्रकार, उपलब्धता विंडो, बुकिंग) के निर्माण के लिए एक पुन: प्रयोज्य डोमेन पैकेज। `calendar` टेम्पलेट और कस्टम शेड्यूलिंग सतहों को शक्ति प्रदान करता है।

आवर्ती कार्य हैं "मैं एजेंट को स्वयं कार्य करने के लिए कैसे बाध्य करूं?" शेड्यूलिंग पैकेज है "मैं एक कैलेंडर ऐप कैसे बनाऊं?" अलग-अलग चिंताएं.
