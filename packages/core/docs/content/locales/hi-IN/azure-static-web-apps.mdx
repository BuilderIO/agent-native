# Azure Static Web Apps

<Badge label="Beta" color="orange" icon="rocket" />

Azure Static Web Apps आपके लिए आपके ऐप को host करता है, इसलिए कोई server set up
करने या चालू रखने की ज़रूरत नहीं होती। यह ऐप की static files को सीधे serve करता
है और ऐप के server को managed Azure Functions के रूप में चलाता है, और ऐप को HTTPS
के साथ एक public address देता है।

यह guide शुरुआत से एक standalone ऐप deploy करने के चरण बताती है। आप ऐप बनाएंगे,
उसे production database और auth secret देंगे, database तैयार करेंगे, उसे Azure के
लिए build करेंगे, एक static web app बनाएंगे, और फिर Static Web Apps CLI से तैयार
build upload करेंगे।

<Callout tone="info">

Node.js `22.22+` आवश्यक है।

</Callout>

आपको एक Azure account भी चाहिए। इस guide के commands अपने computer पर चलाएं। आप
ऐप को Node.js से build करते हैं, और Static Web Apps CLI तैयार build को Azure पर
upload करता है।

## चरण 1: ऐप बनाएं {#step-1-create-the-app}

अपना नया standalone ऐप बनाएं। नीचे दिया गया उदाहरण Chat template से ऐप बनाता है,
लेकिन आप किसी भी template से शुरू कर सकते हैं। ऐप के folder में जाएं और उसकी
dependencies install करें। `corepack enable` वह `pnpm` version चालू करता है
जिसकी ऐप को ज़रूरत है, इसलिए आपको `pnpm` खुद install करने की ज़रूरत नहीं है।

```bash
npx --yes @agent-native/core@latest create my-app --standalone --template chat

cd my-app

corepack enable

pnpm install
```

चाहें तो `my-app` को अपने ऐप के नाम से बदल दें। इस guide का बाकी हिस्सा मानता है
कि आप ऐप के folder के अंदर हैं।

## चरण 2: Environment secrets configure करें {#step-2-configure-environment-secrets}

ऐप अपनी production settings environment variables से पढ़ता है:

| Variable             | आवश्यक | उद्देश्य                                                       |
| -------------------- | ------ | -------------------------------------------------------------- |
| `DATABASE_URL`       | हां    | ऐप को उसके PostgreSQL database से connect करता है              |
| `BETTER_AUTH_SECRET` | हां    | User sessions sign करता है                                     |
| `BETTER_AUTH_URL`    | नहीं   | वह public address सेट करता है जिससे लोग आपके ऐप तक पहुंचते हैं |

नीचे दिए गए exports से आगे के commands इस shell में काम करते हैं। Deploy करने
से पहले, यही variables अपने host की project या service environment settings में
save करें। चरण 5 बताता है कि उन्हें Azure में कैसे save करें।

### Database URL {#database-url}

Local development के दौरान, `DATABASE_URL` unset होने पर ऐप data को local
database में store करता है। Deployed ऐप को एक असली PostgreSQL database चाहिए जो
deploys के बीच अपना data बनाए रखे। Azure Functions requests के बीच files नहीं
रखते, इसलिए database को static web app के बाहर होना चाहिए। अपने provider से
connection string copy करें और उसे export करें:

```bash
export DATABASE_URL='your-postgres-url-string'
```

[Database provider guides](/docs/neon) बताती हैं कि हर provider के लिए connection
string कहां मिलती है, जिसमें
[Azure Database for PostgreSQL](/docs/azure-postgresql) भी शामिल है।

<Callout tone="warning">

एक persistent PostgreSQL provider चुनें: Neon, Supabase, Amazon RDS, आदि।

</Callout>

### Auth secret {#auth-secret}

इसे एक बार generate करें और सभी deploys में इसे एक जैसा रखें।

ऐप user sessions sign करने के लिए `BETTER_AUTH_SECRET` का उपयोग करता है। अगर यह
बदलता है, तो हर signed-in user sign out हो जाता है। नीचे दिया गया command एक
random value generate करता है:

```bash
export BETTER_AUTH_SECRET="$(openssl rand -hex 32)"
```

Generate की गई value को किसी सुरक्षित जगह save करें, जैसे password manager में।
हर बार deploy करते समय यही value इस्तेमाल करें।

### Public URL {#public-url}

वैकल्पिक। इसे तब सेट करें जब आप custom domain, reverse proxy, या ऐसा auth/OAuth
flow इस्तेमाल करें जिसे fixed public origin चाहिए।

`BETTER_AUTH_URL` वह public address है जिससे लोग आपके ऐप तक पहुंचते हैं। इसके
बिना, ऐप हर incoming request से अपना address पता करता है। Azure के दिए गए address
पर आमतौर पर यह ठीक रहता है, लेकिन custom domain connect करते समय इसे सेट करें,
ताकि sign-in links और OAuth redirects उसी domain का इस्तेमाल करें।

```bash
export BETTER_AUTH_URL='https://your-domain.example'
```

## चरण 3: Migrate करें {#step-3-migrate}

Migrations आपके database में वे tables बनाती और update करती हैं जिनकी ऐप को
ज़रूरत है। पहले deploy से पहले इसे चलाएं:

```bash
pnpm migrate:production
```

यह command आपके computer पर चलता है और चरण 2 में export किए गए `DATABASE_URL` से
production database से connect करता है। ऐप upgrade करने के बाद, नया version
deploy करने से पहले इसे फिर से चलाएं।

## चरण 4: Build करें {#step-4-build}

### ऐप build करें {#build-the-app}

ऐप को Azure Static Web Apps के लिए build करें:

```bash
NITRO_PRESET=azure-swa pnpm build
```

`NITRO_PRESET=azure-swa` ऐप को उस format में build करता है जिसकी Azure Static Web
Apps को ज़रूरत है। Build, static files को `.output/public` में और server functions
को `.output/server` में लिखता है। यह ऐप के folder में एक `staticwebapp.config.json`
file भी लिखता है, जो Azure को बताती है कि requests को कैसे route करना है और server
किस Node.js version पर चलेगा।

### API runtime सेट करें {#set-the-api-runtime}

Azure ऐप के server को उस Node.js version पर चलाता है जो
`staticwebapp.config.json` में दिया गया है। Build यह version `package.json` के
`engines` field से चुनता है, लेकिन सिर्फ़ तब जब field ठीक `20` या `22` हो। नए ऐप
को `>=22.22.0` चाहिए, इसलिए build इसके बजाय Node.js 18 लिखता है, जो ऐप के लिए बहुत
पुराना है और जिसे Azure अब support नहीं करता।

हर build के बाद, version को Node.js 22 पर सेट करें:

```bash
node -e "const fs = require('node:fs'); const file = 'staticwebapp.config.json'; const config = JSON.parse(fs.readFileSync(file, 'utf8')); config.platform = { ...config.platform, apiRuntime: 'node:22' }; fs.writeFileSync(file, JSON.stringify(config, null, 2));"
```

यह command सिर्फ़ `apiRuntime` setting बदलता है और build की लिखी file का बाकी
हिस्सा वैसा ही रखता है। Build हर बार file को फिर से लिखता है, इसलिए deploy करने से
पहले, हर build के बाद यह command चलाएं।

## चरण 5: Static web app बनाएं और secrets save करें {#step-5-create-the-static-web-app-and-save-the-secrets}

Azure portal में, एक नया **Static Web App** बनाएं। Subscription, resource group,
नाम, और plan चुनें। **Deployment details** में **Other** चुनें, क्योंकि आप GitHub
repository connect करने के बजाय build खुद upload करते हैं।

ऐप के **Overview** page पर **Manage deployment token** से deployment token copy
करें, और उसे export करें:

```bash
export SWA_CLI_DEPLOYMENT_TOKEN='your-deployment-token'
```

Static Web Apps CLI चरण 6 में यह variable पढ़ता है। Token को private रखें, क्योंकि
जिसके पास भी यह है वह आपके ऐप पर deploy कर सकता है।

फिर दोनों आवश्यक variables save करें। Azure portal में static web app खोलें,
**Settings** > **Environment variables** पर जाएं, **Production** environment
चुनें, और चरण 2 में export की गई values के साथ `DATABASE_URL` और
`BETTER_AUTH_SECRET` जोड़ें। अगर आपने `BETTER_AUTH_URL` सेट किया है, तो उसे भी इसी
तरह जोड़ें। Azure ये values ऐप के server functions को environment variables के रूप
में देता है।

## चरण 6: Deploy करें {#step-6-deploy}

<Steps>

### Build upload करें

ऐप के folder से, static files और server functions को production पर upload करें:

```bash
npx @azure/static-web-apps-cli deploy .output/public --api-location .output/server --swa-config-location . --env production
```

`.output/public` में static files होती हैं, और `--api-location .output/server`
server functions की ओर point करता है। `--swa-config-location .` ऐप के folder की ओर
point करता है, जहां build ने `staticwebapp.config.json` लिखी थी। इसके बिना, Azure
को चरण 4 का API runtime नहीं दिखता। `--env production` preview environment के
बजाय आपके production address पर publish करता है।

### ऐप खोलें

Command पूरा होने पर यह ऐप का address print करता है, जो `azurestaticapps.net` पर
खत्म होता है। उसे खोलें और पहला account बनाएं।

</Steps>

## Updates deploy करें {#deploy-updates}

नया version ship करने के लिए, migrations चलाएं, फिर से build करें, और upload करें:

```bash
pnpm migrate:production

NITRO_PRESET=azure-swa pnpm build

node -e "const fs = require('node:fs'); const file = 'staticwebapp.config.json'; const config = JSON.parse(fs.readFileSync(file, 'utf8')); config.platform = { ...config.platform, apiRuntime: 'node:22' }; fs.writeFileSync(file, JSON.stringify(config, null, 2));"

npx @azure/static-web-apps-cli deploy .output/public --api-location .output/server --swa-config-location . --env production
```

नए shell में `SWA_CLI_DEPLOYMENT_TOKEN` फिर से export करें। Save किए गए environment
variables static web app पर बने रहते हैं, इसलिए आपको चरण 5 दोहराने की ज़रूरत नहीं
है।

## Request limits {#request-limits}

Azure Static Web Apps ऐप के server पर आने वाली किसी भी request को 45 seconds के बाद
खत्म कर देता है, और यह WebSockets support नहीं करता। Agent-Native पहले से ही chat
turn को लगभग 40 seconds के बाद खत्म करता है और उसे browser से जारी रखता है, इसलिए
लंबे agent turns फिर भी पूरे होते हैं, लेकिन वे एक के बजाय कई चरणों में चलते हैं।
अगर आपके ऐप को लंबी requests चाहिए, तो ऐसा host इस्तेमाल करें जिसमें यह limit न हो,
जैसे [Node.js](/docs/node-js) या [Docker](/docs/docker)।
