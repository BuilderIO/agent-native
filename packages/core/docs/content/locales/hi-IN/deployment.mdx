# तैनाती

एजेंट-नेटिव ऐप्स हुड के तहत [Nitro](https://nitro.build) का उपयोग करते हैं, जिसका अर्थ है कि आप शून्य कॉन्फ़िगरेशन परिवर्तनों के साथ किसी भी प्लेटफ़ॉर्म पर तैनात कर सकते हैं - बस एक प्रीसेट सेट करें।

## तेज़ रास्ता: Chat ऐप को स्थानीय रूप से self-host करें {#self-host-quickstart}

शुरू करने के दो अच्छे तरीके हैं:

- **ऐप बना रहे हैं?** [Getting Started](/docs/getting-started) से शुरू करें और ऐप को स्थायी जगह पर रखने के समय यहां लौटें।
- **ऐप चला रहे हैं?** पहले स्थानीय Docker रास्ता आज़माएं। इससे छोटे सर्वर पर उपयोग होने वाला Node.js, Postgres, authentication और environment variables का वही आकार जांचा जाता है।

स्थानीय stack जानबूझकर उदाहरण authentication secret और स्थानीय Postgres volume का उपयोग करता है। यह `localhost` के लिए है, इंटरनेट पर प्रकाशित करने के लिए नहीं। पूरी Compose फ़ाइल और copy करने योग्य steps के लिए [English quickstart](https://www.agent-native.com/docs/deployment#self-host-quickstart) देखें। यह quickstart PostgreSQL 18 के volume layout का उपयोग करता है। PostgreSQL 17 या उससे पुराने संस्करण से बनाए गए volume को दोबारा उपयोग न करें। image या mount path बदलने से पहले मौजूदा डेटा का backup लेकर migration करें।

### 1. ऐप बनाएं

```bash
npx @agent-native/core@latest create my-app --standalone --template chat
cd my-app
pnpm install
```

### 2. स्थानीय stack चलाएं

```bash
docker compose up --build
```

[http://localhost:3000](http://localhost:3000) खोलें। Embedded agent का उपयोग करने के लिए स्थानीय `.env` फ़ाइल में `ANTHROPIC_API_KEY` जोड़ें।

## तैनाती करने से पहले: एक स्थायी डेटाबेस चुनें {#persistent-database}

प्रत्येक तैनात ऐप को एक सतत SQL डेटाबेस की आवश्यकता होती है। स्थानीय विकास में, एजेंट-नेटिव `data/app.db` पर SQLite फ़ाइल पर वापस आ जाता है; यह आपकी मशीन पर सुविधाजनक है, लेकिन यह कंटेनर, पूर्वावलोकन, या सर्वर रहित वातावरण में टिकाऊ नहीं है जहां फ़ाइल सिस्टम को रीसेट किया जा सकता है।

किसी ऐप को उत्पादन के लिए प्रचारित करने से पहले अपने परिनियोजन प्रदाता में `DATABASE_URL` सेट करें। एजेंट-नेटिव स्कीमा और प्रश्नों के लिए Drizzle का उपयोग करता है, इसलिए डेटा परत Drizzle-संगत SQL बैकएंड में पोर्टेबल है और फ्रेमवर्क URL से बोली का स्वतः पता लगाता है। एडॉप्टर सूची और बोली विवरण के लिए [Database](/docs/database#production) देखें।

`DATABASE_AUTH_TOKEN` का उपयोग केवल तभी करें जब आपके डेटाबेस प्रदाता को एक अलग टोकन की आवश्यकता हो, जैसे Turso/libSQL। कार्यस्थानों के लिए, सभी ऐप्स को डिफ़ॉल्ट रूप से रूट `DATABASE_URL` प्राप्त होता है; जब एक ऐप को अलग डेटाबेस का उपयोग करना चाहिए तो `<APP_NAME>_DATABASE_URL` सेट करें।

## कार्यस्थान परिनियोजन: एक उत्पत्ति, अनेक ऐप्स {#workspace-deploy}

यदि आपका प्रोजेक्ट [workspace](/docs/multi-app-workspace) है, तो आप इसमें प्रत्येक ऐप को एक कमांड के साथ एक ही मूल में भेज सकते हैं:

```bash
npx @agent-native/core@latest deploy
# https://your-agents.com/mail/*       → apps/mail
# https://your-agents.com/calendar/*   → apps/calendar
# https://your-agents.com/forms/*      → apps/forms
```

प्रत्येक ऐप को `APP_BASE_PATH=/<name>` और `VITE_APP_BASE_PATH=/<name>` के साथ बनाया गया है, फिर लक्ष्य Nitro प्रीसेट के लिए पैक किया गया है। क्लाउडफ्लेयर पेज डिफ़ॉल्ट प्रीसेट है और `dist/_worker.js` पर जेनरेटेड डिस्पैचर वर्कर का उपयोग करता है; Netlify `.netlify/functions-internal/<app>-server` प्लस जेनरेटेड रीडायरेक्ट में प्रति ऐप एक फ़ंक्शन का उपयोग करता है; वर्सेल बिल्ड आउटपुट API का उपयोग करके एक कार्यक्षेत्र-स्तर `.vercel/output` लिखता है।

समान-मूल परिनियोजन आपको निःशुल्क दो बड़ी जीत प्रदान करता है:

- **साझा लॉगिन सत्र** - किसी भी ऐप में लॉग इन करें, हर ऐप लॉग इन है।
- **ज़ीरो-कॉन्फिग क्रॉस-ऐप A2A** — मेल से `@calendar` को टैग करना एक समान-मूल फ़ेच है; कोई CORS नहीं, कोई JWT भाई-बहनों के बीच हस्ताक्षर नहीं।

आउटपुट को इसके साथ प्रकाशित करें:

```bash
wrangler pages deploy dist
```

Netlify एकीकृत परिनियोजन के लिए, Netlify प्रीसेट का उपयोग करें:

```bash
npx @agent-native/core@latest deploy --preset netlify
```

वर्सेल एकीकृत परिनियोजन के लिए, वर्सेल प्रीसेट का उपयोग करें:

```bash
npx @agent-native/core@latest deploy --preset vercel
```

प्रदाता बिल्ड कमांड को कॉन्फ़िगर करते समय, `--build-only` के साथ उसी कमांड का उपयोग करें। वर्सेल को `npx @agent-native/core@latest deploy --preset vercel --build-only` चलाना चाहिए; कमांड सीधे `.vercel/output` लिखता है, इसलिए कार्यक्षेत्र रूटिंग के लिए कोई `vercel.json` आवश्यक नहीं है।

होस्ट किए गए कार्यस्थान निर्माण के लिए परिनियोजन प्रदाता परिवेश में `A2A_SECRET` की आवश्यकता होती है।
इससे Slack, इनबाउंड webhooks और क्रॉस-ऐप A2A हस्ताक्षरित होकर काम फिर से शुरू कर देते हैं
बैकग्राउंड प्रोसेसर। स्थानीय `--build-only` आर्टिफैक्ट जांच अभी भी इसके बिना चलती है।

प्रति-ऐप स्वतंत्र तैनाती अभी भी समर्थित है - बस एक स्टैंडअलोन मचान की तरह `cd apps/<name> && npx @agent-native/core@latest build`।

## प्रीसेट सेट करना {#setting-the-preset}

डिफ़ॉल्ट रूप से, Nitro Node.js के लिए बनता है। किसी भिन्न प्लेटफ़ॉर्म को लक्षित करने के लिए, अपने `vite.config.ts` में प्रीसेट सेट करें:

```ts
import { agentNative } from "@agent-native/core/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [agentNative({ nitro: { preset: "vercel" } })],
});
```

या निर्माण समय पर `NITRO_PRESET` पर्यावरण चर का उपयोग करें:

```bash
NITRO_PRESET=netlify npx @agent-native/core@latest build
```

## Node.js (डिफ़ॉल्ट) {#nodejs}

डिफ़ॉल्ट प्रीसेट. बनाएं और चलाएं:

```bash
npx @agent-native/core@latest build
node .output/server/index.mjs
```

श्रवण पोर्ट को कॉन्फ़िगर करने के लिए `PORT` सेट करें (डिफ़ॉल्ट: `3000`)।

उत्पादन परिनियोजन के लिए वर्तमान Node.js LTS लाइन का उपयोग करें। मई 2026 तक, वह
Node.js 24 है; Node.js 20 का जीवन 30 अप्रैल, 2026 को समाप्त हो गया और अब नहीं
अपस्ट्रीम सुरक्षा अद्यतन प्राप्त करता है।

### डॉकर {#docker}

```dockerfile
FROM node:24-slim AS build
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile
COPY . .
RUN pnpm build

FROM node:24-slim
WORKDIR /app
COPY --from=build /app/.output .output
# data/ एक रनटाइम-निर्मित SQLite निर्देशिका है - किसी डेव DB को उत्पाद में कॉपी न करें।
# उत्पादन के लिए, DATABASE_URL को होस्ट किए गए Postgres या Turso इंस्टेंस पर सेट करें।
RUN mkdir -p /app/data
ENV NODE_ENV=production
ENV PORT=3000
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

## वर्सेल {#vercel}

```ts
// vite.config.ts
export default defineConfig({
  plugins: [agentNative({ nitro: { preset: "vercel" } })],
});
```

Vercel CLI या git पुश के माध्यम से परिनियोजन करें:

```bash
vercel deploy
```

कार्यक्षेत्र के लिए, प्रत्येक ऐप को एक वर्सेल बिल्ड आउटपुट API बंडल में बनाएं:

```bash
npx @agent-native/core@latest deploy --preset vercel
```

वर्सेल गिट परिनियोजन के लिए, बिल्ड कमांड को यहां सेट करें:

```bash
npx @agent-native/core@latest deploy --preset vercel --build-only
```

वर्कस्पेस बिल्ड प्रत्येक ऐप के Nitro `vercel` आउटपुट को रूट `.vercel/output` में कॉपी करता है, प्रत्येक फ़ंक्शन को अपना माउंट-पाथ वातावरण देता है, और रूट कॉन्फिगरेशन लिखता है जो `/<app-id>` पर ऐप्स को सर्व करता है।

## नेटलिफाई {#netlify}

Nitro `netlify` प्रीसेट अच्छी तरह से काम करता है और, व्यवहार में, हमें बाहरी Postgres (नियॉन) से बात करने वाले टेम्पलेट्स के लिए क्लाउडफ्लेयर पेज (~ 200ms TTFB बनाम ~ 9s) की तुलना में बहुत तेज शुरुआत दी है। या तो प्रीसेट को `vite.config.ts`:

```ts
// vite.config.ts
export default defineConfig({
  plugins: [agentNative({ nitro: { preset: "netlify" } })],
});
```

…या निर्माण समय पर `NITRO_PRESET=netlify` सेट करें।

कार्यस्थान के लिए, प्रत्येक ऐप को एक Netlify साइट से चलाकर तैनात करें:

```bash
npx @agent-native/core@latest deploy --preset netlify
```

वर्कस्पेस बिल्ड `dist/_workspace_static/` के तहत स्टैटिक एसेट लिखता है और प्रत्येक ऐप को बिना किसी एसेट रीडायरेक्ट के अपने स्वयं के नेटलाइज़ फ़ंक्शन पर रूट करता है, इसलिए सर्वर फ़ंक्शन ऐप रूट को संभालने से पहले `/mail/assets/...` जैसी फ़ाइलों को स्टेटिक रूप से परोसा जाता है।

### Keep-warm और स्केल-टू-ज़ीरो डेटाबेस {#netlify-keep-warm}

सक्षम होने पर, Netlify बिल्ड एक शेड्यूल्ड फ़ंक्शन बनाता है जो **हर मिनट** `/_agent-native/health` को अनुरोध भेजता है। इससे सर्वर फ़ंक्शन और उसका डेटाबेस गर्म रहता है, ताकि निष्क्रिय अवधि के बाद अगला विज़िटर कोल्ड स्टार्ट (Neon पर 1–5 सेकंड) न चुकाए।

Keep-warm **डिफ़ॉल्ट रूप से अक्षम** है, क्योंकि हर मिनट जगाने से मीटर्ड स्केल-टू-ज़ीरो डेटाबेस में ऑटोसस्पेंड रुक जाता है। जब अगले विज़िटर की कम विलंबता सक्रिय डेटाबेस समय के लायक हो, तब `AGENT_NATIVE_ENABLE_KEEP_WARM=1` सेट करें।

| `AGENT_NATIVE_ENABLE_KEEP_WARM`             | सर्वर और डेटाबेस की शेड्यूल्ड वॉर्मिंग सक्षम करता है। डिफ़ॉल्ट रूप से सेट नहीं है।             |
| `AGENT_NATIVE_DISABLE_KEEP_WARM`            | संगतता के लिए डिसेबल स्विच; सेट होने पर यह ऑप्ट-इन फ्लैग पर प्राथमिकता रखता है।                |
| `AGENT_NATIVE_KEEP_WARM_SCHEDULE`           | सक्षम होने पर कैडेंस बदलता है; डिफ़ॉल्ट `* * * * *` है और अपठनीय मान बिल्ड को विफल करता है।    |
| `AGENT_NATIVE_DISABLE_KEEP_WARM_BACKGROUND` | keep-warm सक्षम होने पर केवल बैकग्राउंड फ़ंक्शन की वॉर्मिंग हटाता है और सर्वर को गर्म रखता है। |

यदि आप फ़्री या कोटा-सीमित डेटाबेस टियर पर हैं, तो `AGENT_NATIVE_ENABLE_KEEP_WARM` सेट न करें। यदि इसे सक्षम करते हैं, तो धीमी कैडेंस चुनें या `AGENT_NATIVE_DISABLE_KEEP_WARM_BACKGROUND=1` सेट करें।

### ऑन-डिमांड स्कीमा DDL {#skip-ensure-tables}

प्रत्येक store अपने पहले डेटाबेस संपर्क पर `ensureTable()` कॉल करता है, जो `information_schema` / `pg_indexes` की जाँच करता है और केवल वास्तव में अनुपस्थित वस्तुओं के लिए `CREATE TABLE` / `ADD COLUMN` / `CREATE INDEX` चलाता है। लंबे समय चलने वाले Node सर्वर पर यह लागत प्रति बूट एक बार लगती है और अदृश्य रहती है। सर्वरलेस पर «पहला संपर्क» **हर कोल्ड स्टार्ट** पर होता है, लगभग 57 stores में — इसलिए एक कोल्ड अनुरोध वास्तविक काम शुरू करने से पहले कुछ सौ क्रमिक राउंड ट्रिप चुका सकता है।

इसे दो चीज़ें कम करती हैं:

- जाँचें प्रत्येक तालिका, कॉलम और इंडेक्स के लिए एक-एक क्वेरी के बजाय **प्रति डेटाबेस एक बैच इंट्रोस्पेक्शन पास** (दो क्वेरी) से उत्तरित होती हैं। यह स्वतः होता है और किसी कॉन्फ़िगरेशन की आवश्यकता नहीं।
- `AGENT_NATIVE_SKIP_ENSURE_TABLES=1` जाँच-और-DDL तंत्र को पूरी तरह छोड़ देता है, जो उपलब्ध सबसे बड़ा कोल्ड-स्टार्ट लेटेंसी लाभ है।

`AGENT_NATIVE_SKIP_ENSURE_TABLES=1` सेट करें जब आपका डेटाबेस स्कीमा पहले से माइग्रेट हो और आप नहीं चाहते कि एप्लिकेशन बूट तालिकाएँ बनाए या बदले — वास्तविक माइग्रेशन चरण वाले प्रोडक्शन परिनियोजन का सामान्य मामला।

<Callout tone="risk">

**यह फ़्लैग fail-closed नहीं होता, और हो भी नहीं सकता।** यदि स्कीमा वास्तव में अनुपस्थित है, तो पहली वास्तविक क्वेरी मौके पर ठीक होने के बजाय ज़ोर से विफल होती है — यही उद्देश्य है, लेकिन इसका अर्थ है कि माइग्रेशन की ज़िम्मेदारी आपकी है। ऐसे परिनियोजन पर इसे सेट न करें जो तालिकाएँ बनाने के लिए एप्लिकेशन बूट पर निर्भर है।

</Callout>

## SSR कैशिंग {#ssr-caching}

हर SSR HTML रिस्पॉन्स और हर React Router `.data` रिस्पॉन्स एक ही गैर-व्यक्तिगत, सार्वजनिक शेल है: `createH3SSRHandler` रेंडर करने से पहले कुकीज़ हटा देता है, इसलिए वही बाइट्स हर विज़िटर के लिए सही होते हैं और सारा पर्सनलाइज़ेशन लोड होने के बाद क्लाइंट पर होता है। यही कारण है कि इन रिस्पॉन्स पर डिफ़ॉल्ट रूप से एक ही हार्ड-कैश पॉलिसी लगाना सुरक्षित है:

```txt
cache-control: public, max-age=600, stale-while-revalidate=604800, stale-if-error=3600
```

यही मान `cdn-cache-control` और `netlify-cdn-cache-control` पर भी दोहराया जाता है। इसके बाद एक साझा CDN एंट्री हर अनुरोध के लिए अलग रेंडर करने के बजाय पूरी साइट को सर्व करती है, जो पहले-रिस्पॉन्स लेटेंसी पर सबसे बड़ा एकल लीवर है — इसे चालू रखें, जब तक कि नीचे दिए गए मामलों में से कोई आपके परिनियोजन पर लागू न हो।

### `AGENT_NATIVE_SSR_CACHE` के साथ ओवरराइड करना {#ssr-cache-env}

पूरी परिनियोजन के लिए पॉलिसी बदलने के लिए डिप्लॉय एनवायरनमेंट में `AGENT_NATIVE_SSR_CACHE` सेट करें:

| मान                                                 | परिणाम                                                                              |
| --------------------------------------------------- | ----------------------------------------------------------------------------------- |
| अनसेट, `on`, `default`, `true`, `1`                 | ऊपर दी गई डिफ़ॉल्ट पॉलिसी, अपरिवर्तित। अनुशंसित — सर्वश्रेष्ठ प्रदर्शन।             |
| `off`, `false`, `0`, `none`, `no-store`, `disabled` | `cache-control`, `cdn-cache-control`, और `netlify-cdn-cache-control` पर `no-store`। |
| एक अवधि: `30`, `30s`, `5m`, `2h`                    | `public, max-age=<n>, stale-while-revalidate=<n>, stale-if-error=3600`।             |

साधारण नंबर सेकंड होते हैं। `stale-while-revalidate` जानबूझकर कस्टम अवधि के लिए `max-age` को दोहराता है: एक छोटी ताज़गी विंडो को डिफ़ॉल्ट सात-दिन की स्टेल विंडो के साथ जोड़ने पर ठीक वही बासीपन वापस मिल जाएगा जिससे आप बचना चाहते थे। कोई अपरिचित मान चेतावनी लॉग करता है और डिफ़ॉल्ट पर वापस आ जाता है, इसलिए कोई टाइपो कभी भी चुपचाप CDN को अक्षम नहीं कर सकता।

इसे कम करें या बंद करें जब इनमें से कोई एक सच हो:

1. **आपका होस्ट डिप्लॉय पर अपने CDN को पर्ज नहीं करता।** Netlify और Vercel करते हैं; कुछ सेल्फ-मैनेज्ड सेटअप नहीं करते। पर्ज के बिना, एक शिप किया गया बिल्ड `max-age` प्लस `stale-while-revalidate` तक पिछला शेल सर्व करता रह सकता है।
2. **आपके लोडर्स परिवर्तनशील सार्वजनिक डेटा लौटाते हैं।** एक सफल म्यूटेशन के बाद, `useRevalidator()` या एक्शन-के-बाद रीडायरेक्ट री-फ़ेच ताज़ा लोडर आउटपुट के बजाय ब्राउज़र की कैश की गई `.data` कॉपी पढ़ सकता है।

यह सेटिंग हर सार्वजनिक-शेल सतह पर लागू होती है: React Router SSR HTML और `.data`, लॉगिन HTML शेल, `/_agent-native/speculation-rules.json` रूट, डॉक्स साइट, और forms टेम्पलेट में सार्वजनिक-फॉर्म SSR। जनरेट किया गया Cloudflare Worker इसे बिल्ड टाइम पर रिज़ॉल्व करता है, इसलिए बिल्ड चलने से पहले इसे डिप्लॉय एनवायरनमेंट में सेट करें।

ध्यान रखने योग्य तीन बातें:

- **कैशिंग बंद करने से SSR पर्सनलाइज़्ड नहीं हो जाता।** रेंडर से पहले कुकीज़ अब भी हटाई जाती हैं और SSR लोडर्स अब भी अनाम ब्रांच देखते हैं। प्रति-उपयोगकर्ता डेटा को अब भी क्लाइंट-साइड पर रिज़ॉल्व करना होगा। यह वेरिएबल केवल कैश की _अवधि_ नियंत्रित करता है।
- **यह डिज़ाइन के अनुसार पूरे परिनियोजन पर लागू होता है, प्रति-रूट नहीं।** प्रति-रूट या प्रति-अनुरोध कैश ओवरराइड ही वह तरीका है जिससे एक विज़िटर का पेलोड किसी दूसरे विज़िटर की साझा CDN एंट्री में पहुँच जाता है, इसलिए फ्रेमवर्क ऐसा कोई विकल्प नहीं देता — `guard:ssr-cache-shell` इसे लागू करता है।
- **म्यूटेशन के बाद ताज़ा डेटा के लिए, कैश अक्षम करने के बजाय actions को प्राथमिकता दें।** ऐप डेटा [actions](/docs/actions-overview) में रहता है, जिसे क्लाइंट से `useActionQuery` / `useActionMutation` से पढ़ा जाता है और `useDbSync()` पोलिंग द्वारा लाइव रखा जाता है; इनमें से कुछ भी SSR शेल कैश से होकर नहीं गुजरता। SSR लोडर्स को सार्वजनिक शेल रेंडर करते रहने दें, और इस वेरिएबल का इस्तेमाल तभी करें जब आपको सचमुच लोडर डेटा को अधिक ताज़ा चाहिए हो।

डेटाबेस कनेक्शन वेरिएबल (`DATABASE_URL`, `DATABASE_AUTH_TOKEN`, प्रति-ऐप `<APP_NAME>_DATABASE_URL`) [Database](/docs/database#production) में रहते हैं।

### उत्पादन-संवेदनशील कॉन्फ़िगरेशन {#env-required-prod}

ये सेटिंग्स उत्पादन-संवेदनशील व्यवहार को नियंत्रित करती हैं। फ़्रेमवर्क प्रमाणीकरण वाली स्वतंत्र ऐप को स्थिर `BETTER_AUTH_SECRET` और स्थायी डेटाबेस चाहिए; इसके न होने पर फ़्रेमवर्क अनुरोध, टेम्पलेट या होस्टिंग संदर्भ से सार्वजनिक auth URL का अनुमान लगाता है। Workspace और A2A सेटिंग्स उपयोग की गई सुविधाओं पर निर्भर हैं। गुम मान या तो सुरक्षित रूप से विफल होते हैं या तेज़ चेतावनी के साथ कमजोर व्यवहार पर लौटते हैं।

| वेरिएबल                                     | विवरण                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BETTER_AUTH_SECRET`                        | 32+ वर्ण की random string। Session cookies sign करती है और `OAUTH_STATE_SECRET` तथा app-local encrypted values की fallback है। Existing shared-vault ciphertext के लिए legacy read candidate भी है। Production में अनिवार्य है।                                                                                   |
| `BETTER_AUTH_URL`                           | इस ऐप के सार्वजनिक मूल का वैकल्पिक override (उदा. `https://mail.example.com`)। न होने पर अनुरोध, टेम्पलेट और होस्टिंग संदर्भ से इसका अनुमान लगाया जाता है।                                                                                                                                                        |
| `ANTHROPIC_API_KEY`                         | एम्बेडेड उत्पादन एजेंट के लिए API कुंजी। **बहु-किरायेदार तैनाती में**, जब उपयोगकर्ता के पास प्रति-उपयोगकर्ता कुंजी नहीं होती है तो फ्रेमवर्क इस पर वापस आने से इंकार कर देता है - अपनी खुद की कुंजी लाने की आवश्यकता होती है। एकल-किरायेदार स्व-होस्ट किए गए इंस्टॉल इसे वैश्विक कुंजी के रूप में उपयोग करते हैं। |
| `OAUTH_STATE_SECRET`                        | OAuth राज्य लिफाफे के लिए समर्पित HMAC कुंजी (Google, एटलसियन, ज़ूम)। अनसेट होने पर वापस `BETTER_AUTH_SECRET` पर आ जाता है, लेकिन एक समर्पित मान की अनुशंसा की जाती है ताकि एक को घुमाने से दूसरा अमान्य न हो। `openssl rand -hex 32` के माध्यम से उत्पन्न करें।                                                  |
| `A2A_SECRET`                                | Inter-app A2A JSON-RPC के लिए shared HMAC। Dedicated workspace key न होने पर shared vault इस value से purpose-derived key उपयोग करता है, इसलिए इसे rotate करने से vault key भी rotate होती है।                                                                                                                    |
| `WORKSPACE_SECRETS_ENCRYPTION_KEY`          | Shared workspace vault के लिए preferred stable AES-256-GCM key। इसे पढ़ने वाले हर app में समान value रखें; यह app-local OAuth encryption से अलग है।                                                                                                                                                               |
| `WORKSPACE_SECRETS_ENCRYPTION_KEY_PREVIOUS` | Rotation window में optional previous workspace key। इसे नई key के साथ deploy करें, reads से rows migrate होने दें, फिर हटाएँ।                                                                                                                                                                                    |
| `SECRETS_ENCRYPTION_KEY`                    | App-local encryption और vault के लिए legacy combined key। यह समर्थित है, लेकिन नए multi-app deploys में dedicated workspace key उपयोग करें।                                                                                                                                                                       |

### प्रामाणिक एवं पहचान {#env-auth}

OAuth प्रदाता क्रेडेंशियल (Google, GitHub), स्थिर MCP बियरर फ़ॉलबैक (`ACCESS_TOKEN` / `ACCESS_TOKENS`), और ईमेल-सत्यापन टॉगल [Authentication](/docs/authentication) में प्रलेखित हैं। उन्हें आपके द्वारा चुने गए प्रमाणीकरण मोड के अनुसार वहां सेट करें।

### इनबाउंड Webhooks {#env-webhooks}

प्रत्येक मैसेजिंग एकीकरण के लिए उत्पादन में अपने स्वयं के हस्ताक्षर रहस्य की आवश्यकता होती है (रहस्य गायब होने पर जाली अनुरोधों पर हैंडलर विफल हो जाते हैं)। प्रति-एकीकरण चर [Messaging](/docs/messaging) और [Security](/docs/security) में सूचीबद्ध हैं। केवल स्थानीय विकास के लिए, `AGENT_NATIVE_ALLOW_UNVERIFIED_WEBHOOKS=1` "चेतावनी दें और स्वीकार करें" का विकल्प चुनता है - इसे कभी भी उत्पाद में सेट न करें।

### सुरक्षा कॉन्फ़िगरेशन (ऑप्ट-इन) {#security-config}

डिफ़ॉल्ट सख्त हैं। मुट्ठी भर ऑप्ट-इन फ़्लैग व्यवहार को शिथिल करते हैं (डीबग स्टैक ट्रेस, असत्यापित webhooks, वर्कस्पेस-स्कोप्ड कुंजी फ़ॉलबैक, MCP हब मल्टी-ऑर्ग स्विच, रनटाइम एनवी-वर राइट्स)। उन्हें [Security](/docs/security) में उनके सुरक्षा ट्रेड-ऑफ़ के साथ प्रलेखित किया गया है। जब तक आप विशेष रूप से आरामदायक मार्ग नहीं चाहते, उन्हें सेट न करें।

### कार्यस्थान .env वंशानुक्रम {#env-inheritance}

कार्यस्थान के अंदर, रूट `.env` स्वचालित रूप से प्रत्येक ऐप में लोड हो जाता है, इसलिए `ANTHROPIC_API_KEY`, `A2A_SECRET`, `BETTER_AUTH_SECRET`, और `OAUTH_STATE_SECRET` जैसी साझा कुंजियों को केवल एक बार सेट करने की आवश्यकता होती है। प्रति-ऐप `apps/<name>/.env` संघर्ष पर जीतता है।

### मजबूत रहस्य उत्पन्न करना {#env-generate-secrets}

"32+ चार यादृच्छिक" (`BETTER_AUTH_SECRET`, `OAUTH_STATE_SECRET`, `A2A_SECRET`, `WORKSPACE_SECRETS_ENCRYPTION_KEY`, `SECRETS_ENCRYPTION_KEY`, `AGENT_NATIVE_BUILDER_RELAY_SECRET`) चिह्नित किसी भी रहस्य के लिए, इसके साथ नए मान उत्पन्न करें:

```bash
openssl rand -hex 32
```

प्रत्येक उदाहरण पर env var को प्रतिस्थापित करके और पुनः तैनात करके उन्हें घुमाएं - पुरानी कुंजी के तहत हस्ताक्षरित सत्र / OAuth राज्य लिफाफे अमान्य हो जाते हैं, इसलिए उपयोगकर्ताओं को फिर से साइन इन करने की आवश्यकता हो सकती है।

## उत्पादन एजेंट उपकरण {#production-agent-tools}

प्रोडक्शन एजेंटों को ऐप के पंजीकृत actions प्लस फ्रेमवर्क टूल मिलते हैं
एजेंट चैट प्लगइन. SQL निरीक्षण डिफ़ॉल्ट रूप से सक्षम है; डेटाबेस writes
typed app actions से गुजरते हैं, जब तक ऐप स्पष्ट रूप से raw write tools सक्षम न करे:

```ts
// server/plugins/agent-chat.ts
export default createAgentChatPlugin({
  frameworkTools: {
    database: "read", // "write" | "read" | "off" — default "read"
    extensions: true, // default false
  },
});
```

```ts
// server/plugins/core-routes.ts
export default createCoreRoutesPlugin({
  extensionTools: true,
});
```

- `database: "read"` - डिफ़ॉल्ट। केवल `db-schema` और `db-query` पंजीकृत करता है;
  एजेंट SQL से डेटा देखते हैं लेकिन writes के लिए typed app actions का उपयोग करते हैं।
- `database: "write"` या `true` - deliberate raw SQL maintenance के लिए
  `db-exec` और `db-patch` भी पंजीकृत करता है। writes मौजूदा उपयोगकर्ता/संगठन
  तक scoped रहते हैं और schema changes blocked रहते हैं।
- `database: "off"` या `false` - कच्चे डेटाबेस टूल को हटा देता है
  एजेंट सतह इसलिए ऐप का actions ही एकमात्र डेटा एक्सेस पथ है।
- `extensions: true` - ऐप के लिए फ्रेमवर्क एक्सटेंशन-प्रबंधन actions और
  मार्गदर्शन (`create-extension`, `update-extension`, आदि) चालू करता है।
  प्रमाणित REST निर्माण की अनुमति देने के लिए इसे दोनों plugins पर सेट करें।
  एक्सटेंशन डिफ़ॉल्ट रूप से बंद रहते हैं।

बाकी समूह बूलियन हैं और डिफ़ॉल्ट रूप से सभी चालू हैं: `sharing`, `review`, `history`, `featureFlags`, `localization`, `audit`, `contextXray`, `userProfile`, `automation`, `docs`, `resources`, `web`, `workspaceApps`, `chat`, `email`।
वॉइस-फ़र्स्ट या single-purpose ऐप में `frameworkTools: "minimal"` से सभी एक बार
में बंद करें, या `frameworkTools: { preset: "minimal", resources: true }` से
सिर्फ़ एक रखें — स्पष्ट रूप से दी गई समूह कुंजी हमेशा preset पर भारी पड़ती है।

कोई समूह बंद करने पर वह केवल **एजेंट** सतहों से हटता है: इंटरैक्टिव चैट, MCP,
A2A और बैकग्राउंड रन। संबंधित HTTP action रूट माउंट रहते हैं, क्योंकि UI उन्हें
क्लाइंट hooks से कॉल करती है — `sharing` बंद करने से स्क्रीन पर दिख रहे शेयर
डायलॉग को 404 नहीं मिलना चाहिए। यह parity लागत पहले तोलें: फ़्रेमवर्क का अनुबंध
है कि जो UI कर सकती है वह एजेंट भी कर सकता है, इसलिए दिखते शेयर बटन के साथ
`sharing: false` एक जानबूझकर किया गया उल्लंघन है और तभी उचित है जब ऐप में वह
सतह ही न हो।

इस विकल्प से स्वतंत्र, फ़्रेमवर्क टूल अब डिफ़ॉल्ट रूप से पहली मॉडल रिक्वेस्ट में
लोड नहीं होते। वे खोजने योग्य रजिस्ट्री में रहते हैं और `tool-search` से आते हैं,
या तुरंत यदि ऐप उन्हें `initialToolNames` में नाम दे।

<Callout tone="warning">
  शीर्ष-स्तरीय `databaseTools` और `extensionTools` विकल्प
  `frameworkTools.database` और `frameworkTools.extensions` के पक्ष में
  deprecated हैं। वे अभी भी मान्य हैं, लेकिन कोई शीर्ष-स्तरीय फ़्लैग और उसका
  `frameworkTools` समकक्ष परस्पर विरोधी मानों पर सेट होने पर plugin स्टार्टअप पर
  त्रुटि देता है, बजाय ऐसी टूल सतह के साथ चलने के जिसे किसी ने नहीं चुना।
</Callout>

## उत्पादन कोड निष्पादन {#production-code-execution}

डिफ़ॉल्ट रूप से, उत्पादन एजेंट कोड-निष्पादन उपकरण के बिना चलते हैं। वे ऐप actions, डेटाबेस टूल्स, MCP टूल्स, ब्राउज़र/सेशन टूल्स और अन्य पंजीकृत फ्रेमवर्क टूल्स को कॉल कर सकते हैं, लेकिन उन्हें शेल या फ़ाइल सिस्टम एक्सेस नहीं मिलता है।

नोड-संगत परिनियोजन एजेंट चैट प्लगइन या पर्यावरण ओवरराइड के माध्यम से उत्पादन कोड निष्पादन का विकल्प चुन सकते हैं:

```ts
// server/plugins/agent-chat.ts
export default createAgentChatPlugin({
  codeExecution: { production: "sandboxed" },
});
```

उपलब्ध मोड हैं:

- `off` - डिफ़ॉल्ट। कोई भी कोड-निष्पादन उपकरण उत्पादन में पंजीकृत नहीं है।
- `sandboxed` - `run-code` को पंजीकृत करता है, एक पृथक Node.js JavaScript धावक, एक साफ़ वातावरण के साथ, एक ताज़ा अस्थायी निर्देशिका, आउटपुट / समय सीमा, और `provider-api-request`, `provider-api-docs`, `provider-api-catalog`, `web-request`, और प्रयुक्त संसाधन-समर्थित कार्यक्षेत्र फ़ाइल ब्रिज जैसे सूचीबद्ध पंजीकृत टूल के लिए एक लोकलहोस्ट ब्रिज। `workspaceRead` / `workspaceWrite` द्वारा.
- `trusted` - `run-code` प्लस पूर्ण कोडिंग टूल रजिस्ट्री (`bash`, `read`, `edit`, `write`) को पंजीकृत करता है। इसका उपयोग केवल एकल-किरायेदार या ऑपरेटर-नियंत्रित तैनाती के लिए करें जहां होस्ट तक पूर्ण शेल पहुंच जानबूझकर है।

कोड परिवर्तन के बिना किसी विशिष्ट परिनियोजन के लिए प्लगइन विकल्प को ओवरराइड करने के लिए `AGENT_PROD_CODE_EXECUTION=sandboxed` या `AGENT_PROD_CODE_EXECUTION=trusted` सेट करें। `AGENT_PROD_CODE_EXECUTION=off` प्लगइन विकल्प सक्षम होने पर भी कोड निष्पादन को बंद कर देता है।

`run-code` सैंडबॉक्स प्रक्रिया-स्तरीय अलगाव है, ओएस कंटेनर नहीं। यह चाइल्ड प्रोसेस वातावरण से ऐप रहस्यों को हटा देता है और उपलब्ध होने पर नोड अनुमति मॉडल का उपयोग करता है, लेकिन आउटबाउंड नेटवर्क को नोड द्वारा अवरुद्ध नहीं किया जाता है; प्रमाणित कॉल को टूल द्वारा उजागर किए गए ब्रिज हेल्पर्स के माध्यम से जाना चाहिए।

## उत्पादन में UI को अद्यतन करना {#updating-ui-in-production}

सामान्य deployed app agent app tools - actions, database, MCP और configured integrations - के माध्यम से काम करता है; उसे app source का ambient access नहीं मिलता। Source changes repository development workflow में होते हैं। Embedded, local या Builder frame repository edit कर सकता है जब उसे जानबूझकर workspace और write tooling दी गई हो।

[production code execution](#production-code-execution) को छोड़कर एक मानक उत्पादन परिनियोजन में, एजेंट के पास ऐप टूल्स (actions, डेटाबेस, MCP) तक पहुंच होती है, लेकिन फ़ाइल सिस्टम तक नहीं। इसका मतलब है कि एजेंट डेटा पढ़ और लिख सकता है, actions चला सकता है, और बाहरी सेवाओं के साथ बातचीत कर सकता है - लेकिन यह आपके React घटकों को संपादित नहीं कर सकता है या तैनात उदाहरण पर नए मार्ग नहीं जोड़ सकता है।

### Builder.io: प्रोडक्शन में विजुअल एडिटिंग {#builderio}

[Builder.io](https://www.builder.io?utm_source=agent-native&utm_medium=docs&utm_campaign=framework&utm_content=deployment) एक अलग managed code-capable workflow है जहाँ agent production में app UI बदल सकता है। Repository को Builder.io (free tier उपलब्ध) से जोड़ें और UI changes सीधे माँगें - redeploy की जरूरत नहीं।

**यह कैसे काम करता है:**

1. अपने एजेंट-मूल रेपो को Builder.io (free tier उपलब्ध) से कनेक्ट करें
2. Builder.io एजेंट, विज़ुअल संपादन और वास्तविक समय सहयोग के साथ एक क्लाउड फ्रेम प्रदान करता है
3. एजेंट को UI परिवर्तन करने के लिए कहें - यह आपके घटकों, मार्गों और शैलियों को लाइव संपादित करता है
4. परिवर्तन आपके रेपो में वापस कर दिए जाते हैं

एम्बेडेड एजेंट पैनल बनाम क्लाउड फ़्रेम विकल्पों पर अधिक जानकारी के लिए [Frames](/docs/frames) देखें।

## मल्टी-इंस्टेंस परिनियोजन {#multi-instance}

एजेंट-नेटिव ऐप्स सभी स्थिति को Drizzle के माध्यम से SQL में संग्रहीत करते हैं और UI को [polling](/docs/key-concepts#polling-sync) के माध्यम से डेटाबेस के विरुद्ध सिंक करते हैं - कोई फ़ाइल-सिस्टम स्थिति नहीं, कोई चिपचिपा सत्र नहीं, कोई इन-मेमोरी कैश नहीं। इसका मतलब है कि मल्टी-इंस्टेंस और सर्वर रहित परिनियोजन बॉक्स से बाहर काम करते हैं: प्रत्येक इंस्टेंस को एक ही `DATABASE_URL` पर इंगित करें और वे स्वचालित रूप से परिवर्तित हो जाते हैं। [Key Concepts — Data in SQL](/docs/key-concepts#data-in-sql) और [Portability](/docs/key-concepts#hosting-agnostic) देखें।
