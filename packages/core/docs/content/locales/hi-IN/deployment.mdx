# तैनाती

Agent-native ऐप्स हुड के तहत [Nitro](https://nitro.build) का उपयोग करते हैं। इसका मतलब है कि आप बिना किसी config बदलाव के किसी भी platform पर तैनात कर सकते हैं। बस एक preset सेट करें।

## तैनात करने से पहले: एक स्थायी डेटाबेस चुनें {#persistent-database}

एक **स्थायी** डेटाबेस वह है जिसका डेटा रीस्टार्ट, फिर से तैनात करने, और एक साथ कई सर्वर इंस्टेंस पर चलने के बावजूद भी बचा रहता है। हर तैनात किए गए ऐप को यही चाहिए।

<Comparison>

### पहले

Local development `data/app.db` पर एक SQLite फ़ाइल पर वापस चला जाता है। यह आपकी मशीन पर सुविधाजनक है, लेकिन फ़ाइल local filesystem पर रहती है, जिसे containers, previews, और serverless platforms कभी भी reset कर सकते हैं।

### बाद में

Production को एक स्थायी डेटाबेस चाहिए, जैसे Postgres या Turso/libSQL, जो रीस्टार्ट, फिर से तैनात करने, और एक साथ कई instance पर चलने के बावजूद भी बचा रहे।

</Comparison>

एक कनेक्ट करने में तीन चरण लगते हैं:

<Steps>

### एक प्रोवाइडर चुनें

कोई भी Postgres-compatible host (Neon, Supabase, Railway, RDS, और इसी तरह के) या एक libSQL/Turso डेटाबेस काम करता है। Agent-native [Drizzle](https://orm.drizzle.team) के ज़रिए पढ़ता और लिखता है, जो एक TypeScript library है जो आपके schema को हाथ से लिखे SQL के बजाय type-safe queries में बदल देती है, इसलिए वही app code इन सभी में से किसी के भी साथ चलता है।

### एक connection string प्राप्त करें

आपका provider आपको एक URL देता है जो डेटाबेस की पहचान करता है और बताता है कि उस तक कैसे पहुंचा जाए, उदाहरण के लिए `postgres://user:pass@host:5432/dbname`।

### `DATABASE_URL` सेट करें

इसे अपने पहले production deploy से पहले अपने deploy provider के environment variables में सेट करें। Agent-native URL को पढ़ता है और स्वतः पता लगा लेता है कि किस **dialect** (कौन सा underlying database engine, Postgres या SQLite/libSQL) से बात करनी है। पूरी adapter सूची के लिए [डेटाबेस](/docs/server-database#production) देखें।

</Steps>

<Callout tone="info">

Turso या किसी अन्य libSQL provider का उपयोग कर रहे हैं जो अलग token से authenticate होता है? `DATABASE_URL` के साथ `DATABASE_AUTH_TOKEN` भी सेट करें। एक से ज़्यादा ऐप वाला [कार्यस्थान](/docs/multi-app-workspace) बना रहे हैं? हर ऐप डिफ़ॉल्ट रूप से root `DATABASE_URL` inherit करता है। केवल उस एक ऐप के लिए `<APP_NAME>_DATABASE_URL` सेट करें जिसे अलग डेटाबेस चाहिए।

</Callout>

### स्वचालित schema सेटअप {#skip-ensure-tables}

शुरू करने के लिए आपको एक अलग migration step की ज़रूरत नहीं है। जब आपके ऐप का कोई भी हिस्सा पहली बार डेटाबेस को छूता है, तो agent-native जांचता है कि उसे चाहिए tables, columns, और indexes पहले से मौजूद हैं या नहीं, और जो भी missing है उसे बना देता है। यह हर server boot पर एक बार होता है और सामान्य उपयोग में अदृश्य रहता है।

ठोस रूप से, हर data store पहली बार इस्तेमाल होने पर एक internal `ensureTable()` function को कॉल करता है। वह function डेटाबेस के अपने catalog (उदाहरण के लिए Postgres का `information_schema`) की जांच करता है और केवल उसी के लिए `CREATE TABLE`, `ADD COLUMN`, या `CREATE INDEX` चलाता है जो वाकई missing है। ये **DDL** statements हैं, Data Definition Language का संक्षिप्त रूप, SQL का वह हिस्सा जो rows को पढ़ने या लिखने के बजाय tables को आकार देता है।

### Serverless पर cold-start latency घटाना {#reducing-cold-start}

एक लंबे समय तक चलने वाले server पर, यह जांच बूट पर एक बार चलती है और आप शायद इसे कभी notice भी नहीं करते। Serverless platforms अलग तरह से काम करते हैं। एक **cold start** तब होता है जब platform किसी request को handle करने के लिए आपके server का बिल्कुल नया instance spin up करता है, और serverless पर, "पहला टच" हर cold start का मतलब हो सकता है, करीब 57 अलग-अलग stores में। यह किसी request के असली काम शुरू करने से पहले कुछ सौ round trips तक जुड़ जाता है।

तीन चीज़ें इसे काबू में रखती हैं:

- **Batched introspection.** हर table, column, और index के लिए एक-एक query चलाने के बजाय, ऊपर दी गई जांचें प्रति डेटाबेस एक ही introspection pass के रूप में चलती हैं, बस कुल दो queries। यह अपने-आप होता है और इसके लिए किसी configuration की ज़रूरत नहीं।
- **Managed serverless पर स्वचालित skip।** Netlify Functions, AWS Lambda, और Vercel Functions production में यह जांच पूरी तरह skip कर देते हैं, बिना किसी setup के।
- **`AGENT_NATIVE_SKIP_ENSURE_TABLES=1`।** इसे उन deployments पर सेट करें जिन्हें automatic skip cover नहीं करता, जैसे कोई लंबे समय चलने वाला Node server, Docker, या कोई अन्य self-hosted setup, एक बार जब आपका schema पहले से migrate हो चुका हो और आप नहीं चाहते कि application boot tables बनाए या बदले।

<Callout tone="risk">

न तो flag और न ही automatic serverless skip fail-closed हो सकता है। अगर कोई table वाकई missing है, तो उसे चाहने वाली पहली असली query चुपचाप ठीक होने के बजाय ज़ोर से fail होती है। यह जान-बूझकर है (एक silent repair असली migration bug को छुपा देगा), लेकिन इसका मतलब है कि यहां से migration की ज़िम्मेदारी आपकी है। इस flag को उस deployment पर सेट न करें, और automatic skip पर भरोसा न करें, जो अपनी tables बनाने के लिए application boot पर निर्भर है।

</Callout>

एक ही origin पर एक से ज़्यादा ऐप तैनात करना, या Docker Compose के साथ किसी कार्यस्थान को self-host करना, अपने आप में एक अलग पेज है: देखें
[कार्यस्थान तैनाती](/docs/workspace-deployment)।

## Preset सेट करना {#setting-the-preset}

डिफ़ॉल्ट रूप से, Nitro Node.js के लिए build करता है। किसी अलग platform को target करने के लिए, अपने `vite.config.ts` में preset सेट करें:

```ts
import { agentNative } from "@agent-native/core/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [agentNative({ nitro: { preset: "vercel" } })],
});
```

या build time पर `NITRO_PRESET` environment variable का उपयोग करें:

```bash
NITRO_PRESET=netlify npx @agent-native/core@latest build
```

अपने platform के लिए build और deploy विवरण के लिए वह पेज देखें:

- [**Node.js और Docker**](/docs/node-docker): डिफ़ॉल्ट preset, साथ ही एक standalone Dockerfile
- [**Vercel**](/docs/vercel)
- [**Netlify**](/docs/netlify): scale-to-zero डेटाबेस के लिए keep-warm शामिल है
- [**Cloudflare**](/docs/cloudflare): Pages और Workers
- [**अन्य प्लेटफ़ॉर्म**](/docs/other-platforms): AWS Lambda और Deno Deploy

डिफ़ॉल्ट SSR shell cache policy, और `AGENT_NATIVE_SSR_CACHE` से इसे override करने का तरीका, अपने आप में एक अलग पेज है: देखें [SSR कैशिंग](/docs/ssr-caching)।

पूरा production पर्यावरण चर reference (build/runtime, ज़रूरी secrets, auth, webhooks, security opt-ins, कार्यस्थान `.env` inheritance, और strong secrets generate करना) अपने आप में एक अलग पेज है: देखें
[तैनाती: पर्यावरण चर](/docs/deployment-environment-variables)।

एक तैनात production agent के पास `frameworkTools` और `codeExecution` के ज़रिए कौन से framework tools और code-execution capabilities होती हैं, यह अपने आप में एक अलग पेज है: देखें
[प्रोडक्शन एजेंट एक्सेस](/docs/actions-agent-tools)।

launch के बाद एक तैनात ऐप का UI कैसे update होता है, जिसमें production में visual editing के लिए Builder.io का अलग managed workflow भी शामिल है, यह अपने आप में एक अलग पेज है:
देखें [Production में UI अपडेट करना](/docs/updating-ui-in-production)।

## मल्टी-इंस्टेंस तैनाती {#multi-instance}

Agent-native ऐप्स Drizzle के ज़रिए सारी state SQL में store करते हैं और डेटाबेस के against UI को [polling](/docs/key-concepts#polling-sync) से sync करते हैं। कोई file-system state नहीं, कोई sticky sessions नहीं, और कोई in-memory caches नहीं। इसका मतलब है कि multi-instance और serverless तैनाती बिना किसी अतिरिक्त काम के चलती हैं: हर instance को एक ही `DATABASE_URL` पर point करें और वे अपने-आप converge हो जाते हैं। देखें [मुख्य अवधारणाएं — SQL में Data](/docs/key-concepts#data-in-sql) और [Portability](/docs/key-concepts#hosting-agnostic)।
