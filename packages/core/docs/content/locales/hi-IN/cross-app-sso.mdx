# संगठन SSO और ऐप फेडरेशन

संगठन SSO, एक Agent-Native deployment में कंपनी के OIDC या SAML प्रदाता से साइन-इन की सुविधा देता है। ऐप federation अलग deployments के बीच सत्यापित identity या संगठन संदर्भ साझा करता है। इनके setup और trust boundaries अलग हैं।

Exact registered first-party Agent-Native apps के sign-in pages पर "Continue
with Agent-Native" action उपलब्ध है। यह Dispatch के मौजूदा verified-email flow
को शुरू करता है। यह पेज browser, Desktop और server-side federation को बताता है।

## ऐप federation

### Packaged Desktop workspace

Workspace sign-in, Desktop Settings में एक explicit action है। Enabled होने पर Desktop
अपने dedicated broker के जरिए eligible registered apps को provision कर सकता है। हर
target app अपना local user store, session और access checks रखता है। Desktop app के
sign-in page पर anonymous browser navigation को intercept नहीं करता।

App तभी eligible है जब:

- Desktop उस app के लिए workspace SSO enable करे।
- Production URL exact HTTPS हो।
- Dispatch में app का exact server-side registration हो।
- <code>desktop.workspace-sso</code> rollout flag enabled हो।

Device preference <code>desktopSsoEnabled</code> default रूप से enabled है। Explicit false
opt-out बना रहता है। Flag, preference, registration या eligibility check उपलब्ध न होने
पर normal per-app sign-in उपलब्ध रहता है।

### Server-side federation

Broker और server-side callers short-lived, server-verified protocol का उपयोग
करते हैं। Exact registered first-party apps पर user "Continue with Agent-Native"
चुनकर इसी protocol को शुरू कर सकता है:

1. Caller exact registered app binding मांगता है।
2. Dispatch workspace identity authenticate करके short-lived one-time authorization code
   लौटाता है।
3. Target app server अपने PKCE verifier से code redeem करता है।
4. Target app signed assertion, exact app binding, callback, scope, nonce और expiry verify
   करता है।
5. Target app verified email से local user link या create करता है और normal local
   session जारी करता है।

Assertion केवल server-to-server exchange से लौटता है। यह browser URL में नहीं आता और
reusable bearer token नहीं है।

## Organization federation

<code>organization.cross-app-federation</code> flag default रूप से off है।
Enable होने पर source app अपनी local organization को Dispatch में register करता
है और exact
<code>(identity_authority, identity_id)</code> mapping रखता है। Target app
server-verified assertion से केवल canonical organization ID, name और verified
membership role स्वीकार करता है।

Organization names, email domains और browser cookies join keys नहीं हैं। Mapping के बिना
local organization explicit migration तक unchanged रहती है। Linked memberships target
app के normal access checks का उपयोग जारी रखती हैं।

Federation हर registered source app के लिए अलग credential उपयोग करती है:

- Source app में <code>AGENT_NATIVE_IDENTITY_FEDERATION_SECRET</code> सेट करें।
- Dispatch में matching
  <code>AGENT_NATIVE_IDENTITY_FEDERATION_SECRET_&lt;NORMALIZED_APP_ID&gt;</code>
  सेट करें।
- इस authority boundary के लिए <code>A2A_SECRET</code> reuse न करें।

App ID suffix non-alphanumeric characters की हर लगातार श्रृंखला को underscore
से बदलकर परिणाम को uppercase बनाता है। उदाहरण के लिए

<code>workspace-reports</code> app ID में
<code>AGENT_NATIVE_IDENTITY_FEDERATION_SECRET_WORKSPACE_REPORTS</code> उपयोग
करें।

Identity और organization writes additive हैं। Same-email users बिना बदलाव reuse होते हैं।
नया verified email local user बनाता है। Federation बंद करने से data delete नहीं होता।

## Configuration

<code>AGENT_NATIVE_IDENTITY_HUB_URL</code> server और browser paths के लिए
Dispatch hub बताता है, जब self-hosted app को explicit configuration चाहिए। Exact
registered first-party apps के sign-in pages पर "Continue with Agent-Native"
action उपलब्ध है। <code>browser.identity-sso</code> rollout flag silent
<code>prompt=none</code> sign-in और local sign-in के बाद bootstrap को control
करता है। Local sign-in fallback के रूप में उपलब्ध रहता है।

Self-hosted Dispatch में हर custom app को exact app ID, client ID, HTTPS origin, callback
path और <code>identity-sso</code> capability के साथ

<code>IDENTITY_SSO_APP_REGISTRY_JSON</code> में register करें।

Production registrations में HTTPS और exact callback path जरूरी हैं। Localhost केवल local
development के लिए allowed है। Unknown subdomains, mismatched app IDs, arbitrary paths
और cross-origin callbacks reject होते हैं।

## Verification और rollback

Deployment के बाद:

1. Browser में email, password, magic-link और configured provider sign-in काम करते रहें।
2. "Continue with Agent-Native" action दिखने और local sign-in उपलब्ध रहने की
   पुष्टि करें। <code>browser.identity-sso</code> बंद होने पर भी explicit action
   और local sign-in काम करें। इसे चालू करने पर silent <code>prompt=none</code>
   और local form fallback की पुष्टि करें।
3. Desktop SSO enabled हो तो Desktop Settings के explicit action से एक exact registered
   app verify करें।
4. Organization federation enabled हो तो target app में exact organization ID और
   membership role verify करें।

Silent browser या Desktop path को rollback करने के लिए उसका feature flag बंद
करें। Self-hosted app से explicit browser action हटाने के लिए

<code>AGENT_NATIVE_IDENTITY_HUB_URL</code> या उसका exact app registration हटाकर
redeploy करें। Local sign-in उपलब्ध रहेगा और additive identity तथा organization
records बने रहेंगे।

## Browser identity SSO rollout runbook

पहले `browser.identity-sso` को केवल एक test email के लिए enable करें। Dispatch में sign in करें, target app से sign out करें और अगली load पर silent probe जांचें। Hub session के बिना फिर जांचें और `login_required` पर local form लौटने की पुष्टि करें, फिर cohort बढ़ाएं। पहली enablement पर मौजूदा sessions को एक बार revoke करना पड़ सकता है।
