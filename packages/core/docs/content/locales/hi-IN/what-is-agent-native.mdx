# Agent-Native क्या है?

Agent-native सॉफ़्टवेयर बनाने का एक तरीका है जहाँ AI एजेंट और उसके चारों ओर का प्रोडक्ट सरफेस **बराबर के साझेदार** होते हैं। सामान्य रास्ता chat से शुरू होता है, typed actions जोड़ता है, inline structured results रेंडर करता है, और उसी SQL state के इर्द-गिर्द durable app pages में बढ़ता है। महत्वपूर्ण बात यह है कि agents और मनुष्य एक ही actions, database, और state साझा करते हैं।

यदि आप इस पृष्ठ से एक ही बात याद रखते हैं, तो यह याद रखें: आज के अधिकांश AI ऐप्स उपयोगी होने से एक कदम पहले रुक जाते हैं, और यह अंतर अभी इस क्षेत्र की सबसे बड़ी गलती है।

## यह एक उपयोगकर्ता के रूप में कैसा दिखता है {#what-it-looks-like}

एक background worker, inbox, calendar, form builder, या analytics dashboard की कल्पना करें। अक्सर पहली स्क्रीन chat होती है: आप पूछते हैं कि आप क्या चाहते हैं, एजेंट setup में मार्गदर्शन करता है, एक table या chart दिखाता है, और सही app view खोलता है। कभी-कभी chat एक पूर्ण एप्लिकेशन के दाईं ओर docked होती है। कभी-कभी कोई custom screen नहीं होती क्योंकि workflow एक scheduled job, queue, script, या external-agent integration है। उन सभी रूपों में, आप कर सकते हैं:

- **असली operation से शुरू करें।** एक durable action CLI, HTTP, MCP, A2A, app-agent loop, और बाद में एक UI से चल सकता है।
- **जब UI हो तो सामान्यतः जो क्लिक करते हैं वह क्लिक करें।** सभी buttons, lists, dashboards, keyboard shortcuts — ये सभी वही operations call करते हैं जो agent call कर सकता है।
- **या बस पूछें।** Agent में "reply to the email from Sara saying I'll be there by 3" टाइप करें। यह सही thread खोलता है, reply का draft बनाता है, और आपकी मंजूरी के लिए दिखाता है — बिल्कुल वैसे जैसे आपने खुद किया हो।
- **देखें कि वह क्या देखता है।** एक email खोलें, और agent को पता चलता है कि कौन सी। एक chart चुनें, और agent को पता चलता है कि कौन सा। एक paragraph हाइलाइट करें और Cmd+I दबाएं, और agent केवल उस paragraph पर कार्य करता है।
- **इसे काम करते देखें।** जैसे agent काम करता है — views खोलता है, drafts संपादित करता है, reports चलाता है — UI real time में अपडेट होता है। आप इसे रोक सकते हैं, redirect कर सकते हैं, या किसी भी क्षण mouse से संभाल सकते हैं।
- **इसे एक teammate की तरह steer करें।** Feedback दें, दूसरा task queue करें, इसके instructions संपादित करें, ऑडिट करें कि इसने कल क्या किया। यह याद रखता है, और समय के साथ आपके workflows में बेहतर होता जाता है।

यही वह अनुभव है जिसके लिए agent-native डिज़ाइन किया गया है। अब यहाँ बताते हैं कि अधिकांश products वहाँ तक क्यों नहीं पहुँचते।

## अधिकांश "AI ऐप्स" क्यों कम पड़ते हैं (The Ladder Principle) {#the-ladder}

अधिकांश teams एक progression चढ़ती हैं, जैसे एक सीढ़ी, और अधिकांश एक पायदान बहुत जल्दी रुक जाती हैं।

### पायदान 1 — एक single LLM call (anti-pattern) {#rung-one}

एक text box एक prompt भेजता है, AI एक string वापस करता है, और आप उसे display करते हैं। शायद spinner के साथ। उपयोगकर्ता के लिए course-correct करने का कोई तरीका नहीं, AI के लिए action लेने का कोई तरीका नहीं, यह देखने का कोई तरीका नहीं कि क्या हुआ या क्यों।

आप इसे हर जगह देखते हैं: "AI features" जो मूल रूप से एक SaaS product पर bolted "Summarize" button हैं। वे demos में प्रभावशाली लगते हैं और उस क्षण टूट जाते हैं जब वास्तविकता जटिल हो जाती है। यह product नहीं है; यह एक toy है।

### पायदान 2 — tools के साथ एक chat {#rung-two}

अब AI _काम कर सकता है_। इसके पास tools हैं — "draft email," "search contacts," "run query" — और एक chat interface जहाँ यह आपके सामने काम करता है, जैसे-जैसे चलता है tool calls और results दिखाता है। Claude, ChatGPT, और Cursor hood के नीचे ऐसे ही दिखते हैं।

यह एक real कदम आगे है। लेकिन अपने आप में, यह अभी भी एक chat window है। कोई proper UI नहीं। कोई dashboards नहीं, कोई lists नहीं, कोई forms नहीं, कोई keyboard shortcuts नहीं, कोई team collaboration नहीं। यदि AI confused हो जाता है, तो आप सही button क्लिक करने के बजाय retyping में फंसे रहते हैं। Non-developers इस format में real काम करने में संघर्ष करते हैं।

### पायदान 3 — agent + UI बराबर के साझेदार के रूप में {#rung-three}

यही agent-native है। आप agent के चारों ओर एक real, full-featured app जोड़ते हैं — और महत्वपूर्ण रूप से, agent जो भी action ले सकता है, वह UI में एक button भी है, और user जो भी button क्लिक करता है, वह वही logic चलाता है जो agent उपयोग करता है। एक implementation, दो तरीके से प्रवेश।

पायदान 3 तक पहुँचने पर तीन चीजें बदलती हैं:

- **आपने chatbot में buttons जोड़ना बंद कर दिया। आपने एक app में agent जोड़ा।** यह दोनों तरफ से बहुत उच्च-गुणवत्ता का product है।
- **Agent के पास real context है।** यह देखता है कि आप क्या देख रहे हैं, आपने क्या select किया है, आपने अभी क्या किया। यह उसी database में लिखता है जिससे UI पढ़ता है, इसलिए इसका काम तुरंत दिखता है।
- **बाहरी agents भी इसका उपयोग कर सकते हैं।** अन्य agent-native apps [A2A protocol](/docs/a2a-protocol) के माध्यम से इसके actions call कर सकते हैं। Claude Code, Codex, ChatGPT custom MCP apps, Cursor, और अन्य MCP hosts इसे [MCP server](/docs/mcp-protocol) के रूप में drive कर सकते हैं। एक app, कई entry points।

यही पायदान 3 है। यही agent-native है।

## हर agent को UI की आवश्यकता क्यों है {#why-every-agent-needs-a-ui}

यहाँ तक कि जब agent सारा भारी काम करता है, मनुष्यों को अभी भी ज़रूरत होती है:

- **देखना कि यह क्या कर रहा है** — progress, intermediate output, इसने क्या छुआ
- **इसे steer करना** — feedback देना, interrupt करना, अगला task queue करना
- **इसे manage करना** — इसके instructions, skills, memory, scheduled jobs, connected accounts संपादित करना
- **इसके काम का निरीक्षण करना** — drafts की समीक्षा करना, audit history, गलतियाँ वापस करना
- **इसका output share करना** — dashboards, reports, forms, teammates को भेजने के links

न्यूनतम रूप से, "agent के लिए एक UI" एक observability और management dashboard है। अधिकतम रूप से, यह एक full SaaS app है जिसमें agent co-pilot के रूप में embedded है। दोनों सिरे agent-native हैं, और surface एक से बिना rewrite के बढ़ सकता है।

आपको हर surface को पहले से चुनने की ज़रूरत नहीं है। Agent rich chat में शुरू हो सकता है, native inline UI render कर सकता है, एक full application के अंदर रह सकता है, या एक ही action surface के आसपास automation और external-agent channels से चल सकता है — concrete shapes और APIs के लिए [Agent Surfaces](/docs/agent-surfaces) देखें।

## हर app को agent से लाभ क्यों होता है {#why-every-app-benefits-from-an-agent}

दूसरा पहलू भी उतना ही महत्वपूर्ण है। मौजूदा SaaS products एक ही दीवार से टकराते रहते हैं: आपको जो 80% चाहिए वह बढ़िया काम करता है, और 20% आप बस बदल नहीं सकते। एक chat sidebar जोड़ना शायद ही इसे ठीक करता है — chat आमतौर पर वास्तव में वे काम _नहीं कर सकती_ जो UI कर सकता है।

Agent-native इसे पलट देता है। क्योंकि app का हर action एक बार defined होता है और button और agent tool दोनों के रूप में expose होता है, agent बिना एक अलग "AI world" को maintain किए — वह सब कर सकता है जो buttons कर सकते हैं — और अधिक भी। Natural language clicks के साथ-साथ एक first-class input बन जाती है।

तर्क यह नहीं है कि "agents UI की जगह लें।" यह है: "**agents applications के अंदर होने चाहिए, ऊपर UI के साथ, बराबर के साझेदार के रूप में।**" यहाँ तक कि automation-first app को भी मनुष्यों के लिए supervise, configure, और steer करने के लिए कुछ surface की ज़रूरत होती है — आमतौर पर chat, job history, या एक छोटा status page। देखें [Agent Surfaces — Automation-first app](/docs/agent-surfaces#headless)।

## Agent + UI parity {#agent-ui-parity}

यह defining principle है।

- **UI से** — buttons क्लिक करें, forms भरें, views navigate करें। UI database में लिखता है; agent results देखता है।
- **Agent से** — natural language, A2A के माध्यम से अन्य agents, Slack, Telegram। Agent database में लिखता है; UI स्वचालित रूप से अपडेट होता है।

एक अच्छा mental model है एक shared state machine। User surface और agent
surface दोनों typed actions submit करते हैं; वे actions reducer events की तरह व्यवहार करते हैं जिनके चारों ओर
एक schema और permission boundary होती है: input validate करें, actor authorize करें,
state update apply करें, फिर result broadcast/render करें। UI ज़्यादातर
उस resulting state का projection है। Agent DOM से अनुमान नहीं लगा रहा या
private component state को directly mutate नहीं कर रहा; यह उसी typed
action layer के माध्यम से interact करता है जो UI उपयोग करता है।

## Customization जो आमतौर पर power tools के लिए reserved है {#workspace-customization}

Claude Code जैसे tools इतने powerful क्यों लगते हैं इसका कारण model नहीं है — यह **customization layer** है: per-project instructions, skills, memory, sub-agents, connected services। आप agent को अपने codebase, अपनी preferences, अपनी team के अनुसार shape कर सकते हैं।

Agent-native हर user को वही customization layer देता है — app छोड़े बिना। हर app personal **agent resources** के साथ आता है जिन्हें आप (या आपकी team का कोई भी) उपयोग कर सकते हैं:

- Team-wide rules संपादित करें जो सभी के agent पढ़ते हैं
- Agent को आपकी preferences automatically याद रखने दें जैसे-जैसे आप इसे correct करते हैं
- Reusable how-to guides को `/slash` commands के रूप में लिखें
- विशिष्ट कार्यों के लिए custom sub-agents रखें (`@mentions` के साथ invoke)
- Cron पर चलने के लिए jobs schedule करें (जैसे "हर सोमवार सुबह, पिछले सप्ताह का सारांश करें")
- Per-user MCP servers के माध्यम से external services (Gmail, Stripe, Slack, internal APIs) connect करें

मोड़ यह है: यह सब filesystem में नहीं, database में stored है। कोई dev environment spin up नहीं करना, कोई container per user नहीं। हर user को agent resources का अपना full set मिलता है — personal memory, personal connections, personal skills — essentially मुफ़्त में, क्योंकि यह सब एक table में rows हैं। यही Claude-Code-level flexibility को real multi-tenant SaaS product के अंदर viable बनाता है।

पूर्ण concept के लिए [Agent Resources](/docs/agent-resources) देखें।

## यह अलग क्या बनाता है {#what-makes-it-different}

| Approach                               | विवरण                                                                                                                                             |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **AI bolted on वाले Traditional apps** | AI एक afterthought है। Autocomplete, summaries, या एक chat sidebar तक सीमित जो app में कुछ भी नहीं कर सकती।                                       |
| **Pure chat / agent interfaces**       | Powerful लेकिन inaccessible। कोई dashboards नहीं, कोई workflows नहीं, कोई persistence नहीं। Non-developers इन्हें effectively उपयोग नहीं कर सकते। |
| **SaaS के लिए Claude Code / Codex**    | Devs के लिए अपनी machines पर बढ़िया। Multi-tenant SaaS में translate नहीं होता — dev-box पर प्रति user एक codebase scale नहीं होता।               |
| **Agent-native apps**                  | Agent एक first-class citizen है। यह वही database, वही state साझा करता है, और वह सब कर सकता है जो UI कर सकता है — और इसके विपरीत भी।               |

## पूरी team का development {#whole-team-development}

Agent-native केवल developers के लिए नहीं है। Embedded agent पूरी team को app operate करने का एक shared तरीका देता है, जबकि source-code changes app के normal development workflow का हिस्सा रहते हैं और एक frame को जो intentionally workspace और write tooling granted हो उसे delegate किए जा सकते हैं:

- **Designers** agent के माध्यम से directly app data और workflows अपडेट करते हैं
- **Product managers** workflows configure करते हैं और development team के लिए बदलाव describe करते हैं
- **QA** app test करता है और agent के माध्यम से broken चीज़ें report करता है
- **Team का कोई भी व्यक्ति** natural language के माध्यम से contribute करता है

दृष्टिकोण: कम handoffs, एक व्यक्ति एक छोटी team का काम करता है।

## Template से शुरू करें और customize करें {#fork-and-customize}

Agent-native apps एक start-from-a-working-app model का पालन करते हैं। आप एक **template** से शुरू करते हैं — Calendar, Content, Slides, Analytics, Mail, Clips, Design, Forms, Dispatch — और इसे अपना बनाते हैं। हर एक एक complete, working SaaS product है, न कि blank scaffold:

1. [agent-native.com/templates](/templates) पर एक template चुनें
2. इसे immediately एक hosted app के रूप में उपयोग करें (जैसे mail.agent-native.com)
3. जब customize करना हो तो template से अपना app बनाएं — "हमारा Stripe account connect करें," "एक cohort chart जोड़ें"
4. अपने repository और development workflow में source customize करें
5. अपना app अपने domain पर deploy करें — या agent-native.com पर रहें

क्योंकि यह _आपका_ app है, shared infrastructure नहीं, आप इसके source के मालिक हैं और shared framework को बदले बिना इसे evolve कर सकते हैं। Embedded agent deployed app को default रूप से इसके actions और data surface के माध्यम से operate करता है, और जब इसके frame को explicitly code-enabled किया जाए तो source modify कर सकता है। पूरी story के लिए [Templates](/docs/cloneable-saas) देखें।

पूरे template से शुरू करने के लिए तैयार नहीं हैं? आप agent-native को एक **skill** जोड़कर एक coding agent में भी try कर सकते हैं जो आप पहले से उपयोग करते हैं — `npx @agent-native/core@latest skills add visual-plan` के साथ Plans skill install करें। [Skills Guide](/docs/skills-guide#app-backed-skills) देखें।

## Composable agents {#composable-agents}

Agent-native apps एक दूसरे से बात कर सकते हैं। Mail app के अंदर से, आप analytics agent को data query करने और एक draft email में result शामिल करने के लिए tag कर सकते हैं। Agents discover करते हैं कि कौन से अन्य agents उपलब्ध हैं, एक दूसरे के बीच काम hand off करते हैं, और results उस UI में surface करते हैं जिसमें आप पहले से हैं।

यह hood के नीचे [A2A](/docs/a2a-protocol) और [MCP](/docs/mcp-protocol) द्वारा powered है — same definition, multiple surfaces — लेकिन एक user के रूप में, आपको बस यह जानना है कि "मैं किसी भी चीज़ के साथ मदद के लिए अपने किसी भी app से पूछ सकता हूँ जो उनमें से कोई भी कर सकता है।"

## Code में यह कैसा दिखता है? {#what-does-it-look-like-in-code}

एक action, कई surfaces: agent इसे tool के रूप में call करता है, UI इसे typesafe mutation के रूप में call करता है, [native chat](/docs/native-chat-ui) explicit widget results render कर सकता है, external agents [A2A](/docs/a2a-protocol) के माध्यम से इसे reach करते हैं, और MCP hosts app के [MCP server](/docs/mcp-protocol) के माध्यम से इसे call करते हैं, वैकल्पिक रूप से framework द्वारा handled MCP Apps UI resources और standard remote MCP OAuth के साथ। पूर्ण reference के लिए [Actions](/docs/actions) देखें।
