# डेटा और सिंक

क्लाइंट एप्लिकेशन से ऐप डेटा पढ़ने और लिखने का प्राथमिक तरीका [action](/docs/actions-overview) हुक के माध्यम से है। रिक्वेस्ट को actions में एम्बेड करके, आपका क्लाइंट और एजेंट दोनों आपके एप्लिकेशन के साथ एक ही तरीके से इंटरैक्ट कर सकते हैं।

नीचे दिए गए उदाहरण में, एक टिकट को वर्तमान उपयोगकर्ता को पहले मैन्युअल रूप से एक ड्रॉपडाउन के माध्यम से असाइन किया जाता है, और फिर चैट एजेंट के माध्यम से। UI और एजेंट दोनों एक ही action का उपयोग करते हैं।

### Action हुक {#action-hooks}

दो action हुक हैं जिनका उपयोग करने की सबसे अधिक संभावना है: `useActionQuery()` और `useActionMutation()`। ये दो हुक आपके ऐप की actions तक एक्सेस प्रदान करते हैं।

यह हुक केवल-पढ़ने योग्य actions के लिए उपयोग किए जाने का इरादा है। यह [useQuery()](https://tanstack.com/query/latest/docs/framework/react/reference/useQuery) फ़ंक्शन के इर्द-गिर्द एक पतला रैपर है।

नीचे दिए गए उदाहरण में, `list-tickets` action को कॉल किया जाता है। यह सभी टिकट के लिए GET रिक्वेस्ट बनाने जैसा है।

```ts
import { useActionQuery } from "@agent-native/core/client/hooks";

const { data, isLoading } = useActionQuery("list-tickets", {});
```

निम्नलिखित उदाहरण `get-ticket` action के माध्यम से एक ही टिकट को फ़ेच करने के लिए एक रिक्वेस्ट दिखाता है। क्वेरी को केवल एक विशिष्ट टिकट लौटाने के लिए स्कोप करने के लिए एक `ticketId` प्रदान किया जाता है। अतिरिक्त `enabled` विकल्प यह सुनिश्चित करने के लिए प्रदान किया गया है कि क्वेरी स्वचालित रूप से नहीं चलती है, और केवल तब चलती है जब कोई `ticketId` मौजूद हो।

```ts
import { useActionQuery } from "@agent-native/core/client/hooks";

const { data, isLoading } = useActionQuery(
  "get-ticket",
  { ticketId: ticketId ?? "" },
  { enabled: Boolean(ticketId) },
);
```

यह हुक उन actions के लिए उपयोग किए जाने का इरादा है जो डेटा बदलती हैं, जैसे बनाना, अपडेट करना, या कुछ भेजना। यह [useMutation()](https://tanstack.com/query/latest/docs/framework/react/reference/useMutation) फ़ंक्शन के इर्द-गिर्द एक पतला रैपर है।

`useActionQuery()` के विपरीत, action का इनपुट हुक को स्वयं पास नहीं किया जाता है। इसे `mutate()` या `mutateAsync()` को पास किया जाता है जब आप म्यूटेशन चलाने के लिए तैयार हों।

नीचे दिए गए उदाहरण में, `send-ticket-reply` action को किसी टिकट पर रिप्लाई पोस्ट करने के लिए कॉल किया जाता है। किसी इवेंट हैंडलर से, जैसे किसी बटन के `onClick` से, `mutate()` कॉल करें।

```ts
import { useActionMutation } from "@agent-native/core/client/hooks";

const { mutate, isPending } = useActionMutation("send-ticket-reply");

mutate({ ticketId, body: draft });
```

निम्नलिखित उदाहरण एक `onSuccess` विकल्प के साथ वही म्यूटेशन दिखाता है। कैश इनवैलिडेशन हर म्यूटेशन के बाद स्वचालित रूप से होता है, इसलिए `onSuccess` की आवश्यकता केवल लोकल साइड इफ़ेक्ट के लिए होती है, जैसे रिप्लाई भेजने के बाद रिप्लाई कंपोज़र को साफ़ करना।

```ts
import { useActionMutation } from "@agent-native/core/client/hooks";

const { mutate, isPending } = useActionMutation("send-ticket-reply", {
  onSuccess: () => setDraft(""),
});

mutate({ ticketId, body: draft });
```

### रिसोर्स के अनुसार इनवैलिडेशन {#resource-scoped-invalidation}

दोनों हुक एक वैकल्पिक `resources` ऐरे स्वीकार करते हैं। क्वेरी पढ़े जाने वाले रिसोर्स बताती है और म्यूटेशन बदले जाने वाले रिसोर्स बताता है। पूरे रिसोर्स प्रकार के लिए `type` और किसी खास ID के लिए `type:id` उपयोग करें। स्थानीय म्यूटेशन के मिलान में, `type:id` टैग का पहला कॉलन प्रकार और ID को अलग करता है। प्रकार में कॉलन नहीं होना चाहिए, लेकिन ID में कॉलन हो सकते हैं। सिंक इवेंट प्रकार और ID को अलग-अलग रखते हैं।

```ts
import {
  useActionMutation,
  useActionQuery,
} from "@agent-native/core/client/hooks";

const tickets = useActionQuery("list-tickets", {}, { resources: ["ticket"] });
const ticket = useActionQuery(
  "get-ticket",
  { ticketId },
  { resources: [`ticket:${ticketId}`] },
);
const reply = useActionMutation("send-ticket-reply", {
  resources: [`ticket:${ticketId}`],
});
```

बिना कॉलन वाले प्रकारों और गैर-खाली रिकॉर्ड ID वाले टैग के लिए स्थानीय म्यूटेशन और सिंक इवेंट का मिलान सममित है। पूरे प्रकार के स्थानीय बदलाव के लिए `type` उपयोग करें, `type:` नहीं। स्थानीय म्यूटेशन के मिलान में `design:layer` का अर्थ प्रकार `design` और ID `layer` है। जिस सिंक इवेंट का `resourceType` `design:layer` है, उसका प्रकार `design` से अलग है और वह `design` क्वेरी टैग से मेल नहीं खाता। `ticket` टैग, `ticket` और किसी भी `ticket:id` टैग से मेल खाता है। `ticket:123` टैग, `ticket` और `ticket:123` से मेल खाता है, लेकिन `ticket:456` से नहीं। बिना टैग वाली क्वेरी सावधानी से अमान्य की जाती हैं। बिना टैग वाला म्यूटेशन सभी action क्वेरी अमान्य करता है।

action सिंक इवेंट के लिए `resourceType` और `resourceId` बदले गए रिसोर्स को अलग-अलग पहचानते हैं। `resourceId` न हो या खाली हो तो उस प्रकार से मेल खाने वाली सभी क्वेरी अमान्य होती हैं। किसी भी न दबाए गए action इवेंट में `resourceType` न होने पर पूरे बैच का रिसोर्स फ़िल्टर बंद हो जाता है और सभी action क्वेरी पात्र होती हैं। वैकल्पिक प्रेडिकेट फिर भी इनवैलिडेशन फ़िल्टर कर सकता है।

जिस बैच में action इवेंट हों और केवल action या app-state इवेंट हों, उसका रिसोर्स फ़िल्टर न दबाए गए action इवेंट में बदले गए किसी भी रिसोर्स से मेल खाता है। `actionInvalidatePredicate` देने पर क्वेरी को फ़िल्टर और प्रेडिकेट दोनों पास करने होते हैं। प्रेडिकेट को दबाए गए action इवेंट सहित सभी संबंधित गैर-awareness इवेंट का पूरा बैच मिलता है। बैच में डेटा बदलने वाला कोई अन्य स्रोत भी हो तो रिसोर्स फ़िल्टर बंद होता है, लेकिन प्रेडिकेट लागू रहता है। डेटा बदलने वाला अन्य इवेंट होने पर और न दबाए गए action इवेंट के बिना बैच में भी प्रेडिकेट व्यापक action इनवैलिडेशन फ़िल्टर करता है।

किसी action का `changeResource` इवेंट की डिलीवरी और एक्सेस जाँच के लिए एक रिसोर्स पहचानता है। यह ज़रूरी नहीं कि action द्वारा लिखे गए सभी रिसोर्स की पूरी सूची हो। रिकॉर्ड-विशिष्ट क्वेरी टैग तभी सुरक्षित हैं जब हर संबंधित action का डिलीवर किया गया मार्कर उन सभी रिकॉर्ड को दर्शाए जिन पर क्वेरी निर्भर है। मार्कर के प्रकार के भीतर बल्क राइट या कई रिकॉर्ड पर निर्भरता के लिए पूरे प्रकार का क्वेरी टैग डिलीवर हुए इवेंट से मेल खा सकता है। अलग-अलग प्रकारों के बीच निर्भरता के लिए क्वेरी टैग में हर डिलीवर हुए इवेंट का प्रकार शामिल करें या बिना टैग वाली क्वेरी उपयोग करें। अलग-अलग डिलीवर होने वाले कई इवेंट प्रभावित रिकॉर्ड को कवर कर सकते हैं, बशर्ते हर संबंधित दर्शक को ऐसा इवेंट मिले जिसके लिए उसे अनुमति हो। क्लाइंट टैग का दायरा बढ़ाने से केवल डिलीवरी के बाद मिलान बदलता है। इससे वह इवेंट उस दर्शक को दिखाई नहीं देता जिसके पास उसके डिलीवरी रिसोर्स का एक्सेस नहीं है। सुनिश्चित करें कि संबंधित दर्शकों को ऐसा इवेंट मिले जिसे वे एक्सेस कर सकते हैं।

यह फ़ंक्शन React रेंडर फ्लो के बाहर इंपेरेटिव वन-ऑफ़ action कॉल के लिए है, जैसे कोई सादा इवेंट हैंडलर, एक स्क्रिप्ट, या कोई अन्य नॉन-React कोड पथ। यह एक हुक परिणाम के बजाय सीधे एक प्रॉमिस लौटाता है।

नीचे दिए गए उदाहरण में, `update-ticket` action को एक कीबोर्ड शॉर्टकट हैंडलर से React के रेंडर फ्लो के बाहर कॉल किया जाता है, जो टिकट को एक रेप को असाइन करता है।

```ts
import { callAction } from "@agent-native/core/client/hooks";

await callAction("update-ticket", {
  ticketId,
  assignedToEmail: "jordan@example.com",
});
```

निम्नलिखित उदाहरण `timeoutMs` विकल्प के साथ वही कॉल दिखाता है, जो उन actions के लिए उपयोगी है जो वैध रूप से डिफ़ॉल्ट 60 सेकंड टाइमआउट से अधिक समय लेती हैं।

```ts
import { callAction } from "@agent-native/core/client/hooks";

await callAction(
  "update-ticket",
  { ticketId, assignedToEmail: "jordan@example.com" },
  { timeoutMs: 120_000 },
);
```

हर `useActionQuery()`, `useActionMutation()`, और `callAction()` रिक्वेस्ट 60 सेकंड के टाइमआउट से बंधी है, और टाइमआउट बिना साइलेंट रीट्राई के त्रुटियों के रूप में सामने आते हैं। `useActionQuery()` React Query के एबॉर्ट सिग्नल का उपयोग करते हुए सुपरसीडेड रिक्वेस्ट को भी स्वचालित रूप से कैंसल करता है।

### विफल डेटा लेखन {#write-failures}

जब उपयोगकर्ता द्वारा शुरू किया गया सेव विफल होता है, तो ऐप कुछ न दिखाने के बजाय एक साझा टोस्ट दिखाता है। `useActionMutation()` यह अपने-आप करता है। विफल `mutate()` टोस्ट दिखाता है, जब तक कोई `onError` उस विफलता को न संभाले, चाहे वह हुक के विकल्पों में हो या `mutate()` कॉल में। विफल `mutateAsync()` टोस्ट तभी दिखाता है जब अस्वीकृति अनहैंडल्ड रह जाए, जैसे किसी `await` के ऊपर `try/catch` न हो। जो `catch` मूल त्रुटि की जगह नई `Error` फेंकता है, उसकी रिपोर्ट नहीं की जाती।

`errorNotification` विकल्प इस डिफ़ॉल्ट व्यवहार को बदलता है:

| मान                 | व्यवहार                                                                                                                         |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `"auto"` (डिफ़ॉल्ट) | टोस्ट केवल तब दिखाता है जब विफलता को कोई और न संभाल रहा हो।                                                                     |
| `"shared"`          | हर विफलता पर टोस्ट दिखाता है, भले ही आपका अपना `onError` मौजूद हो। इसका उपयोग तब करें जब हैंडलर केवल रोलबैक या लॉग करता हो।     |
| `"caller"`          | कभी टोस्ट नहीं दिखाता। इसका उपयोग बैकग्राउंड सेव, जानबूझकर अनदेखी की गई विफलता, या ऐसी जगह के लिए करें जो त्रुटि खुद दिखाती है। |

`errorLabel` टोस्ट के शीर्षक को आपके अपने पहले से अनूदित पाठ से बदल देता है। नीचे दिए उदाहरण में, असाइनमेंट विफल होने पर सामान्य शीर्षक के बजाय यही शीर्षक दिखता है।

```tsx
import { useActionMutation } from "@agent-native/core/client/hooks";

const assign = useActionMutation("update-ticket", {
  errorLabel: t("tickets.assignFailed"),
});

assign.mutate({ ticketId, assignedToEmail: "jordan@example.com" });
```

अगले बदलाव पर फिर से प्रयास करने वाले ऑटोसेव को उपयोगकर्ता का काम नहीं रोकना चाहिए, इसलिए वह इससे बाहर रहता है।

```tsx
import { useActionMutation } from "@agent-native/core/client/hooks";

const saveDraft = useActionMutation("save-ticket-draft", {
  errorNotification: "caller",
});
```

`useActionMutation()` के अलावा कोई भी लिखने का काम, जैसे अपलोड के लिए `fetch` या ऐसा `catch` जो त्रुटि निगल लेता है, `reportWriteFailure()` से अपनी विफलता बताता है। सादे `fetch` की त्रुटि में स्टेटस नहीं होता, इसलिए टोस्ट में आपका लेबल या सामान्य शीर्षक दिखता है। सादा `useMutation()` `meta: surfaceMutationError(label)` पास करके इसमें शामिल होता है, जो वही वैकल्पिक लेबल लेता है।

```ts
import { reportWriteFailure } from "@agent-native/core/client/write-failure";

try {
  const response = await fetch(uploadUrl, { method: "PUT", body: file });
  if (!response.ok) throw new Error(`Upload failed with ${response.status}`);
} catch (error) {
  reportWriteFailure(error, { label: t("tickets.uploadFailed") });
}
```

टोस्ट का पाठ विफलता पर निर्भर करता है। रद्द किए गए अनुरोध पर कुछ नहीं दिखता। ऑफ़लाइन होना, टाइमआउट, `401` और `403` में से हर एक शीर्षक के नीचे एक छोटा अनूदित संदेश दिखाता है। `5xx` पर केवल शीर्षक दिखता है, क्योंकि सर्वर अपना त्रुटि पाठ छिपा देता है। जब कोई action `fail()` से टाइप्ड `4xx` त्रुटि के साथ मना करता है, तो टोस्ट वही संदेश दिखाता है जो action ने लिखा था; देखें [action विफल करना](/docs/actions-defining#failing)। `401` या `403` पर सर्वर का पाठ कभी नहीं दिखता।

`AppProviders` उन विफलताओं को सुनने वाला कंपोनेंट `WriteFailureToaster` हमेशा माउंट करता है। वह ऐप के `Toaster` के ज़रिए अपना टोस्ट दिखाता है, इसलिए जो ऐप `toaster={null}` पास करता है, उसे अपना `Toaster` रेंडर करना होगा। जो ऐप `AppProviders` इस्तेमाल नहीं करता, वह `QueryClientProvider` के अंदर और अपने `Toaster` के बगल में `@agent-native/toolkit/app/shared` से `<WriteFailureToaster />` रेंडर करता है। इसके बिना कोई टोस्ट नहीं दिखता।
