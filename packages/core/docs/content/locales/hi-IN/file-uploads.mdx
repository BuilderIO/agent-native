# फ़ाइल अपलोड

फ्रेमवर्क एक फ़ाइल अपलोड एब्स्ट्रैक्शन प्रदान करता है जो अपलोड को एक कॉन्फ़िगर करने योग्य प्रदाता के माध्यम से रूट करता है। टेम्प्लेट `uploadFile()` को कॉल करते हैं और एक URL वापस प्राप्त करते हैं। स्टोरेज बैकएंड को एप्लिकेशन कोड बदले बिना स्वैप किया जा सकता है।

## यह कैसे काम करता है {#how-it-works}

अपलोड अनुरोध `POST /_agent-native/file-upload` पर जाते हैं, जो सक्रिय प्रदाता को भेजता है। आप जाँच सकते हैं कि कौन सा प्रदाता `GET /_agent-native/file-upload/status` पर कॉन्फ़िगर किया गया है।

प्रदाता समाधान क्रम इस प्रकार है:

1. **उपयोगकर्ता-पंजीकृत प्रदाता**: `registerFileUploadProvider()` के माध्यम से पंजीकृत कस्टम प्रदाता।
2. **Builder.io प्रदाता**: अंतर्निहित, और Builder.io कनेक्ट होने पर यह स्वचालित रूप से सक्रिय हो जाता है।
3. **कोई प्रदाता नहीं**: अपलोड अस्वीकार कर दिया जाता है और चैट एक स्टोरेज सेटअप CTA दिखाता है। बाइनरी डेटा कभी भी SQL में सेव नहीं किया जाता।

उपयोगकर्ता-पंजीकृत प्रदाताओं में से, पहला वह प्रदाता जीतता है जो पंजीकृत होने पर खुद को कॉन्फ़िगर किया हुआ रिपोर्ट करता है। `registerFileUploadProvider()` प्रत्येक `id` के लिए इडेम्पोटेंट है। जो `id` पहले से उपयोग में है उसके तहत पंजीकरण करने पर मौजूदा प्रदाता बदल जाता है।

UI यह तय करता है कि स्टोरेज-सेटअप प्रॉम्प्ट दिखाना है या नहीं, केवल सिंक्रोनस `isConfigured()` जाँच का उपयोग करके, अपलोड की कोशिश करने से पहले। वास्तविक अपलोड `isConfigured()` और `isConfiguredForRequest()` दोनों की जाँच करता है। जो प्रदाता खुद को कॉन्फ़िगर किया हुआ केवल `isConfiguredForRequest()` के माध्यम से रिपोर्ट करता है, वह सेटअप प्रॉम्प्ट के लिए अदृश्य रहता है, भले ही उसके माध्यम से अपलोड सफल होते हों।

## स्थायी अपलोड के लिए आवश्यक स्टोरेज {#storage-required}

जब कोई प्रदाता कॉन्फ़िगर नहीं किया जाता है, तो `uploadFile()` `null` लौटाता है और मल्टीपार्ट रूट `503` लौटाता है। चैट अटैचमेंट केवल मौजूदा अनुरोध के लिए उपलब्ध रहते हैं, एजेंट को एक स्टोरेज सेटअप संकेत मिलता है, और ट्रांसक्रिप्ट में बाइनरी पेलोड के बजाय एक सेटअप मार्कर सेव होता है। यह फेल-क्लोज्ड व्यवहार SQL को छोटा रखता है और गायब कॉन्फ़िगरेशन को स्पष्ट दिखाता है।

## Builder.io होस्टिंग {#builder-hosting}

जब आपका ऐप Builder.io से कनेक्ट होता है, तो फ़ाइल अपलोड स्वचालित रूप से Builder की एसेट होस्टिंग पर रूट हो जाते हैं। Builder.io के फ्री टियर में यह मैनेज्ड स्टोरेज शामिल है। फ़ाइलें बिना किसी कॉन्फ़िगरेशन की आवश्यकता के CDN से परोसी जाती हैं, और स्थायी URL चैट थ्रेड में सेव किया जाता है ताकि बाद के टर्न इसे फिर से उपयोग कर सकें। यह अनुशंसित प्रोडक्शन सेटअप है।

## कस्टम प्रदाता {#custom-providers}

फ्रेमवर्क पहले से ही S3-संगत स्टोरेज (AWS S3, Cloudflare R2, MinIO, और इसी तरह के अन्य) के लिए एक अंतर्निहित प्रदाता प्रदान करता है। इसे एनवायरनमेंट वेरिएबल्स के साथ या साइडबार ऑनबोर्डिंग चेकलिस्ट के माध्यम से कनेक्ट करें। किसी कोड की आवश्यकता नहीं है। देखें [Onboarding](/docs/onboarding)।

किसी अलग तरह के बैकएंड के लिए ही एक कस्टम प्रदाता पंजीकृत करें। यह उदाहरण `fetch()` का उपयोग करके एक सामान्य HTTP API के माध्यम से अपलोड करता है:

```ts filename="server/plugins/file-upload.ts"
import { registerFileUploadProvider } from "@agent-native/core/file-upload";
import { defineNitroPlugin } from "@agent-native/core/server";

export default defineNitroPlugin(() => {
  registerFileUploadProvider({
    id: "my-storage",
    name: "My Storage",
    isConfigured: () => !!process.env.UPLOAD_ENDPOINT,
    upload: async ({ data, filename, mimeType }) => {
      const endpoint = process.env.UPLOAD_ENDPOINT!;
      const body = new FormData();
      body.append("file", new Blob([data], { type: mimeType }), filename);

      // This example assumes an upload API that accepts a multipart file
      // and returns { url }. Adjust the request and response handling to
      // match your own provider's actual contract.
      const response = await fetch(endpoint, { method: "POST", body });
      if (!response.ok) {
        throw new Error(`Upload failed with status ${response.status}`);
      }

      const { url } = await response.json();
      return { url, provider: "my-storage" };
    },
  });
});
```

जब प्रदाता को कोई वास्तविक क्रेडेंशियल चाहिए, जैसे कि एक API key, तो एनवायरनमेंट वेरिएबल के बजाय `@agent-native/core/server` से `resolveSecret()` का उपयोग करें। देखें [सुरक्षा — सीक्रेट प्रबंधन](/docs/security#secrets)।

## अपलोड API {#upload-api}

`FileUploadProvider` इंटरफ़ेस:

```ts
interface FileUploadProvider {
  id: string; // Unique id, e.g. "s3"
  name: string; // Human-readable name
  isConfigured: () => boolean; // True when ready from sync runtime state
  isConfiguredForRequest?: () => Promise<boolean>; // True from scoped DB secrets
  upload: (input: FileUploadInput) => Promise<FileUploadResult>;
}

interface FileUploadInput {
  data: Uint8Array | Buffer; // File contents
  filename?: string; // Original filename
  mimeType?: string; // MIME type, e.g. "image/png"
  ownerEmail?: string; // For request-scoped provider credentials
  stableUrl?: boolean; // Builder.io hint: one stable URL while compression finishes
  recordAsset?: boolean; // Builder.io hint: set false to skip the asset library
}

interface FileUploadResult {
  url: string; // Public URL for the uploaded file
  id?: string; // Provider-specific id
  provider: string; // Which provider handled it
}
```

actions या सर्वर कोड में `@agent-native/core/file-upload` से `uploadFile()` का उपयोग करें:

```ts
import { uploadFile } from "@agent-native/core/file-upload";

const result = await uploadFile({
  data: fileBuffer,
  filename: "photo.jpg",
  mimeType: "image/jpeg",
});

if (result) {
  // Provider handled it. result.url is the public URL.
} else {
  // No provider configured. Show the storage setup CTA, or skip.
}
```

## रिज्यूमेबल / स्ट्रीमिंग अपलोड {#resumable}

एक प्रदाता वैकल्पिक रूप से `FileUploadProvider` पर एक `resumable` ब्लॉक लागू कर सकता है, उन अपलोड के लिए जिन्हें पूरी फ़ाइल को पहले बफर करने के बजाय डेटा आने पर ही स्टोरेज में स्ट्रीम करने की आवश्यकता होती है। Clips टेम्प्लेट इसका उपयोग रिकॉर्डिंग को स्टोरेज में चंक-बाय-चंक रिले करने के लिए करता है, जबकि यह अभी भी रिकॉर्ड की जा रही होती है, बजाय इसके कि रिकॉर्डर रुकने के बाद पूरा ब्लॉब असेंबल किया जाए।

```ts
interface FileUploadProvider {
  // ...id, name, isConfigured, upload...

  resumable?: {
    startSession(
      filename: string,
      mimeType: string,
      maxBytes: number,
    ): Promise<ResumableUploadSession>;
    relayChunk(
      session: ResumableUploadSession,
      contentRange: string,
      bytes: Uint8Array,
      options?: { mimeType?: string },
    ): Promise<ResumableChunkResult>;
    completeSession(
      session: ResumableUploadSession,
      filename: string,
      options?: { stableUrl?: boolean; recordAsset?: boolean },
    ): Promise<string>;
    // Best-effort provider cleanup for a session the caller will not resume.
    abortSession?(session: ResumableUploadSession): Promise<void>;
  };
}

interface ResumableUploadSession {
  sessionId: string; // Provider-specific: GCS Location URI, S3 UploadId, etc.
  meta: Record<string, unknown>; // Provider state carried between calls
}

interface ResumableChunkResult {
  ok: boolean;
  status: number;
  updatedMeta?: Record<string, unknown>; // Merged back into the stored session
}
```

जब `resumable` मौजूद होता है, तो डेटा स्ट्रीम करने वाले कॉलर (जैसे कि एक रिकॉर्डर) `startSession` को एक बार, `relayChunk` को बाइट्स आने पर बार-बार, और स्ट्रीम समाप्त होने पर `completeSession` को कॉल करते हैं। यह एकल बफर्ड `upload()` कॉल की जगह लेता है। जिस प्रदाता के पास कोई `resumable` ब्लॉक नहीं है, वह हमेशा केवल बफर्ड पथ ही देखता है। इसे तभी लागू करें जब आपके स्टोरेज बैकएंड के पास कोई नेटिव चंक्ड/रिज्यूमेबल अपलोड API (S3 multipart, GCS resumable uploads, आदि) हो जिसे उजागर करना उचित हो।
