# Developer Guide

This page is for developers running or extending the Chat template: the
quick start, every built-in action, the core tables it runs on, how auth is
configured, and the admin pages — Database, Observability, and Extensions —
that ship by default whether or not you ever open them. See
[Chat](/docs/template-chat) for what the app does.

## Quick start {#quick-start}

This walks through running Chat from nothing installed to a live
conversation with the agent. The commands are identical whether you're in
Terminal on macOS or PowerShell/Command Prompt on Windows, they're plain
Node.js tooling.

<Steps>

### Create the app

```bash
npx @agent-native/core@latest create my-chat-app --standalone --template chat
cd my-chat-app
pnpm install
```

This needs [Node.js](https://nodejs.org) 22 or later and
[pnpm](https://pnpm.io) installed first. See [Getting
started](/docs/getting-started) if you haven't installed either yet.

### Start the dev server

```bash
pnpm dev
```

The app opens at `http://localhost:8080`. If it doesn't open automatically,
visit that URL in your browser.

### Sign in and connect an LLM

On the Welcome screen, select **Continue as local dev** — no email or
password needed for local development. Then connect an LLM: select
**Connect Builder.io** for free credits, or **Custom keys** to add an
Anthropic/OpenAI key or a local Ollama model. Chat ships with no domain data
to seed, so once an LLM is connected there's nothing else to set up before
you can start chatting.

</Steps>

## Action inventory {#actions}

Every operation is a TypeScript file in `actions/`, auto-mounted at
`POST /_agent-native/actions/:name`.

| Action        | What it does                                                            |
| ------------- | ----------------------------------------------------------------------- |
| `hello`       | Example action; returns a greeting. Replace it or add actions beside it |
| `view-screen` | Standard context action; reads the current view back for the agent      |
| `navigate`    | Standard navigation action; moves the UI to a route                     |

`server/plugins/agent-chat.ts` is where the chat runtime itself is
configured: it registers every action in `actions/` as a callable tool
(`loadActionsFromStaticRegistry`), resolves the current org for scoping
(`resolveOrgId`), sets the system prompt, and declares which tools the model
sees on the very first turn (`initialToolNames`) — see [Your First Feature in
Chat](/docs/template-chat-first-edits#first-edits) for what that last part
means when you add a new action.

## Core tables and live sync {#tables}

Chat adds no domain tables of its own (see [What ships](/docs/template-chat#what-ships)). It runs entirely on the framework's core tables: chat threads and messages, `application_state`, `settings`, sessions, resources, and run history.

`useDbSync()` is already wired into the app shell: when the agent (or anyone else) writes to SQL, the client receives the change over SSE, or the 2-second polling fallback, and invalidates the matching React Query caches — no manual refresh, no websocket you have to manage yourself. See [`useDbSync`](/docs/client-data#usedbsync) for the full hook API.

## Auth {#auth}

Auth runs on Better Auth: login, signup, sessions, and organizations, configured in `server/plugins/auth.ts` via `createAuthPlugin`. The same flow runs locally and in production, except that development skips email verification so you can sign up and start building immediately. `createAuthPlugin` also takes the login page's marketing copy — app name, tagline, and feature bullets — as plain config in that same file. See [Authentication](/docs/authentication) for the full auth model (sessions, organizations, protected routes).

**Database** (`/database`) is the same `DbAdminPage` every template gets — a direct table browser/editor over the app's SQL database. See [Database](/docs/server-database) for the connection model behind it.

**Observability** (`/observability`) is the same zero-config `ObservabilityDashboard` every template gets: traces, cost, evals, and feedback for every agent run, computed from data already in your own database. See [Agent Observability](/docs/observability).

**Extensions** are sandboxed Alpine.js mini-apps your users can ask the agent to build inside the running app — a custom widget or checklist, no deploy required. Chat mounts the routes that view and run them (`/extensions/:id`) by default, even before you or your users create one; `/extensions` itself just redirects into the Extensions tab of Settings rather than showing its own list. See [Extensions](/docs/extensions) for what they can and cannot do.

## Customizing it {#customizing}

Every part of the app is editable source. Start here:

- `actions/` — add a new file with `defineAction` to expose new capability
  to both the agent and the frontend.
- `app/routes/` — the UI. The app uses file-system routing (`flatRoutes()`
  in `app/routes.ts`), so adding a route file is enough to mount it.
- `server/db/schema.ts` — add your own tables with Drizzle once you outgrow
  the core tables above. Keep the code dialect-agnostic so the app runs on
  SQLite, Postgres, Turso, D1, and Neon.
- `AGENTS.md` — agent instructions. Update this when you teach the agent new
  capabilities or conventions.
- `.agents/skills/` — detailed patterns the agent follows.

If you add a feature, remember to update all four areas: UI, action, skill
or AGENTS.md entry, and any application state the agent needs to see. That
is what keeps the agent and the UI in parity.
