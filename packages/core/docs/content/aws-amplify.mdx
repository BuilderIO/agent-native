# AWS Amplify

AWS Amplify Hosting supports the Nitro deployment specification directly. Set
Nitro's `aws_amplify` preset and publish the generated `.amplify-hosting`
directory. The framework does not need an Amplify runtime package or an AWS
SDK dependency.

## Build with Nitro

For a standalone app, add this `amplify.yml` at the project root:

```yaml filename="amplify.yml"
version: 1
frontend:
  phases:
    preBuild:
      commands:
        - nvm use 24
        - corepack enable
        - pnpm install
    build:
      commands:
        - NITRO_PRESET=aws_amplify pnpm build
  artifacts:
    baseDirectory: .amplify-hosting
    files:
      - "**/*"
```

The Nitro build produces the Amplify SSR deployment contract:

- `.amplify-hosting/static` contains the browser assets.
- `.amplify-hosting/compute/default/server.js` starts the Node server on
  Amplify's port 3000.
- `.amplify-hosting/deploy-manifest.json` routes static files to the static
  primitive and all other requests to the compute primitive.

For a monorepo, run the build from the repository root and point the artifact
base directory at the app's output. For example, a calendar app under
`templates/calendar` uses `NITRO_PRESET=aws_amplify pnpm --filter calendar build`
and `templates/calendar/.amplify-hosting`. The matching Amplify environment
variable is `AMPLIFY_MONOREPO_APP_ROOT=templates/calendar`.

The framework sets Nitro's `awsAmplify.runtime` to `nodejs24.x`, matching the
Node 24 build phase and the repository's server runtime requirements.

## Runtime variables and CLI

Amplify exposes environment variables to the build container but does not
automatically expose them to every SSR runtime. The Agent-Native Amplify
adapter writes only keys declared by the app's `.env.example` plus the core
deployment keys into the Nitro compute bundle. Its generated `server.js` loads
that file with Node's native `process.loadEnvFile()` before starting Nitro.

The file is inside `compute/default`, not the public `static` directory. It
still travels with the server artifact, so do not commit a populated `.env` or
grant artifact access more broadly than necessary. Prefer Amplify secret
management or an external secret store for production credentials.

You can configure app-level variables with the AWS CLI. Amplify's update
commands replace the complete environment-variable map, so retrieve the
current map and merge overrides before updating. Keep these JSON files outside
the repository and remove them after the update:

```json filename="amplify-env-overrides.json"
{
  "APP_URL": "https://calendar.example.com",
  "DATABASE_URL": "<persistent-database-url>",
  "BETTER_AUTH_SECRET": "<stable-auth-secret>"
}
```

```bash
aws amplify get-app \
  --app-id <app-id> \
  --query 'app.environmentVariables' \
  --output json > amplify-env-current.json
jq -s '.[0] * .[1]' amplify-env-current.json amplify-env-overrides.json \
  > amplify-env-next.json
aws amplify update-app \
  --app-id <app-id> \
  --environment-variables file://amplify-env-next.json

aws amplify get-branch \
  --app-id <app-id> \
  --branch-name <branch-name> \
  --query 'branch.environmentVariables' \
  --output json > amplify-branch-env-current.json
jq -s '.[0] * .[1]' amplify-branch-env-current.json amplify-env-overrides.json \
  > amplify-branch-env-next.json
aws amplify update-branch \
  --app-id <app-id> \
  --branch-name <branch-name> \
  --environment-variables file://amplify-branch-env-next.json
aws amplify start-job \
  --app-id <app-id> \
  --branch-name <branch-name> \
  --job-type RELEASE
```

App-level values apply to branches by default. Use `update-branch` when a
branch needs an explicit override. The build must run again after an env
change so Nitro can include the declared runtime values.

## Configure the app

Amplify Hosting compute is serverless. Configure a persistent PostgreSQL database and
the production secrets in the Amplify environment variables:

- `DATABASE_URL` for a hosted PostgreSQL database such as Neon, Supabase, or RDS.
- `BETTER_AUTH_SECRET` as a stable 32+ character secret.
- Any provider credentials required by the app.

Enable SSR app logs in Amplify after connecting the repository. Run schema
migrations in the release pipeline or as a separate controlled task. Do not
use local PGlite as production storage.

## CloudFront caching

Amplify serves SSR applications through CloudFront. Nitro sets the standard
`Cache-Control` header on the public SSR HTML and React Router `.data` shell:

```txt
public, max-age=600, stale-while-revalidate=604800, stale-if-error=3600
```

Amplify honors that origin header, so no Amplify-specific header file is
required. CloudFront uses the ten-minute freshness window, can serve the
stale shell while revalidating, and can serve it during an origin error. The
framework's client-side actions and private routes keep user-specific data out
of that public shell.

Amplify's static asset policy already gives static files a one-year maximum
TTL. The hashed Vite assets are therefore edge-cacheable without adding a
platform-specific rewrite or custom header. Continuous-deployment releases
clear the Amplify cache.

Keep Amplify's default **Remove cookies from cache key** setting enabled. The
SSR handler strips cookies before rendering the public shell, so excluding
cookies improves the shared cache hit rate without making the shell
personalized. Do not add a global `Cache-Control` override in `customHttp.yml`:
it can override `no-store` responses on private routes. Use
`AGENT_NATIVE_SSR_CACHE` when a deployment needs a shorter or disabled SSR
policy.

See [SSR Caching](/docs/ssr-caching) for the shared policy and
[Amplify's cache-key documentation](https://docs.aws.amazon.com/amplify/latest/userguide/cache-key-cookies.html)
for the hosting setting.

## Streaming requests

Nitro's agent-chat and framework sync endpoints use `text/event-stream` and
are intentionally private and non-cacheable. The framework sends a named
keepalive frame every ten seconds on the shared sync stream so an idle
connection stays open through CloudFront; keep these routes out of custom
cache rules. The public SSR shell and hashed assets remain edge-cacheable.

Amplify compute instances can run for up to 15 minutes, but managed Amplify
Hosting still sits behind a CloudFront path that may buffer token-sized
chunks. That is a compute lifetime, not a guarantee that a browser receives
each chunk immediately.

For direct token streaming, keep Amplify Hosting as the app and SSR origin and
add a dedicated Nitro Lambda Function URL:

```bash
cd templates/calendar
agent-native amplify-stream \
  --amplify-app-id <amplify-app-id> \
  --branch main \
  --region us-east-1 \
  --env-file .env
```

The command builds with Nitro's `aws-lambda` preset and response-streaming
runtime, creates or updates a Node.js 24 Lambda with a 900-second timeout,
configures a `RESPONSE_STREAM` Function URL, merges
`VITE_AGENT_NATIVE_AGENT_CHAT_STREAM_URL` into the selected Amplify branch,
and starts a branch release. The browser first gets a short-lived bearer token
from the same-origin Amplify app, then sends the chat POST to the Function URL.
No AWS SDK or Amplify-specific runtime package is required.

The Function URL is intentionally a direct origin: do not put CloudFront or a
cache in front of the stream endpoint. The SSR shell, React Router `.data`
shell, and hashed assets keep the normal shared SWR and immutable edge-cache
policy above. The CLI needs AWS CLI credentials with permission to manage the
Lambda, IAM role, Function URL, and Amplify branch release. `APP_URL`,
`BETTER_AUTH_SECRET`, the database variables, and provider credentials still
come from the app's `.env` and must identify the same foreground deployment.

Use `--skip-release` when you only want to update the branch variable. The
next Amplify build must include that variable so the client knows the stream
origin. If the handoff is unavailable, the client logs a warning and uses the
normal Amplify chat route, preserving availability without claiming direct
streaming.

See [AWS's Amplify deployment specification](https://docs.aws.amazon.com/amplify/latest/userguide/ssr-deployment-specification.html)
and [AWS Lambda response streaming](https://docs.aws.amazon.com/lambda/latest/dg/configuration-response-streaming.html)
for the platform limits and Function URL contract.

## Verify the deployment

After the first build, check the public URL and confirm that:

1. `/` returns the SSR shell and its `Cache-Control` header.
2. A hashed `/assets/*` file returns successfully.
3. Sign-in, database reads and writes, and any OAuth callbacks used by the app
   work against the configured persistent database.

Amplify's deployment output must contain the Nitro-generated
`deploy-manifest.json`; a static-only upload is not an SSR deployment.

See [AWS's SSR deployment specification](https://docs.aws.amazon.com/amplify/latest/userguide/ssr-deployment-specification.html)
and [Nitro's AWS Amplify provider guide](https://nitro.build/deploy/providers/aws-amplify)
for the platform contract.
