# Deploy an app

Deploying a standalone Agent-Native app puts it on the internet with a real
database, so other people can sign up and use it. Every hosting guide follows
the same five steps. This page explains what each step does and helps you pick a
host. Each host's guide then gives the exact commands.

<Callout tone="info">

Node.js `22.22+` is required.

</Callout>

## Choose a host

| Host                                                | Where the app runs                                     |
| --------------------------------------------------- | ------------------------------------------------------ |
| [Node.js](/docs/node-js)                            | A server you manage, such as a virtual machine         |
| [Docker](/docs/docker)                              | A container on a server or container host you manage  |
| [Vercel](/docs/vercel)                              | Vercel's hosting, with no server to manage             |
| [Netlify](/docs/netlify)                            | Netlify's hosting, with no server to manage            |
| [Cloudflare Workers](/docs/cloudflare#cloudflare-workers) | Cloudflare's network, with no server to manage    |

Choose Node.js or Docker when you want full control over the machine the app
runs on. Choose Vercel, Netlify, or Cloudflare Workers when you want the host to
run the app for you and give it a public address with HTTPS.

## The steps every deployment follows

### Step 1: Create the app

Create a standalone app and install its dependencies. The guides use the Chat
template as an example, but you can start from any template or use an app you
already have. [Getting Started](/docs/getting-started) explains how to create
and run an app locally.

### Step 2: Configure environment secrets

The app reads its production settings from environment variables:

| Variable             | Required | Purpose                                              |
| -------------------- | -------- | ---------------------------------------------------- |
| `DATABASE_URL`       | Yes      | Connects the app to its PostgreSQL database          |
| `BETTER_AUTH_SECRET` | Yes      | Signs user sessions                                  |
| `BETTER_AUTH_URL`    | No       | Sets the public address people use to reach your app |

Save these variables in your host's environment settings, not only in the app's
local `.env` file. Each guide shows how to do this for its host.

`DATABASE_URL` must point to a persistent PostgreSQL database, such as Neon,
Supabase, or Amazon RDS. The [database provider guides](/docs/neon) show where
to find the connection string. `BETTER_AUTH_SECRET` must stay the same across
deploys, because changing it signs every user out. Set `BETTER_AUTH_URL` when
you use a custom domain or a reverse proxy.

The [deployment environment reference](/docs/deployment-environment-variables)
lists every other production setting.

### Step 3: Migrate

Migrations create and update the tables the app needs in your database. Run them
against the production database before the first visit, and again after every
upgrade:

```bash
pnpm migrate:production
```

Do not skip this step. In production, and especially on serverless hosts, the
app does not always create missing tables by itself. A missing table then makes
the first real query fail.

### Step 4: Build

Build the app for your host. Each guide sets `NITRO_PRESET` so the build
produces the format that host expects, such as `node`, `vercel`, `netlify`, or
`cloudflare_module`.

### Step 5: Deploy

Start or upload the build. On Node.js and Docker, you start the server or
container yourself. On Vercel, Netlify, and Cloudflare Workers, a command-line
tool uploads the build and prints the app's public address.

<Callout tone="warning">

Do not use the local development database in production. It stores data on the
machine running the app, so it is lost on most hosts. The **Continue as local
dev** shortcut also works only during local development. A deployed app uses
the sign-up and sign-in flow backed by your production database and auth
secret.

</Callout>

## Check the deployment

After the first deploy, open the app's public address and check that:

- You can create an account and sign in.
- Data you create is still there after you reload the page.
- Any OAuth sign-in or webhook your app uses points to the public address.
