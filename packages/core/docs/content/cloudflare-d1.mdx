# Cloudflare D1

Cloudflare D1 is a supported SQLite database. Choose the deployment section
that matches your Cloudflare runtime, and bind the database with the exact name
`DB`.

## Cloudflare Workers

Pair D1 with the [Cloudflare Worker deployment preset](/docs/cloudflare#cloudflare-workers).

## Configure the binding

Build first so the framework generates the Wrangler config used by the module
Worker deployment:

```bash
npx @agent-native/core@latest build
```

Merge the D1 binding into the generated `.output/server/wrangler.json`:

```jsonc filename=".output/server/wrangler.json"
{
  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "agent-native-app",
      "database_id": "YOUR_DATABASE_ID"
    }
  ]
}
```

Preserve the generated `main`, `assets`, and `compatibility_flags` properties,
then deploy that same generated config:

```bash
npx wrangler deploy --config .output/server/wrangler.json
```

The framework reads the `DB` binding from the Cloudflare runtime. Do not set
`DATABASE_URL` for a D1 deployment because a URL takes precedence over the D1
binding and selects another database dialect.

## Cloudflare Pages

The `cloudflare_pages` preset publishes the Pages Function and static assets to
`dist/`. Configure the binding in the Pages Wrangler config or in the
Cloudflare dashboard:

```jsonc filename="wrangler.jsonc"
{
  "pages_build_output_dir": "./dist",
  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "agent-native-app",
      "database_id": "YOUR_DATABASE_ID"
    }
  ]
}
```

Build and deploy the Pages output with the [Cloudflare Pages preset](/docs/cloudflare#cloudflare-pages):

```bash
npx @agent-native/core@latest build
npx wrangler pages deploy dist
```

The Pages config and `wrangler pages deploy` flow are separate from the
generated Worker config above. If D1 is configured in the Cloudflare dashboard,
redeploy the Pages project after adding the `DB` binding.

## Migrations

D1 deployments cannot load migration files from the server filesystem. Keep app
migrations as SQL entries embedded with `runMigrations()` as shown in the
[database migration guide](/docs/server-database#migrations). Publishing with
Wrangler does not execute those entries. Do not use a static root request as a
migration check: Pages can serve that response from its asset layer, and a
request-path migration is not an authorized release runtime. For a fail-closed
release step, manage app-owned D1 migrations as Wrangler SQL files and apply
them explicitly before deployment:

```bash
# Worker preset
npx wrangler d1 migrations apply agent-native-app --remote --config .output/server/wrangler.json

# Pages preset
npx wrangler d1 migrations apply agent-native-app --remote --config wrangler.jsonc
```

These commands fail the release when D1 rejects a migration. If an app must
keep migration logic embedded in `runMigrations()` instead, execute it from a
dedicated Worker release job or protected dynamic endpoint that explicitly
claims migration duty; the generic Pages deploy does not run those entries.

Use one migration owner for each app-owned schema change; do not apply the same
SQL through both Wrangler migrations and embedded `runMigrations()` entries.

Never run `drizzle-kit push` against a production database.
