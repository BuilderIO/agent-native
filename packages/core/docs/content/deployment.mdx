# Deployment

Agent-native apps use [Nitro](https://nitro.build) under the hood. That means you can deploy to any platform with zero config changes. Just set a preset.

## Before You Deploy: Pick a Persistent Database {#persistent-database}

A **persistent** database is one whose data survives restarts, redeploys, and running on more than one server instance at once. That is what every deployed app needs.

<Comparison>

### Before

Local development falls back to a SQLite file at `data/app.db`. That's convenient on your machine, but the file lives on the local filesystem, which containers, previews, and serverless platforms can reset at any time.

### After

Production needs a persistent database, such as Postgres or Turso/libSQL, that survives restarts, redeploys, and running on more than one instance at once.

</Comparison>

Connecting one takes three steps:

<Steps>

### Pick a provider

Any Postgres-compatible host (Neon, Supabase, Railway, RDS, and similar) or a libSQL/Turso database works. Agent-native reads and writes through [Drizzle](https://orm.drizzle.team), a TypeScript library that turns your schema into type-safe queries instead of hand-written SQL, so the same app code runs against any of them.

### Get a connection string

Your provider gives you a URL that identifies the database and how to reach it, for example `postgres://user:pass@host:5432/dbname`.

### Set `DATABASE_URL`

Set it in your deploy provider's environment variables before your first production deploy. Agent-native reads the URL and automatically detects which **dialect** (which underlying database engine, Postgres versus SQLite/libSQL) to talk to. See [Database](/docs/server-database#production) for the full adapter list.

</Steps>

<Callout tone="info">

Using Turso or another libSQL provider that authenticates with a separate token? Set `DATABASE_AUTH_TOKEN` alongside `DATABASE_URL`. Building a [workspace](/docs/multi-app-workspace) with more than one app? Every app inherits the root `DATABASE_URL` by default. Set `<APP_NAME>_DATABASE_URL` only for the one app that needs a different database.

</Callout>

### Automatic schema setup {#skip-ensure-tables}

You don't need a separate migration step to get started. The first time any part of your app touches the database, agent-native checks whether the tables, columns, and indexes it needs already exist, and creates whatever is missing. This happens once per server boot and is invisible in normal use.

Concretely, each data store calls an internal `ensureTable()` function the first time it's used. That function checks the database's own catalog (Postgres's `information_schema`, for example) and only issues `CREATE TABLE`, `ADD COLUMN`, or `CREATE INDEX` for what is genuinely missing. Those are **DDL** statements, short for Data Definition Language, the part of SQL that shapes tables rather than reading or writing the rows inside them.

### Reducing cold-start latency on serverless {#reducing-cold-start}

On a long-lived server, this check runs once per boot and you likely never notice it. Serverless platforms work differently. A **cold start** is when the platform spins up a brand-new instance of your server to handle a request, and on serverless, "first touch" can mean every cold start, across roughly 57 different stores. That adds up to a few hundred round trips before a request does any real work.

Three things keep that in check:

- **Batched introspection.** Instead of one query per table, column, and index, the checks above run as a single introspection pass per database, just two queries total. This is automatic and needs no configuration.
- **Automatic skip on managed serverless.** Netlify Functions, AWS Lambda, and Vercel Functions all skip this check entirely in production, with no setup required.
- **`AGENT_NATIVE_SKIP_ENSURE_TABLES=1`.** Set this on deployments the automatic skip doesn't cover, such as a long-lived Node server, Docker, or another self-hosted setup, once your schema is already migrated and you don't want application boot creating or altering tables.

<Callout tone="risk">

Neither the flag nor the automatic serverless skip can fail closed. If a table really is missing, the first real query that needs it fails loudly instead of being silently repaired. That's deliberate (a silent repair would hide a real migration bug), but it means you own the migration story from here. Don't set this flag, and don't rely on the automatic skip, on a deployment that depends on application boot to create its own tables.

</Callout>

## Setting the Preset {#setting-the-preset}

By default, Nitro builds for Node.js. To target a different platform, set the preset in your `vite.config.ts`:

```ts
import { agentNative } from "@agent-native/core/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [agentNative({ nitro: { preset: "vercel" } })],
});
```

Or use the `NITRO_PRESET` environment variable at build time:

```bash
NITRO_PRESET=netlify npx @agent-native/core@latest build
```

See the page for your platform for build and deploy details:

- [**Node.js & Docker**](/docs/node-docker) — the default preset, plus a standalone Dockerfile
- [**Vercel**](/docs/vercel)
- [**Netlify**](/docs/netlify) — includes keep-warm for scale-to-zero databases

## Multi-instance deploys {#multi-instance}

Agent-native apps store all state in SQL via Drizzle and sync the UI via [polling](/docs/key-concepts#polling-sync) against the database. There's no file-system state, no sticky sessions, and no in-memory caches. That means multi-instance and serverless deployments work out of the box: point every instance at the same `DATABASE_URL` and they converge automatically. See [Key Concepts — Data in SQL](/docs/key-concepts#data-in-sql) and [Portability](/docs/key-concepts#hosting-agnostic).
