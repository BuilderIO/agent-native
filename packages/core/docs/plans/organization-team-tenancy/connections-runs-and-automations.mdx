# Connections, runs, and automations

Parent: [organization-team tenancy implementation plan](./plan.mdx)

## Decision

Connections remain organization-owned credentials with separately governed app and team grants. Durable execution records retain initiating actor and scope for auditability, but current authority is revalidated at credential resolution, resume, and before every external side effect. Revocation creates an explicit blocked outcome; it does not imply cancellation of an already accepted remote effect.

## Grounded seams

- `packages/core/src/workspace-connections/store.ts` includes `WorkspaceConnectionStatus` and `workspaceConnectionsTable()`; `credentials.ts` resolves credential use.
- `packages/core/src/agent/run-manager.ts`, `run-store.ts`, and `run-loop-with-resume.ts` own durable run creation, persistence, and resumption.
- `packages/core/src/automations/service.ts` owns automation service behavior.
- `packages/core/src/jobs/scheduler.ts` defines `SchedulerDeps` and scheduled-job execution dependencies; `background-automation-runner.ts` is the background automation boundary.

## Ordered steps

1. Extend connection grant modeling in `workspace-connections/store.ts` for team and app use without placing credentials in team-owned records. Require organization owner/admin management for these grants.
2. Add a single credential-resolution authorization path in `workspace-connections/credentials.ts` that checks connection status, app grant, current team grant, requested execution scope, and actor authority. Return a typed denied/blocked result distinct from an unavailable credential.
3. Persist initiating actor and validated organization/team scope with durable runs through `run-manager.ts` and `run-store.ts`; do not treat stored scope as a perpetual authorization grant.
4. Revalidate current authority in `run-loop-with-resume.ts` before resume and before each external side effect. Record a clear terminal outcome when authority is revoked.
5. Apply the same authority model to organization/team automations in `automations/service.ts`, `jobs/scheduler.ts`, and `background-automation-runner.ts`. Give them a governed, revocable automation identity with current scope and credential grants. Personal schedules remain creator-run. Creator departure alone does not stop an organization/team automation.
6. Write an explicit transition plan and proof for the existing mixed organization implementation. Distinguish legacy `runAs` owner authority from creator authority, revalidate at each effect, and return a blocked outcome after revoked authority.
7. Add focused tests for app/team-grant revocation, actor removal, archived teams, the legacy transition, resume after revocation, blocked schedule review/reassignment, and a remote effect already accepted before revocation.

## Acceptance criteria

- A resource share never grants connection use.
- Credential, resume, and effect boundaries all consult current authority, and secrets never enter prompts, application state, or logs.
- Revoked authority produces an explicit blocked/denied result rather than an apparent successful empty execution.
- Background automations cannot continue under stale authority. Organization/team automation identity is revocable and personal schedules remain creator-run.

## Risks and non-goals

- Do not attempt to cancel an external request once its provider accepted it.
- Do not infer grants from a run ID, selected team, or a stale automation payload.
- Do not introduce team-owned credentials.
