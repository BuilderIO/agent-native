# UI selection and administration

Parent: [organization-team tenancy implementation plan](./plan.mdx)

## Decision

The UI exposes team administration and an active-team selector, but all actions derive authorization from server-side organization/team context. Canonical selection lives in URLs and deep links, mirrors into application state for agent context, and is sent as an explicit requested target; none of those values grants access.

## Grounded seams

- `packages/core/src/client/org/TeamPage.tsx` is the organization administration seam.
- `packages/core/src/org/handlers.ts` and `packages/core/src/org/context.ts` remain the mutation and validation boundary.
- `packages/core/src/application-state/handlers.ts` is the application-state write boundary.
- `packages/core/src/resources/handlers.ts` and `packages/core/src/sharing/access.ts` must authorize direct reads and mutations independently of selection.

## Ordered steps

1. Extend `TeamPage.tsx` with team lifecycle and membership controls only for the authorities defined in `org/handlers.ts`. Support leadless teams and do not impose lead replacement requirements.
2. Establish one URL/deep-link selection representation and validate it in `org/context.ts`. Mirror only the validated selection through `application-state/handlers.ts` for agent context. A stale, foreign, or archived selection returns an explicit failure and never silently defaults placement. No team selection preserves existing personal and organization placement.
3. Thread explicit requested target scope through create and move affordances. The server decides whether an actor may target that scope; list filters may use the active selection only after access filtering.
4. Audit direct links, resource detail routes, cross-team shares, and create/move UI so they use actual scope and grants instead of treating selection as a guard.
5. Add UI and handler-level tests for invalid/foreign/archived selection, direct cross-scope read, selector clearing, owner/admin team targeting, ordinary member targeting, lead limitations, and selection persistence without authority escalation.

## Acceptance criteria

- The active team filters lists and defaults valid creation placement without blocking authorized direct links or cross-scope shares.
- Forged URL, application-state, request, stale, foreign, or archived selection values cannot create team authority or silently choose placement.
- Team administration presents server-enforced membership constraints without a sole-lead or replacement invariant.
- Create and move requests are explicit about target scope and remain subject to shared access/move validation.

## Risks and non-goals

- Do not create a client-only permission model or duplicate `accessFilter` in the UI.
- Do not make a selected team hide inherited organization resources through a deny override.
- This plan does not add a new visual canvas or prototype; it specifies architecture and boundary behavior for a later UI implementation.

## Dependencies

Depends on [governance and schema](./governance-and-schema.mdx), [shared scope, access, and moves](./shared-scope-access-and-moves.mdx), and [connections, runs, and automations](./connections-runs-and-automations.mdx). It is required before a user-facing family flag enables team scope.
