To create a software prototype, write down the one question it must answer. Then pick the one flow that answers it: the path of screens a person takes to finish one task. Sketch those screens, build them as clickable screens and test them with about five real users.

It works for a new app or a feature, with no design or coding skills. The example throughout is a class-booking app for a small yoga studio.

![The finished yoga studio booking prototype, three of its four phone screens side by side. They show the class list, a class's details with a "Book this class" button, and the booking confirmation.](https://cdn.builder.io/api/v1/image/assets%2FYJIGb4i01jvw0SRdL5Bt%2F99b41f94b8af4c068a92ae2a844f7181)

## What you need

- Your idea in one sentence
- Five people who'd use it
- Paper or a whiteboard
- A prototyping tool

## How to create a software prototype

### 1. Write down the question the prototype must answer

The question your prototype must answer decides which screens you build, how finished they look and what you test, so it comes first. Write it as **one sentence you can test**. "Can a new member book a class without asking anyone?" works. "Is the app good?" doesn't, because no test can answer it.

Most prototypes answer one of these:

- Usability: can people complete the task on their own?
- Desire: do people want this enough to use it?
- Buy-in: will the team, a client or an investor understand the idea?

The yoga app's question is about usability, because it asks whether a new member can book on their own.

### 2. Pick the one flow to prototype

Your question is about one task, so the prototype only needs the screens for that task. Pick **only the flow your question is about**, from the first screen to the result, and write each screen down in order. For a feature in an existing app, the flow starts at the screen where the feature appears.

For the yoga app, the flow is four screens: the class list, a class's details, Book your spot (choosing how to pay) and the confirmation. Sign-up, the member profile, the teacher pages and settings stay out, because none of them helps answer the booking question.

### 3. Sketch the screens and the taps between them

A paper sketch is the cheapest place to change the order of a flow. Draw **each screen as a box and each tap as an arrow** to the screen it opens. Inside each box, sketch only what the person needs to see and tap at that point: a list, a button, a price.

Walk through the sketch as the user would. If you need a tap that has no arrow, add the missing screen now. If a screen has nothing to tap, it may not need to exist.

### 4. Choose how finished it should look

How finished a prototype looks is its fidelity. **Match the fidelity to the kind of question** you wrote in [the first step](#1-write-down-the-question-the-prototype-must-answer):

| Your question is about | Build | Why it fits |
|---|---|---|
| Usability | Plain clickable screens with real labels | Testers stay on the task instead of the styling |
| Desire | Screens that look like a real app, with real content | People decide whether they want something by how real it feels |
| Buy-in | A polished walkthrough of the one flow that you present | A team or an investor reacts to a picture of the finished product |

The yoga question is about usability, so plain styling would do. Booking means choosing a time and a price, though, so the content must be real. Styled screens work for a usability test too, as long as you [keep testers on the task](#all-the-feedback-is-about-colors-and-fonts).

### 5. Build the clickable screens

The clickable version is the sketch turned into screens a person can tap through on a phone or laptop. Build only the screens on your list, and **link each tap to the screen it opens**. Three kinds of tool do this:

- Design tools (such as Figma): you draw each screen and link them by hand.
- No-code builders: you drag in parts and connect them.
- AI tools (such as Agent-Native Design): you describe the screens and the agent builds them.

With an AI tool, paste your screen list from the sketch. A specific list gets you the flow you planned instead of a guess.

![The yoga app's four screens side by side in a design tool: the class list, class details, Book your spot and the confirmation.](https://cdn.builder.io/api/v1/image/assets%2FYJIGb4i01jvw0SRdL5Bt%2F575a8e541c004d12b66da48fe486fe83)

### 6. Fill the screens with real content

Filler text and made-up labels make testers react to the layout instead of the product. Use **the content a real user would see**. For the yoga app, that means real class names, teachers, times, prices and spots left.

Add the awkward cases too:

- one long class name, to see if the layout breaks
- a full class, so testers meet a disabled button
- an empty state, such as a day with no classes

The class list now looks like Juniper Yoga's timetable on an ordinary Thursday.

![The yoga app's class list with realistic classes, teachers, times and prices, one long class name, and one class marked full.](https://cdn.builder.io/api/v1/image/assets%2FYJIGb4i01jvw0SRdL5Bt%2Fae75c1a5f98f420ca2634ad03e6ad6a6)

### 7. Test the prototype with five people

[Nielsen Norman Group recommends testing with about five users](https://www.nngroup.com/articles/why-you-only-need-to-test-with-5-users/) and running several small rounds instead of one big study. **Find people who match who it's for**, such as yoga students from other studios. Skip friends and teammates: they know the idea and want it to work.

Give each person **one task, and don't explain anything**. For a usability question, use this script:

1. "This is an early version of an app for booking yoga classes."
2. "Please book a spot in Thursday's 6pm class. Say what you're thinking as you go."
3. Watch. Note every pause, wrong tap and question.
4. Afterwards: "What did you expect to happen when you got stuck?"

For a desire question, end by asking whether they'd use it instead of what they do now. For buy-in, show the flow and ask them to explain the idea back.

Where people stopped answers your question.

### 8. Change the prototype and decide what comes next

The test notes tell you which of three things to do next. **Fix where two or more people got stuck**, then pick one:

- Test again if you changed the flow, with new people.
- Ask a new question if the first one is answered, and build a new prototype for it.
- Hand it to whoever builds the app, with the question, the notes and the final screens. If a coding agent builds it, [turn the notes into a spec your coding agent can read](https://www.agent-native.com/use-cases/specs-for-coding-agents/).

For the yoga app, if three testers missed the full class and tapped it anyway, label it "Full, join the waitlist" and test again before anyone builds the booking system.

## Common problems

### Testers get stuck on something you didn't mean to test

A missing screen or a dead tap stops the test before it reaches your question. Walk through the whole flow yourself before the first tester, tapping every button they might try. Add any missing screen, or make the dead button show a short "Not in this prototype" message.

### All the feedback is about colors and fonts

The prototype looks more finished than your question needs, so people judge the styling. Ask about the task instead: "What would you do next?" If the question is about the flow, make a plain grey version with the same labels and test that. With an AI tool, ask for it in one sentence.

### Your tester can't be in the room

A tester watching you click through gives you no answer, because they have to do the tapping themselves. On a video call, give them control of your screen if the call tool allows it. Or send a link they can open on their own device, if your prototyping tool makes one.

### The prototype keeps growing

Each new screen feels small, but together they turn the prototype into an unfinished app. Go back to your question and remove every screen that doesn't help answer it. Put the rest on a list for the next prototype.

## Questions

### What is a software prototype?

A software prototype is a set of screens you can tap through that shows how an app or feature would work, so people can try it before it's built. It usually covers one flow, and nothing works behind the screens: a button only opens the next screen. You test it to learn what to change while changes cost little.

### What are the four types of prototypes?

The four types of prototypes usually named in software are throwaway, evolutionary, incremental and extreme. A throwaway prototype is built to learn, then discarded: pick it to test an idea. An evolutionary one is refined until it becomes the product, which suits teams that already know what to build.

Incremental prototypes build separate parts that join later, for large systems. Extreme prototyping, for web apps, goes from static screens to screens backed by fake data, then connects the real services. Most founders and product teams testing an idea make throwaway prototypes.

### Can AI create a prototype?

Yes, AI tools can create a clickable prototype from a description of the screens. Agent-Native Design, for example, builds clickable screens from your screen list and fills them with realistic content. The AI builds the screens. You still decide what the prototype must answer and test it with real people.

### Can I create a prototype for free?

Yes, a paper prototype costs nothing. For a usability question it can be enough: the tester taps a sketch, and you swap in the sketch of the screen that tap opens. Check a tool's pricing page before you build clickable screens in it. What costs effort is finding five people who match who it's for, so start there.

### What's the difference between a prototype and an MVP?

A prototype is a model you test to learn something; nothing works behind its screens. An MVP (minimum viable product) is the smallest real product that people can use, with working code and data. You make a prototype to decide what to build, and an MVP to see whether people keep using what you built.

### What software can I use to create a prototype?

You can create a prototype in a design tool such as Figma, a no-code builder, or an AI tool such as Agent-Native Design that builds screens from a description. Paper works for low fidelity. Pick the tool that reaches the fidelity your question needs: hand-drawn sketches for the order of screens, clickable screens for testing a task.
