"@agent-native/core": patch

Hide embed start URLs and their tickets from direct MCP tool results when they are nested in another URL, used as an object key, or sit beside a `ticket` field, including a ticket beside `_agentImages`, and in error messages, action links and image notes. Direct results are read as JSON before anything else, so a `toJSON` method or getter cannot add a start URL after the check. When anything a call produced holds a start URL, including a proxied tool's `_meta` or a URL an action's link builds, the call's text and `structuredContent` drop every `ticket` field and replace any whole string that echoes that ticket, raw or escaped, and `_meta` leaves out any entry that carries it other than the widget's embed start and source. A result the check cannot fully read, because it is not JSON data (such as one holding a BigInt) or holds a string escaped more deeply than the check reads, is withheld whole. A write, told by its effect rather than by whether it sends change events, still reports success and records its change, its resource hint read from the result as the action returned it, as it does when building its response fails after it ran, and its widget still gets any session it minted; a read fails. An action with an MCP output contract instead fails, read or write, with its `output_contract_violation` error, which tells the model not to retry a write, and a write still records its change; such a result that is not JSON as returned (a function or symbol at its root, a `toJSON` that returns `undefined`, or a BigInt or cycle in an image entry) now fails that way, where it used to be sent as `{}` or lose the image. An error that cannot be read, such as one whose getter throws, becomes a fixed failure instead of a protocol error. A value an action's schema, gate or handler throws that cannot be classified is replaced, before any caller sees it, by a plain error that says so, so MCP, HTTP and A2A routes, the agent loop and the audit log all get an ordinary failure, and what the call did follows its write evidence. Server warnings that print an error or an output schema's issues hide any start URL in them. A widget write that produced nothing is still flagged `isError`, so the host mounts no empty widget, but it says its change was saved and records it. A proxied tool keeps the failure its upstream reported: its `raw.isError` is read once, before anything else can fail, so an inherited, hidden or getter flag counts, and neither a JSON copy nor a directory projector can clear it. A status that cannot be read is never taken for success: the response says so, with `isError`, and a write still records its change. A failure after the action ran is described once, checked whole, its error code included, against everything the call had built by then, directory projections and links included. That one description goes to the response and, when the call is recorded as an error, to MCP analytics. One that cannot be checked becomes a fixed sentence, which for a result that is not JSON data says so, and only that is sent to error capture. An error from before the action returned, thrown by the action or by its approval request, has a start URL in its message and type hidden in the response and MCP analytics alike. An action's link is built from the result as the action returned it, and checked with the rest of the response. Images are checked against everything the call built, and one that carries a credential is left out whole; image bytes are not scanned while the call's credentials are collected. A `ticket` field is read in any escaping the check decodes. Shared MCP action calls hide echoed tickets the same way, and report an unreadable result as a `result`-stage failure. App-only tools such as `create_embed_session` now return their start URL in `_meta["agent-native/embedStart"]` instead of `structuredContent`, and the embed widget reads it from there.
