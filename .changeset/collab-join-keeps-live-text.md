A tab opening a shared document no longer deletes another tab's unsaved text. When an editor using `useCollabReconcile` sets the new `discoverCollabPeers` and `flushCollabUpdates` options (with `requestCollabSync`) and opens onto a live document that differs from the stored body, it learns who else is open, records their reports, and then catches up with the server, catching up again whenever a report changes meanwhile. It keeps the document if a collaborator reported holding the stored revision or a newer one. Each such client reports its revision in awareness as `reconciledRevision`, but only after the server has every update behind it. Without a report, or without the options, the editor applies the stored body as before. From the moment it seeds until the document holds the stored body, kept on such a report or applied, the editor is read-only, reports no update to save and returns `isJoinPending()` as true, which a host calls before saving the document by any other path. If it cannot learn who else is open, or the stored body has not reached the document 20 seconds after it learned, it stays that way, leaves the document as it is and returns `joinEvidenceFailed: true` with a `retryJoinEvidence()` to try again; the failure clears, and the stored body becomes the editor's base, once the document and the stored body match. A waiting editor checks again when a collaborator's report changes, so it finishes once the lead merges the stored body into a document that also holds unsaved text. It also checks right before it applies the stored body, so a report that lands in between, even before it starts listening for reports, keeps the document. Until the document holds a stored body, the editor applies the newest one instead of merging against the one it opened on, and ignores any snapshot older than the newest it has taken, counting a save acknowledged meanwhile as taken, even one the document matches. An acknowledgement it ignores this way stays ignored once the document holds a stored body, so it cannot replace that body as the editor's base later, and props older than ones it has already observed cannot move the revision it reports back. A snapshot stored after an acknowledgement of the same body counts as a snapshot of its own, so an acknowledgement it ignores cannot hold the join open. When another client's seed wins an empty document with a different body, such an editor leaves that body unapplied and joins as it would onto any live document, instead of taking it as applied. Same-time snapshots it cannot order count in the order they arrive, so one it has taken another over cannot come back. It fails the join, instead of reporting the body as held, when a plugin refuses the transaction that applies it. `reconcileDocAgainstBase` likewise returns `failed` when a plugin refuses its transaction. `useCollaborativeDoc` gains `discoverPeers()`: one presence request that resolves `ready`, `failed` (including an unreadable answer) or `unavailable`, and that runs even in a hidden tab. A presence answer or presence event with no list of states, or with a state the client cannot read, now changes nothing, and `discoverPeers()` resolves `failed` on such an answer. Before, the first removed every collaborator the client knew and the second removed the one it could not read. A `ready` result carries `current()`, which turns false once such an answer or event arrives after its request was sent, because it may name a collaborator the discovery did not; an editor using `useCollabReconcile` then asks again instead of applying the stored body. A presence answer older than one the client has already applied is dropped, so a poll answering after `discoverPeers()` cannot remove the collaborators it reported. The collab server stores presence from a caller below the editor role with `canFlushDocument: false`, so a reader cannot claim to hold a revision or to lead, and refuses such a caller's presence with 400 unless it is a JSON object. Such a caller may replace or clear only an entry that expired or that was stored from such a caller: replacing an editor's live entry is refused with 403, and any change is refused with 503 while stored presence cannot be read. Such a caller's change applies only to the stored entry it was checked against: if a writer on another server stores an entry under that id in between, that entry stays and a replacement is refused with 403. A change that cannot be saved is refused with 503.
