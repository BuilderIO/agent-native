A tab opening a shared document no longer deletes another tab's unsaved text. When an editor using `useCollabReconcile` sets the new `discoverCollabPeers` and `flushCollabUpdates` options (with `requestCollabSync`) and opens onto a live document that differs from the stored body, it learns who else is open, records their reports, and then catches up with the server, catching up again whenever a new report arrives meanwhile. It keeps the document if a collaborator reported holding the stored revision or a newer one. Each such client reports its revision in awareness as `reconciledRevision`, but only after the server has every update behind it. Without a report, or without the options, the editor applies the stored body as before. From the moment it seeds until the document holds the stored body, kept on such a report or applied, the editor is read-only, reports no update to save and returns `isJoinPending()` as true, which a host calls before saving the document by any other path. If it cannot learn who else is open, or the stored body has not reached the document 20 seconds after it first learned, however often it asks again for the same stored revision, it stays that way, leaves the document as it is and returns `joinEvidenceFailed: true` with a `retryJoinEvidence()` to try again; the failure clears, and the stored body becomes the editor's base, once the document and the stored body match. A waiting editor checks again when a collaborator's report changes, so it finishes once the lead merges the stored body into a document that also holds unsaved text. It also checks right before it applies the stored body, so a report that lands in between, even before it starts listening for reports, keeps the document. A stored body the editor adopts without applying, because the live document wrote it (`collabContentRevision` equals `contentRevision`), counts as held once the editor catches up to it, so a later snapshot is merged against it as against an applied one. Until the document holds a stored body, the editor applies the newest one instead of merging against the one it opened on, and ignores any snapshot older than the newest it has taken, counting a save acknowledged meanwhile as taken, even one the document matches. An acknowledgement it ignores this way stays ignored once the document holds a stored body, so it cannot replace that body as the editor's base later, and props older than ones it has already observed cannot move the revision it reports back. A snapshot stored after an acknowledgement of the same body counts as a snapshot of its own, so an acknowledgement it ignores cannot hold the join open. When another client's seed wins an empty document with a different body, such an editor leaves that body unapplied and joins as it would onto any live document, instead of taking it as applied. Same-time snapshots it cannot order count in the order they arrive, so one it has taken another over cannot come back. It fails the join, instead of reporting the body as held, when a plugin refuses the transaction that applies it. `reconcileDocAgainstBase` likewise returns `failed` when a plugin refuses its transaction. `useCollaborativeDoc` gains `discoverPeers()`: one presence request that resolves `ready`, `failed` (including an unreadable answer) or `unavailable`, and that runs even in a hidden tab. A presence answer that is not JSON, or a presence answer or event with no list of states or with a state the client cannot read, now changes nothing, and `discoverPeers()` resolves `failed` on such an answer. Before, the first removed every collaborator the client knew and the second removed the one it could not read. A `ready` result carries `current()`, which turns false once a later presence request fails or such an answer or event arrives after its request was sent, because either may hide a collaborator the discovery did not see; an editor using `useCollabReconcile` then asks again instead of applying the stored body. Readable presence answers and events still replace the collaborators a client knows in the order they arrive, so an older or partial list can leave one out; an editor using `useCollabReconcile` keeps every revision a collaborator reported since it started joining, so such a list cannot take a report back. The collab server refuses presence whose state is not a JSON object with 400, from any caller, since clients refuse a whole list with a state they cannot read. While stored presence cannot be read, it answers an editor's presence request with 503, keeping that editor's own entry, instead of with a list that omits collaborators only the store knows. It stores presence from a caller below the editor role with `canFlushDocument: false`, so a reader cannot claim to hold a revision or to lead. Such a caller may replace or clear only an entry that expired or that was stored from such a caller, judged on both the entry the server holds in memory and the stored entry the change applies to: replacing an editor's live entry is refused with 403, even one the server holds as a reader's under the same id, and any change is refused with 503 while stored presence cannot be read. Such a caller's change applies only to the stored entry it was checked against: if a writer on another server stores an entry under that id in between, that entry stays and a replacement is refused with 403. A change whose stored entry changed or went since it was read is judged again once on a fresh read. An editor's entry the server learns while such a change is being saved stays in its memory and its answers, and an entry cleared meanwhile stays cleared. A presence request that waits on the store answers from the document's presence as it stands when it answers, so a clear that empties the document meanwhile cannot hide an editor that opens after it. Where an editor's entry and a reader's share an id, presence answers list the editor's, whichever was stamped later. A change that cannot be saved is refused with 503.
