Actions the dev server loads from an app's `actions/` folder keep the same settings a production build keeps. The dev scan carried only a few of them, so in dev an action with `needsApproval` ran without asking, its schema defaults were not applied before a `retrySafe` predicate read the input, and settings such as `timeoutMs`, `parallelSafe` and `capabilityScopes` were ignored. When the dev server can't import an action and falls back to running it through `pnpm action`, it now parses the source for `needsApproval`, `persistInBrowser`, `uiOnly` and `toolCallable` too, in the action's options or as named exports beside `tool` and `run`, and trusts only a literal that lifts a limit: `needsApproval: false`, `persistInBrowser: true`, `uiOnly: false` or `toolCallable: true`. Any other value, such as a predicate or a variable, keeps that limit. Options it can't see (spread in from another object, passed by name, built by another helper, re-exported, or exported through a binding the module reassigns or changes) and a source it can't read or parse keep all four: the action asks every time, runs only from the app's UI, takes no tool calls and keeps its results out of the browser.

Every action loader also dropped `persistInBrowser`, in production too, so a GET action that set it to `false` still had its results saved to the browser's query cache. That included the framework's own API key list, email log bodies and infrastructure status. Loaded actions now keep it.
