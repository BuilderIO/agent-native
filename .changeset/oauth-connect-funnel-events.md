MCP OAuth connections now report where people drop off. Serving the authorize page (the sign-in page or the consent page) sends `$mcp_oauth_authorize_opened` with `$mcp_oauth_signed_in`, and serving the sign-in page also sends `$mcp_oauth_login_wall_shown`. A new user's attempt serves two pages, the sign-in page and then the consent page after sign-in, and a returning signed-in user sees only the consent page. So `$mcp_oauth_signed_in = false` (or the login wall) counts signed-out arrivals and `true` counts everyone who reached the consent page, new and returning together; neither is "starts" on its own, and adding them double-counts new users. Silent `prompt=none` checks, requests answered with an error or redirect, and the deploy's setup-required page serve no sign-in or consent page and are not counted. Both events carry the connecting client's name, `$mcp_client_key` (the same normalized client key `agent_connected` reports, so a client's events join on it), the redirect host, `$mcp_oauth_route` (`directory` or `mcp`) and the same app label as `agent_connected`. `$mcp_vendor_client` is classified from the client's name as on every other MCP event, and from a known redirect host (`chatgpt.com`, `openai.com`, `claude.ai` and their subdomains, never a substring) only when the name gives none; `$mcp_vendor_source` is `redirect_host` when the host gave the same label and `client_name` otherwise. Both are the client's own registration, so they label a vendor without proving who the client is. The events never include PKCE values, state, client ids or the redirect path. Measurement only: the authorize flow behaves exactly as before, and a tracking failure is logged instead of failing the sign-in.
