Add opt-in MCP output contracts. An action with `outputErrorStrategy: "strict"` and `mcpOutputSchema: true` advertises its `outputSchema` to MCP clients in the shape they receive (array roots wrapped as `{ items }`, open-link fields for linked actions, embed credentials removed, and embed start URLs masked in place as `"[hidden embed URL]"`), and each `structuredContent`, including its formats, is validated against it. Schemas whose constraints redaction or the open-link fields could break are refused when the action is defined. Actions without the opt-in advertise no output schema, as before. A strict output mismatch, an output validator that throws, or a contracted result that cannot be serialized now raises `ActionOutputContractError` (`errorCode: "output_contract_violation"`). A connection request or stop signal raised while a result is checked stays that signal under any output strategy, but with a framework message that never includes returned values. Both carry `effect: "committed"` once a write entered its handler, in the call or in one nested in it (even under a read-only action), and `effect: "none"` otherwise; writes are classified from the call's validated arguments. Committed failures still refresh other sessions over MCP, HTTP, and the in-app agent. The in-app agent reports them as completed side effects, keeps them in the replay journal so a continued turn replays the failure instead of running the write again, and the single-tool result used by A2A carries `completedSideEffect` on failures too. A connection request raised this way keeps its provider, reason, app, and source in its fields, its message, and HTTP `details`. The in-app agent, the plan-mode action registry, HTTP action routes, and MCP now prepare each call once, validating its arguments and classifying it, and run exactly that preparation through `runPreparedActionCall`, which accepts only a call `actionCallIntent` prepared: approval, plan mode, the unknown-write block, parallel batching, read caching, replay, and the action itself all see the validated arguments, defaults applied, without parsing them again. Preparation stops with the run's abort signal and the tool's deadline. A call whose arguments are invalid fails before any gate, never reaches its handler, and is still audited and tracked, discovered actions included. Preparation reads the validated arguments once, property by property, into a frozen plain-data snapshot and hashes its exact, type-tagged encoding (a Date by its time). The snapshot itself is never handed out: each gate (classification, access, approval, plan mode, audit) and the handler gets its own copy of it, so a value changed after preparation, read differently a second time, or changed by another gate, never runs. Validated arguments that have no such snapshot (a getter or setter, a `Map` or `Set`, a class instance, a function) fail the call as invalid before any gate, with or without approval. `needsApproval` now receives a copy of the snapshot, in the in-app agent and over MCP, and an approval binds to its hash: the approval card still shows the call as the model sent it, but a pending approval stores an `arguments_hash` (a new nullable column on `agent_tool_approvals`), so one recorded before this release is asked for again, and the `approval_required` event carries `argumentsHash`. `runAgentLoop` accepts a plain approval key only with `consumeApproval`, which checks the stored hash; a transport that echoes the key back without one binds it with `approvalKeyWithArguments`, now exported from `@agent-native/core/server`. Every reuse of a call's outcome keys on that hash instead of the raw input. Each `tool_done` carries the `argumentsHash` its call ran with, and a continued turn replays a call only when it recorded a committed effect for that same hash. Reads are deduplicated, cached and reused from the turn's history only for the same hash, so two calls whose defaults prepare differently both run. A call id that more than one call of the turn used, in the journal or the history, names no hash, so none of its results is reused. The zombie-result ledger stores the hash too (a new nullable `arguments_hash` column on `agent_tool_ledger`), and an interrupted write recovers only a result recorded for the same hash; any other stops as an unknown outcome instead of running again. Calls and results recorded before this release are never reused: their reads run again, and an interrupted write stops. A read is held back only when its own run recorded an unknown outcome, and cached reads are dropped after any committed or unknown effect. Post-turn autosave (`onAgentTurnComplete`) also runs after a call that failed once its changes were saved.
