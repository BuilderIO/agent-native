Once `updatesRefused` turns true, a `useCollaborativeDoc` connection with `durableUpdates` stops keeping the doc's unsent updates, in localStorage or in memory for the page's next visit, so neither a reload nor a revisit sends the refused update again. Other connections keep them in memory as before. The new `rebuild(write)` saves the doc again: `write` puts the caller's content onto the server's copy, and the hook moves to a new doc, under a new client id, that sends it as one update. While that update would still be refused, `rebuild` resolves `too_large` and keeps it under a key of its own. A connection with `durableUpdates` holds a Web Lock named for it while it keeps anything in localStorage, and writes its entries only while it holds that lock. A page adopts another connection's kept updates only while holding that connection's lock. It waits for the lock while that tab is still open, so a reload adopts what the page before it kept once that page lets go. In a browser without Web Locks, a page adopts every entry it finds, as before. A page that applies another connection's entry but cannot keep its own leaves that entry, and holds that connection's lock, until its own entry, its candidate or the server's acknowledgment holds the content. A rebuilt doc that cannot keep its first update takes over the old doc's candidate the same way, so a later candidate replaces that one rather than repeating it. The collab routes' default payload limit and the live copy's default size limit now come from shared constants, and `collabUpdateFits(updateBytes, resultingStateBytes)` tells a client whether the server would take an update that leaves the document at a given size.
