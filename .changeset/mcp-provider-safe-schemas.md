Advertise MCP tool input schemas that pass the Anthropic, OpenAI and Gemini schema rules Core pins. A root `anyOf`, `oneOf` or `allOf` is flattened into one object, and the schema description lists the argument sets it combined. Hand-written JSON schemas get the same keyword stripping as Zod schemas. A typeless `const` or `enum` gets an explicit type taken from its values, so Codex no longer narrows `{ "const": 1 }` to a string. A string `const` is advertised as a one-value `enum`, which Gemini honors, and `maxItems` moves into the description, because Gemini refuses a forced call to a large bounded array. Gemini's `enum` holds strings only, so an `enum` that lists a number, boolean or `null` keeps its type and lists its values in the description instead; one value becomes a `const`. Over MCP every rewrite only widens what the schema accepts, boolean subschemas included. The in-app copy does too, except that it admits no array directly inside an array, because the in-app Gemini adapter drops `$ref`, so nothing there can recurse. Actions still validate calls against their own schema.

A schema reference that does not resolve, including one that names an inherited property such as `#/$defs/__proto__`, now fails with a named error instead of disappearing when its branch is flattened. References spelled as encoded pointers or `$anchor` names are rewritten to plain pointers first; an `$id` below the root, a non-local `$ref` and `$dynamicRef` are refused. A `const` that its own `enum` does not list, or an empty `enum`, `anyOf` or `oneOf`, is refused the same way, since that position accepts no value. A property or definition named `__proto__` or `constructor` keeps its own entry through every rewrite. In the in-app agent and over MCP, an app action with such a schema is left out of the tool list and logged as an error, so the other tools keep working. Over MCP the instructions do not name it either, and `tools/call` answers it as an unknown tool. A remote MCP tool with one is held back when its server's tools are listed: the server stays connected with its other tools, and its integration status names the unusable tool and why. Reconnecting the server from Integrations lists its tools again over the same connection, so calls already running on it are not interrupted. Those lists run one at a time per server, so an older answer cannot replace a newer one. When the server refuses that list over HTTP, as it does once an OAuth grant is revoked, the server is left as a refused connect leaves it: its tools are no longer offered, a call to one fails because the server is not connected, and Reconnect reports it disconnected, so choosing Reconnect again starts OAuth for a server set up with OAuth. A list that fails without an HTTP refusal, such as a JSON-RPC error or a timeout, keeps the connection and the tools listed before, and Reconnect answers with the error.
