Meaning search's pgvector table can be made at release, since hosted request functions refuse every schema statement. `semanticVectorStoreMigration({ version, name })` is a named migration that installs `vector` and makes the meaning lane's table at 1,024 dimensions (`DEFAULT_EMBEDDING_DIMENSIONS`, which every built-in embedding family uses; pass `dimensions` for another size), and `pgVectorIndexMigration({ version, name, namespace, dimensions })` does the same for any namespace, and refuses an empty `dimensions` list, a bad size or a bad namespace when it's built, before a release makes any table. A database without pgvector defers either one to a later release, as does a server migrating at boot whose database role may not install the extension or make the table; a release fails instead. `ensurePgVectorIndex` now checks that the table its name finds has its `audience_ids` column and both indexes before sending any schema statement, so a request can use a table the release made. A migration entry can set `changesSchema: true` so a `run` callback that makes tables uses the migration connection, as SQL migrations do, rather than the app's, and a failing `run` callback is logged with its migration's name. `searchNamespaceIdentifiers` refuses a namespace too long for its vector table names, which Postgres would cut short at 63 characters.
