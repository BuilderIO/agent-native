# 7.1a Notebook model and actions

Lane C (Notebook). Size M. Not gated (no new UI; 7.1b renders it).
Depends on: nothing. Blocks: 7.1b, 7.2b, 7.3, 7.4, 7.5.

Paths are relative to `templates/analytics/` unless they start with
`packages/` or `docs/`.

## 1. Goal

A notebook is a saved artifact with ordered cells: SQL cells, chart cells and
text cells. The agent and the UI can create one, add Markdown text between
query results, and turn a legacy saved analysis into a notebook without losing
the original. This unit lands the data contract and actions only, so that 7.1b
(page), 7.2b (chained cells), 7.3 (agent edits), 7.4 (from a thread) and 7.5
(publish) all build on one shape.

## 2. What the code does today

- Analyses are legacy. `save-analysis` says "Legacy compatibility only ... new
  requests become dashboards" (`actions/save-analysis.ts:116`). `/analyses`
  redirects to `/dashboards` (`app/routes/analyses._index.tsx:10`). The agent
  guide says "dashboards are canonical and legacy analyses remain readable"
  (`AGENTS.md:3`). The `adhoc-analysis` skill says new durable results go to
  dashboards (`.agents/skills/adhoc-analysis/SKILL.md:211`, `:230`).
- An analysis row is one Markdown blob plus a JSON evidence blob, with no cells:
  `analyses` has `result_markdown` and `result_data` (`server/db/schema.ts:135-150`).
  The page renders `resultMarkdown` with the in-app `Markdown` component
  (`app/pages/analyses/AnalysisDetail.tsx:367-372`).
- A SQL dashboard is already an ordered list of query panels with a chart type:
  `SqlPanel { id, title, sql, source, chartType, width, config }`
  (`app/pages/adhoc/sql-dashboard/types.ts:112-122`) inside
  `SqlDashboardConfig { name, filters, variables, panels }` (`:131-150`).
  Chart types include `table`, `line`, `bar`, `section`, `callout`, `extension`
  (`:10-23`). Rows live in `dashboards` with `kind` of `explorer` or `sql` and a
  JSON `config` text column (`server/db/schema.ts:18-34`).
- Dashboards already have what notebooks need: sharing
  (`server/db/index.ts:37-47`), revisions and restore
  (`dashboard_revisions`, `server/db/schema.ts:56-79`;
  `actions/restore-dashboard-revision.ts`), agent edits with a rendered-result
  check (`actions/mutate-dashboard.ts`, `verifyPanelWrite` in
  `server/lib/dashboard-panel-verification.ts:959`), filters with `{{var}}`
  interpolation, and screen context in `view-screen`
  (`actions/view-screen.ts:196-213`).
- There is no Markdown text panel. `section` renders a heading plus a plain
  `config.description` (`app/pages/adhoc/sql-dashboard/SqlChartCard.tsx:330-390`).
- "Has no query" is spelled `chartType === "section" || chartType === "extension"`
  at many call sites: `hasSqlToRun` (`server/lib/dashboard-panel-verification.ts:184-186`),
  `validatePanelSql` (`actions/update-dashboard.ts:569`), report rendering
  (`server/lib/dashboard-report-render.ts:132`, `:1008`), time scope
  (`server/lib/dashboard-time-scope.ts:302`), inspection
  (`actions/inspect-dashboard-panel.ts:100`). `git grep '=== "section"'` finds 21
  non-test sites.
- Renderer config keys are registered in `PANEL_CONFIG_KEYS`
  (`shared/panel-render-contract.ts:45-68`) with optional `onlyFor` chart types;
  unknown keys become static issues during verification (`:295-...`).
- Root config keys are not whitelisted: `normalizeDashboardConfig` only touches
  panels (`shared/dashboard-config-normalization.ts:14-44`), so a new root key
  such as `layout` survives saves.
- Dashboard summaries project fields from the config JSON in SQL, not by
  parsing in JS (`server/lib/dashboards-store.ts:1029-1043`), so a cheap
  `layout` projection fits the existing pattern.

## Plan corrections

- "Saved analyses gain ordered cells" would revive a table the app has
  deprecated, and it would not get revisions, render-checked agent edits,
  filters or panel rendering. **Notebooks are SQL dashboards with
  `config.layout: "notebook"`.** Cells are panels. Legacy analyses stay readable
  at `/analyses/:id` unchanged, and gain an "Open as notebook" conversion that
  copies them into a new notebook.
- No new table and no new `dashboards.kind` value. Adding a kind would touch
  every `kind` switch for no gain; `layout` is a render mode of a SQL dashboard.

## 3. Build

1. **Layout flag.** Add `layout?: "grid" | "notebook"` to `SqlDashboardConfig`
   (`app/pages/adhoc/sql-dashboard/types.ts`). Absent means `grid`. Validate it
   in `collectDashboardConfigIssues` (`actions/update-dashboard.ts:259`): any
   other value is a `dashboard_config` issue with a message naming the two
   values.
2. **Text cell type.** Add `"text"` to `PANEL_CHART_TYPES`
   (`app/pages/adhoc/sql-dashboard/types.ts:10`). Add `markdown?: string` to
   `SqlPanelConfig` and register `markdown: { onlyFor: ["text"] }` in
   `PANEL_CONFIG_KEYS` (`shared/panel-render-contract.ts:45`). Cap
   `config.markdown` at 20,000 characters in config validation, with an error
   that says to split long text into several text cells.
3. **One boundary for "panel has no query".** Add
   `panelRunsQuery(chartType: string): boolean` to
   `shared/panel-render-contract.ts` returning false for `section`,
   `extension` and `text`. Replace every "section or extension means no query"
   check with it (verification `hasSqlToRun`, `validatePanelSql`, time scope,
   inspect-dashboard-panel, report-render fetch loop, `SqlChartCard`
   `shouldLoadData`). Leave checks that mean "section is a group heading"
   (layout grouping in `dashboard-layout.ts`, section columns normalization)
   alone. Do not add a third `|| chartType === "text"` anywhere.
4. **Report rendering.** In `server/lib/dashboard-report-render.ts:1008`, render
   a text cell like a section note: escaped plain text of the Markdown (strip
   Markdown syntax with a small pure helper), never raw HTML.
5. **Summaries.** In `listDashboardSummaries`
   (`server/lib/dashboards-store.ts:989`) project
   `config::jsonb ->> 'layout'` next to `parentId` and return
   `layout: "grid" | "notebook"` on `DashboardSummaryRecord` (`:68-88`). Map an
   unexpected stored value to `grid` only after logging it; do not throw a list
   read over a cosmetic field. Pass it through `list-sql-dashboards`.
6. **Create action.** Add `actions/create-notebook.ts` (`defineAction`):
   input `{ name: string, cells?: NotebookCellInput[] }`, where a cell is
   `{ kind: "sql" | "chart" | "text", title?, sql?, source?, chartType?, markdown? }`.
   It builds a config `{ name, layout: "notebook", panels }` with generated
   cell ids (`cell_<8 lowercase letters or digits>`, so 7.2b can use them as table names), `width: 1`, SQL cells as
   `chartType: "table"`, and saves through the same store write as
   `update-dashboard` (`upsertDashboardWithRetryOutcome`), owner and org from
   the request context. Agent callers go through `verifyPanelWrite`, the same
   gate `mutate-dashboard` uses. Return `{ dashboardId, url, verified,
   unverified[] }` and a `link` builder like `save-analysis.ts:218`. Zero cells
   creates one empty text cell so the page is never blank.
7. **Convert action.** Add `actions/convert-analysis-to-notebook.ts`: input
   `{ analysisId }`. Read with `getAnalysis` (access-checked,
   `server/lib/dashboards-store.ts:2643`). Build text cells: the first holds
   the question; then `resultMarkdown` split at `## ` headings into cells of at
   most 20,000 characters. Do not copy `resultData` into cells (it is evidence,
   and some of it is large); keep `config.description` = analysis description
   and add `config.sourceAnalysisId`. Create with the store write from step 6.
   The legacy analysis is not modified or deleted. Converting twice creates two
   notebooks; return the new id each time.
8. **Agent context.** In `buildDashboardAgentContext` (`server/lib/agent-readable-resource-context.ts:193`, used by
   `view-screen.ts:207`) include `layout` and, for notebooks, a one-line
   ordered cell list (`#n id title kind`). Keep it inside the existing
   character budget.
9. **Skills and instructions.** Read `.agents/skills/writing-agent-instructions`
   first. Create `.agents/skills/notebooks/SKILL.md` (name `notebooks`,
   description "Create and edit notebooks: ordered SQL, chart and text cells.
   Use when the user asks for a notebook, converts an analysis, or edits a
   cell."). Cover: notebooks are dashboards with `layout: "notebook"`; cell
   kinds and how each maps to a panel; `create-notebook` and
   `convert-analysis-to-notebook`; that `width` is ignored and must be `1`;
   that text cells hold Markdown up to 20,000 characters. Add one line to
   `AGENTS.md` "Data questions" pointing at the skill. Update
   `.agents/skills/adhoc-analysis/SKILL.md` Step 6 to say a durable
   step-by-step analysis can be a notebook. 7.3 extends this skill for edits.
10. **Application state.** None new in this unit. Navigation already reports
    `view: "adhoc"` and `dashboardId` for notebooks
    (`app/hooks/use-navigation-state.ts:38-47`); 7.3 adds the cell to
    `selected-object`.
11. **Changelog.** From `templates/analytics`:
    `agent-native changelog add "Notebooks: ordered SQL, chart and text cells, and saved analyses open as notebooks" --type added`
    after 7.1b lands (one entry for the pair).

## 8. Defaults for open questions

- **[Default] Notebook = SQL dashboard with `layout: "notebook"`**, not a new
  table or kind. Change only with a reason the dashboard model cannot meet.
- **[Default] Text cells are a new `text` chart type** rather than reusing
  `section`, because `section` drives grid grouping.
- **[Default] SQL cell = panel with `chartType: "table"`; chart cell = panel
  with its own SQL and a chart type.** After 7.2b a chart cell can read an
  earlier cell instead of repeating its SQL.
- **[Default] Markdown cap 20,000 characters per text cell**, conversion splits
  at `## ` headings.
- **[Default] Conversion keeps the legacy analysis** and records
  `config.sourceAnalysisId`; it does not hide or redirect the analysis.
- **[Default] Ship live, no feature flag.**

## 9. Do not

- No behavior changes outside this unit. Grid dashboards render exactly as
  before.
- Schema stays additive: no new columns needed; never alter `analyses` or
  `dashboards`.
- No new `/api` routes for app data; everything goes through actions.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value (for
  example, a failed analysis read must not become an empty notebook).
- No large payloads in SQL: do not copy `resultData` into the config.
- Do not delete or rewrite legacy analyses, and do not change `save-analysis`.
