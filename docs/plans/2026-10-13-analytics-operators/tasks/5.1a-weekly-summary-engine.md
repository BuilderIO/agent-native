# 5.1a Weekly summary: facts, delivery and schedule

Lane B (Founders). Size M. Split from plan unit 5.1, which is L as written;
5.1b turns it on by default after the first dashboard and adds the Settings
control and open tracking.

## 1. Goal

Once a week, each person who turns it on gets one short email, written by the
agent, about the dashboards they care about: what moved compared with the week
before, the alerts that fired, and the agent's best explanation of the biggest
change, with a link to each dashboard. When some numbers could not be loaded,
the email says which ones and why instead of quietly leaving them out. A
growth lead can read it on Monday morning and know where to look.

## 2. What the code does today

All paths are relative to `templates/analytics/` unless noted.

**Report subscriptions (the delivery we build on)**

- Subscriptions are daily only. The type is `frequency: "daily"`
  (`server/lib/dashboard-report-subscriptions.ts:23-44`, line `29`). The
  column enum is `["daily"]` (`server/db/schema.ts:111-113`). Recipients are
  capped at 5 (`dashboard-report-subscriptions.ts:58`).
- `save-dashboard-report-subscription` creates or updates one per dashboard
  (`actions/save-dashboard-report-subscription.ts:13-44`), owned by the
  caller (`dashboard-report-subscriptions.ts:394-466`).
- A due subscription is claimed by the sweep in `server/jobs/dashboard-report.ts:105-198`
  and rendered by `sendDashboardReportSubscription`
  (`server/lib/dashboard-report.ts:220-343`). `collectReportSnapshot`
  (`dashboard-report.ts:142-176`) resolves the dashboard under the owner's
  access and default filters. `fetchReportPanelData`
  (`server/lib/dashboard-report-render.ts:121-127`) runs every panel with a
  per-panel status (`query-failed`, `missing-credential`, `not-emailable`, ...).
  `renderReportEmail` (`dashboard-report-render.ts:996`) turns them into HTML.
- A run where every panel failed throws instead of mailing
  (`dashboard-report.ts:256-273`), and a degraded run is labeled degraded
  (`dashboard-report.ts:282-306`). That is the honesty contract this unit
  keeps.
- The subject is hardcoded English with an em dash:
  `` `Daily dashboard: ${snapshot.title} — ${reportDate(snapshot)}` ``
  (`dashboard-report.ts:308`). Not this unit's to fix, but the new subject
  must not copy it.
- Email templates are registered with `defineTransactionalEmail` in
  `server/lib/emails.ts:1-45` (`ANALYTICS_DASHBOARD_REPORT_EMAIL_ID`).
- The sweep runs every 60 s in-process when enabled
  (`server/plugins/dashboard-report-jobs.ts:27-58`) or from the platform
  scheduler on serverless. **No agent is involved**: a report is panel data
  rendered to HTML. There is no narrative and no week-over-week comparison.

**Alerts**

- Alert rules are thresholds over first-party events: count or distinct count
  in a window (`actions/save-analytics-alert-rule.ts:23-75`; type at
  `server/lib/analytics-alerts.ts:73-98`). Channels include inbox, email, a
  per-rule Slack webhook and a generic webhook (`save-analytics-alert-rule.ts:52-73`).
- Every firing writes a row to `analytics_alert_incidents` with rule id,
  window, threshold, observed value and severity (`server/db/schema.ts:712-728`,
  insert at `server/lib/analytics-alerts.ts:1724`). That table is the source
  for "alerts this week".

**Scheduled agent work**

- The repo rule is that AI work runs through the agent, and background agent
  work runs on the core automation runner, not a custom job. The runner
  executes a markdown body with the full agent loop and the app's actions, and
  records status, failures and pauses (`.agents/skills/automations/SKILL.md`).
- Analytics already creates a scheduled automation from an action:
  `actions/set-index-schedule.ts:44-95` calls `defineAutomation` /
  `updateAutomation` from `@agent-native/core/triggers` and needs `ctx.appId`
  so the scheduler can match the app (`set-index-schedule.ts:50-58`).
- `DefineAutomationInput` takes `schedule`, `timezone`, `body` and an optional
  `delivery` target (`packages/core/src/automations/service.ts:73-92`). The
  runner can post the run's result to a messaging platform when
  `deliveryPlatform` and `deliveryDestination` are set
  (`packages/core/src/jobs/background-automation-runner.ts:875-906`).
- An automation that needs a model and has no usable credential pauses with
  `missing_credentials` and emails its owner once (automations skill, Failure
  handling). That is the right failure for a summary that cannot be written.

## 3. Build

1. **Storage (additive).** Add `analyticsWeeklySummaries` to
   `server/db/schema.ts` and a migration in `server/plugins/db.ts` (next free
   `version`, unique `name: "weekly-summaries-table"`):
   `id TEXT PRIMARY KEY, owner_email TEXT NOT NULL, org_id TEXT, week_start TEXT NOT NULL, week_end TEXT NOT NULL, dashboard_ids TEXT NOT NULL DEFAULT '[]', headline TEXT NOT NULL, body TEXT NOT NULL, coverage TEXT NOT NULL DEFAULT '{}', status TEXT NOT NULL, error TEXT, sent_at TEXT, opened_at TEXT, created_at TEXT NOT NULL DEFAULT (now()::text)`.
   Index `(owner_email, org_id, week_end)`. `body` is capped at 4,000
   characters by the action; it is the summary text, not a payload. Scope all
   reads by `owner_email` and `org_id`.

2. **Settings record.** Per-user settings under a new user-setting key
   `analytics-weekly-summary` (`getUserSetting` / `putUserSetting`, same as
   `actions/update-analytics-notification-preferences.ts:31-53`):
   `{ enabled: boolean, dashboardIds: string[] (max 3), dayOfWeek: 0-6, timeOfDay: "HH:mm", timezone: string, recipients: string[] (max 5, default [owner]), automationName: string }`.
   An absent record means "never decided" (5.1b depends on that difference).
   Keep the shape in `shared/weekly-summary.ts` so the client and server share
   it.

3. **`server/lib/weekly-summary.ts`.**
   - `collectWeeklySummaryFacts(ctx, { dashboardIds, weekEnd })`: for each
     dashboard (owner access via `getReportDashboard`), build the snapshot the
     way `collectReportSnapshot` does. When the dashboard has a date or
     date-range filter, run the panels twice through `fetchReportPanelData`:
     once for the last 7 days and once for the 7 days before, by overriding
     that filter. Without a date filter, run once and mark each panel
     `comparison: "unavailable"`. Return per panel: id, title, chart type,
     the current and previous values for single-value panels, or the first 20
     rows for others, and the panel status. Add `alerts`: incidents for the
     owner's rules in the window, newest first, capped at 20, with rule name
     and observed value versus threshold. Add `edits`: count of dashboard
     revisions in the window per dashboard. Add `coverage`:
     `{ panelsAttempted, panelsLoaded, failed: [{ dashboardId, panelId, reason }] }`.
     Bound total work with the same deadline pattern as
     `sendDashboardReportSubscription` and report timed-out panels as failed,
     never as empty.
   - `renderWeeklySummaryEmail({ headline, body, facts, links })`: reuse
     `renderEmail` from `@agent-native/core/server` (as `emails.ts` does). Put
     the agent's text first, then one line per dashboard with an "Open
     dashboard" link, then a "Some numbers didn't load" block listing
     `coverage.failed` when it is not empty. Links point at
     `/dashboards/<id>?ws=<summaryId>` (5.1b reads `ws`).
   - `recordWeeklySummary` and `listWeeklySummaries` (bounded, newest first,
     `limit` default 10, max 50).

4. **Actions** (`defineAction`, zod schemas, descriptions written per
   `writing-agent-instructions`):
   - `actions/get-weekly-summary-facts.ts`: `readOnly`, agent tool. Args
     `{ dashboardIds?: string[], weekEnd?: string }`; defaults to the saved
     settings. Returns the facts above. Fails with a typed error when the user
     has no dashboards configured.
   - `actions/send-weekly-summary.ts`: agent tool. Args
     `{ headline: string (max 120), body: string (max 4000), dashboardIds: string[], weekEnd: string }`.
     It re-reads coverage server-side for that week instead of trusting the
     caller, so a summary built on partial data always carries the "didn't
     load" block. It sends one email per recipient from settings with
     `sendEmail` and the new template id, records the row with
     `status: "sent" | "partial" | "failed"`, and returns
     `{ summaryId, status, recipients }`. Email failure is `status: "failed"`
     with the error and a thrown action error, not a success.
   - `actions/set-weekly-summary.ts`: enable, disable or reconfigure. Saves the
     settings record, then creates or updates one **personal** scheduled
     automation named `analytics-weekly-summary` using `defineAutomation` /
     `updateAutomation`, following `set-index-schedule.ts:44-95` (including
     the `ctx.appId` check). Cron from `dayOfWeek` and `timeOfDay`
     (`"0 9 * * 1"` default), `timezone` from settings. Disabling sets
     `enabled: false` on the automation; it never deletes it.
   - `actions/get-weekly-summary.ts`: `readOnly`. Returns settings, the
     automation's `lastRun`, `lastStatus`, `lastError` and `pausedReason`
     (from `listAutomationDefinitions`), and the last 5 summaries. A missing
     automation for an enabled setting is reported as
     `scheduleMissing: true`, not as healthy.

5. **Automation body** (constant in `server/lib/weekly-summary.ts`, written
   per `writing-agent-instructions`). Steps the agent follows:
   1. Call `get-weekly-summary-facts`.
   2. If `coverage.panelsLoaded` is 0, call `send-weekly-summary` with a
      headline saying the numbers could not be loaded and a body naming the
      reasons from `coverage.failed` and what to fix. Stop.
   3. Pick the two or three largest changes. For the largest one, the agent
      may run at most three follow-up reads with existing actions
      (`inspect-dashboard-panel`, `query-agent-native-analytics`, or the
      panel's own source action; not `query-dashboard-panel`, which is
      `agentTool: false`) to find a likely cause. Any cause is
      stated as likely, with the source named.
   4. Mention alerts that fired, by rule name and count.
   5. Write at most 200 words, plain sentences, no em dashes, numbers
      formatted for the reader, then call `send-weekly-summary`.
   6. Never report a change for a panel whose comparison is unavailable.

6. **Email template.** Register `analytics.weekly-summary` in
   `server/lib/emails.ts` with `defineTransactionalEmail`, a preview, trigger
   and recipient text. Subject: `Weekly summary: {headline}`.

7. **Skills.** Add a "Weekly summary" section to
   `.agents/skills/dashboard-ops/SKILL.md` (it already owns reports and
   alerts): the four actions, that the summary runs as the user's
   `analytics-weekly-summary` automation, that partial data is always called
   out, and that the agent uses `set-weekly-summary` when a user asks to turn
   it on, off, or change the day, time or dashboards. Add the actions to
   `AGENTS.md` if it lists actions by area.

8. **Application state.** Not applicable in this sub-unit. 5.1b adds the
   `weeklySummaryId` navigation field when a summary link is opened.

9. **UI.** None in this sub-unit; 5.1b adds the Settings row. The agent and
   the CLI can drive everything here.

10. **Changelog.** From `templates/analytics`:
    `agent-native changelog add "Get a weekly summary email, written by the agent, about what changed on your dashboards." --type added`
    (land it with 5.1b if 5.1a ships first without UI).

## 4. Copy

Email copy is server-rendered. Analytics has no server-side catalog for email
today (`server/lib/emails.ts` and `dashboard-report.ts` are English), so these
strings live in `server/lib/weekly-summary.ts` and are flagged in the PR as
English-only for the i18n backlog:

| Id | English |
| --- | --- |
| subject | Weekly summary: {{headline}} |
| preheader | What changed on your dashboards last week |
| open link | Open dashboard |
| partial heading | Some numbers didn't load |
| partial line | {{panel}} on {{dashboard}}: {{reason}} |
| footer | You get this because the weekly summary is on in Analytics settings. |
| manage link | Change or turn off |

The automation body is agent instructions, not UI copy.

No `app/i18n` change in 5.1a. If any string reaches the UI, add it to
`templates/analytics/app/i18n/{en-US,ar-SA,de-DE,es-ES,fr-FR,hi-IN,ja-JP,ko-KR,pt-BR,zh-CN,zh-TW}.ts`
together and run `pnpm guard:i18n-catalogs` and `pnpm guard:i18n-changed-copy`.

## 5. Tests

- `server/lib/weekly-summary.spec.ts`: facts for a dashboard with a
  date-range filter return current and previous values; a dashboard without
  one marks `comparison: "unavailable"`; a failed or timed-out panel lands in
  `coverage.failed` and never as a zero; alert incidents outside the window
  are excluded; the 20-row and 20-incident caps hold.
- `actions/send-weekly-summary.spec.ts`: partial coverage always renders the
  "didn't load" block even when the body omits it; email failure records
  `failed` and throws; body over 4,000 characters is rejected.
- `actions/set-weekly-summary.spec.ts`: enabling defines one personal
  automation with the right cron and timezone; enabling again updates it;
  disabling sets `enabled: false` and keeps the file; missing `ctx.appId`
  fails with `app_id_required`.
- Migration: the new table appears after migrations run (existing db migration
  spec pattern, `server/plugins/db.spec.ts`).
- No source-reading tests.

## 6. Verify

```bash
pnpm --filter analytics exec vitest --run server/lib/weekly-summary actions/send-weekly-summary actions/set-weekly-summary
pnpm guard:additive-migrations
pnpm --filter analytics dev
cd templates/analytics
pnpm action get-weekly-summary-facts --dashboardIds '["<a dashboard id with a date filter>"]'
pnpm action set-weekly-summary --enabled true --dashboardIds '["<id>"]' --dayOfWeek 1 --timeOfDay 09:00 --timezone UTC
pnpm action get-weekly-summary
pnpm action db-query --sql "SELECT id, status, sent_at FROM analytics_weekly_summaries ORDER BY created_at DESC LIMIT 5"
```

Then run the automation once with `manage-automations` `run-now` from the
agent chat (or Settings › Automations › Run now) and confirm a row with
`status = 'sent'` or `'partial'` and the email in the dev mail log. Break one
panel's credential and run again: the email must list it under "Some numbers
didn't load".

Not verifiable locally without a configured email provider and model
credential: real delivery and the agent-written text. With no model
credential the automation pauses with `missing_credentials`; confirm that
status shows in `get-weekly-summary`.

## 7. Dependencies

- Needs: none to build. Better numbers after 1.4 (fresh panels) and 1.5
  (plain-language failure reasons, which `coverage.failed` should reuse).
- Optional: 5.2 for Slack delivery through the automation `delivery` target.
- Soft: 4.2b adds "at most" and change-versus-baseline alert rules for growth
  teams without new incident columns. When it lands, each `alerts` fact
  should carry the rule's condition (read from the rule, not the incident) so
  the summary says "signups fell below 5 an hour" rather than "fired".
- Hotspots: `server/db/schema.ts` and `server/plugins/db.ts` (every unit that
  adds a table; take the next free migration version at rebase time, keep the
  unique `name`), `server/lib/emails.ts`, `server/lib/dashboard-report-render.ts`
  (1.4 and 1.5 change panel statuses), `.agents/skills/dashboard-ops/SKILL.md`.

## 8. Defaults for open questions

- **[decide] Cadence:** Monday 09:00 in the user's timezone.
- **[decide] Scope:** up to 3 dashboards per person; the summary is personal,
  not per dashboard.
- **[decide] Recipients:** the owner only by default, up to 5 addresses, the
  same cap as report subscriptions.
- **[decide] Comparison:** last 7 days versus the 7 before, only for
  dashboards with a date filter.
- **[decide] Explanation budget:** three follow-up reads, 200 words.
- **[decide] Storage:** summaries are kept in SQL for history and open rate.
  No retention job yet; add one if the table grows past a year of weekly rows
  per user.
- **[decide] It runs as an automation, not as a report subscription with a
  new frequency.** Report subscriptions stay daily and agent-free.

## 9. Do not

- No behavior changes outside this unit. Daily report subscriptions and
  alert evaluation are untouched.
- Additive-only schema: one new table, one index.
- No new `/api` routes for app data; everything is actions. The automation
  runner and the existing cron routes are reused.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials; panel reads use the
  owner's existing credential resolution.
- No `catch` or default that turns a failure into a normal-looking value: a
  failed panel is reported as failed, a failed send is `failed`, a missing
  schedule is `scheduleMissing`.
- No large payloads in SQL: summary text only, capped; no rendered HTML, chart
  images or raw rows stored.
- Do not call a model from the server lib directly; the agent writes the text
  inside the automation run.
