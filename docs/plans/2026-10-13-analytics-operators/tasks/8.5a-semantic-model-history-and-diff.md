# 8.5a Semantic model editing with a reviewable diff and history

Lane E (Holy-shit features). Size M. Gated: the Review changes step, the
History tab and the definition change card are new UI; build only after the
"Semantic layer: review changes" and "Semantic layer: history" screens in
`prototypes/analytics-operators/` are signed off. Where the signed-off
prototype differs from this brief, the prototype wins.

Depends on: 3.4b (built: chat-suggested definitions), 2.1b (built: generated
Postgres entries). Blocks: 8.5b (endorsement records into the same history).

Paths are relative to `templates/analytics/` unless they start with
`packages/`.

## 1. Goal

When an admin edits what "active account" means, they see the change as a
before and after per field before it saves, and the definition keeps a
history: who changed what, when, and from which chat, with Restore on any
earlier version. When the agent changes a definition, the chat shows the same
diff with Undo. Nobody loses a definition to an overwrite, and a buyer can
answer "who changed our churn definition last month?".

## 2. What the code does today

- Entries are org settings `data-dict-<id>` (user settings with
  `u:<email>:data-dict-` when there is no org)
  (`server/lib/data-dictionary-store.ts:12`, `:40-45`, `:95`).
- `save-data-dictionary-entry` overwrites the setting
  (`actions/save-data-dictionary-entry.ts:223-227`) after an admin check
  (`:140-142`, `requireAnalyticsAdminContext` in
  `server/lib/db-admin-connections.ts:85-111`). It keeps `createdAt` and chat
  provenance (`:154-158`, `:218`) and stamps `updatedAt` and `author`
  (`:219-220`). There is **no history**: each save replaces the previous
  value.
- Other writers: `propose-metric-definition` (insert-if-absent,
  `actions/propose-metric-definition.ts`, store `:127-182`),
  `withdraw-metric-definition` (deletes, `actions/withdraw-metric-definition.ts:69-72`),
  `delete-data-dictionary-entry` (`actions/delete-data-dictionary-entry.ts:30-34`,
  with its own `KEY_PREFIX` at `:14`), and Approve on the Semantic Layer page
  (`app/pages/SemanticLayer.tsx:299-324`, calling the save action).
- The editor is `DefinitionPanel.tsx` (draft model `:63-81`, approve switch
  `:379-388`, "Suggested by" with the chat link `:175-178`, `:287-301`,
  delete hidden for generated entries `:214`). Generated entries (`pg-*`,
  `index-*`) are `sourceIndex: true` and not editable as definitions.
- 3.4b's proposal shows a core record-change card with Undo through
  `withdraw-metric-definition` (`propose-metric-definition.ts:28-32`, `:103-110`).
- Highest migration on the integration branch is 173; 174 and 175 are
  reserved; 176 to 189 belong to 8.1 to 8.3; 190 to 192 to 8.4d, 8.4f2 and
  8.4g1.

## Plan corrections

- The writers each call the settings store directly (and delete has its own
  key prefix), so a history added to one action would miss the others. This
  unit routes every dictionary write through one store function that records
  the revision, and deletes the duplicate prefix.

## 3. Build

1. **Schema (additive), migration 193.** Table `data_dictionary_revisions`
   (`version: 193`, `name: "data-dictionary-revisions-table"`; 176 to 189 are
   8.1 to 8.3, 190 to 192 are 8.4d, 8.4f2, 8.4g1): `id TEXT PRIMARY KEY, entry_id TEXT NOT NULL, org_id TEXT, owner_email TEXT NOT NULL, change TEXT NOT NULL, entry TEXT, changed_by TEXT NOT NULL, thread_id TEXT, created_at TEXT NOT NULL`.
   `change` is `created | edited | approved | unapproved | deleted | restored | endorsed | unendorsed` (the last two for 8.5b). `entry` is the
   entry JSON after the change (null for `deleted`), capped at 32 KB with a
   typed error on save beyond it (entries are short text; the cap is a
   guard). Index `(org_id, entry_id, created_at)`. Keep 100 revisions per
   entry. Run `pnpm guard:additive-migrations`.
2. **One write path.** In `server/lib/data-dictionary-store.ts` add
   `writeDictionaryEntry(ctx, { entryId, next | null, change })` that writes
   the setting and the revision in one call (settings write first, then the
   revision; if the revision insert fails, the action fails loudly and says
   the definition saved without history, rather than returning success).
   Route `save-data-dictionary-entry`, `propose-metric-definition`,
   `withdraw-metric-definition`, `delete-data-dictionary-entry` and Approve
   through it; delete the duplicate `KEY_PREFIX`.
3. **Diff.** `shared/dictionary-diff.ts`: `diffDictionaryEntries(before, after)`
   returns changed fields with before and after text, and a word diff for
   `definition`, `knownGotchas` and `queryTemplate` (line diff for SQL).
   Reuse 8.4d's `lineDiff`/`wordDiff` from `shared/dashboard-review.ts` if
   8.4d has merged; otherwise add them here and let 8.4d import them.
4. **Actions.**
   - `list-data-dictionary-history` (read-only, GET): `{ entryId, limit? }`
     returns revisions newest first with `change`, `changedBy`, `createdAt`,
     `threadId` and the field diff against the previous revision.
   - `restore-data-dictionary-revision` (admin): `{ entryId, revisionId, expectedUpdatedAt }`
     writes that revision's entry back through `writeDictionaryEntry` with
     `change: "restored"`; a stale `expectedUpdatedAt` is a conflict error.
   - `save-data-dictionary-entry` gains `expectedUpdatedAt` (optional; when
     given and stale, a conflict error) and returns `{ entry, diff, undo: { revisionId } }`.
     Its chat UI uses the core record-change card (as 3.4b does) with the
     diff lines and Undo calling `restore-data-dictionary-revision`.
5. **UI (gated).**
   - DefinitionPanel: Save becomes Review changes when the draft differs:
     it swaps the form for a field-by-field diff (changed fields only, added
     text `bg-primary/10`, removed text struck through on `bg-muted`), with
     Back and a primary Save at the compact size. A conflict shows "Someone
     changed this definition while you were editing" with Reload.
   - A History tab in the definition sheet lists revisions (who, when, what
     changed, the chat link when there is one), each expandable to its diff,
     with Restore for admins (an `AlertDialog` confirm, since it overwrites
     the current version; not red, nothing is deleted: the current version
     stays in history).
6. **Application state.** The open definition and tab are already in the
   URL (`?definition=<id>`, `SemanticLayer.tsx:67-73`); add `&tab=history`.
   No new app-state key.
7. **Skills.** `.agents/skills/data-querying/SKILL.md` (definitions section):
   definitions have history; read it with `list-data-dictionary-history` to
   answer "who changed this"; pass `expectedUpdatedAt` when editing; undo is
   a restore.
8. **Changelog.** `agent-native changelog add "Definitions show what changed before you save, and keep a history you can restore" --type added`.

## 8. Defaults for open questions

- [Default] Generated entries (`pg-*`, `index-*`) get no history; they are
  regenerated from their source.
- [Default] Members still propose through chat (3.4b); only admins edit and
  restore.
- [Default] 100 revisions per entry.

## 9. Do not

- Do not write a dictionary setting anywhere except `writeDictionaryEntry`.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
