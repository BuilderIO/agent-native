## 1. Goal

An investigation finds eight accounts at churn risk. The user clicks
"Update CRM fields…" and asks to "set Health to At risk and add the
reason". Analytics drafts one update per company with the exact before and
after, and the card says "8 proposed updates" with the rows. Nothing
changes in HubSpot yet. The user chooses "Apply in HubSpot…", and the agent
applies the saved draft with one HubSpot request through the workspace's
HubSpot connection. The chat shows the approval card for that apply; only
Approve sends it. Analytics then reads the companies back and the card says which
updates landed. No separate CRM app is needed: the workspace's own CRM
connection in Integrations does the work.

## 2. What the code does today

- **Analytics reads HubSpot through the workspace connection.**
  `hubspot-records`, `hubspot-deals`, `hubspot-metrics` and
  `hubspot-pipelines` are `readOnly: true` (`actions/hubspot-records.ts:19`,
  `:50`), and `hubspot-records` points the agent at
  `provider-api-catalog`, `provider-api-docs` and `provider-api-request`
  for anything it does not model (`:22`).
- **The provider API substrate covers HubSpot and Salesforce** with the
  workspace connection (`workspaceProvider: "hubspot"` and `"salesforce"`
  in `packages/core/src/provider-api/index.ts`).
- **`provider-api-request` writes do not ask for approval.** Analytics'
  `actions/provider-api-request.ts` passes no `needsApproval`, so a POST,
  PUT, PATCH or DELETE runs as soon as the agent calls it. A core change to
  gate every provider write by default was considered and dropped on
  2026-10-14 because it reaches eight apps and would stop unattended
  automation writes. So this unit applies updates with its own action
  marked `needsApproval: true`, as `send-dashboard-report-now` is
  (`actions/send-dashboard-report-now.ts`).
- **The HubSpot connection asks only for read scopes** such as
  `crm.objects.companies.read` (`packages/core/src/connections/catalog.ts`,
  the `hubspot` entry). Updating a company needs
  `crm.objects.companies.write`. An OAuth connection missing a catalog
  scope reports `needs_reauth`
  (`packages/core/src/workspace-connections/store.ts:1001-1015`), which
  Data sources shows as "Reconnect needed" on HubSpot
  (`app/lib/data-source-status.ts:241`; HubSpot is a workspace OAuth source
  at `:117-124`).
- **The account map links HubSpot companies by id**: `provider` `hubspot`,
  `externalId`, `label`, `domain` (`server/db/schema.ts:1003-1030`). Its
  providers are `stripe`, `hubspot` and `product` (`:1015-1017`); no
  Salesforce link exists yet.

## Plan corrections

- The earlier draft of this brief handed updates to the hidden CRM
  template. The owner ruled that out: not every workspace will want another
  app. Updates go through the workspace's HubSpot (and later other CRM)
  connection, applied by a dedicated action that needs approval; its
  approval card is the confirm step.
- Writes need the write scope on the shared HubSpot connection. This
  follows the owner's Jira call (people who connect a tool want read and
  write access); existing OAuth connections reconnect once.

## 3. Build

1. **Kind.** Append `crm_update` (local, target the workspace CRM
   connection) to `INSIGHT_ACTION_KINDS`. `list-next-actions`: available
   when the source names at least one account with a HubSpot link and the
   workspace has a usable HubSpot connection for Analytics;
   `not_connected` otherwise.
2. **Scope (`packages/core`, minor changeset).** Add
   `crm.objects.companies.write` to the HubSpot OAuth scopes in
   `packages/core/src/connections/catalog.ts`. Existing OAuth connections
   then report `needs_reauth`: Dispatch's Integrations list shows "Needs
   reauth" and Data sources shows "Reconnect needed" with the workspace
   OAuth setup, where an admin reconnects once. Private app tokens keep
   whatever access their token has.
3. **Draft** `actions/draft-crm-updates.ts` (`defineAction`, audited with
   `recordInputs: false`): input `{ actionId, items: [{ accountId, field,
   value, reason }] }`, at most 25 items, one field per item. For each item
   it takes the HubSpot company id from the account map link (never agent
   text), checks `field` against HubSpot's company property metadata, and
   reads the current value with the read-only batch read through
   `executeProviderApiRequest` (provider `hubspot`, the workspace
   connection). It saves `{ accountId, name, hubspotCompanyId, field,
   before, value, reason }` per item in the record's artifact and sets
   `draft`. Accounts with no HubSpot link go to `skipped` on the record. It
   writes nothing to HubSpot. It also returns the one request that applies
   the draft: `{ provider: "hubspot", method: "POST", path:
   "/crm/v3/objects/companies/batch/update", body }`, built from the saved
   items only.
4. **Apply** `actions/apply-crm-updates.ts`: input `{ actionId }`,
   `needsApproval: true`. It rebuilds the batch request from the saved
   items (never from agent text) and sends it through the Analytics
   provider runtime on the workspace HubSpot connection. The approval card
   lists every company and value before Approve. Analytics adds no second
   confirm dialog. The agent instructions say to apply CRM updates only
   with this action, never with `provider-api-request`; a test pins
   `needsApproval: true`.
5. **Read back** `actions/verify-crm-updates.ts`: input `{ actionId }`.
   Reads the companies again with the batch read and compares each field
   with its proposed value. All match: `confirmed`, with `confirmed_by`
   and `confirmed_at`. Some match: stays `draft` and lists the rest as not
   applied. A read that fails is a typed error, never a match. A 401 or 403
   on the draft or the read returns `crm_scope_missing`.
6. **UI (gated).** "Update CRM fields…" joins the next-action row after
   "File an issue…". Card: "N proposed updates", rows of account name,
   field, before and after, a skipped line for accounts with no HubSpot
   link, "Apply in HubSpot…" (primary at the compact size; it sends the
   apply request to the agent with `sendToAgentChat`), and Discard. After
   the read back: "Updated N records in HubSpot", with an amber line for
   updates that did not apply. On `crm_scope_missing`, an amber line with
   "Reconnect HubSpot", which opens Data sources focused on HubSpot.
7. **Application state.** None new. `view-screen` already lists the
   notebook's insight actions (8.2a).
8. **Skills.** Extend `.agents/skills/insight-actions/SKILL.md`: CRM field
   changes are drafted with `draft-crm-updates`, applied only with the
   request it returns through `provider-api-request` after the user
   approves, then checked with `verify-crm-updates`; read HubSpot property
   names before drafting; never report an update as done before the read
   back; never edit the request body between draft and apply.
9. **Changelog.** `agent-native changelog add "Draft CRM field updates for the accounts an investigation found, and apply them to HubSpot after you approve" --type added`.

## 8. Defaults for open questions

- [Decided by the owner, 2026-10-14] No CRM app dependency. CRM updates go
  through the workspace's HubSpot and other CRM connections in
  Integrations, and every write waits for the user's approval.
- [Default] HubSpot only in v1, because the account map links only HubSpot
  companies. Salesforce and other CRM connections use the same path once
  the account map links them.
- [Default] The shared HubSpot connection asks for
  `crm.objects.companies.write`, following the owner's Jira call.
- [Default] One field per item, at most 25 items, one batch request per
  apply.

## 9. Do not

- Do not write to a CRM without the approval card, and do not change the
  request between the draft and the apply.
- Do not take CRM record ids from agent text.
- Do not report an update as applied before the read back confirms it.
- Do not read CRM credentials from `process.env`; use the workspace
  connection.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
