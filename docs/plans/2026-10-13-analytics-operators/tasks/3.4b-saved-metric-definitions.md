# 3.4b: Save a metric definition the first time the agent has to ask

Lane B. Size M. Split from 3.4; independent of 3.4a.

## 1. Goal

Teams without dbt get a shared glossary that fills itself in. When the agent
has to ask what a term means ("what counts as an active account?") and
someone answers, that answer is saved right away as a team definition marked
"Suggested in chat", the agent uses it from then on, and an org admin can
approve it on the Semantic Layer page. Nobody has to answer the same question
twice, and the definition is visible to the whole team instead of sitting in
one person's private memory.

## 2. What the code does today

- The agent is told to ask once with `ask-question` when a metric definition
  is ambiguous, and to skip asking when the dictionary already answers
  (`templates/analytics/.agents/skills/data-querying/SKILL.md:17`,
  `templates/analytics/.agents/skills/adhoc-analysis/SKILL.md:46`,
  `templates/analytics/.agents/skills/cross-source-analysis/SKILL.md:47-51`).
  Nothing tells it to save the answer.
- A background sweep 15 minutes after a run finds sentences such as "X means
  Y" in the user's messages (`templates/analytics/server/lib/analytics-memory-extractor.ts:267-281`)
  and saves them to the user's personal memory with `save-memory --scope personal`
  (`templates/analytics/server/lib/analytics-memory-capture.ts:332-356`;
  idle delay at `analytics-memory-capture.ts:16`). Teammates never see them,
  and the data dictionary is not touched.
- The dictionary is the team glossary: entries stored as org settings
  `data-dict-<id>` (`templates/analytics/actions/save-data-dictionary-entry.ts:22`,
  `save-data-dictionary-entry.ts:224-228`), injected into agent context with
  trust labels "approved/canonical", "unreviewed/human" or "ai-suggestion"
  (`templates/analytics/server/lib/data-dictionary-context.ts:35-55`).
- Only org owners and admins can write org entries
  (`save-data-dictionary-entry.ts:141-143`; same gate on delete,
  `templates/analytics/actions/delete-data-dictionary-entry.ts:27`), so the
  agent cannot save a definition a regular member gave it.
- The existing-entry read swallows every error as "not found"
  (`save-data-dictionary-entry.ts:153-160`), so a failed read overwrites the
  entry and drops its earlier fields and `createdAt`.
- Semantic Layer shows "Approved", "Suggested" (AI generated) or
  "Unreviewed" (`templates/analytics/app/pages/SemanticLayer.tsx:69-90`),
  checks the org role (`SemanticLayer.tsx:156`), and the definition panel has
  approved and AI-generated toggles (`templates/analytics/app/components/semantic-layer/DefinitionPanel.tsx:348-367`).
- The chat has a built-in record-change card for action results
  (`ActionChangeResult` with title, url and undo,
  `packages/core/src/action-ui.ts:24-52`).
- The repo has a semantic layer for dbt (`templates/analytics/actions/query-dbt-semantic-metric.ts`,
  `templates/analytics/server/lib/dbt-connection.ts`) used only when a dbt
  workspace connection exists (`templates/analytics/AGENTS.md:16`). This unit
  is for teams without it.

## Plan corrections

- The plan implies definitions are "saved" today in some form. They are,
  but privately, 15 minutes later, and only for "X means Y" phrasings. The
  shared dictionary needs a member-level "suggest" path because writes are
  admin-only.
- The swallowed read in `save-data-dictionary-entry.ts:153-160` is a data
  loss bug on the same path; fix it here because the new action shares the
  read.

## 3. Build

1. Store helper `templates/analytics/server/lib/data-dictionary-store.ts`:
   - `readDictionaryEntry(scope, id)` returns `{ status: "absent" }` or
     `{ status: "found", entry }` and throws on a read error.
   - `findDictionaryEntryByMetric(scope, metric)`: match by slug of the
     metric and by case-insensitive metric name across `data-dict-*` keys
     (reuse the listing `list-data-dictionary` already does).
   - Switch `save-data-dictionary-entry.ts` to `readDictionaryEntry` so a
     failed read fails the save instead of overwriting.
2. Action `templates/analytics/actions/propose-metric-definition.ts`
   (`defineAction`, any signed-in org member):
   - Args: `metric`, `definition` (the user's words, verbatim), optional
     `source`, `table`, `cuts`.
   - If an entry with the same id or metric name exists, return
     `{ status: "exists", entry }` and write nothing.
   - Otherwise write `{ approved: false, aiGenerated: false, origin: "chat", author: <email>, threadId, status: "active", createdAt, updatedAt }`
     plus the args. `threadId` comes from the request run context when
     present.
   - Return an `ActionChangeResult`: `verb: "created"`, `kind: "definition"`,
     `title: metric`, `url` to `/semantic-layer?definition=<id>`, `undo`
     calling `withdraw-metric-definition`.
3. Action `templates/analytics/actions/withdraw-metric-definition.ts`: the
   proposer or an org admin can delete an entry with `origin: "chat"` while
   it is unapproved; otherwise `fail(..., { errorCode: "not_withdrawable", statusCode: 403 })`.
4. Shared helper `proposeDictionaryDefinition()` used by the action and the
   capture sweep. In `templates/analytics/server/lib/analytics-memory-capture.ts`
   `processJob`, after extracting candidates, call it for each
   `kind: "metric"` candidate. It is a fallback for answers the agent did not
   save; `exists` is a normal outcome. Keep the personal memory write as is.
   Track `metric_definitions_proposed` in the existing capture outcome event.
5. Context: in `templates/analytics/server/lib/data-dictionary-context.ts`
   `renderEntry`, add `  - origin: defined by a teammate in chat, not yet approved`
   for `origin: "chat"` unapproved entries (trust label stays
   "unreviewed/human").
6. UI (`templates/analytics/app/pages/SemanticLayer.tsx`,
   `templates/analytics/app/components/semantic-layer/DefinitionPanel.tsx`):
   - Status "Suggested in chat" for unapproved `origin: "chat"` entries
     (amber like "Suggested").
   - In the definition panel, a muted provenance line "Suggested by {{name}}
     in chat" with an "Open conversation" link to the thread when
     `threadId` is present. Render nothing when absent.
   - For org admins, an outline "Approve" button in the panel header for
     unapproved entries; it saves through `save-data-dictionary-entry` with
     `approved: true`, optimistic with rollback and a toast on failure.
   - Support `?definition=<id>` to open that entry (the chat card links
     here). Keep it in the existing navigation state for the page.
7. Skills and instructions:
   - `templates/analytics/.agents/skills/data-querying/SKILL.md` step 3,
     `adhoc-analysis/SKILL.md:46`, `cross-source-analysis/SKILL.md:47-51`:
     "Before asking what a term means, check the injected dictionary and
     `list-data-dictionary`. When you ask and the user defines it, call
     `propose-metric-definition` with their words before you query, then use
     that definition and say it was saved."
   - `templates/analytics/AGENTS.md`: one line in "Data questions".
   Read `writing-agent-instructions` before editing these.
8. Application state: no new keys. The Semantic Layer selection already
   lives in `navigation` (`view: "semantic-layer"`); add the selected
   definition id if the page does not already write it.
9. Changelog: `agent-native changelog add "When the agent asks what a term means, your answer is saved as a team definition you can approve on the Semantic Layer page." --type added`.

## 8. Defaults for open questions

- DECISION: any org member can suggest; only admins approve. Suggestions are
  used by the agent with the "unreviewed/human" trust label.
- DECISION: the first answer wins; a later different answer for the same
  term returns `exists` and the agent tells the user an existing definition
  was used, with a link to edit it.
- DECISION: the capture sweep also proposes definitions, as a fallback.
- DECISION: no LLM rewriting; the user's words are stored verbatim.

## 9. Do not

- No behavior changes outside this unit besides the read-error fix.
- Additive-only schema; entries stay in settings, new fields are optional.
- No new `/api` routes for app data; use actions.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value:
  `absent`, `exists` and a read error are different outcomes.
- No large payloads in SQL; a definition is short text.
- Do not let a suggestion overwrite an approved or human-edited entry.
