# 1.9 Dashboard header: Share first, an Add menu, insert in place, views in the filter bar, a grouped ⋯ menu

Lane A (Reliability). Size L. **Gated: build only after the dashboard header
screens in `prototypes/analytics-operators/` are signed off** ("Dashboard:
share with people", "Dashboard: share with agents", "Dashboard: add menu",
"Dashboard: insert between rows", "Dashboard: actions menu", "Dashboard:
history", "Filter bar: view picker", "Filter bar: edited view", "Filter bar:
save as new view"). Depends on no unit; merges after 1.3b and 1.7b, which
touch the same header and share surfaces.

Paths are relative to `templates/analytics/` unless they start with
`packages/`, `prototypes/` or `docs/`.

## 1. Goal

The dashboard header reads as one primary action and a few quiet controls,
all at the compact header size (32px, 12px text, 14px icons). Share is the
primary action on the page: the toolkit split control Clips uses, a solid
primary Share button joined to a quick copy link button in the same primary
fill, opening People and Agents tabs, drawn at the compact size with no
user-plus icon. Add is the secondary action: a secondary "+ Add" button with a
chevron, immediately left of Share, opening a short text-only menu (Chart…,
SQL query…, Section) that adds to the end of the dashboard. A thin insert bar
between dashboard rows opens the same menu and inserts at that gap (New).
Views leave the header for the filter bar, where a view is a saved set of
filter values: one View picker and one save path. The ⋯ menu holds only
actions, in three groups, with no read-only metadata block.

The owner's first report: the header "feels rather busy", the primary action
is Share and should reuse "the share affordance from Clips with the split
button and share with people & agents dialog", Add panel "likely an icon
button would suffice", and the ⋯ menu "has a lot of stuff packed into it". On
the second prototype (2026-10-14) the owner asked whether a bare "+" was clear
and whether Add "adds or inserts into the existing dashboard" (the sidebar's
"+" now means New dashboard, so a header "+" was ambiguous), found the Share
button's size "pretty enormous" against the other header controls while
keeping it the primary variant, made Add a secondary button beside Share, and
moved Views into the filter bar. On the share popover (2026-10-14) the owner
asked "why does the share dialog feel like it was made for giants and doesn't
follow the density or sizing of the rest of our apps?" and why the People tab
repeats "copy share link" when the split button already copies it. The owner
decided the fix is toolkit-wide, "all apps should match": the share panel
moves to the compact density (24px controls, 12/16 text, 28px rows) in every
app that renders it, and the People tab drops its Share link row whenever the
split button's copy segment is there.

Final order, left to right: title and certified shield; then the presence bar
(when the agent is active), Add, the Share split control, ⋯, and the agent
toggle the layout header owns.

**Where Add puts a panel (`index.tsx`, `dashboard-layout.ts`, `actions/mutate-dashboard.ts`)**

- `handleSavePanel` (`index.tsx:1502-1513`) replaces a panel by id or appends
  it (`[...dashboard.panels, panel]`) and saves the whole config through
  `persistThrow`, which calls `update-dashboard` (`index.tsx:606`). There is no
  way to place a new panel anywhere but the end from the UI.
- The Describe tab sends the agent a request whose context tells it to call
  `mutate-dashboard` with `{op:"insertPanel", …, position:"bottom"}`
  (`PanelEditorDialog.tsx:373-407`).
- `mutate-dashboard`'s placement targets are `position`, `index`,
  `beforePanelId`, `afterPanelId`, `nextToPanelId`, `rowNumber` and
  `rowPosition` (`"start" | "end"`) (`mutate-dashboard.ts:63-71`, resolved in
  `dashboard-mutation-api.ts:497-525`). `rowNumber` puts the panel inside an
  existing visible row, and an array `index` or `beforePanelId` is repacked by
  width (`buildDashboardRows`, `dashboard-layout.ts:170-207`), so none of
  them makes the panel its own row between two visible rows.
- Drag to reorder already has that placement: a row drop slot
  (`DashboardDropSlot` `{ type: "row", groupKey, rowIndex }`,
  `dashboard-layout.ts:21-32`) and `movePanelToDropSlot`'s row branch
  (`:434-497`), which splices a one-panel row into the group and flattens.
  The grid renders a row slot before the first row and after every row of
  each group (`renderRowDropLine`, `index.tsx:2633-2704`). Each is a 24px
  in-flow `dashboard-row-drop-slot` with `-0.25rem` block margins, so it fills
  the 16px row gap (`app/global.css:563-576`), and it is `aria-hidden`
  (`index.tsx:242-252`). The server builds the same rows for
  `get-sql-dashboard`'s `layout.groups[].rows[].rowNumber`
  (`server/lib/agent-readable-resource-context.ts:4,17-33`, importing
  `dashboard-layout.ts`).

**Views (`ViewsMenu.tsx`, `DashboardFilterBar.tsx`, `Sidebar.tsx`, the view actions)**

- A view is a saved set of `f_*` filter params (`DashboardView`,
  `app/hooks/use-dashboard-views.ts:6-13`). `ViewsMenu` in the header
  (`index.tsx:2038-2040`) is a ghost `Button size="sm"` with `text-xs`, an
  `IconLayoutGrid`, the active view's name or "Views", and a chevron, with the
  tooltip "Saved views" (`ViewsMenu.tsx:177-189`). The active view is the
  `?view` param's view only while its filters match, else any view whose
  filters match (`:113-120`), so a view whose filters were changed shows as
  "Views": there is no edited state. The menu lists "Saved views", each view
  with a Default badge and a hover trash button, then "Save current view",
  which opens a "Save view" dialog with a name field, "Set as default for
  this dashboard" and the no-active-filters note (`:190-336`).
- `DashboardFilterBar` has a second save path: when filters are active, a
  hover-revealed ghost "Save view" opens a "Save as View" dialog with the same
  fields, and "Clear all" removes every `f_*` param and `view`
  (`DashboardFilterBar.tsx:106-193`, `:247-263`, `:287-340`). The bar renders
  only when the dashboard has filters (`index.tsx:2537-2544`).
- Both paths make the id by slugging the name (`ViewsMenu.tsx:58-66`,
  `index.tsx:1959-1972`), and `save-dashboard-view` upserts by id, so saving
  a name that already exists silently overwrites that view.
- `save-dashboard-view` (`actions/save-dashboard-view.ts`) can update an
  existing view: with an `id` of a view on this dashboard,
  `saveDashboardView` updates its name and filters, and with `isDefault: true`
  clears the old default and sets this one
  (`server/lib/dashboards-store.ts:3407-3470`). Two gaps: `filters` falls
  back to `{}` (`args.filters ?? {}`, `save-dashboard-view.ts:33`), so an
  update that leaves filters out erases them; and `isDefault: false` never
  clears a default. `list-dashboard-views`, `save-dashboard-view` and
  `delete-dashboard-view` are all `agentTool: false`: the agent cannot call
  them today.
- The default view is applied on load (`resolveDashboardFilterRestoreStep`,
  `index.tsx:1060-1080`). The sidebar lists a dashboard's views under it as
  links to `?<filters>&view=<id>`, active by the `view` param, with delete
  (`app/components/layout/Sidebar.tsx:979-1030`). `view-screen` reports the
  `f_*` params as `activeFilters` (`actions/view-screen.ts:180-184`) but not
  `view`. The agent changes filters with the framework's `set-search-params`
  (`actions/navigate.ts:53`).
