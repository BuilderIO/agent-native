# 4.1d Retention and cohort panels

Lane D (Growth). Size M. Gated: build the UI only after the 4.1a prototype is
signed off. The compiler part (steps 2 to 4) can start before sign-off.

## 1. Goal

A growth lead adds a Retention panel that answers "of the people who signed up
each week, how many came back in week 1, 2, 3 and so on". They pick a first
event and a return event (or "Any event"), a period and how many periods. The
panel shows a cohort grid: one row per cohort with its size, one column per
period, each cell shaded by the share that came back. Periods that have not
finished yet are blank, never 0%. The agent builds the same panel through the
same definition.

## 2. What the code does today

- There is no retention chart type. Chart types are
  `app/pages/adhoc/sql-dashboard/types.ts:10-23`. The closest renderer is the
  heatmap (`app/components/dashboard/SqlChart.tsx:2581-2688`), which shades
  each cell by its z-score within the column using raw `hsl()` colors
  (`:2633-2642`). For retention that shading is misleading: a 40% cell can
  look red because the column average is higher.
- Retention panels today are hand-written SQL with many variants: the
  canonical `retention-over-time` panel has eight legacy SQL strings kept for
  repair (`server/lib/first-party-metric-catalog.ts:768-787`) plus a
  separately maintained BigQuery version
  (`server/lib/canonical-first-party-dashboard-repair.ts:373`). The catalog
  hard-codes a minimum cohort size of 5 (`first-party-metric-catalog.ts:143`).
- First-party tables include the per-day active-user rollup
  `analytics_user_days` (`server/db/schema.ts:628-635`). On the PostgreSQL
  sink it is written at ingest (`server/lib/first-party-analytics.ts:952`). On
  the BigQuery sink it maps to a `_user_days` relation
  (`server/lib/first-party-analytics-backend.ts:264-275`, `:1298-1305`), which
  the setup script defines as a view over the raw events
  (`scripts/first-party-analytics-bigquery.sql:90`), so it saves nothing
  there.
- Chart types are also listed in `app/routes/chart.tsx:13-23`,
  `app/components/AnalyticsReviewArtifactPreview.tsx:39-52`, the agent prompts
  at `app/components/layout/NewDashboardDialog.tsx:26` and
  `app/pages/adhoc/sql-dashboard/PanelEditorDialog.tsx:392`, and the editor
  list `PanelEditorDialog.tsx:53-66`. Email reports render non-chart panels
  as HTML (`server/lib/dashboard-report-render.ts:1088-1096`).
- 4.1b provides `shared/growth-panels.ts` (definition union, compiler,
  `panelRunnableSql`), the write-boundary compile in
  `normalizeDashboardConfig`, the `panel_growth_*` rules and
  `list-analytics-event-names`.

## 3. Build

1. Prototype gate for steps 5 to 7: confirm the 4.1a retention screens are
   signed off.
2. Definition (`shared/growth-panels.ts`): add `retentionDefinitionSchema` to
   the union: `{ kind: "retention", version: 1, startEvent: { eventName:
   string | null, filters? }, returnEvent: { eventName: string | null,
   filters? }, period: "day" | "week", periods: 1..12 (default 8 weeks or 14
   days), countBy: "user" }`. `eventName: null` means any event.
3. Compiler: `compileGrowthPanelSql` for retention emits rows `cohort` (period
   start date `YYYY-MM-DD`), `cohort_size`, `period` (1 to `periods`),
   `retained` and `retained_pct`:
   - Cohort: each person's first start event inside the dashboard range,
     truncated to the period. Every CTE that reads `analytics_events` carries
     its own `dashboardTimeRangeFilter("event_date")` bound.
   - Period k: the person did the return event on any day in
     `[cohort_start + k * length, cohort_start + (k + 1) * length)`.
   - Emit every (cohort, period) pair, with `retained = 0` when nobody came
     back. When the period's end is after the last day the range can contain
     (`min(today, range end)`), emit `retained` and `retained_pct` as NULL.
     NULL means "not measurable yet"; 0 means "nobody came back". The renderer
     and the agent depend on that difference.
   - When both events are null and the sink is PostgreSQL, read
     `analytics_user_days`; otherwise read `analytics_events`. The compiler
     cannot know the sink, so default to `analytics_events` with an
     `event_name` predicate when an event is set, and `analytics_user_days`
     only for "any event" on both sides (on BigQuery that is a view, which is
     correct, just not cheaper).
   - Same translator constraints, literal helper and tests as 4.1b.
4. Validation (`collectDashboardConfigIssues`, `actions/update-dashboard.ts:259`):
   a retention definition requires `chartType: "retention"`; the
   `panel_growth_time_filter` rule applies. Register `growth` for
   `["funnel", "retention"]` in `PANEL_CONFIG_KEYS`
   (`shared/panel-render-contract.ts:45-68`).
5. Chart type: add `"retention"` to `PANEL_CHART_TYPES` (`types.ts:10-23`),
   `app/routes/chart.tsx:13-23`, `AnalyticsReviewArtifactPreview.tsx:39-52`,
   the editor list (`PanelEditorDialog.tsx:53-66`), and the two agent prompts
   (`NewDashboardDialog.tsx:26`, `PanelEditorDialog.tsx:392`). In the render
   plan (`shared/panel-render-contract.ts:690-749`) add a `retention` plan:
   cohorts, periods and cells; the panel is empty only when there are no
   cohorts.
6. Renderer: `RetentionRenderer` in a new
   `app/components/dashboard/RetentionGrid.tsx`, called from `SqlChart.tsx`
   next to the heatmap branch (`:1433-1437`). A `table` with a sticky first
   column (cohort date via `useFormatters()`), a People column, then
   Day N or Week N columns. Cell text is the percent (`useFormatters()`),
   background is the primary token mixed with transparent in proportion to
   the percent (CSS variable only, no raw colors; run `guard:no-raw-colors`).
   NULL cells are blank with a `Tooltip` (`retentionIncomplete`). Each cell
   has an `aria-label` (`retentionCellLabel`). Use logical CSS properties so
   it works right to left.
7. Editor: in `PanelEditorDialog.tsx`, for `chartType === "retention"` and
   First-party Analytics, show a `RetentionEditor` (new file next to
   `FunnelStepsEditor.tsx` from 4.1c, reusing its event combobox): First
   event (with an Any event option), Return event (with Any event), Period
   (Days, Weeks) and Number of periods. Same time range filter handling and
   Edit as SQL dialog as 4.1c.
8. Email reports: render retention panels as HTML through the heatmap path in
   `server/lib/dashboard-report-render.ts:1088-1096` with blank NULL cells, or
   a small `renderRetentionHtml` beside `renderHeatmapHtml` if the heatmap
   shading cannot be reused without the z-score.
9. Skills: in `.agents/skills/dashboard-management/SKILL.md` (the growth
   section from 4.1b, and the retention guidance at `:544-560`), add retention
   definitions with one example and the NULL versus 0 rule. In
   `.agents/skills/data-querying/SKILL.md:26` note that saved retention panels
   should use the definition.
10. Application state: `growthKind: "retention"` in the panel selection
    (`app/hooks/use-dashboard-chat-context.ts:163-176`, added in 4.1b).
11. Changelog: `agent-native changelog add "Retention panels show cohorts by day or week from first-party events" --type added`.

## 8. Defaults for open questions

- [Default, reviewer can change] A cohort is a person's first start event
  inside the dashboard range, not their first event ever. "First ever" needs
  an unbounded history scan.
- [Default] Columns start at period 1; the cohort size column stands in for
  period 0.
- [Default] No minimum cohort size; small cohorts show like any other. The
  canonical panel's threshold of 5 stays where it is.
- [Default] A new `retention` chart type instead of reusing `heatmap`, because
  the heatmap's per-column z-score shading would misread retention.
- [Default] Count by person only in v1.
