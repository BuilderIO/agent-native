# 1.1b Click to edit tables: resize and drag to reorder columns

Lane A (Reliability). Size M. **Gated:** build only after the resize and
reorder interaction in the prototype (`prototypes/analytics-operators/`) is
signed off. Where the signed-off prototype differs from this brief, the
prototype wins.

Second half of the plan's PR 1.1. It reuses everything 1.1a builds: the
`panel-edits.ts` helpers, `applyPanelEdit` and the `mutate-dashboard` write
path.

## 1. Goal

A person editing a table panel can drag a column's right edge to make it
wider or narrower, double-click that edge to reset it, and drag a column
header to a new position. The new widths and order show at once, save
through `mutate-dashboard`, survive reload and apply for everyone who opens
the dashboard. Keyboard users can do both without a mouse.

## 2. What the code does today

All paths relative to `templates/analytics/`.

- `TableColumnConfig` (`app/pages/adhoc/sql-dashboard/types.ts:58-64`) has no
  width. Column order is the order of `config.columns`, or result order when
  it is empty (`app/components/dashboard/SqlChart.tsx:1766-1775`).
- The table is `<table className="w-full text-sm">` inside
  `relative overflow-x-auto` (`SqlChart.tsx:1860-1861`); header cells are
  `whitespace-nowrap` with no width (`:1869-1906`). Column widths come from
  content only. There is no resize handle and no reorder affordance.
- The heatmap renderer has its own table (`SqlChart.tsx:2646-2654`), which
  this unit does not touch.
- The dashboard page already wraps the grid in a dnd-kit `DndContext` with a
  `PointerSensor` and a 5px activation distance (`app/pages/adhoc/sql-dashboard/index.tsx:1539-1541`,
  `:2567`). Panels are dragged by an explicit handle
  (`app/pages/adhoc/sql-dashboard/SqlChartCard.tsx:89-129`). `@dnd-kit/core`,
  `@dnd-kit/sortable` and `@dnd-kit/utilities` are dependencies
  (`package.json:27-29`).
- After 1.1a, column moves exist only as Move left and Move right menu items.

**Plan corrections:** none beyond the 1.1a corrections. The plan lists resize
and reorder inside PR 1.1; they are split out here because they add a width
field, pointer interactions, a nested drag context and their own
accessibility work.

## 3. Build

1. **Type.** Add `width?: number` (CSS pixels) to `TableColumnConfig` in
   `types.ts`. Extend the `config.columns` shape check added in 1.1a in
   `shared/panel-render-contract.ts`: `width` is an integer from 64 to 640
   and a multiple of 8.
2. **Pure helpers** in `app/pages/adhoc/sql-dashboard/panel-edits.ts`:
   `setColumnWidth(panel, rowKeys, key, width | null)` (null removes the
   width) and `reorderColumn(panel, rowKeys, key, toIndex)`. Both snap and
   clamp with one `clampColumnWidth` function, and each emits one
   `updatePanelPath` op with path `columns`, like 1.1a.
3. **Render widths.** In `TableRenderer`, when any visible column has a
   width, switch the table to `table-layout: fixed` with a `<colgroup>` whose
   `<col>` elements carry each width (columns without one get `auto`). Cells
   then truncate with an ellipsis and a `title` with the full value. Without
   widths, render exactly as today.
4. **Resize handle** in `app/components/dashboard/TableColumnHeader.tsx`
   (created in 1.1a): an 8px hit area on the header's inline-end edge,
   `cursor-col-resize`, visible as a 1px border token on hover and focus.
   Pointer drag updates a local preview width every frame and calls
   `onPanelEdit(setColumnWidth(...))` once on pointer up. Double-click resets
   (width null). The handle is a focusable `role="separator"` with
   `aria-orientation="vertical"`, `aria-valuenow` and a label; Left and Right
   arrow keys change the width by 8px and commit on key up, Home resets. Use
   logical positioning (`end-0`) so it sits on the correct edge in RTL.
   `pointerdown` stops propagation so it never starts a panel drag or a sort.
5. **Drag to reorder.** Wrap the header row in its own `DndContext` with
   `@dnd-kit/sortable` (`SortableContext`, `horizontalListSortingStrategy`)
   and a `PointerSensor` with the same 5px distance, so a plain click still
   sorts. The nested context keeps column drags from reaching the dashboard's
   panel drag. Use `KeyboardSensor` with `sortableKeyboardCoordinates` for
   keyboard reorder. On drop, call `onPanelEdit(reorderColumn(...))`. Pass
   localized `accessibility.announcements` and `screenReaderInstructions`;
   dnd-kit's defaults are English.
6. **Editors only.** Viewers get neither the handle nor drag. Section and
   extension panels are unaffected.
7. **Application state.** No new key. A resize or reorder publishes the same
   `selected-object` column selection 1.1a adds (call `onSelectColumn` on
   pointer down), so "this column" stays correct after a drag.
8. **Skills.** Add one line to the "Table column edits" subsection 1.1a adds
   in `.agents/skills/dashboard-management/SKILL.md`: `columns[].width` is
   pixels, 64 to 640 in steps of 8, and order is array order. Read
   `.agents/skills/writing-agent-instructions` first.
9. **Email reports.** `server/lib/dashboard-report-render.ts` already follows
   array order. Ignore `width` there (email clients size tables themselves);
   say so in a one-line comment, since a later change might try to add it.
10. **Changelog.** `agent-native changelog add "Resize and drag to reorder table columns" --type added`
    from `templates/analytics`.

Four-area check: UI (steps 3 to 6), actions (none new; `mutate-dashboard`
from 1.1a already accepts the write), skills (step 8), application state
(step 7).

## 8. Defaults for open questions

Reviewer-changeable decisions:

- **D1. Widths are pixels, 64 to 640, in 8px steps.** Matches the 8pt grid.
- **D2. Widths are shared, not per viewer.** They are panel config, like
  format.
- **D3. Fixed layout only when a width is set**, so untouched tables keep
  today's content-sized columns.
- **D4. Email reports ignore widths.**
- **D5. Resize commits once on release**, not on every pointer move, so one
  drag is one revision.

## 9. Do not

- No behavior changes outside this unit: panel drag, sort and the heatmap
  table stay as they are.
- Schema changes are additive only; this unit adds no table or column.
- No new `/api` routes for app data; use actions.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value: a
  failed save rolls the width or order back and says so.
- No large payloads in SQL.
- No hand-built absolute-positioned popovers; the handle is a plain element,
  menus stay shadcn.
