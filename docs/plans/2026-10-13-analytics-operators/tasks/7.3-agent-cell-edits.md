# 7.3 Agent cell edits

Lane C (Notebook). Size M. Not gated: no new surface; it adds context to the
existing panel selection and changes agent instructions. Depends on 7.1a and
7.1b (and on 7.2b for chained-cell edits).

Paths are relative to `templates/analytics/` unless they start with
`packages/` or `docs/`.

## 1. Goal

A user can say "add a text cell explaining this", "move the chart above the
table" or "make cell 3 read from cell 2" and the agent does it through the same
actions the UI uses. The agent reports a cell edit as done only when the
rendered result checks out, and says plainly when it could not check (timeout,
missing connection, data program not run). Selecting a cell tells the agent
which cell, by number and id.

## 2. What the code does today

- `mutate-dashboard` already inserts, updates, duplicates, moves and removes
  panels by id in one atomic save (`actions/mutate-dashboard.ts:106-155`),
  validates SQL for the panels it touched (`:376-...`), and gates agent
  callers on `verifyPanelWrite` (`server/lib/dashboard-panel-verification.ts:959`).
  Statuses are `ok`, `empty`, `missing-columns`, `query-error`,
  `render-error`, `unverified` with notes `timeout`, `missing_credential`,
  `skipped:program`, `too_expensive`, `not_executed:over_budget` (`:40-53`).
  Section and extension panels are checked as `visualOnly` (`:82`, `:497`).
- Placement targets: `position`, `index`, `beforePanelId`, `afterPanelId`,
  and the grid-only `nextToPanelId` and `rowNumber`/`rowPosition`
  (`actions/dashboard-mutation-api.ts:493-526`). `isVisualPlacementTarget`
  (`:528-532`) is the one place that tells the grid-only targets apart.
- `insertPanel` requires an integer `width` 1 to 6
  (`actions/mutate-dashboard.ts:86-93`).
- The agent guide makes `verified: true` the only proof a dashboard edit is
  done (`AGENTS.md`, "Data questions", first bullet).
- Clicking a panel writes `selected-object` with `type: "dashboard-panel"`,
  dashboard id and kind, panel id, title, chart type and source, and stages a
  chat context chip with the same lines
  (`app/hooks/use-dashboard-chat-context.ts:146-188`). It has no position or
  layout field.
- `view-screen` returns the dashboard context and `selectedObject`
  (`actions/view-screen.ts:170-213`).
- `get-sql-dashboard` returns compact summaries and, with `panelIds`, full SQL
  for chosen panels (`actions/get-sql-dashboard.ts:25`).

## Plan corrections

- The plan implies new cell-edit actions. They are not needed: cells are
  panels, so `mutate-dashboard` is the cell-edit action and already has the
  rendered-result check. This unit closes the gaps: grid-only targets, cell
  numbers in context, text and chained cells in verification, and agent
  instructions. Adding parallel `add-cell` / `move-cell` actions would create a
  second write path the UI does not use.

## 3. Build

1. **Grid-only targets on notebooks.** In `applyDashboardMutationOperations`,
   where a target is resolved and `isVisualPlacementTarget` is checked, throw
   when the config's `layout` is `notebook`: "Notebooks are one column. Use
   index, beforePanelId, afterPanelId or position." One check at that
   boundary; not per operation.
2. **Width.** Keep the `width` requirement. The notebooks skill tells the
   agent to pass `width: 1`. No server default for notebooks.
3. **Verification for new cell kinds.** Confirm (and test) that `text` cells
   verify as `visualOnly` through 7.1a's `panelRunsQuery`, that their
   `config.markdown` key passes the config-key check, and that `cells` panels
   (7.2b) execute with their inputs. `describeVisualOnly`
   (`dashboard-panel-verification.ts:1083-1091`) should say "text" for text
   cells, so the agent reports "the text changed; there was no data to check"
   rather than claiming a data check.
4. **Selection context.** In `use-dashboard-chat-context.ts`, add
   `dashboardLayout` and, for notebooks, `cellNumber` (1-based position) to the
   `selected-object` value and a context line "Cell n of m". For `cells`
   panels add "Reads from: <ids>". Update the `SelectedDashboardObject`
   consumers in `actions/view-screen.ts` and
   `actions/clear-selected-dashboard-object.ts` only if they validate shape.
5. **Screen context.** 7.1a adds the ordered cell list to the dashboard agent
   context. Confirm `view-screen` on a notebook returns it within budget, so
   "cell 3" resolves to an id without an extra call.
6. **Agent instructions.** Read `.agents/skills/writing-agent-instructions`.
   Extend `.agents/skills/notebooks/SKILL.md` with an "Editing cells" section:
   - Resolve "cell n" from `view-screen` or `selectedObject.cellNumber`, then
     read the cell with `get-sql-dashboard` `panelIds`.
   - Edit with `mutate-dashboard`; batch related cell edits in one call.
   - Ordering ops: `movePanels` with `index`, `beforePanelId`,
     `afterPanelId` or `position`; never row targets.
   - Text cells: `insertPanel` with `chartType: "text"`, `width: 1`,
     `config.markdown`; no `sql` or `source`.
   - Chained cells: the `cells` descriptor; inputs must be above.
   - Done means `verified: true`. On `unverified`, tell the user which cell
     was not checked and why, in plain words, and do not say it worked.
   Add the notebook case to the first "Data questions" bullet in `AGENTS.md`
   in a few words ("dashboards and notebooks"), not a new paragraph.
7. **Action description.** Add one sentence to the `mutate-dashboard`
   `operationsHelp` (`actions/mutate-dashboard.ts:208-210`): "In a notebook,
   panels are cells in order; use index, beforePanelId or afterPanelId." Keep
   the tool schema compact.
8. **UI.** No new controls. The existing panel click selection now carries the
   cell number; 7.1b's cell toolbar already shows the cell.
9. **Application state.** `selected-object` gains `dashboardLayout` and
   `cellNumber` (described above). No new keys.
10. **Evals.** `evals/` has no dashboard edit cases today (no file references
    `mutate-dashboard`), so this unit adds none; the unit tests in section 5
    carry the contract.

## 4. Copy

No new UI strings. The context lines in step 4 are agent-facing and stay in
English (they are prompt text, not UI). The error in step 1 is agent-facing;
keep it plain because the agent may relay it.

## 5. Tests

- `actions/mutate-dashboard.spec.ts`: on a notebook config, `nextToPanelId`
  and `rowNumber` throw the step 1 message; `index` and `beforePanelId` move
  cells; on a grid config, behavior is unchanged.
- `actions/compose-dashboard-verified-write.spec.ts` or
  `update-dashboard-verified-write.spec.ts` pattern: inserting a text cell via
  `mutate-dashboard` as an agent caller returns `verified: true` with the text
  cell listed as visual only; a `cells` panel whose input times out returns
  `verified: false` with `unverified[]` naming the cell.
- `app/hooks/use-dashboard-chat-context.spec.tsx` (exists): the
  selection for a notebook cell carries `cellNumber` and `dashboardLayout`.

No source-reading tests.

## 6. Verify

```bash
cd templates/analytics
pnpm exec vitest --run actions/mutate-dashboard.spec.ts actions/update-dashboard-verified-write.spec.ts app/hooks
pnpm typecheck
pnpm --filter analytics dev

pnpm action mutate-dashboard --dashboardId <notebook id> --operations '[{"op":"movePanels","panelIds":["<chart id>"],"nextToPanelId":"<cell id>"}]'   # expect the one-column error
```

Then in the browser with the agent sidebar open on a notebook: click cell 2,
ask "add a text cell under this saying what it shows", and confirm the cell
appears under cell 2 and the reply cites `verified: true` semantics (no claim
of a data check for text). Ask "move the chart to the top" and confirm order.
Close tabs and stop the server.

Cannot be verified locally: agent behavior against production model latency;
use the local agent.

## 8. Defaults for open questions

- **[Default] No new cell actions; `mutate-dashboard` is the cell API.**
- **[Default] Grid-only placement targets are errors on notebooks**, not
  silently translated.
- **[Default] `width: 1` stays required**, taught by the skill.
- **[Default] Cell numbers are 1-based and computed at selection time**, never
  stored.

## 9. Do not

- No behavior changes outside this unit; grid dashboard edits behave as before.
- Additive-only schema (none needed).
- No new `/api` routes and no new parallel write actions for cells.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value: an
  `unverified` cell is never reported as done.
- No large payloads in SQL or application state (selection carries ids and
  numbers only).
