# 4.4: Product usage joined with revenue

Lane D. Size M. Needs 3.3a and 3.1b.

## 1. Goal

A growth or product lead can ask "which features do expanding accounts use?"
or "what do churned accounts stop doing?" and get a table: for each feature,
the share of accounts in the revenue group that used it, the share of a
comparison group, the difference, and how many accounts each share is based
on. Accounts come from the account map, revenue movement from the Stripe
metrics program, and usage from first-party events. The answer always states
how many customers could be matched to product users, so a thin match is
visible instead of hidden in a confident table.

## 2. What the code does today

- No action joins revenue and usage. `account-deep-dive` reports
  `productUsageIncluded: false` (`templates/analytics/actions/account-deep-dive.ts:610`),
  and the account-health skill makes usage a separate, manual step
  (`templates/analytics/.agents/skills/account-health/SKILL.md:29-40`).
- Revenue movement per customer will come from 3.1b's program view
  `customers` (`movement`: new, expansion, contraction, churned, flat,
  reactivation). Account links (Stripe customer to product users) come from
  3.3a.
- First-party events have `user_id`, `event_name`, `timestamp` and
  `event_date` (`templates/analytics/server/plugins/db.ts:290-312`), indexed on
  (`event_name`, `timestamp`) (`db.ts:318-320`). The rollups
  `analytics_event_daily_rollups` (per event per day, no user) and
  `analytics_user_days` (per user per day, no event)
  (`templates/analytics/server/db/schema.ts:276-290`, `schema.ts:628-635`)
  cannot answer "which users did which event", so this needs one bounded read
  of raw events.
- Raw first-party reads can be delivered through BigQuery and are a known
  cost (`templates/analytics/server/lib/first-party-analytics-backend.ts:1298-1303`
  maps the virtual tables; plan section 2 notes the cost). The query action
  `query-agent-native-analytics` is the read path with tenant scoping
  (`templates/analytics/actions/query-agent-native-analytics.ts:54-110`).
- The SQL in `templates/analytics/actions/conversion-analysis/` is for
  funnels (4.1), not for account-level feature use.

## Plan corrections

- "Through the account map from 3.3" also needs 3.1b's per-customer view;
  the map alone has no revenue.
- Feature use has no rollup that keeps both user and event today. Brief
  1.4c proposes `analytics_user_event_days` (event date, event name, user key,
  user id). Read that table when it exists; fall back to one bounded raw read
  only when it does not.

## 3. Build

1. Server function `templates/analytics/server/lib/revenue-feature-usage.ts`
   and action `templates/analytics/actions/revenue-feature-usage.ts`
   (`defineAction`, `readOnly: true`, `grounding: true`, `chatUI` with the
   core data-table renderer):
   - Args: `group` (`expansion` default, `contraction`, `churned`, `new`,
     `reactivation`), `compareTo` (`flat` default, or `all_others`),
     `windowDays` (default 90, max 365), `minAccounts` (default 3), `limit`
     (default 25, max 100), `excludeEvents` (optional list).
   - Revenue: `runDataProgram` on 3.1b's program with `view: "customers"`
     and `months` covering the window. `background_pending` returns
     `{ status: "pending", message }`; a failure returns its error code. No
     rows are invented.
   - Accounts: map Stripe customer ids to accounts and accounts to product
     user ids through 3.3a's link tables (decision `rejected` excluded). One
     account counts once even with several Stripe customers; if those
     customers have different movements, use the account's summed MRR change.
   - Usage: one aggregate per chunk of 1,000 user ids, through the same
     backend `query-agent-native-analytics` uses (server function, not a
     nested agent call). When 1.4c's `analytics_user_event_days` exists:
     `SELECT user_id, event_name, COUNT(*) AS active_days FROM analytics_user_event_days WHERE event_date >= <window start> AND user_id IN (...) AND event_name NOT IN (<noise>) GROUP BY user_id, event_name`.
     Otherwise the same shape over `analytics_events` with a `timestamp`
     bound. Record which table was read in `evidence`. Cap at 10,000 user ids
     and say so.
     The default noise list lives in
     `templates/analytics/shared/usage-noise-events.ts` (page views, session
     start and end, identify, autocapture-style events); confirm the names
     against `list-event-catalog` output while building.
   - Compute per feature (event name): accounts in the group that used it,
     share of the group, the same for the comparison group, difference in
     percentage points, and keep features where the group count is at least
     `minAccounts`. Sort by difference.
   - Return `{ status: "ok", rows, schema, coverage, evidence }`, where
     `coverage` = Stripe customers in window, customers in the group,
     customers matched to an account, accounts with product users, product
     users queried, `usersCapped`, `revenueCoverageComplete` (from 3.1b), and
     `evidence` follows 3.4a's shape (sources Stripe program, account map,
     first-party events; window; filters; row counts; the SQL).
   - When fewer than `minAccounts` accounts in the group have product users,
     return `{ status: "insufficient_match", coverage }` instead of a table.
2. Skills:
   - Add a "Revenue and usage" section to the `revenue-metrics` skill (3.1b):
     when to call `revenue-feature-usage`; always report coverage first;
     describe results as association ("expanding accounts use X more"), not
     cause; suggest `sync-account-map` when the match is thin.
   - `templates/analytics/.agents/skills/account-health/SKILL.md`: one line
     noting this action compares groups of accounts; for a single named
     account keep using the deep dive plus usage queries.
   - `templates/analytics/AGENTS.md`: one line under "Data questions".
3. UI: no new screen. Results render in chat through the core data-table
   renderer; the user can ask the agent to put the table on a dashboard.
4. Application state: not applicable; no new view or selection.
5. Changelog: `agent-native changelog add "Ask which features expanding or churned accounts use, joined across Stripe, the account map and product events." --type added`.

## 4. Copy

No UI catalog strings: column names come from the result schema and are
data (`feature`, `group_accounts`, `group_share`, `comparison_accounts`,
`comparison_share`, `difference_pts`). Action messages are agent facing.

## 5. Tests

- `templates/analytics/server/lib/revenue-feature-usage.spec.ts`: stub
  `runDataProgram`, the link reads and the events query. Cases: expanding vs
  flat with known shares; an account with two Stripe customers counts once;
  rejected links are ignored; `minAccounts` filters features; noise events
  excluded; user cap sets `usersCapped`; program pending returns `pending`;
  thin match returns `insufficient_match`; chunking splits 2,500 users into
  three queries.
- `templates/analytics/actions/revenue-feature-usage.spec.ts`: schema
  defaults and the result shape the data-table renderer expects.
- No source-reading tests.

## 8. Defaults for open questions

- DECISION: a "feature" is a first-party event name. A mapping from events to
  named features can come later through the data dictionary.
- DECISION: comparison group defaults to flat accounts.
- DECISION: 90-day window, 3-account minimum, 10,000-user cap.
- DECISION: first-party events only in v1. Postgres (2.1) and PostHog usage
  are follow-ups.
- DECISION: no dashboard panel or data program wrapper in v1.

## 9. Do not

- No behavior changes outside this unit.
- Additive-only schema; none expected.
- No new `/api` routes for app data; use actions.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value:
  `pending`, `insufficient_match` and errors are distinct from an empty
  table.
- No large payloads in SQL; nothing new is stored.
- No unbounded reads of `analytics_events`: always a time window and a user
  list.
- Do not describe the results as causal.

## Reviewer notes

- The usage query interpolates up to 1,000 user ids per chunk into
  `user_id IN (...)`. Ids are emails from the account map, which is user
  editable. Build the list with one literal helper that doubles single
  quotes (the same rule 4.1b uses), or pass ids as a bound parameter if the
  first-party query path supports one; never join raw strings. Add a test
  with an id containing a quote.
