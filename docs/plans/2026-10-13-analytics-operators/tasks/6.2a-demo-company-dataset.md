# 6.2a: Demo company dataset and query action

Lane B. Size M. Not gated (no new surface; the action and data are server
side). Blocks 6.2b. Split from plan PR 6.2, which is L as one unit: 6.2a is
the data and the agent's way to query it, 6.2b is the dashboard and first-run
UI on top.

Paths are relative to `templates/analytics/` unless they start with
`packages/` or `docs/`.

## 1. Goal

Before connecting anything, a visitor can ask the agent a cross-tool question
about a made-up startup and get a real, joined answer: "Using the demo
company, which accounts are at risk of churning?" returns accounts whose
Stripe MRR is at stake, whose product usage is falling, and whether HubSpot
has an open renewal deal, joined by domain, and labeled as demo data. The
data is fictional, deterministic, generated in process with no network call
and no SQL storage, and always looks current because it is anchored to
today's date.

## 2. What the code does today

- The only demo data is a hosted Prometheus endpoint. The `demo` panel
  source fetches `DEFAULT_DEMO_PROMETHEUS_URL` (a public demo host) or an
  `ANALYTICS_DEMO_PROMETHEUS_*` override (`server/lib/demo-source.ts:22-30`,
  `:60-72`) and returns Prometheus series rows
  (`server/lib/demo-source.ts:173-199`), cached in memory for 30 seconds
  (`:32`, `:201-224`). There is no business, billing, CRM or product data
  anywhere in the demo.
- It feeds one auto-installed dashboard, "Demo Node Exporter Full", built
  from the `node-exporter-full` seed (`server/lib/demo-dashboards.ts:15-21`),
  installed per user on every app open (`app/root.tsx:123-131`, calling
  `ensure-demo-dashboards`, `actions/ensure-demo-dashboards.ts:33-40`).
- The agent has no demo query tool. Its rule is "never cite the public
  `demo` source as real evidence unless asked" (`AGENTS.md:17`), and catalog
  search hides demo panels unless the question says "demo" or "node
  exporter" (`server/lib/analytics-query-catalog.ts:789-793`).
- The response guard only accepts an answer with numbers if a grounding
  action ran (`server/lib/real-data-actions.ts:1186-1200`). Grounding actions
  are those whose definition sets `grounding: true`
  (`server/lib/real-data-actions.ts:80-93`), registered from the generated
  action registry at plugin load (`server/plugins/agent-chat.ts:14`,
  `:49-50`). Example: `actions/hubspot-metrics.ts:10-18`.
- An in-process filter, group and aggregate engine already exists and is
  exported: `runAggregateQuery(rows, query)` with `where`, `groupBy`,
  `aggregate`, `select`, `orderBy`, `orderDir`, `limit`
  (`packages/core/src/provider-api/staged-datasets-aggregate.ts:33-41`,
  `:227`), published as `@agent-native/core/provider-api/staged-datasets-aggregate`
  (`packages/core/package.json:426`). The template's `query-staged-dataset`
  action uses the same query shape (`actions/query-staged-dataset.ts:6-80`).
- The first-turn tool list is `INITIAL_TOOL_NAMES`
  (`server/lib/agent-chat-plan-mode.ts:1-22`), asserted by
  `server/plugins/agent-chat.spec.ts:717-752`. Anything else is found through
  tool search, which costs a turn.
- The `cross-source-analysis` skill already teaches the safe-join rule and
  per-source provenance (`.agents/skills/cross-source-analysis/SKILL.md:94-113`,
  `:142-154`); the demo should follow it so the demo answer looks like a real
  one.

## Plan corrections

- "Replace the demo data" should not remove the Node Exporter demo in this
  unit. It stays as is; 6.2b decides what installs by default. This unit adds
  a second demo dataset beside it.
- The plan implies the demo needs Stripe, HubSpot and a database connected in
  some form. It does not: a generated dataset shaped like those tools, with
  the same join key real accounts use (domain), shows the same cross-tool
  answer without credentials, network or SQL rows.

## 3. Build

1. Shared query contract `shared/demo-company.ts` (pure, imported by server
   and by 6.2b's panel parser):
   - `DEMO_COMPANY_NAME = "Acme Cloud"`, `DEMO_COMPANY_DATASET = "company"`.
   - `DEMO_COMPANY_TABLES`: the table and view names below, as a const tuple.
   - `DemoCompanyQuerySchema` (zod): `{ table: enum(DEMO_COMPANY_TABLES),
     where?, groupBy?, aggregate?, select?, orderBy?, orderDir?, limit? }`,
     with the same `where` ops and `aggregate` ops as
     `actions/query-staged-dataset.ts:6-31`. `limit` 1 to 2,000, default 100.
     Reuse the zod pieces by moving them out of `query-staged-dataset.ts`
     only if that file can import them back unchanged; otherwise declare them
     here.
2. Generator `server/lib/demo-company/generate.ts`:
   - `generateDemoCompany(now: Date): DemoCompanyData`, deterministic from a
     fixed seed (a small seeded PRNG such as mulberry32; no dependency). All
     dates are offsets from `now` truncated to the UTC day, so the same day
     always yields the same rows and the shape is identical every day.
   - Memoize the result for the current UTC day in module scope
     (`Map<dayKey, DemoCompanyData>`, keep one entry). Generate lazily on the
     first call, never at module load (performance skill, "Protect startup
     and the first paint").
   - Target: under 150 ms and under 10 MB in memory. Measure in the test and
     record the number in the PR.
3. Tables (names mirror the source tool so the agent's demo answer reads like
   a real one; money is integer cents, timestamps ISO strings):
   - Stripe: `stripe_customers` (`id` `cus_...`, `name`, `email`,
     `domain`, `created`), `stripe_subscriptions` (`id` `sub_...`,
     `customer`, `status` active | canceled | trialing | past_due, `plan`
     starter | growth | business, `mrr_cents`, `start_date`, `canceled_at`),
     `stripe_invoices` (`id` `in_...`, `customer`, `subscription`,
     `period_start`, `period_end`, `amount_paid_cents`, `status` paid | open
     | uncollectible).
   - HubSpot: `hubspot_companies` (`id`, `name`, `domain`, `industry`,
     `numberofemployees`, `hubspot_owner`, `lifecyclestage`),
     `hubspot_deals` (`id`, `company_id`, `dealname`, `dealtype` newbusiness
     | renewal | expansion, `amount`, `dealstage` appointmentscheduled |
     qualifiedtobuy | presentationscheduled | contractsent | closedwon |
     closedlost, `pipeline` default, `createdate`, `closedate`).
   - Product database: `app_workspaces` (`id`, `domain`, `name`, `plan`,
     `created_at`), `app_users` (`id`, `workspace_id`, `email`,
     `signed_up_at`, `last_active_at`), `app_weekly_activity`
     (`workspace_id`, `week_start`, `active_users`, `reports_viewed`,
     `dashboards_created`) for the last 26 weeks.
   - Derived views computed from the tables above (not stored separately).
     Money in views is whole dollars, because dashboard panels format it with
     `yFormatter: "currency"` (`app/pages/adhoc/sql-dashboard/types.ts:74`);
     raw Stripe tables keep cents like the real API.
     `accounts` (one row per domain: `domain`, `company_name`,
     `stripe_customer_id`, `hubspot_company_id`, `workspace_id`, `segment`
     smb | mid_market | enterprise, `plan`, `status` active | churned |
     trialing, `mrr`, `churned_at`, `owner`, `open_deal_type`,
     `open_deal_amount`, `open_deal_stage`, `open_deal_close_date`,
     `wau_now`, `wau_4_weeks_ago`, `wau_change_pct`, `uses_reports`,
     `expansion_mrr_12m`),
     `mrr_by_month` (`month`, `starting_mrr`, `new_mrr`, `expansion_mrr`,
     `contraction_mrr`, `churned_mrr`, `ending_mrr`, `active_customers`) for
     18 months ending with the current month to date, with
     `contraction_mrr` and `churned_mrr` as negative numbers so a stacked
     bar reads below zero, and
     `pipeline_by_stage` (`dealstage`, `deals`, `amount`).
4. Planted story. These are invariants the tests assert, so the demo
   answer is the same for every visitor (DECISION, owner may change the
   numbers, not the shape):
   - About 420 Stripe customers, 360 active today; about 520 HubSpot
     companies (paying customers plus prospects); about 570 workspaces
     (paying plus trials). Every paying customer has the same `domain` in all
     three tools; prospects and trials exist in only one or two, so a naive
     join shows the coverage gaps a real join has.
   - MRR grows in 16 of the last 17 complete months. Exactly one complete
     month, three months before the current one, has negative net new MRR,
     caused by 9 SMB churns.
   - Each of those 9 churned accounts had `active_users` fall by at least 50
     percent over the 6 weeks before `canceled_at`.
   - Today exactly 14 active accounts have `wau_change_pct <= -40`. Five of
     them have an open `renewal` deal in HubSpot closing within 60 days.
     These 14 are the answer to "which accounts are at risk".
   - Accounts with `uses_reports = true` expand at least twice as often as
     the rest over the last 12 months (gives 4.4 and growth questions a
     signal).
   - All domains end in `.example` (reserved, RFC 2606) and all emails use
     those domains. Company names come from fixed word lists of invented
     words; no real company names, people or brands.
5. Query function `server/lib/demo-company/query.ts`:
   `queryDemoCompany(query: DemoCompanyQuery, now = new Date())` validates
   with `DemoCompanyQuerySchema`, picks the table or view, applies
   `runAggregateQuery`, then the limit. Returns
   `{ dataset: "company", company: DEMO_COMPANY_NAME, fictional: true,
   table, asOf, columns, rows, rowCount, totalRows, truncated }`.
   `truncated` is true whenever rows were cut by `limit`; `totalRows` is the
   count before the cut. An unknown column in `where`, `groupBy`, `select`,
   `orderBy` or `aggregate` throws a typed error naming the column and the
   table's columns; it never returns empty rows.
6. Action `actions/query-demo-company.ts` (`defineAction`):
   - `readOnly: true`, `grounding: true`, `http: { method: "GET" }`,
     `mcpTool: false`, schema `DemoCompanyQuerySchema`.
   - Description (agent-facing, keep it short): "Query the built-in demo
     company, Acme Cloud: fictional Stripe, HubSpot and product-database
     data joined by domain. Use only when the user asks about the demo
     company or demo data, or is viewing the demo company dashboard. Tables:
     ... Views: accounts (one row per domain across all three tools),
     mrr_by_month, pipeline_by_stage. Always say the figures are demo data
     from a fictional company."
   - Throws the typed error from step 5 as an action error (follow the
     template's action error pattern; `no-bare-error-in-actions` checks
     added lines).

## 5. Tests

- `server/lib/demo-company/generate.spec.ts`:
  - Determinism: two calls with the same `now` deep-equal; a call with
    `now + 1 day` has the same row counts and every date shifted by one day.
  - Planted story invariants from step 4, computed from the tables, not from
    the derived views (so a bug in a view cannot hide a bug in the data):
    one negative net-new month exactly three months back, 9 churns in it,
    each with a 50 percent drop; 14 at-risk accounts, 5 with an open renewal
    closing within 60 days; reports users expand at least twice as often.
  - Join integrity: every paying customer's domain exists in all three tools;
    every `hubspot_deals.company_id` and `stripe_subscriptions.customer`
    resolves.
  - Every domain ends in `.example`; every email's domain is one of them.
  - Budget: generation for one `now` takes under 150 ms on CI hardware
    (allow headroom, assert under 500 ms) and the memo returns the same
    object on a second call for the same day.
- `server/lib/demo-company/query.spec.ts`: `accounts` with the at-risk
  filter returns the 14 domains; `mrr_by_month` returns 18 rows ending in the
  current month; `limit` sets `truncated: true` and `totalRows`; an unknown
  column throws a typed error naming the column (not an empty result).
- `actions/query-demo-company.spec.ts`: the action runs through
  `defineAction` with CLI-style args, and declares `readOnly` and
  `grounding`.
- `server/plugins/agent-chat.spec.ts:717-752`: add `query-demo-company` to
  the expected initial tools.
- `server/lib/real-data-actions.spec.ts`: a turn whose only data call is
  `query-demo-company` counts as a data query attempt (registry derived
  through `deriveGroundingActionNames`).
- No source-reading tests (the skill is not asserted by reading its file).

## 8. Defaults for open questions

- DECISION: the fictional company is "Acme Cloud", a B2B SaaS with three
  plans. Owner may rename; change `DEMO_COMPANY_NAME` only.
- DECISION: data is generated in code from a seeded PRNG, not shipped as a
  JSON fixture (keeps the server bundle small) and not stored in SQL (no
  per-user rows, no migration, nothing to back up).
- DECISION: query shape is the staged-dataset filter and aggregate shape,
  not SQL. A SQL surface over the demo can follow once 7.2a picks an
  in-memory SQL engine; do not add one here.
- DECISION: `query-demo-company` is in the first-turn tool list. Reviewer may
  move it to tool search if prompt size matters more than first-run latency.
- DECISION: `mcpTool: false`. External MCP callers do not need the demo.
- DECISION: dates anchor to the current UTC day, so "last quarter" always
  has data.
- DECISION: the Node Exporter demo and the `demo` Prometheus path are
  untouched in this unit.

## 9. Do not

- No behavior changes outside this unit: the Prometheus `demo` source, the
  Node Exporter dashboard and its installer stay as they are.
- Additive-only schema; this unit adds no table or column.
- No new `/api` routes for app data; the action is the only surface.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials (the demo needs none).
- No `catch` or default that turns a failure into a normal-looking value: an
  unknown table or column is a typed error, a cut result says
  `truncated: true`, never a silent empty or partial list.
- No large payloads in SQL; the dataset lives in memory only.
- No generation at module load or server start.
- No real company, person, brand or domain in generated data.
- Never let the agent present demo figures as the user's own numbers.
