# 2.2b Stripe OAuth code path

Lane B (Founders). Size M. Not gated.

Paths starting with `packages/` are repo-relative; everything else is relative
to `templates/analytics/`. This unit changes `packages/core` and needs a
`.changeset/*.md`.

## 1. Goal

When the deployment has a Stripe app client id and secret configured, the
Stripe card on Data sources shows a Connect button that sends the user through
Stripe's authorization screen and back, with no key to paste. Analytics,
run-code and data programs then read Stripe through that connection, and the
token refreshes on its own. When the deployment has no client id (the case
today, because the Stripe platform registration only the plan owner can make
has not happened), the button is hidden and the restricted-key path from 2.2a
is the only option. Nothing in this unit can be proven against Stripe until the
registration exists; everything else is built and tested.

## 2. What the code does today

- Workspace OAuth providers are a closed union and set in
  `packages/core/src/server/workspace-provider-oauth.ts:52-80`
  (figma, gmail, five Google products, github, hubspot, salesforce, jira,
  sentry, notion). Stripe is not one.
- The same provider list is copied in `packages/core/src/server/core-routes-plugin.ts:3653-3676`,
  which mounts `/_agent-native/connections/oauth/<provider>/start|callback`
  for each. Adding a provider means editing both.
- Token exchange `exchangeWorkspaceProviderOAuthCode`
  (`workspace-provider-oauth.ts:619-805`) is a stack of per-provider branches:
  github (`:631`), hubspot (`:664`), salesforce (`:694`), jira (`:724`), then a
  generic path with more per-provider conditionals for figma, sentry, Google
  and notion (`:755-792`). Identity resolution has the same shape
  (`:808-1010`).
- Client credentials come from `resolveSecret` with names derived per provider
  (`clientCredentialKeys`, `:1232-1260`): default `<PROVIDER>_CLIENT_ID` /
  `<PROVIDER>_CLIENT_SECRET`. `hasWorkspaceProviderOAuthCredentials`
  (`:117-122`) answers "is this deployment configured", and other templates use
  it as an onboarding `isAvailable` gate (`templates/mail/server/onboarding.ts:29`).
- Token refresh for provider-api calls dispatches by provider in
  `packages/core/src/provider-api/index.ts:4852-4885`, one function per
  provider, and throws for unknown providers.
- The connection catalog `packages/core/src/connections/catalog.ts` has no
  Stripe entry; OAuth config lives in each entry's `oauth` field (`:68-74`).
- The provider API definition for `stripe`
  (`packages/core/src/provider-api/index.ts:1708-1722`) is plain bearer with
  `STRIPE_SECRET_KEY`. HubSpot shows the dual mode this unit needs:
  `type: "oauth-bearer-or-bearer-key"` with `workspaceProvider`
  (`:1359-1370`).
- Analytics side:
  - `server/lib/stripe.ts:13-21` resolves only `STRIPE_SECRET_KEY` with
    `resolveCredential`.
  - `server/lib/provider-credentials.ts:288-313` `resolveAnalyticsProviderCredential`
    already tries a workspace OAuth connection first (`:180-220`), then a
    workspace credential, then the local key. HubSpot uses it.
  - One-click sources are a hard-coded set,
    `app/lib/data-source-status.ts:83-88`; Data sources renders the Connect
    button through `WorkspaceOAuthView` and `startWorkspaceOAuth`
    (`app/pages/DataSources.tsx:556-604`).

### Plan corrections

- Plan section 6.3 asks whether a Stripe App listing is required. This brief
  assumes the Stripe Apps OAuth flow (see Defaults D1). The implementer must
  confirm the current authorize URL, token URL, token lifetime, refresh
  behavior and client authentication against Stripe's public docs before

## 3. Build

### Core (`packages/core`)

1. **One provider list.** Export `WORKSPACE_OAUTH_PROVIDERS` (readonly array)
   from `workspace-provider-oauth.ts`, derive the union and
   `SUPPORTED_PROVIDERS` from it, and make `core-routes-plugin.ts:3653-3676`
   iterate it. Delete the copy. 2.2c depends on this.
2. **Declarative token request.** Before adding Stripe, replace the branch
   stack in `exchangeWorkspaceProviderOAuthCode` with a per-provider
   descriptor on the catalog entry's `oauth` field:
   `tokenRequest: { encoding: "form" | "json"; clientAuth: "body" | "basic" | "basic-secret-only"; pkce?: boolean }`.
   Move github, hubspot, salesforce, jira, figma, sentry, Google and notion into
   descriptors with identical wire behavior, and keep one code path that reads
   the descriptor. The existing
   `packages/core/src/server/workspace-provider-oauth.spec.ts` must pass
   unchanged; add a case per provider that asserts the exact request body and
   headers before and after (write those cases first, against the current
   code). If any provider cannot be expressed, leave it as an explicit branch
   and say why in a comment.
3. **Stripe provider.**
   - Add `"stripe"` to `WORKSPACE_OAUTH_PROVIDERS`.
   - Catalog entry in `connections/catalog.ts`: `id: "stripe"`,
     `label: "Stripe"`, `capabilities: ["search", "import"]`,
     `recommendedTemplateUses: ["analytics"]`, `credentialKeys: []`, `oauth`
     with the Stripe authorize URL, token URL, refresh URL, the read-only scope
     the docs specify, and `tokenRequest` per what the docs say (D1 expects
     `clientAuth: "basic-secret-only"`, where the app's secret key is the
     HTTP basic username).
   - `clientCredentialKeys("stripe")`: `STRIPE_CLIENT_ID`, `STRIPE_CLIENT_SECRET`
     (deployment secrets, resolved with `resolveSecret`, never `process.env`).
   - Identity: resolve the connected account with `GET https://api.stripe.com/v1/account`
     using the new token; account id is the stable id, business name or email
     the label.
   - Refresh: add `refreshStripeOAuthToken` next to the other refreshers in
     `provider-api/index.ts` and dispatch to it from `:4852-4885`. A permanent
     refresh failure must surface `throwWorkspaceConnectionRequired(... reason: "reauthorize")`,
     not return the expired token.
4. **Provider API.** Change `stripe` auth to
   `{ type: "oauth-bearer-or-bearer-key", oauthProvider: "stripe", tokenLabel: "Stripe OAuth token", key: "STRIPE_SECRET_KEY", fallbackKeys: ["STRIPE_SECRET_KEY"], workspaceProvider: "stripe" }`
   matching HubSpot. Update `packages/core/src/eject/provider-api-definitions.ts`
   and `eject/workspace-connections.ts` if their tests enumerate providers.
5. **Changeset** `.changeset/<slug>.md`: `@agent-native/core` minor, one line
   ("Add Stripe as a workspace OAuth connection and describe OAuth token
   requests per provider").

### Analytics (`templates/analytics`)

6. **Resolver.** `server/lib/stripe.ts:13-21` `getToken` calls
   `resolveAnalyticsProviderCredential({ provider: "stripe", keys: ["STRIPE_SECRET_KEY"], ctx })`
   so an OAuth connection wins and the local key is the fallback. Cache keys
   (`:42`) must include the credential source and connection id so switching
   from key to OAuth does not serve the other account's cached response.
   A missing credential keeps the existing typed message.
7. **One-click set.** Add `"stripe"` to `workspaceOAuthSourceIds` and
   `dataSourceWorkspaceProviderIds` in `app/lib/data-source-status.ts:74-88`.
8. **Availability.** `actions/data-source-status.ts`: include
   `oauthAvailable: await hasWorkspaceProviderOAuthCredentials("stripe")` on
   the Stripe provider's `workspaceConnection` summary (add the optional field
   to `WorkspaceConnectionProviderSummary` in `app/lib/data-source-status.ts:16-31`).
   `shouldShowWorkspaceOAuthSetup` (`:94-107`) also requires
   `oauthAvailable !== false`, so the button never appears on a deployment
   that cannot complete the flow.
9. **UI.** The existing `WorkspaceOAuthView` renders the Connect button; above
   the restricted-key walkthrough show "Or paste a restricted key" as a ghost
   disclosure when OAuth is available. No new component.
10. **Onboarding.** In a server module loaded by `server/plugins/onboarding.ts`,
    `registerOnboardingStep({ id: "stripe", required: false, isAvailable: () => hasWorkspaceProviderOAuthCredentials("stripe"), methods: [{ kind: "link", url: "/_agent-native/connections/oauth/stripe/start?scope=organization&appId=analytics&return=/data-sources?source=stripe" }], isComplete: ... })`
    modeled on `templates/mail/server/onboarding.ts:24-60`. `isComplete` checks
    the workspace connection or the local key.
11. **Application state.** None new; the Data sources view already reflects
    `?source=stripe` through `focusedDataSourceFromSearchParams`
    (`app/lib/data-source-status.ts:144-156`).
12. **Skills.** Template `.agents/skills/provider-api/SKILL.md` Stripe notes:
    a Stripe workspace connection is preferred; the agent never asks for a
    secret key when `data-source-status` shows Stripe OAuth is available;
    `connectionId` can be passed like HubSpot. Template
    `.agents/skills/secrets/SKILL.md` needs no change.
13. **Changelog.** Only when the client id ships; until then the change is not
    user-visible, so no entry (D5).

## 8. Defaults for open questions

- **D1** Flow: Stripe Apps OAuth (install link, short-lived access token,
  refresh token), not legacy Connect OAuth. Confirm against Stripe's docs; if
  Stripe requires Connect for read access to an existing account, switch the
  descriptor and say so in the PR.
- **D2** Deployment secrets are `STRIPE_CLIENT_ID` and `STRIPE_CLIENT_SECRET`.
- **D3** Default connection scope is organization, so one founder connects for
  the team; personal scope stays available through the core flow.
- **D4** OAuth wins over a saved key when both exist; the key is kept, not
  deleted.
- **D5** No changelog entry until a deployment can show the button.
- **D6** The token-request refactor ships in this unit because adding a ninth
  branch to that function is the pattern the repo rules ask us to stop.

## 9. Do not

- No behavior changes outside this unit: every existing provider's OAuth
  request must be byte-for-byte the same after the refactor.
- Additive-only schema; none expected.
- No new `/api` routes; the OAuth routes are the core framework routes.
- No raw `fetch` from client code; the Connect button navigates to the core
  start route as `startWorkspaceOAuth` already does.
- No `process.env` reads for provider credentials; client id and secret come
  from `resolveSecret`, user tokens from the OAuth token store.
- No `catch` or default that turns a failure into a normal-looking value: an
  expired token with a failed refresh is a reconnect state, never a silent
  retry with the old token.
- No large payloads in SQL.
- Do not show a Connect button that cannot finish.
