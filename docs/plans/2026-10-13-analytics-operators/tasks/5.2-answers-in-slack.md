# 5.2 Answers in Slack

Lane B (Founders). Size M.

## 1. Goal

Someone types a question to the Analytics bot in Slack ("how many signups
did we get last week, and from where?") and gets the answer in the thread,
computed with the same actions and data access as the web app, plus a link
that opens the full conversation, dashboard or analysis in Analytics. This
works whether Analytics runs on its own or inside a workspace where Dispatch
owns the Slack app.

## 2. What the code does today

Paths outside `templates/analytics/` are repo-relative. The task said to check
what core integrations already provide before designing anything. Most of
it exists.

**Core already provides the Slack path**

- Every app gets a default integrations plugin when it ships none of its own:
  `integrations: "defaultIntegrationsPlugin"` in the default plugin registry
  (`packages/core/src/deploy/route-discovery.ts:113-125`), mounted for any
  missing stem (`packages/core/src/server/framework-request-handler.ts:806-822`).
  Analytics has no `server/plugins/integrations.ts`
  (`templates/analytics/server/plugins/` listing), so it gets the default.
- The plugin handles the Slack webhook, queues work in SQL, runs the agent in
  a separate execution, and replies in the thread
  (`.agents/skills/integration-webhooks/SKILL.md`, flow section). Slack OAuth,
  the app manifest and installation selection are in
  `packages/core/src/integrations/slack-oauth.ts`, `slack-manifest.ts` and
  `adapters/slack.ts`. Setup UI is the shared Settings › Integrations page
  (`packages/toolkit/src/app/settings/shell/pages/integrations.tsx`).
- Identity: verified DMs run as the linked org member; shared channels run as a
  service principal; guests can't borrow personal access
  (`templates/analytics/.agents/skills/external-agents/SKILL.md:277-282`). The
  sender gets `editor` on the resulting thread so the link works for them
  (`packages/core/src/integrations/webhook-handler.ts:787-803`).
- Replies carry an **Open thread** button when the app base URL is known
  (`packages/core/src/integrations/adapters/slack.ts:1133-1150`).

**What is wrong or missing for Analytics**

- **The default plugin has none of Analytics' actions.** With no options,
  `localActions` is `{}` (`packages/core/src/integrations/plugin.ts:836`).
  The agent gets only integration memory and `call-agent`
  (`plugin.ts:838-859`), and the generic integration prompt
  (`plugin.ts:413-419`). It cannot run a query, read a dashboard or call a
  provider. Mail shows the fix: its own plugin passes
  `loadActionsFromStaticRegistry(actionsRegistry)` and a system prompt
  (`templates/mail/server/plugins/integrations.ts:1-45`).
- The web agent's actions, initial tool set and data-source rules are already
  packaged in Analytics: `actions: loadActionsFromStaticRegistry(actionsRegistry)`
  and `initialToolNames: INITIAL_TOOL_NAMES`
  (`server/plugins/agent-chat.ts:1241-1242`), plus the exported
  `analyticsExtraContext()` that wraps `ANALYTICS_PROMPT_RULES`
  (`server/plugins/agent-chat.ts:276-320`).
- **The Open thread link 404s in Analytics.** Core builds
  `${appBaseUrl}/chat/<threadId>` (`packages/core/src/integrations/webhook-handler.ts:1379-1382`).
  Eight templates have `app/routes/chat.$threadId.tsx` (assets, chat, design,
  dispatch, factory, mail, plan, slides). Analytics does not. Its thread
  route is `/ask/<threadId>` (`shared/ask-route.ts`, `app/routes/ask.$threadId.tsx`),
  so `/chat/<id>` hits the catch-all `NotFound` (`app/routes/$.tsx:1-16`).
- **In a workspace, Dispatch owns Slack** and delegates data questions to
  Analytics over A2A (`packages/dispatch/src/server/plugins/integrations.ts:18-31`,
  "analytics (data/dashboards)"). Dispatch relays the downstream answer as is
  (same file, "RELAY IT DIRECTLY"). Analytics' web prompt already expects that
  delegation (`server/plugins/agent-chat.ts:302`). The link back in that path is
  whatever the Analytics answer contains, and the Open thread button points at
  Dispatch's thread, not Analytics'.

## 3. Build

1. **Analytics integrations plugin.** Create
   `server/plugins/integrations.ts`, modeled on Mail's:
   ```ts
   createIntegrationsPlugin({
     appId: "analytics",
     actions: loadActionsFromStaticRegistry(actionsRegistry),
     initialToolNames: INITIAL_TOOL_NAMES,
     systemPrompt: ANALYTICS_INTEGRATION_SYSTEM_PROMPT,
   });
   ```
   Keep the built-in adapters (do not pass `adapters`), so Teams, Discord and
   the rest keep working as they do in the default. Do not set `model`;
   inherit the framework default as Dispatch does.

2. **Integration prompt.** Add `server/lib/analytics-integration-prompt.ts`
   exporting `ANALYTICS_INTEGRATION_SYSTEM_PROMPT`, written per
   `writing-agent-instructions`. It is the core integration guidance (short
   replies, light markdown) plus `analyticsExtraContext()` plus these
   Slack-specific rules:
   - Answer with the number or short table first, then one sentence on the
     source and time window.
   - End with one link to the Analytics artifact that holds the answer: the
     dashboard or analysis when one was used or created (use the action's
     `link` result), otherwise nothing extra, because the Open thread button
     already links the conversation.
   - Never paste more than 10 rows; offer the link for the rest.
   - When a channel request runs as the service principal and needs personal
     data access, say so and ask the person to DM the bot.
   - A partial answer is labeled partial with what is missing (matches 1.6).
   Import `analyticsExtraContext` from `server/plugins/agent-chat.ts`. If that
   import pulls the whole plugin module at boot, move `ANALYTICS_PROMPT_RULES`
   and `analyticsExtraContext` to `server/lib/analytics-prompt-rules.ts` and
   re-export from `agent-chat.ts` (no change to the web prompt text).

3. **Fix the Open thread link.** Add `app/routes/chat.$threadId.tsx` as an
   alias route that redirects to `analyticsAskThreadPath(threadId)`, following
   the alias pattern in `app/routes/dashboard.tsx` (loader and clientLoader
   both throw `withSsrHtmlContentType(redirect(...), { varyByQuery: true })`).
   The redirect is derived from the path only, so the SSR shell stays
   impersonal (`guard:ssr-cache-shell`).

4. **Workspace path (Dispatch).** No Dispatch code change in this unit. Verify
   that a Slack question routed through Dispatch reaches Analytics over A2A
   and that the relayed answer contains the artifact link from step 2's rule.
   If the A2A path does not use the integration prompt, add the same "end
   with one artifact link" rule to Analytics' A2A answer guidance (the
   workspace routing rule at `server/plugins/agent-chat.ts:302` is the place).
   **[decide]** whether Dispatch should also show Analytics' thread link is a
   Dispatch change, out of scope.

5. **Skills.** Add a "Slack" section to
   `templates/analytics/.agents/skills/external-agents/SKILL.md` (it already
   covers Slack identity): Analytics answers in Slack with its full action
   set; replies end with an artifact link; standalone installs connect in
   Settings › Integrations; in a workspace, Slack goes through Dispatch. Add a
   pointer in `AGENTS.md` if it lists entry points.

6. **UI.** None. Setup uses the shared Settings › Integrations page; do not
   build an Analytics-specific Slack card (`CLAUDE.md`, external service UI
   rule).

7. **Application state.** Not applicable: Slack runs have no screen. The
   thread's `source` already records the platform
   (`webhook-handler.ts:775-779`), which the web UI shows when the person
   opens the link.

8. **Changelog.** From `templates/analytics`:
   `agent-native changelog add "Ask Analytics questions in Slack and get the answer with a link back." --type added`.

## 8. Defaults for open questions

- **[decide] Same action set as the web agent.** Slack gets every Analytics
  action; write actions keep their own access checks.
- **[decide] Link rule:** one artifact link when an artifact exists, otherwise
  rely on Open thread.
- **[decide] No Analytics-specific Slack setup UI.**
- **[decide] Dispatch unchanged.**

## 9. Do not

- No behavior changes outside this unit. The web agent's prompt text and tools
  stay the same.
- Additive-only schema; none needed.
- No new `/api` routes for app data; the integrations plugin owns its
  framework routes.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials; Slack credentials stay in
  the core integrations store and vault.
- No `catch` or default that turns a failure into a normal-looking value: a
  failed query in Slack is reported as failed, never as "no data".
- No large payloads in SQL; Slack replies stay short and never store raw
  result sets.
- Do not add a per-app Slack OAuth flow, webhook route or bot token setting.

## Reviewer notes

- **Slack answers skip the Analytics answer guards.** `IntegrationsPluginOptions`
  (`packages/core/src/integrations/types.ts:239-281`) has no
  `finalResponseGuard` and no answer time budget, so a Slack turn built by
  step 1 runs without `realDataFinalGuard` (`server/plugins/agent-chat.ts`),
  without 1.3a's unchecked-edit guard and without 1.6a/1.6b's five minute
  budget. The core receipt guard still runs inside the loop. Before
  building, confirm how the integration run calls the agent loop; if the
  guard cannot be passed, either add optional `finalResponseGuard` and
  `answerTimeBudgetMs` to `IntegrationsPluginOptions` in this unit (core
  change, changeset) and pass Analytics' own, or record it as a known gap in
  the PR and the external-agents skill. Do not ship it silently.
