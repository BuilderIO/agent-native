# 2.3a Imported datasets and CSV import (store, actions, panel source)

Lane B (Founders). Size M. Not gated (backend and agent surface; the UI is 2.3b).

Paths starting with `packages/` are repo-relative; everything else is relative
to `templates/analytics/`. Touches `packages/core` (quota scope), so it needs a
`.changeset/*.md`.

## 1. Goal

A founder can hand Analytics a CSV (a pipeline export, a pricing sheet, a
customer list) and then ask questions about it, join it with Stripe or HubSpot
in a data program, and put it on a dashboard their team can see. The original
file is kept in private file storage, the rows become a staged dataset, and the
import is a named, shareable record with an honest row count and a "truncated"
flag when it hit a limit. This unit builds the store, the import pipeline, the
agent actions and the `import` panel source; 2.3b adds the upload UI and chat
attachments.

## 2. What the code does today

- Staged datasets exist and are agent-queryable:
  `actions/list-staged-datasets.ts`, `actions/query-staged-dataset.ts`,
  `actions/delete-staged-dataset.ts` wrap core factories with
  `appId: "analytics"`. They are only written by `provider-api-request` with
  `stageAs` (`.agents/skills/provider-api/SKILL.md:25-32`).
- Core store `packages/core/src/provider-api/staged-datasets-store.ts`:
  - Two tables, `staged_datasets` (metadata, `owner_email`) and
    `staged_dataset_rows` (one JSON text row per data row) (`:15-36`).
  - Caps `MAX_ROWS_PER_APP = 200_000` and `MAX_BYTES_PER_APP = 50 MB`
    (`:5-6`), summed over every owner of the app (`getAppRowCount` and
    `getAppByteSize`, `:110-126`, filter only on `app_id`). On a hosted
    multi-tenant deployment one user's imports can block everyone's staging.
  - Every read is owner-only (`:240-288`), so a teammate cannot read a
    dataset someone else staged.
  - `getStagedDatasetRows` returns `[]` when the dataset is missing or owned by
    someone else (`:249-251`). Callers must check `getStagedDatasetMeta`
    first, or "missing" reads as "empty". The core query action does
    (`packages/core/src/provider-api/actions/staged-datasets.ts:225-231`).
  - In-process aggregation: `runAggregateQuery` in
    `packages/core/src/provider-api/staged-datasets-aggregate.ts:227` with
    where, groupBy, aggregate, select, orderBy, limit (types `:1-41`).
- Private file storage: `mintAttachmentRef` and `resolveAttachment` in
  `packages/core/src/private-blob/attachment-ref.ts:271` and `:408`, with
  typed outcomes (`:1-19`); `deleteAttachment` at `:438`. Analytics already
  mints refs in `actions/upload-journey-frame.ts:61-80` (base64 in, typed
  `private_storage_unavailable` failure out).
- CSV parsing: there is no CSV parser in the repo. Core's spreadsheet parser
  (`packages/core/src/ingestion/spreadsheet.ts:121`) handles XLS/XLSX only,
  samples 40 rows per sheet for prompt text (`:45-50`), and loads `xlsx` as an
  optional peer.
- Shareable resources in Analytics: tables use `ownableColumns()` plus
  `createSharesTable()` (`server/db/schema.ts:17-41`) and are registered in
  `server/db/index.ts:37-115`. Migrations are a named, versioned list in
  `server/plugins/db.ts` (last entry `version: 167`, `name:
  "source-index-runs-table"`, `:1797-1801`).
- Panel sources are a closed list (`server/lib/dashboard-panel-query.ts:21-29`,
  moved to `shared/dashboard-panel-sources.ts` by 2.1a). JSON-descriptor
  sources are a chained condition in `normalizeDashboardPanelQuery`
  (`:106-114`): `prometheus || demo || program`.

### Plan corrections

- The plan says "rows become a staged dataset the agent can query". Staged
  datasets as they stand are private to one user and share an app-wide quota,
  so an import built only on them cannot appear on a shared dashboard and can
  be blocked by someone else's scratch data. This brief adds an
  `analytics_data_imports` record that owns access, and scopes the quota per
  owner.
- Excel files are not in scope here (no full-row parser exists). See D7.

## 3. Build

1. **Core quota per owner.** In `staged-datasets-store.ts`, change
   `getAppRowCount`/`getAppByteSize` to filter `app_id = ? AND owner_email = ?`
   and pass `options.ownerEmail`; keep the constants; update the error text to
   "you already store". Add a spec. Changeset `@agent-native/core` patch:
   "Staged dataset limits apply per owner instead of per app".
2. **Table** in `server/db/schema.ts` (use the file's existing `table` helper
   for consistency, see D8):
   `dataImports = table("analytics_data_imports", { id, name, kind: text enum ["csv", "google_sheet"], status: text enum ["ready", "failed"], fileRef: text (nullable, attachment ref, never truncated; refs can be 4,096 chars), fileName: text nullable, fileBytes: integer nullable, spreadsheetId: text nullable, sheetRange: text nullable, stagedDatasetId: text not null, columns: text not null (JSON [{ name, type }]), rowCount: integer not null default 0, sourceRowCount: integer nullable, truncated: boolean not null default false, lastSyncedAt: text, lastErrorCode: text nullable, createdAt, updatedAt, ...ownableColumns() })`
   with an index on `(owner_email, updated_at)` and
   `dataImportShares = createSharesTable("analytics_data_import_shares")`.
   The Google Sheets columns are here so 2.3c needs no second migration.
3. **Migration** in `server/plugins/db.ts`: append one entry with the next free
   version at merge time and `name: "data-imports-table"`; `CREATE TABLE IF NOT
   EXISTS` for both tables and the index. Additive only.
4. **Sharing.** `registerShareableResource({ type: "data-import", resourceTable: schema.dataImports, sharesTable: schema.dataImportShares, displayName: "Imported data", titleColumn: "name", getResourcePath: (r) => \`/data-sources?import=${r.id}\`, allowPublic: false, requireOrgMemberForUserShares: true, getDb })`
   in `server/db/index.ts`.
5. **CSV parser** `server/lib/csv.ts` (new, no dependency, see D6): RFC 4180
   quoting and doubled quotes, CRLF/LF, UTF-8 BOM stripped, delimiter detected
   from the first line among comma, tab, semicolon. Invalid UTF-8 is a typed
   `encoding_unsupported` failure. Header row required; blank or duplicate
   headers become `column_2`, `name_2`. Ragged rows: missing cells are `null`,
   extra cells are a typed `ragged_row` failure with the line number.
6. **Type inference** in the same file over the first 1,000 rows: a column is
   `number` only if every non-empty value matches a plain decimal (no thousands
   separators, no currency symbols), `boolean` for true/false, `date` for ISO
   `YYYY-MM-DD` or ISO datetime, otherwise `string`. Empty cells are `null`. A
   value that breaks a column's type turns the whole column into `string`; no
   value is ever silently dropped or zeroed.
7. **Import service** `server/lib/data-imports.ts` (new):
   - `createCsvImport({ bytes, fileName, name, ctx })`: cap 20 MB of file and
     50,000 data rows (`truncated: true`, `sourceRowCount` = total rows seen)
     and 200 columns (typed `too_many_columns`). Mint an attachment ref for
     the original bytes (`mintAttachmentRef`, request org, metadata
     `{ appId: "analytics", resourceType: "data-import" }`); a non-`ok` result
     fails closed with `private_storage_unavailable` (retryable) and nothing is
     written. Stage rows with `upsertStagedDataset({ id: "ds_imp_" + importId, appId: "analytics", ownerEmail, name: "import:" + name, rows, columns })`.
     Insert the import row last. If staging fails after minting, delete the
     minted attachment.
   - `readImportRows(importId, ctx)`: `resolveAccess("data-import", id)`; no
     access is a typed `access_denied`; then `getStagedDatasetMeta` with the
     import's `ownerEmail`; `null` is a typed `import_data_missing`, never `[]`;
     then `getStagedDatasetRows`.
   - `deleteImport(importId)`: `assertAccess(..., "editor")`, delete the staged
     dataset, `deleteAttachment(fileRef)`, delete the row. If the blob delete
     fails, keep going but return `fileDeleted: false`.
   - All failures are one `DataImportError` with a `code`; actions convert it
     with `fail(message, { errorCode, statusCode })` (no bare `Error` in
     actions; `no-bare-error-in-actions` guard).
8. **Actions** (all `defineAction`, zod schemas, `http` set like neighbors):
   - `import-csv`: `{ name?: string, attachmentRef?: string (max 4096), fileBase64?: string, fileName?: string }`,
     exactly one of `attachmentRef` or `fileBase64`. `fileBase64` is capped at
     4 MB decoded so the request fits serverless body limits (D4). Opens refs
     with `resolveAttachment` + `unwrapAttachment` (typed stops for
     `notFound`, `forbiddenScope`, `expired`, `malformed`; retryable for
     `storageUnavailable`). Returns `{ importId, name, rowCount, truncated, sourceRowCount, columns }`.
   - `list-data-imports`: `readOnly`, `accessFilter`, projects only list
     columns (no `fileRef`), limit 100 with `nextCursor`.
   - `get-data-import`: `readOnly`, returns metadata plus up to 20 sample rows.
   - `query-data-import`: `readOnly`, `grounding: true`; schema copied from
     `actions/query-staged-dataset.ts:6-81` with `importId` instead of
     `datasetId`; result carries `truncated` from the import.
   - `rename-data-import`, `delete-data-import`: editor access.
9. **Panel source `import`.** Add `"import"` to
   `shared/dashboard-panel-sources.ts` and to the descriptor-source set. While
   there, replace the chained condition at `dashboard-panel-query.ts:106-114`
   with a `DESCRIPTOR_PANEL_SOURCES` set and a serializer map, so the next
   descriptor source is one entry. Descriptor:
   `{ "importId": "imp_...", "where"?, "groupBy"?, "aggregate"?, "select"?, "orderBy"?, "orderDir"?, "limit"? }`
   validated with the same zod schema as `query-data-import`. Resolver branch
   calls `readImportRows`, then `runAggregateQuery`, returns
   `{ rows, schema, truncated }`; `access_denied` and `import_data_missing`
   throw with `code: message` like `runProgramPanel` does
   (`dashboard-panel-query.ts:390-402`). Label "Imported data" in
   `PanelEditorDialog.tsx` (SQL textarea shows the JSON descriptor, as for
   `program`). Embeddable in `/chart` (D5).
10. **Agent context.** Do not add the new actions to `INITIAL_TOOL_NAMES`;
    tool search finds them. `grounding: true` on `query-data-import` is what
    makes answers from it count as data.
11. **Application state.** None in this unit (2.3b adds `importId` to
    navigation).
12. **Skills.**
    - `.agents/skills/data-querying/SKILL.md`: "Imported data" section: use

## 4. Copy

This unit adds no component strings. Agent-facing messages (English, tool
results):

- `private_storage_unavailable`: "File storage isn't available right now, so the file wasn't imported. Try again in a few minutes."
- `too_large`: "This file is larger than 20 MB. Split it or import it from Google Sheets."
- `inline_too_large`: "Files sent directly are limited to 4 MB. Attach the file in chat or use the import button instead."
- `encoding_unsupported`: "This file isn't UTF-8 text. Save it as CSV UTF-8 and try again."
- `ragged_row`: "Line {{line}} has more cells than the header row."
- `too_many_columns`: "This file has more than 200 columns."
- `access_denied`: "You don't have access to this imported data."
- `import_data_missing`: "The rows for this import are missing. Import the file again."
- truncated result note: "Imported the first 50,000 of {{total}} rows."

Panel source label (provider-style label, same convention as the other
labels in `PanelEditorDialog.tsx:69-76`, which are not catalog-backed):
"Imported data". If the reviewer wants it localized, add
`panelEditor.sourceImport` to all eleven catalogs in `app/i18n/`
(`en-US.ts`, `ar-SA.ts`, `de-DE.ts`, `es-ES.ts`, `fr-FR.ts`, `hi-IN.ts`,
`ja-JP.ts`, `ko-KR.ts`, `pt-BR.ts`, `zh-CN.ts`, `zh-TW.ts`). Unlike provider
names, "Imported data" is translatable prose, so the default is: **add the
catalog key** (D9).

No em dashes.

## 5. Tests

- `server/lib/csv.spec.ts`: quoted commas and newlines, doubled quotes, BOM,
  CRLF, tab and semicolon detection, duplicate headers, ragged rows, invalid
  UTF-8, type inference (a stray "n/a" makes a numeric column `string`).
- `server/lib/data-imports.spec.ts` (PGlite-backed if the template's other
  store specs are; follow `server/lib/dashboards-store.*.spec.ts`): create,
  truncation at 50,000 with `sourceRowCount`, storage unavailable writes
  nothing, staging failure deletes the minted blob, a non-owner without a
  share gets `access_denied`, a missing staged dataset gives
  `import_data_missing` not `[]`, delete removes all three.
- `actions/import-csv.spec.ts`: exactly one input; 4 MB inline cap; each
  attachment outcome maps to the right error code.
- `server/lib/dashboard-panel-query` import case: descriptor validation and a
  shared viewer can render; an unshared viewer gets `access_denied`.
- `packages/core/src/provider-api/staged-datasets-store` spec: a second owner
  is not blocked by the first owner's rows.
- No source-reading tests.

Local, with file storage configured (Settings, File uploads; private blob

2. `pnpm action import-csv --fileName deals.csv --fileBase64 "$(base64 -i deals.csv)"`
   returns an `importId` and the right `rowCount`.
3. `pnpm action query-data-import --importId <id> --groupBy '["stage"]' --aggregate '[{"column":"amount","op":"sum"}]'`
   matches a spreadsheet pivot of the same file.
4. Add a panel with `source: "import"` through `mutate-dashboard`, open the
   dashboard, confirm it renders with no console errors.
5. With file storage turned off, step 2 fails with
   `private_storage_unavailable` and no row exists.

## 8. Defaults for open questions

- **D1** Limits: 20 MB file, 50,000 rows (more are cut with `truncated`), 200
  columns.
- **D2** New imports default to organization visibility when the creator has
  an org, so a dashboard shared in the org renders for teammates; personal
  otherwise.
- **D3** Storage is required. With no private storage the import fails closed;
  rows are never stored without the original file.
- **D4** Inline base64 upload capped at 4 MB; larger files go through a chat
  attachment ref (2.3b) or Google Sheets (2.3c). A chunked upload route is a
  follow-up if users hit the cap.
- **D5** `import` panels are embeddable; access is checked per viewer.
- **D6** Own small CSV parser instead of a dependency. If a reviewer prefers a
  library, check the latest version with `pnpm view` first.
- **D7** CSV and TSV only. Excel import is a follow-up.
- **D8** Use `server/db/schema.ts`'s existing `table` helper so the file stays
  consistent, even though the `storing-data` skill prefers `drizzle-orm/pg-core`
  builders; switching the whole file is a separate change.
- **D9** "Imported data" goes in the catalog under `panelEditor.sourceImport`.
- **D10** Core quota is per owner with the same numbers.
- **D11** Dashboard filter variables are not interpolated into import
  descriptors in this unit; the panel shows the whole dataset query.

## 9. Do not

- No behavior changes outside this unit beyond the per-owner quota (which is
  required for imports to work on shared deployments).
- Additive-only schema: new tables only; no changes to `staged_datasets`.
- No new `/api` routes; uploads in this unit go through actions.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value:
  missing rows are `import_data_missing`, not an empty table; a cut file says
  `truncated`.
- No large payloads in SQL: never store the file body, base64 or a `data:` URL
  in `analytics_data_imports`, settings or `application_state`; only the
  attachment ref.
- Never truncate an attachment ref.
