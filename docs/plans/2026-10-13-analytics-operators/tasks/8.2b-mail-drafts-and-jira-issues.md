## 1. Goal

An investigation finds the 14 accounts whose usage dropped after a release.
The user clicks "Draft emails to affected accounts…". Mail gets one queued
draft per account, written by Mail's agent from a short brief and a few
facts per account, and the card in Analytics says "14 drafts in Mail" with
"Open draft" into Mail's draft queue. Nothing is sent: the user reviews and
sends in Mail. Accounts with no email on file are listed as skipped.

The user also clicks "File an issue…". The agent drafts a Jira issue in
Analytics (summary, description, the evidence and a link back). The card
shows "Confirm…", which opens a dialog with the project, issue type and
every field that will be written. Only "File issue" in that dialog, or an
agent call the user approves in chat, creates the issue. The card then
shows the issue key and "Open in Jira".

## 2. What the code does today

- **Mail queued drafts.** `queue-email-draft` queues a draft "for an
  organization member to review, edit, and send" and returns `reviewUrl`
  (`templates/mail/actions/queue-email-draft.ts:7-63`). A row is one draft
  to one recipient set with status `queued`, `in_review`, `sent` or
  `dismissed` (`templates/mail/server/lib/queued-drafts.ts:17`,
  `:191-254`). Queuing needs an active organization and membership
  (`:125-145`). Mail's agent is told to "draft/queue by default" and to use
  `queue-email-draft` for teammate requests (`templates/mail/AGENTS.md:34`,
  `:51`). The review pages are `templates/mail/app/routes/draft-queue.tsx`
  and `draft-queue.$id.tsx`. Mail exposes no draft read over A2A (only
  `get-email`, `get-thread`, `list-emails`, `list-inbox-threads`,
  `search-emails` and `sync-inbox` carry `publicAgent`).
- **A2A ledger kinds.** `ArtifactReceipt.kind` has no draft kind
  (`packages/core/src/artifacts/detect.ts:1-30`), so a queued draft cannot
  be verified across A2A today.
- **Recipients.** Account links carry `email` for Stripe customers and
  product users, never raw provider records
  (`server/db/schema.ts:1003-1030`; the identity policy calls it "a
  customer's address", `server/db/index.ts:50-57`).
- **Jira is read-only in Analytics.** The `jira` action is `readOnly: true`
  with modes `search`, `issue`, `projects`, `statuses`, `boards`, `sprints`,
  `analytics` (`actions/jira.ts:18-34`), and needs `JIRA_BASE_URL`,
  `JIRA_USER_EMAIL`, `JIRA_API_TOKEN` or the Jira connection
  (`:69-73`). Every call is a GET through `executeProviderApiRequest`
  (`server/lib/jira.ts:11-48`).
- **The Jira OAuth connection asks only for read scopes**:
  `["read:jira-work", "read:jira-user", "offline_access"]`
  (`packages/core/src/connections/catalog.ts:507`). Creating an issue needs
  `write:jira-work`. API-token connections already carry the user's write
  permission.
- **Provider writes need approval.** Analytics' `provider-api-request`
  accepts POST, PUT, PATCH and DELETE (`actions/provider-api-request.ts:18`,
  `:40`) and passes no `needsApproval`, so those writes run unconfirmed.
  This unit files issues with its own action that needs approval, so the
  dialog shows the exact fields and nothing reaches Jira unconfirmed.
- **The integrations UI already shows a missing scope.** An OAuth
  connection that lacks a scope its catalog entry lists reports
  `needs_reauth` (`connectionStatusForProvider`,
  `packages/core/src/workspace-connections/store.ts:1001-1015`). Dispatch's
  Integrations list labels it "Needs reauth"
  (`templates/dispatch/app/i18n-data.ts:61`), and Analytics' Data sources
  shows "Reconnect needed" on the source (`app/lib/data-source-status.ts:241`)
  with the workspace OAuth setup for admins
  (`shouldShowWorkspaceOAuthSetup`, `:148-161`; Jira is a workspace OAuth
  source at `:117-124`).

## Plan corrections

- Jira is not a sibling app: Analytics owns the Jira connection, so filing
  an issue is an Analytics provider write behind the confirm gate, not an
  A2A handoff. The issue draft lives in Analytics until confirmed.
- The OAuth Jira connection cannot file issues until it asks for
  `write:jira-work`. This unit adds the scope to the shared Jira
  connection: the owner decided that people who connect Jira want read and
  write access, and the connection is managed in the workspace's
  Integrations. Existing OAuth connections reconnect once.

## 3. Build

1. **Kinds.** Append `email_drafts` (target `mail`) and `issue` (target
   `jira`, local) to `INSIGHT_ACTION_KINDS` (`shared/insight-actions.ts`,
   8.2a). `list-next-actions`: `email_drafts` is available when the source
   names at least one account (an output or item with account map ids or
   domains that resolve) and Mail resolves; `issue` when a Jira connection
   or key resolves, else `not_connected`.
2. **Core (`packages/core`, minor changeset).** Add `email-draft` to
   `ArtifactReceipt.kind`, map `queue-email-draft` to it in
   `TOOL_ARTIFACT_KINDS` (`packages/core/src/artifacts/detect.ts:60-110`),
   take `id` and `reviewUrl` from its result, and allow `email-draft` in
   `ARTIFACT_RESOURCE_TYPES` (`packages/core/src/a2a/artifact-response.ts:112-121`).
   In `packages/core/src/connections/catalog.ts:507` add `write:jira-work`
   to the Jira scopes. No new reconnect UI: existing OAuth Jira connections
   then report `needs_reauth`, so Dispatch's Integrations list shows "Needs
   reauth" and Analytics' Data sources shows "Reconnect needed" on Jira with
   the workspace OAuth setup. An admin reconnects once there and the new
   grant carries the write scope. API-token connections are unchanged.
3. **Email drafts (Analytics side).** In `buildInsightArtifact`, an
   `email_drafts` item is `{ accountId, name, domain, email, facts[] }`:
   `email` comes from the account's Stripe link, else its most recently seen
   product user link, read from the account map; `facts` are at most three
   lines of 200 characters the agent writes from the source. Accounts with
   no email go to `skipped` on the record, not into the artifact. At most 25
   accounts per handoff. The handoff objective tells Mail to queue one draft
   per account with `ownerEmail` set to the requester, `source: "agent"`, a
   `context` line naming the investigation and its link, and never to send.
   The outcome reader turns verified `email-draft` identities into
   `DraftRef`s labeled with the account name; fewer drafts than accounts
   leaves the record `draft` and lists the missing accounts; none is
   `failed`. Mail's "organization required" error maps to
   `receiver_failed` with that message.
4. **Mail.** One sentence in `templates/mail/AGENTS.md` (the drafting
   bullet at `:34`): when another workspace app asks for drafts, queue them
   with `queue-email-draft` for the requester and never send. No new Mail
   action.
5. **Issue drafts (Analytics).**
   - `actions/draft-jira-issue.ts`: input `{ actionId, projectKey?,
     issueType?, summary (max 255), description (Markdown, max 8,000),
     labels? (max 10) }`. Saves the fields into the record's artifact and
     sets `draft`. It writes nothing to Jira. Returns the card.
   - `actions/file-jira-issue.ts`: input `{ actionId, projectKey, issueType,
     summary, description, labels? }`; `needsApproval: true` for agent
     calls. Claims the record (`draft` to `confirming`, conditional update),
     converts the Markdown to Atlassian Document Format with a small pure
     helper (paragraphs, headings, bullet lists, links, code), appends the
     evidence block (source, window, rows and as-of from 3.4a's evidence for
     answers, or the notebook's named cells) and the link back, and POSTs
     `/rest/api/3/issue` through `executeProviderApiRequest` with provider
     `jira`. Success sets `confirmed`, `confirmed_by`, `confirmed_at` and a
     `DraftRef` `{ app: "jira", id: <key>, url }`, where `url` is built from
     the connection's site URL; when the site URL is unknown, `url` is null
     and the card shows the key, never a guessed link. A 401 or 403 returns
     `jira_scope_missing`; a 400 returns Jira's field errors; any failure
     sets the record back to `draft` with the error. Filing an already
     confirmed record returns its key and files nothing.
   - `actions/jira.ts`: add mode `issueTypes` (`project` required) that
     reads `/rest/api/3/issue/createmeta/{project}/issuetypes`, so the
     dialog and the agent list the same types.
6. **UI (gated).**

   - Email card: "N drafts in Mail", account rows linking to each draft's

     Jira source (its "Reconnect needed" state and the workspace OAuth

7. **Application state.** None new. `view-screen` already lists the

## 8. Defaults for open questions

- [Default] One queued draft per account, at most 25 per handoff, to the
  Stripe billing email, else the latest product user email.
- [Default] Mail's agent writes the email text; Analytics sends facts, not
  copy.
- [Default] The issue draft lives in Analytics; nothing reaches Jira before
  File issue.
- [Default] No file attachments on the issue in v1; the evidence is text and
  a link back.
- [Decided by the owner, 2026-10-14] The shared Jira connection asks for
  read and write access (`write:jira-work`). Existing OAuth connections
  reconnect once through the integrations UI.

## 9. Do not

- Do not send email from Analytics or ask Mail to send.
- Do not take recipient addresses from agent text.
- Do not create Jira issues through `provider-api-request`.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
