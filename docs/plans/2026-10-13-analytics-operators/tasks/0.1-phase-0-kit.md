internal Analytics usage by role and question type from the actions the app

## 2. What the code does today

All paths are relative to `templates/analytics/`.

- `list-dashboard-usage-stats` returns one row per dashboard in the active org
  with owner, visibility, pageviews, edit count, engagement events, unique
  viewers, saved views and archive state (`actions/list-dashboard-usage-stats.ts:9-31`).
  It is org owner or admin only (`list-dashboard-usage-stats.ts:126-127`) and
  reads `analytics_events` rows whose path is under `/dashboards/` or
  `/adhoc/` (`list-dashboard-usage-stats.ts:166-240`). It has **no per-user
  breakdown and no role**: `uniqueUserCount` is a count only.
- Nothing in the app stores a person's job role. Org roles (owner, admin,
  member) are permissions, not job functions. So "by role" needs a role map
  the plan owner supplies.
- Agent runs are first-party events with `event_name = '$ai_generation'`. Their
  properties include `run_id`, `thread_id`, `duration_ms`, `status`,
  `tool_calls`, `failed_tools` and a bounded `tools` array of tool names
  (never args or results) (`.agents/skills/data-querying/SKILL.md:81-90`).
  That gives question type (by tool family) and time-to-answer without
  reading anyone's chat text.
- `query-agent-native-analytics` runs scoped SQL over `analytics_events`,
  `analytics_event_daily_rollups` and `analytics_user_days`, routes to
  BigQuery for orgs whose events live there, and excludes QA identities
  (`actions/query-agent-native-analytics.ts:52-58`).
- The client also emits `agent_chat_lifecycle` events with `phase`,
  `chat_surface` and `thread_id` (`packages/core/src/client/analytics.ts:1449-1464`,
  repo-relative), which separates the full-page Ask surface from the sidebar.
- Demo data today is a Prometheus demo source (`server/lib/demo-source.ts`),
  not Stripe, HubSpot or a support tool. The cross-tool demo question needs
  revenue, CRM and support data, so the interview demo needs its own
  synthetic setup until 6.2 lands.

## 3. Build

1. **Create `phase-0/usage-by-role.md`** with these sections. Use the content
   below as the draft; tighten wording, keep the steps.

   **Before you start.** Run everything from the Analytics app's Ask page,
   signed in as an org owner or admin of the internal org. Results stay on
   your machine. Keep the role map in the repo's gitignored `.tmp/phase-0/`
   folder, never in `docs/`.

   **Step 1. Role map.** Make `.tmp/phase-0/roles.csv` with columns
   `email,role`. Roles: `founder`, `product`, `growth`, `revops-gtm`,
   `engineering`, `data`, `other`. One row per person who used Analytics in
   the last 90 days (Step 2 lists them by user key).

   **Step 2. Agent questions by person, week and question type.** Paste into
   Ask:

   > Using query-agent-native-analytics, for the last 90 days of
   > `$ai_generation` events where app is analytics, return one row per user
   > key and ISO week with: runs, completed runs, failed runs, median and 90th
   > percentile duration_ms, and the run count per tool family below. Classify
   > a run by the first matching family in its `tools` array. Do not read
   > thread text. Return at most 5,000 rows as a table I can download.

   Tool families (first match wins):

   | Family | Tool names |
   | --- | --- |
   | Dashboard edit | `mutate-dashboard`, `update-dashboard`, `compose-dashboard`, `reorder-dashboard-panels`, `restore-dashboard-revision` |
   | Product events | `query-agent-native-analytics`, `list-event-catalog`, `list-session-event-names` |
   | Warehouse | `bigquery`, `bigquery-query`, `search-bigquery-schema`, `bigquery-table-info` |
   | Revenue | `stripe`, or `provider-api-request` with provider stripe |
   | CRM | `hubspot-deals`, `hubspot-records`, `hubspot-metrics`, `hubspot-pipelines` |
   | Calls | `gong-calls`, `gong-native-insights`, `run-gong-native-insight` |
   | Support | `pylon-issues` |
   | Account | `account-deep-dive` |
   | Replay and errors | `list-session-recordings`, `get-session-replay-summary`, `list-error-issues`, `get-error-issue` |
   | Code and programs | `run-code`, `get-data-program`, `list-data-programs` |
   | Other provider | any other `provider-api-request` |
   | No tools | empty `tools` |

   If the agent's query fails or the `app` value differs, ask it to first list
   distinct `app` values for `$ai_generation` in the last 7 days.

   **Step 3. Dashboard usage.** Ask: "Run list-dashboard-usage-stats and give
   me the table." Download it.

   **Step 4. Join locally.** Join Step 2 and Step 3 to the role map on email or
   user key, in a spreadsheet or a script under `.tmp/phase-0/`. Produce:
   - Weekly active askers by role.
   - Runs by role and tool family, as share of that role's runs.
   - Median and 90th percentile time-to-answer by tool family.
   - Failed-run share by tool family.
   - Dashboards created, edited and viewed by owner role.
   - Share of runs that touch more than one family (cross-tool questions).

   **Step 5. Write up.** Record only aggregates in
   `phase-0/usage-by-role-results.md`. Suppress any role group with fewer
   than 3 people. No names, emails, dashboard titles, customer names or
   costs.

2. **Create `phase-0/interview-script.md`** for 30-minute calls with five
   outside founders (10 to 200 people, no data team) and five outside product
   or growth leads. Sections, in order:

   **Set-up (before the call).** Recruit from people who do not work here.
   Ask permission to record. Prepare the demo on **synthetic data only**: a
   Stripe test-mode account with made-up customers and a few cancelled
   subscriptions, and a HubSpot developer test account with matching made-up
   companies and support tickets, both connected to a local or beta Analytics
   with no internal data. Never show internal dashboards or real customer
   data to an outside person.

   **Opening (2 min).** Who you are, that this is research and nothing is for
   sale on the call, how long it takes, recording consent.

   **Their world (8 min).**
   - What's your role, and how many people are on the team?
   - Which tools hold your company's numbers? Where does revenue live, where
     do customers live, where does product usage live?
   - Tell me about the last time you needed a number you didn't have. What
     was the question, what did you do, and how long did it take?
   - Who do you ask when you need a number? What happens when they're busy?
   - What do you use today for dashboards or analysis? What do you like and
     dislike about it?

   **Product and growth leads only (5 min).**
   - Which funnels and retention views do you check every week?
   - How do you find out something broke or spiked? How fast do you need to
     know?
   - When a metric moves, how do you work out why?

   **Founders only (5 min).**
   - Which numbers do you report to your board or investors, and how do you
     put them together?
   - Have you ever tracked revenue metrics like MRR or churn yourself? Where
     did the numbers disagree?

   **Demo (8 min).** Show one question typed into Ask: "Which churned accounts
   had support escalations last quarter?" Let it run without narrating the
   wait. Then ask:
   - What did you expect to happen?
   - Do you trust that answer? What would you need to see to trust it?
   - How would you answer this today, and how long would it take?
   - What would you ask next?

   **Wrap-up (5 min).**
   - If this worked on your data, what would you stop using?
   - What would stop you connecting your own Stripe or HubSpot?
   - What do you pay for analytics tools today, roughly, and who approves it?
   - Who else should we talk to?

   **After the call.** Fill in a one-page note per interview: segment, team
   size, tools, top three jobs, demo reaction (trust, time, next question),
   blockers to connecting, and one sentence on whether they would use it
   weekly. No names in shared notes; use an interview number.

   **Reading the results.** Tally across the ten calls: how many named a
   cross-tool question unprompted, how many said they'd connect a source in
   the first week, the top blocker, and which segment reacted more strongly.
   That tally answers the plan's open decision 1.

## 9. Do not

- No behavior changes; this unit adds docs only.
- Additive-only schema: no schema changes at all.
- No new `/api` routes for app data; the kit uses existing actions through the
  chat.
- No raw `fetch` from client code; no code at all.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value: if a
  query in the kit fails, the doc says to stop and fix it, not to fill zeros.
- No large payloads in SQL.
- No names, emails, Slack quotes, internal dollar figures, customer names or
  internal URLs in any committed file. The role map and raw exports stay in
  `.tmp/`.
