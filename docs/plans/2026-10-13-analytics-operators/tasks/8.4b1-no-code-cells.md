# 8.4b1 No-code cells: Filter, Table display, Single value and Pivot

Lane E (Holy-shit features). Size M. Gated: the four no-code cell kinds in
the add-cell menu and their editors are new UI; build only after the
"Notebook: no-code cells" screens in `prototypes/analytics-operators/` are
signed off. Where the signed-off prototype differs from this brief, the
prototype wins.

Depends on: 7.1a, 7.1b, 7.2b (the `cells` source and descriptor), 8.4a3 (the
`pivot-table` renderer). Merge after 7.3 and 7.5. Blocks: 8.4b2 (Map cell
uses the same no-code spec), 8.4c (the graph reads no-code inputs).

Paths are relative to `templates/analytics/` unless they start with
`packages/`.

## 1. Goal

In a notebook, someone who doesn't write SQL adds a cell under a result and
picks what it does: Filter (keep rows where plan is Pro and MRR is over 1,000),
Table display (show the columns they want, formatted), Single value (one big
number with its change against a comparison column), or Pivot (rows, columns
and values). Each reads an earlier cell through the chained-cells engine, so
nothing goes back to the warehouse, and each cell's settings are the source of
truth: the SQL it runs is generated from them and shown read-only, so the agent
and the UI edit the same thing.

## 2. What the code does today

- The cell engine exists: `runCellSql({ sql, inputs, maxRows, timeoutMs, signal })`
  (`server/lib/notebook-cell-engine.ts:684-823`), DuckDB in memory, one
  statement that must be a read query (`:756-776`), inputs capped at
  `CELL_ENGINE_MAX_INPUT_ROWS = 100_000` and `CELL_ENGINE_MAX_INPUT_BYTES` of
  25 MB (`:24-25`, checked in `prepareInputs` `:418-485`), dialect
  `CELL_ENGINE_DIALECT = "DuckDB"` (`:23`), typed errors
  `CellEngineUnavailableError`, `CellEngineTimeoutError`,
  `CellEngineInputTooLargeError`, `CellEngineSqlError` (`:52-113`).
- Notebooks, the `cells` source and the descriptor
  `{ inputs: string[]; sql: string }` are not built: 7.1a, 7.1b and 7.2b are
  briefs (`tasks/7.1a-notebook-model-and-actions.md`,
  `tasks/7.1b-notebook-page.md`, `tasks/7.2b-chained-cells.md`). No notebook
  code exists on the integration branch besides the engine.
- `shared/dashboard-panel-sources.ts:1-11` is the one source list (2.1a);
  7.2b adds `cells` there.
- The single-value renderer is `MetricRenderer`
  (`app/components/dashboard/SqlChart.tsx:1645-1677`): it picks `yKey` or the
  first number column, sums when there are several rows, formats with
  `yFormatter`, and has no comparison or change.
- Table display today is `TableRenderer` with `config.columns`
  (`SqlChart.tsx:1858`, columns `:1873-1882`); 1.1a adds the column menu.
- A precedent for "settings are the source, SQL is derived": 4.1b's
  `config.growth`, which normalization recompiles into `sql` (1.1a brief,
  step 4, and `tasks/4.1b-funnel-definitions-and-compiler.md`).
- Filter types the notebook already has as inputs are dashboard filters
  (`types.ts:22-42`); a no-code Filter cell is different: it filters rows of
  one upstream cell, not a dashboard-wide variable.

## Plan corrections

- "No-code cells on 7.1a's cell model" means no new storage. A no-code cell is
  a `cells`-source panel whose `config.noCode` spec compiles to the 7.2b
  descriptor; the compiled SQL is what runs. No second execution path.
- The Map cell is split into 8.4b2 because it needs a geography dependency.

## 3. Build

1. **Spec.** New `shared/no-code-cells.ts`:
   - `NoCodeSpec` union:
     - `{ kind: "filter"; input: string; match: "all" | "any"; conditions: { column: string; op: "eq" | "neq" | "gt" | "gte" | "lt" | "lte" | "contains" | "in" | "isEmpty" | "notEmpty"; value?: string | number; values?: string[] }[] }` (at most 10 conditions)
     - `{ kind: "table"; input: string; columns: TableColumnConfig[]; sort?: { column: string; direction: "asc" | "desc" }; limit?: number }`
     - `{ kind: "value"; input: string; column: string; agg: "sum" | "avg" | "min" | "max" | "count" | "last"; compareColumn?: string; compareLabel?: string }`
     - `{ kind: "pivot"; input: string; pivotTable: <8.4a3 shape> }`
   - `compileNoCodeCell(spec, inputColumns): { inputs: [input]; sql: string }`:
     DuckDB SQL over the input table, identifiers quoted the way 7.2b's engine
     wrapper quotes them, values as escaped literals (never string-joined
     unescaped). Filter compiles to `WHERE`; table to `SELECT <cols> ORDER BY
     LIMIT`; value to one aggregate row (`value`, `compare`, `change`); pivot
     to `SELECT *` (the pivot runs in the 8.4a3 builder on returned rows).
   - Typed errors: `no_code_input_missing`, `no_code_column_missing` (names the
     column), `no_code_invalid`.
2. **One normalization boundary.** In `normalizeDashboardConfig`
   (`shared/dashboard-config-normalization.ts`), a panel with `config.noCode`
   gets `source: "cells"` and `sql` = the compiled descriptor, every save. A
   save that sends a hand-edited `sql` for a no-code panel is rejected by
   validation (`collectDashboardConfigIssues`) with "This cell is built from
   its settings. Edit the settings, or convert it to SQL." Do not add a second
   `if` per kind elsewhere: compile once here, and validation, verification,
   reports and the browser read the compiled descriptor.
3. **Chart types.** Filter and Table display cells use `chartType: "table"`;
   Pivot uses `pivot-table` (8.4a3); Single value uses `metric` with two new
   config keys `compareKey` and `compareLabel`, registered in
   `PANEL_CONFIG_KEYS` with `onlyFor: ["metric"]`. `MetricRenderer` shows the
   change below the value when `compareKey` is set ("+12.4% vs last month"),
   in `text-muted-foreground`; no red or green for direction, an arrow icon
   (`IconArrowUpRight` / `IconArrowDownRight`) carries it.
   Register `noCode` in `PANEL_CONFIG_KEYS` (all chart types the four kinds
   use).
4. **Editors (gated UI).** 7.1b's add-cell menu gains, under a separator,
   Filter, Table, Single value and Pivot (text-only items). Each opens the
   cell with an inline settings row above its result:
   - Reads from: 7.2b's picker, single select.
   - Filter: Match all or any (`Select`), then one row per condition: Column
     (`Select` of input columns), Operator (`Select`, labels by column type),
     Value (`Input`, `notebook.noCode.conditionValue`, or a multi-select of distinct values when the input has at
     most 50), and Remove; Add condition.
   - Table: 1.1a's column menu works on the result; Sort and Limit `Select`s.
   - Single value: Column, Aggregation, Compare to (optional column), Label.
   - Pivot: 8.4a3's Rows, Columns and Values controls.
   - A collapsed Generated SQL section shows the compiled SQL read-only with a
     Convert to SQL cell button that drops `config.noCode` and keeps the SQL
     (one `updatePanel`), so a user can outgrow the no-code cell.
   Every change saves through the page's save path (7.1b) with `applyPanelEdit`.
5. **Errors.** Typed errors map to 1.5a's panel error states with a fix button
   that opens the settings row on the bad field.
6. **Agent.** `mutate-dashboard` `insertPanel` / `updatePanelPath` with
   `config.noCode`; the server compiles. Add `compile-no-code-cell`
   (read-only, `http: { method: "GET" }`) returning the compiled descriptor or
   the typed error, so the agent and the Generated SQL section see the same
   output.
7. **Application state.** `selected-object` for a no-code cell adds
   `noCodeKind` (7.3's notebook selection fields stay). No new key.
8. **Skills.** `.agents/skills/notebooks/SKILL.md` (created by 7.1a): a "No-code
   cells" section with the four spec shapes, that the spec is the source and
   SQL is derived, that a hand SQL edit means Convert to SQL first, and the
   engine caps. Read `.agents/skills/writing-agent-instructions` first.
9. **Changelog.** `agent-native changelog add "Notebook cells you build without SQL: filter, table, single value and pivot" --type added`.

## 8. Defaults for open questions

- [Default] Four kinds in v1: Filter, Table, Single value, Pivot. Map is 8.4b2.
- [Default] Each no-code cell reads exactly one cell above it.
- [Default] Generated SQL is visible read-only; Convert to SQL is one way.
- [Default] Single value change uses an arrow, not red and green.

## 9. Do not

- Do not add a second execution path: no-code cells run as `cells` panels.
- Do not let a stored no-code panel's `sql` drift from its spec.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
