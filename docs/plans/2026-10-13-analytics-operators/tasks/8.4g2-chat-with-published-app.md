# 8.4g2 Chat with a published app, scoped to its data

Lane E (Holy-shit features). Size M. Gated: the Ask about this app entry and
the scoped chat state in the app view are new UI; build only after the
"Published app: ask" screen in `prototypes/analytics-operators/` is signed
off. Where the signed-off prototype differs from this brief, the prototype
wins.

Depends on: 7.5 (published apps), 7.2b (the cell engine path), 1.7a (built).
Merge after 8.4g1. Blocks: 8.5c (embedded apps reuse the scope).

Paths are relative to `templates/analytics/` unless they start with
`packages/`.

## 1. Goal

A teammate who can view a published notebook app (not edit it) opens it,
clicks Ask about this app and asks "which region grew fastest last quarter?".
The agent answers from that app's cells only, with the viewer's current
inputs, and says which cells it used. It cannot query other sources, cannot
edit the notebook and cannot reach data the app does not show. If the answer
needs data the app doesn't have, it says so instead of reaching for the
warehouse.

## 2. What the code does today

- Any signed-in user can use the agent chat; a dashboard viewer gets the full
  tool set. Analytics configures no per-run tool allowlist:
  `INITIAL_TOOL_NAMES` (`server/lib/agent-chat-plan-mode.ts:2-23`, wired at
  `server/plugins/agent-chat.ts:1359`) is a starter catalog for lazy loading,
  not a permission list, and the full registry stays reachable through
  `tool-search` (`packages/core/src/agent/production-agent.ts:1840-1850`).
  Edits are blocked only in the store (`assertAccess("dashboard", id,
  "editor")`, `server/lib/dashboards-store.ts:1722`).
- Core has the seam for a real per-run surface: `resolveActionSurface`
  (`packages/core/src/agent/production-agent.ts:1822`) returning
  `AgentActionSurface { allowedActionNames; actionScope? }` (`:1265-1268`)
  with details `{ event, ownerEmail, orgId, threadId, mode, ... }`
  (`:1286-1297`); plugin option at
  `packages/core/src/server/agent-chat/plugin-options.ts:156`. Setting it
  disables trusted shell tools (`agent-chat-plugin.ts:2014-2016`). Analytics
  does not set it.
- The sidebar chat is scoped to the dashboard on screen:
  `analyticsScope = { type: "dashboard", id, contextKey }` from the path
  (`app/components/layout/Layout.tsx:64-80`).
- The agent learns the open dashboard from `view-screen`, which loads it with
  the caller's own access (`actions/view-screen.ts:275-291`) and
  `buildDashboardAgentContext` (`server/lib/agent-readable-resource-context.ts:193-237`,
  with `role`, `canEdit`, `canManage` at `:224-226`).
- `query-dashboard-panel` takes raw SQL from the client and runs it with the
  caller's credentials; `dashboardId` and `panelId` are only used to attribute
  cost (`actions/query-dashboard-panel.ts:36-44`, `:62-66`); it has no
  dashboard access check. It is `agentTool: false` (`:45-47`). This unit must
  not route app answers through it.
- Shared chats open read-only with Continue (1.7a): `resolveThreadAccessWithRole`
  (`packages/core/src/chat-threads/store.ts:962`), `SharedThreadReadOnlyBar`
  in the toolkit.
- 7.5 (brief) publishes an app to the notebook's share list and renders app
  mode at `?mode=app`; viewers run cells with their own credentials.

## Plan corrections

- "Scoped to its data" has to be enforced by the server, not by the prompt:
  the default agent can reach every source the viewer can. This unit sets
  the core action surface for these runs, and adds two read actions that
  answer only from the app's cells.

## 3. Build

1. **App scope.** When the chat starts from app mode, the client sends the
   scope `{ type: "notebook-app", id: dashboardId }` (extend
   `analyticsScope` in `Layout.tsx:64-80` when `notebookMode === "app"`). The
   scope is bound to the thread at creation and cannot be changed by a later
   message.
2. **Action surface.** In `server/plugins/agent-chat.ts`, set
   `resolveActionSurface`: for a thread whose scope is `notebook-app`, load the
   notebook with `getDashboard` as the run's user; if they are not an editor
   and the app is published, return `{ allowedActionNames: [...], actionScope: { kind: "notebook-app", dashboardId } }`
   with exactly `view-screen`, `get-notebook-app-data`,
   `query-notebook-app-cells` and `set-search-params` (to change the app's
   inputs). Nothing else: no provider, query, data program, run-code,
   navigation, definition or write actions. Editors and unpublished notebooks get
   the default surface. A load failure fails the run with a plain message;
   it never falls back to the default surface.
3. **Read actions** (both `readOnly`, `http: { method: "GET" }`, and both
   refuse with `not_in_app_scope` when called outside the scope's dashboard):
   - `get-notebook-app-data`: `{ dashboardId, inputs?: Record<string,string> }`.
     Checks viewer access and `config.app.published`. Builds every
     non-`hideInApp` cell's query from the stored config (never from client
     SQL), runs it with the caller's credentials through
     `runDashboardPanelQuery`, and returns per cell `{ cellId, title, kind, columns, rows (first 200), rowCount, truncated, status }`
     plus the inputs used. Failed cells come back with their typed status,
     not as empty rows. Bounded by the existing concurrency limit and a total
     deadline.
   - `query-notebook-app-cells`: `{ dashboardId, sql, inputs? }`: one DuckDB
     read query over the app's visible cells as tables named by cell id,
     through `runCellSql` (`server/lib/notebook-cell-engine.ts:684-823`,
     single SELECT, locked down, input caps `:24-25`). This lets the agent
     aggregate and compare inside the app's data and nowhere else.
4. **Prompt rule.** When the scope is `notebook-app`, add one short system
   rule (through the existing prompt-rules list in
   `server/lib/analytics-prompt-rules.ts`): answer only from these cells;
   name the cells used; if the question needs other data, say what is missing
   and suggest asking the notebook's owner. Keep it in the scope branch so
   other runs' prompts do not grow.
5. **UI (gated).** In app mode (7.5), for viewers, the header shows an outline
   Ask about this app button at the compact size (`Button variant="outline"
   size="sm" className="text-xs gap-1.5"`, as 7.1b's Re-run) with
   `IconMessageCircle`. It opens the agent sidebar in the app scope with the
   composer placeholder "Ask about {{app}}". The sidebar header shows a chip
   "Answers from this app only" with a tooltip listing what the agent can and
   cannot do. Suggested questions are out of scope.
6. **Sharing a scoped chat.** A scoped thread shared with another viewer opens
   read-only (1.7a); Continue forks it with the same scope, re-evaluated for
   the new user.
7. **Application state.** `navigation.notebookMode` (7.5) is what the client
   uses to pick the scope; the server trusts only the thread's stored scope
   and the role check.
8. **Skills.** `.agents/skills/notebooks/SKILL.md`: "Answering inside a
   published app": the two actions, citing cells, and refusing out-of-scope
   data plainly.
9. **Changelog.** `agent-native changelog add "Ask questions about a published notebook app, answered from that app's data" --type added`.

## 5. Tests

- `server/plugins/agent-chat.action-surface.spec.ts` (new): a viewer's
  `notebook-app` thread gets exactly the allowed names; an editor gets the
  default; an unpublished app gets the default; a load failure fails the run
  (never the default surface).
- `actions/get-notebook-app-data.spec.ts` (new): access and published checks;
  queries built from stored config, never client SQL; `hideInApp` cells
  excluded; failed cells keep their status; out-of-scope refusal.
- `actions/query-notebook-app-cells.spec.ts` (new): runs over visible cells
  only; a non-SELECT is refused by the engine; a hidden cell name is
  `input_missing`.
- `app/components/layout/Layout.spec.tsx` (extend or new): app mode sends the
  `notebook-app` scope.

No source-reading tests.

## 8. Defaults for open questions

- [Default] Scoped chat applies to viewers of published apps; editors get the
  normal agent.
- [Default] Answers use the viewer's credentials, as the app's cells do.
- [Default] 200 rows per cell to the agent; aggregation goes through
  `query-notebook-app-cells`.

## 9. Do not

- Do not route app answers through `query-dashboard-panel` or any action that
  takes SQL against a source.
- Do not rely on the prompt alone for the scope.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
