# 8.3a Named outputs and the read-only data contract

Lane E (Holy-shit features). Size M. Not gated (no new UI; 8.3c adds the
control that names outputs, and the agent can name them today through
`mutate-dashboard`).

Depends on: 7.1a (`panelRunsQuery`; merge after it). Works with 7.5's input
cells when present. Blocks: 8.3b, 8.3c, 8.3d.

Paths are relative to `templates/analytics/` unless they start with
`packages/` or `templates/`.

## 1. Goal

A dashboard or notebook can mark some of its query cells as **named
outputs**: `mrr_by_month`, `at_risk_accounts`, `weekly_signups`. Another
workspace app (the Design app in 8.3b, the published mini-app in 8.3d) can
then read those outputs, and only those, through one Analytics action. The
read runs as the person asking, checks they can open the dashboard, applies
the dashboard's own inputs, caps the rows, says how fresh each output is,
and fails with a typed reason instead of an empty table. This is the single
data channel a generated app gets: it never sees SQL, sources or
credentials, and it cannot ask for anything the notebook does not name.

**Requirement (owner, 2026-10-14).** Anyone who reads through this contract,
including people using a published app (8.3d), sees only data they can
already see in Analytics: the same dashboard access check, their own
credentials, and the same inputs. No read ever runs with the author's or a
service identity.

## 2. What the code does today

- Panels are `{ id, title, sql, source, chartType, width, config }` inside a
  dashboard config with `filters` (`app/pages/adhoc/sql-dashboard/types.ts:107`,
  `:126`, `:141`); a filter is `{ id, label, type, default?, options? }`
  (`:36-42`). Renderer config keys are registered in `PANEL_CONFIG_KEYS`
  (`shared/panel-render-contract.ts:45`), and config validation lives in
  `collectDashboardConfigIssues` (`actions/update-dashboard.ts:267`). 7.1a
  adds `panelRunsQuery` to the contract (brief 7.1a, step 3).
- The browser's panel read takes a client-built query and is UI-only
  (`agentTool: false`, `actions/query-dashboard-panel.ts:34-47`), so it
  cannot serve another app.
- Server-side panel reads already exist for reports: `buildPanelQuery`
  interpolates a panel with variables and `runResolvedPanel` runs it with a
  timeout through the same resolver the page uses, returning rows, schema,
  `truncated` and freshness, or `query-failed` / `missing-credential`
  (`server/lib/dashboard-panel-runner.ts:17-26`, `:80-125`). Reports map
  `f_<id>` filters to variables (`server/lib/dashboard-report-render.ts:95-103`).
- Access: `getDashboard(id, ctx)` calls `resolveAccess` and returns null
  without access (`server/lib/dashboards-store.ts:819-842`).
- Read cost is attributed by caller: `page`, `verification`, `inspect`,
  `report`, `alert`, `agent` (`server/lib/panel-read-tracking.ts:14-29`).
- Analytics exposes read actions to sibling apps with `publicAgent: {
  expose: true, readOnly: true, requiresAuth: true }`
  (`actions/hubspot-records.ts:50`). Over A2A, an organization-secret token
  proves only the organization and must not read person-owned data
  (the repo-root `.agents/skills/a2a-protocol/SKILL.md`, "Authentication").
- 7.5 (brief) publishes a notebook as a read-only page inside Analytics:
  input cells are dashboard filters, and cells marked `hideInApp` are left
  out; viewers' own credentials run the queries.

## Plan corrections

- 7.5 stays the quick path: a read-only page inside Analytics. 8.3 is the
  designed path in Design. They share two things, defined once here: the

## 3. Build

1. **Config.** Add `outputName?: string` to `SqlPanelConfig`
   (`types.ts:73`) and register it in `PANEL_CONFIG_KEYS`. Validation in
   `collectDashboardConfigIssues`: `^[a-z][a-z0-9_]{0,47}$`; unique per
   dashboard; only on panels where `panelRunsQuery` is true; at most 24 per
   dashboard. Names are set through `mutate-dashboard` (`setConfigPath`, as in
   `actions/dashboard-mutation-api.ts:141`), so revisions, undo and 1.3b's
   card cover them. No schema change; no migration.
2. **Shared** (`shared/named-outputs.ts`, new): the caps (`MAX_OUTPUTS_PER_READ`
   12, rows default 200 and at most 500 per output, 256 KB of rows per
   read); the result types; `notebookAppCells(config)` (query cells in
   order, minus 7.5's `hideInApp` cells; 7.5 imports it if it lands later,
   or this unit imports 7.5's if it lands first); and `outputNameFromTitle`
   (a unique slug, for 8.3c's dialog).
3. **Library** (`server/lib/named-outputs.ts`, new):
   `readNamedOutputs({ dashboardId, outputs?, inputs?, mode, maxRows },
   ctx)`:
   - Requires a user identity (`getRequestUserEmail()`); an
     organization-only principal gets `user_identity_required`.
   - `getDashboard(dashboardId, ctx)`; null is `dashboard_not_found`
     ("deleted or you no longer have access"), never an empty list.
   - `inputs` keys must be filter ids on the dashboard; values are checked
     against the filter type and options; anything else is `invalid_input`
     naming the key. Unset inputs take the filter default. They become
     variables the same way reports map filters.
   - `mode: "schema"` runs nothing and returns each output's `name`,
     `title`, `chartType` and the dashboard's inputs (id, label, type,
     options, default).
   - `mode: "rows"` runs each requested output with `buildPanelQuery` and
     `runResolvedPanel` under `ctx`, at most 3 at a time, 30 seconds each
     within a 60 second budget, with read caller `app` (add it to
     `PANEL_READ_CALLERS`). Each result is `{ name, status: "ok", columns,
     rows, rowCount, truncated, truncatedReason?, asOf }` or `{ name,
     status: "error", code, message }` with `code` one of
     `output_not_found`, `missing_credential`, `query_failed`, `timed_out`.
     Rows beyond `maxRows` or the byte budget set `truncated: true` with
     `truncatedReason` `max_rows` or `byte_budget`. Messages pass through
     the runner's secret redaction.
   - The result carries `dashboardId`, `dashboardName`, `asOf` (the oldest
     output's) and `outputs` in the order asked.
4. **Action** `actions/read-named-outputs.ts` (`defineAction`): input as
   above; `readOnly: true`; `http: { method: "GET" }`; `publicAgent: {
   expose: true, readOnly: true, requiresAuth: true }`; `grounding: true`.
   Describe it as the one way another app reads a dashboard's data: names
   only, never SQL; inputs are filter ids. The agent can call it too.
5. **Agent context.** In `buildDashboardAgentContext`
   (`server/lib/agent-readable-resource-context.ts:193`), add
   `output=<name>` to a cell's line in 7.1a's cell list when it has one.
6. **Application state.** None new.
7. **Skills.** In `.agents/skills/notebooks/SKILL.md` (7.1a) add "Named
   outputs": what they are, how to set `config.outputName` with
   `mutate-dashboard`, the naming rule, and that apps read them with
   `read-named-outputs`. One line in the "Sharing" section of
   `.agents/skills/dashboard-management/SKILL.md`: reading outputs never
   widens access, because each read runs as the person asking.
8. **Changelog.** None in this unit (no visible change); 8.3c records the
   user-facing entry.

## 4. Copy

No new UI strings. Error messages are agent-facing English in the action
source and must still read plainly when relayed, for example "This
dashboard was deleted or you no longer have access to it." and "This
dashboard has no input named plan." No em dashes.

## 5. Tests

- `actions/update-dashboard-validate-config.spec.ts`: `outputName` pattern,
  uniqueness, refused on a text, section or extension cell, the 24 cap.
- `server/lib/named-outputs.spec.ts` (PGlite, source runner mocked):
  `dashboard_not_found` for no access and for deleted; an organization-only
  principal is refused; unknown and invalid inputs are `invalid_input`;
  defaults apply; schema mode runs nothing; rows mode keeps order, caps rows
  and bytes with the right `truncatedReason`, maps missing credentials and
  timeouts to their codes, and never returns an `ok` output with zero rows
  for a failed query; reads attribute to `app`.
- `shared/named-outputs.spec.ts`: `notebookAppCells` order and `hideInApp`;
  `outputNameFromTitle` uniqueness.
- `actions/read-named-outputs.spec.ts`: the action is exposed read-only to
  peers (`publicAgent` shape) and rejects a SQL field in its input.
- `server/lib/named-outputs.parity.spec.ts` (PGlite, source runner mocked
  per user): for the owner and for a user the dashboard is shared with, the
  rows equal what the same panel returns to that user in Analytics; two
  users whose credentials see different rows get different rows from the
  same call; a user it is not shared with and a service identity get no
  rows.

No source-reading tests.

## 8. Defaults for open questions

- [Default] Outputs must be named explicitly; nothing is exposed by
  default.
- [Default] Rows default to 200 and stop at 500 per output and 256 KB per
  read.
- [Decided by the owner, 2026-10-14] People using a published app see only
  data they can already see in Analytics. The reader's own access and
  credentials run every read; there is no "publish with my credentials".
- [Default] Grid dashboards and notebooks both support outputs.

## 9. Do not

- Do not accept SQL, a source or a panel config in the read input.
- Do not return SQL, source names, credentials or panel config in the
  result.
- Do not cache rows across users.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
