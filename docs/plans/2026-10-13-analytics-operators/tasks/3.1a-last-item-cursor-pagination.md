# 3.1a: Last-item cursor pagination for provider list endpoints

Lane B. Size M. Split from 3.1 (Stripe metrics data program); 3.1b builds on it.

## 1. Goal

Agent answers and data programs that page through Stripe (and any other API
that pages by "the id of the last item you saw", such as Stripe's
`starting_after` plus `has_more`) read every page, and say so honestly when
they stop early. Today the documented Stripe recipe silently stops after the
first 100 records and reports the result as complete, so revenue, customer
and charge counts built on it are quietly wrong.

## 2. What the code does today

- `providerFetchAll` in the run-code sandbox reads the next cursor only from a
  response path: `const cursorPath = pagination.nextCursorPath || pagination.cursorPath;`
  (`packages/core/src/coding-tools/run-code.ts:1913`), then
  `_getByPath(page, cursorPath)` (`run-code.ts:1943`). When that value is
  missing it falls through to `lastCursor = null` (`run-code.ts:1961`) and the
  loop breaks with `stoppedReason` still `"completed"`; `hasMore` is computed
  only from `lastCursor !== null` (`run-code.ts:1995`). A missing cursor and a
  finished list are the same value.
- `providerSearchAll` has the same cursor logic (`run-code.ts:1735`,
  `run-code.ts:1765`, `run-code.ts:1838`, `run-code.ts:1873`).
- The sandbox path reader splits on `.` and only rewrites `[n]` brackets
  (`run-code.ts:1417-1424`); `_getByPath` indexes the parts directly
  (`run-code.ts:1426-1433`). So `"data.-1.id"` reads `data["-1"]`, which is
  `undefined`. Negative indexes are not supported.
- Server-side staging (`provider-api-request` with `stageAs`) has its own
  copy: `getAtPath` splits on `.` (`packages/core/src/provider-api/staging.ts:94-104`),
  `extractNextCursor` returns `null` for a missing value
  (`staging.ts:132-137`), and the loop does `if (!next) break;`
  (`staging.ts:345-347`) without setting `truncated`. The pagination type has
  no last-item or has-more option (`staging.ts:45-54`).
- Provider corpus jobs have a third copy (`packages/core/src/provider-api/corpus-jobs.ts:597-640`,
  path reader at `corpus-jobs.ts:1342-1350`); a missing cursor ends the job as
  `completed` with `stoppedReason: "no-next-cursor"` (`corpus-jobs.ts:631-633`).
- The `provider-api-request` action schema documents only
  `nextCursorPath`, `cursorParam`, `cursorBodyPath`, `pageParam`,
  `offsetParam`, `pageSize`, `maxPages`
  (`packages/core/src/provider-api/actions/provider-api.ts:24-70`).
- The analytics skills teach the broken recipe for Stripe:
  `nextCursorPath: "data.-1.id"` in
  `templates/analytics/.agents/skills/provider-api/SKILL.md:197-210` and
  `templates/analytics/.agents/skills/cross-source-analysis/SKILL.md:63-70`.
- The core test that "covers" Stripe staging mocks a `next_cursor` field that
  Stripe never returns (`packages/core/src/provider-api/staging.spec.ts:480-516`).
- Sibling in the template: `getInvoices` requests one page of 100 and ignores
  `has_more` (`templates/analytics/server/lib/stripe.ts:267-281`; the list type
  carries `has_more` at `stripe.ts:175-180`). `getSubscriptions` and
  `getRefunds` also pass `limit: "100"` with no follow-up
  (`stripe.ts:382-389`, `stripe.ts:432-448`). The `stripe` action returns
  those lists as complete (`templates/analytics/actions/stripe.ts:119-165`).
- The Stripe provider is registered in core at
  `packages/core/src/provider-api/index.ts:1708-1723` (bearer
  `STRIPE_SECRET_KEY`, base `https://api.stripe.com/v1`).

## Plan corrections

- The plan says `providerFetchAll` "can't follow" Stripe pages. True, and
  worse: the documented workaround (`data.-1.id`) looks like it works and
  returns only the first page with `hasMore: false` and staging
  `truncated: false`. Fix the helpers and the docs together.
- There are four paginators, not one: run-code `providerFetchAll`, run-code
  `providerSearchAll`, staging, and corpus jobs. All four need the same option
  or the bug ships again through the next one.
- Stripe search endpoints (`/v1/*/search`) return `next_page`, which the
  existing `nextCursorPath: "next_page"` plus `cursorParam: "page"` already
  handles. Only list endpoints need the new mode.

## 3. Build

1. Add two pagination options everywhere pagination is accepted:
   - `lastItemCursorPath` (string): read the cursor from the last item of the
     page's items array at this path (for Stripe, `"id"`), and send it through
     `cursorParam` or `cursorBodyPath`.
   - `hasMorePath` (string): a boolean in the response (for Stripe,
     `"has_more"`). When present, `false` ends pagination as `completed`,
     `true` with no usable cursor ends it as `cursor-missing` with
     `hasMore: true`.
   Validation: `lastItemCursorPath` without `cursorParam` or `cursorBodyPath`
   is a schema error (same rule staging already enforces at
   `staging.ts:200-205`). `lastItemCursorPath` and `nextCursorPath` together
   is a schema error.
2. Also accept negative array indexes in response paths (`data.-1.id`) in all
   four path readers, so recipes already in chat history and docs keep working.
3. Core TS paginators (`packages/core/src/provider-api/staging.ts`,
   `packages/core/src/provider-api/corpus-jobs.ts`): create one shared module
   `packages/core/src/provider-api/pagination-cursor.ts` exporting
   `readPathValue(value, path)` (with negative indexes) and
   `nextPageCursor({ body, items, pagination, previousCursor })` returning a
   discriminated result `{ kind: "next", cursor } | { kind: "done", reason } | { kind: "stopped", reason, hasMore: true }`.
   Use it from both files and delete their local cursor branches. When the
   cursor is missing and `hasMorePath` says more exist, staging sets
   `truncated: true` and returns a `stoppedReason`; corpus jobs end
   `paused`/`completed` with `stoppedReason: "cursor-missing"` and keep the
   job's coverage fields honest.
4. Run-code sandbox (`packages/core/src/coding-tools/run-code.ts`): the
   sandbox prelude is a string, so it cannot import the TS module. Port the
   same algorithm into `_pathParts`/`_getByPath` (negative index) and into a
   single sandbox helper `_nextPageCursor(page, items, pagination, lastCursor)`
   used by both `providerFetchAll` and `providerSearchAll`. Add
   `stoppedReason: "cursor-missing"` with `hasMore: true` when `hasMorePath`
   is true but no cursor was found. Update the tool description line at
   `run-code.ts:153` to list `lastItemCursorPath` and `hasMorePath` with the
   Stripe example.
5. `provider-api-request` schema (`packages/core/src/provider-api/actions/provider-api.ts`):
   add the two fields with `.describe()` text that names Stripe as the example.
   Mirror them in `corpus-jobs.ts` schema (`corpus-jobs.ts:56-60` area).
6. Template sibling fix (`templates/analytics/server/lib/stripe.ts`): make
   `getInvoices`, `getSubscriptions` and `getRefunds` follow `has_more` with
   `starting_after` up to a cap (default 20 pages), and return
   `{ items, truncated }`. Update `templates/analytics/actions/stripe.ts` to
   pass `truncated` through in every mode's result (`invoicesTruncated`, etc.)
   so the agent can report partial billing history.
7. Skills and docs:
   - Replace the Stripe examples in
     `templates/analytics/.agents/skills/provider-api/SKILL.md` and
     `templates/analytics/.agents/skills/cross-source-analysis/SKILL.md` with
     `pagination: { cursorParam: "starting_after", lastItemCursorPath: "id", hasMorePath: "has_more", maxPages: 50 }`.
   - Add a short "List endpoints that page by last id" note to
     `templates/analytics/.agents/skills/data-programs/SKILL.md` "The sandbox
     surface" section.
   - `packages/core/docs/content/data-programs.mdx`: add one example of the
     last-item mode next to the existing `providerFetchAll` example
     (`data-programs.mdx:117-125`). Update the same section in all ten
     locale copies under `packages/core/docs/content/locales/{ar-SA,de-DE,es-ES,fr-FR,hi-IN,ja-JP,ko-KR,pt-BR,zh-CN,zh-TW}/data-programs.mdx`.
8. Changeset: `.changeset/last-item-cursor-pagination.md`, `@agent-native/core`
   patch: "Provider pagination follows last-item cursors (Stripe
   `starting_after`) and reports a missing cursor as partial instead of
   complete."
9. Four-area check:
   - UI: none. This is a data-access fix; the visible effect is correct counts.
   - Actions: `provider-api-request`, `provider-corpus-job` schemas; template
     `stripe` action result fields.
   - Skills: the three analytics skills above plus the core docs page.
   - Application state: not applicable, nothing on screen changes.

## 8. Defaults for open questions

- DECISION: option names `lastItemCursorPath` and `hasMorePath`. Reviewer may
  rename; keep the names identical in all four paginators.
- DECISION: support negative indexes as well, so existing `data.-1.id`
  recipes work. Without `hasMorePath`, the last-item mode costs one extra
  request that returns an empty page; that is acceptable.
- DECISION: template Stripe list helpers cap at 20 pages (2,000 records) and
  report `truncated` rather than paging without limit inside a request.
- DECISION: no behavior change for callers that use `nextCursorPath` today,
  except that a path ending in a negative index now resolves.

## 9. Do not

- No behavior changes outside pagination and the Stripe list helpers.
- Additive-only schema (no schema change is expected here).
- No new `/api` routes for app data; use actions.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials; keep using the existing
  resolver in `server/lib/stripe.ts` and the provider-api credential path.
- No `catch` or default that turns a failure into a normal-looking value: a
  missing cursor with more pages is `hasMore: true` / `truncated: true`, never
  `completed`.
- No large payloads in SQL beyond what staging already stores.
- Do not add a Stripe-only branch to the paginators; the option is generic.
