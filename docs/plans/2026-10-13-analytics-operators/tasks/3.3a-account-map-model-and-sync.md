# 3.3a: Account map data model, sync and resolve

Lane B. Size M. Split from 3.3 (account map across tools); 3.3b adds the
page, 3.3c moves `account-deep-dive` onto it.

## 1. Goal

Analytics keeps one team-wide map of "who is this customer" across tools:
each account links its Stripe customers, HubSpot companies and product users,
matched by email domain or exact email, with every match marked as automatic,
confirmed or rejected. The agent resolves a named account through the map
instead of guessing from a search, and people's corrections survive every
re-sync. This unit is the backend and agent surface; 3.3b is the screen.

## 2. What the code does today

- `account-deep-dive` resolves an account by free-text HubSpot search for
  deals (`templates/analytics/actions/account-deep-dive.ts:431-445`), then
  associated companies, falling back to a company search
  (`account-deep-dive.ts:477-503`). It covers HubSpot and Gong only and says
  so (`account-deep-dive.ts:610`: `productUsageIncluded: false`, no Stripe).
  Nothing is stored between calls.
- The cross-source skill's join rule asks for stable id plus normalized email
  and to label match quality exact, partial or unmatched
  (`templates/analytics/.agents/skills/cross-source-analysis/SKILL.md:94-113`).
  The account-health skill requires an identity lock before usage queries
  (`templates/analytics/.agents/skills/account-health/SKILL.md:15-28`).
  Neither has a stored map to lock against.
- Stripe customers carry email and name (`templates/analytics/server/lib/stripe.ts:182-245`).
  HubSpot companies are searchable through `searchHubSpotObjects`
  (`templates/analytics/server/lib/hubspot.ts`, used at
  `account-deep-dive.ts:487-493`).
- First-party events have `user_id`, `user_key` and JSON `properties` /
  `context` but no account or email column
  (`templates/analytics/server/plugins/db.ts:290-312`).
- Template schema helpers come from `@agent-native/core/db/schema`
  (`templates/analytics/server/db/schema.ts:1-11`); migrations are an ordered
  list with names in `templates/analytics/server/plugins/db.ts` (latest
  version 167 at `db.ts:1793-1797`). Identity-shaped columns must be declared
  with `registerIdentityColumns` (`templates/analytics/server/db/index.ts:19-36`;
  rule in `templates/analytics/.agents/skills/storing-data/SKILL.md`,
  "Identity-shaped columns need a policy").
- Data programs give background execution (10-minute budget), per-viewer
  credentials and a 10,000-row cap per run
  (`templates/analytics/.agents/skills/data-programs/SKILL.md:97-130`), and
  `runDataProgram` is callable from server code
  (`packages/core/src/data-programs/execute.ts:338`).

## Plan corrections

- "Product users" have no email column in first-party events. The sync can
  only use user ids that are emails, or an email in event properties, plus
  2.1's Postgres users table. Say so in the UI and skill instead of implying
  full coverage.
- One sync run of all providers can pass the 10,000-row program cap. Run the
  candidate program once per provider (three cache entries) and report
  `coverage_complete` per provider.

## 3. Build

1. Schema (`templates/analytics/server/db/schema.ts`), additive, new tables:
   - `analytics_accounts`: `id` (text pk, `acct_` prefix), `scope_key` (org id,
     or `user:<email>` without an org), `org_id` (nullable), `owner_email`,
     `name`, `primary_domain` (nullable), `status` (`active` | `merged`,
     default `active`), `merged_into_id` (nullable), `created_at`,
     `updated_at`, `updated_by`. Indexes: (`scope_key`, `primary_domain`),
     (`scope_key`, `status`, `name`).
   - `analytics_account_links`: `id`, `scope_key`, `account_id`, `provider`
     (`stripe` | `hubspot` | `product`), `external_id`, `label`, `email`
     (nullable), `domain` (nullable), `match_method` (`domain` | `email` |
     `manual`), `decision` (`auto` | `confirmed` | `rejected`, default
     `auto`), `merged_from_account_id` (nullable), `last_seen_at`,
     `created_at`, `updated_at`, `updated_by`.
     Unique index (`scope_key`, `provider`, `external_id`); index
     (`scope_key`, `account_id`).
   - `analytics_account_map_syncs`: `id`, `scope_key`, `provider`, `status`,
     `started_at`, `finished_at`, `candidate_count`, `created_count`,
     `updated_count`, `coverage_complete` (boolean), `error_code`,
     `error_message`. Keep the last 20 per scope and provider.
   Add three named migrations at the end of the list in
   `templates/analytics/server/plugins/db.ts` (next free version at merge
   time; coordinate, other units add migrations too). Run
   `pnpm guard:additive-migrations`.
2. Identity policy in `templates/analytics/server/db/index.ts`:
   `analytics_account_links.email` retain/retain (a customer's address),
   `analytics_accounts.updated_by` and `analytics_account_links.updated_by`
   retain/retain (attribution), `analytics_account_map_syncs` has none.
   `owner_email` on accounts is the creator; declare transfer. Run
   `pnpm guard:identity-columns-registered`.
3. Scoping: the map is one per organization (or per user without an org).
   Every read and write filters by `scope_key` from
   `getRequestOrgId()` / `getRequestUserEmail()` in one helper
   `templates/analytics/server/lib/account-map-scope.ts`. Any org member can
   read and edit (decision in section 8).
4. Candidate program `templates/analytics/seeds/data-programs/account-map-candidates.js`
   (`background: true`, `refreshMode: "manual"`), param `provider`:
   - `stripe`: `/customers` with 3.1a last-item pagination; emit
     `external_id`, `label` (name or email), `email`, `domain`.
   - `hubspot`: `/crm/v3/objects/companies` with `properties: name,domain`
     and `paging.next.after`; emit `external_id`, `label`, `domain`.
   - `product`: `appAction("query-agent-native-analytics", { sql })` with one
     bounded aggregate over the last 90 days: distinct `user_id` values that
     contain `@`, `LIMIT 10000`. Read 1.4c's `analytics_user_event_days`
     (which stores `user_id`) when it exists, else `analytics_events` with a
     timestamp bound. Emit `external_id` (user id), `email`, `domain`. When
     2.1a's Postgres source is configured and 2.1b's schema snapshot
     (`readPostgresSchemaSnapshot`) has a users-like table with an email
     column, also read it through `appAction("postgres", { sql })` with the
     same cap.
   - Every row carries `coverage_complete`.
   Installed idempotently by `ensureAccountMapPrograms` in
   `templates/analytics/server/lib/account-map-sync.ts`, same reuse-first
   rules as 3.1b.
5. Sync `templates/analytics/server/lib/account-map-sync.ts` and action
   `templates/analytics/actions/sync-account-map.ts`:
   - For each provider that is connected (skip unknown status, report it),
     call `runDataProgram`. `background_pending` returns
     `{ provider, status: "running" }`; a failure returns its error code.
     Neither is turned into zero candidates.
   - Normalize: lowercase and trim emails and domains; strip `www.`; ignore
     free-mail domains from `templates/analytics/shared/free-email-domains.ts`
     (a short list: gmail.com, googlemail.com, outlook.com, hotmail.com,
     live.com, yahoo.com, icloud.com, me.com, aol.com, proton.me,
     protonmail.com, gmx.com, yandex.com, qq.com, 163.com).
   - Upsert links by (`scope_key`, `provider`, `external_id`). Existing links
     keep their `account_id` and `decision` when the decision is `confirmed`
     or `rejected`; only `label`, `email`, `domain`, `last_seen_at` change.
   - New links: join an account with the same `primary_domain` (company
     domain), else an account that already has a link with the same exact
     email (free-mail customers become person accounts named by email), else
     create an account. `match_method` records which rule matched.
   - Never delete links that were not seen; `last_seen_at` shows staleness.
   - Batch writes (one insert per chunk of 500), no per-row round trips.
   - Record a row in `analytics_account_map_syncs` per provider.
6. Read and edit actions (all `defineAction`, Zod schemas, bounded):
   - `list-accounts` (read-only): `search`, `needsReview` (has `auto` links
     from two or more providers that disagree, or an `auto` domain match),
     `provider`, `cursor`, `limit` (default 50, max 100). Returns projected
     rows `{ id, name, primaryDomain, counts: { stripe, hubspot, product }, needsReview, updatedAt }`
     plus `nextCursor` and the latest sync per provider. Counts come from one
     grouped query, not per row.
   - `get-account` (read-only): account plus its links (cap 500, `truncated`).
   - `resolve-account` (read-only, `grounding: true`, `mcpTool: true`):
     `query` (domain, email, name, Stripe id or HubSpot id). Returns
     `{ status: "resolved" | "ambiguous" | "not_found" | "map_empty", accounts: [...] }`
     with links and `matchQuality` (`confirmed`, `auto`). `map_empty` means
     no sync has run, which is different from `not_found`.
   - `update-account-link` (write): `linkId`, `decision`
     (`confirmed` | `rejected` | `auto`), optional `moveToAccountId` or
     `moveToNewAccount: true`. Moving a link sets `match_method: "manual"`
     and `decision: "confirmed"`.
   - `merge-accounts` (write): `sourceAccountId`, `targetAccountId`; moves
     links (setting `merged_from_account_id`), sets source
     `status: "merged"`, `merged_into_id`. Returns an `undo` payload that
     calls `unmerge-accounts`.
   - `unmerge-accounts` (write): `sourceAccountId`; moves links whose
     `merged_from_account_id` is the source back, sets it `active`.
   - `rename-account` (write): `accountId`, `name`, optional
     `primaryDomain`.
   - Write actions return an `ActionChangeResult` (`@agent-native/core/action-ui`)
     so the chat shows "Updated account" with undo where there is one.
   - Expected failures use `fail(message, { errorCode, statusCode })`
     (`account_not_found` 404, `link_not_found` 404, `merge_into_self` 400,
     `account_merged` 409).
7. Skills and instructions:
   - New section "Account map" in
     `templates/analytics/.agents/skills/cross-source-analysis/SKILL.md`:
     resolve accounts with `resolve-account` before any cross-tool account
     question; treat `auto` domain matches as partial (one key) and say so;
     `map_empty` means run `sync-account-map` or tell the user; product
     user coverage is limited to email-shaped user ids.
   - `templates/analytics/.agents/skills/account-health/SKILL.md` identity
     lock: step 1 becomes "resolve through `resolve-account`"; record the
     account id with the other identity fields.
   - `templates/analytics/AGENTS.md`: one line under "Data questions".
8. UI: none here (3.3b). Application state: none here (3.3b adds the
   `accounts` view and selection).

## 5. Tests

  database (follow the PGlite-backed pattern in
  `templates/analytics/server/lib/error-capture.spec.ts`): domain match joins Stripe and HubSpot; free-mail email becomes a

## 8. Defaults for open questions

- DECISION: one map per org, readable and editable by every org member, not
  an ownable per-user resource. Reviewer may restrict edits to org admins.
- DECISION: matching keys are company domain and exact email only. No fuzzy
  name matching; name-only matches stay separate accounts for a person to
  merge.
- DECISION: product users come from email-shaped first-party user ids and
  2.1's Postgres users table; PostHog persons are out of scope.
- DECISION: sync is manual (agent or button), not scheduled. A recurring job
  can come later.
- DECISION: links are never deleted by sync.

## 9. Do not

- No behavior changes outside this unit; `account-deep-dive` changes in 3.3c.
- Additive-only schema; new tables only, with named migrations.
- No new `/api` routes for app data; use actions.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials; providers resolve through
  the data program's viewer credentials.
- No `catch` or default that turns a failure into a normal-looking value:
  `running`, `failed`, `unknown`, `map_empty` and `not_found` are distinct.
- No large payloads in SQL: store ids, labels, emails and domains only, never
  raw provider records.
- No fuzzy or LLM matching inside the sync.
