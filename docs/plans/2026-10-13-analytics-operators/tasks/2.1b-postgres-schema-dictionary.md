# 2.1b Read the Postgres schema into the data dictionary

Lane B (Founders). Size S. Not gated.

Paths are relative to `templates/analytics/`.

## 1. Goal

Right after a founder connects Postgres, Analytics reads the database's tables,
columns, row estimates and foreign keys, and the agent sees them as generated
data dictionary entries. The first question ("how many active customers do we
have?") finds the right table without the agent guessing names, and the Data
sources card shows how many tables were read and when. The user can re-read the
schema with one click after a migration.

## 2. What the code does today

- There is no schema read for `POSTGRES_URL`. The only Postgres runtime code is
  `server/lib/postgres.ts:44-66` (`runQuery`, `testConnection`), replaced by
  2.1a's `runReadOnlyQuery`.
- Dictionary entries come from three places, assembled twice:
  - `actions/list-data-dictionary.ts:81-91`: org settings with prefix
    `data-dict-`, the org source index, then user settings
    `u:<email>:data-dict-` (`:93-96`).
  - `server/lib/analytics-query-catalog.ts:1397-1465`: the same three sources
    for the agent's catalog-first search (`find-data` and the preloaded
    `analytics-catalog` references), with per-source failure logging.
- The generated source index is a single org setting
  `analytics-source-index` (`server/lib/source-index-store.ts:9`), validated by
  a strict zod schema whose `sourceKind` enum is `dbt | code | sigma`
  (`server/lib/source-index-schema.ts:6`). Both writers replace the whole
  bundle: `actions/build-data-index.ts:105` and
  `actions/import-data-dictionary-index.ts:30`. Writing a Postgres snapshot into
  that bundle would erase a dbt index, so the snapshot needs its own key.
- `sourceIndexDictionaryEntries` (`server/lib/source-index-store.ts:129-164`)
  shows the generated-entry shape the readers already accept (`sourceIndex:
  true`, `approved: false`, `aiGenerated: true`, freshness fields).
- `readSourceIndex` (`:88-127`) is the precedent for a bounded, cached,
  typed read: `not-configured | unavailable | invalid | available`, never a
  silent empty value.
- On credential save, `actions/update-data-source-credentials.ts:143-161`
  already runs a follow-up for GA4 (seeds a dashboard). Saving does not run
  provider work for other sources.
- The Data sources card for Postgres is `app/lib/data-sources.ts:357-383`;
  the page tests connections through `app/pages/DataSources.tsx:228-238`.

### Plan corrections

- The plan says "read the schema on connect to seed the data dictionary". The
  dictionary has no per-source store for generated entries other than the
  single org source index, so seeding means a second generated source. The
  brief adds one and a shared collector so the two readers above do not each
  grow a fourth branch.

## 3. Build

1. **Snapshot reader** `server/lib/postgres-schema.ts` (new):
   - `readPostgresSchema()` runs through 2.1a's `runReadOnlyQuery` (so the read
     is read-only, timed out and host-checked) three bounded queries over
     `information_schema.columns`, `pg_class.reltuples` joined to
     `pg_namespace`, and `information_schema.table_constraints` +
     `key_column_usage` + `constraint_column_usage` for foreign keys, excluding
     `pg_catalog`, `information_schema` and `pg_toast`.
   - Caps: 400 tables, 80 columns per table, 15 s total. Return
     `{ tables: [{ schema, name, kind: "table"|"view", rowEstimate, columns: [{ name, type, nullable }], foreignKeys: [{ column, references: "schema.table.column" }] }], truncated, capturedAt, urlFingerprint }`.
     `urlFingerprint` is a SHA-256 of host, port and database name (never the
     password) so a changed URL makes the old snapshot visibly stale.
2. **Snapshot store** in the same file:
   - Key `analytics-postgres-schema`. Store in the same scope the
     `POSTGRES_URL` credential resolved from: use `resolveCredentialDetailed`
     and write with `putUserSetting` for `scope: "user"` or `putOrgSetting` for
     `scope: "org"`.
   - `readPostgresSchemaSnapshot(ctx)` returns
     `{ status: "not-configured" } | { status: "unavailable" } | { status: "invalid" } | { status: "stale"; snapshot } | { status: "available"; snapshot }`,
     cached 30 s per scope like `readSourceIndex`. `stale` means the fingerprint
     no longer matches the current URL.
   - Bound the serialized value at 256 KB; if the capped snapshot is still
     larger, drop column lists from the smallest tables first and set
     `truncated: true`. Never store sample rows.
3. **Generated entries.** `postgresSchemaDictionaryEntries(snapshot)` maps each
   table to one entry: `id: "pg-<schema>-<table>"` (slugified),
   `metric: "<schema>.<table>"`, `definition` ("Table in the connected
   PostgreSQL database, about N rows."), `source: "postgres"`,
   `sourceKind: "postgres"`, `entryType: "table"`, `table`, `columnsUsed`
   (comma list `name type`), `joinPattern` from foreign keys, freshness from
   `capturedAt`, `approved: false`, `aiGenerated: true`, `sourceIndex: true`.
4. **One collector.** Create `server/lib/generated-dictionary-entries.ts`
   exporting `collectGeneratedDictionaryEntries({ orgId, ctx })` that returns
   source-index entries plus Postgres entries with a per-source status. Change
   `actions/list-data-dictionary.ts:84-90` and
   `server/lib/analytics-query-catalog.ts:1407-1465` to call it instead of
   reading the source index themselves. Keep each reader's existing logging of
   unreadable sources; an unreadable Postgres snapshot is reported, not
   treated as "no tables".
5. **Action** `actions/refresh-postgres-schema.ts` (new, `defineAction`):
   no args; reads and stores the snapshot; returns
   `{ tableCount, truncated, capturedAt }`. Not `readOnly` (it writes a
   setting). `grounding: false`. Description: call after the user connects or
   migrates Postgres, or when generated table entries look stale. Errors are
   the typed `PostgresSourceError` codes from 2.1a.
6. **Status action** extend `actions/data-source-status.ts` so the
   `postgresql` provider entry carries
   `schema: { status, tableCount, capturedAt, truncated }` from
   `readPostgresSchemaSnapshot`. Keep it cheap: it reads the cached setting
   only and never connects to the database.
7. **On connect.** In `actions/update-data-source-credentials.ts`, when
   `POSTGRES_URL` was saved, do not run the read inline (it can take 15 s and
   the save must stay fast). Return `followUp: "refresh-postgres-schema"` in
   the result. The UI calls that action right after a successful save and test
   (step 8). The agent, after helping a user connect, calls it directly.
8. **UI** in `app/pages/DataSources.tsx`, inside the Postgres source detail
   only:
   - After a successful save, call `refresh-postgres-schema` through
     `useActionMutation`; show a `Spinner` in the row while it runs.
   - One status line under the connection status: "Read 42 tables, 5 minutes
     ago" (use `useFormatters()` for the relative time), or "Schema changed
     since the last read" when `stale`, or the typed error.
   - A `Button variant="outline" size="sm"` "Read schema again"
     (`IconRefresh` from Tabler) next to Test connection.
   - No new card, title or description. Loading uses a `Skeleton` line of the
     same height.
9. **Application state.** None new. The data sources view already reports the
   page in `actions/view-screen.ts:741-759`; add `postgresSchema` (the same
   small status object) to `screen` when `nav.view === "data-sources"` so the
   agent can see whether the read ran.
10. **Skills.** `.agents/skills/data-querying/SKILL.md` "Connected PostgreSQL"
    section (added by 2.1a): generated `pg-*` entries list tables and columns;
    check them first, then `information_schema` for anything truncated; call
    `refresh-postgres-schema` when the user says they changed the schema.
    `.agents/skills/storing-data` needs nothing.
11. **Changelog.** `agent-native changelog add "Connecting PostgreSQL now reads your tables so the agent knows where your data lives" --type added`.

## 5. Tests

- `server/lib/postgres-schema.spec.ts` (new), with a fake `runReadOnlyQuery`:
  caps at 400 tables and sets `truncated`; the 256 KB bound drops columns and
  sets `truncated`; fingerprint ignores the password and changes with the
  database name; a failed read returns the typed error and does not write a
  snapshot.
- `server/lib/generated-dictionary-entries.spec.ts` (new): source index and
  Postgres entries both appear; an unreadable Postgres snapshot yields a
  status of `unavailable` and leaves source-index entries intact; a stale
  snapshot is returned with `sourceIndexStale: true`.
- Extend `actions/list-data-dictionary.spec.ts` and
  `server/lib/analytics-query-catalog.spec.ts` with one case each that a
  stored snapshot's table shows up in results.
- Extend `actions/data-source-status.spec.ts`: the `postgresql` entry carries
  `schema.status` and never opens a connection.
- No source-reading tests.

```bash
pnpm exec vitest --run server/lib/postgres-schema.spec.ts server/lib/generated-dictionary-entries.spec.ts actions/list-data-dictionary.spec.ts server/lib/analytics-query-catalog.spec.ts actions/data-source-status.spec.ts

cd ../.. && pnpm guard:i18n-catalogs && pnpm guard:i18n-changed-copy
```

With a local Postgres connected (see 2.1a):

1. `pnpm action refresh-postgres-schema` returns a `tableCount` equal to
   `select count(*) from information_schema.tables where table_schema not in ('pg_catalog','information_schema')`.
2. `pnpm action list-data-dictionary --search <a table name>` returns the
   `pg-...` entry.
3. In the browser, save the Postgres credential and watch the status line
   appear; click "Read schema again"; no console errors or failed requests.
4. Ask the agent a question that names a business concept stored in one
   table; confirm the first `postgres` call uses the right table name.

Cannot be verified locally: behavior against very large hosted schemas (the
caps are unit tested).

## 8. Defaults for open questions

- **D1** Snapshot lives in settings under the credential's own scope, not in
  the org source index and not in a new table. Precedent: the source index is
  one bounded org setting.
- **D2** Caps: 400 tables, 80 columns per table, 256 KB, 15 s.
- **D3** The read runs after save through a separate action call, never
  inline in the save and never at boot.
- **D4** One generated entry per table; no per-column entries.
- **D5** No scheduled re-read. Manual button plus agent call.
- **D6** Views are included and marked `kind: "view"`; materialized views too.

## 9. Do not

- No behavior changes outside this unit; do not change how dbt or Sigma
  indexes are built or stored.
- Additive-only schema; this unit should need none.
- No new `/api` routes; the read is an action.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value: an
  unreadable snapshot is `unavailable`, not zero tables; a capped read is
  `truncated: true`.
- No large payloads in SQL: never store sample rows or column statistics.
- Do not write into `analytics-source-index`.
