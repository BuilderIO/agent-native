# 4.2a Fresh events for alerts

Lane D (Growth). Size M. Not gated (no new UI).

## 1. Goal

An alert on first-party events fires about a minute after the events arrive,
even when the workspace stores its events in BigQuery and even while delivery
to BigQuery is behind. A team that sets "more than 20 failed checkouts in 10
minutes" hears about it in the same minutes, not after the next delivery and
the next five-minute sweep, and an alert never quietly misses events that are
still waiting to reach BigQuery.

## 2. What the code does today

- Ingest writes every event to Postgres first. With the BigQuery sink,
  `recordAnalyticsEvents` inserts into `analytics_events` and a delivery queue
  row in one transaction (`server/lib/first-party-analytics.ts:175-200`,
  `:930-937`). With the Postgres or dual sink the event stays in Postgres
  (`:938-957`).
- Delivery to BigQuery is a sweep, not a stream: `runFirstPartyAnalyticsBigQueryDeliveryOnce`
  (`server/lib/first-party-analytics-delivery.ts:686-799`) claims batches and
  sends them with `insertAll` (`server/lib/first-party-analytics-backend.ts:433-500`).
  On Netlify the sweep runs every minute (`scripts/emit-netlify-dashboard-report-cron.ts:48`,
  `BIGQUERY_SCHEDULE = "* * * * *"`). A failed batch retries with backoff from
  1 minute up to 60 minutes (`first-party-analytics-delivery.ts:17-18`,
  `:543-552`).
- After delivery, Postgres keeps the event for 10 minutes and then deletes it
  (`DELIVERY_CLEANUP_RETENTION_MS`, `first-party-analytics-delivery.ts:19`;
  cleanup on `delivered_at <= now - 10 min` at `:583-680`).
- Alerts for a BigQuery-sink workspace read only BigQuery. `loadCandidateEvents`
  sends every such rule to BigQuery (`server/lib/analytics-alerts.ts:1519-1563`),
  and the sweep batches eligible BigQuery rules into one aggregate query
  (`server/jobs/analytics-alerts.ts:103-133`, `:153-193`;
  `server/lib/analytics-alerts.ts:1052-1156`). Events still in the delivery
  queue are invisible to those queries, so an alert misses them until delivery
  succeeds.
- The Postgres read path for alerts already exists and is scoped and
  test-identity aware: `loadCandidateEventsFromSql`
  (`server/lib/analytics-alerts.ts:1632-1680`), backed by the
  `(event_name, timestamp)` and `(org_id, owner_email, timestamp)` indexes
  (`server/plugins/db.ts:316-321`).
- Alert sweeps run every 5 minutes on Netlify (`ALERT_SCHEDULE = "*/5 * * * *"`,
  `scripts/emit-netlify-dashboard-report-cron.ts:36`) and every 60 seconds
  in long-lived runtimes (`server/plugins/analytics-alert-jobs.ts:4`). Every
  enabled rule is evaluated on every sweep; there is no per-rule interval
  (`server/lib/analytics-alerts.ts:738-768`).
- Event timestamps can never be later than the time the event was received:
  `normalizeAnalyticsTimestamp` replaces a future timestamp with the receive
  time (`server/lib/first-party-analytics.ts:576-603`). So any event whose
  `timestamp` falls inside the last W minutes was received inside the last W
  minutes, and was delivered no earlier than that.

## Plan corrections

- "Instead of waiting on BigQuery batches" is half right. BigQuery rows are
  visible seconds after `insertAll`; the waits are (1) the 5-minute alert
  schedule on Netlify, (2) the 1-minute delivery sweep, and (3) up to 60
  minutes of retry backoff when delivery fails, during which alerts miss the
  pending events entirely. This unit fixes all three.
- The collector's own storage is the Postgres `analytics_events` table, which
  on the BigQuery sink is an outbox holding pending events plus the last 10
  minutes of delivered ones. Reading it alone is complete only for windows up
  to that retention, so long windows still need BigQuery for older events.

## 3. Build

1. Measure first. Ask the plan owner to run `get-first-party-analytics-health`
   against production for an affected workspace and record `pendingCount`,
   `oldestPendingAt` and `lastDeliveredAt` in the PR. If delivery is healthy,
   the schedule (step 6) is the main fix; say so in the PR.
2. One constant for the hot window. In
   `server/lib/first-party-analytics-delivery.ts` export
   `FIRST_PARTY_ANALYTICS_HOT_WINDOW_MINUTES = 60` and set
   `DELIVERY_CLEANUP_RETENTION_MS` to `(FIRST_PARTY_ANALYTICS_HOT_WINDOW_MINUTES + 10) * 60_000`.
   Comment the trap: alerts read Postgres alone for windows up to the hot
   window, so lowering retention below it makes those alerts silently miss
   events.
3. Hot path. In `loadCandidateEvents` (`server/lib/analytics-alerts.ts:1519`),
   when the sink is `bigquery` and `rule.windowMinutes <=
   FIRST_PARTY_ANALYTICS_HOT_WINDOW_MINUTES`, call
   `loadCandidateEventsFromSql` and do not touch BigQuery. In
   `runAnalyticsAlertsOnce` (`server/jobs/analytics-alerts.ts:103-133`), send
   those rules to `individualRules` instead of a BigQuery batch.
4. Long windows on the BigQuery sink (`windowMinutes` above the hot window).
   Let `hotStart = now - hot window`.
   - Postgres part: all events with `timestamp` in `[max(windowStart,
     hotStart), now]`, plus pending events with `timestamp` in
     `[windowStart, hotStart)`. Pending means a delivery queue row with
     `delivered_at IS NULL`, or a migration fallback marker still in the
     `pending` state (`first-party-analytics.ts:204-226`). Add one function in
     `first-party-analytics-delivery.ts` that returns those pending rows for a
     scope, event name and time range, at most `ALERT_PENDING_ID_CAP = 5_000`.
   - BigQuery part: the existing queries with the upper bound changed from
     `now` to `< hotStart` and `id NOT IN (<pending ids>)`. Change
     `buildBigQueryAlertQuery` (`analytics-alerts.ts:1336-1369`) and the
     candidate branches of `buildBigQueryAnalyticsAlertBatchQuery`
     (`:1052-1156`). Excluding pending ids matters because a row being
     delivered right now may already be in BigQuery.
   - Merge: for the row path, concatenate and dedupe by `id`. For the batch
     path, add Postgres counts to `count_<i>`, union distinct values into the
     `distinct_<i>` set, and keep the newest five samples across both. Put the
     merge next to `normalizeBigQueryAlertAggregate` (`:1202`).
   - Over the cap: throw `AlertDeliveryBacklogError` with the plain message
     "Too many events are still waiting to reach BigQuery to check this alert
     exactly. It will be checked again when delivery catches up." The sweep
     records it through `markAnalyticsAlertRuleError`
     (`server/jobs/analytics-alerts.ts:76-90`), so the rule shows Error, not OK.
5. Evaluation interval. Rules that query BigQuery (long windows on the
   BigQuery sink) run at most every 5 minutes; every other rule runs on every
   sweep. Skip a BigQuery rule in `runAnalyticsAlertsOnce` when its
   `lastEvaluatedAt` is less than 5 minutes old, before claiming it, so the
   faster schedule does not multiply BigQuery cost. Export the interval as one
   constant.
6. Schedule. Change `ALERT_SCHEDULE` to `"* * * * *"` in
   `scripts/emit-netlify-dashboard-report-cron.ts:36` and update
   `server/plugins/platform-scheduled-jobs.spec.ts` if it pins the value. The
   atomic claim (`claimAnalyticsAlertRuleEvaluation`,
   `server/lib/analytics-alerts.ts:790-814`) already stops two overlapping
   sweeps from evaluating one rule twice.
7. Notification metadata: add `evaluationSource: "collector" |
   "collector_and_bigquery" | "postgres"` to the metadata passed to
   `notifyWithDelivery` (`analytics-alerts.ts:854-890`), so an incident shows
   where its numbers came from.
8. Actions: update the description of `save-analytics-alert-rule`
   (`actions/save-analytics-alert-rule.ts:24-25`) with one sentence: rules
   with windows up to 60 minutes are checked about every minute from the
   collector; longer windows on the BigQuery backend are checked every 5
   minutes. No new action.
9. Skills: update `.agents/skills/dashboard-ops/SKILL.md:80-86` (cadence,
   hot window, retention coupling, the backlog error).
10. UI: none. The Alerts tab already shows status, last checked time and the
    error text (`app/pages/settings/AlertRulesSettingsCard.tsx:600-650`). The
    backlog error appears there as stored text.
11. Application state: none. Alerts run server-side and have no screen state.
12. Changelog: `agent-native changelog add "Alerts on first-party events are checked about every minute, including events still on their way to BigQuery" --type improved`.

## 8. Defaults for open questions

- [Default, needs plan owner] Hot window 60 minutes, so Postgres keeps
  delivered events for 70 minutes instead of 10 on the BigQuery sink. Lower it
  to 10 to keep today's storage; then only windows up to 10 minutes skip
  BigQuery.
- [Default, needs plan owner] Netlify alert schedule every minute instead of
  every 5. That is five times the scheduled invocations.
- [Default] BigQuery-backed rules keep a 5-minute minimum interval.
- [Default] Pending id cap 5,000; above it the rule errors loudly instead of
  guessing.
- [Default] Assumes the late alerts were on the first-party collector with
  the BigQuery sink. If they were on a warehouse table loaded by another
  pipeline, this unit does not change them; tell the plan owner.

## 9. Do not

- Do not change delivery batching, retries or the BigQuery insert path.
- Do not change how Postgres-sink or dual-sink alerts are evaluated.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
