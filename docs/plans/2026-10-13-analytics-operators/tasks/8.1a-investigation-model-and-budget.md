## 1. Goal

"Why did this change?" becomes a bounded agent run with a record of its own.
An investigation has a subject (a funnel conversion between two steps, an
event alert's count, or a time-scoped chart panel), a comparison window, a
fixed plan of seven steps, and a time and spend budget (5 minutes and $0.50
by default). It runs as a core agent-teams background task whose only tools
are the investigation actions, so every step is a recorded tool call with a
result. Every step ends either done, with findings that carry evidence, or as
"couldn't check" with a typed reason. When it finishes, or runs out of time,
the result is saved as a notebook (`layout: "notebook"`, 7.1a) marked as an
investigation, with a plain-language answer and a confidence label the code
computes. Anything cut short is labeled partial, never complete.

This unit lands the model, the budget, the run, the first step (Confirm the
change) and the notebook write. 8.1b and 8.1e add the other checks; 8.1c adds
the triggers and delivery; 8.1f and 8.1d draw it.

## 2. What the code does today

  (`packages/core/src/server/agent-teams.ts:1748-1777` options, body from
  `:1777`): it creates a thread, saves the task, calls `parentSend` (`:1858`)
  and enqueues a durable run (`:1880`). The tool allowlist is copied into the
  run payload only when the ambient request run context already has one
  (`:1866-1876`), so a server job cannot restrict a task's tools.

  from the sub-agent registry and base prompt, filtered by
  `payload.allowedActionNames`

  answer time budget.

  `packages/core/src/server/agent-teams.ts:1365-1400`); an app cannot opt out.

  `@agent-native/core/server` exports only `spawnTask`, `getTask`,

  `resolveAnswerTimeBudgetMs` (`packages/core/src/agent/run-manager.ts:403`)

## Plan corrections

- **1.6a's budget cannot bound an investigation as built.** It applies to
  interactive chat turns, and agent-teams runs never receive it. Investigations
  enforce their own deadline and spend cap at the step action and in the sweep,
  reuse the 45 second closeout reserve, and reuse 1.6a's rule that a cut-short
  result is labeled partial. No change to `runAgentLoop`.
- **Core needs four small additions** (step 1): an explicit tool allowlist and
  a completion notification opt-out on `spawnTask`, an exported stop, and a
  spend reader for one thread.
- **Migration 176 is taken** on the integration branch by x1. This unit uses
  177; 8.1c uses 178.
- **Seven fixed steps.** The prototype's main example draws seven steps
  including "Check support tickets". Every investigation gets the same seven,
  in this order: Confirm the change, Break it down by segment, Check what
  shipped, Check errors, Watch replays, Find affected accounts, Check support
  tickets. A step that does not apply to the subject ends "couldn't check"
  with `not_applicable`; it is never dropped from the plan. The prototype's
  signup example draws "Check referrers" and "Check ad campaigns"; referrer
  is a segment dimension in 8.1b, and there is no ad campaign check in v1.
- **Stop maps to partial.** The prototype shows Partial after Stop. A user
  stop after at least one step finished ends `partial` with `stoppedBy:
  "user"`; `cancelled` is only a stop before any step finished.

     `payload.allowedActionNames` regardless of the ambient run context; a
     name that is not in the registry throws before the task is saved.
   - `completionNotification?: boolean` (default `true`), saved on the task.
     `ensureTaskCompletionNotification` returns reconciled without inserting
     when it is `false`.
   - `parentSend` becomes optional (no-op default) for server-started tasks.
   - Export `stopTask(taskId, { reason, scope })` from
     `@agent-native/core/server`, a thin wrapper over
     `stopAgentTeamBackgroundRun`.
   - `getThreadUsageSpend({ threadId, ownerEmail })` in
     `packages/core/src/usage/store.ts`, exported from the usage entry:
     `{ costCentsX100, rows, source }` where `source` is `none` (no rows
     yet), `reported`, `estimated`, `mixed`, or `unavailable` (any row has
     `cost_source = 'unavailable'`). `none` and `unavailable` are different
     values; neither is a zero spend.
2. **Schema (additive), migration 177** in `server/db/schema.ts` and
   `server/plugins/db.ts` (`version: 177`, `name:
   "analytics-investigations-table"`). Table `analytics_investigations`:
   `id TEXT PRIMARY KEY`, `owner_email TEXT NOT NULL`, `org_id TEXT`,
   `status TEXT NOT NULL DEFAULT 'queued'` (`queued`, `running`, `complete`,
   `partial`, `failed`, `cancelled`), `origin TEXT NOT NULL` (`alert`,
   `panel`, `chat`, `slack`), `dedupe_key TEXT`, `trigger_ref TEXT NOT
   NULL` (JSON, a reference: `{ kind: "alert_incident", ruleId, incidentId }`,
   `{ kind: "panel", dashboardId, panelId }` or `{ kind: "chat", threadId }`),
   `subject TEXT NOT NULL` (JSON subject metric ref and windows), `title TEXT
   NOT NULL`, `budget TEXT NOT NULL` (JSON `{ preset, timeMs,
   spendCentsX100, maxQueries }`), `deadline_at TEXT`, `task_id TEXT`,
   `thread_id TEXT`, `notebook_id TEXT`, `rerun_of TEXT`, `steps TEXT NOT
   NULL DEFAULT '[]'`, `findings TEXT NOT NULL DEFAULT '[]'`, `change TEXT`,
   `answer TEXT`, `summary TEXT`, `confidence TEXT`, `confidence_reason
   TEXT`, `outcome TEXT`, `stopped_by TEXT`, `spent_ms INTEGER`,
   `spent_cost_cents_x100 INTEGER`, `spend_source TEXT`, `query_count
   INTEGER NOT NULL DEFAULT 0`, `error TEXT`, `delivery_error TEXT`,
   `created_at`, `started_at`, `finished_at`, `updated_at`. Indexes:
   unique `(dedupe_key)` where not null; `(owner_email, org_id,
   created_at)`; `(status, deadline_at)`. Run `pnpm guard:additive-migrations`.
3. **Model** `shared/investigations.ts` (pure, no server imports):
   - `INVESTIGATION_STEPS`: `confirm`, `segments`, `releases`, `errors`,
     `replays`, `accounts`, `support`, in that order.
   - `InvestigationStep { kind, status: "waiting" | "running" | "done" |
     "could_not_check", checked?, result?, reason?, message?, fix?,
     startedAt?, endedAt? }`. `checked` and `result` are one-line English
     content strings written by the check ("Merged pull requests and deploys
     in GitHub, Oct 1 to Oct 11"); the step label comes from the UI catalog
     by `kind`.
   - `CouldNotCheckReason`: `no_connection`, `no_access`, `over_budget`,
     `timed_out`, `no_data_in_window`, `not_applicable`, `not_run`,
     `stopped`, `unavailable` (the check is not built yet), `failed` (the
     check threw; `message` carries the error).
   - `fix?: { kind: "connect", provider } | { kind: "agent", prompt } |
     { kind: "link", href }`.
   - `InvestigationFinding { id, step, kind: "segments" | "release" |
     "errors" | "replays" | "accounts" | "text", title, summary, explains:
     boolean | null, causeKey?, evidence: AnswerEvidencePayload, data }`.
     `explains: null` means the finding describes impact, not cause
     (accounts). Caps: title 120 chars, summary 280, `data` 12 KB serialized,
     12 findings per investigation. A check that exceeds a cap gets a typed
     `InvestigationFindingTooLargeError`; checks cap their own rows and set
     `truncated`.
   - `INVESTIGATION_BUDGETS`: `standard` = 300,000 ms, $0.50 (5,000
     cent-hundredths), 40 queries; `extended` = 900,000 ms, $1.50, 120
     queries.
   - `investigationConfidence({ status, steps, findings })` returns `{ label:
     "High" | "Medium" | "Low", reason }`. Count the independent cause checks
     whose finding has `explains: true`: `segments`, `releases`, `errors`,
     `replays` (confirm and accounts never count). 3 or more is High, 2 is
     Medium, 0 or 1 is Low. A `partial` investigation is at most Medium. A
     step that could not run never counts for or against; when one of the
     four could not run, the reason names it ("The accounts check didn't
     run" style, from a fixed template per step). The agent never sets the
     label.
   - `investigationOutcome`: `no_change` when Confirm finds the change did not
     hold up, else `explained` (at least one explaining finding) or
     `unexplained`. A `no_change` investigation has no confidence label.
4. **Store** `server/lib/investigations-store.ts`: `createInvestigation`
   (insert; a `dedupe_key` conflict returns the existing row with `deduped:
   true`), `getInvestigation(id, ctx)` (owner and org match; otherwise
   `resolveAccess("dashboard", notebook_id, ...)` on its notebook, and a
   shared viewer gets the steps, findings and answer but not `trigger_ref`
   or `task_id`), `listInvestigations(ctx, { status?, origin?, limit <= 50
   })` (projection without `findings`), `updateStep`, `appendFindings`,
   `finishInvestigation`, `markInvestigationFailed`. Every write is a
   compare-and-set on `status IN ('queued', 'running')`; a write that loses
   the race returns a typed `investigation_not_running` result, not a
   silent no-op.
5. **Subject** `server/lib/investigation-subject.ts`:
   `resolveInvestigationSubject(input, ctx)`:
   - Alert incident: load the incident and its rule as the rule owner. A
     `funnel_conversion` rule (4.2c `source_ref`) gives `{ kind:
     "funnel_conversion", dashboardId, panelId, fromStepIndex, toStepIndex }`
     with the rule's look-back as the current window and the window before
     it as the comparison. An event rule gives `{ kind: "event_count",
     ruleId, eventName, filters, thresholdMode, distinctBy }` with the rule's
     window and 4.2b's baseline offset (or the previous window of the same
     length).
   - Panel: `getDashboard` for the caller; the panel must be time-scoped
     (`extractDashboardTimeVariables`) or carry a funnel `config.growth`
     with a step pair; otherwise a typed `panel_not_time_scoped` failure.
     Compare presets `last_1d`, `last_7d` (default), `last_30d`, each
     against the window before it.
   - Title: `Why <from> to <to> conversion fell` (or `rose`) for funnels,
     `Why <event> fell` (or `rose`) for event rules, `Why <panel title>
     changed` for panels until Confirm knows the direction, then renamed.
6. **Step registry** `server/lib/investigation-checks/index.ts`:
   `registerInvestigationCheck(kind, check)`. A check is `(ctx) =>
   Promise<CheckResult>` with `ctx = { investigation, subject, change,
   priorFindings, meter, signal }`. `meter.query(label)` counts a query and
   throws `InvestigationBudgetExceeded` past `maxQueries`; `signal` aborts at
   the per-step timeout (60 s standard, 120 s extended). `CheckResult` is
   `{ status: "done", checked, result, findings }` or `{ status:
   "could_not_check", reason, checked, message, fix? }`. 8.1a registers:
   - `confirm` (`server/lib/investigation-checks/confirm.ts`): measures the
     subject in both windows and as a daily series (hourly when the window
     is a day or less), at most 60 points, through `runDashboardPanelQuery`
     or `queryFirstPartyAnalytics` with a new `investigation` caller in
     `PANEL_READ_CALLERS`. For funnels use the same compile path as 4.2c's
     evaluation and preview. Writes `change = { current, previous, unit:
     "percent" | "count" | "value", delta, direction, onsetAt,
     onsetPrecision: "hour" | "day" | null, series }`. Onset: the first
     bucket of the current window past the midpoint between the two window
     means that stays past it for the rest of the window; none found is
     `onsetAt: null`, never the window start. No change (under 2 points for
     a conversion, under 10% for a count or value, and the alert condition
     no longer met) ends the run early with outcome `no_change`.
   - `support`: `no_connection` "No support tool is connected." when no
     support provider connection exists; `not_applicable` "Investigations
     don't read support tickets yet." when one does.
   - Kinds not registered yet end `unavailable` "This check isn't available
     yet." (only between 8.1a and 8.1e merging).
   Every result carries `AnswerEvidencePayload` evidence; a thrown check
   ends `failed` with its message, never `done`.
7. **Actions** (all `defineAction`; the agent and the UI share them):
   - `start-investigation` (POST): `{ subject: { kind: "alert_incident",
     incidentId } | { kind: "panel", dashboardId, panelId, fromStepIndex?,
     toStepIndex? }, compare?: "last_1d" | "last_7d" | "last_30d", budget?:
     "standard" | "extended", rerunOf?: string }`. Refuses a service
     identity (core's `parseServiceIdentityEmail`,
     `packages/core/src/org/service-identity.ts`) with `service_identity`. Dedupe:
     an alert incident is `alert_incident:<id>`; a panel or chat start with a
     queued or running investigation for the same subject and window returns
     it. Creates the record and its notebook, then the run (step 10).
     Returns `{ investigationId, status, notebookId, threadId, taskId,
     deduped }` and a `link` to the notebook.
   - `get-investigation` (GET, read-only): status, steps, findings (owner and
     notebook viewers), change, budget, `spend: { elapsedMs, costCentsX100:
     number | null, source }`, `overdue`, notebook id, thread id.
   - `list-investigations` (GET, read-only): `{ status?: string[], origin?,
     limit? }`.
   - `cancel-investigation` (POST): stops the task with `stopTask`; no
     finished step means `cancelled`, otherwise waiting steps end `stopped`
     "Didn't run: the investigation was stopped." and the notebook is
     written as `partial`.
   - `run-investigation-check` (POST, for the investigator run): `{
     investigationId, step }`. Steps run once each, in plan order. Before a
     step: if less than 45 s plus the per-step timeout remains, or spend has
     reached the cap, the step ends `over_budget` and the result says
     `closeout: true`. Returns the step, its findings, `nextStep`,
     `remainingMs`, `spend` and `closeout`.
   - `finish-investigation` (POST, for the investigator run): `{
     investigationId, answer (<= 1,200 chars), summary (<= 160 chars, one
     line), replayCaptions?: Record<recordingId, string <= 120> }`. Rejects
     an em dash with a message to restructure. Waiting steps end `not_run`
     "Didn't run: the investigation ended first." Computes confidence and
     outcome, writes the notebook (step 8), sets `complete` (every step done
     or could not check for `no_connection`, `no_access`,
     `no_data_in_window` or `not_applicable`) or else `partial`, records
     spend, and calls the
     `onInvestigationFinished` hooks (8.1c registers delivery). Add it to
     `DASHBOARD_EDIT_TOOLS` and return `_receipt`, `editOutcome` and `undo`
     as `create-notebook` does (7.1a reviewer note).
8. **Notebook** `server/lib/investigation-notebook.ts`:
   - Append `finding` to `PANEL_CHART_TYPES`
     (`app/pages/adhoc/sql-dashboard/types.ts:5`), add it to
     `panelRunsQuery`'s no-query set (7.1a; never a new `||` clause), and
     register `finding: { onlyFor: ["finding"] }` in `PANEL_CONFIG_KEYS`

   - Validate a root `investigation: { id: string }` key in

   - At start, create the notebook with 7.1a's store write: `{ name: title,
     layout: "notebook", investigation: { id }, panels: [one text cell] }`
     whose Markdown is "Investigating. This notebook fills in when the checks

   - At finish, replace the panels in one write (one revision): an `answer`
     finding cell (answer, confidence, reason, outcome), the findings in
     step order, and one `could_not_check` finding cell listing every step

   - Until 8.1d, `SqlChartCard` and `dashboard-report-render.ts` render a

9. **Instructions** `server/lib/investigation-instructions.ts`: the
   investigator's task instructions, self-contained because its tools are

   `run-investigation-check` for each step in order; when a result says
   `closeout: true`, stop and call `finish-investigation`; write the answer

10. **Run** `server/lib/investigation-run.ts`: inside

11. **Sweep** `server/jobs/analytics-investigations.ts`

## 4. Copy

like alert text, stays English and goes in 1.5's inventory: the notebook
