# 8.3b Design data apps: bind to Analytics outputs through one data channel, in a sandbox

Lane E (Holy-shit features). Size M. Gated: the live data control in the
Design editor and the data-app preview are new UI; build only after the
"Design: data app" and "Design: data app preview" screens in
`prototypes/analytics-operators/` are signed off. Where the signed-off
prototype differs from this brief, the prototype wins.

Depends on: 8.3a (the read contract). Blocks: 8.3c, 8.3d.

Paths are relative to `templates/design/` unless they start with
`packages/` or `templates/analytics/`.

## 1. Goal

A design project in Design can be **bound** to an Analytics dashboard or
notebook's named outputs. Its screens then show real numbers: a revenue
chart, an at-risk accounts table, a signup tile, all branded with the
workspace design system. The screens never fetch anything themselves. There
is exactly one data channel: the Design page reads the outputs from
Analytics as the person viewing (through 8.3a's contract) and posts them
into the screen's sandboxed frame, which has no network access at all. A
viewer who cannot open the notebook in Analytics sees a plain "you don't
have access to this data" state, never someone else's numbers. Inputs on a
screen (a plan picker, a date range) send a request back up the same
channel, and only for inputs the notebook defines.

**Requirement (owner, 2026-10-14).** A person viewing a bound design, in the
editor, in Present or in a published app, sees only data they can already
see in Analytics. The read is always theirs, never the author's.

## 2. What the code does today

- A design is a row with a free JSON `data` column and an optional
  `designSystemId` (`server/db/schema.ts:12-28`); `update-design` writes
  `data` (`actions/update-design.ts:538-556`). `create-design` links the
  caller's default design system when none is given
  (`actions/create-design.ts:34-41`).
- Screens are inline HTML with Tailwind and Alpine. The editor canvas frames
  a screen with `srcDoc` and a sandbox from `getDesignCanvasIframeSandbox`
  (`app/components/design/DesignCanvas.tsx:8288-8300`); the editable inline
  sandbox includes `allow-same-origin` and the read-only one does not
  (`app/components/design/design-canvas/external-preview.ts:206-210`).
- The Present route frames the active screen with `sandbox="allow-scripts"`
  (`app/pages/Present.tsx:284-288`) from a document built at `:136-143`.
- A locked-down document already exists for template previews: CSP with
  `default-src 'none'`, `connect-src 'none'`, `frame-src 'none'`,
  `form-action 'none'`, and only the page's own render origins for images
  and styles (`app/components/templates/template-preview-document.ts:38-112`).
- Design already reads from another app over A2A in the other direction:
  Analytics calls Design's `get-design` as a direct read
  (`templates/analytics/server/routes/api/session-replay/storyboard.post.ts:652-670`),
  authenticating with `resolveA2ACallerAuth({ audience:
  canonicalA2AAudience(url), userIdentityOnly: true })` (`:934-945`).
- `view-screen` returns the open design, screen and selection
  (`actions/view-screen.ts:232-240`).
- Design has no notion of data bound to a design.

## Plan corrections

- The guarantee "the app runs sandboxed and cannot fetch" holds in the
  preview (Present) and in the published app (8.3d). The editor canvas keeps
  its editing sandbox, because visual editing needs same-origin access; it
  receives data the same way, but it is the author's own surface.

## 3. Build

1. **Shared** (`shared/data-app.ts`, new): `DesignDataBinding = { app:
   "analytics"; dashboardId; dashboardName; outputs: Array<{ name; title;
   chartType; columns: Array<{ name; type }> }>; inputs: Array<{ id; label;
   type; options?; default? }>; boundAt; boundBy }`, at most 12 outputs and
   50 columns each. Stored at `data.analyticsBinding`. A parser that returns
   `{ kind: "none" } | { kind: "bound"; binding } | { kind: "invalid";
   reason }`, so a corrupt binding is visible, not treated as unbound.
2. **Server** (`server/lib/analytics-data.ts`, new): resolve Analytics with
   `resolveAgentInvocationTarget("analytics", { selfAppId: "design" })`;
   authenticate as the current user with `resolveA2ACallerAuth({ audience,
   userIdentityOnly: true })`; call `invokeAgentAction` with action
   `read-named-outputs`. Map the transport and the contract's codes to typed
   results (`analytics_unavailable`, `dashboard_not_found`,
   `user_identity_required`, `invalid_input`, and per-output codes), never
   to empty outputs.
3. **Actions** (`defineAction`):
   - `bind-design-data`: input `{ designId, dashboardId, outputs: string[]
     } | { designId, binding: null }`. `assertAccess("design", id,
     "editor")`. Reads the contract in `schema` mode, then `rows` mode with
     `maxRows: 5` to learn columns; refuses names the dashboard lacks;
     writes `data.analyticsBinding` through the normal design write so a
     version is recorded. Returns the binding.
   - `read-design-app-data` (`http: { method: "GET" }`, read-only): input
     `{ designId, inputs?, outputs? }`. `assertAccess("design", id,
     "viewer")`; reads the binding; checks `inputs` keys against the
     binding's inputs; calls the contract in `rows` mode as the viewer.
     Returns `{ status: "ok", asOf, outputs }` or a typed failure. No rows
     are stored anywhere in Design.
4. **The screen runtime** (`app/components/design/data-app/runtime.ts`,
   new): a small inline script injected into a bound screen's document. It
   creates `Alpine.store("an", { state, asOf, outputs, inputs })`, where each
   output is `{ status, columns, rows, rowCount, truncated, asOf, error? }`,
   listens for `message` events only from `window.parent` carrying the
   frame's nonce, and exposes `$store.an.setInput(id, value)`, which posts
   `{ type: "an:set-input", nonce, id, value }` to the parent. Screens read
   `$store.an.outputs.<name>` and nothing else.
5. **The data-app document** (`app/components/design/data-app/document.ts`,
   new): wraps a bound screen with the runtime and the template-preview CSP
   (copy the policy, `connect-src 'none'` included); framed with `sandbox=
   "allow-scripts"` and no `allow-same-origin`.
6. **The parent channel** (`app/components/design/data-app/use-design-app-data.ts`,
   new): `useActionQuery("read-design-app-data", ...)`, then
   `postMessage` to the frame's `contentWindow` with the nonce on load and
   on every result. On `an:set-input`, accept only messages whose
   `event.source` is that frame and whose input id is in the binding, then
   re-query. No other message types.
7. **UI (gated).**
   - Present: a bound design renders through the data-app document (step 5)
     and the channel (step 6).
   - Editor canvas: bound screens get the runtime and the same channel
     (they keep the canvas sandbox; see Plan corrections).
   - Editor top bar: one "Live data" button (outline, compact) when the
     design is bound. Its tooltip gives the as-of time; it opens a
     `Popover` listing each output with its status and a Refresh (ghost),
     and an amber triangle when any output failed. No new header text.
   - A screen whose read failed shows the runtime's error state that the
     screen markup draws; the skill (step 9) requires every bound screen to
     draw loading, empty, truncated and error states.
8. **Application state.** `view-screen` adds `dataBinding: { dashboardName,
   outputs: [{ name, status }], asOf }` for a bound design, so the agent
   knows what the screen is bound to and what failed.
9. **Skills.** New `.agents/skills/analytics-data-apps/SKILL.md` (read
   `writing-agent-instructions` first): bind with `bind-design-data`;
   reference data only through `$store.an.outputs.<name>` and inputs only
   through `$store.an.setInput`; never write fetched rows into screen HTML,
   never add `fetch`, `XMLHttpRequest`, forms or frames (the CSP blocks them
   anyway); draw loading, empty, truncated and error states; take colors,
   type and spacing from the linked design system's `agentContext`. Point to
   it from `.agents/skills/design-generation`.
10. **Changelog.** From `templates/design`: `agent-native changelog add "Bind a design to Analytics data and preview it with live numbers" --type added`.

## 5. Tests

- `shared/data-app.spec.ts`: parser returns `none`, `bound` and `invalid`;
  caps.
- `server/lib/analytics-data.spec.ts` (A2A mocked): each contract code maps
  to its typed result; a transport failure is `analytics_unavailable`, not
  empty outputs; the token is a user identity bound to Analytics' audience.
- `actions/bind-design-data.spec.ts`: editor only; unknown output names
  refused; unbind clears the binding; a version is recorded.
- `actions/read-design-app-data.spec.ts`: viewer access required; input ids
  outside the binding refused; nothing written to Design's database; a
  viewer who can open the design but not the notebook gets the no-access
  result and no rows; for two viewers, the A2A call carries each viewer's
  own identity, never the author's, and returns that viewer's rows.
- `app/components/design/data-app/document.spec.ts`: the CSP has
  `connect-src 'none'`, `frame-src 'none'` and `form-action 'none'`; the
  runtime script is present.
- `app/components/design/data-app/use-design-app-data.spec.tsx`
  (happy-dom): ignores messages from other sources, wrong nonces, unknown
  message types and unknown input ids; posts only to the frame.

## 8. Defaults for open questions

- [Default] One binding per design, to one Analytics dashboard.
- [Default] The data is read fresh on open and on Refresh; Design keeps no
  copy of rows.
- [Default] Present and the published app are the sandboxed surfaces; the
  editor canvas is not.

## 9. Do not

- Do not let screen code fetch, frame or post forms; do not relax the CSP
  for bound screens.
- Do not store rows in Design's database or in application state.
- Do not read outputs with the author's identity for a viewer.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
