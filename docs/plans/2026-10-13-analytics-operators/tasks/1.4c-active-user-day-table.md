# 1.4c Fresh, cheap panels: an active-user daily table for first-party panels

Lane A (Reliability). Size M. Not gated. **Build only if 1.4b's measurement
says so** (1.4b D1).

Part of the plan's PR 1.4, split out because the existing rollups cannot
answer the expensive panels (see 1.4b section 2). This unit adds the table;
1.4d moves panels onto it.

## 1. Goal

First-party active-user panels (daily, weekly and monthly active users, new
versus recurring, retention) can read one compact row per user, per event
name, per day instead of every raw event, while still honoring the
dashboard's internal-email filter, the signed-in rule and the app filter.
The table is kept up to date at ingest on Postgres, can be backfilled, and on
the BigQuery backend is read from an optional physical table the owner
creates with SQL this unit ships. Nothing reads it yet except tests and the
agent; 1.4d switches panels.

## 2. What the code does today

All paths relative to `templates/analytics/`.

- The two rollups and their ingest write, backfill and query allow-list are
  described in 1.4b section 2 (`server/db/schema.ts:276-289`, `:628-635`;
  `server/lib/first-party-analytics.ts:141-151`, `:951-953`;
  `server/lib/first-party-analytics-rollups.ts:67-181`;
  `server/jobs/analytics-rollup-backfill.ts`).
- `analytics_user_days` has no event name, no email, no `signed_in` and no
  template (`schema.ts:628-635`), which is why the active-user panels, which
  filter `event_name = 'session status' AND signed_in = 'true'`, resolve a
  template from `properties`, and filter on the user's email domain
  (`server/lib/canonical-first-party-dashboard-repair.ts:587-602`,
  `server/lib/first-party-metric-catalog.ts:214-222`), cannot use it.
- Test identities are filtered at read time per table by
  `TEST_IDENTITY_COLUMNS` (`first-party-analytics.ts:1085-1091`); daily event
  rollups rely on ingest excluding them instead.
- BigQuery logical-to-physical mapping is a fixed map of three names
  (`server/lib/first-party-analytics-backend.ts:263-273`, `:1299-1304`) and
  the validator requires all four physical tables to exist (`:1620-1665`).
- Rollup row ids come from `indexedRowId` over the key parts
  (`first-party-analytics-rollups.ts:96-102`), and inserts are idempotent
  upserts, so a replayed batch does not double count.

## 3. Build

1. **Schema (additive).** Add `analyticsUserEventDays` to
   `server/db/schema.ts`: `id` (text pk, `indexedRowId("aued", [tenantKey,
   eventDate, eventName, template, userKey])`), `tenant_key`, `owner_email`,
   `org_id` (nullable), `event_date`, `event_name`, `template` (not null,
   default `''`, the resolved template: reuse the exact `TEMPLATE_EXPR`
   precedence from `first-party-metric-catalog.ts:77-78`, computed in
   TypeScript at ingest), `user_key`, `user_id` (nullable; the account email
   when the event has one), `signed_in` (boolean, true if any event that day
   had `signed_in = 'true'`), `event_count` (integer). Unique index on
   `(tenant_key, event_date, event_name, template, user_key)` and an index on
   `(tenant_key, event_date)`. Add the migration to `server/plugins/db.ts` in
   the existing numbered list with `CREATE TABLE IF NOT EXISTS` and
   `CREATE INDEX IF NOT EXISTS`, nothing else. Run
   `pnpm guard:additive-migrations`.
2. **Ingest.** Extend `upsertFirstPartyAnalyticsRollups`
   (`first-party-analytics-rollups.ts:67`) to also aggregate these rows from
   the same normalized batch and upsert them in the same transaction:
   `event_count = event_count + excluded.event_count`, `signed_in =
   signed_in OR excluded.signed_in`, `user_id = COALESCE(user_id,
   excluded.user_id)`. Skip rows with no `user_key`, as user-days does.
   Extend `NormalizedFirstPartyAnalyticsEventRow` with `userId`, `signedIn`
   and the raw template inputs it needs; the caller at
   `first-party-analytics.ts:951-953` already has them.
3. **Backfill.** Teach `server/jobs/analytics-rollup-backfill.ts` (and its
   route `server/routes/api/analytics-rollups/backfill.post.ts`, an existing
   job endpoint) to fill the new table for a tenant and date range from
   `analytics_events`, in bounded batches with the existing lock
   (`server/lib/analytics-rollup-lock.ts`). Do not run it at startup
   (`performance` skill; `no-boot-data-work` guard).
4. **Query surface.** Add `analytics_user_event_days` to
   `FIRST_PARTY_QUERY_TABLE_NAMES` and `FIRST_PARTY_ROLLUP_TABLES`
   (`first-party-analytics.ts:141-151`), and `analytics_user_event_days:
   "user_key"` to `TEST_IDENTITY_COLUMNS` (`:1087-1091`) so test identities
   stay filtered. Make sure tenant scoping (`scopedTableSource`, `:1097` on)
   covers it like the other rollups.
5. **BigQuery, optional.** Add `userEventDays: tableName(table,
   "_user_event_days")` to `firstPartyAnalyticsPhysicalTables` and the
   source map (`first-party-analytics-backend.ts:263-273`, `:1299-1304`).
   **Do not add it to the required tables in the validator** (`:1620-1665`):
   a deployment without it must keep working. When the table is missing, a
   query naming `analytics_user_event_days` on the BigQuery backend fails
   with a typed error (`FirstPartyAnalyticsUnsupportedSqlError` with a clear
   construct name), which 1.4d uses to keep the raw SQL. Ship the DDL and a
   scheduled-query statement that builds it from the raw table, partitioned
   by `event_date` and clustered by `tenant_key, event_name`, in
   `docs/first-party-analytics-bigquery.md` (create if missing; check
   `templates/analytics/docs/` first). Creating it in the production project
   is the plan owner's step.
6. **Agent.** Add the table and its columns to
   `actions/query-agent-native-analytics.ts:55-64` (description and column
   list) and say when to prefer it: active users, new versus recurring,
   retention, any per-user daily question. Add one line to
   `.agents/skills/data-querying/SKILL.md:26-31`.
7. **Health.** Add the new table's row count and, on BigQuery, its presence
   to `get-first-party-analytics-health`'s table report from 1.4b.

Four areas: **actions** (steps 4 to 7), **skills** (step 6), **UI** (none;
no surface reads it until 1.4d), **application state** (does not apply).

## 5. Tests

- `server/lib/first-party-analytics-rollups.spec.ts`: one batch with two
  events for the same user, day and event name yields one row with
  `event_count` 2; a replayed batch does not double count; `signed_in` is
  true if any event was signed in; rows without a user key are skipped.
- `server/lib/first-party-analytics.spec.ts`: a query on
  `analytics_user_event_days` is scoped to the caller's tenant and excludes a
  test identity.
- `server/jobs/analytics-rollup-backfill.spec.ts`: a backfill over existing
  raw rows produces the same rows as ingest did.
- `server/lib/first-party-analytics-backend.spec.ts`: the validator passes
  without the optional table; a query on it without the table raises the
  typed error.
- `server/plugins/db.spec.ts` or the existing migration spec: the migration
  is additive.
- No source-reading tests.

## 6. Verify

```bash
cd templates/analytics
pnpm exec vitest --run server/lib/first-party-analytics-rollups.spec.ts \
  server/lib/first-party-analytics.spec.ts server/jobs/analytics-rollup-backfill.spec.ts \
  server/lib/first-party-analytics-backend.spec.ts
pnpm guard:additive-migrations && pnpm guards
pnpm --filter analytics dev   # once, so the migration runs
pnpm action db-query --sql "SELECT COUNT(*) FROM analytics_user_event_days"
pnpm action query-agent-native-analytics --sql "SELECT event_date, COUNT(DISTINCT user_key) AS users FROM analytics_user_event_days WHERE event_name = 'session status' AND signed_in AND event_date >= '2026-10-01' GROUP BY event_date ORDER BY event_date"
```

Send a few `/track` events locally first (the collector endpoint) so the
table has rows. Stop the dev server afterwards.
Cannot be verified locally: the BigQuery table and scheduled query (needs
the plan owner to create them in the production project).

## 8. Defaults for open questions

- **D1.** One table keyed by user, day, event name and template, not a
  per-panel materialization: it serves the whole active-user family and the
  agent's own questions. *Reviewer may change.*
- **D2.** The email filter keeps working by storing `user_id` (the account
  email the raw rows already store) on the row. No separate internal-domain
  flag, which would bake one company's domain into ingest. *Reviewer may
  change.*
- **D3.** BigQuery table is optional and owner-provisioned; the template
  does not create BigQuery tables. *Reviewer may change.*

## 9. Do not

- No behavior changes outside this unit: no panel or catalog SQL changes
  (1.4d), no change to the existing two rollups.
- Additive-only schema: new table and indexes, no altered or dropped column.
- No new `/api` routes for app data; the backfill route is the existing job
  endpoint.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value: a
  missing BigQuery table is a typed error, not zero rows.
- No large payloads in SQL: no `properties` JSON on the new table.
- No work at cold start: the backfill runs only through the job.
