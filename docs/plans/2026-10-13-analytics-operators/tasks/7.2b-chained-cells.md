# 7.2b Chained cells

Lane C (Notebook). Size M. **Gated: the "Reads from" control and the "Query
this result" and "Chart this result" menu items need prototype sign-off.**
Depends on 7.1a, 7.1b and 7.2a.

Paths are relative to `templates/analytics/` unless they start with
`packages/` or `docs/`.

## 1. Goal

A notebook cell can query the result of a cell above it. The user writes
`SELECT plan, sum(mrr) FROM revenue GROUP BY plan` where `revenue` is an
earlier cell, and gets an answer without rewriting or re-running that cell's
warehouse query. "Chart this result" on a SQL cell adds a chart cell that reads
from it, so charting a result never copies its SQL.

## 2. What the code does today

- Panel sources are a fixed list: `DASHBOARD_PANEL_SOURCES`
  (`server/lib/dashboard-panel-query.ts:21-29`). The same list is repeated by
  hand in `actions/mutate-dashboard.ts:93-104` (insert schema),
  `actions/update-dashboard.ts:397-405` (`validSources`),
  `app/pages/adhoc/sql-dashboard/types.ts:1-8` (`DataSourceType`),
  `app/pages/adhoc/sql-dashboard/PanelEditorDialog.tsx:66-74` (`SOURCES`) and
  `app/routes/chart.tsx:24` (`VALID_SOURCES`).
- Each source resolves through a registry built from that list
  (`server/lib/dashboard-panel-source-resolver.ts:33-62`) into
  `runDashboardPanelQuery` (`server/lib/dashboard-panel-query.ts:404-516`).
- The `program` source already carries a JSON descriptor in `panel.sql`
  instead of SQL, normalized by `normalizeDashboardPanelQuery` (`:102-120`).
- The browser computes each panel's query from the panel alone:
  `interpolateDashboardPanelSql(serializePanelSql(panel.sql), vars, panel)`
  (`app/pages/adhoc/sql-dashboard/index.tsx:334-341`), then `SqlChart` sends
  `{ source, query }` to `query-dashboard-panel`
  (`app/components/dashboard/SqlChart.tsx:1177-1190`, `app/lib/sql-query.ts:152-160`).
  `query-dashboard-panel` runs it with the viewer's credentials
  (`actions/query-dashboard-panel.ts:23-38`).
- The server builds the same query with `buildPanelQuery(panel, vars)`
  (`server/lib/dashboard-panel-runner.ts:75-86`), called by verification
  (`server/lib/dashboard-panel-verification.ts:501`) and email reports
  (`server/lib/dashboard-report-render.ts:114`). Neither sees sibling panels.
- There is no stored per-panel result. Repeat reads are served by per-source
  caches: the BigQuery cache table (`bigquery_cache`, `server/db/schema.ts`,
  with `expires_at`), the first-party cache (`first_party_analytics_cache`),
  and a data program's last good run.

## Plan corrections

- "Without going back to the source" holds only while the upstream result is in
  that source's cache. There is no durable cell result, and storing one in SQL
  would break the no-large-payloads rule. v1 reads upstream rows through the
  existing caches: a warm cache costs no source query, a cold one costs one.
- The source list is duplicated in five places. Adding `cells` by hand to each
  would be the sixth copy. 2.1a already plans the consolidation into
  `shared/dashboard-panel-sources.ts`; this unit reuses it.

## 3. Build

1. **Use the shared source list.** 2.1a creates
   `shared/dashboard-panel-sources.ts` with `DASHBOARD_PANEL_SOURCES` and
   `EMBEDDABLE_PANEL_SOURCES` and replaces the hand-copied lists; 2.1a is a
   hard dependency of this unit (build waves in the plan README put it in
   wave 1). Add `"cells"` there and leave it out of
   `EMBEDDABLE_PANEL_SOURCES` (chat embeds cannot chain). Do not consolidate
   the lists yourself.
2. **Descriptor.** A `cells` panel stores
   `panel.sql = JSON.stringify({ inputs: ["revenue"], sql: "SELECT ..." })`.
   Add `shared/notebook-cells.ts` with:
   - `parseCellsDescriptor(raw): { inputs: string[]; sql: string }` (throws a
     typed error on bad JSON or a missing field).
   - `buildCellsQuery(panel, panels, vars, depth = 0)`: for each input id,
     find the panel, require it to sit **above** this panel in `panels`, build
     its query (recursing for `cells` inputs, depth cap 4), and return the
     serialized payload
     `{ sql, inputs: [{ name, source, query }] }`.
   - Errors are typed: `input_missing`, `input_not_above`, `input_depth`,
     `input_is_text` (text, section, input and extension cells have no rows).
3. **One builder for client and server.** Change `buildPanelQuery` to
   `buildPanelQuery(panel, vars, panels)` and route `cells` through
   `buildCellsQuery`. Update its two callers to pass the config's panels. On
   the client, compute `resolvedSql` at `index.tsx:334` with the same shared
   builder, passing the notebook's panels.
4. **Resolver.** In `runDashboardPanelQuery` add `source === "cells"`: parse
   the payload, run each input through `runDashboardPanelQuery` (bounded with
   the existing `MAX_CONCURRENT_SQL_QUERIES` from `shared/sql-query-limits.ts`),
   propagate the first input failure as a typed error naming the input
   (`input_failed`, with the upstream message), then call `runCellSql` from
   7.2a with the inputs as tables named by cell id. Input rows over the 7.2a
   caps return `input_too_large` naming the cell. Map
   `CellEngineUnavailableError` to `engine_unavailable`. Return the standard
   `{ rows, schema, truncated }` shape.
5. **Trust boundary.** Input queries come from the browser exactly as every
   panel query does today, and run with the viewer's credentials. Do not add
   owner credentials or skip the per-source access path.
6. **Validation.** In `collectDashboardConfigIssues` /
   `validatePanelSql` (`actions/update-dashboard.ts`) validate `cells` panels:
   descriptor parses, inputs exist and are above, no text or input cells as
   inputs. Input ids become table names: ids matching
   `^[a-z][a-z0-9_]{0,62}$` (7.1a generates `cell_xxxxxxxx`) are used bare;
   any other id (for example with `-`, from the agent or a converted grid
   panel) is quoted as an identifier by the engine wrapper, and the editor
   shows the quoted form. Reject only ids no quoting can express (empty, or
   containing a double quote).
7. **Verification.** `verifyPanel` passes the config's panels to
   `buildPanelQuery`; a `cells` panel executes (no dry run). Its inputs share the
   per-save budget. Timeouts stay `unverified` with note `timeout`.
8. **Editor UI (gated).** In the notebook SQL cell:
   - A "Reads from" `Popover` with a `Command` list of the cells above that
     return rows, multi-select. Selecting one switches the cell's source to
     `cells`. Show the engine's dialect name in the SQL editor placeholder.
   - SQL cell menu items (text only): "Query this result" inserts a `cells`
     SQL cell below with `SELECT * FROM <id>`; "Chart this result" inserts a
     chart cell with `source: "cells"`, the same input and `SELECT * FROM <id>`.
   - Errors render through the plain-language panel error states (1.5): map
     each typed code in step 2 and 4 to the copy below, with a button that
     opens "Reads from" when the fix is picking another cell.
9. **Application state.** No new keys. `selected-object` for a cell already
   carries `source`; 7.3 adds the input list to the chat context lines.
10. **Skills.** Extend `.agents/skills/notebooks/SKILL.md`: the `cells` source,
    the descriptor shape, the dialect, "inputs must be above", the caps, and
    that a cold upstream cache runs the upstream query once. Add `cells` to
    "Valid Panel Sources" in `.agents/skills/dashboard-management/SKILL.md:89`
    with one line saying it is for notebooks. Read
    `.agents/skills/writing-agent-instructions` first.
11. **Changelog.** `agent-native changelog add "Notebook cells can query the results of earlier cells" --type added`.

## 8. Defaults for open questions

- **[Default] Cells read only cells above them.** Order is the dependency
  order, so cycles cannot exist.
- **[Default] Inputs are listed explicitly in the descriptor**, not inferred by
  scanning SQL for names.
- **[Default] No durable cell result cache in v1.** Revisit with blob storage if
  cold upstream runs prove costly.
- **[Default] Chain depth cap 4.**
- **[Default] `cells` is notebook-only in the UI.** The server accepts it on any
  SQL dashboard so the agent is not surprised, but the grid editor does not
  offer it.

## 9. Do not

- No behavior changes outside this unit; existing sources resolve exactly as
  before.
- Additive-only schema (none needed).
- No new `/api` routes for app data; the source goes through
  `query-dashboard-panel`.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials, and no switch to owner
  credentials for inputs.
- No `catch` or default that turns a failure into a normal-looking value: an
  input failure is never an empty input table.
- No large payloads in SQL or application state; no persisted cell rows.
- Do not add `cells` by hand to a sixth source list.
