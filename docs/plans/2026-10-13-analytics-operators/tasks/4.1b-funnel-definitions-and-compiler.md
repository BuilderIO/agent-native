# 4.1b Funnel definitions and SQL compiler

Lane D (Growth). Size M. Not gated (no new UI; the builder UI is 4.1c).

## 1. Goal

A funnel panel is defined by its steps ("Signup viewed", then "Signup
clicked", then "Signed up", within 7 days), not by hand-written SQL. The agent
can create or change one through `mutate-dashboard` by writing a small
definition, the stored SQL is always generated from that definition, and the
same panel runs unchanged on the PostgreSQL and BigQuery first-party backends.
Numbers from two funnels with the same steps always agree, because one
compiler writes the SQL.

## 2. What the code does today

- A `funnel` chart type already exists (`app/pages/adhoc/sql-dashboard/types.ts:10-23`).
  It renders whatever rows the SQL returns: `resolveDashboardFunnelRows`
  (`shared/dashboard-funnel.ts:33-83`) takes a label column and a numeric column
  and computes share of first step and step-to-step drop-off. The render plan
  wires it in `shared/panel-render-contract.ts:707-713`, the UI draws it in
  `app/components/dashboard/SqlChart.tsx:1427-1430` and `:2526-2579`, and email
  reports draw it (`server/lib/dashboard-report-render.ts:419-427`, `:1065`).
  The agent is told to keep stage order with `ORDER BY`
  (`.agents/skills/dashboard-management/SKILL.md:225-228`).
- Every ordered funnel today is hand-written SQL. The activation funnel
  (`server/lib/first-party-metric-catalog.ts:1137-1190`) chains `LEFT JOIN
  LATERAL` subqueries per step. `LATERAL` is on the list of constructs with no
  BigQuery translation (`server/lib/first-party-analytics-backend.ts:1273-1286`,
  "set-returning PostgreSQL functions"), so that panel returns
  `unsupported_by_backend` for a tenant on the BigQuery sink
  (`server/lib/dashboard-panel-query.ts:461-497`).
- Hand-written growth SQL drifts. Retention alone has eight legacy SQL
  variants kept for repair matching (`server/lib/first-party-metric-catalog.ts:768-787`)
  and a separate hand-written BigQuery version
  (`server/lib/canonical-first-party-dashboard-repair.ts:176`, `:373`).
- First-party panels are PostgreSQL SQL over `analytics_events`,
  `analytics_event_daily_rollups`, `analytics_user_days` and
  `session_recordings` (`server/lib/first-party-analytics.ts:141-147`), checked
  by `validateFirstPartyAnalyticsSqlShape` (`:991-1079`) and translated to
  GoogleSQL for the BigQuery sink (`first-party-analytics-backend.ts:1199-1297`).
  Every top-level CTE that reads `analytics_events` needs its own time bound
  (`.agents/skills/dashboard-management/SKILL.md:115-133`,
  `server/lib/dashboard-time-scope.ts:296`).
- The shared time-range SQL helpers (`daysAgoSql`, `todaySql`,
  `dashboardTimeRangeFilter`) are private to the server metric catalog
  (`server/lib/first-party-metric-catalog.ts:150-157`, `:172-180`), so client or
  shared code cannot reuse them.
- Panel SQL reaches the query path through `interpolateDashboardPanelSql(sql,
  vars, panel)` (`app/pages/adhoc/sql-dashboard/interpolate.ts:36-57`), called
  by the dashboard page (`app/pages/adhoc/sql-dashboard/index.tsx:336`), panel
  verification, the report runner, sheet export, review previews and
  `validatePanelSql` (`actions/update-dashboard.ts:548-600`). `SqlChart` falls
  back to the raw `panel.sql` when it gets no resolved SQL
  (`app/components/dashboard/SqlChart.tsx:1180`). The client sends the
  resolved string to `query-dashboard-panel` (`actions/query-dashboard-panel.ts:14-17`).
- Every validating writer normalizes panels inside
  `collectDashboardConfigIssues` (`actions/update-dashboard.ts:269-270`, which
  calls `normalizeDashboardConfig` from `shared/dashboard-config-normalization.ts:14-52`).
  `update-dashboard`, `mutate-dashboard` (`actions/mutate-dashboard.ts:48-52`,
  `:545`) and GitHub folder sync (`server/lib/dashboard-github-sync/folder-sync.ts:441`,
  `:485`) all go through `assertValidDashboardConfig`. `compose-dashboard` does
  not call it; it only imports the time-scope check (`actions/compose-dashboard.ts:24`).
- New panel config keys must be registered in `PANEL_CONFIG_KEYS`
  (`shared/panel-render-contract.ts:45-68`) or the build fails.
- Event names for a picker come only from Lab-gated actions:
  `list-event-catalog` (`actions/list-event-catalog.ts:78`) and
  `list-session-event-names` (`actions/list-session-event-names.ts:41`) both
  call `assertSessionsTriageLabEnabled`. The catalog read also returns an empty
  result when the index is not ready (`server/lib/session-event-index.ts:729-737`),
  which a picker cannot tell apart from "no events".

## 3. Build

1. Move the time-range helpers to shared code. Create
   `shared/first-party-time-filter-sql.ts` exporting `daysAgoSql`, `todaySql`
   and `dashboardTimeRangeFilter`, moved byte for byte from
   `server/lib/first-party-metric-catalog.ts:150-157,172-180`, and import them
   back into the catalog. Repair code compares stored SQL text against these
   strings, so the output must not change by a single character.
2. Create `shared/growth-panels.ts`:
   - `growthEventFilterSchema` (zod): `{ field, op, value }` with `op` in
     `equals | not_equals | contains | in | exists`, the same operators alert
     filters use (`actions/save-analytics-alert-rule.ts:10-21`). Allowed
     `field` values: `app`, `template`, `path`, `hostname`, `signed_in`,
     `properties.<key>`, `context.<key>`, where `<key>` matches
     `^[A-Za-z0-9_.-]{1,64}$`.
   - `funnelDefinitionSchema`: `{ kind: "funnel", version: 1, steps: [{
     eventName, label?, filters? }] (2 to 8 steps), countBy: "user" | "session"
     (default "user"), conversionWindow: { value: 1..90, unit: "hour" | "day" }
     (default 7 days) }`. Export `growthPanelDefinitionSchema` as a
     discriminated union on `kind` so 4.1d can add `retention`.
   - `compileGrowthPanelSql(definition): string`. For a funnel, emit one CTE
     per step. Step 1: first time per user (or session) the step's event
     happened in the dashboard range. Step N: first time the step's event
     happened at or after step N-1's time and within the conversion window of
     step 1. Each CTE reads `analytics_events` with its own
     `dashboardTimeRangeFilter("event_date")` bound. The final `SELECT` is a
     `UNION ALL` of exactly one row per step: `step_index`, `step` (the label,
     or the event name when there is no label) and `count`, ordered by
     `step_index`. A step nobody reached returns 0, never a missing row.
   - Identity: `countBy: "user"` uses `NULLIF(user_key, '')`;
     `countBy: "session"` uses `NULLIF(session_id, '')`. Rows with a null key
     are excluded from every step.
   - Only use constructs the BigQuery translator round-trips: no `LATERAL`,
     `FILTER (WHERE ...)`, `generate_series`, `DISTINCT ON`, or `AT TIME ZONE`
     (`first-party-analytics-backend.ts:1273-1286`). Property filters use the
     `properties::jsonb ->> 'key'` form the translator rewrites
     (`translatePostgresJsonOperators`, `:1174`). Prove both dialects in tests
     (step 9) rather than reasoning about it.
   - Every user-supplied string (event names, labels, filter values, property
     keys) goes through one literal helper that doubles single quotes. Never
     interpolate a raw value.
   - `panelRunnableSql(panel)`: returns `compileGrowthPanelSql(panel.config.growth)`
     when the panel has a valid growth definition, else `panel.sql`. Throws a
     typed `GrowthPanelDefinitionError` (with the panel id and the zod issue)
     for an invalid definition. Never fall back to `panel.sql` for an invalid
     definition: that would show stale numbers as if they were current.
   - `GROWTH_COMPILER_VERSION = 1`.
3. Make `interpolateDashboardPanelSql` (`app/pages/adhoc/sql-dashboard/interpolate.ts:36-57`)
   use `panelRunnableSql(panel)` instead of its `sql` argument when
   `panel.config.growth` is set. Add one comment: the stored `sql` of a growth
   panel is a cache of the compiler output, so running it directly would run
   an older compiler's SQL. Change `SqlChart.tsx:1180` to fall back to

## 8. Defaults for open questions

- [Default, reviewer can change] Conversions count only inside the dashboard
  range. A user who did step 1 on the last day and step 2 the next day is not
  converted until the range includes that day. Simpler and always bounded.
- [Default] Step N must happen at or after step N-1 and within the window
  measured from step 1 (the usual product-analytics definition).
- [Default] Only the `timeRange` dashboard filter applies to growth panels.
  Other dashboard filters are ignored and the skill says so.
- [Default] 2 to 8 steps; window 1 to 90 days or hours.
- [Default] The definition lives in `config.growth` on a `first-party` panel
  rather than in a new `source` value. A new source would touch about ten
  switch sites that 2.1 is also changing.
- [Default] `list-analytics-event-names` is not Lab-gated. Reviewer may
  instead graduate `list-event-catalog` out of the Lab.
