# 3.3c: Account deep dive resolves through the account map and adds billing

Lane B. Size S. Split from 3.3; needs 3.3a and 3.1b.

## 1. Goal

When someone asks about a named customer, the deep dive starts from the
account map: it locks onto one account (or says the name is ambiguous and
lists the candidates), pulls HubSpot and Gong evidence for that account's
linked companies, and adds the account's Stripe billing (current MRR, recent
movement, recent invoices). Answers stop mixing two customers that share a
word in their names.

## 2. What the code does today

- Identity is a free-text HubSpot deal search for the user's words
  (`templates/analytics/actions/account-deep-dive.ts:431-445`), then
  companies associated with those deals, else a company search
  (`account-deep-dive.ts:477-503`). Several unrelated deals can match one
  word and all of them are merged into one bundle
  (`account-deep-dive.ts:473-475`, `account-deep-dive.ts:551-563`).
- The result has HubSpot and Gong sections and a coverage block with
  `productUsageIncluded: false` and no Stripe at all
  (`account-deep-dive.ts:582-615`, `productUsageIncluded: false` at
  `account-deep-dive.ts:610`). The guidance string tells the agent the bundle
  lacks cross-source identity validation (`account-deep-dive.ts:613-614`).
- The action is an MCP read (`account-deep-dive.ts:419-422`,
  `templates/analytics/actions/mcp-action-contract.spec.ts:40`) and its
  existing spec is `templates/analytics/actions/account-deep-dive.spec.ts`.
- `templates/analytics/AGENTS.md:18` sends named-account questions to
  `account-deep-dive`.

## Plan corrections

None. The plan's "generalizes what account-deep-dive does for one account"
is done by 3.3a's map; this unit makes the deep dive use it.

## 3. Build

1. `templates/analytics/actions/account-deep-dive.ts`:
   - Add optional `accountId` to the schema. When absent, call 3.3a's
     resolver (`resolveAccount(query)`, the server function behind
     `resolve-account`) first.
   - `resolved`: use the account's linked HubSpot company ids as the company
     set (`getAssociatedHubSpotObjects` from companies to deals, contacts,
     tickets, notes, emails), skipping the free-text deal search.
   - `ambiguous`: return early with `identity: { status: "ambiguous", candidates }`
     and no merged evidence; the agent asks which one.
   - `not_found` or `map_empty`: keep today's search path and set
     `identity: { status: "unmapped", reason }` so the answer says identity
     was not locked.
   - Add `identity: { status, accountId, name, domains, links: { stripe, hubspot, product }, matchQuality }`
     to every result.
   - Add a `stripe` section for resolved accounts: per linked customer,
     `mrr_current`, `mrr_window_start` and `movement` read from 3.1b's
     `customers` view through `runDataProgram` (cached; a
     `background_pending` or failure is reported in `coverage.gaps`, never as
     zero MRR), plus the last six invoices from `getInvoices` (3.1a makes it
     paginate and report `truncated`).
   - Coverage: add `stripeIncluded`, `identityLocked`. Keep
     `productUsageIncluded: false` (4.4 adds usage).
   - Update the `guidance` text: attribute identity to the account map and
     state match quality.
2. Skills: `templates/analytics/.agents/skills/account-health/SKILL.md`
   identity lock references `identity.status` from the deep dive;
   `templates/analytics/.agents/skills/cross-source-analysis/SKILL.md`
   "Account Deep-Dive Recipe" step 1 becomes "resolve through the account
   map".
3. UI: none. Application state: when the Accounts sheet (3.3b) is open, the
   agent passes `selected-object.id` as `accountId`; document that in the
   account-health skill. No new keys.
4. Changelog: `agent-native changelog add "Account deep dives lock onto one customer through the account map and include Stripe billing." --type improved`.
