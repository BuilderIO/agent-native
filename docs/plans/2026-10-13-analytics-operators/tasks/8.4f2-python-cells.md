# 8.4f2 Python cells in notebooks

Lane E (Holy-shit features). Size M. Gated twice: on the 7.6 spike's five go
conditions (inherited from 8.4f1; do not start until 8.4f1 has merged with
all five recorded), and on prototype sign-off for the Python cell, its

`prototypes/analytics-operators/`). Where the signed-off prototype differs
from this brief, the prototype wins.

Depends on: 8.4f1, 7.1b, 7.2b, 8.4c (graph and stale states). Merge after
8.4c. Blocks: nothing.

Paths are relative to `templates/analytics/` unless they start with
`packages/`.

## 1. Goal

An analyst adds a Python cell under a SQL cell, writes pandas against `df`
(the cell above's result), assigns `result`, and presses Run. A few seconds
later the cell shows the result table, and cells below can read it like any
other cell. The code never sees credentials, files or the network: its only
input is the one table it was given. A run that times out, runs out of memory
or crashes says so plainly. The agent can add and edit Python cells the same
way.

## 2. What the code does today

- 8.4f1 provides `runPython({ code, input, timeoutMs, memoryCapBytes, maxOutputRows, signal })`
  in `packages/core`, runnable only inside `server-agent-background` on hosted
  runtimes (brief `tasks/8.4f1-python-sealed-evaluator.md`).
- Panel queries run in the `server` function: the browser calls
  `query-dashboard-panel` (`actions/query-dashboard-panel.ts`, readOnly,
  `agentTool: false`, `:45-47`) with the caller's credential context
  (`:49-52`), into `runDashboardPanelQuery`
  (`server/lib/dashboard-panel-query.ts:541-711`). `server` functions time out
  at 75 s (`netlify.toml:22-23`) and will not carry Pyodide (8.4f1 entry
  criterion 5).
- The background function routes non-chat work through processors:
  `AGENT_BACKGROUND_PROCESSOR_FIELD` with `a2a`, `integration`, `agent-team`
  and `route` (`packages/core/src/agent/durable-background.ts:64-69`), and
  `resolveDurableBackgroundDispatchPath` (`:131`).
- Private blob storage: `putPrivateBlob`
  (`packages/core/src/private-blob/registry.ts:417`) and its readiness check
  (`:393`). 2.3a already stores imports there.
- The `cells` source and descriptor are 7.2b's (brief); inputs must sit above.
- Highest migration on the integration branch is 173; 174 and 175 are
  reserved (1.4c, 4.2c); 176 to 189 belong to 8.1 to 8.3; 8.4d owns 190.

## Plan corrections

- A Python cell cannot run inside a panel query: Pyodide lives only in the
  background function (entry criterion 5), which is asynchronous. So a Python
  cell is run then read: Run sends the job to the background function, the
  output table goes to private blob storage, and the cell reads the stored
  output. A run record in SQL holds only status, hashes and the blob handle.
- Python cells do not auto-run on every input change in v1 (cold start is
  seconds per run); after an upstream change they show 8.4c's stale state
  until Run.

## 3. Build

1. **Schema (additive), migration 191.** Table `notebook_python_runs` in
   `server/db/schema.ts` and `server/plugins/db.ts` (`version: 191`,
   `name: "notebook-python-runs-table"`; 176 to 189 are 8.1 to 8.3, 190 is
   8.4d): `id TEXT PRIMARY KEY, dashboard_id TEXT NOT NULL, panel_id TEXT NOT NULL, code_hash TEXT NOT NULL, input_hash TEXT NOT NULL, status TEXT NOT NULL, reason TEXT, error TEXT, output_blob TEXT, row_count INTEGER, truncated BOOLEAN NOT NULL DEFAULT false, cold_start_ms INTEGER, started_at TEXT NOT NULL, finished_at TEXT, owner_email TEXT NOT NULL, org_id TEXT`.
   Index `(dashboard_id, panel_id, started_at)`. `error` capped at 4,000
   characters; the traceback beyond that is cut with a marker. Rows never
   hold data. Keep the last 10 runs per cell. Run `pnpm
   guard:additive-migrations`.
2. **Source.** Add `"python"` to `shared/dashboard-panel-sources.ts`, not to
   `EMBEDDABLE_PANEL_SOURCES`. A Python panel stores
   `panel.sql = JSON.stringify({ input: "<cell id>", code: "<python>" })`
   (descriptor, as 7.2b does), parsed by `parsePythonDescriptor` in
   `shared/notebook-python.ts` with typed errors. Code is capped at 50,000
   characters.
3. **Run action.** `actions/run-python-cell.ts`: `{ dashboardId, panelId }`.
   `assertAccess("dashboard", id, "editor")`. Builds the input cell's query
   through 7.2b's builder, runs it with the caller's credentials in `server`
   (the same path as any panel), checks it fits 8.4f1's caps, writes the input
   table to private blob storage as columnar JSON, inserts a `running` run
   row with `code_hash` and `input_hash`, and dispatches a background job with
   `{ runId }` through the `route` processor
   (`durable-background.ts:64-69`). Returns `{ runId }` at once. If private
   blob storage is not configured (readiness check), it fails with
   `blob_storage_missing` and the cell says so; it never runs without storing.
4. **Background job.** A processor route in the template
   (`server/lib/python-cell-runner.ts`) loads the run, reads the input blob,
   calls `runPython` with 60 s, 1.5 GB and 100,000 rows, writes the output
   blob, and updates the row to `ok` (with `row_count`, `truncated`,
   `cold_start_ms`) or `failed` (with `reason` and `error`). A job that dies
   without writing leaves `running`; a run older than 3 minutes in `running`
   reads as `failed` with `reason: "lost"`.
5. **Read.** In `runDashboardPanelQuery` add `source === "python"`: find the
   latest run for the panel whose `code_hash` matches the panel's code. If
   none: typed `python_not_run`. If its `input_hash` differs from the current
   input query's hash: return the stored rows with `stale: true` (8.4c shows
   Out of date). If `running`: typed `python_running`. If `failed`: typed
   `python_failed` with reason and message. If `ok`: read the output blob and
   return the standard `{ rows, schema, truncated }`. Cells below read a
   Python cell through `cells` like any other cell.
6. **UI (gated).** 7.1b's add-cell menu gains Python. The cell: a code editor
   (8.4e1's CodeMirror with `@codemirror/lang-python`; `pnpm view` its
   version) under a Reads from picker (single cell), a Run button
   (`IconPlayerPlay`, compact) and Cmd/Ctrl+Enter, then the result table.
   States: not run ("Run this cell to see its result"), running (a spinner on
   Run, the previous result dimmed, elapsed seconds), stale (8.4c), failed
   (1.5a's error state with the reason: timeout, memory, crashed, lost; the
   Python traceback in a collapsible `pre`), and blob storage missing. Show
   "Python can only read the table above. It has no internet or file access."
   as a tooltip on the cell's kind badge, not as a subtitle.
7. **Agent.** `mutate-dashboard` inserts and edits Python cells (descriptor);
   `run-python-cell` runs one (agent tool); `get-python-cell-run` (read-only)
   returns the latest run's status, reason, error and row count. Add both to
   the notebook skill and `DASHBOARD_EDIT_TOOLS` only for the write.
   8.4f1's `run-code` `language: "python"` stays off the agent's tool
   description in this unit.
8. **Application state.** `selected-object` for a Python cell adds
   `pythonRunStatus`. No new key.
9. **Skills.** `.agents/skills/notebooks/SKILL.md`: "Python cells": `df` is
   the one input, assign `result`, pandas and numpy only, no network or
   files, 60 s and 1.5 GB limits, run then read, and how to report a failed
   run. Read `.agents/skills/writing-agent-instructions` first.
10. **Changelog.** `agent-native changelog add "Python cells in notebooks: run pandas on the result above" --type added`.

## 8. Defaults for open questions

- [Default] Run then read with stored output; no auto-run for Python cells.
- [Default] One input table per cell; no provider access from Python.
- [Default] Output stored in private blob storage, last 10 runs per cell.

## 9. Do not

- Do not run Python in the `server` function or in the browser.
- Do not store input or output rows in SQL or application state.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
