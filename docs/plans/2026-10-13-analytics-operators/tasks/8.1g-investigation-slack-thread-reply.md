# 8.1g Post a finished investigation back to the Slack thread it was asked in

Lane E (Holy-shit features). Size S. Not gated: it adds no UI. The reply
uses the answer and confidence wording of the signed-off 8.1 screens.
Depends on: 8.1c (the Slack route and the delivery hook; its server half is
enough), 8.1a, 5.2. Blocks: none.

Paths are relative to `templates/analytics/` unless they start with
`packages/` or `docs/`. Code facts were read on the integration branch
`claude/analytics-template-competitor-3faa16` at `5e021f7b35`; re-check
line numbers before editing.

## 1. Goal

Someone asks "Why did signups drop?" in a Slack direct message. The agent
replies at once with one line and the notebook link (8.1c). When the
investigation finishes, a second reply lands in the same thread: the
plain-language answer, the confidence label ("High confidence.") or "No
change found.", and the absolute notebook link. A partial or failed
investigation says so in that reply. The in-app notification still goes out
(8.1c); the Slack reply is in addition to it, never instead of it.

## 2. What the code does today

- An action that runs inside a Slack turn can see the message it came
  from: the integration run sets `integration.incoming` on the request
  context (`packages/core/src/integrations/webhook-handler.ts:1119-1135`;
  the field is declared at `packages/core/src/server/request-context.ts:164-188`,
  and `getRequestContext` is exported from `@agent-native/core/server`).
  A Slack message carries `platformContext.channelId`, `threadTs`, `teamId`
  and `threadRef` (`packages/core/src/integrations/adapters/slack.ts:272-301`),
  and an `installationKey` when the install is named (`:739-743`).
- Core can post into a Slack thread after the turn has ended.
  `PlatformAdapter.sendMessageToTarget(message, target)`
  (`packages/core/src/integrations/types.ts:217-220`) takes an
  `OutboundTarget { destination, threadRef, tenantId, installationKey }`
  (`:96-103`). The Slack adapter resolves the bot token for the target,
  posts with `chat.postMessage` and `thread_ts`, splits long text, and
  throws when Slack returns no message timestamp, so a post is never
  assumed (`adapters/slack.ts:598-665`).
- Late replies already use it: background automations post their result to
  a saved channel and thread (`packages/core/src/jobs/background-automation-runner.ts:875-897`),
  and Dispatch's `send-platform-message` posts to a destination and thread
  with the exported `slackAdapter` (`packages/dispatch/src/actions/send-platform-message.ts:129-139`).
  A2A continuations post a late result back into the original thread from
  the stored incoming message, with an idempotency key
  (`packages/core/src/integrations/a2a-continuation-processor.ts:925-931`).
- Each Slack thread maps to one internal chat thread in
  `integration_thread_mappings`, with the Slack context
  (`packages/core/src/integrations/thread-mapping-store.ts:8-20`, saved at
  `webhook-handler.ts:749-765`).
- Analytics: `analyticsWebAddress()` gives the absolute base for links
  (`server/plugins/integrations.ts:18-21`); the messaging rules live in
  `server/lib/analytics-integration-prompt.ts`. 8.1a (brief) gives
  `analytics_investigations` the `slack` origin, `answer`, `summary`,
  `confidence` and `outcome`, and the `onInvestigationFinished` hook. 8.1c
  (brief) starts investigations from Slack direct messages only and
  registers delivery on that hook.

## Plan corrections

- **No new core API is needed.** 8.1c assumed core could not post into a
  thread once the turn ended. `sendMessageToTarget` does that today.
- **The thread is captured at start, not looked up at the end.** The finish
  runs in the investigator's background task, which has no incoming
  message. `start-investigation` stores the reply target while the Slack
  turn is still live.

## 3. Build

1. **Schema (additive), migration 179** in `server/db/schema.ts` and
   `server/plugins/db.ts` (`version: 179`, `name:
   "analytics-investigation-slack-reply"`): `ALTER TABLE
   analytics_investigations ADD COLUMN IF NOT EXISTS reply_target TEXT`,
   `ADD COLUMN IF NOT EXISTS reply_status TEXT` and `ADD COLUMN IF NOT
   EXISTS reply_error TEXT`. Existing rows stay null. Run
   `pnpm guard:additive-migrations`.
2. **Capture** (`actions/start-investigation.ts`, 8.1a): when the origin is
   `slack` and `getRequestContext()?.integration?.incoming` is a Slack
   message, store `reply_target` as JSON `{ platform: "slack", destination:
   <channelId>, threadRef: <threadTs>, tenantId: <teamId>,
   installationKey? }` and `reply_status: "pending"`. A deduped start
   (8.1a) that reuses an investigation keeps its first target; the second
   thread gets only 8.1c's link reply. No other origin stores a target, and
   the target never comes from agent input.
3. **Post** `server/lib/investigation-slack-reply.ts`, called from 8.1c's
   delivery (`server/lib/investigation-delivery.ts`) after the in-app
   notification:
   - Claim the reply with a conditional update (`reply_status` from
     `pending` to `sending`), so a retried hook cannot post twice.
   - Text, server-written English like 8.1c's notification text: for
     `complete`, 8.1a's `answer`, a blank line, then "<High> confidence.";
     for `no_change`, the answer then "No change found."; for `partial`,
     "Partial: some checks didn't run." before the answer; for `failed`,
     "The investigation couldn't finish: <error>." Then "Open the
     investigation: <link>", with the absolute link from
     `analyticsWebAddress()` and `/dashboards/<notebookId>`. With no web
     address, the line names the notebook by title and has no link. The
     adapter splits long answers; nothing is cut.
   - Send with `slackAdapter().sendMessageToTarget(slackAdapter().formatAgentResponse(text),
     target)` (from `@agent-native/core/server`, as Dispatch does) inside
     `runWithRequestContext` for the investigation owner.
   - Success sets `reply_status: "sent"`. A thrown post (no token for that
     workspace, the conversation gone, no message timestamp) sets
     `reply_status: "failed"` and `reply_error`, with a log line; the
     investigation status and the in-app delivery stay as they are. Never
     set `sent` unless the adapter returned.
4. **Read back.** `get-investigation` adds `reply: { status, error? } |
   null`, so the agent can answer "did it post back?" truthfully.
5. **Messaging rules** (`server/lib/analytics-integration-prompt.ts`, next
   to 8.1c's direct-message rule): the first reply says in one line that the
   answer will post in this thread when it is ready. Update
   `.agents/skills/slack-answers/SKILL.md` (Reply rules) and its
   byte-identical template copy if one exists, and the delivery section of
   `.agents/skills/investigations/SKILL.md`.
6. **Application state:** none.
7. **UI:** none.
8. **Changelog:** `agent-native changelog add "Investigations asked in Slack post their answer back in the same thread" --type added`.

## 4. Copy

No UI copy. The Slack reply text ("<High> confidence.", "No change found.",
"Partial: some checks didn't run.", "The investigation couldn't finish:
<error>.", "Open the investigation: <link>") is server-written English like
8.1c's notification text; list it in 1.5's inventory. No em dashes.

## 5. Tests

- `server/lib/investigation-slack-reply.spec.ts` (adapter mocked): a
  Slack-started investigation posts once to its channel and thread with the
  answer, the confidence label and the absolute link; `no_change`,
  `partial` and `failed` each get their text; a second hook call posts
  nothing; a throwing adapter sets `failed` with the error and leaves the
  investigation status and the in-app notification alone; no web address
  means no link; an investigation without a `reply_target` (chat, panel,
  alert) posts nothing.
- `actions/start-investigation.spec.ts` (extend): a start inside a Slack
  integration context stores the channel, thread and team; a start outside
  one stores nothing; a deduped start keeps the first target.
- `server/plugins/integrations.spec.ts` (extend): the messaging prompt says
  the answer posts back in the thread.

## 8. Defaults for open questions

- [Decided by the owner, 2026-10-14] A question asked in Slack gets its
  finished answer posted back in the thread where it was asked.
- [Default] Investigations still start only from Slack direct messages
  (8.1c), so the thread is the direct message thread. If channel starts are
  allowed later, the same capture posts into the channel thread.
- [Default] One finished reply per investigation. A re-run started from the
  notebook in Analytics posts nothing to Slack; its result arrives in-app.

## 9. Do not

- Do not post anywhere but the thread the question came from, and do not
  take the target from agent text.
- Do not report the reply as posted without the adapter's confirmed post.
- Do not replace the in-app notification with the Slack reply.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
