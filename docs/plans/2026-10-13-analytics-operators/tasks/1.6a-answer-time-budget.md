# 1.6a Time budget for questions: a hard cap that ends in a labeled partial answer (framework)

Lane A (Reliability). Size M. Not gated. Touches `packages/core` and
`packages/toolkit`; needs a changeset.

The plan's PR 1.6 is split in two. This unit adds the mechanism to the
framework: an app can give a user's question a wall-clock budget, and when
the budget is reached the agent stops calling tools, writes what it has as a
partial answer, and the chat labels it partial. 1.6b turns it on for
Analytics, adds plain-word progress, and logs time to answer.

## 1. Goal

When an app sets an answer time budget, no single question runs past it.
Shortly before the budget runs out, the agent is told to stop gathering and
answer from what it already has. Its answer starts by saying it is partial
and what is missing, and the chat shows a "Partial answer" label on that
message, so a partial answer is never presented as complete. If even the
closing answer cannot be written in time, the run ends with a clear "ran out
of time" state instead of hanging or erroring. Apps that set no budget behave
exactly as today.

## 2. What the code does today

Paths are repo-relative.

- **Bounds that exist.** Each run chunk has a soft timeout: 40 s by default
  on hosted foreground runs, 13 min for background runs
  (`packages/core/src/agent/run-manager.ts:96-99`, `:372-395`;
  `packages/core/src/app-config/run-lifecycle-invariants.ts:9`). A chunk that
  hits it ends with `run_timeout` and the turn continues in a new chunk:
  up to 3 automatic continuations for foreground turns
  (`packages/core/src/agent/auto-continue.ts:10`) and up to 20 chained
  background continuations (`run-lifecycle-invariants.ts:23`). A turn is
  refused further chaining after 90 minutes of wall clock
  (`run-lifecycle-invariants.ts:15`, enforced only when chaining at
  `packages/core/src/agent/production-agent.ts:10099-10112`). A run with no
  real progress is stopped after 150 s by default, 3 min for Analytics
  (`run-lifecycle-invariants.ts:11`; `run-manager.ts:112-145`;
  `templates/analytics/server/plugins/agent-chat.ts:52-53`, `:1248-1249`).
  Iterations per chunk are capped by `maxIterations`
  (`production-agent.ts:6388-6396`, default from
  `packages/core/src/agent/loop-settings.ts:140-145`), and a per-turn input
  token budget stops the turn outright (`production-agent.ts:5895-5901`,
  `:6377-6386`).
- **What is missing.** None of these is a per-question budget, and every one
  of them ends a turn either by continuing (so a question can run up to 90
  minutes) or by stopping with an error-like message such as "I stopped after
  N minutes without finishing this request" (`production-agent.ts:10107-10110`),
  which the client maps to `interrupted` (`packages/core/src/client/chat/run-outcome.ts:117`).
  No path asks the model for a closing answer when time runs out.
- **A closeout pattern exists.** When the loop breaker stops a repeating
  tool loop, the loop pushes a user message "Write one concise closing
  message saying what you completed and what remains ... Do not call tools"
  (`production-agent.ts:8689-8700`), runs one more iteration with no tools
  (`:6483-6489`, extra iteration allowed at `:6388`), and ends
  (`:7048-7055`). The new budget reuses this.
- **Turn start is readable.** `readTurnStartedAt` reads the first run's
  start for a turn (`production-agent.ts:9583-9596`). Its one caller turns a
  failed read into 0 elapsed (`:10102`), which silently disables the 90
  minute check when the read fails.
- **Configuration.** Per-app run limits are plugin options
  (`packages/core/src/server/agent-chat/plugin-options.ts:58-59`,
  `runSoftTimeoutMs`, `runNoProgressTimeoutMs`), mirrored in app config
  (`packages/core/src/app-config/agent.ts:87-94`).
- **Hooks for apps.** `onAgentRunComplete(scope, run, { turnContinues })`
  runs once per chunk (`plugin-options.ts:26-35`, called at
  `packages/core/src/server/agent-chat-plugin.ts:3708-3713`); it has no turn
  start time.
- **Chat copy.** The toolkit already shows "Working for {{duration}}" while a
  run is active (`packages/toolkit/src/app/i18n/catalogs/en-US.ts:1399`).
  Toolkit catalogs are `packages/toolkit/src/app/i18n/catalogs/*.ts`
  (`en-US`, `zh-CN`, `zh-TW`, `es-ES`, `fr-FR`, `de-DE`, `ja-JP`, `ko-KR`,
  `pt-BR`, `hi-IN`, `ar-SA`).

## 3. Build

1. **Option and config.** Read `.agents/skills/configuration` first. Add
   `answerTimeBudgetMs?: number` to `AgentChatPluginOptions`
   (`plugin-options.ts`, next to `runSoftTimeoutMs`) and an optional
   `agent.answerTimeBudgetMs` field in `packages/core/src/app-config/agent.ts`
   (`.meta({ env: ["AGENT_ANSWER_TIME_BUDGET_MS"], doc })`; plugin option
   wins). Unset or 0 means no budget. Add an invariant in
   `run-lifecycle-invariants.ts`: when set, it must be below
   `MAX_TURN_WALL_CLOCK_MS` and at least 2 x the closeout reserve.
2. **Turn start in the loop.** At chunk start, read the turn start once with
   `readTurnStartedAt` and pass `turnStartedAtMs` and `answerTimeBudgetMs`
   into `runAgentLoop` (`production-agent.ts:5851`). If the read fails, use
   this run's own start (a known lower bound) and mark
   `turnStartSource: "run"`; never treat it as 0.
3. **Closeout at the budget.** At the top of each iteration
   (`production-agent.ts:6388`), when `now - turnStartedAtMs >=
   answerTimeBudgetMs - CLOSEOUT_RESERVE_MS` (reserve 45 s, D2) and no
   closeout is active: send a new event `{ type: "answer_budget_reached",
   budgetMs, elapsedMs }`, push a closeout user message, and run one more
   iteration with `tools: []`, the same path as `loopBreakerCloseout`
   (`:6483-6489`, `:7048-7055`). Generalize `loopBreakerCloseout` into a
   `closeout: { kind: "loop_breaker" | "answer_budget", ... } | null` rather
   than adding a second flag beside it. Closeout message (agent-facing, not
   catalog copy): "Time is up for this question. Do not call tools. Write the
   answer now from the tool results above. Start with one line that says this
   is a partial answer and what is missing. Then give what you found, with
   its source and time window. End by offering to keep going."
   **Final-response guards during closeout.** The receipt guard and an app's
   `finalResponseGuard` can ask for a retry (`production-agent.ts:7141-7194`),
   and an app guard can expand the tool surface. During an answer-budget
   closeout a retry would ask a model with no tools to go query again. So in
   that closeout, still run both guards but cap their retries at 0 and use
   their `exhaustedDraftPrefix` path (`:7195-7205`); a guard that needs a
   retry to be honest gets its prefix shown above the partial answer instead.
   Add a `closeout: "answer_budget" | "loop_breaker" | null` field to
   `AgentLoopFinalResponseGuardContext` (`:3900-3915`) so app guards can see
   it.
4. **Stop chaining.** In the continuation decision
   (`production-agent.ts:10090-10112`), refuse to chain when the answer
   budget is reached, with terminal reason `answer_time_budget`. When the
   closeout iteration already produced the answer, the turn ends
   `completed` with that reason.
5. **Hard cap.** If the closeout iteration has not finished by
   `turnStartedAtMs + answerTimeBudgetMs`, abort it and end the turn with
   terminal reason `answer_time_budget_exhausted` and no partial text. A
   foreground chunk soft timeout that fires during closeout must not
   auto-continue it (`auto-continue.ts` `isTimeLimitStop`): add the two new
   reasons to the non-continuable set.
6. **Client outcome.** In `packages/core/src/client/chat/run-outcome.ts`, map
   `answer_time_budget` to `succeeded` with a new `partial: true` field on the
   report, and `answer_time_budget_exhausted` to `interrupted`. Add both to
   the code list so the exhaustiveness check covers them. Handle the
   `answer_budget_reached` event in `packages/core/src/client/sse-event-processor.ts`
   (beside `loop_limit`, `:2154`) by marking the current assistant message
   `partial`.
7. **The label.** In the toolkit message rendering
   (`packages/toolkit/src/app/chat/AgentKitAssistantChat.tsx` and
   `conversation/AgentConversation.tsx`), render a small muted label above a
   partial message: `IconHourglass` plus `agentChat.run.partialAnswer`, with
   a shadcn `Tooltip` holding `agentChat.run.partialAnswerTooltip`. Amber
   text token, no red. For `answer_time_budget_exhausted`, show
   `agentChat.run.answerTimeBudgetExhausted` through the existing interrupted
   message path. Read `.agents/skills/frontend-design` first.
8. **Expose turn timing to apps.** Extend the `onAgentRunComplete` outcome
   (`plugin-options.ts:31-35`, call site `agent-chat-plugin.ts:3708-3713`)
   with `turnStartedAtMs: number | null` (null when unreadable, never 0),
   `turnStartSource: "turn" | "run"`, and `answerBudget?: { budgetMs: number;
   reached: boolean }`. 1.6b uses these for time to answer.
9. **Docs and changeset.** Add `.changeset/<name>.md` (minor,
   `@agent-native/core` and `@agent-native/toolkit`). Document the option in
   `packages/core/docs/content` where `runSoftTimeoutMs` is documented (find
   it with `rg runSoftTimeoutMs packages/core/docs/content`), and update the
   matching localized docs under `packages/core/docs/content/locales/*` or
   list the locales that need follow-up in the PR.

Four areas: **actions** (none; this is the agent loop), **UI** (step 7),
**skills and instructions** (the closeout prompt in step 3 and the docs in
step 9; no app skill changes in this unit), **application state** (does not
apply: the partial flag lives on the run and message, which the agent and the
chat already read).

## 5. Tests

- `packages/core/src/agent/production-agent.answer-budget.spec.ts` (new,
  same harness as `production-agent.write-receipts.spec.ts`): with a fake
  clock and a budget, a tool-calling model gets the closeout message once the
  reserve is reached, the closeout iteration has no tools, the turn ends
  `completed` with `answer_time_budget`, and the event is sent once; with no
  budget nothing changes; a closeout that overruns ends

## 8. Defaults for open questions

- **D1.** The budget is wall clock from the turn's first run, across
  continuations, not per chunk. *Reviewer may change.*
- **D2.** Closeout reserve is 45 s: enough for one model call without tools
  on current models. *Reviewer may change.*
- **D3.** A partial answer ends the turn as `succeeded` plus `partial`, not a
  new outcome, so every existing outcome consumer keeps working.
  *Reviewer may change.*
- **D4.** No "Keep going" button. The closeout text offers it and the user
  replies; a button would duplicate the composer. *Reviewer may change.*
- **D5.** The existing `null -> 0` at `production-agent.ts:10102` is left as
  is in this unit and flagged as a follow-up, because changing it changes
  the 90 minute cap for every app. The new code does not repeat it.
  *Reviewer may change.*
- **D6.** Background automations and scheduled jobs are exempt: the budget
  applies only to interactive chat turns. *Reviewer may change.*

## 9. Do not

- No behavior changes outside this unit: apps without a budget must see no
  difference in timeouts, continuations, outcomes or copy.
- Schema: none expected; if the run record needs the new terminal reasons
  stored, they fit the existing text column; additive only otherwise.
- No new `/api` routes.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials; the new env alias goes
  through app config.
- No `catch` or default that turns a failure into a normal-looking value: an
  unreadable turn start is reported as such, an overrun closeout is
  `answer_time_budget_exhausted`, never an empty successful answer.
- No large payloads in SQL or in run events: the event carries two numbers.
- Do not raise or lower any existing timeout constant.
