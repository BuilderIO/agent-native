# 4.3 Funnel step to replays

Lane D (Growth). Size M. Gated: build only after the 4.1a prototype is signed
off (the step menu and the Sessions funnel chip are new UI).

## 1. Goal

On a funnel panel, a growth lead clicks the step where people fall off and
picks "Watch replays of people who dropped off here". Sessions opens filtered
to exactly those people (the same people the funnel counted, not an
approximation), with a removable chip that names the step and says how many
of them have a replay. The agent can do the same thing from "show me replays
of people who dropped off at signup".

## 2. What the code does today

- Sessions can filter by events a session tracked: `didEvents` and
  `didNotEvents` on `list-session-recordings`
  (`actions/list-session-recordings.ts:126-139`). They are per session, they
  ignore order, and they require the Sessions triage Lab (`:177-189`,
  `server/lib/sessions-triage-lab.ts:50-60`). The index behind them only
  covers sessions after its coverage start and drops "didn't" matches for
  sessions with gaps (`server/lib/session-event-index.ts:466-620`).
- A per-person funnel (4.1b counts by `user_key` by default) cannot be
  reproduced with those filters: "did signup viewed, did not do signed up" in
  one session is not "reached step 1 and did not reach step 2 within 7 days".
- Recordings carry `session_id`, `user_id` and `anonymous_id`
  (`server/db/schema.ts:775-790`), plus session associations
  (`:829-847`). An event's `user_key` is its user id, or its anonymous id
  when there is no user id (`server/lib/first-party-analytics.ts:830-841`).
- The list function applies filters in `listSessionRecordingsPage`
  (`server/lib/session-replay.ts:2557`, event conditions at `:2666-2670`) with
  access scoping through `accessFilter` (`:2575`). Filter types:
  `SessionReplayListFilters` (`:126-162`).
- The Sessions page builds its list call from URL params
  (`app/pages/sessions/SessionsTriagePage.tsx:243-304`, call at `:424-458`)
  and keeps event conditions in repeatable `event` / `noEvent` params
  (`shared/session-events.ts:7-9`, helpers at
  `SessionsTriagePage.tsx:199-213`). `view-screen` mirrors Sessions params for
  the agent (`actions/view-screen.ts:54-74`, `:256-420`).
- The funnel renderer draws plain rows with no interaction
  (`app/components/dashboard/SqlChart.tsx:2526-2579`). Dashboard filter values
  use the `f_` URL prefix (`app/pages/adhoc/sql-dashboard/filter-vars.ts:3`).

## Plan corrections

- "Sessions filters in `list-session-recordings`" are not enough: they are
  session-level, unordered and Lab-gated, so they would show a different set
  of people than the funnel counted. This unit adds a funnel filter that asks
  the funnel itself who dropped off.

## 3. Build

1. Prototype gate: confirm the 4.1a step menu and Sessions chip screens are
   signed off.
2. Compiler (`shared/growth-panels.ts`): add
   `compileFunnelStepPeopleSql(definition, stepIndex, outcome, limit)`.
   `outcome: "dropped"` returns the people (or sessions) who reached step
   `stepIndex - 1` and not step `stepIndex`; `outcome: "reached"` returns those
   who reached `stepIndex`. Columns: `key` and `reached_at`, newest first,
   `LIMIT limit + 1` so truncation is detectable. Same CTEs and bounds as the
   count query so the two can never disagree. `dropped` is invalid for step 1.
3. Server (`server/lib/growth-funnel-drilldown.ts`, new):
   `resolveFunnelStepPeople(scope, { dashboardId, panelId, stepIndex, outcome,
   filterValues })`. Load the dashboard with `getDashboard` (access-checked,
   `server/lib/dashboards-store.ts:819`); fail with a typed
   `funnel_panel_unavailable` error if it is missing, not shared with the
   viewer, or the panel has no funnel `config.growth`. Interpolate with the
   dashboard's filter defaults overlaid by `filterValues`, run with
   `queryFirstPartyAnalytics` for the viewer's scope, cap at 1,000 keys and
   report `truncated`. Return `{ keys, countBy, stepLabel, truncated }`. Keys
   never leave the server.
4. Filter (`server/lib/session-replay.ts`): add `funnel?: { dashboardId,
   panelId, stepIndex, outcome, filterValues? }` to
   `SessionReplayListFilters` (`:126-162`). In `listSessionRecordingsPage`,
   resolve the people, then add the condition: for `countBy: "user"`,
   `user_id IN keys OR anonymous_id IN keys`; for `"session"`, the recording's
   `session_id` or an associated session is in the keys. Default the
   `from`/`to` bounds to the funnel's resolved range when the caller gave
   none. Add to the page result: `funnel: { stepLabel, outcome, people,
   withReplay, truncated }`, where `withReplay` is the number of distinct keys
   that matched at least one visible recording. A funnel filter always returns
   the paginated shape.
5. Action (`actions/list-session-recordings.ts`): add the `funnel` object to
   the schema with a description: it lists replays of the exact people a
   funnel step counted; `people` and `withReplay` say how many had a replay;
   it does not need the Sessions triage Lab. Do not add a Lab check.
6. Funnel panel UI (`SqlChart.tsx` `FunnelRenderer`, `:2526-2579`): for a
   panel with a funnel `config.growth`, each step row is a button that opens a
   `DropdownMenu` (text-only items). Step 1 offers only the reached item;
   later steps offer both. Items are `DropdownMenuItem asChild` wrapping a
   router `Link` to `/sessions?funnelDashboard=...&funnelPanel=...&funnelStep=N&funnelOutcome=dropped|reached`
   plus the dashboard's current `f_<filterId>` values, so Cmd or Ctrl click
   and middle click open a new tab (read the `native-navigation` skill). Use
   the session-worded items when `countBy` is `session`. The button has an
   `aria-label` (`funnelStepActions`) and visible focus. SQL-only funnels get
   no menu.
7. Sessions UI (`app/pages/sessions/SessionsTriagePage.tsx`):
   - Read the four `funnel*` params and the `f_*` values; pass `funnel` in the
     list call (`:424-458`). Add the param names to `view-screen`'s
     `SESSION_FILTER_KEYS` (`actions/view-screen.ts:54-74`) and pass the
     filter through its Sessions branch (`:256-420`).
   - Show a chip in the filter row: `Badge` with the step text
     (`funnelFilterDropped` or `funnelFilterReached`) and an icon button with
     `IconX` (`funnelFilterClear`) that removes the four params. A `Tooltip` on
     the chip shows `funnelCoverage`.
   - When the result has people but no recordings, show `funnelEmpty` in the
     list's empty state, not the generic one. When `truncated`, show
     `funnelTruncated` as a muted line above the list. When the server returns
     `funnel_panel_unavailable`, show `funnelUnavailable` with the chip still
     clearable.
   - The page's own range control shows the range the funnel resolved, so the
     user sees why a replay is or is not included.
8. Application state: when a funnel step menu opens, add `funnelStep: {
   index, label }` to the `dashboard-panel` selection in
   `app/hooks/use-dashboard-chat-context.ts:163-176`, so "these people" in
   chat means that step. Sessions keeps its state in the URL, which
   `view-screen` reports after step 7.
9. Skills and instructions:
   - `AGENTS.md`, "Sessions and state": one line for the `funnel` filter.
   - `.agents/skills/session-replay/SKILL.md`: when to use the funnel filter
     instead of `didEvents` / `didNotEvents`, and the coverage numbers.
   - `.agents/skills/dashboard-management/SKILL.md` growth section: step
     drill-down to replays.
10. Changelog: `agent-native changelog add "Open replays of the people who dropped off at any funnel step" --type added`.

## 8. Defaults for open questions

- [Default, reviewer can change] Clicking step N offers "dropped off here"
  (reached N-1, not N) and "reached this step". This matches the drop-off
  percent the renderer shows on row N.
- [Default] Cap at the 1,000 most recent people; the page says when it
  truncates.
- [Default] Not Lab-gated.
- [Default] Only funnels built from steps (`config.growth`) get the menu;
  hand-written SQL funnels do not.
- [Default] Replays are limited to the funnel's range, not to the time after
  each person's step.

## 9. Do not

- Do not change `didEvents` / `didNotEvents` behavior or their Lab gate.
- Never send user keys or anonymous ids to the client.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
