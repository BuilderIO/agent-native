# 1.5b Plain-language empty, partial and render-error panel states

Lane A (Reliability). Size M. Not gated (builds directly).

Second half of the plan's PR 1.5. It reuses `PanelStateMessage`,
`shared/panel-state.ts` and the fix actions from 1.5a.

## 1. Goal

When a panel loads but has nothing useful to show, the viewer learns why and
what to do, in one sentence and one button: "No rows match these filters"
with Reset filters when their own filter choices emptied it; "This query
returned no rows" when it is empty with the dashboard's defaults; "The query
returned rows, but this chart has nothing to draw" when the config does not
fit the result; "This chart uses columns the query no longer returns" in
place of today's developer banner; and "This chart couldn't be drawn" instead
of a blank page when a renderer crashes. The agent's skill describes the
same states in the same words.

## 2. What the code does today

All paths relative to `templates/analytics/`.

- Empty: when `planPanelRender` reports `empty`, `SqlChart` shows the generic
  `common.noData` ("No data") with no action
  (`app/components/dashboard/SqlChart.tsx:1356-1369`). A result with rows that
  draw nothing (a funnel or heatmap whose keys do not fit) shows the same
  "No data", plus the missing-columns banner when one applies (`:1366-1368`).
  `plan.renderedRowCount` and `plan.rows` already tell the two apart
  (`shared/panel-render-contract.ts:679-681`, `:743`).
- Filters: the panel does not know whether the viewer changed any filter.
  `SqlChartCard` gets the effective variables (`filters` prop,
  `app/pages/adhoc/sql-dashboard/SqlChartCard.tsx:83`, set from `effectiveVars`
  in `app/pages/adhoc/sql-dashboard/index.tsx:314`) and a per-chart time range
  override (`index.tsx:301-313`, `:410`), but not whether they differ from the
  defaults. The filter bar computes that with a private `hasActiveFilters`
  (`app/pages/adhoc/sql-dashboard/DashboardFilterBar.tsx:55-75`, used at
  `:214`) and clears filters with a private `clearAllFilters` (`:165-176`).
- Missing columns: `ConfigWarning` renders the hardcoded English banner
  "Ignored missing result columns: a, b" in amber
  (`SqlChart.tsx:1133-1141`), with no action.
- Render crash: `planPanelRender` runs inside `useMemo` with no guard
  (`SqlChart.tsx:1216-1219`), and the only error boundary is the app root's
  (`app/root.tsx:187`). A renderer exception takes down the whole page, not
  one panel. Agent verification already treats this as `render-error`
  (`server/lib/dashboard-panel-verification.ts:612-621`).
- The agent's view of these states is the "Reading Panel State" section of
  `.agents/skills/dashboard-management/SKILL.md:510-527`, which quotes the UI
  text "No data" and "Ignored missing result columns". The test
  `server/plugins/agent-chat.spec.ts:630` asserts the skill contains
  "Ignored missing result columns".

**Plan corrections:** the plan's example "No rows match these filters" is
only true when the viewer's own filters caused it; the same empty result
with the dashboard's defaults needs different copy, and the panel needs to
know which case it is in. The verification statuses this unit covers
(`empty`, `missing-columns`, `render-error`) are mapped in 1.5a's
`PANEL_STATE_FOR_VERIFICATION`.

## 3. Build

1. **Filter helpers.** Move `hasActiveFilters` and the body of
   `clearAllFilters` from `DashboardFilterBar.tsx` into
   `app/pages/adhoc/sql-dashboard/filter-vars.ts` as exported pure functions
   (`activeFilterIds(filters, searchParams)` returning the ids that differ
   from defaults, and `clearDashboardFilterParams(params)`), and have the
   filter bar use them. Add `panelUsesFilters(sql, ids)`: true when the panel
   SQL contains a `{{id}}`, `{{id:list}}`, `{{idStart}}` or `{{idEnd}}` token
   for any id. Reuse the token pattern the verification code uses rather
   than writing a new one.
2. **Pass the filter state down.** In `PanelCell` (`index.tsx:267`), compute
   `filtersNarrowed = panelUsesFilters(panel.sql, activeIds) ||
   validTimeRangeOverride !== null` and pass it with an `onResetFilters`
   callback (clears filter params and the per-chart override) through
   `SqlChartCard` to `SqlChart`.
3. **Empty states** in `SqlChart.tsx` (replacing `:1356-1369`), all through
   `PanelStateMessage`:
   - `plan.rows.length === 0` and `filtersNarrowed`: "No rows match these
     filters", fix Reset filters.
   - `plan.rows.length === 0` otherwise: "This query returned no rows", fix
     Ask the agent why (secondary; the agent gets panel id, resolved filters
     and the fact that the query returned zero rows).
   - `plan.rows.length > 0` and `plan.empty`: "The query returned rows, but
     this chart has nothing to draw", fix Ask the agent to fix it.
   Keep the empty block's height classes so the card does not jump.
4. **Missing columns.** Replace `ConfigWarning` with the compact
   `PanelStateMessage` variant: "This chart uses columns the query no longer
   returns: {{columns}}" (columns joined with `useFormatters()` list
   formatting), fix Ask the agent to fix it, amber triangle as today. Viewers
   who cannot edit get Ask the agent.
5. **Render errors.**
   - Wrap the `planPanelRender` call in `SqlChart` so an exception becomes a
     `render-error` state carrying the message (shown under Details), not a
     thrown error.
   - Add `app/components/dashboard/PanelErrorBoundary.tsx`, a small class
     error boundary around `SqlChart` in `SqlChartCard` (card body and the
     full-screen dialog), that renders the same `render-error` state with
     Try again (remounts the chart) and Ask the agent to fix it. Reset it
     when the panel config changes.
   - "This chart couldn't be drawn" is the message.
6. **Application state.** Use the `state` field 1.5a adds to the panel chat
   context and `selected-object.panelStateCode` for these states too, with
   codes `no_rows`, `no_rows_for_filters`, `nothing_to_draw`,
   `missing_columns` and `render_error`. 1.5a names its union
   `PanelFailureCode` (load failures only). Add an exported
   `PanelStateCode = PanelFailureCode | <these five>` in
   `shared/panel-state.ts`, type the chat context `state.code` and
   `selected-object.panelStateCode` with it, and keep `PanelFailureCode`
   for the classifier.
7. **Skills and instructions.**
   - `.agents/skills/dashboard-management/SKILL.md`, "Reading Panel State":
     replace the quoted "No data" and "Ignored missing result columns" with
     the new messages, one line each on what causes it and what its button
     does. Keep the guidance on `config.pivot`, `yKeys` and filters. Read
     `.agents/skills/writing-agent-instructions` first.
   - Update the assertion in `server/plugins/agent-chat.spec.ts:630` to the
     new missing-columns phrase in the same change. It is an existing
     skill-content test; do not add another.
8. **Changelog.** `agent-native changelog add "Empty and broken panels now say why, with a fix like Reset filters" --type improved`
   from `templates/analytics`.

Four-area check: UI (steps 2 to 5), actions (none: these states come from
results the page already has), skills (step 7), application state (step 6).

## 8. Defaults for open questions

Reviewer-changeable decisions:

- **D1. "These filters" only when the panel's SQL uses a changed filter** or
  the per-chart time range override is set. A panel untouched by the changed
  filter gets the default-filters copy.
- **D2. Reset filters resets the whole dashboard's filters**, the same as the
  filter bar's Clear all, plus the per-chart override.
- **D3. Missing columns keeps the chart visible** under the message, as the
  banner does today.
- **D4. Ask the agent why is secondary** for a plain empty result, because an
  empty result is often correct.
- **D5. Email reports keep "No rows returned."**
  (`server/lib/dashboard-report-render.ts:597-599`); email copy is a separate
  change.

## 9. Do not

- No behavior changes outside this unit: do not change what counts as empty
  (`planPanelRender` stays as is), and do not change filter behavior beyond
  moving the two helpers.
- Schema changes are additive only; this unit adds no table or column.
- No new `/api` routes for app data; use actions.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value:
  the render guard and the boundary show `render-error` with the message
  under Details; they never fall back to an empty chart or "No data".
- No large payloads in SQL.
- No em dashes in copy; no red for these states.
