# 8.2a Insight to action: the handoff contract, next actions and draft cards

Lane E (Holy-shit features). Size M. Gated: the next-action buttons on an
investigation notebook, a notebook and an answer, and the draft card, are new
UI; build only after the "Investigation: notebook" (its Next steps
section), "Investigation: draft emails", "Investigation: file an issue" and
"Investigation: make a deck" screens in `prototypes/analytics-operators/` are signed off. Where
the signed-off prototype differs from this brief, the prototype wins. The
next-step chips under chat answers also need an "Ask: next steps under an
answer" screen, not drawn yet, drawn and signed off before they build.

Depends on: 3.4a, 1.3b, 3.3a (built); 7.1a and 7.1b (the notebook
placement); 8.1a (the investigation source; the answer and notebook
placements can land first). Merge after 7.1b. Blocks: 8.2b, 8.2c, 8.2d, 8.3c.

Paths are relative to `templates/analytics/` unless they start with
`packages/` or `templates/`.

## 1. Goal

An investigation (8.1), a notebook or an answer ends with what to do about
it. Under the evidence, the user sees next-action buttons such as "Make a
deck…". Under a chat answer, the same next actions show as contextual chips,
so the chat guides the user to the next step. Clicking one hands the job to
the agent, which packs a small,
bounded artifact (what was found, the ids it was found on, a link back) and
sends it to the sibling app that owns the job over A2A. The sibling makes a
**draft** there (a deck in Slides in this unit; email drafts in 8.2b; a
Design app in 8.3c). Jira issues (8.2b) and CRM field updates (8.2c) go
through Analytics' own workspace connections instead, as drafts the user
confirms. The result comes
back as a draft card in the chat and on the notebook, with "Open draft". A
draft never leaves its app without a person: anything that would write
outside a draft goes through a confirm dialog that shows the exact change.
Nothing is reported as done unless the receiving app proved it.

This unit lands the contract (the typed next-actions list, the draft-result
record, the A2A handoff, the confirm gate) and proves it end to end with one
kind, a plain deck in Slides. 8.2b to 8.2d and 8.3c add kinds.

## 2. What the code does today

- Analytics already calls siblings over A2A, but only from the agent loop
  (`call-agent` is the second of `INITIAL_TOOL_NAMES`,
  `server/lib/agent-chat-plan-mode.ts:1-24`) and from one grandfathered
  upload route that hands replay screenshots to Design with
  `invokeAgentAction` and a hand-resolved target
  (`server/routes/api/session-replay/storyboard.post.ts:652-697`, `:934-945`;
  `server/lib/replay-storyboard-design-target.ts:126-186`). There is no
  record of what a handoff produced.
- The `call-agent` rule: natural-language messages by default; a direct
  `action` + `input` call "is never for a create, update, delete, send,
  save, publish, or other side effect"
  (`packages/core/src/server/agent-chat/context-tools.ts:147`).
- `invokeAgent` returns only `{ target, prompt, responseText }` for an
  ordinary peer (`packages/core/src/a2a/invoke.ts:90-96`, `:349-379`). The
  `callAgent` underneath throws `A2ATaskTerminalError` carrying the task for
  `failed`, `canceled` and `input-required` (`packages/core/src/a2a/client.ts:1990-2003`),
  and `A2ATaskTimeoutError` carries `taskId` and `lastTask` (`:52-60`,
  `:150-160`). Neither error class is exported from the package index
  (`packages/core/src/a2a/index.ts:24-37`); `call-agent` recognizes them by
  name. `A2AClient.getTask` reads a task later (`client.ts:683`).
- When a delegated run reaches a `needsApproval` action, the receiver stores
  an A2A approval and ends the task `input-required` with a data part
  `{ kind: "agent-native/approval-required", approvalId, tool, approvalUrl }`
  (`packages/core/src/server/agent-chat-plugin.ts:2905-2950`). Nothing on
  the caller side reads that part today.
- Receivers sign a persisted-artifact ledger into their A2A answer
  (`includePersistedArtifactMarker`, `agent-chat-plugin.ts:2825`). Callers
  can read verified identities `{ resourceType, id, sourceAction, url }`
  (`packages/core/src/a2a/artifact-response.ts:50-64`) with
  `extractA2AArtifactIdentities`, which reads the signed marker from a
  `call-agent` result summary (`:1146-1166`), but the package index exports
  only `extractA2APersistedMutationReceipts` and
  `stripA2APersistedArtifactMarkers`
  (`packages/core/src/a2a/index.ts:131-135`). Decks and designs are already
  ledger kinds (`packages/core/src/artifacts/detect.ts:1-30`; `create-deck`
  maps to `deck` at `:72`). The ledger is signed with `A2A_SECRET`; with no
  secret, no identity verifies (`artifact-response.ts:130-135`).
- Chat cards: an action declares `chatUI` and the app registers a renderer,
  as 1.3b does (`shared/dashboard-edit-outcome.ts:224-230`,
  `actions/mutate-dashboard.ts:476`,
  `app/lib/register-dashboard-edit-renderer.tsx:15-30`). Answers get extra
  UI under the final assistant message through
  `registerAssistantMessageSupplement` (`app/lib/register-answer-evidence.tsx:5-8`),
  whose props carry `message`, `threadId` and the run's tool calls
  (`packages/toolkit/src/app/chat/chat/message-supplement-registry.tsx:12-17`).
- The chat already draws suggestion chips with the toolkit's
  `AgentSuggestionBar` (`packages/toolkit/src/composer/AgentSuggestionBar.tsx:142`),
  which `AgentKitSuggestedPrompts` wraps for the "context-chips" placement
  (`packages/toolkit/src/app/chat/AgentKitAssistantChat.tsx:6142-6176`;
  placement type at `packages/toolkit/src/app/chat/chat/surface-types.ts:215-220`).
- UI hands work to the agent with `sendToAgentChat`
  (`app/pages/adhoc/sql-dashboard/SqlChartCard.tsx:339-358`).
- The account map holds ids, labels, emails and domains per account, never
  raw provider records (`server/db/schema.ts:975-1030`; `getAccount` in
  `server/lib/account-map-store.ts:428`).
- Shareable resources register in `server/db/index.ts:67`, after the
  identity-column policy list (`:35-65`). Migrations run by version with a
  unique name (`server/plugins/db.ts:1863-1879`); Phase 8 reserves 176 to
  189, and 8.1a takes 177 (`analytics_investigations`, with `notebook_id`
  pointing at the investigation's notebook; brief 8.1a step 2).
- Slides creates a deck with the caller's or workspace default design system
  (`templates/slides/actions/create-deck.ts:28-31`), and already tells its
  agent to ask Analytics for data rather than query sources itself
  (`templates/slides/.agents/skills/analytics-data-for-decks/SKILL.md:18-31`).

## Plan corrections

- "The A2A call" is message delegation, not `invokeAgentAction`: every
  handoff asks the receiver to create something, and direct invocation is
  read-only by rule. The bounded artifact rides in the message.
- The receiving agent's prose is not proof. A handoff counts as a draft only
  when the receiver's signed ledger names the artifact, or the receiver asks
  for approval. Anything else is a typed failure that shows the receiver's
  words, never a draft card.

   `confirmed_at TEXT`, `confirmed_by TEXT`, `created_at`, `updated_at`; an
   index on `(owner_email, source_kind, source_id, created_at)`. Pair it with
   `createSharesTable("analytics_insight_action_shares")`. Migration 180
   `analytics-insight-actions-table`, 181
   `analytics-insight-action-shares-table`. Register it in
   `server/db/index.ts` with `registerShareableResource` (type
   `insight-action`, private by default) and add `owner_email` (rekey,
   transfer) and `confirmed_by` (retain, retain) to the identity list. Run
   `pnpm guard:additive-migrations`.
2. **Shared types** (`shared/insight-actions.ts`, new):
   - `INSIGHT_ACTION_KINDS` (append-only; this unit ships `deck`).
   - `InsightSource`: `{ kind: "answer"; threadId; messageId }`,
     `{ kind: "notebook"; dashboardId }`, `{ kind: "investigation";
     investigationId; notebookId }`. An investigation is 8.1a's
     `analytics_investigations` row and its evidence notebook
     (`notebook_id`); the contract needs only those two ids.
   - `NextAction`: `{ kind; available: true }` or `{ kind; available: false;
     reason: "app_unavailable" | "not_connected" | "nothing_to_act_on" }`.
   - `InsightActionStatus`: `preparing`, `waiting` (the receiver accepted
     the task and is still working), `draft`, `needs_approval`, `confirming`,
     `confirmed`, `discarded`, `failed`. `confirmed` means a person
     confirmed a write outside a draft (8.2b's Jira issue, 8.2c's CRM
     updates). Drafts that live in the sibling (decks, emails, designs)
     stay `draft`:
     Analytics cannot see the sibling's own review, and never claims it.
   - `InsightArtifact` (the composable-mini-apps handoff shape):
     `{ artifactType: "analytics-insight", artifactId, createdAt, source,
     title, summary, items, links }`. Caps: `summary` 1,500 characters,
     `items` 25 entries of at most 200 characters per field, the whole
     artifact 8 KB serialized. Over the cap is a typed `artifact_too_large`
     error that tells the agent what to trim, never a silent cut.
   - `DraftRef`: `{ app, resourceType, id, label, url }`.
3. **Library** (`server/lib/insight-actions.ts`, new):
   - `resolveInsightSource(source, ctx)`: notebooks and investigations load
     with `getDashboard(id, ctx)` (access-checked); no access and deleted
     both return `source_not_found`. Answers check the thread is the
     caller's or shared to them.
   - `buildInsightArtifact(...)`: validates agent-supplied item ids against
     the source (panel ids exist on the notebook; account ids exist in the
     account map through `getAccount`). It reads emails and domains from the
     account map, never from agent text. Links are built with
     `buildDeepLink`.
   - `resolveInsightTarget(app)`: `resolveAgentInvocationTarget(app,
     { selfAppId: "analytics" })` with typed failures, as
     `replay-storyboard-design-target.ts:126-186` does for Design.
   - `runInsightHandoff(action, objective)`: `invokeAgent` with the
     objective and the artifact as a fenced JSON block, `async: true`, a
     90 second timeout, `idempotencyKey: action.id` and caller auth from
     `resolveA2ACallerAuth`. Read the outcome in this order: on success,
     verified identities (`extractA2AArtifactIdentities([{ tool:
     "call-agent", result: responseText }])`) become `DraftRef`s and
     `draft`; an `A2ATaskTerminalError` in `input-required` with an approval
     part (step 4) becomes `needs_approval` with its URL; an
     `A2ATaskTimeoutError` becomes `waiting` with its `taskId`; everything
     else is `failed` with `receiver_failed` (the task's `errorCode` kept),
     `unverified_result` (the receiver answered but its ledger names
     nothing) or `target_unavailable`, keeping at most 500 characters of the
     receiver's text for the card.
   - Status transitions in one place with a conditional update (`WHERE
     status = <expected>`), so a double click cannot hand off twice.
4. **Core (`packages/core`, minor changeset).** From
   `packages/core/src/a2a/index.ts`, export `A2ATaskTerminalError`,
   `A2ATaskTimeoutError`, `extractA2AArtifactIdentities` and its types, and
   a new pure `readA2AApprovalRequest(task)` that returns `{ id, tool, url }`
   from the task's `agent-native/approval-required` data part, or null.
   No behavior change for existing callers.
5. **Actions** (all `defineAction`; writes are audited with
   `recordInputs: false`):
   - `list-next-actions` (`http: { method: "GET" }`, read-only): input
     `{ source }`; returns `NextAction[]` in a fixed order. `deck` is
     available when the source resolves and Slides resolves; otherwise
     `app_unavailable` or `nothing_to_act_on`.
   - `prepare-insight-action`: input `{ source, kind, title, summary,
     items? }`; creates the record in `preparing` with the built artifact;
     returns `{ actionId, artifact, targetApp }`.
   - `handoff-insight-action`: input `{ actionId, objective }` (at most
     2,000 characters: what the receiver should make, in plain words, and
     that it must make a draft and not send or publish); runs
     `runInsightHandoff`; declares `chatUI` with renderer
     `analytics.insight-action`; returns the card.
   - `refresh-insight-action`: input `{ actionId }`; for `waiting`, reads the
     remote task with `A2AClient.getTask` and applies step 3's outcome rules
     to its final message; for any other status, returns the card
     unchanged.
   - `discard-insight-action`: input `{ actionId }`; `preparing`, `waiting`,
     `draft`, `needs_approval` or `failed` to `discarded`. It never deletes
     the sibling's draft; the card says the draft stays in that app.
   - `list-insight-actions` (`GET`): input `{ source }`; the newest 20
     records for that source, projected for the card.
   Describe `prepare` and `handoff` so the agent always runs them as a pair
   after a next-action click, and so it treats `failed` and
   `unverified_result` as failures to report.
6. **UI (gated).**

## 8. Defaults for open questions

- [Default] Discard never deletes the sibling's draft.
- [Default] A handoff waits 90 seconds, then becomes `waiting` with Check
  again; there is no background poller.
- [Decided by the owner, 2026-10-14] Next steps also show as contextual
  chips under chat answers, to guide the user. They build only after their
  prototype screen is drawn and signed off.
- [Default] Chips show only on the latest answer, and only when its run
  queried data.
- [Default] Records are private to whoever made them, like dashboards
  before sharing.

## 9. Do not

- Do not call a sibling's write actions with `invokeAgentAction`.
- Do not turn receiver prose into a draft card, and do not build sibling
  URLs from agent text.
- Do not paste rows, panel SQL or provider payloads into the artifact.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
