# 1.5a Plain-language panel errors with fix buttons

Lane A (Reliability). Size M. Not gated (builds directly).

The plan's PR 1.5 is split in two. This unit (1.5a) covers panels that fail
to load: missing credentials, data program failures, timeouts, unsupported
SQL and query errors, plus the data source connection labels. 1.5b covers
panels that load but have nothing to show: no rows, rows that do not plot,
missing columns and render crashes. Both share the state component and
classifier this unit creates.

## 1. Goal

When a dashboard panel cannot load, the viewer reads one plain sentence that
says what is wrong in their terms, and one button that fixes it or takes the
next step: "Connect BigQuery", "Run this data program", "Try again", "Ask the
agent to fix it". No `Action query-dashboard-panel failed:` prefixes, no
`background_pending:` codes, no bare request ids in the message. The raw
error and its reference id stay one click away under Details, for people who
need them. Every string is localized.

## 2. What the code does today

All paths relative to `templates/analytics/`.

**How a panel failure reaches the screen**

- The page loads each panel through `useSqlQuery` → `executeSqlQuery`
  (`app/lib/sql-query.ts:138-187`) → the `query-dashboard-panel` action
  (`actions/query-dashboard-panel.ts:11-40`) → `runDashboardPanelQuery`
  (`server/lib/dashboard-panel-query.ts:404-516`).
- Typed failures are flattened to a string on the client. When the action
  returns `{ error, message }` (a missing credential or an unsupported
  backend), `executeSqlQuery` throws `new Error(message || error)`
  (`app/lib/sql-query.ts:171-177`): the code, the source label, the
  credential key and `settingsPath` are dropped. When the action throws, the
  core client throws `Error("Action query-dashboard-panel failed: <message>")`
  and attaches `errorCode`, `details`, `status`, `requestId` and
  `actionMessage` as properties (`packages/core/src/client/use-action.ts:483-537`);
  the panel reads only `.message`.
- The client deadline aborts with no reason (`app/lib/sql-query.ts:63-84`,
  abort at `:69`), so a slow panel and a user navigating away both surface as
  an `AbortError`, which `formatSqlChartError` reports as "interrupted", not
  as slow.
- `formatSqlChartError` (`app/components/dashboard/SqlChart.tsx:160-182`)
  maps three regexes to hardcoded English sentences (not in the i18n
  catalog) and otherwise prints the raw message.
- The error view (`SqlChart.tsx:1293-1316`) is red `text-destructive` text
  plus one Refresh button, whatever the cause. A failed refresh over existing
  rows shows a red banner with the raw message (`:1318-1345`).

**Failure sources and their current text**

| Source | Where | What the viewer sees today |
| --- | --- | --- |
| Missing credential (BigQuery, Google Analytics, Amplitude, Prometheus) | `dashboard-panel-query.ts:122-134`, checks at `:416-459` and `:501-508`; returned as `{ error: "missing_api_key", key, label, message, settingsPath: "/data-sources" }` | Red "Connect your BigQuery account to see this data" with a Refresh button, which cannot fix it |
| Unsupported backend (first-party SQL with no BigQuery translation) | `dashboard-panel-query.ts:461-492` | Red developer sentence naming the SQL construct |
| Data program failure (no last good run) | `runProgramPanel`, `dashboard-panel-query.ts:355-401`; codes from `packages/core/src/data-programs/execute.ts:42-52`: `program_not_found`, `access_denied`, `archived`, `timeout`, `emit_missing`, `emit_shape_invalid`, `sandbox_error`, `run_code_unavailable`, `background_pending`, `result_too_large` | Red `Action query-dashboard-panel failed: background_pending: This data program is still computing` followed by an em dash and `check back shortly` (raw code in the sentence) |
| Provider query error (BigQuery, GA4, Amplitude, Prometheus, first-party) | thrown from the source runners | Red raw provider message behind the action prefix |
| Server error | any 5xx | "This chart could not be loaded. Try again." |
| Client deadline | `sql-query.ts:69` | "This chart load was interrupted. Try again." |

**Verification statuses (agent side)**

`PanelVerificationStatus` (`server/lib/dashboard-panel-verification.ts:40-46`)
and `PanelUnverifiedNote` (`:48-53`) are computed only for agent writes and
the `inspect-dashboard-panel` action. No UI code reads them (searched `app/`
and `shared/`). They name the same failure classes the viewer can hit, so
this unit maps them to the same viewer states (section 3, step 2). The note
text for `missing_credential` already claims "the viewer sees a connect
prompt" (`:136-137`); today that is not true.

**Credential states on the Data sources page**

`SharedConnectionStatusKind` (`app/lib/data-source-status.ts:59-65`):
`ready`, `needs_grant`, `needs_credentials`, `local_credentials`,
`needs_reauth`, `error`. Their labels are a hardcoded English map
(`:178-185`), rendered by `SharedConnectionBadge` as a fallback for four of
the six kinds (`app/pages/DataSources.tsx:610-635`). The page already shows
the fix control for each kind (connect, grant, reconnect, add local key) in
`DataSources.tsx:1257-1365`.

**Plan corrections**

- The plan says to map every `PanelVerificationStatus` to user copy. The UI
  never receives those statuses; it receives `query-dashboard-panel` results
  and errors. The real fix is to stop the client from flattening typed
  failures, then classify them once. The verification statuses map onto the
  same classes and are listed below so the vocabulary matches.
- "Reconnect HubSpot" is not reachable from a panel today: HubSpot is not a
  panel source (`DASHBOARD_PANEL_SOURCES`, `server/lib/dashboard-panel-query.ts:21`
  type; sources in `app/pages/adhoc/sql-dashboard/types.ts:1-8`). HubSpot data
  reaches panels only through data programs, whose provider failures arrive
  as free-text `sandbox_error` messages with no provider field. This unit
  shows "Ask the agent to fix it" for those. A typed provider credential
  error from the program sandbox is a follow-up in `packages/core`.

## 3. Build

1. **Typed client error.** In `app/lib/sql-query.ts`, add an exported
   `PanelQueryError extends Error` with `code: PanelFailureCode`, optional
   `sourceLabel`, `credentialKey`, `settingsPath`, `programCode`, `programId`,
   `requestId`, `status` and `detail` (the raw message). `executeSqlQuery`:
   - on `{ error: "missing_api_key" }` throws code `missing_credential` with
     the label, key and settings path;
   - on `{ error: "unsupported_by_backend" }` throws `unsupported_backend`
     with the construct in `detail`;
   - on a thrown action error, reads `errorCode`, `details`, `status`,
     `requestId` and `actionMessage` from the core error and throws
     `program_failed` (when `errorCode` is `data_program_failed`),
     `server_error` (5xx without a code) or `query_failed`;
   - aborts the deadline controller with a `PanelQueryDeadlineError` reason
     and, when that is the reason and the caller's signal is not aborted,
     throws `timeout`; a caller abort stays an `AbortError`.
   Keep `SqlQueryResult.error` (string) for `resultOverride` callers; it
   classifies as `query_failed`.
2. **One classifier.** Create `shared/panel-state.ts`:
   - `PanelFailureCode`: `missing_credential`, `unsupported_backend`,
     `timeout`, `interrupted`, `server_error`, `query_failed`,
     `program_not_found`, `program_access_denied`, `program_archived`,
     `program_pending`, `program_timeout`, `program_failed`,
     `program_too_large`, `program_unavailable`.
   - `classifyPanelFailure(error: unknown)`: returns `{ code, detail,
     requestId?, sourceLabel?, ... }`. It reads `PanelQueryError` fields
     first. The existing timeout and abort regexes from
     `formatSqlChartError` move here as the fallback for untyped errors and
     are the only place they live.
   - `PANEL_STATE_FOR_VERIFICATION`: a typed map from
     `PanelVerificationStatus` plus `PanelUnverifiedNote` to the viewer state,
     exported so a test can prove every status and note is covered:

     | Verification | Viewer state | Unit |
     | --- | --- | --- |
     | `ok` | renders | n/a |
     | `empty` | no rows, or nothing to draw | 1.5b |
     | `missing-columns` | missing columns | 1.5b |
     | `render-error` | render error | 1.5b |
     | `query-error` | `query_failed` (or `unsupported_backend`, `program_*` by error code) | 1.5a |
     | `unverified` + `timeout` | `timeout` | 1.5a |
     | `unverified` + `missing_credential` | `missing_credential` | 1.5a |
     | `unverified` + `skipped:program` | the panel's own program state; the viewer runs it | 1.5a |
     | `unverified` + `too_expensive` | renders (the viewer's load is not capped today; see 1.4) | n/a |
     | `unverified` + `not_executed:over_budget` | renders (agent-only cap) | n/a |
     | `unverified` with no note | `server_error` | 1.5a |

## 8. Defaults for open questions

Reviewer-changeable decisions:

- **D1. Data program provider failures say "This chart's data program
  failed"** with Ask the agent to fix it, not "Reconnect HubSpot", until the
  sandbox returns a typed provider credential error.
- **D2. Connect goes to the Data sources page**, not an inline dialog, and
  does not add a return link to the dashboard (browser back returns).
- **D3. No red.** Failure states use a muted or amber tone with a triangle;
  red stays for destructive actions.
- **D4. Raw detail stays available** under Details, with the reference id,
  so support can still trace a failure.
- **D5. Program HTTP statuses** as listed in step 3.
- **D6. Viewers who cannot edit** get Ask the agent (an explanation) instead
  of Ask the agent to fix it.
- **D7. Explorer dashboards** (`app/pages/adhoc/_shared/KpiChart.tsx`) are out
  of scope; they keep their current states.

## 9. Do not

- No behavior changes outside this unit: do not change what loads, when, or
  how often (that is 1.4), and do not change agent verification verdicts
  (that is 1.3).
- Schema changes are additive only; this unit adds no table or column.
- No new `/api` routes for app data; use actions.
- No raw `fetch` from client code; keep `callAction`.
- No `process.env` reads for provider credentials; the credential check stays
  `resolveCredential`.
- No `catch` or default that turns a failure into a normal-looking value:
  an unknown failure is `query_failed` with its raw detail, never an empty
  chart; a typed code that the client does not recognize is shown as
  `query_failed`, not dropped.
- No large payloads in SQL.
- No em dashes in copy, no bare error ids or codes in the sentence, no
  browser `alert`.
