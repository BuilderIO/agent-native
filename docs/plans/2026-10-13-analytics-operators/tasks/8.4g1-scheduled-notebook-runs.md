## 1. Goal

An author sets a notebook (or any dashboard) to rerun every morning or every
Monday, with fresh data, not cached results. When something changed since the
last run (a new number, new rows), the people on the schedule get an email
and an inbox notification naming the cells that changed, with a link. When
nothing changed, the author can choose to hear nothing. A run where a cell
failed says which and why; it never reports "no change" for a cell it could
not read.

## 2. What the code does today

- Report subscriptions are daily only: `frequency: "daily"`
  (`server/lib/dashboard-report-subscriptions.ts:29`, `:318`, `:444`); the
  column is `text("frequency", { enum: ["daily"] })` in
  `dashboard_report_subscriptions` (`server/db/schema.ts:103-132`, enum at
  `:111-113`); `last_status` is `success | error | running`. Recipients are
  capped at 5 (`MAX_DASHBOARD_REPORT_RECIPIENTS`, `:58`). Scheduling helpers
  are `nextDailyRunAt` (`:255`) and `lastDailyRunAt` (`:270`);
  `saveDashboardReportSubscription` (`:394`), `claimDueDashboardReportSubscriptions`
  (`:503`), `markDashboardReportResult` (`:579`).
- The sweep claims due subscriptions and runs each under the owner's request
  context (`server/jobs/dashboard-report.ts:107-140`); `collectReportSnapshot`
  reads the dashboard with the owner's access (`server/lib/dashboard-report.ts:143`)
  and `fetchReportPanelData` runs every panel with per-panel status
  (`server/lib/dashboard-report-render.ts:128-140`); a run where every panel
  failed throws instead of mailing, and a degraded run is labeled degraded
  (5.1a brief section 2). On Netlify a cron every 15 minutes triggers the sweep
  worker (`scripts/emit-netlify-dashboard-report-cron.ts:29-32`, `:73-96`).
- 5.1a built a separate weekly summary on core automations, with the agent
  writing the text (`server/lib/weekly-summary.ts`, `applyWeeklySummarySettings`
  `:377`, cron at `shared/weekly-summary.ts:76`). It did not add weekly to
  subscriptions.
- Alerts notify through `notifyWithDelivery` from `@agent-native/core/notifications`
  (`server/lib/analytics-alerts.ts:3`, call at `:1212`), with inbox always
  added (`ensureInboxNotificationChannel`, `:1272`).
- 7.1b's notebook actions menu has no Email reports item, by the owner's
  2026-10-14 decision ("add them only when someone asks").
- Highest migration on the integration branch is 173; 174 and 175 are
  reserved; 176 to 189 belong to 8.1 to 8.3; 190 is 8.4d and 191 is 8.4f2.

## Plan corrections

- "Reuse report subscriptions/recurring jobs": subscriptions already have
  the claim, owner context, deadline and honesty contract a scheduled run
  needs, so this unit extends them rather than adding a second scheduler. No
  agent is involved in a scheduled run: it is a data refresh plus a diff.
- This puts a schedule item in the notebook menu, which 7.1b left out on
  purpose; this unit is the "someone asks". Listed for the owner in section 8.

## 3. Build

1. **Schema (additive), migration 192.** On `dashboard_report_subscriptions`
   add `day_of_week INTEGER` (nullable; 0 to 6, used when weekly),
   `notify_on TEXT NOT NULL DEFAULT 'always'` (`always` or `change`) and
   `last_result_digest TEXT` (nullable; JSON `{ [panelId]: string }` of
   SHA-256 digests, at most 60 entries, never rows). Migration in
   `server/plugins/db.ts`, `version: 192`, `name:
   "dashboard-report-subscriptions-change-detection"` (176 to 189 are 8.1 to
   8.3, 190 is 8.4d, 191 is 8.4f2). Widen the TypeScript enums: `frequency`
   gains `weekly`, `last_status` gains `unchanged`. Run `pnpm
   guard:additive-migrations`.
2. **Library.** In `dashboard-report-subscriptions.ts`: `nextWeeklyRunAt` and
   `lastWeeklyRunAt` beside the daily helpers, and validation (weekly needs
   `day_of_week`). In `dashboard-report.ts`, for a subscription with
   `notify_on = 'change'`:
   - add a `forceRefresh` argument to `fetchReportPanelData`
     (`dashboard-report-render.ts:128-134` has none today) and pass it to
     `runDashboardPanelQuery`, whose args already take it, so a scheduled run
     never reports a cache;
   - digest each panel's rows (`stableStringify` then SHA-256) in
     `shared/report-digest.ts`;
   - compare with `last_result_digest`: changed panels are those whose digest
     differs; a panel that failed now or failed last time is never
     "unchanged", it is listed as failed with its reason;
   - no changed and no failed panels: `last_status = 'unchanged'`, no email,
     digest kept;
   - otherwise send, with the changed and failed panels named first.
   `notify_on = 'always'` behaves as today plus the digest update.
3. **Notification.** Email through the existing report email, with a short
   "What changed" block (panel titles, and for single-value panels the old and
   new value) above today's content. Also an inbox notification through
   `notifyWithDelivery` with title "{{name}} changed" and a link to the
   notebook. Subject has no em dash (do not copy the existing subject's).
4. **Actions.** `save-dashboard-report-subscription` gains `frequency:
   "weekly"`, `dayOfWeek` and `notifyOn`; `list-dashboard-report-subscriptions`
   returns them and `lastStatus: "unchanged"`. Add `run-dashboard-report-now`
   only if no action already queues one (`queueDashboardReportSubscriptionNow`,
   `dashboard-report-subscriptions.ts:558`, is the library call; check the
   existing actions first and reuse).
5. **UI (gated).** On a notebook, the actions menu (7.1b) gains Schedule…
   after Publish as app…; on a grid dashboard, the existing email reports
   entry gets the same new fields. Schedule… opens a shadcn `Dialog` (title
   only): Repeat (`Select`: Every day, Every week), Day (for weekly), Time and
   Time zone (as the existing report form), Recipients (as today, max 5),
   Notify (`RadioGroup`: Every run, Only when something changes), and a
   primary Save at the compact size. A scheduled notebook shows a small
   `IconClock` in the header with a tooltip "Runs {{schedule}}. Last run
   {{ago}}: {{status}}."; status reads Changed, No change, Failed or Partly
   failed.
6. **Application state.** None new.
7. **Skills.** `.agents/skills/notebooks/SKILL.md` and the report section of
   `.agents/skills/dashboard-management/SKILL.md`: weekly and change-only
   schedules, that change detection compares panel results by digest, and
   that a failed panel is always reported.
8. **Changelog.** `agent-native changelog add "Schedule a notebook to rerun daily or weekly and hear only when something changes" --type added`.

  2026-10-14 call to keep Email reports out of it.

## 9. Do not

- Do not involve the agent in a scheduled run.
- Do not store result rows to compare; store digests only.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
