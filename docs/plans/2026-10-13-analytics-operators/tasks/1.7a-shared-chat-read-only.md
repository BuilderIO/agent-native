# 1.7a Shared chats open read-only with Continue

Lane A (Reliability). Size M. Split from plan unit 1.7, which is L as written;
1.7b covers "Request edit access" on dashboards.

## 1. Goal

When someone opens a link to a chat a teammate shared with them, they see that
teammate's conversation exactly as it was, with the composer replaced by a short
read-only notice and a **Continue** button. Continue copies the conversation
into a new chat the viewer owns and drops them into it, so their follow-up
question runs in their own thread. Nothing the viewer types can land in the
owner's thread, and no prompt is ever pasted into the viewer's existing chat.

## 2. What the code does today

Paths outside `templates/analytics/` are repo-relative.

**How a chat gets shared**

- The share button for chats lives in the shared agent panel header.
  `packages/toolkit/src/app/chat/AgentPanel.tsx:1288-1296` renders
  `<ShareButton resourceType="chat_thread" allowedRoles={["viewer", "editor", "admin"]} shareUrl={getChatThreadShareUrl(activeTab.id)} />`.
- `getChatThreadShareUrl` (`AgentPanel.tsx:1182-1198`) uses the panel's
  `threadUrlSync.getPath` when it has one. Otherwise it takes the
  **current page URL** and adds `?thread=<id>`.
- Analytics mounts that panel through `AgentSidebar` with no `threadUrlSync`
  (`templates/analytics/app/components/layout/Layout.tsx:297-323`). So a chat
  shared from the sidebar on a dashboard becomes
  `/dashboards/<id>?thread=<threadId>`. The sidebar's chat is scoped to the
  dashboard or analysis on screen (`Layout.tsx:64-80`).
- The full-page Ask route renders `AgentChatHome` with `showHeader={false}`
  (`templates/analytics/app/pages/Ask.tsx:58-72`). That hides the header, so
  `/ask/<threadId>` has **no share button**.
- Chat threads are registered as a shareable resource of type `chat_thread`
  with `getResourcePath: /?thread=<id>` and `allowPublic: false`
  (`packages/core/src/chat-threads/store.ts:897-910`). That path is the link
  the share email sends.

**What the viewer gets when they open it**

- A `?thread=` link opens the sidebar (`packages/core/src/client/agent-sidebar-state.ts:191`).
  `MultiTabAssistantChat` reads the id once into `deepLinkedThreadId` when URL
  sync is off (`packages/toolkit/src/app/chat/MultiTabAssistantChat.tsx:1118-1122`)
  and passes it to `useChatThreads` as `routeThreadId` (`MultiTabAssistantChat.tsx:1286-1290`).
- `useChatThreads` loads the thread with `GET /threads/:id`
  (`packages/core/src/client/use-chat-threads.ts:154-174`) and adds it to the
  thread list once its transcript is confirmed (`use-chat-threads.ts:1248-1300`).
- The server allows that GET for the `viewer` role and returns the raw
  `ChatThread` row (`packages/core/src/server/agent-chat-plugin.ts:7085-7096`).
  The response includes `ownerEmail` (`packages/core/src/chat-threads/store.ts:306-321`)
  but **not the viewer's role**. Nothing on the client records that this
  thread is read-only for this viewer. The only read-only composer state is
  for sub-agent tabs (`MultiTabAssistantChat.tsx:4006-4021`).
- Sending a message needs `editor`. The run path calls
  `resolveThreadAccess(..., "editor")` and throws `404 Thread not found` when
  the viewer only has `viewer` (`agent-chat-plugin.ts:3900-3910`, again at
  `4092-4101`). The viewer gets an editable composer that fails with "not
  found" when they press send.
- Forking already accepts `viewer` access: `POST /threads/:id/fork` checks
  `resolveThreadAccess(..., "viewer")` and copies the thread to the caller
  (`agent-chat-plugin.ts:7533-7577`). The client wrapper is `forkThread`
  (`use-chat-threads.ts:1955-2050`), and the UI already uses it as "Fork chat"
  through `handleForkChat` (`MultiTabAssistantChat.tsx:3587-3597`). That is the
  mechanism Continue needs.
- There is a second, separate share mechanism: a public token link
  (`POST /threads/:id/share`, admin only, `agent-chat-plugin.ts:7580-7618`)
  that serves a server-rendered HTML transcript
  (`packages/core/src/server/agent-chat/shared-thread.ts:239-259`, English
  hardcoded at `shared-thread.ts:201`). It is already read-only and is not the
  reported path.
- Slack-originated threads grant the Slack sender `editor` on the thread
  (`packages/core/src/integrations/webhook-handler.ts:787-803`). Those viewers
  must keep their editable composer.

**The reported problem.** A teammate opened a shared chat link, and the
prompt went into their own conversation instead of showing the shared thread.
I could not reproduce the exact sequence from the code alone. Two code paths
fit it: (a) the deep link misses because of scope (the GET applies
`threadMatchesRequestedScope`, `agent-chat-plugin.ts:7092`) and the viewer's
composer starts a new chat of their own; (b) the viewer has `viewer` role, the
send 404s, and a retry path creates a fresh thread. Step 1 of Build
reproduces this before any change.

## 3. Build

1. **Reproduce first, and write down which path it was.** Run the analytics
   app with two signed-in users in the same org (see Verify). As user A, ask a
   question in the sidebar on a dashboard shared with B, then share the chat
   with B as Viewer. As B, open the link from the share email (`/?thread=<id>`)
   and the copied link (`/dashboards/<id>?thread=<id>`). Record what B sees and
   what happens when B types and sends. Note the result in the PR description.
   If path (a) reproduces (scope mismatch hides the thread), fix it in step 3
   by making the deep-linked lookup ignore the request scope only for a thread
   the viewer has share access to. Do not widen anything else.

2. **Return the viewer's role with the thread (core).** In
   `packages/core/src/server/agent-chat-plugin.ts`, in the
   `GET /threads/:id` branch (`7085-7096`), also resolve the caller's role.
   Use `resolveAccess("chat_thread", threadId, { userEmail, orgId }, { skipResourceBody: true })`
   the way `hasThreadAccess` does (`store.ts:922-938`). Respond with
   `{ ...thread, access: { role } }`. Additive field only, no change to who may
   read. Add `access?: { role: ShareRole | "owner" }` to the client
   `ChatThreadSummary` type the hook uses, and keep it when the hook merges the
   fetched thread (`use-chat-threads.ts:1294-1300`).

3. **Read-only state in the shared chat UI (toolkit).** In
   `packages/toolkit/src/app/chat/MultiTabAssistantChat.tsx`, derive
   `readOnlyThread = access.role` is `viewer` or `commenter` for the active
   tab. When it is set:
   - Pass `composerDisabled` and the new read-only placeholder, as the
     sub-agent case does (`4006-4021`).
   - Render a one-line bar above the composer: the notice text on the start
     side and a `Button` (shadcn, `variant="default"`, size per the 24px
     control baseline) labeled **Continue** on the end side. Put the
     explanation in a `Tooltip` on the button, not a second line. Tabler icon:
     none (text-only button).
   - Continue calls the existing `handleForkChat(tabId)`. While it runs, show
     the button's pending state (no full-pane spinner). On `false`, show the
     error toast below and leave the read-only view in place. Never fall back
     to creating an empty thread or re-sending the last prompt.
   - Hide "Fork chat" from the message menu for this tab, since Continue is
     the same action.
   - Owners and `editor`/`admin` sharees see no change.

4. **Guard the send path so it can't silently start a new chat.** Find where
   a failed send to a thread the user cannot write leads to a new thread or a
   re-sent prompt (the path step 1 found) and make it fail visibly instead. A
   send to a read-only thread is not possible from the UI after step 3. The
   guard covers stale tabs and the agent-side retry. A 404 from the run start
   on a thread the client knows is shared must surface as the read-only state,
   not as "start over".

5. **Give the Ask page a share button.** `/ask/<threadId>` has no header
   (`Ask.tsx:72`). Add the same `ShareButton` the panel uses, placed in the
   Ask page's existing top-end area, with `shareUrl` built from
   `analyticsAskThreadPath(threadId)` (`templates/analytics/shared/ask-route.ts`).
   Show it only when the thread has messages (same rule as `AgentPanel.tsx:1281-1285`).
   Use `analyticsAskThreadPath` as the share URL so links from Ask open the full
   page instead of a dashboard sidebar.

6. **Make shared links land on the thread view.** Change `getResourcePath`
   for `chat_thread` only if step 1 shows `/?thread=` does not open the thread
   in analytics. If it needs to change, do it per app: let the template
   override the path through a registration option rather than hardcoding
   `/ask/` in core. Default decision: keep `/?thread=` and confirm it works
   (the sidebar opens on deep links).

7. **Skills and instructions.**
   - `templates/analytics/.agents/skills/sharing/SKILL.md` is a byte-identical
     copy of the root `.agents/skills/sharing/SKILL.md` (checked with `diff`).
     Add the same short "Chats" section to both: a viewer opens a shared chat
     read-only and continues in a fork; editors keep the composer. Keep them
     identical. Read `writing-agent-instructions` first.
   - No agent tool change: the agent never runs inside a thread the viewer
     can only read.

8. **Application state.** Not applicable. The read-only thread never runs the
   agent, and after Continue the viewer is in their own thread, which the
   existing navigation state already covers (`app/hooks/use-navigation-state.ts`).

9. **Changesets and changelog.** Add `.changeset/*.md` for `@agent-native/core`
   and `@agent-native/toolkit` (patch). From `templates/analytics`, run
   `agent-native changelog add "Shared chats open read-only, and Continue copies them into your own chat." --type fixed`.

## 8. Defaults for open questions

- **[decide] Read-only roles:** `viewer` and `commenter` are read-only;
  `editor`, `admin`, owner keep the composer. Reviewer can change.
- **[decide] Continue copies the whole thread.** It does not fork from a
  selected message. Reviewer can change.
- **[decide] No owner name in the notice.** Showing "Shared by <name>" needs a
  profile lookup the GET does not do. Add later if wanted.
- **[decide] Share link format stays `/?thread=<id>`** unless step 1 proves it
  broken.
- **[decide] The public token page (`/shared/<token>`) is out of scope.** It
  is already read-only. Its hardcoded English is a separate follow-up.

## 9. Do not

- No behavior changes outside this unit. Owners and editors keep today's chat.
- Additive-only schema; this unit should need no schema change at all.
- No new `/api` routes for app data; the chat thread routes are framework
  routes and only gain a response field.
- No raw `fetch` from template client code; the toolkit and core client
  modules already own the thread calls.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value: a
  failed Continue is an error toast, never an empty new chat, and a missing
  `access` field means "unknown", not "owner". Treat unknown as today's
  behavior and log it.
- No large payloads in SQL.
- Do not widen who can read a thread, and do not change the run path's
  `editor` requirement.
