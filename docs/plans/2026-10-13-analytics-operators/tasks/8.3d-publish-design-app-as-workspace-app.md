# 8.3d Publish a Design data app as a workspace mini-app that reads Analytics over A2A

Lane E (Holy-shit features). Size M. Gated: the "Publish as app…" item and
dialog in Design are new UI; build only after the "Design: publish as app"
screen in `prototypes/analytics-operators/` is signed off. Where the
signed-off prototype differs from this brief, the prototype wins.

Depends on: 8.3b (binding), 8.3c (apps arrive from Analytics). Merge after
8.2b (`packages/core/src/artifacts/detect.ts`). Blocks: nothing.

Paths are relative to `templates/design/` unless they start with
`packages/` or `templates/analytics/`.

## 1. Goal

The account health app looks right in Design. The author chooses "Publish
as app…", confirms a name and an app id, and Design hands the screens and
a fixed data contract to Dispatch, which starts building a real workspace
app (`apps/account-health`) on a Builder branch. The finished app has one
way to get data: a server action that asks Analytics for the notebook's
named outputs over A2A as the signed-in person. It holds no provider
credentials, runs no SQL and stores no rows. Anyone in the workspace can
open it; each person sees only data they could already see in Analytics.
That last part is a requirement (owner, 2026-10-14), tested below.
Publishing goes through Builder in v1 (owner, 2026-10-14): it is a reason
to use a Builder account, and there is no other host.
The dialog reports what Dispatch actually returned (branch, path, status),
and nothing more.

## 2. What the code does today

- Dispatch's `start-workspace-app-creation` takes `{ prompt, appId?,
  template?, description?, secretIds?, resourceIds?, attachments? }` and is
  the Builder handoff for a new workspace app under `apps/<app-id>`; its
  description says first-party data should be reached "via links or A2A"
  (`packages/dispatch/src/actions/start-workspace-app-creation.ts:38-89`).
  It returns one of `builder-unavailable`, `app-id-taken`, `local-agent`,
  `coming-soon` or `builder` with `appId`, `path`, `branchName`, `url`,
  `status` (`packages/dispatch/src/server/lib/app-creation-store.ts:2822-2878`).
  In local dev it returns a code-agent prompt instead of a branch.
- The turn-into-app guide for Dispatch: never invent a branch URL; a reply
  with only an acknowledgement is unverified
  (`.agents/skills/turn-into-app/references/fresh-project.md:32-49`).
- Design's `export-coding-handoff` returns tokenized raw and ZIP URLs and a
  prompt for the design's current state, with an expiry, and is a
  read-only peer action (`actions/export-coding-handoff.ts:36-59`,
  `:93-127`). The editor's handoff UI is driven from
  `app/pages/design-editor/domains/use-editor-export-and-handoff.ts`.
- 8.3b stores the binding at `data.analyticsBinding`; 8.3a's
  `read-named-outputs` refuses organization-only principals and runs as the
  caller.
- No ledger kind exists for a started workspace app
  (`packages/core/src/artifacts/detect.ts:1-30`).

## Plan corrections

- Publishing starts a build; it does not deploy an app in one step. The
  workspace app exists when Builder's branch merges and the workspace
  deploys. The dialog says "Publishing started" with the branch, and never
  "Published".

## 3. Build

1. **Core (`packages/core`, minor changeset, after 8.2b).** Add a
   `workspace-app` ledger kind: map `start-workspace-app-creation` to it
   when the result's `mode` is `builder` (id `appId`, url `url`) or
   `local-agent` (id `appId`, no url) in `TOOL_ARTIFACT_KINDS`
   (`packages/core/src/artifacts/detect.ts:60-110`), and allow it in
   `ARTIFACT_RESOURCE_TYPES` (`packages/core/src/a2a/artifact-response.ts:112-121`).
2. **Handoff bundle.** When a design is bound, `export-coding-handoff`
   adds two files to the bundle: `data-contract.json` (the binding: dashboard
   id and name, output names, titles, columns, inputs; no rows) and
   `actions/read-analytics-outputs.ts`, a reference action that calls
   `invokeAgentAction({ target: "analytics", action: "read-named-outputs",
   input: { dashboardId, outputs, inputs }, ... })` with
   `resolveA2ACallerAuth({ audience: canonicalA2AAudience(url),
   userIdentityOnly: true })` and returns the contract's typed results
   unchanged. Unbound designs get the bundle as today.
3. **Action** `actions/publish-data-app.ts` (`defineAction`): input
   `{ designId, appId, name, description? }`. `assertAccess("design", id,
   "editor")`; refuses an unbound design (`not_bound`); creates the handoff
   with `export-coding-handoff`; builds the brief (at most 6,000
   characters): the app's name and job, the screens to build from the
   bundle, and the data rules (data only through
   `read-analytics-outputs`; render loading, empty, truncated, no-access
   and error states; no provider credentials, SQL or stored rows; template
   `chat`, branded as the app). Then delegates to Dispatch by message with
   `invokeAgent` (target `dispatch`, idempotency key from the design id and
   app id): run `start-workspace-app-creation` with that `appId`,
   `description`, `template: "chat"`, the brief as `prompt`, and the ZIP
   URL as a `url` attachment. Reads a verified `workspace-app` identity, or
   the `mode` Dispatch reports, into `data.appPublish = { status: "started"
   | "local_agent" | "failed", appId, url?, branchName?, startedAt, error?
   }` and returns it. `app-id-taken`, `builder-unavailable` and
   `coming-soon` are `failed` with that reason; a reply with no verified
   identity is `failed` with `unverified_result`.
4. **UI (gated).** "Publish as app…" beside the existing handoff actions,
   shown only for a bound design. Dialog: title "Publish as app"; App name
   (`Input`, the design title); App id (`Input`, a slug of the name,
   validated with the workspace app id rule); one line saying who can see
   what ("People in the workspace can open it. Each person sees only the
   data they can see in Analytics."); Cancel (outline) and Publish (primary
   at the compact size). After the call, the dialog shows the result:
   "Publishing started" with "Open branch" when there is a URL, or the
   local-agent prompt notice, or the amber failure reason. Reopening the
   dialog shows the last `appPublish`.
5. **Application state.** `view-screen`'s `dataBinding` (8.3b) adds
   `publish: { status, appId, url? }`.
6. **Skills.** Extend `.agents/skills/analytics-data-apps/SKILL.md`:
   publish with `publish-data-app`; report Dispatch's result exactly; the
   published app reads only through `read-analytics-outputs`. Add to
   `.agents/skills/export-handoff/SKILL.md` that bound designs carry the
   data contract and the reference action.
7. **Changelog.** From `templates/design`: `agent-native changelog add "Publish an Analytics data app from Design as a workspace app" --type added`.

## 8. Defaults for open questions

- [Default] The published app starts from the `chat` template and is
  visible to the workspace; data access is per person through Analytics.
- [Default] Publishing again with the same app id is refused by Dispatch
  (`app-id-taken`); updating a published app is a later unit.
- [Decided by the owner, 2026-10-14] Publishing is Builder-only in v1, and
  that is a value prop for Builder accounts. Without Builder, publishing
  fails with a plain reason; there is no Design-hosted fallback.
- [Decided by the owner, 2026-10-14] People using the published app see only
  data they can already see in Analytics.

## 9. Do not

- Do not give the published app provider credentials, SQL, or a way to
  read Analytics other than `read-named-outputs`.
- Do not report a branch or URL Dispatch did not return.
- Do not embed rows in the bundle or the brief.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
