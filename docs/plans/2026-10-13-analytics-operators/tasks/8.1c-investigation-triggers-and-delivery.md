# 8.1c Investigation triggers and delivery

Lane E (Holy-shit features). Size M. Gated in part: the "Why did this
change?…" panel menu item and its dialog, and the "Investigate when it
fires" switch in the alert dialogs, are new UI covered by the 8.1 prototype
sign-off ("Panel: why did this change?" and "Investigation: alert fires"
screens). The server half (the alert option, queueing on fire, delivery and
the chat and Slack routes) is not gated and may land first.
Depends on: 8.1a, 8.1b, 4.2b; 4.2c for funnel conversion alerts; 5.2.
Blocks: 8.1f, 8.1g.

Paths are relative to `templates/analytics/` unless they start with

## 1. Goal

Investigations start where the question comes up, and the answer comes back
the way the alert or question came in.

- An alert rule has "Investigate when it fires", on by default for funnel
  conversion alerts (4.2c) and growth alerts (4.2b's at most, drop and rise
  conditions). When the Activation funnel alert "Dashboard conversion
  dropped" fires, one investigation is queued for that incident, and the
  alert notification carries its id so 8.1f can show "Investigating…".
- Any time-scoped chart panel, and any funnel panel, has "Why did this
  change?…" in its menu. It opens a small dialog with the change, a
  comparison and a budget, and Investigate starts the same investigation.
- "Why did signups drop?" in Ask, the agent sidebar or a Slack direct message
  starts one when the question names a panel, funnel step pair or alert the
  agent can resolve; otherwise the agent answers as it does today.
- When it finishes, the result goes to the in-app notifications, and for an
  alert also to that alert's own channels (Slack webhook, email, webhook),
  with a link to the notebook. A question asked in Slack also gets the
  answer back in its thread (8.1g).

## 2. What the code does today

- Alert rules have no investigate option: `analytics_alert_rules`
  (`server/db/schema.ts:705-756`) and `save-analytics-alert-rule`
  (`actions/save-analytics-alert-rule.ts:26-104`) carry name, event, filters,
  4.2b's `comparison`, channels, email recipients, Slack and webhook URLs and
  enabled.
- On a trigger, `evaluateAndNotifyAnalyticsAlertRule` notifies first
  (`server/lib/analytics-alerts.ts:1233`), marks the rule `error` when no
  channel delivered, and only then records the incident (`:1275`), whose id
  is generated inside `recordIncident` (`:2611`). Inbox is always added
  (`ensureInboxNotificationChannel`, `:1296-1300`) and the rule's Slack and
  webhook URLs travel as delivery metadata (`alertNotifyDeliveryMetadata`,
  `:1301-1308`).
- Core channels deliver Slack and webhook from `metadata.slackWebhookUrl` and
  `metadata.webhookUrl` (`packages/core/src/notifications/channels.ts:1-22`);
  `NotificationInput` takes an `idempotencyKey`
  (`packages/core/src/notifications/types.ts`).
- 4.2c (brief, not built) adds `kind: "funnel_conversion"`, `source_ref`,
  `evaluateFunnelConversionRule` with its own notification, and a conversion
  dialog that shares the dialog shell extracted from
  `app/pages/settings/AlertRulesSettingsCard.tsx` (event dialog `<Dialog>` at
  `:868`, Channels at `:1163`, Enabled at `:1251`).
- The chart panel menu (`app/pages/adhoc/sql-dashboard/SqlChartCard.tsx`)
  opens with "Chat with panel" (`:857-865`, `selectForChat`), with leading
  icons today (`IconMessageCircle`, `:863`). Panel help goes to the agent
  through `sendToAgentChat` (`:339-358`).
- `requestAgentTaskOpen` opens a background task's thread in the agent
  sidebar (`packages/core/src/client/agent-chat.ts:825`).
- Slack (5.2): the integrations plugin passes the whole action registry and
  the messaging prompt (`server/plugins/integrations.ts:76-86`);
  `analyticsWebAddress()` gives the absolute base for links (`:16-21`); the
  messaging rules live in `server/lib/analytics-integration-prompt.ts:16-22`.
  A channel message runs as the shared service principal; a direct message
  runs as the linked member (`.agents/skills/slack-answers/SKILL.md`,
  Identity).
- 8.1a (brief) provides `start-investigation`, the `alert_incident` and
  `panel` subjects, dedupe per incident, the `service_identity` refusal and
  the `onInvestigationFinished` hook; 8.1a's confirm step measures a subject.

## Plan corrections

- **The incident id has to exist before the notification.** To put the
  investigation id on the alert notification, generate the incident id
  first, queue the investigation, notify, then record the incident with that
  id. If no channel delivered, cancel the queued investigation, so today's
  behavior (no incident without a delivered alert) holds.
- **Slack channel messages cannot own an investigation.** They run as the
  service principal, so the notebook would be private to nobody. Investigations
  start from a Slack direct message only; in a channel the agent answers
  directly and says a direct message can run the full investigation.
- **The finished summary posts back into the Slack thread, in 8.1g.** The
  direct message reply links the notebook right away. When the
  investigation ends, 8.1g posts the answer, the confidence label and the
  link in the same thread through `PlatformAdapter.sendMessageToTarget`
  (`packages/core/src/integrations/types.ts:217-220`), which posts after
  the turn has ended. This unit only leaves the delivery hook for it.

## 3. Build

1. **Schema (additive), migration 178** in `server/db/schema.ts` and
   `server/plugins/db.ts` (`version: 178`, `name:
   "analytics-alert-investigations"`; 176 is x1's, 177 is 8.1a's):
   `ALTER TABLE analytics_alert_rules ADD COLUMN IF NOT EXISTS
   investigate_on_fire BOOLEAN NOT NULL DEFAULT false` and `ALTER TABLE
   analytics_alert_incidents ADD COLUMN IF NOT EXISTS investigation_id TEXT`.
   Existing rules stay off.
2. **Rule option** (`server/lib/analytics-alerts.ts`,
   `actions/save-analytics-alert-rule.ts`, `actions/list-analytics-alert-rules.ts`):
   `investigateOnFire?: boolean`. On create, an omitted value is `true` for
   `funnel_conversion` rules and for `at_most`, `drop_vs_baseline` and
   `rise_vs_baseline`, `false` for `at_least`; on update an omitted value
   keeps the stored one. The default rules from
   `ensureDefaultAnalyticsAlertRules` stay off. Describe the field so the
   agent turns it on or off on request.
3. **Queue on fire** (`server/lib/alert-investigations.ts`, called from the
   event path and 4.2c's funnel path):
   - After the cooldown check and before `notifyWithDelivery`: `incidentId =
     randomUUID()`. When `investigateOnFire`, call
     `queueInvestigationForAlert({ rule, incidentId, windowStart, windowEnd,
     evaluation })`, which creates the investigation `queued` through 8.1a's
     store (subject from the rule and the evaluation, since the incident row
     does not exist yet; `dedupe_key` `alert_incident:<incidentId>`).
   - If an investigation for the same rule is already queued or running,
     reuse it: no new record, and the notification says
     `investigationReused: true`.
   - Notify with `investigationId` in the metadata (body and title
     unchanged). Then `recordIncident` takes the pre-generated id and stores
     `investigation_id`.
   - Delivered: start the run (8.1a's run step). Not delivered: cancel the
     queued investigation with "The alert notification wasn't delivered."
   - Queueing that throws: the alert still goes out, with
     `investigationError: <code>` in the metadata and a log line; the rule's
     status is unaffected. 8.1f shows "Couldn't start the investigation."
     Never report a queued investigation that does not exist.
4. **Delivery** `server/lib/investigation-delivery.ts`, registered as 8.1a's
   `onInvestigationFinished` hook:
   - `notifyWithDelivery` with title `Investigation complete: <title>`,
     `Investigation partial: <title>` or `Investigation failed: <title>`;
     body: the one-line summary, then "<High> confidence." or "No change
     found."; metadata `{ kind: "analytics_investigation", investigationId,
     notebookId, status, outcome, confidence, link: "/dashboards/<notebookId>"
     }`; `idempotencyKey: investigation:<id>:finished`; owner = the
     investigation owner.
   - Channels: an alert investigation uses the rule's channels through
     `ensureInboxNotificationChannel` and `alertNotifyDeliveryMetadata`, plus
     its email recipients; others use `inbox`. For Slack, email and webhook,
     append the absolute notebook link built from `analyticsWebAddress()`;
     with no web address, add no link.
   - No channel delivered: record `delivery_error` on the investigation; its
     status stays what it was.
5. **Chat route:** in `actions/start-investigation.ts`'s description and the
   `investigations` skill: when the user asks why a panel, a funnel step pair
   or an alert changed, resolve it (the selected panel from screen context,
   or `list-analytics-alert-rules`), call `start-investigation`, and say it is
   running and takes up to the budget; the result comes back to the same chat
   (8.1a passes `parentThreadId`). When nothing resolves, answer directly.
   Add one line to `.agents/skills/data-querying/SKILL.md` pointing at this.
6. **Slack route:** add to the messaging rules in
   `server/lib/analytics-integration-prompt.ts`: in a direct message, start
   the investigation and reply with one line and the absolute notebook link;
   in a channel, answer directly and say a direct message can run the full
   investigation. `start-investigation` already refuses the service
   principal (8.1a). The finished answer posts back in the same thread
   (8.1g). Update `.agents/skills/slack-answers/SKILL.md` (Reply
   rules) and its byte-identical template copy if one exists.
7. **`preview-investigation-change`** (new, GET, read-only): runs 8.1a's
   confirm measurement only (at most 2 queries, caller `investigation`) for
   a panel and a compare preset, and returns `{ text, current, previous,
   unit, direction }`, where `text` is the change in words ("Connected a
   data source to Built a dashboard fell from 69.0% to 52.4%"). For a funnel
   panel with no step pair it picks the pair whose conversion changed most
   and returns it. Unreadable is a typed failure.
8. **UI (gated):**
   - Panel menu (`SqlChartCard.tsx`, chart panel menu at `:857`): add "Why
     did this change?…" right after "Chat with panel", only for panels whose

## 8. Defaults for open questions

- [Default] "Investigate when it fires" is on by default for new funnel
  conversion and growth alerts (at most, drop, rise) and off for at least
  rules and existing rules.
- [Default] One investigation per incident, and at most one queued or running
  per rule; a later incident reuses it.
- [Default] Alert results go to the alert's own channels; other results go
  in-app only.
- [Default] Investigations start from Slack direct messages only.
- [Decided by the owner, 2026-10-14] An investigation asked in Slack posts
  its finished answer back in the thread where it was asked. 8.1g builds it
  on this unit's delivery hook; this unit replies with the notebook link
  and delivers the result in-app.

## 9. Do not

- Do not change event or funnel rule evaluation, cooldowns or the alert
  notification's title and body.
- Do not record an incident for an alert that was not delivered, or report
  an investigation that was never queued.
- Do not start an investigation from a channel message or another service
  identity.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
