# 4.2c Funnel conversion alerts

Lane D (Growth). Size M. Gated: the conversion bell on the funnel panel and
the conversion alert dialog are new UI covered by the 4.1a prototype sign-off
("Funnel" and "Funnel: conversion alert" screens).

## 1. Goal

On a funnel panel, a growth lead clicks the bell on the conversion line
between two steps (for example between "Connected a data source" and "Built
a dashboard"), picks a condition (below or above a percent, or a drop of N
points against the previous period) and a comparison window, sees when the
alert would have fired over the last 7 days, and saves it. They get told when
that step-to-step conversion rate crosses the line, not when a step's raw
event count moves. The alert watches the panel itself, so editing the
funnel's steps updates what the alert checks, and deleting the panel turns
the alert into a visible error instead of a silent OK. The agent can create
the same alert from a request like "tell me if signup to workspace
conversion drops under 60%".

## 2. What the code does today

- Alert rules only count events (`server/lib/analytics-alerts.ts:28-98`,
  rule columns in `server/db/schema.ts:677-710`). They cannot reference a
  dashboard panel or compute a ratio between two event sets.
- Funnel panels with a definition come from 4.1b: `config.growth` (kind
  `funnel`), `compileGrowthPanelSql`, and `interpolateDashboardPanelSql`
  compiling growth panels (`app/pages/adhoc/sql-dashboard/interpolate.ts:36-57`).
  Output rows are one per step: `step_index`, `step`, `count`.
- Dashboards are read with access checks through `getDashboard(id, ctx)`
  (`server/lib/dashboards-store.ts:819-840`, which calls `resolveAccess`).
  First-party queries run as a scope with `queryFirstPartyAnalytics`
  (`server/lib/first-party-analytics.ts:1571`); the alert sweep already runs
  each rule inside the owner's request context
  (`server/jobs/analytics-alerts.ts:111-121`).
- The funnel renderer (`FunnelRenderer`, `app/components/dashboard/SqlChart.tsx:2526-2579`)
  draws each step as a label, value, share of first step and drop-off
  percent, with no interaction. 4.1b adds the conversion line between two
  steps, 4.3 turns step rows into replay menus, and this unit puts the bell
  on the conversion line.
- First-party freshness is read by `get-first-party-analytics-health`
  (`lastDeliveredAt`, 4.2a).
- The alert dialog and list are `app/pages/settings/AlertRulesSettingsCard.tsx`
  (dialog `:774-1046`). 4.2a adds per-class evaluation
  intervals; 4.2b adds `comparison`, `min_baseline_count`, the
  `insufficient_baseline` status and `decideAlert`.

## 3. Build

1. Schema (additive), in `server/db/schema.ts:677-710` and a new versioned
   migration in `server/plugins/db.ts`:
   - `kind TEXT NOT NULL DEFAULT 'event'` (`event` or `funnel_conversion`).
   - `source_ref TEXT` (null for event rules): JSON `{ dashboardId, panelId,
     fromStepIndex, toStepIndex, lookbackDays }`. It is a small reference, not
     a copy of the panel.
   - Funnel rules reuse 4.2b's `comparison` column with three values valid
     only for `funnel_conversion`: `conversion_below`, `conversion_above`
     (threshold is a percent, 1 to 100) and `conversion_drop_points`
     (threshold is percentage points, 1 to 100, measured against the
     previous window of the same length). They reuse `cooldown_minutes` and
     `min_baseline_count` (people at the from step, default 20).
   Existing rules stay `event`.
2. Library (`server/lib/analytics-alerts.ts`):
   - Validate on save: `fromStepIndex < toStepIndex`, `lookbackDays` one of
     1, 7, 14 or 30, the threshold range for the comparison, the dashboard
     exists for the saver, the panel has a funnel `config.growth`, and both
     step indexes exist.
   - Evaluate `funnel_conversion` rules in a new `evaluateFunnelConversionRule`:
     load the dashboard with `getDashboard` as the rule owner; find the panel;
     interpolate with `timeRange = "custom"`, `timeRangeStart = today -
     lookbackDays`, `timeRangeEnd = today`; run with `queryFirstPartyAnalytics`
     for the owner's scope; read the two step counts. Conversion =
     `to / from * 100`. For `conversion_drop_points`, run the previous window
     too and compare.
   - Outcomes through `decideAlert`: crossing the line is `triggered`; fewer
     people than the minimum at the from step is `insufficient_baseline`;
     anything that cannot be read is an error with a plain message, never OK:
     "The funnel this alert watches was deleted or you no longer have access
     to it.", "The funnel this alert watches no longer has those steps.", or
     the query error.
   - `previewFunnelConversionRule(input)`: the daily conversion for each of
     the last 7 days with the same compile path, which days would have fired
     after the cooldown, the previous-window conversion for a drop rule, and
     `lastEventAt` for the to step's event. It returns a typed failure, not
     an empty series, when the funnel cannot be read.
   - Interval: funnel rules run at most once an hour (extend 4.2a's interval
     constant with a funnel class).
   - Notification: title stays `Analytics alert: <name>`; body like
     "Connected a data source to Built a dashboard converted 58% over the
     last 7 days (3,620 of 6,240 people). Alert when below 60%." Metadata
     adds `kind`, `dashboardId`, `panelId`, both step labels and counts, and
     a dashboard link built the way other app links are built.
   - Keep funnel rules out of the BigQuery event batch
     (`server/jobs/analytics-alerts.ts:103-133`).
3. Actions:
   - `actions/save-analytics-alert-rule.ts`: add `kind` and a `funnel` object
     (`dashboardId`, `panelId`, `fromStepIndex`, `toStepIndex`,
     `lookbackDays`) plus the three conversion comparisons. Describe it so
     the agent maps "alert me if conversion from X to Y drops below N%" to
     this kind, and tells it to read the panel with `get-sql-dashboard` first
     to find step indexes.
   - `actions/preview-funnel-conversion-alert.ts` (new, read-only, `http: {
     method: "GET" }`): wraps `previewFunnelConversionRule` so the dialog and
     the agent see the same preview.
   - `list-analytics-alert-rules` returns `kind` and the parsed reference.
4. UI:
   - Bell on the conversion line (`FunnelRenderer` in `SqlChart.tsx`; 4.1b
     draws the line between each pair of steps with "69.0% continued" and
     the people who dropped): for a panel with a funnel `config.growth`, add
     at the line's end an icon button with `IconBell` (or `IconBellRinging`
     in amber when an alert exists for that pair), shown on line hover and
     focus and always when an alert exists. Tooltip: `funnelConversionAlertSet`,
     or the rule's summary when one exists. Editors only; viewers and
     SQL-only funnels get no bell. There is no bell on a step row.
   - The bell opens the conversion alert `Dialog` in place over the
     dashboard (extract the dialog shell from `AlertRulesSettingsCard.tsx`
     `:774-1046` so Settings and the funnel share it). Fields, in order:
     - Title `Create conversion alert` or `Edit conversion alert`, no
       subtitle.
     - Freshness line: a live dot and "Checks once an hour against live
       events. The last {{event}} event arrived {{ago}}." from the preview's
       `lastEventAt`; when it cannot be read, say so in the same line.
     - Name (prefilled from the to step, for example "Dashboard conversion
       dropped").
     - From step and To step (`Select` of the panel's step labels; To lists
       only steps after From).
     - Condition (`Select`: Below, Above, Drops by) and its value: Conversion
       (%) for Below and Above, Points versus the previous period for Drops
       by.
     - Over the last (`Select`: 1 day, 7 days, 14 days, 30 days), with a
       tooltip that conversion alerts are checked once an hour.
     - Cooldown minutes.
     - Preview: bars of the last 7 days of conversion, the threshold as a
       dashed line, days that would have fired in amber, and "Would have
       fired N times in the last 7 days" (or "Wouldn't have fired in the last
       7 days"). It reruns on every condition change.
     - Channels and Enabled, as in the event dialog.
     - Run check and Save alert (Update alert when editing).
   - No event name, filters, threshold mode or window minutes for this kind:
     a funnel alert never counts a step's raw events.
   - New alerts started from New alert in Settings stay event rules (the
     shipped dialog with 4.2b's conditions); there is no funnel picker there
     in v1, and the funnel never opens the event dialog.
   - List: the condition summary uses `alertConversionSummary`; a rule whose
     panel is gone shows its error text as today.
5. Application state: no new key. The dialog opens in place, so nothing goes
   in the URL. The funnel panel selection (`growthKind: "funnel"`, 4.1b)
   tells the agent which panel "this funnel" means; `view-screen` needs no
   change.
6. Skills: in `.agents/skills/dashboard-management/SKILL.md` (growth section)
   add two sentences: conversion alerts watch the conversion between two
   steps of a funnel panel by reference; create them with
   `save-analytics-alert-rule` kind `funnel_conversion`, and check
   `preview-funnel-conversion-alert` before saving.
7. Changelog: `agent-native changelog add "Get an alert when the conversion between two funnel steps crosses a target" --type added`.

## 8. Defaults for open questions

- [Default, reviewer can change] The alert references the panel; it does not
  snapshot the steps. Editing the funnel changes what the alert checks.
- [Decided by the owner, 2026-10-13] Funnel alerts watch the conversion
  rate between two steps, started from the bell on the conversion line. The
  step bell event alert is gone from the funnel.
- [Decided] Conditions: below or above a percent, or a drop of N points
  against the previous window of the same length.
- [Default] Look-back 1, 7, 14 or 30 days, checked hourly; the preview
  always shows the last 7 days.
- [Default] Conversion alerts can only be started from a funnel panel (or by
  the agent), not from New alert in Settings.

## 9. Do not

- Do not change event-rule evaluation.
- Do not copy panel SQL or rows into the rule.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
