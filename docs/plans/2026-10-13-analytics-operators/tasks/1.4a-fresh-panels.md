# 1.4a Fresh, cheap panels: no reload storms, visible-and-stale refresh, "as of", Refresh that bypasses the cache

Lane A (Reliability). Size M. Not gated.

The plan's PR 1.4 is split in two. This unit (1.4a) fixes how panels load and
refresh and makes their age visible. 1.4b moves first-party panels off the
raw events table where a rollup can answer them.

## 1. Goal

Dashboards stop reloading on their own. A panel loads when it scrolls into
view, and loads again only when it is on screen and its data is older than
its freshness window, or when the person clicks Refresh. Every data panel
shows when its numbers are from ("As of 2:14 PM"), and says so when it is
showing an older saved result because the latest run failed. Refresh on a
panel always gets new numbers from the source, for every source, which fixes
the stale signup count that Refresh did not clear. The agent sees the same
"as of" time when it inspects a panel.

## 2. What the code does today

All paths relative to `templates/analytics/` unless they start with
`packages/`.

**Loading and refetching (client).**

- SQL dashboard panels load through `useSqlQuery`
  (`app/lib/sql-query.ts:189-263`), called once per panel from `SqlChart`
  with key `["sql-chart", dashboardId || panel.id, sql, panel.source]`
  (`app/components/dashboard/SqlChart.tsx:1187-1197`). Defaults: no interval,
  no refetch on mount, focus or reconnect, no retry, `staleTime` 5 minutes
  (`sql-query.ts:230-236`). Nothing on this path polls.
- A panel loads lazily: `SqlChartCard` starts an `IntersectionObserver` and
  **disconnects it after the first intersection**
  (`app/pages/adhoc/sql-dashboard/SqlChartCard.tsx:285-309`), so it never
  knows again whether the panel is on screen.
- The root `useDbSync` bridge (`app/root.tsx:91-104`) has no `realtime`
  reason, so by the `real-time-sync` skill it opens no background transport;
  its `actionInvalidatePredicate` (`app/root.tsx:106-122`) keeps action and
  sync invalidations away from `["sql-chart"]`, `["data","sql-dashboard"]`
  and the sidebars, and invalidates **every other query**.
- Explorer dashboards are a second panel path that is not excluded. Each
  `ChartCard` reads `["explorer-config", configId]` with `staleTime` 60 s and
  `["dashboard-chart", configId, sql]` through `useMetricsQuery`
  (`app/pages/adhoc/explorer-dashboard/ChartCard.tsx:109-121`,
  `app/lib/query-metrics.ts:44-58`), and the page key includes
  `useChangeVersions(["dashboards","action"])`
  (`app/pages/adhoc/explorer-dashboard/index.tsx:327-333`). Any mutating
  action, including the dashboard page's own debounced filter-preference save
  (`app/pages/adhoc/sql-dashboard/index.tsx:1161-1199`), therefore refetches
  every visible explorer chart. `useMetricsQuery` also uses a raw `fetch` to
  `/api/query` (`app/lib/query-metrics.ts:13-30`), against the client rule.
- **No code path found that reloads SQL panels on a 60 second timer.** The
  candidates for the reported "every 60 seconds" are: the 60 s idle poll and
  SSE fallback in `useDbSync` (`packages/core/src/client/use-db-sync.ts:60-62`)
  if any mounted hook on the page opts into a transport (the collaborative
  doc on the SQL dashboard, `app/pages/adhoc/sql-dashboard/index.tsx:829-839`,
  is the first to check); the 60 s `explorer-config` stale time above; and
  the public status page's 60 s refetch (`app/routes/status.$slug.tsx:107`),
  which is not a dashboard. This must be measured, not guessed (step 1).
- Likely sources of the reported errors: 500 from `query-dashboard-panel`
  when a first-party query times out or a program reports
  `background_pending` (both throw, `server/lib/dashboard-panel-query.ts:395-407`,
  `:461-494`); 409 from `update-dashboard`'s `dashboard_conflict`
  (`actions/update-dashboard.ts:942-948`) when a page save races another
  writer. Plain-language error copy for these is 1.5, not this unit.

**Caching and Refresh (server).**

- The panel action is `query-dashboard-panel` (`actions/query-dashboard-panel.ts`,
  UI only, `agentTool: false`), which takes `forceRefresh` and passes it
  through the resolver (`server/lib/dashboard-panel-source-resolver.ts:38-50`)
  to `runDashboardPanelQuery` (`server/lib/dashboard-panel-query.ts:410-516`).
- **The client sends `forceRefresh` only for `bigquery`**
  (`app/lib/sql-query.ts:157-159`). Refresh on a first-party, program, GA4,
  Amplitude or Prometheus panel refetches but the server returns its cache.
- `bigquery` panels go to `runQuery` with a 24 h cache, L1 plus the
  `bigquery_cache` table, keyed with the UTC date only when the SQL uses
  `CURRENT_DATE` (`server/lib/bigquery.ts:472-504`, `:1105-1160`);
  `forceRefresh` skips both and sets `useQueryCache:false`
  (`bigquery.ts:1137-1144`, `:1213`).
- `first-party` panels always pass `cache: true` and never `forceRefresh`
  (`dashboard-panel-query.ts:461-476`). On Postgres they use a 5 minute L1
  plus `first_party_analytics_cache` table cache
  (`server/lib/first-party-analytics-cache.ts:15`, `first-party-analytics.ts:1743-1756`).
  On the BigQuery backend they skip that cache and call `runQuery`
  (`first-party-analytics.ts:1624-1668`,
  `first-party-analytics-backend.ts:1591-1604`), so they get the 24 h
  BigQuery cache and **no way to bypass it**. This is the most likely cause of
  the stale signup count Refresh did not fix.
- `program` panels call `runDataProgram`, which already returns `asOfMs`,
  `stale` and `cacheHit` and accepts `forceRefresh`
  (`packages/core/src/data-programs/execute.ts:54-63`, `:96`, `:416-419`).
  `runProgramPanel` drops all three, never passes `forceRefresh`, and when the
  run fails it **returns `lastGoodRun` rows as if they were current**
  (`dashboard-panel-query.ts:355-408`, fallback `:382-388`). That is a failure
  presented as a normal result.
- No result carries a time. `QueryResult` has `cached?: boolean` only
  (`bigquery.ts:790-797`); both cache tables already store `created_at`
  (`bigquery.ts:669-678`; `server/plugins/db.ts:1136-1145`), but the L2 reads
  select only `result` (`bigquery.ts:648-657`,
  `first-party-analytics-cache.ts` `getL2`).
- `inspect-dashboard-panel` (the agent's way to see what a panel renders)
  accepts `forceRefresh` (`actions/inspect-dashboard-panel.ts:108-115`) and
  returns `PanelVerification`, which has no time field
  (`server/lib/dashboard-panel-verification.ts:55-87`).

## 3. Build

1. **Measure the reload first.** With `pnpm --filter analytics dev`, open
   (a) the seeded first-party SQL dashboard and (b) an explorer dashboard, and
   leave each idle and visible for 5 minutes with the network panel recording.
   Count `query-dashboard-panel`, `/api/query`, `/_agent-native/poll` and
   `update-dashboard` requests and their status codes per minute, then repeat
   after changing one filter. Record which query keys refetch (React Query
   devtools or a temporary `queryCache.subscribe` log, removed before
   commit). Put the table in the PR. Fix whatever the measurement shows; the
   steps below cover the candidates in section 2, and any extra cause found
   gets fixed at its source, not with a new special case in the predicate.
2. **Stop the explorer storm.** Exclude `["dashboard-chart"]` and
   `["explorer-config"]` in `shouldInvalidateAnalyticsQueryForAction`
   (`app/root.tsx:106-122`), the same way `["sql-chart"]` is, and drop
   `"action"` from the explorer page's `useChangeVersions` list
   (`explorer-dashboard/index.tsx:327`) so a filter-preference save no longer
   refetches the dashboard. Keep `"dashboards"`. `useMetricsQuery`'s raw
   `fetch` goes to the grandfathered `server/routes/api/query.post.ts`;
   moving it onto an action is a separate cleanup (flag it with a follow-up
   task), not part of this unit.
3. **Track visibility, not just first sight.** In `SqlChartCard`
   (`:285-309`), keep the observer connected and hold `isVisible` state;
   keep `shouldLoadData` latching true after the first sight, as today. Pass
   `isVisible` to `SqlChart`, and pass
   `enabled: shouldQuery && (isVisible || !hasData)` to `useSqlQuery`. React
   Query refetches a stale query when its observer goes from disabled to
   enabled, so a panel scrolled back into view refetches only if older than
   its `staleTime`, and an off-screen panel never refetches. Turn on
   `refetchOnWindowFocus: true` for panels only: React Query refetches only
   enabled and stale queries, which are the visible, stale ones. Keep
   `refetchInterval` unset. Treat the expanded full-screen dialog
   (`SqlChartCard.tsx:787-806`) as visible.
4. **A time on every result.** Add to `DashboardPanelQueryResult`
   (`server/lib/dashboard-panel-query.ts`) the fields
   `asOf: string | null` (ISO), `cache: "hit" | "miss" | "bypassed"`, and
   `staleFallback?: { reason: string; failedAt: string }`.
   - `bigquery.ts`: stamp `computedAt` on a fresh result before it is cached
     (`finishCacheQuery`, `:659-700`, and L1 `setL1`). On a hit, return the
     stored `computedAt`. For rows written before this change, select
     `created_at` in `getL2` and use it. If neither exists, return
     `asOf: null`, never `now`.
   - `first-party-analytics-cache.ts`: same, from L1 `createdAt` and L2
     `created_at`.
   - `runProgramPanel`: map `asOfMs` and `cacheHit`; on failure with
     `lastGoodRun`, return its rows with `asOf` from `lastGoodRun.asOfMs` and
     `staleFallback: { reason: result.error.code, failedAt: now }`.
   - GA4, Amplitude, Prometheus and demo: `asOf` is the time the call
     returned and `cache: "miss"`, unless the helper caches. Check each
     helper (`runGa4Panel`, `runAmplitudePanel`, `runPrometheusPanel`) before
     claiming that.
5. **Refresh bypasses every cache.** In `app/lib/sql-query.ts:157-159`, send
   `forceRefresh` for every source. In `runDashboardPanelQuery`, pass it to
   `queryFirstPartyAnalytics` as a new `forceRefresh` option: on Postgres,
   skip the cache read and write the new result; on the BigQuery backend,
   pass `forceRefresh` to `runQuery`. Pass it to `runDataProgram` with
   `triggeredBy: "manual_refresh"` (already a valid trigger,
   `packages/core/src/data-programs/execute.ts:80-85`). Return
   `cache: "bypassed"`. The existing refresh-token logic in `useSqlQuery`
   (`sql-query.ts:205-260`) already sends `forceRefresh` once per click; keep
   it.
6. **Shorter cache for first-party events on BigQuery.** Add an optional
   `cacheTtlMs` to `RunQueryOptions` (`bigquery.ts:799-803`) and have the
   first-party BigQuery path pass 15 minutes. The warehouse `bigquery` source
   keeps 24 h. This keeps the cost saving of the cache while bounding how old
   a first-party number can be without a click.
7. **Show it.** In `SqlChartCard`'s header, after the title and before the
   menu, render muted `text-xs` `sqlDashboard.asOf` using `useFormatters()`
   (time only for today, short date and time otherwise), with a shadcn
   `Tooltip` holding the full time and, for a cached result,
   `sqlDashboard.asOfCachedTooltip`. Hide the label when the card is narrower
   than its title needs (CSS container query or the existing width prop);
   the tooltip on the Refresh item still carries it. For a `staleFallback`,
   show an amber `IconAlertTriangle` beside the time with
   `sqlDashboard.staleFallback` in the tooltip, and keep the Refresh menu
   item (`SqlChartCard.tsx:742-745`). For `asOf: null`, render no label (see
   D4). Plumb the fields through `executeSqlQuery`'s return
   (`sql-query.ts:183-186`, add `asOf`, `cache`, `staleFallback` to
   `SqlQueryResult`).
8. **Agent sees the same.** Add `asOf`, `cache` and `staleFallback` to
   `PanelVerification` (`dashboard-panel-verification.ts:55-87`) from the
   runner result, and include them in `describePanelOutcome` for
   `inspect-dashboard-panel` ("renders 14 rows as of 2026-10-13T14:02Z from
   cache"). Update `.agents/skills/dashboard-management/SKILL.md` "Reading
   Panel State" (`:510-527`): when a user says a number is stale, call
   `inspect-dashboard-panel` with `forceRefresh: true`, report the new
   `asOf`, and tell them to click Refresh on the panel to see it.
9. **Changelog.** `agent-native changelog add "Dashboard panels show when their numbers are from, refresh only when visible and out of date, and Refresh always loads the latest data." --type improved`.

Four areas: **UI** (steps 2, 3, 7), **actions** (steps 4, 5 extend
`query-dashboard-panel`'s result and `inspect-dashboard-panel`'s; no new
action), **skills** (step 8, plus `.agents/skills/performance` needs no edit;
read it and `real-time-sync` before step 2 and 3), **application state**
(does not apply: freshness is a property of the server cache, which the
agent reads through `inspect-dashboard-panel`; writing per-panel times into
`application_state` would add a write per panel load).

## 8. Defaults for open questions

- **D1.** No background interval refresh on dashboards. They are
  read-mostly; the `real-time-sync` skill says refresh on focus or
  navigation. A per-dashboard "auto refresh" is a later, opt-in feature.
  *Reviewer may change.*
- **D2.** Freshness window stays the existing 5 minute client `staleTime`
  for every source. *Reviewer may change.*
- **D3.** First-party events on BigQuery cache for 15 minutes; warehouse
  BigQuery stays 24 h. *Reviewer may change.*
- **D4.** A result with no known time shows no "As of" label rather than a
  guessed time. Such rows only exist in caches written before this change and
  expire within 24 h. *Reviewer may change.*
- **D5.** Explorer dashboards get the reload fix only, not the "as of"
  label; they are the legacy path. *Reviewer may change.*
- **D6.** The agent has no separate "refresh the user's panel" action;
  `inspect-dashboard-panel` with `forceRefresh` refreshes the server cache,
  and the user's next Refresh or stale refetch shows it. *Reviewer may
  change.*

## 9. Do not

- No behavior changes outside this unit: no change to which SQL runs, the
  first-party scoping, byte limits, or verification rules.
- Schema: none expected (both cache tables already have `created_at`); any
  change additive only.
- No new `/api` routes for app data; extend `query-dashboard-panel`.
- No raw `fetch` added in client code.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value: a
  failed program run with old rows is a `staleFallback`, a missing time is
  `null`, never `now`.
- No large payloads in SQL: do not add columns to the cache tables for the
  result rows; `computedAt` lives inside the existing cached JSON.
- Do not add a manual polling loop or a second `EventSource`.
