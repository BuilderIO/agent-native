# 8.4c Reactive cell graph: auto-run, stale cells and a Graph view

Lane E (Holy-shit features). Size M. Gated: the run mode control, the stale
and waiting cell states and the Graph view are new UI; build only after the
"Notebook: graph" and "Notebook: manual run" screens in
`prototypes/analytics-operators/` are signed off. Where the signed-off
prototype differs from this brief, the prototype wins.

Depends on: 7.1b, 7.2b, 8.4b1 (no-code inputs are graph edges), 7.5 (input
cells are graph nodes). Blocks: 8.4g1 (scheduled runs walk the graph).

Paths are relative to `templates/analytics/` unless they start with
`packages/`.

## 1. Goal

In a notebook, changing an input or editing a cell reruns exactly the cells
that depend on it, top to bottom, and nothing else. While an upstream cell
runs, the cells below it say they are waiting for it instead of showing old
numbers as if they were current; when an upstream cell fails, its dependents
say which cell failed. An author working on an expensive notebook can switch
to Manual: edits mark cells stale and nothing runs until they press Run. A
Graph view draws the notebook as boxes and arrows (inputs, cells, which cell
reads which), and clicking a box scrolls to that cell.

## 2. What the code does today

- Filter changes already rerun only the panels whose SQL changes: each
  `PanelCell` computes `resolvedSql` from the panel and `effectiveVars`
  (`app/pages/adhoc/sql-dashboard/index.tsx:351-359`), and `SqlChart` keys its
  query on it: `useSqlQuery(["sql-chart", dashboardId || panel.id, sql, panel.source], ...)`
  (`app/components/dashboard/SqlChart.tsx:1235-1248`). A new key means a new
  fetch; an unchanged key keeps its cached result (`staleTime` 5 minutes,
  `app/lib/sql-query.ts:320`).
- Off-screen panels wait: `enabled: shouldQuery && (isVisible || !hasShownResult)`
  (`SqlChart.tsx:1242`) with an `IntersectionObserver` in `SqlChartCard.tsx:465-498`.
- `panelUsesFilters` and `panelSqlTokenNames` find which filters a panel's SQL
  reads (`app/pages/adhoc/sql-dashboard/filter-vars.ts:254`).
- The closest thing to a dependency set is verification's `touchedPanelIds`,
  whose `affected` list is panels whose resolved SQL changed because a filter
  or variable changed (`server/lib/dashboard-panel-verification.ts:253-287`).
  There is no `dependsOn`, `upstream` or `downstream` concept for panels.
- 7.2b (not built; brief `tasks/7.2b-chained-cells.md`) adds explicit inputs
  in the `cells` descriptor and requires inputs to sit above, so the graph is
  acyclic by construction; its payload embeds each input's resolved query, so
  an upstream SQL change already changes a downstream query key.
- 7.5 (not built) makes input cells render filters; 8.4b1 makes no-code cells
  read one input.

## Plan corrections

- "A cell reruns when an upstream cell or input changes" is mostly what React
  Query keys already do once 7.2b lands. The gaps are visibility (a cell does
  not show it is waiting on, or blocked by, an upstream cell), a manual mode,
  and the graph itself. This unit adds those, not a second scheduler: query
  execution stays in `SqlChart` and `useSqlQuery`.

## 3. Build

1. **Graph model.** New `shared/notebook-graph.ts`:
   - `buildNotebookGraph(config): { nodes: { id; kind: "input" | "sql" | "chart" | "text" | "no-code" | "python"; title; index }[]; edges: { from; to; via: "cells" | "filter" }[] }`.
     Edges come from the `cells` descriptor inputs (7.2b), `config.noCode.input`
     (8.4b1), and filter tokens (`panelSqlTokenNames`) mapped to the input
     cell bound to that filter (7.5). Unbound filters appear as one
     "Notebook filters" node.
   - `downstreamOf(graph, ids)` and `upstreamOf(graph, id)`.
   - A cycle cannot occur (inputs must be above), but the builder asserts it
     and throws a typed error rather than looping.
2. **Run state, per notebook, client side.** New
   `app/pages/adhoc/notebook/use-notebook-run-state.ts`: subscribes to each
   cell's query status (the `useSqlQuery` result `NotebookBody` already has)
   and derives for each cell `ready | running | waiting(upstreamId) | blocked(upstreamId) | stale | error`.
   `waiting` and `blocked` come from `upstreamOf`: a cell whose input is
   running is waiting; whose input failed is blocked. A blocked cell does not
   send its query (its `enabled` is false) and shows "{{cell}} failed, so this
   cell didn't run" with a Go to cell button. This is visibility, not a new
   executor.
3. **Run mode.** Add `runMode?: "auto" | "manual"` to `SqlDashboardConfig`
   (root key; validated in `collectDashboardConfigIssues`, any other value is
   an issue). Absent is `auto`.
   - Auto: today's behavior.
   - Manual: each cell keeps the query key it last ran with. Edits and input
     changes compute the new key but do not enable the query; the cell shows
     `stale` with "Out of date" and the notebook header's Re-run (7.1b)
     becomes Run {{count}} stale cells. Run on a cell runs it and its
     downstream (`downstreamOf`), in order. Store the last-run keys in memory
     only; a reload in manual mode shows every query cell stale until Run.
4. **Graph view.** A Graph item in the notebook's actions menu (7.1b, text
   only) opens a shadcn `Sheet` on the right with an SVG of the graph: one
   column per depth (layered by longest path from a root), nodes as rounded
   rectangles with the cell number, title and kind label, edges as lines with
   arrowheads, tinted by run state through theme tokens: amber with
   `IconAlertTriangle` for stale, waiting, blocked and failed cells, muted for
   ready ones. No red: nothing is destroyed. Clicking a node scrolls the cell into
   view and selects it. No graph library: the layout is a small pure function
   `layoutNotebookGraph(graph)` in `shared/notebook-graph.ts`.
5. **Actions.** `get-notebook-graph` (read-only, `http: { method: "GET" }`):
   `{ dashboardId }` returns the graph (nodes and edges, no SQL) through
   `getDashboard` with access checks. The agent uses it to answer "what feeds
   this chart?" and to know what a cell edit will rerun. Run mode is set with
   `mutate-dashboard` `setDashboard` `{ runMode }`.
6. **Application state.** `selected-object` for a notebook cell adds
   `upstreamIds` and `downstreamIds` (ids only, at most 20 each) so "what
   uses this?" needs no call. The Graph sheet open state is local UI state.
7. **Skills.** `.agents/skills/notebooks/SKILL.md`: a "Dependencies and run
   mode" section: how edges are found, that editing a cell reruns its
   downstream in auto mode, that manual mode leaves cells stale until the user
   runs them, and `get-notebook-graph`.
8. **Changelog.** `agent-native changelog add "Notebook cells rerun when what they read changes, with a manual mode and a Graph view" --type added`.

## 8. Defaults for open questions

- [Default] Edges are explicit (descriptor inputs, no-code input, filter
  tokens), never inferred by scanning SQL for cell names.
- [Default] Manual mode remembers last-run keys in memory only.
- [Default] Run mode is saved on the notebook, so it applies to every viewer.

## 9. Do not

- Do not build a second query scheduler; React Query stays the executor.
- Do not show a cached upstream result as current while its input reruns.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
