# 1.4b Fresh, cheap panels: measure and attribute first-party read cost

Lane A (Reliability). Size M. Not gated.

The plan says "read from cached rollups instead of the raw events table". The
code shows that is not a rewrite of existing panels: the existing rollups
cannot answer them, and on the BigQuery backend the rollup tables are not
created by this template and may be views over the raw table (section 2).
So PR 1.4's cost half is split into three units:

- **1.4b (this unit):** measure which reads cost what, attribute them to a
  dashboard, panel and caller, find out what the BigQuery rollup tables
  actually are, and give the agent the guidance it needs. No panel SQL
  changes.
- **1.4c:** an active-user daily table the expensive panels can read, in
  Postgres and as an optional BigQuery table.
- **1.4d:** move the expensive panels onto it, each proven equal to the raw
  result.

1.4c and 1.4d are built only if this unit's numbers show the panels they
target are still the top cost after 1.4a's cache fixes (D1).

## 1. Goal

The team can see, per day, how many bytes first-party panel reads scan, and
which dashboard, panel and caller (someone viewing the page, an agent edit
check, a scheduled report, an alert, an agent inspect) caused each one, and
whether it was a cache hit. The health action says whether the BigQuery
rollup tables are real tables or views. The agent prefers rollups when it
writes a new first-party panel that a rollup can answer, and is told when it
cannot.

## 2. What the code does today

All paths relative to `templates/analytics/`.

- **Rollups exist.** Postgres has `analytics_event_daily_rollups` (tenant,
  date, event name, app, template, count) and `analytics_user_days` (tenant,
  date, user key) (`server/db/schema.ts:276-289`, `:628-635`), written in the
  same transaction as each ingest batch (`server/lib/first-party-analytics.ts:951-953`,
  `server/lib/first-party-analytics-rollups.ts:67-181`) and backfilled by
  `server/jobs/analytics-rollup-backfill.ts`. Both are allowed in agent and
  panel SQL (`first-party-analytics.ts:141-151`), and the query action already
  tells the agent to prefer them (`actions/query-agent-native-analytics.ts:55-64`).
- **But the panels that cost the most cannot use them.** The seeded
  first-party dashboard has 48 panels; 43 read `analytics_events`
  (`seeds/dashboards/agent-native-templates-first-party.json`). Of those, 30
  bind the internal-email filter (`'{{emailFilter}}'` on `user_id`, see
  `server/lib/first-party-metric-catalog.ts:214-222`), and every one of the
  remaining 13 reads `user_id`, `signed_in` or `properties`. Neither
  rollup carries a user email, `signed_in` or properties, so 0 of 43 can be
  rewritten onto the existing rollups. The metric catalog has 72 raw reads
  and none on rollups (`server/lib/first-party-metric-catalog.ts`), and the
  canonical repair SQL is the same shape
  (`server/lib/canonical-first-party-dashboard-repair.ts:587-602`).
- **On BigQuery the rollups are external.** After cutover, Postgres stops
  receiving first-party events and rollups (description of
  `actions/migrate-first-party-analytics-to-bigquery.ts:116-117`). Ingest
  inserts only raw rows into BigQuery (`server/lib/first-party-analytics-backend.ts:439-455`).
  Queries map `analytics_event_daily_rollups` and `analytics_user_days` to
  `<table>_daily_rollups` and `<table>_user_days`
  (`first-party-analytics-backend.ts:263-273`, `:1299-1304`), which the
  template only checks for by name in `INFORMATION_SCHEMA.TABLES`
  (`:1620-1665`) and never creates. The `data-querying` skill says these are
  "served by partitioned BigQuery data and views"
  (`.agents/skills/data-querying/SKILL.md:26-31`). If they are views over the
  raw table, a rollup read on BigQuery scans raw data anyway.
- **Cost is invisible per panel.** `queryFirstPartyAnalyticsInBigQuery`
  returns rows, schema and truncated, and drops `bytesProcessed` and `cached`
  (`first-party-analytics-backend.ts:1610-1614`). The pressure ledger records
  only slow or failed queries, never bytes
  (`server/lib/first-party-analytics-health.ts:198-204`), classified as
  `raw-events`, `rollups`, `mixed`, `session-replay` or `other` (`:178-196`).
  `query-dashboard-panel` takes only `source`, `query` and `forceRefresh`
  (`actions/query-dashboard-panel.ts:14-18`), so a read cannot be tied to a
  dashboard or panel. The browser keeps a per-tab byte counter only
  (`app/lib/sql-query.ts:179-181`, `app/lib/cost-tracker.ts`).
- **Who reads.** The page (`query-dashboard-panel`), agent edit checks and
  `inspect-dashboard-panel` (`server/lib/dashboard-panel-verification.ts`
  through `runResolvedPanel`), scheduled reports
  (`server/lib/dashboard-report-render.ts:118`) and alerts
  (`server/lib/analytics-alerts.ts`, which reads `analytics_events`
  directly) all reach `runDashboardPanelQuery` or the first-party query path,
  and so share its cache.

## 3. Build

1. **Find out what the BigQuery tables are.** In
   `get-first-party-analytics-health` (`actions/get-first-party-analytics-health.ts`),
   when the sink is BigQuery, read `table_name, table_type` from the same
   `INFORMATION_SCHEMA.TABLES` query the validator uses
   (`first-party-analytics-backend.ts:1646-1651`) and return
   `bigqueryTables: [{ name, type: "BASE TABLE" | "VIEW" | "MATERIALIZED VIEW" | "missing" }]`.
   A failed read returns `bigqueryTables: { status: "unreadable", reason }`,
   not an empty list. Update the action description to mention it.
2. **Carry cost out of the BigQuery path.** Return `bytesProcessed` and
   `cached` from `queryFirstPartyAnalyticsInBigQuery`
   (`first-party-analytics-backend.ts:1610-1614`) and from
   `queryFirstPartyAnalytics`, and pass them through
   `runDashboardPanelQuery` (1.4a adds `cache` and `asOf` on the same result;
   reuse its `cache` field rather than a second one).
3. **Attribute reads.** Add optional `dashboardId` and `panelId` to
   `query-dashboard-panel`'s schema and send them from `executeSqlQuery`
   (`app/lib/sql-query.ts:138-187`; `SqlChart` has both). Add a
   `caller: "page" | "verification" | "inspect" | "report" | "alert" | "agent"`
   to the runner options, set by each caller listed in section 2. On every
   first-party or BigQuery read that was not a cache hit, call
   `track("analytics_panel_read", { source, query_class, bytes, cache,
   caller, dashboard_id, panel_id, duration_ms })` with
   `@agent-native/core/tracking` (the same call `mutate-dashboard` uses,
   `actions/mutate-dashboard.ts:656-667`). Never send SQL text or row data.
   Use `classifyFirstPartyAnalyticsQuery` for `query_class`.
4. **A daily cost view for the agent.** Add a summary to
   `get-first-party-analytics-health`: bytes and read counts for the last 7
   days grouped by `caller` and by the top 10 `dashboard_id`/`panel_id`, read
   from wherever `track` lands. First check where core tracking delivers in
   this app (`packages/core/src/tracking/registry.ts`); if the events land in
   this app's own first-party `analytics_events`, query that with a bounded
   date range; if they go only to an external provider, return
   `costSummary: { status: "unavailable", reason }` and say in the PR where
   to read it instead. Do not build a second store for it.
5. **Agent guidance.** In `server/lib/dashboard-panel-verification.ts`, when
   a touched first-party panel's SQL reads `analytics_events` and its only
   columns are `event_date`, `event_name`, `app`, `template` and a `COUNT(*)`,
   add a `hint`: "This panel can read analytics_event_daily_rollups instead of
   analytics_events at a fraction of the cost." (Use
   `classifyFirstPartyAnalyticsQuery` and the agent SQL parser the module
   already imports; no regex over SQL.) In
   `.agents/skills/dashboard-management/SKILL.md` "First-Party User Metrics"
   (`:538-561`), add the rule: count panels read the daily rollup; panels that
   filter on email, `signed_in` or properties must read the raw table with a
   bounded time filter until 1.4c's table exists. Update the BigQuery note in
   `.agents/skills/data-querying/SKILL.md:26-31` with what step 1 found.
6. **Report.** Run the measurement for a week on the deployed app (D2) and
   write the result into the PR or a follow-up comment: top 10 panels by
   bytes, share by caller, cache hit rate, and the table types from step 1.
   That decides whether 1.4c and 1.4d are built.

Four areas: **actions** (steps 1 to 4 extend `get-first-party-analytics-health`
and `query-dashboard-panel`), **skills** (step 5), **UI** (only the two extra
arguments sent from `executeSqlQuery`; no visible change), **application
state** (does not apply: cost is server telemetry, not view state).

## 4. Copy

No user-facing strings. The verification `hint` and action descriptions are
agent-facing and stay out of `app/i18n/*`. No em dashes in them.

## 5. Tests

- `actions/get-first-party-analytics-health` spec (add beside the action):
  returns table types from a mocked `INFORMATION_SCHEMA` result, `missing`
  for an absent table, and `unreadable` when the read throws.
- `server/lib/first-party-analytics-backend.spec.ts`: `bytesProcessed` and
  `cached` survive `queryFirstPartyAnalyticsInBigQuery`.
- `actions/query-dashboard-panel.spec.ts`: a cache miss tracks one
  `analytics_panel_read` with the given dashboard and panel ids and no SQL;
  a cache hit tracks nothing.
- `server/lib/dashboard-panel-verification.spec.ts`: a count-only raw panel
  gets the rollup hint; a panel with the email filter does not.
- No source-reading tests.

## 6. Verify

```bash
cd templates/analytics
pnpm exec vitest --run actions/query-dashboard-panel.spec.ts \
  server/lib/first-party-analytics-backend.spec.ts \
  server/lib/dashboard-panel-verification.spec.ts
pnpm action get-first-party-analytics-health
pnpm guards
```

Load the seeded first-party dashboard in the browser once with the dev
server and confirm one `analytics_panel_read` per cache miss and none on
reload. Cannot be verified locally: the BigQuery table types and real byte
counts; both need the production BigQuery project and a week of traffic
(needs the plan owner, D2).

## 8. Defaults for open questions

- **D1.** 1.4c and 1.4d are built only if, after 1.4a, active-user panels
  (DAU, WAU, new vs recurring, retention) are still more than half of
  first-party bytes. Otherwise they are dropped and the cache is the fix.
  *Reviewer may change.*
- **D2.** One week of measurement on the deployed app. Turning it on needs
  the change deployed, which follows the normal ship path.
  *Reviewer may change.*
- **D3.** Attribution is a tracked event, not a new SQL table, so no new
  storage and no retention policy. *Reviewer may change.*

## 9. Do not

- No behavior changes outside this unit: no panel SQL is rewritten here, and
  no cache TTL changes beyond 1.4a.
- Schema: none.
- No new `/api` routes; extend the two actions.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value:
  unreadable table types and an unavailable cost summary are typed states,
  never an empty list.
- No large payloads in SQL or in tracked events: no SQL text, no rows, no
  user emails in `analytics_panel_read`.
- Do not name a company, customer or internal domain in skills or
  descriptions; say "the internal-email filter".
