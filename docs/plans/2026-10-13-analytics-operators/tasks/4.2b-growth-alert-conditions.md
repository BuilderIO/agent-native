# 4.2b Growth alert conditions: drops, floors and changes

Lane D (Growth). Size M. Not gated: it adds fields to the existing alert
dialog. The 4.1a prototype shows the dialog for review, but this unit does not
wait for sign-off unless the reviewer asks.

## 1. Goal

A growth team can be told when something good stops happening, not only when
something bad spikes: "fewer than 5 signups in the last hour", "checkouts down
30% from the same hour last week", "activation events up 50% from yesterday".
The alert compares against the same window yesterday or last week, ignores
changes on tiny numbers, and says "Baseline too small" instead of a false OK
when there is not enough history to judge.

## 2. What the code does today

- A rule can only fire on "at least": `evaluateAnalyticsAlertRuleRows` sets
  `triggered: observedValue >= rule.threshold`
  (`server/lib/analytics-alerts.ts:938-958`), and the BigQuery batch path does
  the same with its counts (`:1202`). There is no "at most" and no comparison
  with an earlier window, so "signups dropped" cannot be expressed.
- `threshold` must be at least 1 (`actions/save-analytics-alert-rule.ts:48`,
  `server/lib/analytics-alerts.ts:468`), so "no signups at all" (at most 0)
  cannot be expressed either.
- Rule columns: `server/db/schema.ts:677-710`. Statuses are `ok`,
  `triggered`, `cooldown`, `error`, `running` (`:702-704`). Migrations are
  versioned entries in `server/plugins/db.ts` (alert columns were added with
  `ALTER TABLE analytics_alert_rules ADD COLUMN IF NOT EXISTS` at `:1015`,
  `:1020`).
- The notification body is server English built in `alertBody`
  (`server/lib/analytics-alerts.ts:1743-1753`).
- UI: the alert dialog (`app/pages/settings/AlertRulesSettingsCard.tsx:846-960`)
  has Threshold mode, Threshold, Distinct by, Window minutes and Cooldown
  minutes. The rule list summarizes the condition with `formatThreshold`
  (`:1095-1111`) and the status with `statusLabel` / `statusDotClass`
  (`:1060-1080`). Invalid numbers are silently replaced:
  `parseInteger(value, fallback)` (`:198-201`) turns a typo in Threshold into
  1 on save (`:379`).
- 4.2a adds the hot path, the BigQuery evaluation interval and the pending-row
  merge. Baseline windows are older than the hot window, so they always read
  BigQuery on the BigQuery sink.

## 3. Build

1. Schema (additive). Add to `analytics_alert_rules` in
   `server/db/schema.ts:677-710` and a new versioned migration in
   `server/plugins/db.ts`:
   - `comparison TEXT NOT NULL DEFAULT 'at_least'` with values `at_least`,
     `at_most`, `drop_vs_baseline`, `rise_vs_baseline`.
   - `baseline_offset_minutes INTEGER` (null unless the comparison is a
     change; allowed values 1440 and 10080).
   - `min_baseline_count INTEGER` (null means 20).
   - Allow `last_status = 'insufficient_baseline'` (text column; add the value
     to the TypeScript enum at `:702-704`).
   Existing rules keep `at_least`, so nothing they do changes.
2. Library (`server/lib/analytics-alerts.ts`):
   - Extend `AnalyticsAlertRuleInput`, `AnalyticsAlertRule` and `rowToRule`
     (`:50-98`, `:388-416`).
   - Validation in `saveAnalyticsAlertRule` (`:452-547`): for `at_least`
     keep threshold 1 or more; for `at_most` allow 0 or more; for the two
     change comparisons threshold is a percent, 1 to 100 for a drop and 1 to
     1,000 for a rise, and `baselineOffsetMinutes` is required. Reject, do
     not clamp.
   - One `decideAlert(rule, current, baseline?)` function used by both the row
     path and the batch path, returning `triggered`, `ok` or
     `insufficient_baseline`, plus `changePercent`. A change rule with a
     baseline below `minBaselineCount` returns `insufficient_baseline` and
     sends nothing.
   - Baseline counts. Row path: load the shifted window
     `[windowStart - offset, windowEnd - offset]` with the same loader 4.2a
     uses. Batch path: add a shifted-window candidate branch and
     `baseline_count_<i>` / `baseline_distinct_<i>` aggregates to
     `buildBigQueryAnalyticsAlertBatchQuery` (`:1052-1156`), and read them in
     `normalizeBigQueryAlertAggregate` (`:1202`). Never default a missing
     baseline aggregate to 0: throw, as the existing count parsing does.
   - Treat change rules as BigQuery-backed for 4.2a's 5-minute interval on
     the BigQuery sink.
   - Status: `markRuleStatus` writes `insufficient_baseline` with
     `lastError: null`.
   - `alertBody` (`:1743-1753`) and notification metadata (`:854-890`): say
     what was compared, for example "12 signup events in the last 60 minutes,
     down 40% from 20 at the same time last week (threshold: 30% drop)." Add
     `comparison`, `baselineValue`, `changePercent` and `baselineOffsetMinutes`
     to metadata and to the incident's sample payload. Do not add incident
     columns.
3. Actions:
   - `actions/save-analytics-alert-rule.ts`: add `comparison`,
     `baselineOffsetMinutes` (1440 or 10080) and `minBaselineCount` with
     `.describe()` text that maps requests to fields: "fewer than N" is
     `at_most`; "dropped X% versus last week" is `drop_vs_baseline` with
     10080. Change `threshold` to `.min(0)` and let the library enforce the
     per-comparison range.
   - `actions/list-analytics-alert-rules.ts` returns the new fields through
     `rowToRule`; no code change beyond types.
4. UI (`app/pages/settings/AlertRulesSettingsCard.tsx`):
   - Add a Fire when `Select` above Threshold with the four comparisons.
   - Threshold's label follows the comparison: Threshold for counts, Change
     (%) for the change comparisons.
   - For change comparisons, show Compared with (`Select`: Same time
     yesterday, Same time last week) and Minimum baseline count (`Input`, with
     an info `Tooltip` for the hint).
   - Validate these fields and show the field error inline; do not use
     `parseInteger` with a fallback for any new field.
   - `formatThreshold` (`:1095-1111`) uses the new summary keys, one full
     sentence per case (no concatenated fragments).
   - `statusLabel` and `statusDotClass` (`:1060-1080`) handle
     `insufficient_baseline` with the muted dot, not amber or red.
5. Skills and instructions: `AGENTS.md:25` gains one clause: alerts can fire
   on at least, at most, or a drop or rise against yesterday or last week. The
   action descriptions carry the rest.
6. Application state: none. The Alerts tab is already a navigable settings
   page (`buildSettingsRoute("app", "alerts")`, per
   `.agents/skills/dashboard-ops/SKILL.md:105-108`).
7. Changelog: `agent-native changelog add "Alerts can fire when a count falls below a floor or changes against yesterday or last week" --type added`.

## 8. Defaults for open questions

- [Default, reviewer can change] Baselines are the same window yesterday or
  the same window last week, nothing custom.
- [Default] Minimum baseline count 20.
- [Default] "Baseline too small" is its own status, shown with the muted dot.
- [Default] Drops are capped at 100%; rises at 1,000%.
- [Default] Change rules on the BigQuery sink run at most every 5 minutes
  (4.2a's interval).
- [Default] Leave the existing `parseInteger` fallback on old fields alone in
  this unit (behavior change outside scope); flag it to 1.5.

## 9. Do not

- Do not change how existing `at_least` rules evaluate or notify.
- No new incident columns.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
