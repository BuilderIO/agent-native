# 1.7b Request edit access on dashboards

Lane A (Reliability). Size M. Split from plan unit 1.7; 1.7a covers shared
chats.

## 1. Goal

Two people get a way to ask instead of a dead end:

- Someone who can **view** a dashboard but not edit it (an org-visible or
  Viewer-shared dashboard) sees **Request edit access** in the dashboard
  header. The owner and admins get an inbox notification and an email, and
  approve or decline in one click. After approval the requester can edit
  without reloading.
- Someone who opens a dashboard link they **can't open at all** sees a "You
  don't have access" screen with **Request access**, instead of today's blank
  dashboard.

Both go through the framework's existing access request flow, so the agent,
the Share panel and the email all agree.

## 2. What the code does today

Paths outside `templates/analytics/` are repo-relative.

**The framework already has access requests, but only for people who can't
open a resource.**

- Registrations opt in with `accessRequests: true`
  (`packages/core/src/sharing/registry.ts:118-123`). Content is the only
  adopter (`templates/content/server/db/index.ts:23`).
- `resolveLinkStatus` offers a request only when the viewer's state is
  `denied` (`packages/core/src/sharing/access-requests.ts:117-135`).
- `requestResourceAccess` returns `{ state: "allowed" }` and sends nothing when
  the viewer can already open the resource, whatever their role
  (`access-requests.ts:357-376`, the check is at `373`). So a viewer can't ask
  to become an editor today.
- The request row records `grantedRole` on approval but has **no requested
  role** (`packages/core/src/sharing/access-request-store.ts:15-37`, DDL at
  `45-63`). Approval takes a role and defaults to `viewer`
  (`packages/core/src/sharing/actions/approve-resource-access-request.ts:12-14`).
- The request, approve and decline actions are `agentTool: false`,
  `mcpTool: false` because they email other people
  (`packages/core/src/sharing/actions/request-resource-access.ts:17-21`).
- Requests are reviewed at `/access-requests/:id`
  (`access-requests.ts:66-68`). The default template mounts
  `AccessRequestApprovalPage` there
  (`packages/core/src/templates/default/app/routes/access-requests.$requestId.tsx`).
  Analytics has no such route (`templates/analytics/app/routes/` has no
  `access-requests.*` file).
- Managers also see pending requests inside the Share dialog when
  `controller.canManage` (`packages/toolkit/src/app/sharing/ShareDialog.tsx:89-90`).
- The client gate hook is `useResourceAccessGate`
  (`packages/core/src/client/sharing/useResourceAccessGate.ts:97-121`), which
  calls `get-resource-access-status` and `request-resource-access` through
  `useActionQuery` / `useActionMutation`. The screen is `ResourceAccessScreen`
  (`packages/toolkit/src/app/sharing/ResourceAccessScreen.tsx`), already
  localized under `agentChat.accessGate.*`. Content wires both in
  `templates/content/app/components/editor/DocumentAccessScreen.tsx:1-60`.

**Analytics dashboards**

- The `dashboard` registration has no `accessRequests` flag
  (`server/db/index.ts:37-47`).
- `fetchDashboard` calls `get-sql-dashboard` and turns **any** failure into
  `null` (`app/pages/adhoc/sql-dashboard/index.tsx:504-566`; the catch is at
  `562-565`). A `null` dashboard renders `<BlankDashboard />`
  (`index.tsx:2391-2399`). A denied viewer, a missing id and a network error
  all look like an empty dashboard. That is the coercion the repo rules ban.
- The page already knows the viewer's role: `get-sql-dashboard` returns
  `role`, `canEdit`, `canManage` (`index.tsx:558-561`), and
  `canEdit = resourceCanEdit(resourceAccess)` (`index.tsx:705`, helper in
  `app/lib/resource-access.ts:14-24`). Edit controls hide when `!canEdit`.
- The header renders `ShareButton` for `dashboard` (`index.tsx:2042-2047`).

## 3. Build

1. **Core: let a viewer request a stronger role.** In
   `packages/core/src/sharing/`:
   - `access-request-store.ts`: add a nullable `requested_role TEXT` column.
     Use an additive `ALTER TABLE resource_access_requests ADD COLUMN IF NOT EXISTS requested_role TEXT`
     next to the existing `ensureTableExists` call, and add `requestedRole:
     ShareRole | null` to `AccessRequestRow`. `null` means "access", which is
     every existing row.
   - `access-requests.ts`:
     - `requestResourceAccess` takes optional `role` (`"commenter" | "editor"`).
       If `role` is set and the viewer's state is `allowed` with a role that
       does not satisfy it (`roleSatisfies`), open the request with
       `requestedRole: role`. If the viewer already satisfies it, return
       `{ state: "allowed" }` as today. Without `role`, behavior is unchanged.
       Reuse the same row, limits, cooldown and delivery code. Do not add a
       second request path.
     - `resolveLinkStatus` returns, for `allowed` viewers on a registration
       with `accessRequests`, `canRequestEdit: boolean` and their open edit
       request if any. It is false when the role already satisfies `editor`.
     - Notification and email copy branch on `requestedRole === "editor"`
       ("asking to edit" instead of "asking for access").
     - `approveAccessRequest`: when the caller passes no role, default to the
       row's `requestedRole ?? "viewer"`.
   - `actions/request-resource-access.ts`: add `role` to the schema
     (optional enum). Keep `agentTool: false`.
   - `actions/approve-resource-access-request.ts`: make `role` optional so
     the default can come from the row. Keep the explicit role winning.
   - `AccessRequestApprovalPage` (toolkit) preselects the requested role.
   - `packages/core/src/email-catalog/system-emails.ts`: add an edit-request
     sample to the `CORE_ACCESS_REQUESTED_EMAIL_ID` preview args.

2. **Analytics: opt dashboards in.** Add `accessRequests: true` to the
   `dashboard` registration in `server/db/index.ts:37-47`. Leave
   `dashboard-folder`, `analysis` and `session-recording` unchanged.
   **[decide]** analyses could follow later.

3. **Analytics: review route.** Add
   `app/routes/access-requests.$requestId.tsx` rendering
   `<AccessRequestApprovalPage landmark />`, copying the core default
   template. Check it renders inside the app shell the way Settings does; if
   the layout needs a pathless wrapper, follow `client-side-routing`.

4. **Analytics: access screen instead of a blank dashboard.**
   - Make `fetchDashboard` stop returning `null` for failures. Return a typed
     result: the dashboard, `not-found` (the action's 404), or an error.
     Keep the report screenshot path's existing throw.
   - Create `app/pages/adhoc/sql-dashboard/DashboardAccessScreen.tsx` modeled
     on Content's `DocumentAccessScreen`: `useResourceAccessGate({ resourceType: "dashboard", resourceId, onAccessGranted: reload })`
     and `ResourceAccessScreen` with `request` wired for `denied`. Show the
     layout-matching skeleton (`DashboardSkeleton`) while status loads. Its
     `actions` slot gets one link back to `/dashboards`.
   - Render it when the fetch says `not-found`. A real error renders the
     existing error state with Retry (or 1.5's plain-language state if it has
     landed), never the blank dashboard.

5. **Analytics: Request edit access in the header.**
   - Next to `ShareButton` (`index.tsx:2042`), when the dashboard loaded and
     `!canEdit` and the status says `canRequestEdit`, render a shadcn
     `Button` with `variant="outline"` (row-action rule), text only, labeled
     **Request edit access**, with a `Tooltip`.
   - Click opens the same note dialog `ResourceAccessScreen` uses. If the
     toolkit does not export it, add a small `RequestAccessDialog` export to
     `packages/toolkit/src/app/sharing/` and use it in both places, rather
     than copying it into analytics. On send, call
     `request-resource-access` with `{ resourceType: "dashboard", resourceId, role: "editor", note }`
     through `useActionMutation`. Show the button as disabled **Edit access
     requested** while a request is open.
   - When the gate's status flips to `editor`, refetch the dashboard so edit
     controls appear (the hook already polls while a request is pending,
     `useResourceAccessGate.ts:114-115`).
   - Optimistic: switch the button to the requested state on click, roll back
     with a toast on failure. The action fails loudly when nobody could be
     notified (`access-requests.ts`, `access_request_undelivered`); show that
     message, never "sent".

6. **Skills and instructions.**
   - Root `.agents/skills/sharing/SKILL.md` and its byte-identical copy
     `templates/analytics/.agents/skills/sharing/SKILL.md`: document
     `role` on `request-resource-access`, `canRequestEdit` on the status, and
     that approval defaults to the requested role.
   - `templates/analytics/.agents/skills/dashboard-management/SKILL.md`: when
     a user who can only view a dashboard asks the agent to change it, the
     agent says so and points them to **Request edit access** in the header.
     The agent cannot send the request itself (the action is not an agent

7. **Application state.** Not applicable: the role is already returned by

8. **Changesets and changelog.** `.changeset/*.md` for `@agent-native/core`

## 8. Defaults for open questions

- **[decide] Only dashboards opt in now.** Analyses, folders and recordings
  stay as they are.
- **[decide] Viewers and commenters can request `editor`.** Requesting
  `admin` is not offered.
- **[decide] The request reuses the one row per resource and requester.** An
  open access request and a later edit request for the same person are the
  same row with a new generation.
- **[decide] Approval defaults to the requested role.** The approver can still
  pick another role.
- **[decide] The access screen links back to `/dashboards`.**

## 9. Do not

- No behavior changes outside this unit. Callers that omit `role` keep today's
  behavior exactly.
- Additive-only schema: one nullable column, no rename, no default rewrite.
- No new `/api` routes for app data; use the framework sharing actions.
- No raw `fetch` from client code; use `useResourceAccessGate`,
  `useActionMutation`.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value: a
  failed dashboard fetch is never a blank dashboard, and a request nobody was
  told about is never shown as sent.
- No large payloads in SQL; the note stays capped at 500 characters
  (`ACCESS_REQUEST_NOTE_MAX_LENGTH`).
- Do not make the request action an agent tool.
