# 1.3b The agent can't claim success that didn't happen: change summary with one-click undo

Lane A (Reliability). Size M. Not gated (section 7 of the plan lists the
surfaces that need a prototype; this card is not one of them).

Second half of the plan's PR 1.3. 1.3a adds the `editOutcome` field and makes
the agent's words match it. This unit shows that outcome in the chat as a
change summary and gives the user a one-click undo.

## 1. Goal

Every dashboard edit the agent makes shows a compact card in the chat, under
the tool call: which panels were added, changed, moved or removed, whether
each one was checked, and the plain reason when it was not. The card has an
Undo button that puts the dashboard back the way it was before that edit, in
one click, without opening history. If someone changed the dashboard after
the edit, Undo refuses and offers history instead of overwriting their work.
What the card says comes from the action result, so it stays true even when
the model's sentence is wrong.

## 2. What the code does today

All paths relative to `templates/analytics/` unless they start with
`packages/`.

- **Revisions exist, but the edit result does not name one.** Every changed
  save snapshots the pre-save state into `dashboard_revisions`
  (`server/lib/dashboards-store.ts:1595-1645`); `snapshotDashboardRevision`
  returns the revision id, reusing the latest row when it already matches
  (`:1617-1623`). Both write paths in `upsertDashboardWithOutcome` call it and
  drop the id (`:1770-1775` fenced, `:1778-1783` unfenced), and
  `DashboardUpsertOutcome` has only `dashboard` and `didWrite` (`:1697-1700`).
  So `mutate-dashboard`'s result (`actions/mutate-dashboard.ts:683-737`) has
  no revision id to undo to.
- **Restore already does the right thing for undo.**
  `restore-dashboard-revision` (`actions/restore-dashboard-revision.ts`)
  takes `dashboardId`, `revisionId` and an optional `expectedUpdatedAt`
  fence, snapshots the current state first and returns that snapshot as
  `snapshotRevisionId`, queues collab sync so open editors update, and for
  agent callers verifies the restored panels in `report` mode. The UI already
  wraps it in `useRestoreDashboardRevision`
  (`app/hooks/use-dashboard-revisions.ts:52-90`), which invalidates the
  dashboard, revision and panel caches on success. The history panel uses it
  (`app/components/dashboard/DashboardHistoryPanel.tsx`).
- **The chat has a per-action renderer hook.** An action declares
  `chatUI: { renderer, when, projectResult }`
  (`packages/core/src/action-ui.ts:54-62`); the app registers a component
  for that renderer id with `registerActionChatRenderer`
  (`packages/toolkit/src/app/chat/tool-render-registry.tsx:81-85`), and the
  tool call display resolves it (`packages/toolkit/src/app/chat/chat/tool-call-display.tsx:912-932`).
  Analytics already does this for `query-agent-native-analytics`
  (`actions/query-agent-native-analytics.ts:87-92`,
  `app/lib/register-analysis-result-renderer.tsx:69-73`, imported in
  `app/root.tsx:25`). The renderer gets `args`, `resultJson` and `isRunning`
  (`tool-render-registry.tsx:4-18`).
- **Today a `mutate-dashboard` call renders as a generic tool row** with the
  humanized name, because no renderer is registered for it.
- **Panel titles are not in the result.** `compactDashboardResult` returns
  ids only (`actions/dashboard-panel-order.ts:153-169`); titles appear only in
  `verification` and `unverified[]` entries. 1.3a's `editOutcome.panels`
  carries titles for verified panels; changes that touch no data panel (a
  title or width edit) still need titles.
- **i18n.** The app catalog is `app/i18n/en-US.ts` with ten other locales
  loaded in `app/i18n/index.ts:5-18`: `zh-CN`, `zh-TW`, `es-ES`, `fr-FR`,
  `de-DE`, `ja-JP`, `ko-KR`, `pt-BR`, `hi-IN`, `ar-SA`. History copy lives
  under `dashboard.history*` (`app/i18n/en-US.ts:174-186`).

## 3. Build

1. **Return the undo point from the store.** Add
   `previousRevisionId: string | null` to `DashboardUpsertOutcome`
   (`server/lib/dashboards-store.ts:1697-1700`); set it from the
   `snapshotDashboardRevision` return value in both branches (`:1770-1783`);
   `null` for a create (no prior state) and for `didWrite: false`. Thread it
   through `upsertDashboardWithRetryOutcome` (`:1928-1965`) unchanged. Callers
   that ignore it keep working.
2. **Name the undo in the edit result.** In `actions/mutate-dashboard.ts`,
   when `changed` and not a dry run, return
   `undo: { revisionId, expectedUpdatedAt }` where `revisionId` is
   `persisted.previousRevisionId` and `expectedUpdatedAt` is
   `savedUpdatedAt` (`:625`). Omit `undo` when there is no revision id. Do the
   same in `update-dashboard` and `compose-dashboard` where they write an
   existing dashboard, and in `restore-dashboard-revision`, whose undo is
   `{ revisionId: snapshotRevisionId, expectedUpdatedAt: dashboard.updatedAt }`
   (undo of a restore puts back what the restore replaced).
3. **Name the changed panels.** Add `changes` to the same results: at most 12
   `{ panelId, title, kind: "added" | "changed" | "moved" | "removed" }`,
   built from `finalMutation` (`mutate-dashboard.ts:635-644`): titles of added,
   changed and moved panels from the saved `root`, titles of removed panels
   from `originalRoot`. Plus `dashboardFieldsChanged.length > 0` as one
   `{ kind: "dashboard" }` entry. Titles through the same one-line sanitizer
   1.3a uses. Put the builder in `server/lib/dashboard-agent-write.ts` next to
   `dashboardEditOutcome` so all four actions share it.
4. **Declare the renderer.** Add `ANALYTICS_DASHBOARD_EDIT_RENDERER =
   "analytics.dashboard-edit"` to `shared/dashboard-edit-outcome.ts` (created
   in 1.3a). On `mutate-dashboard`, `update-dashboard`, `compose-dashboard`
   and `restore-dashboard-revision` add
   `chatUI: { renderer: ANALYTICS_DASHBOARD_EDIT_RENDERER, when: (args, result) => hasEditOutcome(result), projectResult: projectDashboardEdit }`
   where `projectDashboardEdit` keeps only `dashboardId`, `name`,
   `editOutcome`, `changes`, `undo` and `dryRun`. `when` excludes dry runs and
   help-only calls (`mutate-dashboard.ts:486-492`).
5. **The card.** Create `app/components/dashboard/DashboardEditSummary.tsx`
   and `app/lib/register-dashboard-edit-renderer.tsx` (registered like
   `register-analysis-result-renderer.tsx`, imported from `app/root.tsx`).
   Layout, following `frontend-design` and the repo density rules:
   - One header line: the title (`dashboardEdit.title`), with the dashboard
     name as an internal link to `/dashboards/<id>` (native navigation, so
     Cmd/Ctrl-click opens a new tab; read `native-navigation`). No
     description line under it.
   - A list of up to 5 changes, each one line: the change text
     (`dashboardEdit.panelAdded` etc.) and a trailing status: a muted
     `IconCircleCheck` plus `dashboardEdit.statusChecked`; an amber
     `IconAlertTriangle` plus `dashboardEdit.statusNotChecked` with the
     plain reason in a shadcn `Tooltip`; for a problem, `IconAlertTriangle`
     plus `dashboardEdit.statusProblem` with the reason in the tooltip. Amber,
     not red: nothing was destroyed. More than 5 shows
     `dashboardEdit.morePanels` collapsed under a shadcn `Collapsible`.
   - A trailing outline `Button` (size sm, the 24px control) `Undo` with
     `IconArrowBackUp`. Disabled with tooltip `dashboardEdit.undoUnavailable`
     when `undo` is absent.
   - Theme tokens only (`no-raw-colors`), logical spacing for RTL, a
     layout-matching `Skeleton` while `isRunning`.
6. **Undo behavior.** The button calls
   `useRestoreDashboardRevision(dashboardId)` with `{ dashboardId,
   revisionId: undo.revisionId, expectedUpdatedAt: undo.expectedUpdatedAt }`.
   Acknowledge within 100 ms (button shows `dashboardEdit.undoing` with a
   `Spinner`, disabled). On success the card swaps the button for a muted
   `dashboardEdit.undone` label and a toast; the hook's invalidations reload
   the open dashboard. On a conflict (the fence fails because someone saved
   after this edit), show `dashboardEdit.undoConflict` with an
   `dashboardEdit.openHistory` action that opens the existing history panel
   (reuse whatever opens `DashboardHistoryPanel` today; do not build a new
   one). On any other failure, toast `dashboardEdit.undoFailed` with the
   message. No `confirm()`; undo is itself reversible from history.
   The store already fences: `restoreDashboardRevision` throws
   `DashboardConflictError` when `expectedUpdatedAt` is stale, both before
   and inside the write (`dashboards-store.ts:2162-2165`, `:2208-2222`). But
   the action does not translate it (`actions/restore-dashboard-revision.ts:46-51`
   has no catch), and the error class carries no status code
   (`dashboards-store.ts:560-565`), so the client cannot tell a conflict from
   any other failure. In the action, catch `DashboardConflictError` and
   `fail(..., { errorCode: "dashboard_conflict", statusCode: 409 })`, the same
   shape `update-dashboard` uses (`actions/update-dashboard.ts:942-948`). The
   card branches on `errorCode === "dashboard_conflict"`, never on message
   text.
7. **The undone state survives reload.** The card's local "undone" state is
   lost on reload, and the result in the thread still says `undo` is
   available. On mount, compare the dashboard's current `updatedAt` (from the
   cached dashboard query when present, else no extra request) with
   `undo.expectedUpdatedAt`; when they differ, render the button disabled
   with `dashboardEdit.undoStale` tooltip. Do not fetch per card in a long
   thread.
8. **Agent parity.** Add to `.agents/skills/dashboard-management/SKILL.md`
   (the revisions paragraph at `:56-60`): "To undo your last edit, call
   `restore-dashboard-revision` with the `undo.revisionId` and
   `undo.expectedUpdatedAt` from that edit's result." The agent and the button
   then use the same action and the same fence.
9. **Changelog.** `agent-native changelog add "Each dashboard edit the agent makes now shows what changed, whether it was checked, and an Undo button." --type added`.

Four areas: **UI** (steps 5 to 7), **actions** (steps 1 to 4: result fields
and `chatUI`; no new action), **skills** (step 8), **application state**
(does not apply: the card reads the tool result in the thread; undo goes
through the restore action, whose revision row records who restored it and
the chat context (`requestRevisionChatContext`,
`dashboards-store.ts:324-327`), so the agent sees the new state the next time
it reads the dashboard).

## 5. Tests

- `server/lib/dashboards-store.interleave.spec.ts` (or a new
  `dashboards-store.revision-outcome.spec.ts` beside it): an update returns
  `previousRevisionId` equal to the id `list-dashboard-revisions` shows for
  the pre-save state; a no-op returns `null`; a create returns `null`.
- `actions/mutate-dashboard.spec.ts`: a changed agent save returns `undo`
  and `changes` with titles; a removed panel's title comes from the old
  config; a dry run returns neither.
- `actions/restore-dashboard-revision.spec.ts`: restoring with a stale
  `expectedUpdatedAt` fails with `errorCode: "dashboard_conflict"` and status
  409 and writes nothing; a restore returns `undo` pointing at
  `snapshotRevisionId`.
- `app/lib/register-dashboard-edit-renderer.spec.tsx` (pattern:
  `app/lib/register-analysis-result-renderer.spec.tsx`): renders checked, not
  checked (with tooltip reason) and problem rows; Undo calls the restore
  mutation with the fence; a conflict shows the history action; a missing
  `undo` disables the button.
- No source-reading tests.

## 8. Defaults for open questions

- **D1.** The card shows for agent edits only. UI edits made by clicking
  already show on the dashboard itself. *Reviewer may change.*
- **D2.** Undo goes back to the state before this one edit, not the start of
  the turn. A turn with three edits shows three cards; undoing the last one
  first is the expected order. *Reviewer may change.*
- **D3.** Undo is fenced on `updatedAt`. A later edit by anyone, including
  the agent's next edit in the same turn, disables earlier cards' Undo. This
  is deliberate: no undo overwrites newer work. *Reviewer may change.*
- **D4.** Five rows visible, the rest collapsed. *Reviewer may change.*
- **D5.** No "Ask agent to fix" button on problem rows in this unit; 1.5
  owns fix buttons. *Reviewer may change.*

## 9. Do not

- No behavior changes outside this unit: restore semantics, revision pruning
  (`dashboards-store.ts:1575-1593`) and history UI stay as they are.
- Schema: none; `previousRevisionId` is a return value, not a column. If a
  column ever seems needed, additive only.
- No new `/api` routes; the card uses the existing action through
  `useActionMutation`.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value: a
  failed undo never shows "Undone", and a missing `undo` disables the button
  rather than hiding it.
- No large payloads in SQL or in the projected result: `changes` and
  `editOutcome.panels` are capped at 12, and `projectResult` drops everything
  else.
- No custom popovers or modals with absolute positioning; shadcn `Tooltip`,
  `Collapsible`, `Button` only. No `alert`/`confirm`.
