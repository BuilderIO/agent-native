# 5.1b Weekly summary: on by default, Settings control, open tracking

Lane B (Founders). Size M. Second half of plan unit 5.1; needs 5.1a.

## 1. Goal

The first time someone creates a dashboard of their own, their weekly summary
turns on for that dashboard, addressed only to them, and their bell inbox
tells them so with a link to change it. In Settings › Notifications they can
switch it off, pick up to three dashboards, and choose the day and time. If
the summary is paused (for example, no model connection), the row says why
and how to fix it. Opening a dashboard from the email is counted, so the team
can read the weekly summary open rate the plan tracks.

## 2. What the code does today

All paths are relative to `templates/analytics/` unless noted.

- **Nothing fires when a dashboard is created.** `upsertDashboardOutcome`
  returns `{ dashboard, didWrite }` with no "created" flag
  (`server/lib/dashboards-store.ts:1696-1699`, `1844-1854`).
  `upsertDashboardWithOutcome` knows, because it loads `existing` first
  (`dashboards-store.ts:1707-1710`). No dashboard-created event or tracking
  call exists in `actions/` or `server/lib/` (searched for `dashboard_created`
  and `dashboard.created`).
- **Dashboards are created from several places.** Callers of the upsert
  helpers: `actions/compose-dashboard.ts:280`, `actions/save-explorer-dashboard.ts`,
  `actions/clone-creative-context-dashboard.ts`, `server/lib/dashboard-agent-write.ts`,
  and seed paths that must not count: `actions/ensure-native-v2-dashboards.ts`,
  `actions/ensure-risk-meeting-dashboard.ts`, `server/lib/demo-dashboards.ts`.
  The dashboard page saves through `update-dashboard`
  (`app/pages/adhoc/sql-dashboard/index.tsx:606`).
- **Notification preferences** are one user setting read by `get-user-pref`
  and written by `update-analytics-notification-preferences`
  (`actions/update-analytics-notification-preferences.ts:11-54`). The
  Settings page renders them as `SettingsRow`s with a `Switch` and optimistic
  rollback (`app/pages/Settings.tsx:46-85`, rows at `121-150`). Search entries
  come from `buildAnalyticsNotificationsSearchEntries`
  (`app/pages/settings/settings-search.ts`).
- **Navigation state** is derived from the URL in
  `app/hooks/use-navigation-state.ts:26-80`. A dashboard route sets
  `view: "adhoc"` and `dashboardId`; there is no field for "opened from an
  email".
- 5.1a defines the `analytics-weekly-summary` user setting (absent means
  never decided), `set-weekly-summary`, `get-weekly-summary`, and email links
  of the form `/dashboards/<id>?ws=<summaryId>`.

## 3. Build

1. **Know when a dashboard was created.** Add `created: boolean` to
   `DashboardUpsertOutcome` (`dashboards-store.ts:1696`), true only when
   `upsertDashboardWithOutcome` inserted the row. Additive; existing callers
   ignore it.

2. **Default-on helper.** In `server/lib/weekly-summary.ts` (from 5.1a) add
   `maybeEnableWeeklySummaryByDefault(ctx, dashboard)`:
   - Return early when the user setting exists (any value, including
     `enabled: false`), when the dashboard is demo or seeded, or when the
     owner is not the caller.
   - Otherwise call the same internal function `set-weekly-summary` uses, with
     `{ enabled: true, dashboardIds: [dashboard.id], recipients: [owner], enabledBy: "default" }`
     and the user's timezone from their localization setting (UTC if unset).
   - Send one inbox notification with `notify` from
     `@agent-native/core/notifications`, channel `inbox` only, linking to
     `buildSettingsRoute("notifications")`.
   - If enabling fails, log a warning with the cause and leave the setting
     absent so the next creation tries again. Do not fail the dashboard write.
     Do not write a setting that claims it is on.

3. **Call it from the user creation paths only.** After a successful write
   with `created: true` in `actions/compose-dashboard.ts`,
   `actions/save-explorer-dashboard.ts`, `actions/clone-creative-context-dashboard.ts`,
   and the `update-dashboard` create path. Not from `ensure-*` actions or
   `demo-dashboards.ts`. Pass `ctx.appId` through (5.1a's automation needs it).

4. **Settings row.** In `app/pages/Settings.tsx`, add a `weeklySummaryRow` in
   the Notifications › Email group, after the error email row:
   - `SettingsRow` with a label only (no description; this is a new row, and
     the default-chrome rule applies to added lines). A `Switch` bound to
     `get-weekly-summary` / `set-weekly-summary` through `useActionQuery` /
     `useActionMutation`, optimistic with rollback and a toast, the same shape
     as `useNotificationPreferences` (`Settings.tsx:54-85`).
   - A **Manage** button (`variant="outline"`, text only) opening a shadcn
     `Popover` with: a dashboards multi-select (reuse the multi-select from
     the dashboard filters shipped in #7250 if it is a shared component;
     otherwise shadcn `Command` in a `Popover`), max 3; a day `Select`; a time
     `Select` in 30-minute steps; a recipients input that validates emails, max
     5. Save writes all fields in one `set-weekly-summary` call.
   - When `get-weekly-summary` reports `lastStatus: "paused"`,
     `scheduleMissing`, or a `lastError`, show one amber line under the row
     with `IconAlertTriangle` (amber, not red: nothing is destroyed) and a fix
     action: "Turn on again" for a pause, "Connect a model" linking to the
     agent settings page for `missing_credentials`.
   - Loading uses a `Skeleton` matching the row height.
   - Add search entries for "weekly summary" in `settings-search.ts`.

5. **Open tracking.** Add `actions/mark-weekly-summary-opened.ts`:
   `http: { method: "POST" }`, `agentTool: false`, args `{ summaryId }`. It
   sets `opened_at` once, scoped to the caller's own summary, and returns
   `{ opened: true, firstOpen: boolean }`. A summary id that is not the
   caller's returns a 404, not a silent success. In the dashboard page, read
   `ws` from the URL on load and call it once with `useActionMutation`. Also
   `trackEvent("weekly_summary_opened", { summary_id })` from
   `@agent-native/core` client analytics so the first-party dashboards can
   chart it.

6. **Application state.** In `app/hooks/use-navigation-state.ts`, add
   `weeklySummaryId?: string` to `NavigationState`, set from `ws` on a
   dashboard route. The agent then knows the user arrived from a summary and
   can answer "why did that drop" with `get-weekly-summary` in context. Keep
   `ws` in the URL; do not strip it.

7. **Skills.** In `.agents/skills/dashboard-ops/SKILL.md` (the section 5.1a
   adds): the summary turns on by default for the first dashboard, addressed
   only to its owner; the user can change it in Settings › Notifications or
   by asking; when `weeklySummaryId` is in navigation state, read that
   summary before answering. In `.agents/skills/dashboard-management/SKILL.md`,
   one line: creating a user's first dashboard may turn on their weekly
   summary, and the agent should mention it once if the tool result says so
   (`compose-dashboard` returns `weeklySummaryEnabled: true` in that case;
   add the field).

8. **Changelog.** From `templates/analytics`:
   `agent-native changelog add "Your weekly summary turns on with your first dashboard. Change it in Settings, Notifications." --type added`.

## 8. Defaults for open questions

- **[decide] What counts as the first dashboard:** the first one the user
  creates and owns, through the agent or the UI. Demo, seeded and cloned
  starter dashboards do not count. If 3.2's seeded company dashboard should
  count, flip that in one place in the helper.
- **[decide] Addressed to the owner only** when turned on by default. Adding
  other recipients is always a deliberate choice in Manage.
- **[decide] Users are told once, in the bell inbox.** No banner on the
  dashboard.
- **[decide] Turning it off is remembered.** The default never turns it back
  on.
- **[decide] Open rate counts a click to a dashboard from the email.** No
  tracking pixel.

## 9. Do not

- No behavior changes outside this unit. Creating a dashboard behaves the same
  apart from the one-time enable.
- Additive-only schema: no table changes beyond 5.1a; `created` is a return
  field, not a column.
- No new `/api` routes for app data; open tracking is an action.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value: a
  failed default enable leaves "never decided", not "on"; a foreign summary
  id is a 404, not `opened: true`.
- No large payloads in SQL.
- Do not email anyone other than the owner without the owner choosing it.
