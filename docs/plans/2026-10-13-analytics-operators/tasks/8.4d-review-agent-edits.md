# 8.4d Review agent edits: per-cell diff, accept or reject, a version per thread

Lane E (Holy-shit features). Size M. Gated: the Review changes sheet, its
per-cell diff and the Accept and Reject controls are new UI; build only after
the "Notebook: review agent changes" and "Dashboard: review agent changes"
screens in `prototypes/analytics-operators/` are signed off. Where the
signed-off prototype differs from this brief, the prototype wins.

Depends on: 1.3b (built: the change card and undo), 7.3 (agent cell edits),
7.1b (notebook page). Merge after 7.4. Blocks: nothing.

Paths are relative to `templates/analytics/` unless they start with
`packages/`.

## 1. Goal

After the agent has edited a notebook or dashboard over a conversation
(rewrote two SQL cells, added a chart, deleted a text cell), the user opens
Review changes from the change card and sees every cell the thread touched,
each with a before and after: SQL as a line diff, text as a word diff, chart
settings as a short list of what changed. They keep the cells they like and
reject the rest, one by one or all at once; rejecting a cell puts that one
cell back as it was before the thread started. The state before the thread is
saved as a named version ("Before: Churn deep dive") that stays in history,
so the user can always get back to it even after 50 later saves.

## 2. What the code does today

- Every save snapshots the state it replaces into `dashboard_revisions`
  (`server/db/schema.ts:57-81`; `snapshotDashboardRevision`,
  `server/lib/dashboards-store.ts:1595-1646`), stamped with the run's chat
  context `{ threadId, runId, turnId }` (`AnalyticsRevisionChatContext`,
  `:173-177`; read by `requestRevisionChatContext`, `:324-327`, from
  `getRequestRunContext()`). The snapshot holds the pre-write state stamped
  with the context of the run that replaced it. `turnId` is only written by
  the after-turn autosave (`server/plugins/agent-chat.ts:157-194`, registered
  at `:1288`), because `RequestRunContext` has no `turnId`.
- Revisions are pruned to `DASHBOARD_REVISION_LIMIT = 50` per dashboard
  (`dashboards-store.ts:246`, `pruneDashboardRevisions` `:1575`). An early
  pre-thread state can be pruned away during a long session.
- `DashboardUpsertOutcome.previousRevisionId` is the undo point of each write
  (`dashboards-store.ts:1696-1704`).
- 1.3b's card (`app/components/dashboard/DashboardEditSummary.tsx`) lists up to
  5 changes (`VISIBLE_CHANGES`, `:39`) with Added, Changed, Moved, Removed and a
  checked state per row (`rowStatus` `:54-74`), and one Undo for the whole edit
  (`UndoControl` `:281-389`) through `restore-dashboard-revision` with an
  `expectedUpdatedAt` fence; a newer version disables Undo (`:305-308`) and a
  server conflict shows Open history (`:505-522`, `?history=1` read at
  `app/pages/adhoc/sql-dashboard/index.tsx:531`).
- The only panel diff is `diffDashboardEdit(before, after)` and
  `dashboardEditChanges` in `server/lib/dashboard-agent-write.ts:322` and
  `:378`: ids of inserted, changed, moved and removed panels, no content diff.
- `DashboardHistoryPanel.tsx` lists revisions with title, time and author and
  restores the whole dashboard without a fence (`:72-85`); it does not show
  chat context or diffs. `list-dashboard-revisions`
  (`actions/list-dashboard-revisions.ts:17-43`) returns `chatContextStatus`
  and `chatContext`.
- Highest migration on the integration branch is 173
  (`server/plugins/db.ts:1874`); 174 and 175 are reserved for 1.4c and 4.2c,
  176 to 189 for 8.1 to 8.3.

## Plan corrections

- "A version saved per agent thread" exists in data already (every revision
  carries the thread id) but not durably: pruning can delete the pre-thread
  state. This unit pins it with a label instead of adding a version table.
- Accept and reject are per cell, so they cannot be a whole-dashboard
  restore. Rejecting writes typed `mutate-dashboard` operations that put the
  chosen cells back, so it merges with anything else that changed and goes
  through the same validation and render check.

## 3. Build

1. **Schema (additive), migration 190.** In `server/db/schema.ts` add
   `label TEXT` (nullable) to `dashboard_revisions`, and a migration in
   `server/plugins/db.ts` with `version: 190`, `name:
   "dashboard-revisions-label"` (migrations 176 to 189 are taken by 8.1 to
   8.3; this unit owns 190). `pruneDashboardRevisions` skips labeled rows
   when counting toward the 50, and keeps at most 20 labeled rows per
   dashboard (oldest labeled pruned first). Run `pnpm
   guard:additive-migrations`.
2. **Pin the thread base.** In the store, when a write's chat context has a
   `threadId` and no labeled revision exists yet for
   `(dashboard_id, threadId)`, label the snapshot it takes
   (`previousRevisionId`) as `thread-base:<threadId>`. That is the state
   before the thread's first edit. One place: inside
   `snapshotDashboardRevision`'s caller in `upsertDashboardWithOutcome`, not
   per action.
3. **Diff library.** New `shared/dashboard-review.ts`:
   - `reviewDashboardChanges(base, current): PanelReview[]` with, per panel id
     present in either, `{ panelId, title, kind: "added" | "removed" | "changed" | "moved", fields: { name: "sql" | "markdown" | "title" | "chartType" | "source" | "config"; before?: string; after?: string }[] }`.
     Config changes list the top-level keys that differ (`colors`, `topN`,
     `noCode`, ...) with stable-stringified before and after values, capped
     at 2,000 characters each, with a `truncated` flag instead of a silent cut.
   - `lineDiff(a, b)` and `wordDiff(a, b)` (a small Myers diff; no new
     dependency unless `pnpm view` shows a maintained one the repo already
     uses).
   - `rejectOperations(base, current, panelIds): DashboardMutationOperation[]`:
     for a changed panel, `updatePanel` back to the base panel; for an added
     one, `removePanels`; for a removed one, `insertPanel` at its base index
     (`index`); for a moved one, `movePanels` with `index`. Order is removals,
     inserts, updates, moves.
4. **Actions.**
   - `review-dashboard-thread-edits` (read-only, `http: { method: "GET" }`):
     `{ dashboardId, threadId }`. Access through `getDashboard`. Finds the
     `thread-base:<threadId>` revision (typed error `no_thread_base` when the
     thread made no edits), runs `reviewDashboardChanges(base.config,
     current.config)` limited to panels the thread changed (ids from
     `diffDashboardEdit` across the thread's revisions), and returns
     `{ baseRevisionId, baseCreatedAt, currentUpdatedAt, panels: PanelReview[], otherChanges: number }`
     where `otherChanges` counts panels changed by anyone else since, so the UI
     can say so.
   - `resolve-dashboard-edit-review` (write): `{ dashboardId, threadId, reject: string[], expectedUpdatedAt }`.
     Builds `rejectOperations` and applies them through the same function
     `mutate-dashboard` uses (`applyDashboardMutationOperations`, `actions/dashboard-mutation-api.ts:919`, and the store
     write), so validation, the agent render check and the revision snapshot
     all happen. A stale `expectedUpdatedAt` fails with `dashboard_conflict`
     (409), as `restore-dashboard-revision` does. Accepting is not a write:
     cells not rejected stay. Returns 1.3b's `editOutcome`, `changes` and
     `undo`, so the change card renders for the reject too. Add the action to
     `DASHBOARD_EDIT_TOOLS` (`server/plugins/agent-chat.ts:63`).
   - `list-dashboard-revisions` returns `label` (additive field).
5. **UI (gated).**
   - 1.3b's card gains a secondary Review changes button next to Undo when the
     run had a `threadId` and changed at least one panel.
   - Review changes opens a shadcn `Sheet` from the right (non-modal over the
     notebook, so the cells stay visible): title "Review changes", then one
     section per panel in notebook order with the cell number, title and kind
     badge; SQL and Markdown diffs in a monospace block with added lines
     tinted `bg-primary/10` and removed lines `bg-muted` with strike-through
     (no red; nothing is destroyed by reading a diff); config changes as one
     line each ("Chart type: Line to Bar").
   - Each section has Keep (default) and Reject toggles (a shadcn
     `ToggleGroup`), and the footer has Reject all, then a primary Apply at
     the compact size, disabled until something is set to Reject. Apply calls
     `resolve-dashboard-edit-review` with a pending state inside 100 ms; on
     conflict show "Someone changed this after the agent did. Reload the review
     to see the latest." with Reload.
   - When `otherChanges > 0`, an amber line "{{count}} other cells changed
     since. Rejecting only touches the cells listed here."
   - History: labeled revisions show their label ("Before: <thread title>")
     with the thread link; `DashboardHistoryPanel` reads `label` and
     `chatContext` from the existing list action.
6. **Application state.** The open review publishes `selected-object`
   `{ type: "dashboard-review", dashboardId, threadId }` so the user can ask
   the agent "why did you change cell 3?" while reviewing. No new key name.
7. **Skills.** `.agents/skills/notebooks/SKILL.md` and
   `.agents/skills/dashboard-management/SKILL.md` ("Reporting Edit Outcomes"
   subsection): after a multi-step edit, point the user at Review changes;
   use `review-dashboard-thread-edits` to answer "what did you change?"; use
   `resolve-dashboard-edit-review` when the user says "undo the chart change
   but keep the SQL fix".
8. **Changelog.** `agent-native changelog add "Review the agent's changes cell by cell and keep or reject each one" --type added`.

## 8. Defaults for open questions

- [Decided by the owner, 2026-10-14] Review is inline: each changed cell shows its diff with Keep and Undo, and a bar above the cells offers Keep all. There is no separate review sheet. The prototype screen `nb-review` is the reference.
- [Default] The thread base is labeled on the thread's first write and never
  moves.
- [Default] Accept means "leave it"; only rejects write.
- [Default] Works on grid dashboards and notebooks alike (cells are panels).
- [Default] At most 20 labeled revisions per dashboard.

## 9. Do not

- Do not restore the whole dashboard to reject one cell.
- Do not add a second write path; rejects go through the mutation apply.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
