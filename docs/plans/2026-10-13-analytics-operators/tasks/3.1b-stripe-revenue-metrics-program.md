# 3.1b: Stripe revenue metrics data program

Lane B. Size M. Split from 3.1; needs 3.1a.

## 1. Goal

A founder who connects Stripe can ask "what's our MRR?", "how much did we
lose to churn last month?" or "how do our 2025 cohorts retain?" and get the
same answer every time, computed by one shared, saved data program with
written definitions, with history rebuilt from invoices. The agent stops
writing a fresh MRR calculation per question, and every number states its
window, currency and coverage.

## 2. What the code does today

- The `stripe` action is per customer only: it resolves customers by email,
  id or name (`templates/analytics/actions/stripe.ts:22-35`) and returns that
  customer's invoices, charges, refunds or subscriptions
  (`stripe.ts:89-165`). There is no account-wide revenue view.
- Stripe is reachable from the sandbox through the provider API (`stripe`
  provider, bearer `STRIPE_SECRET_KEY`,
  `packages/core/src/provider-api/index.ts:1708-1723`), so the agent can
  compute MRR ad hoc with `run-code`, but nothing stores the method.
- Data programs are the stored, cached, shareable form of a run-code script:
  `upsertDataProgram` (`packages/core/src/data-programs/store.ts:193-281`),
  per-viewer credentials, TTL or manual refresh, background mode with a
  10-minute budget, 10,000-row and 4 MiB caps
  (`templates/analytics/.agents/skills/data-programs/SKILL.md:97-130`).
- New programs are always created `private` (`store.ts:277`), and the
  by-name lookup is per owner (`getDataProgramByName`, `store.ts:332-355`), so
  two teammates who each install by name get two copies. Data programs can be
  shared to the org but never made public (`store.ts:81-92`); the visibility
  change goes through the core `set-resource-visibility` action
  (`packages/core/src/sharing/actions/set-resource-visibility.ts:22-60`).
- The installed-program precedent is `ensure-risk-meeting-dashboard`: reads
  JS seeds from `templates/analytics/seeds/data-programs/`
  (`templates/analytics/actions/ensure-risk-meeting-dashboard.ts:58-96`) and
  upserts by name (`ensure-risk-meeting-dashboard.ts:120-141`). Its test
  mocks the store (`actions/ensure-risk-meeting-dashboard.spec.ts:1-80`).
- Panels bind to a program with `source: "program"` and a JSON descriptor
  `{ programId, params }` (`templates/analytics/server/lib/dashboard-panel-query.ts:57-91`).
  There is no row filter on a program panel, so each distinct `params` is its
  own cache entry and its own run.
- Metric definitions live in the data dictionary as org or user settings
  under `data-dict-<id>` (`templates/analytics/actions/save-data-dictionary-entry.ts:22`,
  `save-data-dictionary-entry.ts:224-228`). Org writes require an org owner
  or admin (`save-data-dictionary-entry.ts:141-143`). Entries are injected
  into agent context with a trust label (`templates/analytics/server/lib/data-dictionary-context.ts:35-55`).
- Stripe list endpoints page by `starting_after` plus `has_more`; until 3.1a
  lands the helpers stop after page one (see 3.1a section 2).

## Plan corrections

- "One saved, shared data program" needs explicit org visibility and a
  reuse-before-create lookup, because programs default to private and the
  name lookup is per owner (`store.ts:277`, `store.ts:332-355`).
- Recent Stripe API versions changed the invoice line item shape (price and
  subscription references moved under nested objects). The program must pin
  `Stripe-Version` or read both shapes; verify the current shape with
  `provider-api-docs` before writing the parser.

## 3. Build

1. Definitions module `templates/analytics/server/lib/stripe-revenue-definitions.ts`:
   export `STRIPE_REVENUE_DEFINITIONS`, an array of
   `{ id, metric, definition, knownGotchas, cuts }` for the eight metrics in
   section 4. This is the single source for the dictionary entries and the
   program's `description`.
2. Program seed `templates/analytics/seeds/data-programs/stripe-revenue-metrics.js`
   (follows the Risk Meeting `.js` seed precedent; see section 8). Logic:
   - Params: `view` (`"monthly"` default, `"cohorts"`, `"customers"`),
     `months` (default 24, max 60), `currency` (optional, lowercase ISO).
   - Fetch `/invoices` with `created[gte]` = start of window minus 12 months
     (to catch annual invoices that cover the window), `limit: 100`,
     `status` filtered client-side to `paid` and `open`, via
     `providerFetchAll("stripe", "/invoices", { query, pagination: { cursorParam: "starting_after", lastItemCursorPath: "id", hasMorePath: "has_more", maxPages: 200 } })`.
     For any invoice whose `lines.has_more` is true, page
     `/invoices/{id}/lines` the same way.
   - Send header `Stripe-Version` pinned to the version the parser was
     written against (decision in section 8), and keep a small adapter that
     reads either line shape.
   - Recurring lines only: lines tied to a subscription item, not
     `proration`, not one-off invoice items. Monthly value =
     (line amount minus line discount amounts) / period length in months
     (rounded from `period.end - period.start`, minimum 1). Tax excluded.
   - Customer MRR for month M = sum of monthly values of lines whose period
     covers the last second of M. The current month is marked
     `is_complete: false`.
   - Movements per customer from M-1 to M: new (no MRR ever before),
     reactivation (MRR before, zero in M-1), expansion, contraction, churned
     (MRR in M-1, zero in M). Net new = new + reactivation + expansion -
     contraction - churned, and must equal MRR(M) - MRR(M-1); if it does not,
     throw (a bug, not user state).
   - Group by currency. Never add amounts across currencies. If `currency` is
     unset and more than one currency exists, emit rows per currency with a
     `currency` column.
   - `view: "monthly"` emits one row per (month, currency): `month`,
     `currency`, `mrr`, `new_mrr`, `reactivation_mrr`, `expansion_mrr`,
     `contraction_mrr`, `churned_mrr`, `net_new_mrr`, `customers`,
     `new_customers`, `churned_customers`, `is_complete`. Amounts in major
     units (cents / 100) as numbers.
   - `view: "cohorts"` emits (cohort_month, months_since_start, currency):
     `customers_start`, `customers_active`, `logo_retention`, `mrr_start`,
     `mrr_active`, `net_revenue_retention`.
   - `view: "customers"` emits one row per customer: `customer_id`, `email`,
     `name`, `currency`, `first_paid_month`, `mrr_window_start`,
     `mrr_current`, `movement` (new, expansion, contraction, churned, flat,
     reactivation). 3.3a and 4.4 read this view.
   - Restricted keys (2.2a accepts `rk_` keys): the program needs read
     access to Invoices and Customers. A 403 from Stripe throws an error
     whose message starts `stripe_permission_missing:` and names the
     resource, so the panel and agent can say which permission to add.
   - Coverage: include `coverage_complete` (boolean) on every row and log the
     invoice count and stop reason. If the fetch hit `maxPages` or a
     `cursor-missing` stop, set `coverage_complete: false`. Never emit a
     partial history as complete.
3. Install action `templates/analytics/actions/ensure-stripe-revenue-metrics.ts`
   (`defineAction`, not read-only, `mcpTool: false`):
   - Look for an accessible program named `stripe-revenue-metrics` with
     `listDataPrograms(appId, ctx)` first (org-visible or owned); reuse it.
     Only create when none is accessible. Update code only when the caller
     can edit it and the stored code differs.
   - `refreshMode: "ttl"`, `refreshTtlMs: 6h`, `background: true`.
   - When the request has an org, set visibility `org` through the core
     `set-resource-visibility` action (`resourceType: "data_program"`). If
     that fails, return `shared: false` with the error code; do not swallow.
   - Write the eight dictionary entries from step 1 with `source: "stripe"`,
     `action: "run-data-program"`, `queryTemplate` set to the panel
     descriptor JSON, `owner: "Analytics template"`. Org dictionary writes
     need an org admin: if the caller is not one, skip the writes and return
     `definitionsSaved: false, reason: "needs_org_admin"`. Never overwrite an
     existing entry a person edited (`author` not equal to the template
     marker) or one marked approved.
   - Return `{ programId, created, shared, definitionsSaved, reason? }`.
     Install needs no Stripe key; the key is resolved per viewer when the
     program runs.
4. Agent wiring:
   - `templates/analytics/.agents/skills/data-programs/SKILL.md`: add a
     "Stripe revenue metrics" worked example (params, views, definitions, how
     to read `coverage_complete`).
   - New skill `templates/analytics/.agents/skills/revenue-metrics/SKILL.md`
     (read `writing-agent-instructions` first): when a revenue question comes
     in, call `ensure-stripe-revenue-metrics` once if the program is missing,
     then `run-data-program` with the right view; quote definitions by name;
     state currency, window, `is_complete` and coverage; never recompute MRR
     ad hoc with `run-code` when the program answers it.
   - `templates/analytics/AGENTS.md` "Data questions": one line pointing
     revenue questions to the `revenue-metrics` skill.
5. UI: none in this unit. The program is visible in the existing data
   program surfaces and its definitions on the Semantic Layer page; 3.2 puts
   it on a dashboard.
6. Application state: not applicable. No new screen or selection.
7. Changelog: from `templates/analytics`,
   `agent-native changelog add "Revenue questions use one shared Stripe metrics program with written definitions for MRR, churn and retention." --type added`.

## 4. Copy

No catalog strings: dictionary entries and the program description are stored
content in English, like the shipped dashboard seeds. DECISION: reviewer may
require localized definitions later. Definitions to store (plain sentence
case, no em dashes):

| id | metric | definition |
| --- | --- | --- |
| `stripe-mrr` | MRR | Monthly recurring revenue: the monthly value of every active subscription line on paid or open Stripe invoices at the end of the month, after discounts and before tax. Annual plans count as one twelfth per month. |
| `stripe-new-mrr` | New MRR | MRR from customers who had no MRR in any earlier month. |
| `stripe-reactivation-mrr` | Reactivation MRR | MRR from customers who had MRR before, had none last month, and have some this month. |
| `stripe-expansion-mrr` | Expansion MRR | The increase in MRR from customers who had MRR last month and have more this month. |
| `stripe-contraction-mrr` | Contraction MRR | The decrease in MRR from customers who had MRR last month and still have some, but less, this month. |
| `stripe-churned-mrr` | Churned MRR | MRR lost from customers who had MRR last month and have none this month. |
| `stripe-logo-retention` | Logo retention | The share of customers who started in a month and still have MRR a given number of months later. |
| `stripe-net-revenue-retention` | Net revenue retention | A cohort's MRR a given number of months after it started, divided by its MRR in its first month. Includes expansion, contraction and churn. |

Shared `knownGotchas` text for all eight: "History starts at the first Stripe
invoice. Prorations, one-off charges, refunds and credit notes are not
counted. Amounts are not converted between currencies. The current month is
partial."

## 8. Defaults for open questions

- DECISION: one program with a `view` param. Each view is its own cached run,
  so a dashboard with monthly and cohort panels fetches invoices twice per
  TTL. Alternative for later: a row filter on program panel descriptors.
- DECISION: count `paid` and `open` invoices; exclude `draft`, `void`,
  `uncollectible`.
- DECISION: MRR snapshot at month end; current month flagged incomplete.
- DECISION: no FX conversion.
- DECISION: pin `Stripe-Version` to the version the parser targets, chosen at
  implementation time from `provider-api-docs`; keep the dual-shape adapter.
- DECISION: seed as `.js` beside the Risk Meeting seeds because it is
  sandbox program text, not app source. Reviewer may prefer a TS module that
  exports the program as a string.
- DECISION: definitions are saved approved when the installer is an org
  admin, since installing is accepting the template's definitions.
- DECISION: TTL 6 hours, background mode.

## 9. Do not

- No behavior changes outside this unit (the `stripe` action is unchanged
  except for 3.1a's pagination fix).
- Additive-only schema; none expected.
- No new `/api` routes for app data; use actions.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials; the program uses
  `providerFetch*`, which resolves the viewer's connection.
- No `catch` or default that turns a failure into a normal-looking value:
  partial history is `coverage_complete: false`, a mixed-currency total is
  never produced, a skipped dictionary write is reported.
- No large payloads in SQL: emitted rows stay within the data-program caps;
  never stage raw invoices into settings or app state.
- Do not build a dashboard here; that is 3.2.
