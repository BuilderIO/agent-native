# 1.4d Fresh, cheap panels: move expensive first-party panels onto rollups

Lane A (Reliability). Size M. Not gated. **Build only if 1.4b's measurement
says so** (1.4b D1).

Last part of the plan's PR 1.4 cost work. 1.4c adds the active-user daily
table; this unit switches the panels 1.4b ranked most expensive onto it (or
onto the existing daily event rollup), each one proven to return the same
rows.

## 1. Goal

The first-party dashboards' most expensive panels show the same numbers as
today and scan a fraction of the data. Someone viewing the seeded first-party
dashboard sees no change except speed. The agent, when it builds a new
active-user panel, writes it against the rollup by default.

## 2. What the code does today

All paths relative to `templates/analytics/`.

- Known first-party dashboards are repaired at read time:
  `pageDashboardConfig` applies `repairKnownFirstPartyDashboardQueries` to the
  config the page and the verifier both read
  (`server/lib/dashboard-panel-verification.ts:31`, `:166-190`;
  `server/lib/canonical-first-party-dashboard-repair.ts`). Stored SQL is not
  rewritten. This is the existing way to change canonical panel SQL without
  touching saved dashboards.
- The canonical active-user SQL (new versus recurring users, retention, and
  their legacy and bounded variants) lives in
  `canonical-first-party-dashboard-repair.ts:261-262`, `:587-602`, and the
  metric catalog builds panels for `compose-dashboard` from
  `server/lib/first-party-metric-catalog.ts` (72 raw reads). The seeded
  dashboard is `seeds/dashboards/agent-native-templates-first-party.json`
  (43 raw panels).
- After 1.4c, `analytics_user_event_days` exists in Postgres and optionally
  in BigQuery.

## 3. Build

1. **Pick the panels.** Take the top panels by bytes from 1.4b's report that
   the new table or the daily event rollup can answer exactly. Write the
   list, with each panel's bytes before, into the PR.
2. **Rewrite each one with a proof.** For each panel, write the rollup SQL
   next to the raw SQL in `canonical-first-party-dashboard-repair.ts` (for
   panels on the seeded and canonical dashboards) and
   `first-party-metric-catalog.ts` (for catalog panels), keeping every
   filter token (`{{timeRange}}`, `{{emailFilter}}`, `{{appFilter}}`) and the
   output column names and order. Add a repair rule that swaps the raw SQL
   for the rollup SQL only when the stored SQL matches the known canonical
   text, so user-edited panels are untouched.
3. **Fallback on BigQuery without the table.** When the backend is BigQuery
   and the optional `_user_event_days` table is missing (the typed error from
   1.4c), the repair must not apply. Decide it once per request from the
   backend's table report (cache it with the backend config,
   `server/lib/first-party-analytics-backend.ts:189-216`), not by catching a
   query failure per panel.
4. **Equivalence tests.** One fixture of raw events covering: two templates,
   docs traffic, signed-in and signed-out sessions, internal and external
   emails, a test identity, users first seen inside and outside the window,
   and days with no events. For every rewritten panel and every value of
   each filter, the raw SQL and the rollup SQL return identical rows. A panel
   without this test is not rewritten.
5. **Agent defaults.** In `.agents/skills/dashboard-management/SKILL.md`
   "First-Party User Metrics" (`:538-561`), replace 1.4b's interim rule with:
   active-user and retention panels read `analytics_user_event_days`;
   event-count panels read `analytics_event_daily_rollups`; read the raw
   table only for a property or URL the rollups do not carry, with a bounded
   time filter. Extend 1.4b's verification hint to cover the active-user
   shape.
6. **Measure after.** Re-run 1.4b's report for a week and put before and
   after bytes per rewritten panel in a follow-up comment.
7. **Changelog.** `agent-native changelog add "First-party dashboards load faster and cost less to run: active-user panels now read compact daily tables." --type improved`.

Four areas: **actions** (none new; the repair runs inside existing read
paths), **skills** (step 5), **UI** (none; the panels look the same),
**application state** (does not apply).

## 5. Tests

- `server/lib/first-party-rollup-equivalence.spec.ts` (new; PGlite, the
  same setup `server/lib/first-party-analytics.spec.ts` uses): step 4's
  matrix for every rewritten panel.
- `server/lib/first-party-dashboard-repair.spec.ts`: the repair applies to
  the canonical text, skips a user-edited panel, and skips when the BigQuery
  table is absent.
- `server/lib/first-party-metric-catalog` tests if they exist, else
  `server/lib/dashboard-catalog.spec.ts`: catalog panels build the rollup SQL.
- No source-reading tests.

## 6. Verify

```bash
cd templates/analytics
pnpm exec vitest --run server/lib/first-party-rollup-equivalence.spec.ts \
  server/lib/first-party-dashboard-repair.spec.ts server/lib/dashboard-catalog.spec.ts
pnpm guards
pnpm --filter analytics dev
```

Open the seeded first-party dashboard before and after the change with the
same local data and compare every rewritten panel by eye and by
`pnpm action inspect-dashboard-panel --dashboardId agent-native-templates-first-party --panelId <id>`
(row counts and sample rows must match). Screenshot both. Stop the server.
Cannot be verified locally: BigQuery byte savings (needs the production
project and 1.4b's telemetry).

## 7. Dependencies

- Needs: 1.4b (panel ranking and go decision), 1.4c (the table).
- Hotspots: `server/lib/canonical-first-party-dashboard-repair.ts`,
  `server/lib/first-party-metric-catalog.ts` (4.1 builds funnels and

  `.agents/skills/dashboard-management/SKILL.md`.

## 8. Defaults for open questions

- **D1.** Rewrite through the read-time repair, never by editing users'
  stored dashboards. *Reviewer may change.*
- **D2.** Only canonical text is swapped; a panel a person or the agent has
  edited keeps its SQL. *Reviewer may change.*
- **D3.** A panel whose rollup result differs from raw in any fixture case
  is left on raw and listed in the PR. *Reviewer may change.*

## 9. Do not

- No behavior changes outside this unit: the numbers a viewer sees must not
  change; only the table read.
- Schema: none (1.4c owns it); additive only if anything.
- No new `/api` routes.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value: a
  missing BigQuery table means the raw SQL runs, decided up front, never a
  caught error that returns empty rows.
- No large payloads in SQL.
- Do not name a company, customer or internal domain in skills, comments or
  test fixtures; use placeholder domains such as `example.com` and
  `internal.example`.
