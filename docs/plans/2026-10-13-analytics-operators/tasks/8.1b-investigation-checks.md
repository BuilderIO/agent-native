## 1. Goal

The three cause checks of an investigation: where the change is
concentrated (segments), what shipped when it started (releases), and which
errors started with it (errors). Each check is a server function registered
in 8.1a's step registry. It returns findings with 3.4a-shaped evidence, or a
typed "couldn't check" reason with a plain message and, where one exists, a
fix. Each finding says whether it explains the change, which feeds 8.1a's
confidence rule. In the prototype's main example these produce: "The drop is
in new Postgres connections" (27.6%, down from 71.2%; other segments moved
under 3 points), "It started when #4182 shipped on Oct 8", and "Schema sync
started timing out 9 minutes later".

The segments check also fixes who was affected (people in the dropped
segment who did not reach the next step), which errors, replays (8.1e) and
accounts (8.1e) use.

## 2. What the code does today

- Funnels compile from `config.growth` through `compileGrowthPanelSql` in
  `shared/growth-panels.ts` (4.1b, not built; its brief step 2): one CTE per
  step reading `analytics_events`, step filters on `app`, `template`, `path`,
  `hostname`, `signed_in`, `properties.<key>`, `context.<key>`, every value
  through one literal helper, and only constructs the BigQuery translator
  round-trips. 4.3 (brief step 2) adds `compileFunnelStepPeopleSql` for the
  people who reached one step and not the next.
- First-party events carry `app`, `template`, `path`, `hostname`,
  `referrer`, `signed_in`, `properties` and `context`
  (`server/db/schema.ts:249-271`). The catalog keeps each event's property
  keys in `analytics_event_catalog_latest.property_keys`
  (`server/db/schema.ts:374-394`).
- GitHub is a provider API with workspace-connection auth (`GITHUB_TOKEN`
  credential key, OAuth provider `github`)
  (`packages/core/src/provider-api/index.ts:982-1007`), reached through
  `executeProviderApiRequest` (`server/lib/provider-api.ts:93`).
  `github-repo-files` takes `owner` and `repo` on every call
  (`packages/core/src/provider-api/actions/github-repo-files.ts:25-26`);
  nothing stores which repositories ship the app. No action reads pull
  requests or deployments today.
- Connection status by provider comes from `data-source-status`
  (`actions/data-source-status.ts:161` names github, pylon, Sentry keys).
- First-party errors: `listErrorIssues` (`server/lib/error-capture.ts:1860`)
  returns `ErrorIssueSummary` with `firstSeenAt`, `eventCount`,
  `usersAffected` and a 14-day daily `sparkline`
  (`:1413-1432`, `SPARKLINE_DAYS` at `:60`, query at `:1460-1500`).
  Occurrences live in `error_events` with `occurred_at`, `user_key`,
  `session_recording_id`, and an `(issue_id, occurred_at)` index
  (`server/db/schema-errors.ts:86-130`). Storage is sampled after 20 events
  per fingerprint, one per minute plus one per new user
  (`error-capture.ts:784-787`, `:883-899`), so stored rows undercount volume
  while `eventCount` stays exact. The Errors deep link is
  `/monitoring?view=errors&issue=<id>` (`actions/match-error-issues.ts:17-18`).
- Sentry: `listIssues(project, query, statsPeriod, orgSlug, connectionId)`
  (`server/lib/sentry.ts:164`) returns issues with `count`, `userCount`,
  `firstSeen`, `lastSeen` and optional `stats` (`:105-119`); events carry an
  optional `user.email` (`:121-129`). The action resolves Sentry credentials
  through the workspace connection (`actions/sentry.ts:51-60`).
- Settings: org settings `getOrgSetting` and `putOrgSetting`
  (`packages/core/src/settings/org-settings.ts:18`, `:26`); user settings
  `getUserSetting` and `putUserSetting`
  (`packages/core/src/settings/user-settings.ts:30`, `:83`).
- 8.1a (brief) provides the step registry, the `meter` and `signal`, the
  `change` record (direction, `onsetAt`, `onsetPrecision`, series) and the
  finding shape.

## Plan corrections

- **"What shipped" needs a repository list.** GitHub access exists but no
  setting says which repositories ship the app. This unit adds a small
  investigation setting (`githubRepositories`, at most 5) with actions, so the
  agent can set it; without it the step says so and offers the fix.
- **Error volume from stored rows is sampled.** Spike timing uses stored
  `error_events` (hourly), and totals use the issue's exact `eventCount`. The
  evidence says so.
- **Replays and accounts move to 8.1e** to keep both units at size M.

## 3. Build

1. **SQL** in `shared/growth-panels.ts` (append; 4.1b owns the file):
   - `compileFunnelSegmentSql(definition, { fromStepIndex, toStepIndex,
     field, current, previous })`: the same step CTEs as
     `compileGrowthPanelSql`, with the segment value taken from the from
     step's event row, returning `period` (`current` or `previous`),
     `segment`, `from_count`, `to_count`. The top 8 values per period by
     `from_count`; the rest roll up as `(other)`, and `distinct_values`
     reports how many there were.
   - `compileEventSegmentSql({ eventName, filters, thresholdMode,
     distinctBy }, { field, current, previous })` for event rules: counts per
     segment and period with the same top 8 rule.
   - Allowed fields are 4.1b's filter fields plus `referrer_host`. Prove both
     dialects in tests as 4.1b does.
2. **Affected people** `server/lib/investigation-people.ts`:
   `resolveAffectedPeople(investigation, ctx)` re-runs 4.3's
   `compileFunnelStepPeopleSql` (dropped at the to step) with the dropped
   segment's filter added to the from step, for the current window from the
   onset (or window start when `onsetAt` is null), capped at 500 people with
   `truncated`. Each person is `{ key, userId | null }` (`user_id` is the
   signed-in email; anonymous people have none), so the people SQL selects
   `user_id` next to 4.3's `key`. It stores the query spec on the investigation (`change.affected
   = { kind: "funnel_dropped", fromStepIndex, toStepIndex, segment, from, to
   }`), never the keys. Event-rule subjects: people who fired the event in
   the previous window and not the current one, same cap. Panel subjects
   without a funnel: `not_applicable`.
3. **Segments** `server/lib/investigation-checks/segments.ts`:
   - Dimensions: `app`, `signed_in`, `referrer_host`, plus up to 4
     `properties.<key>` keys of the from step's event from the catalog, in
     catalog order. Skip a dimension whose `distinct_values` is over 20 and
     list the skipped ones in the evidence filters. One query per dimension
     (both periods in one query), so at most 7 queries, each through the
     `meter`.
   - Concentration rule: a segment value explains the change when it holds
     at least 20 people at the from step in both windows, its own change
     accounts for at least 60% of the total change (weighted by its share of
     people), and every other value of that dimension moved less than a third
     of the total change. The first dimension, by contribution, that has
     such a value wins.
   - Finding (`kind: "segments"`): title from a template ("The drop is in
     <value> <dimension label>", "The rise is in ..."), `data = { fmt: "pct"
     | "count", dimension, rows: [label, previous, current, people] (<= 8),
     note, droppedSegment: { field, value } }`, `explains: true` and
     `causeKey: "segment:<field>=<value>"` when the rule holds. When no value
     holds, one finding "The change is spread across segments" with
     `explains: false` and the compared dimensions.
   - Evidence: source `first-party`, window `{ kind: "range" }` for both
     periods as text, filters, `rowCount` = people at the from step, query =
     the SQL of the winning dimension, `queryLanguage: "sql"`.
   - Couldn't check: `not_applicable` "This panel isn't built from events,
     so I couldn't split it by segment." (plain SQL panels);
     `no_data_in_window` "Fewer than 20 people reached <from step> in the
     window, so segments aren't comparable."; `over_budget` and `timed_out`
     come from the registry.
4. **Repositories setting** `server/lib/investigation-settings.ts` and two
   actions:
   - `get-investigation-settings` (GET, read-only) and
     `update-investigation-settings` (POST) with `{ githubRepositories:
     string[] }` (each `owner/repo`, at most 5, validated). Stored with
     `putOrgSetting` under `analytics-investigation-settings` when the
     caller has an org, else `putUserSetting`. Describe it so the agent sets
     it when the user names the repo that ships the app.
5. **Releases** `server/lib/investigation-checks/releases.ts`:
   - For each repository, through `executeProviderApiRequest` with the
     workspace GitHub connection: `GET /repos/{owner}/{repo}/pulls?state=closed&sort=updated&direction=desc&per_page=100`
     (at most 2 pages; stop once `updated_at` is before the window), keep
     those with `merged_at` in the current window plus the day before it;
     `GET /repos/{owner}/{repo}/deployments?environment=production&per_page=30`
     and the statuses of at most 10 deployments in the window, matched to a
     PR by `merge_commit_sha`. Release time is the first successful
     production deployment of that commit, else `merged_at` with
     `deployTimeRecorded: false`.
   - Matching: with an hour onset, a release time in `[onset - 6 h, onset +
     15 min]`; with a day onset, on the onset day or the day before; with no
     onset, anywhere in the current window but then it never explains. The
     match explains when exactly one release matches, or the closest match
     before the onset is at least 2 hours nearer than the next one. Several
     equal matches give a finding "Several releases shipped around the
     change" with `explains: false` and up to 5 listed.
   - Finding (`kind: "release"`): "It started when #<n> shipped on <date>",
     `data = { repo, pr: { number, title, author, mergedAt, deployedAt |
     null, url }, othersInWindow, onsetAt, series: change.series }`,
     `causeKey: "release:<repo>#<n>"`. No release in the window is a done
     step with a `text` finding "No release in the window lines up with the
     change", `explains: false`.
   - Evidence: source `github`, the window, `rowCount` = PRs scanned, query
     = the request paths, `queryLanguage: "http"`.
   - Couldn't check: `no_connection` "GitHub isn't connected." (fix: connect
     github); `not_applicable` "No GitHub repository is set for
     investigations." (fix: agent, "Set the GitHub repository that ships this
     app"); `no_access` "GitHub refused access to <owner/repo>." on 403 or
     404. Never read a token from `process.env`.
6. **Errors** `server/lib/investigation-checks/errors.ts`:
   - First-party: `listErrorIssues` for the owner's scope (`sort:
     "eventCount"`, `limit: 50`, `status: "all"`); candidates are issues first
     seen in the current window plus the 10 with the most events. One grouped
     query over `error_events` gives hourly stored counts per candidate for
     the current window and the 7 days before. Spike start is the first hour
     whose count is at least 3 times the median hourly count of the 7 days
     before and at least 5 stored events; a new issue's spike start is its
     `firstSeenAt`.
   - Sentry, when connected: `listIssues` with `statsPeriod` covering the
     window; candidates first seen in the window. For the top candidate only,
     read up to 100 events for user emails.
   - Matching: spike start within 60 minutes after the matched release time,
     or inside the onset bucket when no release matched. It explains when the
     timing matches and either at least 30% of the issue's distinct users in
     the window are affected people (first-party `user_key`, Sentry event
     emails), or the issue is new in the window. With no affected people
     (not applicable), timing plus a new issue is enough.
   - Finding (`kind: "errors"`): "<Error type> started <N> minutes after the
     deploy" (or "...when the change started"), `data = { source:
     "first-party" | "sentry", issue: { id, title, culprit, eventCount,
     usersAffected, firstSeenAt, spikeStartAt, href }, daily (<= 14 points),
     overlap: { matched, of } | null, minutesAfterRelease | null }`, `href`
     `/monitoring?view=errors&issue=<id>` or the Sentry permalink, `causeKey:
     "error:<source>:<id>"`. No candidate is a done step with "No new errors
     line up with the change", `explains: false`.
   - Evidence: source `first-party-errors` or `sentry`, window, rows =
     issues scanned, and the filter note "Stored events are sampled; totals
     come from the issue count." for first-party.
   - Couldn't check: `no_connection` "No error source is connected." only
     when first-party capture has no issues for the scope and Sentry is not
     connected; a Sentry failure with first-party results is a done step that
     names the Sentry failure in its evidence, not a silent drop.
7. **Register** the three checks in `server/lib/investigation-checks/index.ts`
   and add `run-investigation-check` evidence to 3.4a's mapper
   (`shared/answer-evidence.ts`, `answerEvidenceFromToolCall`): the step's
   evidence payload, so the investigation thread's "How this was answered"
   panel lists what each step read.
8. **Application state:** none.
9. **Skills:** extend `.agents/skills/investigations/SKILL.md` with the three

10. **Changelog:** `agent-native changelog add "Ask why a metric changed and the agent checks segments, releases and errors within a time budget and saves the evidence as a notebook" --type added`.

## 8. Defaults for open questions

- [Default] Concentration rule: 60% of the change from one value, the other
  values under a third each, at least 20 people per window.
- [Default] Release match: 6 hours before to 15 minutes after an hour onset;
  same day or day before for a day onset; deployment time over merge time.
- [Default] Error match: spike within 60 minutes after the release, and 30%
  user overlap or a new issue.
- [Default] Repositories are an org setting (user setting with no org), at
  most 5, set by the agent or later by a settings control.
- [Default] Sentry is read only when connected; first-party capture is read
  always.

## 9. Do not

- Do not read every pull request or every error event; respect the page,
  candidate and query caps and say when a cap was hit.
- Do not count a release or an error as explaining a change without a timing
  match; no onset means it cannot explain.
- Do not store affected people's keys or emails; store the query spec.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
