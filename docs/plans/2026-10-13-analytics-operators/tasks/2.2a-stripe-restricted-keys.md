# 2.2a Stripe restricted keys

Lane B (Founders). Size S. Not gated.

Paths are relative to `templates/analytics/`.

## 1. Goal

A founder connecting Stripe is steered to a read-only restricted key, the key
they paste is checked for the right shape before it is saved, and Test
connection succeeds for a restricted key that has only the read permissions
Analytics needs. A full secret key still works but the card says it can also
write. A publishable key is refused with a clear message instead of failing
later.

## 2. What the code does today

- The credential key is `STRIPE_SECRET_KEY` (`server/lib/credential-keys.ts:63`,
  provider config `:200-204`, alias `:339`). One resolver reads it:
  `server/lib/stripe.ts:13-21`, which sends it as `Authorization: Bearer`
  (`:49-54`). A restricted key (`rk_live_`, `rk_test_`) is also a Bearer token,
  so restricted keys already work for every read in `server/lib/stripe.ts`
  once stored.
- The card copy contradicts itself: step 1 says "Create a restricted key with
  read-only access, or use your secret key"
  (`app/lib/data-sources.ts:396-397`), step 2 says "Paste your secret key
  (starts with "sk_live_" or "sk_test_")" with placeholder `sk_live_...`
  (`:403-407`).
- Test connection calls `GET https://api.stripe.com/v1/balance`
  (`server/routes/api/test-connection.post.ts:156-164`). A restricted key
  without the Balance read permission fails this test with "Invalid API key"
  even though every Analytics read would work.
- Analytics reads these Stripe objects (`server/lib/stripe.ts`): customers and
  customer search (`:185-229`), subscriptions and subscription search
  (`:236`, `:385`), invoices (`:280`), products (`:336`, `:412`), charges
  (`:361`), payment intents (`:372`), refunds (`:437-446`).
- Saving goes through `actions/update-data-source-credentials.ts`;
  `validateCredential` (`:35-57`) validates only the Google service-account JSON.
- The core provider API definition for `stripe` uses bearer auth with
  `STRIPE_SECRET_KEY` (`packages/core/src/provider-api/index.ts:1708-1722`), so
  run-code and data programs use the same key.

### Plan corrections

- The plan says restricted keys need to be "accepted". They already are; the
  real gaps are the contradictory copy, a test that fails for a correct
  read-only key, and no shape check.

## 3. Build

1. **Shape check** in `actions/update-data-source-credentials.ts`
   `validateCredential`: for `STRIPE_SECRET_KEY`, accept `rk_live_`, `rk_test_`,
   `sk_live_`, `sk_test_`; reject `pk_` with the copy in section 4; reject
   anything else with the "doesn't look like" message. Never echo the value.
   Keep the existing early return for other keys, written as a small
   `validators: Record<string, (value) => string | null>` map so the next key
   does not add another `if` (the function already special-cases one key).
2. **Key kind** helper `stripeKeyKind(value): "restricted" | "secret" | "unknown"`
   in `server/lib/stripe.ts` (pure, exported for tests).
3. **Test connection** in `server/routes/api/test-connection.post.ts:156-164`:
   call `GET /v1/customers?limit=1` instead of `/v1/balance`. On 401 return
   "Stripe rejected this key." On 403 return the permission message with the
   permission name from Stripe's error body when present. Return
   `{ ok: true, keyKind }` on success. This edits a grandfathered route in
   place; do not add a route.
4. **Status** in `actions/data-source-status.ts`: for the `stripe` provider,
   add `keyKind` computed from the resolved value on the server (never return
   the value). This lets the UI show the write warning without a test click.
5. **UI** `app/pages/DataSources.tsx` Stripe detail: when `keyKind === "secret"`,
   show one amber line with `IconAlertTriangle` (warnings use amber, red is
   for destructive): "This key can also change your Stripe data. A restricted
   read-only key is safer." No new card or title.
6. **Walkthrough** `app/lib/data-sources.ts:386-411`: rewrite both steps
   (section 4); placeholder `rk_live_...`; input label "Restricted key".
   Step 1 lists the read permissions in section 4 and links
   `https://dashboard.stripe.com/apikeys/create` (public Stripe URL).
7. **Application state.** None. The Stripe detail is a section of the existing
   Data sources view.
8. **Skills.** `.agents/skills/secrets/SKILL.md` in the template needs no
   change. In `.agents/skills/provider-api/SKILL.md` (Stripe notes) and
   `.agents/skills/cross-source-analysis/SKILL.md`, add one line: a 403 from
   Stripe usually means the restricted key lacks a read permission; tell the
   user which object type and point them to Data sources, do not ask for a
   full secret key.
9. **Changelog.** `agent-native changelog add "Stripe setup now recommends a read-only restricted key and tests it with the permissions Analytics uses" --type improved`.

## 8. Defaults for open questions

- **D1** Keep the credential key name `STRIPE_SECRET_KEY` for restricted keys.
  Renaming would split one credential across two resolvers.
- **D2** Full secret keys stay accepted, with a warning, so existing users are
  not broken.
- **D3** The test probe is `GET /v1/customers?limit=1`.
- **D4** Balance transactions read is in the recommended list because 3.1
  needs it, even though no current Analytics read uses it.
- **D5** Walkthrough copy stays in `app/lib/data-sources.ts` like every other
  source; moving all walkthroughs into the catalog is a separate task.

## 9. Do not

- No behavior changes outside this unit (do not touch other providers' tests
  or validation).
- Additive-only schema; none needed.
- No new `/api` routes; edit the existing Stripe case in place.
- No raw `fetch` from client code beyond the existing `testConnection` helper.
- No `process.env` reads for the Stripe key.
- No `catch` or default that turns a failure into a normal-looking value: a
  403 is a permission problem, not "connected".
- No large payloads in SQL.
- Never return, log or echo the key value, including in validation errors.
