# 1.3a The agent can't claim success that didn't happen: truthful edit outcomes

Lane A (Reliability). Size M. Not gated (no new surface; the visible part is
1.3b).

The plan's PR 1.3 is split in two. This unit (1.3a) closes the remaining ways
an unchecked dashboard edit can still read as done: the action result, the
per-reason next step, the analytics answer guard and the agent instructions.
It also adds the structured `editOutcome` field that 1.3b renders. 1.3b adds
the change summary card in chat with one-click undo through
`restore-dashboard-revision`.

## 1. Goal

When the agent edits a dashboard and the edit saved but could not be checked
(the check timed out, the source is not connected, the panel is a data
program, the query was too expensive to run automatically, or more panels
changed than one save checks), the agent's answer says so in plain words and
names the reason, and never says the chart "now shows" anything. When an
edit was checked and failed, the agent fixes it or says it failed. When
nothing was written, the agent says nothing changed. Each reason comes with
a next step that can actually work: the agent no longer calls an inspect
action that is certain to hit the same wall (a disconnected source, a data
program), and it asks before running a query that was skipped to keep cost
down.

## 2. What the code does today

All paths relative to `templates/analytics/` unless they start with
`packages/`.

**What #6881 and #6908 already fixed.** `git log` on
`actions/mutate-dashboard.ts` and `server/lib/dashboard-agent-write.ts` shows
`a9b523afa8` (#6881, "Report unchanged Analytics mutations accurately") and
`005805a11b` (#6908, "verify Analytics dashboard edits before saving").

- Agent calls verify every touched panel before the save
  (`actions/mutate-dashboard.ts:508-521`, gate in
  `server/lib/dashboard-panel-verification.ts:959-1064`). A directly edited
  panel that would show "No data", drop configured columns, or fail is
  refused and nothing is written (`blocksSave`,
  `dashboard-panel-verification.ts:655-667`; refusal at `:999-1005`). This
  covers the Oct 6 "cleared banner left the chart on No data" shape unless the
  agent passed `allowEmptyResult: true`, which saves with `verified:false`
  (`mutate-dashboard.ts:213-214`).
- A no-op save returns a receipt with `changed:false`
  (`server/lib/dashboard-agent-write.ts:66-76`), and the core loop forces one
  retry for it (`packages/core/src/agent/write-receipts.ts:195-202`).
- Every agent write returns a reserved `_receipt`
  (`mutate-dashboard.ts:699-709`; `restore-dashboard-revision.ts`,
  `compose-dashboard.ts` and `update-dashboard.ts` also emit one). The loop
  reads it before truncation (`packages/core/src/agent/production-agent.ts:8280`).

**What still lets an unchecked outcome read as done.**

1. *The five unchecked reasons all share one next step that dead-ends for two
   of them.* The notes are `timeout`, `missing_credential`, `skipped:program`,
   `too_expensive`, `not_executed:over_budget`
   (`dashboard-panel-verification.ts:48-53`, reasons `:137-146`). Every
   unchecked data panel except over-budget ones gets the same
   `nextStep`: "REQUIRED: call inspect-dashboard-panel ... confirm the panel
   renders" (`:1043-1049`). But `inspect-dashboard-panel` runs the same
   `verifyDashboardPanels` (`actions/inspect-dashboard-panel.ts:108-115`),
   which always returns `skipped:program` for a program panel
   (`dashboard-panel-verification.ts:512-518`) and `missing_credential` for a
   disconnected source (`:589-594`). The agent is told to do something that
   cannot succeed, and after that the model is left to improvise. For
   `too_expensive`, inspect runs with `maxBytesToExecute: Infinity`
   (`inspect-dashboard-panel.ts:113`), so following the next step silently
   runs the expensive query the save skipped on purpose.
2. *The final-answer guard retries once, then lets the claim through.* For a
   receipt with `verified:false` the core guard allows one retry
   (`write-receipts.ts:195-202`). If the retried draft still says "Fixed",
   the exhausted path prints the draft with a `Write check:` prefix
   (`production-agent.ts:7195-7205`, prefix text `write-receipts.ts:199-201`).
   The user sees "Fixed. Refresh and the line is on the chart." under a block
   that reads `mutate-dashboard: changed=true verified=false. Saved 1 op(s)
   ... NOT verified`, which is developer text. A receipt with
   `verified:"unverified"` (no panel was checked at all, for example a restore
   whose check threw, `restore-dashboard-revision.ts:76-83` and
   `dashboard-agent-write.ts:106-114`) gets no retry at all: "`unverified`
   alone only annotates the answer" (`write-receipts.ts:180-183`).
3. *The analytics guard treats any changed save as success.*
   `hasSuccessfulDashboardSave` counts a receipt as success when
   `receipt.changed` is true, whatever `verified` says
   (`server/plugins/agent-chat.ts:210-238`, the receipt branch at `:226`), and
   once it is true a draft without metric claims passes with `null`
   (`agent-chat.ts:990-995`). The existing spec confirms the analytics guard
   alone is inert on a pushback turn with an unverified write
   (`server/plugins/agent-chat.write-receipts.spec.ts:99-119`).
4. *The result leads with a success phrase.* `summary` starts with
   `Applied N dashboard mutation op(s)` (`mutate-dashboard.ts:671-681`), and
   only `annotateSummary` prepends `SAVED BUT NOT VERIFIED`
   (`dashboard-panel-verification.ts:1093-1121`). `message` repeats it
   (`mutate-dashboard.ts:732-736`). There is no single field that says, in
   one word, what happened.
5. *Instructions cover verified and verified:false, not how to word an
   unchecked save.* `AGENTS.md:13` says an edit is done only on
   `verified: true` and to call `inspect-dashboard-panel` otherwise. The
   `dashboard-management` skill says the same
   (`.agents/skills/dashboard-management/SKILL.md:491-502`, `:598-603`).
   Neither tells the agent what to say for each reason, nor that two of the
   reasons cannot be cleared by inspecting.
6. *The UI shows nothing about the outcome.* A `mutate-dashboard` call
   renders as a generic tool row; analytics registers only the analysis
   result renderer (`app/lib/register-analysis-result-renderer.tsx:69-73`).
   1.3b covers this.

**Whether the Oct 6 report still reproduces.** Not confirmed by reading code.
The "No data after clearing" shape is now refused before saving (point 1 of
"already fixed"). The "chart changed twice and didn't" shape can still happen
two ways: a save with an unchecked reason that the model words as done
(points 1 to 3 above), or a checked save whose panel the open page keeps
showing from its cache (the page keys panel data by SQL text,
`app/components/dashboard/SqlChart.tsx:1187-1197`, so a config-only change
re-renders but a stale server cache does not refetch; 1.4a covers that).
Step 1 below re-runs it.

## 3. Build

1. **Reproduce first (Phase 0 re-test).** On current main with the dev
   server (`pnpm --filter analytics dev`), open a dashboard with a
   first-party panel and a data-program panel, and ask the agent to (a) add a
   7-day moving average to the first-party line chart, (b) rename the program
   panel and change its SQL params, (c) clear a filter so a panel shows "No
   data". Record each answer, the `mutate-dashboard` result's `verified`,
   `unverified[]` and `nextStep`, and what the panel shows after reload. Put
   the three outcomes in the PR description. If none of them can be made to
   read as done, still ship steps 2 to 6: they close the paths in section 2
   that the repro may not hit.
2. **One outcome field.** In `server/lib/dashboard-agent-write.ts` add
   `dashboardEditOutcome(verdict, { changed, saved })` returning
   `editOutcome: { status, panels }` where `status` is one of
   `"checked"` (saved, every touched panel rendered, or `noRenderAffected`),
   `"saved_not_checked"` (saved, at least one panel has an unverified note and
   none failed), `"saved_with_problems"` (saved, a panel is empty, missing
   columns, or failed and was not a blocker, for example an affected panel),
   `"nothing_changed"` and `"not_saved"` (dry run). `panels` is at most 12
   entries `{ panelId, title, source, state: "ok" | "not_checked" |
   "problem", reason?: PanelUnverifiedNote | "empty" | "missing_columns" |
   "query_error" | "render_error" }`. Titles go through the existing
   `oneLine` sanitizer (`dashboard-agent-write.ts:22-29`). Add `source` to
   each `verdict.unverified[]` entry in `verifyPanelWrite`
   (`dashboard-panel-verification.ts:1034-1040`) so the outcome can name the
   source. Return `editOutcome` from `mutate-dashboard`,
   `restore-dashboard-revision`, `update-dashboard` and `compose-dashboard`
   wherever they already return `verdictFields(verdict)`. This is the field
   1.3b renders; keep its shape in one exported type
   `DashboardEditOutcome` in `shared/dashboard-edit-outcome.ts` so the client
   can import it.
3. **A next step per reason.** In `verifyPanelWrite`
   (`dashboard-panel-verification.ts:1041-1062`) build `nextStep` per note
   instead of one sentence for all:
   - `missing_credential`: "Saved. Tell the user `<title>` could not be
     checked because its `<source>` source is not connected, and link Connect
     data sources. Do not call inspect-dashboard-panel; it fails the same
     way."
   - `skipped:program`: "Saved. Tell the user `<title>` is a data program
     panel, which this check does not run. Do not call
     inspect-dashboard-panel for it."
   - `timeout`: "Call inspect-dashboard-panel once for `<ids>`; it has a
     longer budget. If it also times out, tell the user the edit saved but
     could not be checked in time."
   - `too_expensive`: "Saved. Tell the user `<title>` was not run to keep
     query cost down and ask before running it. Do not call
     inspect-dashboard-panel without the user's go-ahead."
   - `not_executed:over_budget`: keep today's text (`:1055-1059`).
   - Problems that are not notes (empty, missing columns, query or render
     error): keep today's REQUIRED inspect text (`:1043-1049`).
   Keep `nextStep` the first thing in the retry message, as today.
4. **Lead with the outcome in the result text.** In
   `actions/mutate-dashboard.ts:671-681`, build the summary from
   `editOutcome.status` first: `Saved and checked: ...`, `Saved, not checked:
   <reason per panel>`, `Saved with problems: ...`, `Nothing changed: ...`,
   `Dry run: ...`. Keep `Applied N op(s)` as the second clause, not the
   first. Update the action `description` (`mutate-dashboard.ts:439-443`) to
   name `editOutcome.status` as the field to report from, alongside
   `verified`. Do the same for `restore-dashboard-revision`'s `message`.
   Receipt summaries (`dashboard-agent-write.ts:86-164`) keep their current
   shape; they are bounded at 200 chars and the core reads only them.
5. **Analytics answer guard for unchecked edits.** In
   `server/plugins/agent-chat.ts`, add `uncheckedDashboardEditGuard(context)`
   and call it at the top of `realDataFinalGuard` (after the plan-mode return
   at `:863-865`). It reads `context.receipts`
   (`packages/core/src/agent/production-agent.ts:3903-3904`) for tools in
   `DASHBOARD_EDIT_TOOLS` (`agent-chat.ts:55-67`) whose latest receipt per
   subject has `verified !== true` and `changed === true`, after the same
   supersede rule core uses (a later verified write to the same subject that
   rechecks the failing ids clears it; reuse the rule by exporting
   `stillFlaggedReceipts` from `packages/core/src/agent/write-receipts.ts`
   rather than re-implementing it). If any remain and
   `context.retryCount === 0`, return `{ retryMessage, maxRetries: 1 }` whose
   message tells the model to state, per panel, that the change saved but
   was not confirmed, the plain reason, and the next step from the result,
   and to make no claim that the chart shows anything. On `retryCount > 0`
   return `null`: the model has been told once, and a guard that keeps
   retrying cannot tell an honest rewrite from a dishonest one without
   matching words in the user's language, which this unit does not do. Net
   effect: `verified:false` keeps its one retry (now with the per-reason
   instruction merged in, `write-receipts.ts:211-230`), and
   `verified:"unverified"` gets the one retry it gets none of today. Do not
   add any user-visible fallback text here; on exhaustion the core block
   still prints, and 1.3b's card shows the truth independent of the model's
   words. That card, not text matching, is the guarantee. Also change `hasSuccessfulDashboardSave`
   (`agent-chat.ts:226`) to count a receipt as a successful save only when
   `changed && verified === true`, so an unchecked save no longer
   short-circuits the metric-claim checks below it at `:990-995`. That is
   the boundary fix; do not add a second special case beside it.
   **Core change.** `write-receipts.ts` is not exported publicly today (only
   the `AgentLoopFinalResponseGuardContext` type is, from
   `packages/core/src/server/index.ts:178`). Export `stillFlaggedReceipts`
   (and the `ToolWriteReceipt` type) from `packages/core/src/agent/write-receipts.ts`
   through `packages/core/src/server/index.ts`, and add
   `.changeset/<name>.md` (patch, `@agent-native/core`).
6. **Instructions.**
   - `AGENTS.md:13`: replace the inspect clause with: report from
     `editOutcome.status`; `checked` is done; `saved_not_checked` means say it
     saved, name the reason, follow `nextStep`, and do not say the chart shows
     anything; `saved_with_problems` means fix it or say what is wrong;
     `nothing_changed` means say nothing changed. Keep the line short; the
     skill owns the per-reason detail.
   - `.agents/skills/dashboard-management/SKILL.md:491-502` and `:598-603`:
     add the per-reason table from step 3 and one example answer for
     `saved_not_checked` ("Saved the new title on Signups by app. I could not
     check that it renders because HubSpot is not connected.").
   - `ANALYTICS_PROMPT_RULES` (`agent-chat.ts:276-316`) already says "open an
     edit with 'Changing <panel title> on <dashboard>'". Do not add a new rule
     there; the guard in step 5 is the mechanism.
   Read `.agents/skills/writing-agent-instructions` before editing these.
7. **Changelog.** From `templates/analytics`, run
   `agent-native changelog add "Dashboard edits the agent could not check now say so and why, instead of reading as done." --type fixed`.

Four areas: **Actions** (steps 2 to 4), **instructions** (step 6),

## 8. Defaults for open questions

- **D1.** `editOutcome` is added beside `verified`, not instead of it.
  `verified` stays for existing callers and specs. *Reviewer may change.*
- **D2.** `too_expensive` asks the user before running. The alternative,
  running it with a capped byte budget, spends money without consent.
  *Reviewer may change.*
- **D3.** Program panels stay unchecked in this unit. Checking a program
  panel against its last cached run (cheap, no execution) is a good follow-up
  but changes `verifyDashboardPanels` semantics; left to 1.5 or later.
  *Reviewer may change.*
- **D4.** One guided rewrite, no text matching on the draft. Matching
  phrases like "not verified" works only in English and would retry honest
  answers in other languages. *Reviewer may change.*
- **D5.** The core exhausted-path `Write check:` block is left as is. Making
  it plain language needs a localized client rendering of receipts, which is
  a framework change for every app. 1.3b covers analytics in the UI instead.
  *Reviewer may change.*

## 9. Do not

- No behavior changes outside this unit: do not change what blocks a save,
  the verification budget, or which panels are checked.
- Schema changes: none expected; if any, additive only.
- No new `/api` routes for app data; everything goes through the existing
  actions.
- No raw `fetch` from client code.
- No `process.env` reads for provider credentials.
- No `catch` or default that turns a failure into a normal-looking value: an
  outcome that cannot be computed is `saved_not_checked` with reason
  `unknown`, never `checked`.
- No large payloads in SQL or in the tool result: `editOutcome.panels` is
  capped at 12.
- Do not weaken `blocksSave`, `allowEmptyResult`, or the receipt supersede
  rule.
