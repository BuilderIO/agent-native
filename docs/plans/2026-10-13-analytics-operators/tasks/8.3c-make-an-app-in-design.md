# 8.3c Make an app in Design from a dashboard or notebook

Lane E (Holy-shit features). Size M. Gated: the "Make an app in Design…"
menu item and its dialog are new UI; build only after the "Make an app in
Design" screen in `prototypes/analytics-operators/` is signed off. Where the
signed-off prototype differs from this brief, the prototype wins.

Depends on: 8.3a (named outputs), 8.3b (binding and sandbox in Design),
8.2a (handoff record and card). Merge after 1.9 (the dashboard actions
menu) and 7.5 (the notebook actions menu items). Blocks: 8.3d.

Paths are relative to `templates/analytics/` unless they start with
`packages/` or `templates/`.

## 1. Goal

From a dashboard or notebook, an editor opens the ⋯ menu and chooses "Make
an app in Design…". A dialog lists the query cells with a name for each
(checked by default for the cells a published app would show), plus an
optional "What should it do?". Make app names the chosen outputs, hands the
job to the agent, and the agent asks Design to build it. Design creates a
project with the workspace design system, binds it to those outputs (8.3b),
and lays out a few distinct screens (an overview, a list with a detail, a
filtered view) that read only through the data channel. The card in
Analytics says "App draft in Design" with "Open draft". 7.5's "Publish as
app" stays the quick read-only page; this is the designed path.

  and `read-named-outputs`; names are set through `mutate-dashboard`
  (`setConfigPath`, `actions/dashboard-mutation-api.ts:141`).
- 8.2a adds `prepare-insight-action`, `handoff-insight-action` and the draft

  (`packages/core/src/artifacts/detect.ts:105`: `create-design` maps to

- In Design, `create-design` links the caller's default design system when

- Design shows a new design to the user at `/design/:id`

## 3. Build

1. **Kind.** Append `app` (target `design`) to `INSIGHT_ACTION_KINDS`. An
   `app` artifact's items are the outputs `{ name, title, chartType }` (at
   most 12) and the dashboard's inputs `{ id, label, type }`; its summary is
   the editor's "What should it do?" text (at most 1,000 characters) plus
   the dashboard name; its links are the dashboard URL. No rows, SQL or
   columns: Design reads those itself through the contract.
2. **Dialog** (`app/components/insight-actions/MakeDesignAppDialog.tsx`,
   gated): title "Make an app in Design", no subtitle. A list of the
   dashboard's query cells, each a `Checkbox`, the cell title, and an
   `Input` for its output name (prefilled with the existing `outputName` or
   `outputNameFromTitle`; validated live against 8.3a's rule). Checked by
   default: `notebookAppCells` on a notebook, every query panel on a grid
   dashboard, up to 12. Then "What should it do?" (`Textarea`, optional).
   Footer: Cancel (outline) and "Make app" (primary at the compact size),
   disabled with nothing checked or a name invalid. Editors only.
3. **Submit.** One `mutate-dashboard` call sets the chosen names (so undo
   and 1.3b's card cover it), then `prepare-insight-action` with kind
   `app`, then `sendToAgentChat` (`openSidebar: true`, `submit: true`) with
   the catalog prompt and `context: { actionId }`. The agent runs
   `handoff-insight-action` with an objective that asks Design to create a
   project with the workspace design system, bind it with
   `bind-design-data` to this dashboard and these outputs, generate two to
   four distinct screens with `generate-screens` following
   `analytics-data-apps`, and keep it a draft. A failed `mutate-dashboard`
   stops before the handoff and shows its error in the dialog.
4. **Menu items (gated).** "Make an app in Design…" in the dashboard ⋯ menu
   (first group, after the add items 1.9 places there) and in the notebook ⋯
   menu after "Publish as app…" (7.5). Text only. Hidden for viewers;
   disabled with a tooltip when Design does not resolve
   (`list-next-actions` returns `app` with `app_unavailable`). The
   next-action row (8.2a) skips the `app` kind; it lives only in the menu.
5. **Card.** 8.2a's card with "App draft in Design" and "Open draft" to the
   design. While Design is still generating, the handoff may come back
   `waiting`; Check again refreshes it.
6. **Design.** Extend `templates/design/.agents/skills/analytics-data-apps/SKILL.md`
   (8.3b) with "When Analytics asks for an app": create the design (no
   `designSystemId`, so the default links), bind, plan screens from the
   output names and inputs, and author each screen against
   `$store.an.outputs`; read `get-design-system` once first. One pointer in
   `templates/design/AGENTS.md` (one line).
7. **Application state.** None new. The dialog is local UI; the agent gets
   the action id in the handoff context, and `view-screen` lists the
   notebook's insight actions (8.2a).
8. **Skills (Analytics).** Extend `.agents/skills/insight-actions/SKILL.md`:
   the `app` kind, that output names are set before the handoff, and that
   the agent never passes rows to Design.
9. **Changelog.** From `templates/analytics`: `agent-native changelog add "Make an app in Design from a dashboard or notebook, built on its live outputs" --type added`.

## 5. Tests

- `app/components/insight-actions/MakeDesignAppDialog.spec.tsx`
  (happy-dom): defaults checked as described; invalid and duplicate names
  block Make app; more than 12 blocks it; submit writes names, prepares the
  action and sends the agent request in that order; a failed name write
  shows the error and sends nothing.
- `server/lib/insight-actions.app.spec.ts` (PGlite): the `app` artifact
  holds names, titles, chart types and inputs only; unnamed outputs are
  refused; a verified `design` identity becomes a draft.
- The menu: visible for editors, hidden for viewers, disabled when Design
  does not resolve (extend the existing `index.tsx` or
  `DashboardActionsMenu` spec).

## 8. Defaults for open questions

- [Default] Editors only; viewers cannot name outputs.
- [Default] At most 12 outputs, two to four screens.
- [Default] The design uses the workspace default design system; the user
  can switch it in Design.
- [Decided by the owner, 2026-10-14] An app made here is published only
  through Builder in v1 (8.3d), as a value prop for Builder accounts. This
  unit makes the draft in Design; nothing here needs Builder.

## 9. Do not

- Do not send rows, SQL or columns to Design.
- Do not create the design from Analytics with a direct action call.
- No behavior changes outside the unit; additive-only schema; no new /api
  routes for app data (use actions); no raw fetch from client code; no
  process.env reads for provider credentials; no catch or default that turns a
  failure into a normal-looking value; no large payloads in SQL.
