# Delegated framework registry diff (main vs companion)

## Baseline: what "main" is here

- **The baseline is the actual pre-filter registry at parent `9f2cdd94055d`, not an execution of current `origin/main`.** It is captured through the real `createAgentChatPlugin` with each template's real plugin and generated action registry, at the input of `filterDelegatedRegistry`. Nothing in this report was produced by running `origin/main`.
- Why that registry stands in for main's: since merge-base `817dfb3` the branch's committed changes to registry construction are only framework markers (`frameworkMcpTool`); `preferMcpAppActions` affects only the direct-MCP mount maps. Static, not executed.
- Current `origin/main` is `ffec6ed7aa58` (26 commits past the merge-base; read from the local ref, not fetched by this work). A name-status diff of the merge-base against it shows no added or deleted action files under `templates/*/actions`, `packages/*/src/actions`, `packages/core/src/*/actions`, and no change to `action-discovery.ts`, `framework-tools.ts`, `agent-chat-plugin.ts`, `core/src/mcp`, or `core/src/action.ts`.
- The one registry-adjacent change on `origin/main` is `server/agent-chat/browser-team-tools.ts` (a bounded `waitMs` read of agent-team tasks; no tool added or renamed) plus `agent/production-agent.ts` repeat-guard handling for that wait. Same names, different behavior of an existing tool. **Unverified:** whether main's served map is name-for-name equal to 9f's. That conclusion rests on the diff above, not on an execution.
- "After" is the registry the agent loop receives on each surface: A2A receiver, MCP `ask_app` (default catalog), MCP `ask-agent` (full catalog).

## Two ways the harness runs

- **Ordinary CI (default):** `agent-chat-plugin.delegated-template-inventory.spec.ts` with no environment selects Analytics and proves, on production and dev through the real plugin, that `bigquery`, `search-bigquery-schema` and `query-agent-native-analytics` (`mcpTool:false`) stay registered, in the first request and `availableTools`, callable through tool-search, and dispatched after the delegated filter, over A2A and MCP. It also loads every framework action loader. It writes nothing into the repo.
- **Isolated 17-template audit (manual, produces this report):** `INVENTORY_TEMPLATES=<id>` selects an exact template (unknown or empty names throw) and `INVENTORY_OUT=<file.json>` names where by-name results merge. `.tmp/run-each.sh` runs one template per vitest process with `--maxWorkers=1`, requires exit 0 and exactly 3 passed tests (loader check plus production and dev) for each, and regenerates this file only when all 17 pass. The merged JSON (`.tmp/delegated-template-inventory/inventory.json`, gitignored) holds the full per-run before/after lists.
- **Why one template per process:** a template that imports a package (Dispatch, creative-context) registers that package's actions on a process-wide registry (`action-discovery.ts`, `getPackageActionRegistry`), and every later boot in the same process merges them in. Brain alone has 229 delegated actions; after Analytics and Assets ran first in one process it had 262, the 33 extras being creative-context actions, and templates after Dispatch routed `ask_app` to Dispatch's gateway. Production runs one app per process, so this is a harness limit, not an app defect. The registry is production code and is unchanged; the same sharing probably affects the existing `advertised-catalog.harness.ts`, which loads every template in one process (not verified).
- Each boot's real plugin close hooks run in `afterEach`; a failing hook fails the test. The MCP client and server close per call and the temp cwd is removed in `afterAll`.
- **Coverage limit:** both surfaces boot from an empty temp cwd. A dev server's loose-script tools (a template's own `scripts/` folder, the coding factories) are not in these registries. `agent-chat-plugin.delegated-runtime.spec.ts` covers the real coding factories separately.
- Ownership of an action comes from the entry the app serves, not from the actions folder or the generated registry: a name served as a marked framework twin is the framework's even when a same-named file exists under `templates/<id>/actions`.
